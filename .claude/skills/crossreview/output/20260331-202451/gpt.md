- **Summary**:  
This PR is thoughtful and surprisingly complete for a platform-specific adapter: it has a coherent architecture, good fail-closed sender authorization, useful tests, and a pragmatic split between read-only server-side ingestion and session-context sending. The session-routing reuse from Telegram is a strong design choice. However, there are several **must-fix security and platform-risk issues** before this should ship broadly: most notably **prompt/command injection into the bootstrap shell snippet via unescaped sender**, **unenforced authorization on the reply/logging endpoint**, **privacy leakage through logs and temp files**, and **fragile SQLite polling assumptions on Apple's private Messages DB schema and WAL behavior**. It is close to viable as an experimental/macOS-only feature, but not ready for production without hardening.

## 2. Critical Issues (Must Fix)

### Issue 1: Bootstrap command injection via unescaped `sender`
- **What**:  
  In `wireIMessageRouting.buildBootstrapMessage`, the bootstrap text includes:
  ```ts
  cat <<'EOF' | ${replyScript} "${sender}"
  ```
  `sender` is interpolated directly into shell syntax shown to the agent. If a sender identifier contains `"`, backticks, `$()`, backslashes, or shell metacharacters, the generated command becomes unsafe. While authorized senders are intended to be phone/email identifiers, this is not enforced structurally at the point of use.
- **Why it matters**:  
  This is the most serious issue in the PR. A malicious or malformed sender value could turn the "reply command" into an arbitrary shell payload when the agent follows instructions. This is effectively a command-injection sink.
- **Suggested fix**:  
  Do **not** embed raw sender into shell examples. Use one of:
  1. Strict validation: allow only E.164 phone numbers and a conservative email regex before registration/routing.
  2. Proper shell escaping with a dedicated function.
  3. Better: avoid shell interpolation entirely, e.g. instruct the agent to run:
     ```bash
     .claude/scripts/imessage-reply.sh --recipient-file /path/to/file
     ```
     or pass recipient via environment/file generated by the server.
- **Section reference**:  
  `src/commands/server.ts` -> `buildBootstrapMessage()`

---

### Issue 2: `/imessage/reply/:recipient` lacks recipient authorization enforcement
- **What**:  
  The reply endpoint logs outbound messages and clears stall tracking for **any** `recipient` provided in the URL, as long as the caller has server auth. It does not verify that the recipient is in `authorizedSenders`, nor that it maps to an active/known session.
- **Why it matters**:  
  This creates an integrity and privacy problem:
  - Any authenticated caller can forge outbound iMessage logs for arbitrary recipients.
  - Stall tracking can be cleared for unrelated senders.
  - If the script or API is abused, the system state becomes misleading.
- **Suggested fix**:  
  Require all of:
  1. `ctx.imessage.isAuthorized(recipient)` must be true, or explicitly allow only recipients already present in the registry/log.
  2. Optionally require that `recipient` matches the current session->sender mapping.
  3. Return 403 for unauthorized recipients.
  4. Consider signing script-originated notifications with a local shared secret distinct from the main API bearer token.
- **Section reference**:  
  `src/server/routes.ts` -> `POST /imessage/reply/:recipient`

---

### Issue 3: Sensitive data leakage via logs and temp files
- **What**:  
  The implementation writes:
  - conversation history and latest message into `/tmp/instar-imessage/bootstrap-...txt`
  - long inbound messages into `/tmp/instar-imessage/msg-...txt`
  - outbound/inbound logs into `stateDir/imessage-messages.jsonl`
  - debug logs containing file paths and partial message contents
- **Why it matters**:  
  iMessage content is highly sensitive. `/tmp` is a poor default for durable sensitive content; files may be readable by other local processes/users depending on permissions/umask and operational setup. Logs may retain PII indefinitely. This is a privacy and compliance risk.
- **Suggested fix**:  
  1. Store temp files under `stateDir` or another app-private directory, not `/tmp`.
  2. Create files with mode `0600`.
  3. Add retention/cleanup for bootstrap and long-message files.
  4. Minimize logging of message text and file paths.
  5. Add explicit privacy documentation and configuration for retention.
- **Section reference**:  
  `src/commands/server.ts` -> bootstrap temp file logic  
  `src/core/SessionManager.ts` -> long-message temp file logic  
  `src/messaging/imessage/IMessageAdapter.ts` -> message logging

---

### Issue 4: Session prompt injection risk from raw message content
- **What**:  
  Incoming iMessage text is injected directly into Claude sessions, either inline or via temp file reference. This is by design, but the bootstrap also includes operational instructions ("mandatory", "critical", shell snippet). A malicious user can exploit prompt injection to get the model to ignore relay constraints, exfiltrate context, or run tools unexpectedly.
- **Why it matters**:  
  This is not classic OS command injection, but it is a serious **LLM prompt injection** surface. Since the session appears to have tool access and shell access, this becomes a practical security issue.
- **Suggested fix**:  
  1. Add a stronger system/session boundary for messaging adapters.
  2. Treat inbound text as untrusted content and isolate operational instructions from user content.
  3. Wrap user content in a clearly delimited block and instruct the model that user text may contain adversarial instructions.
  4. Consider a response-review or allowlist gate before any shell/tool execution in iMessage sessions.
- **Section reference**:  
  `src/commands/server.ts` -> bootstrap composition  
  `src/core/SessionManager.ts` -> `injectIMessageMessage()`

---

### Issue 5: Apple platform fragility is under-specified and under-defended
- **What**:  
  The adapter relies on direct reads from `~/Library/Messages/chat.db`, assumes schema stability, assumes WAL-readable access with `query_only`, and assumes the LaunchAgent/session-context split for Automation permission. These are all fragile Apple-internal behaviors.
- **Why it matters**:  
  This feature can silently break on:
  - macOS upgrades
  - Messages schema changes
  - TCC / Full Disk Access changes
  - iCloud sync delays
  - DB locking/WAL behavior changes
  - Apple Intelligence / Messages app architectural changes
- **Suggested fix**:  
  1. Mark feature as **experimental/macOS-version-bounded**.
  2. Add startup compatibility checks against expected schema.
  3. Surface explicit degraded states and diagnostics.
  4. Add a fallback ingestion mode or at least operator guidance.
  5. Document exact TCC/Automation/FDA requirements and support matrix.
- **Section reference**:  
  `src/messaging/imessage/NativeBackend.ts` and overall design comments

---

### Issue 6: Hash-based synthetic topic IDs can collide
- **What**:  
  `injectIMessageMessage()` hashes sender strings into a 32-bit signed integer and uses `Math.abs(hash)` as a synthetic topic ID for pending injection tracking.
- **Why it matters**:  
  Two different senders can collide, causing incorrect stall clearing or cross-session tracking bugs. It may be rare, but it is unnecessary risk.
- **Suggested fix**:  
  Store pending injections keyed by sender string directly, or use a composite structure `{ platform: 'imessage', sender }` instead of forcing into numeric `topicId`.
- **Section reference**:  
  `src/core/SessionManager.ts` -> `injectIMessageMessage()` and `clearIMessageInjectionTracker()`

---

### Issue 7: Polling startup lookback may replay old messages without durable checkpointing
- **What**:  
  On connect, `lastRowId` is initialized to `maxId - 50`. There is no persisted checkpoint across restarts.
- **Why it matters**:  
  This can cause duplicate handling after restart, or message loss if more than 50 rows arrive while the service is down. Dedup by message ID only covers the in-memory process lifetime.
- **Suggested fix**:  
  Persist the last processed `ROWID` or message GUID watermark in `stateDir`, and reconcile carefully on startup.
- **Section reference**:  
  `src/messaging/imessage/NativeBackend.ts` -> `connect()`

## 3. Strengths

### Strong architectural separation
- The split between:
  - **read-only server-side ingestion** from `chat.db`
  - **session-context sending** via `imessage-reply.sh`
  
  is a pragmatic response to macOS Automation/TCC realities. This is one of the best parts of the design.

### Good reuse of existing Telegram session-routing pattern
- `wireIMessageRouting()` mirrors the proven Telegram flow:
  1. inject into alive session
  2. respawn dead session
  3. spawn missing session  
- Reusing an established routing model reduces conceptual complexity and operational surprise.

### Fail-closed inbound authorization
- Requiring `authorizedSenders` and rejecting all messages when empty is correct and security-conscious.
- Normalization to lowercase/trim is sensible.

### Reasonable observability and test coverage
- There is strong route coverage, adapter lifecycle coverage, and session-management E2E coverage.
- The tests demonstrate real thought about "feature alive" checks and prompt readiness behavior.

### Improved session readiness handling
- The move from a narrow prompt check to `detectClaudePrompt()` plus retry/extended wait is a practical reliability improvement.
- Auto-accepting consent dialogs is operationally useful, though it deserves product/security scrutiny.

### Explicit non-support of server-side sending
- `send()` throwing with a clear explanation is good API honesty. It avoids pretending the feature is more portable than it is.

## 4. Gaps & Missing Elements

### Security gaps
- No explicit threat model for:
  - prompt injection from inbound iMessages
  - forged reply notifications
  - local attacker reading temp/log files
  - abuse of authenticated internal endpoints
- No validation spec for sender format beyond lowercasing/trimming.
- No mention of rate limiting on iMessage routes.

### Privacy gaps
- No data retention policy for:
  - `imessage-messages.jsonl`
  - temp bootstrap files
  - long-message files
- No documented handling of attachments beyond metadata mention.
- No user-consent/privacy statement for reading full conversation history from Messages DB.

### SQLite/WAL operational gaps
- No durable checkpointing.
- No strategy for schema migration if Apple changes `chat.db`.
- No handling of backfill windows larger than 50 rows.
- No explicit handling of `guid` uniqueness assumptions across services/chats.

### Apple platform risk gaps
- No support matrix by macOS version.
- No startup self-test for:
  - Full Disk Access
  - Messages DB readability
  - expected schema/tables/columns
  - `imsg` CLI availability from session context
- No rollback/disable plan if Apple changes behavior after an OS update.

### Failure mode gaps
- What happens if:
  - session sends iMessage successfully but callback POST fails?  
    Current behavior warns, but no reconciliation mechanism exists.
  - callback POST succeeds but `imsg send` failed?  
    Script avoids this, which is good, but no idempotency key exists.
  - multiple messages arrive during spawn?  
    Current `spawningSenders` set causes later messages to be skipped, not queued.
  - group chats are involved?  
    The model assumes sender maps cleanly to a single conversational identity.
  - attachments arrive?  
    Adapter mentions attachments metadata, but routing and context behavior are undefined.

### Missing product/ops sections
- Rollout plan
- Kill switch / feature flag behavior beyond config
- Operator runbook for TCC/FDA issues
- Monitoring/alerts for polling health, row lag, duplicate rate, dropped messages

## 5. Industry Comparison

### Compared to existing solutions
This resembles the common "consumer messaging bridge" pattern used by hobbyist and prosumer automation tools:
- read from a local client datastore
- send through UI automation / AppleScript / third-party CLI
- keep business logic outside the platform-specific edge

That is pragmatic, but it is **less robust** than official APIs or cloud-managed messaging providers.

### Compared to industry best practices
**Aligned with best practices:**
- fail-closed authorization
- explicit unsupported operations
- adapter abstraction
- route-level capability exposure
- test coverage across unit/integration/E2E

**Not aligned with best practices:**
- storing sensitive message content in `/tmp`
- using private Apple DB schema as a production interface
- lack of durable cursor/checkpointing for polling
- embedding unescaped user identifiers into shell command examples
- weak endpoint integrity model for reply callbacks

### Known patterns and anti-patterns
**Good patterns:**
- "ingest read-only, send from privileged edge context"
- "reuse existing session routing pattern"
- "degrade gracefully when adapter init fails"

**Anti-patterns present:**
- polling private SQLite DB without robust checkpointing
- command construction with raw user-derived strings
- in-memory dedup only
- dropping messages during spawn instead of queueing
- overloading numeric topic tracking with hashes

## 6. Scalability Assessment

### Phase 1 (MVP, 10-50 users): Will it work?
- **Yes, probably**, if "users" really means a small number of trusted senders on a single macOS host.
- Main risks at this scale are not throughput; they are:
  - platform brittleness
  - privacy leakage
  - duplicate/missed messages on restart
  - prompt/command injection

### Phase 2 (Growth, 50-500 users): What breaks?
- The architecture starts to strain:
  - 2s polling over `chat.db` becomes noisier and more failure-prone.
  - Session-per-sender mapping may create too many long-lived tmux sessions.
  - Logs and temp files grow quickly.
  - No queueing during spawn means message loss/skips become visible.
  - Manual authorized sender management becomes cumbersome.
- Operationally, one consumer macOS host is not a scalable messaging backend.

### Phase 3 (Scale, 500-5000 users): Architecture changes needed?
- **This design is not suitable** for that scale.
- Required changes would include:
  - event-driven ingestion or a supported API (if available)
  - durable message queue
  - persisted offsets/checkpoints
  - worker pool instead of one persistent session per sender
  - stronger authn/authz and audit model
  - explicit privacy/compliance controls
- At this point, the whole "native macOS Messages bridge" would likely need to become a niche edge connector, not the primary architecture.

### Spike handling: What happens under sudden load?
- Sudden bursts will likely cause:
  - skipped messages while `spawningSenders` is set
  - delayed session startup
  - increased tmux/session churn
  - possible duplicate replay after restart
  - more DB lock contention or stale reads
- There is no queue, no backpressure strategy, and no batching.

## 7. Recommendations (Prioritized)

1. **Eliminate command-injection risk in bootstrap/reply instructions**  
   Remove raw `sender` interpolation from shell snippets. Enforce strict sender validation and/or pass recipient via file/env/opaque token rather than direct shell argument embedding.

2. **Harden the reply callback endpoint**  
   Require recipient authorization and session/registry correlation on `POST /imessage/reply/:recipient`. Consider a separate local callback secret or signed nonce so the endpoint cannot be abused merely with the main bearer token.

3. **Fix privacy handling for temp files and logs**  
   Stop writing sensitive content to `/tmp`; move to app-private storage with `0600` permissions, retention limits, and cleanup. Minimize message text in logs and document retention.

4. **Add durable polling state and message queueing**  
   Persist last processed DB cursor/message GUIDs across restarts, and queue inbound messages per sender during spawn instead of dropping/skipping them.

5. **Explicitly scope and gate Apple platform risk**  
   Mark feature experimental, add startup compatibility checks (FDA/TCC/schema), publish a support matrix, and add operator diagnostics/kill switch behavior for macOS or Messages DB breakage.
