### 4. Gaps & Missing Elements
- **Missing edge cases**:
  - Network partition during tmux capture: `captureSessionOutput` failure (e.g., tmux unresponsive) lacks retry/backoff; could loop on stale snapshots.
  - Commitment with `cadenceMs < 60s` clamped but no user warning on declaration (e.g., skill proposes 30s, server clamps silently).
  - Multi-topic commitments: Spec assumes one `topicId`; what if agent declares "working on topic A and B"?
- **Unaddressed failure modes**:
  - LLM provider outage > cadenceMs: Fail-open to templated is good, but no circuit-breaker (e.g., degrade all beacons for 1h if 3 consecutive 5xx).
  - `deliveryMessageId` verification fails (e.g., message deleted post-reference): Spec says transition to `verified` only if exists/non-proxy; unclear if partial failure (e.g., proxy message) retries or notifies.
  - Boot-time reconciliation races: If `commitmentTracker.isReady()` false during PromiseBeacon boot, no backoff/retry specified.
- **Implicit assumptions needing explicitness**:
  - `sessionEpoch` relies on `claudeCodeSessionUuid` from metadata file; assumes file always present/accurate (add "if absent, treat as mismatch").
  - `globalMaxOpen: 20` hardcoded in config example but not justified (e.g., timer slot exhaustion math).
  - Prompts: Tier selection logic references prompts but no examples (e.g., Tier-1 Haiku prompt for `NO_OBSERVABLE_PROGRESS`).
- **Missing sections**:
  - **Migration plan**: Schema v2 bump good, but no "pre-flight check" script for existing deployments (e.g., validate all pending commitments have `ownerMachineId`).
  - **Prompt engineering**: Inline Tier-1/2/3 prompt skeletons.
  - **Metrics**: No Prometheus/Grafana export (e.g., `heartbeat_fired_total{ tier, topic }`, `llm_spend_cents_total`).
  - **Accessibility**: `⏳` prefix assumes emoji support; fallback text for plain-text clients.

### 6. Scalability Assessment
- **Phase 1 (MVP, 10-50 users)**: Fully works – in-memory timers/mutexes handle 20 open × 10min cadence (~2/min peak); `LlmQueue` caps spend; jitter prevents thundering herd.
- **Phase 2 (Growth, 50-500 users)**: Breaks at ~200 open commitments (timer exhaustion if Node event loop starves; `globalMaxOpen=20` per-machine mitigator). Multi-machine without Phase 3 leases duplicates heartbeats. LlmQueue daily cap hit → all templated (acceptable degradation).
- **Phase 3 (Scale, 500-5000 users)**: Needs Redis-backed `LlmQueue` + distributed locks (file-lease → etcd/Redis TTL); migrate cold storage to DB (e.g., SQLite → Postgres); sharded hot files by `userId`. Bus events → Kafka for fanout.
- **Spike handling**: User flood → `globalMaxOpen` + `mutate()` bounded queue (256 depth) reject excess (503); PresenceProxy lane reservation (40%) prevents starvation. Snapshot-hash + metadata skip amortizes to O(1) per tick.
