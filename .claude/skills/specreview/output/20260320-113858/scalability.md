# Scalability Review: Dashboard Observability — Jobs, Health, and Agent Insights\n\n**Review ID:** 20260320-113858\n**Round:** 1\n**Reviewer Role:** Scalability and Infrastructure Specialist\n**Spec:** `specs/dashboard-observability.md`\n**Date:** 2026-03-20\n\n---\n\n## Approval Status: CONDITIONAL\n\nThe spec is sound for its immediate context (single-agent, single-machine, personal use) but contains two time-bombs that will cause real pain within months: an unbounded JSONL ledger with no retention policy, and a monolithic 156KB HTML file that will become a maintenance and load-time liability. Neither is a blocker today, but both need a plan now — retrofitting retention on a production ledger is harder than building it right the first time. All other concerns are low-risk at the current scale.\n\n---\n\n## Research Findings\n\n### Polling vs WebSocket Scaling\n\nFor dashboards updating every 30 seconds, polling and SSE are both appropriate and simpler to operate at scale than WebSockets. The critical finding for this spec: **WebSockets create horizontal scaling complications** — when you add servers, existing clients stay pinned to original servers and equilibrium recovery time is theoretically unbounded. For a 30-second health poll, HTTP polling or SSE is the better long-term choice. The spec already uses both (polling for health/jobs, WebSocket for session output), which is reasonable, but the suggested extension of job events onto the existing WebSocket should be weighed against SSE as a simpler alternative.\n\n### Job History Storage at Scale\n\nSQL Server Agent data (a direct analogue) shows measurable startup degradation at 100,000+ history rows, with documented 45-60 second slowdowns. Best practice across job orchestration systems (Airflow, Kubernetes CronJobs, GitHub Actions) is **per-job capped retention** (e.g., keep last 100 runs per job) plus optional time-based cutoff (e.g., 90 days). The instar ledger currently has 1,229 records at ~320 bytes/record = 385KB after approximately 1 day of operation. Growth rate projection: ~60MB/month, ~440MB at 12 months, ~880MB at 24 months — all from a single agent running 23 jobs. This is the highest-probability pain point in the spec.\n\n### JSONL at Scale\n\nJSONL's append-only model is excellent for writes, but history queries require full-file sequential scans when filtering by slug. At current growth rates, a `GET /jobs/history?slug=health-check&limit=50` query requires scanning the entire file, which means: 37ms at 1 month, 220ms at 6 months, 440ms at 12 months. These are synchronous I/O operations in a Node.js event loop — at 6+ months they become user-noticeable. The fix is indexing, not format change.\n\n### Vanilla JS DOM Performance\n\nVanilla JS has no framework overhead and performs excellently for dashboards of this size. The concern is not framework overhead but **render frequency and DOM mutation patterns**. Updating 23 job rows every 30 seconds via innerHTML replacement is fine. The risk is if polling intervals tighten or if the Reports view streams large volumes of text into the DOM — these can cause jank on low-power devices (phones, older iPads). The spec's own \"data density over decoration\" principle and lazy-loading approach directly mitigate this.\n\n---\n\n## Phase Assessment\n\n| Phase | Users/Agents | Data Volume | Key Bottleneck |\n|-------|-------------|-------------|----------------|\n| MVP | 1 agent, 1 user | ~60MB/month ledger | None — everything fits comfortably |\n| Growth | 1-5 agents, 2-3 users | ~300MB/month ledger | JSONL slug-filter scan time starts degrading (200ms+) |\n| Scale | 5-20 agents, 5-10 users | 1-3GB/month ledger | Ledger scan becomes blocking; monolithic HTML hits 300KB+ |\n| Viral | 20+ agents, shared infra | Multi-GB | JSONL is no longer viable without indexing; single-file dashboard unmanageable |\n\n**Context note:** This is a personal agent platform. \"Viral\" means Justin runs 20+ agents or instar becomes a multi-tenant product. The MVP and Growth phases are the practical near-term concern. The Scale/Viral phases are directional warnings, not imminent risks.\n\n---\n\n## Critical Issues\n\n### ISSUE 1 — Unbounded JSONL Ledger (hits at ~3-6 months)\n\n**Severity: High**\n**When it bites:** ~3 months for noticeable query slowdown; ~12 months for storage annoyance\n\nThe spec explicitly flags this in Open Questions but does not require a resolution. The ledger is currently growing at ~2MB/day (1,229 records, 385KB in ~1 day of operation). Projections:\n\n- 3 months: ~180MB, slug-filter scan ~100ms\n- 6 months: ~360MB, slug-filter scan ~220ms\n- 12 months: ~720MB, slug-filter scan ~440ms\n- 24 months: ~1.4GB, slug-filter scan ~880ms\n\nThe 30-second dashboard poll hits `GET /jobs/history` lazily (on job selection), but `/jobs` itself must read and aggregate state from this ledger on every poll. If the server is doing full-file reads on each `/jobs` request, this degrades linearly with ledger size.\n\n**The fix is simple and should be decided now:** Cap retention at 500 runs per job (configurable), with a nightly trim job. This bounds the ledger at ~3.5MB permanently for 23 jobs × 500 runs × 320 bytes. The spec mentions this as an open question — it should be a pre-condition for building the Reports view, not an afterthought.\n\n### ISSUE 2 — Monolithic Dashboard File Growth (hits at ~156KB, worsens over time)\n\n**Severity: Medium**\n**When it bites:** Already 103KB; spec additions bring it to ~156KB; Phase 3 additions push toward 200KB+\n\nThe spec estimates +53KB for Phase 1-2 additions. Phase 3 (Health, Evolution, Autonomy tabs) will add another 40-80KB. At 200KB+ of vanilla JS, HTML, and CSS in a single file:\n\n- Initial parse time on mobile increases from ~40ms to ~80ms+ (rough estimate for mid-range Android)\n- Debugging and maintaining the file becomes genuinely difficult (3,512 lines currently; projected 5,500+ lines after Phase 3)\n- The `switchTab()` pattern renders all tab content simultaneously — all 23 job rows, all history entries, all panels — even on inactive tabs\n\nThis is not a blocking scalability issue at MVP but is a code quality and UX issue. Tab content should be rendered on-demand rather than hidden with CSS. The lazy-loading principle stated in UX Principles #3 should be applied to tabs themselves, not just history rows.\n\n---\n\n## Recommendations\n\n### Mandatory (pre-build or concurrent)\n\n**R1. Define retention policy now, not after Reports view is built.**\nSettle the open question in section 5. Recommended: keep last 500 runs per job, prune nightly via a trim job. Add `maxHistoryPerJob: 500` to `jobs.json` config and a `trim-job-history` job to the scheduler. This bounds storage permanently and keeps all query times under 5ms.\n\n**R2. Add a slug index to the job history ledger.**\nWhether retention is added or not, the server-side `GET /jobs/history?slug=` implementation should maintain an in-memory index (slug → [line offsets] or slug → [runIds]) populated at server startup and updated on each append. This reduces slug-filter queries from O(n) file scan to O(1) lookup + targeted reads. At current ledger size this is premature optimization; at 6 months without retention it is necessary.\n\n**R3. Render job tab content on demand, not on page load.**\nWhen `switchTab('jobs')` fires, fetch and render job data. When the user navigates away, the DOM can be cleared or preserved with a staleness flag. This prevents loading 23 job rows + their DOM nodes on every page open regardless of whether the user visits the Jobs tab.\n\n### Recommended (good practice, low effort)\n\n**R4. Use SSE instead of extending the existing WebSocket for job events.**\nIf Open Question 2 (real-time job events) is answered \"yes,\" use a new SSE endpoint (`GET /jobs/events`) rather than multiplexing job events onto the existing session WebSocket. SSE is unidirectional (matches the use case), requires no protocol changes, and avoids coupling session-output latency requirements with job-event latency requirements.\n\n**R5. Paginate `/jobs/history` server-side from day one.**\nThe spec requests `limit=50` on the history endpoint. Ensure the server implements this as a true server-side limit (not fetch-all-then-slice). Without actual pagination, adding the `?slug=` filter without server-side limit enforcement means the server scans the full ledger and returns up to 50 records from potentially thousands.\n\n**R6. Set a `Cache-Control` header on `/jobs` responses.**\nThe 30-second poll is well-chosen and matches the server's own health check interval. Returning `Cache-Control: max-age=25, stale-while-revalidate=5` allows the browser to serve cached data immediately on tab switch while still triggering background refresh. This eliminates the perception of latency on tab re-entry.\n\n### Stretch (worth noting for Phase 3+)\n\n**R7. Consider tab grouping before adding Phase 3 tabs.**\nThe spec raises this in Open Question 3. At 7 tabs (Sessions, Files, Drop Zone, Jobs, Health, Evolution, Autonomy), the tab bar overflows on 320px screens. A \"System\" group dropdown containing Jobs, Health, Evolution, and Autonomy is the right call before Phase 3 ships. This is a UX scalability issue, not a data scalability issue.\n\n**R8. Plan for multi-agent dashboard at the data model level.**\nThe job history records already include `machineId`. If Justin runs multiple agents and wants a unified dashboard, the current per-agent architecture will require either a federation layer or a combined view. The `machineId` field is good forward-thinking — ensure the dashboard filters/displays it when multiple values are present in the ledger.\n\n---\n\n## Observations\n\n**What the spec gets right from a scalability standpoint:**\n\n- 30-second poll interval is well-calibrated — not so frequent that it creates server load, not so slow that it feels stale\n- Lazy loading of job history (on selection, not on tab open) is exactly correct\n- No external dependencies keeps the deployment footprint zero — no CDN dependency failures, no versioning drift\n- The `/health` endpoint being auth-free is sensible — vital signs should never be gated behind a PIN timeout\n- The spec acknowledges that job output persistence is unresolved. At 156KB with Phase 1-2, it remains manageable. At 200KB+ with Phase 3, the developer experience degrades meaningfully — `Ctrl+F` to find a function in a 6,000-line file is not the same as navigating a module. This is not a user-facing scalability issue but a maintainability cliff. If the dashboard is going to become a serious operational tool (and this spec says it should), a build step and module splitting will eventually be worth the overhead.\n\n**The real bottleneck today is sessions, not the dashboard:**\n\nThe spec's motivating example — health-check hitting 8 consecutive spawn-errors because sessions are maxed at 3/3 — is a compute scheduling problem, not a dashboard problem. The dashboard makes this visible, which is valuable, but the root cause (session saturation blocking health monitoring) needs to be addressed in the scheduler, not the UI. This is out of scope for the spec but worth flagging: a dashboard that shows \"8 failures\" without the ability to take action (kill a session, raise the max) is observation without control. The \"Run Now\" and \"Enable/Disable\" buttons are steps in the right direction.\n\n---\n\n## Scalability Assessment\n\n### Database & Storage\n\n- **Job ledger (JSONL):** Growing at ~2MB/day, ~60MB/month. Low risk, easy win.\n\n### Compute\n\n- **Expensive operations:** \"Run Now\" → `POST /jobs/:slug/run` spawns a Claude session. This is the most expensive action in the entire UI — a session spawn with LLM inference. No throttling or rate limiting is mentioned. No N+1 query risk in the job list view.\n- **History pagination:** As noted, must be true server-side pagination, not client-side slicing of a full scan.\n- **Attention queue:** Small, bounded by human consumption rate.
