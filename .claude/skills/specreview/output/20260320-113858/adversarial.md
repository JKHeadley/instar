# Adversarial Review: Dashboard Observability — Jobs, Health, and Agent Insights\n\n**Review ID:** 20260320-113858\n**Round:** 1\n**Spec:** dashboard-observability.md\n**Reviewer:** Red Team Specialist\n**Date:** 2026-03-20\n\n---\n\n## Approval Status: CONDITIONAL\n\nThis spec exposes genuinely sensitive agent infrastructure through a UI that already has known architectural weaknesses. The core authentication model (PIN → bearer token, localStorage storage) combined with the new attack surface (job trigger endpoint, operation log, evolution proposals, trust controls, attention queue) creates a risk profile materially higher than the existing dashboard. Several issues require mitigation before implementation, but none are fundamental blockers if addressed.\n\n---\n\n## Research Findings\n\n### Unauthenticated Health Endpoints as Reconnaissance Entry Points\n\nResearch confirms this is a well-documented real-world attack pattern. The `/health` endpoint — explicitly called out in the spec as **not requiring auth** — is the canonical reconnaissance gift. A 2026 Medium writeup (\"The TMI Endpoint\") documents exactly how unauthenticated health checks expose OS version, Python version, CPU count, total memory, disk usage, and full filesystem paths. Each datum narrows attacker effort dramatically: disk paths reveal deployment layout, version strings enable targeted CVE lookup, session counts reveal load patterns.\n\nThe spec's `/health` response already includes: `status`, `uptime`, `sessions (current/max)`, `memory`, `disk`, `job failures`, and `system review`. This is a detailed operational fingerprint served to anyone who can reach the port.\n\n### SSRF via Dashboard-Proxied Requests\n\nSSRF featured in OWASP Top 10 2025. When a monitoring dashboard fetches data from internal APIs and renders it, any user-controlled URL parameter becomes a potential SSRF vector. The spec's \"Reports sub-view\" fetches session output via `GET /sessions/:name/output` where `:name` comes from job history data. If job names or session names can be influenced, this path becomes a redirect target.\n\n### Job Trigger API Abuse (IDOR + CSRF)\n\nOWASP BOLA (Broken Object Level Authorization) is the #1 API risk. The new `POST /jobs/:slug/run` endpoint accepts a job slug from the client and executes the corresponding job. This is a textbook IDOR setup. If the auth token is not validated server-side for every execution, any bearer token holder can trigger any job. CSRF is also relevant: the spec uses a bearer token (presumably stored in localStorage or a JS variable), making it vulnerable to XSS-escalated CSRF.\n\n### Real-World Monitoring Dashboard Compromises\n\nGrafana's 2025 GitHub Action incident (post-incident review published May 2025) demonstrated how monitoring infrastructure is high-value: attackers targeted Grafana specifically because of its access to observability data across customer environments. The attack vector was a misconfigured CI workflow, not the UI itself — but the lesson is that dashboards with \"run now\" and \"configure\" capabilities represent remote code execution primitives in disguise.\n\nThe CVE-2026-23660 (Windows Admin Center) pattern is directly analogous: a `/api/health` endpoint was used for initial reconnaissance before privilege escalation.\n\n---\n\n## Critical Issues\n\n### CRIT-1: Unauthenticated `/health` Exposes Operational Fingerprint\n\n**Likelihood: High | Impact: High | Priority: P0**\n\nThe spec explicitly states: \"All endpoints require `Authorization: Bearer <token>` (except `/health`).\" The vital signs strip polls `/health` every 30 seconds. The health response contains: server status, uptime, current/max sessions, memory pressure, disk percentage, job failure count, and system review summary.\n\n**The attack:** Any attacker who can reach the instar server port (LAN, exposed tunnel, or Cloudflare quick-tunnel URL shared incautiously) gets a real-time operational inventory without credentials. Disk at 97% telegraphs a near-full filesystem. Session saturation (3/3) signals the agent is under load and spawning windows are available for timing attacks. Job failure counts reveal what subsystems are broken.\n\n**Compounding factor:** The spec mentions Cloudflare tunnel integration. Quick tunnels generate public URLs on `*.trycloudflare.com`. If a tunnel is active, `/health` is internet-accessible to anyone who knows or guesses the URL. Cloudflare quick-tunnel URLs are not secret — they appear in logs, are sometimes cached, and can be enumerated through subdomain bruteforcing.\n\n**Defense:**\n- Require auth on `/health` for the detailed response. Provide an unauthenticated `/ping` that returns only `{\"status\":\"ok\"}`.\n- Or: serve a sanitized `/health` (no disk paths, no session counts, no failure details) to unauthenticated callers and the full response to authenticated ones.\n- Rate-limit the public endpoint to frustrate automated polling.\n\n---\n\n### CRIT-2: `POST /jobs/:slug/run` — Arbitrary Job Execution via Token Theft or XSS\n\n**Likelihood: Medium | Impact: Critical | Priority: P0**\n\nThe new \"Run Now\" button calls `POST /jobs/:slug/run`. This endpoint, once implemented, is a remote code execution primitive: jobs run arbitrary Claude sessions with configurable prompts and tool access. If an attacker obtains the bearer token (via XSS in the dashboard, token leakage in logs, shoulder surfing the PIN, or network interception on HTTP), they can trigger any of the 23 jobs on demand.\n\n**Escalation path:** Some jobs likely have write access to the filesystem, git, or external APIs (the spec mentions evolution proposals, trust changes, and operation gate decisions). Triggering jobs out-of-sequence or repeatedly could:\n- Exhaust session capacity (denial of service via session saturation — already a demonstrated failure mode)\n- Cause unintended state mutations (evolution proposals approved, trust levels modified)\n- Generate excessive Claude API spend (quota exhaustion attack)\n\n**The CSRF angle:** If the token is stored in a JS variable or localStorage and the dashboard doesn't enforce CSRF tokens, a malicious page open in another browser tab can POST to `localhost:4042/jobs/:slug/run` using `fetch()` with credentials. SameSite cookie protections don't apply to bearer tokens in Authorization headers sent by JS.\n\n**Defense:**\n- Require explicit CSRF token (separate from the bearer token) for all state-mutating endpoints.\n- Add a server-side rate limit per token on `/jobs/:slug/run` (e.g., max 1 run per job per 60 seconds).\n- Log all \"Run Now\" invocations with timestamp and source IP.\n- Consider requiring a second confirmation for critical-priority jobs (the spec already proposes this for disable — extend to run).\n\n---\n\n### CRIT-3: `PATCH /jobs/:slug` Enable/Disable — Silent Infrastructure Sabotage\n\n**Likelihood: Medium | Impact: High | Priority: P1**\n\nThe spec adds `PATCH /jobs/:slug` to enable or disable any job. An attacker with a valid token can disable the `health-check` job (priority: critical) silently. The dashboard shows the job as dimmed/disabled — but only if someone is watching. If no one checks the dashboard, health monitoring ceases and the agent degrades without notification.\n\n**Chained attack:** Disable health-check → trigger resource exhaustion → wait for agent to become unresponsive → the very monitoring that would catch this is now off.\n\n**Defense:**\n- Require a second factor (e.g., PIN re-entry) to disable critical-priority jobs, not just a confirmation prompt (which can be bypassed by replaying the API call directly).\n- Emit an attention queue item whenever a critical job is disabled.\n- Log disable actions with source IP and timestamp separately from normal operation logs.\n\n---\n\n### CRIT-4: Evolution Proposals — Approve/Reject as Agent Behavioral Manipulation\n\n**Likelihood: Low | Impact: Critical | Priority: P1**\n\nPhase 3 includes an Evolution Tab with \"Approve/Reject actions for pending proposals.\" Evolution proposals presumably modify agent behavior, CLAUDE.md, job configurations, or system prompts. An attacker who compromises the dashboard token can approve malicious evolution proposals or reject legitimate ones.\n\n**The threat model:** This isn't a traditional security concern — it's a behavioral integrity concern. If an attacker (or even a confused legitimate user) approves a proposal that modifies how the agent handles trust, autonomy, or external operations, the damage may not be visible until much later. There's no audit trail proposed in the spec.\n\n**Defense:**\n- Approving/rejecting evolution proposals must require PIN re-entry, not just a valid session token.\n- All approve/reject actions must be logged in `.instar/security.jsonl` with full proposal text, actor, and timestamp.\n- Consider a \"review window\" — proposals approved via dashboard don't take effect for N minutes, giving time to notice and revert.\n\n---\n\n### CRIT-5: Operation Log Exposure — Revealing Blocked Operations to Attacker\n\n**Likelihood: Medium | Impact: Medium | Priority: P1**\n\nThe Autonomy & Trust tab shows `GET /operations/log` — \"Recent operations evaluated by the gate. Decision for each: allowed, blocked, plan-required. Filterable by service, decision, time range.\"\n\n**The attack:** An attacker with a valid token reads the operation log to learn exactly which operations are blocked and why. This is the gate's rulebook in plaintext. They now know: which services are monitored, what operation types trigger plan-required decisions, what trust levels each service has, and what strings/patterns are being matched. This enables targeted evasion: craft a future attack to look like an \"allowed\" operation.\n\n**Compounding factor:** The log also reveals what the agent has been doing — external service names, operation patterns, timing. This is a full behavioral map of the agent's external interactions.\n\n**Defense:**\n- The operation log should be behind an elevated-access control (admin tier vs. read-only tier), not the same token that grants dashboard read access.\n- Sanitize logged operation details before display — show decision and category, not the full operation parameters that would reveal matching logic.\n\n---\n\n## Recommendations\n\n### REC-1: Tiered Authentication\n\nThe current model is binary: unauthenticated or fully authenticated. The spec adds actions of wildly different risk levels (view job list vs. trigger a job vs. approve an evolution proposal). Implement two tiers:\n- **Read tier** (current token): view all dashboards, job history, health data, operation logs (sanitized)\n- **Action tier** (PIN re-entry or separate elevated token): Run Now, Enable/Disable, Approve/Reject evolution proposals, modify trust levels\n\nThis limits blast radius from token theft: stolen tokens give observability but not control.\n\n### REC-2: Authenticate `/health` or Sanitize It\n\nThe unauthenticated health endpoint is the most immediate and easiest fix. Either:\n- Require auth (breaking change for any health monitoring that hits this endpoint without auth)\n- Or return a minimal public response: `{\"status\": \"ok\", \"uptime\": <seconds>}` and gate all operational details behind auth\n\nThe vital signs strip will still work — it just needs the token (which it already has post-login).\n\n### REC-3: CSRF Protection on All Mutating Endpoints\n\nAdd a `X-Instar-Request: 1` header requirement on all state-mutating endpoints. The dashboard JS sends this header; fetch() from cross-origin pages cannot set custom headers without CORS preflight (which the server should deny for non-dashboard origins). This is already present in some existing instar calls (seen in CLAUDE.md examples) — make it mandatory and enforced server-side.\n\n### REC-4: Immutable Audit Log\n\nAll dashboard-initiated actions (Run Now, Enable/Disable, Approve/Reject, Acknowledge/Dismiss attention items) must be written to an append-only log. This enables post-incident forensics. The log should be separate from the normal operation log and not deletable through any dashboard action.\n\n### REC-5: Rate Limiting on Job Execution\n\n`POST /jobs/:slug/run` must be rate-limited per job slug: at most once per schedule interval (e.g., a job that runs every 5 minutes cannot be manually triggered more than once per 5 minutes). This prevents the quota exhaustion and session saturation attacks described in CRIT-2.\n\n### REC-6: Content Security Policy\n\nThe monolithic `index.html` dashboard should include a strict Content Security Policy header. XSS in the dashboard is the most practical path to token theft. A CSP that blocks inline scripts and restricts `connect-src` to `localhost:4042` would materially reduce XSS exploitability. This doesn't prevent XSS but eliminates most exfiltration paths.\n\n### REC-7: Tunnel URL Hygiene\n\nWhen a Cloudflare tunnel is active, display a clear warning in the dashboard that the server is internet-accessible. Remind the user to not share the tunnel URL. Consider adding a `tunnel-exposed` indicator to the vital signs strip (already proposed) that turns red when a tunnel is active, to prevent forgetting about exposure.\n\n---\n\n## Observations (Lower Priority)\n\n### OBS-1: Job Slug Enumeration via History Endpoint\n\n`GET /jobs/history?slug=<slug>` enables slug enumeration: an attacker can probe for job slugs to map the agent's job inventory before having access to `GET /jobs`. Low impact since `GET /jobs` is also auth-gated, but defense-in-depth suggests the history endpoint should 404 (not 200 empty) for unknown slugs.\n\n### OBS-2: Handoff Notes Injection\n\nPhase 2 displays handoff notes inline in the Reports view. Handoff notes are presumably written by the agent itself during job runs. If a job's output or handoff note contains HTML/JS (e.g., from external data ingested during a job), and the dashboard renders it without sanitization, this is a stored XSS vector. The spec uses vanilla JS — verify that all user-generated content is escaped via `textContent`, not `innerHTML`.\n\n### OBS-3: Attention Queue Dismiss Without Confirmation\n\n`DELETE /attention/:id` permanently removes an attention item. If an attacker can dismiss attention items (e.g., the `ci-release-token-missing` HIGH priority item shown in the spec), they can bury alerts that require action. The spec doesn't propose any confirmation or rate limit on dismissal. A soft-delete (mark as dismissed, keep in log) would be safer than hard delete.\n\n### OBS-4: Session Output Retrieval in Reports View\n\nPhase 2 fetches session output via `GET /sessions/:name/output`. Session names appear to come from job history records (server-generated). However, if session naming can be influenced by job parameters or external data, this becomes a path traversal risk depending on how the server resolves session names to file paths.\n\n### OBS-5: Unbounded Job History Ledger\n\nThe spec notes: \"Currently the ledger grows unbounded.\" This is a disk exhaustion vector. On a system already at 97% disk (mentioned in the spec itself), a high-frequency job that logs verbose output will fill the disk. The spec asks this as an open question — it should be answered before the Reports view is built, because the Reports view incentivizes retaining more history.\n\n### OBS-6: Mobile Responsive PIN Exposure\n\nThe spec notes mobile responsiveness at 768px. PIN entry on a mobile device in a public location is shoulder-surfing vulnerable, especially since the dashboard is likely used ad-hoc on a phone. This is a social engineering vector more than a technical one, but worth noting.\n\n### OBS-7: Tab Overflow Reveals Feature Inventory\n\nAdding 4-6 tabs (Jobs, Health, Evolution, Autonomy) publicly reveals the agent's capability inventory to anyone who gets a brief look at the browser. This is a minor social engineering/reconnaissance concern — an observer learns what systems are in play before the dashboard locks.\n\n### OBS-8: WebSocket Event Injection\n\nThe spec proposes adding job events (`job_started`, `job_completed`, `job_failed`) to the existing WebSocket. If the WebSocket authentication is weaker than the REST auth (e.g., doesn't re-verify the token on each message), a compromised WebSocket connection could inject fake job completion events, causing the UI to display incorrect state.\n\n---\n\n## Scalability Assessment\n\n**Attack surface grows non-linearly with phase count:**\n\n- **Phase 1** (vital signs + jobs tab): Relatively contained. New attack surface is `POST /jobs/:slug/run` and `PATCH /jobs/:slug`. Primary risk is job execution abuse and the health endpoint.\n- **Phase 2** (reports + attention queue): Adds stored XSS surface via handoff notes and session output rendering. Adds soft-targets in the attention queue (dismiss suppresses alerts).\n- **Phase 3** (health, evolution, autonomy tabs): This is where risk compounds sharply. Evolution proposal approval and trust level modification are agent behavioral controls — compromising these at scale means an attacker can systematically alter agent decision-making. If multiple agents run this dashboard pattern (multi-agent Threadline network), a single compromised dashboard token cascades into cross-agent behavioral manipulation.\n\n**At scale (multi-agent / multi-user):**\n- The current single-token model doesn't support multi-user access. If the dashboard is shared (e.g., multiple team members access the same instar instance), there's no per-user accountability — all actions appear as the same principal.\n- The attention queue as designed holds operational security items. At scale, an adversary targeting this platform would specifically target the attention queue to understand what the operator knows and suppress alerts.\n- Cloudflare tunnel + internet-accessible `/health` is a meaningful reconnaissance surface. Automated scanning would detect instar instances and build a catalog of their capabilities based on the health payload.\n\n---\n\n## Score: 5.5 / 10\n\n**Justification:** The spec solves a real operational problem well and the design is thoughtful. The UX decisions (lazy loading, existing component reuse, no external dependencies) are sound. However, the authentication architecture is insufficient for the privilege level of the new controls being exposed. The unauthenticated `/health` endpoint is a pre-existing liability that this spec amplifies by making it the backbone of the vital signs strip — now it's polled every 30 seconds by every dashboard user, and its exposure is explicitly documented. The `POST /jobs/:slug/run` endpoint, if implemented naively, is a remote code execution primitive behind a single bearer token. Phase 3's evolution and trust controls are agent behavioral modification surfaces that require stronger access controls than anything currently in the system.\n\nThe score reflects: good intent and strong UX thinking offset by authentication design that hasn't scaled with the sensitivity of the new capabilities. Address CRIT-1 through CRIT-3 at minimum before Phase 1 ships.
