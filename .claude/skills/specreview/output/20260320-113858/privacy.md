# Privacy & Ethics Review — Dashboard Observability Spec\n\n**Review ID:** 20260320-113858\n**Spec:** Dashboard Observability — Jobs, Health, and Agent Insights\n**Reviewer:** Privacy & Ethics Specialist\n**Date:** 2026-03-20\n**Round:** 1\n\n---\n\n## Approval Status: CONDITIONAL\n\nThe spec describes a well-intentioned operational dashboard for a single-user, self-hosted AI agent system. The core privacy posture is acceptable for its intended scope, but several issues require resolution before implementation — particularly around error message data leakage, unbounded data retention, the unauthenticated `/health` endpoint, and the absence of any explicit access control model. These are not blocking in the ethical sense, but they are concrete risks that are cheap to address now and expensive to address after the dashboard is in broad use.\n\n---\n\n## Research Findings\n\nIndependent research conducted prior to this review surfaced several relevant findings:\n\n**On operational dashboards and data exposure:** Operational dashboards concentrate sensitive signals in a single surface. Error messages in dashboards are a documented information leakage vector — stack traces, file paths, session identifiers, and internal error codes reveal system architecture to anyone with dashboard access. Best practice is to log full error details server-side and surface only generic status messages in UI. (Source: CQR Web Vulnerabilities; IBM Data Leakage)\n\n**On AI agent monitoring and inherited permissions:** AI agents that aggregate data from multiple subsystems create a \"concentration target\" — the dashboard becomes more valuable to an attacker than any single underlying API because it aggregates across all of them. Inherited permissions mean that anything the agent can see, the dashboard can expose. (Source: Metomic; Obsidian Security; Kiteworks/Cloudera Report)\n\n**On GDPR and log retention:** For operational logs, a 6–12 month retention period is generally defensible under GDPR proportionality principles, but the key requirement is that a retention period exists and is justified. Unbounded log growth fails this test. Automated deletion schedules and the ability to export and purge records are baseline requirements. (Source: Last9 GDPR Log Management; Observo.ai)\n\n**On AI agent autonomy and user control:** 2026 governance guidance consistently emphasizes that users must have meaningful, granular control over autonomous agents — not just visibility, but the ability to intervene, modify, and override. Dashboards that surface autonomy profiles and trust systems without providing actionable controls create a \"display only\" problem: the user sees what the agent decided, but cannot effectively participate in those decisions. (Source: ProcessMaker Ethical AI; IBM Agentic AI Ethics; OneTrust 2026 Privacy Trends)\n\n**On consent for AI agent data collection:** For agent-to-agent or single-user deployments, formal GDPR consent mechanisms may not apply. However, the principle of data minimization — collect only what is needed for the defined task — applies regardless of regulatory context. Topic conversation data surfaced in the dashboard (topic list, message counts, memory sections) requires particular care because it captures behavioral and preference information that users may not consciously intend to expose. (Source: Curity; GDPR Local; SecurePrivacy.ai)\n\n---\n\n## Critical Issues\n\n### 1. Unauthenticated `/health` Endpoint Feeds Dashboard Data\n\nThe spec notes that `/health` is the only endpoint that does not require authentication, and the Vital Signs Strip polls it every 30 seconds. The `/health` endpoint returns: server status, uptime, sessions (current/max), memory pressure, disk usage, and job failure counts.\n\n**Risk:** Anyone who can reach the server — on the local network, via a misconfigured tunnel, or following link sharing — can observe the agent's operational state without credentials. This is low-severity in a purely local deployment, but Cloudflare tunnels are a first-class feature of Instar. A quick-tunnel URL shared once becomes a permanent health beacon for as long as the tunnel runs.\n\n**Recommendation:** Either require authentication on `/health` for all non-trivial data fields (reserving unauthenticated responses for a minimal `{\"status\":\"ok\"}` ping), or add a configuration option to restrict the unauthenticated surface. The dashboard should fall back gracefully if the full health payload requires auth.\n\n---\n\n### 2. Error Messages in Run History Expose Internal State\n\nThe spec includes detailed error messages in the Jobs tab run history, such as: `\"Max sessions (3) reached. Running: session-a, session-b\"` and error strings passed through directly from server-side responses.\n\n**Risk:** Error messages are a well-documented information leakage vector. Surfacing raw server error strings in the dashboard UI reveals session names, resource limits, internal architecture, and potentially file paths or model identifiers. In a tunneled or shared-access scenario, this constitutes unintended information disclosure.\n\n**Recommendation:** Sanitize and categorize error messages before rendering. Map known error codes to user-friendly descriptions (e.g., `spawn-error: Max sessions reached` → `Session limit reached`). Log full error detail server-side. The dashboard should never render raw exception text or internal identifiers directly.\n\n---\n\n### 3. No Data Retention Policy for Job History Ledger\n\nOpen Question 5 in the spec acknowledges this: \"the ledger grows unbounded.\" This is not just an operational concern — it is a data minimization issue. Indefinite retention of every job run, every error string, every handoff note, and every operation gate decision creates a growing record of the agent's complete behavioral history.\n\n**Risk:** Under GDPR Article 5(1)(e), personal data must not be kept longer than necessary. Even in a single-user deployment, if the agent handles topics involving other people (conversations, relationships, attention queue items referencing third parties), that data is subject to proportionality requirements. An unbounded ledger that accumulates years of behavioral logs fails the necessity test.\n\n**Recommendation:** Define and enforce retention limits before building the history UI. Suggested defaults: job run history capped at 90 days or 500 runs per job (whichever is lower); operation gate log retained for 30 days; attention queue items deleted after dismissal. Expose retention configuration in the dashboard settings. Provide a \"Clear history\" action per job.\n\n---\n\n### 4. Topic and Conversation Data in Dashboard Surface\n\nPhase 3 (Evolution Tab, section 3 — Memory & Learning) exposes topic memory statistics, topic list, and message counts. The operation log (Autonomy & Trust Tab) surfaces per-service gate decisions.\n\n**Risk:** Topic lists and message counts reveal conversation patterns and behavioral fingerprints. If topics include user names, project names, or sensitive subject matter, this data becomes personally identifiable in context. The operation log reveals what external services the agent attempted to contact, which services were blocked, and with what frequency — a behavioral profile that may be sensitive.\n\n**Recommendation:** Apply display-level minimization: show aggregate counts rather than topic titles by default, with explicit expansion required to see topic names. Treat topic titles as potentially sensitive and render them only within the authenticated session. For the operation log, consider whether the service name + decision is sufficient without surfacing full operation parameters.\n\n---\n\n### 5. \"Run Now\" and \"Enable/Disable\" Controls — No Action Logging\n\nThe spec proposes `POST /jobs/:slug/run` (run now) and `PATCH /jobs/:slug` (enable/disable) controls accessible from the dashboard. There is no mention of logging these user-initiated actions.\n\n**Risk:** In a multi-access scenario (e.g., a pinned dashboard session left open on a secondary device, or a tunneled URL with a shared token), user-initiated job runs and enable/disable changes are indistinguishable from agent-initiated changes. Without an action log, it is impossible to audit who triggered what and when. This is both a security and an accountability gap.\n\n**Recommendation:** Log all user-initiated dashboard actions (job runs, enable/disable, attention item dismissal, autonomy profile changes) to a dedicated dashboard action log, including timestamp, action, and (if multi-user access is ever supported) identity token. Surface this log in the dashboard settings or a dedicated audit view.\n\n---\n\n## Recommendations\n\n**R1 — Tiered health endpoint:** Separate the public health ping (`{\"status\":\"ok\",\"uptime\":N}`) from the rich health payload. Require auth for the rich payload. The Vital Signs Strip can still work — it just needs a token.\n\n**R2 — Error message sanitization layer:** Add a server-side or client-side mapping from raw error types to display-safe strings. This is a small investment with meaningful leakage reduction.\n\n**R3 — Retention policy before history UI:** Implement retention limits in the server before the job history tab ships. The UI should not be able to display data that should not exist. Consider making retention settings visible (and configurable) in the dashboard.\n\n**R4 — Aggregate-first for topic and memory data:** Default to showing counts and summaries. Require a deliberate expansion click to see topic titles or memory content. This respects the principle that users should make an active choice to surface detailed behavioral data.\n\n**R5 — Dashboard action audit log:** Implement before enabling any mutating dashboard controls (Run Now, Enable/Disable, Dismiss attention item, Change autonomy profile). Audit logs are cheap infrastructure that become essential later.\n\n**R6 — Tunnel awareness in the UI:** If a Cloudflare tunnel is active, the dashboard header should display a visible indicator. Users should not need to check separately whether their dashboard is publicly reachable. This is a consent and awareness issue — users should always know when the dashboard is internet-exposed.\n\n**R7 — Session name masking in error detail:** Specific session names (`session-a`, `session-b`) should not appear in error messages surfaced to the UI. These are internal identifiers that leak implementation details. Map them to anonymous references (e.g., `Session 1`, `Session 2`) or omit them from display entirely.\n\n---\n\n## Observations (Ethical Considerations to Monitor)\n\n**O1 — Power asymmetry in the autonomy display.** The Autonomy & Trust Tab proposes displaying the agent's current trust profile, evolution mode, and per-service trust levels — along with buttons to change them. This is good transparency. However, trust levels that \"auto-elevate based on successful operations\" without explicit user confirmation create an autonomy creep dynamic. The dashboard should make auto-elevation visible as a distinct event, not just a background state change. Users should be able to opt out of automatic trust elevation.\n\n**O2 — Evolution proposals as a consent surface.** The Evolution Tab exposes self-improvement proposals with approve/reject controls. This is a genuinely good design — it makes the agent's self-modification process transparent and subject to human review. The ethical risk is the reverse: if proposals are approved by default (i.e., auto-approved after a timeout, or approved implicitly by inaction), the approve/reject UI becomes theater. Ensure the approval model is genuinely blocking, not advisory.\n\n**O3 — Surveillance potential of operation log.** The operation gate log records every attempted external interaction: what service, what operation, what decision. This is primarily a safety and accountability tool — and a valuable one. But if the agent operates in a context where it interacts with other people's services or data, the operation log becomes a record of those people's data being accessed. At scale, this is a privacy concern for third parties. No immediate action required for single-user deployment, but the data model should be designed with eventual deletion of third-party-referencing records in mind.\n\n**O4 — Handoff notes as persistent behavioral memory.** The Reports sub-view surfaces handoff notes (\"Disk at 97%, monitor for further rise\") inline between job runs. Handoff notes can contain whatever the agent chose to write — including content from conversations, attention queue items referencing people, or observations about user behavior. These notes are currently ephemeral (passed between runs) but the Reports view makes them persistent UI state. If handoff notes are stored in the job ledger long-term, their content should be subject to the same retention policy as job history.\n\n**O5 — AI-to-AI consent gap.** The spec describes an agent (Echo) building a dashboard for observing its own systems. The agent has no independent interests separate from the operator in this deployment. However, as Instar scales to multi-agent deployments (Threadline is already present in the codebase), dashboards that expose per-agent behavioral data will affect agents whose \"consent\" is architectural rather than informed. This is a nascent concern, but the dashboard's data model should be designed to support per-agent data scoping from the start rather than treating all agents as a single monolithic data subject.\n\n---\n\n## Scalability Assessment\n\nThe spec is scoped explicitly to a single-user, self-hosted deployment. The privacy posture at that scale is acceptable with the critical issues addressed. Privacy risks escalate significantly at each of the following thresholds:\n\n**Shared dashboard access (multiple users, same agent):** The current auth model (PIN → bearer token) is a single-principal model. There is no concept of user identity, role, or access scope. If two people share dashboard access, every action is attributed to the same principal and the operation log is unauditable. Before adding any collaboration features, a proper identity model is required.\n\n**Multi-agent deployments:** When multiple agents share a dashboard or their data is aggregated, the topic list, operation log, and memory sections become cross-agent behavioral profiles. Data minimization requirements multiply and data subject identification becomes possible through correlation.\n\n**Tunneled/internet-exposed deployments:** The `/health` unauthenticated endpoint and the error message leakage risks become substantially more serious. At scale, a shared Cloudflare tunnel with a guessable or leaked URL exposes operational state to the open internet. Rate limiting and auth requirements must be enforced before tunnel features are promoted.\n\n**Job history growth over years:** An unbounded ledger that accumulates without deletion eventually becomes a comprehensive behavioral archive. GDPR erasure requests, right-to-be-forgotten obligations (for any third-party data touched by the agent), and storage costs all scale with this growth. The retention policy recommendation above must be implemented before the system reaches long-term production use.\n\n---\n\n## Score: 7 / 10\n\n**Justification:** The spec demonstrates strong awareness of user needs and operational transparency. The auth model is functional, the PIN-gated bearer token approach is appropriate for the deployment context, and the design does not introduce new data collection beyond what the system already generates. The score is held back by: the unauthenticated health endpoint (a concrete leakage risk), the unbounded ledger (a data minimization failure), the raw error message display (an information leakage risk), and the absence of any action audit logging for mutating dashboard controls. These are all tractable problems. With the five critical issues addressed, this spec would score 9/10.\n\n---\n\n*Review conducted using independent web research.
