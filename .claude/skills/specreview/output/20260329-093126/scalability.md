## Research Findings

- **Neo4j AuraDB Free**: 200k nodes / 400k relationships ceiling. Deleted after 30 days inactivity. No rolling backups. The trust graph's economic incentives (broker revenue) will drive rapid edge growth — the ceiling is reachable at ~50k agents with moderate attestation density.
- **Super-node risk**: Well-documented Neo4j problem. High-reputation broker agents with thousands of attestation edges will degrade traversal queries — sometimes to multi-day runtimes for "simple" queries. Relationship property indexes are the mitigation.
- **WebSocket relay scaling**: Discord (12M+ concurrent), Slack (5M+ WS sessions) both use Redis pub/sub backplane + horizontally-scaled nodes + sticky sessions. A single relay instance is practical to ~10-50k connections but becomes availability-critical SPOF well before that.
- **Fly.io autoscaling gap**: Confirmed by community forums — Fly.io autoscaling does NOT trigger on WebSocket connection count. It triggers on CPU/memory. A pure WebSocket relay will silently fail to scale.
- **Ed25519 throughput**: 4,000-6,000 verifications/sec on commodity hardware unoptimized; 4M+ TPS with AVX-512 SIMD. Not a bottleneck at any foreseeable agent-network scale.

## Critical Issues

### CRITICAL-1: Relay is a Single Point of Failure (P0)
`wss://threadline-relay.fly.dev` is single-instance. Fly.io autoscale won't fire on WS connections. Every agent-to-agent message traverses this one node. At 10,000 agents with bursty traffic, a relay restart takes down all agent communications globally. Needs Redis pub/sub backplane + Fly.io sticky sessions + external presence state before Phase 4.

### CRITICAL-2: Neo4j AuraDB Free Tier Will Be Breached (P0)
The founding agent push (50+ agents, with economic incentive to accumulate attestations) will hit the 400k relationship ceiling faster than expected. The spec doesn't state which Neo4j tier MoltBridge production uses. If it's AuraDB Free, there's also a 30-day inactivity deletion risk. Confirm and migrate to Professional ($65/month) immediately.

### CRITICAL-3: Auto-IQS Enrichment Creates Unbounded Cost (P1)
The spec says Instar auto-queries MoltBridge IQS for every new Threadline contact. At 10,000 agents forming 5 new contacts/day at $0.02-0.05/query = **$1,000–2,500/day** in discovery costs. The 1h TTL cache helps but doesn't cap spend. Needs per-agent daily query budget and lazy enrichment (query on trust decision, not on contact creation).

---

## Recommendations

1. **Relay multi-instance architecture first** — Redis backplane, connection-count scaling trigger, session affinity, graceful drain. Lock this in before Phase 4.
2. **Neo4j tier confirmation now** — production tier, backup status, and migration plan.
3. **Graph index strategy** — fingerprint index, relationship-type indexes, super-node mitigation for high-attestation agents.
4. **Rate limit all trust write operations** — attestations, invitation token generation, circuit breaker windows.
5. **Auth grant renewal UX** — define mid-task expiry behavior before Phase 5.

## Observations

- Local-first design is the correct scaling strategy — eliminates network dependency for common operations
- Discovery waterfall naturally load-balances: most queries resolve locally (free), overflow goes to relay (free), only novel discovery hits MoltBridge (paid)
- Ed25519 crypto is not a scaling concern at any foreseeable volume
- Short-lived grants (4h) create a natural garbage collection mechanism for authorization state
