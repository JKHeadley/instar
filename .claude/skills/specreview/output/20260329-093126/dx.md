## Research Findings

- MCP tool design conventions favor explicit parameter schemas with Zod validation, descriptive tool names, and structured error responses
- Best-in-class agent platforms (LangGraph, CrewAI) provide "hello world" quickstarts that complete in under 5 minutes
- Discovery API patterns in the ecosystem favor capability-based search with filter/sort/pagination
- Band-based scoring (vs. exact scores) is a recognized DX pattern for reducing cognitive load in trust UIs

---

## Critical Issues

### C1: MCP Tool API Surface Underspecified (HIGH)

`moltbridge_discover`, `moltbridge_trust`, and `moltbridge_attest` are named but have no parameter schemas, return types, or error codes defined. An agent trying to use these tools can't know what to pass or what to expect back.

**Fix**: Define Zod schemas for each tool: input parameters, return shape, error codes.

### C2: Invitation UX is a Black Box (MEDIUM-HIGH)

The invitation flow describes token generation and acceptance but not the user-facing experience. What does the token look like? What does the agent say when a token expires or is reused? How does the human share it?

**Fix**: Design the invitation UX end-to-end: token format, sharing methods (link, QR, paste), expiry messaging, error states.

### C3: No Onboarding Path for Non-Instar Integrators (MEDIUM-HIGH)

The spec says CrewAI, LangGraph, and AutoGen agents can connect, but there's no quickstart guide or integration path for them. A developer building with CrewAI who wants Threadline messaging has no entry point.

**Fix**: Define a "Hello, Agent" 5-step quickstart during spec phase. If it can't be written cleanly, the design has hidden friction.

## Observations (What's Done Well)

- **Discovery waterfall** (local → relay → MoltBridge) is excellent DX layering — progressively more expensive, progressively wider reach
- **Same-machine fast path** eliminates crypto-ceremony friction for the common case (same-laptop agents)
- **Band-based IQS surfacing** protects context window vs. exact scores
- **Permission matrix** in Section 3.6 is exactly what developers need to understand authorization
- **Non-goals section** is unusually well-specified — prevents scope creep
- **Phase sequencing** (identity first) respects DX concerns — get the foundation right before adding complexity
