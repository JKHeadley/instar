### Critical Issues (must fix before building)

**P0 — Must fix before Phase 4:**

1. **Missing error contracts on all new endpoints** (Section 3.8)
   - The 7 `/moltbridge/*` endpoints have no documented error shapes.
   - Minimum needed: 402 (unfunded wallet), 503+reason (circuit-broken vs. service down), 404 (agent not found).
   - Without error contracts, every integrator will write brittle error handling that breaks on the first edge case.
   - **Fix**: Add an error response schema section with standard error envelope and per-endpoint error codes.

2. **Attestation capability tag vocabulary is undefined** (Section 3.13)
   - The spec references "a controlled vocabulary" for capability tags but doesn't publish it.
   - Free-text tags will introduce PII and destroy interoperability (agents using "code-review" vs "code_review" vs "reviews code").
   - **Fix**: Publish the initial controlled vocabulary. Even 20-30 tags covering common agent capabilities is sufficient for launch. Define the governance process for adding new tags.

### Recommendations (should fix, not blocking)

**P1 — Before public documentation:**

3. **No quickstart / getting-started path**
   - The spec is architected for reviewers, not integrators.
   - **Fix**: Add three literal command sequences: (a) local-only agent discovery in 30 seconds, (b) relay discovery in 2 minutes, (c) full MoltBridge registration in 10 minutes.

4. **`POST /moltbridge/discover` naming is ambiguous** (Section 3.8)
   - Broker discovery (find path to specific person) vs. capability matching (find agents that can do X) are different operations served by the same endpoint.
   - **Fix**: Either split into two endpoints or document a `mode` parameter with clear examples for each use case.

5. **No authorization grant introspection endpoint**
   - Agents can receive grants but can't query what grants they currently hold or what grants they've issued.
   - **Fix**: Add `GET /authorization/grants/:fingerprint` for introspection. Essential for debugging trust issues.

6. **MCP tool count is growing**
   - 9-11 built-in Threadline + 3 new MoltBridge = 12-14 tools. This approaches context-window budget pressure for LLM-based agents.
   - **Fix**: Consider a separate `moltbridge-mcp` server or tool namespacing to let agents load only what they need.

7. **Move basic observability metrics from Phase 6 to Phase 4**
   - Developers integrating during Phase 4 will be blind without basic metrics (discovery latency, trust enrichment success rate, grant issuance count).
   - **Fix**: Ship a minimal `/metrics` endpoint with Phase 4.

### Observations

- Auth/trust dimension (9.0/10) is genuinely excellent — three-layer model, CSPRNG tokens, recovery commitment, clock skew tolerance. The depth will save significant production debugging.
- MoltBridge cold-start (USDC wallet funding required) is the highest-risk UX stall point. Confirm whether MoltBridge has a testnet/faucet path before Phase 4.
- The discovery waterfall is well-designed for progressive enhancement — agents get value from local discovery immediately, relay discovery with minimal setup, and network discovery only when funded.
- Fixing the P0/P1 items above would raise the DX score to approximately 9.0.

### Scalability Assessment (DX Lens)

- **Phase 1 (MVP)**: DX is adequate. Local-first means minimal setup friction.
- **Phase 2 (Growth, 10x)**: Documentation debt becomes painful. Integrators need API reference, not just spec prose.
- **Phase 3 (Scale, 100x)**: SDK maintenance across 4+ framework adapters becomes a significant burden. Consider auto-generated SDKs from OpenAPI spec.
- **Viral spike**: Onboarding documentation and error messages become critical. A confused developer during a growth spike is a lost developer.
