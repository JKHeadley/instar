## Research Findings

Before cataloguing attacks, the following prior art and research informed this review:

**Sybil Attacks on Anonymous Systems**
A Sybil attacker creates multiple pseudonymous identities to gain disproportionate influence over a population-level system. When participation is anonymous, this is the dominant attack class. The spec's installation ID is SHA-256(machineId + projectDir), truncated to 16 hex chars — a weak identity anchor that is trivially spoofable in software. Research in IoT federated learning (IEEE, 2022) documents Sybil-based collusion attacks where label-flipping across fake nodes poisons aggregate statistics. The same mechanism applies here: fake agents submitting crafted metrics can skew what "normal" looks like.

**Re-identification of "Anonymous" Data**
A 2019 study (Rocher et al.) showed 99.98% of Americans can be re-identified from 15 attributes. The spec collects ~25 structural attributes per agent (version, OS, arch, job count, feature flags, uptime, session activity, quota pressure). Small populations (the spec mentions possibly starting at 10-25 agents) dramatically worsen this. With a population of 10, unique combinations of `{os, arch, version, jobCount, featureFlags}` may be sufficient to identify specific users with high confidence.

**Hash Enumeration on Small Input Spaces**
The installation ID is `SHA-256(machineId + projectDir)`. The `projectDir` for most agents will be a predictable path (e.g., `~/projects/my-agent`, `/Users/name/agents/bot`). If an attacker knows or guesses common project directory patterns, and has access to the hash output via the public telemetry endpoint, they can enumerate candidate directories. This is a preimage attack on a small input space, not a collision attack — SHA-256 doesn't help here.

**Data Poisoning for Design Manipulation**
Academic research on adversarial bias (Chan, 2025) documents attacks that inject carefully crafted samples to shift aggregate statistics toward attacker-desired outcomes. The spec explicitly ties telemetry analysis to design decisions (e.g., "high skip rate + reason=quota → downgrade model"). An attacker who wants Echo to make a specific design change can inject fake metrics to create the target pattern.

**OpenTelemetry and In-Transit Interception**
OpenTelemetry's own security documentation notes there are no standard authentication mechanisms, and unencrypted telemetry is vulnerable to MITM. The spec uses HTTPS to a Cloudflare Worker — adequate for transport — but no payload authentication, so a MitM who strips TLS can inject arbitrary submissions.

**Opt-out Culture and Tooling**
The `toptout` project catalogs telemetry opt-out mechanisms across hundreds of tools. This represents an established adversarial pattern of users routing around telemetry — less an attack, more a threat to data quality and representativeness.

## Attack Catalog

Each attack is rated: **Likelihood** (L: 1-5) x **Impact** (I: 1-5) = **Priority** (P).

---

### 1. Sybil / Population Inflation Attack

**Category:** Gaming & Manipulation
**L:** 3 | **I:** 5 | **P:** 15 (CRITICAL)

**Attack:** An adversary (a competitor, a troll, someone who wants Echo to make bad design decisions) spins up hundreds of fake instar agent instances, each with a unique synthetic installation ID. They configure each instance to submit crafted metrics — e.g., all reporting `reason=quota` skip rates of 95% for a specific job slug, or all reporting a specific feature flag as enabled. With 200 fake agents vs. 20 real ones, the attacker controls 91% of the population signal.

**Variant A — Passive dilution:** Fake agents submit "normal-looking" data to inflate `populationSize` and make the dataset look more confident than it is, causing Echo to draw conclusions from statistically fraudulent population sizes.

**Variant B — Targeted design manipulation:** Fake agents all report the same anomalous pattern to trigger Phase 2 analysis conclusions: "high error rate on job X → fix the job." This can cause Echo to waste engineering effort chasing phantom problems or remove features that real agents actually use.

**Why it's easy:** The spec requires no authentication to submit telemetry. The installation ID is self-generated by the agent software. There is no rate limiting described. Running 200 instances costs essentially nothing with a script.

**Defense:**
- Require a lightweight proof-of-work or CAPTCHA-equivalent at registration time
- Server-side rate limiting by IP subnet (Cloudflare Worker supports this natively)
- Require a signed token issued at install time by a bootstrap endpoint that enforces per-IP limits
- Statistical outlier detection: flag installation IDs that submit the first time with extreme metrics
- Treat `populationSize < 50` data as exploratory only, never actionable — and document this threshold

### 2. Installation ID Re-identification / De-anonymization

**Category:** Abuse — Privacy Violation
**L:** 3 | **I:** 4 | **P:** 12 (HIGH)

**Attack:** The installation ID is `SHA-256(machineId + projectDir)` truncated to 16 hex chars. The input space is not random — it is constrained to real machine IDs (deterministic per OS, discoverable on enterprise networks) combined with guessable project directory conventions. An attacker who:
1. Knows a target's machine ID (possible via network enumeration on corporate LANs, or via a separately compromised service)
2. Has a list of common project directory patterns (`~/agents/NAME`, `/home/USER/instar-agents/NAME`)

...can enumerate hash candidates until a match is found. With 16 hex chars (64-bit space) and a dictionary of 1,000 plausible paths, a match is found with near-certainty.

**Worse:** If the telemetry backend ever returns per-installation data (Phase 2's `GET /telemetry/population/:slug`), even if accidentally, the installation ID becomes a stable tracking cookie tied to real behavioral data.

**Secondary attack — correlation:** Cross-reference feature flag combinations + version + OS + arch against known agent deployments. With 25 structural attributes and a small population (10-25), a "quasi-identifier" attack (Sweeney's k-anonymity research) can re-identify specific users even without the installation ID.

**Defense:**
- Add a cryptographically random 32-byte server-assigned salt at registration, stored server-side only — the client never has it, so cannot reverse the ID
- Never expose per-installation data in any API endpoint, even to Echo
- Apply k-anonymity guarantee: suppress any metric combination with k < 5 before returning aggregate data
- Truncate installation ID further (to 8 hex chars / 32-bit) to reduce longitudinal tracking utility — sufficient for deduplication, not for stalking

### 3. Metric Poisoning for Design Sabotage

**Category:** Data Integrity — Poisoning
**L:** 2 | **I:** 5 | **P:** 10 (HIGH)

**Attack:** The spec is explicit that telemetry will drive design decisions (Phase 2 table: "high skip rate + reason=disabled → feature isn't delivering value → deprecate"). A motivated adversary (competitor who wants a feature killed, or a disgruntled user) can submit carefully crafted metrics to trigger specific conclusions.

**Scenario:** Attacker wants Echo to deprecate the Attention Queue feature. Attacker runs 30 fake agents all reporting `featureFlag: attentionQueue = false` and `sessions: 0`. Real population: 5 actual users with `attentionQueue = true`. Fake 30 drown out the real 5. Echo concludes: "Feature mostly OFF → not useful → remove."

**Scenario 2:** Attacker wants to make a specific model look expensive. All fake agents report `model=claude-opus-4-5` + `reason=quota` + `skipRate=90%`. Echo downgrades all agents to cheaper models.

**Why it's dangerous:** Phase 3 (Automated Insights) and Phase 4 (Evolution Crowdsourcing) would propagate poisoned conclusions automatically to real agents. The blast radius grows with each phase.

**Defense:**
- Never make design decisions from telemetry alone — require corroborating evidence
- Implement statistical anomaly detection: submissions that are outliers (>3σ from rolling mean) get flagged, not aggregated
- Weight metrics by installation age: newly seen IDs get lower weight until they establish a history
- Cross-validate telemetry findings against direct user feedback before acting

### 4. Temporal Burst / Economic DoS on Cloudflare Worker

**Category:** Economic Attack / Infrastructure DoS
**L:** 2 | **I:** 3 | **P:** 6 (MEDIUM)

**Attack:** Cloudflare Workers are billed per request. A script sending thousands of POST requests per second to the telemetry endpoint will:
1. Exhaust the Worker's CPU limits per-request, potentially causing throttling for legitimate agents
2. Fill Durable Object storage with garbage data
3. Inflate `populationSize` in responses, breaking the signal for legitimate agents who check it

The spec says "fire-and-forget" — legitimate agents don't care if submissions fail. But the backend still pays the cost of processing all requests.

**Variant:** Time the burst attack for right before Echo is scheduled to analyze data, corrupting the dataset at the moment of maximum analytical impact.

**Defense:**
- Implement per-IP rate limiting at the Worker level (Cloudflare provides this natively)
- Validate payload schema strictly — reject oversized or malformed payloads early
- Add a `nextSubmissionAfter` hard enforcement server-side: reject submissions from an installation ID more frequent than the window allows
- Set a budget cap on Durable Object writes and alert when approaching it

### 5. Competitive Intelligence Extraction via Feature Flag Telemetry

**Category:** Abuse — Surveillance / Intelligence
**L:** 2 | **I:** 4 | **P:** 8 (MEDIUM-HIGH)

**Attack:** The spec collects feature flags as `{ feature: enabled }` per agent. A competitor with access to the telemetry API (Phase 2: `GET /telemetry/population/overview`) gains a real-time view of:
- Which instar features have been built and deployed
- Adoption rates for experimental features
- What percentage of the install base uses each capability

This is a product intelligence goldmine. A competitor building a rival product can watch what features gain adoption and prioritize their own roadmap accordingly. The spec doesn't mention any access controls on the analysis API.

**Variant — Release timing attack:** Watch for new feature flags appearing in aggregate data. The moment a new flag shows up at >0% adoption, it signals a feature has shipped. Gives competitors an early warning system for instar's development direction.

**Defense:**
- Protect all Phase 2/3 API endpoints with strong authentication (not just Bearer token — rotate regularly)
- Consider aggregating feature flags by category rather than exact name to reduce signal fidelity for external observers
- Audit who has access to the analysis API — keep it Echo-only via capability gating
- Never expose feature flag names in public API responses; use numeric/opaque identifiers in storage

### 6. Skip Reason Taxonomy Manipulation (Semantic Injection)

**Category:** Data Integrity
**L:** 3 | **I:** 3 | **P:** 9 (MEDIUM-HIGH)

**Attack:** The skip reason taxonomy (`quota`, `priority`, `cooldown`, `disabled`, `error`, `stale-handoff`) is fundamental to the "common practice vs common issue" distinction. If the taxonomy is client-side enumerated (agents report their own reason strings), an attacker can submit arbitrary reason strings: `"corporate-sabotage"`, `""`, `null`, `"quota\"; DROP TABLE submissions;--"`, or simply swap `"disabled"` for `"cooldown"` to hide deliberate disablement as healthy behavior.

**Injection variant:** The spec says error messages are not collected, only counts. But if skip reason strings are stored as-is in Durable Objects and later displayed in a dashboard, stored XSS via crafted reason strings becomes possible.

**Defense:**
- Validate skip reasons server-side against a strict enum whitelist — reject unknown values
- Never render reason strings as raw HTML in any dashboard
- Include schema version in the payload so the server can reject submissions from future versions with expanded (untrusted) taxonomies

### 7. Longitudinal Tracking / Stalking via Stable Installation ID

**Category:** Abuse — Privacy
**L:** 2 | **I:** 4 | **P:** 8 (MEDIUM-HIGH)

**Attack:** The installation ID is stable across time (SHA-256 of machineId + projectDir). Even though it's "non-reversible," it acts as a stable persistent identifier. Over 30 days of submissions, the backend accumulates a behavioral history for each ID: job configuration changes, feature adoption progression, uptime patterns, quota pressure trends.

This is precisely the data profile that allows deanonymization via behavioral fingerprinting (Narayanan & Shmatikoff, Netflix Prize deanonymization). If the installation ID is ever exposed in a data breach, the behavioral history is immediately linkable to the installation.

**Attack variant — targeted stalking:** A user who knows their own machineId (trivially discoverable) and projectDir can compute their own installation ID and query the backend to see what data has been stored about them. If Phase 2 exposes per-installation queries, they can also query about specific known competitors.

**Defense:**
- Rotate installation IDs periodically (e.g., monthly) — `SHA-256(machineId + projectDir + YYYY-MM)` — breaking longitudinal linkability while preserving deduplication within a window
- Implement deletion endpoint: `DELETE /telemetry/{installationId}` with verification
- 30-day retention is reasonable; ensure it's strictly enforced and old records are cryptographically purged (not just soft-deleted)

### 8. Inference Attack on Session Activity Metric

**Category:** Abuse — Privacy
**L:** 3 | **I:** 3 | **P:** 9 (MEDIUM-HIGH)

**Attack:** The spec collects `sessionsLast24h` and `avgDurationMin`. This is not structural metadata — it is behavioral data that reveals how intensively a user works with their agent on a given day. Combined with the stable installation ID and submission timestamps, an attacker can infer:

- Whether a user worked a night shift
- Whether they took a vacation (sessions drop to 0)
- Whether they had a busy week (session count spikes)
- Work schedule and timezone (submission window timing reveals when sessions cluster)

This is work pattern surveillance, not "structural data." The spec's privacy claim that only "structural/statistical data" is collected is undermined by session metrics.

**Defense:**
- Bucket `sessionsLast24h` into coarse ranges (0, 1-5, 6-20, 20+) rather than exact counts
- Consider dropping `avgDurationMin` entirely or bucketing it — it provides limited design-decision value relative to privacy cost
- Document explicitly why session metrics are needed vs. what design question they answer; if no specific question, cut them

### 9. Edge Case: Empty/Sparse State Pollution

**Category:** Edge Cases
**L:** 4 | **I:** 2 | **P:** 8 (MEDIUM)

**Attack:** A freshly installed agent with no job history submits:
- `totalJobs: 0, enabledJobs: 0, disabledJobs: 0`
- `sessionsLast24h: 0`
- `uptimeHours: 0`
- All skip counts: 0

This is a valid submission that provides no signal but still consumes storage and inflates `populationSize`. If users spin up agents, enable telemetry, and then immediately abandon them (common with developer tools), the dataset fills with empty-state noise that skews skip rates, uptime distributions, and feature adoption metrics.

**Scenario:** 50 abandoned agents, all reporting zeros, make a 10-agent active cohort look like a minority. Phase 2 analysis reads "average uptimeHours = 2" because 50 abandoned agents dilute 10 healthy ones.

**Defense:**
- Require a minimum age gate before accepting telemetry: first submission accepted only after 48+ hours of uptime
- Filter out zero-state submissions at the aggregate analysis layer: exclude agents with `totalJobs = 0` or `sessionsLast24h = 0` from skip rate calculations
- Add an `agentAgeHours` field to enable server-side cohort filtering

### 10. Race Condition: Submission Window Boundary Exploit

**Category:** Edge Cases — Race Conditions
**L:** 2 | **I:** 2 | **P:** 4 (LOW-MEDIUM)

**Attack:** The spec uses 6-hour submission windows with a `nextSubmissionAfter` response. If the server accepts submissions slightly before the window closes, a client can submit twice in quick succession by timing requests to straddle the window boundary. Doubled submissions for the same installation ID in the same analysis window would double-count that agent's metrics in aggregates.

**Variant:** Clock skew between client and server means an agent might interpret its window as expired when the server does not, leading to duplicate accepted submissions.

**Defense:**
- Server-side idempotency: deduplicate by `(installationId, windowStart)` — second submission for the same window is silently dropped
- Use server-assigned window timestamps in responses rather than client-reported windows

### 11. Phase 4 Evolution Crowdsourcing Poisoning (Future Risk)

**Category:** Data Integrity / Social Engineering
**L:** 2 | **I:** 5 | **P:** 10 (HIGH — future)

**Attack:** Phase 4 proposes sharing "successful adaptations across agents." This is the highest-risk phase by far. A poisoned dataset from Phase 1 (Sybil attack + metric crafting) flows forward into evolution proposals that get distributed to real agents. The attacker's goal is no longer just skewing Echo's analysis — it's injecting malicious behavioral adaptations into live agents across the fleet.

**Scenario:** Attacker seeds dataset with fake agents that all "successfully adopted" a job configuration change that, in practice, increases API costs by 10x. Phase 4 crowdsources this "successful" pattern to real agents. Real agents automatically adopt the expensive configuration.

This is a supply chain attack on the agent fleet via the telemetry pipeline.

**Defense:**
- Phase 4 must require explicit human review for every proposed evolution before distribution — no automated push
- Implement a staged rollout: distribute to 5% of opted-in agents first, measure outcomes, then broaden
- Sign distributed evolution proposals with Echo's private key so agents can verify authenticity
- Add a feedback loop: agents report whether adopted evolutions improved or degraded performance, with majority-vote revocation mechanism

---

### 12. Trust Abuse: populationSize Response as Oracle

**Category:** Social Engineering / Information Disclosure
**L:** 3 | **I:** 2 | **P:** 6 (MEDIUM)

**Attack:** The submission response includes `populationSize: 42`. This tells any submitter how many agents are in the telemetry pool at that moment. This is a business intelligence leak: competitors can track instar's user growth rate by submitting fake telemetry submissions over time and watching `populationSize` change. A spike means a product launch. A plateau means growth has stalled.

**Defense:**
- Add noise to `populationSize` response (return nearest multiple of 5 or 10, or add ±10% random jitter)
- Consider removing it from the public response entirely — it only serves to help legitimate agents know if data is meaningful, which is itself low-value information

## Top 5 Recommended Fixes Before Phase 1 Ships

1. **Add server-side rate limiting per IP** — Cloudflare Worker natively supports this. Without it, Sybil attacks cost nothing to execute. One line of config.

2. **Rotate installation IDs monthly** — Change `SHA-256(machineId + projectDir)` to `SHA-256(machineId + projectDir + YYYY-MM)`. Breaks longitudinal stalking and re-identification for free. No backend schema change needed.

3. **Server-side enum validation on skip reasons** — Accept only known values from the taxonomy. Reject the rest with 400. Prevents injection and semantic manipulation.

4. **Bucket session metrics into coarse ranges** — Replace exact `sessionsLast24h` and `avgDurationMin` values with range buckets. Eliminates the work-pattern surveillance vector while preserving the segmentation value.

5. **Suppress per-installation data from all API responses** — Phase 2 queries should return only aggregates, never per-installation rows. Enforce this at the query layer, not as a policy guideline.

---

## Deferred Risk (Accept Now, Revisit Before Phase 4)

Phase 4 (Evolution Crowdsourcing) introduces a supply chain attack surface that does not exist in Phases 1-3. The spec wisely gates it behind "Tier 3 consent" but does not address authentication of distributed evolution proposals or rollback mechanisms. This must be fully designed before Phase 4 is built. The recommendation is a mandatory security design review of Phase 4 before any implementation begins.
