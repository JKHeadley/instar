Q1. Is the runtime-reconciliation detection claim TRUE?

No, not as stated. It is a useful detector for one narrowed case, but the spec overstates both the available inputs and the discriminating power of `looked === 0`.

`expectedTickMs` exists in the current manifest type (`src/monitoring/guardManifest.ts:36-37`) and the current posture view already uses a `5x` multiplier for `lastTickAt` staleness (`src/monitoring/guardPostureView.ts:43-44`, `src/monitoring/guardPostureView.ts:243-255`). But it is not populated for all surveyed tick-loop guards. The chokepoint survey names 19 TICK-LOOP guards (`.phase-b-census/chokepoint-survey.md:29-49`); comparing those keys to the manifest found 8/19 without `expectedTickMs`. Concrete examples: `multiMachine.sessionPool.holdForStability.enabled` has `expectRuntime: true` but no `expectedTickMs` in its entry (`src/monitoring/guardManifest.ts:217-228`), `multiMachine.sessionPool.staleOwnerRelease.enabled` has no `expectedTickMs` (`src/monitoring/guardManifest.ts:235-244`), `multiMachine.leaseSelfHeal.preferredCaptainHandback.enabled` has no `expectedTickMs` (`src/monitoring/guardManifest.ts:257-266`), and `monitoring.promptGate.enabled` has no `expectedTickMs` (`src/monitoring/guardManifest.ts:935-942`).

The claim is worse for FUNNEL guards. The survey names 9 FUNNEL guards (`.phase-b-census/chokepoint-survey.md:50-62`), but most have no periodic cadence in the manifest; e.g. `writeAdmission` has no `expectedTickMs` (`src/monitoring/guardManifest.ts:110-119`), and `monitoring.completionClaimVerification.enabled` has no `expectedTickMs` (`src/monitoring/guardManifest.ts:881-889`). More importantly, a funnel can legitimately have `looked === 0` because no request hit the funnel. A `5x expectedTickMs` rule is meaningful for a periodic tick loop, not for traffic-driven admission paths.

The proposed verdict table does not model the states needed to distinguish bypass from non-eligibility. It maps `looked === 0` directly to `never-evaluated` (`/tmp/spec-v5.md:458-463`) and the runtime-reconciliation paragraph says this is "provably not being invoked through the wrapper" after `5x expectedTickMs` (`/tmp/spec-v5.md:412-415`). Current source shows why more inputs are needed: disabled guards are classified before staleness today (`src/monitoring/guardPostureView.ts:299-305`), and the `/guards` build path passes `now` but no process-start/uptime or awake-window input (`src/monitoring/guardPostureView.ts:361-369`, `src/server/routes.ts:8703-8708`). Standby/awake gating also affects whether a loop exists at all; for example, the scheduler is constructed only under `config.scheduler.enabled && coordinator.isAwake` (`src/commands/server.ts:7031-7034`).

Correct narrower claim: for an enabled tick-loop guard with a declared cadence, a registered counters row, and a process that has been continuously eligible/awake for more than `5x expectedTickMs`, `looked === 0` is strong evidence of no wrapped invocation. It does not distinguish direct-call bypass from disabled config, funnel idleness, standby/sleep ineligibility, or just-started process unless those become explicit inputs to the schema.

Q2. Does `registry.act()` actually fix the `didAct` trust split?

Partly. Moving `didAct` off the guard's verdict handle is a real fix to the prior handle-level trust split: the proposed `verdict(key)` exposes only `wouldAct` (`/tmp/spec-v5.md:365-369`), while `act(key, perform)` is separate and increments after the wrapped function returns (`/tmp/spec-v5.md:371-378`).

But the spec's `act<T>(key, perform: () => T): T` is not sufficient. First, it is sync-shaped. If `perform()` returns a `Promise`, the sample increments `didAct` immediately after Promise creation, not after the side effect succeeds. That contradicts the spec's own "only AFTER the side effect actually completes" wording (`/tmp/spec-v5.md:371-377`). Source has async action paths in the scoped families: Telegram topic creation is `async createForumTopic(...)` (`src/messaging/TelegramAdapter.ts:1489-1493`) and the actual side effect is awaited later (`src/messaging/TelegramAdapter.ts:1536-1543`); `findOrCreateForumTopic` awaits it too (`src/messaging/TelegramAdapter.ts:1592-1603`).

Second, the capability split is not specified strongly enough. Current `GuardRegistry` is a normal exported mutable class with public methods (`src/monitoring/GuardRegistry.ts:40-71`), constructed once at boot (`src/commands/server.ts:6941-6945`) and passed as a full object into server/route contexts (`src/server/AgentServer.ts:709-710`, `src/server/AgentServer.ts:3748-3756`, `src/server/routes.ts:1517-1521`). If the implementation adds public `act()` to that same object and threads the full registry the same way, any code with `ctx.guardRegistry` can call it. That is not yet a proof that a guard cannot reach `didAct`; it needs separate capabilities, e.g. `GuardVerdictSink` for guard code and an `ActionSink`/async `act` wrapper only at side-effect seams.
