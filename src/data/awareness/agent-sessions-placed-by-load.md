---
title: Helper sessions placed by load
---
A topicless helper started with `POST /sessions/spawn` can ask to run where there is room: add `"placement": "auto"` to the body. It still starts on this machine while this machine has room. When this machine is busy (its own load verdict is saturated or impaired, it is short of memory, or its load is at or above 1.0 per core), the helper starts on another machine in the pool that has room and memory to spare, through that machine's own `/sessions/spawn`. Without the field, nothing changes. Every agent-started spawn also writes where it would have gone to `logs/agent-session-placement.jsonl` (no prompt text), so you can see how much load could move.

Only `name`, `prompt`, `workWeight`, `framework` and `model` travel for a helper. A request with a `topicId` (unless topic placement below is on), `jobSlug`, `ultracode`, `spawnRole`, `topicName`, `requireTopicBinding`, `targetMachineId` or a bind token stays here (`placementReason: "options-do-not-travel"` or `"topic-bound"`). A placed helper runs in the OTHER machine's agent home, so use `auto` only when its prompt is location-independent: it fetches its inputs from a shared source (a pushed branch, a document, a message) and returns results through a shared channel.

Answers: `201` with `placementOutcome: "peer"` and `placedOn` (started there), `"local"` or `"local-fallback"` with `placementReason` (started here). `409 placementOutcome: "exists-on-peer"` means that name is already running on the named machine. `409 placement-bound-elsewhere` means the name was placed earlier and its outcome is not known: check that machine, then use a NEW name. `202 placementOutcome: "unconfirmed"` means the hand-off timed out and the helper may have started there. Do not start the same work again under a new name; this machine keeps checking and raises one attention item if it cannot confirm. `GET /sessions/<name>/output` works for a placed helper (read from its machine). A kill answers `409 placed-on-peer`: stop it on that machine.

```bash
curl -X POST http://localhost:{{port}}/sessions/spawn -H "Authorization: Bearer $AUTH" -H 'Content-Type: application/json' \
  -d '{"name":"review-pr-123","prompt":"Check out PR 123 in a fresh worktree, review it, post the review on the PR.","placement":"auto"}'
```

Topic-bound spawns (`multiMachine.placement.agentSessions.topicBound`, live on a development agent): a spawn with `"placement": "auto"` AND a `topicId` into a topic with no live owner can start on a less-loaded peer the same way a person's first message does, when this machine holds the pool lease and is busy (or a peer is clearly less loaded). It never travels with `model`, `framework`, `jobSlug`, a bind token or `workWeight: "heavy"`, and only to a peer that advertises `agent-brief@1`; the session there reads the prompt as the agent's own fresh task. Answers: `202 placementOutcome: "peer-accepted"` with `placedOn` and `tmuxSession: null` (the target names the session; later messages in the topic go there), `202 "unconfirmed"` (the topic stays claimed for that machine: do not start the work again), `201 "local-fallback"` (claimed and started here), or a local start with `placementReason`. With it on, ANY topic-bound spawn into a topic another machine owns answers `409 topic-owned-elsewhere` with the owner and `ownerReachable`: message the conversation instead of starting a second session. The brief is copied to every pool machine as a `topic-spawn-brief` record and marked completed when the session ends.
