---
title: Local Verify: likely failures run first
---
Local Verify can run likely failures first in each lane of a change's verify. `monitoring.localVerify.likelyFailingFirst` is `off` (default), `on` or `alternate`, read per machine at the start. First parts contain the change's own test files, its previous failures and files that failed for other changes in the last seven days. A final failure can end a verify there; a clean first part runs the rest. A pass still requires every file of every lane to pass under the existing acceptance rules. Main verifies are unchanged. A failed first part's record names its failures; unrun files are stopped, not missing.

In `alternate`, the coordinator assigns each pull request once to with or without first parts, keeping that assignment across retries, heads and machines. There are no comparison runs. Each run machine writes one observation per verify to `logs/local-verify-first-part-observations.jsonl`, keeping 30 days and permanent trial markers. `GET /local-verify/first-part-report` works on every run machine, including a peer. Use `curl -H "Authorization: Bearer $AUTH" "http://localhost:{{port}}/local-verify/first-part-report?evaluate=1"` to open any new suspects without evaluating cost limits or advancing the daily clock. Tables cover every alternate verify in the current trial, including empty first parts and setup failures. After a stop, the ended trial remains visible until a new alternate verify starts. `POST /local-verify/first-part-report/new-trial` starts a fresh counting period without changing the setting; use it on the pilot machine when the other machine joins.

A file suspect has at least four final failures across at least three pull requests in one group and at most a third as many in the other, excluding the failing change's own test files. Both directions count. The table shows file exposure in each group; these counts are reasons to investigate, not proof. The coordinator also records confirmed red-main episodes, with commits since the last green and whether their passing verifies used first parts. Only a known first-part pass makes an episode a suspect; missing evidence is unknown.

The session operating the line owes each suspect a finding within three days. Investigate away from the active verify line. POST `/local-verify/first-part-finding` with `{"suspect":"<file path or red head>","finding":"explained","reason":"<at most 300 characters>"}` (optionally `trial` from the report). Findings are confirmed, explained or unknown. Unknown stays unresolved and may be replaced. OVERDUE means more than three days without a finding. An explained or confirmed file reopens after four additional different pull requests fail on it in that group, or when it qualifies in a later trial. Findings and episodes remain on the machine that wrote them, across coordinator moves.

Two daily cost evaluations in a row, each with new observations, switch this machine off and raise one attention item if either limit holds: passing median more than one minute higher with first parts (at least eight passes per group), or at least three lane/total deadline errors with first parts at more than twice the other group's rate (at least twenty verifies per group). A failed config write is reported and judged again the next day; no separate hold file overrides config. Suspects and red main never automatically switch the feature off. One confirmed case requires the operating session to stop both machines that hour; two unresolved file suspects across both machines require that session to pause both. An unknown red main or a file still failing changes requires a joint decision that day, recorded in the reason.

`GET /local-verify` shows the setting, likely-failing list and open/overdue counts. The list stays on the coordinator and travels with peer requests; an unreadable list is empty and rebuilds. The report states when observations are stale and does not claim proof that no verdict changed.
