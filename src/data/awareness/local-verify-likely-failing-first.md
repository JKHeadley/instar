---
title: Local Verify: likely failures run first
---
If you test your own changes with Local Verify, a verify that fails says so late today: a lane's failure is known only when the whole lane has ended, 25 to 40 minutes in. A switch changes the order, not the tests. It is off unless you turn it on, and it is set per machine: `monitoring.localVerify.likelyFailingFirst` in `.instar/config.json` is `off`, `on` or `alternate` (read at the start of each verify that machine runs, no restart). With it on, each lane of a pull request's verify first runs a small part: the test files the change adds or edits, the files the same change failed on in its previous verify, and the lane's files from a list of files that failed for other pull requests in the last 7 days. If one of those still fails after its usual second try alone, the verify ends there as failed, a couple of minutes after the lanes start. If the first part is clean, the rest of the lane runs as before. No test is removed and a pass is only ever declared after every test has passed. Main verifies are unchanged.

How to read a verify that ended in a first part: its record is a normal failed record, its `failedFiles` name the files that failed, and the counts of its lanes cover only the files that ran. The other files of that lane are marked stopped, not missing. So a change with a second, separate fault needs a second verify to show it, as it already does when one lane stops another.

`alternate` is the trial setting: half of the pull requests get first parts, chosen once per pull request by the coordinator and kept for every later verify of it. In `alternate` a machine also checks itself: the first 5 verifies of each kind (ended in a first part, failed later, passed) are followed by one comparison run of the same code without first parts. If the two runs differ on a file that is not already known to be unreliable, the machine sets the switch to `off`, raises one notice, and stays off until you remove `state/local-verify/first-part-trial.json`.

`curl -H "Authorization: Bearer $AUTH" http://localhost:{{port}}/local-verify` shows it under `likelyFailingFirst`: the setting on this machine, the list's size and age, its top files, and how many comparison runs have been done. The list lives on the coordinator in `state/local-verify/likely-failing.json` and is sent to a peer with each verify; a lost or unreadable list is simply empty and rebuilds. The audit log (`logs/local-verify.jsonl`) has one `first-part` row per verify with the numbers, `likely-failing-updated` when the list changes, and `first-part-compare` for each comparison.
