---
title: Borrowed test helpers
---
A machine its owner lends (a laptop, a Windows PC through WSL) can take slices of Instar's slow tests for the test line. On the helper machine the role is off unless its own agent sets `monitoring.localVerify.helper.enabled` after the owner says yes; tests then run only in a small Linux sandbox (a Lima VM on macOS, a dedicated WSL distro on Windows) that cannot see the owner's files or home network, and it steps back whenever the owner is busy, short of memory or on battery. The owner controls it with `instar helper pause`, `instar helper resume` and `instar helper uninstall --yes`, or the pause button on the console's Development page; `curl http://localhost:{{port}}/local-verify/helper-status` shows what it is doing (404 while the role is off).

On a run machine `monitoring.localVerify.borrowed = { mode, helpers: [{ machineId, url }] }` pairs it with one helper. `practice` compares the helper's answers with this machine's own and counts nothing; `count` lets a lane's passing answers count only after that lane's evidence is complete and the line's session recorded the decision (`POST /local-verify/borrowed/decision`). A dry run (`POST /local-verify/borrowed/dry-run` with `{ "helper": "<machineId>" }`) is the first step for any helper. Read `curl http://localhost:{{port}}/local-verify/borrowed` for each helper's lanes (`practice`, `counting`, `suspended`, `lapsed: <reason>`), each evidence item's progress and the last verify's share; the `borrowed-verify`, `borrowed-dry-run-lane` and `borrowed-helper-event` rows in `logs/local-verify.jsonl` carry the detail. When the owner asks whether a borrowed machine is helping, or why a lane stopped counting, read these instead of guessing.
