---
title: Local Verify hold and front controls
---
If you run a Local Verify test line, you can change what it does next without restarting the server, so no running test is thrown away. There are two controls. Hold keeps one pull request from being tested until you release it: use it when a change is known to be wrong or is waiting on something. Front makes one pull request the next change to start: use it when a change was promised or unblocks others. Front works even when the queue is full and the pull request is not in it yet. Neither control stops a test that is already running. Both are off until `monitoring.localVerify.queueControls` is set to `true` in `.instar/config.json` on the machine that runs the line (read live, no restart); until then the routes answer 404, and a machine that does not run the line answers 409.

```
curl -X POST -H "Authorization: Bearer $AUTH" -H 'Content-Type: application/json' http://localhost:{{port}}/local-verify/queue/hold -d '{"pr":123,"by":"your-session-name","reason":"waiting on PR 120","until":"2026-12-01T18:00:00Z","blockMerge":true}'
curl -X POST -H "Authorization: Bearer $AUTH" -H 'Content-Type: application/json' http://localhost:{{port}}/local-verify/queue/release -d '{"pr":123,"by":"your-session-name"}'
curl -X POST -H "Authorization: Bearer $AUTH" -H 'Content-Type: application/json' http://localhost:{{port}}/local-verify/queue/front -d '{"pr":124,"by":"your-session-name","reason":"unblocks 14 other changes"}'
curl -X POST -H "Authorization: Bearer $AUTH" -H 'Content-Type: application/json' http://localhost:{{port}}/local-verify/queue/unfront -d '{"pr":124,"by":"your-session-name"}'
```

`by` (who is asking) is required on all four, and `reason` on hold and front; both go to the audit log. A hold stops testing, not merging: a change that already passed could still merge. Add `"blockMerge": true` to mean "do not test and do not merge": the same request then also sets the merge-side hold marker, and the answer says which of the two were applied. A release does not remove that marker. A released change comes back with the waiting time it had earned. A hold lasts until you release it; `until` is the date you expect to release by, and one reminder is raised when a hold passes it, or after 24 hours with none. The holds live on the machine that runs the line: if another machine takes the line over, it starts with none. Set `monitoring.localVerify.operatorSession` to the name of the session that operates the line, so the old machine sends that session one message listing the held and fronted changes to set again; without it the list goes to the attention queue. At most 3 changes can be fronted at once, and a check of the shared code that is due still goes first. `curl -H "Authorization: Bearer $AUTH" http://localhost:{{port}}/local-verify` lists held and fronted changes under `operator`. Do not edit the queue file or restart the server to reorder the line any more.
