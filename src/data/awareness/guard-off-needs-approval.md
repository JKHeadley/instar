---
title: Switching a guard off needs the owner's approval
---
Switching a guard off through the settings API with only the API token is a trust loosening, like widening external operations or evolution autonomy. So is weakening one that stays on: dry run, an input guard check turned off or its action lowered, or the response review set to observe-only. A guard here means anything `GET /guards` lists (every `monitoring.<name>.enabled` switch and the guard manifest), plus the input guard and the response review. `PATCH /config` answers `403 operator-approval-required` with the reasons in `raises`, and nothing is written. To ask the owner, open `POST /trust/requests` with `{"change":{"kind":"config-patch","patch":<the same body>}}`: the owner gets an approval card, and on their yes the change is made. A feature switch does this for you, from any path, including the owner's phone, where the card is one tap once the phone is set up to approve. A single-path write, such as a commitment's config correction, is refused the same way. Switching a guard on, and tuning one that stays on, need no approval. The self-action governor's emergency switch keeps its separate dashboard PIN check.
