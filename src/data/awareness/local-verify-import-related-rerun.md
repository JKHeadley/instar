---
title: Local Verify second try for a failed test that imports changed code
---
If you test your own changes with Local Verify, a pull request that edits widely imported code gets no second try for a failed test file today: any file that imports a changed file is refused its solo re-run, so a known flaky test anywhere fails the whole verify. A switch changes that for one narrow case. It is off unless you turn it on: set `monitoring.localVerify.importRelatedRerun` to `true` in `.instar/config.json` on the coordinator (read live at each run start, no restart), and on a peer verifier too if you want it applied to runs handed to that peer. With it on, such a file is re-run alone three times, and cleared only if all three pass, when every test that failed in it has already failed and then passed alone, by the same full name, on a main verify this machine ran itself in the last 7 days. A test that is not on that list, a file the pull request edited, a file-level error, a failed name that occurs twice in the file, or a file whose list of test names differs from the one main saw: no second try, exactly as before. The evidence starts empty and fills as tests flake on main, so expect little effect on the first day and the full effect after about a week. Every clear is written to the audit log with the test names, when main showed each one flaky, and both failure lines. `curl -H "Authorization: Bearer $AUTH" http://localhost:{{port}}/local-verify` shows a cleared file under the record's `flakyRetried` with `importRelated: true`. To review the rule after a week, run `node scripts/local-verify-import-related-review.mjs` on each machine: it only reads the audit log and prints, per cleared file, how often it failed on main before and after. Setting the key back to `false` returns every run that starts afterwards to the old rule.
