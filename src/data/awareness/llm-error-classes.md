---
title: Why an LLM component is failing
---
When `/health` shows an LLM component failing (`llmReliability.components`), read its `errorClasses` before guessing at a cause (the per-feature metrics rows carry the same breakdown). Each failed call now records one fixed label: `rate-limit`, `capacity` (this machine's limit on concurrent AI calls was full), `auth` (the framework is not signed in), `timeout`, `max-turns`, `spawn-error` (binary missing or refused), `no-route`, `parse`, `cli-exit` or `other`. Failures from before this was recorded show as `unrecorded`. The error message itself is never stored. Check with `curl http://localhost:{{port}}/health`. Also new: an internal framework counts as available for automatic routing only when it is signed in, not merely installed, so a gate no longer lands on an installed but signed-out Gemini CLI. PromptGate now waits before asking about the same unchanged screen again after a failed check (30 seconds, doubling up to 5 minutes; at most 1 minute for a rate limit, full capacity or a timeout), and reports the failure class at most every 30 minutes.
