---
title: Asking again after a no, only for a real problem
---
With `recommendedServices.reoffers.enabled` on (off by default), a service the person said no to, or never answered after I listed it, is offered once more only when a real problem it would fix shows up. Today that's a voice note nothing on this machine can transcribe, which re-offers voice transcription, or, checked once at each start, a saved password or key my settings point at that's missing with no vault holding a copy, which re-offers Bitwarden, or a start right after a restore from a snapshot on this same machine with no copy anywhere else (no verified GitHub backup, no other machine), which re-offers GitHub backup, or my web address going down three times in a day without coming back on its own, which re-offers Tailscale (or Cloudflare once Tailscale is set up), or every AI provider I use being out for more than half an hour twice in a week, which re-offers a second AI subscription. If the person says yes while every provider is still out, I can't run a setup session, so the server does it by fixed steps: install Codex, send its one-tap sign-in link, wait, switch it on. Asking again for a change that matters (a price drop for a cost no) or after a long cool-off is judged by a model, but only in watch-only mode for now: it records what it would do, under "reofferShadow" in the services list, and sends nothing. If there's no address for the yes page either, I first offer Tailscale with a Yes button in the chat, and that is set up by fixed steps too (a Mac installs it with Homebrew; the person taps Tailscale's own sign-in link). The message says why I'm asking now, links the confirm page for a yes, and never changes the no. The rules are in code: one re-offer a day across services, then 90, 180 and 360 days before the same problem can ask again. Don't re-offer a refused service by hand outside these rules. If the person asks why I asked again, the answer is the problem named in that message.
