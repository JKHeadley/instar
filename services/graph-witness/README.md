# Conversations witness runtime

Conversations uses the same durable custody engine on enrolled owned machines by default. No external service, account or purchase is required. A separately hosted external copy is optional. Neither deployment enables graph routes or certifies the storage increment by itself. A copy on the recording machine is device-local durability; it must never be described as an independent machine-loss recovery copy. The deployment instructions below describe the optional external server, followed by the embedded owned-host composition.

The production entry is `services/graph-witness/start.mjs`; it imports the compiled `dist/server/graphWitnessServer.js`. `GRAPH_WITNESS_CONFIG_FILE` names a secret-mounted JSON configuration file. `PORT` defaults to 8094. The process listens on all interfaces and requires a firewall plus an HTTPS reverse proxy; production clients accept only HTTPS and reject redirects or credentials embedded in a URL.

Optional external-server configuration has `databasePath`, `witnessId`, `failureDomain`, independent Ed25519 `signingPrivateKey`, `installedFailureDomains`, and `enrollments`. Each enrollment is keyed by agent ID and contains that agent's pinned owner-root Ed25519 `ownerPublicKey` and a strong unique `bearerToken`. The witness does not receive the owner private key or any plaintext source decryption key. Each installed member needs its registered Ed25519 signing key and a separately registered X25519 sealing key.

Mount the persistent data directory with restrictive permissions and ownership matching the runtime's `node` user (uid 1000 in the Docker image). SQLite uses WAL and synchronous FULL; the database file is mode 0600. A new empty disk must never silently replace a lost witness disk under the old identity. The Dockerfile is built with the repository root as its context. Its container build still requires verification on the selected deployment host.

Initial enrollment posts an owner-signed membership epoch 1 to `/v1/agents/:agentId/membership`. Later epochs must increment by one and name the previous signed membership hash. Mutations require authenticated per-agent transport, exact signed installed lease evidence, and writer packet/action signatures; bearer possession alone cannot prepare, cancel, or erase an operation. Before returning a witness preparation proof, the exact original writer packet signature is fsynced with the immutable packet; operation/recovery responses bind its hash in the signed state proof. Clients verify it with the owner-signed historical writer membership, never re-sign it as the successor. Source encryption uses the common recovery envelope containing the exact original core and authorization plus application bytes, so a surviving member can reconstruct from witness-only ciphertext after the accepting writer is lost. Prototype rows lacking an original signature fail visibly as missing evidence. A witness preparation proof is separate from the final certificate. Final graph certification requires durable receipts from every installed member, followed by separate receipts proving every member persisted the final certificate.

Cancellation first records a signed, durable decision that races atomically with commit. It advances the immutable source sequence only after an all-member cancellation certificate. Erasure records a durable fence before suppressing ciphertext and sealed envelopes. `checkpointErasure` performs and verifies WAL truncation. External backup verification stays false unless an independently pinned infrastructure auditor supplies an exact request-bound signed provider-policy attestation. Optional enrollment/client `backupPolicyAuditorPublicKey` pins this separate Ed25519 public key. POST `/backup-erasure-attestation` accepts only that signature, bound to the signed erasure proof, managed failure domain, provider resource hash and sealed evidence-artifact hash, and a validity period of at most 24 hours. Clients verify it independently. A valid signature records the auditor’s attestation; it does not replace the actual provider read/purge ceremony. SQL suppression and WAL cleanup do not prove provider snapshot erasure. Provider backups must either be verified absent or participate in an independently verified erasure and recovery policy. Every signed erasure request survives inventory/replacement, including overlapping and completely redundant requests. Per-operation historical proof identity is retained even when another valid request covers the same bundle. Request identities remain available for checkpoint and provider-policy evidence after import. Optional bootstrap `backupAttestations` archives existing provider evidence under its exact signed hash and separately pinned `historicalBackupPolicyAuditorPublicKeys`; historical evidence never certifies the replacement failure domain. A stale snapshot restore must not bypass the retained erasure/fence chain.

Old packets remain immutable. POST `/adopt-pending` supports ordinary lease renewal/failover with unchanged installed membership and no owner reapproval, using a fresh current native lease plus signed source/head/dependency revalidation and separate encrypted-envelope rewrap. POST `/recover-pending` activates an owner-signed membership transition only after every new member has fsynced and reloaded the exact source manifest. The owner plan binds every pending adoption/refusal, the highest certified tip and higher fence. The service signs a retained activation certificate and immutable adoption sidecars. GET `/recovery-manifest` supplies full inventory; POST `/inventory` signs a caller-random freshness challenge, full terminal manifest and all erasure proofs. POST `/bootstrap` supports empty-disk replacement: configuration pins `historicalWitnessPublicKeys` by prior witness ID, while an additional owner signature over `graphWitnessBootstrapPayload` binds the exact imported immutable proofs, ciphertext bundles, erasures, membership chain and prior fence. The complete certified chain, every historical signature, ciphertext hash and manifest must verify before the higher-fence recovery transition can activate. Every new installed member must already have staged and fsynced the exact source. The required owner `rewrapInventoryHash` and every new-member transfer receipt bind the same canonical sorted full operation-key/envelope-hash inventory (absent envelopes use `canonicalHash(null)`), including historical certified records. Pending and historical sidecars are validated against that exact hash before activation; a different otherwise valid envelope cannot be substituted after members sign. Historical envelopes remain separately erasable. Original historical certificates and authorization are unchanged; a new member receives an activation/materialization proof and never invents an old-epoch source receipt. A common proof context is stored once per epoch and fetched through signed bounded pages; per-operation responses carry only a hash reference. `recover` hydrates the existing source materialization proof outside the immutable packet. Import and activation are one SQLite transaction, with durable idempotency for interrupted replies. HTTP input and output remain bounded to 3 MB. `GraphWitnessClient.bootstrap` uses owner-signed `/bootstrap-transfers`: each membership, operation/ciphertext bundle, erasure request, manifest entry, revalidation and transfer receipt is individually verified and durably staged before final activation. The owner signature binds the exact complete array hashes; finish refuses missing, corrupted or mismatched rows. Ciphertext operation history is hashed and imported through bounded SQLite row reads, never concatenated in memory. Transfer IDs derive from the signed payload, so retries resume the same durable transfer after restart. No new membership is visible before final atomic import/activation. The current manifest contract bounds history to 20,000 rows and pending outcomes to 512; imported operation count now matches the manifest bound. `maxBootstrapStagingBytes` configures a global durable staging quota (default 64 GiB); exhaustion refuses further chunks without discarding admitted history. Owner-signed abort permanently fences an incomplete transfer. Completed or aborted staging suppresses actual ciphertext/rewrap bodies while retaining their hashes; normal erasure/WAL checkpoint purges recoverable copies. Inventory uses challenge-bound signed snapshot headers/pages with exact full inventory hashes; snapshots occupy a bounded eight-slot transport cache (global 4 GiB), while canonical operation/erasure history remains untouched. An overwritten snapshot fails verification and requires a fresh challenge, never a partial readiness grant. No old signing key or plaintext source key is imported. Immutable adoption and commit/cancellation certificates contain only the rewrap hash; actual sealed envelopes live exclusively in a separate erasable witness/source sidecar. Erasure suppresses that sidecar before checkpoint, leaving the original historical signature verifiable. Indexed per-bundle bindings cover key-bearing rows in every unfinished transfer, not only the activated plan. Erasure nulls all matching staged ciphertext/envelope bodies, marks affected unfinished plans stale, and fences subsequent chunks/finalization; checkpoint repeats that indexed purge before reporting local WAL completion. Keyless, valid owner erasure manifests remain admissible. Existing prototype staging receives a one-time binding-index backfill on upgrade; normal erasure never walks unrelated staged JSON history. A stale restored old witness remains excluded by the installed membership/native lease authority; production coordinator enforcement of that authority is required. `GraphWitnessRecoveryCoordinator.revalidate(eventId)` derives current subject heads/dependencies from the actual source `certifiedUnion(reader,dropped)`, validates the exact original core/authorization/signatures, runs the real graph reducer, checks the current native lease and `WriteAdmission`, and actually decrypts before rewrapping. It checks effort existence, current observed heads, front-door/cycle guards and the nearest effort scope against actual `ScopeVerifier` Telegram topic bindings and full configured chat ID. Unknown Slack/app bindings refuse until their authoritative binding seam exists. Verified Saving sources are excluded only from certified-state partial accounting; malformed, conflicted, terminal and quarantined records cannot be hidden. The production caller must serialize semantic revalidation and adoption with the writer’s graph mutations; integration wiring and independent review are still required. NEW source writes must also pass the actual installed `WriteAdmission` seam; the witness bridge is a verifier of retained native `FencedLease` evidence, not a second election authority.

Tests cover member-only encrypted recovery, exact signatures, all-member source and final-certificate receipts, original lease fencing, immutable idempotency, commit/cancel serialization, erased-payload replay rejection, real HTTP transport, and hard process death/restart through the shipped production entry. These local proofs do not prove managed remote independence, provider backup erasure, or an enabled product release.

Permanent semantic custody is separate from erasable application custody. Every new packet requires `controlHash`, computed before its original writer signature over the exact strict capsule `{v:1,coreType,core,authorizationProof}`. The witness validates actual semantic and historical authority schemas and persists the capsule transactionally before source preparation; recovery returns it after application ciphertext erasure. Capsules contain opaque relationship/control facts and historical public verification material only, with no application title, salt, transcript, dispatch message, secret, or key envelope. Experimental packets missing this binding are refused; no migration invents original authority.

Priority erasure may precede source preparation. `/erased-control` accepts only the exact historically authenticated frozen packet/capsule under current native admission and an existing matching signed logical tombstone. It enforces the same closed witnessed prefix, preserves an existing commit, and stores a terminal-only row without ciphertext. That row has `prepareProof:null` and a separate `GraphWitnessErasedControlProof` in the `graph-witness-erased-control-v1` signature domain; it never grants Saved/source-custody authority. Only cancellation-phase durable member receipts and final terminal-certificate persistence may advance this erased sequence. A later source prepare remains forbidden. Original packets, hashes and queue sequences are never rewritten to bridge a gap.

Priority captured-data erasure uses `GraphFleetErasureCoordinator` and the runtime's authenticated `erase-forward`/`erase-purge` peer actions. The owner route resolves the real owner before `acceptOwner`; external bodies never supply owner authority. A registered ingress machine signs only agent-local principal, method, request identity, typed target and acceptance time. Grant/token material is not retained. Local serving denial and inspected source/intake/transfer/capture-cache purge precede W or ordinary graph work. The opaque ingress ledger publishes by fsynced temporary plus exclusive link; complete signed scratch can recover, torn slots remain explicit debt and cannot block other requests. Runtime shutdown stops new erasure jobs and drains prepublication work before releasing its lifetime lock.

W retains signed owner ingress and every historical installed-key deletion obligation. A later membership transition does not remove retired-copy debt. Replacement imports retain signed tombstones as debt even when original ingress is unavailable; that missing ingress remains `null`, never a fabricated owner grant. Plans, recipient pages and signed member-purge receipts use bounded HTTP pages, preserving the existing parser cap. A signed member receipt covers only the four live graph-custody engines after actual disk inspection. W physical purge requires a fresh challenge-bound witness signature; an unsigned `walPurged` flag grants nothing.

`liveGraphStoresPurged` and `memberBackupDebt` distinguish live-store deletion from installed-machine backups. Installed Time Machine/APFS/snapshot/other backup policies are currently **unknown**. Every historical recipient therefore retains explicit unknown backup debt and `fleetComplete` remains false, even with valid W-domain provider backup evidence. A witness backup auditor cannot certify Mac backup deletion. No global backup settings or host snapshots are changed by this flow. The scope excludes original legacy transcripts, externally sent platform copies and phone downloads; it does not claim those were erased. These controls still require independent review and the complete increment-A release proofs before feature exposure.

Membership activation uploads also use bounded durable transport: `GraphWitnessClient.recoverPending` sends a strict `/recovery-uploads` header, individually verified manifest/revalidation/receipt/envelope rows, then an atomic finish. Incomplete or changed chunks cannot activate membership. A restarted client reuses the frozen row hashes, including after a successful activation whose reply was lost; replay never restores the erased staging body. Recovery uploads share bootstrap erasure indexes, quota and abort fences.

A second or later witness replacement must archive every prior actual activation and its common hash-only recovery context. `recoveryArchive()` fetches the verified owner/all-member/witness activation chain and signed context pages; the bootstrap owner signature binds the complete archive hash. Activation/context pages stay below the existing HTTP cap. Missing historical activation evidence refuses replacement rather than treating a proposed owner roster as an active role. Old contexts contain hashes and native public lease proofs, never sealed envelopes. They remain available to verify old certified materialization and negative custody after another replacement.

A pinned witness key alone cannot authorize irreversible erasure. `erasureAuthority(proof)` fetches an endorsement of the exact ledger tombstone from the currently activated witness, together with its actual owner-signed membership and complete activation chain. `verifyGraphErasureAuthority` anchors that chain in the installed profile. New unseen erasures require this authority before any source denial/purge; a future merely proposed witness or a signed proof absent from the actual witness ledger is refused. Persisted verified historical fences retain their role archive as negative facts across offline restarts. This role proof does not certify remote failure-domain independence or backup deletion.

New immutable operation admission also respects the recovery manifest population bound: every operation state, including canceled and erased-control history, counts toward the shared 20,000-entry ceiling. An optional `maxHistoryEntries` resource budget may only lower that ceiling (1 through the shared bound); a larger or invalid budget fails configuration. Existing exact idempotent operations remain retryable at capacity. Separate priority logical-erasure tombstones are not restricted by this operation admission budget. This witness guard does not itself prove earlier source/intake reservation capacity; those custody ingress checks remain part of the complete release proof.

## Owned-machine composition

`GraphCustodyProfile` is a strict owner-signed deployment identity bound to the full membership context, custody role public key, exact host signing identity and failure domain. `mode: owned-machine` permits the engine on its named enrolled machine; `mode: external` does not. Profiles cannot be relabeled by a client boolean, hostname or transport choice. Legacy profile-less certificates retain their historical external interpretation; they do not authorize an owned-host deployment. The custody role key is distinct from member and owner signing keys.

`GraphWitnessDispatcher` supplies a single endpoint table used by both HTTP routes and the in-process adapter. `createInProcessGraphCustodyTransport` invokes that table without opening a socket. `createPeerGraphCustodyTransport` uses the existing registered signed-peer request channel and still runs every response through the same GraphWitnessClient cryptographic verifiers. Input/output remain bounded to3MiB; no production test-loopback exception is used. The runtime host handler checks the actual signed host/profile before dispatch. A transport object never grants owner or writer authority.

`openPublishedOwnedGraphCustody` consumes the authenticated boot owner's `GraphCustodyBootstrapPublication` and actual MachineIdentityManager/IdentityStore. It derives the active installed roster, checks the pinned owner/profile/native admission and exact role key, then calls GraphCustodyBootstrapStore.openDatabase. Every installed member's signed pin is required before first canonical genesis. The one-shot durable database claim precedes SQLite creation. The engine lives at `stateDir/conversation-graph/custody.sqlite`; publication and pins live under `stateDir/conversation-graph/bootstrap/<agent-hash>/`. A missing acknowledged database or interrupted prior claim remains recovery quarantine, never a blank replacement. Normal reopen verifies the original genesis and configured current membership. This is not proof of old-backup freshness; runtime tail/erasure reconciliation is still required.

The factory does not create a human owner root or decide that a native lease constitutes owner consent. Root publication comes only from the actual authenticated owner-request seam; the native lease serializes it. Owner/custody private keys remain in SecretStore and are never copied into this database or public profile. Optional external hosting does not gate healthy standalone local operation.

A prepare signature alone describes actual custody on the signed host. Local recording, independently copied custody and all-installed shared commitment remain distinct outcomes. Unknown/sleeping members retain named pending work; no missing source or certificate receipt is manufactured. Immediate local hiding and historical member backup debt remain unchanged. Production owner-route/default-boot/queued-intent integration requires its own end-to-end release evidence; the earlier external-profile tests do not prove those new defaults.

Owned recovery trust boundary: installed members retain owner-signed, recipient-sealed owner-control recovery envelopes separately from application data. Bootstrap pins bind actual per-member fsync/reload/decryption receipts. The custody role private key is never distributed. Replacement must preserve the original owner root and use a new role key under a verified activation; missing authority material does not authorize a new genesis. These recovery ceremonies remain under implementation and are not a release/readiness claim.

Restore checks compare a restored local copy against a current surviving owned custody/peer frontier. Missing acknowledged databases, interrupted creation claims, mismatched pins, and known managed restores must remain quarantined before private serving. There is no software oracle for complete rollback of every authority, disk and sealing key together. A single-machine complete state/keychain rollback is not advertised as erasure-safe; unknown member backups remain explicit debt and prevent fleet-complete erasure. No third-party account, purchase, backup deletion or host-setting change is required or implied by this limitation. Independent privacy review is required before enabling the feature.
