## What Changed

A phone notification for an agent reply in an app conversation said only "New reply". It can now show what the reply says (docs/specs/mobile-native-chat-media.md §4.11, increment 4).

- The push payload for a reply carries the reply's message id and machine (never its text). Apple still only sees "New reply".
- New route `GET /mobile/chat/app/:conversationKey/preview/:messageId` answers `{title, body}`: the reply's first 100 characters, or "sent a photo" / "sent a video" / "sent a voice message" / "sent a file: <name>" / "sent N files", then the caption. Open to the paired device, its notification read token (which until now opened only the attention title), and the agent's own token. A deleted conversation, an operator message or a reply not yet copied to that machine answers 404, and the phone keeps "New reply".
- Peer push triggers carry the message id too.

- Telegram files in the Instar iPhone app (docs/specs/mobile-native-chat-media.md §4.9, Telegram half). When files in app conversations are on, every photo, document and voice note that arrives in a Telegram topic is also copied into the app's file store and recorded as a durable event that is copied to the agent's other machines.
- The app's view of a Telegram conversation now shows those files: a phone reading a topic's history gets each recorded file as an `attachments` entry, and can download it with `GET /mobile/media/<hash>?ref=telegram:<topicId>`. Only a file recorded in that topic can be downloaded through that topic.
- A phone never sees a server file path any more: history rows (and the conversation list's preview line) show `[photo]`, `[file: <name>]` or `[voice note]` instead of the path, whether or not the file was recorded.
- The copy uses the same checks as the agent's reply files: the store's size limit, the disk-space floor, the 50 MiB file limit, a hash, and the file type read from its bytes. A voice note is copied before the Telegram handler deletes its download. If the copy fails (store full, disk low), the session still gets the Telegram message exactly as before and the failure is reported.
- The session's Telegram messages, the agent's Bearer reads of topic history, and the app conversation routes are unchanged.

- The Plans page's "In the way" list shows a conversation's name where a line mentioned it by topic number.

- `GET /machine-maintenance?scope=pool` and `GET /machine-maintenance/lock-state?scope=pool`: one call from any machine returns every online machine's watch-only maintenance state (uptime, last practice run, holds, browser care) or lock reading, each tagged with `machineId` and `machineNickname`. A machine that is dark, offline, on an older version without the route, or unreachable is listed under `pool.failed` with a normalized reason, never a 500 and never a peer address or token. Read-only: the view carries `authority: "none"`, `canRestart: false`, `canStopWork: false`. Peer fetches go through the shared pool poll cache when it is on.
- The console Machines page now shows each machine's restart-care line on that machine's own card, and names the machines it could not read.
- A short awareness section reaches fresh agents and existing agents through the CLAUDE.md migration.

`npm run release:local` refuses while any publish.yml run is unfinished. It queried GitHub by status (queued, in_progress, waiting, requested, action_required), which never returns a run GitHub marks `pending` while it waits behind another run in `concurrency: publish`. It now also lists the 100 most recent publish.yml runs unfiltered and counts every run not `completed`, so a pending run is named among the runs to cancel. A failed query is still unknown, which stops a real release.

- A pull request aimed at a feature branch (a "stacked" PR) can no longer be merged by the merge tooling: `scripts/safe-merge.mjs` refuses any base other than main (`refused:non-main-base`) before any other step, on every path including `--auto`. A new `stacked-pr-guard` workflow turns such a PR's GitHub badge red with a "retarget to main" instruction, so it no longer shows as clean. The green-PR watcher skips stacked PRs (`non-main-base`) and its stuck-red alarm ignores them. Closes ACT-053.
- Every job in `.github/workflows/ci.yml` now declares `timeout-minutes` (unit 60, integration 50, e2e 70, everything else 15), sized from the slowest of 79 recent runs, so a hung job fails within about an hour instead of GitHub's 6-hour default. Closes ACT-059.

## What to Tell Your User

Once your iPhone app updates, a notification for my reply shows the start of what I said, or "sent a photo", instead of just "New reply". The text goes from me to your phone directly; Apple never sees it.

Photos, documents and voice notes you send in a Telegram topic now show up in that conversation in the Instar app, and you can open them there, on any of my machines. This only works while files in app conversations are switched on. The app needs its next update to display them.

The Plans page names your conversations instead of showing their internal numbers.

You can now ask me about restart care or screen locks for all your machines at once, not only the one I am on. Each answer names the machine, and if one of them cannot be read I say which one and why instead of guessing. The Machines page in the console shows the same per machine. It is still watch-only: nothing restarts or closes.

Nothing changes for you day to day. If you develop Instar itself: a pull request aimed at another pull request's branch now shows a red "retarget to main" check and the merge tooling will not merge it there. Merge the one underneath into main first, then point this one at main.

## Evidence

Unit tests for the preview phrases and the payload; integration test for the route through the real device authenticator (signed device, read token, wrong token, read token refused on history, agent token, unknown message, bad key). Existing push tests updated for the message id.

- Unit tests: the new event kind's validator (refuses an app conversation key, a mismatched id, a bad platform id, an empty file list), the replicated wire round trip, the index (a reference for downloads and the store size, never a chat message, appended once, rebuilt from the files), the copy (blob then event, type from the bytes, a duplicate, store full and disk floor refusals that hold nothing), the path replacement, and the Telegram adapter hook (a voice note is handed over while its download still exists; a throwing hook never stops delivery; no hook means no copy).
- Integration tests through the real device authenticator: a recorded photo and document appear as attachments with no path in the text; a row from before the feature also has no path; the Bearer read is unchanged; a download with `ref=telegram:42` serves the bytes; a hash recorded in another topic, an unknown hash and a bad ref answer 404; a Bearer token cannot download; the same message twice keeps one event; media off answers 503.
- End-to-end test: an AgentServer on a development agent with a real TelegramAdapter wires the hook; a Telegram photo is recorded on the production path, a phone paired through the production path sees it in the topic's history and downloads it. A fleet agent sets no hook.

- Live scan of every dashboard page found one raw topic number, on Plans; on the preview with this change it shows the conversation's name. Unit test covers known and unknown numbers.

- Unit tests cover the merge (this machine, an answering peer, a failed peer, an older peer without the route, a dark self, id-shaped names) and every failure reason, and check no address, token or raw error text appears.
- An integration test serves both routes through the real server with real peer HTTP servers: an answering peer, an older peer (404), a dark peer (503) and a closed port.
- Console model tests cover per-machine lines and an older server that ignores the pool scope.
