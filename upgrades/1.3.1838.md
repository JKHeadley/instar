## What Changed

The dashboard scoped-session feature (SEC-002b, still switched off) gives your browser a short-lived, revocable pass instead of the permanent master key when you unlock with your PIN. But the **phone-tap** sign-in (the owner-phone "console ticket") was missed — it kept handing back the permanent key even with the feature on, a second door outside the safer model. This closes that gap: when the feature is on, the phone-tap sign-in now mints the **same short-lived `dst_` pass** the PIN unlock does.

Ships **dark** (`security.dashboardScopedToken.enabled` default false); with it off, the console sign-in returns the master token exactly as before (byte-identical).

The Chief of Staff's done-item evaluator moved from `server.ts` into `ChiefOfStaffEvidence.buildDoneItemEvaluator` and gained the second deterministic form from the approved spec (docs/specs/chief-of-staff-topic.md §1.3): `PR owner/repo#N merged`. It reads the PR through the agent's authenticated GitHub access, only for a repo the project links, and passes only when the PR merged into that repo's default branch. Anything unreadable or unlinked is `unknown`, never `fail`. The existing `page <url> contains "<text>"` form behaves as before. A Feature notes entry tells agents to write done items in the checkable forms and to fill linked repos.

The feedback executor's independent review now leaves out the two files the executor itself adds to each fix after the confined session finishes: its decision-audit record under `.instar/instar-dev-decisions/` and its release note under `upgrades/next/`. A file is left out only when it is a new file at this fix's exact paths and its bytes equal what the executor writes, rebuilt for that attempt. Any edit made after publishing keeps it in view. The review prompt names the omitted files in trusted text. Without this, the review rule that treats any `.instar/` edit as a finding refused every executor PR after #3209 (first seen on PR 3235). Rule 2 still applies to every other path, and the CODEOWNERS check still reads the full file list.

Test only. The last case in `tests/e2e/job-launch-lifecycle.test.ts` (added on 2026-11-16 to prove the scheduler's memory gate still refuses a job) asserted that the mock binary's call log held exactly one launch line. The mock logs every call it receives, and on a loaded machine a second call from the first job landed in that log, so the case failed on a correct product (Local Verify run of PR 3227 on the Mac Studio, 2026-11-16T11:54Z: two launch lines, neither from the refused job). The case now asks tmux whether a session exists for the refused job's own slug. The other assertions of the case are unchanged: the 409 refusal, the single `memory-pressure` skip record, the skip event text and the absence of a run row.

The encrypted secret store addresses secrets by dotted names (for example `telegram.token`). Names reach it from several callers, and a name could contain a segment that refers to JavaScript's built-in object machinery rather than to stored data. Following such a segment touched shared process state instead of the vault's own contents, and reading a built-in name returned a JavaScript function instead of "no such secret".

The store (`src/core/SecretStore.ts`) now refuses a write whose name contains `__proto__`, `prototype` or `constructor` as a segment, reads such names and other inherited names as absent, treats a delete of one as a no-op, and follows only the vault's own stored keys. A write through a stored `null` or plain value now replaces it with a nested group instead of throwing. Found by the standing security review; triaged hardening.

## What to Tell Your User

Nothing changes yet — this ships switched off, like the feature it completes. When that feature is turned on (after its full live dashboard test), signing in to your dashboard by tapping on your paired phone will give your browser the same short-lived, revocable pass that typing your PIN does — instead of a permanent key. Both doors behave the same way, so there's no permanent key left in your browser from either path.

When I set up a project for you to track, I can now write its finish line so I can check it myself: "this pull request merged" is now something I verify directly with GitHub. Projects written that way stop showing "not known yet" once their work lands. If you'd like, I can rewrite the finish lines of your existing projects into that form; you'd approve each one before it changes.

Automatic fixes for reported problems were being turned down by their own safety review because of a record the system adds itself. That is fixed, so good fixes can now be approved.

Nothing changes for you. This is a behind-the-scenes hardening of how your agent stores its passwords and keys. No real secret uses the refused names, so every existing secret reads and saves exactly as before.

## Summary of New Capabilities

- The owner-phone console-ticket redeem returns a scoped `dst_` session token (not the master) when `security.dashboardScopedToken.enabled` is on — mirroring `/dashboard/unlock`, so every dashboard sign-in path uses the short-lived, revocable pass.
- Dark-gated: returns the master token byte-identically when the feature is off.

- Chief of Staff done items of the form `PR owner/repo#N merged` are checked automatically against GitHub (linked repos only).

None. This is a fix to the existing feedback executor.

- Hardened dotted key-path handling in the secret store: reserved segments are refused on write and read as absent; only own stored keys are followed.
