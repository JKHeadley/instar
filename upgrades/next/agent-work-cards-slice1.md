# Every request you make becomes a card the agent carries, asking nothing (slice 1)

<!-- bump: minor -->

## What Changed

Slice 1 of docs/specs/agent-work-cards-default.md (the request-to-card core; owners, blocker links and the app screens are later slices):

- **A recorded request writes its own card.** `POST /commitments` from an operator conversation (a Telegram topic, a Slack thread or an app conversation) now writes a Work Board card for the request on the lease holder, with an id derived from the commitment's replicated identity `(originMachineId, id)`, so a retry, the sweep, or any machine that sees the replicated commitment writes the same card and never a second one. The response carries the derived `cardId` and `cardPending: true`; the card is written after the response is sent. A paced sweep on the pickup controller's tick writes any card the first write did not land (`daily-card-ceiling`, `store-unavailable`, `rate-limited`), records a terminal reason where none can be written (`not-operator-conversation`, `backfill-skipped-stale`), repairs a card's `refs`, and on its first run for a team writes one `enabled-at` record and backfills open requests younger than `requestCards.backfillMaxAgeDays` (uncounted toward the daily ceiling). `GET /commitments?cardPending=1` lists the requests whose card is not written yet.
- **The team owner's own request is the yes.** The requester is read from the durable message row at recording time, on the recording machine, per adapter arm (a native Telegram row with `forwarded: false` from the owner id or a linked member; an app or phone-mirrored row through the device record held on this machine; Slack by the configured id with no bot marker). A session binding never names a requester. When the owner asked, the card carries approval from the request under either board policy: its `need` is the owner's whole message, locked (`need-locked-to-request`), shown as "Asked: …" with "asked N days ago", "recorded in the agent's words" when the agent's `userRequest` differed, and "changed since asked" when the agent edited the title or items. A flip to outward or to a person carrier returns the ordinary approval rule; a withdrawal tap revokes it.
- **Agent-work cards ask nothing.** An agent-written card with `outward: false`, carried by the agent, with no owner-confirms item needs neither `recommendation` nor `whyYou`; both are required again on any record that makes it an ask (outward, a person carrier, an owner-confirms item, a `waiting-on` a person). `outward` now defaults to `false` for the agent and `true` for a person. The gate-only fields (`requester`, `requestTextHash`, `recordedAsHash`, `pickupHold`) are accepted only from the in-process gate (`gate-only-field` otherwise); `by.isOwner` is stamped by the server.
- **`not-started`, one aggregated row.** Under the strict policy an agent-work card without approval (a member's, an unverified sender's, or the agent's own) reads `not-started`: it is in no one's Waiting-on-you lane, refuses the agent's `evidence`, `note` and `claimed-done` with `409 not-started` (counted for the graduation record), and the team's unstarted cards appear in Needs-you as ONE row, "N internal cards are waiting for your approval or board setting", with `boardJson.notStartedCards { count, cardIds, shown[], more }`. Two owner controls (console PIN): `POST /work-board/not-started/approve` (one signed approve per shown card, `stale-card` per card) and `POST /work-board/not-started/approve-and-widen` (the same, then the `board-policy` trust request is raised with the record it rests on, and the response says where to answer it or why it could not be raised).
- **Progress notes from where the work happens.** `POST /work-board/cards/:id/notes { text }` from a Bearer session or a scoped session bound to the card's conversation OR the conversation that recorded the request (a Telegram topic session). The note lands in the card's conversation at once as an agent-role `work-board-note` event ("Work board: the agent noted: …", the writer's binding recorded); the replicated-journal emit is reserved before the durable append (`appendWithEmit`), so `503 rate-limited` means nothing was written anywhere. The lease holder writes a `note` pointer record per event on its tick (paced `noteDrainPerTick`, reconciled by event id, seeded by one bounded scan at boot or takeover), coalescing to one pointer per `noteCoalesceMinutes` above `maxNotesPerCardPerDay`. A note counts as agent activity for the quiet clock and is never evidence. The card read carries `lastNote` ("pending" when the event has not replicated here) and `lastEvidenceAt`.
- **Pickup hold and one self-heal before the quiet row.** A gate-written card is held for the conversation that recorded it: no card session is started while that conversation's session is live (app and Telegram checked; Slack is treated as live, so no second worker ever starts on a guess). The hold lifts, one per tick and only while no work pickup is pending, when the conversation has no live session and a person's cause arrived, or when the card has had no agent record for `quietAfterHours`; the `hold-lifted` record is the pickup's cause. A quiet unheld card gets one automatic re-pickup (`quiet-repickup`, keyed on the newest agent record) before the owner sees anything; a second quiet period parks under the existing churn brake, and that park is what derives `quiet`. The quiet clock reads agent activity (its records, note pointers, the card's creation, a delivered hand-over), never a person's tap.
- **Delivering a commitment writes to the card.** `POST /commitments/:id/deliver` runs the gate first when the commitment has no card, writes a note "Delivered: …", and writes evidence only when the body names `itemId` (evidence up to the card's 32,000 limit; the commitment's own `resolution` keeps its 500-character slice), claiming the card done only when that was the last item.
- **Feedback is not a trigger.** With the board on, `POST /feedback` requires `source: { kind: "agent" | "other-agent" | "user" }` (`400 source-required`) and refuses `operator-conversation` with `400 operator-request-not-feedback`, both naming the commitment and card routes. The agent instructions, the built-in `/feedback` skill (a migration adds the field to installed copies) and the awareness entry carry the rule.
- **Trust-request queue.** An agent-raised chat request that was not delivered no longer counts toward the open cap of 3; undelivered requests have their own cap of the same size (`too-many-undelivered`), and the acceptance flush sends `min(cap − delivered open, undelivered)`, newest first. `DELETE /trust/requests/:id` withdraws an unanswered agent-raised request (its chat card is told, its code approves nothing, the same change is refused `withdrawn-recently` until the card would have expired); a `board-policy` request cannot be withdrawn.
- **Config, migration, awareness.** New owner-tunable settings `workBoard.requestCards { duplicateHintHours 24, backfillMaxAgeDays 14, sweepPerTick 25, unrecordedWorkMinutes 10, floorRecentHours 72 }`, `limits.noteText 4000`, `maxNotesPerCardPerDay 50`, `noteCoalesceMinutes 60`, `noteDrainPerTick 25`, `softOpenBlockers 10`, `maxOpenAsksPerCard 5` (added by migration with existence checks; `requestCards.enabled` is never written: omitted means on where the board is on; the sweep and the drain are clamped together to the journal bucket). New awareness entry `agent-work-cards`. `general` is a valid project key for a card with no project.

## What to Tell Your User

- **Your requests are tracked without being asked twice**: "When you ask me for something in our chat, a card for it appears on the Work Board under its project the moment I record it. Because the request came from you, it starts at once; you never get a 'needs your approval' row for your own ask. The card shows exactly what you asked, word for word, and tells you if I later reworded it or changed its milestones."
- **Requests from team members wait quietly for one tap**: "A request from a team member, or one I started myself, waits for your approval, but you see one line for all of them, 'N internal cards are waiting for your approval or board setting', not a card each. From there you can approve the ones shown, or let internal cards start without asking from now on, which raises the usual approval request to your chat or phone."
- **You can watch progress on the card itself**: "I keep progress notes on the card from wherever I am working; they appear in the card's conversation right away. Finishing work is still evidence per milestone; a note never counts as proof."
- **Your direct requests are never filed as 'feedback to the maintainers'**: "If you ask me to do something, it is a card I carry. The feedback queue is for reports about Instar itself."

## Summary of New Capabilities

| Capability | How to Use |
|-----------|-----------|
| Record a request and get its card | `POST /commitments` with `sourceMessageId` (and `sourceConversationKey` from a Bearer session); read `cardId` in the response |
| Requests whose card is not written yet | `GET /commitments?cardPending=1` |
| Write a progress note from the working session | `POST /work-board/cards/:id/notes { text }` |
| See the team's unstarted internal cards | `GET /work-board` → `notStartedCards`; one Needs-you row |
| Approve the shown unstarted cards (owner, PIN) | `POST /work-board/not-started/approve { pin, cards: [{ id, materialHash, titleHash }] }` |
| Approve them and ask to start internal cards without asking (owner, PIN) | `POST /work-board/not-started/approve-and-widen { pin, cards }` |
| Deliver a commitment onto its card | `POST /commitments/:id/deliver { deliveryMessageId?, evidence?, itemId? }` |
| Report feedback (agent's own) | `POST /feedback { ..., source: { kind: "agent" } }` |
| Withdraw an unanswered trust request | `DELETE /trust/requests/:id` |

## Evidence

Unit (`tests/unit/agent-work-cards-{store,gate,runtime,trust}.test.ts`, 50 tests): both sides of the ask-fields rule per discriminator, the outward default by writer, gate-only fields by principal, request approval from an owner row (two commitments on one message both approved; a member's not; a flip to outward and a withdrawal end it; the agent's edits keep it; `need` locked, also against a replicated edit), the divergence labels, `not-started` and its counted refusals, the quiet clock baseline and the churn park, the hold and its lift as the cause, every requester arm (native owner, linked member, unknown, agent-originated, relayed, forwarded, forwarded-undefined, mirrored row with an active/revoked/mismatched/other-machine device, team phone with no device, app event owner/member/older/agent, Slack absent/owner/bot, no id, not found, unreadable, budget, too long, credential), the deterministic card write and linking, the daily ceiling as a retryable reason drained by the sweep, a pickup session's commitment linking to its card, the sweep (enabled-at once, backfill by age, pace, refs repair, a replica's text with the origin absent), deliver (gate first, note only without an item, evidence with one, claim on the last), notes (prefix and binding, rate-limited writes nothing, pointer drained by event id across a takeover, daily ceiling coalescing), the holder pass being synchronous, and the trust queue (undelivered cap, bounded flush, withdraw rules, `withdrawn-recently`). Integration (`tests/integration/agent-work-cards-routes.test.ts`, 7 tests over the real AgentServer): owner request → request-approved card with the derived id in the response and `cardWritten` on the commitment; member request → `not-started`, the aggregated count, the owner's PIN approve and `stale-card`; a chosen `cardId` refused; notes over HTTP with `lastNote`; deliver with an item closing the card; `/feedback` refusals naming both routes; `DELETE /trust/requests/:id` statuses; approve-and-widen raising the request; every new route 503 with the board off. E2E (`tests/e2e/agent-work-cards-alive.test.ts`, through `AgentServer.start()` with a real CoherenceJournal, emitter, peer-stream reader and CommitmentTracker): an owner's commitment over HTTP is a card with the agent (never waiting on him) and under `GET /work/projects`; a note appears in the card's conversation; a member's commitment yields exactly one `work:not-started` Needs-you row and no per-card row; a second boot over the same journal shows the same cards and the same `enabled-at`.
