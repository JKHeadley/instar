## What Changed
Fifteen more faults in the locked-screen proof driver, and one gap in its evidence (`scripts/locked-proof/`), found in the live run on the Mac Mini on 2026-11-05 after the viewer-wait fix let it start. Proof tooling only; no runtime code changes.

1. Cases 12.1 and 12.6 freeze the server with SIGSTOP, but the server ran as a tmux pane process and tmux resumes a stopped pane process at once, so the server never froze and the case judged a running server. Both cases now serve the agent under launchd first and put it back in tmux afterwards, and `stop-server` throws unless `ps` shows the process stopped.
2. After `start-server` or `serve-under-launchd` the driver went straight on while the new server still read the lock state as "unknown", so the final sample read "unknown" and the next case's viewer had no machine to open. Both now wait up to 120 seconds for a known lock state.
3. `readLockState` returned agent A's "unknown" without asking agent B. An agent that does not know yet is now skipped like one that is down.
4. The driver took a proof server's `/desktop/locked/status` as the lock state. That value is a cache which only refreshes while a viewer is connected, so it read "unlocked" for a locked Mac and "unknown" after a start, and verdicts could be wrong in both directions. The driver now reads the Mac's own flag from IORegistry (`IOConsoleUsers`, `CGSSessionScreenIsLocked` for the proof user) and asks a server only when the proof user has no console session. Every sample records the servers' reading beside it as `serverLockState`.
5. Case 12.3 kills the proof user's tmux server, which takes agent B down with agent A, and the driver restarted only A. `start-server` now always starts agent A, as before, and also starts agent B when it is not listening.
6. `recover()` failed a case when it tried to resume a process that had already exited. Resuming a process that is gone is now skipped; stopping or killing one that is gone still throws.
7. The `typing` trigger meant "the input helper is running". That helper runs for the whole grant, so case 12.2e ("Node killed mid-typing") killed the server before any password was sent and judged a run in which nothing was typed. `typing` now means a duty exists in state owed, Enter is not yet pending, and the helper is running. Cases 12.9 and 15.9 use the same trigger.
8. Case 12.5a ("Guard killed in owed") killed the guard and then waited for a relock without ever ending the session. While a grant is live and its server alive, an owed duty stays owed and the Mac stays open for the person using it; the server's job is to replace the guard. The case now stops the viewer once the replacement guard has taken over, so it can show the Mac ending locked.
9. The `revoke` step used an operator session the driver had made for itself. The server only lets the session that opened a request end it, so the revoke was refused with 403 and the case went on to judge a grant that was still open. The step now uses the viewer page's own session, read from the page's unlock answer, and throws when a revoke is refused.
10. The "guard or typist still running after the duty closed" rule also fired when no duty had ever existed, because the input helper of a live grant counts as a typist. Case 12.17 types one letter, opens no duty and expects the grant to stay alive, so it could not pass. The rule is now judged only once a duty exists and has closed.
11. Case 12.9 waits for a duty's 10-minute deadline but had no timeout of its own, so the driver stopped watching after 270 seconds and the case could never reach its second step. It now watches for 840 seconds.
12. "Deadline immediately before Enter" (15.3) aimed Enter a fixed 1.5 seconds after the grant's ceiling. Typing the whole password takes 0.73 seconds on the Mini, so typing was due to start after the ceiling, when the page has closed the password box. Enter now trails the ceiling by half the typing time taken from calibration, so the ceiling falls while the password is being typed.
13. The check for the owner's security item looked once, straight after a failed relock. The item is raised by a 10-second sweep, so the check recorded "not raised" for an item raised 9.4 seconds later. It now waits up to 15 seconds when a duty has ended relock-failed.
14. When a typed password got no answer the driver recognised, it recorded only "no-result-within-60s". It now also records what the page's status line said while it waited (`pageSaid`), so the row shows what a person would have seen.
15. Case 15.9 failed any run in which the half-typed-field marker was still set when the case ended. The spec says that marker outlives its request and is cleared by the next input helper before any password can be typed. The case now opens a next grant (`next-helper-clears-field`) and checks the marker goes there. Follow-on (`then`) steps are also kept in the evidence row.
16. Case 12.9 froze the typist and the first guard but left the owning server running. That server's sweep replaces a frozen guard within 10 seconds, so the replacement relocked at the deadline and the other agent's grant was rightly refused; the deadline-based recovery by another agent, which the case is about, was never reached. The case now also freezes the owning server (served under launchd), so nothing replaces the guard.
17. The driver did not know the page's wording for the helper's `shield-not-confirmed` refusal ("This Mac's lock screen is not ready for a password right now…"), so it recorded "no result". It is now mapped.
18. The deadline cases aimed from "the moment the driver saw the grant open, plus 10 minutes". Over 33 duties the server's own end time for a grant came a median 0.64 s earlier than that (range 0.44 to 2.9 s), so a password aimed half the typing time ahead still arrived after the grant had ended (15.3, rerun at 16:03 PST: no duty, page said "Desktop access ended"). The driver now reads the grant's `expiresAt` from the page's own responses and aims from it; the row records it as `grantExpiresAt`.
19. The new `next-helper-clears-field` step ended its extra grant with an ordinary click on Stop and did not notice when that did not go through, so the extra grant's helper was still running at the end and the case failed its leftover check (15.9, 16:42 PST; the field itself read cleared in 11 ms). The step now tries the click for 3 seconds, records the result as `stopClick`, stops the grant from script if the click did not go through, and records `helperGone`.
20. Aimed 0.6 s ahead of the server's expiry, 15.3 created its duty 0.21 s before the ceiling and the ceiling arrived before the first character (rerun 17:09 PST: duty `relocked`, Mac's own flag locked throughout, 0 submissions, verdict "the password was never typed"). The lead is now 0.8 s.
21. The "lock screen is not ready" refusal. Measured live with an observer that evaluates the helper's own two conditions five times a second: a few seconds after the Mac locks, or after its display wakes, loginwindow lets go of secure input for about half a second and takes it back (for example 5.1 and 5.6 s after two locks, for 0.66 and 0.59 s). A password arriving in that moment is refused before any attempt is spent, and the page tells the person to try again. The driver now does the same: at most two more tries, 1.5 s apart, each waiting for the page's answer, recorded as `notReadyRetries`. Deadline cases type once.
22. Two earlier attempts at this were wrong and are withdrawn: waking the display (`caffeinate -u`) at the start of each case, then right before the grant. With the first in place the refusal rose to 6 of 16 passwords in one run. The wake is kept only ahead of deadline typing, where ten idle minutes is also the Mac's display-sleep time.
23. The leftover-process rule counted any input helper. A helper that refused the password before reserving belongs to no duty; with its server frozen it stays up. The rule now looks only at the guard and typist the duty recorded.
