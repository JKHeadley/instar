## What Changed
Ten more faults in the locked-screen proof driver (`scripts/locked-proof/`), found in the live run on the Mac Mini on 2026-11-05 after the viewer-wait fix let it start. Proof tooling only; no runtime code changes.

1. Cases 12.1 and 12.6 freeze the server with SIGSTOP, but the server ran as a tmux pane process and tmux resumes a stopped pane process at once, so the server never froze and the case judged a running server. Both cases now serve the agent under launchd first and put it back in tmux afterwards, and `stop-server` throws unless `ps` shows the process stopped.
2. After `start-server` or `serve-under-launchd` the driver went straight on while the new server still read the lock state as "unknown", so the final sample read "unknown" and the next case's viewer had no machine to open. Both now wait up to 120 seconds for a known lock state.
3. `readLockState` returned agent A's "unknown" without asking agent B. An agent that does not know yet is now skipped like one that is down.
4. The driver took a proof server's `/desktop/locked/status` as the lock state. That value is a cache which only refreshes while a viewer is connected, so it read "unlocked" for a locked Mac and "unknown" after a start, and verdicts could be wrong in both directions. The driver now reads the Mac's own flag from IORegistry (`IOConsoleUsers`, `CGSSessionScreenIsLocked` for the proof user) and asks a server only when the proof user has no console session. Every sample records the servers' reading beside it as `serverLockState`.
5. Case 12.3 kills the proof user's tmux server, which takes agent B down with agent A, and the driver restarted only A. `start-server` now always starts agent A, as before, and also starts agent B when it is not listening.
6. `recover()` failed a case when it tried to resume a process that had already exited. Resuming a process that is gone is now skipped; stopping or killing one that is gone still throws.
7. The `typing` trigger meant "the input helper is running". That helper runs for the whole grant, so case 12.2e ("Node killed mid-typing") killed the server before any password was sent and judged a run in which nothing was typed. `typing` now means a duty exists in state owed, Enter is not yet pending, and the helper is running. Cases 12.9 and 15.9 use the same trigger.
8. Case 12.5a ("Guard killed in owed") killed the guard and then waited for a relock without ever ending the session. While a grant is live and its server alive, an owed duty stays owed and the Mac stays open for the person using it; the server's job is to replace the guard. The case now stops the viewer once the replacement guard has taken over, so it can show the Mac ending locked.
9. The `revoke` step used an operator session the driver had made for itself. The server only lets the session that opened a request end it, so the revoke was refused with 403 and the case went on to judge a grant that was still open. The step now uses the viewer page's own session, read from the page's unlock answer, and throws when a revoke is refused.
10. The "guard or typist still running after the duty closed" rule also fired when no duty had ever existed, because the input helper of a live grant counts as a typist. Case 12.17 types one letter, opens no duty and expects the grant to stay alive, so it could not pass. The rule is now judged only once a duty exists and has closed.

## Evidence
Live on the Mac Mini, 2026-11-05. (1) Case 12.1 failed with "marker ended owed, expected relocked; Mac ended unlocked"; during a rerun `ps` showed the server in state `Ss+` and its lease file was renewed every 10 seconds, and a control (`tmux new-session 'sleep 120'`, then `kill -STOP`) read `Ss+` 0.3 s later while the same signal outside tmux read `T`. With the server under launchd the stop read `T`, the guard moved the duty from owed to watching 39 s later and to relocked, and 12.1 passed. (2) and (3) Cases 12.2a and 12.2c failed with "Mac ended unknown, expected locked" although the guard had relocked, and 12.2b and 12.2d failed at the viewer wait right after a restart; in the rerun with these fixes 12.2a, 12.2b, 12.2c and 12.2d passed. Unit tests in `tests/unit/locked-proof-driver.test.ts` cover each fix. (4) Cases 12.5b and 12.5c failed with "Mac ended unlocked, expected locked" while the duty read "relocked"; a once-a-second log at 12:30 PST showed IORegistry "locked" beside server A "unlocked" for 25 seconds. With the driver reading IORegistry, 12.5c passed at 12:39 with the Mac open for one second and locked through the 120 s watch. (5) 4097 stopped listening after case 12.3 and 12.6 then ended "unknown". (6) Cases 12.9 and 12.10 failed with 'refusing to signal pid …: owned by "nobody"'. 58 of 58 unit tests pass. (7) Case 12.2e failed twice with "no duty was ever opened: the password never reached the Mac"; its samples show the kill 3.6 s into the case with no duty and the Mac's own flag locked throughout. The corrected trigger is covered by a unit test (59 of 59 pass); a live rerun of 12.2e, 12.9 and 15.9 was still owed when this was written. (8) Case 12.5a failed twice with "marker ended owed, expected relocked; Mac ended unlocked"; its samples show the guard killed 6.5 s in, the Mac open from 7.2 s, a replacement guard from 15.1 s (inside the spec's 10 s sweep), and the grant still alive at the end. A live rerun of the completed case was still owed when this was written. (9) Case 12.14a failed twice with "guard or typist still running after the duty closed"; its row shows the revoke answered `{"status": 403, "error": "Desktop revocation unavailable"}`, the duty closed left-unlocked and the grant still alive. A live rerun was still owed when this was written. (10) Case 12.17 failed with that reason while its row shows no duty, the Mac's own flag locked throughout and the grant alive, which is what the case asks for. A live rerun was still owed when this was written.
