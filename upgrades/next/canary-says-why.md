# Feedback executor: a failed sandbox check records what it observed, and resuming has a lever

## What Changed

- `src/feedback-factory/execute/confinementCanary.ts`: a failed must-succeed probe's `detail` now carries a bounded tail of the command's own `stderr` then `stdout` (new exported `failureTail`, `PROBE_TAIL_CHARS = 700` per stream), with the canary's own nonce redacted before slicing so a straddling value cannot leave a fragment. The must-fail and session-path probes already recorded their evidence; the runner-path must-succeed probes recorded only `exit <n>` and discarded the captured output, and the workspace that produced it is deleted with the attempt — so the cause was unrecoverable after the fact. The verdict expression (`exitCode === 0 && !timedOut`) is byte-identical; the capture runs after it, on the failure branch only.
- `src/feedback-factory/execute/executePolicy.ts` + `FeedbackExecutorService.ts`: new `confinedCacheEnv(tmpDir)` carries every cache redirect for a confined command — `TMPDIR`, `VITEST_CACHE_DIR`, `ESBUILD_CACHE_DIR`, and now `npm_config_cache` (plus `update_notifier`/`fund`/`audit` off) — and is used by BOTH the canary and `verifyFix`'s base/lint/related runs. `npx` and `npm run` read and write npm's cache under `HOME`, which the confinement denies. One helper on purpose: the canary rehearses the very commands `verifyFix` later runs, so a redirect in one and missing in the other would let the rehearsal pass on a condition the real gate still hit, burning attempts under a misattributed `base-check:`/`gate:lint` reason instead of latching once and honestly.
- `src/feedback-factory/execute/executePolicy.ts` + `FeedbackExecutorService.ts`: `CANARY_PROBE_DETAIL_BUDGET = { maxBytes: 8192, maxChars: 2000 }` replaces the inline 2048/300 budget, so a captured tail survives storage instead of being truncated to its first line. Bounding stays in the canary because `scrubForStore` replaces an over-size field wholesale, and a ratchet test couples `PROBE_TAIL_CHARS` to the budget so raising one without the other fails.
- `src/feedback-factory/execute/FeedbackExecutorService.ts` + `src/server/routes.ts`: `retryCanaryNow(by)` and `POST /feedback-factory/execute/canary-retry` clear the canary latch's WAIT only — the canary still runs and still has to pass — refused while a tick is in flight, rate-limited by a cooldown in its own `exec:canary_clear` row (keyed inside the latch it would vanish the moment a failing canary rewrote the row, releasing the brake in exactly the case that costs a full canary run), with the retry-ladder position retained so a genuinely broken sandbox still backs off. Halting was automatic and free; resuming had no lever at all.
- `src/feedback-factory/execute/executePolicy.ts`: `effectiveLatchUntil()` is now the single reader of the legacy flat-day migration, so the availability check and the clear lever cannot disagree about whether a wait is in force; and `clampProbeDetail()` keeps a detail's END behind a `[…truncated]` marker when the scrubber's redaction expansion pushes it past the budget, instead of head-slicing the informative end away silently.

Why: live 2026-10-22 → 2026-10-24, `base-unit-smoke` failed five consecutive canary runs (ladder 1 h → 24 h, so the executor sat at a full day), and every stored record read `{ probe: "base-unit-smoke", detail: "exit 1" }`. Three hypotheses were tested by hand and all three refuted; the evidence that would have settled it was discarded at the moment of failure, and hand-patched logging on the running machine was wiped by each auto-update. No route could clear the wait, so the fix could not be exercised until the day elapsed.

## What to Tell Your User

When the check that rehearses the fix-writing sandbox fails, it now says what the failing command actually printed instead of only its exit code, so a stop explains itself instead of needing an investigation. And once the cause is fixed, the check can be re-run straight away rather than waiting out the remainder of a day-long pause. Nothing about *when* it stops has changed.

## Summary of New Capabilities

- `GET /feedback-factory/execute/status` → `profileUnenforceable.failedDetail[].detail` carries the failing command's own output tail (`exit 1 — stderr: … | stdout: …`), up to 2000 scrubbed characters, instead of `exit 1`.
- `POST /feedback-factory/execute/canary-retry` (Bearer + `X-Instar-Request: 1`) → `{ cleared: true }`, or `409 { cleared: false, reason: 'not-latched' | 'cleared-too-recently', retryAt? }`. Clears the latch's wait only; audited as `execute:canary-latch-cleared`.

## Evidence

`execute-units.test.ts`: a failing `npx vitest` probe's detail contains both streams' text; `failureTail` is bounded per stream, redacts `canary-secret-<nonce>` and the bare nonce, and reports `no output` when both streams are empty; `2 * PROBE_TAIL_CHARS + overhead` fits `CANARY_PROBE_DETAIL_BUDGET.maxChars`; `confinedCacheEnv` returns the shared redirect set with every path inside the run's temp dir. `execute-service.test.ts`: a full-length two-stream tail survives the latch write intact, and a clear drops `until` to 0 while keeping `episode` and `failures`, is refused inside the cooldown, and answers `not-latched` when there is nothing to clear. The three canary assertions fail on unpatched source for the right reasons (`expected 'exit 1' to contain 'EPERM'`, `failureTail is not a function`, `expected undefined to be '<tmpDir>/npm'`). Executor unit group 5/5 files green (149 tests), units+service 130/130, `npm run lint` clean.

Three adversarial second-pass review rounds (CONCERN → CONCERN → CONCUR), all findings resolved. Round 1: the redirect had been added to the canary but not to the runs it rehearses (now one shared helper); the bounding test was self-referential; and three Under-block omissions were named — must-succeed output is the one probe output the leak checks never scan, a secret that is neither the canary nonce nor a known credential shape is caught by neither redaction layer, and the smoke lane can quote instar's own adversarial test fixtures into durable operator-read text. Round 2 mutation-tested round 1's fixes and found three more: the "end-to-end" test never touched `profileUnenforceable`'s scrub+slice (narrowing it to 300 left every test green), the ratchet's hand-counted overhead was 3 short of the real worst case (`exitCode: null` co-occurs with ` (timed out)` on the SIGKILL timeout path), and the lever's cooldown was keyed on a field the failing canary rewrites, so the brake released exactly when a clear costs a whole canary run. Round 3 found that the clamp's WIRING was unguarded — removing `clampProbeDetail` from the store path left every test green, because the existing fixture's detail did not overflow after scrubbing — and that one mutation claim here was non-discriminating. Both corrected: a credential-dense fixture now drives a real tick whose post-scrub detail overflows the budget, and the ratchet mutation was re-run at the discriminating `PROBE_TAIL_CHARS` 980 rather than 1000 (1000 fails the old arithmetic too, so it proved only that a ratchet exists). Round 3 also fixed a latent clamp overflow at a degenerate budget and the lever's write order (the wait is now cleared before the cooldown is consumed, so a failed second write cannot spend the caller's only move for nothing). Mutation-verified guards: narrowing the stored slice to 300, keying the cooldown inside the latch, removing the in-flight refusal, unwiring the clamp, head-slicing instead of keeping the end, and `PROBE_TAIL_CHARS` at 980.

Honest limit: the npm cache redirect is the leading suspect for the five latches, not a confirmed cause — and a sibling path (`depsCache`'s native rebuild) hit the same class of problem and needed a full `HOME` redirect rather than a cache-path one, which is reason to stay humble about it. The capture is the load-bearing half — if the suspect is wrong, the next failure names the real cause itself, and the lever means that next failure happens within minutes of the fix installing rather than at the end of a 24-hour wait.
