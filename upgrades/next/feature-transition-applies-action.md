# Upgrade Guide — vNEXT

## What Changed

- `src/server/routes.ts` `POST /features/:id/transition`: moving a feature to `enabled`/`disabled` now also SENDS the feature's own `enableAction`/`disableAction` (a loopback request to the server's own route, over the socket the transition arrived on, with the server's Bearer token) and answers with `apply: { direction, outcome: applied | refused | failed | not-applied, httpStatus, detail, at }`, `effective` and `viaOperatorSwitch`. Before, nothing ever called the action: the switch recorded "on" in `discovery.db`, `config.json` never changed, and the next boot's `bootstrap()` silently moved the row back to disabled. Two switches on one feature run one after the other (per-feature serial queue). The recorded choice is kept when the setting change is refused; the response and the shown state say so.
- `src/core/FeatureActionApplier.ts` (new): the client sends ONLY the four exact method/path pairs the definitions use (`PATCH /config`, `PATCH /api/files/config`, `POST /telemetry/enable`, `POST /telemetry/disable`); anything else a definition names is `not-applied`, never sent. Redirects are not followed. 10 s timeout, reported as unconfirmed ("may still land").
- `src/core/FeatureRegistry.ts`: `feature_state.last_apply_json` (schema v5, nullable, idempotent `ALTER TABLE`); `FeatureState.lastApply`; `operatorSet()` (the operator's switch: any state → enabled/disabled, writes an `explicit-written` consent record for network/self-governing tiers, logs `trigger: 'operator-switch'`); `getEffectiveState()` / `deriveEffectiveState()` (recorded vs configured vs at-boot → one of `on` · `off` · `on-after-restart` · `off-after-restart` · `recorded-only` · `not-recorded`, a plain `summary`, `detail`, `lastAttempt`); `readMergedConfig()` (config.json on disk over runtime config, one level deep); `setConfiguredResolver()`; new definition fields `defaultOn`, `configEnabledValue`, `honestyNote`, `switchable`. `resolveConfigValue()` reads an absent key as the consumer's default and a section object without a boolean `enabled` likewise (it used to read any object as on).
- `GET /features`, `GET /features/:id`, `GET /features/summary` carry `effective` per feature.
- One-time state change on first boot after update: the seven default-on features (publishing, tunnel, git backup, file viewer, input guard, external operations, evolution system) bootstrap as `enabled` wherever their key is absent — matching what the runtime already did — so the Features tab shows them On and the boot log's enabled count rises.
- Operator path: a valid `X-Instar-Operator-Session` (the dashboard PIN-unlock proof) switches from any state; a PRESENT-but-invalid proof answers 401 `OPERATOR_PROOF_INVALID` instead of silently falling back to the agent path. With no header the agent path is unchanged (discovery graph, consent record, activation challenge).
- `switchable: false` (evolution-system — `server.ts` constructs `EvolutionManager` regardless of `evolution.enabled`): the transition route refuses enable/disable with 409 `FEATURE_NOT_SWITCHABLE`; the shown state follows the key with the honesty note.
- `src/core/FeatureDefinitions.ts`: Threadline's switch now writes `threadline.relayEnabled` (the key `bootstrapThreadline` reads; `threadline.enabled` had no consumer); Autonomous Evolution writes `evolution.approvalMode: 'autonomous' | 'ai-assisted'` with `configEnabledValue: 'autonomous'` (`evolution.autoImplement` had no consumer); `defaultOn: true` on publishing, tunnel, git-backup, file viewer, input guard, external operations, evolution; the tunnel's enable body drops `type: 'quick'` (it would have overwritten a named tunnel); Threadline's and evolution-system's reversibility notes no longer promise what `PATCH /config` cannot do.
- `src/commands/server.ts`: installs the autonomous-evolution resolver (explicit `evolution.approvalMode`, else `PROFILE_DEFAULTS[autonomyManager.getProfile()].evolutionApprovalMode`) so bootstrap and `effective` agree with the consumer; `PROFILE_DEFAULTS` is now exported from `AutonomyProfileManager`.
- `src/server/fileRoutes.ts`: `createFileRoutes` no longer returns an empty router when the viewer is off at boot; the existing per-request guard (every file route except `/api/files/config` answers 404 while disabled) covers both cases, so the switch can turn the viewer on without a restart. `GET`/`PATCH /api/files/config` are therefore reachable while off (same handlers, CSRF header and validation).
- `src/server/routes.ts` `POST /telemetry/disable`: local deprovision, log clear and config write now happen BEFORE the awaited remote deletion (same 5 s timeout, same pending-deletion file shape), so a slow remote cleanup can never land the local "disabled" after a later enable.
- `dashboard/index.html` Features tab: the toggle shows the disclosure (description, data implications, reversibility) before enabling a network/self-governing feature; sends the operator proof; tracks `operatorSessionExpiresAt`; on 401 asks for the PIN once and retries; shows `apply.outcome`/`effective.summary` as toasts; every card always shows `effective.summary` (red on a mismatch or failed attempt); the detail panel shows it under "Right now"; a read-only switch renders disabled with the note as tooltip. `dashboard/console/` is untouched (owned by `feat/console-native-1`).
- Reversibility notes: every restart-dependent feature's undo note now says "saves <key>: false; … at the next server restart" (they promised immediate shutdowns `PATCH /config` cannot deliver); Threadline carries an `honestyNote` naming the `THREADLINE_RELAY_ENABLED=true` environment override, shown on its card.
- CLAUDE.md template + `migrateClaudeMd`: new section "Feature switches apply their setting" (`FEATURE_SWITCH_CLAUDEMD_SECTION`), content-sniffed, idempotent.

## What to Tell Your User

Until now, flipping a feature on in the dashboard only wrote down your choice — the agent's actual setting never changed, so the feature stayed off, and after the next restart the switch quietly flipped itself back. The switch now really changes the setting, tells you if the change was refused and why, and the Features page says plainly what is happening: "On", "Saved as on; it may not start until the next restart", or "Switched on, but the setting is still off: <reason>". It never says "running" for something only just saved. Turning on a feature that shares data shows you what it shares first, and your PIN unlock counts as your consent. Two switches were quietly broken (Threadline and Autonomous Evolution wrote settings nothing read) and are fixed; one (the evolution system) is shown read-only because this version ignores its setting. After this update, several features that were always running (publishing, the tunnel, backups, the file viewer, input guard, external operations) show as On instead of Off — nothing started; the page just stopped being wrong about them.

## Summary of New Capabilities

- Feature switches apply their setting; `POST /features/:id/transition` returns `apply` + `effective`.
- `effective` on every feature read: recorded vs configured vs at-boot, with a plain sentence and the last failed attempt.
- The operator's dashboard switch (PIN-unlock proof) sets any feature on/off from any state and is its own consent record.
- Read-only switches (`switchable: false`) for keys the runtime ignores.
