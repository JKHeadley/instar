## What Changed

The console gets a **Settings → Context** page (context-budget-layered-summaries §11; Phase 1 S14). It is read-only and shows, for this machine:

- each conversation's running summary: whether it is current, cost per turn, and how much of the operator's own writing is still word for word in the session (sizes, repeated work and message counts in the tap-through detail);
- whether recovery after a compression actually works, per AI app and version (the compaction canary);
- what keeping the summaries current costs against its daily allowance;
- the "send only what changed" trial (`/context-budget/delta-shadow`, when the server has it);
- the watcher's own upkeep: last check, refreshes settling, leftover pauses cleared.

It reads `GET /context-budget/layers`, `/metrics`, `/sentinel` and `/delta-shadow`. When the feature is off (503) the page says so in one sentence, and a route this version lacks (404) is "not on this version yet", never an error.

**Home's count** gains a `context` source (`needs-model.js`, reading only `/context-budget/sentinel`): a memory refresh stuck past the 15-minute reconciliation bound, an unreadable refresh record, or a compression-recovery check that has gone `diverged` (one row per machine). The page leads with these, each with a link to ask the agent. Stuck and unreadable rows are matched to the watcher's own Attention item by fold id, so one incident counts once; the unreadable-record notice title now names its fold for that. A watcher that has stopped checking in makes the count read "can't tell" rather than "nothing". Rolled-back folds, breaker trips, pending Anchor confirmations and `checkpoint-unreachable` events join the count once their backends exist.

`src/core/EnrollmentWizard.ts` named the Claude engine (`'claude-code'`) in two separate conditions. The second one arrived with the stale follow-me sign-in fix (#3147), which was tested on a base from before the framework-id ratchet (`scripts/lint-framework-name-ratchet.mjs`, added by #3098) existed. Once both were on main the ratchet counted 1136 literals against a baseline of 1135, so `npm run lint` failed on main and on every change tested on top of it.

Both conditions now call one file-local helper, `isClaudeCodeLogin(login)`, so the file holds a single literal, as the baseline records. Behaviour is identical: the same two Claude-only steps run for the same logins. The baseline file is not changed.

Scheduled jobs can now set an optional `thinkingMode` (`off`, `low`, `medium`, `high` or `max`) that says how hard the AI should think on each run. The scheduler translates it for the engine that runs the job: Claude Code gets an effort level, Codex gets its reasoning-effort setting, and engines without such a setting record `not-supported` rather than failing. A job that does not set the field launches exactly as before; a golden test locks today's start-up command for every engine.

Every scheduled model run (the scheduler's main path) now records what was actually launched: the engine, the settings that were applied or dropped (with the reason), and the engine's version. This is stored next to the existing framework and model fields in the run history, and it is built from the exact command handed to tmux, so the record cannot claim a setting the command did not carry. Script jobs and triage sessions carry no record, and if the final command does not carry what the builder reported, no record is written and an evidence error is logged instead.

- **Definition paths.** The field survives every way a job is defined or moved: jobs.json, AGENT.md job files, built-in jobs, job migration and portable bundles.
- **Evidence.** Each main-path run writes one `jobs.launchIntent` evidence row, and a dev-rung counter turns those rows into the spec's graduation floor.
- **Ratchet.** A new CI lint keeps engine-name checks outside the engine adapters from growing past today's count.
- **Awareness.** The CLAUDE.md template gains one Job Scheduler line, and existing agents receive it through an idempotent migration.

Android phones running the Instar app can now get notifications. A phone registers with `provider: "fcm"` on `POST /mobile/device/push` (absent still means an iPhone, read exactly as before), and the agent sends through Google's Firebase Cloud Messaging with the vault key `fcm_service_account_json`, under the same rules as iPhones: the same events, the same fold and daily limits, and no message text sent to Google (the phone fetches it with the read-only token). The register answer now carries `ready`, so a phone can say when notifications cannot arrive yet. A Firebase problem pauses only Android, kept in its own `pausedFcm` field; tokens are cleared only on Google's typed "token gone" answers; a pause re-checks itself at most 6 times over about 31.5 hours, and the new `POST /mobile/push/recheck` re-arms it on every machine after the agent fixes the cause. Android notifications never say "Face ID", and approval notices go only to phones that can approve. iPhone and Android sends run side by side, so iPhones never wait for Google. `GET /mobile/push` adds `fcmConfigured`, `pausedReasons` and each device's `provider`. instar.sh now serves `/.well-known/assetlinks.json` so pairing links open the Android app, and the pairing page says "your phone (iPhone or Android)". The agent's CLAUDE.md push section is rewritten for both kinds of phone.

A follow-me pending login (one tied to an expected account email and a config-home slot) was re-driven on every expiry for as long as it stayed pending. The completion sweep closes such a login only when the slot's auth revision changes from a baseline, every reissue takes a new baseline, and on Linux no auth revision is readable at all. So a login whose sign-in had finished another way was renewed forever. On 2026-11-13 one on Mama PC had been renewed 1113 times in 11 days for an account that was active and reading quota.

`EnrollmentWizard.reissueExpired()` and `recoverAfterRestart()` now accept optional `AlreadySignedInDeps` (`accountIsHealthy`, local state only). With them, before re-driving a Claude follow-me login the wizard requires (1) that this machine's pool already holds the account `active`, as the expected email, with no identity drift, and (2) that the slot answers the identity oracle's live read (the read used for `proof: 'live-identity'`) as exactly that email. Then it completes only the stale login; the pool is not written. Codex logins, unhealthy or drifted accounts, a different account, an unreadable slot, a probe error, a login without an expected email, or a login that changed during the read all re-drive as before. The server passes the deps on both paths. `refresh()`, the reissue route and the completion sweep are unchanged.

## What to Tell Your User

There is a new page under Settings called Context. It shows what I keep in each conversation's running summary, whether it is up to date, what our conversations cost per reply, and whether my memory recovers properly when a long conversation gets compressed. If something there needs you, it shows up on Home too. It only covers the machine the dashboard is running on for now.

Nothing changes for you. This repairs a development check so that new features can be tested and merged again.

I can now run a scheduled job with lighter or heavier AI thinking, and every scheduled AI job run records which engine, settings and version were actually used. That lets us check whether lighter thinking saves usage on routine jobs without making them worse.

Android phones with the Instar app can now get notifications from me, just like iPhones, once the Firebase key is in place. Nothing changes for iPhones. Pairing links on Android will open the app directly once the app's signing fingerprint is published.

If an account showed a sign-in request even though it was working, that request now clears by itself within a few minutes, and the agent stops starting a new sign-in for it every quarter hour. Nothing for you to do.

## Summary of New Capabilities

- Console Settings → Context page (read-only).
- Home's count includes stuck memory refreshes, unreadable refresh records, and broken compression recovery.

| Capability | How to Use |
|-----------|------------|
| None (internal repair) | Not applicable |

- Optional per-job `thinkingMode`, translated per engine.
- A launch record (engine, applied/dropped settings, version) on every scheduled model run.
- A CI ratchet on engine-name literals outside the adapters.

| Capability | How to Use |
|-----------|-----------|
| Android notifications through Firebase | Automatic once `fcm_service_account_json` is in the vault |
| Phone told whether notifications can arrive | `ready` in the `POST /mobile/device/push` answer |
| Re-check an Android pause after a fix | `POST /mobile/push/recheck` with `{"provider":"fcm"}` |
| Android App Links for pairing | instar.sh `/.well-known/assetlinks.json` |

- Pairing no longer fails when the owner's private Telegram message is slow or held (for example during a Telegram send outage). The phone keeps waiting: the message's Approve, Decline and code still work when it arrives late, and the owner can approve from an owner phone instead (fb-e6b7ee2b-a8c).

| Capability | How to Use |
|-----------|------------|
| Stale follow-me sign-ins close themselves when the account already works | Automatic on the next reissue sweep or restart |
