## What Changed

`vitest.config.ts` aliases `@sagemindai/threadline-core` to the live source in
`packages/threadline-core/src/index.ts`, with the stated intent that "tests resolve it to the
live source so cross-implementation tests need no install or build". `vitest.e2e.config.ts`
carries the same alias.

`vitest.push.config.ts` did not — and that is the config CI runs for
`Unit Tests (node N, shard M/4)`, which is one of the twelve REQUIRED status checks on `main`.
So under the push gate, three test files could not be LOADED:

    Error: Failed to load url @sagemindai/threadline-core ... Does the file exist?

A collection failure fails the entire shard. From the commit that added those tests
(2026-10-16) onward a required check failed on EVERY open pull request, and no pull request
armed with GitHub auto-merge could land however green the rest of it was. The affected files
are spread across shards, which is why affected PRs showed several shard failures rather than one.

This adds the same alias to `vitest.push.config.ts`.

## What to Tell Your User

Nothing user-visible. This repairs the project's own test setup so finished work can merge again.

## Summary of New Capabilities

- None. A missing alias restored to one test config.

## Evidence

- CI, PR 2201, `Unit Tests (node 20, shard 4/4)`: `Test Files 1 failed | 850 passed | 2 skipped (853)`,
  `Tests 11487 passed | 39 skipped`, the single failure being the unresolvable import above.
  Every executed test passed. Shard 2/4 failed the same way on two more threadline files.
- With the alias added, and with `@sagemindai/threadline-core` NOT installed in `node_modules`
  (verified unresolvable via `require.resolve`), the three threadline files the push config
  matches run green under that config: `Test Files 3 passed (3)`, `Tests 40 passed (40)`, exit 0,
  zero collection failures.

## Why an alias and not a dependency

Declaring the published `@sagemindai/threadline-core@0.1.0` as a devDependency also makes the
bare specifier resolve, and was the first fix attempted here. It is the wrong one: it tests the
PUBLISHED artifact rather than the in-repo source, which contradicts the intent recorded in
`vitest.config.ts`, and it adds an install the design deliberately avoids. The alias keeps the
three configs consistent and the tests pointed at live source.

Not changed: `vitest.integration.config.ts` and `vitest.contract.config.ts` also lack the alias.
Neither currently matches a file that imports threadline-core, so adding it there would be
speculative; if either grows such a test it will need the same line.
