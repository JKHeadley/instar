## What Changed

- When Telegram accepts a reply but the origin store cannot save the receipt, the server no longer says "outcome unknown". It answers the new outcome `accepted-unrecorded` with Telegram's message id (`delivered: true`), keeps the receipt in a small fallback file (`state/telegram-origin-unrecorded-receipts.jsonl`), and the recovery tick folds it back into the store through the existing `reconcileReceipt` once the abandoned claim is reaped.
- New read: `GET /telegram/origins/operations/:operationId/outcome` (ordinary API auth; no operator session) answers `delivered`, `partially-delivered`, `pending`, `not-delivered` or `unknown`, with `safeToResend`, the Telegram message ids and a plain detail line. Never message content. A dispatched request with no recorded answer stays `unknown`, never `not-delivered`.
- Every held 409 now carries `checkOutcome` (the lookup path).
- `telegram-reply.sh` handles `409 telegram-origin-held`: it asks the lookup once and prints DELIVERED / HELD / MAY ALREADY BE DELIVERED / NOT SENT. Only NOT SENT says a resend is safe. It used to print "Failed (HTTP 409)" and exit 1, so sessions resent.
- An `accepted-unrecorded` reply is written to message history (`telegram-messages.jsonl`) and recorded for content and delivery-id duplicate protection, so a resend of the same text is suppressed.
- On a forwarded (cross-machine) send, the holder answers an `accepted-unrecorded` result as sent, and its receipt check reads the fallback record, so the forwarding machine never re-forwards a delivered message.
- The pre-change relay script SHA is registered so deployed agents receive the new script; a CLAUDE.md section ("Held reply outcome:") is added for new and existing agents.

Every production script job now writes a durable result record before it runs and records its outcome before releasing its claim. The scheduler compares those records with independent job history at startup and every 30 seconds. A missing or unfinished record is shown as unchecked, and a broken write holds that job's script route for repair. The job report shows the count, status, model-call audit, and gaps. Canary assertions have their own durable log.

The Jev judgment and outage replacement code is installed with its decision gates off. The required live benchmark, one-provider trial, pool roster, and quality evidence must pass before those model decisions are enabled.

- `WindowRunLivenessAuthority`: a transcript heartbeat up to 5 s newer than the sample time now counts as fresh (it was refused, which marked an actively-writing session as having a stale heartbeat; the incident had a heartbeat 65 ms after the sample).
- A recovery refresh refused with `session-busy` is recorded as `executor-busy`, not a failed recovery: the run re-samples at once and returns to active when green, stays at-risk otherwise, and still fails at the existing 15-minute recovery ceiling. Other refusals still stall loudly.

## What to Tell Your User

If I ever say a message "may already be delivered", I now check whether it actually arrived before doing anything, instead of sending it again. You should stop seeing the same message from me twice after a hiccup in my message records.

Scheduled script results now have a record that can be checked against the job history. If a result cannot be recorded safely, that script job pauses its cheaper route and raises attention. The new AI result check is still being tested and is not yet handling live job results.

A long autonomous run that was working could be wrongly marked stalled, with its active status removed. Two causes are fixed: a heartbeat a few milliseconds newer than the check counted as stale, and a session too busy to restart counted as a failed recovery. A busy session is now treated as alive.

## Summary of New Capabilities

- Agents can ask whether a held reply reached the chat, by operation id, and get delivered / pending / not delivered / unknown.

- Review script result coverage and unchecked outcomes through the existing job report.
- See which script jobs are held after a result-recording failure.

- `GET /window-run-liveness` can show recovery outcome `executor-busy` (the session was alive and mid-work, so it was not restarted).

## Evidence

With the change: new unit tests (held-reply-outcome 10/10, relay-script held branch 5/5), the updated origin-service tests, and an integration test over the full reply HTTP pipeline with the real adapter (409 accepted-unrecorded with message id → lookup says delivered with only Bearer auth → message in history → identical resend suppressed, one network call).

Focused scheduler, store, route, integration, and lifecycle tests cover registration before execution, restart recovery, bounded evidence, canary logging, and the report denominator. Synthetic Jev and Luna benchmark results are recorded in the approved design's evidence report; they do not authorize the decision gates.

Unit tests in `tests/unit/window-run-liveness-authority.test.ts`: a heartbeat 65 ms after the sample is fresh and active; a heartbeat 60 s in the future is still refused; a busy refusal with a green re-sample returns active with no notice; a busy refusal without green stays at-risk, heals on a later green tick and never calls recovery twice; a busy run that never turns green fails at the ceiling; the production refresh mapping marks only `session-busy` as busy.
