## What Changed

DF-0001, stage 1 of `docs/specs/design-standard-enforcement.md`. The phone and Mac apps' account list (`GET /mobile/accounts`) used to sort each account's usage limits by percentage. A limit that had already reset still decided the account's colour, its usage line and the "nearly out" notice. The server and the web console also coloured from different figures: the server used the rounded percentage and the web the unrounded one, so 89.6% showed "90%" in red on one and amber on the other.

Now `usageWindows()` returns the limits in a fixed order (5-hour, weekly, Fable weekly). Each limit carries three new fields:
- `name`: "5-hour", "Weekly" or "Fable weekly"
- `tone`: `null` below 75, `'attn'` from 75 to 89, `'bad'` from 90, taken from the rounded figure that is displayed
- `rolledOver`: true when the limit's reset time has passed since the reading; such a limit has no tone, and its percentage is still sent

`topWindow()` picks the highest limit that has not reset. That limit now drives the account's tone, its usage line, the account sort and the pool's "nearly out" notices. The web console colours limits and accounts through the same rounded rule, and adds a name tie-break to its account sort. `label` and `schemaVersion` are unchanged, because the change is additive.

## What to Tell Your User

- **Usage limits read the same everywhere**: "Each account's usage limits now always show in the same order: 5-hour, then weekly, then Fable weekly. A limit that has already reset no longer makes an account look full. The colours now match the number you see, so 90% is red in the web dashboard and the apps alike."

## Evidence

- `tests/unit/usage-tone-parity.test.ts`: one vectors file (`src/data/design/usage-tone-vectors.json`: 74, 75, 89, 89.6, 90, 100, and 100 with a past reset) runs through both the server and the web. Each case checks the limit's tone, whether it decides the account, and the account's tone. It also checks that the server's display names equal the web's. Changing either side's threshold or rounding fails it.
- `tests/unit/mobile-native-capacity-screens.test.ts`: the limits come back in fixed order whatever their percentages. A reset 100% limit keeps its figure but has no tone, is not the top limit, does not set the usage line and raises no notice. 89.6% is `bad` for both the limit and the account.
- `tests/integration/mobile-native-capacity-screens.test.ts`: `GET /mobile/accounts` serves `name`, `tone` and `rolledOver` on each limit.
- Neighbour suites green: console-accounts, console-live-check-fixes, console-unreachable-model, framework-id-ratchet, mobile-native-secrets-writes (160 unit tests); console-static-serving with the capacity-screens integration test (23); console-home-lifecycle with the capacity-screens alive test (e2e, 22).
