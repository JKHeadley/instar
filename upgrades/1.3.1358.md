## What Changed

In an app without MCP elicitation (Claude Desktop, for one), `threadline_pair_open`, `threadline_pair_finish` and `threadline_pair_forget` no longer refuse. The threadline-mcp that owns pairing on this computer serves a small approval page on `127.0.0.1` only (random port, a one-time 32-byte random token in the path) and opens it in the person's default browser itself. The page asks the same questions the app would have: a text box for the pasted invite, radio buttons for the decision with the safe choice first, and Submit or Cancel. The tool call does not wait for the person: it returns `{ ok: true, pending: true, opened: true, note }` at once, and the final result appears in `threadline_pair_status` as `lastApproval` (with `pendingApproval` while the page is open). The page closes when the action finishes or after 10 minutes; an unanswered question counts as no answer, and nothing is decided.

The model is never given the page's address (Echo review R2-1). Only when the browser cannot be opened (or `THREADLINE_NO_BROWSER=1`) does the result carry the link, flagged `fallback: 'link-in-chat'`, with a note saying this is weaker.

The page refuses any request whose Host is not exactly `127.0.0.1:<port>` (and a request with no Host), any POST whose Origin is present and not exactly `http://127.0.0.1:<port>`, and any form whose per-question random token does not match. Every response sets `Cache-Control: no-store`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`, and `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; form-action 'self'; frame-ancestors 'none'`. Only GET and POST are served; an unknown token is a bare 404. All text is escaped (claimed names come from the other agent).

Apps with elicitation are unchanged: the choice is made by the client's declared elicitation capability alone, never by the app's name.

A threadline-mcp that does not own pairing now refuses in plain words that name the owning app ("Pairing is open in Claude Desktop. Finish it there, or close that app and try again."), never a pid or a setting. The owner records the app's name (mapped from its MCP client name to what a person calls it: Claude Desktop, Claude Code, Cursor, VS Code, the ChatGPT app, Goose) on the second line of its owner lock; a lock holding only a pid (0.5.x) is still read. Ownership is live: when the owning app closes, the next pairing step or credential send in another app takes ownership and works there. The proxy-mode and credential refusals are plain words too, with no setting names, ports or file paths.

The README now has a no-terminal install section per app: Claude Desktop (one-click extension, coming with this release), Cursor and VS Code (install links pinned to `threadline-mcp@0.6.0`), ChatGPT desktop (settings), and Claude Code (ask your agent). Every route except the Claude Desktop extension needs Node.js, from the nodejs.org installer.

## What to Tell Your User

If your app can't ask you a pairing question itself, Threadline opens a page in your browser with the question instead. Answer it there; it stays open for 10 minutes, and if you don't answer, nothing changes. The page is a little weaker than an app's own dialog, because a program on your computer that learned its address could answer it, but your agent is never given that address, and opening an invite still needs the invite you paste in.

## Summary of New Capabilities

- Pairing (open, finish, unpair) in MCP apps without elicitation, through a local approval page the person answers in their browser.
- `threadline_pair_status` shows `pendingApproval` and `lastApproval`.
- The non-owner pairing refusal names the app that owns pairing.

## Evidence

- `tests/unit/threadline-core/approval-page.test.ts`: binds 127.0.0.1 only; wrong or missing Host refused; unknown token 404; GET/POST only; security headers; enum rendered as radios in order with a hostile `<script>` name escaped; Submit resolves with the values; Cancel and expiry resolve null and the page then 404s; a bad per-question token or a foreign Origin decides nothing; the coordinator returns pending without waiting, and neither the result nor status contains the link or token unless the browser could not be opened.
- `tests/unit/threadline-core/approval-page-pairing.test.ts`: over a fake relay wire, both sides pair through their own pages to mutual-verified; Decline pins nothing; an expired page decides nothing; Cancel on unpair keeps the pairing.
- `tests/e2e/threadline/threadline-mcp-approval-page.test.ts`: the built server over stdio, with a client declaring no elicitation, pairs with a real Instar agent through the page (link captured from a stub browser opener, never from a tool result) and delivers a credential; a second server on the same state directory refuses naming the owning app.
- `tests/e2e/threadline/threadline-mcp-stdio-pairing.test.ts`: a client with elicitation still pairs through the app and never gets a pending page.
- `tests/unit/threadline-core/state-lock.test.ts`: app name recorded and read, pid-only lock still read.
- Breakage: 3 tried, 3 caught. Removing the Host check fails the Host test; making the coordinator wait for the action instead of returning pending fails the coordinator and flow tests (timeouts); putting the link back into the browser-opened result fails the leak assertions in the unit, flow and stdio E2E tests.
