## What Changed

First increment of the approved agent-held Google passkeys spec
(`docs/specs/agent-held-google-passkey.md` §6). Prototype passkeys are stored in the vault as
top-level keys named `google_passkey_*`. Secret sync no longer copies them between machines: the
sending side leaves them out, and a receiving machine that is sent them by an older build drops them
and records that it did, while still storing the rest of the batch. A copy a machine already holds is
never deleted. Reading one of these keys through the vault read script still works, so the existing
sign-in scripts keep running, but each read is now recorded (key name and time only) in
`.instar/logs/passkey-legacy-reads.jsonl`.

## What to Tell Your User

The sign-in keys your agent keeps for your Google accounts are no longer copied from one of your
machines to the others. Nothing you use today changes — sign-ins keep working exactly as before.

## Summary of New Capabilities

- Machine-bound sign-in keys stay on the machine that made them.
- A machine on an older version can't cause the rest of secret sync to fail.
- Every use of these keys is recorded, so it's visible which tools still depend on them.

## Evidence

- Unit tests: `tests/unit/secret-sync-legacy-passkey.test.ts` covers the key matcher, the sending-side
  filter, the payload the provisioner actually encrypts, an old-build sender pushing to a new-build
  receiver (keys dropped, the rest stored, logs carry names only), a receiver's existing copy left
  untouched, and the recovery namespace still rejecting the whole batch.
- `tests/unit/secret-get-legacy-passkey-read-log.test.ts` runs the real script against a real
  encrypted vault: the value is returned, one audit line is written without the value, and ordinary
  keys are not logged.
- The existing secret-sync unit tests pass unchanged.
