## What Changed

SEC-113. When Local Verify hands a verify to a peer machine, the peer now signs its answer with its machine key, over the request it ran and the result. The coordinator checks the signature against the key it has pinned for that peer, at its own receive time, on the raw answer and after the existing field checks. An answer that fails is refused and the verify runs on the coordinator; a peer with no pinned key is never sent work. This applies to PR and main verifies on peers.

A peer's green on main now has bounded authority (this part rides the existing `monitoring.localVerify.mainOnPeers` switch, off by default). It never becomes the isolation baseline and never writes flaky history. A second "not verified on this machine" clock that peers cannot move turns main suspect at most three hours after the first merge the coordinator has not verified itself. Main is routed back to the coordinator before that, at a refresh age derived from its own measured main durations, and a coordinator with no local green of its own keeps main local. If the coordinator's own run fails twice on the exact commit a peer called green, that peer stops getting main; a third machine is asked once, and only if it cannot settle it is the owner told, with a Clear button on the console.

Signed pool reads (a session list, a transcript, pool history) ask another machine over the signed mesh first, and send the agent token only when that machine says it can't serve the read. Mesh answers are not signed, so a party on the network path could forge that answer to get the token sent (SEC-114, active form).

Each machine now remembers the highest version it has ever seen for each of its peers. The record is persisted, machine-local and never lowered. Once a peer has been seen at 1.3.1740 or later, the fallback to it is refused whatever the answer says. A refusal is counted (`fallbacksRefused` on `GET /pool/signed-reads`) and reported as a degradation, at most once per machine and kind of read per 15 minutes.

This is an interim mitigation that raises the cost of the attack. The full fix is signed mesh answers.

The Chief of Staff now opens one Work Board card for each tracked project that is waiting on the owner, and closes it itself when a later check, the owner's pause or the project's close clears the wait (never on an unreadable check). The card says what the check saw, the goal and checklist, a recommendation and why it needs the owner, and links the project conversation. It is server-owned: sessions cannot write to it, and a person's taps still work. Agent cards written through the route must now carry `recommendation` and the new `whyYou` field (`recommendation-required` / `why-you-required`). A card the owner carries that sends nothing outward no longer waits for an Approve tap; an agent's claim on such a card is finished only by the owner's Confirm done. A card can name the plan or pull request it is about (`covers`); Needs you then shows that item once, in its own words and with its own action, with a link to the card. The Chief of Staff cards follow `workBoard.chiefOfStaffCards` (on for development agents, off on the fleet).

Every Work Board read (`GET /work-board`, `GET /mobile/work-board`) now carries `myBoard.sections`: the cards that need the reader, each card once under its most pressing reason, in Luna's order: "Waiting for your approval", "Waiting for your reply", "Your cards", "Cards you were added to" and "Held for later". Each section lists `cardIds` (untouched cards first, then started ones, newest first), `notStarted`, and `more` when the board's soft limit cut some. Nothing is stored and no rule changes: the sections are worked out on each read from the same cards the lanes show, and a team member's sections come only from cards they can already see. The waiting lane's soft cut now breaks equal-time ties by card id, so every machine keeps the same cards.

The Work Board is still switched on only for development agents.

A person can now close a work card in Luna's two ways: **Done** with a closeout note, or **Not important** with a reason. Both are the owner's own tap (the dashboard PIN, or Face ID on the phone, where the note is part of what Face ID signs); the agent can never close a card. A close is an `archive` tap with `closeAs` (`done` or `not-important`) and a required `note`; `unarchive` reopens it. A Done card shows with the done cards and its note; a Not important card is archived.

"Not important" reasons become the agent's lessons: `GET /work-board/lessons` lists them with who gave them and which card they came from, and the agent's card-create answer carries the newest ten, so it sees them at the moment it raises a new card.

Every card now says whose turn it is (`turn`: `you`, `agent`, `others` or `nobody`) so screens can colour it, whether work has started (`started`, `startedAt`; untouched cards are listed first), and names its own conversation with the existing read and send routes (`conversation`), so the card and its chat can sit on one page.

The Work Board is still switched on only for development agents.

Each project on the Work door now says what the Chief of Staff knows: its latest report on the project, why it is waiting on you, when it is next checked, why it stopped retrying, and each done item in words ("Passes", "Waiting for you to check", "Checked by you"). The phone gets four actions on a project: Ask for an update (the Chief of Staff checks it now, or on its next round), Pause and Resume, Mark checked on an item only you can judge, and Finish. The last three need Face ID on the owner's phone; the agent cannot do them for you.

Routes: `POST /work/projects/check` (bearer) and `POST /mobile/work/projects/check` (owner phone); `POST /mobile/work/projects/pause`, `/done-item` and `/finish` (owner phone, Face ID, challenge actions `project-pause`, `project-item-check`, `project-finish`). The read's new fields are additive.

## What to Tell Your User

- **Helper machines can't fake a passing test run**: "When another of my machines runs tests for me, it now signs the result, and I check the signature before I believe it. Even a signed pass on the main code only counts for a while before I check it myself."

Nothing to do. One way someone on your network could have tricked your agent's computers into sending each other the agent's master key is now closed off. If one of your computers ever has a real problem answering, you'll see a notice saying so, instead of the key being sent.

- **Decisions show up as cards**: "When one of your projects is waiting on you, it now shows up as a card on the work board, with what it needs, my recommendation and why it needs you. It closes by itself once you have answered."
- **Fewer taps**: "A card that only asks you to do something no longer needs an Approve tap first."

- **My board**: "Your Work tab now opens on the cards that need you, grouped by why: waiting for your approval, waiting for your reply, your own cards, and anything on hold. Each card shows once, and the ones nobody has touched yet come first."

- **Closing cards**: "You can close a card as Done with a short note, or as Not important with a reason. I read those reasons before I raise a new card, so I stop asking about things you've told me don't matter."
- **Whose turn**: "Each card now says whether it's waiting on you or moving, so your screen can colour it, and cards nobody has touched yet come first."

- **Projects tell you what is happening**: "Each project on the Work page now shows my latest report, what it needs from you, and when I'll check it next."
- **You can act from your phone**: "You can ask me to check a project right now, pause it, tick off the items only you can judge, and finish it, each with one tap and Face ID."

## Summary of New Capabilities

| Capability | How to Use |
|-----------|-----------|
| Signed peer verify results | Automatic wherever peers are configured |
| Bounded authority for a peer's main green | Automatic with `mainOnPeers` on |
| Clear a helper machine kept off main | Console: Work, then Development, card "A helper machine no longer tests main" |
| Peer trust status | `GET /local-verify` → `peers.trust` |

- The signed-read bearer fallback is refused for any peer ever seen at a version that serves the read.
- `GET /pool/signed-reads` counts refused fallbacks.

| Capability | How to Use |
|-----------|-----------|
| Chief of Staff wait cards | Automatic when the board is on; `workBoard.chiefOfStaffCards` switches them |
| Required recommendation and why-you on agent cards | `POST /work-board/cards` with `recommendation` and `whyYou` |
| A card linked to its Needs-you item | `covers: ["plan:<id>"]` or `["pr:<n>"]` on the card |

| Capability | How to Use |
|-----------|-----------|
| My board sections | `myBoard.sections` on `GET /work-board` and `GET /mobile/work-board` |

| Capability | How to Use |
|-----------|-----------|
| Close a card as Done or Not important | Owner tap with `action: "archive"`, `closeAs`, `note` (PIN on the console, Face ID on the phone) |
| Dismissal lessons | `GET /work-board/lessons`; also `lessons` on the agent's `POST /work-board/cards` answer |
| Whose turn, started, conversation | `turn`, `started`, `startedAt`, `closeout`, `conversation` on every card read |

| Capability | How to Use |
|-----------|-----------|
| Ask for an update on a project | `POST /work/projects/check {key}`, or the button on the project's row in the app |
| Pause / Resume, Mark checked, Finish from the phone | Buttons on the project's row in the Instar app (Face ID) |
