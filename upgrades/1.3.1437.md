## What Changed

- `src/feedback-factory/execute/executePolicy.ts`: `buildClaudeSandboxSettings` no longer writes one Read/Edit deny rule per entry under `<agent home>/.worktrees/`. Claude Code folds every such rule into the Bash sandbox profile it passes on the shell's command line; with 2,279 sibling worktrees (Mac Studio, 2026-10-25) that profile held 4,891 deny rules, the command line passed 1 MB, and every Bash call in the confined session failed with `E2BIG` before running. The canary's `session-bash-write-in-workspace` probe failed, and after eight failures the executor latched for a day. Siblings stay covered without the list: the sandbox filesystem block already read-denies the whole home and re-allows only the attempt's trees, and `dontAsk` refuses the file tools every path outside the exact allow list. `ClaudeSettingsInput.worktreeChildren` is removed. The agent home's own entries are still denied one by one.
- `src/feedback-factory/execute/confinementCanary.ts`: new fixture `siblingNoncePath` (a nonce file directly under `.worktrees/`, beside the workspace); the runner canary adds `bash-read-sibling-worktree` and `bash-write-sibling-worktree` (must fail) and the session canary adds steps 17–21: Bash `cat` and the Read tool on the sibling nonce, then Read, Write and Grep through a workspace symlink to the sibling directory (made by trusted code, because the file tools' allow rule matches the path as written). Judged by the existing nonce-never-read and transcript read checks, a new `write-sibling-worktree` effect check, and three new transcript checks: `session-write-probes-attempted` / `session-grep-probes-attempted` (an answered Write call per exact write target — steps 6, 16, 20 — and an answered Grep call on the exact sibling path; a skipped must-fail step no longer passes by absence) and `session-grep-never-matched` (a Grep answer naming the nonce or the nonce-named file `sib-<nonce>.txt` fails, so a wrongly allowed search that matched nothing is still caught). `SESSION_CANARY_STEPS` 16 → 21. The fixture directory is removed by `close()`, and `pruneScratch` sweeps a crash leftover after 14 days. `session-git-status` now also fails on `could not start` / `E2BIG`: on 2026-10-25 a shell that never started reported that for step 9, which matched none of the failure words, so the probe passed.
- `CANARY_VERSION` → `feedback-canary-v2`, and the canary latch records the version that wrote it. `effectiveLatchUntil` treats a latch from another canary version (or from code that predates the field) as not in force, so a fix that changes the canary clears its own latch on install instead of serving out a day-long wait. A failing current canary re-latches under the new version and climbs the ladder as before.
- `src/feedback-factory/execute/attemptFs.ts`: `shortAttemptTmpDir` takes an optional `scope`; the executor passes its agent home. Without it two executors on one host with the same initiative id shared one `/private/tmp/fb-<id>` directory, and `ensurePrivateAttemptTmpDir` removed it under the other one's live attempt. That is the cause of the feedback-executor unit tests failing about one run in two under concurrent suites (the canary report vanished mid-attempt). An attempt live across this upgrade recomputes a different temp path; none was live on the operated host.

The standalone `instar-witness` CLI can now talk to a Witness registry (built by Dawn; the current default address lives in the one constant `DEFAULT_REGISTRY`, and `--registry <url>` points at another). `witness publish record.json --binding binding.json` verifies the record here first (and sends nothing if that fails), posts it, checks the server's `recordHash` against the one computed locally, and prints `{ ok, recordHash, duplicate, registered }`; a 422 prints the server's reason unchanged. `witness lookup --subject <did>` / `--issuer <did>` and `witness get <hash>` re-verify every returned record against the binding the server supplied and label each `verified`, `expired` or `failed(reason)`, with each line led by the issuer; a `revokedBy` is shown only when the revocation itself verifies and comes from the same issuer; everything the server merely asserts is reported under `unverified`. `witness stats` prints the server's counts as its word. Node's built-in fetch, no new dependency, 15 s timeout, 4 MiB response cap, https only (plain http for localhost). The record-against-binding check is now one shared function (`verifyRecordWithBinding`) that `verify`, `publish`, `lookup` and `get` all use. Only `packages/witness` changes (published as `instar-witness` 0.2.0); no Instar server code.

## What to Tell Your User

The safety check before the feedback pipeline writes a fix kept failing because the sealed workspace's shell could not start: its rules listed every other work folder on the machine, and with over two thousand folders the list became too long to launch. The rules no longer grow with the number of folders, a new check proves other folders stay unreadable, and the day-long pause that failure caused clears itself when this update installs.

Nothing changes for Instar agents. If you use the separate witness command, it can now publish a signed record to the shared registry and look up what other agents have recorded, and every record it shows you has been re-checked on your own machine; the registry is a place to find records, never the thing that makes them true.

## Summary of New Capabilities

None — internal fix. The canary gains sibling-worktree read/write probes (direct and through a workspace symlink); the latch gains a version field.

- `witness publish` sends a locally verified record to the registry and refuses a mismatched server hash.
- `witness lookup` and `witness get` re-verify every record read back and label it; revocations count only when they verify.
- `witness stats` shows the registry's counts, labelled as the server's word.
