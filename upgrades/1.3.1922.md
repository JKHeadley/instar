## What Changed

A verify that fails says so late: a lane's failure is known only when the whole lane has ended, 25 to 40 minutes in on the Studio. Local Verify can now run a small first part of each lane before the rest, so a failure in a likely file shows a couple of minutes after the lanes start. It is off by default and set per machine.

- **The setting.** `monitoring.localVerify.likelyFailingFirst` is `off` (the default), `on` or `alternate`. Each run machine reads its own value at the start of each verify it runs. With it off, a verify runs exactly as before: the same commands and the same reports.
- **Three things happen whatever the setting,** so that the switch can be turned on for one machine at any time:
  - The coordinator keeps the likely-failing list up to date (`state/local-verify/likely-failing.json`, one `likely-failing-updated` audit row per change).
  - A verify record may carry one new optional field, `rerunCutOff`: the failed files whose second try was cut off because another lane had already failed. Only when there is such a file. The list leaves those files out.
  - The coordinator assigns each new pull request to the trial's "with" or "without" group when it is first queued, writing `state/local-verify/first-part-groups.json` and one `first-part-assigned` audit row. With the setting off nothing reads the assignment.
- **The first part.** For a verify of a pull request, each of the three lanes first runs:
  - the test files the change adds or edits,
  - the files the same change failed on in its previous verify,
  - the lane's files from a list of files that failed for other pull requests in the last 7 days.
  - Limits: 80 files in the unit lane; 20 in integration and 12 in end-to-end, each also held to 60 seconds of recorded time.
- **What a failure there does.** The existing rules are applied earlier, not changed. A failed file still gets its second try alone. If it still fails, the lane does not start the rest of its files, the existing fail-fast stops the other lanes, and the verify is recorded as failed. With fail-fast off, nothing ends early.
- **No test is removed.** A clean first part only lets the rest of the lane start. A pass is declared only after every test in the run has passed.
- **The list.** The coordinator updates it whenever it records a failed verify of a pull request, its own or one a peer ran. A file keeps one entry per pull request (its latest failure). It sends the list with each verify it hands to a peer. A lost or unreadable list is empty and rebuilds.
- **The trial setting.** In `alternate`, the coordinator assigns each pull request once to "with" or "without" first parts and keeps that for every later verify of it. A machine in `alternate` also checks itself: the first 5 verifies of each kind (ended in a first part, failed later, passed) are followed by one comparison run of the same code without first parts. A difference on a file that is not already known to be unreliable sets the switch to `off` on that machine and raises one notice.
- **Main verifies are unchanged.**
- **The verifier's version changes** with this build, as with any change to the lane flow. A coordinator and its peer must install it together: until both have, the coordinator hands the peer nothing.

The native password helper now refuses Enter if its exact owed relock record is missing, belongs to a different request or producer, is already relocking, or cannot be saved. Both validation and atomic replacement must succeed. Existing cancellation and field-clearing behavior stays in place.

The combined locked-Mac proof harness waits for its exact approved request receipt as well as visible controls before starting a case. Missing or expired evidence fails after a bounded wait.

Case 12.18 arms a request-scoped stale immutable heartbeat before password submission, leaving the real guard and production controller unchanged. It recognizes the viewer's real refusal and requires measured guard identity, unchanged heartbeat, no submission, grant termination, fixture restoration and a locked final screen. A durable ownership receipt records the server grant deadline and possible submission before the password UI starts. Failed revocation retains the fault until exact revocation or original grant expiry, including startup and rollback recovery.

Internal: Correct locked-Mac proof human-step sequencing. User-switch checks wait for departure, dwell and return; logout starts the watch and confirms departure/old producer exit before the login cue. Delayed unlock cues use the recorded watch start and new observations. Switch/logout native lock-call evidence remains explicitly unmeasured. No live proof or rollout readiness claimed.
Human cues now require a confirmed full Telegram receipt (or explicit console-only mode), carry case/run and START BY times, and fail on partial, unknown or late delivery. No automatic resend. The visible deadline does not cancel messages held by the transport.
The first relevant human action must also be observed before START BY. Repeated-unlock cases wait for the initial locked watch before cueing and require a fresh first unlock, without claiming to count all manual repetitions.

Account-switch/logout proofs now require complete A+B histories, exact child exit, unchanged native counts, and final reads after the observed human return.

## What to Tell Your User

Nothing changes until you turn it on. If you use Local Verify to test your own changes, I can now run the test files most likely to fail first, so a failing change is found in minutes instead of half an hour. Every test still runs before anything is called a pass. It is a setting per machine, and there is a trial mode that uses it for half of the pull requests and compares.

A locked-screen password submission stops safely if its relock record cannot be saved. Locked-screen access still requires the existing hardware proof before it can be enabled.

No new action is needed. This improves developer proof reliability; a live Mac acceptance run is still required.

No new action is needed. This is a proof-harness reliability change; live Mac acceptance and fleet enablement remain separate.

The instructions for the locked-Mac checks now include a deadline and wait for the requested action to be observed. Ignore a cue that arrives late or belongs to a stopped test. These are test-runner corrections; locked-screen access is not enabled by this change.

No new action is needed. This is a proof-harness reliability change; live Mac acceptance and fleet enablement remain separate.

The locked-Mac test runner now rejects timing it cannot establish, including an interruption that starts before Enter but finishes afterward. This corrects test evidence; it does not change remote desktop lock behavior or enable locked-screen access.

A previous passing result for either case needs fresh evidence of when the server actually expired the connection.

No new user action is needed. This improves the developer proof harness; it does not claim that a live locked-Mac acceptance run has passed.

The proof can now distinguish a measured zero from missing evidence. This does not enable locked-screen access or certify a Mac. Updating the native helper requires the usual permission validation.

## Summary of New Capabilities

| Capability | How to use it |
|---|---|
| Run likely-failing test files first | Set `monitoring.localVerify.likelyFailingFirst` to `on` in `.instar/config.json` on a run machine |
| Trial on half of the pull requests, with a self-check | Set it to `alternate` |
| See the setting, the list and the trial counts | `GET /local-verify`, field `likelyFailingFirst` |
| Audit rows | `first-part` per verify, `likely-failing-updated`, `likely-failing-unreadable`, `first-part-compare`, `first-part-switched-off` in `logs/local-verify.jsonl` |

No new operator action or permission. This tightens an existing safety check.

No product capability added. Proof sequencing now rejects an asynchronous response-body race.

The developer proof harness can establish and recover an exact missing-acknowledgement fault before password submission. Product authorization and relock policy are unchanged by this harness change.

None. Existing proof steps now reject unconfirmed messages and stale or late action evidence.

The developer proof harness requires a positively confirmed next grant before accepting takeover evidence. Product authorization and relock policy are unchanged by this harness change.

None. Existing proof checks now require sufficient raw timing evidence. No native helper changes, migrations, or product restarts.

Developers can now distinguish an unmeasured expiry from an early duty closure in the same report.

The proof harness can check an actual watch-end failure with bounded independent recovery and exact security-item timing. Product relock policy is unchanged.

Read-only guardObservation and observedLoginSession fields on GET /desktop/locked/status support bounded native proof evidence. Missing, incomplete or restarted histories never count as a zero.
