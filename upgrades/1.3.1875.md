## What Changed

After a restart, the Conversations pages (including Suggested efforts) could wait behind the agent's start-up checks for many minutes and end with "Your agent did not answer in time." A page that only reads is now answered from the conversation history that is already open, after a short wait of about 1.5 seconds. Saving a change still waits for every check. When the page truly cannot get an answer yet, it says so in plain words and tries again by itself every 15 seconds for about 5 minutes. The log now names the step the agent was busy with, and records "ready" after a restart.

The dashboard has a new "Machine care" page (under Capacity, and linked from the Machines page). It says in one sentence per machine whether it is signed up for its weekly clean restart, when it last started, and whether a night is skipped. For the machine you opened it on, it has Sign up, Skip once, Change window and Restart now. Skip and Change window ask for your dashboard PIN. Sign up and Restart now send you a card in Telegram, and nothing happens until you tap it there. It works on a phone.

The person can now approve a change that widens what the agent may do, from their own direct chat with the agent (trust journey stage 0, part B; docs/specs/trust-journey.md). The agent opens the exact request; the server sends a card into the owner's Telegram private chat with the bot (or Slack DM) that says, in plain words, everything the change would widen, and the person replies `approve <code>` to that card. The first time, the person is asked once to send back a one-sentence acceptance that replies from their account count as their approval. Only a reply that really arrived from the platform counts: not the agent's token, not the dashboard PIN, not a phone tap, not a message replayed after an outage. Every approval says plainly that it came from an account the agent can also use. Trust changes are now kept in a durable log (replicated where the machines share one), and at startup each stored setting is checked against it: anything wider than what was approved is put back, and the owner is told once. A console switch whose setting needs approval now opens the request instead of failing.

External tool calls now follow the person's trust settings (trust journey stage 0, part C; docs/specs/trust-journey.md). The agent server, not the agent, now works out what each tool call does from its real name and input. Kinds of action the agent already used before this update keep exactly their old behaviour until the person changes them. A new kind of action, signing in with a stored password in the browser, or anything that speaks publicly first asks the person: a card listing the exact call goes to their direct chat, and the call runs only after they reply `approve <code>`. One approval covers that one call, and a changed or repeated call asks again. A kind the person has set to "Do it and show me" or "Just do it" runs without asking when its effect is clear. When the agent server cannot be reached, a governed call is refused instead of slipping through, while known reads and unchanged kinds keep working. Each admitted governed action gets an entry in a new outcome record. A trust settings file that cannot be read is rebuilt from the durable change log, keeping every restriction. Instar's own internal parity check is now a system service and no longer needs a trust setting.

## What to Tell Your User

- **Conversations after a restart**: "Right after I restart, the Conversations pages now load quickly. If my history is still opening, the page says so and keeps trying by itself; you don't need to tap anything."

- **Machine care page**: "The dashboard now has a Machine care page. It shows each machine's restart status in one line, and for this machine you can sign it up, skip a night, change the restart hours or restart it now. Signing up and restarting still need your tap on the card I send you."

- "When you want me to stop asking about something or to work more on my own, I'll send a short card to our private chat. Reply to it with the code it shows, and only then does the setting change. Any other reply changes nothing."
- "The first time, I'll ask you to send one sentence back once, confirming that your replies count as your approval."

- "If I need to do something new on your behalf, like using a service for the first time or signing in with a saved password, I'll send you a card in our private chat showing exactly what I want to do. Reply with the code and I'll do it once. Everything I already did before keeps working as it did."
- "Anything that would post publicly in your name always comes to you first."

## Summary of New Capabilities

| Capability | How to Use |
|-----------|-----------|
| Conversations reads answer during start-up | Automatic |
| Suggestions page retries by itself | Automatic |

| Capability | How to Use |
|-----------|-----------|
| See and control a machine's weekly restart | Dashboard → Capacity → Machine care |

- Approving a widening from the person's own direct chat: a server-written card, answered with `approve <code>`.
- A durable trust change log, with a startup check that puts back any setting wider than what was approved.

- Tool calls are classified by the agent server from their real name and input, and new or sensitive kinds ask the person first with a one-action card.
- Existing kinds keep their old behaviour; governed calls fail closed when the server cannot be reached.
- A rebuilt-from-log recovery for an unreadable trust settings file.
