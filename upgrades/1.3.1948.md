## What Changed

SEC-139. The relay derived every caller address from the first `x-forwarded-for` entry, which the caller writes, so per-address rate limits (sign-in attempts, messages, registry, A2A) could be bypassed by changing it on each request, and A2A thread scoping could be aimed at another caller's address. Now `resolveClientAddress` (`src/threadline/relay/clientAddress.ts`) is the single source for the WebSocket, registry and A2A paths: it trusts only the header named by `RELAY_CLIENT_IP_HEADER` (set to `fly-client-ip` in `fly.toml`), takes the right-most entry when that header is `x-forwarded-for`, requires a valid IP, folds IPv4-mapped IPv6, keys IPv6 callers by their /64 network for rate limits (one subscriber usually holds a whole /64) while A2A thread scope keeps the exact address, and otherwise uses the socket address. The relay's own per-address state is bounded too: `RelayRateLimiter` and the registry rate-limit maps delete idle keys (swept at most once a minute) and have hard ceilings: 100,000 keys for the rate limiter, dropping the least recently used first and never the global window, and 50,000 per registry map, dropping the entries whose window started earliest.

The A2A bridge also allows one waiting message per conversation, so an agent reply can only go to the caller that asked; a second message before the reply gets error -32005.

Self-hosted relays behind a proxy must set `RELAY_CLIENT_IP_HEADER` to the header their proxy sets; without it every caller shares the proxy's address.

A machine whose lease role changes asks for one planned restart (`state/restart-requested.json`, `requestedBy: role-change`). The request waits while a Local Verify run is in progress. If the role went back to what it was at boot while the request waited, the restart still ran. On 2026-11-20 the Mac Studio lost the lease at 15:43Z, had it back at 15:53Z, and was restarted at 16:03Z for "this machine gave up the lease". The restart ended the verify in progress and left the lease unrenewed for the length of a boot.

`reconcileRole` in `src/commands/server.ts` now calls `withdrawRoleRestart()` (new, in `src/core/roleFollowRestart.ts`) when the role matches the boot role. It removes the request only when it was written for a role change by this same process. Requests from an update or any other writer are left alone. The 15-minute stamp is kept, so the limit on role restarts is unchanged.

- New shared rule `src/core/unroutableOwner.ts`: a topic owner is *unroutable* when the machine registry marks it revoked, or when it is absent from the registry and the pool view and its replicated journal has been silent at least 9 minutes (with a fresh journal sync, outside the first 9 minutes after boot). An unreadable registry, no journal evidence, or recent activity all read as routable.
- Session router: an inbound message for a topic whose owner is unroutable is taken over by the lease holder (version-conditioned `force-claim`, journaled as a placement) and answered there, after the usual local placement checks. Before, the owner-dead path used `place`, which the ownership FSM refuses on a live record, so the message waited in custody forever.
- Stale-owner engine: unroutable owners are treated as expired without adverts or probes, and their claims land even while the engine is in dryRun (opt-out `multiMachine.sessionPool.staleOwnerRelease.unroutableOwnerLive: false`). Lease-holder-only, per-tick cap and per-topic budget are unchanged.
- `POST /pool/transfer`: a topic owned by an unroutable machine now really moves (force-claim to the target, `seatMoved: true`), and the transfer no longer asks for an unsatisfiable confirmation because the dead owner's run state "could not be verified".
- Fixes the U4.2 evidence-5 mirror lookup: it read `streams[machineId]`, but journal streams are keyed `<machineId>.<kind>`, so every owner looked quiet. The check now sees real recent activity.

## What to Tell Your User

- **Relay hardening**: "The public relay no longer believes a caller about its own address, so its speed limits can no longer be dodged by writing a fake one, and it cannot be made to fill its memory with fake callers."

Nothing to do. When one of your computers briefly lost the lead role and got it back, it could still restart several minutes later for no reason, which threw away a test run in progress. It no longer does.

If one of your computers is wiped or replaced, the conversations it was handling now move to a working computer by themselves, so your messages keep getting answered instead of only "your message didn't reach the session" notices. Moving a conversation by hand also works in that situation now.

## Summary of New Capabilities

| Capability | How to Use |
|-----------|-----------|
| Trusted caller-address header for the relay | Set `RELAY_CLIENT_IP_HEADER` for a relay behind a proxy (Fly: already set) |

| Capability | How to Use |
|---|---|
| A waiting role restart is cancelled when the role is back to its boot value | Automatic. The server log says "the waiting role restart is withdrawn" |

- Conversations owned by a removed or replaced machine are taken over automatically by the machine in charge.
- Manual moves of such conversations succeed and report truthfully.
