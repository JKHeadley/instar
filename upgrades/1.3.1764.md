## What Changed

`SessionBuildContextStore` keeps one row per tmux session (where it was spawned, where it is working), so a restarted session can be told which worktree it was in. A row older than six hours is never restored, but nothing removed it: every session ever spawned kept its row.

`record()` now writes the store without the rows past the max age (`withoutExpired`). Reads are unchanged. An unchanged session still writes nothing.

One consequence: a session that has stayed in one worktree past the max age loses its row at the next write, and the monitor's next pass records it again as current. Before, that row stayed expired and a restart did not restore a worktree the session was still in.

`LocalVerifyService.doRestoreQueue()` rebuilt each restored entry with `baseSha: view.baseRefOid`, the PR's base as of its last update on GitHub, and kept the saved `baseResolvedAt`. `request()` and the pre-start refresh never use `baseRefOid` (see the `baseHead` seam: "can be days stale"); restore did. Because the reconcile loop re-requests queued PRs every few minutes, the saved `baseResolvedAt` was usually seconds old, `mainMovedAt` is in-memory and null after a restart, so `decideBaseRefresh` was false and the first local start and the first peer dispatch after a restart ran on the stale base.

Now a restored entry keeps the saved `baseSha` (the last one this service resolved through `baseHead`), and a non-reserved entry comes back with `baseResolvedAt: 0`, so the pre-start refresh always runs for it. An entry reserved for a peer attempt is unchanged. `0` is not written to the durable queue.

Also in this change: a run on a peer machine that ends red now writes a `run-detail` row (`source: "peer-run"`, with the attempt id, reasons and each failed file's first error) to that machine's own audit log. The coordinator imports only the record, so a peer failure named no file on either machine.

`LocalVerifyService.shutdown()` treated any in-flight run as interrupted: it sent SIGTERM to the run's group, counted an interruption, put the entry back at the head of the queue, and left the run's result file unread. A planned restart is released by `PlannedRestartVerifyGuard` as soon as the run child is no longer alive, which can be before the server has handled the child's exit event. In that window the run is finished and its result is on disk, and `shutdown()` discarded it.

`shutdown()` now reads the in-flight run's result file first. If it holds a result object, the run reached its verdict (the child writes the file with a temporary name and a rename as its last act, after its own cleanup): the server audits `settled-at-shutdown` and runs the normal exit handling, so the record is journaled before the process exits. Nothing is counted as an interruption.

Not settled when the server can see that the verifier on disk has changed (an update replaced it; a change it cannot see, or a policy change, is not covered): the restart then loads a verifier whose index ignores a record this one writes, so the run has to happen again anyway, and the interruption path keeps the entry at the head of the queue for that.

`onExit` handles a run exactly once (a `settled` latch on the in-flight object), so the child's real exit event arriving after the settle cannot record a crash over the verdict.

A run with no result file at shutdown is an interruption, exactly as before.

`AutoUpdater` keeps a durable restart deferral (`state/auto-updater.json` → `restartDeferral`) when an installed update's restart must wait for in-flight work. `start()` re-arms its retry from that record. The record was cleared only when the updater itself performed the restart. When anything else restarted the server while the deferral waited (a planned restart request, the supervisor, a crash), the new process booted on the target version, resumed the stale deferral and restarted again onto the version it was already running. While a deferral is pending, Local Verify pauses dispatch.

`start()` now calls `dropSatisfiedRestartDeferral()` first: when a deferral is active, `ProcessIntegrity` holds the version this process booted with, both versions parse, and the target is not newer than the running version, the deferral is cleared and state saved. Otherwise nothing changes.

## What to Tell Your User

Nothing changes that you will see. A file the agent re-read many times a minute had grown without limit; it now stays small, which removes a steady drag on how quickly the agent answers.

Nothing changes that you will see. After a restart, the first changes tested could be checked against code that was hours out of date and fail for reasons already fixed. They are now always checked against the current code.

Nothing changes that you will see. When the agent's server restarts for an update just as a test run finishes, the result of that run is now kept, where before the run could be thrown away and started again.

Nothing changes that you will see, except that after some updates the agent used to restart twice in a row and now restarts once.

## Also fixed here

`readResult` returned whatever the result file parsed to. A file holding a bare JSON string, number, boolean or array parsed without error, and the exit handler's `'degradations' in result` then threw a `TypeError` out of the exit promise: an unhandled rejection in the server and no record for the run. `readResult` now returns `null` for anything that is not a JSON object, which the exit handler already records as a crash and retries. Found because this change's own junk-file test raised that rejection: all 157 tests passed and the file still exited 1 (the Local Verify failure of this PR on 2026-11-13 16:51Z, "unit lane exit 1, 0 failed tests"). One test added; 158 pass with no unhandled error.
