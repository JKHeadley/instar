# R2 — Acceptance gates now count the work they accepted

The Phase 4 acceptance gate used to look for a piece of text such as `7 ok, 0 fail` or `0 fail` in a command's output. That sounds reasonable until ordinary substring rules are applied: the characters `0 fail` also occur inside `10 fail`. The mistake is latent rather than an actively exploitable release hole because the same gate checks the command's exit code, and the parity runner currently exits non-zero when a scenario fails. The exit-code check happens to catch the bad run today. It does not make the text assertion correct.

Those two checks answer different questions. The exit code answers whether the runner says anything failed. The output assertion is supposed to prove that the expected population of work actually happened. A runner that executes zero scenarios and exits zero is green according to the exit code, even though it proved nothing. The old substring assertion could not reliably distinguish that empty run from a real seven-scenario pass, and it could mistake ten reported failures for zero.

R2 gives the parity CLI a machine-readable `--json` mode. It emits one versioned JSON document with exact `total`, `passed`, `failed`, and `skipped` counts derived from the typed `ParityResult[]` the runner already produces. The acceptance manifest now declares the precise counts it expects. Structural parity must account for seven results: five pass and the two real-API scenarios skip because real API is disabled. Real-API parity must account for seven passes with no failures and no skips. The checker parses the whole JSON document, verifies its schema, and compares those fields by type and exact value.

The controls make the distinction visible. A marker-backed runner that prints `10 fail` and exits zero is rejected. A runner that reports one structured failure but exits zero is rejected, proving the new assertion does not lean on the exit code. A runner that reports zero scenarios and exits zero is rejected. An exact seven-scenario all-pass summary is accepted. The ordinary human-readable parity report remains available when `--json` is absent, and the unrelated smoke test can continue using its `PASSED` text sentinel.

No new package was added. The old manifest named `npx tsx` even though `tsx` is not present in the committed lockfile or installed dependency tree. R2 uses the repository's already-pinned `vite-node` entry instead. Vitest acceptance commands explicitly disable their mutable results cache, so the proof does not silently depend on or rewrite shared scheduling state.
