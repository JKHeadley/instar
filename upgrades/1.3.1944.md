## What Changed

An agent with no Cloudflare tunnel, no Tailscale name and no Telegram (every agent the Windows app makes today) could not pair a phone: pairing answered `409 stable-address-required`. Now the owner can add a first phone at home, on the same Wi-Fi, at the agent's own computer. The computer asks for the dashboard PIN, opens a small second HTTPS listener with the agent's own certificate, and shows a version-2 pairing link (a QR code in the apps) carrying that certificate's public-key hash. The phone pins the hash before it speaks, redeems, and shows a six-digit number the agent issued; the owner types it at the computer, and the phone signs its own activation. The phone is then an owner phone for conversations that cannot approve yet. The listener is closed until asked, opens only on a network the owner allowed, closes itself when nothing uses it, and serves no dashboard, PIN, token or computer-bound route. Nothing arriving on it is ever treated as local. New terminal command: `instar mobile add-phone`.

The home-network port defaults to the main port + 20000 (4040 -> 24040): the first default, main + 1000 (5040), is held by Windows' own Connected Devices Platform service on every Windows 10/11 PC. A caller may ask for an exact port (`port` in `POST /mobile/phone-setup`, `--port` in the terminal); it is never swapped for another and never moves while a phone is paired on the home address (`409 port-fixed`).

The Instar app on the agent's own computer (identity A5) may start the setup with a one-time credential instead of the PIN, which an app-made agent's owner was never told: `instar mobile ceremony-credential`, run as the agent's own user inside its own system, writes the credential's hash to a 0600 file and prints it once. It is accepted only on the main listener from this computer (the exact loopback Host, no forwarding header), only where the app the installer enrolled on this machine exists, only for an agent with no owner phone and no Telegram owner, on the lease holder, once, within ten minutes. Any refusal is final: it never falls back to the PIN.

Inside WSL the home address reads WSL's networking mode (`wslinfo`, else the Windows user's `.wslconfig` and WSL 2's NAT default) instead of guessing it from the address range. NAT opens on WSL's own NAT address; mirrored stays closed (`409 wsl-networking-mode`) unless the Windows app says it enforces the network rule (`windowsAppHandlesNetworkRule: true`), and then binds loopback with the per-address limit on; unknown or other modes stay closed. Owner actions on the home address (open, allow, close) now run one at a time, the ceremony credential's file is checked through the one handle it is read from, and the two fields that mark a phone let in at the computer are kept in agreement by the device store. Anything arriving on the home address other than the pairing redeem and ping needs a verified device signature even on an agent with no token, a home or at-computer phone is never a document device, and approval notices are not pushed to a phone let in at the computer.

Before, only the dashboard sign-in screen had full protection against PIN guessing. Several owner actions had none, step-up and the mandate PIN counted every internet caller as one, and the money-layer routes kept one counter that could lock everyone out for 15 minutes. Now one policy covers them all:
- **Public routes** (sign-in, step-up, the email-code page) use the sign-in screen's limits: each visitor has its own budget, and an overall cap of 20 wrong guesses per 5 minutes survives a restart.
- **Approval links** are limited per live request, so a stranger cannot use one up.
- **Owner actions behind sign-in** are limited per credential, so another caller's wrong guesses never refuse the owner's right PIN.
- **The guess counter file** is pruned and capped. If it is damaged, PIN sign-in from unknown browsers pauses for one window rather than letting guesses through. A failed write keeps counting in memory.
- **Settings** can now only make the limits stricter. The old off switch is ignored.

The iMessage adapter creates a hard link to the Mac's `~/Library/Messages/chat.db` inside the agent's state folder at start-up, so the agent's server can read iMessage history without itself holding Full Disk Access. Until now the source of that link was hard-coded to the real home folder, so every test that built the adapter without an explicit `dbPath` reached for the operator's real Messages database. On a Mac whose privacy (TCC) state answers that reach with a pending "Allow Full Disk Access" approval instead of a fast refusal, the `link()` system call parks in the kernel until someone clicks — and on an unattended machine nobody does. That is what froze the Studio's Local Verify unit lane at exit from ~12:46 PST on 2026-11-20 (every PR verify cut off at the 40-minute deadline) while the M5 ran the same PRs fine.

- `IMessageAdapter.ensureChatDbHardlink(stateDir, messagesDir?)` now takes the Messages directory as a parameter. Its default, `IMessageAdapter.defaultMessagesDir(stateDir)`, is the real `~/Library/Messages` in production (the `VITEST` environment variable absent) and a never-created stand-in directory inside `stateDir` under the test runner.
- Under test the helper therefore sees "no chat.db here", returns its existing fallback path, and issues no filesystem call against the real Messages folder. A test that wants to exercise the linking code passes a fake Messages directory explicitly.
- Production behaviour is byte-identical: no production caller passes the new argument and the production default is the previous hard-coded value.

On a two-machine Local Verify line (a coordinator and a peer verifier), each planned coordinator restart used to cost the peer work in two ways: no new work was handed to the peer while the coordinator waited to restart, and a peer run that spanned the restart was thrown away because the coordinator came back at a new lease epoch. Measured over two days that was up to about 105 peer-minutes a day.

Behind one live setting, `monitoring.localVerify.peerWorksThroughRestart.enabled` (absent or anything but `true` = off = today's behaviour exactly; no config default is written):

- **Dispatch during a restart pause.** The coordinator may hand a PR verify to an idle peer while a restart is pending, unless the verifier on disk already changed or the restart is forced (`bypassHolds`). A `main` verify is never handed out then, and the coordinator's own slot still starts nothing.
- **Restart episodes.** The coordinator tracks each pending update or planned restart as an in-memory restart episode. An attempt sent during its pause carries the episode id (`sentDuringPause`) and does not hold that episode's restart; after the episode ends without a restart it holds later restarts like any other. Each episode ends with a `restart-episode-ended` audit row (`restarted`, `qualifying`, `peerIdleMs`, `attemptsInFlightAtRestart`, `pauseDispatches`).
- **Adoption across the coordinator's own restart.** PR 3451's holding record (`peer-trust.json`) gains `holding.since`, the first epoch of this machine's unbroken holding. After a restart the coordinator keeps a peer attempt dispatched at an earlier epoch when that holding is unbroken since the dispatch, the entry, verifier and policy are unchanged, and it is not a `main` verify (`adoptedEpoch`, audit `peer-attempt-adopted`). While the lease read is unreadable, unheld or not yet caught up it waits without cancelling (`peer-attempt-adoption-waiting`). Anything else abandons with a `lease-changed:holding-broken|entry-moved|verifier|main|disabled` reason. A `lease-changed:verifier` abandon gives the attempt back once per entry. The peer's signed record must still name the dispatch-time epoch.
- **Progress, not the clock alone, ends a peer attempt.** At 60 minutes an attempt is judged on progress read from the run's `*.progress.json` files: it keeps running while files keep finishing within twice their recorded duration (times this run's measured slowdown; a file with no history uses its lane's hang deadline), and ends when it stalls, when progress cannot be read, when the run child is gone, or at a 150-minute backstop. Both sides judge (`peer-attempt-judged`); a running peer answer carries `progress`.
- **The progress files are exact at the end of a test process (also with the setting off).** The test reporter now writes one last progress snapshot when its process's tests are over: nothing running, every started file counted as finished. Before, a completion inside its 5-second write throttle could leave a finished process's files listed as still running. A lane's first part ("likely-failing files first") reads as its lane in the progress check. A process that is killed leaves its snapshot as it was, so the lane-deadline forensics are unchanged.
- **Kill switch.** Turning the setting off makes every lease change abandon and cancel as before, including attempts already adopted.

`GET /local-verify` shows `peers.worksThroughRestart`, `peers.restartEpisode`, and per reserved attempt `sentDuringPause` and `adoptedEpoch`. Existing agents' CLAUDE.md peer line is rewritten (idempotent, content-sniffed) to name the setting, and a feature note is added.

Local Verify already kept a per-file duration history (`.worktrees/.verify/file-durations.json`) for the integration and e2e lanes, which it uses to balance their shards. It now records unit-lane files as well. Shard planning reads only a lane's own files, so unit entries never change an integration or e2e plan. Each run also logs one `unit-wall-factor` row: the unit lane's wall time divided by its file time spread across the workers (1.22 measured on the Studio on 2026-11-18). Later sharding and borrowed-machine slice planning need both numbers (spec `docs/specs/local-verify-borrowed-unit-slices.md`, part A).

A `unit-wall-factor` row carries two marks that say it is not a clean sample, so a reader leaves it out: `firstPart: true` when the lane used a first part ("likely-failing files first"; the first part's own run is inside the wall time) and `reran: true` when files were re-run alone (the wall time holds the re-runs, and the report holds a re-run file's solo time). A unit first part is sized by file count alone, so recorded unit times do not change which files it holds.

The history file grows from about 94 KB to about 315 KB, well under its 2 MB and 20,000-entry caps. The change touches the verifier, so the verifier version changes once with this release; run machines and peers must be on the same release to share work, as with any verifier change.

SEC-126. The Threadline pipe-mode spawner built tmux shell commands and its prompt file path from the thread id a peer agent sent, without checking it. A trusted peer could send a thread id containing shell syntax and run a command as the agent. `PipeSessionSpawner` now refuses any thread id that does not match the canonical thread-id allowlist (`THREAD_ID_RE`) in both `shouldUsePipeMode` and `spawn`, before any command or file is built. Such a message takes the normal reply path instead.

SEC-136. `RelayClient` emits `error` for a relay `{type:'error'}` frame, and `ThreadlineClient` re-emitted it. On the agent server (`ThreadlineBootstrap`) nothing listens for `ThreadlineClient`'s `error`, and an `error` event with no listener throws, so one error frame from any relay exited the server process. `ThreadlineClient` now re-emits only when a caller listens; otherwise `reportUnheardRelayError` (`src/threadline/client/relayErrorReport.ts`) logs one line and reports a health degradation (`ThreadlineClient.relayErrorFrame`), at most once per error code per 10 minutes, with the relay text stripped of control characters and cut to 200 characters. A frame that is not an object, or whose fields are the wrong shape (a challenge with no nonce, a null envelope, a discover result with no list), can no longer throw out of the relay message handler either, an envelope is accepted only when its fields are really text, and the server's two async relay listeners catch their own failures (a throw there was an unhandled rejection, also fatal): it is dropped and reported the same way, with at most 5 reports per 10 minutes in total and only the code in the report. Callers that listen still get the frame. The ban handling that runs on these frames is unchanged.

Boot claim safety, increment 1 of the takeover-ready pool (spec `docs/specs/takeover-ready-pool.md` R1, feedback fb-2bf6ccd0-705, outage repair N4/A4). Fix id: `boot-claim-safety`.

On 2026-11-20 a restarted Laptop read its own `lease-local.json` ("I held last, lapsed"), could not reach the Studio in its first ~10 s, and claimed the next epoch while the Studio was the live holder. The two then fought over the lead (36 moves in six hours). The ask-peers-first step was skipped whenever `preferredAwakeMachineId` was set, because `server.ts` makes `survivorMayHold()` hard-false then, and the boot claim ran before the lease pull loop started.

Now, from process start until the *boot hold* ends:

- A machine whose own lease lapsed (or that has none) asks its peers before any claim, whatever `survivorMayHold`, `soloCaptainHold` or the preferred machine say.
- A machine that is not the named preferred machine and has reached no peer defers every claim.
- While the named preferred machine answers at all, no other machine claims. A signed reply always counts. An unsigned reply counts only if it carries Instar's own response marker (the new `X-Instar-Machine` header, a fingerprint of the machine id) on a Tailscale or named-tunnel endpoint, and only for a bounded window: 45 s + 3 min for now, or the preferred machine's published restart time + 60 s once it publishes one (floor 45 s, ceiling 10 min). A tunnel edge's 52x/530, an error page without the marker, a LAN or quick-tunnel address, and a legacy dial with no endpoint kind never count.
- The hold ends when a peer's view names a live holder or a strictly newer epoch than this machine's own record (a standby holding the same stale view does not count), or when the preferred machine has been silent on at least 3 probes spanning at least 45 s. With no preferred machine named, or on the preferred machine itself, every known peer must have answered without a live holder or stayed silent that long. A git store with no remote never counts as a peer answer.
- After the hold, the normal rules still need the holder's lease to have lapsed. The preferred machine is not exempt: on return it adopts the current epoch and gets the lead back only through hand-back.
- The boot claim now runs after the lease pull loop starts, and the moment the hold ends the pull loop runs the lease tick once (instead of waiting up to a heartbeat).
- Each decision is logged `boot-hold: <rule> <verdict>`; each ended hold is one row in the feature evidence log (`multiMachine.takeoverReadyPool`).
- `HttpLeaseTransport` records each lease pull per peer as a signed answer, an unsigned Instar answer, or silence (before, every non-2xx collapsed to unconfirmed). The AgentServer and the boot health beacon set the marker on every response, errors included.

Switch: `multiMachine.takeoverReadyPool.bootClaimSafety.enabled`. Live on development agents, dark on the fleet. `multiMachine.takeoverReadyPool.enabled: false` turns it off everywhere. Off is the old acquisition path, unchanged. Values: `silentProbes` (default 3), `silentSpanMs` (default 45000).

Rollout note: the Laptop (Echo and Luna) and the Mini currently run a hand-applied hotpatch with similar logic. Once a release carries this fix, installing it overwrites the patched file with the same behavior, so nothing needs removing by hand. Until then, auto-apply stays held on those machines.

## What to Tell Your User

- **Your first phone, at home**: "If you don't have Tailscale or Telegram set up, you can still add your phone: at your agent's computer choose Add your phone, then At home only. It asks for your PIN, shows a code to scan, and then a number from your phone to type in. That phone works on your home Wi-Fi."

- **Safer PIN**: "Every place that asks for your dashboard PIN now has the same protection against guessing, and a stranger guessing at the sign-in page can't lock you out of your own actions. With the right PIN, nothing changes for you."

- **Test runs on an unattended Mac no longer freeze on a privacy prompt**: "My own test suite was reaching into the real iMessage database on this Mac, and macOS was silently waiting for someone to approve Full Disk Access — forever, since nobody was at the screen. Tests now use a stand-in and never touch your real messages. Nothing changes in how I read your iMessages when actually running."

- **Helper machine keeps testing through restarts**: "If you turn it on, the second machine that runs tests for me keeps getting work while this machine waits to restart, and a test it was already running is kept across my restart instead of thrown away, as long as no other machine took over in between. A slow but healthy test run is no longer cut off at one hour; it gets up to two and a half hours if it keeps making progress."

- **Test timing record**: "My test line now keeps a record of how long every quick test takes, not just the slow ones. Nothing about how tests run changes; the record is what any later speed-up gets planned from."

- **Safer agent-to-agent replies**: "Another agent I talk to can no longer slip commands into the label of our conversation. Its questions still get answered as before."

- **Steadier agent network connection**: "An error message from the agent network relay can no longer shut me down. I note it on my health page and keep going."

If your agent runs on more than one computer: when one of them restarts, it no longer grabs the lead from the computer that is already answering. It waits until it has checked with the others, and it takes over only if the main computer really stays silent for most of a minute. You don't need to do anything.
