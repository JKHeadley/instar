## What Changed

When a machine's overload brake (work admission) is enforced and refuses to start a session for an incoming message, the message is saved and the person is told so. The saved message is now placed on a machine with room on its first retry, instead of retrying the overloaded machine up to ten times (about 25 minutes) before moving. If placement picks the same machine because it has recovered, the message is delivered there; if no machine can take it yet, it keeps waiting and retrying as before, so nothing is lost. Messages saved for other reasons are unchanged. A new counter, `admissionRefusalReplaced`, shows how often this happened.

Groundwork for "Always available" on Mac. When the Instar app runs an agent as a system service, it leaves a record, and Instar's start-up helpers (auto-start install, the fleet watchdog, restart commands, recovery and update self-heals) respect it so the agent never runs twice. Nothing changes until the app's switch is turned on.

For Always available on Mac: `instar always-available token --email <account>` stores a Claude setup-token code (read from stdin) as the agent's Claude sign-in, after checking that it belongs to that account. `token-clear` puts the earlier sign-in back, and `status` reports FileVault and the code's state. The Instar app uses these behind its switch.

When the agent records a promise to keep a setting at a value, it checks the setting and puts it back if it drifts. That correction now writes only what the config API (`PATCH /config`) would accept from the same caller: the same list of settings, nothing that needs the operator's PIN, nothing that chooses which program a session runs, and nothing that raises trust or autonomy. A setting outside those rules is still checked and its drift is still reported, but it is no longer changed automatically. The rule lives in one place (`src/config/bearerConfigWrite.ts`) and uses the config API's own lists.

- The dashboard Conversations pages say "group" where they said "effort": "Your groups", "Suggested groups", "Back to your groups", "Create group", "Rename group", "Group name", "Open group", "Forget group name", "No groups yet. Your conversations are in All.", the Overview tile "Groups", and the related status lines. Owner decision 2026-11-17. Routes, data, the `effort` node kind and stored records keep their names.
- The agent's Conversations awareness says "group" and tells the agent to call them groups to the user (a group may be linked to a project the Chief of Staff tracks, or be plain). Existing agents on the full CLAUDE.md layout have the three old phrases rewritten once by `migrateClaudeMd`.
- `GET /conversation-graph/nodes/:ref/messages` now gates on the graph runtime's private-serving check (`privateReadsServable()`: alive and private custody allowed, the same check the owner's read view needs) instead of the 60-second write-readiness proof. On a busy lease holder that proof is absent most of the time, and the route answered 503 `conversation-graph-off` to 25 of 30 owner reads while the page itself loaded. Owner proof, source resolution and the post-fetch re-checks are unchanged.

Cards created from a message now show **From: Original message** in the console. The link opens the existing conversation reader and highlights the exact message. Older history can be searched in further batches, with failed or unavailable reads stated clearly.

If the Needs-you response contains fewer rows than its total count, the strip states how many rows are available and omitted. Expansion counts only received rows and keeps source failures visible.

The Work page uses the shared console name validator for project headings. Missing or ID-only titles display “Project name unavailable”; original keys and conversation destinations remain intact.

The Work board starts Done and Archived folded with their totals visible. Expanding a history lane reveals its cards and paging together. An explicit later Done page opens automatically; refresh preserves a user's expansion choice.

Documents can ask the owner for a decision. The agent attaches one question to a document (`decision: {question}` on create or revise, or `POST /docs/:id/decision-ask`). The owner answers Approve or Decline in the Instar iPhone app on a native sheet with biometric Face ID; on a computer the document's Approve and Decline buttons send the question to the phone. The answer is a replicated row signed by the owner's phone, bound to the exact version and question, and re-verified on every machine. The phone posts "Approved version N of …" into the document's own conversation as the owner's message, and the document shows "Approved by … · version N". A new version after a Decline asks again. Needs-you lists documents waiting on the owner; `GET /docs/:id/decision` is the record the agent acts on. On a multi-machine agent, decisions wait until every recently active machine has this update. Until SEC-088 lands, a decision is applied (Approved shown, Needs-you cleared, session told) only on the machine the owner's phone is paired with; other machines keep the owner's Approve and Decline, add a note that an answer from the phone is waiting for confirmation, and change nothing else. Do not roll a machine back below this release once decisions exist.

The feedback executor's automated fix sessions were being refused by the independent safety review for rules they were never shown: a test fixture with token-looking values and a replaced home directory (PR 3261), a catch widened beyond the brief with no test (PR 3252), and existing tests weakened by added delays (PR 3292). The fix session's prompt only said it had no network and no credentials.

The six review rules (Scope, Tooling, Secrets and reach, Tests, Injection, Breakage) now live in one module, `src/feedback-factory/execute/reviewRules.ts`. The reviewer reads its rules from there, word for word as before (its prompt is byte-identical, pinned by a hash test). The fix session's prompt now carries the same rules under "Your change will be refused by an independent reviewer if any of these hold:", followed by short practical guidance: change only what the brief needs, tests use temporary directories only and never HOME or real paths, no credential-looking literals in tests, never weaken, delay or delete existing assertions, and every behaviour change needs a test that fails without it. A spec-drafting session gets the spec variant of the rules.

SEC-098. The confined session that writes a fix from outside feedback could READ everything in the machine's shared temp folder (`/private/tmp` on macOS). Its own temp directory is placed there on purpose (the path must stay short), and the list of shared temp folders to deny was filtered to drop any folder that contains it. That filtering is needed for writes (in the sandbox a write deny beats a write allow), but the same filtered list also fed the read deny list, so every other file in the shared temp, such as throwaway agents' config files with live bot and auth tokens, was readable. Writes stayed closed.

Reads now deny every shared temp root, and only the attempt's own temp directory is re-allowed (in the sandbox a read allow beats a read deny). The write rules are unchanged. The confinement canary gains must-fail probes that read a nonce file planted in the shared temp: two for the runner (bash and node) and step 22 of the session canary. The canary version moves to `feedback-canary-v6`, so every agent runs a fresh full-gate canary before its next fix attempt. On Linux, where a read-denied folder becomes an empty, private, writable mount inside the sandbox, the shared-temp write probe is now judged by whether anything reached the host's temp.

The dashboard's file downloads used the same 1 MB limit as file previews, so any file over 1 MB could be neither shown nor downloaded. Downloads now have their own limit, `dashboard.fileViewer.maxDownloadSize`, 1 GB by default and never lower than the preview limit; `GET /api/files/config` reports it. On the new console's Files page, a file too big to show says "You can still download it" and has a Download button; a file over the download limit says so with both sizes. `GET /api/files/link` now returns a link to the new console's Files page (`/dashboard/console/#/settings/files?path=...`) instead of the legacy dashboard.

Each read of the conversation graph (roots, a node, destinations, unassigned conversations) now runs against one verified view built at its start (`ConversationGraphReplicationRuntime.withPinnedReadView`, via the read source's `scoped`). Before, while any write was in flight the view could not be cached, and each effort title on the page (`EffortHeaderStore.titleOf` → `retainedForRead`) rebuilt the whole view: `certifiedUnion` plus the source inventory, decrypting every payload. On the accept-all rig that held the event loop 20-28 s per page read during Accept all. The pin lasts only for the synchronous read call; writes are unchanged.

`GraphSourceObservationRecoveryCoordinator` (the source-observation revalidation run by `validatedContinuation`, once per record continued during Accept all) verified the whole source collection three times per call, synchronously: every row to find pending rows, every row again inside `certifiedUnion`, and every union row a third time. At ~550 rows that held the event loop for 2-5 s per call. It now tests the cheap terminal flags before verifying (only pending rows are verified), and skips re-verifying rows `certifiedUnion` just verified against their own writer in the same synchronous step (new read-only `verifiedEventIds` on the union result; rows the union rebuilds are excluded). The per-observation admission check (`assertGraphSourceObservationAdmission`) gets the same treatment: one copy of the rows instead of two, flags before verification, no re-verification of union-verified rows. The checkpoint branch indexes union rows by source id and by newest producer sequence instead of scanning every row per entry (quadratic before). Verdicts are unchanged.

`ConversationGraphReplication.certifiedUnion` verified every stored row on every call (`verify`, then `fullyPersisted`, then the descriptor hash), and it runs once per revalidation during Accept all, once per read-view build and in the source inventory runner. At ~550 rows that is 1-3 s of synchronous CPU per call on a loaded host. It now remembers each stored row's results (per row object, WeakMap) and reuses them while the row's top-level values and a per-pass context are unchanged. The context covers everything the per-row work reads that can change: a verifier epoch bumped at the class-local erasure and member-loss state writes, the local deny fence's grow-only answer signature (root check, corrupt flag, deny-set size of the shared state), a signature of the witness key map and a hash of the installed membership. Rows whose checks read the clock, files or custody lineage (materialization, erasure, member-loss adoption, erased control, custody activations) are always verified fresh. Answers are unchanged.

Tests run with a check mode (`INSTAR_GRAPH_VERDICT_MEMO_CHECK=1`, set in `tests/vitest-setup.ts`): every reuse is recomputed and compared, stored rows' values are frozen so a nested edit fails, and any divergence fails the test. `INSTAR_GRAPH_VERDICT_MEMO=off` (read at start) turns the memo off.

`instar install --answers` now uses the AI named in the answers file's `door` even when a different AI is the only one found on the computer, or the installer runs inside one. Before, the Mac app's "Which AI account do you have?" answer was overridden by a Claude already on the Mac, so a ChatGPT pick produced a Claude agent with no sign-in step. An unknown `door` is refused with the valid names.

The Telegram origin layer refreshes its settings snapshot every 5 seconds and holds outbound replies once the last good snapshot is older than 30 seconds. Each refresh had a 10 second budget. Under a busy event loop (back-to-back 2-5 second tasks on the Studio, 2026-11-17/18) a refresh, which takes about six event-loop hops, routinely ran past 10 seconds and was discarded. Two in a row aged the snapshot past 30 seconds and replies were held ("config snapshot unavailable: origin-config-reader-timeout", 32 times in one evening). The read budget is now 25 seconds, and the two small state files read on each refresh (`agent-attention-topic.json`, `topic-profiles.json`) are read synchronously instead of in four async hops each. The 30 second freshness bound is unchanged and still counts from before the bytes were read; real refusals still revoke at once.

When an agent records a promise to its person with a target time (`softDeadlineAt`) and that time passes with the promise still open, the person now gets one plain message in the same conversation. It says what was promised, the time, and that it isn't marked done. Before this, nothing read that time, so a missed promise was silent.

If the session that made the promise is running, it gets a note 30 minutes before the time and another when the time passes, asking it to deliver, or to say why it is late and give a new time. A session that is not running is not restarted.

The messages are bounded:
- one per promised time, and three per promise in all;
- one per conversation per hour;
- 3 conversations per check, and 12 per hour.

Automatic deadlines worked out from words like "soon" are ignored, and so are promises waiting on the person.

`POST /commitments` now answers with `dateMissing` when the promise's words name a time ("by noon") but no target time was set. Setting a target time clears a "no follow-through needed" reason, and age-expiry waits for a future target time.

It rides on the dated check-in reminder: live on development agents, and off by default elsewhere until `commitments.checkInReminder.dryRun` is false.

After the owner taps "Stop this app", the app's card leaves Needs-you and reads "Stopped by you. Turning it back on comes in a later update." Approving it again is refused, with plain words. The project's row and conversation strip show "<app> · Stopped" with no Open button, and an app not yet approved shows "Waiting for your approval". Summary counts past three are kept, not cut.

If the Instar app on a Mac loses the key it connected to an agent with (after a reinstall, for example), it can now connect again. `instar install --app-ticket --key <new> --replace-app-key` writes a ticket that replaces only connections this same Mac's app made. The agent removes the old key and accepts the new one in one step, and tells the person. Connections from other computers, and phones the person paired, can't be replaced this way.

After a script job runs, the scheduler builds a short summary (at most 2,000 characters) for the result reviewer. When a job reported many conditions, such as the health check on a server with a dozen warnings, the summary went over the limit, the scheduler treated that as a broken script, and held the job. A held job runs as a full AI session instead of its script. The summary is now packed to fit: the result, named readings and outside confirmation are always kept, warnings are listed while they fit with a plain count of any left out, and the free-text tail gets the room that remains. A summary with warnings left out is never treated as enough for routine closure. Scripts that really break the contract are still refused as before. A job already held for this reason stays held until its hold is released with a recorded reason.

The agent learns the owner's preferences from corrections in conversation. A message from a team member (through their phone or the app) was meant to be excluded from that learning, but the mark that says "a team member wrote this" was dropped before the learning step read it. The mark is now kept, and one shared rule (`src/core/ownerWords.ts`) decides what counts as the owner's own words for every learning path. It is an allowlist on the owner: a Telegram message whose verified sender is the owner (any verified sender when no owner is configured), or an app message from the owner's paired phone, and never forwarded text. Team members, another person's paired phone, other people in a shared topic and senders that could not be verified never count. Their turns still enter the conversation window the learning step reads, marked as not the owner's, so nothing is learned from them as the owner's preference.
