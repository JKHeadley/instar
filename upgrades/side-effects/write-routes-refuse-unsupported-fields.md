# Side-effects review: write routes refuse fields they would not apply

Change: a shared `refuseUnsupportedFields(res, body, supported)` (src/server/refuseUnsupportedFields.ts) called by every PATCH/PUT route in routes.ts and fileRoutes.ts that lacked its own refusing allowlist; `PATCH /attention/:id` stores `resolution` (alias `reason`); `PATCH /initiatives/:id` refuses against `INITIATIVE_UPDATE_FIELDS` (compiler-checked against `InitiativeUpdateInput`); `PATCH /api/files/config` applies `enabled` (runtime 404 for file routes when off, persisted via liveConfig); a source-scanning ratchet test.

Principle check: the change is input validation on write routes. It adds no detector and no blocking authority over agent behavior or message flow; it makes an existing write honest about what it did. Signal-vs-authority does not apply beyond that.

1. **Over-block** — a caller that sends an extra field the route never used now gets 400 where it used to get 200. Searched every in-repo caller (dashboard/index.html, src/, scaffold templates, job templates, skills, init.ts curl examples, FeatureDefinitions): all send only supported fields, except `releaseReadinessWiring` (`reason`, now accepted as an alias) and the agent template's `resolution` (now accepted and stored). One integration test pinned the old silent-ignore on the Telegram bridge config route; it now asserts the refusal. A deployed agent typing an undocumented extra field by hand will see a 400 naming it; that is the intended outcome.
2. **Under-block** — POST routes with partial-apply semantics are not covered by the ratchet (it scans PATCH/PUT only); nested objects are not checked below the top level (e.g. `rollout` on an initiative). `/config` keeps its own top-level allowlist and one-level merge.
3. **Level of abstraction** — the check sits in each route because the supported set is route-specific; the single helper keeps the response shape uniform. Express-level schema middleware would be a larger change for the same effect.
4. **Signal vs authority** — not a gate on agent behavior; a 400 on a malformed request.
5. **Interactions** — the refusal runs before `refuseInadmissibleWrite` and before any store write, so a refused request never reaches write admission or the stores. On the PIN-gated class-review routes it runs after the PIN check (no field information before authentication). On `/subscription-pool/:id` it runs after the existing `email` and `configHome` 409s so those specific refusals still win; a credential-shaped field is now refused as unsupported (still refused, different message).
6. **External surfaces** — HTTP responses of ~20 routes for malformed requests only. The file-viewer `enabled:false` now takes effect immediately (it never did); `enabled:true` re-enables only when the server started with the viewer on (otherwise the routes were never registered, unchanged behavior, and the persisted value applies at the next start).
7. **Multi-machine posture** — machine-local by design: each machine validates requests to its own routes. The remote-ack relay forwards `{status}` only and is unaffected.
8. **Rollback cost** — revert the commit; no data migration. The only persisted addition is an optional `resolution` string on attention items, ignored by older code.
