# GitHub pull request approval repair

The existing [trust journey spec](../../docs/specs/trust-journey.md) defines server-owned effect classification, owner proof, and approval delivery. The installed classifier treated the GitHub connector prefix as the verb for writes, and the effect table had no repository rule. The request service compared only the nominal trust levels, so the initial standing permission at the default level could be mistaken for a no-op. The operation route also discarded the delivery service's paired-device setup instructions.

- **Over-block.** A known GitHub pull request destination lets the matching, proven operation setting apply. A malformed or missing destination still asks. A previously imported legacy policy for pull request creation continues to use its original modify policy until an explicit write decision is recorded.
- **Under-block.** A same-level write or modify decision that can admit one of the registered GitHub effects requires owner proof. Older audit and narrowing records without a matching consumed owner receipt cannot create this permission. Lowering a setting still applies immediately. If that leaves the operation without proof at its new permissive level, the next call asks. A previous explicit modify block still stops creation. Merging requires exact approval even when a legacy modify rule exists. Creation and editing use separate operation settings. After legacy policy import, creation, updates, and merge wait for the server if the installed hook cannot reach it. Existing installations receive the updated hook through the built-in hook refresh.
- **Authority.** The server derives the verb and repository from the exact connector schema. Standing GitHub pull request permission is limited to JKHeadley/instar. The owner sees that repository on the approval card, and the resulting receipt binds that repository. The existing policy keys continue to govern other GitHub tools. A message about delivery supplies no permission.
- **Interactions.** The hold response uses the delivery service's own explanation and keeps the instruction to retry the identical action after approval. The direct grant route and the approval request route agree that an enabling same-level change needs owner proof. Daily approval channels, exact-action identity, and consuming a one-time approval still use the existing implementation.
- **External surfaces.** This can admit pull request creation through the existing connector after the owner approves the setting. It does not send GitHub requests during testing. Paired-device setup may ask the owner to open Changes to approve when no approval key has been accepted.
- **Multiple machines.** The serving lease still controls governed admission. Grant and consumption rows use the existing replicated trust journal. No new state file or background job is needed.
- **Rollback.** Reverting restores the former connector classification and hold text. Proof and audit rows remain readable and historical same-level statements need no rewrite.
