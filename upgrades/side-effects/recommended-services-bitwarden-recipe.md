# Side-Effects Review — Bitwarden setup recipe (dark), and the master password off the command line

**Tier 2 by risk** (credentials: a vault master password is stored and used; a copy of every agent secret is written to an outside service), with second-pass review. Spec: `docs/specs/recommended-services.md`, First recipes: Bitwarden ("the agent's own folder only. The confirm page lists the secrets copied. The master password never goes in a process argument, which means fixing `BitwardenProvider` unlock first"). ELI16: `docs/specs/recommended-services-bitwarden-recipe.eli16.md`. Dark: the catalog row keeps `setupRecipe: null`; only a proving agent reaches it.

**Size:** 7 source files (1 new), 6 test files (2 new); about 230 lines of source. **Effort:** no spec rounds (parent spec converged and approved); 1 commit attempt expected.

## Summary

- `BitwardenProvider.ts`: `unlock` and `login` pass the master password to `bw` through `--passwordenv` and the child's environment (`INSTAR_BW_MASTER_PASSWORD`), never as an argument. New `logout()`; "not logged in" counts as signed out.
- `bitwardenVault.ts` (new): `BitwardenSurface` (status, unlock, itemNames, put, logout), `realBitwardenSurface(agentName)` over `BitwardenProvider` (folder `instar/<agent>`), `copiedSecretNames(secrets)` (every string leaf of the vault except `secretDrops.*` and the master password), `configHeldSecrets(config)` and `copySourceNames` (the auth token, dashboard PIN, messaging and tunnel tokens a fresh agent still keeps in its config file, named `config.<path>`; a `{ secret: true }` placeholder is skipped because the vault walk already has it), `VAULT_CHECK_ITEM`. The live proof found the gap: a freshly initialised agent's copy came out empty because its secrets were all still in config (the throwaway's own session filed it, fb-1b0a0b01-d96). `readCopyValue` on the routes reads a `config.*` name from the config and anything else from the vault.
- `recipes.ts`: `bitwarden-v1`. `secretName: bitwarden_master_password`. `verify`: program present and logged in (else fail, `absent`), stored password opens the vault, folder readable and holding the marker; unknown when the surface is missing or the folder can't be read. New optional `sync(deps)` on a recipe: writes every named secret and the marker as Secure Notes; returns names only. `stop`: removes the stored password, signs out only when `absentBefore` (the login was setup's), leaves a Bitwarden the person was logged in to; says the copies stay and offers to delete them. `RecipeDeps.bitwarden`, `SyncDeps`, `StopDeps.absentBefore`.
- `recommendedServiceRoutes.ts`: `POST /recommended-services/:id/sync` (header, grant, recipe with `sync`), returning names; the confirm page gets `copies` (names) for such a recipe; the regular check refreshes a working copy every 24 h (`lastSyncAt`, `copies` in setup state), quietly; `stop` receives `absentBefore`. `recipeDeps()` gathers the recipe inputs in one place.
- `routes.ts`: `readSecretNames` from the real vault, `bitwarden` from the real CLI surface scoped to this agent's name.
- `service-yes.js`: a "What gets copied" section listing the names.

## Decision-point inventory

- `bitwarden-v1.verify` — add — pass/fail/unknown for the Bitwarden row (only on proving agents).
- `POST /:id/sync` — add — refuses without the header, a grant, or a recipe that keeps a copy.
- `reconcile` daily refresh — add — a timer, not a judgment.
- `BitwardenProvider.unlock/login` — modify — same decision, different transport for the password.

## 1. Over-block

- `verify` fails without a stored master password even when the machine's own `bw` session is unlocked. Deliberate: the server must be able to open the vault on its own later (the daily refresh), so a setup that only unlocked in the session is not done.
- `copiedSecretNames` skips `secretDrops.*` (transient, consumed on use) and non-string leaves. A structured secret stored as an object is copied leaf by leaf under its dotted name, which is what the vault holds today.
- The daily refresh writes every leaf every time (`put` is an update for an existing item), one `bw` call per secret. With tens of secrets that is tens of CLI calls a day; acceptable, and the item count is recorded.

## 2. Under-block

- `absentBefore` for a switch-off comes from the first preflight (`absentBeforeSetup`). A person who logs the machine in to Bitwarden by hand during the session's run would see the switch-off sign that login out. Narrow window, bounded (one login restores it), same shape as Tailscale's recorded residue.
- The recipe trusts `bw status` for "logged in"; a logged-in CLI for a different account than the one the person meant is still "logged in". The brief tells the session to say whose account it is and ask before using it.
- `sync` writes values through `bw create/edit item`. Before this change the provider passed the item as a base64 argument on the `bw` command line; the reviewer showed that this change would have turned that latent exposure into a daily all-secrets exposure, so it is fixed here: the item (and the folder create) goes to `bw` on stdin, pinned by tests that no `bw` call carries a value in its arguments. The pre-existing exposure for agents on the Bitwarden backend is filed as fb-f848e867-36c.
- `verify` is honest about reading: `listOwnItemNames` is read-only (never creates the folder) and throws a fixed message on a CLI failure, so `itemNames()` is `[]` for "no folder yet" and `null` for "could not read" → `unknown`, which never takes a pass away. `unlock()` short-circuits when the server's own environment already holds an unlocked `bw` session, so in that rare setup a wrong stored password would still pass until that session expires; recorded, not changed.
- A failed daily refresh waits six hours before another try, and after three failures in a row the check is re-run (the attempt stamp moves first, so a re-check that cannot run also waits six hours). A re-check that fails tells the person once what stopped working, clears the old restart budget (the long-dead session would otherwise read as "dormant, waiting on the person"), and the next tick starts setup again to ask for what changed. The row never says "working" for ever on a dead copy, and the degradation log gets at most a few fixed-text records a day. Nothing downstream of the CLI reaches a `report()` reason.
- A status read that fails (a 15 s timeout, a broken CLI) is a third state, `null` on the surface: `verify` answers `unknown` and `sync` answers not-ok, never "not logged in". Without that, a slow vault would have failed a working copy on the re-check and then set `absentBeforeSetup` on the misread, so a later switch-off could sign out the person's own login.
- The server looks for `bw` in Homebrew, the system folders, `~/.local/bin`, `~/.npm-global/bin`, Volta and every nvm Node's bin, because a server started by launchd or the lifeline has a short PATH; the brief tells the session to install where the server looks. `getOrCreateFolderId` now throws a fixed message too, closing the session-in-error-text class for every provider caller.
- The confirm page's `copies` list is served by the unauthenticated page route (the PIN is checked on submit, not on open), so anyone holding that link learns the names of the agent's stored secrets, never values. The spec requires the list before the yes; recorded here as the trade.
- Two machines of one agent write into the same folder with the same item names, so differing `authToken`/`dashboardPin` values overwrite each other's copy daily. Recorded: a per-machine name part is a later change if a multi-machine Bitwarden proof shows it matters.
- The `vault-check` marker proves the folder is the agent's and writable; it does not prove every secret has a copy. The daily refresh is what keeps the copy complete; `verify` deliberately does not fail on a missing item, because that would restart setup on a working service.

## 3. Level-of-abstraction fit

The copy is written by the server inside the recipe, not by the session, because the session must never hold secret values. The surface wraps the existing `BitwardenProvider` rather than re-implementing the CLI. `sync` is a recipe method because only the recipe knows where its copy lives; the route and the regular check decide when.

## 4. Signal vs authority compliance

- [x] No — this change has no block/allow surface over content. `verify` is the recipe's own deterministic check, as for Jev and Tailscale; the sync route's refusals are invariants (header, grant, recipe shape). Reference: `docs/signal-vs-authority.md`.

## 4b. Judgment-point check

No new static heuristic at a competing-signals decision point. The daily refresh is a timer; `absentBefore` is recorded fact.

## 5. Interactions

- **Shadowing:** `sync` is refused for a service without a grant before the recipe runs, like `verify` and `key`.
- **Double-fire:** the session's `sync` call and the daily refresh share `syncCopy`; both are idempotent (update-or-create per item). A refresh that overlaps a session call writes the same items twice; harmless.
- **Races:** the refresh runs inside `reconcile` before the restart logic and only for a verified-pass service; a no that lands removes the grant and the next tick skips it (`hasGrant` branch comes first).
- **Jev/Tailscale:** `recipeDeps()` now passes `bitwarden` to every recipe's `verify`; they ignore it. `stop` receives `absentBefore` for all; only Bitwarden reads it.

## 6. External surfaces

- Dark on the fleet: the catalog row stays unavailable, the e2e test pins `/sync` → 404 and `available: false` for Bitwarden on a plain agent.
- On a proving agent: Secure Notes are written into the person's (or the agent's) Bitwarden vault under `instar/<agent>`. Nothing else in the vault is read or changed. Values go from this process to `bw`.
- `GET /recommended-services/:id/confirm` gains `copies` for a recipe with `sync`; `GET /recommended-services` rows carry `lastSyncAt`/`copies` only through setup state (not exposed yet).
- `BitwardenProvider.unlock/login` behaviour change affects the one existing caller (`deriveBitwardenSession`, the org-vault probe): same result, password now in the environment. `bw` has supported `--passwordenv` for years; the Mini runs 2026.7.0.
- **Operator surface (Mobile-Complete):** the yes/no and the copy list are on the confirm page; credentials come through Secret Drop; no API-only operator action.

## 6b. Operator-surface quality

1. **Leads with the primary action?** Yes; the copy list is one more section above the PIN box, after "If you say no", and the yes button is unchanged.
2. **Zero raw internals as primary content?** The list shows dotted secret names such as `tunnel.token`. They are identifiers, de-emphasised inside one sentence that explains them; values never appear. Acceptable: the spec requires the page to list the secrets copied, and the names are the only honest way to do that.
3. **Destructive actions de-emphasized?** Unchanged from the previous change.

## 7. Multi-machine posture

- The copy is **per machine by design** (`machine-local-justification: physical-credential-locality`): each machine's vault holds that machine's secrets, and each machine that has a yes writes its own items into the same folder (names collide across machines only where the secrets are the same, which is the intended "one agent" picture). The master password is stored per machine through the key route, which needs a yes on that machine.
- The choice itself replicates through the existing ledger; a switch-off from another machine is obeyed here as for the other recipes.
- One voice: the only owner-facing words are the switch-off notice through `tellOwner` (already gated) and what the session says in its own topic.

## 8. Rollback cost

A revert removes the recipe, the sync route and the surface; the provider's `--passwordenv` change reverts to the argument form (a security step backwards, so prefer a fix forward). Items already written to a vault stay; nothing reads them. Setup state fields `lastSyncAt`/`copies`/`absentBeforeSetup` are ignored by older code.
