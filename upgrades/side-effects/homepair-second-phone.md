# Side effects: home pairing ends when a second phone uses the code, and counts phones on every machine

In plain words: when a second phone presents the code of a home-pairing setup, the whole setup now ends and the phone already waiting is turned away; the computer says why and asks the owner to start again. The number screen tells the owner to type only the number on their own phone. The "first phone only" rule now counts owner phones paired through any of the agent's machines, and refuses when it cannot ask one of them.

Tier 1 (security hardening of an existing ceremony; no new route, no config, no migration). Size: 3 source files (`src/server/phoneSetupRoutes.ts`, `src/server/mobilePairingRoutes.ts`, `src/commands/mobileAddPhone.ts`), 1 new unit test file, new cases in 2 test files.

## What changes for running agents
- Second phone on one code (setups approved at the computer only): `PhoneSetupStore.secondPhone(id)` ends a setup that is `waiting-number` or `number-accepted` with reason `second-phone`, drops its number, and the routes decline the waiting phone and close the home address if nothing else uses it. Called from the redeem route when the setup already has a phone. A retry from the waiting phone itself (same key, its first reply lost) is refused but ends nothing. The handler runs synchronously from reading the setup to attaching the phone, so two redeems cannot interleave. A finished setup, a Telegram-path setup, and a setup with no phone yet are left alone. The phone's signed activation then answers `ended`.
- `GET /mobile/phone-setup/:id` carries a `say` line: the number-screen wording while waiting for the number, and the second-phone explanation once it ended for that reason. The number route's `setup-ended` detail uses the same explanation. `instar mobile add-phone` prints both.
- First-phone rule: `POST /mobile/phone-setup` (PIN and ceremony-credential paths, no Telegram owner) now also asks every other active machine in the machine registry for its devices (`GET /mobile/devices`, the pool token, 5 s each, at most 16). Any owner phone there refuses with `phone-already-paired`. Any active machine with no address, an error, an unreadable answer or no answer refuses with the new `phone-check-incomplete` (409), so a first phone is never set up when the agent cannot tell. On the ceremony path this runs before the credential is spent. A single-machine agent asks nothing and behaves as before.
- `publicDeviceView` adds `localInstall: true` for the app enrolled on that machine's own computer, so a peer can leave it out of the count. An older peer without the marker counts its active app record (fails closed).
- Known limits, accepted: a machine registry that does not exist at all counts as a single machine (an unreadable one refuses). A peer answers over the same address-and-token trust the pool devices view already uses, so a stale peer address that answered with an empty list would pass. A peer with phone pairing switched off answers 503 and refuses the setup, and the message says to check that.
- Not changed: the final activation check (`activate-at-computer`) still counts this machine's phones only; the setup-time check above is the gate. Where the phone's key is held is not recorded by any pairing path yet; a phone added at home still cannot approve anything, and a tracked item (CMT-028) keeps that true until it is recorded.

## Second-pass review

**Reviewer:** independent reviewer subagent (general-purpose, fresh context, given the diff, the spec and the three intended changes), 2026-11-21. Verdict: concur, no blocking findings. It traced the redeem handler (no await between reading the setup and attaching the phone, so no interleaving), the synchronous decline, and the activation route, and found no way for a second phone or a photographed code to get in: the race can only cause a restart. It confirmed the pool check fails closed on every can't-tell case it found. Non-blocking findings, handled: a line on the code-refused branch could never fire (removed); a same-key retry would have cancelled the owner's own setup (now refused without ending it); the second-phone handler could raise an unhandled rejection (now caught and reported); a peer with pairing off gave a misleading message (reworded). Accepted and recorded above: the missing-registry case, the peer trust model, and the local-only activation check. Tests added for its gaps: the same-key retry, no pool context, and an address the guard refuses.

## Signal vs authority
The change only removes ways in: a setup ends sooner, and a setup is refused when the agent cannot rule out an existing owner phone. Nothing new is granted.

## Rollback
Revert the commit. No state or config is written; the `second-phone` end reason and the `localInstall` field disappear with it.

- `tests/unit/owner-phones-other-machines.test.ts` (new): a single machine asks nothing; an active owner phone on a peer counts while browsers, the app record, team phones and inactive rows do not; an old peer fails closed; every machine that cannot be asked is named; an unknown own id or an unreadable registry refuses.
