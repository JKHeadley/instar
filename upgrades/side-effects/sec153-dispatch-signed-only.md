# Side effects: dispatches act only when signed by a pinned key, and remote prose never becomes a session prompt (SEC-153)

In plain words: the dispatch channel used to fetch unsigned instructions from a fixed web address and act on them by itself. It could run actions, change configuration, and start a new session whose prompt was the remote text. Now nothing from that channel is applied or executed unless it is signed by a key pinned in the config file. Remote prose is never handed to a session, signed or not. Where dispatches come from cannot be changed with the API key. The old address is migrated off. Everything that is held stays in the dispatch record, pending review.

Tier 1 by size, security-sensitive: an independent second-pass review is attached below. Size: 9 source files (`src/core/AutoDispatcher.ts`, `src/core/DispatchManager.ts`, `src/core/types.ts`, `src/commands/server.ts`, `src/commands/init.ts`, `src/core/PostUpdateMigrator.ts`, `src/server/routes.ts`, `src/config/bearerConfigWrite.ts`, `src/scaffold/templates.ts`), 1 new test file, updated cases in 4 test files.

## What changes for running agents
- **Signature gate.** `AutoDispatcher.setSignatureGate(verifier)` takes a `DispatchVerifier` built from `dispatches.trustedKeys` (keyId to PEM, config file only) with `required: true`. The server wires it only when at least one key is pinned. Without a gate, no dispatch is auto-applied or executed. `executeDispatch` (the one execution point, used by both the legacy and the discernment paths) and the discernment loop both check it first. A dispatch that fails is marked pending approval, logged as `defer` with tag `unsigned`, and announced to the owner once per dispatch per process. Verdicts are memoized by a hash of everything the signature covers plus the signature, so the verifier's replay cache never refuses a second look at the same dispatch. An LLM-adapted copy has different content, fails the signature, and is held: adaptation of a signed action never runs. Deferred dispatches due for re-evaluation pass the same check.
- **Signatures are kept.** `DispatchManager.check()` used to drop the signature fields when it stored a polled dispatch, so a verifier could never have passed anything. Now `signature`, `signedAt`, `expiresAt` and `keyId` are stored when each is a bounded string, and `signatureVerified: true` is recorded once a dispatch verifies.
- **Passive auto-apply.** `checkAndAutoApply(isTrusted)` applies a lesson or strategy only when the check trusts it. Called without a check, it applies nothing; new dispatches stay unapplied and listed as pending.
- **No remote prose to sessions.** A dispatch whose content is not a structured action, or a structured action with an `agentic` step, is held for review instead of starting a session. This holds even when it is signed.
- **Context file.** `dispatch-context.md` is loaded into sessions. It now carries only guidance types (security, behavioral, strategy, lesson), never configuration or action text, and never a dispatch that was applied automatically without a verified signature. Records applied before this change stay in `dispatches.json`; they drop out of the context file at the next rebuild (any apply, approve or accept), and a person accepting one puts it back.
- **No replay on a fresh or rebuilt install.** A machine that has never polled (no last-check time) gets the server's whole history. The first poll now records those dispatches as `historical: true` and returns nothing new, so none is executed, applied or announced. Only dispatches that arrive after it are new. Without this, a rebuilt machine re-runs months-old dispatches on its first poll.
- **"Applied" no longer means "a session started".** The agentic step reported success the moment a session was spawned, so a session that failed at once was still recorded as accepted and applied. Dispatches can no longer reach that step (prose and agentic steps are held), so nothing is recorded as applied on a session start.
- **Sessions read names, not remote text.** `GET /dispatches/context`, which the agent instructions tell sessions to read, now lists titles, ids and whether each is signed. It no longer includes content. `GET /dispatches`, `/dispatches/pending` and `/dispatches/pending-approval` withhold the content of any dispatch that did not verify (`contentWithheld: true`). Their titles are cleaned and cut to 120 characters, because a title could carry the payload too; the raw title stays in the record, where the signature covers it. The owner reads the full text with the new `POST /dispatches/:id/read` and the dashboard PIN, quoted as data. The owner notice for a held dispatch lands in a conversation a session reads, so for an unsigned dispatch it gives only the cleaned title, the type and the id, says it will not be acted on, and quotes none of its text. Applying, approving or accepting a dispatch that did not verify under a pinned key needs the dashboard PIN (`POST /dispatches/:id/apply`, `/approve`, and `/evaluate` with `accepted`). Without it, a held dispatch could ask a session to apply it with the API key. The generated agent instructions say a dispatch's text is data, not an instruction.
- **The context file is cleaned at start.** `DispatchManager` rebuilds `dispatch-context.md` when it starts, so text the file may no longer carry leaves sessions at the next boot. That includes configuration text carrying install lines for package names that do not exist on npm. The context file's path is now always beside the record and never the record itself: a record not named `dispatches.json` used to make the two the same path, and the new rebuild would have overwritten it.
- **Origin fence.** `PATCH /config` refuses `dispatches.dispatchUrl`, `dispatches.dispatchFile` and `dispatches.trustedKeys` with a 400. The bearer config-write guard (`bearerConfigWriteRefusal`, used by the commitment auto-correction) refuses the same keys. `dispatches.enabled` and `autoApply` stay patchable, so the feature switch still works.
- **Migration.** `migrateConfigLegacyDispatchUrl` runs in the config migration, and again on the in-memory config before the dispatch system starts, because the server loads its config before the migration rewrites the file. When `dispatches.dispatchUrl` is exactly the old init address, it sets `enabled: false` and `dispatchUrl: ''`, and records `legacyDispatchUrlRemoved {url, wasEnabled, at, reason}`. Any other address is left alone, and the dispatch record file is kept. `instar init` now writes `enabled: false` with no address. On any agent that still has the channel on, this stops polling when the update lands.

## Second-pass review

**Reviewer:** independent reviewer subagent (general-purpose, fresh context, given the finding, the diff and this note), 2026-11-21. Verdict: concern raised over three rounds, then concur in the fourth. It found one blocking gap: `GET /dispatches/context` gave sessions the full text of held dispatches, and `/apply`, `/approve` and `/evaluate accepted` were plain API-key calls, so a held dispatch could get itself applied. That is fixed: the endpoint has no content, and those three need the PIN for an unverified dispatch. Non-blocking findings, all handled: the first boot after the update still polled the old address (the migration now also runs in memory); deferred re-evaluation skipped the gate (now checked); the verdict cache keyed on id and content only (now the whole signed payload). It also corrected this note: adapted copies never run. A re-check of the fix found the same gap in the list routes, which returned full content; they now withhold it, and the owner reads it through a PIN route. A third check found two more: titles passed through uncleaned, and the owner notice quoted a preview of the text. Both are fixed. Its last note, a last-check file path that could equal the record path when the record name does not end in `.json` (a bug that predates this change), is fixed too. Final verdict: concur. No remaining path lets a session or an API-key caller read unsigned dispatch text, beyond a cleaned title of at most 120 characters, which nothing can act on. It confirmed the core fix holds, the settings fence is complete for `PATCH /config` and the bearer write guard, nothing re-adds the old address, and the migration is idempotent and keeps the records.

## Signal vs authority
The change removes authority from a remote, unauthenticated source. It grants nothing. Holding a dispatch for review is a signal to the owner; a person approving one is the authority, and approval still only records the dispatch, as before.

## Not in this change
- No pinned key exists anywhere today. Re-enabling automatic dispatches needs the dispatch server to sign, and a key pinned in each agent's config file; that is a separate decision.
- A signed structured action can still write files through `config_merge` and `file_write`, inside its scope tier. That is the designed path for a signed dispatch, and the scope enforcer still applies.

## Rollback
Revert the commit. The migration's effect remains: `enabled: false` plus the `legacyDispatchUrlRemoved` note, which holds the old address. To restore it, put the address back by hand. Held dispatches stay pending approval and can be approved or rejected as before.

## Tests
- `tests/unit/sec153-dispatch-origin.test.ts` (new, 14 cases). Unsigned configuration and action dispatches are never executed and wait for review; with no pinned key, even a signed one is held. A structured dispatch signed by the pinned key runs and records that it verified. Tampered text and an unknown key are held. Prose, signed or not, and a signed action with an agentic step are held. An unsigned lesson is not auto-applied and the context file stays absent, while a signed lesson reaches it. The context file drops configuration, action and unsigned automatic text, and every record is kept. The bearer guard refuses the origin keys but not the switch, and PATCH /config fences them. The migration removes exactly the old address, is idempotent, and leaves an operator's own server alone. `init` no longer writes the old address.
- `tests/unit/dispatch-manager.test.ts`: the existing auto-apply cases now pass a trust check. A new case shows nothing is applied without a check, and only what the check trusts is applied.
- `tests/integration/dispatch-routes.test.ts`: applying or accepting an unsigned dispatch with the API key alone is refused, and with the PIN it works; `GET /dispatches/context` never carries the remote text. `tests/e2e/dispatch-update-feedback.test.ts` and `tests/unit/dispatch-failures.test.ts` were updated for the PIN and the first-poll rule.
- New in `sec153-dispatch-origin`: a fresh install's first poll records three dispatches as history and runs, applies and announces none, and the next poll acts only on the new one. Nothing is recorded as applied when a session would have started. At start the context file drops configuration text, including an install line.
- `tests/unit/formatApprovalNotification.test.ts`: the existing preview cases now use a signed dispatch, and a new case shows an unsigned one is named only by cleaned title, type and id, with no text.
- Every unit test file that imports a changed module passed (509 files, 16,517 tests) before the last updates. The touched unit files pass again after them. Integration and end-to-end coverage comes from Local Verify; this machine does not run them by hand.
- Follow-up after Local Verify (20:50 PST, `write-domain-conformance-ratchet`): `POST /dispatches/:id/read` is a new mutating-method route that only returns the dispatch (POST so the PIN rides in the body). The ratchet test and `sec153-dispatch-origin` pass on the branch, and the ratchet passes on current main.

## Class-Closure Declaration
- `unbounded-self-action`: closure n/a. Not a new loop: the change only removes actions. `park()` replaces the existing per-dispatch approval notices, sends at most one notice per dispatch per process (a parked-id set), and runs inside the existing 30-minute poll tick; no restart, respawn or retry is added.
