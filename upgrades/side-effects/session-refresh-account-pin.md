# Explicit Account Refresh Side Effects

- Over-block. Intentional refusals cover protected sessions, local Codex, unavailable idle evidence, and sessions without a verified running Telegram binding.
- Under-block. A later launch failure can still require normal session recovery. The accepted response does not confirm completion.
- Abstraction. The route resolves the exact account. SessionRefresh owns idle and stop admission. SessionManager owns the existing Codex rollout placement and launch.
- Signal versus authority. The session work gate decides idle. The pin only carries an explicitly chosen target and the identity revalidation into the existing refresh authority.
- Interactions. Revalidate the exact identities and check the Telegram delivery and pending injection records after the asynchronous work check. Hold the rebrief in a private recovery record before stop. Require confirmed termination and skip the legacy second kill for explicit pins.
- External surface. A default-off, optional refresh field with the existing bearer authority. No change to automated quota placement. Delivery can be ambiguous if the server stops after sending the rebrief and before clearing the record.
- Fleet posture. Machine-local by design. The named subscription has to be executable on the machine that holds the current session.
- Rollback. Turn the flag off. No quota is redeemed. Existing private rebriefs remain available for explicit recovery when they match the stopped source. An interruption before the matching killed-state receipt is saved leaves the private record with replay disabled.
