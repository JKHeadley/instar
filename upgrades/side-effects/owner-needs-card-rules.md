# Needs You admission side-effects review

This review covers the local prototype. The fleet rollout, migration, source queue routing and final release verification remain pending. The checkpoint leaves the production provider unwired.

1. **Over-block.** Missing classifications, absent presentation templates and an unavailable authority hold a row. Existing owner decisions need verified source adapters and supported clients before the release can enable the gate.
2. **Under-block.** The projection cannot prevent a separate notification or Attention detail route from showing an unclassified item. Each source must prove that owner and agent paths apply the same rule.
3. **Placement.** Source writers own durable routing and exact request identity. The common projection checks eligibility and counts exclusions. The action service retains authority to execute.
4. **Signal and authority.** Use typed action identifiers and signatures verified by source services. Wording, urgency, a dashboard link and a Work Board lane do not authorize an action. See docs/signal-vs-authority.md.
5. **Interactions.** Run a fresh projection per caller. A verified stale approval is absent. A source failure for a known owner approval reports that it could not be checked and provides no executable action.
6. **External surfaces.** Verify web, phone, Mac, Telegram and direct detail routes separately. Existing fixtures cover a signed individual approval and a reviewed physical instruction. Completion and credential paths still need combined acceptance.
7. **Multiple machines.** Use complete coordinator and serving-holder reads for decisions. An uncertain journal write or incomplete peer history holds the corresponding request. Fleet queue routing still needs proof for each source.
8. **Rollback.** Use the release feature switch to restore the prior projection. Preserve request authority and the source queue. Never remove decision or withdrawal journal records during rollback.

## Opt-in server and signed credential fixture checkpoint

The server can construct its owner provider when the acceptance setting is explicitly true. It resolves a Work Board policy request from the trust store by exact reference and checks the active accepted device against that request. This does not authorize any trust change, and all execution stays on the signed trust route. Other references need their own source adapter. Pooled private inputs with no proven audience remain absent from counts.

The old synthetic canary cannot exercise the new typed path. The opt-in server stops scheduling it and returns the explicit off status for its status route. The legacy configuration keeps its existing scheduler. Fleet activation still requires a replacement verification path.

The signed credential consent module loads in the same source tree and retains the standalone verified single-field fixture boundary. It is not mounted on production routes. The test principal, disclosure proof and submission are disposable. No token or value is carried in the owner card. A request change, expiry, reassignment or replay must refuse before storage. Existing Secret Drop storage remains responsible for the one-time write.

The production default stays off at this checkpoint. An ordinary install or update does not enable this opt-in setting. Default-on migration, verified project delivery and full browser/native signed acceptance remain separate release requirements.

The independent authority reviewer concurred for opt-in acceptance. Clients with no negotiated contract receive HTTP 426 when the setting is true. Use the setting only with disposable or expressly authorized acceptance agents until the remaining genuine actions have been verified. Setting it to false and restarting the server restores the legacy owner list.

## Pending trust approvals and device setup

The opt-in provider recognizes verified, open native requests for six explicit settings and authority proposal types. The signed device must already belong to the owner. A request pending during approval enrollment contributes only an unavailable count. It becomes actionable under its original request ID when the device can retrieve the exact signed disclosure. Turning off app approvals removes its action while preserving the pending count.

One-off operations still need verified source triage. The opt-in provider does not yet cover approvals delivered through chat or genuine actions that lack a typed and authorized source adapter. These paths require separate proof before enabling the gate for a live agent. The fleet setting migration is a separate change.
