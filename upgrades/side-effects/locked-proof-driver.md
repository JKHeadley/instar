**Version / slug:** `locked-proof-driver`
**Date:** `2026-11-02`
**Author:** `Echo`
**Tier:** 1 (maintainer scripts, no runtime source change, nothing runs without `--execute`). Size: 7 new files under `scripts/locked-proof/` (~750 lines), 1 test file. Effort: no spec rounds; first commit attempt.

## Summary of the change

The locked-Mac proof plan (`.instar/lanes/locked-mac-proof-plan-134088.md`, items M3 and M5) needs a driver for P12/P15 and repeatable throwaway-user setup. This adds them as scripts only. One change from the plan, per the brief for this work: the agent types the throwaway user's password through the remote-desktop viewer, instead of the operator typing it about 30 times. The password is generated by the setup script, never chosen by a person, kept in the agent vault (`locked_proof_user_password`, stored through `credential-store.mjs` with the value on stdin, Bitwarden first), and read once into the driver's memory. It is not the owner's password: the spec's "no agent ever handles it" concerns the owner's real password, which this run never touches (the test account is empty and throwaway). The user is created without a forced password change at first login (`pwpolicy -clearaccountpolicies`; the plan's `newPasswordRequired` step is dropped).

Files: `lib.mjs` (cases, expected table, runner, verdict, password generator, attempt reset rule, target check), `driver.mjs` (real target: sudo against the proof user, the proof agents' HTTP API, the real viewer page through playwright-core with system Chrome), `create-proof-user.sh`, `pty-feed.py`, `stage-proof-agents.sh`, `configure-proof-agent.mjs`, `reset-attempts.py`, `remove-proof-user.sh`.

## Decision-point inventory

None in runtime code. The driver's verdict is a test-harness judgement recorded with its evidence; it gates nothing by itself (a passing record still goes through a normal PR to the proven-versions table).

## Review follow-ups (independent review on #2598)

1. Signals are owner-checked: `serverPid` asks `lsof -a -u instarproof` (only the proof user's listener), and `kill()` reads the pid's owner (`ps -o user=`) immediately before every signal and throws for anyone but `instarproof`. `assertProofTarget` now gets the real owner of each agent's listening process and of each agent directory, not a constant.
2. `runCase` runs the case in try/finally: whatever throws, `target.recover()` resumes every pid the run SIGSTOPped, clears the guard-stopper and locks the proof session; a recovery problem or the error fails the case by name. `close()` runs the same recovery.
3. `configure-proof-agent.mjs` and `reset-attempts.py` refuse without `--execute`, and refuse anything that does not resolve inside `/Users/instarproof` (the reset script's only other accepted root is a test root inside the system temporary directory named by `LOCKED_PROOF_TEST_ROOT`).
4. Expectations without a measurement now fail as "not measured" instead of passing silently. Measured from the run's own samples: relock time after a transport drop (15.5/15.6, must be at least the 30 s resume window) and whether the password field is left dirty at the end (15.9, from the store's `dirty` flag, which blocks any later Enter). Lock calls against another session (12.12/12.13) have no observable source yet, so those two cases fail as "not measured" until one exists.
5. Bitwarden: the agent's `credential-store.mjs` put the base64 item (which holds the password) on `bw`'s command line. Echo's copy on this machine now pipes it on stdin (`bw create item` / `bw edit item <id>` read the encoded JSON from stdin, per `bw --help`, version 2026.7.0). `create-proof-user.sh` refuses to run if the helper it would call still puts the item on the command line, so the Laptop's copy must be updated before setup. The password is on no command line in this flow: stdin to the helper, stdin to `bw`, the pty prompt to `sysadminctl` and `dscl`.

## 1. Over-block

None: no runtime path changes.

## 2. Under-block

- The verdict can only judge what it observes. "Lock call against another session" (12.12/12.13) is not directly observable from outside the helper; the driver records the marker outcome and leaves that sub-check to the helper's own audit rows, read at the sitting.
- The loginwindow submission count is recorded as raw evidence (`loginwindowLines`); its log pattern is unverified until the sitting, so the verdict relies on the helper's `enterPendingAt` records for "no submission after close".
- Timing of "immediately before Enter" depends on calibration; the plan's rerun rule (offset off by more than 500 ms) is applied by the person running the sitting from the recorded timestamps.

## 3. Level-of-abstraction fit

Maintainer tooling outside `src/`, driving the same surfaces an owner uses (viewer page, revoke route, PIN route). It adds no test-only hooks to the helper, so the helper under proof is byte-identical to the shipped one.

## 4. Signal vs authority compliance

Not applicable: no runtime authority. The scripts refuse to act on anything but the `instarproof` user running a `-lockedproof` build.

## 5. Interactions

- Uses `sudo -n` (passwordless sudo on the proof Mac) to signal only the proof user's processes and read its relock store. `reset-attempts.py` takes the helper's own `state.lock` and refuses while a duty is open.
- `create-proof-user.sh` depends on `sysadminctl -password -` prompting on its terminal; if a macOS version does not prompt, `pty-feed.py` fails loudly ("never asked") after storing the vault value, and no user exists. Rerun with `--replace-vault`.
- Starting the proof servers in the proof user's session needs that session to exist (the person's first login).

## 6. External surfaces

None for users or agents. A Bitwarden item "Instar locked-proof test user (<host>)" is created when setup runs.

## 7. Multi-machine posture

Machine-local by design: the proof runs on one Mac, against a user on that Mac.

## 8. Rollback cost

Delete the scripts. If setup was run, `remove-proof-user.sh --execute` deletes the user; the vault key is deleted by the agent.

## Conclusion

Adds the missing driver and setup tooling, with the agent typing the throwaway password so the operator's part is two permission grants and a few local actions. Tier 1.

Not required: no runtime gate, session lifecycle or messaging change.
