# Side-Effects Review — Tailscale and Jev available on every agent, with switch-off and a reach check

**Tier 2 by risk** (a switch-off acts on a working service; a yes is now open to real people), with second-pass review. Spec: `docs/specs/recommended-services.md`, rollout step 3, "Offers go live for new agents with what's proven" (the yes path; the offer itself stays unbuilt). ELI16: `docs/specs/recommended-services-available.eli16.md`.

**Size:** 9 source files, 9 test files (1 new); about 190 lines of source. **Effort:** no spec review rounds (the parent spec is converged and approved), 1 commit attempt expected.

## Summary

- `catalog.ts`: `setupRecipe` is `tailscale-v1` for Tailscale and `jev-v1` for Jev. Each was live-proven on a test agent (2026-11-05 Jev, 2026-11-07 Tailscale, topic 135786). The other seven rows stay `null`; the catalog test pins the exact list.
- `recipes.ts`: each recipe gains `stop(deps)`, the spec's `shutdown: authorized` carried out, and both undo only their own work. Jev removes `typesafe_api_key` (which every Jev feature reads, so one deletion switches Jev off) only when setup stored it; a key the person had before setup stays, and the words say so. Tailscale signs out only when `setUpHere`; a Tailscale that was `alreadyHeld` is left as it was. The sign-out is confirmed from the status read that follows, never from the command's exit alone. `StopResult.changed` says whether anything was undone. New `runTailscaleLogout`.
- `setupState.ts`: `absentBeforeSetup` (the check before setup found nothing of the service here: `VerifyResult.absent`, set for no key, not installed, `NeedsLogin`) and `signedInBySetup` (a pass through the verify route after that, for a keyless recipe only). The evidence a switch-off acts on is chosen per recipe: a recipe with a key uses `keyStoredBySetup` alone (the key route never overwrites a key that was already here); a keyless recipe uses `signedInBySetup`. Both default false, read from the state as it was before the no cleared it; a machine with no record did nothing. `stopped` and `stopRequestedAt` are cleared by a fresh yes and by a new pass, and a pass is never written while the grant is gone, so a service can be switched off, set up again and switched off again, and a no that lands during a check wins.
- `catalog.ts`: `wayIn: true` on Tailscale, Cloudflare domain and Telegram, the rows that are a way to reach the person. Only those wait on `otherRouteWorks`; Jev never does.
- `recommendedServiceRoutes.ts`: `stopService` runs on a no with `shutdown: true` (both the plain no route and the confirm page's no, which is PIN-checked) and on the regular check when another machine's authorized no arrives. Before switching off it asks `otherRouteWorks`; if not, it records `stopRequestedAt`, tells the person once, and the regular check finishes the switch-off later. New deps `canReachOwner` (a yes answers `409 cannot-reach-you` before the token is spent; a restart waits and costs no attempt), `otherRouteWorks`, `deleteSecret`, `tailscaleLogout`. The list gains `stopped` and `switchingOff`; the confirm page gets `canSetUp` and `workingHere`.
- `routes.ts`: `canReachOwner` = a Telegram adapter and the lease (unreadable lease reads as not held); `otherRouteWorks` = Telegram or Slack present; `deleteSecret` through `SecretStore`.
- `service-yes.js`: an unticked "Also switch it off on this machine" box, shown only where this machine's own setup made the service work (`switchOffHere`); a service the person already had is named as theirs to switch off; a plain reason instead of the yes button where this machine can't message the person; the no still works there.
- `services-model.js`: "Switching off" and "Switched off" row words.
- `PostUpdateMigrator.ts`: the CLAUDE.md section's v2 wording, swapped in place on a legacy-layout file once; the reference layout re-renders it from the template. `CapabilityIndex` text updated.

## Decision-point inventory

- `isServiceAvailable` for Tailscale and Jev — modify (data) — a yes is now accepted for these two on every agent.
- `POST /recommended-services/:id/confirm` yes — add — refused with `cannot-reach-you` while this machine can't message the person.
- `reconcile` restart — modify — waits while the machine can't reach the person.
- `stopService` — add — a confirmed no with switch-off, deterministic, PIN-gated upstream; holds while the service may be the only route.

## 1. Over-block

- A yes on a standby machine, or on a machine with no Telegram adapter, is refused. The dashboard served from a standby is rare, and the page says what to do; the token is not spent, so the same page works once the lease is back. An agent with Slack only (no Telegram) is refused a yes everywhere, because setup today opens a Telegram topic (`startSetup` throws without one). That is the existing limit stated plainly rather than a session that can't talk.
- `otherRouteWorks` treats a present Telegram adapter as a working route. A Telegram that is configured but down still counts, so a Tailscale switch-off can proceed while messaging is out. Acceptable: the person just confirmed it on a page they could reach, and the catalog names messaging as the backup; a deeper liveness read belongs with the drills (rollout step 6).
- Both recipes refuse to undo what setup did not do: a Tailscale that was already signed in, or a TypeSafe key that was already stored, stays, and the page never offers the box for it (`switchOffHere` false). A person who wants that switched off is told it is theirs to do, and the agent offers to do it on request. Deliberate, and enforced at the route layer from positive evidence, chosen per recipe: `keyStoredBySetup` for Jev (observed: the key route wrote it), `signedInBySetup` for Tailscale (inferred: nothing was here before setup, then the session's check passed). A Tailscale that was signed in but stopped or offline at the yes is "something here", so a later pass is not counted as setup's. A machine with no setup record at all undoes nothing.

## 2. Under-block

- `canReachOwner` reads the lease at the moment of the yes. A lease that moves a second later leaves a setup session on a machine that can't talk; the existing bounded restarts and the stuck notice cover that, as before.
- Jev's switch-off removes the key but doesn't touch `jobs.scriptTriage.jev.enabled` or the other Jev flags; they are inert without the key, so Jev is off, and a later yes restores it by storing a new key.
- A switch-off runs the recipe once per machine and records `stopped`; a key stored again by hand afterwards isn't removed. A no is sticky in the ledger, so nothing restarts setup.
- `stopService` from the regular check needs the catalog row to carry a recipe; a no with switch-off for a service that lost its recipe records nothing and does nothing, which the spec accepts ("the route to stop a running service ships before any service is available" covers the available ones).
- The plain `/no` route already took `shutdown: true` before this change and only recorded it; now it acts. Any caller that sent `shutdown: true` casually would now switch the service off. Searched: no caller in the tree or the dashboard sends it; the page sends it only from the box. This is a deliberate reading of the spec's "goes through the confirm page": the plain route carries the same PIN proof the page carries today, and the ledger row it wrote was already `authorized`, which every machine's regular check now obeys. Coercing it to `none` would leave a recorded `authorized` that nothing acts on.
- A server wired without `deleteSecret` cannot remove a key; the switch-off then says once that it couldn't and the regular check retries quietly (`stopRequestedAt` as the said-once marker).
- `signedInBySetup` is inferred, not observed: Tailscale's own status has no "who signed this in". `absentBeforeSetup` narrows it to a machine with no sign-in at all before setup; a person who signs the machine in themselves during the session's run, in the window before the session's check, would still be counted as setup's. Bounded (one tap reverses a sign-out) and stated here rather than hidden; a node-key comparison belongs with the drills step.
- `otherRouteWorks` excludes the channel being switched off, so a future Telegram recipe cannot count Telegram as its own backup; Slack likewise.
- The setup-did-it flags (`keyStoredBySetup`, `signedInBySetup`, `absentBeforeSetup`) survive a plain no by design, so a key that died can be replaced on a later yes. If the person, between a plain no and a later yes, removes the agent's key or sign-in by hand and puts their own in its place, the stale flag still says setup did it, and a ticked no would remove the person's own. That needs a hand change outside every surface the spec covers, and telling the two apart needs a node-key or key-value comparison; recorded here, not fixed now.

## 3. Level-of-abstraction fit

The switch-off lives in the recipe, beside `verify`, because only the recipe knows what its setup did. The route decides when (a confirmed no, another machine's no) and the strand check; the recipe decides what. The reach check reuses the coordinator's lease, the same primitive the Telegram origin and the digest use, rather than a new liveness probe.

## 4. Signal vs authority compliance

- [x] No — this change has no block/allow surface over content. The two new refusals are invariants: a yes is refused on a machine that cannot start a conversation (enumerable: no adapter, or no lease), and a switch-off runs only on a PIN-confirmed no that says so. Neither judges text. Reference: `docs/signal-vs-authority.md`.

## 4b. Judgment-point check

No new static heuristic at a competing-signals decision point. `canReachOwner` and `otherRouteWorks` are presence checks on a channel and the lease, not weighings of conflicting signals; the strand hold is a safety guard on an irreversible action (signing a machine out), deterministic by design.

## 5. Interactions

- **Shadowing:** `cannot-reach-you` runs after `not-available` and before the token is consumed and the PIN is read, so a mistyped PIN or a refused machine never spends the page. A no skips it entirely.
- **Double-fire:** `stopService` can be reached from the no route and the regular check for the same no. `stopping` and the `stopped` record make it run once; a second call returns before the recipe. The person is told once: when something was undone (`changed`), when something was working here (`hadSomething`, from the state read before `endSetup` clears `verified` and `alreadyHeld`), or when they were promised word (`stopRequestedAt`). The deferred completion therefore speaks too.
- **Races:** `endSetup` and `stopService` share the setup state file; both write through `updateSetupState` (read-modify-write per call) in the same process, in order. The `before` state feeds both `hadSomething` and `setUpHere`. A strand hold writes `stopRequestedAt`; the completing tick clears it with `stopped`. `beginSetup`'s preflight-pass branch checks the grant once, then writes the pass; a no landing in that gap leaves a pass beside a `stopped` record, and the stop wins: `recordVerify` clears a stop only while the grant stands.
- **Feedback loops:** `reconcile` skipping restarts while unreachable writes nothing, so nothing accumulates; attempts resume unchanged when reachable.
- `recordVerify` after a stop: `verify` is refused without a grant, and a no removes the grant, so no pass can be written over a `stopped` record.

## 6. External surfaces

- Every agent on this release shows "Yes or no" for Tailscale and Jev on the dashboard's Services list. A yes starts a real setup session that talks to the person in a new Telegram topic, uses browsers, and for Jev asks for a payment decision. That is the intended user-facing change.
- Tailscale switch-off runs `tailscale logout` on the person's machine, only where the agent's own setup signed it in, after a PIN-confirmed no with the box ticked.
- Jev switch-off deletes a key from the local secret store.
- `GET /recommended-services` gains `stopped` and `switchingOff`; the confirm page JSON gains `canSetUp` and `workingHere`; responses to a no gain `switchingOff`. Additive.
- **Operator surface (Mobile-Complete):** every new operator action is on the confirm page, phone-sized, PIN-checked. Nothing is API-only.

## 6b. Operator-surface quality

1. **Leads with the primary action?** Yes. The page still opens on what the service involves and the yes button; the switch-off box sits inside "Or say no", under the reason, and is unticked.
2. **Zero raw internals as primary content?** Yes. Error codes map to plain sentences (`cannot-reach-you` included); no ids or JSON shown.
3. **Destructive actions de-emphasized?** Yes. The switch-off is a plain checkbox below the no, never above the yes, and the no's confirmation says in words whether the service is being switched off or stays on.

## 7. Multi-machine posture

- Choices and `shutdown: authorized` are **replicated** through the existing ledger (the coherence journal kind `recommended-service-record`). Every machine's regular check obeys an authorized no from any machine, which this change adds.
- Setup state (`stopped`, `stopRequestedAt`, `signedInBySetup`) is **machine-local by design**: `machine-local-justification: physical-credential-locality`. The key and the Tailscale sign-in live on one disk, so the switch-off and its record are per machine; the person hears from each machine that had something to switch off. A machine where setup never ran has no record, undoes nothing and says nothing: a replicated authorized no cannot sign the person's own Tailscale out of a second machine.
- One voice: the switch-off notice goes through `tellOwner` (the lifeline topic), which is already gated on this machine holding a Telegram adapter; a standby with no adapter says nothing and its record waits in the dashboard row.
- The confirm page's reach check is per machine on purpose: the page runs on the machine that serves it, and its token is bound to that machine already.

## 8. Rollback cost

A revert returns the two rows to unavailable and removes the stop and reach paths. Choices already saved stay and apply again on return (spec, Rollback). A `stopped` or `stopRequestedAt` field left in setup state is ignored by older code. A key already removed by a switch-off is not restored; the person asked for that. Legacy CLAUDE.md files keep the v2 sentence, which stays true (the two can be set up) until the catalog changes again.

### First read

Concern raised: the signal-vs-authority claim holds, but the Tailscale sign-out can run against a machine the agent never signed in, and the `stopped` record is never cleared, so a second switch-off silently does nothing. Three blocking findings, seven non-blocking.

**Signal vs authority — concur.** `canReachOwner` (`src/server/recommendedServiceRoutes.ts:86`, `:404`, `:240`) is a capability precondition on an action that needs the capability (setup must talk), refuse-only (`&&`-narrowing, never widening), checked before the token is consumed, and recoverable by retrying the same page. `otherRouteWorks` (`:141`) holds rather than blocks and is deterministic. Neither reads text or weighs competing signals; both fit the "hard-invariant" and "safety guard on an irreversible action" exemptions in `docs/signal-vs-authority.md`. The lease guard never grants anything and cannot strand a yes permanently: a token minted while reachable and posted later is re-checked at `:404` before `tokens.consume` at `:413`, and a refused yes leaves the token live. `reconcile`'s `continue` at `:240` sits before `decideSetupRestart`, so attempts, dormant and give-up all wait without writing state.

1. **Blocking — `endSetup` clears `alreadyHeld` before `stopService` reads it, so a PIN-confirmed no with the box ticked signs out a Tailscale the person already had.** Both no routes run `endSetup(id)` (`:311`, `:432`), which writes `alreadyHeld: undefined` (`:120`), and only then call `stopService(row, before)`. `stopService` derives `setUpHere: !state?.alreadyHeld` from the fresh read at `:134`, not from `before` (`:151`); `before` feeds only `hadSomething` (`:139-140`). ### Second read

Concern raised: one blocking finding (Jev's `setUpHere` can still be true without the positive evidence that exists for it), four non-blocking. Everything else from the first read checks out in code.

Verified against the code, not the author's summary: `setupState.ts` carries `signedInBySetup`; `recordVerify` writes it only on a pass with neither the call nor the prior state saying `alreadyHeld` (`src/server/recommendedServiceRoutes.ts:193`); `endSetup` (`:117-121`) leaves it and `keyStoredBySetup` alone; a completed stop clears both (`:158`). `stopService` derives `setUpHere` from the pre-`endSetup` `was` or the fresh `state`, positive flags only, default false (`:140-141`); the hold applies only to `row.wayIn` (`:145`); the owner is told on `changed || hadSomething || waiting` (`:160`); the error path is said-once through `stopRequestedAt` (`:171-174`). `clearStop` runs on both yes paths (`:474`, `:511`), and `recordVerify` clears `stopped`/`stopRequestedAt` on a pass only under a standing grant (`:196`). The confirm page offers the box only on `switchOffHere` (`:386`, `dashboard-pair/service-yes.js`). `catalog.ts` marks `wayIn` on tailscale, cloudflare-domain and telegram. `routes.ts` uses `ctx.coordinator?.enabled ? holdsLease() : true`, pinned by `tests/unit/recommended-services-wiring.test.ts:37`. Jev's `stop` leaves a pre-existing key when `!setUpHere` (`src/recommended/recipes.ts:115`). The new Tailscale integration tests cover own-sign-in undone, `alreadyHeld` left, and a replicated no on a no-state machine touching nothing and saying nothing.

(a) **Can `setUpHere` be true without positive evidence?** Yes, through `signedInBySetup`, which is inferred ("a pass arrived through the verify route and preflight did not pass"), not observed:

1. **Blocking — for Jev, `signedInBySetup` overrides the positive signal that already exists, so a key setup did not store can be deleted.** `recordVerify` (`:193`) sets `signedInBySetup` for any recipe, and `stopService` (`:141`) accepts either flag. Jev's own positive evidence is `keyStoredBySetup`, written only by the `/key` route (`:569` region), which refuses to overwrite a pre-existing key. Reachable path: a valid `typesafe_api_key` already on the machine, TypeSafe unreachable at the moment of the yes → preflight `unknown` → `alreadyHeld` never written → session starts → `/key` answers `already-held` → session calls verify → pass → `signedInBySetup: true` → a later ticked no deletes the person's own key, irreversibly, with the "its key is removed" message. The integration helper `working()` in `tests/integration/recommended-services-setup.test.ts:616-627` sets `secret = 'k'` by hand (never through `/key`) and asserts `signedInBySetup` is true, so the test suite enshrines exactly this bypass. Fix: for a recipe with `secretName`, `setUpHere` is `keyStoredBySetup` alone (either skip `signedInBySetup` in `recordVerify` when `recipeFor(row).secretName !== null`, or select the flag by recipe in `stopService`); make `working()` store through `/key` and assert `keyStoredBySetup`.

2. **Non-blocking — for Tailscale, `signedInBySetup` is inferred too, and three preflight outcomes mislabel a pre-existing sign-in as setup's.** `judgeTailscaleStatus` returns `fail` for a signed-in node that is offline (`recipes.ts:217`) or `Stopped` (`:222`), and `unknown` on a timeout. In each case the session finds (or `tailscale up` reconnects) the person's existing login, verify passes, and `signedInBySetup` is written although no sign-in happened. Bounded harm: the person ticked the box naming this machine, and sign-out is reversed by one tap; but the page's promise "only where this machine's own setup made the service work" is not strictly true. Narrowing: record at `beginSetup` whether the preflight saw `NeedsLogin` or `missing` (a structured `signedOutBeforeSetup`), and require it for `signedInBySetup`; or have the session's verify call carry nothing and let the recipe compare the node key before and after.
