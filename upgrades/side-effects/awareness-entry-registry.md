# Side-Effects Review — awareness entry registry

## Summary of the change

Adds `src/awareness/registry.ts` (reads `src/data/awareness/*.md` from the package, validates each entry, renders one "Feature notes" section, finds and replaces a marked block), an empty entry folder with a README, three consumer edits (`generateClaudeMd`, `patchClaudeMdContent`, `buildCanonicalClaudeMd` with a registry-free variant), the Codex/Gemini mirror handling, the legacy-conversion strip, one start-time report in `src/commands/server.ts`, an advisory lint, tests in three tiers, and the author-facing text (repo `CLAUDE.md`, the principles doc, the instar-dev skill). Spec: `docs/specs/awareness-entry-registry.md` (converged in 6 rounds, report in `docs/specs/reports/`). No entry ships.

## Decision-point inventory

1. An entry that fails validation is left out and reported (invariant; spec "Decision points touched").
2. Whether a document holds a well-formed block: none / well-formed / broken, broken means change nothing and report (invariant).
3. Whether an entry applies (`requires: telegram` against the agent's setting) (invariant).
4. The old-way notice: advisory, always exits 0 (judgment-candidate; the reviewer decides).

None of these gates a message, a session or a merge.

## 1. Over-block

- A valid-looking entry is rejected when its body starts with a code fence or a list, contains a heading or a second bold lead, has unbalanced fences, uses a placeholder other than `{{port}}`, or its title repeats another entry's. Each rejection names the reason; the README tells authors the first line must be prose.
- A document whose existing block sits inside an unclosed code fence, or that ends inside one, is treated as broken: its feature notes are not written or updated until the fence is fixed. That is deliberate (the alternative appended a new block on every update) and it is reported.

## 2. Under-block

- An entry's text is not reviewed for meaning by anything automatic; it is reviewed in its PR like today's sections.
- Two entries merged separately can together push the core over its size budget through their titles; the size test on main catches it after the second merge, not before.
- The advisory lint only sees added lines in two functions; awareness added some other way is not noticed.
- A file that already contains the exact stand-in line (`<!-- instar:awareness-registry-held -->`) would have its block restored at the wrong place for one pass and keep a stray comment line; cosmetic, untested.
- `withRegistry(..., { markers: false })` has no read-back: a canonical document that ended inside an open code fence would get the section inside the fence. The canonical document is generated by instar, and the layout tests would show an unclosed fence there.

## 3. Level-of-abstraction fit

The registry is a leaf (it imports only `claudeMdLayout.ts`, which imports only `node:crypto`). The three places the instruction document is built each call it once, last. Entries are data, not code, so there is nothing to compile, index or keep in step with build output.

## 4. Signal vs authority compliance

Validation is a hard structural check over an enumerable domain (an entry file either meets the format or not); it has authority only to leave that entry out, and it reports. The lint is a signal with no authority. Nothing brittle gains blocking power.

## 4b. Judgment-point check (Judgment Within Floors standard)

One judgment-candidate, the old-way notice: its floor is "advisory, exit 0, added lines only, `not checked` without a merge base"; its arbiter is the PR reviewer and the author.

## 5. Interactions

- The legacy patch chain's `content.includes(marker)` guards never see entry text: `patchClaudeMdContent` removes a well-formed block before the chain runs and re-adds it last, and the canonical build passes an empty registry to its two inner calls. Without this an entry quoting a short guard string (for example `/corrections`) could have suppressed a legacy section; found by the second-pass reviewer, tested.
- The canonical document carries the section WITHOUT marker lines, appended after `insertContextDeathClaudeBlock`, so no marker line reaches the layout parser and no earlier unit changes its parent or file (tested by comparing every unit with and without a fixture entry).
- The mirror's legacy loops read a registry-free source in both branches, the copy's own block is removed before they run, and the marker prefix is a slice boundary; a broken copy is left alone and reported.
- The legacy-to-reference conversion removes a well-formed block by its markers before the text comparison; the backup keeps the true original.
- `generateClaudeMd` gained a 7th optional parameter; all existing callers are unaffected (checked by the reviewer over 254 call sites and by `tsc`).
- This change itself triggers the advisory notice, because it adds the last-step lines inside `patchClaudeMdContent`.

## 6. External surfaces

With zero entries (the shipping state) every generated document is byte-identical to before; no agent sees a change. Once entries exist: a `## Feature notes` section at the end of the instruction document's source, landing in a reference file under the reference layout; one extra name per entry in the core's capability list; a marked block in legacy `CLAUDE.md` files without core markers and in `AGENTS.md` / `GEMINI.md`. A damaged block or a bad entry appears as a degradation at server start and as error lines in the migration result.

## 6b. Operator-surface quality

The two operator-visible strings (damaged marker lines in `CLAUDE.md` and in a copy) say what happened, that instar left the section untouched, and what to do. They appear in the migration result, not in a chat.

## 7. Multi-machine posture (Cross-Machine Coherence)

Unified and stateless: entries are data files in the package and each machine renders them from its installed version with its own Telegram setting. Nothing is stored or replicated; no notices, no URLs. The degradation report is per machine, like every other.

## 8. Rollback cost

Revert the commit. With no entries nothing was written to any agent. After entries exist, a revert leaves the last block in legacy marker-less `CLAUDE.md` files and Codex/Gemini copies; the revert PR must add one removal step for a well-formed block. Reference-layout agents need nothing: their files are rebuilt from the canonical document.

## Conclusion

Additive, inert until the first entry, and the paths that write into operators' files refuse to act on anything doubtful. The main residual risk is adoption (authors keep using the old way), which the skill text, the standards text and the notice address and which is reviewed two weeks after merge (CMT-1767).

## Second-pass review

**Reviewer:** independent reviewer subagent (Claude), given the spec and the implementation, not the author's conclusions; read-only (no test run). Three reads.

First read: "Concern raised". `withRegistry` appended a new block on every update when the existing block, or the end of the document, sat inside an unclosed code fence, because the block finder ignores marker lines inside an open fence. Also noted: entry text took part in the legacy chain's `content.includes(marker)` guards; a title could contain a placeholder; `markers: false` was not idempotent; the canonical document was built twice. It confirmed zero-entry byte-identity, no import-time or start-time throw, and all `generateClaudeMd` call sites.

Changes: a read-back check (the result must hold one well-formed block ending at the end, else nothing changes and it is reported); the block is taken out before the legacy chain and the canonical build's inner calls get an empty registry; a title with `{{` is an error; `markers: false` is documented as called once and pinned by a test; one build fills both caches.

Second read: "Concern raised". Those changes introduced a loss: on a broken read-back the two callers kept the text they had already stripped, so an existing well-formed block could be written away, silently in the mirror.

Changes: `holdRegistryBlock` swaps the block for a one-line stand-in while the chain or the mirror's loops run and restores the original bytes before `withRegistry`; a broken result keeps the original block, applies the chain's patches, and reports; the mirror honours `broken`.

Third read: the loss is closed in both callers on every path (a throw writes nothing; a lost stand-in appends the block; no duplication); the stand-in cannot be matched by the block finder, the slice boundary or the layout parser; zero-entry and no-block paths are byte-identical. Left as a nit: a file that already contains the exact stand-in line would get its block restored at the wrong place for one pass and keep a stray comment line (cosmetic; untested). "Concur with the review".
