# Member-loss consent proof component (not recovery enablement)

`src/core/GraphOwnerMemberLoss.ts` is an isolated exact-schema parser and historical dual-signature verifier. It has no filesystem, network, timer, process, enrollment, native revocation, Source allocation, custody-role activation or deployment side effects. It exports no mint/permission factory. Source99e9 and the existing positive/negative admission engines remain unchanged.

The proposed proof binds exact old/new owner-signed owned-machine rosters, REMOVE ONLY with at least one unchanged-key survivor, removed identities' signing/sealing key hashes and native key epoch, old publication/native roster hashes, request/draft/challenge and named confirmation commitment, acknowledged prefix, contiguous known operation allowlist/predecessors, known pending manifest, and explicit unknown removed-tail/historical-copy debt. It requires a distinct action-specific accepting-survivor signature plus an owner-root countersignature. Shared owner-root possession alone does not satisfy the accepting-key signature. No source/core/auth signature is rewritten and no missing machine receipt is invented.

The trusted context is supplied by the future actual owner service; the pure verifier does not establish context freshness or human presence. A structurally valid historical proof is NOT current native-admin authorization, membership activation, physical erasure completion or a Source ACK. The root service must still perform fresh current PIN/device admission and explicit named-loss confirmation, replay protection, policy/roster rechecks and independently reviewed native integration. None of that integration is implemented by this component. No fleet action has been performed.

Normal unit tests use real generated Ed25519/X25519 keys and signed roster/proof fixtures to test cryptographic/structural bindings. They do not claim real human admission or complete recovery. No external service is required or purchased. Design/context: `.instar/state/build/owned-machine-member-loss-adapter-proposal.md`.

The next isolated protocol revision requires `pendingDisposition:'refuse-all-uncommitted'` and each operation's `terminalHash` (null exactly for uncertified Pending, actual final-certificate hash for a committed/canceled/erased decision). A valid commit certificate is preserved even when old delivery/UI status is still Pending. The Source-issued held inventory supplies these facts; the pure parser alone cannot discover certificate completeness or current human consent. This remains unshipped component work, not NativeAdmin approval.
