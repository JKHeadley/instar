# Side-effects review — owner-approved-action-stdio-transport (SEC-018 companion)

Spec: `docs/specs/owner-approved-action-stdio-transport.md` (converged 3 rounds + approved, CoS msg fa844311 + 92e3952c, 2026-11-15). In-scope files: `src/threadline/performApprovedDelete.ts` (new — the one server-side gated-delete op), `src/threadline/ThreadlineMcpHttpService.ts` (extract `evaluateLoopbackGuard`), `src/threadline/mcp-http-client.ts` (`approvedDeleteViaHttp`), `src/threadline/ThreadlineMCPServer.ts` (delete-handler refactor + `approvedDelete` dep), `src/threadline/mcp-stdio-entry.ts` (wire `approvedDelete`), `src/server/routes.ts` (`POST /threadline/approved-delete`), `src/data/awareness/owner-approved-action-stdio-transport.md` (new), tests.

**What it closes:** SEC-018b (PR #3218) gates `threadline_delete` only on the opt-in HTTP MCP transport; the DEFAULT per-session **stdio** helper (separate process) was ungated. This funnels the gated delete for BOTH transports through one server-side `performApprovedDelete` (existence-check → enabled → device-signed-approval consume → the irreversible mutation), invoked in-process for HTTP and over the loopback `POST /threadline/approved-delete` route for stdio. Ships **dark** (`security.ownerApprovedActions.enabled` default false).

## The (c) limit, stated plainly (CoS condition, msg 92e3952c)

**The route does not and cannot authenticate the calling process; its safety rests on redeem-only plus the device signature.** SEC-018's threat model is a local session that can read secrets off disk — and that same session, as the same user, can read a sibling process's env/memory, so no credential or per-spawn nonce distinguishes the real stdio helper from a hostile local process. We therefore did NOT add a helper-identity defense-in-depth layer (it would add complexity and invite being mistaken for a boundary). Instead: the route exposes only "attempt this approved delete" (no caller-facing `consume`/`register-pending`/`clear-pending`/`enabled` action), so a hostile local caller holding every on-disk secret still gets `owner-approval-required` and cannot delete; the authority is the Face-ID device signature on the owner's phone, off the machine. A unit + integration test assert exactly this.

1. **Over-block** — Dark (default): nothing blocked. Enabled: a delete with no device approval returns `owner-approval-required` + a server-composed card; the owner approves in one tap. No legitimate owner delete blocked. An unreachable server (stdio) returns **outcome-unknown** (not a false "failed") so the owner reconciles.
2. **Under-block** — None now: this IS the companion that closes the stdio under-block from #3218. The route exposes no approval-creating action; the existence-check-before-register bounds the pending-registration flood to real threads (a weaker FIFO-eviction residual remains, disclosed in the spec's Residual section, with a per-caller cap as a tracked follow-up — availability-DoS only, never a delete bypass).
3. **Level-of-abstraction fit** — The gate + the mutation live together at the authority (the server process), reached via the existing `/threadline/*` Bearer loopback pattern the stdio helper already uses; `evaluateLoopbackGuard` is extracted (DRY) from the local-MCP admission.
4. **Signal vs authority** — `isLocal` stays a signal; the sole authority is the device-signed owner-presence approval (created only on the phone route after `verifyPresenceSignature`). The gate is **synchronous** server-side (no async-interface fail-open); the only async hop is the stdio helper's HTTP call, which returns the result or outcome-unknown.
5. **Interactions** — Uses the SAME in-memory `OwnerApprovedActionStore` + `PendingApprovalRegistry` the phone routes and the HTTP MCP gate use (via `ctx`), so an approval the phone records is consumed by either transport; Node single-threadedness preserves single-use across transports. Cross-process delete authority is `ConversationStore`'s reload-per-op + per-record CAS + atomic rename (a helper write cannot resurrect a server-deleted thread).
6. **External surfaces** — One new loopback route `POST /threadline/approved-delete` (agent-token + loopback guard; NOT in `THREADLINE_PUBLIC_ROUTES`). The stdio `threadline_delete` behaviour changes ONLY when enabled; disabled is byte-identical when the server is reachable (a server-unreachable delete now fails closed as outcome-unknown rather than deleting locally — disclosed).
7. **Multi-machine posture** — `machine-local` / `physical-credential-locality`: in-memory stores per server process; the helper's calls are hardcoded to `127.0.0.1`; approval recorded + consumed + delete applied on the same machine. Nothing replicates; the route writes no replicated state of its own.
8. **Rollback cost** — `performApprovedDelete`, the route, and the handler refactor ship **live**; only `enabled` is dark-gated. Back-out of a refactor defect is a code **revert** (the config flip only disarms the approval requirement). No migration (config read with optional chaining `=== true`).

## Second-pass review (independent)

This is an auth gate on an irreversible action, so Phase 5 requires an independent second-pass before the gate flips. The implementation is complete, unit-tested (15 tests: `performApprovedDelete` incl. the hostile-caller no-mutation property; `evaluateLoopbackGuard` tunnel-refusal; `approvedDeleteViaHttp` outcome-unknown), tsc-clean, dark. The independent second-pass of the wiring (same store shared across both transports; the handler performs no local `remove`; the dark path byte-identical; the route exposes no approval-creating action) is scheduled as part of the pre-flip gate alongside the live phone-tap proof over the stdio transport. **Verdict pending the pre-flip second-pass + the live proof; the DARK merge carries only un-exercised-dark-code risk, which the e2e alive test covers.**
