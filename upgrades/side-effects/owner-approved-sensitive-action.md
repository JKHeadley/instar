# Side-effects review — owner-approved-sensitive-action (SEC-018 primitive + delete gate)

Spec: `docs/specs/owner-approved-sensitive-action.md` (converged + approved, CoS message f22e0066, 2026-11-15). In-scope files: `src/server/OwnerApprovedActionStore.ts` (new), `src/server/PendingApprovalRegistry.ts` (new), `src/server/mobileOwnerPresenceRoutes.ts` (action-approval routes + the action-bound challenge + the signed message), `src/threadline/ThreadlineMCPServer.ts` (the `OwnerApprovalGate` interface + the `threadline_delete` gate), `src/threadline/ThreadlineMcpHttpService.ts` + `src/server/AgentServer.ts` + `src/server/routes.ts` + `src/commands/server.ts` (wiring the shared store/registry + gate), `src/core/types.ts` (config), `src/data/awareness/owner-approved-sensitive-action.md` (new), tests.

**User-visible-effect (condition 1 — the approval is the restoration of intended behaviour, not a degradation):** A trust grant or a thread deletion was ALWAYS meant to be the owner's decision; the flaw is that `isLocal` let a peer-driven local session make it with no human action. Requiring a real owner approval RESTORES the intended behaviour. When enabled, the owner's experience is one plain Face-ID card naming the exact action ("Delete the conversation "X"?") approved in one tap on any enrolled phone (or the Telegram-identity route) — no new friction on any non-gated action. Ships DARK (`security.ownerApprovedActions.enabled` defaults false); no owner sees anything until the switch is flipped after the live phone-tap proof.

1. **Over-block** — When dark (default), nothing is blocked. When enabled, a `threadline_delete` with no owner approval returns `owner-approval-required` and puts a card on the owner's phone; the owner approves in one tap. No legitimate owner-initiated action is blocked (the owner is the one approving). A genuinely-expired approval simply asks for a fresh tap.
2. **Under-block** — The **stdio** MCP transport builds its own `ThreadlineMCPServer` and is NOT yet passed the gate, so a `threadline_delete` over stdio would still behave as today. The HTTP MCP path (the primary path sessions use) IS gated. The stdio-path gate is a tracked follow-up that MUST land before the feature flips; while dark, both paths behave as today, so there is no live gap.
3. **Level-of-abstraction fit** — The gate lives at the authority (`ThreadlineMCPServer` handler, via the `OwnerApprovalGate` structural interface so threadline stays decoupled from server internals), and the approval routes reuse the EXISTING owner-presence `gate()` (active owner phone + presence key + local TLS) rather than re-implementing any security check. The approval STORE + pending REGISTRY are plain in-memory stores mirroring the existing `BoundSecretStore` pattern.
4. **Signal vs authority** — `isLocal` is demoted to a signal (it no longer authorizes a sensitive action). The authority is a Face-ID-gated owner-presence signature verified server-side by the existing `verifyPresenceSignature`, over a message that commits to `{purpose, actionKey}`. A deterministic signature check, not a brittle heuristic.
5. **Interactions** — Requires `mobilePairing.ownerPresence` (the owner-presence mechanism) to be on as well as `security.ownerApprovedActions`. The store/registry are ONE shared instance (server.ts constructs them; the same instances reach the MCP gate and the phone routes) — if they were not shared, an approval the phone records would never reach the handler (this was the load-bearing wiring decision). When dark, every path behaves exactly as today.
6. **External surfaces** — Four new routes (`/mobile/action-approval/{challenge,,pending,decline}`), owner-presence-gated. The `threadline_delete` MCP behaviour changes ONLY when enabled. The owner's phone apps (echo-instar-app, echo-android-app) consume these routes + the signed-message byte contract (`instar-owner-action-v1\n<deviceId>\n<host>\n<purpose>\n<actionKey>\n<challenge>`), which is locked by a unit test so it cannot drift. Fast-follows (not in this change): surface pending approvals in `/mobile/needs` for the dashboard/Mac count, and the item push.
7. **Multi-machine posture** — `machine-local-justification: physical-credential-locality`. The presence key lives in the owner's phone secure element; verification + the approval store + the pending registry are per-server-process (in-memory), on the machine that applies the action. The trust/thread state they gate replicates as today; this change adds a per-machine authorization check, it does not replicate the approval. A restart drops pending approvals — fail-safe (the owner re-taps).
8. **Rollback cost** — `security.ownerApprovedActions.enabled: false` restores today's behaviour byte-for-byte (the gate is skipped; `threadline_delete` is unchanged). Revert the PR to remove the modules + routes + the gate. No data migration; the stores are in-memory and lapse on their own.

## Second-pass review (independent)

**Reviewer:** this is an auth gate on an irreversible action (`threadline_delete`), so Phase 5 requires an independent second-pass before the gate flips. The server implementation is complete + unit-tested (16 tests) + tsc-clean + dark; the independent second-pass audit of the wiring (that the store/registry are genuinely shared between the MCP gate and the phone routes, that the dark path is byte-identical, that the signed message binds the exact action, and that the stdio-path gap is closed) is scheduled as part of the pre-flip gate alongside the dark-byte-identical proof and the live phone-tap proof. **Verdict pending the pre-flip second-pass + the two proofs; the DARK merge carries the risk only of un-exercised dark code, which the e2e alive test covers.**
