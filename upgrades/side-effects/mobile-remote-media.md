# Side effects: owner phone opens a Slack file held by another machine

Change: `GET /mobile/media/:sha256` takes an optional `machine` query. A named nonlocal machine streams the file for a current owner phone through `buildMediaHolderStream`; a bearer request with `holderHop=1` naming this machine is answered like a download.

1. Over-block: Range is refused for another machine's file, so a cut download restarts. An older holder is refused until it updates. MSP phones with a Slack grant stay local-only.
2. Under-block: bytes written before a revocation are not recalled. The owner check runs before every write and on a 200 ms timer, so only data already handed to the socket can pass after it. An HTTP/1.0 client reading a file of undeclared length cannot tell a broken stream from a finished one; the app uses HTTP/1.1 or later and checks the hash. A revocation after the last check, while the final chunk drains, is not covered, the same as a local download. The holder trusts a hop from any machine holding the agent bearer, the same trust every peer route has: that bearer is peer authorization, not phone or human owner proof, accepted by coordinator decision. The holder's checks are static, run once at request start. All live owner gating is on the near machine. There is no containment of a compromised near machine and no independent holder owner stop.
3. Level fit: the route owns the download checks, so the branch sits there. Transport stays in the pool fetch and URL guard. Owner admission is the shared helper, not a copy.
4. Signal vs authority: fixed owner, trust, ref and hash checks; no brittle judgment holds authority. See docs/signal-vs-authority.md.
5. Interactions: poolPeerFetch may try fallback ropes on a dead dial, each through the guard and the owner check. Slots are separate from the history read. This route now counts in its own 120-a-minute `media-read` bucket, for local downloads too, so files and chat reads no longer share an allowance. Its route timeout is 330 s rather than 30 s; uploads and purge keep 30 s. A holder without the file runs `rep.canFetch` and may run `rep.want`, answering 202: cache hydration as a scoped side effect of the download, under the existing quota, reference and purge controls. This is not a pure read and not a no-replication path.
6. External surfaces: new 403 `owner-only`, 409 `wrong-machine`, 416 `range-unsupported` and 502/503/504 holder codes on this route when `machine` names another machine. No change without `machine`. Slack rows in the new app download whole, local ones too.
7. Multi-machine posture: proxied-on-read through resolvePeerUrls; no new kind of state, though a missing blob may be hydrated into the existing media store (item 5).
8. Rollback: revert the commit; a remote file then fails as it does today.
9. Release note: the fragment gained What Changed and Evidence so the upgrade guide validator accepts it. No behavior change.
