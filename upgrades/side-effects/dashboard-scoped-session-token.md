# Side-effects review — dashboard-scoped-session-token (SEC-002b)

Spec: docs/specs/dashboard-scoped-session-token.md (converged + approved, CoS-ratified 2026-11-15). In-scope files: `src/server/DashboardSessionStore.ts` (new), `src/server/middleware.ts` (dst_ branch + `isDashboardCredentialRoute`), `src/server/AgentServer.ts` (store wiring, unlock scoped-token return, refresh/revoke/step-up endpoints, SSE + WS verifier wiring), `src/server/routes.ts` (SSE accept + stream-close, 2 RouteContext fields), `src/server/WebSocketManager.ts` (scoped accept + stream-close), `src/core/types.ts` (config), `dashboard/index.html` (client lifecycle + step-up), `src/data/awareness/dashboard-scoped-session-token.md` (new), tests (unit + integration + e2e).

**User-visible-effect (condition 1 — the step-up is declared a degradation):** In normal dashboard use, nothing changes — a correct PIN unlocks exactly as before and every ordinary action works identically; the browser invisibly holds a token that expires and can be revoked instead of the permanent master key. The ONE declared added step (a degradation under *Security Fixes Keep the Experience Whole*, surfaced for the independent reviewer to judge): the rare CREDENTIAL operations — reading the raw API token, changing the PIN, rotating the token — now ask the owner to re-confirm with a live PIN (or the paired phone's device approval where they have one) at the moment of the operation. It is UNAVOIDABLE: those operations are exactly how a thief with a stolen session token would escalate to the permanent master, and the only thing the thief lacks is the live PIN / the owner's paired device. It is kept minimal: only those rare operations, at most once per session (a short step-up window covers a burst), paired-phone tap substitutes for typing the PIN. Every normal action keeps zero added friction. SHIPS DARK (`enabled` default false) — no owner sees any of this until the full live dashboard proof passes and the switch is flipped.

1. **Over-block** — Could a legitimate owner be blocked? When dark (default), no. When enabled: a credential operation prompts for the PIN (the declared step-up); a genuinely expired/revoked session falls back to the PIN screen (ordinary session expiry). No normal action is blocked.
2. **Under-block** — What does it still miss? A live stolen scoped token keeps the dashboard's broad read/operate reach, so it could reach the master INDIRECTLY (config/file/log read, session spawn) within its window — the deny-by-default allowlist that closes this is the tracked follow-up SEC-002c. SEC-002b bounds the LIFETIME + direct-credential reach.
3. **Level-of-abstraction fit** — Right layer: the scoped token is verified in `authMiddleware` (the one bearer chokepoint) exactly like the existing `mps_` memory-session pattern; the store generalizes the existing `DashboardOperatorSessionStore`. No parallel mechanism.
4. **Signal vs authority** — The store is deterministic (opaque token → server-side verify; no LLM). The credential-route deny-list + step-up is a real refusal, not a brittle heuristic with hidden authority. A stolen token is bounded by server-side state (expiry, family, cap), not a claim it carries.
5. **Interactions** — When dark, every path returns the master token exactly as today (no interaction). When enabled, the scoped token flows through the SAME routes the master did; the master token remains valid for API/CLI (two accepted principals). SSE/WS accept both and close scoped streams on revoke. The step-up store is distinct from the unlock-time operator session (a bearer cannot serve as a step-up proof).
6. **External surfaces** — Unlock adds `sessionExpiresAt`/`sessionFamilyExpiresAt` to its JSON; three new routes (`/dashboard/session/refresh|revoke|step-up`). The master token is no longer sent to the browser WHEN ENABLED. No change to any route's contract otherwise.
7. **Multi-machine posture** — Machine-local by design (`physical-credential-locality`): a session token is a bearer secret verified against one server's in-memory store, like the existing `DashboardOperatorSessionStore`/`PinAttemptStore`; replicating a bearer secret widens exposure for no gain. The master token stays the cross-machine credential.
8. **Rollback cost** — Single live switch: `security.dashboardScopedToken.enabled: false` makes unlock return the master token again, exactly as today; the middleware/WS/SSE behaviour for the master is unchanged. Revert the PR to remove the module + endpoints. No data migration; session tokens are in-memory and lapse on their own.

## Live dashboard proof (condition 2 — gates the flip, NOT the merge)

Before `enabled` is flipped on anywhere, the REAL dashboard is driven on the scoped token across EVERY surface — every tab, the terminal stream, SSE live updates, file editing, and Remote Desktop — at BOTH 1280px and 390px widths, recording a signed PASS/FAIL matrix; ONE broken tab for the owner FAILS it. The credential-op step-up (and paired-phone substitution) is exercised there. This PR ships the feature DARK; the proof is a pre-flip gate.

## Second-pass review (independent, Phase 5)

An independent reviewer audited the auth wiring against eight invariants. Invariants 1–6 and 8 HOLD (clean dark rollback; a dst_ token never reaches the master compare; credential routes require a step-up proof from a DISTINCT store minted only by a live PIN; refresh/revoke semantics incl. absolute-cap and family kill; SSE + WS close on family invalidation with no listener leak; master-token back-compat on every route; the lifecycle endpoints self-auth correctly before the bearer gate).

**Concern raised and FIXED (invariant 7):** `POST /dashboard/session/step-up` did a bare live-PIN compare with NONE of the unlock route's rate limiting — an unthrottled PIN brute-force oracle — and was registered UNCONDITIONALLY, so it was reachable even when the feature shipped dark (making the dark rollout a NEW attack surface rather than a no-op). Fixed: all three lifecycle endpoints (step-up/refresh/revoke) are now GATED behind `security.dashboardScopedToken.enabled` (404 when dark — a true single-switch no-op), and step-up consumes the SAME per-client + global + durable PIN limiter as `/dashboard/unlock` (`pinAttempts`/`globalPinAttempts`/`PinAttemptStore`, keyed identically). Verified by an in-process probe: dark step-up/refresh → 404; enabled correct-PIN → 200; repeated wrong PINs → 429 (rate-limited). At the #3211 rebase, step-up will be routed through the merged SEC-002 PinThrottle alongside unlock for one shared real-client limiter. **Reviewer:** independent second-pass subagent (Explore, fresh context), 2026-11-15, given the SEC-002b auth wiring; concern raised and fixed before commit; the remaining wiring concurs.
