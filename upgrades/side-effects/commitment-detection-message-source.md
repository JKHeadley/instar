# Side effects of the commitment detection history change

- **History and authority.** The additional SQLite read can expose previously missed live Telegram messages to the existing detectors. Positive topic IDs select the Telegram namespace. SQLite rows labelled as recovered history are excluded because replaying them can register historical promises as new work. Both stores preserve explicit automation provenance. Legacy SQLite rows remain unclassified and receive the sentinel’s existing legacy pairing treatment. Schema version 7 adds one nullable message column.
- **Reads and errors.** Each poll adds one local SQLite query when the store is open. The file read remains capped at 512 KiB. The job requests up to 100 messages, so a burst larger than its window can still leave messages unexamined. Authenticated recent-history requests return 503 for source failure. The sentinel reports read failures through its existing degradation path.
- **Writes and retries.** Action registration precedes bookmark publication. An interruption after registration and before acknowledgement can replay that batch. Concurrent acknowledgements contend for an exclusive staging file. A process killed during publication can leave a `.pending` file that blocks later advances and surfaces an error.
- **Installation.** Update refreshes the built-in job and script and can rewrite the body of a recognized stock legacy job. Schedule and enablement remain operator settings. A customized legacy prompt continues to run its own instructions.
- **Machine scope and rollback.** The job contacts the agent's loopback server. Polling performs no peer lookup or session enumeration. Rollback requires restoring the matching server and installed job bodies together. Both existing bookmark formats remain readable. Previously registered actions persist.
