# Side effects: a never-silent notice that keeps failing goes on the Needs-you list

**Version / slug:** `never-silent-needs-fallback`
**Date:** `2026-11-28`
**Author:** `Echo (Telegram Parity, CMT-2078 step 3)`

Stacked on `never-silent-notice-backoff` (step 2, branch fix/never-silent-notice-backoff) and `never-silent-undelivered-reason` (step 1, PR 4025); this branch contains both.

## Decision and authority

No authority changes: the item is a signal to the person, it approves, moves or sends nothing. `NeverSilentDeps` gains two optional hooks, `raiseNeed(need) → Promise<boolean>` and `clearNeed(id)`. `NeverSilentWatcher.noticeUndelivered` (new, replacing the two inline log calls) logs the failed try as before, then raises one item when the streak has a real failure (`errorCounted`, so an all-held streak never raises), the try number is at least `NOTICE_NEED_AFTER_FAILURES` (3), and this watcher has not already raised that item. Item id `never-silent:<incident>:<kind>` (`needId`), stable, so the attention queue's dedupe on id keeps one row. Raised ids are held in memory (`raisedNeeds`, at most 500). `noticeDelivered` closes the item when a notice of that kind gets through; `clearFinishedNeeds` runs at the end of every sweep and closes items whose incident is closed or gone. A raise that throws or returns false is logged `need-failed` and tried again on the next failed try. With no `raiseNeed` wired the watcher logs `need-unavailable` once per failure streak; the server always wires one (Telegram or the local list), so that row only appears for another caller or in tests. `adoptRaisedNeed(id, incidentId)` lets the server hand back an item raised before a restart. A close that fails is logged `need-clear-failed` (after the `need-cleared` row, which records that the watcher let go of it).

Server wiring (src/commands/server.ts): with a Telegram adapter, `raiseNeed` builds the item with `neverSilentNeedItem` (neverSilentWiring.ts, exported so it is tested) and calls `createAttentionItem` with `{ recordOnly: true }` (stored, never posted to Telegram, so it does not depend on the failing service): category `never-silent`, priority HIGH, `source: 'agent'`, which is what admits it to the Needs-you list (dashboard/console/home-model.js needsOperator). `source?: 'agent'` is now a declared field on `AttentionItem` (src/messaging/TelegramAdapter.ts); the agent server's own notices already set it through a cast. `clearNeed` calls `updateAttentionStatus(id, 'DONE', { silent: true, closedBy: 'cause-cleared' })` and throws when the row is missing, so the watcher logs it. A resolver, `never-silent-need`, registered on the adapter's attention lifecycle pass, returns `cleared` for a `never-silent:<incident>:<kind>` item whose incident is closed or gone and `active` while it is open, so an item raised before a restart, or dropped from the watcher's bounded memory, still closes. No Telegram adapter (a Slack-only agent): the same item goes to the local attention list (`LocalAttentionItems`, state/local-attention-items.json), the list GET /attention serves for such an agent, so GET /needs shows it too. The wiring opens its own `LocalAttentionItems` on the same folder as the agent server's: every call reads and writes the file in one synchronous step with an atomic rename, so the two share it safely in one process. The local list has no lifecycle pass, so at boot the wiring closes each open `never-silent:` item whose incident is closed or gone, and hands each one whose incident is still open back to the watcher (`adoptRaisedNeed`), whose sweep closes it once the wait ends. An item the owner marked WONT_DO is not reopened by a later streak (`LocalAttentionItems.raise` would reopen it, so the wiring checks first) and is not turned into DONE when the wait ends. The boot pass covers every open status (OPEN, ACKNOWLEDGED, IN_PROGRESS). No phone push for this item on either path; it is on the list the apps already show.

## Data and resource effects

At most one attention row per incident and notice kind per failure streak, stored in the attention file; a later streak reopens the same row. Telegram path: the attention queue refreshes an existing id with attention lifecycle on, its default (with `attentionLifecycle.enabled: false` a closed row stays closed and the watcher's raise is not seen; an owner WONT_DO is held for 30 days). Local path: a DONE row reopens; a WONT_DO row is left alone. Item text holds the conversation as `topic <id>` (named by the adapter) or "Slack conversation <channel id>", the try count and the bounded reason label; never message text. No new network call. After a server restart `raisedNeeds` is empty. Telegram path: the lifecycle resolver closes an item raised before the restart once its incident is over. Local path: the boot pass closes it if the wait is already over and otherwise hands it back to the watcher (`adoptRaisedNeed`). A new failure streak after the restart updates the same id on either path. Evidence: `need-raised`, `need-failed`, `need-cleared` and `need-unavailable` map to no evidence kind (neverSilentEvidenceKind returns null), so the error rate is unchanged by this step.

Self-action: none; no kill, restart or retry-on-self path.

## Class-Closure Declaration

unbounded-self-action: guard, covered by the existing registered controller `never-silent-conversation-recovery` (src/testing/selfActionRegistry.ts), whose convergence model already counts the watcher's notices as `notify` self-actions and is proven by tests/unit/self-action-convergence.test.ts. The new raise is another notify from the same controller and the same sweep, and it is bounded: one item per incident and notice kind per failure streak (stable id, deduped by the attention queue and by `raisedNeeds`), raised only from a failed notice try, and those tries are already backed off by step 2 (30 s doubling to 15 minutes). A failed raise is retried only on the next such try, never in a loop of its own. It closes once, on delivery, on the incident closing, or by the lifecycle resolver.

Restart: the registry entry's reset-safe reason names the durable store, but this action's state (`raisedNeeds`, `noticeRetry`) is in memory. A restart is safe for it for a different reason: a re-raise after a restart is an idempotent update of the same open row (same id, record only, no post), so it adds no row and sends nothing. The convergence model itself is not extended in this step (the reviewer's optional suggestion); the bound above rests on the unit tests in tests/unit/neverSilent-watcher.test.ts.
