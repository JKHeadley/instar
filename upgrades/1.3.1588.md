## What Changed

A promise that waits only for the operator's yes or no now has Approve and Decline buttons in the console. Approve hands the next step back to the agent; Decline closes the promise. The decision is posted in the promise's conversation and handed to its session.

The Desktop page and the app now offer guided setup. After the PIN, each machine that is not ready shows its one next step, taken from a live check on that machine: turn it on and restart it, wake or unlock it, allow a pop-up, open the exact System Settings page, or the written path. Readiness is decided only by the live check. The page says so, because the System Settings list can look empty or show several entries when the permission works. New routes: `GET /desktop/setup`, `GET /desktop/setup/:machineId`, `POST /desktop/setup/:machineId` (PIN session required; a Bearer token alone is refused), and the signed machine route `POST /api/desktop/setup`. A paired machine can now claim a machine that has no front yet, without that machine seeing a PIN; that raises a high-priority attention item, is logged in `logs/desktop-setup.jsonl`, and Turn off undoes it. The picker now names peers by the pool's nickname, not the peer's own copy. Guided setup is live on a development agent and dark on the fleet (`remoteDesktop.guidedSetup.enabled`); the picker's label fix applies everywhere.

Fixes #2485, reported by Matt Abate. When a second lifeline started more than five minutes
after the first, it read the holder's `ps` state `S` as wedged and killed it, but a healthy
idle lifeline is in `S` nearly all the time. New locks carry `heartbeatMs`, and the holder
touches the lock's mtime every 30 s. Such a holder counts as wedged only when the mtime is
over five minutes old and stays still through a 45 s second look. A lifeline still on older
code keeps the old test until it restarts onto this version.

Creating the lock is now atomic, and clearing a stale lock needs a short takeover mutex and
an unchanged lock, so only one starter can win.

When the Attention hub posts (an item, or a hub notice such as lost messages), every paired phone that registered for notifications gets an Apple push sent directly by the agent with the operator's APNs key (vault `apns_key_p8`, `apns_key_id`; `mobilePairing.push.teamId`). The payload carries no item text; the phone fetches the title with a per-device read-only token (`GET /mobile/attention/:id`). Per phone: a 2-minute fold, hourly after 40 in a rolling 24 hours, URGENT sooner, Apple 429 backoff; durable across restarts. Other machines of the agent receive the trigger (`POST /mobile/push/notify`) and the same condition notifies once. Registration: `POST /mobile/device/push` (device-signed, revisioned). Status: `GET /mobile/push`. Gate: `mobilePairing.push.enabled` (follows `mobilePairing`, development-agent gated). The service is built on every agent, with or without Telegram; only the hub-post hook needs Telegram.

## What to Tell Your User

When I'm waiting for your go-ahead on something, the dashboard now has Approve and Decline buttons, so you don't have to type the answer in chat.

Setting up Remote Desktop no longer needs me to change anything by hand. Open the Desktop page, enter your PIN, and each machine that is not ready shows one next step and rechecks by itself. Go by that page, not by the list in System Settings, which can be misleading.

A stray second start of my Telegram process could restart a healthy one, which could briefly
interrupt messages. It now exits and leaves the running one alone. A process that is really
stuck is still replaced automatically.

Once your phone is paired and notifications are on, it buzzes when something needs you, with the agent's name and what it is about, even when the phone is locked. Busy days are folded so it never floods.

## Summary of New Capabilities

- `POST /commitments/:id/decide` with `{"decision":"approve"|"decline","note":"..."}` for a pending promise blocked on the operator.

- Guided Remote Desktop setup per machine on the dashboard and in the app.
- A Turn off action for Remote Desktop on any machine, from its front.

- None: this is a reliability fix.

- Push notifications for the Instar iPhone app (`POST /mobile/device/push`, `GET /mobile/push`).

## Evidence

Operator request 2026-11-01 with a screenshot of a waiting promise that offered only "Reply in the conversation" and "I handled this". Unit tests cover the route (approve, decline, refusals) and the page model.

Unit, integration and end-to-end tests cover every guide state, the front ownership check, the refusal on a locked Mac, and the production boot with desktop off (the page is alive, turn-on writes the real config and requests a real restart). The Mac Lan label was measured: the M5's own registry says `Mac Lan` while the Studio's says `Mac M5 Pro`. No real machine's config was changed and no real prompt was shown while building this, so the real-Mac path is not yet proven: a real pop-up, the real settings page and a real turn-on across two machines have not been run.

Reproduced on v1.3.1576: an idle Node process with a 6-minute-old lock was killed, and one
with a 1-minute-old lock was left alone. After the fix, the idle holder survives and a holder
with a stopped heartbeat is replaced (unit tests with real child processes).

Race of 20 real processes starting at once: on the shipped code all 20 won, with no lock and
with a dead holder. The first version of this fix let 2 win in 2 of 5 dead-holder rounds,
which led to the mutex. The final code gave exactly 1 winner in all 40 rounds.

Spec converged at the 6-round cap with GPT-6 Astra and an internal reviewer. Tests: 15 unit (schedule timeline, throttle and URGENT, restart, APNs answers, revision ordering), 4 integration (registration, title read token, peer trigger dedupe, hub hook), production-boot check.
