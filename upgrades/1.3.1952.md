## What Changed

2026-11-20 post-mortem A3. Node 26 bundles undici 8, whose `fetch` negotiates HTTP/2 with any host that offers it (Telegram, Slack, the Claude API, Cloudflare-fronted tunnels). Node 20, 22 and 24 stay on HTTP/1.1. On a Node 26 machine the agent server's main thread got stuck in `Http2Session::SendPendingData` and its memory grew by gigabytes a minute (10 to 37 GB, killed five times in 16 hours). The Telegram egress door could not prevent it: Node 26 refuses the npm-undici dispatcher it passes, so it fell back to Node's default.

Every instar process now starts by replacing Node's default fetch dispatcher with the same class, built with `allowH2: false` (`src/core/http1GlobalFetch.ts`, called from `src/cli.ts` before any command runs). A dispatcher installed on purpose (a proxy agent, a test mock) is left alone and logged. `node:http2` used directly (APNs push) is unchanged. Opt-out: `INSTAR_ALLOW_FETCH_HTTP2=1`.

Security review of home (same-network) first-phone pairing. When a second phone presents a setup's code, the whole setup ends with reason `second-phone`, the phone already waiting is declined, and the home address closes if unused; `GET /mobile/phone-setup/:id` and `instar mobile add-phone` say a second phone tried and to start again. The number screen now says to type only the number shown on your own phone. The first-phone rule also counts owner phones paired through the agent's other machines, asked live; if any active machine cannot be asked, the setup is refused with `phone-check-incomplete`.

The updater's lookup for npm's CLI script next to the runtime node (added in #3603) tries several candidate paths and moves on when one is missing. That catch block now carries the `@silent-fallback-ok` marker with its reason, which brings the no-silent-fallbacks check back under its limit. Comment-only; the updater behaves exactly as before.

A machine that held the lead and restarted for a reason it asked for (a role change, an update, a restart through the API, the app or the dashboard, or the Telegram fix command) came back without it whenever its boot took longer than the lease's time-to-live. On the Mac Studio on 2026-11-21 that was a loop: it received the lead by hand-back, asked for the one planned restart a role change needs, its boot outlasted the lease, boot claim safety made it ask its peers first, the Laptop had taken over meanwhile, and ten minutes later the hand-back gave it the lead again — five restarts between 08:27Z and 09:55Z (feedback fb-135e3043-add).

Now, on a development agent (`multiMachine.takeoverReadyPool.plannedRestartLeaseContinuity`, riding the development-agent gate; `takeoverReadyPool.enabled: false` is the rollback):

- Every writer of `state/restart-requested.json` that lives in the server announces the request before the file becomes visible (`src/core/restartRequestSignal.ts`). While the request is pending, the holder's renewals carry a bounded window as their expiry instead of the TTL: the slowest of its last twenty measured boots plus a margin, or three TTLs plus the margin before any boot is measured (233 s on a 60 s TTL), never above the thresholds after which peers would take over a silent holder. The renewal is also written beside the lease (`state/lease-continuity.json`, signed) and the local lease record carries a pending marker.
- The three writers behind nearly every holder restart (role change, update, API restart) wait up to 8 s for that renewal to be confirmed before they write the request. Requests written outside the process are seen by a 2 s poll and extended at once.
- At boot, such a *window lease* is not held from the local file. The machine asks its peers first and renews the same epoch only after a live peer's identity-verified answer shows no newer epoch; a peer already at a newer epoch is adopted; a pool where every peer is presumed dead or has been silent for boot claim safety's span is kept as a survivor hold. Lease initialisation waits up to 120 s for that verdict. The boot's length is measured and feeds the next window.
- The pending state ends only when the request is withdrawn by this process, is absent for 60 s with no consumer's ledger row, was consumed but the process is still alive after the shutdown bound, or has waited four hours; a consumer's deletion alone never ends it, because the kill follows the deletion.
- A mesh-off pool's legacy lease dial now records a peer whose reply carries an identity ack bound to the request nonce as a signed answer for the boot hold (it read every legacy answer as silence).
- A peer this machine cannot dial for its own reasons (no route, or macOS Local Network permission refusing a home-network address, while the peer is alive by other routes) is treated as alive and unknown, never as dead: no survivor hold is taken on this machine's own blindness; it waits, keeps asking, and lapses to today's behaviour at the window's end.
- `/health` (with your token) shows `multiMachine.syncStatus.pendingRestart` while a restart is pending; the server log says what happened in `lease-continuity:` sentences.

Sibling-machine reach (spec `docs/specs/sibling-machine-reach.md`, commitment CMT-2073, feedback fb-56855d0f-0d2).

On 2026-11-20, after the Mac Studio rebuild, four subscription accounts were missing on the Studio while the Mac Mini held browser profiles signed in to all four. The agent told its operator to open the dashboard, enter his PIN and do four sign-ins. The outbound message check's "agent reach" described only the sending machine, so a per-machine gap looked like a gap in the agent's access.

Now:

- Each machine keeps a memory-only `SiblingHoldingsCache` (`src/core/sibling-holdings.ts`) of what its other machines hold: signed-in subscription accounts (plain `/subscription-pool`, which now names the answering machine) and browser profiles asserted signed in (a new light `GET /playwright-profiles?view=accounts`: agent bearer only, before the dev gate, no vault read, no file written). It refreshes every 10 minutes off the send path, dials at most 12 peers a tick through the admitted ropes only, backs a dead peer off (60 s, then 10 → 20 → 40 → 60 min), keeps each surface's last successful read dated by this machine's clock, discards a read whose responder is a different machine, and reports anything not read within an hour as UNKNOWN (never "none"). Older peers are read for their pool only and never asked for a browser view.
- The outbound gate renders an `OTHER MACHINES` section — this machine's pool accounts plus each other machine's holdings, one account per line, each sibling browser profile tagged with an opaque reference — only when other machines exist, so a single-machine prompt is byte-identical. The section opens with B17 precedence (other machines' holdings never satisfy HELD-ACCESS) and a B21 per-machine sub-clause: a procedure handed to the operator for a sign-in, browser step or missing account on one machine is user-task substitution when another machine has a browser profile signed in to that exact identity (a pool login there is corroboration only; UNKNOWN, same-provider-different-identity, another person's account, a new account, a physical step and a one-tap PIN approval pass).
- In code, other machines' data can only nudge: any B17 or B21 from a prompt that rendered the section is re-reviewed once without it (`reviewWithinBudget`, bounded by the route timeout). A B17 stands only if the local-only review also says B17; a local-only B17 wins over a sibling B21; a re-review with no verdict takes the existing no-verdict path, never a confirmed B17.
- When B21 fires citing a sibling profile reference that validates against the reach that built that prompt, the 422 carries `otherMachine` (machine, admitted address when it still resolves, counts) and `otherMachinesHint` — a server-owned template appended to `suggestion` and `howToProceed`, which the reply scripts already print — and every account identity rendered in the prompt is redacted from the model-written `issue`/`suggestion`.
- `GET /subscription-pool?scope=pool` gains `siblingReach` (per machine: ages, failures; account and browser identities only for the agent's own bearer). The awareness entry *Access you already hold* now says: check every machine with that one lookup, and use a helper session on the machine that can.
- Feature evidence `toneGate.siblingReach`: `hint-attached`, `override-after-hint`, `complied-after-hint`, `b17-overturned`, `b17-unconfirmed`. The refresh loop is registered as the `sibling-holdings-refresh` self-action controller.

Switch: `toneGate.siblingReach.enabled`, read live on every send and tick. Unset = live on development agents, dark on the fleet; an explicit value always wins. Off, or a single machine, is byte-identical to before.

A machine whose server has just come back from a long stall (a sleep, or a heavy build starving it for minutes) could take the multi-machine lead from a healthy machine within a second of waking, because its own copy of the holder's lease had aged past the lease lifetime while it processed nothing (fb-fdb55c1c-a79). A new switch, `multiMachine.takeoverReadyPool.stallReconfirm`, makes the lease coordinator keep its own awake clock: when it has lost more than 30% of a lease lifetime of running time within one lifetime (one long gap or a burst of shorter ones), a claim on a lease another machine holds is held until fresh evidence exists. It first pulls every peer over every route, so a live holder's renewal lands and the claim is refused; it claims only after a full lease lifetime has passed awake and a pull round started after the stall has completed (a machine that keeps stalling is capped at ten lifetimes). Each step is logged as `stall-reconfirm: ...` and recorded on the takeover-ready-pool feature evidence, including a suspected-overlap error if the machine taken over signs a newer renewal soon after. Off by default everywhere; off is exactly today's behaviour.

When the agent installs an update, it rebuilds one compiled dependency (the `better-sqlite3` database driver) and then checks that the new version starts and can open a database with the agent's own Node. The rebuild used to run `npm` from the machine's PATH, which runs under whichever `node` is first on PATH; on a machine where that is a different Node major (Homebrew Node 22 while the agent runs its own Node 24), the binding was built for the wrong Node and every update was refused (Echo Studio, 2026-11-20/21, kept back on 1.3.1944). The updater now runs the runtime Node's own bundled `npm` with that Node, puts the runtime Node's directory first on PATH for the build, and points node-gyp at the runtime's bundled headers (`npm_config_nodedir`) when present. If the runtime Node bundles no `npm`, it falls back to `npm` from PATH under the same PATH prefix and logs that it did. Rollback uses the same invocation. Separately, `POST /updates/apply` now has its own 15-minute request budget: it awaits the whole install, and under the 30-second default the server answered 408 early and then dropped the real answer as a "Suppressed duplicate response send".

## What to Tell Your User

- **Steadier on newer Node**: "On machines with the newest Node, my server no longer risks a runaway memory loop when a web request is cut short. It talks to the outside world the same way it does on older Node."

- **Safer first-phone setup at home**: "If someone else's phone tries the code I show when you add your phone at home, I now cancel that setup and tell you to start again. And I make sure none of my other computers already has your phone before I treat a phone as the first one."

- **Nothing to notice**: "A small housekeeping fix in how updates find npm. Nothing changes in how updates work."

If one of your computers leads the others, it now keeps that role when it restarts for a reason it asked for: an update, a change of role, or a restart you asked for from the app, the dashboard or a message. Before, a slow restart handed the lead to another computer and could hand it back and forth for an hour. A restart you ask for through the API answers up to 8 seconds later than before while the lead is secured. Two things do not change yet: a computer that is killed or loses power still gives up the lead the old way (a later change removes the restart that role changes need), and a machine rolled back to an older version in the middle of a restart boots the old way once. Nothing changes for agents that are not development agents yet.

If your agent runs on more than one computer: before it asks you to sign in, do a browser step or add an account on one of them, it now checks whether another of its computers already has that account signed in — and if so, it does the step itself from there instead of asking you. Nothing to set up. (It reaches other agents only after it has proven itself on the development agent.)

- **Fewer wrong lead changes after a computer freezes (when switched on)**: "If one of my computers freezes for a few minutes, for example during a big app build, it will no longer grab the lead from a healthy computer the moment it wakes up. It checks with the others first. This is switched off until we turn it on for your computers."

- **Updates install again on machines with more than one Node**: "If this machine kept failing to take updates with a message about NODE_MODULE_VERSION, that is fixed: the update now builds its database driver for the same Node that runs me, no matter which Node your system has on its path."
- **Applying an update by hand waits for the real answer**: "When you ask me to apply an update right away, the request now waits for the install to finish instead of timing out after 30 seconds."
