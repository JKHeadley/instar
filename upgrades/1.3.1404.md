## What Changed

- **A Claude login that has stopped working now gets repaired automatically, even when its saved login file can't be read.** Before, if the saved login was unreadable, the account stayed marked "active" (an unreadable file alone is never treated as proof). New sessions kept landing on the dead login and the automatic sign-in repair never started. Now, when Claude Code itself shows "Login expired" in two different sessions under that login within an hour, the account is marked as needing sign-in and the usual repair takes over.
- The session monitor that ends stuck jobs at the "Login expired" screen now reports each sighting to the account checker. The account checker still decides on its own; a working login is never changed by these sightings, and a login whose keychain is merely locked (for example right after a reboot) is deliberately left alone, since a repair could not write to it either.
- The sign-in history now says when an unreadable-login watch ended because the account was confirmed dead ("escalated") rather than because the login came back ("resolved").

- **local-verify re-runs a lane's few failed files once, alone, before calling it red** (spec `docs/specs/local-verify-merge-authority.md`, Throughput budget). On 2026-10-22 the first two server-run `main` verifies each failed exactly one file that passes alone; with `main` moving often, every new head's first failure re-entered `main-suspect`, so one flake per run kept `main` suspect and stopped PR verifies. Now a lane whose only problem is 1–3 failed files re-runs exactly those files once, one at a time, with the same config, env and flags, under what is left of the lane budget (the cap of 3 covers the whole verify). On a PR verify a file the PR changed (or that imports a changed file), or any file when this machine has no green `main` record, is never re-run; a lane with an unhandled error is never re-run, and each re-run gets a fresh temp dir. A file that passes goes in the record's new `flakyRetried` field and the lane passes; one that fails again is a real failure with both messages; more than 3 failed files is a real break (no re-run).
- **Each flaky file becomes a tracked item:** one deduped attention item per file (`local-verify:flaky:<file>`), re-raised with the count when the same file keeps flaking (3 times in 7 days), and `GET /local-verify/status` (and `GET /local-verify`) report `flakyFiles` (file → count, last seen, lane).
- **Main verifies explain themselves (ACT-151):** a `main` verify writes the same bounded `run-detail` audit line as a PR verify (reasons, failures with first and re-run messages, flaky re-runs), and the `local-verify:main-red` item carries it.
- **Fair share for the single slot:** with `main` healthy, a `main` verify starts ahead of waiting PR verifies once its oldest unverified merge is 90 minutes old; while `main` is suspect or red it keeps priority but takes at most every other start while PRs wait. A release commit (`chore: release v… [skip ci]`) that touches only release files and whose only parent this machine already verified (or has queued) triggers no `main` verify of its own.

- **Restarting a dead session by its display name now gets a useful refusal.** The restart call (`POST /sessions/refresh`) takes a session's tmux name (for example `echo-topic-127831`). Given the display name instead (`topic-127831`), the server already pointed at the right name when such a session was running. When the session had died, the same call came back as "not bound to a Telegram topic (checked in-memory + disk registry)" with no hint, which read as a lost topic binding. It was not: the binding was intact and a restart under the tmux name would have resumed the conversation. The refusal now names the tmux name for a dead session too, as long as its topic still points at it, and says that a refresh of that name respawns from the saved conversation. A dead name whose topic has moved to another session is not suggested. The hint is still only a hint; nothing is remapped or restarted differently.

## What to Tell Your User

If one of your subscription logins expires, I should now notice it and start fixing it myself, instead of quietly trying to use the dead login for hours. You may see it switch to "needs sign-in" on the Subscriptions tab while the repair runs.

Nothing to do. My own test runs no longer treat a test that fails once and then passes on its own as a broken build: they re-check it, keep going, and flag that test so it can be fixed. Checks on the main branch also stop crowding out checks on waiting changes.

Nothing changes for you. This only makes one of the agent's internal error messages more accurate.

## Summary of New Capabilities

- No new capability. The existing automatic sign-in repair now also starts when Claude Code's own "Login expired" screen confirms an unreadable saved login.

- `flakyFiles` on `GET /local-verify/status` and `GET /local-verify`.
- `flakyRetried` on local-verify records; `local-verify:flaky:<file>` attention items.
- `run-detail` audit lines for `main` verifies.

- No new capability. One refusal message now tells the caller the name that works.

## Evidence

- 2026-10-22 incident on the Mac Studio: the headley.justin@gmail.com login was dead for about 8 hours and stayed "active" while 40+ sessions stopped at "Login expired". No repair episode was opened.
- New tests: two sessions plus an unreadable login gives "needs sign-in" and the repair accepts the cause. One session, old sightings, a different login, or a readable login change nothing. An end-to-end run from real session kills into the real account checker.

- Unit (`tests/unit/localVerify/orchestrator.test.ts`): one flaky file passes after its re-run and is recorded; two failed files with one failing again ⇒ failure with both messages; four ⇒ no re-run; a zero-collected file ⇒ no re-run; the re-run respects the lane deadline; the per-verify cap.
- Unit (`tests/unit/localVerify/mainHealth.test.ts`): main run-detail and main-red payload; one deduped signal per flaky file and `flakyFiles` across PR and main records; a main whose only failures were flakes leaves main health unchanged; fair share both sides (healthy 2 h window, unhealthy every-other start, unchanged order without inputs) and in the service; release collapse both sides.
- `tests/unit/self-action-convergence.test.ts`: new models `local-verify-flake-rerun` (≤ 3 re-runs per verify, each file once) and `local-verify-main-fair-share` (main starts ≥ 2 h apart while PRs wait; never two in a row).
- Each guard was removed in turn and a test failed (fair share, the re-run, its deadline cap, its per-verify cap, signal dedupe, main run-detail, release collapse).

- `tests/unit/SessionRefresh.test.ts`: a dead session whose topic still points at it is named once (two finished records, one hint) and the authoritative path still refuses without killing anything; a dead session whose topic moved to another session gets no hint; a live match and a dead-bound match under one display name are both listed. The existing running-only wording and the route's 409 test are unchanged.
- Incident: Mama PC, 2026-10-22 ~19:05 UTC, topic 127831. The server log shows the same 10 topic bindings loaded at every boot and no unlink; the refusal came from the display name.
