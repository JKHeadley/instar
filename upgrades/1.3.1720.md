## What Changed

The owner's phone can add a Claude or Codex account with Face ID and go straight to its sign-in page.
- **New route `POST /mobile/accounts/add`** `{provider: "claude" | "codex", nickname?, email, challenge, presenceSig}`: owner phone only, behind the app's Face ID write gate. Challenge `POST /mobile/permissions/challenge {action: "account-add", target: "<provider>"}`, signed line `account-add <provider>`.
- **The server picks everything a phone cannot know:** a fresh pool id (`[codex-]<name>-<4 hex>`, never one already used here, on another machine, by a waiting sign-in or by a login folder), the framework (`claude-code` / `codex-cli`) and the login folder (`~/.claude-followme-<id>` / `~/.codex-followme-<id>`), then starts the sign-in on the serving machine through the follow-me sign-in core (now shared with `follow-me/enroll/start`). The answer is start-cell's shape.
- **The account joins the pool only when its sign-in completes and the signed-in email matches**, through the existing follow-me completion and the pool's verified add. The route accepts no credential: any field beyond the five is refused. An email already in the pool answers 409 `account-already-added` with the account id; a second tap returns the same waiting sign-in.

The owner's phone can start an account sign-in with Face ID instead of the dashboard PIN.
- **New route `POST /mobile/accounts/sign-in/start`** `{accountId, machineId, challenge, presenceSig}`: owner phone only, behind the same Face ID write gate as the app's other owner actions. The challenge is `POST /mobile/permissions/challenge {action: "account-sign-in", target: "<accountId>@<machineId>"}` and the signed line is `account-sign-in <accountId>@<machineId>`, so a proof covers one account on one machine, once.
- **Same core as the dashboard.** The route runs `POST /subscription-pool/matrix/start-cell`'s own write barrier and core (now shared functions in routes.ts) and answers the same body (`verificationUrl`, `loginId`, `machineId`, `expectedEmail`, `ttlExpiresAt`, `notice`, `kind`). The PIN route is unchanged for the dashboard.
- Strict ids (`accountId` as the pool stores it, `machineId` one word with no `@`); a member or team phone, the bearer, a bad signature and a proof for another account are refused and audited in `state/mobile-permission-actions.jsonl`.

An agent that answers is never "can't tell" any more.
- **Unsorted notes are notes.** `GET /mobile/health-issues` no longer turns unsorted items into the verdict `unsure`. They keep the agent off "healthy", reading `running` with the headline "Running, with 2 notes I haven't sorted yet."; only a problem that affects the person raises it to `attention`.
- **`unsure` means a failed reading.** It now means only that the agent couldn't read its own health. The route answers 500 with `verdict: "unsure"`, a `reason` (`timeout`, `health-read-failed` or `summary-failed`) and a plain `detail`. An unreadable /health body summarizes to `unsure` with "I couldn't read my own health just now."
- **Dashboard Health page.** It reads `unsure` with nothing affecting the person, from an older server, as running, and says how many notes are unsorted.

Repairs main. The app conversation context file used a clock-only name with an exclusive write, so two writes in one millisecond threw EEXIST (`tests/unit/app-dispatch-engine.test.ts`). The name now has a random suffix.

An app conversation, and its session, can move to another machine the way a Telegram topic does: `POST /pool/transfer` with `app:<key>`, and the phone's Face ID Move. Part 3b of Justin's 2026-11-06 ask (topic 134088).

**On for development agents only** (`multiMachine.sessionPool.appConversations.enabled`, resolved through the development-agent gate). With it off, this machine doesn't advertise `appConversationsPool`, and the lease holder serves every app conversation exactly as before. It stays off for the fleet until a real two-machine move has run, because a duplicate is still possible when an attempt reached another machine before its delivery event replicates.

- **One owner per conversation.** Each moved conversation has a fenced `SessionOwnershipRegistry` record keyed `app:<key>`. A conversation that never moved has no record, and the lease holder serves it exactly as before. `AppConversationService.isOwner()` is gone: `serves(key)`, `mayReply(key)` and `currentOwner(key)` replace it.
- **Only two things move one.** A completed drain, or the operator's "Bring it back here" (`POST /pool/bring-back`, Face ID on the phone). No pins, no router placement, no overload shed, no automatic takeover.
- **Messages reach the owner.** The phone still talks to the lease holder. The holder stores the message, then delivers it, holds it (mid-move, or for the lease gate) or forwards the signed event to the owner. Forwards are acknowledged only after durable ingest. A held message that runs out at the queue's limits is finished as refused, in words.
- **Stop and pause go to the current owner,** including one draining the conversation, and abort that drain. "Intercepted" is said only on the owner's acknowledgement.
- **The lease gate.** A new lease holder serves no-record conversations only after a `session-status` round, bounded at 30 seconds.
- **Losing a conversation closes its session.** A machine that learns it no longer serves a conversation closes its copy, retried on every reconcile.
- **Older machines stay out.** Moves need `seamlessnessFlags.appConversationsPool` on every online machine. An older machine coming online brings moved conversations home; an older lease holder makes owners release theirs.
- **Support people.** Their conversation moves only to a machine advertising `memoryPrivacyEnforced`.
- **Journal.** App placement rows carry `data.sessionKey` and no numeric topic; older readers skip them. `OwnershipReconciler`, `StaleOwnerReleaseEngine`, `DuplicateSessionReconciler` and the overload shed skip `app:` keys.
- **Inbound queue.** Its drain now delivers by kind, so a queued Slack message is delivered rather than failing as a non-numeric key.

Rollback: revert. Before a deliberate downgrade, move every app conversation back to the lease holder, which releases its record. Leftover `app:` records and pins are inert for serving, but an older machine's overload shed, stranded notice, reconciler or stale-owner engine may still read them.

Three fixes from the first real two-machine move of an app conversation. All are behind the app-conversations pool feature, which is on for development agents only.

- When the machine running a moved conversation stops answering, the phone offers "Bring it back here" after about 2 minutes, instead of 15. The serving machine now counts the other machine as answering only if it reached it directly in the last 2 minutes, the rule pool readiness already uses.
- A message saved while that machine was unreachable is now delivered once it answers, on an agent without Telegram too. Before, the queue passed app messages through a delivery step that only Telegram sets up, so they expired unsent.
- A message saved for a moved conversation now survives a restart of the machine that serves your app. Before, a restart dropped any such message that had waited more than 2 minutes.

Adds the engine checkpoint for the Context Budget work (`src/monitoring/engineCheckpoint.ts`): a byte-exact, hash-verified copy of a session's transcript taken before a fold, kept privately on this machine (0600 under `.instar/state/context-archive/<topic>/checkpoints/`, never served, never backed up, never replicated), and a restore that resumes the original session when it is unchanged or materialises the checkpoint as a new session transcript otherwise. Adds the FoldCoordinator for the Context Budget work (`src/monitoring/FoldCoordinator.ts`, `foldCarriers.ts`, `foldCoordinatorBoot.ts`): the single writer of a durable per-fold record (compare-and-swap transitions fenced by the per-topic fold lock), carriers keyed by fold id and released only by the record's terminal transition, a quarantine handover to the sentinel, a consecutive-rollback breaker, and a boot sweep (`recoverPendingFolds`) that runs on every server start before the inbound-queue and pending-inject sweeps. A crashed fold before the point of no return is discarded; one past it is quarantined; carriers with no record are released and reported. Pending-inject records tagged with a fold are skipped by the generic inject sweep. Fold records and fold-lock files are never backed up. No fold can begin yet (the sentinel and layer kind are later slices), so on a healthy agent the sweep finds nothing.

Adds the egress fold hold for the Context Budget work (`src/monitoring/FoldHoldStore.ts`): while a fold is reorganizing a conversation's working memory, every session-authored send for that conversation is refused `409 fold-hold` at the shared outbound chokepoints (`evaluateOutbound` on every channel, and `authorizeTelegramSessionSend` before the relay fork). Conversations are keyed channel-neutrally (`foldKeyForConversation`), so the hold covers Telegram, Slack, the app, WhatsApp and iMessage. The hold is a carrier of the fold record: written by the coordinator, released only by the fold's terminal transition or the boot sweep, with a scoped fail direction when its store is unreadable, and every refusal audited. A redriven reply refused by a hold is retried after the fold, never reported as lost. Nothing writes a hold yet, so every send is unchanged.

Adds held inbound for the Context Budget work: while a fold holds a conversation, its incoming messages wait in the Durable Inbound Message Queue (frozen, invisible to the drain, their expiry clock stopped) and are released only when the fold's record ends — by the fold's terminal transition, or, after a restart, by a settle pass right after the queue opens. The queue gains a session-level hold table and three additive columns (added once, idempotently, on open). An operator pause/resume never releases a fold's messages and fold time never counts toward the pause limit. If the queue is off at a later boot and expires fold-held messages, the loss notice names the fold. Nothing holds a conversation yet, so the queue behaves exactly as before.

Adds the fold-marker tool policy for the Context Budget work: a PreToolUse hook (`fold-marker-guard.js`, on every Claude Code agent through the shared wildcard hook set, installed by init and every update) that restricts a session the fold coordinator has marked. The third piece of the Chief of Staff (docs/specs/chief-of-staff-topic.md §2–§5): the check-in loop. On the lease holder, every fifteen minutes by default, it reads the replicated store, works out whether the owner's check-in lease is live (a signed renewal younger than 72 hours), and for every bound project that is due it gathers deterministic evidence (merged PRs and net diff on linked branches, run state, the Liveness Reconciler's condition, live session, overdue commitments, conversation timestamps plus a byte-bounded untrusted tail), applies the deterministic floors, asks the metered LLM judge only when a question remains, records the check-event and waits for it to be on disk, and then acts through the action protocol — a bounded restart for a stalled project, a redirect for a drifting one, a verification for one that claims done — within the per-tick, per-project and weekly caps. Notes go out once per cadence at the owner's note time; immediate messages are capped per day. `GET /chief-of-staff` and `GET /chief-of-staff/projects/:key` expose the loop's health, the protocol's status, and one row (or the detail) per bound project. The owner-tunable settings (`chiefOfStaff.tickMinutes`, `defaultCadenceHours`, `maxRunHours`, `operatorLeaseHours`, `noteCadenceHours`, `noteTime`, `maxRestartsWithoutProgress`, `breakerRestartsPerWeek`, `immediateMessagesPerDay`, `judgeDailyCents`) are migrated in with their defaults.

Dev-gated: the loop is constructed only where `chiefOfStaff.enabled` resolves on (development agents); elsewhere the routes answer 503 and nothing changes. Even on a development agent the loop observes only until the owner speaks in the Chief of Staff conversation, which the next release creates.

Hardened by the independent second-pass review before merge: a checklist whose judgment items are marked for agent certification still waits for the owner (no un-judged auto-close); the progress baseline lives on the check-event record (`doneItems`), so restart caps survive a process restart or a holder change; an unreadable group member count sends the note to the owner's DM, never the forum; a run whose session fails to start is marked ended at once (`AutonomousRunStore.findByRunId`); the first tick after a holder change checks but does not act; a routed restart counts only when the owning machine actually started it, and its refusals reach the note.

The second piece of the Chief of Staff (docs/specs/chief-of-staff-topic.md §2.4): the action protocol. Every side-effecting action the Chief of Staff will take (restart a stalled project by injecting a continuation or starting a bounded run, redirect a drifting one) now has one durable state machine — `claimed → executing → started | superseded | rejected | lost | aborted` — recorded as immutable events in the `chiefOfStaff` replicated store. The lease holder signs each claim; the conversation's ownership machine verifies that signature against the current lease holder and a fresh renewal, re-checks ownership, the open-intent rule and the stand-down list under the conversation lock, writes `executing` and waits for it to be fsynced before doing anything, and records `started`. Recovery never marks an action lost without the owner's tombstone; a new owner refuses to act until the previous owner's open intents have outcomes; duplicates return the recorded outcome. Two mesh verbs (`cos-action`, `cos-settle`) carry this between machines. The Liveness Reconciler, the resume queue and the silence heartbeat each gained an optional stand-down read so they never act on a conversation the Chief of Staff is acting on. Autonomous run records can carry `cosNoRespawn` and `idempotencyKey`. The `chiefOfStaff` config block and its dev-gate entry are declared.

Dormant: nothing calls the protocol yet (the check-in loop is the next release), the operator check-in lease reads as expired until that loop derives it, and the protocol is constructed only where `chiefOfStaff.enabled` resolves on (development agents; dark on the fleet).

The first piece of the Chief of Staff (docs/specs/chief-of-staff-topic.md): a new replicated-record kind, `chief-of-staff-record` (store key `chiefOfStaff`), and the pure store module behind it (`src/core/ChiefOfStaffStore.ts`). It carries the Chief of Staff's conversation tree, project bindings (goal, definition of done, cadence, linked repos), binding lifecycle events, check events, action intents with their transition log, operator check-in renewals, graduation records and loop liveness markers — every one an immutable event, with open/closed state, intent state, restart brakes and lease expiry derived by folding the union, so two machines can never disagree and arrival order cannot change a view. `CoherenceJournal` gains `emitReplicatedRecordWithSeq` and `awaitDurableSeq`, the wait the action protocol needs before any spawn. Retention for the kind is never-delete. Nothing emits yet: the kind is registered but dark on every agent.

The fourth piece of the Chief of Staff (docs/specs/chief-of-staff-topic.md §1.4, §3, §4, §6): its own conversation and the surfaces around it. On an agent where the feature is on, the lease holder creates one Telegram topic for it, pins the greeting inside that topic (the app and the dashboard are where it floats to the top; Telegram cannot pin a topic itself), renames it when the owner changes the display name, and only ever unpins (never deletes) it when the feature is switched off; standby machines adopt the holder's topic like the Attention and Updates topics. Only the owner's messages in that topic are routed; anything else is dropped, logged, and answered once a day with a plain line saying only the owner can talk there. The app's conversation list carries the pinned conversation on the first page and a parent link on every row for the owner, so a new app build can draw the tree while older builds keep seeing the conversation where it always was. The dashboard's conversations page now leads with whatever the Chief of Staff needs from the owner (the same rows Home counts), lists the pinned conversation first with sub-topics indented under their projects, and offers a PIN-gated Check-in button (the app's own check-in arrives with the next piece). The note's "Needs you" items carry one-tap buttons (Unpark, Confirm done) that are owner-checked before anything runs, and a tap also counts as a check-in. The agent's own CLAUDE.md gains one line: when the owner starts an effort in that conversation, draft its binding.

Dev-gated like the earlier pieces: nothing is created, pinned or shown on an agent where `chiefOfStaff.enabled` is off.

Conversations now have pinned messages, any number, like Telegram (docs/specs/conversation-pinned-messages.md).
- **A new `pin` event in the conversation store.** A pin or unpin is kept with the conversation (app conversations, Telegram topics and Slack conversations), so every machine shows the same pins, newest first. Up to 100 per conversation.
- **Routes for the app and the dashboard.** `GET /mobile/chat/app/:key/pins`, `GET /mobile/chat/:topicId/pins`, `GET /mobile/chat/slack/:conversationId/pins?machine=` list them (`{conversationKey, pins:[{messageId, pinnedAt, pinnedBy:{name, role}, preview, source}]}`); a device-signed `POST` to the same paths with `{messageId, pinned, requestId}` (plus `machine` for Slack) pins or unpins and answers `{ok, pinned, changed, mirror, mirrorDetail?, pins}`. Every history read also carries `pins`. Pinning follows the same access as sending; seeing pins follows reading. The agent's own token can read pins but never change them.

## What changed

Agents now offer to handle safe account tasks, read complete account pages before acting, and treat recovery codes as break-glass credentials requiring specific informed authorization. The normal macOS Chrome helper surfaces a review advisory before scripts on detected recovery-code or account-hold pages while retaining fixed read-only page inspection. Existing agents receive the helper and guidance on update.

Developers can use the opt-in GitHub development-release workflow while npm publishing is unavailable. Checksummed packages install through the normal candidate, native validation, promotion and migration path. The next official npm patch returns development agents to stable.

## What to do

Continue ordinary authorized sign-ins. Never use recovery codes to bypass an unavailable security key or browser restriction. Read every page chunk and compare fingerprints before an account action. On a flagged page the session agent must read the complete page and record its review against the current fingerprint before continuing. Deliberate recovery still needs specific informed operator approval; an agent acknowledgment is not that approval.

Development/test agents needing updates during a publishing outage can follow docs/development-releases.md. This is explicit per-agent installation, with normal session-aware restart afterward. Normal stable updates are unchanged.

## Limits

The browser safety floor covers known top-level page warning/form shapes in the normal macOS Chrome helper. Other drivers and frames still require the same safe workflow. It is not a universal provider-lockout guarantee.
