## What Changed

The context budget gains A and G, the Anchor and the decisions/evolutions ledger (context-budget-layered-summaries §6.1, §6.2; Phase 1 S6). While `contextBudget.enabled` is on:

- **The Anchor.** Each topic's Anchor is the operator's first substantive message (an opening "hey" is skipped), plus any further framing messages sent before the agent's first reply (at most three). Only the operator's own typed rows count, as U labels them; forwarded, relayed and other people's rows never anchor a topic. A topic with no such message reads `no-anchor`. The record holds pointers to the rows (message id, hash, length), never the words.
- **The ledger.** Decisions and changes of purpose ("evolutions") are recorded per entry, with `supersedes` links, and replicate per entry. They come from the topic-intent evidence model rather than a new authority:
  - **A decision** settles only when the operator's own message is bound to it and that message's referent stub says it answers or directs (`derived-settled`). It becomes `settled` when the operator re-affirms or re-references it later. Anything else is `pending`: an agent proposal, another person's message, a question, a hypothetical, a rejection, or no stub.
  - **An evolution** is a new goal stated after the Anchor. It is `user-directed` (bound to the operator's message) or `insight-derived` (the agent's), and it is `additive` or `narrowing` according to the extractor's own contradiction read, which is recorded with its evidence. It starts `tentative`. It is confirmed only by the operator: a re-reference or affirmation for their own change, and an explicit yes, after it was surfaced, for the agent's narrowing insight. Silence never confirms it. If the confirmation lapses, the operator's own change stays in force as `unconfirmed`, and an agent insight becomes `expired`. Nothing is deleted.
- **Confirmation queue, extended.** Evolution confirmations take priority over ordinary ones; a displaced confirmation is requeued, not dropped. A full queue now defers instead of dropping, with a counter. An evolution's 7-day clock starts only when the next agent reply surfaces it, and needs a user message since. The topic-intent briefing shows a pending evolution as "PURPOSE CHANGE TO CONFIRM". Queue changes now take the topic file's lock.
- **Live set.** Superseded, withdrawn and expired entries archive first. A settled or confirmed entry in the current phase, or re-referenced in the last 20 operator turns, never archives. Then newest first within about 3K tokens.

New route: `GET /topic/:id/anchor` (bearer only) returns the Anchor's row pointers, every entry's type, cause, effect, status and links, the live-set summary and the confirmation queue's shape, never message text; 503 while the layers are off. `GET /context-budget/metrics` now reports real Anchor and ledger counts in place of "anchor-ledger-not-built", and `GET /context-budget/layers` shows the builder's counters.

The context budget gains the Anchor and ledger backfill (context-budget-layered-summaries §6.1, decision 9, §12; Phase 1 S7), behind a new switch, `contextBudget.backfill.enabled` (default off, read live), on top of `contextBudget.enabled`:

- **A background lane** rebuilds existing conversations' Anchor and decisions/evolutions ledger from TopicMemory history, on the machine that owns the conversation only (a single machine owns all of them; in a pool the ownership record must name this machine, and an unknown owner is skipped). It takes conversations newest first, starts at most 20 a day, works a few per 10-minute tick in bounded pages, and keeps a small resume file so a restart neither redoes nor skips a conversation. It makes no model call: it reads the refs and referent stubs the extractor already wrote.
- **History entries are `backfilled-unconfirmed`**: usable, labelled, with their normal derivation kept beside them. Only entries bound to the operator's own message are rebuilt; agent proposals and other people's messages from history are left out. A later re-reference, affirmation or confirmation from the operator gives an entry its normal status; a withdrawal still applies.
- **One confirmation per conversation**, a new `backfill` kind in the existing confirmation queue (ranked below a live purpose change, above ordinary confirmations). The topic-intent briefing shows it only after the user has written since it was queued, as one line to fold into the reply, never as a message of its own; it is asked exactly once, in that reply, and then leaves the queue; it settles early when nothing is left unconfirmed, and the entries stay labelled until the operator's own words move them. This also closes S6's gap: old purpose changes on an existing conversation are now covered by it instead of asking nothing.
- `GET /topic/:id/anchor` gains a `backfill` block; `GET /context-budget/metrics` gains `anchors.backfill` (conversations rebuilt, entries still unconfirmed, `pendingConfirmations` for the dashboard card and Home's count, and the lane's status); `GET /context-budget/layers` gains the lane's status. A Registry-First row points agents at it.

The Codex adapter's next-prompt seed and its verification suite (context-budget-layered-summaries §9.6 Codex column, §9.1, §16 Phase 1; slice S17).

- **Codex sessions get their context back after a compaction.** Codex has no hook that seeds a session right after it compacts, so the per-prompt hook now carries the seed. On the first Codex prompt after a compaction, the server checks the session's own rollout. The newest `compacted` entry is the compaction, and its `window_id` is the context epoch. The server returns the topic's verified standing packet with a note saying it is delivered with this prompt, and the hook prints it in place of the usual topic briefing.
- **Seeded once per compaction.** The server reads "already seeded" from the rollout itself: Codex records the hook's output as model input, so a seed the model received is never repeated. A delivery Codex dropped is retried once, on the next topic prompt. The hook then acknowledges, which writes the seeded marker. Only the topic's own live Codex session is offered its packet, and only on the first topic prompt after the compaction (one retry). A packet that fails verification is never sent: that prompt gets the usual briefing.
- **Routes.** `POST /context-budget/codex-seed`, `POST /context-budget/codex-seed/ack`, and `GET /context-budget/codex-seed` for the counts.
- **The canary can verify Codex recovery.** A Codex compaction waits for its next topic prompt. It counts as recovered once the seed appears in the rollout as model input, and as diverged if that prompt passed without one. A compaction followed by another before any topic prompt is superseded and is judged neither way. A Codex row stops at `accruing`, because no test compaction is wired for Codex yet.
- **The Codex adapter verification suite.** It runs on one throwaway headless Codex thread and is refused under a channel topic. It records every row of the §9.6 table, measured, per machine, engine and version. The sentinel reruns it whenever the Codex binary's version changes; it is off unless `contextBudget.adapterSuite.enabled` is on.
- **Recorded once on the development machine.** Codex 0.167.1 returned 8 rows supported, 3 partial and 5 absent (4 of those unmeasured). It found that this Codex has PreCompact, PostCompact and post-compaction SessionStart hooks and a usable compaction-window setting, which the spec had expected to be missing. See `docs/specs/reports/context-budget-codex-adapter-suite.md`.
- **Dev-gated.** Everything here sits behind `contextBudget.enabled` (live on development agents, dark on the fleet). With it off, the hook prints exactly what it printed before.

This adds H3, the long-term view, and makes it the single writer of the topic summary table (context-budget-layered-summaries §6 row H3, §6.5, §14; Phase 1 S9). It applies while `contextBudget.enabled` is on (dev-gated: live on development agents, off on the fleet).

- **H3 is rebuilt from a bounded selection, never the whole history.** The floor, never dropped, is every chunk not yet in a range (pending gaps included, labelled as gaps) plus the chunks of the current phase. Ranges are read newest first under a 24K-token input default: through their member chunks while budget allows, then through their range (C2) summary. The oldest ranges are left out only when even their range summaries do not fit. The record and the summary text say in-band which ranges were read through C2 or left out.
- **When it runs.** H3 rebuilds when a chunk or range closes, at most once per 10 minutes per topic; a request inside that window schedules one rebuild at its end. Each build is one model call on the shared background queue (daily cap), under the layers' `LayerUpdate` budget. If the budget is over or no model is available, the build is deferred and the previous view stands.
- **Guards on the model call.** The output must be strict JSON (a one-line purpose and a summary), and any quotation must be copied exactly from the input. A floor over the input budget asks once for a range close. Past a hard ceiling nothing is sent. An H3 too large to replicate is rebuilt once under a tighter range selection.
- **One writer for the topic summary.** Every write to the summary table now goes through one funnel (`TopicSummaryTable`), the only caller of `saveTopicSummary`. With the layers on, H3 writes the row: `lastMessageId` is the last message its selection covers, and `purpose` is H3's own derived line. The old rolling summary is kept as `h3/legacy-retired` before H3 first overwrites it.
  - `POST /topic/summary` returns `409 summary-written-by-h3` with a plain reason.
  - `POST /topic/summarize` returns the H3 text with `writer: h3` and its freshness, and never asks the caller to write.
  - The rolling `TopicSummarizer` is off.
- **With the layers off (the fleet default), nothing changes.** The summarizer and both routes behave exactly as before.
- `GET /context-budget/layers` gains `h3` counts. `GET /context-budget/metrics` gains a per-topic `h3` row: built or not, freshness, and how much was read through range summaries.
- CLAUDE.md gains a Registry-First row for the long-term view and the single-writer rule. New agents get it from the template and existing agents get it through `migrateClaudeMd`.

The compaction canary can now fix what it finds (context-budget-layered-summaries §9.1; Phase 1 S11). It applies only where the ContextBudgetSentinel is on (`contextBudget.sentinel.enabled`, default off), the context-budget layers are on (`contextBudget.enabled`, dev-gated), and compaction recovery is on.

- **One context epoch.** Every writer and reader of the seeded marker now derives the epoch the same way: the compact-boundary entry's id after a compaction, the fold id after a fold, the spawn id otherwise. The compaction hook still leaves the epoch for the server to bind (it runs before the boundary is written); a test drives the real hooks and the server writer and shows they agree.
- **The server writes the seeded marker** after it delivers a compaction's context itself (the idle-gated fallback, or a heal). A server marker only ever covers its own compaction.
- **The heal ladder, by cause.** For each compaction the canary finds without its recovery:
  - the hooks are not installed ⇒ the hook and settings migration re-runs;
  - the hooks are installed but the briefing never reached the session (missing or cut to a preview) ⇒ the conversation's standing packet is re-staged and delivered once, at an idle prompt, through the same idle-gated path as the fallback, with a preamble that tells the session not to reply about it;
  - anything else (session gone, superseded, no packet to re-seed, a press with no compaction) ⇒ recorded only.
  Brakes: one episode per machine, session and epoch; at most 3 attempts (10 min, then 1 h apart) within 30 minutes; at most 3 runs per session per day; 3 fixes of the same cause in a day stop that cause and raise one Attention item. A completed fix restarts the canary's verification epoch.
- **The synthetic press.** The sentinel presses `/compact` on a throwaway session (named `cb-press-…`, bound to no channel, not a job, idle) so the canary has its positive control and can reach `healthy`. It never presses a conversation session. At most 3 a day, an hour apart, and only while the canary lacks a positive control.
- `GET /context-budget/sentinel` now shows the ladder's recent decisions, open breakers and the press's last outcome.

This adds the standing packet and its verifier (context-budget-layered-summaries §9.5, §9.7; Phase 1 S10). It applies while `contextBudget.enabled` is on (dev-gated: live on development agents, off on the fleet).

- **The standing packet.** Each topic with a live session keeps a packet: what its conversation needs to resume after an unplanned compaction. The packet lists, in priority order:
  - the Anchor's framing messages;
  - the live decisions and evolutions ledger;
  - the operator's last 20 messages, verbatim from TopicMemory, each with its derived referent stub beside the quote;
  - then H1 (current work) and H2 (phase, or `absent`) with their `as of` stamps and author;
  - H3 (the long-term view);
  - chunk and range pointers for lookup, and every "unsummarized gap".
  A missing layer is a line that says so.
- **When it is rebuilt.** It is re-rendered after every committed layer write, debounced 5 seconds per topic, and only for topics with a live session on this machine. The spawn path also builds it fresh.
- **It fits what Claude Code delivers.** Claude Code passes hook output whole only up to 10,000 characters, so the delivered packet is bounded to 6,000 and rides whole inside the 9,000-character recovery block.
  - Over that bound, it is reduced in the spec's order: H3 first, then the chunk list, then H2 and H1, and only then the operator's rows, oldest first.
  - The Anchor and the newest turns go last. Each row is kept whole or left out, never cut, and leaves a line in its place.
  - The full packet is then saved privately under `state/context-layers/_recovery/` (0600, never served or backed up, pruned after 7 days), and the packet tells the session to Read it now. Every omission is listed in the packet.
- **The verifier.** A packet is used only after verification. Every quoted operator row must be byte-identical to its stored reference and to the TopicMemory row now. Every required section must be present outside any quote, every present summary layer must carry its `as of` stamp, and the packet must be under budget. A failed packet is never delivered: nothing is staged, the session gets today's recovery block, and the failure is counted (`GET /context-budget/layers` → `standingPacket`) and reported through DegradationReporter and feature evidence.
- **Where it is read.**
  - The compaction hook prints the staged packet in place of today's conversation context, only on the recovery-on Claude Code path and only when its hash, length, topic and age check out. The RF fitter keeps it whole.
  - The spawn path (`formatContextForSession`) and the server's compaction-resume path carry it in place of the rolling summary.
  - The PreCompact steering hook now gets its keep-instructions: the Anchor, the live ledger and the in-flight work. A fold's own keep-instructions are never overwritten.
- **New route.** `GET /topic/:id/standing-packet` (bearer) returns sizes, sections and the verifier's verdict, never the words. It returns 503 with the layers off.
- **With the layers off, nothing changes.** Any packet a previous run staged is removed at boot, so recovery is exactly today's.
- CLAUDE.md gains a Registry-First row for the packet: new agents through the template, existing agents through `migrateClaudeMd`. The compaction-recovery and fitter hook scripts update through `migrateHooks`, which always overwrites them, and through `init`.

The context budget gains U, the protected user corpus, with its referent stubs (context-budget-layered-summaries §6 row U, §6.2, §6.4, §8; Phase 1 S5). While `contextBudget.enabled` is on:

- **U is built from TopicMemory sender rows, never from transcript roles.** Hook output that arrives as "user" in a session transcript is not the user and never enters U. Every `from_user=1` row and every row that came through another agent is listed as a protected row reference (message id, sha256, length) with its time and a label. The operator's words are never copied into the layer store.
- **Labels and authority.** The operator's own typed rows (not forwarded, no relay or A2A origin, the sender resolved as the operator through memory privacy) are the protected class, `authority: operator`. Forwarded rows, relayed or A2A rows and other people's rows are kept and labelled `forwarded`, `relay` or `third-party`, with `authority: none`.
- **Large pastes.** A row over 4,000 characters is flagged as a pasted artifact and kept whole. The excerpt-and-pointer handling once a paste is superseded arrives with the Phase 2 folds.
- **Referent stubs ride the extractor's existing call.** For an operator message, the same topic-intent extraction call also returns a one-line bracketed stub such as "[answering: should the gate block or warn?]", with a `kind` (`answer | directive | question | hypothetical | rejection | other`) and the agent message it answers. No second model call is made. The stub is checked deterministically after the call: one line, at most 160 characters, bracketed, a known kind, a reference to a message that precedes the user's in TopicMemory, and none of the user's own sentences inside it. A rejected stub is counted and dropped; the message itself is unaffected. A valid stub is stored beside the quote as a derived record and replicates; U itself is rebuilt from rows on each machine and does not replicate.
- **Short answers count.** An operator's bare reply such as "yes" right after an agent question now reaches the same extractor call, so it gets its stub; the shed, rate and budget brakes still apply, and every operator message that got no stub is counted by reason.
- **Bounded listing.** U is listed at most 200 rows per turn from a persisted per-topic watermark (the current message first), re-listed when the operator binding changes, and a stub whose quote is relabelled is withdrawn.
- **Measured.** U's size per topic (tokens and messages, per label) and stub coverage are reported.

New route: `GET /topic/:id/user-corpus` (bearer only) returns sizes, labels, pasted-artifact flags and stub coverage, never the message text; 503 while the layers are off. `GET /context-budget/layers` now also shows U's builder counters. `TopicMemory` gains three read methods: `getUserCorpusRows`, `messagePrecedes` and `getAgentMessagesBefore`.

With the switch off, the topic-intent extractor's prompt, parse and result are byte-identical to before.

## What to Tell Your User

Nothing changes for you yet. On development agents I now note what each conversation was started for, using your own first real message, and keep a record of your decisions and of any change of direction. I only treat something as decided when your own message answered or directed it. If you change the purpose, I mention it once and treat it as unconfirmed until you say so, never by silence. I keep pointers to your messages, never copies.

Nothing changes for you unless the rebuild is switched on. When it is, I go back over older conversations in the background, a few a day, and note what each was for and which of your decisions I can find in your own messages. I treat those as unconfirmed. The next time you write in one of them, I add one line to my reply asking you to correct anything wrong; I never send it as a separate message.

On development agents, a conversation running on Codex now picks up where it left off after Codex compresses its memory. The next message carries a short summary of what that conversation is about, its decisions, and your recent words, so you don't have to repeat yourself. Nothing changes on other agents.

Nothing changes for you yet. On development agents, each conversation's long-term summary is now written in one place only. It is rebuilt from the short summaries of each stretch of work, so it no longer drifts or gets overwritten by a second writer. If a conversation has not been compacted yet, its older summary stays as it was until the first one is written.

Nothing changes for you unless the context-budget watcher is switched on (it is off by default). Where it is on, if a conversation loses its place after its memory is compacted and the usual briefing did not reach it, the agent now notices and quietly hands that conversation its context back once, at a moment it is not busy. If the same problem keeps happening, it stops retrying and tells you once.

Nothing changes for you yet. On development agents, when a long conversation is compacted, the agent now gets your own words back exactly as you wrote them: what the conversation is for, the decisions you made and your recent messages, followed by its summaries of where the work stands. If that set is too large to hand over at once, it gets the most important part and is told to read the rest. If anything in it does not match what you actually wrote, it is not used at all and the agent recovers the way it did before.

Nothing changes for you yet. On development agents I now keep a protected list of your own messages in each conversation, separate from forwarded or relayed messages and other people's, and note beside each one what it was answering, so "yes, the second one" still makes sense after my earlier messages are summarised away. I keep pointers to your messages, never copies of the words.

## Summary of New Capabilities

- The Anchor per topic, from the operator's framing message rows.
- The decisions/evolutions ledger with the decision transition, supersession and live-set selection.
- Evolution confirmations in the existing confirmation queue: priority with requeue, deferral and a surfacing clock.
- `GET /topic/:id/anchor`, and Anchor and ledger counts in the context-budget metrics.

- The backfill lane: owner only, newest first, 20 conversations a day, resumable, background.
- `backfilled-unconfirmed` ledger entries from history, operator-bound only.
- A `backfill` confirmation kind, asked only inside a reply after user activity.
- Pending backfill confirmations on the anchor route and in the context-budget metrics.

- Next-prompt seed delivery of the standing packet for Codex sessions, once per compaction.
- Canary verification of Codex compaction recovery.
- A re-runnable Codex adapter verification suite, with a recorded result for Codex 0.167.1.

- H3, the long-term view per topic, built from a bounded, disclosed selection of chunk and range summaries.
- A single-writer funnel for the topic summary table: H3 with the layers on, the legacy writers with them off.
- `POST /topic/summarize` returns H3 (`writer: h3`) and `POST /topic/summary` returns 409 while the layers are on.

- A heal ladder by cause for missed post-compaction recovery, bounded by the SelfHealGate, with a same-cause breaker.
- A gated synthetic compaction press on throwaway sessions, the canary's positive control.
- A shared context-epoch derivation and a server-side seeded-marker writer.

- A per-topic standing packet, re-rendered and verified on every layer commit, delivered whole after a compaction and at spawn.
- A packet verifier (byte identity against TopicMemory, required sections, freshness stamps, size), whose only action is choosing the older recovery block.
- Pre-rendered PreCompact keep-instructions per live session.
- `GET /topic/:id/standing-packet`: sizes, sections and verdict per topic.

- U, the protected user corpus, built from sender rows with labels and authority.
- Referent stubs from the existing extractor call, validated deterministically.
- `GET /topic/:id/user-corpus` for U's size, labels and stub coverage.
