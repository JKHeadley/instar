## What Changed

Instar now depends on `@sagemindai/threadline-core` at exactly 0.1.0, the package `threadline-mcp` already uses, and takes its invite pairing from it instead of keeping its own copy (spec `threadline-standalone-pairing`, D1 and rollout step 3). `src/threadline/PairingInvite.ts`, `PairingInviteFlow.ts` and `PairingInviteStore.ts` are now re-exports of core, under the same paths and names, so nothing else in Instar changed its imports. The identity-key helpers that are the same code in both (key generation, signing, X25519 exchange, the Ed25519 to X25519 key maps, the fingerprint, the pairing id) also come from core. `AgentTrustManager` declares that it implements core's `InviteTrust`. The SAS word list, the Telegram and dashboard pairing screens, `AgentTrustManager` itself, `verify` and the `MessageEncryptor` class stay in Instar, because core's versions of those behave differently in small ways (listed in the side-effects review).

An Instar agent and a `threadline-mcp` agent now run the same invite code, so the two cannot drift. Wire formats are unchanged.

Behaviour that changes, all from fixes already made in core:

- The invite message uses the same host-neutral words as `threadline-mcp`: it tells the person to ask their agent to open a Threadline invite and paste it into the box shown, not into the chat, and, for an Instar agent, to forward it to its Telegram or paste it in its dashboard. It also says the invite works once.
- Names the other agent chose are cleaned more thoroughly before they are shown: bidirectional overrides, zero-width characters and C1 control characters are removed, and the text is NFKC-normalised.
- On the receiving side, a Finish is accepted only for an invite this agent's person approved, from that inviter, for that invite, at most 24 hours after it expired, and only once (a retried Finish is acknowledged again without changing anything). An invite approved before this upgrade and finished after it is refused; the person sends a new invite.
- If the accept cannot be sent (the relay is not connected), Approve now says so and keeps the invite waiting to be approved again, instead of failing with an error.
- `pairing-invites.json` also records the invites this agent approved. If the file is not valid JSON it is moved aside as `pairing-invites.json.unreadable-<time>` and reported, instead of being silently replaced. If it cannot be read at all, invite pairing is turned off with a logged error, and the rest of Threadline keeps running.

`--push-only` finishes a release whose version is already on npm. When npm does not show the version, it says npm may still be reviewing it. But `--push-only` cannot tell a version npm is still reviewing from one that was never published at all. It now adds a line saying that if the version was never published (for example the publish step itself failed), `--push-only` cannot finish it, and you should run the release again normally instead. The install-check message after a publish doesn't get this line, because by then npm has already accepted the upload.

The code and the spec also now record a deliberate difference. When npm can't answer at all, the post-publish check treats the version as "probably still in review", while `--push-only` reports "unknown". Both stop safely and neither publishes again.

On the first real local release, npm accepted the upload but kept the new version in an automated review it calls "Validating" for over 40 minutes. During that time the version can't be downloaded and only the package owner can see why. The release tool's install test timed out and stopped, correctly, with the command to finish the release later.

The tool now says what is probably happening. When the install test fails and npm does not show the version yet, the message explains that npm may still be reviewing it, gives the owner's link to check (the Versions tab on npmjs.com), and says not to publish again. `--push-only`, the command that finishes a release without publishing, behaves the same way: it keeps refusing while npm does not show the version and never claims nothing was published. Once npm shows it, it finishes. If the version is visible and the install test still fails, that is reported as a real failure of the published package.

The spec also records a coming date. npm says tokens that skip two-factor checks stop working for publishing in January 2027. Local releases will need another sign-in route by then, and Justin is choosing which.

When `--push-only` refuses because npm does not show the version yet, its notice gives two instructions: one for a version that was never published, and one for a version that was published and is still in npm's review. The second now begins "Otherwise (published, still in review):", so the two no longer read as contradictory.

Three follow-ups to Instar taking invite pairing from `@sagemindai/threadline-core` (spec `threadline-standalone-pairing`, step 3).

- **A paused pairing stays paused.** When an invite is used by two agents, the agent that accepted first is paused (spec `a2a-pairing-invite-link` §4.4.2). The shared invite code refuses a late Finish for a paused pairing, but it could not see Instar's pause because Instar did not record it. Instar now records the pause on the trust profile and shows it to the invite code. A Finish that arrives after the pause is refused, and the pairing stays unverified until a new invite completes. The pause survives a restart. A new invite approved by the person, a completed pairing, or a 12-word confirm ends it.
- **Weak identity keys are refused when pinning.** A small-order or non-canonical identity key is now refused on every path that pins one: the invite accept and finish, the 12-word pairing (start, pending, and the copy inherited from another of the agent's machines). This matches what threadline-core already does (spec D8, SEC-16). A real agent's key is never weak, so real pairings are unaffected. Starting a 12-word pairing with such a key returns a clear refusal from the pairing route.
- **"Invite pairing is off" now shows in health.** If `threadline/pairing-invites.json` cannot be read, invite pairing is turned off and the rest of Threadline keeps running, as before. That used to be only a log line. It is now reported as a degradation, so it appears in `/health` and in the degradation digest. The file is still left untouched.

- Ordinary chat to an agent paired by invite is now always encrypted, to the identity key pinned when the two people paired. Before this, an Instar agent encrypted only when the relay had handed it the peer's keys during the current session; after a restart, or for a peer the relay had not described yet, it sent plaintext, even to a paired peer. `ThreadlineClient.sendAuto` now asks a new resolver (`setEncryptToResolver`) first, and `hasEncryptedSendPath` reports the pinned path too. Spec: `docs/specs/threadline-standalone-pairing.md` (approved r5.2; D9, D11, rollout steps 5 and 5b).
- The resolver returns a key only for peers that are `mutual-verified` AND were paired by invite. An acceptor still waiting for the inviter's Finish keeps the old rule, because the inviter cannot read a message encrypted by an agent it holds no key for yet. A peer paired by the older SAS method keeps the old rule too, because it may run a version from before 1.3.1345, which cannot decrypt to a pinned key without a cached one. Both sides of an invite pairing run 1.3.1352 or later, which can.
- **Explicit pairing method.** Trust profiles now record `pairingMethod` (`invite`, `sas` or `inherited`). The resolver keys on `pairingMethod === 'invite'` rather than on a missing SAS fingerprint (an inherited pairing has none either). Profiles from before the field are backfilled on load: a `mutual-verified` profile gets `sas` when it holds a SAS fingerprint, else `invite`; an existing value is never overwritten.
- **Live switch `threadline.encryptToPinned`** (`{ enabled?, dryRun? }`, same gate as `threadline.relayUnknownSenderTrust`: `enabled` omitted is live on a development agent and dark on the fleet; `dryRun` defaults true). Off: today's behaviour. Watch (`dryRun` not false): sends unchanged; each send that would have gone encrypted to the pinned key is counted (`wouldEncryptToPinned`). Enforce (`dryRun: false`): encrypted to the pinned key. Mode and counters: authed `/health` → `threadline.encryptToPinned`.
- **Never plaintext in enforce.** When the pinned send cannot be built or handed to the relay, `sendAuto` throws ("no plaintext fallback") instead of trying the relay-key or plaintext paths.
- **Every chat send path, and fail closed.** The pinned rule now covers every send method that can carry ordinary chat, including `sendPlaintext` (a collaboration re-drive nudge to an invite-paired peer now goes encrypted). In enforce, a peer whose pin cannot be looked up, or whose pinned key is malformed, is refused rather than sent plaintext (502 on relay-send; counters `lookupErrors`, `resolverErrors`, `malformedPinnedKey`). A refused re-drive nudge is not counted as a re-drive, and a refused a2a redelivery is not counted as redelivered.
- **Receive-side label (enforce only, never a refusal).** Plaintext ordinary chat under the fingerprint of an invite-paired, mutual-verified peer is delivered with a fixed server notice ("unverified sender … the relay could have written it") and at no more than `verified`. Watch counts it (`wouldLabelUnverified`).
- **Pairings follow the agent across its machines (step 5b).** With pairing replication on (`multiMachine.stateSync.threadlinePairing.enabled`, default off and unchanged), the replicated pairing record carries `pairingMethod` as an optional sixth field, and every merge (and once at startup) inherits the replicated pin on the agent's other machines, so whichever machine holds the relay connection encrypts to the same pinned key. An invite pairing is never downgraded by a record from an older machine, and a pairing made on a machine is never overridden by a replicated one. On upgrade, local invite pairings re-send their record so the method reaches the other machines.
- **Unpairing reaches every machine.** The revoke record names the pinned key; every other machine forgets the pairing it inherited for that key (never a pairing made locally, never a different key), so it stops encrypting to that peer and stops sending it credentials. A newer pairing record after the revoke wins.
- **Startup warning.** A machine of a multi-machine agent logs a warning when `encryptToPinned` is enforce and pairing replication is off.
- **relay-send answers 502** when an enforced pinned send fails; nothing is recorded as sent, and a standby forwarding through the relay holder gets that 502 back.
- Decrypting is unchanged. Every version that can pair by invite already decrypts messages encrypted to its pinned key.

When an invite pairing is paused (its invite was used twice) and another of the same agent's machines later verifies that agent, the pause now ends on this machine too, but only if that verification was made after the pause. A verification from before the pause, or one with no usable time, keeps the pause. Before, the pairing became verified but kept a stale pause marker, which would have refused a later invite Finish from that agent. Also added: a code comment on how the pause must be read, and a note in the side-effects review that keys pinned before the weak-key check are not re-checked.

- **No downgrade after encryption.** When an agent paired by invite sends this agent an encrypted message, and the signature matches the key pinned when the two people paired, Instar now remembers that (`encryptedSeenAt` on the trust profile). After that, a plaintext message in that agent's name can only be the relay's word, so it is refused. Pairing messages and credentials do not count, because they are always encrypted. Spec: `docs/specs/threadline-standalone-pairing.md` (D6, D11, rollout step 6).
- **Live switch `threadline.refuseDowngrade`** (`{ enabled?, dryRun? }`, the same gate as `threadline.encryptToPinned`: live on a development agent, dark on the fleet, `dryRun` defaults true). Off: nothing is recorded or refused. Watch: the fact is recorded, and plaintext that would have been refused is counted (`wouldRefuseDowngrade`) and delivered. Enforce: it is refused (`refusedDowngrade`). Mode and counters: authed `/health` → `threadline.refuseDowngrade`. Listed on `/guards` as `a2aRefuseDowngrade`.
- **One record across the agent's machines.** With pairing replication on (`multiMachine.stateSync.threadlinePairing.enabled`), each machine shares what it recorded, every machine keeps the earliest time any of them saw, and only the person unpairing removes it. So a relay cannot get plaintext through by aiming at whichever machine takes over.
- Agents paired the older way, by comparing words, keep the rule they had.
- `@sagemindai/threadline-core` gains `earliestMark`, `unifyEncryptedSeen` and `PinnedKeyStore.mergeEncryptedSeen`, the shared rule for the record. Instar carries an identical copy (checked by a parity test) until a core release exporting it is published and Instar's pin moves to it.

## What to Tell Your User

Pairing works as before. The invite message now has the same wording whether it comes from an Instar agent or from an app running threadline-mcp, and it says where to paste it in either. If you approved an invite just before this update and the other side had not finished yet, ask them to send a new one.

Nothing for agent users. This only changes a message in the maintainers' release tool.

Nothing changes in normal use. If an invite you sent was used twice and the first pairing was paused, a late Finish no longer completes it; send a new invite. If invite pairing ever turns off because its file cannot be read, the agent's health report now says so.

If you paired me with another agent using an invite, everything I send that agent is now encrypted, every time. Before, my ordinary messages to it went out unencrypted after I restarted, until the relay reminded me of its keys. Secrets were already protected and still are. Agents you paired the older way, by comparing words, work exactly as before.

Nothing changes in normal use. If an invite pairing was paused and the agent was then verified from another of your agent's machines, it now counts as verified everywhere, with no leftover pause, as long as that verification happened after the pause.

If you paired me with another agent using an invite, and that agent has sent me an encrypted message, I can now refuse unencrypted messages that claim to come from it, because those could have been written by the relay in between. This is off by default. If that agent's owner ever goes back to an older version that sends unencrypted messages, unpair and pair again.

## Summary of New Capabilities

- None for the user. Instar and threadline-mcp now share one implementation of invite pairing, published as `@sagemindai/threadline-core`. A fix to it is published once, then Instar bumps its exact pin.

- None. The release tool's `--push-only` message is clearer.

- None new for the user. The health report now covers invite pairing being off.

- `ThreadlineClient.setEncryptToResolver(fp => Buffer | null)`: the pinned key to always encrypt ordinary chat to.
- Invite-paired, mutual-verified peers: ordinary chat always encrypted to the pinned key.

- None new. A paused invite pairing no longer stays paused after the same agent is verified from another of your agent's machines.

- `threadline.refuseDowngrade` (off | watch | enforce), read live.
- `AgentTrustManager.markEncryptedSeen` / `mergeEncryptedSeen`; the trust profile's `encryptedSeenAt`.
- Replicated mark and unpair records on the `threadline-pairing-record` stream.
