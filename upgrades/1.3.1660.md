## What Changed

Telegram issues-group topics now default to Codex with `gpt-6.1-sol`. The optional `topicProfiles.groupDefaults.issues` config can override that group default. A topic's verified operator pin still wins. New Codex `gpt-6.1-sol` model IDs are recognized; a machine with a Codex CLI older than 0.166.0 uses `gpt-6-sol` with a plain note instead of starting a dead session. A framework-aware resume read keeps an old Claude session ID out of a new Codex launch.

The locked-Mac proof scripts (test tooling, not shipped behaviour) now follow the desktop page when it opens the screen by itself, give each proof agent a dashboard PIN from the operator's vault without printing it, and name the required finalize step at every stage.

The Instar iPhone app can now list permission slips and feature switches natively, and the owner's phone can approve or decline an agent's waiting authorization request and turn a feature switch on or off, each with a fresh Face ID or passcode check. Two read routes, `GET /mobile/permissions/slips` (waiting requests and active slips, this machine plus other online machines read-only) and `GET /mobile/permissions/features` (switches, this machine plus others read-only), answer an owner phone or the agent's token. Four write routes (`POST /mobile/permissions/challenge`, `/mobile/permissions/requests/:id/approve`, `/mobile/permissions/requests/:id/decline`, `/mobile/permissions/features/:id`) accept only an active owner phone with a configured dashboard PIN, over the machine's own TLS front or loopback, carrying the phone's presence-key signature over a single-use 60-second challenge that names the exact action (the approved proposal's hash, the shown consent disclosure's hash, the decline reason's hash). They run the console's own approve, decline and operator-switch code, extracted into shared functions; the console routes behave as before. The agent's token is refused on every write. Every write and refusal is recorded in `state/mobile-permission-actions.jsonl` beside the console's own records, which now also name the phone. The writes are dark on the fleet and live on a development agent (`mobilePairing.permissionActions.enabled`).

Instar now prepares each automatic update in a separate directory. It checks the new CLI startup and opens a real in-memory SQLite database with the Node runtime used for agent restarts before replacing the active install. A failed rebuild, missing package, startup failure, or failed SQLite query leaves the current install in place and keeps the update pending for retry.

Rollback uses the same checks. If an interruption occurs during the final switch, the boot wrapper and supervisor restore the previous installation before starting; existing agents receive the new wrapper through the update migration.

After a confirmed yes, the agent can now start the work itself: a session in the service's own conversation, briefed to do the whole setup, with a real check that decides when it's done. A regular check stops the work after a no from any machine and restarts a session that dies, up to a limit. This only runs on a throwaway or development agent that has chosen to prove a recipe, so nothing changes on other agents.

`instar set-claude-key` no longer needs the Claude CLI to be installed. It used to load the whole config only to find the `.instar` folder, and loading the config refuses when the `claude` binary is missing. A headless install that runs on a key alone often has no CLI, and that is the case this command exists for. The key is still written to the same place, `.instar/config.json` in the project folder.

A session that hits its subscription account's usage limit now moves to another account with room and carries on, instead of sitting stuck until the limit resets. The watchdog has a separate usage-limit signal, the move covers sessions that were started on the default login without an account label, new sessions are labelled with a pool account when they start, and a new session never starts on an account the agent already knows is full. The standby message now recognises the current Claude Code limit screen, which it used to read as "recovered". All of this is one switch, `subscriptionPool.wallRescue.enabled`, on by default and active only when the agent has 2 or more working accounts of the same kind. Existing agents get the setting on update; an explicit `false` is kept. Status: `GET /subscription-pool/wall-rescue`.

## What to Tell Your User

New Echo Bugs topics start and restart on Codex by default. A machine that still has an older Codex version will use GPT-6 Sol and say so.

Nothing changes for you. This only affects the test scripts used to prove the locked-screen feature on a spare Mac.

When the app update arrives and your agent turns this on, your agent's page in the app gets a Permissions section. You can see what agents are asking permission for and approve or decline it, and see the agent's feature switches and turn them on or off. Every change asks you to confirm, then asks for Face ID. Only your own phone can do this, and only for things the console with your PIN could do.

An update that cannot run safely will leave your agent online on its current version. Instar records the failure and retries the update on the next cycle.

Nothing changes for you yet. This is the part where your agent does the setup itself, and it's still being proven.

If you set me up on a machine without the Claude app and saving my key failed, it works now. Ask me to save the key again and paste the same key you made before.

If you have more than one subscription account connected, a conversation that runs out of usage on one account now switches to another account with room and keeps going on its own. You'll only hear about a usage limit when none of your accounts has room left, and then the message says plainly when it resets. If you have one account, nothing changes.

## Summary of New Capabilities

| Capability | How to Use |
|---|---|
| Issues group default | No configuration needed. An optional `topicProfiles.groupDefaults.issues` entry overrides the default. |

| Capability | How to Use |
|---|---|
| Proof driver follows the viewer's auto-open | automatic in the locked-Mac proof driver |
| Proof agents get a dashboard PIN from the vault | stage-proof-agents.sh --agent-home DIR |

- The owner's phone can approve or decline an agent's waiting authorization request, Face ID-confirmed.
- The owner's phone can turn a feature switch on or off, Face ID-confirmed, seeing the same "your data" disclosure as the console before turning one on.
- Waiting requests, active slips and switches from other machines are shown read-only.

- Pre-restart validation of the new installation and its native database dependency.
- Preservation of the active installation when preparation fails.

`POST /recommended-services/:id/verify` and `POST /recommended-services/:id/key`, both answering `no-recipe` unless this agent is proving one. `GET /recommended-services` adds `verified`, `alreadyHeld` and `stalled`.

No new capabilities. This removes a requirement the command never needed.

- Usage-limit rescue: a conversation at its account's usage limit moves to an account with room and continues, labelled or not.
- New sessions start on a pool account with room, never on one known to be full.
- `GET /subscription-pool/wall-rescue` shows whether the rescue is active, how many accounts qualify, and what happened recently.
