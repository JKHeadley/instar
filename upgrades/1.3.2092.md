## What Changed

The mobile and dashboard conversation list showed each Telegram topic's last message by asking for that topic's history. For a topic outside the in-memory cache that meant reading the whole Telegram message log synchronously, once per topic, before the list could answer. A Laptop with 574 named topics (508 of them without a live session) and a 30 MB log spent tens of seconds per cold list with its request queue full. Previews now come from an index of each topic's newest entry, built once in the background in 1 MB steps that let other requests run in between, and kept up to date as messages arrive. Until the index finishes, typically within a second, a topic outside the cache shows no last-activity preview.

## What to Tell Your User

The conversation list opens quickly on a machine with a long Telegram history; right after a restart a few older topics may briefly show no last message.

## Summary of New Capabilities

No new capability. One fix: list previews read only memory, never the log.

## Evidence

Reproduction: Scaling's live profile of the Laptop server (PID 84162, 2026-11-27 06:08 PT) shows GET /mobile/conversations -> localConversationListPage -> AgentServer telegramTopics -> TelegramAdapter.getTopicHistory -> scanLogForTopic -> readFileSync, with getTopicHistory 42 percent and synchronous file reads 32 percent of 21.4 sampled seconds and the listener backlog at 128 of 128. After: tests/unit/telegram-latest-topic-entries.test.ts shows a list request reads nothing from the log, the background build over a generated 30 MB log keeps the largest event-loop gap at 5.6 ms (build 31 ms on the M5), entries logged during the build win over the file, and a missing log builds an empty index.
