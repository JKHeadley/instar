# Backup routes for agent-to-agent messages (ELI16)

When I message an agent that runs on my own computer, I first try to hand the message straight to its server. If that doesn't work cleanly, I send the same message through the shared relay instead. Sometimes the direct hand-over did get through, even though it looked like it failed, for example when the answer was just too slow. Then the other agent gets the message twice and has no way to tell it's a repeat, so it may answer twice.

The other agents are getting a list of the message ids they've already received. My relay copy already uses the same id as the direct attempt. This change adds a small "this is a resend" mark to it whenever the direct attempt might have got through, and makes sure it lands in the same conversation thread as the direct attempt, so "check the conversation" points at the right one. An agent with that list then spots the repeat and tells its session to check the conversation before answering. Only a short list of answers proves the direct attempt never got in (the door was shut, the request was malformed or unauthorised, or the other side said in a fixed, machine-readable way that it couldn't take it). Those get no mark. Anything else gets one. When I'm not sure, I add the mark, because an extra mark only changes the wording of a note.

One thing stays as it is today: if the relay then refuses that copy, my record still says "not delivered", even though the direct copy may have arrived. Changing that would mean changing the rules for how relay answers are recorded, which is a separate decision.

The second change: if I address an agent on my computer by its relay ID instead of its name, which my messaging tool allows, I now notice it's right here and hand the message over directly. That means that if my own connection to the relay is down, I can still reach an agent next to me. Before I hand over, I ask that agent's server two things: who it is, and whether it's the copy of that agent that's actually connected to the relay right now. I only go ahead if it gives back exactly the ID I asked for and says it's connected. A backup copy sitting idle on my computer, or one that got knocked off the relay, gets nothing directly, because it isn't the one handling that agent's conversations. That guards against handing a message to the wrong program on an old port. It isn't proof of identity, just a guard against mix-ups. Secrets sent this way still take the relay's encrypted path. (Secrets I address by name go directly and unencrypted, as they do today; this change doesn't touch that.)

Honest limits: none of this reaches agents on other computers. My background retry sweep is left exactly as it is; making it reuse ids safely needs the relay to say which attempt it is answering, which is tracked as separate work. The problem that started this (Luna's copy on my computer was a standby that wasn't connected to the relay) is fixed by the relay self-heal, not by this. Both changes start switched on only for development agents, and each counts as working only once it has actually been seen working at least once.

**Status.** Approved for building under the operator's standing approval for the agent-to-agent communications track (2026-10-06). It ships switched on for development agents only.
