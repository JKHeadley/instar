## What Changed

A message for a conversation that runs on another machine no longer expires unanswered when that machine cannot take it. Two causes, both fixed. (1) When the owning machine is alive but cannot take forwarded messages (no durable receive), the sending machine kept the message in its queue and retried; its final forced attempt re-placed the conversation, which chose the same machine again, so the message ran out of tries. The final attempt now takes the conversation on the sending machine and answers it there (`SessionRouter.forceReplace` → guarded `takeOverActiveRecord`, a force-claim allowed only while that peer still holds the record). A live message still waits first; nothing is taken from a working machine immediately. (2) With the pool stepped down to dark, a message routed to a peer that had gone tried a plain claim, which never moves an active record, so it queued until it expired; a gone peer's record is now taken over, and the queue's forced attempt at dark takes such a message here instead of giving up. Separately, the never-silent notice for a message held for another machine now says "it's waiting for the other machine that runs this conversation, which can't take messages yet" instead of "the session stopped running" (no session had started).

## What to Tell Your User

If a conversation runs on another of your machines and that machine cannot take new messages, your message is now answered on the machine that received it instead of quietly expiring. While it waits, the notice says it is waiting for the other machine, not that the session stopped.

## Summary of New Capabilities

- A message stuck waiting for another machine is answered on this machine instead of expiring.
- The waiting notice says the message is waiting for the other machine.

## Evidence

Live two-machine test 2026-11-16 (Studio + M5, 1.3.1824): tg-22 queued as owner-lacks-ws11-receive and a second message as routing-only-claim-lost both expired; the user was told the session stopped running. Root cause confirmed in code: the `place` transition refuses any active record (`SessionOwnership.ts`), and the forced re-place chose the same machine. New tests: unit (router takeover branches, notice wording), integration (real router over the real ownership registry, including the root cause), and an E2E lifecycle (real queue on SQLite draining through the real router: queued, retried, then answered here with nothing lost).
