## What Changed

- `SingleInstanceLock` decided whether the recorded lock holder was still running from the pid alone. On a host that recycles pids every few minutes, a dead holder's pid is re-issued to unrelated live processes, the lock reads LIVE indefinitely, and the agent's server refuses to boot until a spawn happens to land on a free pid. The lock record now also carries the holder's absolute process start time (`ps -o lstart=`, via the primitive `hostTestRunnerSemaphore` already uses for the same corroboration); a candidate pid whose start postdates the record by more than the shared 120s skew is treated as a different process and the stale lock is reclaimed. One-sided on purpose; every uncertain case (no recorded start, unreadable candidate start) keeps the previous pid-only verdict.
- `ServerSupervisor` now appends the spawned server's stderr to `logs/server-stderr.log` (`tee -a`) instead of truncating it on every spawn. Past 4 MB the newest 512 KB is kept. The crash-output reader takes a bounded tail rather than reading the whole file.

`POST /internal/telegram-forward` (messages) and `POST /internal/telegram-callback` (inline-button taps) carry Telegram input from the lifeline into the server and take the sender's Telegram user id from the request body. They were protected only by the ordinary Bearer token, which every spawned session holds as `INSTAR_AUTH_TOKEN`. Any session could therefore post a message or an Approve tap that named the operator as the sender, which undermined the operator auto-bind, sender re-validation and every inline-button approval.

- **A lifeline-only secret.** 32 random bytes (hex) in `.instar/state/lifeline-ingress-secret`, mode 0600, created atomically and exclusively by whichever of the lifeline or the server needs it first (`src/core/LifelineIngressSecret.ts`). It is held in the file and in process memory only: never in `process.env`, never a tmux `-e` flag, never logged, never returned by a route. A file that cannot be read is never replaced, and a failed re-read keeps the last good value.
- **The routes require it** in the `X-Instar-Lifeline-Secret` header, compared in constant time (`src/server/LifelineIngressGuard.ts`). The Bearer check is unchanged and still required.
- **Callers updated:** the lifeline's message forward (including the legacy-strict retry and queue replay), the lifeline's callback forward, and the server's own re-injection call (which labels itself `X-Instar-Ingress-Caller: server-self`).
- **No message is refused without proof.** The guard refuses no message until it is armed: the running lifeline has sent the valid secret at least once (persisted), or there is no lifeline to wait for (the server polls Telegram itself, or Telegram is not configured). A current lifeline proves itself through the new `POST /internal/lifeline-proof`, on server-up and on its 15-second tick. Sixty seconds after the server starts, a guard that is still unarmed writes the existing lifeline-restart signal once, so a lifeline on older code restarts onto current code without waiting for a message.
- **While unarmed, an unproven request is handled exactly as before.** In observe, for as long as the guard stays unarmed (a fleet agent's real traffic is never degraded before a development agent has run the strict behaviour); the unarmed guard is reported hourly, raises an attention item after a day, and reads off on `/guards`. In enforce, for at most 24 hours from when the feature first ran on the machine.
- **Once armed (either mode), or in enforce after those 24 hours,** an unproven button tap is refused and an unproven message is delivered with no sender identity.
- **"No sender identity" is applied in one place.** The forward route drops the body's `fromUserId`, `fromUsername`, bot fields and name (it becomes "Unverified sender") right after the check, flags the message `senderUnverified`, and does not claim an exactly-once ledger key for it. Operator auto-bind (both sites), the inbound log's operator uid, the ratifiers, command and topic-profile authority and the agent-to-agent hook therefore see no first-party identity.
- **Two modes**, `telegramIngress.lifelineSecret.enforce` (read live, shipped omitted). `observe` delivers an unproven message that way and counts a `would-refuse`. `enforce` refuses it with HTTP 401 `{ ok: false, error: 'lifeline-secret-required', refused: true, reason }`. Default: enforce on a development agent and where there is no lifeline ingress; observe on every other agent.
- **Observe has an exit.** With the setting omitted on a non-development agent, observe switches to enforce after 24 hours with zero would-refuse and at least 10 verified Telegram requests from the lifeline, or 7 days after arming, whichever comes first. The counters and timestamps are persisted in `.instar/state/lifeline-ingress-secret.guard.json` and survive a restart. `enforce: false` holds observe.
- **A full rollback key.** `telegramIngress.lifelineSecret.bypass: true` restores the previous handling of every request. Both keys are config-file edits only; they cannot be changed over HTTP.
- **A refused message is held, not lost.** A current lifeline re-reads the secret file on a 401 and retries. If the server still refuses, the message stays in the lifeline's durable queue with no drop budget burned (new `ForwardSecretRefusedError`); replay is single-flight, backs off from one minute to fifteen, and after ten minutes the lifeline tells the user once that messages are being held.
- **Restart-signal budget.** Signal writes caused by an unverified request (the guard's, and the forward route's 426 handler) share a persisted budget: one per 12 hours before arming, one per 24 hours after, never with an unknown target version.
- **One tap, one effect.** `TelegramCallbackDedupe` claims each `callback_query.id` before handling and records the outcome. A second delivery of a handled tap returns `{ ok: true, deduped: true }`; of a tap whose handler failed, or whose outcome is unknown, 409. Proven taps are persisted (bounded to 2000 ids, 7 days); unproven ones are claimed in memory.
- **Never served or editable.** The secret, the guard's state file, the tap claim store and the lifeline-restart signal file are in `KEY_MATERIAL_PATHS`, so the file routes refuse to read or save them, backups exclude them, and init plus the existing post-update migration gitignore them. Registered machine-local in the state-coherence registry.
- **Observability.** The authed `/health` gains `telegramIngress.lifelineSecret` (mode, `armed`, `refusing`, `refusingTaps`, `secretAvailable`, exit-rule progress, persisted counters) and `telegramIngress.callbackDedupe`. The guard is a load-bearing row on `/guards` (`telegramIngress.lifelineSecret`). Degradation reports under feature `TelegramIngress.lifelineSecret`; an unproven request after arming, a bypassed guard, and a lifeline still not updated after a day each raise an operator attention item (at most one a day per kind).
- CLAUDE.md template and `migrateClaudeMd` gain "Telegram internal routes need the lifeline secret" (framework-shadowed). Registered in `DEV_GATED_FEATURES`.

**Limit:** no tool hook refuses a read of the secret file today; the protection is the 0600 mode plus the key-material path list (file viewer, backups, git sync). Everything runs as one OS user, so this is a cooperative boundary. It stops a session forging through its normal token. It does not stop a session that deliberately reads the secret file. A read-refusing hook covering this file, `.instar/identity.json` and the dashboard PIN is tracked as ACT-099.

**Rollback note:** rolling the lifeline back by itself to a version from before this change, under a server that has already armed and enforces, gets that lifeline refused. Set `telegramIngress.lifelineSecret.bypass: true` first.

## What to Tell Your User

If one of your agents went quiet for hours and its log showed a long run of "spawns failed before binding", this is the fix. The agent believed a copy of itself was already running because it was identifying that copy by an operating-system ID number the machine had since handed to something else. It now also checks when that process started, so a stale note can no longer keep the agent off. Nothing to configure. Separately, the agent's crash log now keeps the reasons for every failed start instead of only the last one, so a repeat of this kind of outage can be explained in minutes rather than hours.

Messages and button taps from Telegram reach me through a small helper process. Until now, any of my own working sessions could have imitated that helper and sent me a message, or an Approve tap, that looked like it came from you. That door is now closed: the helper and my main process share a private key that my sessions are not given, and I only treat Telegram input as yours when it arrives with that key. A button tap that reaches me twice is now acted on once. Nothing changes in how you talk to me, and no message is lost during the update: I only start refusing messages once the helper has shown it is running the new version. If the helper somehow stays on the old version for more than a day, I will tell you; your messages still reach me either way. One honest limit: a session that deliberately went looking for the key file on the machine could still read it; this stops accidental or casual misuse, not a determined one.

## Summary of New Capabilities

None — this is a reliability fix to an existing guard. No new setting, route, or surface.

- Telegram messages and button taps are accepted as coming from a person only when they arrive through the lifeline, not from a session using the ordinary API token.
- The same button tap delivered twice is applied once.
- The health report shows whether this protection is watching or refusing, and the saved counts behind that.
- The watch-only mode ends by itself after a clean day of real traffic, or after a week at the latest; one setting holds it or forces it.
