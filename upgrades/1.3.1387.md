## What Changed

- **Local Telegram sessions no longer show the headless icon.** The dashboard's live session list for THIS machine comes over the WebSocket, whose rows never carried `platform`, so every local Telegram topic was drawn with 🖥️ (headless) while the same topic seen from another machine (via `GET /sessions?scope=pool`) showed ✈️. The platform derivation moved out of the `GET /sessions` handler into `src/server/sessionPlatform.ts` (`resolveSessionPlatform`), and `WebSocketManager` now takes it as an injected `resolveSessionPlatform` option wired by `AgentServer` to the real Telegram and Slack adapters, so both surfaces fill `platform` / `platformId` / `platformName` from one function.
- **Every session-row badge has a tooltip, and a "?" button opens a legend.** Type (interactive / job), model (with a note when the session started on a bare alias like `opus`, so its exact version is not recorded), platform icon, machine and running time each explain themselves on hover, and the "?" next to + in the Sessions header toggles a small legend that also works on a phone.

- **A pairing message with no buttons now says why.** When an agent can't offer Telegram Approve/Finish (spec §6.1), its "Open the Threadline tab on the dashboard" message used to say only "until its listener protection is fully on". It now names the cause and the agent's Instar version: the listener hasn't proven itself yet (older or not running), the protection is watch-only or bypassed in config, the secret can't be read, or the agent reads Telegram directly. New: `LifelineIngressGuard.tapsUnprovableReason()` and the `whyNoButtons` dep on `PairingInviteTelegram`, wired in `routes.ts`. Nothing about when buttons show changes.

- **Pairing works on an agent with no lifeline.** When the server polls Telegram itself, a forwarded invite answered "I can't take it from this chat", and a pairing tap answered "Approve this on the dashboard". Pairing also dropped every button whenever `isPolling` was true. `TelegramAdapter.setPairingHandler()` (wired in `routes.ts`) now hands invites and `pi:` taps read with `getUpdates` to the same `PairingInviteTelegram` handler, marked as read from Telegram, and the owner, chat and one-time-token checks still apply. Unauthorized senders still get nothing. `enforcing` stays true while polling when the handler is wired. `LifelineIngressGuard.tapsProvable()` now arms a no-lifeline guard on first call, as `health()` already did, so a fresh polling agent's first pairing isn't treated as unarmed. Found by Luna's read-only check of PP (1.3.1384, no lifeline, `armedBy: no-lifeline-ingress`).

## What to Tell Your User

The little icons on each session in the dashboard now explain themselves. Hover over any of them on a computer, or tap the "?" next to the + button on your phone, to see what each one means: the session type, the model it runs on, whether it's linked to Telegram, which machine it's on, and how long it has been running. I also fixed a wrong icon: sessions on the machine you're viewing showed a screen icon ("no messaging") even when they were Telegram conversations. They now show the Telegram plane.

If I ever can't show you pairing buttons in Telegram, I'll now tell you why in the same message, so you know what's wrong without anyone checking my machine.

If I read Telegram myself (no separate listener), pairing now works with buttons too: forward me an invite, tap Approve or Finish, and I'll handle it right in Telegram.

## Summary of New Capabilities

- Tooltips on every dashboard session badge, plus a "?" legend in the Sessions header.
- The platform icon is now correct for this machine's own sessions.

- `LifelineIngressGuard.tapsUnprovableReason()`.

- `TelegramAdapter.setPairingHandler()` / `hasPairingHandler()`.
