## What Changed

A planned restart waits while a Local Verify run is in progress. It judged "in progress" only by whether the run's child process was alive. Between the child exiting and the server starting to handle that exit, the child is gone and the in-flight marker is still on disk (when the server does handle it, it writes the `settling` merge hold, clears the in-flight marker and records the result in one uninterrupted step; the window covers the time until that step starts). A restart consumer that polled in that gap saw no live child and took the restart. On 2026-11-19 at 01:18Z this cancelled a verify 39.6 minutes in whose child had just exited with status 0, and the result was discarded. The same race cost a 24-minute run on 2026-11-13.

The shared restart guard (`src/core/PlannedRestartVerifyGuard.ts`) now also holds a planned, not-bypassed request while the in-flight marker is present and its pid is gone. The hold lasts at most 60 seconds from the first moment either consumer sees the pid gone, ends at once when the server clears the marker, and is never renewed. The first sighting is written to `state/local-verify/inflight-exit-seen.json`, keyed by the run's attempt token, so the server's own watcher and the lifeline's supervisor (separate processes) count from the same moment. A marker left behind by a server that died holds a restart for that one minute and no longer. If the sighting cannot be written, the guard does not hold. The three-hour bound, `bypassHolds`, and the rule that a request three hours old never waits are unchanged. Once the server clears the marker, the existing merge hold (settling 60 seconds, hand-off 10 minutes) takes over as before.

The shutdown path still does not record a finished result when the verifier on disk has changed, because a record written then cannot be merged before the process exits and the next verifier skips it. That discard is now written as its own audit row, `finished-result-discarded-at-shutdown`, with the reason.

Restarts are now counted by the service:

- `logs/restart-requests.jsonl` records carry `plannedRestart` and `bypassHolds` as the request wrote them (`null` when it wrote neither).
- The Local Verify `boot` audit row carries the same two fields when a request explains the boot.
- A new audit row, `restart-interrupted-runs`, is written at every stop of the service: the local run it interrupted (pr or main, head, minutes run, whether the child had exited, whether a verdict was on disk and what became of it), each accepted peer attempt not yet imported (at most 20 listed, with the total), and whether the restart was planned and bypassed holds. It is written with empty lists when nothing was running.

This change edits `LocalVerifyService.ts` and files it imports, so the verifier version rotates. Records made under the old version are not counted after the restart that loads this one, as with any verifier change. Changes waiting in the queue are tested again under the new version.

The lifeline's supervisor runs the code it started with until the lifeline itself restarts. Until then only the server's own watcher has the new hold. The measured loss went through the server's own watcher.

## What to Tell Your User

Nothing to do. A routine restart used to be able to land in the moment between a test run finishing and its result being saved, which threw away up to 40 minutes of testing. It now waits for the result to be saved, for at most one minute. Forced restarts work as before.

## Summary of New Capabilities

| Capability | How to Use |
|---|---|
| A planned restart waits for a just-finished verify to be recorded | Automatic. Bounded at 60 seconds; `bypassHolds: true` skips it |
| Count what each restart interrupted | Read `restart-interrupted-runs` rows in `logs/local-verify.jsonl` |
| Count finished results discarded at shutdown | Read `finished-result-discarded-at-shutdown` rows in `logs/local-verify.jsonl` |
| See whether a restart was planned and whether it bypassed holds | `plannedRestart` and `bypassHolds` in `logs/restart-requests.jsonl` and on the Local Verify `boot` row |

## Evidence

The defect was traced in code and logs for the 2026-11-19 01:18Z loss: the in-process `ForegroundRestartWatcher` consumed a plain planned request while `inflight.json` was still present and its pid was gone, and `shutdown()` then cancelled the run.

Unit tests, run on the change: `tests/unit/planned-restart-verify-guard.test.ts` (43 tests), `tests/unit/ForegroundRestartWatcher.test.ts` (16), `tests/unit/boot-readiness.test.ts` (16), `tests/unit/localVerify/operatorQueue.test.ts` and `tests/unit/localVerify/operatorHoldService.test.ts` passed together (135 tests in 5 files); `tests/unit/localVerify/LocalVerifyService.test.ts` (182), `tests/unit/localVerify/peerVerifier.test.ts` (130), `tests/unit/self-action-convergence.test.ts` (863), `tests/unit/supervisor-kickstart-race.test.ts` (8) and `tests/unit/server-supervisor-respawn-guarantee.test.ts` (18) passed together (1201 tests in 5 files). The guard tests cover: pid alive, pid gone with the marker present, the bound to the millisecond, the marker cleared early, `bypassHolds`, a three-hour-old request, a stale marker from a dead server, a sighting that cannot be written, and both consumers in the gap.

An exit-gap case was added to `tests/e2e/planned-restart-local-verify-lifecycle.test.ts` (production wiring) and to `tests/integration/planned-restart-local-verify.test.ts` (the supervisor, with a real green result on disk). These two files run in Local Verify, not on the authoring machine.
