## What Changed

Four fixes from the locked-Mac proof run (the locked-screen feature itself stays off everywhere). The Mac desktop helper now creates its missing record folders (owner-only) and, when a record operation fails, says why in one fixed word that Instar passes on instead of a bare "unavailable". The locked-screen status now names, for the app and for a browser separately, whether a Mac password could be typed once the Mac is locked and what stands in the way (for example "tunnel-not-active" or "retained-helper-required"); the desktop viewer shows that reason instead of hiding the box, and an open viewer is told the moment the tunnel comes back. The Mac helper also reads who holds secure input from the right place now: before, it never could, so every password typed at a locked Mac was refused as "lock screen not confirmed". Every refusal now shows a plain sentence in the viewer and is recorded in the agent's logs. Every agent now gets a dashboard PIN at start if it has none, whether or not it uses Telegram, stored in its secret store when it has one; a PIN that already exists is never changed, and the PIN is no longer printed in logs.

With Telegram polling set to follow the lease, a machine now waits for the lease before polling at startup, instead of polling first and stopping afterwards. This is off by default, so no agent changes on update.

When private memory can't run, the agent now reports the real reason instead of always saying the platform has no sandbox. The most common real reason found so far is an agent set to use a Claude Code older than private memory needs. Memory privacy is opt-in, so this applies to agents whose owner turned it on. The owner now hears the reason privately, with a link to a page that gives the solution. When a working Claude Code is on the machine, that page can fix it in one click. Everyone else still gets the same fixed reply.

Fixes from the first live run of setup on a throwaway agent. A yes after a no can now replace a dead key that setup stored itself, and a setup session's brief now covers shared folders, disposable email addresses and closing browser windows. This only runs on a throwaway or development agent proving a recipe.

A session on a standby machine can send a Telegram reply through the machine holding Echo's lease. The forwarding design and lease fence already existed, but a reply that was held and later recovered could reach Telegram without appearing in the session machine's topic history. Worse, the standby could label an operation "delivered" from a forwarded receipt that contained no Telegram message ID. The holder's receipt and the standby's outcome now require the actual Telegram ID. When a held reply later succeeds, the standby records that ID and text in the topic history without sending a second copy. If the lease changed while it waited, recovery follows the replacement operation. An uncertain send stays unknown and is never resent blindly.

The lease holder still performs the outbound policy checks. The standby's recovery only records confirmed delivery; it does not grant itself permission to send. The observed Mama PC operation `afe843bf` previously said delivered with no ID while the Studio had Telegram ID 1508. This change closes that false answer. A live reply from Mama PC remains the final verification after the release reaches that machine.

Echo can run on several computers. Only one computer holds the live Threadline connection at a time, so a standby's local connection is intentionally off. The old status answer described that local fact as though Threadline were off for Echo. A session could then tell Justin the agent network was unavailable when the Studio was connected.

The status routes now check the other known machines and lead with whether Echo is reachable, which machine currently carries the connection, and what happens if that machine goes away. A peer must answer with Echo's verified relay identity before its connection counts. If a holder cannot be checked, the answer is **unknown**; the standby's local setting remains visible as secondary detail. The MCP status and discovery tools use the same agent verdict, and discovery can use the holder's server connection from a standby.

The channel registry also checks Slack across known machines. This fixes the measured false "Slack is not enabled" answer from Mama PC while the Studio was connected. A dark peer keeps a negative answer unknown. The session guidance for existing and new installs now tells a session which field describes the whole agent. The existing posture lint and side effects template now ask status surface authors to declare scope. Other local status surfaces are tracked in issue #2697.

## What to Tell Your User

If your agent runs without Telegram and never had a dashboard PIN, it has one now, so the dashboard's owner controls work. Ask me for it whenever you want to open the dashboard. If you already had a PIN, nothing changed.

Nothing to do. This prepares backup machines to stay quiet until they take over.

If you ever see "I can't reply here yet", I'll now send you the reason in a private message, with a link to the solution.

Nothing changes for you yet. The part where your agent sets services up itself is still being proven.

Replies from a standby are forwarded through Echo's connected machine. A delivered answer now includes Telegram's message ID and appears in the topic history. If delivery cannot be confirmed, Echo says unknown and does not send a duplicate.

Threadline is available through Echo's connected machine even when the computer hosting this conversation is on standby. If that machine cannot be checked, Echo says its reachability is unknown.

|-----------|-----------|

| Owner solution link | Sent privately to the verified owner; needs a tunnel so it opens on a phone |

None. `POST /recommended-services/:id/key` accepts a replacement for setup's own key after a no and a new yes.

- Confirmed held replies add a topic history row after delivery.
- Delivery outcomes require a real Telegram message ID.
- Recovery follows a lease transfer without breaking the one-voice fence.

- Whole-agent Threadline status from any machine.
- Standby MCP network discovery through the connected holder.
- Whole-agent Slack channel verdict in `/channels`.
