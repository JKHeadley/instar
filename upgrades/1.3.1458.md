## What Changed

**SessionReaper pressure: real CPU busy % instead of the load average; the memory signal was
designed, measured and withdrawn** (spec `docs/specs/reaper-pressure-signals.md`,
side-effects `upgrades/side-effects/reaper-pressure-signals.md`).

- `computePressure` now grades `cpuTier` from `cpuBusyPct` — sampled real CPU busy % from
  `os.cpus()` tick deltas (`hostCpuBusySampler.ts`) — under the default `cpuSignal: 'busy'`.
  The 1-minute load average is still sampled and reported as `loadPerCore` but no longer
  decides anything: on 2026-10-25 it read 9.4 per core (`critical`) on a laptop whose CPU was
  36-44% idle. An unknown busy sample grades `normal` — memory-only — and deliberately does
  NOT fall back to the load average. `cpuSignal: 'load'` restores the legacy grading exactly,
  and a test drives that lever from a config object through the sampler into the classifier.
- A CPU figure is published only once a full 30 s window has elapsed; a shorter window is
  `null` (unknown), never a startup spike. So for roughly the first 30 s of a server's life
  the tier comes from memory alone — stated, not hidden.
- One `vm_stat` + one `sysctl` per 30 s sample window; every caller (route, reaper,
  cartographer sweep) reads the same frozen cached sample, so a dashboard poll cannot narrow
  the reaper's window.
- **No memory grade ships.** `compressorPct`, `decompressionsPerSec` and
  `kernelMemoryPressureLevel` are REPORTED and decide nothing. Three candidate grades were
  built and each withdrawn on measurement: a healthy Studio reads 35% compressor occupancy
  and 94k decompressions/s at kernel pressure level 1, and the continuous
  `kern.memorystatus_level` reads 59 there while the 2026-10-25 laptop computes to ~67 — every
  candidate said that laptop's memory was fine. The evidence points at process/thread
  crowding instead (CMT-1016 task 3). The readings ship as observability so the next attempt
  starts from data.
- New `monitoring.sessionReaper` keys: `cpuSignal`, `cpuModerateBusyPct` (75),
  `cpuCriticalBusyPct` (90). No compressor key, because no compressor decision ships.
- `GET /sessions/reaper` → `pressure.inputs` gains `cpuBusyPct`, `compressorPct`,
  `decompressionsPerSec`, `kernelMemoryPressureLevel`, `cpuSignal`, `sampledAt`, `windowMs`.
- Migration parity: one exported constant is the single source for the CLAUDE.md bullet, and
  both legacy wordings (the migrator's own and the older template's) are replaced in place on
  every deployed agent.

**The silent-fallback ratchet is back at its baseline, so the merge queue moves again.**

`origin/main` measured 495 flagged catch blocks against the `BASELINE = 494` in
`tests/unit/no-silent-fallbacks.test.ts`, a ratchet whose own comments say the number only
ever decreases. Main was failing its own test.

That does not stay on main. Local Verify tests each PR as the MERGE of the PR and main, so
every queued PR inherited the failure — PR #2371 reported
`file-failed:tests/unit/no-silent-fallbacks.test.ts:1`, and PR #2350 reached
`state: gave-up, lastOutcome: refused:verify-failed` after three attempts.

The flagged catch is `sampleOnce()` in `src/core/machineLoadReport.ts`. It is NOT a swallow:
it logs the error with its message, and a missed sample surfaces downstream as
`loadVerdict: 'unknown'` (a report older than 60 s reads unknown) rather than as a fabricated
healthy reading. It was missing the canonical in-window `@silent-fallback-ok` justification
the scanner reads. This adds it: one comment, no behaviour change, count back to 494.

The baseline was deliberately NOT raised to 495 — the number is the mechanism.

- `src/core/ThrowawayAgentGuard.ts` (new): an agent in a temporary folder, or created with a sandboxed `HOME`, is a throwaway.
- `src/commands/setup.ts` `installAutoStart`: the one function every auto-start installer uses now refuses a throwaway (`--force` overrides) and runs under a per-agent lock shared with teardown. `PostUpdateMigrator` no longer rewrites or reloads the machine-wide fleet watchdog from a throwaway.
- `src/commands/init.ts`: a non-interactive `init` records `autostart.autoInstall: false` (new `--autostart` flag lifts it); a throwaway gets `throwawayAgent.expiresAt` (24h; `--expires-in`, `--keep`).
- `src/commands/server.ts`, `src/lifeline/TelegramLifeline.ts`: an expired throwaway removes its own auto-start (only the unit whose working directory is this agent) and exits; the startup self-heals no longer install a missing unit when `autoInstall` is false; a temp-folder agent with no record gets a 24h expiry at boot.
- `src/scheduler/JobScheduler.ts`: a temp-folder or recorded throwaway refuses every scheduled job (skip reason `throwaway-agent`; override `scheduler.allowOnThrowawayAgent: true`).
- CLAUDE.md template + `migrateClaudeMd()`: "Throwaway test agents" section.

Why: on 2026-10-21 a release-check script made a test agent in a temporary folder with a sandboxed `HOME`. Its server's auto-start self-heal loaded a start-at-login job into the real user launchd, launchd then ran it with the real `HOME`, and for five days it ran scheduled jobs on the operator's Claude subscription (~2.9B tokens, about 12% of that week's Claude use).

## What to Tell Your User

The part of me that decides whether a machine is overloaded was reading the wrong dial for
processor load on a Mac: it called a laptop critical while a third of its processors sat idle.
It now reads what the processors actually did, averaged over half a minute. One setting puts
the old reading back if you ever want it.

I also tried to add a memory-pressure reading, and I am telling you plainly that it did not
work: every way I found to measure it scored a perfectly healthy machine as worse than the
struggling one, so I withdrew it rather than ship something that looks like a safeguard and
is not. The readings are recorded now but decide nothing, and the real cause on that laptop
looks like too many programs and sessions open at once, which is a separate piece of work
already on the list.

Nothing changes in how I behave. One of my internal safety checks had drifted one step past
its own limit, and because every pending change is tested as if it were already merged, that
quietly stopped all of them from being able to land. The code it flagged was already
reporting its errors properly and just needed to say so in the form the check reads. Fixed,
and the queue moves again.

If a test copy of me is ever made in a temporary folder, it can no longer install itself to start at login or run my scheduled jobs on your subscription, and it switches itself off after a day. Your normal agents are not affected.

## Summary of New Capabilities

- `pressure.inputs.cpuBusyPct` / `compressorPct` / `decompressionsPerSec` /
  `kernelMemoryPressureLevel` / `sampledAt` / `windowMs` on `GET /sessions/reaper` (and
  `?scope=pool`) — the three compressor fields as observability, grading nothing.
- `monitoring.sessionReaper.cpuSignal: 'load'` rollback lever, plus the
  `cpuModerateBusyPct` / `cpuCriticalBusyPct` busy thresholds.

- None. One source comment; no new route, config key, behaviour or user-visible surface.

- `instar init --expires-in 6h` / `--keep` / `--autostart`, and `instar autostart install --force`.
- `scheduler.allowOnThrowawayAgent: true` for a test that needs scheduled jobs.
- `.instar/state/throwaway-expired.json` records what an expired throwaway removed.
