## What Changed

- **A failed confinement rehearsal now records what it observed, not just which check failed.** `profileUnenforceable()` wrote only `failed: [probeName]`, and the canary report that explains it (`<tmpDir>/canary-report-<nonce>.json`) is deleted with the attempt tree — so when the executor latched for 24h on `session-git-status`, the cause was unrecoverable and took a full manual sandbox re-run to narrow down. The probe's `detail` now quotes the observed value, distinguishing `<outputs["9"] absent>` (the sandboxed session omitted that entry from its own report) from a genuinely quoted git failure, which the code's `?? 'fatal'` default otherwise renders identical. The latch record gains a bounded, secret-scrubbed `failedDetail`. **The verdict expression is byte-identical and commented as such** — this is recording only, on the failure path, after the decision. All 14 must-fail probes and the latch's 24h semantics are untouched.

- **A promise with a date can now actually carry one.** `POST /commitments` accepts `checkInAt` — the field the dated-reminder feature reads — and stores it on the commitment. Until now the field was silently discarded: the request returned 201, and the stored record had no date. Four places in the code read `checkInAt` (the beacon's trigger resolution, the dated-backlog filter, and both arms of `GET /commitments/check-in-reminder`); none of them could ever have matched anything, which is why that route honestly reported `datedCount: 0` across every commitment on the agent.
- **A bare date is refused rather than quietly resolved.** `2026-10-24` is a valid timestamp to a parser and means midnight UTC — so a check-in promised for "Friday" would have fired at 5pm Thursday for anyone in Pacific time. The request is refused with the reason and an example of the right shape, instead of being resolved to an hour nobody chose.
- **A date alone does not count as follow-through.** Creating a commitment still requires either PromiseBeacon enrollment with a deadline, or an explicit opt-out reason. A dated check-in rides alongside those; it does not replace them, because the reconciler that posts the dated reminder still ships in observation mode and would send nothing.

- **Your agent stops calling itself unhealthy over a job that was switched off.** The health report added up every scheduled job's run of consecutive failures with no time limit. A job's failure count only resets when that job next succeeds — so a job you disabled keeps its last count forever, and nothing can ever bring it down. One agent reported 119 failures while nothing at all was wrong: 118 of them belonged to a job that had been off since 26 September.
- **A failure now counts while it can still change.** A job's failures count toward health if the job is switched on and ran within the last 24 hours. Everything else is still reported, under a separate heading that names the job, its count, its last run, and whether it was excluded for being disabled or for being out of date — so nothing is hidden, it just stops dragging the verdict down.
- **The threshold itself is unchanged.** Five or more current failures still marks the agent degraded, exactly as before. This narrows what counts as current; it does not relax the rule.

## What to Tell Your User

Nothing to do. If the fix pipeline ever stops itself on a sandbox check again, it will say what it saw rather than needing an investigation.

If your agent promised you something "by Friday", the date it was given could not be stored, so nothing was ever going to arrive on Friday. The date is now recorded.

Be aware of the honest scope: recording the date is one half. The part that actually posts the reminder when the moment arrives still ships switched off pending a deliberate decision, so this is not yet "a dated promise always produces a reminder". What changed is that the promise can now hold its date at all — previously the whole feature had no way in.

If your agent has been reporting itself as degraded and you could not find anything wrong, this may be why — check whether the failures it was counting belong to a job you turned off weeks ago. After this update the health report separates the two: the number at the top is what is failing now, and anything historical is listed beneath it with the reason it does not count.

Nothing you need to do. If a job genuinely is failing, you will still hear about it.

## Summary of New Capabilities

- No new surface. `exec:profile_unenforceable` gains an additive `failedDetail` array (≤300 chars per entry, scrubbed); readers of `failed` are unaffected.

- `POST /commitments` accepts and stores `checkInAt`, an absolute instant, with a bare date refused by name.

- The health report distinguishes a job failing now from a job that failed once and was then switched off, and says which is which.

## Evidence

- Live incident: one probe of ~21 failed while every must-fail refusal and every other session probe passed, so the confinement itself held.
- Two hypotheses tested and refuted rather than shipped: the measured macOS `xcrun` cache noise (git exits 0) does **not** match the probe regex and would pass — now pinned by a regression test; and `fatal: not a git repository` cannot apply because the workspace is cloned before the canary runs.
- 45 unit tests pass; three new ones pin the verdict on missing / failing / clean output and assert the detail distinguishes an absent entry from a real failure.

- **Before.** `checkInAt` appears four times in `src/server/routes.ts` as a READ (`commitment.checkInAt` in the beacon trigger, `all.filter(c => !!c.checkInAt)` in the dated backlog, and twice in the reminder route's response) and was declared in `CommitmentTracker.record()`'s input type **zero** times. A live commitment created on 2026-10-21 with `checkInAt` set returned HTTP 200 and the field was absent from the stored record's keys; `GET /commitments/check-in-reminder` reported `datedCount: 0` against 883 commitments.
- **After.** The field is stored, survives a re-read from a fresh tracker over the same state directory, and is matched by the same filter the reminder route applies. A bare date returns 400 naming "bare date"; a non-timestamp returns 400 naming ISO 8601; a date with no other follow-through choice returns 400 naming the follow-through requirement.
- `tests/unit/CommitmentTracker-checkinat-writer.test.ts` (5 tests) and `tests/integration/commitments-checkinat-route.test.ts` (8 tests) pass.

Reproduced from live state and fixed with the real numbers:

- **Before.** `GET /health` on a working agent answered `consecutiveJobFailures: 119` and `status: degraded`. Reading `GET /jobs` showed the source: `w29-working-set-mirror` with `enabled: false`, `consecutiveFailures: 118`, `lastRun: 2026-09-26T07:01:15.227Z` — twenty-five days earlier. The remaining 1 was a single historical session kill. Because the job is disabled it can never run, so the count could never decrease: the agent was permanently degraded over something nothing could fix, and an operator was nearly told it was an active fire.
- **After.** The same two jobs produce `consecutiveJobFailures: 1`, `status: ok`, and `staleJobFailures: { total: 118, windowHours: 24, jobs: [{ slug: "w29-working-set-mirror", failures: 118, lastRun: "2026-09-26T07:01:15.227Z", reason: "disabled" }] }`. Asserted end-to-end through the real route pipeline in `tests/integration/health-stale-job-failures.test.ts` (4 tests), including that five current failures still degrade, and that the excluded detail never appears for an unauthenticated caller.
- **Boundaries.** `tests/unit/job-failure-currency.test.ts` (11 tests) covers both sides of each decision: enabled/disabled, inside/outside the window, exactly at the edge, absent and unparseable timestamps (both count as current, so a corrupt state file cannot silence a real failure), a job that is both disabled and stale (reported as disabled, the actionable reason), and the list cap keeping the worst offenders while the total still counts every excluded failure.
