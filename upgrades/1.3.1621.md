## What Changed

- A session started directly into a topic (the spawn request with a written task) now starts on that topic's pinned model and engine, unless the request names its own. It also records what it started with.
- After a server restart, sessions with no record of how they started are no longer restarted "to apply the pinned profile". That restart was killing freshly started tasks: the new session rebuilt its context from the topic's chat history, which never held the task, so it sat idle. It happened more than 20 times between 2026-11-01 and 2026-11-03.
- When a directly started session does need a real profile restart that starts a new conversation, its original task brief is carried into the new session.

## What to Tell Your User

- **Started tasks keep going after restarts**: "When I start a task in one of our topics, a server restart no longer makes me drop it to switch models. I start on the topic's model to begin with."

## Summary of New Capabilities

| Capability | How to use |
|---|---|
| Direct topic spawns honour the topic profile | automatic |
| Profile restarts carry a direct spawn's brief | automatic |

## Evidence

- On 2026-11-03 two bug sessions (topics 10000001407 and 10000001426) were each restarted within seconds of a server boot by the profile check. The profile log shows `boot-sweep-armed` and then `respawn-applied` with `method: continuation, fresh: true`. Their spawn prompts were not in the topic history, so both sessions idled.
- The profile check's durable record had no entry for either session before the restart. Only the orchestrator's own restart wrote one.
- New tests: the direct-spawn route test (`tests/integration/sessions-spawn-topic-profile.test.ts`) and the full-server test (`tests/e2e/topic-profile-direct-spawn-lifecycle.test.ts`) spawn into a pinned topic, simulate a server restart, and confirm there is no restart. A session with no record is left alone, and a real pin change names the replaced session so its brief can be carried.
