## What Changed

- **local-verify tests a PR's merge with the base branch's current head.** It used the PR's `baseRefOid`, which GitHub reports as the base at the PR's last update and which is days old for older PRs. It now reads the current head (`gh api repos/{repo}/branches/{base}`) when a verify is requested and refuses the request if that read fails.

- **local-verify's status loop now loads safe-merge from the running server's own install** (`<package>/scripts/safe-merge.mjs`) instead of the agent-home checkout. On the first enable after release, the checkout held an older safe-merge, so the loop was never built (`GET /local-verify/status` answered 503 "no safe-merge floor").

- **local-verify survives server restarts** (spec `docs/specs/local-verify-merge-authority.md` §2 "Restarts" and step 6). Three releases on 2026-10-22 each restarted the server and cost verify work: an auto-update cancelled a 35-minute verify, a queued verify started during shutdown, the queue was lost, and every green record was discarded because records were keyed to the package version.
  - **Restart hold:** while a verify runs, an automatic update restart waits for it, through the existing AutoUpdater restart-hold path (`registerLocalVerifyRestartHold`, key `local-verify`). The hold ends at the run's own ceiling (its 120-minute active-work budget plus two 30-minute in-place waits), capped by the gate's `maxDeferralHours`. A manual apply is not held.
  - **Shutdown:** `shutdown()` stops the in-flight run's process group and starts nothing else (no pump, no timer). The cancelled verify goes back to the head of the queue, not counted as an attempt. `POST /local-verify` answers 503 (`stopping`) during shutdown.
  - **Durable queue:** PR verify entries (pr, head, base, first-queued time, attempts, error retries; the in-flight entry first) are written atomically to `state/local-verify/queue.json` on every change. They are restored at boot, dropping PRs that closed, heads that moved, and verifies already recorded green. Restored entries wait for the orphan reap before starting, and a request arriving during the restore waits behind it. `main` verifies are re-derived, not persisted.
  - **No indefinite hold:** while an update is pending and only a running verify delays it, no new verify starts (spec §2 Restarts rule (b)); starts resume after 120 min pending or when something else delays the restart. That wait never counts toward the starved alert.
  - **No crash re-run loop:** a verify that was running when the server died uncleanly is charged one error retry; past the limit it records `error` (`server-restarted`) instead of re-running.
  - **`verifierVersion`** is now a content hash (`vh2:…`) of the verifier's real local import graph (including SafeGitExecutor, SafeFsExecutor, hostTestRunnerSemaphore, reviewGate and the floor script), the installed `typescript` version, the node version, the protected-path list and the policy hash, instead of the package version. A release that does not change any of those keeps its records. The run child recomputes it and refuses (`verifier-mismatch`) if its code on disk differs from the running server's.
  - A corrupt `queue.json` is moved aside (`queue.json.corrupt-<ts>`) and audited; `queue.json` is rewritten only when its content changes.

- **A machine that was perfectly fine could show up as unreachable in the "all my machines" views.** When your agent runs on more than one computer, it asks each of the others for their sessions, jobs, attention items and guard posture. Each machine advertises several ways to be reached (Tailscale, the local network, the Cloudflare tunnel). The code that picked one of those collapsed the whole list to a single address and then checked whether that one was safe to send credentials to. If it was not, the read simply failed — even when another perfectly good, already-proven way to reach that machine was sitting in the list. The picker is now admission-aware: it walks the advertised ways in order and hands back the best one that is actually allowed, so a healthy tunnel is no longer discarded because a private address happened to come first.
- **One destination per request, and the skipped ways are reported instead of vanishing.** The picker returns which ways it passed over and why, so "I could not reach that machine" can say which rope was refused rather than leaving you to guess.
- **The reason given for refusing a Tailscale address is now the true one.** Sending credentials to a Tailscale address over plain `http` is not supported, and that refusal now says exactly that (`cgnat-plaintext-unsupported`) instead of being reported as a disallowed scheme or an unknown host, which pointed at the wrong problem.
- **A pre-existing hole in the IPv6 check is closed.** The pattern meant to recognise private IPv6 addresses also matched several addresses that are *outside* that private range, so they were being treated as private. It now requires the full address shape. The same correction was made for link-local addresses.
- **Your agent's instructions gained a short card** explaining the difference between "that address was refused", "that machine did not answer" and "I have no address for that machine" — three very different situations that used to read the same. Existing agents get the card on update; new ones get it at install.

## What to Tell Your User

Nothing changes for you. A fix to the still-off local test checker so a pass means "safe against today's main", not "safe against an old one".

Nothing changes for you: this fixes a wiring issue in the still-off "test locally instead of waiting on GitHub" work.

Nothing to do. My own test runs for pull requests now survive my updates: an update waits for a run in progress, and anything waiting in line is picked up again after the restart instead of being forgotten. Results stay valid across updates that don't touch the checking code, so they aren't redone.

If one of your machines ever showed as unreachable in the pool views — sessions, jobs, attention, guard posture — while that machine was actually running fine, this is the likely cause and the fix. Your agent now picks whichever of the machine's advertised addresses it is genuinely allowed to use, instead of giving up when the first one in the list was not usable. When it still cannot reach a machine, it can now tell you which route was refused and why.

## Honest Scope

- This fixes **which** way to a machine gets chosen. It does **not** add the ability to send credentials over a plain-`http` Tailscale address — that needs the destination to prove who it is first, which is deliberately left for later and tracked as a commitment (CMT-013) rather than quietly assumed.
- The serving-lease path between machines is untouched by this change.
- One behaviour this does not promise: a way to reach a machine can be allowed and still be dead. Choosing an allowed rope is not the same as recovering from an unreachable one.
