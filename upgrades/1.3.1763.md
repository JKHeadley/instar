## What Changed

Test-only. No production code changes.

`tests/e2e/telegram-origin-notice-policy.test.ts`, "the production observer suppresses after … without consulting the failed workers": it waited for the notifier's CURRENT state to read `suppressed`. For a destination that is still listed but opted out or no longer owned, that state does not rest there while recording is healthy: the next five-second maintenance pass runs `recordingRecovered`, which clears the spent reservation and records `unavailable` / `destination-policy`. The case now reads the decision from the history of states the notifier reported (`onNoticeState`, already collected by the harness, now append-only): a `suppressed` state was reported after the hold notice was requested and no state since was an attempt. It then asserts the resting state per variant (`suppressed` for `unreadable`; `suppressed` or `unavailable`, reason `destination-policy`, for `opt-out` and `ownership`).

`tests/e2e/telegram-origin-runtime-lifecycle.test.ts`, the `admission-unavailable` variant of "reconciles historical … without another notice": it asserted exactly one network call after the recovery pass. In that fixture recording is healthy and only admission fails, so a recovery pass can re-arm the notifier and the failed re-admission then raises a second hub alert 100 ms after the first; whether there were one or two calls depended on timing. The case now asserts exactly one call BEFORE the recovery pass, one or two after it, and for every call where it went (the operator hub, thread 7848) and what it said (the fixed recording-outage text). The `unknown-outcome` variant still asserts exactly one call, to thread 42. The session-notice and hub-send assertions are unchanged.

`TelegramOriginService` gave each recording stage a fixed budget: 250 ms to write evidence to the store, 500 ms to the spool, 1250 ms to a peer, 1000 ms each for verified evidence and admission. They were literals at the call sites.

They are now named (`ORIGIN_STAGE_DEADLINES_MS`, same values) and can be overridden per service through `OriginServiceOptions.stageDeadlines`, read at call time. A value is used only if it is a whole number of milliseconds from 1 to 60,000 (`ORIGIN_STAGE_DEADLINE_MAX_MS`); anything else falls back to the default for that stage. Nothing in production sets the option, so production behaviour is unchanged.

Tests: a helper, `allowSlowOriginRecording(service)` in `tests/helpers/telegramOriginStore.ts`, lifts the service budgets to 20 s per stage. Underneath them the store and spool have their own per-request deadline (2 s by default); the fixtures that pass storage options also raise that to the store's 30 s maximum (`SLOW_DISK_STORE_REQUEST_TIMEOUT_MS`), and the fixtures built through `bootTelegramOrigin` cannot, so for those the effective allowance is about 2 s (8x and 4x the 250 and 500 ms budgets). It is applied in the harnesses of the nine test files that Local Verify's records show failing or being retried on a held send with nothing broken: `telegram-origin-runtime-lifecycle`, `telegram-origin-notice-policy`, `telegram-deterministic-notice-origin`, `telegram-origin-browser-outbox`, `telegram-dashboard-edit-rejection`, `telegram-origin-enrollment` (e2e), `lease-renew-unreachable-peer-sends` (integration), `transport-deadlines` and `late-capacity` (unit, the latter through its shared harness helpers, which also serve the integration and e2e late-capacity files: eleven test files change timing in all).

The per-stage recording budgets of `TelegramOriginService` (250 ms store, 500 ms spool, 1250 ms peer, 1000 ms verified evidence, 1000 ms admit) move to a small import-free module, `src/messaging/telegram-origin/OriginStageDeadlines.ts`. It adds a process-wide default: `setOriginStageDeadlineProcessDefaults(partial | null)`. A stage's budget resolves as the service's own `stageDeadlines` value when valid, else the process default when one was set, else the production budget (`resolveOriginStageDeadline`). `TelegramOriginService.ts` re-exports the moved names, so existing imports are unchanged.

`tests/vitest-setup.ts` sets all five stages to 20 s for every test file.

Production behaviour is unchanged: nothing under `src/` calls the setter, and a unit test scans the source tree to keep it so.

## What to Tell Your User

Nothing changes in the product. Two automated tests that failed at random on a busy machine, and blocked unrelated changes from merging, now check the same behaviour in a way that does not depend on timing.

Nothing changes in the product. Some automated tests about Telegram message recording failed at random on a busy machine because they allowed a disk write a quarter of a second; those tests now allow it longer, so a slow machine is no longer reported as a broken one.

Nothing changes that you will see. This stops a family of tests from failing unrelated changes when the test machine's disk is busy.
