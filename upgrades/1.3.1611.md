## What Changed

- When a machine does not answer, the dashboard's note about it (on Sessions, Schedule and the home screen) now links to the Machines page, where that machine's state is shown.

- The home screen now asks each machine only for its open alerts instead of its whole history, which was over a megabyte on one machine and made that machine miss the time limit.
- The dashboard home screen no longer says "part of the list could not be checked" when one machine misses a single refresh. For up to two minutes it shows that machine's last answer while it asks again; a machine that stays silent longer is reported as before.

- The automatic merger no longer stalls behind a pull request it has given up on. Each round it moves past PRs it cannot act on (given up, or waiting before a retry) to the next-oldest ready one, still making at most one merge attempt per round.

- A session's History on the dashboard now continues past the start of the current session into the conversation's earlier messages, back as far as the message log goes. The topic-messages route accepts a `before` time to page backwards.

- The "The session has stopped. Send a new message to start a fresh session with full conversation context." notice is now sent at most once per unanswered user message, across server restarts. A small ledger (`state/session-monitor-dead-notified.json`) remembers the user message each notice answered; a dead session with no newer user message is never announced again. Before this, the repeat guards lived only in memory, so every restart re-announced the same death.
- Slack: the session monitor no longer treats every channel message as coming from the user. The agent's own posts (its notices included), other bots, people who are not authorized, and chatter the agent deliberately did not take in a mention-only channel no longer count as "a user is waiting". Before this, the agent's own notice counted as a new user message, so the notice re-armed itself and was posted again and again.
- Telegram: same notice ledger applies. A topic whose session dies again later, after a newer user message, is still told.

- The agent no longer sends a name probe into the General topic, and no longer repeats a probe Telegram refused (a deleted topic) at every server start; it waits a week. This removes about 190 refused sends a week on a busy agent.

## What to Tell Your User

"This machine did not answer" notes now link straight to the Machines page.

The "part of the list could not be checked" message now only appears when one of my machines is really unreachable, not every time one is briefly slow.

Finished changes merge on their own again even when an old, stuck change is at the front of the line.

Scroll up in a session's History and it keeps going into the earlier part of the conversation, not just the current session.

If your agent kept posting "The session has stopped" in a Slack channel over and over, that stops after this update. You will still get the notice once if you message the agent and its session has really stopped.

Fewer failed messages in the message records: the agent stopped repeatedly poking topics that Telegram refuses.

## Evidence

- A scan of every dashboard page for failure wording without a link found only the Sessions page's unanswered-machine lines; Schedule and the home screen use the same wording. Unit tests cover which notes get a link.

- On a live agent the full pooled read missed the Laptop in 2 of 10 tries (it sent 1.5 MB of mostly closed alerts). Asking for open alerts only cut that to 140 KB and the read to 0.1–0.7 s. Unit tests cover the merge, the two-minute limit, and failures that name no machine.

- On a live agent, a PR given up on since Oct 26 was the oldest ready one; rounds picked it and stopped, so a fix that passed its checks at 20:10 waited until 20:46. Unit tests cover the skip, and that a real attempt still ends the round.

- History for a topic that began on Oct 20 stopped on Oct 31, where its current session started. Unit and integration tests cover the backwards paging (including very large log files and characters split across read chunks) and the route's new `before` parameter; the dashboard keeps only strictly older messages, so an older server cannot cause repeats.

- Live symptom (2026-11-02): a Slack-only agent posted the notice in one channel about a dozen times in one morning, usually twice in a row, and the day before as well. Read-only inspection of that agent: one machine, about 69 server restarts since the evening of 2026-10-31 (auto-applied updates), mention-only channel, dead channel session, no new message in that channel — each restart's missed-message replay refilled the history with older chatter that counted as a waiting user.
- Unit tests (`tests/unit/session-monitor-dead-notice-once.test.ts`): 12 simulated restarts with no new user message post exactly one notice (was 12); the agent's own notice echoed back by Slack does not re-arm it; mention-only chatter is not a waiting user; a newer real user message is still announced; a corrupt ledger starts empty. The tests fail on the previous code.

- On a live agent, 190 refused sends in a week came from repeated probes of three topics, one per server start. Unit tests cover General being skipped, a refusal being remembered across a restart, and a network failure not being remembered.
