## What Changed

The dashboard PIN unlock (`POST /dashboard/unlock`, reachable over the public tunnel) had two weaknesses found by the security program: every tunnel request looked like it came from the same place (the local tunnel software), so a stranger's wrong guesses shared — and could exhaust — the owner's rate limit (an owner-lockout denial of service); and the only brute-force brake was one weak pooled attempt cap.

The fix (`src/core/PinThrottle.ts`, `src/server/pinUnlockMarker.ts`, wired into the unlock handler) keys the limit to each real visitor's address (read from a header trusted only when the request genuinely came through our own cloudflared), lets any browser the owner has unlocked before in instantly via a signed, httpOnly, agent-bound cookie, puts a hard cap on unknown guessers that an address-rotating botnet cannot evade, exempts genuinely-local requests so the owner at the machine is always let in, and raises one plain-words owner alert when an attack drains the cap. Ships enabled; `security.pinThrottle.enabled: false` restores the old behaviour.

Instar's model registry now lists Google's Gemini 4 Carbon and Gemini 4 Hydrogen on the Gemini door, as recognized but not promoted, next to Gemini 4 Argon. Both were live-checked on 2026-11-15 through the Gemini API and answered. No default model, tier or pin changes. The daily frontier-model check found them.

## What to Tell Your User

In normal use nothing changes — unlocking with the right PIN from any browser you've used before is exactly as fast as before. A stranger can no longer lock you out by guessing, and guessing your PIN is now genuinely hard. If an attack is ever under way and you reach for a brand-new browser you've never unlocked, you might be asked to wait a few minutes — just unlock from a browser you've used before, or from the machine itself (the local dashboard or the paired phone app). You'll get one plain-words heads-up when an attack is happening.

Nothing changes for you. Instar now knows about two newer Gemini models; it keeps using the same defaults until a new model proves itself.

## Summary of New Capabilities

- Per-client dashboard-PIN throttle keyed on the real client, with a known-browser (signed-cookie) bypass, a hard cap on unknown guessers, a genuinely-local exemption, and a plain-words owner alert. Configurable under `security.pinThrottle`.

None.

21 unit tests green (throttle logic + the signed cookie marker); 0 type errors; an in-process behavioral probe against a real AgentServer passed all checks (correct PIN 200 + cookie, stranger refused after the cap, cookie-owner unlocks while the cap is drained, local request exempt, plain-words alert fires, malformed cookie never 500s). Integration + e2e "feature is alive" tests ship with the change. Design converged across 6 cross-model review rounds (GPT-6 + Claude clean-door); spec docs/specs/dashboard-pin-throttle.md.

The models endpoint lists both. A trivial generateContent call returned "OK" from each (2026-11-15, paid Gemini key). The registry lint passes.
