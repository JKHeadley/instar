## What Changed

SEC-134. In the public relay's A2A bridge (`src/threadline/relay/A2ABridge.ts`), the per-address rate-limit windows and the contextId-to-thread map never shrank, and the map was keyed by the bare contextId, so any caller who knew a contextId joined that thread. Now:
- `A2ABridgeRateLimiter` deletes a window once it is empty, never creates a key on a check alone, sweeps keys idle for an hour at most once a minute, and keeps at most 50,000 keys. The forwarded caller address is used only when it is a valid IP.
- `ContextThreadMapper` keys by caller address, agent and contextId, keeps at most 10,000 entries (least recently used dropped first), expires an entry 24 hours after its last use, and does not store messages without a contextId.
- A contextId that is not a string or is longer than 256 characters is refused with JSON-RPC error -32602.

This runs on the relay, so it takes effect when the relay is redeployed.

The disk steward now measures the npm cache again after `npm cache clean`, and records what actually left. Before, an npm error recorded 0 freed even when nearly all of the cache was gone. On the Studio, 13.7 GB went to 0.34 GB and was recorded as 0.

Two false alarms on a fresh agent (seen on every Windows-app agent, and on any agent without Telegram):

- **"Health: Degraded" from the first minute.** Server-down recovery reads the host's sshd key (`/etc/ssh/ssh_host_ed25519_key.pub`) at every start and reported the degradation `ServerDownRecovery.hostSshKey` whenever it could not, which turns `/health` to `degraded`. When the key file does not exist (no SSH server on this machine), the direct SSH recovery route is now recorded as not applicable: no degradation, and the `multiMachine.serverDownRecovery.enabled` entry in `GET /guards` carries `directSshRoute: "not-applicable"` (or `available` / `unreadable`). A key file that exists but cannot be read is still reported as a degradation, now with the error code in the reason.
- **"Scheduled jobs keep failing".** The `dashboard-link-refresh` job (every 15 minutes) called `POST /telegram/dashboard-refresh`, which answered 503 when Telegram was not configured, so the job failed four times an hour. With no enabled Telegram entry in the agent's messaging config, the route now answers 200 `{"action":"skipped","reason":"telegram-not-configured"}` and the job's existing script exits 0. Telegram that is configured but not running still answers 503, so that real failure keeps reporting. No job definition changes, so existing agents get this with the update and no migration.

The "Link this computer to your phone" screen on a document page is rewritten. It says up front what linking lets the computer do (open, read and comment on your documents for 30 days without signing in again; only documents you can see; removable any time under People → Linked computers), then gives five numbered steps that name the iPhone app's exact buttons: Open Instar, tap "People", tap "Link a computer", scan the code, check the code matches, tap "Link for 30 days" and confirm with Face ID. Phones without the People button are told to update the app or open any document and tap "Open on a computer". The scan code is large and centred in its own card with the check code under it; steps and code sit side by side on a wide screen and stack on a narrow one.

Same-agent messages (`POST /messages/send` with `to.session`) now reach the session that holds that role now, even after it came back under another name, such as `echo-echo-x` after a respawn or `echo-topic-N` after a reboot.

**How a session is chosen.** The resolver tries, in order:

1. the exact name;
2. the conversation (topic) the old name served;
3. the same stored name, for roles with no topic;
4. the same name with a doubled prefix collapsed.

It delivers only when exactly one running session fits. If two fit, it refuses and names both. It never types a message into a session that started after the message was written.

**Retries** stay on the session chosen first. If that session has since been replaced, the retry stops with the reason `resolved-session-ended`.

**Notices to the sender.** When a message can't be delivered, the session that sent it gets one notice. A notice lists the failed messages and why, and is marked as quoted data. A sender gets at most one notice per minute. Senders that aren't sessions are counted under `undelivered` in `GET /messages/stats`.

**Changes to `/messages/send`.** The server now sets `from.agent` and `from.machine` itself, and keeps what the caller sent in `from.requested`. The route refuses a caller-made `delivery-notice`.

**Session names.** New sessions whose name already starts with the agent's name no longer get the prefix twice.

**Retry scope.** Retries now touch only messages addressed to this machine. Before, the sending machine's own copy of a cross-machine message was retried into a local session with the same name.

Same-agent messages to a session on another of the agent's machines now reach that session. Before, they never did, for two reasons:
- since August, the sender posted to an address the other machine no longer serves;
- even before that, the receiving machine stored relayed messages and never typed them in.

**Sending.** A message waits as `relaying` while its machine's queue makes one pass over that machine's addresses. It ends:
- `received`, when the other machine confirms with a signed receipt;
- `failed` with the reason, when the other machine refuses it with a signed reason or can't be reached right now.

**Receiving.** The receiving machine checks that the message really came from this agent's own machine before storing it. It types the message into the session holding that role, and never into a session that started after the message was written. If delivery fails there, it sends a signed notice back, and the sending session is told. A machine that stops in the middle of typing a message never types it again; it reports the outcome as unknown.

**Compatibility and clean-up.**
- The old address keeps working for older senders.
- Session messages are no longer written into a folder nothing reads.
- Retries for a machine that is asleep come in a later release.

- Needs-you strip (dashboard): closed by default as one line (tone dot, "Needs you · N" / "N+", first need on one line); opens to the full list with paging, could-not-check sentences at its bottom, and "Hide". The badge reads "N+" for "at least N". Matches the Instar app's build-120 line.
- Unnamed conversations: a Telegram topic with no stored name shows its Chief of Staff project title in the app's conversation list (`GET /mobile/conversations`), conversation search, and the dashboard (`GET /telegram/topics?scope=pool` now carries `fallbacks`). A stored name always wins; the title is never saved as the topic's name.

Overview: `docs/specs/needs-compact-and-name-fallback.eli16.md`.

The agent-home worktree reaper's removal moves off the server's main thread. When removal is live, a niced background child does both the evaluation and the removal, and the server only starts it and reads its results.

- **Supervision.** One child runs at a time. It holds a lock and writes durable rows. Its runner owns the process group, scans asynchronously, adopts the child after a restart, and kills it at the deadline.
- **Removal order.** Each checkout is re-evaluated, archived and re-checked, then renamed into `.worktrees/.trash`, then git's record is pruned, then the trash is deleted through a guarded subprocess. An interruption leaves the checkout either intact or only trash.
- **Closed PRs.** A closed-unmerged PR's checkout counts as finished only when its exact head commit is still on GitHub's PR ref.
- **Cadence.** The reaper checks hourly instead of daily. A run-once migration moves the exact old 24 h default.

Removal stays `dryRun: true`.

One session's `Login expired` screen no longer benches a working subscription account (spec `docs/specs/stale-process-login-expired.md`).

- Before the quota poller marks an account `needs-reauth` because one Claude Code session showed the CLI's expired-login line, it tests the stored login with one contained real call (`src/core/freshLoginProbe.ts`). The call uses no tools, MCP servers, hooks, settings sources or transcript; credential and provider environment is stripped; and the verdict comes from the CLI's structured result (`apiKeySource: none`, `served_by_anthropic: true`).
- If the stored login answers, the account stays usable, and the stuck session is restarted on its OWN account (`SessionRefresh`, conversation resumed), never swapped to another account. If the call is refused, or cannot run, today's mark-and-swap path is unchanged.
- A hold created before the update, or before a probe answered, is released when a validated `ok` lands. The reissue sweep then closes the stuck re-sign-in it caused.
- Bounds: at most 6 probes per account per 12 h (persisted in `state/fresh-login-probe.json`, reserved inside the host spawn cap); never inside the 15-minute token-expiry margin; backoff and a 24 h breaker for inconclusive results; at most 3 in-place refreshes per account per 10 min. Each probe records one `QuotaPoller.freshLoginProbe` feature-metrics row.
- NeverSilent holds an automatic swap or engine move for at most 3 minutes per incident while that check or restart is under way, and sends a plain waiting notice instead.
- Live switch `subscriptionPool.freshLoginProbe.enabled` (default on; `false` restores the previous behaviour exactly).

A machine that lost part of its Telegram message log (the 2026-11-20 Mac Studio rebuild lost about 14,000 messages across 167 topics) had no supported way to put the history back. `POST /topic/rebuild` only replays the live log, and appending old rows to the live log makes old messages look like the newest ones, both to the search index and to the background readers that tail the log.

New `POST /topic/import` (agent bearer token only; a paired phone gets 403). It takes a recovered JSONL file inside the state folder, or inline rows. It checks each row against the store's own schema and keys Telegram ids by the existing key rule, skips any message already held, and publishes the accepted rows as one immutable batch under `.instar/topic-history-imports/`. It never writes the live log. Then it re-sequences each affected conversation so restored messages sit at their message time, with the newest real message still last. The search index is updated, and every run writes an audit line to `.instar/logs/topic-history-imports.jsonl` (counts only, no message text). Boot and `/topic/rebuild` re-apply the batches the same way, so a restore survives a rebuild. A second identical import does nothing. `dryRun: true` reports without writing.

Restored rows are labelled `origin: imported`. They never count as a fresh instruction from the owner: forwarded provenance is narrowed to unknown, and the user corpus labels them `recovered` with no authority. Messages typed in the Instar app (`app:` ids) are refused, because the app keeps its own copy of them. A live copy of a restored message replaces the restored copy when it arrives. The peer row carrier never carries a restored row.

## What to Tell Your User

- **Relay hardening**: "The public relay now forgets old callers and old conversation names, so it cannot be made to run out of memory, and one caller can no longer join another caller's conversation."

Nothing to do. Disk cleanup reports now show the real amount freed.

- **No more false health warnings on a new agent**: "If you set me up without Telegram, or on a computer without remote login, I no longer show a 'degraded' health status or 'scheduled jobs keep failing' for features that don't apply to you."

Linking a computer to your phone is now spelled out step by step on the screen with the code: it tells you what linking lets the computer do, and exactly which buttons to tap in the Instar app (People, then "Link a computer").

- **Messages between my sessions survive restarts**: "When one of my sessions restarts under a slightly different name, the others' messages still reach it, and if a message truly can't be delivered, the session that sent it is told."

- **My machines can pass work to each other's sessions**: "When a session on one of my machines hands work to a session on another, it now actually arrives, and if it can't, the sender is told."

"Needs you" is now a single calm line at the top; tap it to see the list. Conversations that lost their names show their project's title instead of "Name not available yet".

Nothing to do. Cleaning up the agent's old working copies can no longer freeze the agent. Real removal stays off until it is approved.

If one of your conversations got stuck showing an expired sign-in while the account itself was fine, the agent no longer takes the whole account out of use or starts a sign-in that keeps restarting. It checks the account's saved sign-in first, and if that works it just restarts the stuck conversation on the same account. Nothing to do.

- **Lost conversation history can be put back**: "If a machine ever loses part of our conversation history, I can now restore it from the copies my other machines kept. The restored messages slot back into each conversation at the right time, search finds them again, and your newest messages stay at the bottom."
