## What Changed

A machine that accepts a forwarded Telegram message now records the original inbound key before answering, so its reply can close the router's open record. Recovery checks pooled topic history and prior ownership before considering a replay. A possible earlier reply or an incomplete peer read holds the message for verification. A new session receives pooled conversation history and a clear warning if some history may be missing. Echo can reconcile an old stuck row against a reviewed exact reply through a loopback-only audited route.

A machine that gains the lease now starts scheduled jobs through a bounded planned restart. A machine that loses the lease pauses jobs immediately, including when a preferred-machine hint is configured.

Updates now add missing shipped legacy jobs before migration. Git-sync stays disabled unless an operator explicitly enables it, even when the project has a Git remote.

Telegram PDFs now reach a privacy-on session's own inbox. Generated long-message files have their attachment references rewritten to point at that inbox. The copy checks that the server recorded the file for this conversation, verifies its canonical path, and rejects symlink escapes. A failed file read is described as a problem with that file and retried once.

When a new agent pairs its second machine for the first time, sharing now turns on by itself. Both machines get the same settings, the first restarts once, and the bot token reaches the new machine sealed inside the pairing, so it can answer on Telegram from its first start. After the pair has looked healthy for ten minutes, a new conversation can start on either machine. Nothing already running moves.

It stays off when the owner has already set anything about sharing, has set `multiMachine.sessionPool.autoActivate` to false, or uses paid routing. The pairing still works, and the readiness report says why. Agents that exist today do not change on update.

## What to Tell Your User

A temporary machine connection problem will no longer make me answer an old topic message again without checking the previous machine. If I cannot confirm the earlier conversation, I will wait instead of telling you the message was unanswered.

Scheduled jobs now follow the machine holding the lease. If a standby takes over, it starts its scheduler after a planned restart; the former holder stops admitting jobs.

Updates can restore missing built-in scheduled jobs without replacing local edits. Git-sync stays off unless you explicitly enable it.

With memory privacy on, you can send a PDF or another file to your agent. If a particular file cannot be opened, the agent will name that file and ask you to resend it.

From the app's Passwords & keys screen you can now ask for a password or key, and cancel a request that's waiting. Each one needs Face ID. The app never holds the link: open the console to copy or share it. This is on for development agents and off for others until it's promoted.

If you add a second machine, it will start sharing conversations with the first by itself. Nothing changes for an agent on one machine, or for an agent that already has several machines.

## Summary of New Capabilities

Cross-machine replies now carry the original message key. Legacy stuck rows can be reconciled against exact replies without replay.

- The lease holder starts scheduled jobs even when a preferred-machine hint is configured.
- A demoted machine pauses jobs before it can launch new work.

- Missing shipped legacy jobs are added during update.
- Existing custom jobs and disabled settings remain intact.
- A Git remote alone cannot enable git-sync.

Privacy-on sessions can access recent PDFs sent through Telegram and files referenced inside long Telegram or Slack messages without broadening the session's file permissions.

- `POST /mobile/secrets/requests` and `POST /mobile/secrets/requests/<key>/cancel`: owner phone only, each with a fresh Face ID proof, behind `mobilePairing.permissionActions`.
- `GET /mobile/secrets` now says what the phone can do here (`actions`).

| Capability | How to Use |
|---|---|
| Sharing starts at the first pairing | automatic; `GET /session-pool/readiness` shows why it is or is not on |
| Opt out before pairing | set `multiMachine.sessionPool.autoActivate` to false |
| Recover a token that did not arrive | pair the same machine again |
