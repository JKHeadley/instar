## What Changed

- Pairing a phone without Telegram (docs/specs/mobile-native-conversations.md §4.4): on an agent with no Telegram owner and native app conversations on, a phone that opens a pairing link is told to confirm on the dashboard. Its 6-digit code is kept only in the server's memory and shown on the new dashboard **Phones** tab, only after a PIN unlock (`GET /mobile/pairing-approvals` with a dashboard operator session; the API token alone cannot read it). The operator types it into the app or taps "Not my phone" (`POST /mobile/pairing-approvals/:id/decline`). The phone is recorded as approved on the dashboard (`approvedVia: dashboard-pin`). Such a pairing is not cancelled by a serving-lease move; a server restart still cancels it. Agents with a Telegram owner keep the private-chat code exactly as before.
- Push without Telegram (§4.7): every agent reply in an app conversation sends one push to paired phones ("New reply", naming the conversation, never its text), through the existing push limits, and is passed to the agent's other machines so phones paired there hear it too.
- New CLAUDE.md section "Pairing a phone without Telegram" for new and existing agents.

## What to Tell Your User

If I run without Telegram, you can still add me to the Instar iPhone app: open the pairing link I send on your phone, then open my dashboard's Phones tab, unlock it with your PIN, and type the code it shows into the app. You also get a notification on your phone whenever I reply in one of the app's conversations.

## Summary of New Capabilities

- Dashboard Phones tab: waiting phone, its code (after PIN unlock), decline, paired phones and removal.
- `GET /mobile/pairing-approvals`, `POST /mobile/pairing-approvals/:id/decline` (dashboard operator session only).
- Push notification for every agent reply in an app conversation, with or without Telegram.

## Evidence

- Unit tests: the reply push payload carries the conversation and "New reply" but never the text, one push per reply with dedupe and folding; lease loss keeps a dashboard-path pairing and its code; the Phones card shows the code only after unlock and renders names as text.
- Integration tests on the real routes: redeem answers `approval: "dashboard"`; the code route refuses the token alone, a wrong session and a device, and answers an operator session; confirm records `dashboard-pin` with no lease; wrong codes and dashboard decline still cancel; a restart empties the card; a Telegram owner keeps the private-chat path; with native conversations off the old refusal is unchanged; the plaintext code is never written to disk.
- End-to-end on an agent booted with no Telegram and no Slack: PIN unlock, pair through the dashboard, create a conversation, send a signed message, the session's app-reply is accepted, one push goes out naming the conversation, and history reads `originVerified: "verified"` with `originApprovedVia: "dashboard-pin"`.
