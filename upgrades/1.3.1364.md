## What Changed

GitHub Actions concurrency is allotted **per account, shared across every repository the
owner has** — not per repo. Measured on 2026-10-20:

    JKHeadley/instar-2   10 jobs running, 25 queued
    JKHeadley/instar      0 jobs running, 21 queued

So this repo ran at roughly 3 concurrent jobs against a 20-job allowance. One pull request
here needs 8 unit shards (`node-version: [20, 22]` x `shard: [1..4]`), which is why a heavy
`CI` run took **17-19 hours** end to end and a two-file test-config fix sat **3h54m** in the
queue before its first job started.

Part of that is genuine contention between two projects and is not fixable here. The
*avoidable* part is supersession: `ci.yml` declared **no `concurrency` block at all**, so every
push to a branch started a NEW 13-job run while the previous run kept consuming shared slots.
`pull_request_review` is also a trigger, so approving a pull request spawned another full
13-job run alongside the push run. Nothing superseded anything.

The cost showed up as manual labour: **126 stale runs had to be cancelled by hand in one
night** to let a single-line fix reach a runner. A superseded run is waste by definition —
nobody is waiting on its result.

This adds a top-level `concurrency` block:

- **Grouped by pull-request number AND event name.** The event name is load-bearing, not
  decoration. `pull_request_review` is one of this workflow's triggers, so a review event sharing
  a group with the push run would mean **approving a pull request cancels its in-flight required
  checks** and restarts them from zero — trading avoidable waste for a footgun. Scoping by event
  means push runs supersede push runs (the actual problem) while a review run can never cancel
  them. Falls back to the ref for pushes to `main`.
- **Known, and deliberately left alone:** a review event therefore still starts its own run, so
  approving a pull request costs a duplicate 13-job run. Narrowing that needs job-level `if:` on
  the heavy jobs — and a job skipped by `if:` reports as **success** to required status checks,
  which would let a review-triggered run paint a pull request green without the tests having run
  on that commit. That is a safety hole, so it belongs in its own carefully-designed change, not
  slipped in beside a capacity fix.
- **`cancel-in-progress` excludes `main`.** A blanket `true` would be wrong: main's
  post-merge run is the release gate and its record is the evidence a merge was sound. Only
  branch and pull-request runs supersede.

`tests/unit/ci-workflow-concurrency.test.ts` makes it an invariant rather than a decision
someone has to remember — removing the block, dropping `cancel-in-progress`, or letting it
cancel `main` all fail the suite. It also pins the unit matrix at 8 shards, because that figure
is what makes one pull request cost ~2h of shared allowance; if it grows, the capacity question
has to be re-opened deliberately rather than by drift.

- **An invite waiting for approval leaves a notice when a restart clears it.** The recipient side of invite pairing keeps a pasted or forwarded invite in memory only, so its secret never reaches disk. A restart used to drop it silently. Now a marker with no secret in it (a hash of the invite id, the claimed agent and owner names, the expiry) is written to `threadline/pairing-pending-accept-markers.json` (0600) while the invite waits, and deleted when it is approved, declined or expires. On startup, an unexpired marker becomes a notice: at the top of the dashboard pairing card (`GET /threadline/pairing/invites` → `restartNotices`, dismissed with `DELETE /threadline/pairing/restart-notices/:id`), and one Telegram message to the operator naming the agent and the expiry in the owner's time zone when their user profile has one (UTC otherwise). The notice ends when the invite is pasted again, dismissed, or expires. Spec: `docs/specs/a2a-pairing-invite-link.md` §8.
- **The auto-updater holds its restart while an invite waits.** `UpdateGate` gains restart holds (in-flight work a restart would lose rather than resume), and `AutoUpdater.gatedRestart` defers through its existing durable deferral record and retry timer while any hold is in force. Each hold ends at its invite's expiry, or sooner (see below); the re-check runs every 5 minutes or at that expiry, whichever is first. The reason is logged and shown in `restartDeferral`. A manual `POST /updates/apply` is not held.
- **An invite claiming more than 24 hours of life is refused on receipt.** No real invite can (the inviter's engine caps it at 24 h), but nothing checked the expiry an incoming invite carries. Now an invite expiring more than 24 h + 5 min ahead is refused before it is held, with the reason "this invite claims to stay valid for longer than 24 hours, which no real invite does". The restart hold is also capped at 24 h from when the invite arrived and at the updater's existing `maxDeferralHours` (4 h).
- **The dashboard's "Could not reach the agent" error clears itself** on the next refresh that reaches the agent, instead of staying until a page reload.

Messages to agents you've paired with (by invite) are now always encrypted, on every agent. Before this release it was switched off except on development agents.

- `threadline.encryptToPinned` now defaults to on (enforce) for every agent. Ordinary chat to a peer paired by invite is always encrypted to the key you confirmed when you paired, never sent unencrypted. If that cannot be done, the message is not sent and the sender gets an error.
- `threadline.refuseDowngrade` is now on in watch mode for every agent: it notes which paired agents have sent encrypted messages and counts unencrypted ones it would have refused, but still delivers them. It does not refuse yet, because a paired agent on an older Instar can still mix encrypted and unencrypted messages. When it does refuse (an owner can set `dryRun: false`), it says why, says what to do, and tells the sender once an hour with an encrypted notice. It is never silent.
- A multi-machine agent that has not turned on pairing replication is warned at start: its other machines do not yet know the pairing.

Existing agents with these settings in their config keep them. Agents without them get the new defaults.

threadline-mcp 0.6.0 labelled every ordinary message it sent as `chat`. Instar agents read that label as the kind of request being made, and their list of what a trusted agent may do says `message`, not `chat`. So an Instar agent with verified pairing turned on refused every ordinary message from a threadline-mcp agent, including encrypted messages between agents that had paired, and credentials. The sender was not told. It looked as if the message had gone through.

0.6.1 labels ordinary messages and credentials `message`, the same label Instar uses for its own. This applies to all three ways a message leaves: encrypted to a paired agent, a credential to a paired agent, and plaintext to an agent you have not paired with.

Receiving is unchanged. A message labelled `chat` from an older threadline-mcp is still read as an ordinary message, an older credential is still a credential, and encrypted `chat` from a paired agent still counts as that agent having spoken to you encrypted.

Every `vitest*.config.ts` now sets `css: { postcss: {} }`. Vite skips its parent-directory PostCSS search, which aborted on EPERM when the feedback executor's sandbox read-denies the agent home around the fix workspace. Before this, the canary's `base-unit-smoke` probe failed on any agent whose home is an instar checkout, so every executor attempt would have stopped as `profile-unenforceable`.

## What to Tell Your User

Nothing user-visible. Finished work reaches a runner sooner because the project stops spending
its shared build capacity on runs that have already been replaced.

If you paste or forward a pairing invite and I restart before you approve it, the invite is lost, because I never write its secret to disk. I will now tell you when that happens, on the dashboard and in Telegram, and say when the invite stops working, so you can paste or forward it again in time. I also wait to install updates while an invite is waiting for you, up to when that invite expires.

Messages to agents you've paired with are now always encrypted. You don't need to do anything. If your agent runs on more than one computer, it may tell you to turn on pairing sharing so every computer encrypts.

If you paired your agent with an Instar agent and your messages seemed to go nowhere, this fixes it. Messages from your agent now reach Instar agents. There is nothing to set up and you do not need to pair again.

## Summary of New Capabilities

None. This is a build-capacity repair plus the test that holds it in place.

- `restartNotices` on `GET /threadline/pairing/invites`, and `DELETE /threadline/pairing/restart-notices/:id`.
- `AutoUpdater.setRestartHold(key, provider)` / `UpdateGate.setRestartHoldProvider` and `getActiveHolds`.
- A one-time Telegram notice for an invite a restart cleared.

- Encryption to paired peers is on by default for every agent.
- Unencrypted messages from paired agents that have encrypted before are tracked per agent on `/health`; when refused, the refusal is logged with a reason and a fix, and the sender is told.

- None. A fix: ordinary messages and credentials from threadline-mcp are accepted by Instar agents that enforce verified pairing.

## Evidence

**Reproduction.** Open any pull request against `main`, then push a second commit to the same
branch before its `CI` run finishes. Observed before this change: the first run stays
`in_progress`/`queued` and the second run starts alongside it, so one branch holds two full
13-job runs. Approving the pull request adds a third, because `pull_request_review` is also a
trigger.

**Observed before (2026-10-20, PR 2216 — a two-file test-config fix):**

- CI run created `22:52:17Z`; its first job reached `in_progress` at `02:46:27Z`. **3h54m
  queued**, with all 13 jobs reading `queued` throughout.
- Account-wide concurrency at `02:50Z`: `instar-2` 10 running / 25 queued, `instar` 0 running /
  21 queued. Allowance for a free public repo is 20 concurrent jobs, so this repo was getting
  roughly 3.
- Measured throughput across two real runs' job start/complete timestamps: **~3.8 unit shards
  per hour**, against 8 shards per pull request.
- A heavy `CI` run created `05:20:01Z` concluded `00:04:40Z` — **18.7h** creation to conclusion,
  its 13 jobs dripped through shared slots rather than sitting unscheduled.
- **126 stale runs were cancelled by hand** across that night to get a single-line fix to a
  runner. Those cancellations are the manual cost this block removes.

**Observed after.** Not yet observable in production: the superseding behaviour is enforced by
GitHub when the block is present, and this change has not merged. What IS verified here is the
configuration itself — `tests/unit/ci-workflow-concurrency.test.ts` passes with the block (4
tests) and fails without it (3 of 4, by assertion message, not by crash). The production
check, once merged, is that pushing twice to one branch leaves exactly one live `CI` run.

**Not claimed.** This does not fix the cross-project contention, which is the larger half of
the delay and is not a `ci.yml` matter: two projects share one account's allowance with no
arbitration between them.

- `tests/unit/threadline/pairing-pending-accept-markers.test.ts`: the marker file holds neither K, S, the invite text nor the invite id (checked in hex and base64, mode 0600); approve, decline and expiry delete it; a failed send keeps it; a restart yields the notice with the invite's expiry and one Telegram message; after expiry the marker is gone and there is no notice; re-paste and dismiss end the notice.
- `tests/unit/AutoUpdater-restart-holds.test.ts`: the restart is held while an invite waits, on the existing durable deferral, and released when the accept finishes or the invite expires; a manual apply is not held; a run against the real invite engine.
- `tests/unit/dashboard-pairing-panel.test.ts`: the notice sits at the top; the connection error clears itself when the agent answers again; other messages stay.
- `tests/e2e/threadline/pairing-invite-production-path.test.ts`: two real agents on a real relay; the recipient's server and Threadline are restarted on the same state dir; the notice appears with the right expiry, and re-pasting restores the invite.

- Unit tests for the defaults, the upgrade path (no value gets the default; an explicit off or watch is kept) and dev and non-dev agents.
- An end-to-end test on a real relay with three agents: an enforcing agent refuses a paired agent's unencrypted message, records why, and sends it an encrypted notice, while an unpaired agent's unencrypted message is still delivered.

- `tests/e2e/threadline/standalone-instar-pairing.test.ts`, new case: a threadline-mcp agent pairs with a real Instar agent whose verified pairing is on, live and enforcing credentials. Instar's real inbound gate lets through both an ordinary message and a credential from it. With the label put back to `chat`, the gate refuses both (`insufficient_trust ... op=chat allowed=[ping,health,message,...]`) and the test fails.
- `tests/unit/threadline-core/standalone-pairing.test.ts`: all three send paths carry `message` (each one put back to `chat` on its own fails the test), and incoming `chat` and `message` are both handled as ordinary chat, encrypted and plaintext, with the encrypted-chat mark set for both.

On the Mac Studio, using the server's own `SandboxRuntimeRunner` and `runRunnerCanary`, the runner canary had 27/28 probes passing and `base-unit-smoke` failing: exit 1, `EPERM ... open '<agentHome>/package.json'`. With this config the same confined `npx vitest run --no-cache tests/unit/feedback-factory/triage-floors.test.ts` exits 0 with 47/47 tests passing. Outside the sandbox, the unit, integration and e2e configs still run.
