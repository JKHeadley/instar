# A session keeps the name of the conversation it serves

The dashboard and app sometimes showed “Conversation name unavailable” for a conversation the operator already knew. The session was still running and still routed messages correctly. Its display name was the broken part: the list looked only at an adapter's current title cache and discarded a meaningful saved session name when that cache was empty. A replacement session could also change the reverse binding that the dashboard used to find the title. Pool aggregation repeated the same formatting and could erase a name a peer had already supplied.

The fix reads the conversation's durable records using its identity. Telegram titles come from the adapter, persisted topic-name registry, or topic metadata, independently of which session is currently bound. App aliases resolve to the app conversation store; Slack aliases resolve to the channel registry and conversation label. Scheduled runs use the job definition's name. Both the dashboard WebSocket list and app HTTP list use this same resolver. Pool reads preserve valid peer names and can recover Telegram titles from the receiving machine's catalog. Negative app and Slack aliases are never described as Telegram topics.

A genuinely unknown conversation still says its name is unavailable. Routing numbers and generated topic keys do not become pretend names. This change only reads existing state; it adds no session launches, routing decisions, migrations, or remote lookups. A normal revert completely removes it. Regression tests cover stale bindings, renames, saved titles, app and Slack aliases, jobs, pool reads, and production HTTP/WebSocket wiring.
