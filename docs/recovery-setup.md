# Recovery setup

Recovery remains visibly incomplete until each paired target has two fresh peer-observed proofs. Normal work continues while setup is incomplete. A configured key, service, or successful local health check does not qualify either route.

Open `/dashboard/recovery.html` on the agent’s secure dashboard address and unlock with the existing dashboard PIN. Prepare the machine, review its paired-machine recovery scope from the enrolled phone, then finish verification. The phone can enable or turn off the direct and relay routes separately, remove a source machine’s recovery access, or disconnect its own signing key. Ordinary machine grants never clear an explicit route removal. Removal stays pending until the target acknowledges the signed checkpoint. A disconnected target may retain its previous grant for at most the 24-hour offline lease; the interface never promises instant revocation across a partition.

The relay host is commissioned separately. Its per-agent checkpoint private key stays in the relay host’s secret manager; it is never placed in agent state. The signed release certification root must already be independently installed on the relay and agent. A machine cannot enable itself by generating a new root or substituting a request-supplied root.

The host operator runs `scripts/recovery-authority-setup.mjs prepare <private-absolute-directory> <agent-id> <generation>`. The tool creates a private checkpoint key and a signed certificate request, using exclusive creation so it cannot overwrite an installed authority. The request contains only public material. The release certification authority reviews and certifies that per-agent public key. `activate <private-absolute-directory> <certificate-file> <release-roots-file> <https-relay-origin>` validates the actual release signature, agent identity, generation, key possession, certificate lifetime and separate trust store before it writes the authority configuration and private phone-enrollment link. It never prints keys or the enrollment capability.

Install the resulting configuration with `RELAY_RECOVERY_AUTHORITY_FILE`, and independently mount the release trust store with `RELAY_RECOVERY_CERTIFICATION_ROOTS_FILE`. Restart the relay through its normal deployment path. Its deployed entry point requires the existing host admin secret and refuses untrusted recovery certificates before listening. Transfer the private phone-enrollment link through the operator’s existing secure channel within 15 minutes. The phone creates a non-exportable P-256 signing key and proves possession while consuming the one-use token. The relay persists the owner record and token consumption transactionally; restart cannot replay enrollment. Subsequent grants and removals require signatures from that enrolled phone. Disconnecting it persists a terminal owner tombstone, so boot configuration cannot silently reinstate it. Disconnecting the phone removes that phone’s grant authority. Existing machine grants remain approved and may continue renewing until the operator separately removes them; each individual offline checkpoint still has the bounded 24-hour lease.

If the release root, certified signer, relay deployment access or phone enrollment is absent, setup reports the exact missing prerequisite and remains degraded. Disposable test authorities never satisfy production setup. Certificate issuance and actual host deployment require the corresponding existing authority; this setup tool does not invent those privileges.

Initial provisioning is supported even when no recovery root exists. On an explicitly configured secure release host, set `INSTAR_RECOVERY_RELEASE_HOST_SECRET_DIRECTORY` to its protected secret store and run `scripts/recovery-certification-root.mjs bootstrap <absolute-public-pin-output>`. The public output must be named `instar-recovery-certification-root.pem`. The command creates an Ed25519 recovery certification key only in that owned, private directory (0700 directory, 0600 key) and refuses to overwrite either an existing key or public pin. It has no force mode. The existing Instar release root is untouched. This step is never run automatically on an agent or in an unprovisioned development session.

Review the public pin at `src/scaffold/keys/instar-recovery-certification-root.pem` and ship it through the existing authenticated, provenance-signed npm release process. The normal build’s `package-recovery-root.mjs` copies only that reviewed public pin into `dist/keys/instar-recovery-certification-root.pem`; it never generates one. New and updated agents receive the same installed public pin. A missing pin remains an explicit setup prerequisite. Keep the private root solely in the configured release-host secret store. The relay release trust-store JSON contains this independently distributed public PEM. Later root rotation needs a separately released dual-root transition; the bootstrap command cannot rotate an established root.

Release issuance uses `scripts/certify-recovery-authority.mjs <certificate-request.json> <approved-review.json> <certificate-output.json>`. The review binds `decision: approved`, `agentId`, `generation`, the canonical signed request’s `requestDigest` and `expiresAt` (at most 30 days). The tool verifies request key possession, exact reviewed digest, time/generation and the private key’s match to the packaged recovery pin. The private key comes from `INSTAR_RECOVERY_CERTIFICATION_PRIVATE_KEY_PEM`, `INSTAR_RECOVERY_CERTIFICATION_PRIVATE_KEY_PEM_PATH`, or `recovery-certification-private.pem` in the configured release-host secret store. Failure output never contains private material. The root only certifies per-agent checkpoint keys; it never issues admission checkpoints. The issued certificate is installed back on the relay host with the activation tool. Requests, certificates and the packaged pin contain no private keys; an agent cannot self-certify or trust a key from incoming setup data.

A lost or disconnected recovery phone is replaced through a new release-certified checkpoint-authority generation and a fresh host-issued phone enrollment capability. Reusing an old certificate, enrollment URL or token cannot restore that phone. The relay persists the highest installed signer generation and rejects rollback or a changed signer key at the same generation. This is a deliberate host-and-release recovery path; an agent or a peer cannot reset owner enrollment itself.

Recovery notices have a shared durable intent as well as a repair lease. The first notice claim fixes its source machine and logical message key; a different repair peer cannot assign another sender while the original enqueue outcome is unknown. The control plane marks the intent accepted only after that source confirms durable outbox acceptance with the same operation ID. A source restart retries that same logical operation. If the source is unavailable, delivery remains pending on that source instead of creating another message budget; actual delivery can therefore take longer than the normal five-minute attention window. The status retains the pending source without exposing keys or endpoint addresses. Delayed notices describe a recovery episode that needed attention and link to current status rather than asserting the machine is still down. A verified recovery does not erase an ambiguous earlier send.

An unresolved older notice does not hold a new repair episode open. A verified healthy receipt closes that repair incarnation while preserving its separate immutable notice reservation. A later outage can obtain a new fenced repair lease and its own notice identity under the current signed grant; acknowledging the older reserved operation does not consume the newer outage’s budget. The original sender can rediscover its reserved pending operations from the control plane after a restart, even if it crashed before writing its local enqueue intent. The phone shows the count of earlier notices still waiting for their original source.

If a bounded repair episode exhausts its attempts, the enrolled phone offers **Retry bounded recovery**. This is an explicit signed owner event with a new monotone per-target repair epoch. The target acknowledges that epoch before its fresh finite budget applies; source peers re-arm only after verifying a higher epoch in a target-signed status response. Routine checkpoint renewal, ordinary grants and turning a route back on preserve the existing repair epoch and cannot silently reset an exhausted controller. Replayed owner sequences and lower epochs are refused.

The shipped maturation ladder is `multiMachine.serverDownRecovery`. It keeps the approved two-host destructive qualification and the subsequent 48-hour development-agent proof soak as explicit review gates. Report completed qualification through the existing authenticated `POST /maturation/evidence` endpoint: a `fired` row with reason `two-host-destructive-matrix-passed`, followed by an independently graded `outcome: right` row with reason `two-host-destructive-matrix-reviewed` and its `gradesEventId`. The fleet gate separately requires `dev-agent-two-route-48h-soak-passed` and its `dev-agent-two-route-48h-soak-reviewed` grade. Attach the report reference and exact revision in the bounded evidence context. Missing evidence remains missing; historical disposable receipts do not certify production enrollment or a completed soak. The fleet decision is reviewed within 14 days of merge in topic 10000001794. Even a later fleet code graduation cannot mint owner grants or turn an unproven target ready.

Before installing SSH recovery grants, setup reads the effective sshd policy without starting or changing sshd. Only language variables (`LANG` and `LC_*`) may be accepted from clients; user environment files and a global `ForceCommand` override must be disabled. Unqualified `Match` sections, unsafe startup variables, unreadable includes or uncertain policy refuse SSH grant installation. The forced wrapper also starts the retained interpreter with a clean environment and preserves only the quoted transport selector plus fixed host account settings. Setup does not rewrite shared host SSH policy. If SSH cannot be qualified, the enrolled owner can disable that target's SSH route and finish the independent HTTPS route; the missing SSH proof remains visible until policy is qualified and the owner explicitly re-enables it.

Recovery runtime storage has a hard capacity of eight complete or staging slots. A full store refuses a new installation with `recovery-runtime-slot-capacity`; installed listeners keep their current slot. To reclaim old builds, run the local installed recovery entrypoint with `cleanup-runtime-slots /absolute/path/to/.instar/recovery/host.json`, using that slot's Node binary. Cleanup holds the local admission lock, keeps current/prior and transaction-referenced slots, and removes only verified owned slots older than 24 hours. An abandoned staging reservation additionally requires a dead process identity. It never runs through a peer recovery command.
