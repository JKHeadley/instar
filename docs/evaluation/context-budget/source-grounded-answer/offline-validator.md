# Offline Answer And Judge Validator

This internal evaluation command checks captured data, not the meaning of an answer. It does not run a model, execute tool calls, fetch sources, interpret source instructions or authorize a reduction. It uses the committed answer and judge schemas plus a supplied capture manifest. Reverting the script and its direct development dependency removes the feature; no agent configuration or installed files change.

Run `node scripts/evaluation/source_grounded_validate.mjs CAPTURE.json`. The command reads only the explicit capture and committed local schemas, prints a bounded content-free JSON report, and writes no state. Exit 0 means both outputs are structurally consistent. Exit 1 means a failed answer or judge error. Exit 2 means the capture could not be read or its manifest is invalid. Retain original input files separately; the report contains hashes, not a recoverable copy of their contents. Caller custody must preserve every attempted trial and judge output.

The capture is a JSON object with exactly `version: 1`, `caseId`, `submissionId`, `sources`, `availableSourceIds`, `criteria`, `answerRaw` and `judgeRaw`. Each source has `id`, original `text` and the SHA-256 of that text's exact UTF-8 encoding. Each criterion has `id`, `absence` and `critical` booleans. `answerRaw` and `judgeRaw` hold the exact output JSON strings or null for missing output. See the invented fixture in `tests/fixtures/source-grounded-capture.ts`; it is not a private evaluation question.

The validator checks internal consistency only. The caller supplies source text, digests, availability, identities and criteria together; changing them consistently can produce another structurally valid capture. There is no independently authenticated scheduled-trial binding here. A future trusted host must verify a separately frozen input manifest, actual supplied bytes and capture custody before treating those fields as authoritative. Matching hashes do not authenticate a speaker, grant permission or prove complete source capture. The `critical` flag and omission classification are caller declarations, not validator judgments.

Input is capped at 4 MiB, raw answer at 128 KiB and raw judge output at 256 KiB. Parsing rejects duplicate decoded keys, non-finite numbers, nesting deeper than 100 and ill-formed Unicode. UTF-8 file decoding is strict. Source hashes use well-formed text; escaped lone surrogates are rejected rather than silently replaced during hashing. Reports distinguish the parsed object's serialized hash from the exact capture-file UTF-8 digest. Each output has a separate exact raw-string hash. No raw source, answer text or private pathname is echoed in errors.

Answers must match case identity and use unique claim identifiers. Citations must name sources actually supplied to that answering arm. Spans use Unicode code points, zero-based and end-exclusive, with `0 <= start < end <= length`. Judge records must match submission identity, include every criterion exactly once and use only known claim references. Judge source spans resolve against original sources, including sources withheld from the answering arm; this does not make those sources available to the answer. Answer spans resolve `answer`, `claims/<claimId>/text` or `limitations/<index>`. Unlisted-claim spans follow the same rule. Empty judge evidence is structurally allowed only for a host-declared absence criterion; whether the explanation is adequate remains a semantic judgment.

Invalid answers remain `failed-answer` records. Invalid judges remain `judge-error` records. A judge record referencing an invalid answer cannot be structurally validated and is recorded as a judge error without repairing the answer. The validator neither computes semantic verdicts nor aggregates judges, clears critical signals, adjudicates disputes or measures cost. A structurally valid record may contain incorrect or malicious assertions, and the independent semantic judging protocol still applies. `qualificationAuthorized` is always false.

Unit checks cover strict parsing, schemas and Unicode. Integration checks combine the actual schemas, captured manifests and separate output classifications. Lifecycle checks invoke the real command with temporary explicit files and check exit codes, redaction and strict decoding. These focused checks do not substitute for the shared repository full-suite gate before integration. No model trial, hidden-label isolation or live-runtime result follows from them.
