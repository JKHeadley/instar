# Bounded Source-Identity Database Writes

This dormant foundation adds `planSourceClaimWrite` to the actual imported-history writer. It computes a content ceiling before SQLite can grow the durable records that identify each local source. It is not a real disk reservation, user consent, device admission or apply service. The complete local-import journey remains tracked in Easy Setup and unavailable. <!-- tracked: topic-143810 -->

The plan freezes the exact provenance claim and binds the actual store, writer lease, mutation revision and canonical file snapshot. An identical already-durable claim activates in that writer at zero content cost. A changed owner/source/representation cannot borrow another claim. A new claim requires the separately reserved ceiling before even creating the canonical database file. Another plan, mutation, writer exit or failed attempt invalidates the token.

The budgeted path rejects journal/WAL/SHM sidecars before opening SQLite. It also reads the database header directly and rejects WAL read/write versions even when sidecars are absent: opening such a database can create them. This path does not silently recover, migrate or delete unknown state. Existing legacy SQLite-owned recovery remains separate. The complete apply service must admit and account recovery explicitly; refusing an unresolved journal is not proof that nothing committed.

The audited supported pager is better-sqlite3 12.8.0's SQLite3.51.3, using its unmodified default Unix VFS. Budgeted execution verifies that exact SQLite version, rollback DELETE mode by query, auto_vacuum0, page size, OFF cache spilling, MEMORY temp store, FULL synchronization and the effective `max_page_count`. It never changes WAL mode into DELETE as a repair. Schema creation and the fixed single INSERT run in one immediate transaction. The first error aborts the whole transaction and closes SQLite. No retry or continuation, savepoint, ATTACH, extension, custom VFS, file-control change, arbitrary SQL or trigger is used. The old reader synchronization model remains unchanged; no database rename or copy-on-write publication is introduced.

For allowed page count N and page size P, main-file content cannot exceed N×P. Subtract the existing logical file length when calculating new file-length growth. The conservative rollback-journal ceiling is N×(P+8)+2×65536 bytes. The inspected pager writes each original page's P+8-byte record once, suppresses spill headers when cache spilling is off, keeps statement subjournals in memory, and clamps sectors at65536. A page-move failure can clear its journal bit; aborting on the first error is essential. Source locations and primary-source hash are recorded in `evidence/claim-sqlite-pager-bound.json`.

The default page-growth estimate adds the serialized row pages and eight headroom pages. Eight is an initial resource policy, not a physical or authorization floor. A trusted caller may provide another positive page allowance that still fits the original database. SQLite's actual page limit enforces the result, and insufficient room refuses rather than exceeding the ceiling. Tests deliberately force SQLITE_FULL with a smaller allowance. Increasing an allowance does not revive a consumed plan or grant copy consent.

This proves a logical database/journal content bound, not filesystem blocks, inode/directory metadata, lock-file growth or immutable free space. Rewriting existing logical pages can still allocate new physical extents on sparse or copy-on-write filesystems, and rollback can rewrite them again. The real parent must account forward/rollback extent writes separately; `contentBytes` must never be treated as the complete physical disk reservation. The future parent must reserve those costs separately, prove store/ledger volume identity, bind its permit to this plan, recheck actual owner/target/boot/preview, and retain outstanding charge through rollback, SQLite close, actual child exit and uncertain recovery. Legacy unbudgeted methods remain for existing callers; the fixed apply worker must use the planned APIs exclusively. <!-- tracked: topic-143810 -->

Real tests exercise native page refusal, first-error rollback preserving existing database bytes, pre-open sidecar/WAL refusal, actual journal content before commit, and process death before/after durable claim publication. The post-commit death case reopens the real store and reconciles through a zero-content claim plan before writing a synthetic conversation. This is lower-level store lifecycle proof; it supplies no signed apply endpoint, installed app or copy confirmation.

No schema migration, new persistent filename, replication policy or user prompt is added. Existing private source provenance and actual target selection keep their previous multi-machine posture. Revert the new API/helper and associated tests to remove this component. Preserve any unresolved native journal and reservation; never manually remove it merely to make a new import fit.
