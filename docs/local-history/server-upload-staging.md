# Selected History Upload Staging

This internal component owns temporary raw uploads and their stable operation identity. It is not constructed by AgentServer, exposes no HTTP route and enables no Mac import action. The complete feature remains tracked in topic 143810 under the approved `docs/specs/local-history-native-contract.md` contract.

`LocalHistoryUploadStaging` requires the destination's current issuer and an authoritative enrolled-device principal resolver. The caller must already authenticate the native request and retain shared request/response admission. A bearer token, manifest, allocation identifier or verified digest does not establish owner consent or copy permission.

Admission requires a current single-use selection challenge and a frozen manifest. The operation identifier is assigned before the grant reply. Retrying the same live request with an unchanged fingerprint returns that operation without spending another challenge; changed or terminal requests cannot recreate it. Owner, enrolled key, machine, boot, origin and signing-key bindings are checked at each boundary. Selection challenges and uploads have wall-clock and monotonic expiry, so stopped or backward clocks cannot extend authority. Challenges from an earlier staging instance cannot be used after recovery.

The private bounded manifest, raw files and metadata work reservations all use `LocalHistoryDiskLedger`. Reservations precede payload writes. Generated opaque file identifiers are the only accepted storage references; caller paths are not accepted. Chunks must have the exact expected index and length. An exact retry is acknowledged without appending; a conflicting retry terminates the operation. Positive short reads are filled, early EOF is refused and all returned verification buffers are cleared.

Completion enters one asynchronous verification lane. Every file is sealed against further ledger writes before bounded, yielding SHA-256 verification. Current ownership is checked between chunks and before publication. `verified` means exact raw byte length and digest only. It does not mean a valid source conversation, normalized preview, consent, source claim or completed import.

The internal `prepare` method connects verified operations to the actual fixed parser child. It uses the same held custody, with a scoped child lease that releases only after actual exit. The parent streams authorized bounded reads, clears borrowed buffers and reserves every normalized output block before writing. The child checks the actual stable owner's existing source claim before selecting its parser mode. Store metadata hydration occurs inside the bounded child; existing-only access creates no history directories and does not mistake a missing manifest for a missing durable claim. Shared session identity normalization prevents a second identity algorithm.

Successful preparation seals normalized files, publishes a bounded private receipt index, retires raw inputs individually and then publishes `prepared`. A raw cleanup failure offers no prepared result and retains unresolved charges. Cancellation, expiry and stop fence authority immediately but retain child-owned files until the real parse job settles. The per-file deadline is capped by remaining absolute operation lifetime. Duplicate preparation reuses the operation. Status returns bounded counts and digests, never file paths or message payloads. `prepared` is still not a preview confirmation or a copy permit. No apply operation, library read or production HTTP construction is provided.

One actual SQLite parent-and-child custody generation is held for the component's entire lifetime. Startup can reclaim recognized old-generation allocations only after the actual previous parent and all shared child holders have exited. It does not infer that from a process identifier or age. Unknown tags remain charged. This ownership excludes a second staging instance. Preparation borrows this generation; remaining apply/read integration must share the same serial coordinator rather than independently acquiring another parent lease.

Expiry and cancellation invalidate authority before cleanup. Failed cleanup retains its reservation, retries at bounded intervals and emits a fixed internal degradation report after exhaustion. Stop rejects new calls, drains verification and releases handles and custody even when operation metadata is damaged. Low disk does not prevent opening the ledger for recovery, but new admission still requires its free-space floor. Operation, challenge and allocation rows have bounded admission; saturation refuses rather than evicting request barriers. The separately blocked bookkeeping retirement edit is not included.

New disk ledgers atomically create schema version 1 with the sealed-state constraint. Earlier unversioned ledgers are refused intact before admission; this dormant checkpoint does not migrate or remove older state. A production rollout must establish the explicit supported schema path before enabling the feature.

Checks use actual synthetic files and SQLite transactions, including a killed parent and surviving holder process, revocation between verification chunks, stopped-clock expiry, wrong-profile damaged rows, interrupted allocation, failed unlink, exact retries and short reads. HTTP, production initialization and installed-native acceptance remain required for the complete feature. Full suites are coordinated separately.
