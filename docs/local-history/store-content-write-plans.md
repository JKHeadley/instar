# Store Content Plans Before Copying

This dormant store foundation lets an isolated writer calculate the exact serialized content it intends to write. It does not enable local import, publish a preview, obtain copy consent, reserve real disk space or run an apply child. Those remain owned by the Easy Setup flow. <!-- tracked: topic-143810 -->

Inside the real `ImportedHistoryStore.withWriter`, first obtain the separately accounted durable source claim. `planConversationWrite` freezes the actual JSONL append, including a separator after a torn tail, and each missing overflow attachment. Its opaque descriptor contains only `kind` and `contentBytes`, never the selected text or a pathname. One plan per store binds the actual writer lease and mutation revision. Another plan replaces it; existing conversation/project/claim/flush mutations and writer exit invalidate it.

A fixed worker passes its parent's already-reserved content ceiling to `executeWritePlan`. The store rejects a forged, wrong-store, old-writer, reused or insufficient-ceiling attempt before file growth. The accepted attempt is consumed before filesystem mutation, including failed attempts. It rechecks file identity, size, timestamps and tail, checks the actual opened append descriptor, refuses symlinks and uses exclusive creation when the conversation was absent. Private serialization snapshots and revision checks prevent caller changes or reentrant serialization from silently changing the approved content.

`planManifestWrite` is separate because future append and flush require separate parent permits. Its cost is the complete new manifest temporary file, even if the final manifest grows only slightly. Rename transfers that file's content and does not allocate a second content copy. Missing overflow publication similarly writes one exclusive temporary file and atomically links its first final name, then removes only its owned temporary link through SafeFsExecutor. It refuses to replace an attachment that appeared after planning. No-op flush costs zero.

Legacy `addConversation` shares the same preparation and execution functions, and ordinary `flush` retains its existing behavior. They do not acquire a new content budget; the future fixed local-apply worker must use the planned APIs exclusively. Existing export/manual behavior is covered separately. The planning API supplies no device authentication, owner identity, destination authorization or permission to copy.

If an append, temporary write, publication or disposal fails, some bytes may already exist. The token cannot be used again. A fresh writer reconciles the real messages and durable source claim; it does not assume failure meant no copy. A failed temporary file remains physical content and must stay charged until actual disposal or reconciliation by the reservation owner. `ImportWriteCleanupPending` reports a generated basename, conservative retained bytes and verified-inode versus unresolved-creation ownership. Only the exact internally registered inode handle can dispose its temporary link; forged handles cannot remove files. If initial identity inspection fails, the descriptor is still closed, residue remains explicit and disposal refuses without proof.

`contentBytes` measures UTF-8 payload and conservative peak replacement content. It does not measure allocation blocks, filesystem directory/inode/journal metadata, the writer-lock database or source-claim SQLite growth. Future apply must separately reserve these costs, prove store/ledger volume identity, bind each parent permit to the exact plan, debit actual partial writes, retain ambiguous outstanding permits until the real child exits, and enforce current owner/target/boot/preview/expiry/cancellation. This component cannot establish those guarantees by itself.

No replicated state or cross-machine read surface is added. Existing credential custody and selected-target copy rules remain unchanged. Plans live only inside their writer and do not become portable authority. Revert the new store API and its regression together to remove this foundation; no migration or data deletion is required. Full import availability remains false.
