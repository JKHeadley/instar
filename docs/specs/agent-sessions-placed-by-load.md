# Agent-started sessions are placed by load, and shedding starts before the cap

## Problem statement

Justin, 2026-11-17 19:43 PT: "Why are we not load balancing sessions to other machines... well before the mac studio is overloaded?"

Measured on the Mac Studio that evening (16 cores, lease holder): 23 running sessions on the Studio and 0 on the Laptop; load average 36-76 for hours; the agent server stopped answering for 30-90 s at a time; Local Verify runs took 43 min instead of 23. `GET /work-admission`: `lastVerdict` `impaired` for 258 consecutive samples, `wouldRefuse: 21`, `refused: 0`, `dryRun: true`. Of the 23 sessions, 18 are bound to a Telegram topic and 5 are not.

Causes, read from `main`:

1. **`POST /sessions/spawn` starts the session on the machine that received the call.** Agents, skills and the Chief of Staff start topic sessions and helpers through it, so they land where the caller runs (the Studio). Only inbound user messages for a new topic go through pool placement (`SessionRouter.placeAndClaim`), the dashboard can start a topic on a chosen machine (`/sessions/create` `machine`, `startTopicOnMachine`), and `POST /pool/heavy-work/spawn` places heavy helpers. Scheduled job sessions do not use this route at all (`JobScheduler` calls `sessionManager.spawnSession`); they are out of scope here.
2. **The overload shed's source condition never holds.** `OverloadShedPlanner` needs admission closed (`acceptingWork === false`) for 3 min AND 85% of the session cap. The planner does evaluate and audit below stage `rebalance`; no `logs/overload-shed.jsonl` exists because the source condition was never met. It moves only quiet sessions (frees slots, not CPU).
3. **Admission enforcement is off on the Studio** (`monitoring.workAdmission.dryRun: true`). A configuration decision, not code (Step 3).

## Proposed design

### Step 1 (this PR): measure every agent-started session's placement, and place opt-in topicless helpers

**1a. Shadow for every `/sessions/spawn` (rung 0).** When the feature is on (`multiMachine.placement.agentSessions.enabled`, an omitted boolean resolved by `resolveDevAgentGate`, registered in `DEV_GATED_FEATURES`: on for a development agent, off on the fleet), every `/sessions/spawn` that does NOT carry `X-Instar-Placed: 1` (a forwarded or heavy-route loopback spawn is logged once at its origin, tagged `forwarded` here, never as a would-place row) computes, before starting locally exactly as today, the placement it WOULD make and appends one line to `logs/agent-session-placement.jsonl`: time, session name, `topicBound` (bool), weight, this machine's fresh verdict and per-core load, the would-be target and why, and `mode: "shadow" | "live"`. Never the prompt. The file rotates through the existing JSONL rotation helper. This answers "how much would move, and where" for topic and topicless spawns with real numbers, and is the tuning evidence for every threshold below.

**1b. Live placement, opt-in, topicless only (rung 1).** A request with `placement: "auto"`, no `topicId`, and none of the fields that cannot travel, is placed live:

- **Names are unique across this path.** Requests for the same name are serialized in-process (one placement per name at a time; a second waits for the first's answer). Before placing, the route refuses a name already running on this machine (409 `session-exists`, as today), and looks the name up in the placement store (below): a name with a live or pending placement is never placed on a new peer; the route re-checks that same machine and answers its state (`exists-on-peer`, `peer`, or `unconfirmed`). A client that retries after a slow answer therefore lands on the first copy, never a second one. A name with an UNRESOLVED entry (`pending`, `live`, `unknown`, or `not-observed` younger than 24 h, since a slow launch can still land after an empty read) is read-only: the route never sends another start for it, anywhere; it answers the recorded or freshly re-read state (`exists-on-peer`, `peer`, `unconfirmed`, `placement-bound-elsewhere`) naming the peer, nothing starts locally, and to run the work again the caller uses a new name. A `gone` entry (seen running, then no longer running) does not bind the name: a new request for it is a new run, exactly as reusing a local session's name after it ends is today, and the entry is removed when that request arrives. Residual risk accepted (same as on one machine today): a caller that ignores a `202` and re-sends after a short helper has already finished can run it twice. An `exists-on-peer` answer keeps (or creates) the entry pointing at that peer, and does not release a reservation; only a refusal that proves the work is not on the peer removes the entry and releases.
- **Fields that travel:** body `name`, `prompt`, `workWeight`, `framework`, `model` and headers `Authorization` (this agent's token, same agent on both machines), `X-Instar-AgentId`, `X-Instar-Placed: 1` (what `forwardHeavySpawn` sends, plus the marker). `placement: "auto"` does not require the heavy route's `X-Instar-Request: 1` intent header: both routes need the bearer token, and the request already chose placement explicitly. A request carrying `jobSlug`, `ultracode`, `spawnRole`, `topicName`, `requireTopicBinding`, `targetMachineId` or the `x-instar-bind-token` header stays local, with `reason: "options-do-not-travel"`.
- **This machine is preferred.** This machine is removed from the set given to `decide()`, and placement is consulted only when this machine is busy: its own fresh verdict is `saturated` or `impaired`, its own fresh load report says it is short of memory (`memoryPressured`, the shipped 2-of-3 memory reading that `peerMemoryReason` reads), or its fresh per-core load is at or above `HEAVY_WORK_FLOOR.maxLoadPerCore` (the shipped heavy-work floor, 1.0; evidence freshness `LOAD_REPORT_MAX_AGE_MS`, the shipped one-minute rule). A machine with no fresh row of its own has an unknown load; unknown means stay local (today's behavior, the least harmful choice: nothing moves on evidence that is not there).
- **A peer must have room, by weight.** `heavy` requests keep the full `heavyFit` (size or `heavyWork` override AND headroom). `standard`/`light` requests use `heavyHeadroom` (fresh evidence, verdict not saturated/impaired, per-core load not above 1.0); `heavyWork: deny` does not exclude them (it is about heavy work only). Peers whose own fresh report says they are short of memory (`peerMemoryReason`) are excluded for every weight (Studio, 2026-11-17 20:36: about 0.47 GB free, three node processes near 4 GB each; memory, not CPU, was what ran out). Peers whose `quotaState.blocked` is true are excluded for every weight (a headless helper on a walled account does nothing, silently). The self-busy test uses `>= 1.0` and the peer test `> 1.0` (the shipped `heavyHeadroom` comparison): a machine at exactly 1.0 may send work away and, with no reservation on it, may also receive it. Reservations (below) count in both the headroom test and the ranking, so successive placements spread across peers instead of filling the least-loaded one first.
- **Heavy requests reserve like the heavy route.** A `heavy` placement through this route records `heavyReservations.record(target)` and releases it on a definite refusal, exactly as `/pool/heavy-work/spawn` does.
- **Burst spreading.** A separate in-process counter `agentSessionReservations` (3-minute expiry, the same lifetime as heavy reservations) counts standard/light placements this machine sent to each peer, each adding `0.25` per core to that peer's load in THIS route's headroom test (for every weight) AND in its ranking (a new optional `extraLoadPerCore(machineId)` seam on this route's own executor instance, read only by `score()` and added to the per-core load before the reference-core scaling; it is not folded into `pending()`, so the least-loaded peer is not chosen again and again within 3 minutes; a new `extraLoadPerCore` argument to the headroom check; the existing `pendingHeavy` argument keeps its 0.5-per-item meaning and still receives `effectivePending`, so heavy work already reserved or advertised for that peer counts too). It never feeds `heavyReservations`, conversation placement or the shed, so heavy work and conversations do not see phantom load. The 0.25 is a starting weight (a standard helper is typically one busy core on a 4+-core machine), re-tuned from the shadow log; like heavy reservations it is per process, so two deciders can still pick one peer at once (bounded by each peer's own admission).
- **Outcomes: no automatic retry or local start after an ambiguous launch.** Forward via `forwardHeavySpawn` with its shipped 15 s timeout. `started` → `201` with the peer's `tmuxSession`, `placedOn: { machineId, nickname }` and `placementOutcome: "peer"`. A definite refusal that proves the work is NOT on the peer (connection refused before sending; 409 `admission-refused`, `session-capacity-refused`, `codex-accounts-walled`; 429; other 4xx auth/validation errors) → start locally, `placementOutcome: "local-fallback"` with the reason. 409 `session-exists`, and an older peer's duplicate-name answer that `forwardHeavySpawn` classifies as a definite refusal (normalized through `classifySpawnRefusalMessage` to `session-exists`, whatever the HTTP status) → no local start: answer `409` with the peer identity (`placementOutcome: "exists-on-peer"`), because that name may be an earlier attempt of this very request. `unconfirmed` (timeout, 5xx, no answer) → no local start; answer `202` (a new status for this route, documented in the awareness text) with `placedOn`, `placementOutcome: "unconfirmed"`, and the reconciliation below owns the outcome. `queued` / `placement-blocked` / no eligible peer → local, with the reason. Guarantee: one origin machine never starts a name twice (same-name requests through that origin are serialized and routed to the first placement). Two different origins placing the same name at the same moment are not coordinated globally; the receiving machine's own name check refuses the second copy it sees, and a race across two different receiving machines is an accepted residual risk (it needs two callers on two machines to pick the same name within seconds); it inherits resource-aware placement §6's accepted residual risk (the peer started the session and both its record and its answer were lost).
- **The placement store (durable).** `state/agent-session-placements.json` maps session name → `{ machineId, state: pending | live | unknown | gone | not-observed, at, lastSeenAt }` for every live placement this machine made (the entry is written as `pending` BEFORE the forward is sent, so a crash between send and answer still leaves a record to reconcile; `started` updates it to `live`, a definite refusal removes it). It survives restarts, holds at most 200 entries (only `gone` entries, and `not-observed` entries older than 24 h, are ever dropped, oldest first; the audit log and the existing attention item record a full store, naming the peers its unresolved entries point at; when all 200 are unresolved, new `auto` requests start locally with `reason: "placement-store-full"` until some resolve), and a `live` or `unknown` entry is re-read every 10 minutes on the same pool tick; a sighting (running) updates `lastSeenAt`; a successful read where the name is NOT running becomes `gone` (it finished or was stopped; the target keeps only a bounded list of finished sessions, so `gone` deliberately does not claim which). `not-observed` is used for a `pending` entry whose name was never seen running in successful reads within its 10-minute window; it does NOT claim the session never started (a short helper can start and finish between reads, and finished lists are bounded), so it never authorizes another start of that name. A failed read changes nothing (`unknown` stays `unknown`). `pending` and `unknown` entries are kept regardless of age (time alone never ends one). The target URL is never stored: it is resolved at call time from the paired-peer registry (`resolvePeerUrls` / `poolPeerFetch`, as the heavy-work route does).
- **Reconciling unconfirmed placements.** Before answering `unconfirmed`, the route reads the target's `GET /sessions` through `poolPeerFetch` 3 times over 15 s; a found session upgrades the answer to `201`, and a failed read counts as not yet known, never as absent. A `pending` entry not resolved in-request is re-checked on the existing 30 s pool tick (`poolBeat` in server.ts, each pending entry at most once a minute) for up to 10 minutes, then resolved `live` (seen running) or `not-observed` (successful reads within the window never saw it running) or `gone` (seen, then no longer running), or left `unknown` while the target stays unreachable (never forced to absent by elapsed time). `not-observed` or `unknown` after the window raises one attention item naming the session and machine and telling the reader to check that machine's finished sessions and any shared effects (commits, messages) before starting the work again; nothing restarts it. The `202` answer still carries `tmuxSession` (the requested name).
- **Later reads find the session.** `GET /sessions/:name/output`, for a name that is not a local session, looks up the placement store and, for an unresolved or `gone` entry, proxies the read to that machine (target resolved from the paired-peer registry at call time, with `X-Instar-Placed: 1`; a request carrying that header is never proxied again). Kill is NOT proxied: the kill route carries operator provenance (PIN proof, close-via) that a token-only proxy would turn into an agent kill on the peer, so a kill for a placed name with an unresolved entry (by tmux name or session id) answers `409 placed-on-peer` with the machine; the operator stops it with the existing remote session close (REMOTE-SESSION-CLOSE-SPEC, which carries operator provenance), or the caller stops it on that machine.
- **No forwarding loops.** Every forwarded spawn (this route's and the heavy-work route's, including its loopback; the heavy route gains this header in this PR) carries the header `X-Instar-Placed: 1`; a request carrying it is never re-placed. Older peers ignore the header and start locally, which is the safe direction.
- **What the caller must know.** A placed helper runs in the target machine's agent home: its inputs must be in the prompt or fetched from a shared source, and its results returned through a shared channel (a message, a commit, a document). This is stated in a new awareness entry (`src/data/awareness/agent-sessions-placed-by-load.md`), and the existing heavy-work awareness line in `PostUpdateMigrator` and the `/sessions/spawn` line in the CLAUDE.md template (`templates.ts`) gain the `placement: "auto"` option. The awareness text also says: after a `202`, do not start the same work again under a NEW name; check the named machine. Nothing in the repo switches to `auto` until its prompt is location-independent.

### Step 2 (next PR, tracked): topic-bound agent spawns placed like a new conversation

A `/sessions/spawn` with `topicId` and `placement: "auto"`, for a topic with no live owner, is intended to use the existing fenced start protocol `startCheckedTopicOnMachine` (the one the dashboard machine choice and conversation-graph delegation already use: place → one checked deliver → settle; `unknown` keeps the claim, so no duplicate) with a new delivery payload carrying the spawn parameters, handled by the target's inbound path (feasibility unverified here; that PR's own spec checks it). The brief must travel as text (a brief that points at a local file stays local). This is where most of the measured load is (18 of 23); Step 1a's log sizes it.

### Step 3 (configuration decision, tracked): admission enforcement on busy machines

Checked from code (2026-11-17): an enforced, closed admission refuses every `automatic` spawn through `SessionManager.spawnSession` (scheduled jobs, `/sessions/spawn` helpers and topic spawns, inbound new-topic spawns), lets an operator's interactive session through the one host-wide recovery slot, and makes pool placement skip this machine for new conversations (`isRefusingWork` needs `admissionEnforced`), so new user conversations go to peers with room. Local Verify is not gated by it (it runs tests through its own queue, not sessions). The cost on the Studio today: `/sessions/spawn` callers there get a refusal instead of a session until Step 1b/2 can place them elsewhere. The proposal with these facts and the would-refuse counts goes to the Chief of Staff; not flipped by this PR.

### Step 4 (later PR, tracked): shedding from sustained load

A second `OverloadShedPlanner` source condition: fresh verdict `saturated`/`impaired`, or the machine's own `memoryPressured` reading, sustained for the verdict's own window, derived from Step 1a's data, regardless of the session ratio. Memory is a first-class source (the 2026-11-17 20:36 Studio memory exhaustion happened while admission still read CPU-shaped evidence), and a memory-sourced shed prefers sessions holding the most memory, not the quietest ones. Every existing brake stays.

## Decision points touched

- `/sessions/spawn` start location for `placement: "auto"` topicless requests — judgment-candidate; floor: never dropped, never duplicated (`unconfirmed` → no local start), non-travelling options → local, forwarded requests (`X-Instar-Placed`) never re-placed; arbiter: `PlacementExecutor.decide` over the pre-filtered candidates (headroom, quota and self removal applied BEFORE the call); for standard weight it ranks by the conversation score (load, session ratio, memory), for heavy by the heavy least-loaded rule.
- "This machine is busy" trigger — judgment-candidate; floor: reuses the shipped `HEAVY_WORK_FLOOR.maxLoadPerCore` (1.0) and `LOAD_REPORT_MAX_AGE_MS` (60 s), plus the machine's own verdict; no new boundary is introduced. These constants were evidenced for resource-aware placement (§1 of that spec); 1.0 per core is a conservative placement threshold (a load average at the core count), not proof of instantaneous queueing. The shadow log (1a) is the evidence to re-tune them, and the arbiter still chooses among peers. An I/O-bound helper is a legitimate counterexample (it would fit here); the cost of sending it to a peer with room is one hand-off, while keeping it here at load above 1.0 slows every session already here.
- Storage bounds (placement store 200 entries; `live`/`unknown` re-read every 10 minutes; 10-minute reconciliation window before an attention item) — judgment-candidate; floor: none of them loses state silently: only resolved entries (gone, and not-observed older than 24 h) are ever dropped, an unreachable target stays `unknown`, and the window only decides when a person is told, never what is true.
- Standard reservation weight (0.25 per core, 3 min) — judgment-candidate; floor: it only shapes this route's choice and can never block a session (no eligible peer → local); evidence and re-tuning from the shadow log.
- Peer headroom — judgment-candidate; floor: the shipped `heavyFit` headroom test without the size rule; arbiter: `PlacementExecutor.decide`.
- Shadow logging — invariant; basis: enumerable-domain; evidence: it writes one audit line and never changes where a session starts.

## Frontloaded Decisions

- Scope: `/sessions/spawn` only. `/sessions/create` is out (its headless branch is an operator console with no prompt, and it already has placement and a machine choice).
- Opt-in: live placement only with `placement: "auto"`; no field means today's behavior. Flipping to a default later needs every prompt to be location-independent and is a separate decision, not a cheap change.
- Enablement: `multiMachine.placement.agentSessions.enabled` omitted → dev-gated (shadow + opt-in live on Echo, off on the fleet); `migrateConfig` writes no default (that would pin it).
- Config is read at boot; turning it off needs a server restart (routes read the boot `ctx.config`).
- Response field names: `placedOn`, `placementOutcome` (the `/sessions/create` response already uses `placement` as an object; this route does not reuse that name).

## Multi-machine posture

**unified decision.** The decision reads the pool's capacity heartbeats (the same evidence as conversation placement) on whichever machine receives the request. The placed session is an ordinary session on the target; replies go to Telegram from there. No pool or single machine → local, exactly as today. The audit log is per machine by design (it records that machine's decisions); `machine-local-justification: operator-ratified-exception` is not claimed, the log is read per machine like other `logs/*.jsonl` audits and summarized into the stewardship scorecard.

## Rollback

Set `multiMachine.placement.agentSessions.enabled: false` and restart, or revert. Sessions already placed on peers keep running there. Callers that never send `placement: "auto"` are unaffected in every state.
