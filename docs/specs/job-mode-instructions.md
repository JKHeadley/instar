# Job sessions load a short job-mode instruction file

## Problem

Every scheduled job session is a fresh Claude Code session in the agent home. Claude Code loads the project CLAUDE.md
(on Echo 104,892 bytes) and the auto-memory index (23,810 bytes) into the first prompt, and the first prompt is written
to the prompt cache fresh on most runs.

Measured on Echo, 2026-11-21, Claude Code 2.1.330, Haiku 5.5, a trivial prompt in the agent home. These are
settings-level measurements, not a production job; the PR records a real job's before and after.

| Launch | cache write | cache read | total first-turn input |
| --- | --- | --- | --- |
| As job sessions launch today | 65,921 | 14,521 | 80,442 |
| Exclude CLAUDE.md, memory off | 29,784 | 11,842 | 41,626 |
| Exclude CLAUDE.md, memory off, plus a small appended file | 29,830 | 11,851 | 41,681 |
| Exclude CLAUDE.md and AGENTS.md, memory off, plus appended file | 15,656 | 13,860 | 29,516 |

Excluding only CLAUDE.md makes Claude Code fall back to the agent home's AGENTS.md (33,892 bytes, the Codex identity
render), so both must be excluded. Between the first and last rows the probe shows 50,926 fewer first-turn input tokens and 50,265 fewer cache-write
tokens, the more expensive kind. These are probe deltas with a tiny appended file; per-run savings with the real
rendered text come from the scheduler measurement in the PR. The transcripts of these runs show project hooks still ran (SessionStart,
UserPromptSubmit, Stop) and that the appended file reached the model (it answered with a marker only that file held).
The environment switches `CLAUDE_CODE_DISABLE_CLAUDE_MDS` and `CLAUDE_CODE_DISABLE_AUTO_MEMORY` changed nothing on this
version, so the settings route is used.

Job prompts are self-contained task descriptions. Most of CLAUDE.md is for conversations with a person.

## Change

1. **Job-mode instructions rendered at launch and passed inline.** `generateJobModeText()` (beside
   `generateClaudeMd()`) renders the text in memory from this machine's own instar version at every job-mode spawn, and
   the launch passes it directly with `--append-system-prompt <text>`. No file is written or read, so nothing on disk
   (stale, tampered, or synced from a peer) can change what the session receives, and there is no window between a check
   and a read. About 6 KB is the guide. Contents: the agent's name and that this is an unattended scheduled job; API
   access through the session's own environment (`$INSTAR_SERVER_URL`, `$INSTAR_AUTH_TOKEN`), so the text holds no
   per-machine value; never run interactive commands; report instar problems through `POST /feedback`, never GitHub;
   how to message the person if the job's prompt says to (the relay script, plain complete sentences, CLAUDE.md's
   disclosure rules); look things up through the server before claiming; the safety and outbound-disclosure rules for any session, rendered
   from the same shared clause constants that `generateClaudeMd()` uses, so the two modes can never word a mandatory
   rule differently; that
   CLAUDE.md, AGENTS.md and the memory index were not loaded and where they are, so a job that needs more reads them on
   demand. Its last line is a marker, `JOB-MODE-MARKER instar <version>`, used by the check in Change 6. If rendering
   throws, the job launches full and a degradation is reported once per incident.
   Launch records, run records and argv error text record the marker and the text's byte length, never the text itself.
2. **An explicit launch option, never inferred from a job slug.** `SpawnOptions` gains `instructionsMode?: 'job-mode' |
   'full'`. Only `JobScheduler.spawnJobSession` sets it, from the resolved job (Change 3). The triage spawn is excluded. Every other spawn
   (topic sessions, `/sessions/spawn` even with a `jobSlug` in the body, `UpgradeNotifyManager`) passes nothing and
   launches exactly as today. Script-runner jobs start no Claude session and are untouched.
3. **How a job's mode is resolved.** In order, first match wins:
   - an operator override in `.instar/config.json` `scheduler.instructionsOverrides`, keyed by origin and slug
     (`"instar:commitment-checkin-reminder": "full"`, `"user:commitment-detection": "job-mode"`), so an override meant
     for a shipped job never follows a user fork that reuses its slug. It survives updates. Old code ignores the key.
   - for a jobs.json entry, its own `instructions` field (`"job-mode"` or `"full"`). The jobs.json validator ignores
     unknown keys today, so a revert leaves such entries firing. The field is deliberately NOT added to Markdown job
     frontmatter, whose validator skips a job on an unknown key; Markdown jobs use the override map.
   - the default: `"job-mode"` only for a shipped job that is verified (`origin === 'instar'` and
     `lockTrust === 'trusted'`) AND on the reviewed list, a constant in source (`SHIPPED_JOBS_REVIEWED_FOR_JOB_MODE`) keyed by slug and the
     body hash the loader already verifies, added to only when someone has read that exact prompt; a newly signed body
     under a reviewed slug does not match and resolves to full until reviewed; `"full"` for every other job, including a newly shipped job
     nobody has reviewed yet, and every user, legacy, or unverified job, which is today's behaviour.
   - when the parent spec's migration turns a jobs.json entry into a Markdown job, an explicit `instructions` value is
     carried into the override map under the new origin and slug, unless an override for that key already exists. The
     migration records each override it creates in its existing journal; its abort or abandon path removes those
     entries only if they still hold the value it wrote, so pre-existing overrides and later operator edits survive.
   Invalid values are refused per entry with a clear error at load (config load for the map, job load for the field);
   a bad entry resolves that one job to full and never stalls the scheduler. The PR lists every
   shipped job and its resolved mode. On Echo, as a rollout step after merge, I set overrides for its high-frequency
   user jobs whose prompts are self-contained, commitment detection first; that list and the reason for each go in the
   PR.
4. **Launch flags, one helper, both paths.** `claudeHeadlessExtraFlags` gains a `jobMode: { agentHome, text }`
   option. For Claude Code only, it emits `--settings` with `claudeMdExcludes` listing the agent home's `CLAUDE.md`,
   `AGENTS.md` and `.claude/CLAUDE.md` (absolute paths resolved from the same agent-home value the spawn uses as its
   working directory) and `autoMemoryEnabled: false`, plus `--append-system-prompt <text>` (one argv element, passed without a shell). The headless path
   splices these before `-p` and the interactive path appends them, as the helper's output already is today, so both
   paths get identical flags. User-level files such as `~/.claude/CLAUDE.md` are not touched. Codex gets nothing.
5. **Any restricted spawn keeps today's launch.** Job-mode is skipped when the spawn has `confinement` (its own settings
   file with `--setting-sources local`), `confinedTools`, `requireToolConfinement`, or `omitAuthEnv` (no auth token, so
   the job-mode API instructions would be wrong). The launch record names the reason. There is never a second
   `--settings`.
6. **Check what the session actually loaded.** Job-mode launches pass `--session-id <uuid>`, so the transcript path is
   known. After a job-mode run, the completion path reads at most the first 256 KB of that transcript:
   - **pass**: the read reached the first assistant message record (Claude Code writes every instruction-discovery
     record before the first model reply, so reaching it proves discovery is complete), a `prompt_snapshot` before it
     contains the JOB-MODE marker, and no `instructions` entry before it lists the agent home's CLAUDE.md, AGENTS.md, `.claude/CLAUDE.md` or the memory index. (When
     nothing is loaded, Claude Code writes no `instructions` entry at all; this was observed in the measured run.)
     The transcript is found from the uuid the job spawn generates and passes as `--session-id` (stored on the session
     record as its Claude session id), under the config home of the account that ran the session.
   - **fail**: an `instructions` entry lists an excluded file, or a first-turn `prompt_snapshot` is present without
     the marker;
   - **unknown**: anything else, including a read that ended before the first assistant message record, a missing or unreadable
     transcript, or an unrecognised format.
   Pass or unknown changes nothing. A fail sets that job to full and reports a degradation. The check runs on the first
   job-mode run of each job for each pair of instar version and Claude Code version, not on every run; an unknown
   result repeats the check on the next run, at most three runs per version pair, after which the pair is recorded as
   unknown, reported once, and the job runs with full instructions until a version change or an operator clear
   allows a fresh check (unmeasurable counts as a failure, never a pass; amendment 2026-11-21 under the proposed
   article smaller-context-never-costs-coherence). Check state lives in one file per job, `.instar/state/job-mode-checks/<origin>-<slug>.json`, and every
   read-modify-write of a job's state (completion results and operator clears) runs under a per-job lock in the server
   process, so overlapping completions cannot overwrite each other. Each launch captures the job's check generation; an operator
   clear advances it, and a result from an earlier generation is discarded, so a stale probe can never restore a
   cleared failure. The single retry is reserved under the same lock.
   **Configured versus effective mode.** Change 3 gives the configured mode (synced). A failed check sets only a local
   suppression, so the effective launch mode is full on this machine while the configured mode, including an operator's
   job-mode override, is left untouched and resumes after a passing probe.
   **Positive control, once per Claude Code version per machine.** Before the first pass for a new Claude Code version
   is accepted, the server runs tiny probes in a temporary directory holding a CLAUDE.md, an AGENTS.md, a `.claude/CLAUDE.md` and a
   memory index, each with its own sentinel: with exclusions off, and with only CLAUDE.md excluded (the AGENTS.md
   fallback), the checker must find an `instructions` record for each source it claims to check; with the full job-mode
   settings it must find none. If any source's record is not visible when it should be, the transcript format no longer reveals loading, and
   every check on that version is recorded as unknown instead of pass. A failed job returns to job-mode for one probe run when
   either version changes or the operator clears it (`DELETE /jobs/:slug/job-mode-check`), because the exclusion's
   behaviour can only change when one of those two programs changes.

## Multi-machine posture

- Job-mode text: unified by generation. It is rendered in memory from the running instar version at each launch and holds no per-machine value; nothing is stored or synced.
- `.instar/state/job-mode-checks/` (per-job files) and the positive-control result: machine-local BY DESIGN. machine-local-justification: physical-credential-locality — it records how this machine's own Claude Code binary and login honoured the flags; another machine may run a different Claude Code.
- The operator override map and the `instructions` field live in config and job definitions, which already sync.

## Frontloaded Decisions

1. Mechanism: `--settings` with `claudeMdExcludes` (CLAUDE.md, AGENTS.md, .claude/CLAUDE.md) and `autoMemoryEnabled: false`, plus `--append-system-prompt` with text rendered at launch.
2. Explicit `instructionsMode` spawn option, set only by JobScheduler.
3. Resolution order: config override keyed by origin and slug, jobs.json field, verified shipped jobs on a reviewed allowlist; user, legacy and unverified jobs default to full; no Markdown frontmatter field.
4. Unknown values refused.
5. Restricted spawns (confinement, confined tools, required tool confinement, no auth env) and the triage spawn skip job-mode.
6. Transcript check on first run per job per version pair, unknown retried up to three runs; re-probe after a fail on version change or operator clear; per-job state files under a per-job lock; a positive control per Claude Code version gates any pass.
7. Render failure falls back to full, reported per incident.
8. Codex job sessions are out of scope here; a work card under the context budget project covers them, and a synced job in job-mode runs full on Codex until then.
9. Rollout gate `scheduler.jobModeInstructions`: omitted means live on a development agent and dark on the fleet, until graduation (Maturation plan).

## Maturation plan

- **test-agent-live:** a throwaway agent home with one shipped reviewed job and one user job; the scheduler spawns both through the real path, and the run transcripts show the reviewed job loaded no CLAUDE.md, AGENTS.md or memory index while the user job loaded them.
- **per-account checks (amendment 2026-11-21, from the second-pass review):** the positive control runs and is cached
  per Claude config home, and a job's pass is recorded per config home for the current version pair; a run under a new
  config home is checked even when the version pair is unchanged.
- **constitution fit (amendment 2026-11-21, after the operator approved the article "A Smaller Context Never Costs
  Coherence"):** at merge no job runs in job mode (`SHIPPED_JOBS_REVIEWED_FOR_JOB_MODE` is empty and no override is
  set), so the code is inert. Before any job is switched over, the article's obligations apply: a paired replay of
  recent runs of that job, full versus job mode, outcomes graded blind and every token counted through completion
  (tracked on the context budget project's card for the paired replay), with outcome checks continuing while live.
- **dev-agent-live:** live on Echo from the release that carries it, with commitment detection opted in by override. For 3 days, compare first-turn cache writes and reads of job-mode runs against the same jobs' last 3 days before the release, and count transcript-check results (pass, fail, unknown).
- **fleet:** ships under a dev-agent gate (`scheduler.jobModeInstructions`, omitted means live on a development agent and dark on the fleet), then the fleet default flips after graduation.
- **graduation criterion:** on Echo over 3 days, job-mode runs show at least a 40 percent drop in first-turn input tokens for the opted-in jobs, the transcript check records no fail and fewer than 5 percent unknown, and no job-mode run shows a job failing its task where its full-mode runs succeeded. Zero job-mode runs is not a pass.
- **dark-window:** at most 14 days on the fleet after Echo graduates; if the fleet flip has not happened by then, the reason and a new date are recorded on the context budget project's job-mode card.
- **ladder:** test agent, then Echo (dev agent), then the fleet default flip in a later release.

## Non-goals

## Risks and answers

- *A job loses an instruction it relied on.* Only verified shipped jobs default to job-mode, each listed in the PR; user jobs change only by an explicit opt-in; the job-mode text says what was not loaded and where it is.
- *Job sessions stop writing auto-memory.* `autoMemoryEnabled: false` also stops writes; jobs record learnings through the server's memory and feedback routes, which the job-mode text names.
- *Safety rules.* Project hooks still run in non-confined job-mode sessions (seen in the measured transcripts); the job-mode text restates the core rules.
- *Claude Code changes or ignores the setting.* The transcript check catches it on the first run after the change and falls back to full.

## Rollback

Set an override to `"full"` for any job in config (survives updates), or revert the PR. No shipped job file or lock entry
changes. A revert leaves behind only inert data: the `scheduler.instructionsOverrides` config key and any jobs.json
`instructions` fields (old readers ignore both) and the per-job check files under `.instar/state/job-mode-checks/`
(nothing reads them). Clearing saved check results is separate from reverting: the operator clear route, or deleting
that folder.
