## Plain-language overview

The design gives Justin a small number of top-level conversations for each effort while keeping delegated worker conversations intact. The dashboard and mobile app would show a tree of efforts and conversations, with brief, source-linked updates at the top. A user can open the original worker history, see why it was placed there, and correct a wrong relationship. Worker activity stays quiet by default in Instar's view; Telegram and Slack continue to hold the original conversations and can be opened from deep links.

**Overall assessment:** this is a strong product direction because it formalizes a working delegation pattern Justin already uses and directly reduces the cost of finding active work. The strongest version is an Instar-owned Conversations hierarchy with durable source-linked rollups and easy correction. A bot-controlled Telegram or Slack sidebar cannot be the foundation; those clients should provide original history, deep links, and on-demand status. Historical placement should begin as suggestions because real topic names collide and existing work links are sparse. The first release can deliver useful navigation before claiming automatic organization or perfect topic-history coverage.

The graph is separate from project/task status and from message routing. Its job is placement and navigation. It does not grant access to a private conversation or alter where a message is sent. The first dashboard view is owner-only; mobile users with limited grants keep their authorized conversation inventory without inheriting the owner's effort summaries.

Telegram and Slack can contribute real navigation and optional organization. Telegram cannot hide an ordinary worker topic through the Bot API, but a future opt-in second worker group could be archived/muted as a whole while retaining topic history. Slack users can group or mute conversations in their own sidebar. The reliable shared hierarchy remains in Instar's dashboard/app.

The same hierarchy also works conversationally: an owner can request an effort status, worker list, or placement explanation inside the existing front-door topic/thread, and can confirm a proposed move there. A worker can link back to the front door. The chat adapter uses the same graph and owner checks as the app, so it creates no competing source of truth.

## Original versus current draft

The initial draft described a hierarchy and app screens but left storage, conflict handling, permissions, and platform limits broad. Review added one mixed effort/conversation forest, immutable placement events, a no-loss source file plus journal transport, visible concurrent-move conflicts, viewer-scoped digests, owner-only shared placement, and a concrete desktop/mobile interaction contract. It also found a privacy weakness in the existing TopicMemory user-context foundation, filed as `fb-ac09bb24-fcd`, and barred reuse of global summaries in limited views. DAWN's review added enforced cross-machine history coverage, explicit timezone rendering, and a claim-versus-verification split so parent reports cannot launder a worker's “done” statement into fact.

## Current findings and disposition

1. **P1: Durable replication, repair, and redaction.** Design choice made: one write-admitted machine commits to a fsynced graph event source; standby corrections forward with signed idempotency, journal transports immutable events, and peers repair gaps from the source. An offline/behind peer shows the last verified tree with the graph revision itself marked partial. Free-text headers cannot enter the unrotated event source until crash-safe delete/forget compaction is proven; derived digests are invalidated on privacy changes. A format audit separated the event core hash from its authorization receipt. Installed `LeaseCoordinator` and `FencedLease` supply a signed lease and epoch; the graph path must bind that evidence to the `WriteAdmission` verdict and event receipt and test a lease change during commit. It must also prove two-machine recovery, standby forwarding, failover refusal while incomplete, and peer-wide redaction. **Open implementation gate.**
2. **P1: Dashboard human principal.** Source inspection found the existing `/dashboard/unlock` operator-session token and `verifyDashboardOperatorSession` verifier. V1 graph routes require this short-lived proof plus ordinary API auth and map it only to the owner; bearer-only calls must fail. Cross-machine re-unlock remains a route-level test. **Design addressed; implementation gate open.**
3. **P1: TopicMemory private summary exposure.** Existing user-context formatting includes the global summary; feedback filed. The hierarchy design disallows reuse and requires viewer-scoped digests and authorized search. **Design addressed; foundation bug open.**
4. **P2: Deep mobile usability.** Written screen contract and 320 px/accessibility acceptance exist. A clickable visual sample passed a scripted narrow-screen path, move/undo, and conflict check; visual review reduced the initial mobile tree noise. Hands-on screen-reader and production-data testing remain activation gates. **Partially exercised; implementation gate open.**
5. **P2: Inference and notice calibration.** A live read counted 166 TopicMemory records (40 summarized, none named) and 170 Telegram-adapter topics (166 named). Fifteen repeated title values cover 30 named topics; the two stores cannot be joined by name or unscoped topic ID. The Initiative snapshot had sparse topic links. Suggestions stay advisory, and automatic placement/default worker hiding wait for a real-topic pilot. **Open pilot gate.**
6. **P1: History coverage and outcome verification (DAWN).** A large history injector once exposed an old 2 KB slice after a 20 KB handoff, without warning the session it lacked the tail. Single-machine logs also hid half a conversation; a timezone suffix loss caused a wrong local-time reading. A parent report repeated a worker's “done” claim for work committed but not landed. V3 now requires a bounded recent slice plus verified catch-up read before complete coverage, an independent source inventory with machine/store high-water marks, recoverable memory-bearing ranges after machine loss, full timezone offsets, and separate claim/evidence fields. A done badge/notice requires evidence for the actual outcome; a narrow verified result may coexist with an explicitly partial digest. **Design addressed; implementation gate open.**
7. **Peer review: DAWN.** Her verified MacBook reply supplied three concrete topic-history cases and one objection to upward report semantics. She supported the tree shape, owner-only placement, and advisory suggestions. The Workstation thread has no reply; her MacBook review is sufficient first-hand peer input but does not substitute for the owner's required frontier GPT/Claude passes. **Substantive review received and incorporated.**
8. **Frontier model review.** Codex CLI reported `gpt-6-astra`; Claude Code was invoked with `--model opus` and its response self-identified `claude-opus-5-5`.
