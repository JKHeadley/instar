# Fast focused preflight before full PR verification

## Problem and evidence

Local Verify already runs `npm ci`, build, and lint before it claims the host's one full-suite slot. The existing pre-push smoke runner selects affected tests with Vitest, caps breadth, and retries failed files once. It does not run inside Local Verify, so a PR that bypassed or outgrew the pre-push smoke can spend a full verifier run before a small changed test turns red. In the 2026-10-30 06:23 to 2026-10-31 06:23 UTC baseline, 18 of 47 completed checks were red. Seventeen red records named a failed lane: nine unit, seven integration, one E2E. Those are only an upper bound for preflight detection; the journal does not show how many failures a bounded affected-test selection would catch. Adding a check to every green PR can reduce throughput if it costs more than the red work it saves.

## Decision

Add an optional, bounded **PR-only focused preflight** after the existing build and lint steps and before Local Verify takes its full-suite slot. `main` verifies never use it. The preflight reuses the pre-push smoke selection helpers and Vitest JSON parser with tighter verifier-specific caps, using the verifier's exact `baseSha` and synthetic merge worktree as inputs. It does not infer `origin/main`, a branch upstream, or a stale pre-push base. The existing build/lint phases remain the early build check; this increment does not repeat them.

The feature has `off|observe|enforce` modes, default `off` on every machine. `observe` runs the focused check and records its time and result, then runs the full verifier regardless. **Enforce is eligible only for the parent's automatically rediscoverable namespace merge candidates** (open, non-draft, stable head, review precheck passing); an explicitly requested PR outside that gate uses observe behavior even when the host setting is `enforce`, with the effective mode stamped on its record. That prevents a lease move from stranding an outside-namespace PR whose request is not auto-recreated. For eligible candidates, `enforce` stops before the full suite only when two complete, bounded Vitest JSON reports show at least one assertion failure in the **same selected file** on both attempts **and** the installed trusted unhandled-errors reporter shows zero unhandled errors on each attempt. Missing or unreadable reporter evidence is unknown and proceeds to full verification. Exit status alone, a collection/configuration crash, unhandled error, signal, timeout, malformed or incomplete report, zero-test retry, or failure in a different or unselected file cannot establish stable red. It creates a normal red Local Verify record with reason `preflight-red`, selected and failed-file metadata, and no success status. A green, skipped, timed-out, missing, malformed, or infrastructure-error preflight proceeds to the complete unit, integration, and E2E lanes after cleanup is confirmed; only the existing full-suite evaluation can create a green merge-authorizing record. No preflight result derives, extends, or refreshes a prior green record. A red preflight may be a false red and costs liveness; it cannot authorize an unsafe merge. The preflight-red record carries a bounded, validated optional `preflight` field with mode, outcome, reason, elapsed time, exact head/base, selected-file identities/counts, and repeated failed-file identity; `validateRecord`, peer import, journal, and status preserve it. Missing or malformed metadata cannot create `preflight-red` or green authority.

Selection uses `git diff --name-only <exact baseSha>...HEAD` in the synthetic merge worktree, verifies both endpoints, and passes that exact base SHA to the existing pre-push affected-test selector; it never calls its upstream/HEAD~1 base resolver. Then it runs `vitest list --filesOnly --config vitest.push.config.ts --changed <exact baseSha> --json=<bounded report file>` and `vitest list --config vitest.push.config.ts --changed <exact baseSha> --json=<bounded case report file>` before `vitest run --config vitest.push.config.ts --changed <exact baseSha>` for the selected files. It reuses the selector, parser, and harness classifier with **stricter Local Verify caps** pinned in the installed verifier: 40 changed files, five affected test files, 200 affected test cases. The push config's known-flaky exclusions mean this is a subset of changed tests; observe telemetry counts eligible and excluded files separately. Pin the push config and arguments; no pool-shaping CLI override may turn its targeted one-worker lane into a suite admission. Listings have process, CPU, output-size, and time bounds although they do not use a semaphore slot. The 90-second aggregate wall-clock cap begins before selection and includes targeted-lane wait (currently up to 60 seconds), both listings, first run, retry, process-tree teardown, and cleanup. A breadth breach, no selected tests, or indeterminate selection is a named skip, never a pass or a red.

Each attempt gets fresh `TMPDIR` and `TMUX_TMPDIR` through the existing `seams.fs.mkdtemp('lv-*')` helper under its short private `/tmp` root; macOS tmux socket paths cannot use the long verifier worktree path. Vitest cache and bounded result files live in the verifier's isolated run tree. Clean all of them before full lanes. A directory does not isolate TCP ports on macOS: test-agent rehearsal must prove selected files use ephemeral/noncolliding ports, or that file class stays excluded from preflight. The preflight process and descendants obey head-change cancellation. On timeout or error, terminate the process group and confirm its workers exited within a bounded grace period. Only then may the full suite start. If cleanup cannot be confirmed, return a recoverable verifier error and requeue rather than overlap uncertain descendants with a suite. A dirty worktree after preflight is traced to the preflight and returns a recoverable verifier error; the next bounded retry gets a fresh worktree and bypasses preflight. It is not silently treated as a PR failure or carried into full lanes. Any uncontained external side effect found in rehearsal disables that file class. A test process can tamper with its own preflight report because it runs under the same OS user; the report is never a green authority, and missing or inconsistent evidence falls back to the full suite.

The preflight time is accounted for explicitly. Set `effectiveTotalActiveMs = 120 minutes + (enteredPreflight ? 90 seconds : 0)`, where `enteredPreflight` becomes true immediately before the first selection step; a later skip keeps that same 90-second extension. Off/main or verification-ineligible runs never enter it. An outside-namespace PR under a host `enforce` setting is **enforcement-ineligible** but still enters preflight in effective observe mode and receives the extension. The parent orchestrator's existing active-time accounting and slot-wait exclusions remain the clock rule. Record elapsed preflight time and remaining active budget before/after. The later stages retain the original 120-minute allowance because the added stage can consume at most its matching 90-second extension. A preflight timeout includes teardown inside the 90 seconds; the extension is a policy-hashed constant, not a mutable environment override.

The preflight skips when the diff or test harness/config has changed in a way that makes affected-test discovery untrustworthy. Reuse the existing harness classifier/globs, including `tests/vitest-setup.ts`, `scripts/lib/pre-push-scope.mjs`, `.npmrc`, `patches/**`, `tsconfig*.json`, `vitest*.config.*`, package manager locks, and verifier orchestration; do not maintain a second incomplete path list. These paths still receive the full suite. A failed changed file is not dismissed as flaky solely because the first retry passed: a retry pass is an observation and the full suite still runs. `enforce` short-circuits only the stable repeat-red case. Existing isolation re-runs in the full verifier remain unchanged.

An enforced stable-red record creates **one automatic authoritative same-head replay obligation**. Persist the obligation before publishing/dequeueing the `preflight-red` record. On boot, lease acquisition, and peer-result import, reconcile **both** crash directions before normal queue processing: a durable preflight-red record without its obligation recreates that obligation **only after** an authoritative PR read confirms the PR is still open with the same head, target branch, and policy; an unreadable PR stays historical/pending without enqueue, and a stale record never resurrects a cancelled obligation. An obligation without a matching validated exact-head/target preflight-red record is cancelled before enqueueing any replay, leaving the original interrupted attempt to the parent orphan recovery/requeue path. A crash at either boundary cannot strand the PR or run a phantom replay. The durable once-per-(repo, PR, head, baseRefName, policy) marker has `pending | running | retryable-error | completed | blocked` states and survives restarts. Make the first enqueue attempt within 15 minutes of the red result; this is an attempt deadline, **not** a promise of admission or execution time under contention. The normal Local Verify queue admits replay at ordinary priority on an eligible coordinator or compatible peer, with a **fresh enqueue timestamp** behind already-waiting PRs of equal priority; it never inherits the original PR's `firstQueuedAt` or throughput label priority. If the queue is full or held, admission retries use persisted exponential backoff from five minutes to one hour, at most twelve attempts and 24 hours total; after that the obligation becomes `blocked`, enforcement turns off for new attempts on that host, and the existing queue-repair path runs. Routine waiting is pull-only status. After three hours without admission and no advancing full-suite holder, raise one aggregate host-level stalled-replay attention item, deduped for 24 hours and downstream of a failed queue-repair attempt. One real capacity-restored event may rearm a blocked admission **once total** for that key; a second exhaustion remains blocked until head change or auditable repair. It never creates another obligation or an unbounded timer loop.

The replay bypasses preflight and cached `preflight-red` failure handling, runs all three full lanes, and uses the latest exact base SHA for that head and target branch plus the normal peer proof and merge authority gates. **After the first enforced preflight red for a `(repo, PR, head, target, policy)` key, every subsequently admitted verify for that key bypasses preflight**, including after a completed full-red replay, infrastructure exhaustion, base SHA refresh, or explicit same-head request. Keep the marker as a bypass tombstone until a target-branch retarget, new PR head, closed PR, or policy change invalidates it; these transitions cancel old in-flight work. The new target gets its own exact-head/baseRef record and at most one independent replay. A completed authoritative full replay closes the pending work but retains the bypass tombstone. If it is green, its full-suite record supersedes the preflight-red record for **that exact `(repo, pr, headSha, baseRefName)` key** and the PR proceeds normally; if red, retain the full red result and do not schedule another replay. A same-head request while replay is queued joins that work rather than returning a permanently cached preflight red.

An infrastructure `error`, peer loss, or crash after admission moves `running` to `retryable-error` on boot/completion, with the same marker and a fresh queue timestamp. Allow at most two automatic execution retries with five-minute backoff and recheck exact head/target before each; errors do not count as an authoritative full verdict. After exhaustion, mark `blocked`, turn preflight enforcement off for new attempts on that host, and expose the blocked replay and underlying verifier error in status. The existing Local Verify infrastructure recovery path runs first; one deduped stalled-replay attention item is raised only if that recovery fails, and the obligation remains durable. One later healthy main verify or verifier upgrade may rearm the blocked obligation **once total for that replay key**, after rechecking the PR head and target; repeated errors stay blocked until a new head or explicit, auditable repair operation creates a new attempt. There is no automatic daily rearm or unbounded retry loop, and no false green. This preserves a route to green PR liveness when infrastructure recovers but cannot bound wait while all suite slots remain occupied or the verifier remains broken. The possible throughput gain is earlier scheduling of green PRs, not saved total suite minutes. Echo owns recovery without asking Justin to run a diagnostic.

Telemetry is one bounded `preflight` event per PR attempt: exact head/base/target, mode, eligible/excluded/selected file and case counts, elapsed and added green latency, host contention, remaining active budget, `pass|red|skip|timeout|error`, and skip reason. Observe joins its hypothetical stable-red verdict to the **actual full-suite result on the same head**: stable-red/full-red with same failed file, stable-red/full-red elsewhere, stable-red/full-green (false-red signal), and other outcomes. Estimate queue time saved when a stable red returns before that attempt's actual fail-fast full-run duration, and account for the later automatic replay as added machine time; do not claim net suite minutes saved. Report timeout/skip rate, ready-to-green latency, completed green PRs per hour, machine minutes per green/merged PR, and false-red count per host. Observe qualifies **detection accuracy and added overhead only**; it cannot demonstrate the scheduling gain. Do not begin an enforce experiment if any observed stable-red/full-green disagreement lacks a resolved cause and replay mitigation. After a bounded single-host enforce experiment, continued enforcement and expansion require measured improvement in ready-to-green latency **and** no decrease in completed green PRs per hour over a comparable off baseline; added machine minutes are reported as a cost even if those throughput criteria pass. A skipped preflight is never a passed check.

## Multi-machine posture

The mode is resolved on the machine that executes a verify (Studio, Mini, or M5) at child spawn; each peer reports its preflight mode and outcome with its attempt. Installed code fingerprints and existing `verifierVersion`/`policyHash` compatibility checks stay equal; mode is per-attempt telemetry, not a peer policy mismatch. The coordinator accepts a peer's green record only through the existing full-suite and exact-head rules, and imports the validated preflight field even on red peer records. A mode mismatch can change how quickly a red result returns but cannot change what makes green. Rollout and measurement are per host; do not infer M5's overhead from Studio or vice versa. Preflight files and subprocesses remain in that host's existing Local Verify isolated worktree. The replay obligation is coordinator-owned in the same machine-local queue/journal store the parent capacity design uses; only the serving-lease coordinator may publish or enqueue it. On lease movement, the former coordinator stops dispatch; for an enforced result, the new coordinator's watcher rediscovers the namespace merge candidate and starts its own normal exact-head attempt, with its own bounded replay if needed. An outside-namespace PR never receives an enforced early red. Peer records never directly enqueue replay. There is no new cross-machine authority or shared database.

## Rollout and rollback

Ship `off` and keep it off on the fleet. Roll back to `off` at the next attempt; in-flight children keep the mode stamped at spawn, so each record remains interpretable. Do not activate on Studio's `main` path. Existing agents receive the mode and status guidance through `generateClaudeMd()` and `PostUpdateMigrator`; any new config default goes through `migrateConfig()` idempotently. This deterministic substep inherits Local Verify's existing tier0 supervision exception; operational observe telemetry and red-record triage are its escalation layer. It does not add an unsupervised green authority.

## Maturation plan

- **dark-window:** 48 hours with unit, integration, E2E, full suite, and adversarial report/cleanup tests green.
- **test-agent-live:** Rehearse matched full-suite runs with and without preflight on an isolated agent, including integration/E2E repeatability, stale descendants, dirty worktree, ports, and cache; disable unsafe file classes.
- **dev-agent-live:** On Echo, observe one peer for at least 24 hours and at least ten eligible PR attempts, including green attempts and at least one stable-red candidate; if that sample cannot be reached, remain in observe and report the shortfall. Observe must show bounded green overhead, reliable stable-red evidence, and no unresolved false-red signal. It does **not** claim a measured scheduling benefit. If those gates pass, run one 24-hour enforce experiment on that host with automatic rollback to off at its end; continue or expand only if ready-to-green latency improves and completed green PRs per hour do not decline against a comparable off baseline. Repeat per host.
- **fleet:** Opt-in observe then enforce per host, never an automatic flip.
- **graduation criterion:** No unresolved false-red disagreements, confirmed cleanup, improved ready-to-green latency and no reduction in completed green PRs per hour over a comparable sample, with added machine minutes per merged PR accounted for; report sample sizes and confidence limits.

## Acceptance

1. Unit tests cover exact-base selection, all caps, zero/invalid listing, harness changes including `tests/vitest-setup.ts`, excluded files, green/first-red-then-green/stable-red, an assertion failure accompanied by an unhandled error, missing reporter evidence, mismatched or unselected failed-file identity, collection crash, malformed JSON, zero-test retry, timeout, cancellation, cleanup confirmation, budget edge, and mode rollback at next attempt. Only `enforce` stable red records no full-suite lanes; `observe` stable red runs all lanes, and neither authorizes merge. An enforced false red creates exactly one durable same-head/target replay marker and bypasses preflight on replay; base SHA refresh preserves the obligation, target retarget cancels it, queue-full retries stay bounded per poll, replay joins behind already-waiting equal-priority green candidates, and a near-120-minute green run retains its original lane budget.
2. Integration tests use the real Local Verify route and child result pipeline. Observe/off/enforce return honest status and record metadata, including peer red-result import. A missing, malformed, inconsistent, or wrongly bound preflight report cannot create a green or preflight-red record; deliberate same-user tampering remains a stated limit. A timeout with a live descendant cannot start full lanes; a contained preflight leaves their worktree and environment unchanged. A full-green automatic replay supersedes a prior same-head/target preflight red and releases the PR without operator action; stale-head, target-retarget, base-refresh, and repeated-replay cases do not loop. Fault injection on both sides of replay-marker persistence and red-record publication reconstructs exactly one pending obligation when red was published and cancels a phantom obligation when it was not; delayed peer red import after head/target cancellation never resurrects it. Queue-full status is visible and admission retries use the persisted twelve-attempt/24-hour breaker, with at most one real-capacity rearm. Replay executions one, two, and three may each end in infrastructure error; the third error reaches `blocked` with no false green, then a healthy-main or upgrade trigger gives at most one lifetime rearm for that key. A completed full-red replay followed by a base refresh and explicit same-head request uses full lanes directly, never a second enforced preflight red. Lease movement after an enforced namespace red rediscovers the candidate; an outside-namespace requested PR uses observe behavior and never needs replay on the new coordinator.
3. E2E boots production `AgentServer` wiring with the preflight mode dark by default, exercises one bounded PR attempt, and proves the full-suite merge gate remains the only green authority. Observe stable-red/full-green is recorded as a false-red signal and still returns green after the full suites.
4. Build, focused tests, and `npm run test:all` pass. A measured development-agent trial reports ready-to-green latency, completed green PRs per hour, and all added machine minutes including automatic replay; activate only under the same throughput criterion as graduation.
