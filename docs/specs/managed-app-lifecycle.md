# Managed browser and application lifecycle

## Problem statement

Before the November 26 Studio restart, Chief of Staff reported sixteen agent Chrome roots with about two hundred helpers using 12 GB. Process inspection provided no reliable way to tell whom the browsers belonged to or whether their work had ended. Instar needs enforceable ownership at launch and safe cleanup afterward. The parent Bounded Blast Radius standard limits the consequences of any single launch. This design applies it through both a host admission ceiling and an adapter-specific resource containment requirement.

## Proposed design

Extend the existing Machine Care host maintainer to broker Instar-created browser and app instances. Reuse its host authority, audit and pool read surface. The broker is a role in that service, with OS-specific launch adapters, rather than a new daemon. Before starting a new instance, take one slot in a host-wide transaction and record a launch ID, authenticated agent and session, a short purpose, deadline and adapter. The broker owns process creation so the reservation cannot race with spawn. Associate the lease with a verifiable process handle or isolation group and host boot identity. Recover interrupted launches by matching broker-owned process provenance to the reservation. Expire reservations with no process only after reconciliation confirms the launch cannot complete. A stale registration never frees the slot of a process that may still be alive.

Distinguish owned roots, borrowed existing profiles and unmanaged observations. Use the existing PlaywrightSeatLease for the operator profile and BrowserMcpProfileGuard for protected Telegram profiles. PlaywrightSeatLease is authoritative for borrowing that profile. The Machine Care broker projects that seat for reporting and does not keep a second independently writable borrower claim for it. Attachment, renewal, release and closure checks use the same holder and generation. Reject new attachment if the acquired seat, its projection or observed adapter connection is missing or mismatched. Mark the surface stale and hold closure until the authoritative seat lease and adapter observations agree. Rebuild projection from the source. Release only the matching generation with authenticated evidence, without changing another holder’s seat. Test seat without projection, projection without seat, mismatched generations and recovery after agreement. Borrowed operator roots do not occupy managed launch slots. The broker keeps credential profile protections in force and only closes processes it can prove it started. Joining an existing profile grants no right to close it. Revalidate all ownership at close time. Mere process names, CPU use, or absent registry rows never authorize closure. Proven Instar-created orphans can be closed after confirmed owner loss or expiry. Undecidable processes appear in the sweep report with a reason.

Wire the Chrome relogin launchers that use the Chrome DevTools Protocol (CDP) or the regular desktop, generated Playwright browser automation server configuration, normal Chrome helper, and a supported agent app launch entry point. A launch adapter must account for helper processes and OS singleton behavior. A root slot alone cannot bound a browser that fans out. Group the process and its helpers through platform containment and enforce the enrolled host resource policy on aggregate managed use, including process count and memory where the platform provides reliable hard limits. In enforcement, an adapter unable to contain its descendants under the configured policy refuses new owned launches and reports the missing control. Existing shared or operator processes remain outside that managed budget and control. Expose platform capability before enrollment. Test a disposable workload that creates helpers and verify the budget holds while an existing unrelated browser survives. For example, macOS open can return before the intended application starts, and some apps hand work to an existing process. Demand an adapter-specific confirmation of exclusive ownership as a condition of exercising termination authority. Inventory native launcher paths and direct test/tool launches, and publish coverage for each before claiming fleet-wide management.

Explicit task completion and definitive session-end events share the same release path. The deadline timer and hourly sweep reconcile expiry using the closure conditions below. Distinguish a completed task from a finished assistant turn, and a lost heartbeat from a definitively ended session. Attempt graceful closure. A failed close retains the slot and is retried by the bounded sweep before escalating. Audit created, released, closed, still running, unknown and refused outcomes with coarse metadata only. Never store credential profile contents, command arguments, page titles or URLs in the audit.

## Multi-machine posture

machine-local-justification: hardware-bound-resource

PID identity, process handles and slot accounting are local to the physical host. Host-visible inventory and audit summaries use the existing authenticated pool read path, keyed by machine; each machine returns its own freshness and availability. A topic move cannot transfer process ownership or authorize a close on its own. Resolve the original session lifecycle from its host. Deliver operator-facing alerts through the existing one-voice routing.

## Decision points touched

- Process closure — invariant; basis: irreversible-consequence; evidence: closing a shared desktop instance can lose operator state, so closure requires fresh broker-owned identity with no live borrower.
- Slot admission and expiry selection — judgment-candidate; the machine owner sets the ceiling and the launch adapter selects a bounded duration within machine policy. Admission is transactional under the configured ceiling and reports its reason. The root count becomes a hard ceiling only when the owner deliberately sets it as binding, under the direction to add “a per-machine cap [that] refuses a new instance past the limit” (Chief of Staff handoff a1e24c8d-7e0d-4ebc-966c-96180dd674c4). There is no default root count. Below that ceiling, the maintainer judges whether the requested workload fits the host process, memory and activity budget. Explicit off and observe are valid owner-selected modes. Persist the last authenticated and validated mode and policy revision. A previously enrolled host with corrupt, missing or unreadable policy or broker state enters a policy-unknown hold: refuse new managed starts, preserve existing apps and their occupied slots, and record the fault. Return a typed refusal and its reason to the requesting operator or agent through the original launch surface. A refusal never appears as a successful launch. Only a valid policy revision can restore enforcement or switch modes.
- Uncertain owner or process identity — invariant; basis: irreversible-consequence; evidence: PID and profile reuse can point to someone else's application. Preserve the process, count uncertain occupied slots, and report the missing evidence.

## Broker lifecycle and authority

The broker is local and identity-scoped. An authenticated session generation and task handle bind the caller; requests name allowlisted launch adapters and typed parameters. The caller cannot submit an arbitrary executable, argument vector or target PID. Store private operational metadata with restrictive permissions and audit only a purpose enum and noncredential identifiers. The managed pool covers installed agents sharing one broker domain. If more than one operating-system account uses Instar on a host, discovery must show which accounts are enrolled with the same host authority. Until that is verified, report account scope and do not advertise an aggregate per-machine cap. Same-user processes outside the broker can interfere with same-user state. The broker is not an operating-system security sandbox.

In one serial transaction reserve capacity, persist intent and assign the broker generation and launch ID. State progresses from reserved to starting to running to closing to exited. A terminal state cannot be revived by a delayed spawn message. Close and borrow transitions serialize. Closing rejects new borrows and renewals. Only a closer holding the current generation may act. Durable start intent plus an identity-preserving containment handle must cover crashes between spawn and receipt. Keep unresolved managed starts occupied until identity is recovered or a trusted process exit is confirmed. Broker restart fences the old writer. Repeated lifecycle events are idempotent and late events identify their original task and generation. Wall-clock rollback cannot extend an existing duration. Use monotonic time while running and persist a platform monotonic deadline with the boot identity. If the same-boot deadline cannot be recovered, reconcile it as due and still require closure proof. A verified different boot ends old local process leases without matching or signaling any new-boot PID.

The broker may close through a kernel process handle or exclusive containment with identity-preserving closure, such as a verified connection to the dedicated process. Name, PID, profile flags and timestamps support diagnostics. They cannot make a later bare-PID signal safe. LaunchServices and singleton paths remain report-only until their adapter has exclusive ownership proof and a close primitive that does not race PID reuse. While closing denies new borrowers, re-run adapter keep checks immediately before the graceful close against the verified process handle. Retain the slot and defer on a held or unreadable check. Keep adapters observation-only for closure if they cannot make the checks and the close safe in sequence. Disable competing teardown on managed paths and retain the pre-existing behavior when off. A seat expiry does not prove a borrower has left. Require explicit borrower release or confirmed session end with independent lifecycle corroboration before close.

## Cap, expiry and ambiguous state

A configured ceiling belongs to the broker domain and applies across enrolled agents, including mixed deployments. Every enrolled new launch reserves a slot before acting, including an adapter configured to observe its own cleanup. It retains that slot until confirmed exit or proof the attempt cannot produce a process. An enrolled adapter unable to reserve cannot fall back to a direct spawn under enforcement. Observed-only admission reports candidate decisions and exposes that it did not enforce the cap. An older or off-mode agent outside enrollment is reported as uncovered. Never evict when an operator lowers the ceiling. Refuse future launches until lease count falls below it. Unknown observations outside the managed set are reported but consume no broker slots. An unmeasurable enrolled reservation remains occupied. No universal numeric default is imposed.

The owner chooses the deadline policy and may enable a protected-operation class. An adapter requests a finite grant suited to measured or expected task duration. The arbiter is the authenticated machine owner policy. The design imposes no universal maximum grant. Where the owner explicitly sets a maximum, it is a policy preference that can be revised without altering ownership or closure floors. The authenticated task owner requests renewal and the adapter validates fresh evidence of active work against that policy. Every owned launch grant has a finite reconciliation deadline because abandoned owned launches were the incident and a cap alone leaves them occupying every slot indefinitely. An operator-owned persistent browser can be borrowed with a bounded borrow lease; that deadline never confers authority to close the persistent browser. Verified active work can receive another bounded grant within the same configured ceiling, with no lifetime renewal count. Replayed evidence never extends a grant. Renewals are idempotent per task evidence generation and do not create automatic renewal loops. If the work or policy is ambiguous, preserve the process and decline renewal or new launches when the configured cap requires it. If a credential flow borrows a protected browser, its seat and borrower authority continue to govern access. Deadline expiry authorizes reconciliation, not closure. Closure on expiry requires an exclusive lease admitted to an expiry-safe class, no live task claim or borrower, and successful identity and keep checks. A standing owner session can outlive a disposable task. An authenticated expiry-safe grant that has elapsed can retire the task claim while the standing session stays live only if the task registry confirms retirement or the adapter independently corroborates that the work finished through its dedicated workload handle. Missing renewal or protection evidence cannot corroborate retirement. If a delayed renewal is plausible and work cannot be measured, keep the lease occupied. Serialize that corroboration and the close transition with authenticated renewal. Explicit task-end evidence applies to the owning task independently of borrower count. A live task claim, uncertain task or borrower status, an unreadable safety check, a protected save or an active credential flow retains the instance and its slot. These holds take precedence over expiry. Record the deadline and the actual transition independently. Hourly reconciliation follows the direction that “an hourly sweep closes anything unowned or expired and reports what it closed” (Chief of Staff handoff a1e24c8d-7e0d-4ebc-966c-96180dd674c4), subject to the ownership and safety evidence above. It is not a measurement of task completion.

## Reconciliation evidence

Each sweep records its timestamp, broker generation, measured occupancy, uncertain states, reconciliation actions, and directly observed outcomes. Record managed root and descendant process counts and attributable memory before and after close and report unknown measurements. Echo promotion compares these readings with an equivalent workload baseline and confirms resource recovery against observed exits. Track time spent in parked and unresolved slots, rejected launches by reason, and safe launch availability before and after. Graduation requires improving resource pressure without concealing a loss of launch availability behind held slots. For recoverable close failure, reacquire the same launch in a generation-fenced, idempotent retry and revalidate identity before acting. Retain the slot if the process remains alive or cannot be measured. Keep the existing Browser Care audit and breaker interface. The host maintainer chooses a bounded scan budget using measured adapter cost, operator activity and available machine capacity. Charge each probe and close attempt to that budget and persist the fair cursor when it runs out. The hourly sweep still emits its receipt under load or while retries are paused. Recheck cooperative close and observed exit under the same launch identity. Recoverable failures use per-launch increasing backoff under the host maintenance breaker; repeated failures park that launch after the bounded budget for its close episode is exhausted. Repeating the same refusal, even with a fresh timestamp, does not unpark it. A parked launch remains eligible for a read-only probe within the normal fair scan budget, with no automated close attempt on unchanged evidence. A verified change in the prerequisite that caused the failure, such as the target’s cooperative close endpoint recovering, or an authenticated operator decision opens a new episode. Bound episode reopening under the existing host breaker so unstable observations cannot repeatedly reset the action budget. Assert that total close attempts stop growing across repeated sweeps in the sustained-failure test. A failing adapter cannot starve healthy adapters. Bound attempts per pass by the wall-clock budget and prevent overlapping sweeps with the existing host lease. Stop acting when identity is unknown. Report repeated sweep failures through the existing degradation report. The sweep does not raise operator notices. Retain bounded metadata-only receipts in the existing Browser Care audit. Test backoff progression, breaker recovery when fresh evidence arrives, and budget exhaustion during sustained failure.

## Maturation plan

- **test-agent-live:** Run disposable production-path tests under an isolated broker and prove supported launch paths, mixed clients, ownership safety, expiry, cap and hourly reconciliation.
- **dev-agent-live:** Observe on Echo for this rollout. A successor development agent with equivalent platform and adapter coverage can satisfy the development-agent rung. Compare intended decisions with measured inventory and disposition, then enforce on an enrolled host with a machine-specific cap.
- **fleet:** Ship default-off with a registered maturation track. Fleet default-on is a separate reviewed graduation decision after the development-agent enforcement receipts and platform launch coverage are available. Echo evidence is a deliverable of the current project. Fleet graduation takes the registered development-role evidence and is independent of the name of the pilot agent. Upgrade generated MCP entries and existing managed browser helpers through idempotent migration, including existing built-in skills where changed.
- **graduation criterion:** Publish adapter-by-adapter receipts for owned, borrowed, protected, unowned and stranded states. Demonstrate a normal user journey from each supported launch surface and no interruption of a protected profile or user-owned process. Keep uncovered launch paths visible in the coverage ledger. Fleet enforcement can graduate only when ordinary supported launch paths are covered and, on an enrolled host, no supported adapter silently uses the old direct-spawn path. Off and observation deliberately preserve existing choices and expose that their resource ceilings are inactive.
- **dark-window:** Begin on release. The registered maturation track reviews evidence weekly. At the first review with missing or failed receipts, record a dated extension with a named evidence owner or roll back. Repeated extensions require independent graduation review. Fleet enforcement remains off while graduation evidence is incomplete.

## Existing Machine Care foundation

Extend BrowserCareSweep and the existing macOS browser launch, renew and completion helpers. Reuse the Machine Care pool read and audit surface. Adopted profile matches and all pre-upgrade ledger rows are inventory-only because they predate broker launch proof. Retain and recheck the current activity, open sign-in repair, download, protected profile and unsaved or unreadable tab safeguards at closure. The report records the actual mode and distinguishes observed candidate decisions from completed process actions. Test the visible status against the observed process outcome. ## Launch adapter coverage

| Entry point | What establishes ownership | What releases the lease |
| --- | --- | --- |
| macOS `chrome-launch.sh`, `chrome-close.sh`, `chrome-renew.sh` | Broker-spawned dedicated instance. An existing profile reports a borrowed seat. LaunchServices adoption stays observation-only. | The close helper releases its own lease. The renew helper must prove the same task and session generation. |
| Linux `xdrive.sh` and `x-drive.py` | The native launcher creates the dedicated instance through broker containment. | Its native close path releases the lease through the broker rather than signaling another process. |
| Windows and WSL `ndrive.sh` and `native-drive.ps1` | The Windows broker holds the native process or containment handle. Linux process state cannot establish Windows ownership. | The native completion event releases the same Windows lease. |
| CDP relogin, plain relogin and passkey proof | The proof or enrollment owner and job generation substitute for a person’s session when an Instar background job launches a browser. Identity must be exclusive before closing. | The verified terminal job or lease-specific completion signal. |
| Generated Playwright Model Context Protocol (MCP) server | Use an Instar-owned connector to reserve and launch an exclusive browser before the upstream MCP server attaches, or use a pinned audited transport that reserves at actual browser creation. Starting the MCP server alone occupies no browser slot. Update init, setup (including Codex TOML), and PostUpdateMigrator. Any installed transport that cannot enforce admission at browser creation is reported as uncovered and cannot auto-start directly for enrolled enforcement. Borrowing the shared browser remains subject to the existing seat and profile policy. | The browser context releases the borrow or the owned lease. A new borrower cannot attach once closing begins. |
| Managed agent app launcher | Admit only registered native launch adapters supporting verifiable exclusive ownership or an explicit borrow result. | Completion for that launch ID, confirmed owner termination, or expiry under the full closure conditions. |

Use `SessionManager` terminal events to prompt reconciliation against the owning session UUID and generation. Resume reconciliation on boot. Preserve the lease if an event has ambiguous ownership, the agent still has a live session of that generation, or the source is unavailable. Maintain a per-adapter migration and coverage ledger. Unknown desktop apps remain in inventory without granting cleanup authority.

## Simplest robust route

`simplestRobustRoute`: extend Machine Care and its Browser Care inventory and sweep. Add authoritative launch reservations and identity-preserving adapters inside that existing host role. An inventory-only extension cannot reserve before spawn or prove process identity, and the existing shared browser seat regulates access exclusively. A separate service would duplicate host leadership, reporting and deployment with no added ownership proof. Retain a single Machine Care authority and reuse the existing seat lease for shared-profile admission.
