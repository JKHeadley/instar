# One owner tap to add a reviewed set of Chief of Staff projects

## Problem statement

The Chief of Staff's project list is also the front door for the conversation tree. A project conversation that is not bound into that list remains outside the project hierarchy. Justin wrote on 2026-11-26 (Telegram topic 141385, message 4531413501583092), “We're still showing project chats outside of the projects group.” On 2026-11-21 (topic 141385, message 146769), he directed that each project have its own session, tracked cards, and project entry, and said, “Please make sure each project has its appropriate emoji prefix in telegram and in the apps.” The current `POST /chief-of-staff/projects` route requires the dashboard PIN once per binding. Adding a set therefore requires repeated PIN entry, even when one owner request calls for the same organization work.

The change adds a single-use, owner-tapped batch ask. An agent may prepare an exact list of bindings and show the owner every project name, goal, repository, completion checklist, and source messages in one private review surface opened from the owner’s Telegram or Slack conversation. The owner makes one approval tap on that complete set; the first valid decision wins and duplicate entry links become inactive. The ask itself creates no project. Only the owner's authenticated tap on the exact review surface can apply its disclosed drafts. The tap is limited to the stored set; the agent cannot add, remove, or edit an item after the owner sees it.

## Proposed design

### Draft request

Add `POST /chief-of-staff/projects/bind-batch-ask`. It accepts an explicit list of candidate bindings and citations to the owner's request messages. It does not accept a PIN and does not write a binding. It is available only when `chiefOfStaff.projectBindingBatch.enabled` is true and the server can authenticate the current callback receiver. The generic route accepts project-specific repositories and completion checks; it does not require a pull request or a particular repository for unrelated projects. The project-binding drafts use the `JKHeadley/instar` repository and include proposed agent-verifiable completion checks. These checks are proposals, not attributed to Justin; the owner approves the exact criteria together with the bindings. Each also carries the quoted two-message source evidence, exact conversation key, and a project-specific goal and done checklist.

Before sending an ask, the server:

1. Reads the complete Chief of Staff binding view and refuses if it is unavailable.
2. Verifies every cited source as a current, inbound message from the verified owner, using the same source resolver, identity map, and attribution checks as owner pause asks. It stores the exact whole text and marker; callers cannot supply a quote that differs from the source. Approval copies are delivered only to verified one-to-one owner conversations, never to shared project groups, and the transport resolves the owner recipient from the authenticated identity map rather than accepting a caller-supplied destination.
3. Rechecks that each proposed project or child conversation has a valid conversation key accepted by the shared `isValidConversationKey` parser and present in the current authoritative conversation graph, is not already bound, and appears only once. A running process is evidence for drafting, but it is not a binding prerequisite. The current authoritative conversation graph and owner-backed project identity determine whether a stopped or old topic can be bound.
4. Validates every binding using the same `ChiefOfStaffStore` rules as the single-bind route. Each draft has a nonempty goal and a completion definition. A project with a finite deliverable may use agent-verifiable checks or owner judgment, depending on how completion can honestly be known. Every judgment-only item is labeled as owner judgment, and every deterministic item names its observable evidence. An ongoing stewardship project uses an explicit lifecycle check that says the owner retires or closes the responsibility; it is never marked complete from a routine health report alone. Every project-binding draft has its `JKHeadley/instar` repository link where that repository is the source of work. The owner can change proposed goals and completion checks by declining and requesting a revised exact batch.
5. Stores a deep-copied canonical draft set and its hash in the replicated Chief of Staff journal before any message is sent. It renders the entire set in one private interactive review surface reached from each available linked Telegram and Slack conversation. The review lists every project binding and evidence-backed parent placement in plain words, shows the relevant source citations, and includes approve and decline controls beside the disclosure. The complete operation set appears in one private, scrollable review surface with the approve and decline controls fixed beside the disclosure. It does not split the owner’s decision into separate approvals. If the surface has to load long content in chunks, the chunks remain part of one review page and one immutable hash; the controls stay unavailable until all content is loaded. The owner makes one decision on that complete surface. Platform messages are only links into the private review surface, so the channel’s text limit cannot truncate the disclosed set. Channel copies are independently delivered; an outage in one does not disable a complete copy in the other. Shared project groups never receive draft or source text. A delivery retry reconciles exact message records before retrying, never creating a second ask.

The ask ID is random and single-use. The task instruction is that one tap binds exactly the listed drafts and nothing else. This ask grants no standing authority for future project bindings; any future delegation must be a separate, explicit, scoped owner choice with its own expiry and revocation path. The review surface has approve and decline controls bound to the exact ask ID; the hash, full drafts, per-channel message coordinates, and current callback receiver epoch remain in the durable replicated ask record. A fresh ask replaces no other ask and cannot change a prior ask's contents. Message coordinates are not a credential and are replicated with the ask; authorization still comes only from the authenticated owner callback on the currently admitted receiver.

### Owner tap

Extend `ChiefOfStaffLoop.ownerTap` for this one action. The Telegram or Slack adapter must already have authenticated the owner against the configured owner identity. The loop also requires the tap's chat and message IDs to equal those stored with the ask. It reloads the exact pending ask, verifies its hash, re-verifies every owner source message, and re-reads the full binding view and authoritative conversation graph. A temporarily stopped session does not invalidate its project identity. Before the owner tap records approval, any missing or unreadable source, expired ask, changed source, newly bound topic, missing or changed conversation identity, incomplete graph, or mismatched message refuses the whole action before any binding or placement write. Once approval is durably recorded, a conflict caused by a concurrent edit is isolated to that exact entry; unaffected approved entries can continue, and the conflict is reported in the terminal result.

A decline records a terminal declined state for this exact ask and performs no binding writes. After all approval checks pass, the loop records the owner's approval against the exact ask in the replicated journal, then drains only the stored bindings. Turning off the intake flag prevents new asks but does not abandon an already approved batch; an exact approved batch continues under the existing worker until it reaches a terminal result. A repeated delivery is idempotent: bindings already present with the exact draft content and batch identity are counted as completed; a conflicting binding prevents overwrite and blocks only that entry. A later retry does not reject its own earlier writes as “newly bound”; it reconciles the exact record first and resumes missing members. If a durable write fails partway through, the ask remains visibly in progress. The worker retries after process restart and on durable journal-health transitions. For known write errors while the journal reports healthy, each failed attempt increases the delay exponentially with jitter; a token-bucket budget is sized from measured journal capacity and queue depth, and one circuit breaker stops reads when that budget is empty. An exhausted circuit creates a durable agent-owned recovery item for `ChiefOfStaffLoop` to inspect on its normal project tick; the item carries the exact operation, error, and next permitted attempt. `ChiefOfStaffLoop` owns recovery, and a successful repair or verified health transition reopens one token. Repeated “healthy” status alone cannot refill the budget. Disjoint entries may reconcile concurrently up to the shared capacity controller, while writes to the same conversation key remain serialized behind an entry fence. When the journal reports unavailable, no read is attempted. A persisted event cursor prevents missed recovery notifications across restart. The owner does not need to tap again. It never silently sends a replacement ask or changes a draft. The ask is marked completed and its button removed only after readback confirms every exact binding and project-tree link.

The single-bind PIN route remains available for one-off dashboard entry. The batch route does not expose a general-purpose way for an agent to bind projects, and the owner tap continues to be the authority. After repeated owner-approved batches with the same narrow scope, the system may prepare a separate, optional standing-grant offer that states its conversation types, allowed operation, expiry, and revocation path. It never appears as an unchecked default and never activates from the batch approval tap.

### Persistence and machine posture

The canonical draft, the review surface hash, channel entry coordinates, approval, and final binding records use the existing replicated Chief of Staff journal; their reads fail closed unless the complete authenticated view is available. The active callback receiver is checked at both ask creation and tap time. A change of receiver does not invalidate a replicated ask, but the new receiver must reread the exact ask, verify current receiver admission, and authenticate the owner callback itself. An offline or stale receiver cannot accept a tap from a cached view. No machine may infer owner approval from a copied draft or a sent message. An entry link is delivered in each available linked private Telegram and Slack conversation; either link opens the same review and one verified owner action resolves it once. Duplicate or delayed entry links are inert after resolution.

## Decision points touched

| Decision | Classification | Reason and boundary |
|---|---|---|
| Whether an agent may present a batch ask | invariant | Only identity-verified, unbound, distinct valid project conversations from the current graph and fully valid exact drafts may be shown. A refusal is safe and names the failed check. |
| Whether a tap is an owner's binding approval | invariant | The callback's authenticated owner principal, exact stored message coordinates, current verified source messages, exact ask hash, and current complete project view must all match. No text or button label grants authority. |
| Which projects the tap binds | invariant | The tap can apply only the deep-copied drafts whose canonical hash is on the pending ask. Partial write recovery can continue only this exact set. |

## Multi-machine posture

The batch ask, disclosure coordinates, approval record, and project bindings are replicated through the existing Chief of Staff journal. Reads fail closed when the authenticated view is incomplete. A callback is accepted only by a currently admitted callback receiver that rereads the complete current journal and verifies the exact owner tap. Pending state is not machine-local, and a machine cannot accept from a cached view.

## Rollback

Disable `chiefOfStaff.projectBindingBatch.enabled` and remove the new route/button handling. Existing project bindings and the single-bind PIN route remain intact. When the intake flag is disabled during rollback, every unapproved ask receives a durable terminal-cancelled record, its approval controls are removed, and one private notice tells the owner the link no longer applies. Already approved work is drained to an explicit terminal result so an operator toggle cannot strand an authorized batch. Already-created bindings are ordinary Chief of Staff bindings and are not automatically removed by rollback.

## Required tests

- A valid draft set produces one exact owner review surface reachable from each available linked private Telegram and Slack conversation. The surface shows all project bindings and parent placements with source citations and approve/decline controls; no binding exists before the owner taps. Tests assert full disclosure, single-surface visibility, exact ask hash, and the owner tap result. An outage in one channel does not disable a complete copy in the other.
- The exact owner callback applies all and only stored operations: a project binding and its project-tree link, or a parent placement backed by a current recorded creation source. Parent placements never use title similarity as authority.
- Wrong owner, wrong Telegram chat, wrong message ID, modified/replayed ask ID, stale source, unavailable source, incomplete view, missing or changed conversation identity, newly bound topic, invalid draft, duplicate conversation, disabled feature, and wrong callback receiver all refuse before any binding write.
- A decline closes only that ask and writes no binding. Rollback tests prove pending asks are durably cancelled and the owner gets a private fixed notice. A duplicate callback after success or decline creates no second effect and reports the current exact result.
- A write refusal after one or more members leaves the same ask pending; retry binds only missing exact drafts and reports completion only after a full readback.
- A conflicting binding inserted after the ask is never overwritten, gets an explicit blocked entry, and leaves independently valid entries eligible to finish; the ask ends in a visible terminal-with-conflicts state.
- Retry tests prove no polling during an outage, capacity-budgeted retries after verified journal recovery, a circuit breaker on unchanged failing writes, disjoint-entry concurrency within measured limits, and exact recovery across restart without another owner tap. Restart and callback-receiver change tests prove the replicated exact ask survives restart and can be accepted only by the receiver that is currently admitted and has the complete authenticated view. Telegram and Slack owner approval are both exercised through their real current-user paths, and Telegram, app, and any other supported conversation key from the authoritative graph are validated through the shared parser and current access record.
- HTTP integration verifies route switch, owner-source verification wiring, response status, and unchanged PIN requirement for the single-bind route.
- E2E lifecycle starts the server, creates the ask, receives the one tap through the real owner callback path, restarts, and confirms all projects appear exactly once under their conversations.
