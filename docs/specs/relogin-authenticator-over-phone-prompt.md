# Sign-in repair: authenticator code over Google's phone prompt

## Problem

The automatic sign-in repair hands the browser step to a short-lived helper session (navigation `agent-session`, used on macOS development agents and on the Windows path). Instar renders that helper's prompt (`renderHelperPrompt` in `src/core/SubscriptionReloginHelper.ts`). The prompt tells the helper to choose "Try another way" only on a **passkey** screen. For any phone prompt it says: ask the operator for a tap, and treat a phone check as a hard line.

For many Google accounts, the default second step after the password is a phone prompt ("Check your phone", "Open the Gmail app", a number to tap). Google lists the authenticator code under "Try another way". So an account whose authenticator secret IS saved in the vault still stops for a human every time.

Live evidence, 2026-11-26 and 2026-11-25:

- Mama PC, `sagemind-luna` (password + authenticator bound), episode `804b1744`: the repair started unattended at 22:33Z and ended at 22:41Z as `operator-only-challenge / agent-hard-line-phone-confirmation`.
- Laptop, `gearfinity3d` (password + authenticator bound), episode `809f5ae7`: `phone-tap-requested` at 22:55Z, then `agent-helper-exited` at 23:07Z.
- The same accounts repaired unattended on other machines when Google happened to ask for the code directly (Laptop Luna 2026-11-25, Mama PC gearfinity3d 2026-11-24).
- Hypothesis, not yet measured: on these accounts, Google's "Try another way" list includes the authenticator option. The live proof below tests it. If Google withholds the option after the switch, the repair ends at the operator-only handoff (one ask, as today, but through the dashboard rather than a phone tap), and that cell is not retried on its own.

The `/subscription-signin` skill, which the helper follows, has the same gap. Its troubleshooting row "Google asks for a phone tap, SMS, or 'verify it's you' → never try another method to get around it" groups a normal choice of second step together with Google's risk checks.

**Terms:** a *cell* is one account on one machine; a *repair* (*episode*) is one automatic sign-in attempt series for a cell; an *attempt* is one run of it; a *drive* is the browser part of an attempt; the *helper* is the short-lived agent session that does the drive, running on a healthy *seat* account on the same machine; a *driver family* is the set of machines whose helper drives Chrome the same way (macOS through Apple Events, Windows through `ndrive.sh`).

## Decision: two different pages, two different rules

1. **A Google page headed "2-Step Verification", shown after the password.** Google is asking which second factor to use, and it lists the alternatives itself under "Try another way". Choosing the authenticator code there is a sign-in choice the account owner set up, not a way around a check. **New rule (in `on` mode), for an account that signs in with `password+totp` with its authenticator vault entry bound.** If Google asks for the authenticator code directly, nothing changes: the helper enters it as it does today, with no request to Instar. If the page opens on anything else (a phone prompt, a number to tap, a code sent by text), the helper does the following:
   - It asks Instar before choosing "Try another way" and again before each code. Instar answers `proceed`: true only in `on` mode, only for an exact "2-Step Verification" heading, and for at most two codes per attempt.
   - It chooses the Google Authenticator option and enters the code.
   - If Google rejects the code, it asks again for a second, fresh code in the next 30-second window.
   - On a refusal from Instar, or a second rejection, it reports the `phone-confirmation` hard line and stops.
   - If Instar refuses the first request (for example `awaiting-review`), the helper has not left the phone prompt, so it asks for the phone tap as today. Once it has chosen "Try another way", any refusal, a second rejection, or a list with no authenticator option ends at the `phone-confirmation` hard line (the operator-only handoff). It never re-selects the phone method.
2. **Risk always wins.** A CAPTCHA, or a warning of unusual or suspicious activity, makes the page Google's risk check, even under a "2-Step Verification" heading. Ordinary wording on that page such as "Google wants to make sure it's really you" is normal and does not. Any page not headed "2-Step Verification" whose point is to confirm it is really you ("Verify it's you", "Confirm it's you") is also a risk check, even if it lists the authenticator option. **Unchanged:** a risk check is a hard line, handed to the operator once and never worked around. **When the helper cannot read the heading or cannot tell which page it is, it does not use the authenticator.** It does what it does today: it asks for the phone tap if one is waiting, and otherwise reports the hard line.

The heading is the distinguishing fact. Both pages can show "Check your phone" and both can appear after the password, so the page body cannot tell them apart; the page heading can. **Two different kinds of check, on purpose:**
- The exact heading "2-Step Verification" is a deterministic precondition: a floor, not the judgment. It only ever narrows when the step may run, and a miss always falls to today's behaviour. The server enforces it, because it is the server that answers `proceed`. But the server checks the heading text the helper reports, not the page, so it is the authority on what the helper may do next, not an independent witness of what the page said.
- Recognising a risk check is a judgment. The prompt describes such a page by what it is asking (to confirm it is really you, or to flag unusual activity), gives the familiar wordings as examples only, and tells the helper to judge by meaning, not by matching words.

## Changes

0. A new setting, `subscriptionPool.assistedRelogin.authenticatorOverPhone`: `true`, `'shadow'` or `false`. `resolveAuthenticatorOverPhone` resolves it to `on`, `shadow` or `off`. An explicit value wins; omitted means `shadow` on a development agent and `off` on the fleet. `false` restores the old prompt exactly.
1. `ReloginHelperDriveInput.authenticatorMode?: 'on' | 'shadow' | 'off'` (new, optional). It is computed by `helperAuthenticatorMode(mode, loginMethod, secretRefs)`: the resolved mode, applied only when the new exported `helperHasAuthenticator(loginMethod, secretRefs)` holds (`loginMethod === 'password+totp'` and a non-empty `secretRefs.totp`). Otherwise it is `off`. Only the method name and the binding name feed it; no secret value is read.
   - **`shadow`:** at a phone prompt, the helper reads the page heading as in Changes 4. It decides by the `on` rules whether it *would* use the authenticator, and posts `shadow-would-use` or `shadow-would-stop` with the heading. It does not click "Try another way", enters no code, and every request it might make is refused (`not-enabled`). Then it asks for the phone tap exactly as today, and its hard line 2 is today's text.
   - **`on`:** the rules in "Decision" above.
2. `renderHelperPrompt`: in `on` mode, the phone-tap line is replaced by the two rules above (the heading test, the two-code limit, the "when unsure, risk check" default). Hard line 2 names the single allowed step ("the authenticator code on a page headed '2-Step Verification', only while Instar answers proceed:true"). In `off` mode or when the field is absent, the prompt is byte-for-byte the previous text, and a test pins this.
3. `/subscription-signin` skill (`src/data/builtinSkillContent.ts`): one line is added to the agent-run subsection, after the phone-tap line: if the helper's prompt allows the authenticator code on a page headed "2-Step Verification" for this account, follow it exactly, otherwise ask for the phone tap, and **where the prompt and the skill differ, the prompt wins**. The by-hand procedure and the troubleshooting table are unchanged, including the hard-line row "Google asks for a phone tap, SMS, or 'verify it's you'". So the new behaviour lives only in the gated prompt, and agents signing in by hand are unaffected.
4. Server gate and audit trail. The helper reads the page heading from the page itself before acting. On macOS that is the text of the h1 element, read with the same in-page script it uses to check the focused field. On Windows it is the element with the Heading role at the top of the page in `ndrive.sh tree`, confirmed with `ndrive.sh shot`.
   - It also reads the page origin, which must be `https://accounts.google.com`. If the page shows more than one heading and it cannot tell which is the page title, it sends an empty heading, which counts as `unknown`.
   - It posts `{"notify":"authenticator","result":R,"heading":"<the heading text>","origin":"<the page origin>"}`. The outcome reports carry the heading and origin read before the code was entered, not the next page's. R is one of two requests, `intent` (before "Try another way") and `code` (before each code), or one of five reports: `accepted`, `rejected` or `no-option` after the page settles in `on` mode, and `shadow-would-use` or `shadow-would-stop` in shadow mode.
   - `parseHelperBody` accepts exactly that four-key shape, those seven values, and a heading and origin of up to 200 characters each. The route needs the per-episode token like every other notice.
   - `SubscriptionReloginHelper.submit` classifies the reported heading with `classifyAuthenticatorHeading`. It folds case, whitespace, hyphen variants and invisible characters, then gives `2sv` for an exact match, `unknown` when empty and `other` otherwise. The raw text is never stored.
   - **Requests** exist only on the switch path (after a phone prompt). They get `proceed` only when the drive's mode is `on`, the origin is exactly `https://accounts.google.com` (`origin-not-google` otherwise) and the heading is `2sv`. A `code` also needs a granted `intent` in the same attempt (`no-intent` otherwise), and a third code in an attempt is refused with `code-limit`. **Reports** are audit only.
   - **Supervision latch (the first 3 uses per machine).** A *use* is one helper drive that was granted `intent`. Each one is recorded at the moment of the grant as a row in `authenticator_uses`, keyed by a fresh drive id, in a table the store never prunes. A drive resumed after an operator resume, a retry, a readmission or a server restart is a new drive, so it is a new use that needs its own review. That is the strict direction: a resumed repair can never reuse an earlier pass. Reviews live in `authenticator_reviews`, one per use, also never pruned. `SubscriptionReloginStore.authenticatorSupervision(driveId)` gives the latch. While fewer than 3 uses have passed, a new use's `intent` gets `proceed` only when no other use on this machine is unreviewed; the asking drive's own use never blocks it. Otherwise the request is refused with `awaiting-review`. One `fail` closes the step on that machine for good (`review-failed`). **Reopening** needs a new reviewed instar change that ships a migration removing that machine's fail rows, so a mistaken fail costs a reviewed change, never a silent reopen.
   - **Reviews.** The latch paces the rollout; it is not a security boundary against a helper that ignores its prompt (see "Known gap"). The reviewer records one with `POST /subscription-relogin/EPISODE/authenticator-review {"result":"pass"|"inconclusive"|"fail"}` (Bearer). A pass or inconclusive goes to the episode's oldest unreviewed use. A fail goes to its latest use, and may override an earlier review; that is the machine's immediate off switch, and it also refuses further codes in a drive that was already granted. **A fail is accepted at any time**: while a helper is running, for a repair that is still running, and for a repair that was never granted the step (a transcript can show a code entered without asking). In that last case the store records an `ungranted-<episode>` use so the fail closes the latch. **Inconclusive** is for a use whose transcript lacks the evidence to pass (for example no page content at submission): it lets the next supervised use go ahead but never counts toward the 3 passes. The route refuses a pass or inconclusive while any helper drive is running on the machine (`authenticator-review-helper-live`), because a running helper holds the agent's token; a fail can only close the step, so it is never refused for that. For a pass or inconclusive, the store refuses an episode with no recorded use and an episode whose repair is still running (`authenticator-review-drive-live`); a finished, waiting or `suggested` repair can be reviewed, since no drive runs in those states. `isAnyDriving` sees the drives of the current server process; a helper session left over from a crash is reaped by boot cleanup before new drives start. It refuses any review when nothing is left to review (`authenticator-review-already-recorded`).
   - **Code count across a restart:** a drive seeds its granted-code count from the store's `code-1`/`code-2` events since the episode's latest admission or approval (`authenticatorCodesGranted`). A restarted drive cannot get two more codes, and a person's retry starts a fresh count. `GET /subscription-relogin` shows `authenticatorSupervision` (state, grants, passes, fails, unreviewed), so a waiting review is visible without reading events. A helper refused before it switched falls back to today's phone tap; after the switch, to the `phone-confirmation` hard line.
   - Each request and report writes one event `helper-authenticator-<label>` (`SubscriptionReloginStore.recordAuthenticatorEvent`). Labels are built by the server from closed sets, for example `intent-heading-2sv`, `code-1-heading-2sv`, `code-refused-code-limit`, `accepted-heading-other`. They are deduplicated per drive and capped at 12 per drive (a resumed drive starts a new set; the attempt budget bounds the total), except the grant record and the families that block a slow retry (`intent-heading-2sv`, `rejected-*`, `code-refused-*`, `code-1-*`, `code-2-*`, `no-option-*`), which are never dropped.
   - Nothing here settles the drive or queues a notice.
   - **Slow retry:** `challengedSinceAdmission` now also counts `helper-authenticator-rejected-*`, `-code-refused-*`, `-code-1-*`, `-code-2-*` and `-no-option-*`. It is only consulted for an attempt that did not succeed, so any granted code in a failed or unfinished attempt blocks the automatic retry, even when the helper never reported the outcome (a lost answer, an exit after a rejection). A stale secret costs one stop, not a loop.
   - **Helper seat:** the step is offered only when the helper session runs on Claude Code. For any other seat framework the drive's mode is forced to `off`, both in the prompt and at the gate, because the transcript review below reads Claude Code session files.
   - The events are read per machine with `GET /subscription-relogin/EPISODE/events`. The pool view lists episodes, not events.
5. Migration parity: `PostUpdateMigrator.migrateSubscriptionSigninAuthenticatorOverPhone` inserts the one agent-run line after the stock phone-tap line. It is idempotent on its marker. A CRLF copy stays CRLF, local edits are kept, and a copy without the stock anchor is reported as customised and left untouched. The setting needs no config migration: omitted resolves through the development-agent gate.

6. Awareness: `src/data/awareness/relogin-authenticator-over-phone.md` tells every agent the setting, its values and default, the events, and when to read them ("why didn't the repair wait for my phone tap?").

## What does not change

- The server-side fixed page-class driver (`AnthropicReloginBrowserDriver`, navigation `closed`/`agent`, the fleet default) still classifies a phone page as `phone-confirmation` and ends `operator-only`. Teaching it to choose from Google's "Try another way" list needs a new page class and one new allowed action, under its own spec. It is tracked as CMT-034 on the Mac M5 Pro (owner: Subscription Management, first update 2026-12-03). <!-- tracked: CMT-034 (origin m_a804869356b259820b3236e7c5a2ae7d) -->
- Success is still decided only by Instar: a completed login, the verified email, and an authenticated call. The helper's word never counts.
- Backup codes stay out of unattended repair (#3920). This change only touches accounts with an authenticator secret.
- One new route (`POST /subscription-relogin/EPISODE/authenticator-review`, Changes 4) and one new config key, dev-gated (Changes 0). **It is a real change of authority, made in text:** on these accounts the helper may now complete Google's second step with no human present, where before it had to stop. That authority is bounded by the account condition, the heading test, the two-code limit and the unchanged hard lines.

## Signal vs authority

This adds a cooperative gate (the server's `proceed` answer and the latch), not a detector with blocking authority over anything else. The hard lines are fixed server-rendered text and they stay. What changes is the helper's authority at one page type, and the decision there is a model's reading of the page heading. That judgment is bounded by the floor in the table below. The parent design (`skill-driven-signin-repair`) already trusts the helper's intermediate clicks and verifies only the result. This spec does not claim more than that: a model that misreads the heading can still act on the wrong page. That residual risk is stated under Risks and watched under Observability.

## Frontloaded Decisions

1. The 2-Step Verification phone prompt is a choice of second step, not a risk check. Decided here, with the reasoning in "Decision" above.
2. Scope is the agent-session helper prompt and the skill text. The fixed page-class driver is not changed in this spec. It is tracked as CMT-034 with its own spec. <!-- tracked: CMT-034 -->
3. A gated setting (Changes 0) with a shadow step first. Development agents start in `shadow`, where the helper only reads and reports. `on` is set per machine once the shadow evidence below is in. The fleet stays `off`. With the setting off, the prompt is byte-identical to today's. This is not cheap to change after, because `on` lets the helper act on real Google accounts; the shadow step and the gate are what put evidence before that authority.
4. The heading "2-Step Verification" is the test for the allowed page. When the helper is unsure, the default is the risk-check path.
5. At most two codes per attempt, and no automatic retry after any granted code that did not succeed, so at most two codes per episode unless a person approves a retry.

## Observability and evidence (Judgment Within Floors)

- **Where the judgment runs.** Only where both conditions hold. First, the agent-session helper runs: `resolveReloginNavigation` gives `agent-session` on macOS when set, by default on a macOS development agent, and on WSL when set explicitly. Second, `authenticatorOverPhone` resolves to `shadow` (by default only on a development agent) or `on` (only when set explicitly, after graduation). Code entry therefore always needs an explicit `on`. At the time of writing, that means this agent's machines: the M5, the Studio and the Laptop (macOS) and Mama PC (WSL, set explicitly). The fleet default has the setting off and uses the fixed page table, which this spec does not change. The skill's by-hand procedure is unchanged.
- **What is recorded.** Every request and report, with the server's heading class (Changes 4). **The metric:** an attempt counts as an unattended authenticator success only when it took the switch path (`intent-heading-2sv`), was granted one or two codes that match the code submissions in its transcript, recorded `accepted-heading-2sv`, has no `phone-tap-requested` in the same attempt, and that same attempt ended the episode `succeeded`. Direct-code attempts (Google asked for the code itself) are counted separately, as today's path, and are not judged by the switch-path rules. **One revert rule, for switch-path uses:** revert on a machine when the transcript of a switch-path use shows a code entered on a page that was not Google's 2-Step Verification page, or on a page that showed a CAPTCHA or an unusual-activity warning whatever its heading. The review reads the page content the browser returned at the moment of submission, not only the heading. A use whose transcript lacks that content counts as unknown: it cannot pass, and is recorded as inconclusive. Event labels never decide that alone; they point the review at the transcript. Anything `unknown` never counts as a success.
- **Verify the state, not its symbol.**
  - **Symbol:** the helper's notices (requests, reports and the heading text it reported).
  - **State it claims:** the helper entered the code on Google's 2-Step Verification page, and Google accepted it.
  - **Corroboration:** two pieces that are not the helper's word. First, the browser's own output in the helper's session transcript (below), which comes from the page, not from the model. Second, Instar's own verification of the final sign-in (the verified email and an authenticated call). The server's heading check is the audit index and the gate, not corroboration, because it checks text the helper reported.
  - **Unmeasurable cases:** a missing heading is recorded as `unknown` and never counted as success. A helper that skips the notices leaves no event. So during the trial the review reads the transcript of **every** helper attempt on a qualifying cell on a machine in `on` or `shadow` mode: succeeded, failed, unfinished or handed to the operator, with or without an authenticator event. It counts code submissions from the transcript without keeping code values. An attempt whose transcript cannot be read counts as unknown. Keep and graduation decisions rest on transcript-corroborated records, never on the absence of a `heading-other` event alone.
- **Shadow first (evidence before authority).** In `shadow`, each phone prompt on a qualifying account records `shadow-would-use-heading-<class>` or `shadow-would-stop-heading-<class>`, with no action taken. That tests the helper's heading read and its page judgment, including whether it wrongly treats the ordinary "make sure it's really you" subtext as a risk check, before any code is entered.
  - **Graduation from shadow to `on`, per driver family** (macOS helpers together, Windows helpers together): at least 3 transcript-corroborated `shadow-would-use-heading-2sv` records on qualifying cells, zero records where the transcript disagrees with the posted heading or decision, **and one passing fixture run**: a real helper of that family, in shadow mode, driven against a local fixture page headed "2-Step Verification" that also shows a CAPTCHA, must record `shadow-would-stop`. That run tests the risk override, which ordinary live pages may never show. It runs once the shared test line has room, and is tracked as CMT-038 on the Mac M5 Pro. Records on other headings, and correct `would-stop` decisions on real risk checks, count neither way. A disagreement resets the count.
  - **Why 3, and why it is only a minimum:** one record shows the read can work; a second shows it was not luck on one page load; a third, on a different account or day, shows it repeats across Google's page variants on that driver. Beyond that, more records before `on` add little, because shadow cannot test the step that matters (entering a code); that evidence comes from the supervised uses. The arbiter may wait for more records whenever a transcript raises doubt. The count is a floor, never a quota.
  - **Decision and exit:** the arbiter is Subscription Management, reading the transcripts. The conservative default is to stay in shadow. Approving this spec authorises Subscription Management to set `on` per machine after graduation, with no further operator ask, and to record the evidence in CMT-036.
  - **Dated check (CMT-036):** on 2026-12-10, each family either graduates or the reason it has not goes into the report. A family still in shadow at the end of the trial stays in shadow, and only a separate change can take it further.
  - **The first 3 `on` uses per machine are supervised one at a time, by the server** (the supervision latch in Changes 4), because shadow cannot test the choice to enter a code. No second use can start on that machine until the first is reviewed. A review is recorded per use after reading its transcript. Uses of one repair are matched to its drives in the order of their `helper-authenticator-intent-heading-2sv` events, one per drive. A `fail` closes the step on that machine, and the revert decision follows. After 3 passing reviews the latch stays open, but supervision does not end: every later use is still read in the weekly review for the whole trial, and one `fail` closes the step at once. Three is a minimum. The reviewer keeps the latch closed for longer simply by not recording a pass, for example when a use meets a Google page variant not seen before. These first uses are the real evidence for the step itself. The success criterion against the phone-tap default is an unattended `succeeded` with a transcript that shows the 2-Step Verification page and no risk-check page, where the default needs a human every time.
  - Whether Google lists the authenticator under "Try another way" can only be learned in `on` mode. Until then it stays the hypothesis stated in Problem.
- **Known gap, accepted: the gate binds a helper that follows its prompt.** The authenticator vault entry stays on the helper's list in every mode, because today's unattended successes (Google asking for the code directly) rely on it. A helper that ignored `proceed:false` could still make a code. Having the server mint each code instead was considered. It would route every direct-code sign-in through the new latch and slow down the path that already works today, so it is not done here. The transcript review, which counts code submissions, is the backstop.
- **Fixtures, one required.** One fixture run per driver family is a graduation condition (above): the mixed page, an exact heading together with a CAPTCHA. More fixture cases are not added, for cost (each is a full helper run on a machine reserved for the shared test line). Whether Google offers the authenticator can only be learned live.
- **Who reviews, accepted:** the review route takes the agent's own Bearer token, so the reviewer is an agent reading a transcript, not the operator. Requiring the operator's tap for each pass was considered. It would bring back the asks this change exists to remove, on a step whose backstops (the exact heading, the origin, the two-code limit, Instar's own sign-in check, and the off switch any later review can pull) do not depend on the reviewer. The operator sees every review result in the regular report.
- **Non-English accounts:** the exact heading test is English. An account whose Google pages show another language never gets the step and keeps today's behaviour.
- **URL path, recorded for later:** Google's challenge pages may encode the challenge type in the URL path, which would not depend on language. It is not verified, and the shadow notice does not record it in this change.
- **Corroboration that is not the helper's word.** Each helper runs as a Claude Code session named `relogin-<episode>` under the helper seat's account. Its transcript is that account's Claude Code session file on the same machine, kept at least until the weekly review reads it. It records the actual tool output of the heading read: the text the browser returned, not the model's summary of it. For every shadow or accepted record, the review in CMT-035 reads that transcript and checks the h1 output against the posted heading and the action taken. A record with no matching tool output counts as unknown. The transcript is the corroboration; the event is the index into it.
- **If the bars are not reached in time:** phone prompts on qualifying cells have been seen about once a day across the four machines, and most of the trial's early prompts go to shadow and supervised uses, so the fleet bar of 20 `on` attempts may not be reached inside 30 days. Then each machine keeps its current mode, the report says so, and the fleet change waits for the evidence.
- **Review and exit.** The weekly evidence review is CMT-035 (first review 2026-12-03); graduation, the first-use reviews and the live-proof record are CMT-036 (due 2026-12-10). Both are commitments on the Mac M5 Pro (origin `m_a804869356b259820b3236e7c5a2ae7d`), where Subscription Management runs; the same numbers exist on other machines. The owner is Subscription Management; the operator hears the result in the regular report. The review reads the events on every machine above and compares unattended success on `password+totp` cells with the 30 days before merge, which are taken from the same machines' episodes. A reviewed episode whose transcript shows a code entered on a page that was not the 2-Step Verification page means revert. An event label alone never does. A later risk stop by itself is a reason to look, not proof of a misread. The trial ends after 20 qualifying helper attempts or 30 days, whichever comes first. <!-- tracked: CMT-035, CMT-036 (origin m_a804869356b259820b3236e7c5a2ae7d) -->

## Alternatives considered

- **Change the accounts instead** (turn off Google prompts so Google asks for the authenticator code directly). Rejected as the main fix. It needs each account owner to act, which is the ask this work exists to remove, and Google can still show the phone prompt on a new device. It stays available as a per-account choice.
- **Have the server read the heading itself** instead of trusting the helper's report. Rejected for this change: the helper drives an ordinary Chrome window through Apple Events (macOS) or `ndrive.sh` (Windows), under the permissions of its own session, and the server has no debugging connection to that window. Giving it one would undo the parent design's choice of a normal, non-automated browser.
- **Do it in the fixed page-class driver first** (CMT-034). That needs no model judgment, but it needs a new page class for Google's "Try another way" list, which is a larger change with its own spec. The affected machines run the helper path today, so the helper is where the stop happens now. <!-- tracked: CMT-034 -->

## Risks

- **The helper misreads a risk check as the 2-Step Verification step.** Mitigations: the heading read from the page's own h1, the explicit list of risk-check wording, and the "when unsure, treat it as a risk check" default. **Worst case:** the helper answers a Google risk check with the account owner's own authenticator code. If Google accepts it, the sign-in is into the expected account and Instar verifies it. If Google does not accept it, the two-code limit stops the helper before repeated failures can draw a lock or flag. That residual risk is accepted here and watched by CMT-035 and CMT-036.
- **A stale authenticator secret** (re-enrolled elsewhere, clock skew). Two codes, then the hard line holds the account at approval. It is never retried on its own, so a stale secret costs one stop, not a loop.
- **Google wording changes.** The instruction is phrased by meaning ("Try another way" or "More ways to sign in", the authenticator option), and the helper reads the page. A page it cannot match still ends at the phone tap, exactly as today.

## Rollback

- **Fastest, no restart:** record a `fail` review on any finished, granted episode. That closes the step on that machine for every new use and for further codes in a running drive.
- **By setting:** set `subscriptionPool.assistedRelogin.authenticatorOverPhone` on a machine. `false` returns its prompt to today's exact text after the next server restart. `'shadow'` stops code entry after switching from another method, because every request is refused, but keeps the heading report; direct-code entry continues as today. `'shadow'` is the reversible pause; a `fail` review is for confirmed misuse and is permanent. No code change is needed.
- **Full:** revert the PR. The prompt returns to the old text. The one skill line the migration added stays in installed skills, because `installBuiltinSkills` never overwrites. That line is harmless after a revert: it says to follow the prompt, and otherwise to ask for the phone tap, which is the old behaviour.
- **Data:** the new event rows stay after a revert. The old code reads an unknown event class as a plain string, so they are harmless.

## Multi-machine posture

- Helper prompt and skill line: `unified`. Every machine renders the same prompt and gets the same skill line on update.
- The `authenticatorOverPhone` value: `machine-local`.
  machine-local-justification: physical-credential-locality
  It is set per machine because the step is turned on machine by machine (after its driver family graduates), and it lives in that machine's `.instar/config.json`, which is not replicated (it is git-ignored in the agent home). It governs how that machine's helper drives that machine's own browser profiles and logins.
- The supervision latch, its uses (`authenticator_uses`) and its reviews (`authenticator_reviews`), which are authority state: `machine-local`.
  machine-local-justification: physical-credential-locality
  They govern how that machine's helper may use that machine's own logins. A review must be POSTed to the machine that ran the use; the pool view does not route it.
- The new audit events in the sign-in repair store: `machine-local`.
  machine-local-justification: physical-credential-locality
  The store records repairs of the logins and browser profiles that live on that machine's disk, and it is deliberately excluded from backup and replication. The review in CMT-035 reads each machine's events directly.
