# Measuring how long verification really takes

The verification queue needs a reliable scoreboard before we change its capacity. Today, a short failed attempt can look like a finished full suite when all we count is attempts. The saved records also tell us when a test run began and ended, but they do not tell us when that exact published candidate first reached the queue. That makes an exact publication-to-verdict claim impossible to reconstruct honestly.

This change adds a small, machine-local observation file. Once the coordinator reads an eligible published pull request and resolves its exact head and target base, it records the first time it saw those inputs, including a request refused for capacity. Later observations record admission, actual local or peer dispatch, and the journaled verdict. Repeating a request does not reset the first observation. A different head or base receives a separate record. No request text, logs, credentials or test names enter this file.

The first observation is not the actual publication time. Reports say explicitly that elapsed time from that observation is only a lower bound on publication-to-verdict time. Existing records without that observation remain unknown. An optional file-coverage summary distinguishes full inventoried reports from runs stopped early; it never changes whether a verdict is accepted. The report also separates successful full gates, red complete inventories and incomplete or unknown attempts.

The observation file has fixed size, row, age and per-row attempt bounds. A missing, full, corrupt or unwritable file produces a small audit signal and does not stop a test, admit a candidate, change its place, weaken a hold, or authorize a merge. The reporting script reads saved metadata and prints a two-hour report. The coordinator owner schedules and delivers that report separately. Reverting this change removes observation and reporting, with no source, queue or test-result migration required.
