## Owner-surface amendment, November 23, 2026

Justin's later instruction separates purely internal agent work from requests made by people. This amendment supersedes the aggregate and quiet-row display rules below. A pure internal card has no requester, no outward work, an agent carrier, no person waiting or open question, no owner-confirmation criterion and no outstanding completion confirmation. It stays outside default owner board lanes, Projects, Conversations, search, pins, unread counts and Needs you. Filter before counts and cuts. A deliberate `view=agent` board read shows only those cards and contributes zero owner requests. Existing history is retained; creating an internal card does not create an empty owner chat. Materialize execution history only when an allowed note or dispatch requires it.

Additive card fields `agentInternal` and `conversationAvailable` describe these decisions. Owner board/list responses carry `ownerProjectionVersion: 1`; board responses identify `view`. Clients retain compatibility when fields are absent, suppress chat links only on explicit false, and follow cursors across short or empty filtered pages. Requester-backed cards, real questions, outward approvals and owner confirmations remain visible. Held, parked, quiet, unknown or capacity-limited execution alone never means the owner owes a decision. Diagnostic not-started counts never manufacture a Needs-you aggregate. This changes projection and wording; existing execution policy and approval proofs remain enforced. A policy change uses the actual approved trust-journey proof, never a remembered instruction as a substitute for it.


# Agent work cards by default

## Problem statement

The Work Board (work-board-asks, work-board-cards-appear, work-board-my-board) already holds the parts the operator asked for on 2026-11-20: a lane for cards the agent is working (`with-agent`); done items the agent may certify itself, which finish a card with no tap when every item is agent-certified (`doneByAgentOwnEvidence`); a native conversation per card; cards listed under their project (`GET /work/projects` rows, the app's project rows); a `carrier` field (the card's owner) that can name a person; and an `outward-only` board policy under which a card that sends nothing outside the team and spends nothing starts with the agent at once, instead of waiting for the owner's approve tap as every agent-written card does under the default policy.

What is missing is that none of it is the default, and the agent has to remember all of it:

1. **Every agent-written card is an ask.** `POST /work-board/cards` refuses a card without `recommendation` and `whyYou` (work-board-cards-appear §2), `outward` defaults to `true` (so approval is always required), and a new team's board runs `every-agent-card`. On 2026-11-20 the agent opened two tracking cards for the operator's feedback and both landed in his Needs-you list as "needs your approval": the exact noise he had asked, an hour earlier, to remove, and a second yes for work he had asked for in his own chat.
2. **Nothing turns a request into a card.** Requests live in chat and in commitments; whether a card exists depends on the agent thinking of it. The operator's test ("if I share feedback, is it officially recorded and tracked?") found two items tracked only in chat, and the agent had filed one of his direct requests into the external `/feedback` queue, where it is a report to the maintainers, not work he can see.
3. **The agent cannot write on its own card from where it works.** The card read exposes only `conversation.sendPath` (`/mobile/chat/app/<key>`, the phone's route), and `app-reply.sh` is bound to an app-conversation session (`INSTAR_CONVERSATION_ID` + `INSTAR_BIND_TOKEN`). From a Telegram topic session, where most work happens, "the agent keeps progress notes on the card" has no write path, and a scoped session cannot create the ask card R9 needs either (work-board-asks §4).
4. **A task with no project has no home.** `projectKey` is optional and a card without one appears only in the lanes, not under any project; there is no general area and no offer to make a project.
5. **Only the team owner can carry a card, and nothing can block a card.** Phase 1 limited person carriers to the owner and deferred blocker links (work-board-asks Non-goals). The operator uses both daily on the SageMind/Luna board and asked for them here.
6. **The fleet default is the strict one, with no path to the lighter one.** Moving a board to `outward-only` is a trust raise that only the trust-request path can apply (`POST /work-board/settings` refuses it even with the PIN, because the PIN is not the person's proof), but nothing ever raises it, so every team stays where the 2026-11-20 incident happened.

## Operator requirements (topic 134088)

- **R1:** every request or feedback item the operator gives becomes a card the agent is responsible for, under the project it belongs to.
- **R2:** the card carries milestones and completion criteria; the agent keeps its own progress notes on it; nothing is lost or forgotten.
- **R3:** when the work is done the agent closes the card out.
- **R4:** the operator can see these cards in the app under the project, as a secondary view ("the things going on behind the scenes"), for insight, not as asks.
- **R5:** this is the default behaviour of every Instar agent.
- **R6:** a task with no project is handled intelligently: a general category, or the agent proposes a project.
- **R7 (21:14 PST):** nothing reaches the person's attention unless it needs them.
- **R8 (21:41 PST):** cards have owners, integrated with Instar teams: "a critical feature is to have owners of cards which should integrate with Instar teams, and an agent can own some cards or team members can pass ownership to other team members."
- **R9 (21:41 PST):** cards can be blocked by other cards: "in an example where you were working on a card and that task suddenly gets blocked by something you need from me you would simply create a card for me as the owner with what you need from me and it would clearly show what is being blocked by that card."
- **R10 (21:43 PST):** "for requests that I am requesting of you directly those should be cards and never considered external feedback that goes into that queue."

R8 and R9 were listed as later phases in work-board-asks Non-goals ("no card carried or created by a team member (phase 3)"; "no blocker links between cards (phase 2)"). This spec pulls them forward at the operator's request; the remaining later phases stay where work-board-asks lists them.

## Vocabulary

- **Agent-work card:** a card with `carrier: agent`, `outward: false`, no open question to a person and no `owner-confirms` item, written by the agent (or by the gate on its behalf) for work it owns. A kind of use of the existing card, not a new record type.
- **Ask:** a card as work-board-asks defines it: it needs a person's tap (approve, answer, confirm), or is carried by a person.
- **Request:** an operator message the agent takes on as work. Recorded as a commitment (`POST /commitments`: `userRequest`, `agentResponse`, `topicId`, `source: agent | sentinel | manual`). Commitments **replicate** between the agent's machines through the `commitments-sync` mesh verb (`CommitmentsSync`), with the cross-machine identity `(originMachineId, id)`; replicas are read-only on every machine but the origin, and the merged read and `deliver`'s forwarding to the origin machine exist today.
- **Operator conversation:** a conversation in which a person the agent serves speaks to it: an app conversation the team owner or a member may use (`mayUseConversation` under the owner's signed team record); a Telegram topic in the configured owner group; a Slack conversation the configured owner or a linked member uses. Resolved per adapter from recorded configuration and the team record. A conversation is a **place**; it never proves who spoke.
- **Durable message row and the requester.** The stored record of one inbound message, and the sender it proves, per adapter:
  - **Telegram, native message:** the row in `telegram-messages.jsonl` with `fromUser === true` (not agent-originated), `forwarded === false`, and `telegramUserId` equal to `telegram.ownerUserId` (the owner) or to a Telegram id a team person's record links (a member). `forwarded: undefined` on a native row is unproven.
  - **Telegram, app- or team-phone-mirrored row** (`via: 'mobile-device'`): the row's `deviceId` resolved **on the machine that holds that device's record** to a device with `status: 'active'` and no `revokedAt`; the person is `devicePerson({ userId, role })` read from **that record** (role absent on the record ⇒ owner; `team` ⇒ the `teamStanding` person); the row's `senderRole` must equal the record's role, and `senderPerson`, when the row carries it (member and MSP rows carry it; owner rows do not), must equal the record's `{ machineId, userId }`. A record not on this machine, mismatched fields, a `teamPhone` row with no device, or a revoked device ⇒ unproven. An app message cannot be a Telegram forward, so `forwarded` is not consulted on these rows.
  - **App conversation event:** the event's `deviceId` resolved the same way (the device record is the proof; `senderRole`/`senderPerson` must agree with it); an event older than those fields is unproven.
  - **Slack:** the stored row's `user` equal to the configured owner or a linked member id, with no `bot_id` and no `subtype` that marks a bot, edit or system post; Slack has no forward flag, so a Slack row proves its sender only this far, which the detector states.
  - A sender outside the team, or a row with no sender, yields **no requester**; unproven provenance yields `unproven-provenance`. These are the only arms; a session binding is never one.
- **Sender-verified source:** a `(conversation, message)` pair whose durable row the recording machine found at recording time with a requester. The verdict, the requester, the row's **whole** text (credential-checked, up to `SCHEMA_MAX.need`) and its hash replicate with the commitment.
- **Carrier:** the card's owner in the operator's words: the agent, or a person in the team record (the owner, or a person with `team` standing; MobilePeople's vocabulary). Existing field (`Carrier = 'agent' | { personKey }`).
- **Blocker:** a card that another card names in a `blocked-by` record; the named card is the blocker, the naming card is blocked.

## Proposed design

### 1. An agent-work card asks nothing, under either policy

An agent-written card with `outward: false`, `carrier: agent` and no `recommendation` is an **agent-work card**. For it:

- `recommendation` and `whyYou` are **not required** (amends work-board-cards-appear §2). `askFieldsRefusal` keeps the requirement for every card that is an ask at creation: `outward: true`, a person carrier, or any done item with `certify: owner-confirms`. A later `waiting-on`, or a pass to a person (§8), requires both fields on that record, because that is when it becomes an ask.
- The default for `outward` on an agent-written card becomes **`false`** (amends work-board-asks §1); a person-written card keeps `true`. The agent's rule (awareness, §6): set `outward: true` whenever the work sends anything outside the team or spends money, and when unsure whether it does. The external-operation gate and the outbound guards hold regardless of the flag, so a wrong `false` cannot by itself send or spend.
- **The owner's own request is the yes.** A gate-written card whose `created.requester` is the **team owner, read from the durable message row** (§3; a session binding never suffices), carries approval **from the request**: the fold derives `approvedBy: { kind: 'requester-message', conversationKey, messageId }`, valid while the card stays `outward: false` with `carrier: agent` and no withdrawal (a flip to outward or to a person carrier returns the ordinary approval rule; a withdrawal tap revokes it as it revokes any approval). The yes is anchored to **what was asked, whole**: the card's `need` on such a card is the durable row's **entire** text (stored up to `SCHEMA_MAX.need`, 64,000; a row longer than that carries no request approval, `request-too-long`), its hash is `created.requestTextHash`, and it is **immutable** (`need-locked-to-request`); the agent refines `title`, `doneWhen` and `links` without voiding the approval, because the owner approved "do what I asked", not a checklist. Whether an edited milestone is still within what was asked is the working session's judgment; the floors are the locked `need`, the outward flip, the withdrawal tap, and the deterministic labels the row and the card page always carry: **"Asked: <need>"**, **"asked <n> days ago"** (from the row's time), **"recorded in the agent's words"** when `created.recordedAsHash` differs from `requestTextHash` (both hashes taken over the same normalised text, so the label marks a different wording, not a judgment of meaning), and **"changed since asked"** when an agent `edited` touched `title` or `doneWhen` after creation. **Every** commitment recorded on one verified owner message carries this approval while its `need` is that row's text (the owner's "do A and B" recorded as two commitments is two approved cards; the duplicate hint, §3, names them to the agent, which merges or keeps both; identical scope means no widening, so no count and no age caps the owner's own words). An earlier draft bounded the message's age (`sourceMaxAgeHours`); that floor was dropped deliberately: because `need` is locked to the cited message's text, a stale message approves only its own words and nothing newer, so an age cap protected nothing and cost the operator a second yes for a request recorded a day late; the age is shown as a label instead. Under **either** policy such a card is `workable` at once (subject to the hold, §3), accepts the agent's `evidence` and `claimed-done`, and is never asked about again. This amends work-board-asks §4: an approval may rest on the owner's own sender-verified request as well as on a tap. Only the in-process gate can write the fields this derivation reads (§3 "Gate-only fields").
- **Under `outward-only`** every agent-work card is `workable` at once and lands in `with-agent`.
- **Under `every-agent-card`** (the fleet default, unchanged) an agent-work card **without** request approval (requested by a member, by an unverified or absent sender, or started by the agent itself) still needs the owner's approve tap before the agent works it, but it is **not a per-card ask**: a new derived status **`not-started`** (an agent-work card whose approval is required and not valid, with no withdrawal) is **excluded** from `WAITING_STATUSES` and from `myBoardReason`; its lane is `with-agent`; its row reads "not started: waiting for your approval or board setting" with the card's own Approve control; and it refuses the agent's `evidence`, `note` and `claimed-done` (`not-started`), so the label never contradicts the state. Under this policy the agent does **no substantive work** on such a request before the owner approves: the recording session tells the requester, in their conversation, that the owner's approval is needed and that the card is waiting, and does nothing else on it. That is the policy's meaning; the structural floor under it is the external-operation gate on sends and spends plus the card's refusals, the rest is the awareness entry, and the graduation record measures it two ways: refused `evidence`/`note` writes on `not-started` cards (which sees only sessions that tried to write) and the owner-role harness's sample of member requests, whose transcripts show whether work happened. `needs-approval` is unchanged for every other card (an `outward` card, a withdrawn approval, a person-written card the agent will carry).
- **One aggregated row, not zero.** A genuine authorization the agent lacks is surfaced once, not swallowed: while a team has at least one `not-started` card, the owner's Needs-you (console `needs-model.js`, the `work:more` precedent, and the app) shows **one** row for the team, "N internal cards are waiting for your approval or board setting", deduped by team, with two controls: **Approve shown** and **Approve and widen: start internal cards without asking** (§5; the label says what the request says). The expanded row renders, for each listed card, **everything the approval screen shows** (title, requester, need, done items with their certify choice, links, the `outward` flag), oldest first (at most ten; "and k more" expands), and **Approve shown** is N signed approve taps, one per rendered card, each bound to that card's `materialHash` and `titleHash` as every approve tap is (one batch route with per-card results), so the signature covers what was displayed; a card whose hash moved between display and tap is reported `stale-card` and the response says to reopen the row for those; a card that arrived after display is not in the batch. Both controls are the **team owner's**: the owner's PIN on the console (as every console tap, with the PIN's known limit from work-board-asks §4) or the owner's presence-signed phone; from a member's device, or from a bare Bearer, nothing is written and the response says `owner-only`. It is never a push, Telegram or Slack notice; it disappears when no card is `not-started`. Per-card rows never appear.
- It is otherwise **never** a Needs-you row, never in `myBoard.sections`, never a Telegram, Slack or push notice, under either policy. The one exception is the existing `quiet` status, amended (§3 "Quiet"): a workable agent-work card with no agent record for `quietAfterHours` first gets **one automatic re-pickup**, and only if the brake parks a second one does it surface once as a quiet row, because silent abandonment is the failure R2 exists to prevent and a self-heal comes before the person. A card that goes quiet again after a Try again stays a quiet row. A `not-started` card never reads `quiet` (status precedence), which is why the aggregated row exists.
- **Honest limit.** On a team whose owner answers neither the aggregated row nor the offer, cards the owner did not verifiably ask for stay `not-started`: visible under the project, counted in one row, refusing work records, never worked. Cards the owner asked for in their own chat, from their own account or their own paired device, are unaffected; a request whose sender the durable row cannot prove (a forwarded message, a message the log no longer holds, a message with no id, a device record held on another machine, an app event older than the sender fields) is treated like a member's. Notes written by a never-shared Telegram topic session are accepted on the strength of the owner group's binding, which every such session is the agent's; the writing session's binding is recorded on the note event for audit.

### 2. Milestones, notes and close-out

- **Milestones** are the existing `doneWhen` items. An agent-work card has at least one (`createCard` refuses `done-item-required`; the gate always writes one). Items the agent can show itself carry `certify: agent-may-certify`; an item only a person can judge carries `owner-confirms` and may be added at creation (the card is then an ask from the start, §1) or later by an `edited` record when the agent reaches it. Guidance (§6): put the person's judgement **last** and only where it is real ("Justin confirms the screen is clear"), never as a stand-in for a check the agent can run (Live-User-Channel Proof).
- **Progress notes land in the conversation first.** A note is written by the **agent** principal (Bearer, or a scoped `mps_` session whose binding is the card's conversation **or the card's recorded source conversation** — admitted in the route handler, as `/records` already checks its binding in the handler, since the guard's `place` function is a path check) through `POST /work-board/cards/:id/notes { text }`. The route runs the credential guard and the size limit (`limits.noteText`, default 4,000, owner-set up to the hard `SCHEMA_MAX.noteText`, which is the app-conversation store's `MAX_STORED_TEXT` (16,000) minus the fixed prefix, so a maximal note is valid on every replica; a longer text is refused with the limit named and the writer splits it or writes `evidence`), then **reserves the journal emit before writing**: a new `appendWithEmit(event)` on the app-conversation store runs the replicated-journal emit (a synchronous enqueue) **first** and performs the durable local append **only when the emit is accepted** (accepted means enqueued for replication, not fsynced on a peer); a `rate-limited` emit is returned to the agent as `503 rate-limited` with nothing written anywhere, and the agent retries. There is no rollback and no spool, because nothing is written before the reservation. The event is on the card's conversation (agent role; `systemSource: 'work-board-note'`, a widening of the store's `'work-board'` literal in type and validator; text "Work board: the agent noted: <text>"; the writing session's binding recorded on the event), so the person sees it at once on every machine. The **lease holder** then writes the card's **`note` journal record** `{ eventId }` from that event (a new kind in `WORK_RECORD_TYPES`; non-material; it carries the event id, not the text, so the journal stays small and the conversation stays the one copy of the words), paced with the sweep (below). A `note` record counts as activity for `quiet`, is **excluded from `derivePickupCauses`' refold walk** (with `evidence` and `waiting-on`), and is **never** evidence. The card read lists the last note (`lastNote: { text, at }`, cached in the view when the pointer applies; "not yet on this machine" when the event has not replicated), and the row shows "last note" and "last evidence" separately so presence and progress are never confused. Persons write in the card's conversation directly, as today; a `note` record is never written for a person's message.
- **Note rate and the drain set.** The holder writes at most `noteDrainPerTick` (default 25, owner-set) `note` records per tick, oldest events first, and the sweep's and drain's budgets together are clamped to the journal bucket's capacity (100), so the shared `work-card-record` bucket is never exceeded; a `rate-limited` outcome leaves the event pending for the next tick. The holder's **pending set** is reconciled **by event id**, never by time: it holds every `work-board-note` event id on a card's conversation that no `note` record (single or coalesced `eventIds[]`) names; it is fed live by the store's append listener filtered on `systemSource`, and seeded once at boot or takeover by one bounded scan per card conversation (`kind: 'message'`, bounded by the conversation's event count) so a same-timestamp event or an older event replicated after a takeover is never left without a pointer and no conversation is re-read every tick. Above `maxNotesPerCardPerDay` (default 50, owner-set) the holder writes, for that card, **one** `note` record per `noteCoalesceMinutes` (default 60, owner-set, never below 1; an unmeasured default the pilot measures) carrying that interval's event ids, so the journal grows by at most (50 + the day's intervals) records per card per day whatever the conversation holds, and no text is anywhere dropped. The Work page shows the pending-note count per board. The 64 MB journal degradation event stays the signal, and per-card snapshot compaction stays the later-phase item work-board-asks names.
- **Close-out** is the existing path: `evidence` for every item, then `claimed-done`. With every item agent-certified the card is `done` with no tap (`doneByAgentOwnEvidence`) and lands in `done`. The status word `done` means "the agent attested each item"; its `closeout` and its row distinguish two agent-attested finishes: "closed by the agent, with a link or attachment" when at least one counting evidence record carries an `https` link or an attachment, else "closed by the agent on its own word" (a one-word string is accepted by the store, so the label, not a refusal, tells the reader what it rests on). An `owner-confirms` item keeps the current behaviour: `claims-done` → the person's Confirm done. The agent can never archive.
- **Delivering a commitment** (`POST /commitments/:id/deliver`, forwarded to the origin machine as today) first runs the gate when the commitment has no card yet (§3), then writes a note "Delivered: <deliveryMessageId or summary>" on the card. It writes `evidence` **only when the body names the item** (`itemId`, new optional field) and carries `evidence` text (up to the card's evidence limit, 32,000; the commitment's own `resolution` keeps its 500-character slice), and a `claimed-done` only if that was the last unevidenced item; with no `itemId` it writes the note only, however many items the card has. Delivery proves a reply was sent, not that a milestone was met, and the agent names what it proved.

### 3. Every direct request becomes a card (the gate and the sweep)

A card is written **when the request is recorded**, by code, not by the agent, and swept into existence when the first write did not land:

- **Trigger.** `POST /commitments` with `source: agent | manual` (never `sentinel`: a sentinel capture is a guess, and stays in promise-review) whose source resolves to an **operator conversation** (Vocabulary) and that names no `cardId`. The commitment gains optional validated fields the recording session supplies: `sourceConversationKey` (an app conversation key, or `telegram:<topic>` / `slack:<channel>:<thread>`), `sourceMessageId`, `milestones[]` (done items), `outward` (boolean), and, for an outward request, `recommendation` and `whyYou`; the awareness entry tells the session to pass `externalKey` on every request record so a timed-out retry is one commitment (the existing idempotent create). For a scoped session the conversation is **derived from the session's binding** (`res.locals.memorySession.placeKey`; for a never-shared Telegram topic the binding names the owner group, so the body's topic is accepted when it is in that group) and a body value outside the binding is refused `source-mismatch`; the session still passes `sourceMessageId`, which the relay prefix gives it. For **every** principal the requester comes from one place: at recording time, on the recording machine, the **durable message row** for `(conversation, sourceMessageId)` is looked up (an app conversation's event store; for Telegram the adapter's existing backward scan of `telegram-messages.jsonl` by `(topicId, messageId)` under its byte budget and `notBeforeMs` floor; Slack's stored row), and the requester is resolved under the Vocabulary provenance arms, including the device-record lookup for mirrored rows (which only the machine holding the device record can perform; elsewhere the row is unproven). The verdict replicates with the commitment: `sourceVerified: true` with `requesterPersonKey`, `requesterIsOwner`, `requestText` (the row's whole text, credential-checked; a credential-shaped row is withheld, `credential-shaped`, and carries no approval) and `requestTextHash`, or `sourceVerified: false` with `sourceUnverifiedReason: no-message-id | not-found | budget-exceeded | unreadable | no-requester | unproven-provenance | request-too-long | credential-shaped`. A commitment with no resolvable operator conversation is recorded as today with `cardReason: not-operator-conversation`. A scoped session whose binding **is a card's conversation** (a pickup session) records against that card: the gate links the commitment to it (`refs`) and never creates a second card while that card's `refs` has room; the brief carries the card id for Bearer callers.
- **One card per commitment, by identity.** The card id is **derived from the commitment's replicated identity `(originMachineId, id)`** (`serverCard.cardId`, the existing deterministic server-card path from work-board-cards-appear §1), so a retry, the sweep, or any machine that sees the replicated commitment writes the same `created` record, never a second card, and the recording session's judgment that two commitments are two requests is kept. **The card index is the truth** about whether a request has a card: the service keeps a **`refs` index** (commitment identity → the card whose `refs` names it), so "has a card" means that index, or the derived id, resolves to a card; `commitment.cardId` is an **origin-written cache** (set by the origin's gate, or on the origin's boot when it finds its own commitment in the index; written as bookkeeping so it does not re-replicate the row), because replicas are read-only off their origin and the forwarded-mutation ledger is capped, so a dark origin's commitment can have a card and no `cardId` without anything being wrong. When a pickup-session commitment would be the 21st `refs` entry on its card, the gate instead writes that commitment's own derived-id card with a `parent-card` ref to the first, and the brief names it, so the link rule and the `refs` bound never collide. The verified message is attribution and a **hint**: when another open card in the same conversation has the same verified message id, or (absent one) the same normalised title within `requestCards.duplicateHintHours` (default 24, owner-set), both cards carry `possibleDuplicateOf` (read-side, from the service's index) and the pickup brief names it; the agent, the arbiter, merges by closing one with evidence "duplicate of <card>", or keeps both. On `card-exists` the gate links the commitment to that `cardId` and adds its `refs` entry.
- **Gate-only fields.** `created.requester` (`{ personKey, isOwner }`), `created.requestTextHash`, `created.recordedAsHash`, `created.pickupHold` and the `source` that carries request approval are accepted **only from the in-process gate writer** (the server principal, `p.server === true`, the existing `serverKey` pattern); any HTTP writer, Bearer or scoped, gets `gate-only-field`. The fold derives request approval from `created.requester` and nothing else, so no card an agent writes by hand can carry it. `by.isOwner` is stamped by the server on every person write from the team record, never accepted from a body (new code: `byOf` writes no owner fact today).
- **Where and when it runs.** The gate runs on the **origin machine**, after the commitment is persisted and the response sent; the response never depends on the card, and the response and the commitment carry the **derived** `cardId` (derivable before the write) and, once written, `cardWritten: true`. If the write does not land, the **sweep** finishes it: on every boot and on the pickup controller's existing tick, the **lease holder** walks an incremental **needs-card set** (maintained at commitment persist and at `applyPage` for replicas, and emptied for an owner whose replica is replaced on an incarnation change: open or accepted, `source: agent | manual`, an operator conversation, no **terminal** `cardReason`, and no card in the `refs` index or by derived id; never the merged read's duplicate annotation) and writes at most `requestCards.sweepPerTick` (default 25) cards per tick, oldest first, with the same deterministic ids and the replicated `requestText` for `need`, so a dark origin machine's requests are carried by the survivor with the owner's own words. `cardReason` has two classes: **terminal** (`not-operator-conversation`, `backfill-skipped-stale`, `card-exists-linked`, any deterministic store refusal the gate cannot fix by retrying) leaves the set; **retryable** (`mixed-versions`, `daily-card-ceiling`, `store-unavailable`, `rate-limited`, `crash-before-gate`) stays in it until the card exists. For the commitments it touches the sweep also checks that the card's `refs` names the commitment, repairing the card side itself and leaving the `cardId` cache to the origin (the index is authoritative; repair counts join the graduation record). Commitment fields set by the origin propagate through `commitments-sync`; a set `cardId` is never replaced by a `cardPending` on merge.
- **The first run (backfill).** On its first pass for a team, after `caughtUpWithAllPeers`, the holder writes a replicated `enabled-at` record (its own non-card type, like `policy`; id `wb-request-cards:enabled-at:<teamKey>`; earliest `at` wins if two holders wrote one across a takeover); commitments created **before** it are the backfill: cards only for those younger than `requestCards.backfillMaxAgeDays` (default 14, owner-set; a legitimate counterexample is a six-week promise still wanted, which stays in promise-review and gets its card when the agent next records on it or delivers it), uncounted toward the daily ceiling (`serverCard.counted: false`), marked `pickupHold: { kind: backfill }`; older ones get `cardReason: backfill-skipped-stale`. Commitments created after the record are ordinary gate misses (counted, no age floor). Pace is the same 25 per tick.
- **What it writes.** An agent-work card: title = `userRequest` cut at `limits.title` (300) on a word boundary with "…"; need = `requestText` whole on a sender-verified card (locked), else `userRequest` cut at `limits.need` (4,000) the same way (the full text stays on the commitment); `doneWhen` = the body's `milestones[]` (each `certify: agent-may-certify`, each cut at `limits.doneItemText`) or, absent that, **one** item "Done: <agentResponse>" cut at `limits.doneItemText` (500) (no sentence splitting; the agent refines items by `edited` on pickup); `outward` = the body's value, default `false` (the recording session is told to pass it; the external-operation gate is the floor on a wrong `false`); when `outward: true`, `recommendation` = the body's or else `agentResponse`, and `whyYou` = the body's or else "This request sends outside your team or spends money, so it waits for you." — the card is then an ordinary ask (`needs-approval`, in the owner's Needs-you under either policy), which is right for outward work; `projectKey` from the source conversation (§4); `source`, `requester`, `requestTextHash` and `recordedAsHash` (the normalised `userRequest`, the same normalisation as `requestTextHash`) when sender-verified; `refs` = `[{ kind: "commitment", id: "<originMachineId>:<id>" }]` (a **new non-material field**: a typed, bounded list, at most 20 entries, ids `^[A-Za-z0-9_.:-]{1,200}$`, credential-guarded; kinds `commitment`, `blocker-ledger`, `parent-card`; distinct from `links`, which are `https` addresses or attachments and material); `pickupHold` (below). The gate never writes an over-limit field. The commitment gets `cardId`.
- **Pickup hold: the recording conversation owns the work.** The session that recorded the request is already doing the work, so a gate-written `created` carries `pickupHold: { kind: recording-session, conversationKey }` (a backfilled one `pickupHold: { kind: backfill }`). A card is **held** while `pickupHold` is present and no `hold-lifted` record follows. While held: the pickup controller **never spawns a card session** for this card while the recording conversation has a live session, through a **generalised live check** (`hasLiveSession` is app-only today, resolving through the app alias registry; the Telegram and Slack cases resolve through the topic-session registry — build work this spec names beside the inject); a cause that needs the agent (an approve, an answer, an unblock) is **injected into that live session** through a live-only inject seam (a generalised live-only inject for app, Telegram and Slack sessions through the existing inbound queue; the app form is the existing `[app:<alias> … system:work-board]` tag, and the Telegram and Slack forms are `[telegram:<topic> … system:work-board]` and `[slack:<channel>:<thread> … system:work-board]` — build work this spec names; `deliver` is the spawning seam and is not used while a live session exists), and when no live session exists the cause **lifts the hold** (a person's or the system's cause, never the agent's own record) and the ordinary pickup runs under the brake below. The card does not derive `quiet` while held, and the agent's own records never lift the hold. With no cause, the hold lifts only when the card has had **no agent record for `quietAfterHours`** (person taps do not reset that clock); at that lift the recovery brief is **injected into the recording session if it is still live** (a long silent tool run is not a dead session) and a card session is spawned only when it is not. Every lift writes a system record **`hold-lifted { reason }`** (non-material) and is paced: the holder lifts **one per tick, oldest first, and only while no work-cause pickup is pending or in capacity wait**, so a bulk approve, a policy flip, an upgrade or a dead session never causes a wave; the pickup's cause id is that record's id, so the controller's churn brake (which locates a cause by record id) and `foldPickups` see it. A card the agent finishes under the hold simply closes. A live session that ignores an injected cause is recovered only by the quiet lift, which the brief says. A card is never re-held.
- **Quiet, with one self-heal first.** For any workable agent-work card without a hold, no agent record for `quietAfterHours` is a **transition**: the holder writes a system record **`quiet-repickup`** (non-material; idempotent key `wc:<card>:qr:<newestAgentRecordId>`, keyed on the newest **agent-written** record so a park's own system record cannot mint a new key, and written only while no quiet-repickup park stands) and the pickup fires with the recovery brief, the cause id being that record's id, inside the existing agent-caused churn budget (one agent-caused pickup between person records). If the brake parks a second agent-caused re-pickup (`decision:agent-churn`), **that park** is the transition to `quiet`: the card surfaces once as the owner's quiet row with Try again. A capacity or relay wait is not a park (the controller backs off and never parks on time alone), so a transient outage never reaches the row. The fold gains a `newestAgentRecordAt`; the old `newestRecordAt` stays for the other statuses. Amends work-board-asks §5, where inactivity went to the row directly, and makes the row the outcome of a visible brake, not of a clock.
- **Feedback is not a trigger (R10).** When the board is on, `POST /feedback` requires a `source` field from Bearer callers: `{ kind: "agent" | "other-agent" | "user" | "operator-conversation", conversationKey? }`; a scoped session may pass `kind: agent` and its binding fills `conversationKey`; a missing source is refused `400 source-required`; an operator conversation is refused `400 operator-request-not-feedback`; both replies name the commitment route and the card route. The Bearer token is this agent's own, so every Bearer caller ships with this release: the built-in `/feedback` skill, the awareness entry, and the Bearer job scripts that post feedback (the feedback-factory scripts and `failure-callout-investigator`) are updated to pass `source` in the same release, so none answers 400 after the upgrade; peer agents never hold this token. "File this with the maintainers" from the operator becomes a card whose close-out posts the feedback with `source: agent`. The feedback system stays for reports from other agents and users and for the agent's own reports.
- **Sentinel captures.** When the gate writes a card, a pending `sentinel` commitment in the same conversation with the same normalised `userRequest` and `agentResponse` within 24 hours is withdrawn by the existing path (`status: withdrawn`, resolution `superseded-by-<id>`, `supersededBy`), and any beacon on it is paused, so PromiseBeacon and promise-review do not carry it twice. The sentinel dedupe is keyed on `sourceConversationKey` (or `externalKey`) when present, so app and Slack rows dedupe as Telegram ones do.
- **Ceiling.** At the daily card ceiling the gate writes nothing, the commitment reads `cardRefused: daily-card-ceiling` (retryable), the Work page shows the count of refused requests, and the sweep writes the card after the reset. This is the ceiling doing its job and is recorded as a refusal and a count, not a degradation event; a degradation event is emitted only for a real write failure.
- **Chat-only requests** (the operator asks, the agent answers in chat and records nothing) are caught at the chokepoint every operator reply already passes, with no second LLM call: the **existing pre-send tone review** gains one output field, `tookOnWork` (`B27_UNRECORDED_WORK`, judged by meaning like every tone rule; an acknowledgement takes on nothing yet), and the reply is **never** held or `422`ed for it. On the reply's post-2xx completion (the `res.once('finish')` seam that `/telegram/reply` already has, added to the app and Slack reply routes; keyed by the attribution conversation or topic; independent of the correction-learning switch) the server writes a **pending check** as a replicated non-card `work-card-record` of type **`b27-check`** (`wb-b27:<conversationKey>:<inboundMessageId>`), carrying the inbound message id, `replyAt` and `checkDueAt`. The inbound message is **the one the session's current turn was dispatched for** (the server's own dispatch record for that session turn; the relay prefix carries it), so a second inbound that arrives while the reply is being prepared is not mis-indexed; only when no dispatch record exists is the newest operator row before `replyAt` in the durable log used, and never the caller's `metadata`. At `checkDueAt` (`requestCards.unrecordedWorkMinutes` after the reply, default 10, owner-set) the **lease holder** runs a **deterministic lookup**: a commitment with `source: agent | manual` in that conversation whose `sourceMessageId` equals the inbound message settles the check (`b27-check` outcome record `recorded`); a commitment in that conversation without a message id, recorded after the inbound, settles it only when it is the **only** pending check in that conversation; otherwise the holder writes outcome `unrecorded` **and only then** records a **`source: sentinel` commitment** through `CommitmentTracker.record` with the sentinel's dedupe (`externalKey: 'b27:<conversation>:<inboundMessageId>'`, `userRequest` = the inbound text after `detectCredential` (withheld as `[inbound text withheld: credential-shaped]` on a hit), `agentResponse` = the reply's promise, `sourceConversationKey`, `topicId` on Telegram, **`beaconEnabled: false`**), so a commitment exists only for a real omission, the commitments store grows only by omissions, and the row enters promise-review as a guess that never pages anyone and survives the session; the next relay response from that session carries a server-templated one-line note ("Your reply at <time> took on work and nothing is recorded; record the commitment so a card exists") with no operator or reply text echoed, and the conversation's next pickup brief and session-start context name the pending rows until they are recorded or dismissed. Pending checks and their outcomes are journal records under the version floor, counted in the shared bucket, bounded by the existing journal growth signal. The check is unmeasured, and nothing is written, when there is no inbound operator message or the reply was not reviewed (automated replies). The agent's own commitment for the same request supersedes the sentinel one. The graduation record counts checks, `recorded` and `unrecorded` outcomes, rows superseded by an agent commitment, rows recorded inside the window after the note, rows the agent dismissed, and an **independent sample** of inbound operator exchanges (dismissed rows included) checked against the board by the owner-role harness.
- The gate and sweep are **on wherever the board is on** (`workBoard.requestCards.enabled`, omitted ⇒ on; off turns only them off; `migrateConfig` never writes the key).

### 4. A task with no project

- The project is resolved from the source conversation: a conversation that is a project's front door, or inside a project, gives that `projectKey`. Otherwise the card gets `projectKey: general` (a reserved key added to `PROJECT_KEY_RE`; not a conversation), and the Work door and the app show a **General** section after the projects, with the same rows.
- **Proposing a project is the agent's judgment.** The pickup brief for a General card points at `GET /work-board?projectKey=general` (a pointer, as briefs are) rather than listing titles. When the agent judges that several General cards belong together it writes one Conversations suggestion ("Project: <name>", the existing suggestion path), which only the owner's Accept turns into a project; on Accept the cards' `projectKey` is edited to it. The floor: at most one open "Project:" suggestion per proposed name at a time (the suggestion path's existing dedupe on the agent's own structured title); only cards whose conversation the owner may read are moved; the agent never creates a project. No word-matching or threshold decides relatedness.
- General cards have the visibility of any card (§8).

### 5. The lighter policy, per team, through the person

- **The fleet default stays `every-agent-card`** (`WorkBoardService.policy()` is unchanged). R5 is met by what is default for every agent: the gate and sweep, the owner's own request carrying approval, the agent-work card kind and its `not-started` state with one aggregated row, the notes path, carriers and blockers, and an offer of the lighter policy that rests on a record. Moving to `outward-only` widens what the agent starts on its own (member-requested, unverified and agent-initiated inward cards), so it is applied **only through the existing trust path** (`POST /trust/requests {"kind":"board-policy","policy":"outward-only"}`, `boardPolicyRaises`, the owner's `approve <code>` in chat or the paired device's approval): `POST /work-board/settings` refuses that policy today because the PIN is not the person's proof, and this spec keeps that refusal.
- **Existing team: one offer, with its record.** When the lease holder has completed an exchange with every live peer since boot (a new public `WorkBoardRuntime.caughtUpWithAllPeers(sinceBootMs)`; `holdsLease` alone is true with no known holder, so the step waits), it writes a replicated `policy-offer { teamKey, status: pending }` record, raises the trust request, then writes `policy-offer { status: sent, requestId }`. The request says what it rests on, what it covers and that it widens the agent's role: "Start my internal cards without asking? Your own requests already start at once. You have approved <n> other internal cards unchanged, changed <m> and declined <k> so far; <cardsStartingUnder> are waiting now, including <j> a team member passed to me. This widens what I start on my own: every future card that sends nothing outside your team and spends nothing, whoever asked for it; outward cards still wait for you." (The chat form ends "Reply `approve <code>`"; the paired-device form shows the same covers/excludes text natively, the existing `via` choice.) A `pending` with no `sent` after a restart is retried by the holder once per boot; the trust path's `proposalHash` dedupe makes a double raise one request. Delivery follows the trust path's own rules (an undelivered chat card is sent when the owner's chat becomes reachable, on acceptance); the offer is raised once by code and never raised again by code.
- **New team, and any team that has not answered: the request is on the row.** No code-sent offer at team creation. The aggregated row's **Approve and widen** control, and the same control on a `not-started` card's page, are the **owner's** (any other principal: nothing written, `owner-only`) and do two things: approve the shown cards (the signed approve taps above) and **raise the same `board-policy` trust request with the same n/m/k record text** (dedupe: at most one open per team; `proofSubject` for `board-policy` is the change itself, so `proposalHash = proposalHashOf({ kind: 'board-policy', policy: 'outward-only' })` is deterministic). On the owner's paired phone the signed tap line (`WorkCardTapFields` gains `andPolicy: "outward-only"`, the server puts that `proposalHash` into the signed digest, and the phone shows the covers/excludes text on screen before the tap) lets the server raise-or-find the request and then consume the device receipt for it through the existing `onPresenceApproval` path under the `trust` write gate — which requires the owner's device with a current acceptance, `mobilePairing.trustApproval` on, this machine holding the lease, and the request not `too-many-open`; when any of those does not hold the cards are still approved (owner's taps), the request is raised when it can be, and the response says exactly which ("request raised; answer it in your chat or on your phone", or "request not raised: <reason>"). From the console (PIN) the control raises the request and says where to answer it. Nothing but the person's yes through the trust path changes the policy. A request that expires unanswered leaves the row's control as the path back (expiry is not a decline: the trust path has no decline verb, so a later raise from the control is owner-initiated, not a repeat ask).
- **The trust-request queue** gains: (a) an agent-raised request that was **not delivered** (`cardMessageId` empty on a chat adapter) does not count toward `MAX_OPEN_REQUESTS`; undelivered requests have their **own** cap of `MAX_OPEN_REQUESTS` per principal (`too-many-undelivered`), and on acceptance the flush sends `min(MAX_OPEN_REQUESTS − delivered open, undelivered)` of them, newest first, leaving the rest undelivered to expire at `cardTtlDays`. (b) `DELETE /trust/requests/:id` withdraws a request the agent raised and that no person has answered: the stored request becomes `withdrawn`, its chat card (when delivered) is edited to say so, a reply with its code is refused with that reason, and the same `proposalHash` cannot be re-raised for `cardTtlDays` (so withdraw-and-re-raise cannot mint fresh cards; a variant hash is bounded by the two caps and by the per-day raise count the trust page shows). A `board-policy` request written by the boot step or the row control cannot be withdrawn by the agent. Withdrawing never approves anything and is audited like a proposal.

### 6. Default behaviour for every agent

- An awareness entry `src/data/awareness/agent-work-cards.md` tells every agent: recording a commitment for an operator request makes a card by itself, so record it with `sourceMessageId` (the relay prefix carries it), an `externalKey`, and, when it can, `milestones[]`, `outward` and, for outward work, `recommendation` and `whyYou`; a direct operator request is never `/feedback`, and `/feedback` needs a `source`; where the card is (`GET /work-board`, the project row, the `cardId` in the commitment response); write progress with `POST /work-board/cards/:id/notes`, substantive progress as `evidence`; evidence per item then `claimed-done`; set `outward: true` when the work sends or spends or when unsure; put the person's judgement last and only where real; under the strict policy do no substantive work on a member's or unverified request until the card is approved, and say so in that conversation; when blocked by something a person must do, write the ask card from the working session with `POST /work-board/cards/:id/asks` (§9), which links it; pass a card only to a person who can see it (§8); a pickup session records against its own card; General cards and the project proposal; the `B27_UNRECORDED_WORK` note and the pending rows in its brief, and how to answer them (record the commitment, or dismiss the row in promise-review).
- The relay prefix already carries the topic and the message id, and the durable message log carries the sender; `POST /commitments` from a scoped session derives the conversation from its binding (§3) and passes the message id, so the gate has the source without the agent adding more; a Bearer session passes `sourceConversationKey` and `sourceMessageId`.
- `promise-review` keeps reading commitments as the follow-through ledger; `GET /work-board` and the project rows are where a person reads "what is the agent working on". Nothing is switched off.

### 7. The app and the console

- The project row (`ProjectRows`, `GET /work/projects`) already lists `cards`, filtered by what the viewer may read as `boardJson` does. The row's **Needs-you line** comes from the first open ask for the viewer (a card in the viewer's `waiting-on-you` lane with its `needLine`), never from counts; with no open ask the row shows no badge. "Every automatic check passes" is not shown on the row.
- Under the project, cards are grouped **Asks** (waiting on the viewer) then **Agent's work** (`with-agent`, `not-started`, `blocked`, `quiet`, done this week), the second collapsed by default (R4: secondary). Each row shows its carrier (the agent, or a person's display name), "Blocked by: <title>" when blocked, "not started" with the Approve control when `not-started`, "Asked: …" with its age and the divergence labels on a request-approved card, and the close-out label on a done card. Tapping a card opens its page with the conversation, where notes appear as lines.
- A **General** section follows the projects (§4). The aggregated board-setting row (§1) appears once, above the projects, while it applies; `boardJson` gains `notStartedCards: { count, cardIds }` (named so it does not collide with the `myBoard` sections' `notStarted` number) so clients and `needs-model.js` derive it without per-card rows.

### 8. Card owners: any team member (R8)

- **Carrier may be any team member.** `vCarrier` stays a pure validator of shape; the **service** checks, at write, that a person carrier is in the **replicated team record** (the same signed record `mayUseConversation` reads, through the sync `teamStanding` lookup; owner or `team` standing; never `GET /team/people`, which is async and machine-scoped), refusing `not-a-team-member`, or `team-unavailable` when the record cannot be read (no card changes hands on a guess). A card carried by a member is in **that member's** `waiting-on-you` lane and Needs-you (the device viewer carries `personKey`; `boardJson` already passes it); for the owner it is `waiting-on-others`. `laneFor`'s phase-1 rule "only the owner has Waiting on you" is amended to "the card's carrier has Waiting on you". `overSoftBudget` is computed per carrier lane, not only the owner's.
- **Who sees a card (no machine-written grant).** No machine ever writes a team grant: the team-access log's only person writer is the owner's phone, and this spec keeps that. Visibility is a **card-level rule** in `visible`: the owner and the agent see every card; otherwise a person sees a card when they may read its conversation under the owner's grant, **or they are its current carrier**, **or they are its requester as the durable row named them** (`created.requester`, gate-only, §3) — a session binding alone never makes a requester. Carrier and requester visibility hold only while the person's current `teamStanding` is owner or `team`. A carrier or requester sees the card page and its conversation read-only through that rule; writing in the conversation still needs the owner's grant, and the card page tells a carrier without it to use `answer` or ask the owner for the grant. A member's card view omits `refs` ids of cards they cannot read. Blocker titles and close notes are resolved at read time under the viewer's own access (§9).
- **Passing a card** is an `edited` record changing `carrier` (material, as today), written by:
  - the **current carrier** or the **team owner**, person-proven (the owner's PIN or presence; a member's paired device signature, the existing `device` principal), to any team member or to the agent;
  - the **agent**, only for a card it carries, to any team member, under the ask rule (`recommendation` and `whyYou` required on that record; the card becomes an ask). The agent can **never** set `carrier: agent` (it cannot take a card from a person; a person passes to it). Creating an ask for a member and passing one to a member are one rule.
- **Approval after a member's pass.** A `carrier` written by a non-owner person counts as agent-written for `approvalRequired` (the server stamps `by.isOwner` so the fold needs no owner lookup, and records `lastWriter.carrier = 'agent'` for it), so under `every-agent-card` a card a member redirected to the agent still needs the owner's Approve before agent work starts; under `outward-only` it starts, which is that policy's meaning and which the offer text says. A request approval (§1) never covers a card a member passed.
- **Visibility floor on a pass.** A pass to a person who could not see the card (not a reader of its conversation, not its row-named requester) is refused `new-carrier-cannot-see-card`, unless the passer is the team owner, whose pass shares the conversation with the new carrier through the owner's own signed grant from the phone (the existing path; the server writes nothing).
- **A carrier who leaves the team.** The holder reconciles in `AgentServer.afterTeamRows` (the seam that fires on every team-record pull or push) **and on the pickup tick** (a departure that touches no conversation fires no row callback), paced to the journal bucket's remaining budget so a departing member carrying many cards does not burst it: a card whose person carrier is no longer in the record gets a system record **`carrier-departed { carrierEditRecordId }`** (non-material; idempotent key `wc:<card>:cd:<carrierEditRecordId>`, one per carrier assignment, so a later carrier's departure is a new record), which derives a waiting status in the **owner's** `waiting-on-you` with one control, Pass (the owner's tap), **only while the newest `carrier` edit on the card is the one the record names** (the owner's Pass ends it by itself), and one server line in the card's conversation ("Work board: <name> is no longer on the team; this card needs a new owner"); the briefs of cards blocked by it name it. A member re-added to the team does not regain the card: the owner passes it.
- **What a member carrier may do:** write in the conversation when the owner's grant allows; pass the card on; tap `done` (the existing person's close with `closeAs: done`, accepted only from the **current** carrier and bound to the card's material hash, so a tap after a reassignment is refused `not-the-carrier`; the fold counts a non-owner person's close only when they were the carrier at that position) or `answer` an open question addressed to them. Approve (both forms, including the aggregated row), Confirm done on an agent claim, reopen, hold, archive and redact stay the **team owner's** taps.
- **Notification.** A pass writes one server line in the card's conversation ("Work board: passed to <name> by <name>"); the new carrier sees it in their Needs-you lane and the conversation. No push, no Telegram or Slack notice, no row for anyone else.
- The card read and every row show the carrier (`carrier`, `carrierName`) and, when recorded, the requester.

### 9. Blocking links between cards (R9)

- **Records.** `blocked-by { blockerCardId, note? }` on the **blocked** card, written by a principal with **write authority on the blocked card** (the agent for a card it carries or wrote; the card's person carrier; the team owner) who may also read the blocker (a blocker the writer may not read answers `not-found`, as `guardCard` does, so the derived-id space is not an existence oracle); `unblocked { blockedByRecordId, reason }` removes exactly that link, written by the same principals with `reason: cleared` only, or by the **system** writer (in-process only; no HTTP principal maps to it) with its own reasons; the records route refuses any other reason from any caller. Both are non-material. `note` is credential-guarded and bounded by `limits.noteText`. A `blocked-by` naming the card itself, or closing a cycle through open links in the writer's index, is refused `blocker-cycle`.
- **The working session writes the ask.** The R9 flow starts in the scoped session doing the work, which work-board-asks §4 bars from `POST /work-board/cards`. A new scoped operation on the parent card, `POST /work-board/cards/:id/asks { askKey, title, need, carrier, recommendation, whyYou, doneWhen }` (`askKey` `^[A-Za-z0-9_.:-]{1,64}$`; the ask's id is `wc_` plus the first sixteen hex of `sha256(parentId + ':' + askKey)`), allowed for the agent principal and for a scoped session bound to the parent card's conversation or its source conversation (checked in the handler), **creates the ask card and the `blocked-by` link in one idempotent step** (a retry between creation and linking completes the link, never a second ask; a retry whose body differs answers `ask-exists` with the existing id), under the carrier rule (a team person, checked against the replicated team record), the ask rule (`recommendation` and `whyYou` required) and the visibility rule (the carrier sees it by §8). The ask inherits the parent's `projectKey` and carries a `parent-card` ref. **Asks are bounded:** every ask counts toward `maxAgentCardsPerDay` whatever principal wrote it, and a parent card may have at most `maxOpenAsksPerCard` (default 5, owner-set) open asks, refused `too-many-open-asks` with the limit named, so a looping session cannot fill a member's lane.
- **Derived status `blocked`.** A card with at least one `blocked-by` not followed by its `unblocked` has status `blocked`, ranked **after** `needs-approval`, `claims-done` and `done` (a person's pending action is never hidden by a block) and before `parked`. It is not workable; its lane is `with-agent` for an agent carrier or `with-person` for a person carrier; it is **not** a waiting status, so it never enters anyone's `waiting-on-you`. It precedes `quiet`, so a blocked card never reads quiet. The row shows "Blocked by: <blocker title>", or "Blocked by a card you cannot see" (with the blocker id omitted) when the viewer may not read the blocker.
- **The fold stays per card; the holder reconciles; records carry ids, reads carry words.** The blocked card's status depends only on its own records. The **lease holder's runtime** keeps the reverse index (blocker → open `blocked-by` records), rebuilt from replicated records at boot, and **reconciles** at three moments: when a blocker reaches `done`, `archived` or `removed`; when a `blocked-by` arrives (its blocker may already be terminal, in either arrival order); and at boot or takeover (a transition applied at `rebuild()` left nothing to observe). Each reconciliation writes a system `unblocked { blockedByRecordId, reason: blocker-done | blocker-archived | blocker-removed }` on the dependent card (one writer; idempotent key `wc:<card>:u:<blockedByRecordId>`, which fits `RECORD_ID_RE`), bound to that specific link, so a second blocking episode is a new link and a new key. The record carries **only ids and the reason**: the blocker's title, `closeAs` and close note are **resolved at read time** under the viewer's access (the agent, who sees every card, gets them verbatim in its brief, including a member's `done` note or an owner's "Not important"; a viewer who may not read the blocker sees "a card you cannot see"). That record is the dependent's transition into workable, so the existing pickup fires (or, under a hold, the cause goes to the recording conversation) with a brief naming what unblocked it. For churn accounting the cause counts as **agent-caused** when the blocker's finishing record was agent-written, so blocking and self-closing cannot buy pickups outside the budget. A cycle closed by concurrent writes on two machines is detected by the holder, which writes `unblocked { reason: cycle }` on the link with the later HLC; no fold-time cross-card rule. Reopening a finished blocker does not re-block anything: the holder writes one non-material system record `blocker-reopened { blockerCardId }` on each former dependent, rendered at read time as "a card this one was blocked by was reopened" with the title only for viewers who may read it, no pickup; the agent writes a new link if it needs one.
- **The blocker shows what it blocks.** The read derives `blocks: [cardId]` from the reverse index; the blocker's row shows "Blocks: <title>" (same visibility rule).
- **The natural flow.** When the agent's work needs the person, the working session calls the asks operation on its card with the person as carrier and what it needs as `doneWhen`; the ask lands in that person's Waiting on you and the work card shows blocked. When the ask is closed, the system `unblocked` re-enters the work card into workable.
- **Blocker Ledger pointer only.** A card that stands for an entry in the Blocker Ledger carries `{ kind: "blocker-ledger", id }` in `refs`; nothing is merged, and clearing either does not clear the other.
- **Budget, not a refusal, for blockers.** When a card has more than `softOpenBlockers` (default 10, owner-set) open blockers the write succeeds and the response and the brief carry `overBlockerBudget` with the count and the sentence "a chain this deep is usually a project" (§4). Each link is one record under the existing record ceiling.

## Fixed limits

- **At least one done item on an agent-work card** — invariant; basis: enumerable-domain; evidence: `createCard` refuses `done-item-required`, and the gate always writes one; without that refusal the fold's `every()` over an empty list would let a zero-item card finish on a bare claim, which is the reason the refusal exists.
- **Text cut at the existing limits (`title` 300, `need` 4,000 for an unverified request, `doneItemText` 500)** — invariant; basis: external-constraint; evidence: the existing record limits, which the store refuses over; the gate cuts at a word boundary with "…" and the full text stays on the commitment, so it never writes an over-limit field. **A sender-verified request is never cut:** its whole text is stored up to `SCHEMA_MAX.need` (64,000), and a longer row carries no approval (`request-too-long`), because an approval anchored to a cut text would be anchored to less than what was asked.
- **A note-size ceiling exists** — invariant; basis: irreversible-consequence; evidence: the conversation store and the journal replicate to every machine and are never deleted. Its value `limits.noteText`, default 4,000, is a judgment-candidate the team owner sets up to the hard `SCHEMA_MAX.noteText`, which is the app-conversation store's `MAX_STORED_TEXT` (16,000) minus the fixed prefix, so a maximal note is valid on every replica (joins `WorkBoardLimits`, `SETTING_NAMES` and `SCHEMA_MAX`). A longer note is refused with the limit named; the writer splits it or writes `evidence`.
- **A daily note-record ceiling per card exists, and above it records coalesce to pointers at an interval** — invariant; basis: irreversible-consequence; evidence: journal archives are never deleted (`rotateKeep: 0`); the ceiling bounds journal records, never conversation text, which lands at once. The values `maxNotesPerCardPerDay`, default 50, and `noteCoalesceMinutes`, default 60 (never below 1; an unmeasured default the pilot measures), are judgment-candidates the owner sets. A legitimate counterexample to a refusal is a long debugging session, which is why nothing is refused or dropped; a legitimate counterexample to a fixed interval is a live incident wanting prompter journal activity, which is why the interval is owner-set.
- **`requestCards.sweepPerTick`, default 25, and `noteDrainPerTick`, default 25, clamped together to 100** — judgment-candidates; the floor they sit under is an external constraint: the replicated journal's per-kind rate cap (`takeToken`: capacity 100, refill 50 a second) drops emits above it, so `resolveWorkBoardSettings` clamps their sum to the bucket capacity and the defaults use half of it per 60-second tick; system records (lifts, re-pickups, departures, checks) are paced to the remaining budget. A legitimate counterexample is a one-machine team wanting a faster first pass, which the owner can set within the clamp.
- **`requestCards.duplicateHintHours`, default 24** — judgment-candidate; it only decides whether a hint is shown; both cards exist either way.
- **`requestCards.backfillMaxAgeDays`, default 14** — judgment-candidate the owner sets; a skipped commitment stays in promise-review and gets its card on the agent's next record or delivery.
- **`requestCards.unrecordedWorkMinutes`, default 10** — judgment-candidate the owner sets; it only decides when the observe-only lookup runs; a long tool run that records later supersedes the sentinel row.
- **`requestCards.floorRecentHours`, default 72** — judgment-candidate the owner sets; a machine silent longer than this does not hold the version floor; a legitimate counterexample is a laptop closed for a long weekend, which the default admits.
- **Hold lifts and quiet re-pickups: one per tick, and only while no work pickup is pending or in capacity wait; a second agent-caused re-pickup parks** — invariant; basis: external-constraint; evidence: the No Unbounded Loops standard requires every repeating self-action to carry a brake and a settling state; the pickup controller's tick (`pickup.tickSeconds`, default 60) is the grain, the churn budget is the brake, and each lift or re-pickup is a record the brake can see. The shape is the invariant; the tick length is the existing setting.
- **`softOpenBlockers`, default 10** — judgment-candidate, not a refusal: a soft budget carried in the response and the brief.
- **`maxOpenAsksPerCard`, default 5** — judgment-candidate the owner sets; the existence of a hard cap is an invariant with basis: irreversible-consequence; evidence: each ask is a per-card Needs-you row in a person's lane and a replicated card that is never deleted, so an unbounded stream from one parent is attention and storage that cannot be recalled; the refusal names the limit and the owner raises it on the Work page. A legitimate counterexample is a card genuinely waiting on six people, which the owner can allow.
- **One code-raised offer per existing team; one open `board-policy` request per team at a time** — invariant; basis: external-constraint; evidence: *Trust Is Earned by Work and Granted Only by the Person*: an offer declined or left unanswered is not made again without new work; the trust path's `proposalHash` dedupe is the mechanism; the row control is the owner's path back at any time.
- **`MAX_OPEN_REQUESTS` (3) and `cardTtlDays`** are existing limits; this spec adds a second cap of the same size on undelivered requests (basis for a cap existing: irreversible-consequence, a flush on acceptance sends real cards to a person's chat that cannot be unsent; the value reuses the existing constant) and the `cardTtlDays` re-raise refusal after a withdrawal.
- **`maxAgentCardsPerDay` (200)** — existing, unchanged in value; gate cards and asks count whatever principal wrote them; backfilled cards do not; at the ceiling the gate records `cardRefused` and the Work page shows the count; the sweep writes the card after the reset; the commitment plus the needs-card set is the bounded queue, so nothing is lost.
- **`refs` at most 20 entries** — invariant; basis: irreversible-consequence; evidence: `refs` replicates with the card and is never deleted, and the three kinds' real use is one entry each (one commitment, one ledger entry, one parent); a pickup session's commitments link in while there is room and the 21st gets its own card with a `parent-card` ref, so the cap never loses a request; the refusal names the limit.
- **Deliver evidence up to the card's evidence limit (32,000); the commitment's own `resolution` keeps its 500-character slice** — invariant; basis: external-constraint; evidence: the existing field limits of the two stores; the agent's full evidence lands on the card, where it is judged.
- **Aggregated row renders at most ten cards before "and k more"** — presentation; the expanded list approves only what it renders, with every approval-screen field.

## Multi-machine posture

Default posture is unified; every surface is unified through the existing `workBoard` replicated store unless stated.

- **Cards, note pointers, blocked-by/unblocked/blocker-reopened, carrier passes, policy offers, the enabled-at, hold-lifted, quiet-repickup, carrier-departed and b27-check records:** unified (immutable records, whole-record HLC merge; the fold recomputes per card).
- **Note text:** unified through the existing replicated app-conversation store (journal kind `app-conversation-event`, ingested on every machine), written by the writing machine only after the journal emit is reserved, so a note exists on every machine or on none; the holder's `note` record points at the event; the drain's pending set is reconciled by event id against the pointers, never by a machine-local sequence or by time. Conversations keep their existing backup posture (outside backups, replicated), as work-board-asks recorded; no local spool file exists.
- **Commitments and the request text** replicate through `commitments-sync` with identity `(originMachineId, id)`, read-only off their origin (`requestText` joins the clamped and serve-time-redacted text fields); the card id is derived from that identity, so the origin machine's gate and the holder's sweep write the same `created` record, and the sweep writes `need` from the replicated `requestText`. The card index is the truth about "has a card"; `cardId`, `cardPending`, `cardReason` and `cardRefused` are origin-written bookkeeping fields that propagate with the commitment without re-replicating the row, and a set `cardId` is never replaced by `cardPending` on merge. Sender verification happens once, at recording time on the origin, and its verdict replicates; no other machine re-verifies or upgrades it; the holder trusts the origin's row exactly as it trusts every replicated row (first-hop authentication binds it to the pool peer). `state/commitments.json` is not in the backup set today (pre-existing); the card index and the journal are.
- **The one-time offer:** a replicated `policy-offer` record written by the lease holder before and after the raise, after `caughtUpWithAllPeers`; no machine-local ledger is used.
- **Pass lines, departed-carrier lines and note events:** replicated conversation events keyed by the record or note id.
- **System records, the reverse index, the `refs` index, the needs-card set, the note pending set, the sweep, the note drain, hold lifting, quiet re-pickups, `b27-check` evaluation and departed-carrier reconciliation:** the indexes and sets are rebuilt from replicated records at boot on every machine; only the lease holder writes or acts, each with idempotent keys, so a takeover cannot double-write. Held-card causes are injected into the recording conversation's session wherever the mesh routes that conversation.
- **Mixed versions.** An unknown record kind makes a card `unknown` on an older machine and makes the peer-stream applier mark the stream suspect and stop at that line without advancing (`JournalSyncApplier`), so every later record on that stream, ordinary cards included, stops replicating to that machine until it upgrades; unknown **fields** on known kinds fold normally (the validator drops them). So the **new record kinds and the `general` project key** (`note`, `blocked-by`, `unblocked`, `blocker-reopened`, `policy-offer`, `enabled-at`, `hold-lifted`, `quiet-repickup`, `carrier-departed`, `b27-check`, `projectKey: general`) are **written only when the version floor is passed**: every machine in the pool registry whose `MachineLivenessState` is `live`, or `unreachable`/`stale` with `evidenceAgeMs` under `requestCards.floorRecentHours` (this amends `machineLiveness.ts`'s "display only" note: the state now gates one write), has a **current** advert version — `coherenceAdvert.instarVersion` with its `coherenceAdvertReceivedAt`, or after a holder restart has emptied those, `hardware.instarVersion` aged by `evidenceAgeMs`; read beside `PeerVersionFloor`'s ratchet but never from it, because a downgraded peer must lower the floor — at or above the release constant `AGENT_WORK_CARDS_MIN_VERSION`, computed by a getter cached per machine-set change. Machines `unknown`, older than the window, or absent from the registry do not hold the floor; an old build that reconnects is stopped by its own store validator and the applier's `suspect` marking until it upgrades (the version-skew lifeline signal restarts it into the update; it is not itself the guard). Until the floor passes, the notes route, the block routes, the asks operation and the gate answer 503 `mixed-versions` naming the machine, commitments read `cardPending: true, cardReason: mixed-versions` (retryable), the offer step waits, and the sweep drains them when it passes. New **fields** (`refs`, `pickupHold`, `requester`, `requestTextHash`, `recordedAsHash`, `by.isOwner`) need no floor.
- **Member device proof for a pass, a signed tap or a mirrored row's provenance:** accepted only on the machine that holds that phone's device record and presence key; elsewhere the existing write-gate refusal, or `unproven-provenance`.
- machine-local-justification: physical-credential-locality (the device record and presence key live in the per-machine device registry `state/mobile-devices.json`, the existing phone-tap posture from work-board-asks; the requester arm that reads it runs where the record is).
- **Reads:** the app reads the pooled board (`behind` as today).

## Team posture

- **Who sees a card:** the owner and the agent; a person who may read its conversation under the owner's signed record; its current carrier; its row-named requester; the last two only while they stand on the team. Private to the owner and the agent by default. A General card is no different. No machine ever writes a grant. Blocker words and `refs` ids are resolved under the viewer's own access.
- **Who owns a card:** its carrier (the agent or any person in the team record). The team owner may pass any card; a member may pass a card they carry; the agent may pass a card it carries to a member as an ask, never to itself; a carrier who leaves the team hands the card back to the owner's lane.
- **Who widens access:** only the owner, through the existing grant from their phone; a pass by the owner shares the card's conversation with the new carrier; no other pass can.
- **Who acts:** the owner's own sender-verified request approves the agent's inward work on it; the carrier closes (`closeAs: done`) or answers on a card they carry; approve (both forms and the aggregated row), confirm, reopen, hold, archive and redact are the owner's; the policy changes only through the trust path.
- **A team of one** loses nothing: every carrier is the owner or the agent, and every verified request is the owner's.

## Frontloaded Decisions

- An agent-work card is a use of the existing card, not a new record type; the discriminator is `carrier: agent`, `outward: false`, no `recommendation`.
- `recommendation`/`whyYou` are required exactly when a card is an ask at creation or becomes one later; the check runs on the record that makes it one; the gate fills both for an outward request.
- `outward` defaults to `false` for the agent and `true` for a person; the gate writes the recording session's value and an outward request is an ordinary ask; the gates on real sends and spends are untouched; when unsure the agent sets `true`.
- The requester is read from the durable message row's sender for every principal, with provenance proven per adapter: a native Telegram row by `fromUser` and `forwarded === false`; a mirrored or app row by the device record held on this machine (`active`, not revoked) whose role and person fields match the row; a Slack row by the configured id with no bot marker; a session binding proves the conversation only; anything else means no requester.
- The owner's own sender-verified request carries approval for the agent's inward work on it, under either policy, for every commitment recorded on that message, and is never asked again; the yes is anchored to the whole message text (`need` locked, up to `SCHEMA_MAX.need`; a longer row carries none), survives the agent's edits to title, milestones and links (shown by the age and two deterministic labels), and ends on a flip to outward or to a person carrier or on a withdrawal; no age or count caps it.
- The fields request approval reads are written only by the in-process gate; the server stamps `by.isOwner`; any HTTP writer is refused `gate-only-field`.
- Under the strict policy an agent-work card without request approval is `not-started`, a non-waiting status that refuses work records (counted), and the agent does no substantive work on it before approval (measured by the harness sample); the team's unstarted cards surface as one aggregated Needs-you row that renders every approval field per card, with Approve shown (one signed tap per rendered card) and Approve-and-widen, both the owner's only; never per card, never a push; the honest limit is stated.

- The iPhone changes are built in the Apple rebuild project's worktrees (`apps/ios-wt/*`, branch `agent-work-cards`) on the Laptop, and the owner and member journeys are driven on the simulator there before the run claims done; an unavailable machine or source is a reported blocker.

## Rollback

Revert the release on every machine together. Cards that carry one of the ten new record kinds or `projectKey: general` read `unknown` on the old build (non-workable, in no lane) until re-upgraded, and an old build's stream applier stops at the first such record, so ordinary cards written after it stop replicating to that machine until it upgrades; because new kinds are written only under the version floor, a machine that never upgraded holds none. Cards carrying only new fields fold normally on the old build and stay ordinary agent cards (valid under the old rules except for the missing `recommendation`, which the old route only checks on write). Note text stays readable in the conversations. A team moved to `outward-only` keeps that person-proven record, which the owner can set back through the settings route (the strict policy is never a raise). Commitments keep `cardId` and the source fields as ignored data, and `B27` sentinel rows show in promise-review as ordinary sentinel rows; the `enabled-at` record survives so a re-upgrade does not re-backfill. No data migration.
