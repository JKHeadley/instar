# Independent Acceptance for Owner-Facing Work

## Problem statement

An implementation check passed after Camera opened the right app and identified the right computer. The owner still could not complete the link. An agent also wrote approval cards whose titles were readable while their descriptions and completion items exposed internal work. Delivery needs independent proof of what the person can do.

## Proposed design

Design owns the rules and reviews each project's acceptance line before the build. The project owns the work and supplies evidence from the normal journey on the actual phone or screen. An assigned verifier who did not build that candidate decides whether the line passed. Keep acceptance separate from the owner's consent, publication, and any project's existing close authority.

Pilot one explicitly registered terminal project milestone and its automatic completion notice. Before the build, the coordinator records Design's approval of the exact acceptance line and applicable rule references in the Chief of Staff journal. An edit to the line requires new Design approval. The requirement binds the project, milestone, exact candidate commit and installed runtime identity, stable builder principals across respawns, assigned verifier principal, assignment epoch, exact Chief project binding and monotonic revision. Registration and ordinary automatic closure serialize on the exact confirmed project binding and revision. The durable registration event carries both the Design approval reference and the pilot marker in a single append, which the project binding fold projects. A closure that wins first makes registration return Already Closed. A registration that wins first routes automatic closure through acceptance, even if an earlier read was unregistered. Unknown pilot eligibility or an incomplete journal read holds automatic completion before it can report verified or take the ordinary close path. Disabling or expiring a registered pilot holds automatic completion. It cannot restore ordinary automatic closure.

The project supplies a private evidence manifest covering the actual entry point through the visible outcome and resulting state. Before recording Pass, the verifier independently observes a fresh request on the named surface and obtains the resulting state from that runtime using a request unique to that attempt. The coordinator can approve a paired-phone test fixture that uses the same owner role and production journey. Missing access, unresolved provenance or inability to repeat the critical transition yields Pending. Existing Design Standard screenshot requirements remain a separate gate for changed surfaces. Validate bounded private artifacts when submitted, record hashes and authorized pointers, and exclude secrets, private identifiers and reusable links from the journal.

Use strict sessionProducer credential verification and authoritative local live-session assignment lookup for receipt submission. Require the exact assigned stable principal and assignment epoch. Reject fallbacks, generic bearer alone, expired credentials, the builder roster and caller-supplied identity. The coordinator lease holder rechecks the live session incarnation and assignment inside the serialized append and writes a domain-tagged canonical signature over the project binding, milestone, event type, coordinator lease epoch, verifier assignment epoch, sequence and full payload. The lease epoch selects the historical signing authority. The assignment epoch binds the verifier. This trust boundary covers supported interfaces. A compromised holder or unrestricted host principal can access the underlying credentials.

Store Pass, Fail or Pending with the active revision, candidate, artifact hashes, reason, verified principal and server sequence. Pass requires a protected verifier evidence record separate from the immutable project manifest. It binds the unique fresh request, active revision, installed build identity, observed result and independently obtained before-and-after state hashes. A reused request or earlier readback cannot qualify. Canonical request identities are idempotent only for an exact payload. A later Fail or Pending supersedes a Pass. Before issuing a fresh request to retest an active Pass, the assigned verifier commits Pending through the same reservation lock. A reservation that won first remains terminal. In the Camera pilot, use the server-side Camera acceptance receipt write lock keyed by the milestone and active revision. Under that lock the server refuses to issue a fresh verifier request while Pass is active. The verifier must first commit and fsync a Pending receipt for that revision. Changing candidate, manifest, assignment or acceptance line requires a fresh attempt. An unknown, incomplete or contradictory record holds completion.

In the automatic close path in ChiefOfStaffLoop.checkProject, check the active receipt before recording closure or mirroring initiative completion. For the registered pilot, replace the disposable in-memory completion note with one signed durable accepted-completion intent. The intent stages the owner notice and leaves the project and initiative open. The dispatch reservation described below is the automatic closure event. At reservation the current project-wide automatic close conditions and exact project binding must still pass. The normal project fold projects closure from the reservation, and initiative mirroring catches up idempotently after restart. Any owner closure or reservation is terminal for that milestone across revisions and destination changes. A Fail after intent but before reservation leaves both open, including after restart. Decisions recorded after reservation are retained for review and leave the already recorded closure intact. Existing owner-initiated Finish and Confirm Done remain available. Serialize their durable closure with reservation. If owner closure wins, retire the intent without a verified notice, including on restart. If reservation wins, owner closure is already satisfied. Ordinary chat, review requests, consent and draft publication retain their paths.

At the Chief notice dispatcher, serialize requirement and receipt writes with a durable dispatch reservation on the same holder. Deduplicate by project binding, milestone and notice kind. Derive a delivery reference for reconciliation from that identity, destination and authorized revision. A newer decision committed before reservation holds dispatch. The release authority must attest the active installed build and hold a read pin that prevents release replacement through the fsync of the dispatch reservation. A missing pin, absent identity or build different from the tested release holds delivery. The first Camera pilot uses a coordinator-controlled test release whose rollout and reservation use the same lock. A release switch or requirement amendment before reservation invalidates acceptance. The live holder that fsyncs the reservation gets one nontransferable right to invoke transport. Handoff after reservation does not revoke that right, and the successor may never invoke it. Bind the reservation to the originating process incarnation. Reconciliation stays pending until the invocation has returned or the coordinator can establish that the originating process incarnation has terminated and cannot invoke it. Record confirmed delivery durably. Any recovered reservation without a durable outcome is ambiguous, including interruption before the transport call or after acknowledgment. In either case, keep the attempt pending without automatic resending. The coordinator may confirm delivery using a transport receipt matched to the destination and notice ID, or record Delivery Unknown when the adapter cannot prove the outcome. Delivery Unknown is terminal for that notice and cannot trigger another send. Once reserved, do not reopen admission for that notice. A confirmed failure before the transport accepts it is recorded as Delivery Failed. Project closure remains in effect. A coordinator can discuss the outcome through ordinary project conversation without creating a second automated completion notice.

## First acceptance line

**“Justin can finish it on his phone without being redirected.”**

Start on the computer only to make a fresh link code. Before the first snapshot, seed an existing grant for the paired iPhone on a second computer and confirm that the intended computer is visibly unlinked and its expected grant is absent. Scan from the iPhone Camera. Instar must identify the intended computer, explain access, use the phone's native identity check and show that the computer is linked. After the scan, a browser, dashboard, second computer action, typed PIN or separate person fails the line.

For success, cancellation, expiry and used-code replay, snapshot all authoritative grants for the tested phone across computers immediately before and after each trial. Compare sets by grant identity, phone identity, computer identity, access, expiration and revocation state, independent of ordering. Success must add exactly the expected grant for the intended phone, computer and access, with every existing grant unchanged. Cancellation and expiry must leave the intended computer visibly unlinked and preserve the entire starting set. Replay must leave the intended computer visibly linked and preserve the entire post-success set, including the original grant. The second-computer grant must remain unchanged in every trial.

Member approval is a separate path. The observed run opened Instar, matched the fingerprint and stopped on guidance for linking through the dashboard. The computer remained unlinked. Record it as **Fail** for direct phone linking.

PR 3783 is the card-text component. Its separate acceptance line is that Justin can open an approval card on his phone and understand what he would approve and what would happen next. Its verifier must open a rendered approval card as the owner and read its title, description, completion criteria, details and reason for asking him. Apply the Design Standard's plain-language and five-second rules there. The Camera pilot has no approval-card step.

## Decision points touched

- Assignment and receipt origin — invariant; basis: irreversible-consequence; evidence: trusting a builder's own verdict allows unsupported completion to reach the owner.
- Requirement and evidence binding, including the delivered candidate — invariant; basis: enumerable-domain; evidence: compare the active revision, candidate and hashes against the receipt and outbox item.
- Evidence meaning and design compliance — judgment-candidate; an assigned independent verifier decides pass, fail or pending. The floor requires the declared real surface, observed outcome and durable state readback. Missing proof falls back to pending.
- Delivery and milestone completion — invariant; basis: enumerable-domain; evidence: only the latest complete pass for the active binding can admit the structured accepted event.

## Multi-machine posture

Use a complete Chief of Staff journal read at startup and verify each canonical signature against the historically authorized holder for its epoch and require a contiguous pilot sequence. Retain distinct signed event keys so two different valid payloads at one sequence hold the fold instead of being hidden by last-write wins. Cache the folded pilot state against the journal version and update it on each successful append. Missing records, unknown peer coverage and invalid signatures keep the pilot pending. The first pilot runs on its registering lease epoch. Suspend automatic completion on handoff until an authoritative catch-up mechanism is available. Gate the first write on support for the record types by all participating readers. Keep protected captures on the authorized artifact owner.

## Verification and rollout

Camera pilot release requires three test tiers. Unit tests check full grant-set comparisons for all four trials, including deletion and mutation of the second-computer grant, plus redirect, stale candidate and missing evidence. Integration tests cover authenticated receipt submission, builder rejection, and the server refusing a fresh verifier request while Pass is active. Race tests cover both orders under the receipt write lock and show that a crash after fsync of Pending leaves acceptance on hold. A production lifecycle test checks durable receipt recovery after restart, exact-candidate binding and the same request refusal after restart. Run the four trials on the real phone before recording Pass and include the required side-effects artifact.

## First build scope and follow-ups

The first implementation is limited to the Camera computer-link acceptance line. The pilot receipt and gate report a decision for the exact Camera candidate. General enrollment, automatic project closure and owner notices are follow-ups. Their dispatcher, reservation, delivery, handoff and closure tests gate those later changes.
