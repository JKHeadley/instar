# A way back into a stopped machine

Tonight Echo's laptop kept starting and then being killed. Echo's other machines could see the trouble, but none had a tested way to repair that laptop while Echo's main server was down. Another agent happened to find the cause. Instar needs a dependable repair path that does not rely on luck or another agent.

This proposal makes every machine in a multi-machine agent keep two tested ways for one of its *own* paired machines to reach it. The first uses the machine's ordinary SSH service with an Instar key restricted to a small list of repair actions. The second is a small Instar recovery helper that runs separately from the main server and connects through a relay with its own key. If the direct SSH network path is unavailable, the helper can still receive a signed repair request. The two ways are checked before trouble and checked again every few minutes. A key file or an open port by itself does not count as a working way in.

Instar already has much of the groundwork: paired machine identities, an SSH key exchange and probe, a machine health view, a relay, and a separate lifeline. Those parts do not yet provide two live ways to repair a stopped server. The SSH and peer-execution features currently default to dry run, and the existing restricted SSH endpoint stops with the main server. This proposal extends those parts, removes old unrestricted Instar-managed SSH grants before turning on the restricted route, and adds the independent helper.

Only the same agent's paired machines can request repair. Each request is signed, short-lived, limited to named actions and recorded without secrets. The keys stay on their own machines, and each agent has its own recovery signing key. A separate control service confirms current grants and revocations; without a fresh confirmation for 24 hours, both routes close rather than keep accepting a possibly revoked key. The operator can see route health and revoke access from a phone. If a target cannot receive a revocation yet, the phone says it is pending and shows the remaining exposure; it does not claim the key has already been removed.

The repair helper can gather diagnostics, restart Instar's server and briefly hold a clearly identified Instar-owned watchdog rule. A separate host timer restores that rule if repair crashes. It cannot change another agent's watchdog or a rule owned by the person using the machine. The external watchdog involved tonight is outside this work.

Before this can be enabled broadly, it must pass real tests using throwaway agent identities on two actual machines: stop the server, fix it through the direct route, block that route and fix it through the helper, and repeat with a kill loop. No production agent or operator channel is used for those destructive tests. Existing machines get the same setup and checks through an Instar update; new machines get them at enrollment. A machine with only one working route appears as degraded in health before an emergency, and Instar sends a plain notice only when automatic repair cannot restore it or a person must grant access.
