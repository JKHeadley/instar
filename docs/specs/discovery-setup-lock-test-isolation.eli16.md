# Give Discovery Tests Their Own Setup Marker

Discovery tests check that an unfinished setup can record its progress, read that progress later, update it, and remove it when setup finishes. The production discovery module chooses the marker file’s path when the module first loads. The old test files loaded that module before substituting a temporary home directory. Their later home substitution changed directory scanning, but it did not change the marker path that the module had already captured. One unit fixture explicitly removed the computer’s real setup marker, and integration cleanup called a function still bound to that real path.

This change repairs those test fixtures without changing discovery behavior. A shared test-only loader evaluates the real discovery module while its home lookup points at an owned temporary directory. It immediately restores the original lookup in a finally block and clears the temporary module cache. Only the returned marker functions retain the private path. The unit cases call those functions after the ordinary lookup has returned. The integration cases retain their existing temporary home during filesystem discovery, but their marker functions are separately bound to that same private home.

Every original marker case remains: missing files, real writes and reads, deletion, repeated deletion, corrupt JSON, parent directory creation, update and persistence across discovery runs. The corrupt case now checks that the reader actually sees the private corrupt file and leaves it intact. An additional regression evaluates two independent private modules, checks both real JSON files, deletes one marker, and confirms the other still exists with its original contents. Cleanup removes only the test’s owned temporary directory. The operator’s actual marker is never read for comparison, backed up, overwritten or deleted.

The normal runner environment, worker settings, admission rules and production code remain unchanged. No PID or process-liveness behavior is replaced. The whole unit file and integration file are verified sequentially only after independent review and coordinated allocation. The unsafe old fixtures are not run as a baseline. Publication and complete verification remain separate steps with their normal owners. A revert needs no migration, live marker restoration or restart.
