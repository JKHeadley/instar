# Pull-request description lint at open time — ELI16

Every pull request has to carry a proper description before it can merge: a plain-language ELI16 section, a decision record for files that need one, a release note when the change ships something, and a UX Impact section when it touches what a user sees. The merge script (safe-merge) checks all of this at the very end, just before merging.

Until now, the early versions of those checks ran only on pull requests aimed at `main`. A "stacked" pull request, one built on top of another unmerged branch, got no description check at all until it was retargeted. Its first refusal then came at merge time, after a full test run on our machines had already been spent on it. On the morning this was built, 21 open pull requests were stacked, and today's repair briefs found a missing or broken UX Impact section in about half of the older changes.

This change adds an early warning that runs on every pull request, whatever its base, every time the pull request is opened, edited or pushed to. It runs exactly the same description functions safe-merge runs at merge time, and it reads the pull request's live description and file list just as safe-merge does, so the early answer matches what safe-merge would say if the pull request merged as it stands now. UX Impact is its own gate, so it is shown separately. The result appears on the pull request as a status that always passes, with a short note saying what would be refused. It never blocks: it is not required, and nothing in it can turn a pull request red.

To keep it trustworthy, it runs from a kind of GitHub workflow that is always read from `main`, so a pull request cannot change the check that judges it. It treats the pull request's own text and files only as data, and it has the smallest permissions it needs. Nothing in an agent's install changes: this lives only in the repository's CI.
