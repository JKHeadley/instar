# Sign-in repair: unattended on the agent-session path, and slow retry of failed repairs

## Problem statement

Live data from Echo's pool view on 2026-10-14 (`GET /subscription-relogin?scope=pool`):

1. **The no-tap list is ignored on the agent-session path.** Echo's config sets `subscriptionPool.assistedRelogin.mode: "unattended"` and lists `echo@sagemindai.io` in `unattendedPolicy.identities`, with both evidence floors set to 0. `navigation` is omitted, so on a macOS development agent it resolves to `agent-session`. That path forces `approval` whatever `mode` says (`SubscriptionReloginRuntime.createSubscriptionReloginRuntime`, `effectiveMode`). Result: repair episodes for `echo@` on the Mac Studio and the Mac Mini were created in mode `approval`, state `suggested`, and sat untouched from 09:39 / 10:33 that morning.
2. **A failed repair never retries.** An episode that ends `failed` (`attempt-budget-exhausted`) stays `failed` while the account stays signed out: `dawn@` on the Laptop since 2026-09-14, `justin@` on the Mini since 2026-09-25, `justin@` on the Studio since 2026-09-24. The only way forward is an operator tap on **Try repair again**. Nothing re-surfaces it.

## Proposed design

### 1. Every navigation path honors `mode` the same way

`createSubscriptionReloginRuntime` passes the configured mode through unchanged on every path (`effectiveMode = deps.mode`). The admission policy (`evaluateSubscriptionReloginAdmission`) is already the single authority that decides `unattended` vs `approval`, and it is unchanged:

- `unattended` is granted only when the account's **exact email** is on `unattendedPolicy.identities` **and** the evidence floors hold: `successfulRepairs ≥ minimumSuccessfulRepairs` (default 10), `evidenceDays ≥ minimumEvidenceDays` (default 30), zero `wrong-identity`, zero `unexpected-origin` / `permission-expansion` on that account × machine path.
- Every other account is held at `approval` (`unattendedHeld: true`), exactly as today.

Every existing floor of the agent-session path stays, untouched: sign-in origins only, never another account, the helper runs on a **different** healthy account on the same machine (`pickSeat` excludes the account under repair), one helper per machine (seat lease), the 15-minute cap, and success decided only by the server (`verifyIdentity` match + an authenticated call + pool activation + the source incident closing).

**The trust change, stated plainly.** On this path the helper is a trusted local operator whose intermediate actions (which pages it visits, where it types a password) are bounded by the `/subscription-signin` skill's hard lines, not by code (skill-driven-signin-repair, "Named residual risk"). Until now the operator's tap was the outer bound on *when* such a helper runs. After this change, for an account on the no-tap list, the outer bound is the operator's own allowlist plus the evidence floors, and the operator is no longer present at the moment it runs. The server-side floors (other-account helper seat, one helper per machine, 15-minute cap, server-only success, per-account breaker) are unchanged; they bound blast radius and decide success, but they cannot stop a misbehaving helper typing a secret on the wrong page mid-run. The operator chose this trade on 2026-10-14 by putting these identities on the no-tap list and asking for the list to be honored on this path. Accounts not on the list keep the tap.

**Additional unattended floors (added in review).** The general evidence floors count successes per account × machine × provider × framework × login method, not per sign-in path, and on Echo they are set to 0 by the operator. Two structural floors are therefore added to the graduation check, so removing the tap does not lean on prompt text alone:

- **Helper hard-line reports hold the next repair at approval.** Any helper-reported hard line (below) recorded on this account × machine since its last verified success sets `helperHardLines > 0`, which holds the account at `approval` until a verified success clears it. Counted from the audit events, so a later operator cancel cannot erase it. Not breaker evidence (it is an unverified claim).
- **Backup codes.** Accounts whose second step uses single-use Google backup codes (a `backupCode` vault binding) are held at `approval` when the bound entry holds fewer than `maxAttempts + 1` codes (4 by default), or cannot be read. The check runs before **every** unattended run (a first attempt and each slow retry are separate admissions), and one run has at most `maxAttempts` drives. On the browser-driver path one code per drive is enforced in code (`takeBackupCode` removes the code from the vault before it is typed; `backupCodeSpent`), so at least one code survives a run — assuming Instar is the only consumer of that vault entry on that machine and runs one repair at a time there (the seat lease). The count is read fresh at every admission. If a person or another machine also spends codes from the same entry, the floor is a best-effort check, not an allocator. On the agent-session path the helper types codes itself and nothing removes a spent code from the vault, so the stored count cannot be trusted there: **on that path a backup-code account is always held at `approval`**, whatever the count. (Today that is `headley.justin@gmail.com`, `justin@`, `dawn@`; of these only `headley.justin@` is on Echo's no-tap list.) A per-drive code allocation for the helper — taking one code out of the vault before spawning it and handing the helper that single code — would lift this hold; until it exists, the hold is the honest floor. TOTP accounts (echo@, adriana@, luna@) are unaffected.

**Upgrade-time effect.** The admission digest includes `mode`, so for a listed identity the next scan computes a new digest and `SubscriptionReloginStore.suggest` re-admits the cell's `suggested` row under the new inputs (the existing `candidate-readmitted-inputs-changed` path); the service auto-approves it under `unattended-policy`, which is the intended heal for the stuck `echo@` rows. For this to happen the scan now passes the incident's own re-admittable row (`suggested` or `cancelled`) to admission as the current episode: before, that row counted as "another live repair" (`repair-already-live`), so a suggestion whose inputs changed was never re-admitted and the operator's tap on it failed with `approval-input-digest-mismatch` (the integration test reproduced both). And if the operator taps **Repair sign-in** on such a suggestion before the scan re-admits it, the approval now re-admits it on the current inputs and approves that, instead of refusing; the unattended policy may do so only when the fresh mode is `unattended`. The re-admission path is tightened at the same time, so input changes never authorize execution on their own:

- A **`failed`** row is no longer re-admitted on changed inputs at all. Every automatic restart or re-offer of a failed repair goes through the one paced path (`slowRetry`: due time, cap, operator hold, quiet hours, one per machine, governor, `slowRetry.enabled`). When the operator taps **Try repair again** and the inputs changed since, the repair is re-offered on the current inputs (`failed → suggested`, event `operator-retry-readmitted`, no budget spent) for one more tap, instead of the old `approval-input-digest-mismatch` refusal.
- A re-admitted **operator-cancelled** row is stored as `approval` whatever the new inputs say — on every later re-admission too, until the operator approves it again (read from the audit events) — and the service auto-approves only when the stored mode is `unattended`: an operator cancel is never followed by a tap-free run.

### 2. Slow automatic retry of a failed repair

A new step in `SubscriptionReloginService.tick`, `slowRetryDue()`, runs after the scan and the resolved-elsewhere sweep.

**Hard-line stops become operator hand-offs, not failures.** (Terms: a helper report is a *temporary autonomy hold* on that account × machine — it is an input to the unattended decision — but never *verified security evidence*: it does not open the breaker, block re-admission, or count as a `wrong-identity` / `unexpected-origin` mismatch. A verified success, by repair or by hand, clears the hold.) The helper used to end every stop the same way (`agent-sign-in-unfinished`), so a CAPTCHA or a wrong-account screen was indistinguishable from an ordinary unfinished run and would have been retried. The helper's code route gains one more strict shape, `{"notify":"hard-line","line":"captcha"|"phone-confirmation"|"wrong-account"|"unexpected-site"}`, named in its fixed prompt. Every report settles the drive as `operator-only` with the one new class `agent-hard-line` (the line rides the reason token `agent-hard-line-<line>`), so the episode goes to `waiting-operator-only`, the operator gets the existing "needs you / Sign in from your phone" notice, and a slow retry never touches it (retries start only from `failed`). A report can only reduce autonomy. It deliberately does NOT use `wrong-identity` / `unexpected-origin` / `captcha` / `phone-confirmation`: those are breaker, re-admission-blocking and graduation evidence, and a helper's unverified claim must not permanently disable repair for that account; the hold above is its bounded effect instead. A report after the drive's outcome is decided is answered `409 already-settled`, never a false "accepted". Residual: a helper that hits a hard line and exits without reporting it still ends `agent-sign-in-unfinished` and is retried; each retry meets the same hard line and stops again. Limits per incident: at most 3 slow restarts, each a fresh run of at most `maxAttempts` (3) drives, so at most 12 drives in all.

**Two helper prompt lines from the 2026-10-15 manual sign-in of all five cells.** Google now opens some accounts on a passkey screen; the prompt tells the helper to choose "Try another way", then "Enter your password". (`google-passkey` accounts never reach the helper: the drive refuses them before it spawns.) And once Google accepts the second step the helper must finish in the same Chrome window: closing and relaunching right away lost the session and spent a second backup code. Prompt text only; the backup-code floor above is the structural backstop.

**Eligible rows.** State `failed`, no operator hold, and a failure class on an **explicit allowlist** (so a class added later is never retried by default): `attempt-budget-exhausted`, `repair-time-budget-exhausted`, `agent-sign-in-unfinished`. Each ends a run whose last action was safe to repeat: `attempt-budget-exhausted` is only reached after the orchestrator's in-run retries ran out — parent §7's transient set (`seat-busy`, `target-unreachable`, `artifact-expired`, `provider-transient`) plus the existing `verification-failed` (the identity or authenticated-use read was unavailable: a re-observation, not a replayed external action) — or the artifact-reissue budget ran out; `retry()` is never called with anything else, and the last transient class rides the event's reason. `agent-sign-in-unfinished` ends a run without a code having been accepted, and so does `repair-time-budget-exhausted` when it fires before `cli-finishing`. If the 10-minute budget fires later (code already pasted, during `cli-finishing` / `identity-verifying` / `auth-verifying`), the credential may already be written: the poller's authenticated read then activates the account and closes the incident, so admission refuses the retry; if it has not by the time the retry is due, the retry signs the same account in again (redundant, never wrong — identity is re-verified). Either way (a url-code-paste login completes only when Instar pastes the code, which it never did) — and for a device-code login the drive checks the CLI's own credential at every poll and through a settle window after the helper exits, so a sign-in the provider completed is recorded as approved, not unfinished. A provider code issued but never delivered has no effect; the run's own login is abandoned at the next `cli-starting`. If a device authorization completes later still, the CLI writes the credential, the poller's authenticated read activates the account and closes the incident, and the next admission refuses — so a retry hours later does not run over a sign-in that landed in the meantime. A completion in the seconds between a retry's admission and its `cli-starting` is not excluded; then the retry abandons the old login and signs the same account in again, which is a redundant sign-in, not a wrong one (identity is verified again before success). Browser sign-in steps themselves (password, TOTP) are repeatable; spent backup codes are covered by the backup-code floor. **No uncertain action is replayed:** an uncertain external outcome (restart mid-drive / mid-finish) goes to `waiting-operator-only` (`uncertain-external-outcome`), never `failed`, so it is never slow-retried; and before any retry the full admission re-observes the account (still `needs-reauth`, incident still open) — if an earlier run had in fact signed it in, the poller's authenticated read activates it and closes the incident, and admission refuses. Never retried, per §7: the security classes (`wrong-identity`, `unexpected-origin`, `permission-expansion`, `captcha`, `phone-confirmation`), `authority-degraded` (corrupt authority), `provider-rejected` (including a lapsed approval — the operator can tap **Try repair again**), `vault-reference-missing`, `passkey-refused`. `refused` and `cancelled` rows (safety refusals, operator cancels, resolved-elsewhere) and `waiting-operator-only` rows are **never** touched. A run that stopped at any operator-only challenge since it was last admitted or retried (CAPTCHA, phone check, permission expansion, macOS permission, helper hard line — event `operator-only-challenge`), or that asked the operator for a phone tap (event `phone-tap-requested`, now written whenever the helper's phone-tap notice is queued), is never slow-retried either (a helper's `no-healthy-seat` hand-off is a seat shortage, not a challenge, and does not count), even if the operator later resumed it and it then ended `failed` (a resume clears the row's class, so this is read from the audit events: `challengedSinceAdmission`). `isSlowRetryEligible` in the store is the one predicate. A verified wrong identity whose quarantine then failed now ends `failed / wrong-identity` (previously `authority-degraded`), so it is breaker evidence and never eligible.

**Schedule.** Per episode (one episode per source incident, `UNIQUE(sourceEpisodeId, accountId, machineId)`):

- The n-th retry (0-based) is due `delaysMs[min(n, last)]` after the failure — or, for a row that failed longer ago than that (every row at upgrade time), one delay after the tick that first sees it plus a stable per-cell offset of up to an hour (a hash of account × machine), so rows first seen in the same scan do not all fall due together. Within a machine, the one-retry-at-a-time rule below serializes them further. Default `delaysMs = [6 h, 24 h]`, so: 6 h, then 24 h, then 24 h. The fresh delay applies only to a row that has **no** recorded `nextAttemptAt` yet; a schedule already recorded is durable, so after a restart or downtime an overdue recorded retry runs as soon as it is admitted, without a second delay.
- At most `maxRetries = 3` per episode. The count lives in a new durable column, `repair_episodes.slowRetryCount` (additive `ALTER TABLE … ADD COLUMN … NOT NULL DEFAULT 0`), so a restart can never refill it. It increments on the unattended restart and the approval re-offer. Nothing resets it.
- **Breaker accounting.** The per-account breaker (`isBreakerOpen`) now counts failed/refused **runs** from the append-only `repair_events` table (transitions into `failed`/`refused`; schedule and hold events on an already-failed row do not count), not episode rows. A slow retry or an operator retry reuses its row, and each of its failed runs still counts toward "3 in 24 h", so the parent's account-level bound holds across retries; any security-class row still opens it at once. The breaker remains per machine (each machine's own `repairs.db`), as it was.
- The first tick that sees an eligible row records `nextAttemptAt` (new store method `scheduleSlowRetry`, version-checked, audited as `slow-retry-scheduled` with an optional reason token) and does nothing else that tick, so the time is durable and visible before anything acts. Rows that are not eligible and carry no schedule are skipped without any lookup.

**Acting when due.** On a later tick, once `now ≥ nextAttemptAt`:

1. Cheap pre-check: eligible, cap not spent, source incident still open (`sourceIncidentOpen`, the same predicate the orchestrator uses). Otherwise `nextAttemptAt` is cleared (`slow-retry-unscheduled`) so the dashboard never shows a retry that will not happen. With `slowRetry.enabled: false`, every shown `nextAttemptAt` is cleared the same way.
2. **One retry per machine at a time.** If any repair on this machine occupies or is queued for the helper seat (`approved` through `auth-verifying`), or a retry already started this tick, the row waits for a later tick. `waiting-operator-only` and `suggested` rows hold no seat and do not block. Starting several at once would expire the queued approvals.
3. **Re-run the full admission** (`revalidate`, now also returning the resolved `mode`). Every admission floor applies again: account still `needs-reauth`, source episode open and exchange-corroborated, profile unique and dedicated, identity match, no live repair, no pending login other than the repair's own leftover (below), the per-account breaker, and the unattended graduation check including the two added floors.
   - **The repair's own leftover login does not block it.** A failed attempt leaves its CLI login `pending` (the enrollment auto-reissuer keeps it alive), which admission used to read as `pending-login-already-live` forever — the integration test reproduced exactly this. When the runtime **creates** a login for an attempt (`enrollment.start`, never on reuse or reissue), it records that login's `createdAt` on the episode (metadata column `loginCreatedAt`, written by `recordAttemptLogin` without a version bump so the orchestrator's in-flight version stays valid). The write happens synchronously inside the attempt that created the login, and the service runs one tick per episode at a time (its in-flight set), so an earlier attempt's write cannot land after a later attempt's; each new attempt first clears the value at `cli-starting`. Admission ignores a pending login whose `createdAt` equals the recorded value; nothing is abandoned at this step. Rows that failed before the column existed (`loginCreatedAt = null`) fall back to a login created inside the row's own run (`startedAt ≤ createdAt ≤ finishedAt`), so the known stuck rows are not held back forever by their own leftover login; on that match the exact `createdAt` is pinned at once, because a re-offer clears the run window and the operator's later approval must still recognise the login. For a legacy row the window shows timing, not authorship: a login an operator started during that (minutes-long, weeks-old) run after the repair's own left `pending` would also match. Such a login is long stale by now, and replacing a stale pending login is exactly what every repair attempt already does at `cli-starting`; new rows use the exact recorded match. (A replacement created within the same millisecond as the leftover would collide; the clock resolution makes this a named residual, not a demonstrated case.) Why the timestamp identifies the login: the login id is the account id and `PendingLoginStore.issue` refuses a new login for that id while one is `pending`, so a different login can exist only after this one left `pending`, created at a later instant, and reissues keep `createdAt`. The match is used only to *not block* this repair's own retry; the takeover itself is the orchestrator's existing `cli-starting` replacement, and an operator mid-way through finishing the old login would see it replaced — the same thing that happens today when any repair attempt starts. The orchestrator replaces it at `cli-starting`, exactly as it does for any attempt. Any other pending login (an operator's) still blocks.
   - Refused, or no resolved mode → `nextAttemptAt` pushed to the longest delay (24 h), the event carrying `relogin-postponed-<reason>`. Never a tight loop. While admission keeps refusing (an operator's own pending login, an open breaker), the dashboard's "trying again on its own in about N h" is the next *check*, not a promise the run will start; the held failure notice is released by its bound, so the operator is told.
4. **Quiet hours for re-offers.** An approval-mode re-offer that falls due between 23:00 and 08:00 local time (this machine's clock; `slowRetry.quietHours: { startHour, endHour }`, `null` disables) is pushed to the end of the window (`relogin-postponed-quiet-hours`). Unattended retries run whenever due: they need no tap, and a phone-tap request inside them is the existing time-bound notice.
5. **Self-action governor.** `governor.for('subscription-relogin-redrive')` (new policy row: per-target 3 and total 20 per 24 h, `relief`, `hardware-bound`, `open-audited`). Like every class it ships observe-only: it records the would-verdict and allows; the binding limits are the durable cap and the delays until the class is switched to enforce. A non-`allow` verdict (once enforcing) pushes `nextAttemptAt` to the longest delay (`relogin-postponed-governor`).
6. **Start the retry** (new store method `slowRetry`, one transaction, version-checked, refuses past the cap, on a non-eligible row, or when another live repair owns the cell):
   - `unattended` → `failed → approved` with fresh attempt/reissue budgets, `approvedAt` / a 15-minute `approvalExpiresAt`, `slowRetryCount + 1`, the new digest; event `slow-retry-approved`. The service runs it at once. The authority is the same unattended policy that approves a first attempt.
   - `approval` → `failed → suggested` (one new store transition), approval fields cleared, a fresh `suggested` notice; event `slow-retry-suggested`. Nothing runs until the operator taps. A re-offer the operator does not act on simply stays `suggested`: retries only ever start from `failed`, so an ignored re-offer produces no further notices.
   - Prior notice rows for the episode are cleared (except one mid-delivery), and delivery keys carry `.rN` once `slowRetryCount > 0` and `.oN` (every kind) once the operator restarted it (**Try repair again**, or its re-offer on changed inputs), so no notice is de-duplicated against an earlier one. **Try repair again** now also clears the prior run's notice rows, as the slow retry does — before, the retried run's outcome was silently dropped (notices are unique per episode and kind).
   - Each new attempt clears the previous attempt's `loginCreatedAt` at `cli-starting` before recording its own, so a failed record can never leave a stale value.

**Operator hold ("don't retry this").** The dashboard shows a quieter **Don't retry on its own** button under **Try repair again** whenever a failed repair has a next try scheduled (account card and matrix cell). It calls `cancel` on the `failed` repair (the existing cancel route, relayed to a peer cell through the signed `repair-cell` mandate), which now sets a durable `slowRetryHeld` flag and clears `nextAttemptAt`, audited as `slow-retry-held-by-operator`. The row stays `failed` with its failure class, so breaker evidence survives. A held row is never retried or re-admitted automatically; **Try repair again** still works, and the hold lasts for the incident (a retried run that fails again is not slow-retried). The cell then reads "Won't try again on its own. Try repair again any time." A re-offer's notice says the last repair didn't finish.

**Off switch.** `subscriptionPool.assistedRelogin.slowRetry: { enabled?, delaysMs?, maxRetries?, quietHours? }`, read at server start, per machine. Absent ⇒ on with the defaults above. Malformed values fall back to the defaults (a non-array `delaysMs` never breaks the service); `enabled` is off only for `false` or the string `"false"`. Delays are clamped to [1 min, 7 days], `maxRetries` to [0, 10]. No config default is written (absence is the default), so no `migrateConfig` change is needed.

## Decision points touched

| Decision point | Classification | Notes |
|---|---|---|
| Whether a repair needs the operator's tap | `invariant` | Existing policy (`evaluateSubscriptionReloginAdmission`): exact-email opt-in plus the evidence floors, plus the two added holds (helper hard-line report since last success; backup codes below `maxAttempts + 1`, or any backup-code account on the helper path). This change stops the agent-session path from overriding it. Deterministic by design: it is the authority boundary for unattended action. |
| Whether a failed repair is eligible for a slow retry | `invariant` | A closed list of failure classes and the operator hold (`isSlowRetryEligible`). Safety classes are excluded because they are breaker evidence; deterministic because it decides whether an autonomous action may happen at all. |
| When a slow retry is due | `invariant` | Fixed delays, a durable cap, quiet hours for re-offers, one per machine. Pacing, not judgment. |
| Whether a due retry may start | `invariant` | The full existing admission, the breaker, and the self-action governor. No new heuristic. |
| Whether a pending login blocks the retry | `invariant` | Only the login this episode's own attempt created is ignored (matching recorded `createdAt`). A login the operator started after the repair's run blocks the retry. Legacy rows (no recorded value) use the run window, which can also match a login the operator started during that old run; that named residual is replaced like any stale login at `cli-starting`. |
| Whether a helper stop is a hard line | `judgment-candidate` | The helper model decides whether what it sees is a CAPTCHA, phone check, wrong account or unexpected site. **Floor:** a report can only move the repair to `waiting-operator-only` and hold the next one at approval; it is never success, breaker or re-admission evidence; an unreported stop is retried at most 3 times per incident. **Arbiter:** the operator, via the hand-off. **Default:** stop. |

## Multi-machine posture

- **Repair episodes, schedule, slow-retry count and hold:** `machine-local BY DESIGN` (`physical-credential-locality`): each machine repairs its own login in its own browser profile; rows already live in that machine's `repairs.db`.
- **Visibility:** proxied-on-read. `GET /subscription-relogin?scope=pool` already merges every peer's episodes, so `nextAttemptAt` shows on the Studio's dashboard for a Laptop cell.
- **Peer actions:** unchanged; **Try repair again** and cancel (now the retry hold on a failed row) on a peer cell go through the signed `repair-cell` mandate.
- **Notices:** sent from the owning machine only (unchanged). Config (`slowRetry`, quiet hours) is per machine, and quiet hours use the owning machine's clock — correct while the operator and every machine share a time zone (Pacific today).

## Self-heal before notify

The slow retry **is** the self-heal for a failed repair. A `failed` outcome notice is now **held** while a slow retry will still follow (eligible, cap not spent, incident open, slow retry enabled), and at most until one retry delay past the failure plus an hour (for an approval-mode repair: until the end of quiet hours plus an hour, so the held notice never arrives at night ahead of the morning re-offer): if the retry starts, it replaces the held notice; if admission keeps deferring it, the notice is delivered then, so a persistent blocker is never hidden. Unmeasurable incident state ⇒ the notice is delivered. A terminal notice whose repair has since been restarted (a retry raced its delivery) is dropped, never sent as "repair ended". For an approval-mode account the retry's only effect is a re-offer, the existing `suggested` notice, never sent in quiet hours. Hand-offs that need the operator now (phone tap, hard line, macOS permission, no helper seat) are not self-healable and are sent at once, as before. The audit trail is the episode events (`slow-retry-scheduled` with reason, `slow-retry-approved`, `slow-retry-suggested`, `slow-retry-unscheduled`, `slow-retry-held-by-operator`).

## Verify the state, not its symbol

- **Symbol: `state = failed` with an eligible class.** Claimed state: a later attempt could succeed. Corroboration before acting: the source incident is still open in the login ledger (independent of the repair row) and the full admission passes on live pool/profile/ledger data. Unmeasurable (incident lookup throws) ⇒ no change this tick (the schedule is kept). The known stuck rows (`dawn@` Laptop 09-14, `justin@` Mini 09-25 / Studio 09-24) all failed `attempt-budget-exhausted` on the earlier browser-driver paths, before or as the agent-session helper landed; a retry now runs on a different path (the helper, with the passkey-screen guidance), which is why a retry can succeed where the original attempts could not.
- **Symbol: a pending login exists.** Claimed state: someone is mid-sign-in. Corroboration: its `createdAt` equals the `createdAt` this episode recorded when its own attempt created the login (the login store stamps it; reissues never change it); for a legacy row with no recorded value, a `createdAt` inside the row's own run. Otherwise it blocks, as before. This establishes timing, which here implies the creator: while a login for the account is `pending`, no other can be created. It does not establish that nobody is *using* the login: an operator part-way through finishing the repair's own old login would see it replaced when the retry's `cli-starting` runs, the same as for any repair attempt today.
- **Symbol: a helper's hard-line report.** Claimed state: the helper met a CAPTCHA / phone check / wrong account / unexpected site. Corroboration: none is possible server-side. Result: an operator hand-off plus a temporary autonomy hold (cleared by the next verified success); never success, breaker or verified-mismatch evidence.
- **Symbol: the backup-code entry.** Claimed state: enough codes remain for a full run. Corroboration: the codes are counted in the vault value itself, before every run (browser-driver path). Unreadable ⇒ held at approval. On the helper path the count is not trusted at all: every backup-code account is held at approval there (§1).
- **Success of a retried repair** keeps the existing arbiter: `verifyIdentity` match plus an authenticated call.

## Rollback

- Set `subscriptionPool.assistedRelogin.slowRetry.enabled: false` (read at server start, per machine; restart to apply) to stop slow retries; set `mode: "approval"` (or remove an identity from `unattendedPolicy.identities`) to bring the tap back for everyone or one account. One repair: tap cancel on the failed cell to hold its retries.
- Code rollback is a revert. The added columns are additive and ignored by older code — and so are their meanings: an older binary re-admits a `failed` row on changed inputs and does not know an operator hold. Before downgrading an agent where holds matter, set `assistedRelogin.mode: "approval"` (every restart then needs a tap) or disable assisted re-login; the `failed → suggested` transition is only ever taken by the store's `slowRetry` method (a slow re-offer, or an operator's **Try repair again** on changed inputs, `operator-retry-readmitted`).

## Frontloaded Decisions

1. **Unattended on the agent-session path is decided by the existing policy plus two structural holds, not a new graduation rule.** The operator approved the fix on 2026-10-14 16:22 PDT (relayed to the building session by the coordinating desk session). The earlier spec's separate graduation criterion (5 helper repairs, 2 machines, both providers) is superseded; the configured evidence floors, the hard-line hold and the backup-code floor are the bar. On Echo the floors are 0 by the operator's own config, so the helper path starts unattended without its own track record; that is the operator's stated choice, and it applies only to the four listed identities.
2. **Schedule:** 6 h, then 24 h apart, at most 3 per incident; re-offers outside 23:00–08:00 local. Cheap to change afterwards (config, and code defaults with no migration).
3. **Approval-mode accounts are re-offered, never started.** A slow retry never removes a tap that the policy requires.
4. **Operator hold, not cancel-to-cancelled.** "Cancel" on a failed repair holds its retries and keeps the row `failed`, because converting it to `cancelled` would erase breaker evidence.
5. **Notices:** reuse the existing `suggested` / terminal notices with `.rN` keys; a `failed` outcome notice is held while a retry will follow.
6. **Rollout:** the parent spec's other rollout restrictions stay: the agent-session path (and so this unattended change on it) is reached by default only on macOS development agents, and its fleet release still needs the parent's explicit release. Only its graduation criterion is superseded. on by default for agents that already enabled assisted re-login (`enabled: true`, `dryRun: false`), which is itself an explicit operator opt-in to autonomous repair; agents that never enabled it are unaffected. The agent-session path (and so the unattended change on it) is reached by default only on macOS development agents. The per-incident cap, delays and one-per-machine rule bind from the first release; the governor class records in observe mode like every class.
