# Every design mistake the owner points out becomes a rule, and every screen change shows its screens against the rules before it merges

## Problem statement

On 2026-11-21 the owner compared two screenshots and saw that the Mac app's accounts screen was clearly worse than the web dashboard's. The diagnosis (`docs/design-feedback/DF-0001-accounts-usage-mac-vs-web.md`) found fifteen problems. For twelve of them no rule existed anywhere. For the rest a rule existed for the web only. `docs/DESIGN-STANDARD.md` now holds 65 rules for all six surfaces, 27 of them marked machine-checkable, and a table of standard screenshot sizes. Three things are still missing, and each is structural:

1. **Nothing makes a screen change show its screens.** The standard says captures are taken at the standard sizes before anyone is asked to look. Nothing produces them or checks that anyone read them.
2. **No machine-checkable rule has a machine check that runs at merge.**
3. **The feedback loop is a paragraph.** Whether a diagnosis, a rule and a fix follow the owner's remark depends on the session that hears it remembering to do it.

This spec makes all three structural, and it carries the server and web half of the DF-0001 fix as its first build stage.

**What changed after review rounds 1 to 4.** Earlier rounds replaced author-committed pictures with pictures the gate makes from the two trees Local Verify verifies, using the base's own code; put the decision in the `instar/local-verify` status, including on the Actions floor; added a coordinator-held decision beside the write-once record; made earned-rule waivers approval-required phone asks opened only on the author's request; gave each reviewer a one-time secret in its environment; moved the renderer to a persistent folder; had the sweep render every landed commit against its parent within a bound; and bound native captures to their build.

**What changed after review round 5.** An earned-rule loosening could never be approved, because its card was bound to the tree that had to cite it: it is now bound to a request id and the exact reduction, while waivers stay bound to the merge tree with nothing in the tree citing them. Native releases now use a source commit and a separate evidence commit, and each family's capture labels are built in its tracked item. The sweep reuses a comparison only when parent and tree both match; the Actions-floor classification is keyed by main's gate-policy revision; and a completed detector verdict is terminal.

## Words used here

- **Local Verify**: the verifier on the agent's own machines that runs the tests for a pull request and writes a *verify record*. The **coordinator** is the machine that dispatches the run and posts the `instar/local-verify` commit status; the run itself may execute on a peer verifier. **safe-merge** reads the status or record and merges or refuses. A *merge floor* is what safe-merge requires: `local` reads Local Verify, `actions` reads GitHub check results.
- **Base**: the verify record's `baseSha`, the tip of main that Local Verify verified against (it is refreshed to main's current head before each run, never the pull request's fork point). **Head**: the merge tree Local Verify actually tests, the merge of the pull request onto the base. What lands can differ from the head: while main is healthy, safe-merge admits a record verified against an older tip of main (`scripts/safe-merge.mjs:445-448` compares `baseSha` with main's head only when main is not healthy), so the change lands on a newer tip than the one rendered. The daily sweep is the backstop for that (section 6). The gate's own code, rule modes and decision table are always taken from the base.
- **Rendering verifier**: a verifier machine that has the pinned renderer installed and reports it.
- **The lead**: the one machine in the agent's pool that currently runs scheduled work.
- **Maturation review**: the existing weekly review of features still proving themselves.
- **Earned rule**: a rule in the standard marked "Earned from: DF-NNNN". Today 22 rules carry the mark (the phrase also appears twice in the standard's own explanatory text, which the parser does not count).
- **Upkeep list**: the gate's own list of things to fix (inherited earned-rule violations, screens that render inconsistently, merges the sweep could not render, handoffs to app sessions). It is internal state: rows in the `design-feedback` store, read through `GET /design-feedback` and listed at the weekly review. No card carries it.
- **Needs the local floor**: the one shared predicate `needsLocalFloor(paths)` in `scripts/design/ui-surface.mjs`: true when a path is `ui`, a registered source, or one of the gate's policy files (the standard, the coverage map, the modes table, the id lock, and the gate's own files in section 1). The design step, the status projection and the sweep all use it.
- **Development agent**: an agent with `developmentAgent: true` in its config, today Echo.

## Threat model

The agent is cooperating but forgetful, and under time pressure it takes the shortest path. The shortcuts designed against:

- **A picture from another version, or of tidy data.** On the instar side nobody submits pictures: the gate renders the base and the head itself, with seeded data passed through production code. On the native side the release checker reads each capture's pixel size and hash and binds the review to them.
- **Changing the gate in the change being gated.** The gate's code, modes, lint and decision table come from the base, and its files are harness files.
- **Skipping the decision.** The decision is a term of the `instar/local-verify` status that GitHub requires, on both floors: `projectLocal` reads the design decision, and `projectPr`'s mirror branch posts `pending` for any change that needs the local floor, including one that touches only the gate's policy files. So a standby's safe-merge, `safe-merge --auto`, the watcher on either floor and a raw merge all read the same answer.
- **The author answering its own review or waiving its own failure.** Every session holds the same bearer token, so the review route accepts a submission only with the single-use token the coordinator delivered in that reviewer session's environment, never in its prompt, which the session list and the process list show.
- **A waiver the agent grants itself on the owner's rules.** Waiving an earned rule needs the owner's presence tap on his phone, bound to the exact merge tree. The off switch is the agent's, so it is recorded, it tells the owner, it expires within a day, and while it is on, a change touching a screen with an earned-rule violation still needs the owner's card.
- **Feedback attributed to the owner that he did not give.** The server reads the message itself and checks its sender.
- **A check that passes because it could not run.** That result has its own name, `unavailable`, and the sweep retries it.

Not prevented: an admin merge that bypasses the ruleset, or an app build uploaded by hand. The sweep renders the first the next day, as it renders every landed commit. A same-user process that deliberately reads another session's environment could copy a reviewer's token; the token is void after one submission and when that reviewer session ends, which narrows this to a deliberate act rather than a hurried one.

## Frontloaded Decisions

### Yours to decide

1. **Scope is Instar's own development, now.** The gate and the feedback loop run on the development agent, for instar and the apps. *Recommended*: holding other agents' projects through an update would restrict them. Offering it to users is DSE-T1 <!-- tracked: CMT-2165 -->.
2. **Who can let a change through with a rule failing.** For a rule your feedback earned: only you, by a Face ID tap on your phone, for that exact change (the repository, pull request, base, verified merge tree and the rules waived; a new commit voids it, a re-render on another machine does not). You are asked only when the change's author requests a waiver with a written reason; otherwise the author fixes the change. For any other rule: a reviewer that did not write the change, with a written reason, listed in the weekly review. *Recommended*. Alternative: you approve every waiver.
3. **You are never asked to approve or close a design-feedback card.** The card is approved by your own message, the way the agent-work-cards change (pull request 3596, not yet merged) makes your own requests count as approval; the feedback loop is built after that change merges, so no card waits on you in between. The card closes when the server has verified the entry, the rules, the fix on every surface, and the new check. You are shown the before and after pictures where you raised it. "Still wrong" in the same conversation continues the entry. *Recommended*. Alternative: a confirming tap on every card.
4. **Loosening an earned rule needs you.** Removing a surface from it, changing its check from machine to review, retiring it, or turning its check from blocking back to reporting needs your phone tap. Adding and tightening rules is the agent's. The standard's sentence saying so ("How this standard grows", step 3) was written by the agent; your approval of this decision is what makes it your rule, and the approval message will be cited there. *Recommended*.
5. **One constitution article, in both books.** Approving this spec approves both wordings. The standards registry is code-owned by you, so its pull request needs your approval on GitHub, which opens from a link on your phone.

### Decided by the agent; say if you disagree

6. **The gate makes the pictures; nothing visual is committed to instar.** Captures live in the capture store on the verifier, outside git and outside backups, because they can be re-rendered from the commits.
7. **A tool failure never refuses a merge.** A missing renderer, a crashed harness that also fails on the base, a timeout, an unreachable capture, or an older verifier records `unavailable` and the pair of commits joins the next sweep. A head that fails where the base rendered is not a tool failure (decision 9). A base tree that cannot be built is different, because then nothing about the change was measured: the change waits while the design step alone is retried, and only when that retry's breaker trips does it become `unavailable: base-unbuilt` (section 2). These signals stay internal until a declared breaker trips; only then is the owner told. Cost: a change can merge unseen for up to a day.
8. **A change may not add violations; it need not clear old ones.** The exception is a change that says it fixes a feedback entry: that entry's cited rules must pass on the screens it names.
9. **Day one.** From the day the step lands, these refuse: a UI change on the Actions floor, a changed UI file that no screen lists or loads, a visible difference with no review bound to it, a head that fails to render where the base rendered, a change that weakens the standard, and a feedback fix that leaves its rule failing. Every rule check starts in `report`. Pull requests already open are gated on their next verify, because the base is main's current tip.
10. **Promotion to blocking is a judgment** of the maturation review, on evidence: screens, sizes, themes and verifier machines covered, the negative control, every false failure traced. Each check's row carries a date by which it is promoted, changed or retired.
11. **Renderer.** `playwright-core` with the Chromium build the base's lockfile pins, fonts bundled with the harness, installed by each rendering verifier into a persistent verifier-owned folder with its own disk budget. `axe-core` for contrast, names and target size.
12. **The gate starts the reviewer.** A fresh one-shot session started by the coordinator reads the paired base and head evidence for one screen at a time. The server accepts its submission only with the single-use token the coordinator put in that session's environment, the way the session bind token is delivered, so the authoring session cannot supply it. Its model is recorded.
13. **Design feedback is noticed by one fast model call per owner message** on the live seams. The result is only a candidate; the session in that conversation confirms it.
14. **Apps: the release of one product is the unit.** Each release script runs a vendored checker that requires, for every changed registered screen, captures at the standard sizes and an independent reviewer's answers in the private apps repository. Until a family's capture tool exists, captures come from the app's own debug capture mode, as the Apple app session already does for DF-0001. Native automatic checks stay tracked items.
15. **`docs/DESIGN-STANDARD.md` is not code-owned.** Decision 4 and the base-copy lint protect earned rules instead.
16. **DF-0001 stage, three points beyond the brief.** (a) Both sides colour a limit and an account from the rounded percentage that is displayed, so 89.6% shows "90%" in red everywhere. (b) The server adopts the web's handling of a limit that has already reset. (c) The server lists accounts needing sign-in first and the web does not; stage 1 adds the name tie-break only and records the difference on DF-0001 as DSE-T7 <!-- tracked: CMT-2171 -->.
17. **The UX impact lint's dead path is corrected** from `src/dashboard/` to `dashboard/` in the lint. Its workflow's own `paths:` filter has the same dead path and is a protected file, so that change, and whether wording in agent-written messages gets a merge gate at all, is DSE-T6 <!-- tracked: CMT-2170 -->.

**Trust boundary.** All of these join `HARNESS_GLOBS`, and `playwright-core` and `axe-core` join `TOOLCHAIN_PACKAGES`, so a change to any of them needs the independent-review trace. The design step runs every one of them, the lint included, **from the base**. The changed paths are still computed from the merge base to the pull request head, as Local Verify does today, and a path is UI if the base's classifier says so or a registered screen at base or head lists it. When a change edits the gate, the head's copy is also run and its result is shown to the independent reviewer; it decides nothing. If the base has no gate yet (only before stage 2 merges), the step does not apply.

**The classifier.** A path in instar is `ui` when it is under `dashboard/**` (including `dashboard/docs/**`, the Documents page) or `dashboard-pair/**` and is not a test, or when a registered screen lists it. A unit test walks the tree and fails with `ui-path-unclassified` for any `.html` or `.css` file, and any source file that emits a whole HTML document, that is outside these roots and not on a written allow-list. The native families' rules (SwiftUI, AppKit or UIKit imports; `@Composable`; `.xaml` and `.axaml`; asset and string folders) live in each family's vendored copy.

**The screen registry.** Each screen has an id, a title, its main question (`DS-DELIGHT-1`), its surfaces, how to open it, its seed, and its source files. Sources may name server files: the accounts screen lists `src/server/mobileCapacityRoutes.ts` and `dashboard/console/accounts-model.js`. A source may be marked `shared` (stylesheets, shared components, fonts, helpers): a change to it renders every captured screen that loaded it in the base render, which the harness records from its own request log. A screen with no seed yet is `status: "uncaptured"` and cites a tracked card. Stage 2 registers every console route, the legacy dashboard pages, the pairing page, the Documents page and the pages rendered from TypeScript (`PrivateViewer`, `SecretDrop`, `RecoveryPhonePage`, `documentPageRoutes`); only the accounts screen is seeded at first, and the rest are `uncaptured` under DSE-T5 <!-- tracked: CMT-2169 -->, which also carries seeding the remaining console routes, in order of use and feedback history, with the number of captured screens reported at each maturation review.

### 2. How a screen is rendered

**Pinned renderer.** The harness drives the Chromium build that the base's locked `playwright-core` pins, with the bundled fonts, a fixed clock, animations off, a fresh profile, and every network request refused except those to the harness. A rendering verifier installs that build on demand into a persistent verifier-owned folder, `<verifyRoot>/design/renderer/<build>/`, which per-run cleanup never touches. That folder keeps the current and previous builds, removes older ones through `SafeFsExecutor`, and has its own disk budget (default 1 GB, reported in `GET /local-verify`). The browser's profile and temporary files go in the run's `lv-tmp-*` folder, so the profile path on its command line keeps it owned by the leftover reaper with no reaper change. The verifier reports its build in the peer status read. If the build is missing and cannot be installed, the step is `unavailable: renderer-missing`.

**Data comes through production code.** A seed is a small file of synthetic raw inputs. The harness mounts the real route handlers and model functions over those inputs, with a throwaway state directory and home, no agent token in its environment, and no reads of the host's pool, config or machine name. Seeds contain invented people only: the lint refuses an email address that does not end in `@example.com`.

**Stress content is checked, not declared.** For each seed the gate reads the produced API response and verifies the `DS-DELIGHT-6` cases that data can show: a zero, a value at the maximum, a missing value, every optional row present on at least one item, and a name at least as long as the registry's longest name. The busiest realistic count is the one case the registry declares.

**Sizes.** Each affected web screen is rendered at 1280 x 728, 390 x 844, 768 x 1024 and 1440 x 900 in dark, at 1280 x 728 in light, and at 200% zoom of 1280 x 728, plus the named states the seed defines (empty, error, loading). The harness also writes an interaction trace as text: tab order and whether focus survives a refresh.

**Twice, for determinism.** Every screen is rendered twice on each side. If the two renders of one side differ, that screen is `unavailable: nondeterministic`, which allows, and the screen goes on the upkeep list to be made deterministic. It is never read as "no visible difference".

**The base tree and its cache.** The head is the run's own merge tree. The base cache is per (`baseSha`, renderer build) on each verifier: base captures, base violation keys, base traces and base load lists, shared by every pull request verified against that tip there. **Main's own post-merge verify fills it**: that run's head is exactly the new tip, already built, so after each merge it renders every captured screen once and stores the result as the base cache for that tip. A pull request verified after main's verify finishes therefore needs no base build. Only on a cache miss (main's verify not finished, or run on another verifier) does the step build the base itself, in a second worktree at `<verifyRoot>/design/base/<baseSha12>/` that reuses the run's installed dependencies when the lockfile is unchanged. That worktree is removed at the end of the run (the cache is the captures, not the tree), and the orphan sweep in `orchestrator.ts` gains a rule for that folder. Cost bound: at most one base render per screen per main tip per rendering verifier; each pull request adds only the head renders of its affected screens.

**A base build has its own deadline**, the existing `npmCiMs` and `buildLintMs` policy deadlines, outside the render total and inside `policyHash`. If the base cannot be built or runs past its deadline on a UI change, nothing about the change was measured, so it does not merge unchecked: the status is `pending: design-base-retrying`, and the coordinator re-runs only the design step (not the lanes) after 15, then 30, then 60 minutes, or sooner when main's verify fills the cache. The breaker trips after the third failure: the result becomes `unavailable: base-unbuilt` for that run only, which allows like any other `unavailable`, the pair joins the sweep, and the owner is told then. Stage 2's measurement includes the base build, not only the renders.

**The capture store** is a new piece: `.instar/local-verify/design-captures/` on each verifier, named by content hash. It keeps the base cache for main's last three tips and the newest set of each open pull request. It has a byte budget (default 4 GB, set from the stage 2 measurement) and prunes oldest first when it writes, deleting through `SafeFsExecutor`. At the budget, the newest set of an open pull request is never pruned: the overflow raises an internal degradation, and a set pruned anyway is re-rendered on demand before review rather than read as unreachable. `GET /local-verify` reports its size. It is excluded from backups. Captures are read through `GET /local-verify/design/<pr>/captures/<hash>` (the pull request an integer, or `main` for main's tip render, which the native parity reviewer reads; the hash checked against a fixed hex pattern before any file access), proxied over the mesh-authenticated read to the machine named on the record; that name is resolved through the pool's machine registry and never used as a URL. The pull request body carries rule ids, screen ids, hashes and counts only, never element text.

### 3. The design step and the one decision table

**When it runs.** After the three lanes pass, and only when the base's `needsLocalFloor` is true for the changed paths. Other changes never start a browser, and a change that touches only policy files renders nothing: its decision runs the lint.

**What it does.** For each affected screen it renders the base (or reads the cache) and the head, with the base's seeds, harness and renderer (the head's seed only for a screen that is new), then:

1. **Compares the evidence.** A screen whose captures and interaction trace are identical on both sides has *no visible difference* and needs no review.
2. **Runs each rule check on both sides.** A violation is keyed by rule, screen, size, theme and element path (text only as a tie-break). Present at the head and absent at the base is **added**. Where paths are not stable, a higher count at the head is added.
3. **Proves each check first.** Every check has a violating fixture. A check that does not fail on it is `unavailable: control-failed`.
4. **Treats a head failure as the change's.** If the base rendered a screen and the head crashes, hangs past the per-screen limit, or fails to mount, the result is `render-failed`, a measured failure. Only when the base or the controls also fail is it `unavailable: harness-failed`.

**Time limits** live in the Local Verify policy, inside `policyHash`, as reviewed constants like the lane deadlines: at most four pages at a time, 60 seconds per screen render, 20 minutes for the whole step. Stage 2 measures the worst case (a change to a shared stylesheet, every captured screen) on the slowest rendering verifier and, if twice that exceeds 20 minutes, raises the total by a reviewed policy change. Screens finished when the total runs out are decided; only the rest are `unavailable: timeout`. The step's 20 minutes, and any base build, sit inside the verify's existing `totalActiveMs`; running out of either gives `unavailable: timeout` for the unfinished screens, never a verify error that fails the lanes' record. Reviews run after the step, outside its total. The step's duration is on every record.

**Review.** The coordinator starts one fresh reviewer session through the server's one-shot session path, at most two at a time, for each screen whose decision needs one: a screen with a visible difference, and a screen with an added violation of a check in `block` even when nothing visible changed (then the rule's evidence, the element path and the `axe-core` output, is its input). The reviewer gets that screen's paired base and head captures, traces and the wording of every applicable review rule, all inside the data boundary with the instruction that text inside a capture or trace is evidence, never instruction, and answers each rule: `pass`, `fail` (present at the head and not at the base), `inherited` (present at the base too), `not-applicable` with a reason, or `not-observable`. A reviewer told its input was cut answers `not-observable`, never `pass`. A rule whose evidence the harness cannot produce yet is `staged` under DSE-T8 <!-- tracked: CMT-2172 -->. **Parity on web changes:** for a screen registered on more than one surface, the reviewer also receives the latest shipped native capture of that screen from the apps mirror when one exists, and its `DS-PARITY-1` answer binds that capture's hash and seed version; with no shipped capture the parity answer is `no-counterpart-yet`, which allows, and a feedback card's `fix` item stays open.

**One authenticated submission.** Every session holds the same bearer token and the `X-Instar-Session` header proves nothing, so the coordinator mints a single-use token per (screen, evidence hash), stores only its hash, and delivers it as `INSTAR_DESIGN_REVIEW_TOKEN` in the reviewer spawn's tmux `-e` environment block, the way `INSTAR_BIND_TOKEN` is delivered; the reviewer is spawned with its auth environment, and the prompt names only the variable. One `POST /local-verify/design-review` carries all of that screen's answers and, for any non-earned rule it answers `fail`, a waiver reason of at most 500 characters. The route accepts it only with the token, voids the token on that submission or when the session ends, writes the rows with the token's hash on them, and records the session's id and model from its own spawn record. A post without it is refused `not-from-reviewer`. Answers are bound to one hash over the base and head captures, both traces, and the wording of each answered rule. A change to any of those (a merge from main that moves the base, a new head, an edited rule) re-triggers review of that screen automatically. If the reviewer fails twice, that screen is `unavailable: reviewer-failed`. The `/instar-dev` and `/build` skills may run the step locally first as an early look; that result decides nothing.

**The decision table and who re-decides.** Verify records are write-once and may be signed by a peer, so the record's `design` field holds only the run's measurements, the modes hash and the renderer build; nothing amends it. The decision lives in a separate **design decision record** held by the coordinator, keyed by (repository, pull request, `baseSha`, `mergeTree`), stored in the coordinator's Local Verify journal beside the record and linked to it by that key (a peer-run record links the same way). The coordinator evaluates it when the record lands, and again whenever a review answer, a waiver, an owner tap, or a change or lapse of the off switch arrives. Each evaluation runs the base's `gate.mjs` and `modes.mjs`, read from `baseSha` in the coordinator's own clone, over the record's stored measurements plus the replicated answer and waiver rows; it is refused if that modes hash differs from the one on the record. The same evaluation runs the base's lint over base and head (`standard-weakened`, below), which is a tree read and needs no renderer. Each evaluation writes a successor decision; the newest one counts. Like the record, the decision is machine-local and is a cache, not authoritative state: it is a pure function of the record and the replicated rows. A coordinator takeover re-verifies the change, as Local Verify does today, and the new coordinator computes a fresh decision from its own new record, the replicated review rows (reused when their evidence hash equals the new run's) and the Work Board waiver card (reused when its binding equals the new values, which hold no pixel hash, so the owner is not asked twice while main has not moved). A reviewer still running at the takeover loses its submission, and that screen's review restarts.

`StatusReconciler.inputsFor` passes the newest decision for the record's key to `projectLocal`, which gains the design term: a refusal posts `failure` with the reason, a review in progress, a base retry or an open owner waiver posts `pending`, anything else lets the existing terms decide; no decision yet for a UI change is `pending`. When a decision changes, the coordinator calls the reconciler's re-post for that head (the same entry as `onRecord`), so GitHub's status changes within seconds; when the head's projection becomes `success`, it also hands the pull request to the watcher with `tick({ handoff })`, as a green verify does today. safe-merge, the watcher and GitHub's ruleset all read that status, so no merge path can skip it.

| Measurement for a rule on a screen | Decision |
|---|---|
| Pass | Allow. |
| Fail, every violation already at the base, or review answer `inherited` | Allow. An earned rule's violation goes on the upkeep list. |
| Fail with an added violation, check in `report` | Allow. Recorded, and counted in the maturation review. |
| Fail with an added violation, check in `block`, or review answer `fail` | Refuse `design-rule` or `design-review-fail`, unless waived. For an earned rule the refusal is final for that head unless the author requests the owner's waiver. |
| Waived by a valid waiver for this rule and this evidence | Allow. Listed in the weekly review. |
| `staged` | Allow. Listed with its tracked card. |
| `unavailable` (renderer missing, base unbuilt after its retries, harness failed on both sides, nondeterministic, timeout, control failed, reviewer failed, captures unreachable, older verifier, switched off) | Allow, except while switched off as below. One `internalOnly` degradation, keyed by cause and renderer build so one broken renderer is one row, and a row on the upkeep list; the pair of commits is retried by the next sweep. The owner is told only when a declared breaker trips (section 6). |

Structural results sit beside the table. Each is deterministic, the author can always fix it, and each has its own row in `DESIGN_GATE_MODES`, all at `block` from day one:

- `screen-unregistered`: a changed `ui` file that no screen lists, that is not `shared`, and that no captured screen loaded in the base render.
- `review-missing`: a visible difference with no review bound to its current evidence. This is `pending` while the gate's reviewer runs.
- `render-failed`: the head failed where the base rendered. The remedy for a head that moves a registered entry point is to land the registry or harness change first, as its own harness-reviewed change.
- `standard-weakened`: the base's lint, run over base and head, finds a removed rule id, a removed "Earned from" mark, or an earned rule loosened (section 5, lint item 5) without the owner's phone-approved loosening card for that request id and reduction. If that card cannot be read, this refuses rather than allows. It is evaluated by the coordinator's decision whenever the standard, the coverage map, the modes table or the lock file changed, whatever the renderer, the switch, the timeout or the verifier version: an older verifier's record or the step switched off does not skip it.
- `fix-incomplete`: the body says `Design-Feedback: DF-NNNN` and a rule that entry cites still fails, added or inherited, on a screen the entry lists. An optional `(screens: …)` after the entry number limits the check to the screens this change fixes; the feedback card still needs all of them.

**The Actions floor is refused in the status itself.** `ProjectionPr` gains one input, `needsLocalFloor: 'yes' | 'no' | 'unreadable'`, which `StatusReconciler.refreshHeadInputs` computes for a mirror head by running the shared predicate from main's current tip over the pull request's changed paths. The result is cached by the pair (head, main's gate-policy revision), where the revision is the hash of the files the predicate reads at main's tip; when that revision changes, every open pull request is re-classified and re-projected without a new commit. A main tip with no gate yet gives `no`. In `projectPr`, before `projectMirror` is called, `yes` projects `pending: design-needs-local-floor` and `unreadable` projects `pending: design-paths-unreadable`. So a change that only demotes an earned rule's mode cannot merge green on Actions either. The mirror branch is reached only on an install whose configured floor is `actions` and for an ineligible pull request; on a configured-local install an unhealthy Local Verify already holds every pull request on the local floor. Because GitHub requires this status, a raw merge, `safe-merge --auto` and the watcher's Actions-floor path all see a non-green status; safe-merge's synchronous path shows the reason in plain words ("this change touches a screen or the design rules, which only Local Verify checks"). An ineligible pull request (for example from a fork) that needs the local floor waits for the owner's admin merge, or for an eligible author to adopt it; its status says so. The term covers the instar repository, for every author.

**The watcher.** `review-missing`, `design-base-retrying`, `design-needs-local-floor` and an open owner waiver are waits: the watcher acts on the status change and the handoff above, re-reads on its regular tick, and spends no attempt. `design-rule`, `design-review-fail`, `render-failed`, `screen-unregistered`, `standard-weakened` and `fix-incomplete` are terminal for that head. safe-merge surfaces each reason from `GET /local-verify/status` as a stable slug in its classified results, and `GET /green-pr-automerge` shows them.

**Waivers.**

- *A rule that was not earned.* The reviewer gives the reason in its one submission (above). The fix goes on the upkeep list. Every waiver is in the weekly review.
- *An earned rule.* The refusal is final for that head, and the author normally fixes it. A waiver card opens only when the change's author requests one with a written reason, `POST /local-verify/design-waiver { pr, rules, reason }` (at most 500 characters; the author may ask, only the owner grants), at most one card per head. The card is an **ask**: carried by the agent, `outward: false`, with a `recommendation` (so it is not agent work), covering `cos:design-waiver:<owner>.<repo>:<pr>:<binding hash>`, so it is server-owned. The key uses `.` in place of `/` because `NEED_REF_RE` allows no slash. The binding hash is over the repository, the pull request, `baseSha`, the verified `mergeTree` and the sorted waived rule ids, never pixel hashes, so a re-render on another machine does not ask him twice. One fold rule in `WorkCardStore` (beside the `outward` rule) makes any card covering `cos:design-waiver:` approval-required whatever the board policy, so its status is `needs-approval` and the iPhone app shows Approve. `phoneOnlyCard` is extended to it by an OR on that covers prefix, so the console refuses a PIN approval. The server writes the text: the pull request, the screens, each rule's wording beside the author's reason, and the bound values. The decision accepts the waiver only when `approvalValid` is true from a tap, `approvedBy.by.proof` is `presence`, `approvedBy.by.personKey` is the owner's, and the card's binding hash equals the one computed for the current record; a new commit changes the merge tree and so voids it. A waiver card's covers key is never edited: when the waiver is used or no longer needed (the change merged or closed, or its binding changed), the server archives the card. An older pool build computes no approval requirement and shows no Approve, which leaves the change `pending`, the safe direction. If the owner's waiting lane is at its soft budget, no card opens and the change stays `pending` with that reason, re-tried on each reconciler pass. Nothing in the tree cites a waiver card, so binding it to the merge tree is not circular.

- *Loosening an earned rule.* The author requests it on the same route with `kind: loosening`, before or after the change is verified. The server creates a stable request id and opens a card covering `cos:design-loosening:<owner>.<repo>:<request id>`, with the same ask shape, fold rule and `phoneOnlyCard` extension. The coordinator finds the reduction itself from the pull request and its diff against `baseSha`: each loosened rule id, what is removed or changed (lint item 5's list), and a digest of the before and after text of that rule's Rule line, coverage row and mode row. The changelog is not part of the reduction. The card shows and stores that reduction. The changelog row names the rule, the reduction and the request id. The owner's tap is stored on the card, outside git. `standard-weakened` clears when an approved card (`presence`, the owner's person key) exists for that request id and its stored reduction equals the one the coordinator computes now. A later edit or a moved base that changes the reduction voids it, and the server archives the card; any other edit, including adding the changelog row, does not.
- *Server-owned cards are never picked up and never go quiet.* Stage 2 makes `WorkBoardPickupController` skip any card for which `isServerOwnedCard` is true, and adds the same skip to the quiet line of main's `deriveStatus` (`WorkCardStore.ts:809`), so an approved waiver card whose change waits longer than `quietAfterHours` never lands in the owner's waiting lane. Stage 3 extends both skips to pull request 3596's rewritten quiet line and `repickupOneQuiet`. Owner-carried Chief of Staff cards are unaffected. Stage 2 also adds the two new prefixes to `SERVER_COVERABLE_PREFIXES`, and makes the `server-owned-card` refusal (which today names the Chief of Staff) and the records route's phone-only message name the card's own family.

**The off switch.** `monitoring.localVerify.designStepOff: { until, reason }` in the coordinator's config, read live by the coordinator when a run starts and again when it posts the status, and written on the record. It is honoured only until the earlier of `until` and 24 hours after the coordinator first saw that value, and for at most 24 hours in any rolling 7 days, counted from the replicated switch records, so rewriting the value does not extend it. Every new value seen is recorded in the `design-feedback` store (machine, time, reason, value) and raises a degradation, which reaches the owner's attention topic at once, saying in plain words that screen checks are off, why, and until when. This is the one notice that does not wait for a breaker: the agent turning off its own gate is a security-class event. While it is honoured, UI changes are `unavailable: switched-off`, except a change that touches a screen which the latest main render shows with an earned-rule violation: that change waits for the owner's waiver card as above, or for the switch to lapse and the change to be rendered normally. When it lapses the step runs again, whatever the file still says, and the record of the off period stays and is listed in the weekly review with every change merged during it. The lint-based `standard-weakened` refusal still runs while switched off. The switch does not stop the sweep, which renders every commit landed during the off period within its stated bound. An unparseable value is ignored: the step runs.

### 5. The design-feedback loop

**Noticing.** Two live seams: a wrapper chained on `telegram.onMessageLogged`, and a listener on `AppConversationStore.addAppendListener` that acts only on events committed locally (not replicated copies), so each message is seen once, on the machine that received it. Each entry is tested for the owner's own words by the same per-channel sender check the agent-work-cards change uses (Telegram: the configured owner id, not forwarded; app: the sender recorded as the owner person). With no owner identity configured for that channel, nothing is judged and the log says so once. For the owner's own words, one fast-tier call through the shared LLM funnel as component `design-feedback-detector`, never awaited, with ceilings of 60 calls an hour and 300 a day (about three times the owner's busiest day of messages; stage 3 re-measures it and names the day used, leaving out bulk or test traffic from his id). The call sees the message (first 4,000 characters, the detector's own input bound; the card itself stores the whole message up to 64,000 characters), whether it has an image, and the three previous turns (last 1,000 characters each), told when anything was cut, all inside the data boundary. It answers `design-feedback`, `more-about` an open entry, `other` or `unknown`. Slack has its own seam; it is proven in stage 3 or carried by DSE-T9 <!-- tracked: CMT-2173 -->.

**Verdicts, honestly.** Each judged message gets one verdict row keyed by its message id in the replicated `design-feedback` store. A message the detector could not judge (ceiling reached, call failed) gets an `unjudged` row with the reason; that row is pending, and a completed verdict is terminal and supersedes it. There is no catch-up pass over the message log. When a ceiling resets or the funnel recovers, the detector judges the `unjudged` rows still inside the window, newest first, within the same ceilings; the rows hold message ids, so this reads no log. A message logged while the server was down gets no row at all, so the weekly review compares the count of owner messages in the log over the week with the count of verdict and unjudged rows and lists the gap. Rows are kept 30 days; the weekly review lists the unjudged rows still inside that window and replays a sample of 20 owner messages a week through a stronger tier to measure misses. When a row expires the message is no longer counted. The session's own path below stays open for anything the detector missed.

**The session confirms.** A `design-feedback` or `more-about` verdict is a candidate, handed to the session serving that conversation, which confirms it with `POST /design-feedback/cards` or dismisses it with a reason. Dismissals are counted and sampled weekly. When the owner gives design feedback and no candidate arrived, the session uses the same route.

**The route trusts nothing from the caller.** `POST /design-feedback/cards` accepts only `{ conversationKey, messageId }`. The server reads that message through the durable-row read added by the agent-work-cards change, checks the sender with the same rule, and copies the words and attachments itself (`no-verified-owner` or `not-owners-words` otherwise). For `more-about`, the message is added to the open entry's row instead of opening a new card.

**The card.** The in-process server writer creates an ordinary Work Board card with an id derived from the source message, so one message never makes two cards. It is carried by the agent, `outward: false`, and covers `cos:design-feedback:<message key>`, which makes it server-owned: sessions cannot write its evidence, claim it or edit it. Its `need` is the owner's message text, locked to that message, with `requester` set from the verified sender, so under pull request 3596's rule it is approved by the owner's own request and never waits on him. **It never goes quiet and is never picked up** (the skips in section 3): the work belongs to the conversation that confirmed it, and a server-owned card whose `fix` waits days on a native release stays in the agent's lane. The date and the attachment list are on its `design-feedback` row. Before 3596 merges, stage 3 is not built, so no such card exists in a state that waits on him. The card is visible to the owner, the agent, and any device that can read that conversation. Its four done items are `agent-may-certify`, and the server writes each item's evidence under a fixed record key (`wc:<id>:dfe:<item>`), so a retry or a second machine writes the same record:

| Item | Done when |
|---|---|
| `entry` | `docs/design-feedback/DF-NNNN-*.md` is on main, names this card and this message, and lists every problem with the rule it broke or "no rule existed". |
| `rules` | Every problem maps to a rule; each added or sharpened rule carries "Earned from: DF-NNNN"; the changelog has the row; the lint passes on main. |
| `fix` | On every surface the entry lists, every cited rule passes on the entry's screens: on the web, in the latest main render (machine rules measured, review rules answered `pass` on evidence identical to that render); on each native product, in a shipped release whose evidence folder holds that screen's captures and passing answers. A cross-surface rule (`DS-PARITY-1`) passes only on a parity review: a reviewer given same-seed captures of that screen from both products, with its answer bound to both capture hashes; while either capture is missing the item stays open. `staged` never satisfies it. A surface whose evidence does not exist yet keeps the item open. |
| `check` | For every cited rule that already existed, the entry names one of `new-check`, `fixed-check` or `registry-change` with the file that makes it, or `not-checkable` for a rule whose Check is `review`; the lint checks the form. |

**Closing is the server's.** Card status is computed inside the daily sweep (section 6) from main's tree, main's render and the apps mirror, by a pure script, and written to the `design-feedback` store. A server module on the lead writes the evidence from those results, claims the card when all four hold, and sends the before and after captures for each verified surface to the conversation the feedback came from. A card read never triggers a pass. `GET /design-feedback` is the authoritative answer; if a card reads complete while the latest result says an item no longer holds, the module opens a continuation card for the same entry and records why.

**"Still wrong."** The owner says so in the conversation. A `more-about` verdict, or the session, links it to the entry; the server opens a continuation card and the entry gains a numbered round.

**Entry numbers** are the next free number on main; the lint refuses two entries with one number.

**The lint** (`scripts/design/lint.mjs`) is pure and tree-only. It runs from the base in the coordinator's design decision whenever the standard, the coverage map, the modes table or the lock file changed, whether or not the step rendered anything (where items 2, 3 and 5 decide `standard-weakened`); in the sweep over each retried pair that touched those files; as an ordinary unit test on the head as the author's early warning, and in the instar-dev pre-commit gate when the standard or an entry is staged.

1. Every rule has a unique id, every required field, and a Check of `machine` or `review`. The "at a glance" table lists exactly the machine rules.
2. **Ids are permanent.** `docs/design/rule-ids.lock.json` lists every id ever issued; the head's lock contains the base's.
3. **Rule and entry agree both ways**, and an "Earned from" mark or an entry's rules row present at the base still exists at the head.
4. Every numbered problem cites a rule or names the rule added. Every entry that changed rules has one changelog row naming exactly those rules.
5. **An earned rule is not loosened without the owner.** It lists every earned rule whose Rule line changed, that lost a surface, whose Check went from `machine` to `review`, that was retired, whose coverage row went from a test to `staged`, or whose mode went from `block` to `report`. A reduction needs a changelog row naming the rule, the reduction and a loosening request id (section 3); the coordinator's decision checks the owner's card for it. A changed Rule line alone goes to the gate's reviewer, shown both wordings: "does the new wording permit anything the old one refused?" `no` is recorded and passes; `yes` or `unsure` is treated as a reduction.
6. **Entries are safe to publish.** An entry has Card and Source message rows and a unique number. Nothing but `DF-*.md` is under `docs/design-feedback/`. Any email ends in `@example.com`. The owner's words appear only in the session's redacted version, each removal marked; the unedited words stay on the card.
7. **Gate misses are closed.** An entry's "why it was not caught" line that names the gate cites the change that fixes it.
8. **Coverage is complete.** Every machine rule has a row per surface: a test, or `staged` with a tracked card. Every review rule names its evidence kind. Every `uncaptured` screen cites a card.

Each is behind the development-agent gate (none is a default job, and the daily trigger is a server timer behind the same gate, so other agents get nothing), registered in the self-action registry with a pure decision function, and has a sustained-failure test.

**The daily sweep** reads main's tip render from the base cache (rendering it, twice, only on a miss) and does three things. Main's outcome and main health are recorded before it starts, and its time and failures never change either.

1. **Renders every landed commit against its own parent.** Discovery walks first-parent commits on main from its own cursor and adds a **pending pair** (parent, commit) to the `design-feedback` store for each commit whose paths need the local floor by the predicate at its parent. Each pair is always rendered and checked, because what lands can differ from what Local Verify rendered (section "Words used here"); the sweep is the backstop for that. Matching to a verify record is only an optimisation: the record is found by pull request (the commit's pull-request association) and head, and its comparative result is reused only when both its `baseSha` equals the commit's parent and its `mergeTree` equals the commit's tree. Otherwise its captures are reused where their evidence hash matches, and the difference is recomputed against the actual parent. Review answers are reused when the pair's evidence hash equals one already answered, so a reviewer starts only for a screen whose landed evidence nobody has read. Retry takes batches of 10 pairs, oldest first (the brake is reviewer cost), renders each pair, runs the checks, the reviewer and the base lint (when policy files changed), and writes that pair's result as soon as it finishes. While the oldest pending pair is older than 24 hours, the sweep runs further batches until its deadline, and the lead's trigger starts a sweep every hour instead of every day. A pair stays pending until it has a result, whatever the cursor does. A pair not reached is not a failed attempt; a pair that fails in three sweeps is recorded as `could-not-render` with its cause.
2. **Computes card status** for open feedback cards (section 5).
3. **Stores one aggregate count document** per sweep (per rule, screen, size and theme) for the maturation review, kept 90 days.

The sweep has its own policy deadline, `designSweepMs` (default 60 minutes, inside `policyHash`), separate from the step's total. What it finds goes on the upkeep list. A finding from a pair is keyed by (repository, commit pair, rule, screen); an inherited earned-rule violation seen by pull requests is keyed by (rule, screen, size, theme, element path), so fifty pull requests over one old violation make one row. An earned-rule violation or loosening found on main is an upkeep row the agent fixes; nothing asks the owner about a commit already on main. Upkeep is internal state: the owner is told only when a declared breaker trips, through the existing degradation and attention path, with no approval ask, and everything still open is listed at the weekly maturation review.

Self-heal declaration for the sweep:

- `remediation-actions`:
  - retry each skipped commit pair's render and review
  - put each finding on the upkeep list for the agent to fix
- `max-attempts`: three failed sweeps per commit pair, then `could-not-render`; an unreached pair counts no attempt
- `max-wall-clock`: `designSweepMs` per sweep, in batches of 10 pairs
- `backoff`: one sweep per day, carried by a main verify or started by the daily trigger; hourly while the oldest pending pair is older than 24 hours
- `dedupe-key`: (repository, commit pair, rule, screen) for retried pairs; (rule, screen, size, theme, element path) for inherited findings
- `breaker`: any of these tells the owner, once, and stays open until it clears: two days without a successful sweep; the oldest pending pair older than 48 hours; a pair reaching `could-not-render`; a change whose base retries ran out. Until a breaker trips, every `unavailable`, renderer-install failure and apps-mirror failure is an `internalOnly` degradation plus an upkeep row, so the owner is not told about something the next retry heals
- `max-notification-latency`: 48h for a breaker (two days without a sweep), against the recoverable ceiling of 300 seconds; the exception is justified because these are retries of design measurements, not a degraded service, and nothing user-facing waits on them. The 192h figure is the weekly review's cadence, not a degradation notice. Every landed pair is rendered within 48h, or the backlog breaker tells the owner
- `audit-location`: the `design-feedback` store and `GET /design-feedback`
- `class`: recoverable

**The apps mirror** is a fetch-only clone of the private apps repository's tags and `design-evidence/` folder, kept only on rendering verifiers that already hold the agent's GitHub credential for that repository; no credential is copied to a machine to make room for it. Other machines read native items through the mesh from one that holds it. It is fetched once per sweep, with no API calls, and counted in the capture store's budget. Missing or unreadable, it leaves native items unverified and raises one `internalOnly` degradation.

### 7. The apps repository

The unit is the **release of one product**: everything between that product's last shipped mark and the commit being shipped. The products are `ios`, `mac`, `android`, `windows` and `linux`; iPhone and Mac ship separately, so each has its own mark.

- **Vendored checker.** Each family carries `design-gate/`: the checker, that family's classifier rules, a machine-readable copy of the standard, that family's screen registry (with `shared` sources) and coverage rows, and a `VERSION` file with the instar release it came from and a hash of the folder. `scripts/design/vendor.mjs` in instar produces it; a unit test proves the machine-readable standard equals the Markdown. Nothing depends on an installed Instar package. The sweep reports a folder that is behind.
- **The release step.** Each release script first runs the vendored checker **from the commit at that product's last mark**, over the range to the source commit being shipped. A release uses two commits. The app is built from source commit A, and its captures come from that build. They are stored in a separate evidence commit B whose parent is A, whose diff touches only `design-evidence/<product>/<build>/`, and whose manifest names A and the digest of the built artifact that will be uploaded. The checker validates B's evidence against A and that artifact. The mark is the tag `shipped/<product>/<build>` on A, read with `ls-remote`; an unreadable remote stops the release with a plain reason. The tag is written after the upload succeeds.
- **The first release (bootstrap).** The apps repository has no tags today. Before a family's first gated release, its session records for each product a verified last-shipped commit (from the store's or feed's own record of the shipped build, matched to a commit by its build number) and writes the first mark there, with the checker taken from a reviewed `design-gate/` commit. Where no shipped commit can be verified, the first release has no range: it needs evidence for every registered screen of that product, and says so.
- **What it requires.** For every registered screen whose sources changed in the range (a `shared` source counts for every screen that lists it), `design-evidence/<product>/<build>/` must hold captures at that platform's standard sizes, and an independent reviewer's answers for every applicable rule, bound to the capture hashes. The checker reads each capture's pixel size from the image itself, never from its name. Once a family's label writer has merged, its debug capture mode writes, beside each image hash, the build number and commit compiled into the app, the seed version, and the display settings (logical viewport, display scale, effective text setting); no app writes these today. The checker then requires the build number and commit to equal A's build, the seed version to equal the vendored one, and the display settings to match each required case, and a capture identical to the previous release's is accepted when its labels are the current build's. Until that writer merges, the release step requires the captures and the reviewer's answers, with the build number entered by the shipping session, and states plainly that this is self-reported. A `fail` refuses the release; `inherited` is accepted when it cites that screen's capture in the previous release's evidence, or, where none exists yet, an open feedback entry or upkeep row that tracks it. A changed UI file in no registered screen refuses the release as `screen-unregistered`. The shipping session fixes and ships again; an owner tap is never the repair for a release, and the step has no off switch of its own.
- **Where the captures come from.** Until a family's capture tool exists (DSE-T2 <!-- tracked: CMT-2166 -->, DSE-T3 <!-- tracked: CMT-2167 -->, DSE-T4 <!-- tracked: CMT-2168 -->), the shipping session takes them in the app's own debug capture mode with seeded data, as the Apple app session already does for DF-0001, and starts a fresh reviewer subagent. For a cross-surface rule such as `DS-PARITY-1`, that reviewer is also given the same-seed web capture of the same screen from instar's latest main render, and its answer is bound to both hashes. This is trusted as taken and self-reported, and stated so. Native automatic checks are part of those same tracked items and block nothing until they exist.
- **Required from the first release after the step lands** in that family's release scripts. There is no grace period after that. The label writer and a build-time stamp of the commit are built per family as part of that family's tracked native item (CMT-2166 Apple, CMT-2167 Android, CMT-2168 Windows and Linux) and proven on a throwaway clone; the labels become required for a family only once its writer has merged.
- **Evidence** stays in the private apps repository and is never copied into instar.
- **Who builds it.** Echo's design-standards session prepares `design-gate/` and the release-script change for each family on a branch named `design-gate/<family>`, proves it on a throwaway clone, and sends it with a brief to that family's session: the Apple app session, the Android app session, and for Windows and Linux the session the Chief of Staff's project list names. Where none is named, Echo's session applies it itself. Each handoff is an upkeep row, which the sweep clears when that family's main branch calls the checker (read from the apps mirror).

## Multi-machine posture

- **Gate files, standard, registry, coverage map, lock file:** `unified`. Git-tracked.
- **Pinned renderer:** `unified`. A provisioned prerequisite each rendering verifier installs on demand in its persistent renderer folder; no verdict depends on which machine ran.
- **Design decision records:** a cache beside the verify record in the coordinator's Local Verify journal, which nothing replicates. Each is re-derived from the record and the unified review rows and waiver card; a takeover re-verifies and recomputes it (section 3). The authoritative inputs are unified.
- **Capture store and base cache:** `proxied-on-read`. Operational and re-creatable from the commits, the seeds and the renderer build. The record names the machine that holds them; if that machine is gone, the capture is re-rendered from the commits or the result is `unavailable: captures-unreachable`.
- **Apps mirror:** `unified`, provisioned only on rendering verifiers that already hold the agent's credential for the apps repository, and read through the mesh from such a machine elsewhere; rebuilt from the remote at any time.
- **Verify records with the `design` field:** as Local Verify has them today.
- **The off switch:** the coordinator's value governs, read at run start and at status posting and written on the record. The verifier running the run reads nothing from its own copy. Its change history is in the replicated store.

## Over-block and under-block

- **Over-block.** A new screen must come with a seed and be clean of blocking rules, because all of its violations are added. Registering a screen or editing a seed is a harness change. A check can be wrong; that is why every check starts in `report`, and why a false failure of a non-earned rule can be waived by the reviewer. A repeated false failure of an earned check in `block` can be demoted by one owner tap under decision 4 instead of a waiver per change. A change that needs the local floor cannot merge on the Actions floor, and one from an ineligible author waits for the owner's admin merge or adoption. A change whose base cannot be built waits up to about two hours for its retries. A screen that renders differently twice is `unavailable` until fixed, not refused. A release of an app needs captures and a review for every changed screen; a change to a shared component needs them for every screen that lists it.
- **Under-block.** An `unavailable` step lets a change merge unseen until the sweep renders its commit. Non-earned waivers rest on the gate's own reviewer; native captures are self-reported. States the seed does not render (hover, an open dialog) are not compared. A server file that affects a screen and is in no source list is caught only when another change re-renders that screen. A screen marked `uncaptured` has no checks; at the first rung only the accounts screen is captured. Feedback on Slack is caught only by the session's own path until DSE-T9 is closed. A detector outage leaves messages `unjudged` until it recovers and re-judges them; a message logged while the server was down has no row and appears only in the weekly gap count and the session's path. A waiver card cannot open while the owner's waiting lane is at its soft budget, so that change waits. A message longer than 64,000 characters is `request-too-long` and not request-approved, so the session reads the full words from the row. What lands can differ from what Local Verify rendered when main moved after the verify; the sweep renders the landed commit within its bound. An admin merge or a hand-uploaded app build is seen only afterwards. While switched off, only screens the latest main render shows with an earned-rule violation are held; a screen never rendered is not.
- **Cost.** The step adds a base render per main tip per rendering verifier and a head render of the affected screens per UI change, plus one reviewer session per changed screen (counted beside the detector's calls in the cost line). Main's own verify renders every captured screen once per tip to fill the base cache, which serves only the pull requests verified after it. The sweep renders every landed UI commit against its parent, reusing results and answers whose trees or evidence match. The detector adds one fast call per owner message, within its ceilings. Each is measured at each rung and reported beside the lanes.
- **What is not measured.** The headline number measures recurrence. Nothing here measures delight, and the spec does not claim to.

## Rollback

The fast rollback is the switch `monitoring.localVerify.designStepOff` in the coordinator's config: no pull request is needed, so a broken step cannot block its own removal. It is recorded, tells the owner, and lapses within a day, so a longer rollback is a reviewed change: setting rows of `DESIGN_GATE_MODES` back to `report`, or a release without the step. The detector and the cards are turned off by `designStandard.enabled: false`; open cards stay on the board. Stage 1's fields are additive and are not rolled back with the gate. With the step off, no rendering refusal applies; two things still hold: a change to a screen with an earned-rule violation waits for the owner's card or for the switch to lapse, and the lint-based `standard-weakened` refusal still runs, because it is a tree read that needs no renderer. In the apps repository the rollback is removing the checker call from a release script, which the sweep reports.

**First book** (`docs/STANDARDS-REGISTRY.md`, under *Operator-Surface Quality*):

> ### Design Mistakes Become Rules; Screens Are Measured Against the Rules Before They Merge
> **Rule.** Every design mistake the owner points out is diagnosed in writing, naming the practice that was broken, and becomes a rule in the Design Standard or sharpens one; the feedback, the diagnosis, the rule and the fix are linked by a tracked card that closes only when the server has verified each, including passing captures on every surface the feedback concerns. Every change to a screen is rendered at the standard sizes with realistic data and measured against the applicable rules before it merges or ships. Rules that can be measured are measured by machine.
> **Fails.** A change may not add a violation of a blocking rule, and a change that breaks a screen it touches does not merge. A screen change with a visible difference that nobody independent has read does not merge. A check that cannot run is recorded as unavailable by name and retried the next day; it is never recorded as a pass. Turning the check off is recorded, the owner is told, and it lapses within a day and cannot exceed a day in any week. A rule the owner's feedback earned is waived or loosened only by the owner, by a tap on his own phone bound to that exact change. Any other rule may be waived only by a reviewer who did not write the change, with a recorded reason.
> **In practice.** `docs/DESIGN-STANDARD.md` is the one standard and its rule ids are permanent. The design step in Local Verify runs main's copy of the gate, renders main's tip and the merge tree with a pinned renderer, and its decision is part of the verification status every merge path reads, on either merge floor. Captures stay in the agent's private store. Each app's release script runs a vendored checker that requires captures and an independent review. Owner design feedback becomes a Work Board card approved by his own message and closed by the server.
> **Earned from.** 2026-11-21: the owner compared the Mac app's accounts screen with the web dashboard's and found the Mac one clearly worse. The diagnosis found fifteen problems; for twelve no rule existed, and the rest were covered by a rule that applied to the web only. The existing quality standard already said a pull request names the screens that were loaded and at which widths, and nothing checked it.
> **Traces to the goal.** A coherent agent does not make its person point out the same kind of mistake twice, and does not ask them to look at a screen it has not looked at itself.
> **Applied through.** `scripts/design/gate.mjs`; `scripts/design/lint.mjs`; the design step of Local Verify and its status term; the release step in each app; `docs/specs/design-standard-enforcement.md`. **Parent principle:** *Structure beats Willpower*.

## Constitution alignment

- **Structure beats Willpower (parent).** A paragraph in a standard becomes a term of the merge status, a lint, a release step and a card the server closes.
- **Verify the State, Not Its Symbol.** The gate renders the verified merge tree and the sweep every landed commit; native captures are bound to the build being shipped; native captures are checked by their pixels; each remaining symbol is declared with its unmeasurable case.
- **Signal vs. Authority; Judgment Within Floors.** Measurements are signals. The recorded decision holds the authority to merge. Each judgment sits inside a stated floor with a named arbiter.
- **Intelligent Prompts: An LLM Gate Must Not String-Match.** Whether a message is design feedback, and whether a review rule passes, are judged by meaning.
- **No Silent Degradation; the User Experience Is the Product.** `unavailable` is named, recorded and retried by commit, and reaches the owner when a declared breaker trips; a base that cannot be built is retried before anything merges; the off switch is signalled at once and lapses.
- **Close the Loop.** Feedback is a card from the moment it is confirmed; the gate's own leftovers are upkeep rows listed weekly; every staged piece cites a tracked commitment.
- **Agent Proposes, Operator Approves; Approval Only Where Required; The Agent Carries the Loop.** The owner is asked for the constitution article and for his earned rules. His own message approves his feedback card; he is never asked to close one or to approve a waiver of an ordinary rule, and is asked about an earned rule only when an author requests a waiver.
- **Attributed Statements Trace to Their Source.** The origin cites the owner's message; the reservation of earned rules is marked as the agent's wording until he approves it.
- **A Dark Feature Guards Nothing.** The native release step requires real captures and a review now, instead of resting on tools that do not exist yet.
- **Always a Multi-Machine Entity.** Every new piece of state has a posture; the one machine-local item uses a key from the closed list.
- **Updates never restrict existing agents; Migration Parity; Agent Awareness.** Nothing here holds or instructs any agent but a development agent.
- **One Constitution, Two Books Aligned.** Both wordings are above, paired, with every figure that changes.
- **Occam's Razor.** One parser, one classifier, one gate and one decision table serve the verifier, the status, the release scripts and the sweep.
