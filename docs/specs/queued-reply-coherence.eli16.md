# Queued replies should not arrive after the conversation moves on

Instar keeps a reply when Telegram delivery is interrupted. This prevents a short outage from losing an answer, but the saved reply can arrive much later. On November 4, a status written at 6:08 PM reached the Instar App topic at 6:36 PM. Justin had answered its question in the meantime, and Echo had already acknowledged that answer. Another topic received a shorter correction after a fuller correction, followed by an older email update. These late messages made the conversation read backward. PR #2741 explained late delivery after it happened and ordered one older queue. It never checked whether a saved draft still belonged in the current conversation before sending it.

The recovery path now reads the recent messages in the same topic before it tries to send a saved session reply. It checks this machine's history and the pooled view from other known machines. If a newer message from the user or agent has already arrived, Instar retires the saved reply in its durable queue. If the pooled view is unavailable or cannot reach back to when the draft was written, Instar waits rather than guessing. The wait for a machine that cannot answer ends 15 minutes after the reply was written, so a sleeping machine cannot hold a reply until it expires; a newer message on any machine that does answer still retires it. Automated delivery notices do not count as a newer answer; otherwise a notice about a delay would accidentally discard the answer it describes. A reply whose first part already reached Telegram is also left for the existing receipt recovery path. Unknown delivery outcomes remain untouched because Instar cannot safely assume they were never delivered. No message from another topic can retire this topic's reply.

When a reply moves to a different Telegram holder, the durable hold keeps its original session label and draft time. The replacement uses those values for the same chronology check and for its topic-history entry after delivery.

The single dot in the Bugs hub had a different cause: Instar sent a temporary “.” message to ask Telegram for an old topic name, then tried to delete it. Deletion or routing can lag. Name lookup now uses names already captured from real Telegram topic events and existing records. An old topic whose name is unknown keeps its fallback label instead of showing a probe to the user.

PR #2775 handles the separate case where another machine repeats an already answered incoming message after failover. This change only handles outbound saved replies and the visible topic-name probe. The code can be reverted without a schema change. A reply already retired while this fix is active cannot be recreated automatically; the newer conversation remains visible, and the user can ask for the earlier answer if it is still needed.
