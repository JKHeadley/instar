# PATCH Actions Strict Body ELI16

The route `PATCH /evolution/actions/:id` used to behave like a clerk who stamped a form "accepted" even when the form asked for something the clerk could not actually do. The documented update fields for an evolution action are `status` and `resolution`. Before this change, a caller could send some other field, such as `title`, and the server would still answer with `ok: true`. The problem was that the unsupported field was not saved. The response made the caller believe a write had happened, but the stored action stayed exactly as it was.

That is dangerous because this route is used for records that agents and operators rely on as evidence of what was corrected, cancelled, or completed. The real incident was a correction to a false claim: a caller tried to update the action so the correction would be on record, but the field was silently discarded while the route still returned success. From the caller's point of view, the retraction had been recorded. In the actual state, the original error still stood. Silent success is worse than a loud failure here because it creates false confidence and removes the signal that someone needs to retry with the right field.

Now the route treats its request body as a strict patch contract. It accepts only `status` and `resolution`. If any other field is present, it returns `400` and names the unsupported fields plus the supported fields. If the body contains no usable update, it returns `400` instead of sending an empty update through the manager. It also type-checks the supported fields before the store write: `status` must be one of `pending`, `in_progress`, `completed`, or `cancelled`, and `resolution` must be a non-empty string when present. Only fields that were actually present and valid are passed to `updateAction`.

The honest limit is that this is a breaking change for any caller that was sending extra fields. A request like `{ "title": "new title", "status": "completed" }` used to return `200`; it now returns `400` until the caller removes `title` or uses a route that really supports title edits. The documented callers already send only `{status, resolution}`, so the known supported path does not break. The callers affected by this change are the ones whose extra fields were already being silently ignored, which is exactly the behavior this fix is meant to expose.
