# Record a real starting point before asking a feature to improve

A feature's activity counter cannot always tell us what problem it is meant to improve. A feature that has never run also cannot already have the successful results we hope it will produce. We need a real starting point from an observable problem or control population, with a clear account of how it was measured.

This proposal uses the existing initiative and measurement system to give a feature its own outcome plan. The plan names exactly which feature and stage it measures, on which machine, under which policy and method. The current feature ladder still owns activity thresholds, waiting periods and decisions to move. The outcome plan owns the evidence about the intended result and its quality safeguards. Neither can quietly borrow another feature's proof.

A baseline action would read registered measurement sources and record their actual values, sample counts and versions. It accepts no made-up values, timestamps or grades. It does not activate the feature, change its settings or mark it ready. If nothing meaningful can be observed before activation, it says the baseline method is unavailable; a real control population or separately authorized drill is needed.

Old baselines remain in the recorded history when a method is deliberately changed. A fresh baseline cannot silently replace a bad result. The plan and the evidence used for a claim would be retained through the existing state-sharing system, so another machine can still explain them if the original machine is lost. Evidence from another machine remains readable but does not grant local permission to promote a feature. The proposed continuity rule requires every configured machine to confirm the exact retained evidence before a promotion or improvement claim commits. One copy on another machine is useful progress, but cannot guarantee that any remaining machine will know what happened. One offline or unsupported machine can therefore hold promotion; running services continue. A single-machine setup reports that there is no cross-machine survival guarantee. Removed machines lose authority while their retained evidence remains clearly labelled historical. Storage limits pause new captures instead of deleting the only surviving evidence. This sharing needs explicit approval and has not been enabled. Running services continue when proof is missing.

This is a prerequisite proposal for the stricter promotion rule. It adds a feature target and a scoped source mapping to the existing measurement path, rather than a second ledger, registry or evaluator. It is not yet approved, implemented or deployed. The review must settle the complete capture and ownership rules before it can ship.
