# Which projects matter most, and which projects used each account

Instar runs on a group of Claude and Codex subscription accounts, and each one has a weekly allowance. The earlier steps of this work taught Instar to read how full each account is, to forecast where it will land when the week resets, and to work out which account really did each piece of work. The next steps will suggest changes, like moving a conversation to a cheaper model when an account is running low. Before anything can make that kind of suggestion sensibly, two things are missing.

The first is what matters to the owner. Every project on the Work page has a goal and a done list, but nothing says one project matters more than another. So this change adds a priority to each project: high, normal or low. Only the owner sets it, with one tap: in the Instar app on their phone, or on a single button the agent sends when the owner asks for it in a Telegram chat ("make the Android rebuild high priority"). The dashboard shows the priority but can't change it, because the dashboard's PIN is something the agent itself can read, so a tap there wouldn't prove the owner made the choice. The agent can read the priority and pass on the owner's request, but it can never set the priority itself. Setting a priority doesn't restart or nudge any work. A project the owner has never rated shows "Normal (not set)", so nobody mistakes silence for a choice.

The second is where the allowance went. Instar already records every request it sends, and after the last step it knows which account served each one. This change also records which conversation each request belonged to, then uses the Chief of Staff's project list to add it all up. You can ask "of the work recorded on Dawn's Claude account this week, how much went to each project?" and get an answer like "40% the Android rebuild, 25% the dashboard work, 20% conversations that aren't part of any project, 15% background jobs". Work that can't be tied to a project or a proven account gets its own labelled slice, so the slices always add up to the whole and nothing is hidden. If a machine doesn't answer, or its records don't reach back far enough, the result says it is incomplete instead of counting the missing part as zero. These are shares of the work the agent recorded, not of the provider's weekly percentage, and use of the same account outside the agent (the web app, the phone) can't be seen. The priority part is built first; the shares are built right after the previous step's change (which proves which account did the work) is merged.

Nothing in this step acts on either number. Priority and project shares are information only. No work gets slowed, moved or stopped because of them, and a built-in test fails if any other part of the system starts reading them before a later step has been designed and reviewed for that job. It starts on Echo's machines only, behind one switch that turns all of it off, and goes to other agents only after a review of how it worked in real use.
