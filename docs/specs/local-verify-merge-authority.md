## Problem statement

The operator has asked, many times, that sessions run tests locally and stop waiting on GitHub. It never sticks, because the instruction is willpower and the merge path is structure:

- `scripts/safe-merge.mjs` carries a code-pinned `REQUIRED_CONTEXTS_FLOOR` (Type Check, Integration Tests, E2E Tests, Build, decision-audit, eli16) that must be green and produced by `github-actions` from the named workflow file. (The pin binds the workflow file's *name*; a same-repo PR can still edit `ci.yml`.) No local result can satisfy it.
- `--auto` arms GitHub native auto-merge, which waits on GitHub checks.
- The green-PR watcher's candidate gate (`greenPrLogic.ts:170`) requires `pr.statusRollup === 'SUCCESS'`, i.e. GitHub's rollup.
- `.husky/pre-push` says "CI remains the authority".
- And the hardest wall: `main` has **classic branch protection** (separate from the `instar-main-protection` ruleset) that requires 12 GitHub Actions contexts — Type Check, Integration Tests, E2E Tests, Build, and Unit Tests for Node 20 and 22, shards 1–4 — enforced for non-admins (`gh api repos/JKHeadley/instar/branches/main` → `protection.required_status_checks`, checked 2026-10-21). The agent's login (`EchoOfDawn`) is not an admin, so **GitHub itself refuses every agent merge until Actions is green**, whatever any local run says; only the operator, as admin, can merge past it. safe-merge never sees this: `GET /branches/main/protection` returns 404 for a non-admin, and `fetchProtectionContexts` reads that 404 as "no protection". The ruleset by itself requires no status checks, which is why earlier checks of it looked clean.

So every agent merge structurally waits on GitHub Actions, twice over: in the merge tool, and in GitHub's own branch protection. No instruction to "run tests locally" could ever change that.

Measured 2026-10-21 (last 80 merged PRs of JKHeadley/instar, since 2026-10-09): open-to-merge median 2.7 h, p75 10.8 h, p90 33 h, max 108 h. Actions queue wait up to 164 min; CI wall p90 54 min. Each PR fans out to 17 jobs in `ci.yml` (8 unit shards — 2 Node versions × 4 — running the flaky-excluded `test:push` config, plus integration, e2e, build, typecheck, contract, and four checks: repo invariants, docs coverage, cartographer freshness, standards coverage) plus 7 one-job gate workflows; the unit shard matrix is what exhausts Actions billing.

The second cause is local speed. Every vitest config sets `fileParallelism: false`, so a full local run takes 60+ minutes on a 16-core Mac Studio; `test:all` also runs the integration and e2e tiers **twice** (`vitest.config.ts` includes them, then the dedicated configs run them again). Two concurrent runs slow each other, and the watchdog has interrupted runs at the hour mark.

Measured on the Mac Studio (16 cores, Node 24.14.1, other agent servers running), current `main`:

| Lane | Files | Tests | 8 workers, lane alone | Result |
|---|---|---|---|---|
| Unit (`tests/unit` + `tests/real-world-state`) | 2,693 | 49,135 | 3 min 40 s | all passed |
| Integration | 590 | 4,789 | 2 min 45 s (1 worker, today's setting: **14 min 54 s**, all passed) | at 8 workers 1 file failed, passes alone |
| E2E | 434 | 3,522 | 6 min 14 s | all passed |

With integration and e2e kept at 1 worker (§1), measured on the Studio: unit ~4 min + integration **14 min 54 s** + e2e **23 min 44 s** (428 files passed, 6 skipped). So `test:all` is about **43 minutes**, and a full verify about **45 minutes** with install and build, against 60+ today, with no GitHub queue or billing wait. The two isolation follow-ups (ports, tmux sockets) <!-- tracked: CMT-903 --> are what bring it down further; at 8 workers the three lanes measured 12.6 minutes together. The integration lane is a known exception: `vitest.integration.config.ts` pins `maxWorkers: 1` on purpose because a recycled localhost port can hand one test another test's pooled connection (a 401 from the previous fixture server). That race is timing-dependent; one near-clean parallel run does not clear it.

This is the Bors / merge-train shape (test the merge commit, land it), deliberately without a strict queue: the base is not pinned at merge time (§3), and the post-merge `main` verify is the compensating control.

### Alternative considered: self-hosted GitHub Actions runners

A self-hosted runner on the Studio would remove the hosted-runner queue and billing while keeping safe-merge and the watcher unchanged. Rejected for v1: the operator's standing direction (2026-09-17, 2026-10-05, 2026-10-20) is that verification must not depend on GitHub's job dispatch at all — an Actions outage or policy change would still stop merges — and it keeps the 17-job fan-out that is the billing load. (The code-runs-on-our-host concern applies equally to both designs and is not a reason to prefer one.) If GitHub dispatch ever becomes acceptable again, a self-hosted runner is a cheap addition on top of §1.

## Key terms

- **Floor:** the rule safe-merge applies before merging: `actions` (GitHub's checks) or `local` (this spec).
- **Lane:** one group of test files run by one vitest config.
- **Lease / lease holder:** the multi-machine "which machine is in charge" token; only the holder runs the watcher and posts statuses.
- **Harness-changing:** a PR that changes the test setup or the merge machinery itself (§2 list); admitted only with an independent second-pass review of its head (§2). Never routed to the operator: the operator approves constitution changes only, and GitHub enforces that through `.github/CODEOWNERS`.
- **Independent review:** an instar-dev trace (`.instar/instar-dev-traces/*.json`, written by `skills/instar-dev/scripts/write-trace.mjs`) committed in the PR whose second pass ran and concurred, whose `coveredFiles` include every flagged path, and whose side-effects artifact is in the same tree.
- **Attention item:** one deduped notice in the operator's Attention topic.
- **Watcher tick:** the green-PR watcher's 10-minute cycle; the status reconcile loop runs separately every 60 seconds.

## Threat model (decided, so reviewers can contest facts rather than taste)

Only PRs opened under the `gh` login this agent uses (`expectedGhLogin`, today `EchoOfDawn`), from a branch in this repository (not a fork), are verified locally. That login can be shared by sibling agents on the operator's machines, so it identifies "one of the operator's own agents", not "this agent". Every such PR is written by a principal the operator already trusts, and that code is already run every day by builder sessions as the agent user, with the vault, the machine key and the `gh` token in reach, and the agent is the principal that merges. The verifier therefore runs **as the agent user** with a scrubbed environment; it does not add a second OS account, a sandbox profile or signing keys, because none of them changes the stated limit below and each adds a per-machine setup step. If isolation is wanted later, the reuse path is the feedback executor's `SandboxRuntimeRunner` (canary-proven), not a new mechanism.

What the design does guarantee: GitHub itself refuses a merge without the server-posted `instar/local-verify` status (§3), whatever tool, framework or machine a session uses; cannot hand in a result through its tools or by accident (the server's decision comes from memory populated only by the verifier's completion path, §2; deliberately posting a `success` status with the shared login is forgery, which the threat model excludes, see §3 Stated limits), and cannot get a result for different code accepted (head SHA bound, §3). What it does not guarantee, stated plainly: the run reports its own outcome. A PR could replace a test with one that writes a convincing report, or, since tests run as the agent user with the shared `gh` login reachable, post `success` itself. On GitHub Actions a PR can edit `ci.yml` to `exit 0`, but its token is short-lived and repository-scoped; here it is not, so this is weaker than Actions against deliberately malicious code, and acceptable only because every verified PR comes from the operator's own trusted agents, and with no required approvals on `src/` there is no human check on that diff either. Fork PRs, outside contributors and the feedback executor's cross-repo PRs never run here (L14): they stay on the Actions floor.

## Design

Three pieces, one authority. v1 is deliberately small: no signing, no git notes, no second OS user, no cross-machine dispatch, no shadow period.

### 1. Parallel test lanes

Three lanes with explicit, disjoint include sets:

| Lane | Config | Include | Workers |
|---|---|---|---|
| `unit` | `vitest.config.ts` | `tests/unit/**`, `tests/real-world-state/**` | parallel |
| `integration` | `vitest.integration.config.ts` | `tests/integration/**` | **1** (unchanged until the port-reuse race is fixed at the source — a named follow-up <!-- tracked: CMT-903 -->; parallelised only after ten consecutive clean parallel runs) |
| `e2e` | `vitest.e2e.config.ts` | `tests/e2e/**` | **1** (unchanged until each run gets its own tmux socket — a named follow-up <!-- tracked: CMT-903 -->; the config keeps files sequential because legacy prefix-wide cleanup helpers can reap another suite's live pane, and one clean parallel run does not clear that) |

- `vitest.config.ts` narrows its include to the unit lane, so `npm test` is the unit lane and nothing runs twice. `vitest.e2e.config.ts` gains `tests/setup/build-dist.globalSetup.ts` (idempotent; a no-op when `dist/` is newer than `src/`), because its comment currently relies on `vitest.config.ts` having built dist. **`npm run test:all` is the command the Zero-Failure Standard names**: the three lanes one after another, build once up front. The repo `CLAUDE.md`, the CLAUDE.md template and `.husky/pre-push` wording change to match (pre-push keeps running the smoke tier).
- The worker count lives in the configs: `maxWorkers = INSTAR_TEST_WORKERS ?? (cores >= 12 ? 8 : ceil(cores/2))`, `minWorkers: 1`, `fileParallelism: true`.
- Each lane acquires its own host test-runner suite slot in turn. `test:all` holds no slot of its own (a lane that is a descendant of a recorded holder is clamped to 4 workers by the bound once it enforces, which would silently undo the measurement).
- No serial lane: the one file that failed in parallel is in the integration lane, which already runs one file at a time. A serial lane is added the day a unit or e2e file needs one.
- `npm run test:all` still runs the three lanes one after another. The verifier runs them at once, inside one slot (next subsection).

#### Parallel lanes in the verifier (amendment 2026-10-22)

The serial verifier took about 45 minutes per PR, one PR at a time, which brought the hours-long queue back as soon as several PRs were open (five queued on 2026-10-22, the last about three hours out). The verifier now runs all lanes at once:

- The verify process takes **one** full-suite slot of the host bound before the lanes and holds it until they finish. Each lane's vitest is its child, so the bound nests the lane's own request under that slot (and clamps it to 4 workers) instead of queuing it behind its siblings. The host still runs at most one full verification or suite at a time; a busy slot re-queues the verify exactly as a foreign suite seen at start did. The old wait-in-place before lanes 2 and 3 is gone, because there are no later lanes.
- The `e2e` lane runs as two vitest shards (`--shard=1/2`, `--shard=2/2`); their reports are joined into one lane report before the inventory rule. `integration` stays one process with one worker, so its port-reuse race (a pooled connection inside one process) is unaffected.
- Every lane process gets its own `TMPDIR` and `TMUX_TMPDIR`, so each has its own tmux server. This is the per-run tmux socket the `e2e` row above waited for: a prefix-wide cleanup in one shard cannot reach another shard's panes.
- At most 4 + 1 + 1 + 1 = 7 test workers, against the 8 the unit lane used alone; not the test-storm shape. The unit lane's 4 workers are pinned in its environment (`INSTAR_TEST_WORKERS`), so this holds whether or not the bound enforces. Its deadline goes from 10 to 20 minutes.
- A lane's verdict across shards: a file reported by two shards makes the lane report missing (the run fails); a numeric non-zero exit of any shard is the lane's exit code, ahead of a signal exit.

Measured on the Studio, 2026-10-22, on `main` at `70dce25`, with a full serial verify running at the same time (so with more load than a real run): unit 7 min, integration 18 min, e2e shards 11 and 20 min, so about 20 minutes for the lanes against about 42 serial. Results: 58,373 tests, 0 failures except one integration test (`session-watchdog-safe-wait`) that assumed a spinning process gets a whole core within 1.5 s; it is fixed in the test (PR 2319) and passes under full CPU load. An earlier trial's failures were traced to that trial's own environment (temp paths too long for Unix sockets, the session's own `INSTAR_*` variables), not to running in parallel.

### 2. `local-verify` — the run a merge waits for

`POST /local-verify`, body `{ "pr": <positive integer> }` and nothing else. Repo comes from `monitoring.greenPrAutoMerge.repo`, never from the request. Bearer auth. Queue: one pending entry per PR, 10 total (429 when full); queued entries for closed or merged PRs are dropped. Repo-gated: 503 on an install with no instar source checkout, like `/green-pr-automerge`. A standby answers 409 naming the lease holder (the lease-gated-route pattern); it does not proxy.

**Eligibility** (checked by the verifier itself from `gh pr view --json author,isCrossRepository,headRefName,headRefOid,baseRefName,baseRefOid`): author is `expectedGhLogin` or `monitoring.localVerify.operatorGhLogin`, and `isCrossRepository == false`. This decides only what may be **verified** (trusted principals' code, never a fork or an outside contributor). What the watcher may **merge automatically** is unchanged: it keeps its existing `<agentNamespace>/` branch filter, because the shared login cannot tell this agent's PRs from the operator's or a sibling's. Otherwise `refused:untrusted-head`; the PR stays on the Actions floor.

**Run.**

1. Fetch head and base by SHA into a dedicated bare clone used only by the verifier (`~/.instar/agents/<agent>/.worktrees/.verify/repo.git` (under the already-gitignored, Spotlight-excluded `.worktrees/`), never the agent-home checkout, so a test that writes `.git/config` or `.git/hooks` cannot reach the live agent's git), and create a fresh worktree from it under `~/.instar/agents/<agent>/.worktrees/.verify/runs/<headSha12>`; the bare clone's config and hooks directory are reset from a fixed template before every run; fetch with full history (no shallow fetch, matching CI's `fetch-depth: 0`); compute the merge with `git merge-tree --write-tree <base> <head>` (a conflict fails the run as `error:conflict`), wrap it in a commit with `git commit-tree <tree> -p <base> -p <head>` under a fixed local identity (`local-verify <noreply@local>`, set only in the private bare clone and never pushed), and check out that commit so history-reading lints and tests see both parents; `refs/heads/main` and `refs/remotes/origin/main` in the bare clone are set to `baseSha` first, because history lints compute `merge-base origin/main|main HEAD`. All git steps go through `SafeGitExecutor` with a new path-scoped carve-out, `localVerifyCloneOk`, modelled on `feedbackAttemptCloneOk`: an enumerated verb list (`fetch`, `merge-tree`, `commit-tree`, `update-ref`, `config`, `checkout`, `worktree add`/`remove`/`prune`, `diff`, `merge-base`, `status`) allowed only when every target is inside `.worktrees/.verify/`; the shared read tier is not widened. File-level steps (resetting the clone's config and hooks, deleting a dirty run directory) go through `SafeFsExecutor` scoped to the same directory; record `mergeTree` and `baseRefName`. Using a separate bare clone also avoids `index.lock` contention with auto-update operations on the agent's home checkout.
2. `npm ci` into the fresh worktree on every run (the npm download cache keeps it to a minute or two). No shared `node_modules` cache in v1: nothing one run installs can reach another run. A cache is a follow-up only if the measured install time justifies it. <!-- tracked: CMT-903 -->
3. Build once, then the exact command list of `npm run lint` (the `tsc` check plus every lint script it runs, with history-dependent lints (those that diff against the base) run against the merge base), then the lanes, invoking `node_modules/.bin/vitest --config <file> --allowOnly=false` directly (never `npm run`); `--allowOnly=false` makes a stray `.only` a failure. `CI` is removed from the environment so CI-dependent behaviour (for example the test-runner semaphore's checks) matches local runs.
4. Fresh `TMPDIR` and a fresh `TMUX_TMPDIR` per run (so the e2e lane's tmux fixtures and their legacy prefix-wide cleanup talk to a private tmux server and can never reach live agent panes on the host), own process group, `nice`. Deadlines cover the whole run, not just the lanes: fetch 5 min, `npm ci` 10 min, build + lint 15 min, unit lane 10 min, integration lane 30 min, e2e lane 45 min, and an overall active-work deadline of 120 min excluding only slot waits (fixed constants in config, reviewed at Acceptance, never derived from the run's own history); any deadline hit sets `error` naming the step. Process lifecycle reuses `MergeRunner`'s two-phase in-flight protocol verbatim (durable intent with a unique attempt token written **before** spawn, pid/pgid patched in after, and at boot the recorded group is killed only after its identity is corroborated via that token; an uncorroborated record is **kept**, audited `orphan-reap-incomplete`, and blocks any new verify until the recorded process is shown to be gone, exactly as `MergeRunner` does), so a server restart never leaves two verifies running and never kills a recycled process group.
5. The orchestrator computes the inventory itself — every `tests/**/*.test.ts` and `src/**/*.test.ts` in the merge tree, minus an explicit exclusion list in the orchestrator (`tests/contract/**`, which needs a live key; `tests/fixtures/**`, which holds test files used as data by other tests; and `src/providers/adapters/example/**`, the adapter template's example) — and requires each remaining file to appear in exactly one lane's report with zero failed tests, and at least one collected test (passed + skipped + todo > 0) — about 26 files today skip entirely by design behind `skipIf`/`runIf` guards and count as passing, while the static ratchet below stops a PR from adding new skips; a file in no lane, a lane with zero passed tests overall, or any failure fails the run. Skipped and todo counts are recorded per file. The skip ratchet is **static** and parser-based: the orchestrator runs the TypeScript parser (already a dependency) over both revisions of each test file changed in the merge-base→head diff and counts call expressions of `it`/`test`/`describe`/`suite` with `.skip`/`.todo`/`.skipIf`/`.runIf` anywhere in the member chain (so `it.concurrent.skip` and `test.skip.each` count), `xit`/`xdescribe`, parameterized `.each` forms, and runtime `ctx.skip()`/`context.skip()` calls inside a test body; comments and strings are not call expressions and do not count. Known limit, stated: tests registered through custom wrapper functions are not seen. A net addition does not fail the run but routes the PR to the operator like a harness-changing PR (status says `skips-added`; admitted by `operatorApprovedHead`), so a legitimate new `skipIf(!hasTmux)` can still merge with one approval. Deleting is easier than skipping, so the same parse also counts deleted test files, test files moved out of the inventory (for example into `tests/fixtures/**`), and removed test calls: a net loss of either routes the PR the same way (status says `tests-removed`). Packages under `packages/**` and stray `*.test.mjs` scripts run their own `node --test` and are outside this inventory. Any other `src/**/*.test.ts` fails the run until it is moved under `tests/` or added to the exclusion list, which is harness-changing. `vitest.push.config.ts` and its flaky-exclusion list are never used. As CI does, the orchestrator sets `AUDIT_CHANGE_KIND=pull_request`, `AUDIT_CHANGE_BASE_SHA` and `AUDIT_CHANGE_HEAD_SHA` for the unit lane, and after the lanes it fails the run if `git status --porcelain` in the worktree is not empty (a test that wrote into the tree).
6. On completion the verifier's completion path appends the result to a durable completion journal (`state/local-verify/journal.jsonl`, written only by that path, each entry carrying the verifier version and a hash of the harness and policy it ran under) and loads it into the server's in-memory index. At boot the index is rebuilt from the journal, keeping only entries whose verifier version and policy hash match the running code and whose PR is still open; anything else is re-verified. Releases restart the server after most merges, and re-running every green PR after each restart would cost about 45 minutes per PR per restart, so the evidence must survive a restart. A session could hand-edit the journal, exactly as it could post a `success` status with the shared login: deliberate forgery, which the threat model excludes. No other file is ever read as a result. Record: `{ repo, pr, headSha, baseSha, baseRefName, mergeTree, lanes:{name, files, tests, failed, seconds}, nodeVersion, machineId, startedAt, finishedAt, outcome }`.
7. The server posts the commit status `instar/local-verify` (success / failure / error) on the head SHA; the description carries the state label first (for example `harness-changing`) and then the wall time and per-lane counts, cut to GitHub's 140-character limit; the full detail is in the audit record; no link.
8. Worktree removed through `SafeGitExecutor` (`worktree remove`, the same path `agentWorktreeGit.ts` uses); if that refuses a dirty tree (the case a failed porcelain check leaves), the directory is deleted through `SafeFsExecutor` and `worktree prune` follows; the bare clone lives outside any instar source tree's guarded paths and is never deleted, only reset. At most 3 worktrees kept for failed runs. Retention: records while the PR is open plus 14 days, cap 500; `logs/local-verify.jsonl` (metadata only) rotates at 5 MB, 10 files kept. During the Acceptance measurement the SessionReaper's CPU tier is sampled and recorded.

**Where the verifier's own code comes from.** The orchestrator, inventory, eligibility check and harness classifier always run from the agent server's installed copy, never from the merge tree. Only the vitest configs and `tests/setup/**` of a harness-changing PR are taken from the PR.

**Harness-changing PRs.** The trusted side classifies the PR's diff (computed in the bare clone, below) against a glob list: `scripts/local-verify.mjs`, `scripts/safe-merge.mjs`, the status-projection code, every server-side source file of the merge authority (the floor-selection function, the verify queue and orchestrator wrapper, the completion path that is the only writer to the index, the index and its routes, the watcher pre-filter in `greenPrLogic.ts`, `GreenPrAutoMerger.ts`, `MergeRunner.ts`, `greenPrAutomergeWiring.ts`), `vitest*.config.ts`, `tests/setup/**`, `tests/vitest-setup.ts`, the `scripts` and `overrides` blocks of `package.json`, `.npmrc`, `patches/**`, `tsconfig*.json`, any file a `package.json` lifecycle script runs (today `scripts/fix-better-sqlite3.cjs`), a lockfile or manifest change to the test toolchain (`vitest`, `@vitest/*`, `typescript`, `tsx`), the pinned required-context list, and the protected-path list itself. The same diff also sets `protectedPath` (against the watcher's existing protected-path list), so neither flag depends on GitHub's file list. Classification uses `git diff --name-only $(git merge-base <base> <head>) <head>` computed in the bare clone (not GitHub's file list, which is truncated for large PRs); any read failure classifies the PR as harness-changing. Toolchain changes are read from `package-lock.json` and `package.json`, which `npm ci` uses. A failure of the skip ratchet's parser alone is not a read failure of the diff: it does not set `harnessChanging`; the record instead carries `skipsAdded` and `testsRemoved` (what could not be ruled out), so the changed inventoried test files are the paths a review must cover. The parser (`typescript`) is resolved from the run worktree that `npm ci` just installed, then from the verifier's own install, which has no devDependencies (amended 2026-10-23: 23 of 41 runs had been recorded harness-changing because the installed copy could not load it). The flag is stored in the record. Such a PR is verified with **its own** harness (so its test changes are exercised) and the status description says `harness-changing`. Other lockfile changes are not on the list.

**Independent review of a flagged record (amended 2026-10-22).** (operator directive, 2026-10-22 08:58 PDT: “Why am I having to approve these? I should ONLY have to approve constitution changes.”) A record flagged harness-changing, protected-path, skips-added or tests-removed no longer waits for the operator's approval of its head. It is admitted only with an independent second-pass review of that exact head, which the trusted side reads itself: among the files the PR adds or modifies (the same merge-base→head diff), it looks for instar-dev trace files (`.instar/instar-dev-traces/*.json`), reads each **from the head's tree** (`git show <head>:<path>`, so a trace committed after the verified head can never count for it, and a trace already on `main` that the PR did not change never counts), and accepts the first whose `phase` is `complete`, whose `secondPass` is true and `reviewerConcurred` is true, whose `coveredFiles` include every flagged path, and whose `artifactPath` is in the same tree (≥ 200 characters, matching the trace's `artifactSha256`, which is required: a missing one is `artifact-sha-missing`) with a `## Second-pass review` section whose `**Reviewer:**` line names a reviewer (empty, a template placeholder, or "pending" refuses). **The review is bound to the head**, replacing the head-binding the operator approval had (`dismiss_stale_reviews_on_push`): no flagged path may change after the trace's last commit. Through the verifier's git funnel in the bare clone, `git log -1 --format=%H <mergeBase>..<head> -- <trace>` gives the trace's last commit and `git log --format=%H <traceLast>..<head> -- <flagged paths>` must be empty, so the last commit touching any flagged path is the trace's commit or an ancestor of it; a later push that edits a flagged file again needs a new review. These attestations (`secondPass`, `reviewerConcurred`, the Reviewer line) are written by the authoring agent; the pre-commit hook does not check them. That is acceptable under this spec's threat model (trusted principals; the case stopped is the accidental one, not deliberate tampering). The flagged paths are: each path a harness reason names (`package.json` / `package-lock.json` for a manifest reason), every changed path on the protected list, and every changed inventoried test file when skips were added or tests removed; a read failure leaves them unknown, and then no trace can count (re-verify). The judge is one implementation, `scripts/lib/instar-dev-trace.mjs`, shared with the instar-dev pre-commit gate's own coverage and artifact checks. The record stores `independentReview: { trace: <path>, concurred: true }`; the PR body is never read for it. Without one, safe-merge refuses `refused:needs-independent-review` and the projection stays `pending` (`awaiting-independent-review`); the watcher records the refusal for that head without a ladder attempt or attention item and does not run safe-merge again until the head moves (the agent runs the second pass and commits its trace). Constitution files stay operator-only through `.github/CODEOWNERS`, which GitHub enforces; nothing here duplicates or weakens it. safe-merge's review precheck honours the ruleset's `require_code_owner_review`: a PR touching a CODEOWNERS-owned path (CODEOWNERS read from the base branch) whose `reviewDecision` is not `APPROVED` is refused `refused:approval-required` with the review link, never attempted.

**Policy-check parity** (every CI job, kept or moved with a reason):

| CI job | Where | Note |
|---|---|---|
| Type Check (`npm run lint`, full list), Build, Unit / Integration / E2E | verify | as above |
| Repo Invariants, Docs Coverage, Cartographer Freshness | verify | same scripts, no GitHub input |

**Keys.** Execution is deduplicated by merge-tree inputs (head SHA + base SHA). Records are keyed by **(repo, pr, headSha, baseRefName)**: a retargeted PR, or a second PR sharing a head, has no matching record and is verified on its own; retargeting a PR invalidates its old record. Every record carries its `baseSha`; a success record's validity does not depend on it (the base is not pinned, §3) except during main-red (§3). Retry transitions, one table: an `error` (infrastructure: crash, timeout, install failure) is re-run once automatically, then stays until the head moves or someone asks; a `failure` (a test or check failed) is re-run when the head moves, when a `main` verify goes red→green (oldest first up to the queue cap; any overflow stays failed and is logged), or on an explicit request (`POST /local-verify` or `instar safe-merge`, at most once per new base so a prerequisite that landed on `main` can be picked up); a capacity wait is never an attempt. Nothing re-runs a failure on every base move automatically, because at ~45 minutes per verify that would swamp the single slot.

**Who starts a verify.** On every tick the watcher requests a verify for each **namespace** merge candidate (head in `<agentNamespace>/`, open, not draft, review precheck passing, head unchanged for 5 minutes; ordered oldest-ready first, where ready means the review precheck started passing, or the PR opened if no review is required) that has **no authorization record in the server index for its current (pr, head, baseRefName)** (deduped as above; the queue is first-in, first-out by `firstQueuedAt`, which a queued PR keeps when `main` or its head moves — see "The merge line" below — with a `main` verify always first). A record that exists but whose status post failed gets the status re-posted, never a re-run. A moved head cancels the in-flight run for the old head. After a restart or lease move the index is empty; re-verification is **lazy**, and queued verifies start only after `main` is healthy again (only when `main` is unhealthy; a restart with a readable healthy watermark does not enter `main-suspect`): only namespace merge candidates (as defined above; a PR that needs `operatorApprovedHead`, decided before queueing by running the trusted classifier on a name-only merge-base diff in the bare clone, a cheap step that authorizes nothing, is left out until that approval holds, then queued first) are queued, oldest-approved first, so a restart costs one verify per PR that is actually about to merge rather than one per open PR. Restarts per day and the resulting re-verify hours per day are measured and recorded in Acceptance. Other eligible PRs are verified on request: a session POSTs, or `instar safe-merge` enqueues a verify when it finds no record and answers `refused:verify-pending`. Sessions may also POST.

**The merge line (amendment 2026-10-23, CMT-980).** Three rules make the queue a line of PRs merged one after another, each verified on top of the last, instead of a queue that reshuffles whenever `main` moves. (1) *A queued PR keeps its place* (CMT-973): when a request finds the PR already queued and only its base moved, the entry's `baseSha` is refreshed in place (audit `base-updated`) — it is never dequeued and re-pushed, so its `firstQueuedAt`, its position, its paused time and its starved flag are kept; when its head moved (or it was retargeted) the new head takes the old entry's slot and `firstQueuedAt` (audit `queued` with `keptPlace: true`), with attempts reset for the new head; a head pushed during the PR's OWN run (which cancels that run) takes the FRONT of the line with the cancelled run's `firstQueuedAt`. A re-request that confirms the base unchanged also refreshes the entry's `baseResolvedAt`, so the watcher's own tick keeps bases fresh without a pre-start read. Before this, every watcher tick after a `main` move dequeued and re-pushed each queued PR with a fresh `firstQueuedAt`, so a PR went to the back of the line each time (PR 2320: queued 02:12, re-pushed seven times, started 09:26). (2) *Every PR verify starts against today's base*: right before a PR entry starts, the service re-reads the base branch's head (the `baseHead` seam) when `main` has moved since the entry's base was resolved (a merge the line itself made, or a new head the reconcile loop observed) or when the entry has waited five minutes since then (`decideBaseRefresh`, `MERGE_LINE.baseRefreshAfterMs`); a moved base is audited `base-refreshed`, an unreadable base starts the run on the last known base (audited `base-refresh-failed`, never a refusal), and identical merge inputs already verified green under this policy derive a record instead of a second run (`derived-at-start`). The entry stays in the queue during the read, so a concurrent request still finds it. (3) *Merge in order*: a green PR record is handed to the green-PR watcher at once (`LocalVerifyService.setMergeHandoff`, wired by `wireMergeLine`), not left for the watcher's next 10-minute tick, and the verify queue is HELD until that attempt settles — at most `MERGE_LINE.handoffMaxMs` (30 min, the sync merge deadline plus margin) — so the next PR is verified on top of the merge rather than racing it. The hand-off first posts the head's `instar/local-verify` status through the reconcile loop's own serialized per-head writer (`submit`, listing first — `awaitPass`, the running pass or a new one, never a `busy` short-circuit — if the head is not yet known) and reads it back; with live posting, a head GitHub does not hold `success` for is not handed off (the merge would be refused and burn a ladder attempt), and the record waits for the regular tick. The watcher's `tick({ handoff: { pr, head } })` then merges exactly that (pr, head) through every gate a normal tick applies — lease, latches, breaker, warm-up, the local floor, holds, the code-owner wait for constitution files, the independent second-pass review a flagged record needs, and safe-merge's own §3 predicate — selecting nothing else, requesting no verifies, and waiting for an attempt already in flight instead of feeding the busy-skip breaker — released only after the owning tick has SAVED its state (`settleInFlight`), never from inside the attempt, so the waiter's own save can never overwrite the owner's episode, ladder or breaker records; the hand-off's answer is the attempt's classified outcome (`act()` returns it), so an `armed` result is never reported as `merged`. A hand-off never retries: a refusal releases the hold with its reason and the PR is left to the watcher's ticks; a watcher answer arriving after the hold timed out (a long in-flight wait plus the hand-off's own sync merge can exceed 30 min) never reopens the hold, is audited `merge-handoff-late-answer`, and a late `merged` still marks `main` as moved so the next start re-reads its base; one hand-off per record; one hold at a time (a second green record arriving during a hold, e.g. a derived one, is left to the tick, audited `merge-handoff-skipped`). The hand-off carries whether the record's base is the current `main` head (`baseIsCurrentMain`); a record verified on an older base is still handed off when `main` is healthy, exactly as §3 admits it, and the post-merge `main` verify stays the compensating control. `GET /local-verify` reports `mergeLine` (`wired`, the open `hold`, `handoffs`, `merged`, `lastOutcome`); the kill switch `monitoring.localVerify.mergeLine: false` (read live, absent ⇒ on) is read by the service BEFORE a hold opens — a disabled line books no hold, counter or hand-off audit and `mergeLine.enabled` reads false — and returns merges to the watcher's ticks without a restart; without a watcher the line is inert (`wired: false`). Audit events: `base-updated`, `base-refreshed`, `base-refresh-failed`, `derived-at-start`, `merge-handoff`, `merge-handoff-result`, `merge-handoff-late-answer`, `merge-handoff-skipped`, `dequeued` (reason `head-moved`) (service), `handoff`, `handoff-not-eligible`, `handoff-skipped`, `handoff-waited-in-flight` (watcher).

**Merge deadline and flags.** In `local` mode `MergeRunner` gets a third strategy value, `sync`: it runs safe-merge's synchronous path with **neither** `--auto` nor `--admin` (so GitHub's refusal never depends on the agent login lacking admin rights; a test asserts neither flag is passed), under the synchronous deadline `mergeTimeoutMs` (25 minutes), not the 60-second `--auto` arm deadline, because the merge runs the body gates and standards-coverage synchronously.

**Single flight against other suites.** When this was written the host test-runner bound was in watch-only mode, so its slot did not exclude anything (it has enforced since 2026-10-22 07:19 UTC). The verifier does not start (and re-queues without counting an attempt) while the holders file shows a live full-suite holder, but in watch-only mode that is an observation, not a reservation: a builder can still start a suite a moment later. v1 accepts that overlap and measures it: every overlap seen is logged, and a separate oldest-wait threshold covers starvation: if the oldest queued verify has waited more than 3 hours in total, capacity waits included, ONE item is raised (`local-verify:starved`). Since the 2026-10-22 amendment (§1) the lanes run at once inside one held suite slot, so this check is made once, before the lanes, and a busy slot re-queues; there is no wait in place. The exclusion is one-sided until the bound enforces. Exclusion is claimed only once the bound enforces; that flip is the bound's own rollout decision, not this spec's.

**Slots and timing.** Since the 2026-10-22 amendment (§1) the verify process takes one suite slot (60-second acquire budget) after build and lint and holds it for the whole lane phase; each lane's `globalSetup` nests under it. A busy slot, or an internal error of the bound, puts the verify back in the queue; it is not an attempt and does not set `error`. A fail-open admit (the bound cannot confirm a host-local disk) runs the lanes, whose own requests fail open the same way. The slot is released after every lane process has exited, including when one hits its deadline. The e2e lane's deadline error names the shard (`deadline:e2e-1` / `deadline:e2e-2`). An isolation re-run runs alone within its lane; the other lanes may still be running. One pending entry per PR, the cap of 10 and cancel-on-moved-head bound the queue; there is no separate per-PR start cap.

**Restarts.** Releases publish on almost every merge (31 releases against 57 merges in the last 7 days), so an auto-update restart follows most merges and empties the index. Two rules keep that from re-verifying every green PR: (a) the restart hold also covers heads whose last projected status is `success` (the synchronous `UpdateGate.setRestartHoldProvider` cannot make `gh` calls, so it reads the projection cache), each with `until` fixed at first raise as now + 2 × the watcher tick (20 minutes) and never renewed, so verified PRs merge before the restart; (b) "update pending" means `config.autoApply` is true and `AutoUpdater.getStatus().pendingUpdate != null` or `coalescingUntil` holds a time (not the `'notified'` placeholder), timed from `pendingUpdateDetectedAt`; with auto-apply off nothing pauses; new starts pause only while this verifier's own holds are the only thing delaying the restart (otherwise verifies keep starting, since the restart is waiting on other work anyway); that time does not count toward `stalled`, new starts resume if it has been pending more than 120 minutes, and update-pending blackout hours are counted in the go/no-go. An in-flight verify registers with `AutoUpdater`/`UpdateGate.setRestartHoldProvider` (the provider is called each time and returns `until` = now + remaining active-work budget + remaining allowed wait-in-place, capped by the gate's `maxDeferralHours`) so an auto-update waits for it (a manual apply is not held), bounded by the verify's own timeout; a restart forced past that bound loses the run, which is re-queued.

**Post-merge verify of `main`.** Every change of `main`'s head enqueues a verify of it, debounced: it starts only once the head has been unchanged for 10 minutes, so a merge and the release commit that follows it minutes later are verified once; the debounce is capped at 30 minutes from the first unverified head, so a steady stream of merges cannot keep resetting it, and so does every server boot (the index starts empty, and the merge→release→restart sequence is routine, so the compensating control must not be lost across the restart a merge triggers) (same pipeline, no merge step). A `main` verify takes priority over PR verifies and is exempt from the per-PR caps. At most one `main` entry is pending, outside the cap of 10: a newer head replaces a pending one, and a `main` run already in progress is never cancelled. A red result therefore covers every merge since the last green `main`, and the audit log lists them. A failed `main` verify is re-run once before `local-verify:main-red` is raised (a flaky failure must not page the operator; merges pause for the one re-run, in `main-suspect`). While `main` is unhealthy (`main-suspect` or `main-red`, the machine state, not whether an attention item is open) the watcher requests no PR verifies (they fail by construction); POSTed ones still run, which is how a repair gets its record. While `main` is red, most PR verifies on its merge tree fail too (a repair PR is the exception and is admitted as above); that is deliberate (Zero-Failure), and `local-verify:stalled` is suppressed while `local-verify:main-red` is open so the operator hears one cause, not two. A failing `main` verify raises ONE deduped attention item (`local-verify:main-red`). This is the compensating control for not pinning the base (§3): the verified tree and the landed tree can differ, and this catches the difference within one verify of the merge instead of at the nightly.

### 3. Merge path consumes `local-verify`

**Floor selection is one function**, used by safe-merge and the watcher: `floor = (config floor == 'local' && repo == monitoring.greenPrAutoMerge.repo && PR eligible per §2) ? 'local' : 'actions'`. Under the `local` floor, a PR admitted through `operatorApprovedHead` is refused with a named reason (`refused:approver-dependent`) when approver dependence is not covered by a matching acceptance; ordinary PRs are unaffected. It never falls back to the Actions floor. Fleet installs, the feedback executor's `--auto` path, other repos and ineligible PRs all keep today's behaviour. `--capabilities` reports `floorModes`. safe-merge learns the config floor and the record from the local server; `INSTAR_MERGE_FLOOR` exists only as a manual override for a human running safe-merge while the server is down, and can only force `actions`, never `local`. safe-merge reads the server port and token only from the agent's config file, never from the environment, so a session cannot point it at a stand-in server.

The `local` floor swaps the contexts floor **and** the three Actions waits that run before it in safe-merge today (lines ~581–613): the `gh pr checks` settle loop (`refused:checks-timeout`), the any-red-check refusal (`refused:red-checks`) and the e2e-presence refusal (`refused:e2e-missing-or-red`); otherwise every `local` merge would still wait on, or be refused by, the advisory Actions jobs. Everything else in safe-merge runs unchanged: the draft/closed/merged checks, the head pin, the ruleset review precheck with `refused:approval-required` and the one-click review link. The predicate:

```
record = server index lookup (repo, pr, head, baseRefName)        — head validated ^[0-9a-f]{40}$, pr a positive integer
accept iff record exists in the server index   (a file on disk is never consulted)
       && record.repo == repo && record.pr == N
       && record.headSha == PR head SHA (re-read from GitHub now)
       && record.baseRefName == PR base branch (re-read now)
       && record.outcome == 'success'
       && every gating lane: failed == 0 && tests > 0 && files > 0
       && merge-time checks pass now (standards-coverage, eli16, decision-audit, ux-impact, release-fragment, class-closure, runbook, trailer)
       && (!record.harnessChanging && !record.protectedPath && !record.skipsAdded && !record.testsRemoved
           || record.independentReview.concurred == true)

record.independentReview — set by the verifier from a concurring instar-dev trace in the head's tree that
         covers every flagged path (§2 "Independent review of a flagged record"); never from the PR body
```

A harness-changing or protected-path PR is therefore merged by the agent like any other once its head carries a concurring independent review. Until 2026-10-22 this check was the operator's approval of the head (`operatorApprovedHead`) plus the Decision 16 acceptance; both are removed (operator directive, 2026-10-22 08:58 PDT: “Why am I having to approve these? I should ONLY have to approve constitution changes.”). The review precheck is unchanged: where GitHub's own ruleset or CODEOWNERS requires a review (today: the constitution files only), that is GitHub's rule, safe-merge reports it as `refused:approval-required`, and the watcher waits for the code-owner review. While `main` is unhealthy (`main-suspect` or `main-red`: the machine state, not the attention item), the `local` floor admits a PR only if its green record was verified against the **current** `main` head (record `baseSha` == `main` head now): that is how a repair lands. Every other record, including older green ones, is refused (`refused:main-red`), because a red `main` means the verified trees and the landed tree have diverged. The item is closed only by a green verify of a `main` head that equals or descends from the head that went red (`git merge-base --is-ancestor`); a green result for an older head never clears a newer failure. Anything unmeasurable (server down, record absent, GitHub read fails) ⇒ `refused:verify-record-unmeasurable`; **safe-merge never falls back to the Actions floor on its own**, because that fallback is the exact behaviour this spec removes. On the lease holder, safe-merge and the watcher decide from the index, not from the status; everywhere else (a raw `gh pr merge`, a standby's safe-merge) the posted status is the authority GitHub enforces. **The base is not pinned** at merge time: a base that moved since the verify does not refuse, matching today's floor and the sibling spec's Decision 9 (the conflict-rot treadmill); the §2 post-merge `main` verify is the compensating control. Strict base pinning (merge-queue semantics) is re-evaluated once the verify wall time is measured — a named follow-up <!-- tracked: CMT-903 -->. The first follow-up <!-- tracked: CMT-903 --> to evaluate ahead of it is Bors-style batching: one verify of `main` plus several green candidates merged together, which cuts slot-hours roughly by the batch size and restores base pinning for the batch. The merge is `gh pr merge --match-head-commit <sha>` with no `--auto`; GitHub offers no way to pin the base branch at merge time, so a retarget in the moments between the predicate's re-read and the merge call is a stated residual (narrow, and visible in the audit log), not something the predicate can close; `mergeStrategy` is ignored in `local` mode.

`classifyCandidate` (`greenPrLogic.ts`) keeps its `<agentNamespace>/` filter unchanged in both floors (the shared login is not an agent identity). A verified PR outside the namespace is merged by its own session through `instar safe-merge`, exactly as today. The `instar-dev` skill text tells builders to use the namespace so the watcher can pick their PRs up (Decision 14). The watcher's candidate pre-filter in `local` mode requires a record in the index for the current head (it does not read `statusRollup`, which an unavailable Actions would hold `PENDING` forever).

**Which safe-merge runs.** Sessions and the watcher keep running safe-merge as today. A modified or buggy copy cannot merge an unverified PR, because GitHub refuses the merge without the required status (below).

**Direct pushes.** A `git push` to `main` is already refused by GitHub: the `instar-main-protection` ruleset requires a pull request (the release workflow's `RELEASE_TOKEN` is the one exception, see Enablement order).

**The required status is the merge authority GitHub enforces.** GitHub cannot run our tests, but it can refuse to merge a PR whose head lacks a named commit status. So the ruleset `instar-main-protection` gains one required status check, `instar/local-verify`, posted by the agent server (a commit status costs no Actions minutes and never queues). This replaces any merge-guard hook: a direct `gh pr merge`, a GraphQL merge, `curl` against the merge endpoint, or a modified copy of safe-merge from any session, any framework, any worktree, any machine all hit the same GitHub refusal, because the check lives on GitHub, not in the session's tools.

What the server posts on a PR's head:
- **Local floor, eligible PR:** `success` only when the whole §3 authorization holds except the merge-time body checks: a green record for this (repo, pr, head, baseRefName); not harness-changing, protected-path, skips-added or tests-removed, or a record carrying a concurring `independentReview`; `main` healthy, or the record was verified against the current `main` head. Otherwise `pending` (verifying or waiting) or `failure`.
- **Actions floor, or an ineligible PR (fork, other login):** a mirror. The server posts `success` when the Actions floor contexts are green on that head, decided by the same function safe-merge uses (`evaluateRequiredContexts`, with its producer and workflow pins), over one shared floor constant: `REQUIRED_CONTEXTS_FLOOR` extended with the 12 classic-protection contexts pinned in code (used by both the mirror and safe-merge's own Actions floor, so neither loses the unit shards) (read from `GET /branches/main` today; the unit shards have only ever been required through classic protection, so without the pin a fork would merge without unit tests), **excluding `instar/local-verify` itself** (or the mirror could never bootstrap); there is no second implementation; `pending` while they run, `failure` if one fails. This is what keeps forks, outside contributors and the rollback working with the check in place. The mirror reuses the green-PR watcher's existing floor-drift canary, so a renamed context is caught at runtime, and a mirror left at `pending` for more than 6 hours raises one deduped attention item.
- **Shared heads:** a status belongs to a commit, not to a PR. When several open PRs share a head SHA, the server posts `success` only if every one of them is authorized.
- **Posting discipline.** A status is posted only when the projected state for a head differs from the state GitHub reports for `instar/local-verify` on that head (read on every pass from the discovery listing's `statusCheckRollup`; if the context is missing and the rollup may be truncated, the combined-status API is read before posting, and a truncated read is never treated as "absent"), in either direction; a per-head last-posted cache only suppresses posts where GitHub already agrees, so a late write from a former holder, or a status a session posted by hand, is overwritten within one pass; after a restart or lease move the cache is rebuilt by reading GitHub's combined status, never by blind re-posting (GitHub keeps at most 1000 statuses per commit per context, and a head re-posted every tick would hit that within a week, after which a withdrawal would fail silently). A failed post (422, 403 secondary rate limit) is retried with backoff and shown on `/guards`. Every post re-checks `holdsLease()` and the lease epoch at the moment of posting, and the audit log (not the status description) records which machine and epoch posted; on losing the lease, the in-flight verify is cancelled through the `MergeRunner` protocol and nothing is posted. A post already in flight when the lease moves cannot be recalled; the posting discipline above overwrites it on the next pass, so a late write from the old holder lasts at most about 120 seconds (stated residual, with an interleaving integration test).
- **Discovery.** The loop lists open PRs with no author filter (`--base main`, paginated past 100), separate from the watcher's `--author @me` list; if the listing fails, nothing is posted, and a missing status already refuses. Statuses are posted only for PRs whose base is `main`. For ineligible PRs the list call's `statusCheckRollup` decides when a fresh per-head check-run read is needed.
- **One writer per head.** The reconcile loop, the event-driven withdrawal and the verify-completion path all post through a single serialized per-head queue: the state is re-projected immediately before each send, the post is awaited, and only then is the cache updated, so a `success` computed before a withdrawal can never land after it.
- **Status reconcile loop (separate from the watcher).** A dedicated loop on the lease holder runs every 60 seconds and is not gated by the watcher's breaker, warm-up, rollback latch or pool pause. Each pass lists every open PR targeting `main` and: posts `pending` on any head whose `instar/local-verify` is `success` but whose projection for its floor is not `success` (for local-floor heads, the §3 authorization: no record, a condition no longer holding, or a record failing main-health admission; for mirror heads, the Actions-context mirror); enqueues a `main` verify whenever the remote `main` head differs from the last enqueued or verified head (so merges by a standby, the operator, a raw merge or a release push are covered, and the `main-unverified` age is measured from that head); and posts or refreshes the Actions-floor mirror. It also runs immediately at server boot and on lease acquisition, before anything else. Lease acquisition by a **different** machine starts with an empty index (journals are machine-local) and in `main-suspect`, and runs the sweep. A boot, or re-acquisition by the **same** machine at a new epoch, keeps its journal-backed index and the normal admission rules when `main-health.json` is readable and healthy; only a missing or unreadable file, or a different machine, enters `main-suspect`. Either way it runs the sweep.
- **Stuck-status canary.** If an eligible head with a green, admissible record has a posted status that differs from its projection for more than 15 minutes (posting broken, rate-limited, or a bug between the loop, the restart hold and the main-health state), ONE deduped item is raised (`local-verify:status-stuck`). This fails loud in the direction that matters, because safe-merge never falls back.
- **Event-driven withdrawal.** Entering `main-suspect` or `main-red` writes the watermark and then synchronously posts `pending` on every `success` head that the repair rule no longer admits, without waiting for the loop. The remaining window (between a condition changing and the next pass, at most about 60 seconds; or the whole time the server is down) is a stated residual.
- **What `success` requires, in full:** the PR targets `main`; every open PR to `main` sharing that head is authorized; a green record for (repo, pr, head, baseRefName); not harness-changing, protected-path, skips-added or tests-removed unless the record carries a concurring `independentReview` of exactly that head; `main` healthy or the record verified against the current `main` head. No operator approval and no approver-dependence acceptance is part of it (amended 2026-10-22); ordinary PRs need no independent review. Under the 80/20 bar, the standby path (Decision 17) and the shared-head rule are the first pieces to cut if the build proves heavier than measured.
- **Withdrawal:** when a condition stops holding (head moved, PR retargeted, `main` turns unhealthy, an approval or acceptance is withdrawn), the reconcile loop or the event-driven path above re-posts `pending`. A status is a projection of server state; the server is its only writer.

`fetchProtectionContexts` is fixed to read `GET /branches/<b>` (`protection.required_status_checks`, readable by a non-admin) and to stop treating a 404 from `/protection` as "no protection" (with a test); review requirements then come only from the ruleset review policy (`fetchRulesetReviewPolicy`), also with a test; the classic `reviewsRequired` branch reads `/protection` when it is readable (an admin token) and is false otherwise, which is what it effectively is today, since the 404 already hid it. safe-merge reads `instar/local-verify` through the combined-status API, never among check-runs, under both floors: today `evaluateRequiredContexts` looks for every required context among check-runs only, so once the check is required it would refuse every Actions-floor merge (rollback, forks, the feedback executor's `--auto` path). Under the `local` floor the check-run union is not consulted apart from that status. safe-merge in `local` mode keeps the §3 predicate (it also runs the merge-time body checks, which a raw `gh pr merge` skips; those workflows still run but block nothing, as today: an accepted residual). The watcher merges as today. No new CLI subcommand, shim, hook or per-home arming is needed.

Stated limits: once posted, `success` is the authority GitHub enforces for direct merges (and what a standby's safe-merge reads, Decision 17); the server's in-memory index decides only whether to post or withdraw it. The head's code cannot change under a status, but the conditions around it can: a retarget, or `main` turning unhealthy while the server is down, leaves a stale `success` usable until the server is back and withdraws it (within one reconcile pass, about 60 seconds, when it is up; at once on `main-suspect`/`main-red`). Body and diff gates (eli16, decision-audit and the others) are enforced by safe-merge and the watcher, not by the required check, so a raw `gh pr merge` skips them, as it does today. A same-repo PR's own workflow can also post the status with its `GITHUB_TOKEN` (`statuses: write`); the reconcile loop bounds that the same way, and any `instar/local-verify` status whose creator is not the agent's login is logged as `foreign-status` in the audit. The status is posted with the shared `gh` login, so a session that deliberately posts `success` itself could forge it (deliberate tampering, outside the threat model; the reconcile loop overwrites any status the server did not decide within about 60 seconds, so a forgery is a bounded race rather than a lasting authorization, and the audit log shows every status the server posted). If the agent server is down, no new status is posted, so unverified PRs wait; a `success` already posted stays mergeable until the server is back and reconciles (§3 status reconcile loop). The operator's emergency lever, after Decision 19, is an ordered pair: re-add the classic required checks first, then remove `instar/local-verify` from the ruleset, so `main` is never left with no required check. While the check is required and the server is down, no merge can satisfy it (the manual `INSTAR_MERGE_FLOOR=actions` override cannot post the status); that is the case the emergency pair exists for.

Enablement order: the server starts posting `instar/local-verify` on every open PR (mirror mode) **before** the check is made required, so no open PR is stranded. Four release workflows (`publish.yml`, `publish-witness.yml`, `publish-threadline-mcp.yml`, `publish-threadline-core.yml`) push to `main` with `RELEASE_TOKEN`, which already gets past the ruleset's `pull_request` rule, so its user is a bypass actor of `instar-main-protection`; a bypass actor skips every rule in that ruleset, so the check goes into that same ruleset (not a new one) and the release pushes keep working. The first run of each after enablement is watched; if one fails, the emergency lever (remove the check) applies. Making the check required is a ruleset change only the operator can make (the agent's login is not an admin); the approval message carries the direct settings link.

### 4. GitHub workflows become advisory (separate PR, later)

Not part of this run. After the `local` floor has merged PRs live for 7 days, a separate `.github/**` PR (a protected-path PR, admitted with an independent review like any other; amended 2026-10-22) restricts the `pull_request` unit/integration/e2e jobs to **ineligible** PRs (fork heads or authors other than the agent's login, i.e. exactly the PRs that stay on the Actions floor, so their head-bound checks still exist), runs them nightly on `main` (Node 20 and 22) for everything, keeps Type Check and Build on every `pull_request` as advisory, and keeps the full shard matrix (Node 20 and 22) on those ineligible-PR runs, so every context the mirror pins still has a producer; the pinned set and the workflow are changed together in that PR, with a test of a fork merge and of the rollback against the resulting job list. Until it lands, CI keeps running on PRs exactly as today, so the rollback below restores today's behaviour completely. The §4 PR also keeps `workflow_dispatch` on those jobs, so after §4 the manual `INSTAR_MERGE_FLOOR=actions` override still works: the operator (or a session) dispatches the jobs for the PR's head and the Actions floor can be satisfied.

**Nightly results have a consumer.** Whatever runs nightly on GitHub (Node 20/22, Linux, contract tests) reports into the same machinery: a red nightly on `main` raises ONE deduped attention item naming the failing job; it does not freeze merges (it is advisory coverage, not the gate), and it is re-run once before the item is raised.

**The floor follows what GitHub actually enforces.** On every reconcile pass the server reads the two non-admin endpoints (`GET /rules/branches/main` and `GET /branches/main`). The `local` floor takes effect only when the ruleset requires `instar/local-verify` (no `integration_id`, strict off) **and** classic protection has no required contexts; until then the watcher and safe-merge stay on `actions`, and `/guards` shows `awaiting-edit-a` or `awaiting-edit-b`, so the operator's two edits can land in any order of time without breaking merges. If neither endpoint requires any status check, ONE HIGH item is raised at once. The agent's own `current_user_can_bypass` (readable on `GET /rulesets/15247386`, even though the bypass list is not) must be `never` before enabling and is checked every pass afterwards.

**Settings are pool-wide.** `monitoring.greenPrAutoMerge.floor` and `monitoring.localVerify.enabled` are changed on every machine in the pool through the existing pool-wide config path, and the change is acknowledged per machine. On lease acquisition the new holder compares its floor with the floor the previous holder last posted under (recorded in the audit log); while they differ it posts nothing new and raises one item, so a takeover can never silently flip the merge authority back to Actions.

### Rollback

`monitoring.greenPrAutoMerge.floor: 'actions'`, read live by the watcher and served to safe-merge. Once the check is required, the Actions-floor mirror is what lets any PR merge, so the mirror projection stays on whenever the check is required (read from `GET /repos/{owner}/{repo}/rules/branches/main`, readable without admin rights; if it cannot be read, the check is treated as required and the mirror stays on), independent of `monitoring.localVerify.enabled` (turning the verifier off never stops the mirror, and the config-change response says so). Full restoration of today's behaviour is therefore `floor: actions` with the server up, or the operator removing the required check from the ruleset. The flip is the agent-side rollback: `local` mode arms nothing, so there is nothing to disarm; on the `actions` → `local` transition the watcher calls the existing `disarmAllArmed()` once, automatically, so no PR armed under the old floor waits on GitHub; it never uses the pool-wide rollback latch (which is PIN-gated to re-enable). The test-lane change is rolled back independently of the floor: `INSTAR_TEST_WORKERS=1` restores one-at-a-time runs everywhere immediately, and reverting the lane PR restores the old configs. After the §4 workflow PR has landed, rolling back the floor also requires reverting that PR; the spec and the config-change response both say so.

## Verify the state, not its symbol

- **Symbol:** `instar/local-verify = success`. **State:** the suite passed on the merge tree of this head. **Corroboration:** on the lease holder, the server-index record, field by field against the live PR at merge time (the status is not consulted there); elsewhere the posted status is the authority, which is why it is withdrawn whenever the index no longer supports it. **Unmeasurable:** no index entry ⇒ refuse.
- **Symbol:** per-lane counts. **State:** the tests ran. **Corroboration:** the orchestrator's own inventory must equal the union of lane reports. **Unmeasurable:** a lane without a report ⇒ failure.
- **Symbol:** a green verify. **State (claimed):** the *landed* tree passes. **Honest gap:** the verified tree is head-on-base-at-verify-time, not the landed tree. **Corroboration:** the post-merge `main` verify. **Unmeasurable (verify of main errors):** one attention item, never silence.
- **Limit (stated in the threat model):** the run reports its own outcome.

## Self-heal before notify

The verifier is a job, not a monitor; a failed verify of a PR raises no notice (the PR status carries it, and the author's session watches the PR). Degradations: (a) verifier crash / timeout — `recoverable`; self-heal: re-request once per head (dedupe-key head SHA, max-attempts 2, backoff next tick, then status `error`); audit `logs/local-verify.jsonl`. (b) Queue stalled (the queue is non-empty and no lane or step has started or finished in 60 min, slot waits and update-pending time excluded, or the verifier is disabled while `floor: local`; a long backlog of verifies running one after another is not a stall) — `recoverable`; after the same re-request, ONE deduped attention item (`local-verify:stalled`), max-notification-latency `60m`; `GET /local-verify` shows depth, oldest wait and cancel counts; `/guards` carries a row (`on-confirmed` from the last successful verify). (c) `main` verify failed — only `outcome: failure` counts as red; an `error` (registry outage, deadline) re-queues with backoff, at most 3 times per `main` head. Independently of job activity, the server tracks the age of the oldest merge without a green `main` verify after it; if that age passes 3 hours (errors keep repeating, or nothing ran), `main` enters `main-suspect` (repair-only admission) and ONE item (`local-verify:main-unverified`) is raised. Machine state and notice are separate: on the first failure `main` is marked unhealthy at once (an internal `main-suspect` state that refuses as `refused:main-red` but raises no notice; a passing re-run clears it and is logged as a flake), and from that moment the §3 main-red admission rule applies (only repairs verified against the current `main` head can merge); the failed `main` verify is re-run once, and only if the re-run also fails is ONE deduped item (`local-verify:main-red`) raised; its text names the `floor: 'actions'` rollback for a red caused by the environment rather than the code. The boot-time `main` verify skips the 10-minute debounce. Health is cleared only by a green verify of a `main` head equal to or descending from the head that failed. The failed-head watermark is written durably to `state/local-verify/main-health.json` and read at boot, so a restart cannot lift a freeze; it is a restriction, so the file can only make admission stricter, and a missing or unreadable file at boot is treated as `main-suspect` until the boot-time `main` verify comes back green. After a lease move the new holder starts in `main-suspect` for the same reason. This is the self-heal-first order with the merge freeze applied immediately, because a red `main` is already the harm. (d) Orphaned verifier process after restart — healed at boot from `inflight.json`, audited, no notice. Nothing here deletes durable state outside its own worktrees, clones and records.

## Throughput budget

Removing the GitHub wait will likely raise the merge rate. At 12 or more merges a day sustained over a week, Bors-style batching stops being an optional follow-up <!-- tracked: CMT-903 --> and becomes required before more load is added.

Flaky tests: today's CI unit shards run the flaky-excluded `test:push` config, and the verifier never uses that exclusion list, so every quarantined flaky test re-enters the gate. Before the floor flips, each file on that list is either fixed, moved to a named `known-flaky` lane, or deleted with a reason. The `known-flaky` lane is a fourth lane in the inventory (each of its files appears in exactly one lane, as for the others), runs at 1 worker, and is reported per file in the record and status description but is an **advisory** lane: the record marks each lane `gating` or `advisory`, the inventory rule and the §3 predicate's `failed == 0` apply to gating lanes only, and a fixture test covers a run where only the advisory lane fails (outcome `success`, failures listed); moving a file into it is harness-changing (routed to the operator). The go/no-go also counts how often a `main` verify failed and then passed on its re-run (a flake) over the qualifying period.

**Flaky files: evidence per run, not a static list (built 2026-10-22).** The first two server-run `main` verifies each failed exactly one file that passes alone (3/3) and passed in every PR verify that day; since `main` moves often, each new head's first failure re-entered `main-suspect`, so one flake per run kept `main` suspect indefinitely and stopped PR verifies. The `known-flaky` lane above is therefore implemented as a per-run isolation re-run instead of a hand-kept list: after a lane, if its only problem is 1–3 failed files (`LOCAL_VERIFY_LIMITS.isolationRerunMaxFiles`; no file-not-run, no zero-collected file, no deadline; a dirty tree still fails separately), exactly those files are re-run once, one at a time, with the lane's own config, env and flags, under what is left of the lane budget; the cap of 3 covers the whole verify. A real, order-dependent failure must not pass as a flake, so on a PR verify a failed file is never re-run (it is a real failure) when the PR changed it, when it imports a file the PR changed (static relative-import scan, the same graph helper the verifier version uses), when this machine holds no green `main` record, or when that record shows the file did not pass cleanly there (it was itself re-run-passed); `main` verifies keep the plain rule. An unhandled error is never hidden: a trusted reporter (loaded from the installed server) records each lane's and each re-run's unhandled-error count, vitest's own JSON report carrying none; a lane with any unhandled error, or an unknown count, is not re-run, and the lane's original exit code is cleared only when its failed files all passed alone with zero unhandled errors. Each re-run gets a fresh `TMPDIR` and `TMUX_TMPDIR`. A file that passes is recorded in `record.flakyRetried` (`{file, lane, firstMessage}`) and the lane counts as passing, so the outcome stays `success`; a file that fails again is a real failure carrying both messages; more than 3 failed files is a real break and nothing re-runs; a re-run that hits the lane deadline counts as failing again. Each flaky file raises ONE deduped attention item (`local-verify:flaky:<file>`) so it becomes a tracked fix, re-raised as a new episode with the count when the same file is re-run-passed 3 or more times within 7 days (at most once per 7-day window), and `GET /local-verify/status` reports `flakyFiles` (file → count, last seen). Main health is unchanged: it only ever sees a failure that survived the isolation re-run, so a pure flake no longer moves it. Main verifies emit the same bounded `run-detail` audit line as PR verifies (reasons, failures with both messages, flaky re-runs), and `local-verify:main-red` carries it.

**Fair share between `main` and PR verifies (built 2026-10-22).** With one slot, ~1 `main` head per hour (every merge and every release) and ~45-minute verifies, "`main` always first" can spend the whole slot on `main` while PRs wait. The start decision (`decideStart` with `fairShare`, driven by the self-action convergence model `local-verify-main-fair-share`) is: while `main` is healthy, a `main` verify starts ahead of waiting PR verifies once its oldest unverified merge is 90 minutes old (`MAIN_FAIR_SHARE_MS`), otherwise PRs go first, so a healthy `main` never nears the 3-hour unverified alarm just by waiting (90 min + one PR verify + its own verify); with no PR waiting, `main` starts at once. While `main` is suspect or red, `main` keeps priority (the repair path), but at most every other start is a `main` verify while PRs wait. Release commits (`chore: release v… [skip ci]`) never trigger a `main` verify on their own when their single parent is a head this machine holds a `main` record for (or has queued or running) AND their diff against that parent touches only `package-lock.json`, `pnpm-lock.yaml`, `CHANGELOG*`, `upgrades/**` and a root or workspace `package.json` whose patch changes nothing but its `"version"` line (a missing patch is not release-only) (GitHub's commit file list; a list of 300 or more may be truncated and is treated as unknown): a merge and its release collapse into the merge's verify (audit `main-release-collapsed`). Anything else — another file, an unknown file list, a parent with no record here (a force-pushed `main`) — is verified as usual.

**Main-red hold: no doomed PR verifies while `main` fails a known check (built 2026-10-26, CMT-1033).** A PR verify tests the PR's merge with `main`, so while `main` fails a check, every PR that does not fix it fails the same check by construction (2026-10-26: eight 18-minute runs after `main` went red on `tests/unit/no-silent-fallbacks.test.ts`, and three sessions wrote the same fix). The service keeps the failing files of the last failed `main` verify (from its run-detail; `state/local-verify/main-failure.json`, read at boot, removed on green). While the health state is unhealthy WITH a failed head (`main-suspect` after a first failure, or `main-red`) AND those files are known for that head, start admission (`decideMainRedHold`, pure) lets only a `main` verify or a **repair candidate** take the slot: a PR whose diff touches a failing file, or whose title or body names it (its path, file name, or stem such as `no-silent-fallbacks` — both real repairs on 2026-10-26 touched `src/` files and named the check in their text; a rule on the diff alone would have held them). Every other PR entry keeps its place and its `firstQueuedAt` and waits for green; a candidate runs ahead of PRs queued before it; a candidate is admitted past the queue cap while the hold is active (bounded: held entries never exceed the cap). The hold only orders and delays verifies; the §3 merge predicate and safe-merge are unchanged, and a candidate still has to pass its full verify. It is inactive — today's order — when the failure named no file, when the state is an unknown-state suspect (boot, lease move, unverified-too-long), or when the kept files are for another head; a PR whose file list could not be read is held unless its text names the check (the restrictive direction, said in the reason). `GET /local-verify` carries `mainRedHold` (`state`, `redHead`, `failingFiles`, `repairPrs` — the running candidate, then queued candidates, then candidates seen earlier in the episode such as one already verified and waiting to merge — `heldPrs`, a plain `detail`) and each held entry carries `held`; a `POST /local-verify` answer for a held PR carries the same `hold`, which safe-merge prints in its `verify-pending` line; the `already-queued` path re-reads the PR view, so renaming a held PR to name the check makes it a candidate in place. Once `main` is RED (never on the first failure, which raises no notice), ONE deduped attention item for the red episode (`local-verify:main-red-hold`) names the failing check, every PR already fixing it and the count of held PRs, so a second session does not write the same fix; it is re-raised under the same id (the attention row's body refreshes) only when the red head or the sorted list of fixing PRs changes, and closed through the new `clearSignal` seam when `main` is green (a newer red head refreshes the same row; the id is stable, so a restart cannot strand it open); `local-verify:main-red`'s detail carries the same split. Green clears the episode (files, audited holds, the hold item) and `pump()` releases the held PRs in queue order. Kill switch, read live: `monitoring.localVerify.mainRedHold: false`. Spec supervision: tier0. Machine-local like the queue it gates.

**Merge-throughput label: work that speeds up merging verifies first (built 2026-10-26, operator request).** Queue priority had two levels, 100 for the `main` health verify and 0 for every PR. A PR carrying the GitHub label `merge-throughput` now gets priority 10 (`prPriority`, read from the PR view's `labels` at every request, so adding or removing the label and asking again re-ranks the entry in place, and a restored entry re-reads it at boot). The order is `main` verify, then labelled PRs, then ordinary PRs, FIFO within a level. While the main-red hold is active only repair candidates may start at all, so a labelled PR never runs ahead of the PR fixing a red `main` unless it is itself such a repair. Bound: the queue is sorted by `effectivePriority`, which ranks an ordinary PR at the labelled level once it has waited `THROUGHPUT_AGING_MS` (90 min, update pauses excluded; half of `starvedAfterMs`), so a labelled PR queued after it can never pass it; the 3-hour `local-verify:starved` alarm is unchanged. The label only orders verifies; it changes no merge decision. Not part of the policy hash (records stay valid).

**A labelled PR is admitted past a full queue (built 2026-10-27, operator request: merge throughput).** The label above only orders entries already in the queue, and the queue was full (10) for most of 2026-10-26, so two labelled PRs answered `queue-full` for hours and their priority never applied. Now a `merge-throughput` PR is admitted past `queueCap` while the PR queue is shorter than `queueCap + LOCAL_VERIFY_LIMITS.throughputOverflow` (5), audited `queue-full-throughput-admitted`; an ordinary PR is still refused at `queueCap`. A restore at boot brings back every durably queued entry up to that bound plus one (the run the restart interrupted, put back at the head), so restoring the labelled overflow first never drops ordinary entries that were queued below the cap. A pushed head re-queued in its kept place replaces an already-admitted entry and is never refused for capacity (it would otherwise lose its place while the overflow is in use). A repair candidate keeps its own admission and audit (`queue-full-repair-admitted`) even when it is also labelled; a labelled non-repair admitted through the overflow is still held by the main-red hold like any other PR. The re-run-after-green pass still skips at the ordinary cap before calling `request()` (a refused request would mark the new base as tried and spend the PR's one re-run). The label only orders and admits verifies; it changes no merge decision.
**Fail-fast lanes and flaky-on-`main` re-runs (built 2026-10-27, operator request: merge throughput).** Measured over the 121 verifies of 2026-10-20..26 (journal + run logs on the Studio): median wall 18.5 min, 47 not `success` (32 failure, 15 error; every error ended before the lanes, so errors cost no lane time). Of the 48 failed runs, about 15 failed only on `tests/unit/no-silent-fallbacks.test.ts` during one red-`main` episode (the main-red hold above now holds those), and about 15 failed on a file the isolation re-run refused because the last green `main` record showed it re-run-passed there (`subscription-relogin-*`, `messaging-multi-agent`), so a file already flaky on `main` failed every PR that hit its flake. Two changes, both PR verifies only:
(1) **Fail-fast.** The three lanes run at once, so a run whose unit lane fails at ~7 min kept integration and e2e running to ~18 min for a verdict that was already `failure`. Now, once one lane ends with a failure its isolation re-run did not clear (a failed file, a missing report, or a non-zero exit), the lanes still running are stopped through the exec seam's abort signal (an aborted process is never reported as a deadline, which is an infrastructure `error`). A stop, like a deadline, now sends SIGTERM and then, after the grace period, SIGKILL to the process AND every descendant found in a `ps` snapshot taken before the parent is signalled (vitest workers and test subprocesses would otherwise survive it and hold its pipes open); the SIGKILL escalation (sent only to a pid whose start second and command are unchanged since that snapshot, so a pid the system reused in the grace period is not signalled unless the replacement matches both, which sequential pid allocation makes implausible) still fires when the parent settles first (a descendant with its own stdio may have ignored SIGTERM); and after a stop, once the process itself has exited, the wait for its pipes to close is bounded at 5 s, so a surviving descendant can never keep a lane, the suite slot or the cleanup waiting. A step that exits on its own is waited for as before; anything it leaves running is still removed by the service's process-group sweep when the run ends. A stopped lane is reported as `lane-stopped-early:<lane>`, appended after every real reason so the record's `failureReason` is always the real failure; its files are not `file-not-run`; and a stopped lane can never by itself produce a failure (`lane-stopped-without-failure` would name that impossible case). An isolation re-run still in flight when the run stops ends as `stopped` and counts as failing (the verdict is already failure). The outcome of a run is unchanged in every case: a run that would have succeeded never stops early, because only a lane that will fail the run triggers the stop. Cost: the author sees the failing lane's failures and not those of lanes that were stopped; the next verify shows them. A `main` verify always runs every lane, because the main-red hold needs its complete list of failing files. Live switch `monitoring.localVerify.failFast` (absent ⇒ on, read at each start; an unreadable switch reads as off, which is today's behaviour), passed to the child as `VerifyRunInput.failFast`.
(2) **A file flaky on `main` gets its one re-run.** The isolation re-run rule no longer refuses a file because the last green `main` record shows it re-run-passed. The rule that protects against a real failure passing as a flake is unchanged: on a PR verify a failed file is still never re-run when the PR changed it or a file it imports, or when this machine holds no green `main` record; the cap of 3 re-runs per verify, the unhandled-error rule and the per-file `local-verify:flaky:<file>` attention item (re-raised at 3 re-run passes in 7 days) still apply, so the flake stays a tracked fix. The residual risk (a PR that breaks a file by a path the static import scan cannot see, and whose failure then passes alone) is the one the re-run already accepts for every other file the PR does not touch; refusing the re-run only for files known to flake added no protection against that and converted each of their flakes into a PR failure. Each such re-run logs `isolation-rerun-flaky-on-main`.
Neither change touches the policy hash (records stay valid), the §3 merge predicate, or safe-merge.

**Balanced shards (built 2026-10-27, operator request: merge throughput).** The lanes run at once, so a verify lasts as long as its slowest process. Step medians over 2026-10-20..26: unit 7.3 min, integration 15.7 (one process), e2e shard 1 9.3 and shard 2 16.8 — vitest's `--shard=k/n` splits by file count, so the shard holding the slow files set every run's length. Two changes: the integration lane runs as `LOCAL_VERIFY_LIMITS.integrationShards` = 2 processes and the e2e lane as `e2eShards` = 3, each process still at one worker with its own `TMPDIR` and tmux server (so the in-process port-reuse race the single integration worker avoids cannot cross processes); and each shard of a lane is given an explicit file list (`shardPlan.planShards`), longest file first onto the shard with the least work so far, from the per-file wall times of earlier runs on this machine (vitest's `startTime`/`endTime` per file, kept in `<verifyRoot>/file-durations.json`, blended 50/50 with each new run, bounded at 20,000 files; an unknown file counts as the median). When fewer than half of a lane's files have a history (first run, a large new test tree), or the plan would leave a shard empty, the lane falls back to `--shard=k/n` and logs `shard-plan` with `balanced: false`. vitest's positional filters match by case-insensitive substring, so files where one path contains another are planned as one unit onto the same shard (`filterOverlapGroups`); a file can therefore never run in two shards because of the plan. The history file lives where the lanes' test code (same user) can write, so it is read only below 2 MB (`durations-ignored` otherwise) and only ever moves files between shards. The counts are a live setting, `monitoring.localVerify.laneShards` (`{integration, e2e}`, each 1..4, read at each start, invalid values ignored), so the old split (`{"integration": 1, "e2e": 2}`) is one config edit away if the extra processes slow the host. The durations decide only which process runs a file, never whether it runs: the plan assigns every lane file exactly once, and the existing join rules still apply (a file reported by two shards makes the lane report missing; a file in no report is `file-not-run`), so a wrong or stale history can only make a run slower. Worker total: 4 + 2 + 3 = 9, against the 7 before and the 8 the unit lane used alone before the lanes went parallel. The build step regenerates the shared generated assets (`dist`, the standards-registry asset) before any lane starts, so the extra processes' `globalSetup` finds them fresh and writes nothing. `integrationShards` joins `e2eShards` in the policy hash, so records written before this change are re-verified on next use.


At ~45 minutes per verify on one slot: about 7 PR merges a day plus at most one coalesced `main` verify per merge burst is roughly 8–11 slot-hours a day, before re-verifies after pushes and restarts, and the slot is shared with builders' own full suites. That fits in a day but leaves little headroom. Go/no-go for the floor flip: the measured daily slot-hours (PR verifies, `main` verifies, and re-verifies after pushes and restarts, the last estimated as merges per day × green candidates waiting × verify time; plus lease acquisitions per day and hours spent in `main-suspect` after restarts, counted as their own line, each of which pauses merges for at least one `main` verify) over the 10 qualifying verifies must stay under 16 hours a day, and the open-to-merge latency for eligible PRs over the same period must have a median at or under today's 2.7 hours; above that, the flip waits for the two isolation follow-ups <!-- tracked: CMT-903 --> or a second verifying machine. In practice the post-merge `main` verify, not the PR verify, is the real integration gate; that is intended.
