# Local feature outcome plans and genuine baseline capture

## Problem statement

The reviewed move floor needs real baseline observations before a feature starts. D7's ladder synthesis skips dark features, and its all-operational-metrics contract includes run counts that cannot provide meaningful pre-intervention quality evidence. A shipped registry must not embed one agent machine's baseline as every agent's proof. An API caller also cannot currently obtain a corroborated generic baseline without directly writing a ledger. Close this producer/authoring seam before implementing the move floor.

## Existing owners and chosen design

Keep the ladder as the sole owner of operational thresholds, current rung, soak and managed moves. Use a distinct existing InitiativeTracker initiative for the feature's outcome/quality plan, evaluated by the existing generic D7 path and retained in the same observation/evaluation/archive owners. Its id must not equal a ladder subject or overwrite a rollout/accounting initiative. ParentProjectId remains the only effort/component graph. This is an explicit outcome measurement of the exact feature, not borrowing a parent or arbitrary component result.

Add feature to the closed generic MeasurementSubject target kinds, with subject.key equal to the exact ladder entry id. Feature contracts additionally require a closed ladder binding containing local origin, exact ladder subject, target rung and shipped operational policy hash. The hash is computed from the boot-loaded target rung's operational contract; it excludes any embedded machine baseline. Include this binding in measurementSourceRef identity and the full archived contract hash. A rung/policy/origin change cannot recycle a flattering previous series.

The independent collector resolves current ladder entries plus initiative declarations, retaining malformed owners before validation. Distinguish operational-owner and outcome-plan roles in coverage: the ordinary ladder subject and its separate measurement initiative are not duplicate owners of the same role. Exactly one active exact-matching outcome plan can qualify a managed move. Multiple matching plans are ambiguous. Stale-policy, inactive and foreign-origin plans remain visible with explicit reasons but cannot authorize. Feature census totals do not double when a plan is attached; generic evaluation counts remain separate from the legacy operational feature denominator.

This choice is narrower in authority, not necessarily in code, than a capture-only ladder path. It explicitly adds a feature target, a producer mapping adapter, closed binding/hash handling and role-aware resolution. The gain is independent outcome ownership/history and honest pre-start metrics without changing the operational ladder evaluation. It does not claim those additions already exist.

## Registered producer mapping

The current generic source refs are measurement.<hash>, while ladder refs use ladder.<hash>; they cannot be borrowed by string coincidence. Add a closed registered-projections adapter that maps each authored outcome metric id to a named existing producer ref and expected descriptor version. Extend the existing D7 projection map's registration metadata with exact target/ladder scope and descriptor identity; no new persistent producer registry. A feature plan may read only registrations whose feature/subject/rung/policy scope matches its full binding. Legacy unscoped callbacks do not supply feature proof. A shared producer ref may retain multiple exact scopes that the registry actually declares; registration must not let the last feature silently steal a shared callback from another. A caller cannot supply a callback, path, SQL, values, samples, timestamps or grades.

The existing ladder reader already registers projections for all rungs, including dark ones. Expose a scoped reading operation using its existing readInto machinery for only the requested registered descriptors. Do not invoke the full refresh path: refresh also records rung-observed rows and updates watch state. Baseline capture must not reset soak, open commitments, observe a move, activate a feature or run a drill. JSONL, feature metrics and guard readers retain existing file/window/batch limits. At most16metrics and one local owner-census walk are admitted per explicit capture. Population/window metadata comes from the registered descriptor, not a caller label. Capture time is the time of an aggregate snapshot, not proof of new underlying events; expose known sample recency or explicit unknown separately and never freshen a cached source merely by restamping it.

Outcome and quality metric roles must be distinct, cover the authored outcome plan and retain their real sample/window/population semantics. Operational run-count or soak metrics stay in the ladder; they are not presented as a pre-intervention baseline. A registered source returning null, zero samples, incompatible descriptors or no actual population yields baseline-method-unavailable/insufficient-evidence, never a fabricated zero. A meaningful control population or separately authorized drill is necessary when the feature itself has never run. This increment grants no permission to create that population through activation.

## Explicit capture and authoring

Add one authenticated baseline-capture action gated by the existing initiative/measurement owner and its authorization policy on an existing initiative. Input contains the initiative id, expected initiative revision, expected current contract hash (null for initial capture), expected executing origin, an authored method/template with exact producer identifiers/versions and an explicit initial/rebaseline intent. The template contains outcome/owner/method/version, success criteria and quality roles but no caller baseline points or raw observations. Reuse the generic closed schema by separating definition/template validation from baseline-point validation; do not validate with fake temporary baseline numbers.

Resolve the exact current target and producers; read genuine source snapshots. After asynchronous reads, re-resolve initiative revision, origin, required owner sources, target rung/policy and producer descriptor identities before any write. A changed or unavailable owner/policy refuses. Then derive the existing full MaturationEvaluationContract from server-observed values, sample counts, descriptor versions and capture time. Preserve source population/window metadata in the descriptor/adapter. Validate the complete contract with the normal generic parser.

Use the existing ledger to write at most16actual observations, archive at most one exact contract and pin only corroborated actual rows, then persist the contract through InitiativeTracker's existing writer. The process creates no ready evaluation, config mutation, activation, move or soak reset. Normal D7 cadence later evaluates the admitted generic plan. Archive capacity/read/write failure or partial publication is unavailable, never a successful baseline or permission. Genuine orphan observations may remain history after a failed initiative write; no destructive compensation or invented rollback is needed. Recheck persisted binding/hash and exact rows before returning success.

Initial capture refuses if a baseline contract already exists. Rebaseline requires the exact expected old hash and an explicitly new method/baseline version; it preserves the old archive/history and cannot silently replace the original baseline to hide regression. Retrying after a completed but ambiguously delivered capture must return the already-persisted matching version or a conflict, never reset it. One bounded capture per explicit request, no automatic retry loop. Existing transport/request bounds and operational serving-cache retention/capacity apply; retained knowledge follows the non-deleting policy below. No new recurring job.

## Decision points touched

1. **invariant:** capture accepts only closed typed identifiers/templates and exact registered scope; raw values/grades/time are server-derived. Unavailable/changed/ambiguous owners refuse publication. This is data/ownership integrity, not semantic improvement judgment.
2. **invariant:** exact content-hash/member confirmation is a factual completion condition within the approved sharing policy; no queue/cursor substitutes, membership removal or foreign-origin permission is inferred.
3. **invariant:** the baseline authoring operation is non-activating, bounded and cannot create ready evaluations or silently replace an existing version. Actual numerical proof remains with the same ledger/archive.
4. **judgment-candidate:** choosing a meaningful outcome/control population and deciding whether to rebaseline belongs to the existing accountable review, with explicit method/version/reason, no unsupported claims, bounded action scope and deterministic unavailable/no-write fallback. Typed identity does not certify causation or method quality.
5. **judgment-candidate:** managed promotion remains the existing review/model within the operational ladder and approved evidence floors. Capture success alone never permits a move.

1. **Exposure boundary.** Baseline capture must bind an actual intervention/exposure boundary to the authored method and target stage. 2. **Unreadable exclusion state.** The existing DroppedOriginRegistry currently catches corrupt state and returns an empty exclusion set; the existing union may then re-admit preserved origins. That is not the promised conservative failure. Require an explicit unreadable/unknown status from the existing exclusion owner, with affected foreign participation held until repaired. Retained local/historical context remains labelled history and cannot restore authority. Corruption after failed preservation and restart is an acceptance case. This requires a real existing-owner correction, not a competing exclusion registry or a claim that the current substrate already supplies it. Source feedback fb-1843bf83-e0b was stored locally; forwarding is unconfirmed.
3. **Conditional publication.** Bind expected numeric Initiative.version and old contract hash to the metadata installation in one initiative-scoped owner serialization/conditional publication operation. The existing update(ifMatch) is NOT sufficient on its own, and the reason is concrete (round7 source read): with TaskFlow wired, get() re-reads the persisted flow record, update() checks ifMatch synchronously, then awaits a multi-step persistThroughTaskFlow whose state patch re-reads the flow's current revision before writing. A second update() that starts during that await can read the not-yet-advanced persisted version, pass the same ifMatch, and overwrite the first (TaskFlow's own expectedRevision only guards each step against itself, not against another logical writer). Unconditional callers that omit ifMatch also rebuild the whole Initiative from their own read and can clobber a just-installed measurement field. Required correction inside the existing InitiativeTracker owner (no new store): (a) one in-process per-initiative-id serialization covering every mutator of that initiative (create/update/setPhaseStatus/remove and any other writer) from the read used for the version/hash check through persistence completion, so check-and-write is atomic within the owning process for ALL writers, not only capture; (b) the capture compares both expected Initiative.version and the old contract hash inside that critical section, not as a route precheck; (c) under TaskFlow the first flow mutation carries the flow revision observed at the start of the critical section as expectedRevision, so a write from outside this process fails the OCC instead of being overwritten; (d) success is returned only after canonical persistence confirms, and a persistence failure leaves the cached copy rolled back to the persisted record rather than reporting the new contract. No two initial/rebaseline captures may install from the same expected version, and no post-write check can repair lost ownership history. The legacy non-TaskFlow writer is serialized within one process only; cross-process file serialization is not claimed, and capture is unavailable unless the owning process holds the canonical writer. Real concurrent initial/rebaseline, capture-versus-unconditional-update and asynchronous activation tests are required.
