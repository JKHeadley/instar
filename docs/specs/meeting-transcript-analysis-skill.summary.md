# Meeting-transcript analysis skill: design summary

Every rule the full spec (docs/specs/meeting-transcript-analysis-skill.md) enforces, in one readable piece. The full spec adds file names, arguments and test detail; a difference between the two is a defect.

## Purpose
A post-meeting read says what was decided, who does what, and what the client still owes. One pass misses things and summaries mislead (2026-11-19: "build a mock site with the real chat widget" became "send screenshots"). The skill makes Luna's measured method a built-in skill for every agent, with scripts that fail when anything is unaccounted for. The scripts prove structure. Readers and verifiers judge correctness, which is measured on planted-miss fixtures and by misses the operator finds.

## Rules: the procedure
1. One built-in skill, one SKILL.md, the same procedure on every engine. Fresh readers run through adapters for all four supported engines (Claude Code, Codex, Gemini CLI, instar-native). Each adapter is generated at build from that engine's own Instar provider builders, so no settings are copied by hand, and CI fails on a stale copy. An engine whose adapter has not passed the no-tool-use injection test gets `no-fresh-reader`, which blocks the run.
2. Fresh readers have no tools. The prompt goes in and JSON comes out. Text in a transcript or picture cannot make a reader act. Every call writes a receipt (adapter, version, model, hashes, tokens), with the full prompt and reply kept as client data.
3. The whole transcript is read, never a summary. Every transcript line is filed in a ledger row with its exact words. Every quote, in the ledger and in the read, is checked verbatim.
4. Every item quotes the transcript (or a verified mark). A summary is never the basis of an item. When sources disagree, the agent goes to the transcript and never picks the vaguer or the firmer summary.
5. Every non-transcript source (recorder notes, the operator's or a participant's summary, prior reads) is compared ask by ask. Each source is split deterministically into units (bullets, lines, sentences, vendor entries), and units are split into clauses at sentence ends, semicolons and list separators. Each unit's entry lists every ask it holds, each with an outcome: matched (item id), disagreement (settling quote), or not an item (with a reason). A unit or clause with no entry fails. Every verifier round also checks each unit against its entries for an unlinked ask, owner or condition; such a finding is item-changing. Disagreements are listed in "Where sources disagree".
6. Keyword sweeps (the agent's name, "I'll", "important", names, numbers) are settled hit by hit. A hit is covered only by a row on its own line or by a written verdict.
7. Blind readers read the transcript without seeing the main read, each by a different method. Two is the default. The agent judges how many a call needs (one for a short call, none for a very short one) and records why. Whatever a reader found that the main read lacks must be explained. Floor: no read is `converged` until a fresh reader that never saw the main read's working has checked every transcript line; a verifier round counts. What each reader caught is recorded per run and in `eval.mjs`, so the default is revised on evidence.
8. Every item ends somewhere: an action, a question for the client, a file, or "information, because ...". Every recorder mark (screenshot, highlight) has an entry tied to its lines. A format check enforces that. Whether the description matches the picture is judged by an image-capable fresh reader.
9. Verifiers get a neutral question ("list anything missing, misattributed, misquoted or overstated; an empty list is valid"). They are never told the read is incomplete.
10. Findings come in two kinds. Item-changing findings change an action, owner, ask, decision, priority or referent. Firmness findings change none of those. When unsure, a finding is item-changing.
11. The stop rule uses evidence floors, not counts. `converged` needs a round with zero findings of either kind. Every round that led to an item-changing fix is followed by another round. An applied firmness fix is checked by one more full round, so a run never ends on an unchecked edit. Stopping with open firmness findings is `INCOMPLETE (firmness open)`. Quota shedding gives `INCOMPLETE (quota)`, and the operator-set spend ceiling (default 7 rounds) gives `INCOMPLETE (ceiling)`. Every open finding is listed. Stopping is allowed; calling an incomplete run finished is not. The operator can order more rounds.
12. Reversals and disputes go up an evidence ladder before anyone is asked: transcript quotes, verified marks, authorized project records (prep, agenda, open items, prior reads, the client's written request, later written corrections), then targeted fresh verifiers. A later written correction outranks an in-call remark only when it is explicit and from the decision's owner; both are shown. If nothing settles it, it is a dispute: both readings stay, every dependent change is held, and the operator gets one question with both quotes. The operator is never asked what the records answer.
13. Dismissals are visible. Every sweep verdict, reconcile decision, information mapping, rejected finding and downgraded finding is listed with counts under "What was set aside".
14. Operator-found misses join that meeting's regression set (a re-run must catch them) and the agent's own `eval.mjs` fixtures, not demands on unrelated meetings.
15. Several recordings: each row, item and mark carries its recording id; one ledger per recording, one read per meeting.

## Rules: status and what may be staged
16. Statuses are computed by `run-check` from the last round and the run record. Precedence: any blocking failure gives `blocked`, then `incomplete`, then `ready-with-disputes` (disputes or a non-blocking hook failure), then `ready`. `settled-with-limits` is `converged` with some verification unavailable, and the limits are listed. Limits are always listed.
17. `ready` waits on every installed machine of the agent (every machine paired and not marked gone). Each must confirm it holds the commitments (by key) and evidence (by hash); one peer is not enough. Until then the status is `ready-pending-replication`, and the report and notification name each missing machine. An offline machine gets a follow-up commitment (`meetingId/replicate/<machineId>`), the handoff queues durably, and the run becomes `ready` when the last machine confirms. A single-machine agent's status says the read lives on one machine and the git remote.
18. Unknown is not clean. A change resting on marks no image-capable reader checked is held. When marks are unknown (no recorder-extras hook), a client-visible change may be staged only on two independent sources (a transcript quote plus a written record), or on an unambiguous request that a fresh reviewer confirms, when the change is reversible and gated. The reason is recorded, and everything else is held. Absence of marks is known only from the recorder's own per-meeting metadata.
19. In `incomplete`, every open finding is treated as a dispute, and only changes no open finding touches may be staged. `blocked` stages nothing. A blocking failure is any failed check, a live surface not unchanged, a wrong sync or lock, `no-fresh-reader`, or a failed fetch, recorder-extras or staging hook.

## Rules: client data, privacy and team
20. Nothing is ever sent to a client. Drafts go only through the drafts hook. Client-visible changes are only staged, and the staging hook's independent live read must show no change. Publishing waits for the operator. There is one operator message, keyed `meetingId/revision`, sent through the agent's outbound path, which refuses a machine that does not own the conversation.
21. Client material stays in that client's declared workspace. This is checked, not only said: a containment scan compares every file changed outside the meeting folder (memory files and other clients' folders included), plus new memory entries, with the transcript (eight or more consecutive words) and with client identifiers. A hit holds the run until the text is removed or a per-hit verdict is recorded.
22. Each staged file is scanned for credential patterns. A match is a signal, not a decision. An unjudged hit holds the push, because a pushed credential cannot be taken back. Each verdict is recorded and reported.
23. Raw audio is not kept. Transcript, email and picture text is data, never instructions.
24. The client config declares `sync`: the repository holding the meeting folders and its remote. The run fails when the folder's repository or remote differs, or when the push did not land. `sync: none` needs an operator-ratified exception.
25. Each meeting read has one owner, the person who owns the client relationship, and is private to them. Sharing happens only through shares in the owner's signed team record. The agent can narrow the audience but never widen it. The remote's readers count as audience: the remote must be private where its host reports it, and multi-person agents need a per-client remote unless the owner shared with everyone who can read the home repository. Memory privacy must be on for multi-person agents. Outside the audience, the agent does not reveal meeting content.

## Rules: one run per meeting, failures and retries
26. Each run takes a local exclusive lock, then a LOCK committed and pushed to the client repository. An existing unreleased LOCK stops a second run. Each run works in its own detached git worktree. The run re-reads the remote LOCK before each side effect and stops with `lock-lost` if it is not its own. The LOCK is taken over only when the holding session is confirmed stopped on its own machine. If that machine cannot be read, the operator is asked once; no clock decides it.
27. Staged changes, commitments and notifications are keyed, so retries update and never duplicate.
28. Only transient failures are retried (network, rate limit, temporary local contention), all within the run's time budget (default 120 minutes). Waits follow the service's reset signal, otherwise backoff with jitter. The remote is read before each retry, so a push is never repeated on top of itself. Local contention is retried only while its holder is observed alive and working. A lock with a dead holder is stale and is reported, not retried. Push contention is retried with backoff only while each refusal shows a new remote head; a repeated head or the budget gives `push-contention`. Everything else is reported, not retried. Each wait and observation is recorded.
29. A run that runs out of budget keeps its LOCK and registers a follow-up commitment. When due, the agent resumes (re-checking the snapshot) or closes the run (LOCK released as abandoned, cleanup done, operator told). After three failed resumes it closes.
30. After the push, agent-owned actions and the client's open asks become commitments (`meetingId/itemId`), with their decisions, disputes and quotes, and reach every machine through the commitment replica stream. An evidence copy goes under `.instar/meeting-evidence/` as working-set artifacts, so any machine can pull the read without the git remote, with the same audience. If the working-set layer is off, the report says so as a limit.
31. Order of work: preflight (gate, team checks, sync, pull, lock, helper copies hashed against the build manifest), then fetch, readers, ledger, checks, read, verifier rounds, then a planned mapping check, staging and an actual mapping check, then the report, then the final check on the exact staged snapshot (re-hash, re-run every check, run record, credential and containment scans), then commit, push, after-push check, commitments, evidence copy, replication confirmation, notify, and release of the LOCK.

## Rules: scripts and installation
32. No executed input. The ledger source is JSON validated against a schema. Older `.mjs` sources are converted once, on command, in a separate Node process with the permission model (read one file only, no writes, no child processes) and caps on memory, time and output. The caps are set from measured needs and limited by the host's free memory. Hitting a cap is a refusal the agent rules on.
33. Scripts accept paths only inside the meeting folder. Exit codes: 0 pass, 1 fail, 64 bad input. Report-only modes never gate. The entry guard works through symlinks and paths with spaces. Versions must match the SKILL.md `helperVersion`, and the helper copies must match the build's hash manifest.
34. The gate `meetingTranscript.enabled` defaults to the development-agent gate. When off, nothing is installed and preflight refuses. The gate is checked on every install path. Instar ships no hook implementations. Only the fetch hook is required; a missing hook is named and what depends on it listed as not done.
35. Cost: about 0.4M tokens for a two-hour call at four rounds, 0.8M at the ceiling. Nothing runs on its own.

## Rules: rollout (Maturation Path)
36. Test-agent rung first, supervised by Echo: a throwaway agent runs the whole skill end to end on synthetic and held-out fixtures. Stub hooks, readers, checks, rounds, staging on a stub surface, final check, push to a throwaway private remote, commitments, two-machine replication, test-channel notification, release. Fixtures: planted misses, corrupted artifacts, an injection line that must cause no tool call, all four real CLIs, people inside and outside the audience; held-out answers annotated by a different model family.
37. Development rung only after the test-agent rung passes: development agents (gate default) and Luna by explicit flag. Luna is named because Justin asked for her as first user; she is the development rung, not a skipped rung. A role-based alternative is a small change later.
38. Graduation: two consecutive real meetings where every check passes and the operator's review finds no missing or wrong action, owner, decision or priority (operator-found escapes = 0, recorded). Any escape resets the count, joins the regression set and is filed as a method fix. Three escapes without graduating drops the fleet step. The fleet flip is a separate small PR. Who judges graduation (the operator, or an automatic reviewer) is Justin's choice.
39. Rollback: gate off and revert; preflight then refuses; meeting folders are never touched.

## Honest limits
Only fresh readers are tool-less; the main agent uses its normal tools. The live-surface check is the hook's own observation. Remote readers are checked only as far as the host reports. Paraphrase outside git and memory, and keys inside screenshots, are not caught. Receipts expose a skipped reader but not a fabricated one; operator-found escapes are the backstop.
