# Codex model policy continuation design

This draft covers the work tracked in the engine project after the independently deliverable launch-default change.

## Agent-wide override

The logical agent owns the selector revision. A separately authorized operation must write the intent to durable policy custody and distribute it to enrolled machines. It reports which machines applied the revision, which are pending, and which failed. A machine with unknown or stale policy must report that state and retain the last verified policy while it reconciles. Compare intent independently of locally compatible model IDs. Test an offline peer reconnecting, stale revision rejection, and different CLI capabilities. The existing local configuration endpoint remains explicitly machine-scoped.

### B. Existing-agent scan migration design

This design is tracked with the engine project.

This independent migration can seed the installed free-probe wrapper at 04:00 local time for new installs. On update, install the same default for an existing agent with no manifest and no durable opt-out. Preserve the schedule and disabled state of every existing manifest unless affirmative installer-owned provenance establishes that enabling it is intended. Existing schedule strings and absent disable markers provide insufficient evidence. An authenticated operator can still enable the existing job through the supported controls. The change must keep the kill switch authoritative in the scheduler state directory and perform the scan through an integrity-verified packaged prober. Write scheduled observations to a separate projection. Only confirmed manual delivery may advance the manual delivery baseline. Test a scheduled observation followed by a manual scan, and overlap between scans. Verify package execution and concurrent scan behavior before enabling this migration.

### C. Idle running-session reconciliation design

This design is tracked with the engine project.

A separate source change may add opt-in automation after A. Record authenticated selection provenance on the exact session record, including whether the model was inherited from a moving selector, the selector and resolved model, and the process incarnation. Restore prior provenance for an exact resume only when those facts still apply. Pinned, local and unclassified sessions are ineligible. An old or previously native-edited session can become eligible after an explicit operator opt-in establishes fresh provenance and every live proof succeeds. A recorded launch model or the last rollout turn alone cannot establish a live model. Require an independent supported live read tied to the exact active Codex process, or leave the session untouched.

Reuse the existing Codex conversation capture and resume primitives. Prove the current machine owns the conversation through the existing topic ownership and session lease authorities. Require an exclusive admission barrier covering all input paths, including native terminal input, before capture and replacement. Existing topic locking alone is insufficient. Require positive evidence of an empty prompt and absence of pending input, message delivery, running work and helpers, then revalidate ownership, lease fencing token, incarnation, target and config revision before mutation. Missing evidence or a changed condition cancels the attempt. Recheck the launched conversation ID, model and account against the intended values before marking success. Before the first disruptive action, durably journal the exact session incarnation, rollout reference, account, selector generation, durable evidence that this exact rollout can resume under that account, and pending delivery custody. If the original remains independently verified intact and a transient cause has cleared, the guarded path may reassess a retry after a full preflight. After a mutation or uncertain outcome, recover using the journal and existing continuity path. Retain the saved rollout, and preserve ordered input using stable delivery IDs and durable receiver receipts. The receiver must commit durable acceptance and the stable delivery ID before acknowledging or acting on it. A retry returns the original acceptance result. Test a crash at acceptance, after acceptance but before acknowledgement, and after acknowledgement but before the sender updates its journal. Unknown acceptance remains in reconciliation. If ownership changes, the stale owner cannot finish and the new owner must reconcile the journal before dispatch. Fresh conversation creation is forbidden. A crash before or after replacement enters journal reconciliation before any further transition. While the CLI lacks reliable live readback or execution cannot reserve the session across the check and replacement, this phase remains observation-only.
