# Blocker hand-off across machines and surfaces

## Problem statement

An agent may need a person to finish a sign-in, provide a one-time code, approve an action, or operate the agent's machine. Today those requests can fragment across Telegram, Slack, dashboard chat and attention notices. The person may see a stale request after solving it elsewhere. A dashboard can stream terminal sessions from pool machines, but that is not a safe human desktop takeover mechanism. This spec makes one durable blocker episode the source of truth and adds a last-resort, explicitly approved dashboard machine-access path for every supported host.

The operator directed this on 2026-10-27 (topic 127504): prefer the smallest request, make the blocker visible in every interface and close it everywhere after resolution, offer useful autonomy upgrades without nagging, and allow remote access to any machine with an installed agent when needed. This is Tier 2+ because remote input is a new entry path to the host.

## Existing contracts and boundary

Reuse BlockerLedger's `settleTrueBlocker` and SelfUnblockChecklist for exhaustion; B17 Never a False Blocker for false claims; restart-safe blocker classification for durable cause and stale recovery; Secret Drop for operator-only values; existing relogin repair and normal Chrome profile paths for sign-in; TelegramAdapter attention items and pool reads for notices; WS4.4 pool-stable links and the dashboard router holder for links; Correction & Preference Learning Sentinel for explicit user preferences. Standing Computer Use grants **agent observation only** and does not authorize operator remote control. Pool Dashboard Streaming is **terminal watching**, not desktop input. Neither is repurposed as implicit authority.

The existing attention store is TelegramAdapter-local and has status updates; cross-platform alerts are a delivery helper, not a shared lifecycle ledger. This design adds one episode record and projections, not another competing blocker classifier.

## Proposed design

### 1. One blocker episode and a ranked hand-off

Create `BlockerHandoff` as a durable child of a BlockerLedger cause: `{episodeId, blockerId, causeKey, topicId, ownerMachineId, ownerEpoch, generation, revision, phase, neededAction, evidenceRefs, openedAt, expiresAt, resolvedAt, resolutionEvidenceRef}`. The coordinator loads the real BlockerLedger candidate and persisted SelfUnblockChecklist run; caller-supplied identity, evidence, and text are bounded hints, never authority. Stable `episodeId` derives from canonical cause plus generation. Repeated detection reuses the open episode; later recurrence gets a new generation.

**Two-phase admission resolves the current ledger contract.** `settleTrueBlocker()` requires an actual user request reference and timestamp after the failed attempt. After checklist exhaustion, the coordinator first sends the smallest *provisional* request, persists the adapter's actual delivery receipt, and submits its reference to `settleTrueBlocker()`. It reloads the accepted `true-blocker` verdict before fan-out or remote-control offer. Failed delivery never produces a fabricated reference. A crash between send and settle reuses the persisted receipt and idempotency key. Extend BlockerLedger intake to verify this outbox receipt; today it accepts a bounded caller string and cannot itself prove delivery. Existing non-handoff callers retain a compatible path until migrated, but cannot gain remote-access authority through it.

The coordinator writes a `send-intent` before calling an adapter. A crash after platform acceptance but before receipt persistence leaves `delivery-unknown`: reconcile by platform message id/history when available; otherwise pause for explicit bounded reconciliation and **do not blind-resend**. One provisional request per cause/generation is budgeted. If settlement refuses, edit or reply to withdraw that request, recheck cause/evidence, and mark the episode `withdrawn` or `candidate`; remote access remains impossible. A failed withdrawal is tracked as projection lag.

The server uses a bounded Tier-1 adjudicator to choose among `none`, `approval`, `secret-or-code`, `guided-step`, `remote-access`, or `wait`. Inputs are the persisted checklist run, BlockerLedger record, task scope, action risk, available repair paths, target machine, and mobile suitability. Deterministic floors require checklist exhaustion before the provisional ask; settled true-blocker before fan-out or remote access; recorded failure of cheaper applicable rungs before remote access; no credential in chat; existing permission/mandate for actions; no success inferred from delivery. Uncertainty selects a guided request or `wait` with reason, never remote input. Secret Drop or the existing code flow handles a sufficient one-time value.

An episode carries one active `neededAction` at a time. Changing the ask increments `revision`, supersedes old action URLs, and updates every projection. Sensitive values stay in the existing Secret Drop/vault storage; the episode stores only references and redacted descriptions. It does not replicate browser cookies, CLI tokens, screenshots, or passwords.

### 2. One lifecycle across surfaces

Add a `BlockerHandoffCoordinator` with a scrubbed journal and materialized state: `candidate → provisional-sent → settled → awaiting-user → resolving → resolved | expired | withdrawn`, plus `suspended-for-recheck` from active states. A `BlockerLedger.reopenForRecheck` event suspends hand-off, revokes remote input, and marks projections "checking again". A fresh true-blocker verdict for the same cause can resume with a new revision after a verified ask; changed or resolved cause closes the old generation. Each event carries idempotency key, owner epoch, revision, and evidence. Restart rebuilds and reconciles before any resend.

BlockerLedger currently has no recheck event emitter, so this build adds an outbox event at its mutation boundary; the coordinator also reconciles on boot to cover a missed event.

BlockerLedger and checklist files are local and absent from current state sync. Add a redacted replicated **blocker-proof projection** with signed source machine/epoch, blocker id, verdict, checklist digest, taxonomy, revision and expiry. Full records remain on their source machine. A transferred owner must fetch and verify source records over machine-auth before advancing or granting remote input; unreachable source leaves the existing card visible but freezes privileged changes. Journal/outbox replicate through the existing pool store under owner-epoch CAS. At the adapter send commit, recheck epoch independent of SpeakerElection; partition uncertainty fences privileged sends and input.

The existing coherence journal is append-only, not transactional CAS, and `LocalLeaseStore` is local. Implement `HandoffOwnerLease` as a new fixed-membership quorum certificate: each installed pool machine atomically persists its per-episode vote/epoch/expiry **before** returning a signature, and signs at most one owner for an epoch. A candidate gathers signatures from a majority of configured membership (one of one on single-machine; two of two on a two-machine pool; two of three on a three-machine pool). The certificate with epoch, owner, expiry and membership generation is the linearization point. Lease duration is 15 seconds from each signer's own vote; assembled certificate expiry is capped by the **earliest signed vote's expiry**, never assembly time. Owner renews every 3 seconds. Peers reject measured clock skew over 2 seconds against signed peer time. A signer that has voted for an owner uses its own monotonic clock to withhold any successor vote for **at least 19 seconds** after its last old-owner vote (15-second lease + twice the 2-second skew bound), even if wall time jumps. A new owner certificate therefore cannot have an intersecting signer while any old certificate is still accepted. Effect consumers reject certificates at the conservative earliest-vote expiry minus 2 seconds, reject any epoch older than locally observed, and require current membership generation. For external sends, adapter obtains a fresh quorum-backed fence immediately before platform commit; for remote display/input target renews that fence every 3 seconds and closes both streams on missed renewal or conservative expiry. If skew cannot be measured within bound, effects fail closed. Test ±2-second offsets, jumps, delayed signatures and partition overlap.

Membership change requires verified operator action **and a reconfiguration barrier**: durably publish a pending generation to all current members, stop issuance/renewal under old generation, wait 17 seconds (maximum old lease plus skew bound), then activate new generation. If any old member cannot acknowledge the pending barrier, no reconfiguration or new hand-off authority is allowed; operator can later repair membership through a separately approved recovery path, never by silently shrinking quorum. Target and adapters fetch/verify the active generation before any effect and reject old-generation certificates. If quorum or generation verification is unavailable, new privileged effects freeze; passive cards remain readable. `GitLeaseStore`, where present, stays the conversation-owner signal but is not this feature's CAS substrate. This new authority is part of the build and has partition, renewal, clock-skew and membership-race acceptance tests.

Eligible operator-only Telegram topic, Slack destination, dashboard native chat and dashboard attention card show the same episode id, machine nickname, clear action, current status and pool-stable link. Each send re-resolves verified operator identity and topic/channel binding; mixed-audience or unknown Slack channels and misbound Telegram topics are omitted, with sensitive details redacted even on eligible projections. The dashboard attention list is the authoritative read projection; messages are notifications. Each adapter persists `{episodeId, revision, platform, destination, messageId, deliveryState}`. On resolution the coordinator edits or replies to original messages where supported, marks the card complete, and emits one completion note where editing is unavailable. Failed closure is visible as `projection-lag` and retried. Reconnect reads reconcile stale UI. A user saying "done" starts verification, never direct closure.

Delivery is one-voice from the pool owner, using existing one-voice gating. On owner transfer the new owner resumes the episode and projection outbox; old owner is fenced from writes and sends. The operator sees one logical blocker across machines, not one new request per machine.

Cause verification maps the actual BlockerLedger taxonomy: `operator-only-secret` needs a successful scoped use without revealing the value; `operator-only-account` needs expected identity and an authenticated provider call; `legal-billing-authorization` needs the verified human authorization **and** the transaction/result readback; `operator-judgment` needs a verified decision record plus task-specific consequence readback. Unknown subtype or unavailable verifier stays open. The current ledger treats `true-blocker` as terminal, so add a dedicated `resolveTrueBlocker` transition requiring successful post-assistance live-run and on-disk playbook proof. It atomically records resolution on that same blocker generation; the hand-off terminal event follows. Do not misuse `reopenForRecheck` to complete a blocker. A user message, button tap or remote session ending is never proof. Per episode/revision, budget one new notice on each of four surfaces; revisions edit where possible. Delivery-health notices go only to attention hub after failed self-heal. Retain terminal episodes 30 days; snapshot/compact only after replica acknowledgment. Cap active episodes at 1,000 and queued noncritical projection updates at 10,000. Admission **durably reserves one distinct terminal slot per active episode**, so every admitted episode can close even at capacity; no unresolved episode is evicted. Revocations use a separate lossless, synchronously persisted monotonic fence at the **same quorum authority as lease renewal**, plus direct target command, outside projection queue. A revoke intent is durably accepted by majority before UI claims `revoked`; those signers refuse future lease renewals or `not-revoked` attestations for the grant, and quorum intersection prevents another majority from renewing. A received request enters deny/pending before acknowledgment. Every 3-second stream renewal requires a fresh quorum-signed per-grant not-revoked attestation; uncertainty denies renewal. At active cap, reject new admissions with explicit capacity error and one deduped notice, while closure proceeds. At update cap, coalesce stale noncritical updates per episode/platform. If quorum revoke write or direct target delivery fails, UI reports revoke **uncertain** until target confirms; if majority accepted the intent, renewal stops and target closes at conservative lease expiry. If neither quorum nor target received it, immediate containment is unconfirmed and only the current ten-minute grant expiry or local kill switch bounds exposure; do not claim success. Test direct-command loss with healthy quorum and asymmetric partition. Never replace distinct terminal/revocation events with overflow summary. Retention is time-based for compacted snapshots; update cap applies only to pending events. Journal/outbox are 0600, excluded from support bundles, included in `BackupManager`, and restored without grants; restore revalidates epoch, cause and receipts.

### 3. Direct remote desktop and blocker hand-off

The dashboard offers **Open this machine** as a direct operator tool whenever an installed machine has a ready desktop adapter; a blocker is not required. The same tool may be linked from an active `remote-access` hand-off when simpler task-specific requests failed. The operator sees the machine and the full-control scope in plain language and enters the dashboard PIN to open it. This PIN submission is the approval action; no Telegram chat setup, copied command, checkbox, or fingerprint comparison is required. A short-lived dashboard operator session authorizes the exact machine and browser key, and the target rechecks that session throughout capture and input. The PIN proves possession of the dashboard credential, not a distinct human identity or an independent Telegram factor. If PIN verification or the operator session is unavailable, access is refused. This grant authorizes **full human control of the currently logged-in desktop**, including changes in open apps and files; task text is an explanation, not an enforceable application boundary. Existing AuthorizationPolicy/MandateGate continues to govern the agent's own actions, not arbitrary human keystrokes. This paragraph supersedes the original Telegram challenge decision by Justin's 2026-10-27 23:41 PDT instruction in topic 131439.

The target signs a grant bound to the PIN-derived operator session, machine id, browser ephemeral public key, nonce and maximum 10-minute lease. If the session came from a blocker hand-off, the hand-off links its episode and revision to the viewer, but the remote grant is still direct operator authority and does not depend on the blocker remaining open. The target verifies the live operator session, browser proof, revocation state and controller lock at every input; body claims and a relay bearer token never establish authority. One active controller per machine, 2-minute idle expiry, 15-second disconnect heartbeat deadline, explicit revoke and agent-side kill switch. Every stop path immediately fences input and synthesizes release of held keys and mouse buttons. No grant exists because an agent asked for one, and it gives the agent no new authority.

The first Mac adapter captures an active, unlocked macOS desktop session. Its PIN-only dashboard flow does not unlock the operating system. When the Mac is locked or signed out, the target reports unavailable with a plain reason in the PIN-verified viewer and refuses capture and input. The authenticated machine-availability API may also return that reason before PIN entry; it contains no frame or private desktop content. The viewer retains a valid PIN session for Check again and asks for the PIN again only after that session expires. Locked-screen control requires a separately reviewed host adapter and OS authorization; it is not implied by this first-machine test.

Transport requires a **new** browser-to-target WebSocket display/input stream through the pool-stable dashboard URL: current WS4.4 links proxy GET private views, and terminal-stream tickets are read-only. The router forwards to the named target over machine-auth. The target verifies the same signed operator/episode/browser-key grant **before display stream creation**, on every reconnect, and continuously against lease/episode/revocation state; revoke closes display and input together. An authenticated ephemeral key exchange binds the browser key in the signed grant to the target's registered key. AEAD protects frames and input with monotonic sequence numbers, replay rejection and new keys on reconnect; relay cannot substitute a target or forge control. Exact Origin, CSRF token, strict viewer CSP with no third-party scripts, and no grant in URL/analytics/logs are mandatory. The target shows a local "remote control active" indicator and audits session start/stop, controller and coarse input counts, never screen or keystrokes. No separate terminal or file API is exposed, although full desktop control can operate visible applications including a terminal.

One stream per physical host and four streams per pool, including WSL agents sharing a Windows host, each at 5 Mbps and 15 frames/second maximum; the host companion owns the single-controller lock across all its WSL guests. Router reserves a separate control-plane connection pool and at least 1 Mbps per peer for lease/health RPCs. A bounded two-frame video queue drops oldest video, never control messages. Control messages cap at 64 KiB; router cancels video first if the reserved control-plane budget is threatened. Input is never queued across disconnect. Frames, input bytes, challenge and session keys are memory-only; audit metadata lasts 30 days.

Implement a platform adapter contract with capability probe, start/view/input/stop, foreground-session and permission checks. Installer packages companions for macOS, Windows and Linux desktop with locally prompted OS capture/input permissions. WSL delegates only to a separately installed, authenticated Windows host companion bound to that WSL agent. Headless or permission-less hosts report `remote-display-unavailable` and offer another rung. OS-supported capture/input APIs or a host-launched loopback-only remote-desktop service may implement the adapter; no raw VNC/RDP port is exposed to LAN or internet. Live proof must include macOS, Windows, Linux desktop, WSL+Windows, and a headless refusal before "all machines" is claimed; until then UI uses live per-machine capability.

Remote control is a human operation. The agent may observe the hand-off status but cannot read the live video or inject input through this grant. The operator can end it at any time. Ending control does not claim the blocker solved; the cause verifier does that separately. If the viewer cannot reach the target, the episode stays open and offers code/Secret Drop/guided alternatives. An agent can never use this path to silently bypass CAPTCHA, biometric, payment, legal, or other human-reserved steps.

### 4. Autonomy upgrade offers and preference memory

After a successful manual intervention, the coordinator may identify a **specific** existing auto-login or repair capability that would have avoided the step. It offers one concrete opt-in with benefit, scope, and revocation path; it never enables a capability from a conversational answer alone. An affirmative answer routes to the existing verified grant/config flow. A refusal is stored in the existing preference/correction pipeline with capability family, task scope, source, time and consent provenance; no new parallel preference store. The offer is suppressed for that family/scope thereafter. A later explicit request can override it. A frustration signal about repeating the related work may trigger **one** respectful re-offer, subject to the preference sentinel's provenance and cooldown, and never after a hard "do not ask again" instruction. The agent must not infer consent from frustration.

## Multi-machine posture

Episode journal, blocker-proof projection, current state, outbox, grant metadata/revocation epoch and preference decision: **unified**, using named replicated-store kinds `blocker-handoff-episode-v1`, `blocker-handoff-outbox-v1`, `blocker-proof-v1`, and `remote-grant-revocation-v1`; remote reads proxy through pool router. Records key by `(episodeId, generation, revision, eventType)` or `(episodeId, platform, revision)` for outbox, with schema version, owner epoch, source signature and tombstone. Merge accepts only increasing verified epoch/revision; tombstones dominate older writes. Each record caps at 16 KiB; no more than 100 new records/minute/agent, with a separate reserved lane for terminal closure/revocation. Wire send, receive, restore and capability gate for all four kinds. Actual ownership CAS lives in `HandoffOwnerLease`, not append-only replication. Dashboard links use WS4.4 pool-stable links to name target; new protocol handles bidirectional traffic. Full BlockerLedger/checklist records remain at source until fetched over machine-auth; source offline freezes privileged transitions, even if another machine and dashboard are online.

Actual display, input device, active OS session, controller lock and session process: **machine-local** on target. `machine-local-justification: hardware-bound-resource` for each. Browser profiles, OS permissions and target signing key: **machine-local**. `machine-local-justification: physical-credential-locality` for each. Ephemeral stream keys: **machine-local** for target/browser session; `machine-local-justification: hardware-bound-resource` because they bind one live device session. Target keeps last valid revocation epoch and locally expires grants during partition; inability to verify current owner/episode closes both display and input. Only scrubbed availability and grant metadata are shared. Offline target remains visible but uncontrollable.

| Autonomy offer | judgment-candidate | Specific available capability; prior refusal/cooldown/hard-stop floor; existing preference sentinel arbiter; uncertain means suppress. |

## Verify the state, not its symbol

`settled=true` means BlockerLedger accepted evidence, corroborated by the source record and persisted checklist run; missing/unavailable means no activated hand-off. `delivered=true` means a platform accepted a message, not that the user saw it; reconnect reads current episode. `done` reply or grant end is only a symbol; the mapped verifier checks authenticated task state. `remote available` requires live target probe plus an OS input/display session; stale or unavailable probe suppresses the button. `resolved` follows BlockerLedger's accepted resolution; unavailable verification leaves the episode open with a truthful unknown notice. Metrics record provisional-to-settled success, time to verified resolution, remote-rung rate, projection convergence latency and stale-card duration without secret content.

## Self-heal before notify

The coordinator is event-driven after existing self-unblock and relogin repair. A reconciliation watcher retries failed projections and refreshes cause before raising a delivery-health item. Remediation is idempotent resend/re-register; superseded revision is compensated by closure once newer revision lands. Limits: three attempts over 65 seconds (5/15/45-second waits), one active retry timer per `episodeId:revision:platform`, at most four surface sends per cycle, breaker after three failed cycles/hour. At 120 seconds, mark any unfinished self-heal exhausted **before** sending one delivery-health notice. Scrubbed audit: `logs/blocker-handoff.jsonl`. The breaker stops retry but leaves an explicit degraded card, never silent stale status. Security failure revokes input and alerts on the same tick while containment proceeds.

## Frontloaded Decisions

1. Follow the role-derived maturation ladder: test agent first, development agent after live proof, then fleet after the platform matrix and security gates pass. Notice fan-out begins in dry-run; remote access needs explicit operator enablement at each stage. Kill switch immediately closes display and input.
2. Entering the dashboard PIN on the clearly labeled desktop page authorizes remote control for the selected machine. The resulting operator session must remain valid through capture and input. Telegram is not a prerequisite. This supersedes the original independent Telegram challenge decision by Justin's 2026-10-27 23:41 PDT instruction in topic 131439; the loss of independent-factor assurance must be stated honestly.
3. Remote session maximum 10 minutes, 2-minute idle timeout, one controller, no recordings, no durable frames/keys/keystrokes.
4. One episode is the source of truth. Platform messages are projections, reconciled eventually; exact simultaneous visual closure across network partitions is impossible, so stale surfaces show last-sync time and refresh on reconnect.
5. The remote grant provides human control only. It is not an agent computer-use grant and does not authorize anything for the agent.
6. No platform can be advertised as supported without its adapter and live proof. All-machine support is an acceptance gate, not a label.
7. The operator enables the dev gate per agent after the live platform test; enabling remote control additionally requires the dashboard PIN, installed host companion, granted OS permissions and an explicit dashboard setting. Disable/revoke is available to the operator and local agent kill switch.
8. The browser relay and companion ship as part of the Instar installer/update, with signed binaries and content-sniffed migrations; no arbitrary downloaded desktop server. Grant and stream routes are authenticated, rate limited, `Cache-Control: no-store`, and 503 after auth when dark. The dashboard cards use the existing attention API vocabulary; episode API is an authenticated `/blocker-handoffs` namespace with read/create/transition and signed grant issue/revoke routes. The coordinator, not callers, owns transitions.
9. Journal and outbox retention is 30 days for terminal records; backup includes them, restore revalidates all active state, and grants are never restored. A source machine that cannot prove blocker state cannot authorize an owner transfer's privileged action.

## Tests and rollout

Unit: action ranking and floors both ways; provisional-send/settle crash windows including `delivery-unknown`; refusal memory and frustration re-offer; lease epoch CAS and partition; signed grant scoping, missing/expired/revoked PIN session, expiry, revoke, single-controller; cause verifier unknown; new `resolveTrueBlocker` live-run/playbook proof; adapter probe; bounded retry/stream queues. Integration: authenticated episode route and real BlockerLedger receipt verification; projection outbox across Telegram/Slack/dashboard adapters; closure after cause evidence; transfer/restart and source-offline freeze; stale link/revoked grant refused for **display and input** at target; stream Origin/CSRF/replay/AEAD/backpressure and control-plane reservation; no secret/screen data in durable stores. E2E: production boot path returns live episode/card when enabled rather than 503; real pool transfer and backup/restore; test-as-self on macOS, Windows, Linux desktop and WSL host companion, plus headless truthful refusal; PIN-to-stream operator control followed by independent cause verification; offline source showing read-only card; tunnel/PIN abuse. Feature stays dark until required hosts pass. Update `generateClaudeMd()` capability/triggers, `PostUpdateMigrator` existing installs, config defaults, dashboard and adapter migrations. Rollback disables gate, revokes input immediately and retains journal for cleanup.

## Maturation plan

- **test-agent-live:** Exercise the full production boot path in an isolated agent on macOS, Windows, Linux desktop and WSL+Windows, including PIN-to-stream access, actual display/input, quorum partition tests and headless refusal. Only the isolated test agent can expose remote control at this stage.
- **dev-agent-live:** After test-agent evidence passes, enable notice projections in dry-run on Echo, then live; separately enable one remote host at a time with explicit operator consent and verify real end-to-end blocker closure and revocation.
- **fleet:** Graduate by role-derived config, never by hardcoded per-machine defaults, after the platform matrix and security gates pass. Each installed host still requires its own verified operator and OS permission setup before remote control is available.
- **graduation criterion:** All three test tiers green; at least one live control-and-verified-resolution and one live revoke per platform; zero unauthorized display/input; successful partition, delayed-signature, source-offline, restore, and full-queue acceptance tests; seven consecutive dev-agent days with no missed blocker closure or stale active control. Operator reviews the evidence before fleet enablement.
- **dark-window:** At least seven days on the development agent after test-agent proof; fleet remains dark until graduation criteria and operator enablement are met.
