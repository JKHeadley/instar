# Every reference to a waiting ask carries its ask

## Problem statement

An agent ended a message with "Still waiting on you: the screen-lock question I sent at 2:46." No link, no restatement. To answer, the person has to scroll back through the conversation, find the 2:46 message, and work out what reply settles it. The existing named clause "Every ask carries its links" (PR 3097, under *Agent Proposes, Operator Approves*) covers the message that first makes an ask. It says nothing about later references to that ask: reminders, end-of-run summaries, "still waiting on you" lines. That is where the screenshot failed. (The screenshot shows an agent's conversational message; whether a live session or fixed code wrote it is not established from the record. A session-written one is what B26 reviews; a code-built one falls to the tracked commitment named below, CMT-1422 <!-- tracked: CMT-1422 -->.)

Three things make this hard for an agent to get right today:

1. **Nothing checks it.** The clause from PR 3097 is an instruction line only. Its own ELI16 says "Nothing checks the rule yet." (Checking first asks stays with the initiative the registry already names for it, `ask-links-helper-and-review`.)
2. **An agent cannot build the link.** No code in instar produces a link to a Telegram, Slack or app message. The Chief of Staff tried on 2026-11-18 and could not. The Telegram send route returns `messageId` and nothing else, and the reply script the agent uses (`telegram-reply.sh`) throws even that away: on success it prints only "Sent N chars to topic T".
3. **A card link is buildable but not offered.** The console route for a card (`#/work/board?card=<id>`) exists (`dashboard/console/projects-model.js` `cardHref`), but nothing hands an agent the full, phone-openable address.

## The standard (constitution text)

A second named clause under *Agent Proposes, Operator Approves*, right after "Every ask carries its links". The approved draft's two requirements (link; plain restatement with the exact settling reply) are carried word for meaning:

> **Named clause — "Every reference to a waiting ask carries the ask."** Whenever a message mentions something the agent is waiting on the person for (a question, approval, decision or reply), in any message and not only the first one, it (1) links the original ask (the message where it was asked) or the Work Board card that holds it, ideally both; and (2) restates the ask plainly and briefly, as short as it can be while still answerable, with the exact reply that settles it, so the person can answer from that message alone. A reference that is missing either one is a defect; a bare "still waiting on you for X" is the plainest case. Where a channel has no link to a single message, the card link stands in, or failing that the link to the conversation; when no link can be built at all, the restatement carries it alone and the agent says so. A link is taken from the send response, the card or the link route, never written by hand. This clause does not license a reminder: whether a waiting ask is mentioned again at all is governed by *The Agent Carries the Loop* and *Near-Silent Notifications*; it says only what such a mention must carry. When the original message cannot be found, the agent opens a Work Board card holding the ask and links the card (where it has a Work Board). **Ratified by** Justin, Telegram topic 141385, message 145385, 2026-11-18 17:33 PST: *"standard yes"*, approving the proposal that followed his 16:23 PST message (message 145323): *"We should have a required standard that whenever the agent references something they are waiting on the user for they link the original message where the request was or a card that's been created. That has the details or ideally both"*. **Applied through** the outbound rule `B26_WAITING_ASK_UNLINKED` (advisory; development agents first) in `src/core/MessagingToneGate.ts`, the message-link builder `src/core/messageLinks.ts` and `GET /messages/link`, the `messageLink` field on the Telegram and Slack send responses (printed by `telegram-reply.sh` and `slack-reply.sh`), and the agent awareness entry `src/data/awareness/waiting-ask-links.md`. Reminders built by code rather than written by a session are not reviewed by B26; bringing them under the clause is tracked as feedback item fb-e3a446af-c59.

## Design

### 1. Making the link possible (`src/core/messageLinks.ts`, pure, no I/O)

- `telegramMessageLink({ chatId, topicId, messageId })`. A supergroup chat id `-100<n>` gives `https://t.me/c/<n>/<topicId>/<messageId>` for a forum topic, and `https://t.me/c/<n>/<messageId>` for the General topic (`topicId` 1 or absent). Any other chat id (a private chat, a basic group) has no shareable message link: the builder refuses with `chat-not-linkable`. Ids must be positive integers; anything else is refused with `invalid-input`. The link opens only for a member of the chat, which the person always is. Topics in the separate Issues group (internal ids above `ISSUES_TOPIC_OFFSET`, `src/messaging/telegramTopicSpace.ts`) live in a different chat with their own thread ids: for those the builder uses the configured `issuesChatId` and the thread id `topicId - ISSUES_TOPIC_OFFSET`, and refuses with `chat-not-linkable` when no Issues chat is configured. `classifyAskLinks` recognises links to either chat and reports the internal topic id, so the log lookup matches the stored rows.
- `slackMessageLink({ workspaceUrl, channel, ts, threadTs? })` gives `<workspaceUrl>archives/<channel>/p<ts without the dot>`, plus `?thread_ts=<threadTs>&cid=<channel>` for a reply inside a thread. This is Slack's documented permalink shape. `workspaceUrl` is the `url` field of the `auth.test` call the Slack adapter already makes at start (newly kept, `SlackAdapter.getWorkspaceUrl()`); it must be an `https://<team>.slack.com/` address (Enterprise Grid's `<org>.enterprise.slack.com` included) or the builder refuses: `workspace-pending` when no address is known yet, `workspace-unsupported` when the address is not a `slack.com` one. Channel ids and timestamps are shape-checked.
- `appConversationLink(origin, conversationKey)` and `workCardLink(origin, cardId)` give console links through `consolePageUrl`, using the hash routes the console already defines (`chats-model.js` `hashFor`: `#/work/chats?c=app:<uuid>`; `projects-model.js` `cardHref`: `#/work/board?card=<id>`), with the id shape-checked (a uuid; `isCardId`) and URL-encoded. An app link opens the conversation at its newest messages; the console has no per-message anchor today, so for an app ask the card link is the better target and the conversation link is the stated weaker stand-in (standard text above).
- `classifyAskLinks(text, { telegramChatId })` counts, deterministically, the web links in a message by kind: `message` (a `t.me/c/<this chat>/…` link, or a `*.slack.com/archives/…/p…` link), `card` (a link whose hash route is `#/work/board?card=`), `conversation` (`#/work/chats?c=`), `localOnly` (any link to `localhost` / `127.0.0.1`), `other`; and returns the topic and message ids of this chat's Telegram links. These are the facts rendered to the judge (§3).

### 2. The route: `GET /messages/link` (Bearer auth)

The route builds a link from ids the agent already holds; it does not search. Query: `platform=telegram&topicId=N&messageId=M`, or `platform=slack&channel=C&ts=T[&threadTs=]`, or `platform=app&conversationKey=K`, or `platform=card&cardId=ID`. Finding WHICH message holds an old ask stays with existing tools: the send answer captured at ask time (preferred), the Work Board card that holds it, `GET /telegram/search`, or `GET /attribution/trace` (which recalls by meaning across machines). A text search inside this route was considered and dropped in review round 1: a word-match search would report a paraphrased ask as absent, and would read only this machine's history.

Answer: `200 { url, platform, verified }`. For Telegram, `verified` says whether this machine's own history of that topic holds a message with that id: `true`, or `"not-in-local-history"` (the link is still built, because another machine may have served the topic; the agent is told plainly that this machine cannot confirm the id). For the other platforms `verified` is `"unchecked"`. `verified` means only that a message with that id exists in this machine's log of that topic, not that it is the intended ask; for Telegram the answer therefore also returns `matched: { sentBy, timestamp, text }` (the full logged text) when found, so the agent can read what the link points at before sending it. The lookup is the same exact-id pass over this machine's retained log described in §3; a message older than the retained log, or served by another machine, reads `not-in-local-history`. `409 { error: 'not-linkable', reason, retryable }` when the link cannot be built: `chat-not-linkable` and `not-configured` (no Telegram adapter or chat id; no Slack adapter on this machine; Work Board off for a card) are permanent on this machine (`retryable: false`); `workspace-unsupported` (the workspace address is not a `slack.com` one, for example GovSlack) is permanent (`retryable: false`); `workspace-pending` (the Slack adapter has not read its workspace address yet) and `tunnel-pending` are `retryable: true`. `400` on malformed input.

Console links use the operator-facing origin from `createOperatorLinkOriginResolver` (`src/server/dashboardPaths.ts`; one resolver instance made for this route, same construction as the existing ones in `routes.ts`). `public` gives a link; `local/no-tunnel` gives the local link with `localOnly: true` in the answer (an agent with no tunnel has no address a phone can open, and the agent is told so). Both `pending` and `local/tunnel-wait-exceeded` answer `409 tunnel-pending`: an agent that has a tunnel never hands the person a localhost link. The Telegram chat id is read from the running Telegram adapter's configured chat.

**The link at send time.** `POST /telegram/reply/:topicId` adds `messageLink` next to `messageId` on its delivered answer (direct and forwarded sends both leave through it; a quiet-recorded receipt, `sendResult.recorded`, is a message that was held and never posted, so it has no id and gets no link); `POST /slack/reply/:channelId` adds it next to its message timestamp `ts`, using the thread timestamp the handler already resolved for a reply inside a thread. Absent when not linkable. `telegram-reply.sh` prints it: the success line becomes `Sent N chars to topic T (message M) link: <url>` (the link part only when present), so the agent sees the link in the output of the command it already runs. The script change ships to existing agents through the existing relay-script update path: the previous script hash is added to `TELEGRAM_REPLY_PRIOR_SHIPPED_SHAS` so `PostUpdateMigrator` replaces an unmodified deployed copy (the lint `scripts/lint-template-sha-history.ts` enforces that the list is complete). `slack-reply.sh` prints the same way (`… (ts T) link: <url>`), shipped through the Slack relay's own hash-provenance update path (`ensureSlackReplyRelay`, `PRIOR_SHIPPED_SLACK_RELAY_SHA256`). The inline copy of the Telegram script inside `PostUpdateMigrator.getTelegramReplyScript()` is used only when the template file cannot be found and is left as it is (it keeps the plain success line); the template file and the hash list are the real update path. Both scripts keep their existing `Sent N chars to …` prefix, which the stall-triage parser matches. App sends do not get a message link (no per-message anchor exists); the agent uses the card or conversation link.

**The link when found later.** `GET /telegram/search` adds `messageLink` to each result row (same builder; absent when not linkable), so a later session that looks an old ask up gets its link with it. Together with the Work Board card (the durable record of an ask that needs a person's decision) this is how a session that did not send the ask recovers the link; a separate ledger of open asks is not added. A card already has a `links` field, so an agent that opens a card for an ask puts the message link on it, and a later session reads the link from the card. A complied resend goes through the same review again, so "complied" is re-judged, not self-attested. Slack links are built from the workspace address in Slack's documented permalink shape rather than by calling `chat.getPermalink` on every send, which would add a network call and a failure mode to the reply path.

### 3. Enforcement: `B26_WAITING_ASK_UNLINKED` (advisory, judged by meaning)

A new rule in the outbound tone gate. Its mechanics follow `B25_SPEC_APPROVAL_UNCHECKED` (a rule section rendered from a `ToneReviewContext` field inside `buildPrompt`, with no phrase pre-filter); its reaction plumbing follows `B22_SURFACE_REFERRAL` (advisory, comply-or-override).

- **Class** `behavioral-judgment`; **disposition** `advisory`: the message is handed back unsent with `422 tone-gate-advisory`; the agent revises and resends with `toneAdvisoryComplied`, or resends unchanged with `toneAdvisoryAck` + a required `toneAdvisoryAckReason`. Because the baseline disposition is `advisory`, the "override could not be recorded, so block" fallback (`routes.ts`, the `RULE_DISPOSITIONS[rule] !== 'advisory'` check) never turns it into a hold. Not in the advisory-migration exempt set.
- **What the judge sees of the conversation.** The review already receives the topic's recent messages (the last ten, both sides, from topic memory on Telegram; the channel's own recent log on Slack and the app where the route has it), so "asked earlier" and "not answered yet" are judged against the visible conversation as well as the message's own words. Where no recent conversation is available the under-fire default applies.
- **No phrase pre-filter.** *Intelligent Prompts — An LLM Gate Must Not String-Match* forbids deciding by phrase, and the ways to say "still waiting on you" share no wording ("the screen-lock thing is still open on your side", "once you answer my earlier question I can finish", "reminder: I need your call on the budget"). So the rule is rendered for every review where it can matter.
- **Where it is rendered.** The route attaches `waitingAsk` to the review context only when ALL hold: the switch is on; the channel is Telegram, Slack or the app; the message kind is `reply` (a message a live session wrote; `automated`, `health-alert` and `unknown` never get it); `liveArtefactSignals === true` (the caller declared it can react to a nudge: the agent reply routes do, while `/attention` and the updates-topic poster do not, so they never see the rule); and `noReactionPossible !== true` (a queued redrive never sees it). Nothing about the message text decides it. Code-built and scheduled-script reminders are therefore out of B26's reach by design: a nudge they cannot answer would lose the reminder, which is worse than a bare one. They are tracked separately (feedback fb-e3a446af-c59).
- **The facts the judge is given.** All are deterministic, rendered as data, and each can be reported unavailable; none decides anything.
  - (a) Link kinds: `waitingAsk.links = { message, card, conversation, localOnly, other }` from `classifyAskLinks`. The kinds are exclusive: a link to this machine only (`localhost`, `127.0.0.1`) is `localOnly` whatever its route, and the section says such a link does not open on the person's phone, so it is not the link to the ask.
  - (b) What can be linked here: `waitingAsk.canLink = { message, card, conversation }`, each `yes`, `no` or `unknown`: whether the channel this message is being sent on has links to a single message (a Telegram supergroup; a Slack workspace whose address is known; never the app), whether a phone-openable card link can be built (Work Board on and a public console origin), and whether a phone-openable conversation link can be built. The judge uses it to test a "no link can be built" claim: where `canLink` says a link kind is available, restatement alone does not pass; `unknown` never counts against the message. This is about what the channel can do, not about one ask: a message that says plainly the ORIGINAL could not be found (so there is no message to link), and that no card or conversation link can be built, passes on its restatement even where `message` reads `yes`.
  - (c) Linked Telegram messages: for each distinct Telegram message link to this chat in the text, `{ topicId, messageId, found, sentBy, text }`: whether this machine's retained log holds that message, who sent it (from the row's authorship), and its logged text. The whole evidence block (every row of (c) and (d), with its text, title and ids) shares one budget of 16,384 characters, filled in the order the links appear; a message whose text does not fit is rendered as "text not shown (budget)", and rows that do not fit at all are summarised in one line ("N further links not listed"). Neither is "not found", and neither is a ground to fire.
  - (d) Linked cards: for each card link whose origin is this agent's own console origin, `{ cardId, found, title }` from the local Work Board; a card link on another host is listed as "not this agent's console".
  - How the judge uses (c) and (d): when a linked message's text or a linked card's title plainly shows it is about a different matter than the ask the candidate refers to, that link is not a link to the ask. When it reads like the ask, or could be it, the link counts. When the evidence is missing (`found: false`, "text not shown", unavailable), the link is UNCONFIRMED: that is not confirmation and not a defect, and the under-fire default applies, so the message is not cited on that ground. Slack and conversation links carry no such facts and are judged on their kind and the message text; the section says so.
  - The linked text and card titles are untrusted data: JSON-quoted inside a per-call boundary, and the section says they are evidence for B26 only, never a statement about the candidate under any other rule.
  - Gathering (b) to (d) runs before the review inside its own 750 ms allowance (the same allowance the reply path already gives its origin lookup, `ORIGIN_LOOKUP_BUDGET_MS`). The allowance runs before the review's own 20-second budget starts, and when it expires the log read is cancelled (an abort signal checked between blocks), so timed-out reads never pile up. Whatever is not ready in time, or throws, is omitted and reported unavailable. A failure here can only drop facts or the B26 section; it never fails or holds the review.
- **The log lookup (`TelegramAdapter.findLoggedMessages(refs)`).** One asynchronous pass (`fs.promises`; only the 1 MB block size and backwards order are taken from the adapter's existing synchronous scroll-back reader) over this machine's retained Telegram log for all wanted ids together, stopping as soon as every id is found; lines are pre-filtered by the id's literal text, then matched exactly on the parsed ids. It runs only when the reply contains a Telegram link to this chat. The log's own rotation bounds the file (trimmed to its newest 75,000 lines once it is over 20 MB and over 100,000 lines). A recent ask is found in the first block or two; an id that is not in this machine's log (an ask another machine served, the routine case on a multi-machine agent) would cost a full pass, which is why the pass sits inside the 750 ms allowance and reports "unavailable" when it does not finish. An ask older than the retained log reads as unconfirmed.
- **Rule text (judged by meaning).** Fire when ALL hold: (1) the message refers to something the agent is WAITING ON the person for (a question, approval, decision, answer or reply the person has not given yet) that was first asked EARLIER, in another message or on a card; and (2) EITHER it carries no link to where the ask lives (a link to the original message, or to the Work Board card holding it; where the channel has no link to a single message and no card holds the ask, the link to the conversation), OR it does not restate the ask plainly with the exact reply that settles it. A full restatement does not excuse a missing link, and a link does not excuse a missing restatement: a reference to an earlier ask needs both. A link of kind `other` (a pull request, a document, a dashboard page) is not a link to the ask. An open-ended ask has no single settling reply; its restatement says what kind of answer is needed. PASS when: the message makes a genuinely NEW ask for the first time (governed by "Every ask carries its links"); it reports that the person already answered; it is waiting on someone or something other than the person (CI, another agent, a vendor); it only discusses this rule or quotes an old message; it carries the link and the restatement (that is a well-formed ask, not work parked on the person); or it says plainly that no link can be built and restates the ask in full (the accepted shape only where neither a message link nor a phone-openable card or conversation link can be built: for example a private chat on an agent with no tunnel or no Work Board). Under-fire bias: when unsure whether the message refers to an earlier ask the person still owes, do not fire. When it plainly does ("still waiting on you: the X question I sent at 2:46") and lacks the link or the restatement, fire. The suggestion names the way through: take the link from the send output, the card, or `GET /messages/link` (never write a link by hand; if the id cannot be confirmed, say so; if the original message cannot be found, open a Work Board card holding the ask and link the card), add one line restating the ask with the exact settling reply, and resend with `--tone-complied B26_WAITING_ASK_UNLINKED`; or, when no link can exist, override with the reason.
- **Relation to B19.** `B19_PARKED_ON_USER` (blocking) fires only with its own detector signal and concerns the agent handing its own work to the person; the gate defines no precedence between B19 and other rules. A waiting reference is about a decision that is genuinely the person's. So the B26 section itself carries one de-confliction line the judge reads in the same prompt: a reference to a waiting ask that carries its link and restatement is a well-formed ask and is not, for that reason alone, work parked on the person. The base template (and so B19's own text) is not edited. One test covers a linked, restated reminder with the parked-on-user signal present.
- **Switch and ladder.** `toneGate.waitingAskLinks.enabled`, resolved by `resolveDevAgentGate`: unset means live on development agents and dark on the fleet; an explicit true or false wins. Registered in `DEV_GATED_FEATURES` (`src/core/devGatedFeatures.ts`) with its justification. No persisted block, so no config migration. Off: the context is not attached, the rule is not rendered, prompts are byte-identical to today. Evidence comes before authority in two steps: the test-agent stage runs the real gate model over the meaning-level boundary cases and records the verdicts before the release, and only then is the nudge live on the development agent, where every citation is hand-graded for the fleet decision. The nudge itself was the operator's approved shape ("a nudge, not a wall") and is never final: a reasoned override always sends.
- **Prompt identity.** A review that renders B26 records the prompt id with a `-b26` suffix (`tone-gate-sigv1-b26`, `tone-gate-sigv1-jev-b26`; both fit the decision log's label format `^[a-zA-Z0-9_-]{1,64}$`, so they are recorded as themselves and never clamped to `unlabeled-prompt`), so decisions made with and without the rule are never graded as one prompt.
- **Wiring.** The id is added to `VALID_RULES`, `RULE_CLASSES` and `RULE_DISPOSITIONS`; `ToneReviewContext.waitingAsk` is threaded through `review` into `buildPrompt` next to the B25 section; the benchmarked base template (`TONE_GATE_PROMPT_TEMPLATE`) does not contain the rule.
- **Cost.** About 300 prompt tokens per reviewed reply on agents where the switch is on (the same order as B25), plus the linked evidence when a reply carries links: at most 16,384 characters (about 4,000 tokens) of linked text. No extra model call and no stored state. Fact gathering is bounded at 750 ms and reported separately from model latency. The added review latency is measured on Echo during the development-agent period against the route's existing review budget.

## Signal, state and fixed limits

Signal vs authority: B26 is an LLM authority's advisory citation and holds no blocking power (an acknowledged override with a reason always sends). The link counts and `verified` are signals. The link builder and route make no decision about any message.

Symbol and state (each detector): *link counts* — symbol: URL shapes in the text; state claimed: none on its own (the judge reads the message to decide whether a link points at the ask); a `message` or `card` link can be present yet point at a different ask, which only the judge and the agent's own care can catch, and the rule text says so; unmeasurable: rendered as unavailable. *`verified`* — symbol: a row with that message id in this machine's topic history; state: the id names a real message in that topic; a real message served by another machine reads `not-in-local-history`, stated as unconfirmed rather than false.

fixed-limits:
- 16,384 characters for the whole linked-evidence block per review — a prompt-size and latency default, judged inside the floor (not a claimed hard floor): it keeps the B26 section from dominating a review prompt that also serves every other rule, and keeps untrusted linked text small. It is four full Telegram messages, more than a reminder or a multi-ask summary normally links. The floor around it: the cut is disclosed in-band ("text not shown", "N further links not listed"), omitted evidence is UNCONFIRMED and can never be a ground to fire, and the full text stays readable to the agent through the link. If hand-grading during the development-agent period shows citations missed because evidence was not shown, the number is revisited.
- 750 ms for gathering the facts — a share of the outbound review's 20-second budget (`OUTBOUND_GATE_REVIEW_BUDGET_MS`), reusing the allowance the reply path already gives its origin lookup (`ORIGIN_LOOKUP_BUDGET_MS`); basis: external-constraint (the review budget is fixed by the route); overrun cancels the read and reports unavailable, never a verdict.
- No cap on the number of links counted, and no window on the lookup other than the log's own retention and the allowance above.

## Frontloaded Decisions

1. Rule disposition: advisory (a nudge), not blocking. The approved draft says "the gate is a nudge, not a wall".
2. Rule id: `B26_WAITING_ASK_UNLINKED` (B25 is the newest id in use).
3. A reference to an earlier ask needs BOTH a link and a restatement with the settling reply; when no link can be built, the restatement plus a plain note that no link exists.
4. No phrase pre-filter; the rule is rendered for every eligible review (the B25 mechanics).

Adding reply-to support to the agent reply routes would also work on Telegram and in Slack threads, but it only helps inside the same conversation, cannot be carried into a summary or another topic, and leaves cards and the app uncovered; a link covers all of those with one mechanism.

## Multi-machine posture

- **Link builder / route:** pure construction from ids: the same ids give the same Telegram and Slack link on every machine. Console links (card, app conversation) carry the answering machine's own operator-facing origin, the same posture as every other operator link the agent sends. machine-local-justification: physical-credential-locality (the Slack workspace URL comes from the Slack bot login held by the machine running the Slack adapter; a machine without the adapter answers `409 not-configured`, it does not guess). The Telegram chat id is shared config. Work Board cards are a replicated store, so a card link opens from any machine's console; app conversations are served by the replicated app-conversation store.
- **`verified`:** a read of this machine's Telegram history that stores nothing; its answer is explicitly "not in local history" (unknown here), never "does not exist". An ask served by another machine comes back unconfirmed, and the awareness entry says unconfirmed is not wrong. `GET /attribution/trace` remains the cross-machine recall.
- **The rule:** runs where the send is reviewed (relayed Telegram sends are reviewed on the lease holder with `liveArtefactSignals: true`). Nothing persisted, nothing to replicate.

## Side effects and risks

- **Over-fire:** a message that mentions an open ask in passing while making a different point. Mitigated by the under-fire bias, the pass list, and the advisory disposition (the agent overrides with a reason, which is recorded evidence that tunes the rule).
- **Under-fire:** a reminder phrased so obliquely the model misses it. Accepted; the awareness entry carries the norm.
- **A link to the wrong message.** The judge cannot open links. Mitigations: the send output hands the agent the real link at ask time; the route marks an id it cannot confirm; the rule's suggestion and the awareness entry forbid hand-written links.
- **Link correctness:** a `t.me/c/` link for a non-supergroup would not open; the builder refuses those shapes.
- **Privacy:** a message link exposes no content; it opens only for chat members.
- **Existing tests:** development-agent fixtures resolve the switch on; tests that pin tone-gate prompt bytes on the reply routes set the switch off or account for the section.

## Rollback

Set `toneGate.waitingAskLinks.enabled: false` (rule gone, byte-identical prompts), or revert the PR. The route, the `messageLink` fields and the script's extra output are additive.
