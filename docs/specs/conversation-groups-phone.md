# Conversation groups from the phone

## 1. Why

The owner's word for an effort is now "group" (origin above). Grouping suggestions exist only on the dashboard: the phone's route allowlist refuses them (`conversation-graph-suggestions.md` §6, CMT-1651). The dashboard's Accept was orchestrated by the page itself (create, name, preview and move each conversation, set the front door, record accepted: up to 2 + 2N requests with waits between), so a phone client would have to copy that whole state machine. And a group cannot become a Chief of Staff project from the phone at all: binding a project needs the dashboard PIN (`POST /chief-of-staff/projects`).

This spec adds the agent-side routes the phone apps need. It builds no app screen. User-facing words say "group"; internal names stay "effort".

## 2. Suggestions on the phone, and Accept as one server step

- **Routes, same bodies on both surfaces.** Dashboard: `/conversation-graph/suggestions…` (operator session). Owner phone: `/mobile/conversation-graph/suggestions…` (device signature; owner person only; added to the device allowlist).
  - `GET …/suggestions` → the existing `SuggestionView` (`state`, `builtAt`, `items[{id,title,reason,members[{ref,title}],accepting,frontDoor?}]`, `failure?`).
  - `POST …/suggestions/refresh` → unchanged semantics (202 started, 429 too soon / already building, 503 no model).
  - `POST …/suggestions/:id/accept` (body `{}`) → the whole Accept, see below.
  - `POST …/suggestions/:id/reject` (body `{}`) → `{ok:true,id,state:'rejected'}`; the id is never offered again on this machine. Refused with 409 `accept-started` once an Accept has sent its create (the group may exist; rejecting could strand a half-filled one).
- **One server function.** `runSuggestionAccept` (`src/server/ConversationGraphSuggestionAccept.ts`) runs the steps the dashboard page used to run (parent §4: create, name, preview and move each member, record accepted), plus the two project-suggestion steps the page added with the Chief of Staff root work (a project suggestion has a `frontDoorKey`): (0) a project suggestion whose conversation already sits inside anything creates nothing (recorded accepted with `placedElsewhere:true`, so a repeat answers the same) — unless that parent is the group this suggestion's own derived create request made (another machine got that far), in which case the Accept resumes filling it. Only a certain answer closes it as placed elsewhere (the create was never recorded, or it made a different group); an unanswered or pending status is a wait, and a lost owner is `not-owner`; (1) `create-effort`; (2) `set-effort-title` unless it already has a name (a refused name is re-read: a name set meanwhile by another tab or machine is kept; a name still refused is skipped and the group stays unnamed for the owner to name, never stranding the group); before moving anything, every call re-reads the group; (3) for each member a node read, a `preview`, then `set-primary-placement` (a member placed elsewhere since, or no longer movable, is skipped: the owner's placement wins; a refused move is re-read, and counts as moved when another path already put it in this group); (4) `set-front-door` for a project's conversation, only while it still sits in the group (its own parent is the group) and the group has no front door yet: a front door the owner chose is kept, a conversation that left is skipped, and a refused front door is skipped; (5) record accepted with its result. A refused create stops the Accept (409); a refused name, move or front door is a skip. A refused create made nothing, so the Accept's progress is dropped and Reject works again; a create refused because the owner erased that group closes the suggestion (`group-gone`). Every change goes through `ConversationGraphOwnerChanges` with the caller's own request, so the owner proof is the request's and the receipt says `owner-device` or `owner-dashboard`.
- **Derived request ids: one group, from any machine.** Every owner request id is derived: `acceptRequestId(suggestionId, step, extra)` = `sga-` + the first 40 hex of SHA-256 over `conversation-group-accept\n<id>\n<step>\n<extra>`, where `extra` is empty for the create, the suggested title for the name, the member key plus the placement event ids it replaces for a move, and the front-door and placement event ids for the front door. The owner pipeline deduplicates on (owner principal, request id) through the replicated source (`lookupByIdempotencyKey`, promoted by the single graph writer), so a resumed call, another tab, the phone, or another machine with no copy of this machine's progress all send the same create and find it done. Because a move's id carries the placement it replaces, a later change (the owner moved a conversation out, then the suggestion was offered again elsewhere) is a NEW request, never a replay conflict. This holds for machines on this build offering the same suggested member set (suggestion ids are hashes of the members); an older machine's dashboard during a staggered install uses its own ids. An Accept already in flight from before this change keeps the create id it stored.
- **Resumable and bounded.** Each call has a 15 s budget (under the default 30 s request timeout): checked before every synchronous read and preview, and raced against every submit and status wait. When it runs out the call answers 202 `working`; the next call resumes. Synchronous graph reads cannot be interrupted, so one call overruns the budget by at most one read; a call makes at most about 30 reads (up to 12 members, each possibly re-read after a refused move, plus the group and front-door reads). A submit left running when a call gives up is joined by the next call from the same caller grant (one in-flight promise per request id and grant on this machine), never queued again behind itself in the graph's single write queue; an in-flight submit older than 60 s is not joined, so one that never settles cannot hold an Accept (a fresh submit is deduplicated by the pipeline). Progress (opaque request ids and refs only, never titles) is a per-machine cache in the suggestion state file, not the source of truth. One Accept per suggestion runs at a time per machine; a lock older than the budget plus 30 s is treated as gone, so a wait that never returns cannot hold the suggestion forever.
- **The group removed mid-Accept.** "Removed" means the owner erased the group's create event (the graph has no delete), and only the pipeline's own record says so: when the group reads as missing, the Accept asks the create request's status, and only `erased` closes the suggestion (409 `group-gone`, recorded rejected on this machine, progress dropped). A create refused as `erased` does the same. A missing read alone is never proof (it may lag, or be partial): it is a wait, and after at least 3 misses spanning 30 s the owner gets the decision back (409 `group-not-found`: "Tap Accept again later, or Reject", a group already made stays), progress dropped, nothing closed.
- **Nothing waits silently forever.** Answers the pipeline should never give (a committed create without a group, a group without a header, an exception) are a wait twice, then reported as a degradation and handed back to the owner (409 `unexpected-answer`). If no step has finished during 5 minutes of calls (a machine offline, a write held elsewhere), the Accept answers 409 `still-saving` in plain words with progress KEPT, so Continue later resumes exactly there. The brake counts only time while calls keep arriving: after an absence of more than a minute its clock starts again, and bookkeeping saves (request ids) never reset it. The unexpected-answer count starts again whenever a step finishes. Every `working` answer says what it waits for (machines by name, or that the agent is not answering).
- **Answers.** 200 `{id,state:'accepted',group:EffortRef|null,moved,skipped,placedElsewhere}` (a repeat answers the same); 202 `{id,state:'working',step,text,waitingMachines[{machineId,name}],agentNotAnswering,retryAfterMs:3000}`; 409 `{id,state:'refused',step,code,text,next}` (`text` is plain words, never the pipeline code; `next` is read from the server's own state: `finished` = the suggestion is closed, `accept-or-reject` = the Accept was handed back and both Accept again and Reject work, `continue` = progress is kept and Reject is refused until it finishes); 404 `unknown-suggestion` (unknown, rejected, or dropped by a rebuild before the Accept started: the client re-reads the list); 400 `invalid-suggestion-id`; 403 `hierarchy-owner-only`; 503 when the graph is not open; 429 from the phone's rate limit (nothing changed: wait and call again; the Accept continues from where it was). A client calls again while `working`, honouring `retryAfterMs`, runs one Accept at a time (as the dashboard's Accept all does), and stops after 60 s of real time and shows Continue (as the dashboard does). After a refusal the card follows `next`: `accept-or-reject` offers Accept again AND Reject, `finished` ends the card, `continue` offers Continue and keeps Reject off (the server would refuse it). The phone's Accept row has its own rate bucket (30 per minute per device), so repeating it never starves other graph changes.
- **The dashboard uses it.** `dashboard/console/conversation-suggestions.js` calls the one route and repeats it while `working`, for 60 s of real time per Accept (counted by the clock, since each call can itself take up to the budget), then shows Continue.
- **Pages loaded before this change keep working.** `…/:id/start` and `…/:id/accepted` stay as compatibility routes for one release. `/start` answers the same derived create id the server uses, so an old page and the one call make one group; the old page's own name and move requests are ordinary owner changes (a second name is refused and the old page keeps the existing one; a move already made reads as placed).
- **Who can call it.** No job, timer or agent code path calls Accept. The dashboard surface takes an operator session, which proves the dashboard was unlocked, not that a human tapped (the agent can read its own PIN); that is acceptable for Accept, whose every change is an ordinary, undoable owner placement, and for Reject, whose cost is one suggestion not offered again on that machine. Only the phone surface carries the owner's device signature.

## 3. Group to project

- **Draft.** `POST /mobile/conversation-graph/nodes/:ref/project-draft` (and the dashboard twin without `/mobile`), owner only, `:ref` a group. Body `{}` or `{goal?: string ≤4000, done?: string[] ≤64 × ≤2000, repos?: string[] ≤16 of owner/repo}` (the Chief of Staff store's own limits, so the phone may send what the dashboard may; the owner's own words replace the drafted ones). The agent drafts:
  - the bound conversation: the group's front door, else its first conversation with a Chief of Staff key (`telegram:<topic>` in the agent's chat, or `app:<key>`);
  - the goal: from the group's title only (cleaned like all draft text) ("<title>. This project tracks the work in the group "<title>" until the owner says it is finished."), unless the owner sent their own. The title itself may have been written by the model (an accepted suggestion's title, from conversation evidence), so the real guard is the owner's Face ID over the goal shown in full;
  - the done checklist: one owner-confirmed judgment item ("The work in the group "X" is finished, and the owner says so.") unless the owner sent their own;
  - linked repos: only the owner's own.
  What the conversations are about (topic summary and live goals, up to 8 conversations × 300 characters) and the repos they name outright (`github.com/owner/repo` or `owner/repo#123`) are returned BESIDE the draft as `context{about[],suggestedRepos[],conversationsNotShown}` (the count says in band when the group has more conversations than the context covers), for the owner to read and copy in if they choose. Conversation text, which other people may have written, never becomes the goal or a linked repo without the owner putting it there: once bound, the goal steers the Chief of Staff's own check-ins and restarts. Draft text, the group title included, is cleaned: every run of whitespace (line breaks included) becomes one space, then every control and format character (Unicode Cc and Cf: bidi controls, zero-width characters, invisible joiners, tag characters, soft hyphen), U+034F, U+180E and variation selectors are removed. So a multi-paragraph goal is flattened in the draft the owner signs (the dashboard's PIN route, unchanged, keeps line breaks).
- **The draft is self-certifying and stored nowhere.** The answer is 201 `{draftId,draftHash,expiresAt,draft,context,confirm{action:'group-project-confirm',target,proposalHash,actionLine,route}}` where `draft = {v:2,group{ref,title},conversation,binding{conversationKey,goal,doneDefinition,linked},expiresAt}`, `draftHash = canonicalHash(draft)` (SHA-256 of the sorted-key JSON, `GraphWitnessTypes.canonicalJson`), and `draftId = gpd-` + the first 20 hex of the hash. The app MUST show every hashed field (which conversation, the goal in full, every done item, every repo) and MUST recompute `canonicalHash(draft)` from exactly what it shows before asking for Face ID; it carries the draft back with the confirm, so any machine can verify it. Expiry is 1 hour; it bounds how stale a screen may be, not what the owner may sign (the owner may write their own words anyway). Refusals: 409 `group-has-no-conversation` / `already-a-project`; 400 `not-a-group` / `invalid-draft-request`; 404 group not found; 503 `chief-of-staff-off` / `could-not-check-projects` / `conversation-graph-pending`. A draft writes nothing.
- **Confirm reuses the existing Face ID proof.** `POST /mobile/work/projects/drafts/:draftId/confirm` `{proposalHash,challenge,presenceSig,draft}` goes through the existing phone permission write gate (owner phone over this machine's TLS front, presence key enrolled, console PIN set, permission actions on), with a challenge from the existing `POST /mobile/permissions/challenge {action:'group-project-confirm',target:draftId,proposalHash:draftHash}` and a presence signature over `group-project-confirm <draftId> <draftHash>`, exactly as approve-request and work-card taps are proven. Then, in order:
  0. only the machine holding the lease decides (as approve-widening does): elsewhere the challenge itself is refused 409 `not-holder` ("try again in a moment"), so no Face ID is spent, and the confirm checks again before the proof (the lease may move between). Owner changes off here → the same early refusal, 503 `conversation-changes-off` (lasting, not "try again"); graph not open yet → 503 `conversation-graph-pending`. A phone whose machine is a standby gets `not-holder` until the lease moves, as with approve-widening; during a staggered install an old-build holder answers 403 not-allowlisted (update pending);
  1. the carried `draft` is shape-checked (text must already be clean: no hidden characters); its hash must equal the signed hash and its id the target (else 409 `draft-changed`); it must not be expired (410 `draft-expired`) or expire more than an hour (plus 5 minutes of clock skew) from now (400); its `conversationKey` must be the conversation's own key (400 `invalid-draft`);
  2. the Chief of Staff's bound projects are read with a read that FAILS CLOSED (`ChiefOfStaffLoop.boundProjectContents()` over `journal.loadUnionComplete()`: this machine's Chief of Staff journal read COMPLETELY — every archive and the current file, in full, via `CoherenceJournal.readKindComplete` (its own directory read; the archive list re-checked after reading so a rotation in between counts as incomplete), up to 64 MB — plus every peer replica stream, which must each read in full (`ReplicatedPeerStreamReader.peerStreamsReadComplete`: none unreadable, none past its ceiling, no skipped line). The loop's ordinary tail read (newest 1 MB or 10,000 entries of the current file) is never used for this. Any of those failing, or no complete reader wired → null → 503 `could-not-check-projects` with lasting-safe words ("if it keeps saying this, make the project from the dashboard and tell your agent") and a degradation report. An unreadable or partial journal is never "no projects". Deliberately not memoized: one read per draft and per confirm. Growth, stated: the kind never deletes and grows about 80 KB a day on this agent (mostly loop ticks), so the 64 MB cap is roughly two years out; compaction of the Chief of Staff journal is a pre-existing need reported as feedback fb-b58eee8c-aee). The conversation already bound with exactly this draft's goal, done items and repos → 200 `alreadyConfirmed` (a repeat tap once the first write has reached disk; a very fast repeat may write the identical binding a second time, which changes nothing); bound with anything else → 409 `already-a-project` (never overwritten);
  3. the group is re-read now with the confirming phone's own owner view: removed or hidden, renamed (a conservative refusal even when the owner typed their own goal), or no longer holding the chosen conversation (its own parent is no longer the group and it is not the front door; read from the conversation, so a group of any size answers correctly) → 409 `draft-stale` with plain words; graph not answering → 503;
  4. only then `ChiefOfStaffLoop.bindProject` with the draft's binding: the same write the dashboard's PIN-gated `POST /chief-of-staff/projects` makes. 201 `{ok,conversationKey,group}`.
  Every attempt that reaches the write gate is in the permission audit (`group-project-confirmed` / `refused`), which also records which device proved it (the replicated binding records `confirmedBy:'owner'` for both paths). The dashboard twin of the draft route exists for tests and parity; it has no dashboard caller yet.
- **What each path proves.** The phone confirm is a presence-signed tap: the only path here that proves a human owner. The dashboard keeps its existing PIN route for binding, unchanged (out of this change). The agent's bearer token is refused by the write gate.

## 4. Multi-machine posture

- **Accept effects: unified.** The graph changes an Accept makes are ordinary replicated owner events, and their request ids are derived from the suggestion, so any machine resuming any Accept converges on one group.
- **Accept progress: a per-machine cache.** Losing it (another machine, a restore) mostly costs re-reads: each step re-sent finds itself done. One stated exception: a member the owner moved back out while that Accept was still running would be moved in again by a resume that lacks this machine's cache (the cache marks it done). That needs the owner to undo a move during their own unfinished Accept; it is accepted, and goes away with the replicated store (CMT-1650).
- **Suggestion list, rejections, accepted results and group-gone closures: machine-local while migrating to unified** (parent §5 named the move to a replicated store, tracked as CMT-1650). A rejection or closure on one machine is not known to another, which may offer the same grouping again; Accepting it there continues the same group (derived ids), and a closed one refuses after one tap.
  machine-local-justification: migrating-to-unified ratified=5a4efecc1 tracking=commitments.CMT-1650 since=2026-11-11 expires=2027-05-10
- **Drafts: unified.** Self-certifying and carried by the phone; any machine verifies one. The binding a confirm writes replicates through the Chief of Staff journal. Phone confirms are decided only on the lease holder, from a complete read of its own journal and of every peer copy it holds. The remaining window, stated: a binding written on another machine (through the dashboard's PIN route, or by a previous lease holder) that has not yet REACHED the lease holder is unknowable there, and `bindProject` is a put, so the later write wins. That needs two owner actions on the same conversation inside the replication window. It is inherent to the existing last-writer binding record (the dashboard PIN route has the same window and no check at all), so this change narrows it rather than opens it; it is accepted, stated here for the operator.

## 5. Rollback

A revert removes the phone routes and restores the page-orchestrated Accept and its `start`/`accepted` routes. Accept progress fields left in the state file are ignored by the older reader (it spreads unknown fields and keeps `createRequestId`, so an in-flight Accept continues; the older page re-runs naming and moves with its own ids, which are no-ops on a group already named and filled). A phone app that shipped screens for these routes gets 403 not-allowlisted after a revert. Drafts are stored nowhere, so nothing is orphaned. Bindings already written stay, as any owner-confirmed binding does.

## 6. Config

No new switch. All suggestion routes (as before this change), Accept, Reject and the draft route are mounted with owner changes (graph `readEnabled` and `correctionsEnabled` with its scope check); the draft route additionally needs the Chief of Staff (503 otherwise); the confirm additionally needs phone permission actions on (the write gate's own refusal otherwise) and answers 503 `conversation-changes-off` where owner changes are off.

## Frontloaded Decisions

1. **"group" outside, "effort" inside.** Owner's words (origin). Every user-facing text says group.
2. **Accept is one server step for both surfaces; the page-driven `start`/`accepted` routes stay one release for old pages**, with the same derived create id.
3. **Request ids are derived from the suggestion and what each step replaces**, so duplicate groups cannot arise across tabs, phones or machines on this build, and a re-offered suggestion never replays into a conflict.
4. **The owner's placement wins** over advice: a member placed elsewhere is skipped, never moved back.
5. **Reject is refused once the create was sent**; Continue finishes the group instead.
6. **A removed group closes the suggestion** (409 `group-gone`) only when the pipeline says the create was erased; a group that merely reads as missing closes nothing (409 `group-not-found` after 3 misses over 30 s). A refused name or front door is skipped, never stranding the group; 5 minutes without progress answers `still-saving` with progress kept.
7. **Drafts are self-certifying, carried by the phone, 1 h expiry, re-checked at confirm, decided on the lease holder.** Not stored on any machine. A repeat tap is recognized by the whole binding, not the goal alone.
8. **Conversation text is context, never the goal or the repos**; the owner types or copies what they want.
9. **The phone confirm reuses the existing permission write gate and challenge**; no new proof kind.
10. **No new config switch**; availability follows the graph surface, the Chief of Staff and phone permission actions.
11. **The app screen is the app sessions' work** under CMT-1651; this change ships the agent-side contract above, which is a published phone interface (not cheap to change after). The app half is tracked as CMT-1926 (extends CMT-1651; owner: the echo-instar-app session, which commissioned this agent-side change; beacon due 2026-11-20) with the §2 client rules and §3's display-and-recompute rule written into it; the PR number goes to the throughput session for merge.
