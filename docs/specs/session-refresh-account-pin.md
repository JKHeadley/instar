# Explicit Account Selection for Session Refresh

## Contract

When the machine configuration explicitly enables `subscriptionPool.explicitRefreshAccountPin`, an authenticated caller can include `targetAccountId` in `POST /sessions/refresh`. The request specifies one local subscription account for a running Telegram topic using cloud Codex. It uses the existing refresh authority, with the same subscription-pool availability checks and identity reconciliation required before selecting an account. The existing swap and balance endpoints keep their selectors.

The source needs a verified idle determination and a saved Codex thread ID, and cannot be protected. The existing work gate reads the shared Claude and Codex `esc to interrupt` pane footer and descendant process snapshot. The subagent leg looks up the running record’s native thread ID, stored as `claudeSessionId`, in the shared subagent tracker. Both legs must affirm idle. If the work gate is missing, disabled, observing in dry-run, or lacks its evidence, the pin returns 409 without stopping the source. After the awaited probe, refresh synchronously checks the current Telegram delivery slot and the pane’s pending injection record immediately before stopping the source. A queued or injected unanswered turn, or an unavailable delivery read, refuses the pin without sending a stop. These checks cover input known to the running Telegram server, including arrivals during the asynchronous idle probe. The stop itself is synchronous. The native idle evidence is sampled using the existing work authority, including its cached child process snapshot. It is not an atomic native turn-boundary reservation. A later message takes the regular Telegram recovery path and may create a successor. A known queued item can veto the pin, but this is not a general proof of durable queue emptiness across restart. Existing callers retain their work-gate behavior. A malformed request returns 400, a disabled feature returns 403 and an ineligible request returns 409 before stopping the source. A 202 records acceptance and supplies the attempt ID. Only the pinned replacement carries it as a launch receipt. The stopped source carries it separately as the stop receipt. Before treating placement as complete, match the running instance’s attempt ID to the 202 and verify the running instance differs from the source, belongs to the same topic, resumes the saved thread, and reports the requested account and native login identity.

## Decision points touched

- Eligibility, invariant. Refresh applies only to the named eligible local account and verifies the source session, cloud topic, account identity and configuration home again at the last synchronous boundary before stopping the session.
- Work admission, invariant. Explicit pins require a positive idle result from the existing work authority. Force, fresh starts and recovery of dead sessions are outside this operation.
- Launch, invariant. A confirmed termination is required. The replacement uses the established Codex home and rollout placement path. Before the process starts, the launcher checks the cloud framework and the target login email using the existing Codex credential-slot identity reader. It refuses a competing live topic session and never delivers its rebrief through a reused pane. A missing rollout or failed native resume leaves the saved conversation available for normal recovery. Refresh writes the supplied rebrief to a private machine-local record bound to the exact source instance, terminal conversation, and native thread before stopping the source. The stop writes its unique attempt ID onto the killed source record together with the terminal state. Recovery compares that durable receipt to the rebrief. If the daemon exits after that confirmed stop but before launch, the receipt and rebrief already match. Missing or mismatched evidence gets a refusal and preserves the record. A confirmed live source after a refused stop lets refresh discard the unused record. Uncertain stop leaves a private record for reconciliation, with replay disabled. A failed launch keeps the record across server restart. Explicit dead-topic recovery covers launch failure before any successor is registered. A failed replacement from the same attempt is recoverable only when the strict native startup path recorded that no injection was attempted. A different successor or an ambiguous delivery holds the rebrief as evidence. Its presence is not permission to resend. An ordinary continuity-preserving refresh of the same dead topic recovers it through the existing account choice even if stop cleaned up the topic binding. The stopped instance and saved Codex thread must still match, and the local session history must show no newer topic session, including one that already ended. The launcher repeats this check under the conversation lock. The normal Telegram launch and the pinned replacement both use the existing per-conversation launch lock in SessionManager. Inside the lock a pin or recovery refuses an existing successor before any reuse or injection. Launch verifies that the chosen resume thread still equals the one held by the record. This check also applies to the original pinned launch. The asynchronous probe and durable rebrief are exercised with synthetic delivery and launch failures. Live Codex subagent coverage after a daemon restart is an activation prerequisite, outside the dark candidate proof. The activation test must retain a live Codex child across restart while the combined pane and process probe reports idle. It must prove the tracker reports that child under the saved thread, observe a 409 and zero stops, then repeat successfully after the child exits. Do not enable the feature where tracker coverage is unavailable. Both paths wait for initial injection before clearing the record. Recovery never starts automatically and does not assert the account pin succeeded. An interruption after input delivery and before record cleanup can leave delivery ambiguous. Verify the pane before recovering a second time. Server logs record asynchronous refusals. The caller verifies the replacement against the running sessions and pool account identity.

## Frontloaded decisions

The operator opts in per machine and supplies the exact target account ID. Account choice creates no enrollment, quota reset, or credential write. The caller verifies headroom before making a placement decision. The server verifies admission and executes the named placement. Disable the flag in the configuration loaded by the server to roll back the endpoint behavior. The running route reads its server configuration at validation and before stopping the source. Restart may be necessary to load a config-file edit. The choice applies to one launch. Ordinary quota automation retains its existing authority on the replacement. The pin does not add a proactive-swap exemption or change its dwell policy.
