# Normal-Chrome browser skill: the Linux driver (X11 input + AT-SPI reading)

## Glossary

- **The skill:** `/normal-chrome-browser`, the built-in skill specified by `docs/specs/normal-chrome-builtin-skill.md` (macOS) and `docs/specs/normal-chrome-cross-platform.md` (macOS + Windows). This spec is the Linux twin of the second.
- **X11 / Xorg:** the classic Linux display system. Programs (and `xdotool`) can ask the X server to inject keyboard and mouse input through the XTEST extension; to the browser, that input arrives exactly like a physical keyboard's.
- **Wayland:** the newer Linux display system (GNOME and KDE default on many distributions). It deliberately does not let one program inject input into another's window or read global screen coordinates.
- **AT-SPI:** the Linux accessibility bus (the thing screen readers use). Chrome publishes its page as a tree of named, role-tagged objects with on-screen rectangles when accessibility is switched on.
- **Cirrus:** the operator's paired Instar test agent on a Hetzner Ubuntu 24.04 VM, with a TigerVNC user service (`vnc-display1`) running an XFCE desktop on `DISPLAY=:1`. Used for the proof below.
- **xdrive.sh / x-drive.py:** the names this spec proposes for the Linux wrapper (the Instar entry point, bash) and the driver (python3, one command per invocation). They mirror `ndrive.sh` / `native-drive.ps1`.

## Problem statement

The skill's shipped text says Linux "with no Windows underneath" is not built: `chrome-launch.sh`, `chrome-js.sh`, `chrome-mainworld.sh`, `chrome-close.sh`, `chrome-renew.sh` and `chrome-unsaved.sh` stop with `ERR macos-only: the normal-Chrome method uses macOS Apple Events; it does not run on Linux`, and `ndrive.sh` stops with `ERR windows-only: ndrive.sh runs native-drive.ps1 through powershell.exe from WSL ...`. An agent on a Linux machine (a cloud VM such as Cirrus, a Linux laptop) therefore cannot do any task that needs a normal, signed-in Chrome (sign-in, billing, settings and usage pages that refuse or behave differently for an automated browser), and the skill tells it to say so and stop. The operator's rule is that Instar runs on at least Mac and Linux; ACT-138 ("Linux path for the normal-Chrome browser skill", due 2026-11-18) is the recorded item for closing this.

The earlier direction (`.instar/vm-test/README.md`) named the method: a normal Chrome launched in the desktop session; input via `xdotool` (real X events); page reading via the AT-SPI tree (Chrome started with `--force-renderer-accessibility`); no CDP or remote-debugging port. This spec measures that method on a real Linux desktop and turns it into a driver design.

## The measured proof (Cirrus, 2026-11-03, 22:23-22:31 UTC)

Host: Cirrus, Ubuntu 24.04, session type `XDG_SESSION_TYPE=x11`, XFCE on TigerVNC `DISPLAY=:1` (1600x1000), Google Chrome 156.0.8078.79, xdotool 3.20160805.1, python3-gi 3.48.2. Throwaway profile `~/.config/chrome-act138-test`, public pages only (example.com, iana.org, en.wikipedia.org, one `data:` page I wrote), no sign-in. The Chrome I started was killed and its profile deleted at the end; no other process or service was touched. The proof helpers (`atspi-probe.py`: `apps`, `tab`, `text`, `find`, `at`, `tree`; `gclick.sh`: find, hit-test, active-window check, click) were copied to `/tmp` and removed afterwards.

### Step 0: prerequisites (one snag)

`python3-gi` was installed but the AT-SPI typelib was not: `gir1.2-atspi-2.0` and `python3-pyatspi` were missing. The `instar` user has passwordless sudo on Cirrus, so `sudo -n DEBIAN_FRONTEND=noninteractive apt-get install -y gir1.2-atspi-2.0 python3-pyatspi` installed them (4.2 s). The desktop's session bus was not in the ssh shell's environment; it was read from the XFCE session process: `DBUS_SESSION_BUS_ADDRESS=unix:path=/tmp/dbus-7VPaByoIqu,...` (from `/proc/<xfce4-session pid>/environ`); the root window carries `AT_SPI_BUS(STRING) = "unix:path=/run/user/1000/at-spi/bus_1,..."`. `org.a11y.Status IsEnabled` and `ScreenReaderEnabled` were both `false`.

### Step 1: launch, and the accessibility switch (one snag)

```
google-chrome --user-data-dir=$HOME/.config/chrome-act138-test --password-store=basic --no-first-run \
  --no-default-browser-check --force-renderer-accessibility --new-window https://example.com/
```

The window appeared after 1.07 s (`Example Domain - Google Chrome`), but Chrome did **not** register on the AT-SPI bus (`apps` listed xfce4-session, xfwm4, Thunar, ... and no Chrome). `--force-renderer-accessibility` builds the page tree; the likely reason (a hypothesis until the live gate's A/B row) is that the browser process only connects to AT-SPI when it thinks assistive technology is on. Relaunching with **`ACCESSIBILITY_ENABLED=1`** in Chrome's own environment fixed it without changing any session-wide setting: Chrome registered after **0.47 s** (`16 'Google Chrome' 55792`).

### Step 2: read the active tab (URL, title, text)

```
$ python3 atspi-probe.py tab 55792          # 81-137 ms on example.com
FRAME 'Example Domain - Google Chrome' True
OMNIBOX 'Address and search bar' 'example.com'
DOC 'Example Domain' True {'Title': 'Example Domain', 'MimeType': 'text/html', 'URI': 'https://example.com/'}
FRAME '' False
DOC '' True {'Title': '', 'MimeType': '', 'URI': ''}
```

Two sources of the URL: the omnibox text (a display string, scheme hidden, like Windows) and the document's `URI` attribute (the full committed URL, scheme included). The second is better than anything the Windows driver has. The app also exposed two extra frames with empty documents; a driver must scope to the frame in the `active` state that belongs to the bound window. `text` returned the page's paragraphs (example.com's text in six languages) in 71 ms.

### Step 3: click a link found through AT-SPI

```
$ python3 atspi-probe.py find 55792 "learn more"
HIT link 'Learn more' extents (481, 928, 93, 20) True True        # role, name, screen x,y,w,h, showing, visible
$ xdotool getactivewindow   -> 46137347 (pid 55792, our Chrome)
$ xdotool mousemove --sync 527 938 click 1
click -> new document in 675 ms
DOC 'Example Domains' ... 'URI': 'https://www.iana.org/help/example-domains'
```

Page text read back from iana.org (`Example Domains`, `A number of domains such as  and  are maintained ...`). The empty gaps are a snag: inline links are embedded objects (U+FFFC) inside the paragraph's text, and the quick probe dropped them; the driver must expand them through the Hypertext interface.

### Step 5: the click that changed nothing (the most important snag)

`find` returned `link 'assistive technology' extents (253, 541, 144, 18)`; the click at (325, 550) landed, exit 0, and the page did not change. The screenshot showed why: after the extents were read, Wikipedia inserted a donation banner at the top and pushed the article down by about 355 px. The click hit empty space. Re-reading gave the link at (253, 896); the new `at` hit-test (AT-SPI `get_accessible_at_point` at the click point, walked down to the deepest child) answered:

```
at 325 550 -> landmark:'' < section:''
at 325 905 -> static:'assistive technology' < link:'assistive technology' < paragraph:'' < ...
```

With the guard (find showing-only element, hit-test the centre, check the active window, then click):

```
CLICKED 325,905 -> document in 2380 ms
DOC 'Assistive technology - Wikipedia' ... 'URI': 'https://en.wikipedia.org/wiki/Assistive_technology'
```

The same step also showed that `find` on a large page returns off-screen matches (extents y=2673, 8267, 15410 with `showing=False`): the driver must refuse to click those, or scroll first.

### Step 6: a button and a text field

```
CLICKED 728,522 (link 'Search')                       # opens Wikipedia's search field
FOCUSED combo box 'Search Wikipedia'                  # read from the tree's focused state
xdotool type --delay 15 "screen reader"
CLICKED 703,164 (push button 'Search' extents (668, 148, 71, 32))
button -> document in 4659 ms
DOC 'Screen reader - Wikipedia' ... 'URI': 'https://en.wikipedia.org/wiki/Screen_reader'
```

### Step 7: the input is real input

A `data:` page typed into the omnibox carried one button whose click handler wrote `T` or `F` (the event's `isTrusted`) plus `clientX` into its own label. After a guarded `xdotool` click the tree read `push button 'T45'`: the page saw a trusted click. `xdotool` without `--window` injects through XTEST, the same path as a physical device; with `--window` it uses `XSendEvent`, which marks the event as synthetic, so the driver never passes `--window` to an input command.

### Step 8: operator-idle and window-only screenshot

The X session's idle time is readable without new packages through `libXss.so.1` (`XScreenSaverQueryInfo`, via python ctypes): `x-idle-ms 718` right after the driver's own input, so the driver must keep its own-input tick (as the Windows driver does) to tell its input from the operator's. `import -window 46137347 /tmp/act138-win.png` gave a 1050x953 PNG of the Chrome window only.

## Proposed design

### What the Linux driver can and cannot do

Like the Windows driver, and unlike the macOS tools: it **reads** through the accessibility tree (names, roles, rectangles, text, the document URI and title, focus and states) and **acts** through real OS input (mouse, keyboard). Real input carries user activation (an OAuth popup opens, a "a person clicked" check passes). It has **no page-world JavaScript**: there is no Linux equivalent of macOS's "Allow JavaScript from Apple Events", so `chrome-js.sh` / `chrome-mainworld.sh` (read a page's own variables, call its functions, find out why a control refuses) have no Linux twin. When an operator task needs page JavaScript, the agent says so plainly.

Other JavaScript channels were weighed and not chosen:
- **A Chrome extension with native messaging** would give page JavaScript, but branded Chrome no longer honours `--load-extension`, so it needs a Web Store listing or an enterprise policy file under `/etc/opt/chrome/policies` (root); it is visible to pages that probe for extensions; it adds an install and update surface per machine and per profile; and it is a second, privileged control channel into a signed-in profile. Not worth it for the reading the tree already gives.
- **`javascript:` typed into the omnibox** does run in the page, but it is a URL the url rule forbids everywhere, it lands in omnibox history and suggestions, and a non-undefined result replaces the page. Rejected.
- **CDP / `--remote-debugging-port` / WebDriver:** forbidden by the shared rules.

### Threat model (what the rules are, and are not)

On an X11 desktop every client that holds the display's cookie can inject input through XTEST, record other clients' input, and read any application's AT-SPI tree; every process of the same Linux user can read `/proc/<pid>/cmdline` and `/proc/<pid>/environ`, and the agent itself has a shell and could call `xdotool` or `python3` directly. The wrapper and driver are therefore **guardrails against an honest agent's mistakes** (wrong window, wrong page, wrong moment, a secret on argv, a stale coordinate), the same posture `ndrive.sh` states for Windows and the macOS scripts' jail states for macOS. They are not a boundary against same-user code. Two consequences are stated in the skill: a value typed into the signed-in Chrome is visible to every client of that display while it is typed, and the profile directory is as safe as that user's files (see the password store below). The agent's own HTTP file API never serves a profile or the driver's state: `.instar/state/playwright-profiles/` and `.instar/state/xdrive/` (with and without the `.instar/` lead) join `NEVER_SERVED_PREFIXES` in `src/server/fileRoutes.ts`, which also closes the same path for macOS profiles (Windows profiles live on the Windows side, outside the agent home). The profiles prefix keeps its trailing slash, so `state/playwright-profiles.json` is unaffected. Both script headers say this and name the governing standards (Signal vs. Authority; Verify the State, Not Its Symbol; A Decision That Can Block Must Live Where the Checks Can See It).

### Command surface (mirrors `native-drive.ps1`)

All through `.instar/scripts/browser/xdrive.sh <cmd> [args]`; the wrapper runs `/usr/bin/python3 -I x-drive.py` under `env -i` with the same allowlist Chrome gets (the system interpreter in isolated mode with a clean environment, so a venv, pyenv, `PYTHONPATH`, `GI_TYPELIB_PATH`, `LD_PRELOAD` / `LD_LIBRARY_PATH` or a file planted beside the script cannot replace `gi` or the X libraries by accident; the dependency probe checks the same interpreter) with `gi.repository.Atspi` and ctypes `libXtst` / `libXss` / `libX11` / `libXi`, one command per invocation. All input is injected in this one process (`XTestFakeKeyEvent`, `XTestFakeMotionEvent`, `XTestFakeButtonEvent`), and window queries and activation use libX11 directly (`_NET_CLIENT_LIST` with `_NET_WM_PID`, `XQueryPointer`, a `_NET_ACTIVE_WINDOW` client message), so the driver knows exactly which events it injected and `xdotool` is not a dependency. The driver runs under the per-command deadline below. Every driver run starts with the X-side session checks below (the `XWAYLAND` extension query, the EWMH check and the XInput2 version check) in the same process, so a command costs one python start.

| Command | Linux mechanism |
|---|---|
| `launch <profileId> <url> [--new]` | Resolves the profile to `.instar/state/playwright-profiles/<profileId>`. A missing profile folder is refused (`ERR no-profile`: a signed-out browser looks like a lost login) unless `--new` is given, which creates it 0700 and picks its password store; `--new` on an existing folder is refused (`ERR profile-exists`). Execs `/opt/google/chrome/chrome` directly, not the `google-chrome` shell wrapper (resolved from `google-chrome` / `google-chrome-stable`; any other browser binary → `ERR unsupported-browser`) with `--user-data-dir=<dir> --password-store=<store> --ozone-platform=x11 --no-first-run --no-default-browser-check --force-renderer-accessibility --new-window <url>`, under `env -i` with only `DISPLAY`, `XAUTHORITY`, `DBUS_SESSION_BUS_ADDRESS`, `XDG_RUNTIME_DIR`, `HOME`, `PATH`, `LANG`, `LC_*` and `ACCESSIBILITY_ENABLED=1`, detached with `setsid`. Binds the browser pid (the process whose `/proc/<pid>/cmdline` carries that `--user-data-dir` and no `--type=`) with its start time, and its AT-SPI app (matched by pid). Refused if Chrome already runs on that profile (use `attach`). Records the launch in the browser ledger (`chrome-ledger.sh`). |
| `attach <profileId>` | Binds an already-running Chrome on that profile; refuses `ERR no-atspi` if it is not on the AT-SPI bus (launched without `ACCESSIBILITY_ENABLED=1`), and `ERR chrome-environment` if its `/proc/<pid>/environ` carries any variable outside the launch allowlist (a Chrome started some other way may hold the agent's tokens). |
| `target` / `canfocus` / `focus` / `windows` / `switch <n>` | Print the binding (profile, pid, top-level windows, which is active) / read-only "may input be sent now" (exit 2 with the reason when not) / bring the bound pid's most recent window forward (a `_NET_ACTIVE_WINDOW` client message, then verified) / list the bound pid's top-level windows with titles / bring window N forward. `focus` and `switch` obey the operator rule. |
| `nav <url>` / `url` / `title` | Ctrl+L, type the url, Delete (drops an inline autocompletion), Enter; then wait (15 s cap) for the active frame's AT-SPI `document:load-complete` event, which covers a reload of the same URL and a new document alike; a `URI` change with no load event is reported as `SAME-DOCUMENT`; no event and no change → `NAV-TIMEOUT` (exit 3). Prints requested and final URI; a final host other than the requested host → exit 3 `nav-landed-elsewhere` / the active document's `URI` attribute plus the omnibox string / the document title. |
| `text <outfile>` / `tree <outfile>` | Visible text of the active document, embedded objects expanded through the Hypertext interface / the tree (role, name, rect, states) as JSON, UTF-8 without a BOM: the whole document in one best-effort walk of a live page (the agent reads a large file in chunks). A `document:load-complete` event of the active top document, or its `URI` changing, during the walk invalidates it (subframe loads do not): `ERR page-changed; read again` (exit 3), no file kept. The driver iterates the GLib main context without blocking every 500 nodes and before every keystroke, so the event checks actually fire, and re-reads the top document's URI at the end of the walk; output streams to a temporary file in `out/`, renamed when the walk finishes and deleted on `page-changed`. The walk stops at 200000 nodes, 20 MB, or the command deadline minus 5 s, and then the last line is `TRUNCATED at <n> nodes (<reason>); the rest of the document was not read` with exit 3 (the skill says: never conclude something is absent from a truncated read). Ledger updated; binding removed when the process is gone. |

**Post-state, not success.** Every input command ends by printing what is observable 500 ms later: the active document's URI and title, the focused element (role and name), and whether the URI changed. The verdict word is `DELIVERED` (input sent, checks passed). With `XD_EXPECT=nav` the command waits for a new document (250 ms poll, 15 s cap) and answers `NAVIGATED` or `NO-NAVIGATION` (exit 3). Whether the operator's task succeeded (a setting saved, a dialog opened) is the agent's action-specific read-back, which the skill requires; an input command never reports a task as done.

**Page text is escaped, URIs are redacted.** Every page-derived string the driver prints (names, text, URIs) has control characters, newlines and Unicode format and separator characters (categories Cc, Cf, Zl, Zp, incl. bidi overrides) escaped, so a page cannot forge a driver line such as `CLICKED` or `ERR`. Every URI or address string the driver prints or writes (post-state, `nav`, `url` including the omnibox string, `find` including `browser` scope, the tree), with or without a scheme, and with parameter names percent-decoded before matching (a decoded match redacts every value on the line), has the value of every credential-shaped query or fragment parameter (the url rule's list: code, token, key, secret, password, otp, auth, sig, ticket and their variants) replaced by `[redacted]`, so an OAuth redirect's code never reaches the agent's transcript. When an element's accessible name differs from its visible text, `find` prints both and marks `name≠text`.

### Rules the wrapper and driver enforce

- **Platform and session.** `uname -s` must be `Linux` and `powershell.exe` must not be reachable (otherwise `ndrive.sh` is the right tool: `ERR use-ndrive`). The session type is decided by the resolved X server itself, never by an environment variable: the display carries the `XWAYLAND` extension (Xwayland 23.1 and later) or RandR outputs named `XWAYLAND*` (older Xwayland), both queried by the driver at the start of every run → `ERR wayland-unsupported`. `WAYLAND_DISPLAY` in a desktop process's environment and `loginctl` `Type=wayland` (the process's own logind session, read from `/proc/<pid>/cgroup`) only shape the message and drop candidates (below), because a VNC user service started beside a GNOME Wayland login can inherit `WAYLAND_DISPLAY` while running a real X server. The refusal names the ways out: a separate TigerVNC + desktop session for the agent (the arrangement proven on Cirrus; beside a Wayland login of the same user it is a live-gate row below), or logging in to an "on Xorg" session where the desktop still offers one (some KDE Plasma 6 releases do; GNOME 49 and later, and the distributions that ship it, do not). The extension query failing → `ERR session-unknown`. No display → `ERR no-display`.
- **Finding the desktop.** An Instar agent is often started outside the desktop (systemd user unit, tmux, ssh). Candidates: the wrapper's own `DISPLAY` / `XAUTHORITY` / `DBUS_SESSION_BUS_ADDRESS`, and the same three variables (and `WAYLAND_DISPLAY`, read only for the check above) from desktop-session processes (`xfce4-session`, `gnome-session-binary`, `plasmashell`, `mate-session`, `cinnamon-session`) owned by the same uid. A candidate from a process whose own login session is `Type=wayland` (its `DISPLAY` is that session's on-demand Xwayland) is dropped before counting and never connected to, so probing never starts an Xwayland on the operator's session. Nothing else is read from another process's environment, nothing read is logged, and only the resolved three are cached. A candidate counts only after probing: the X server accepts the connection with that `XAUTHORITY` (a file owned by this uid), and the bus address (`unix:path=` under `/run/user/<uid>/` or `/tmp/`, a socket owned by this uid, or `unix:abstract=` with the peer's uid checked through `SO_PEERCRED`) answers `org.a11y.Bus.GetAddress`. More than one live desktop → `ERR ambiguous-desktop` unless `XD_DISPLAY` names one. None → `ERR no-desktop-session`, which names `XD_DISPLAY` as the way to point at a desktop whose session process is not in the list (LXQt, LXDE, a bare window manager from a VNC `xstartup`); a named display is still probed the same way. Never another user's display.
- **Dependencies.** `/usr/bin/python3` with `gi` and the `Atspi 2.0` typelib, `libXtst.so.6`, `libXss.so.1`, `libXi.so.6`, `flock`, `timeout`, and `import` (only for `shot`). A missing one → `ERR missing-dependency: <package>`. The runnable line printed is the one measured on Ubuntu 24.04 (`sudo apt-get install -y python3-gi gir1.2-atspi-2.0 libxss1 libxtst6 libxi6`, plus `imagemagick` for `shot`; the live gate runs this line verbatim in a clean Ubuntu 24.04 container on Cirrus before it is called measured); on other distributions only the package names are printed, as hints. The wrapper never installs anything and never calls sudo.
- **Accessibility switch, scoped.** `ACCESSIBILITY_ENABLED=1` is set only in Chrome's environment. The wrapper never flips the session-wide `org.a11y.Status IsEnabled` or the GNOME `toolkit-accessibility` key.
- **Chrome's environment.** `env -i` plus the allowlist in the `launch` row: Chrome and its renderers never inherit the agent's tokens or keys (`INSTAR_AUTH_TOKEN`, `BW_SESSION`, `GH_TOKEN`, provider keys).
- **Password store.** At profile creation the wrapper picks the store once and records it in `<profile>/.instar-password-store`: `gnome-libsecret` when `org.freedesktop.secrets` answers on the session bus AND its default collection reports `Locked` false (a keyring that a VNC or ssh-started session never unlocked would put an unlock prompt in front of every launch), otherwise `basic` with a warning on every launch (`basic` encrypts with a fixed key Chrome ships, so the profile's sessions are protected only by file permissions). Later launches always use the recorded store (switching would leave the cookies unreadable); an existing profile with no marker → `ERR profile-store-unknown`, never re-chosen; a `gnome-libsecret` profile whose collection is locked at launch → `ERR keyring-locked`, and the skill tells the agent to ask the operator to unlock it. The profile directory is created 0700 and the wrapper refuses a profile directory whose mode is wider (`ERR profile-permissions`).
- **Flags.** The launcher adds exactly the flags above. Extra flags only through `XD_CHROME_FLAGS` with the Windows allowlist (`--disable-extensions`, `--start-maximized`, `--new-window`, `--window-size=W,H`, `--window-position=X,Y`, `--lang=xx`); anything else, in any spelling, is refused. `--force-renderer-accessibility` is an accessibility switch, not an automation flag: it does not set `navigator.webdriver` or open a port.
- **Profile jail.** A profile is a directory `.instar/state/playwright-profiles/<id>` in this agent's home, the same folder the ledger accepts; the id follows the shipped registry rule `^[a-z0-9-]{1,64}$`; the resolved path (realpath) must stay inside that folder (`ERR bad-profile-path` / `ERR profile-outside-agent-home`). Operator profiles (`~/.config/google-chrome*`, `~/.config/chromium`, `~/snap/...`, `~/.var/app/...`) are therefore unreachable by construction.
- **Url rule.** `launch` / `nav` url must carry a scheme, no whitespace, quote or control character, never `javascript:` (`ERR bad-url`), and no credential-shaped query or fragment parameter (`ERR secret-shaped-url`, never echoed), as on the other platforms.
- **Outfile rule.** `text`, `tree` and `shot` write only to an absolute path under `.instar/state/xdrive/out/` (folder 0700, files 0600; no `..`, no control character), so signed-in page content does not land in a synced or shared folder (`ERR bad-outfile`). Outfiles are scratch: the skill says to delete each after reading, and every wrapper call removes outfiles older than 24 h and, beyond 200 MB in total, the oldest ones that are more than 10 minutes old.
- **Binding.** Every command that sends input or reads a page requires `XD_PROFILE=<profileId>` and refuses `ERR wrong-profile` when the binding names another profile, so two sessions of one agent driving two profiles cannot act on each other's Chrome. `.instar/state/xdrive/target.json`: profile, pid, pid start time (`/proc/<pid>/stat`), resolved display. Every command re-checks the pid is alive with the same start time and still carries that `--user-data-dir`; otherwise `ERR no-target`. Any top-level window whose pid is the bound pid is a bound window (`_NET_WM_PID`, set by the client; a same-user program lying about it is outside the threat model), so OAuth popups and new windows are reachable through `windows` / `switch`.
- **One call at a time.** A per-agent lock (`flock` on `.instar/state/xdrive/agent.lock`; bounded wait `XD_LOCK_WAIT` 0-900 s, default 30; the kernel releases it when its holder dies) gives `ERR busy` to a second caller of this agent. Every command that sends input or changes the active window (`launch`, `focus`, `switch`, `nav`, `click`, `invoke`, `clickxy`, the typing commands, `key`, `ctrl`, `close`, and `release`) also takes a per-display lock: `flock` on `/run/user/<uid>/instar-xdrive-<display number>.lock`, the path built from the uid and the display number with host and screen parts removed (so `:1`, `:1.0` and `localhost:1` share one lock), same bound; that folder missing → `ERR busy-lock-unavailable`. Two agents on one desktop never act at once. Order within a call: per-agent lock, then the per-display lock (taken by every input command, and by any call that finds a latch), then the latch check and, when a latch exists, `release` (which then writes the own-input mark), then (for an input command) the latch write; only the lock holder writes or removes the latch, and a refusal before any input creates none.
- **Deadline and unknown outcome.** Each driver run is bounded by `XD_CMD_TIMEOUT` (10-900 s, default 60) through `timeout --kill-after=5`, in its own process group; every AT-SPI call carries a 5 s D-Bus timeout. Before starting any input command the wrapper writes the unknown-outcome latch (`.instar/state/xdrive/unknown-outcome`, recording the bound profile and the resolved display) and removes it only on a clean verdict, so a wrapper killed from outside (the caller's own tool timeout, SIGKILL) still leaves the latch. The wrapper passes its own pid and start time to the driver as arguments; before every keystroke and click the driver checks them against `/proc` and stops when the wrapper is gone, so it never acts unwatched (a parent-death signal would watch `timeout`, not the wrapper). The driver tracks every key and button it has pressed and not yet released; on any stop, refusal or caught signal it releases them before exiting, and whenever the latch exists, the next wrapper call (any command, before anything else) runs `x-drive.py release`, which, under that display's lock and on the display the latch records, first runs part (1) of the operator rule against the existing mark: with the operator active it sends nothing, keeps the old mark and answers `refused: operator active` (the release stays pending; it never releases a key the operator may be holding mid-drag); otherwise it sends a release for every keycode and buttons 1-5 (a release of a key that is not down is a no-op) and then writes the own-input mark. The pending release is also recorded per display (`/run/user/<uid>/instar-xdrive-<display number>.release-pending`, written with the latch, removed by `release`), and every agent's input command on that display runs the pending release first under the display lock, so another agent cannot type with a modifier the crashed driver left held. Together, a key left held by a killed driver is released before any further input on that display, by any agent. On a timeout, a crash, or a signal, the wrapper kills the process group, waits for it to exit, and answers `ERR driver-timeout` / `ERR driver-crash` (exit 1). While the latch exists every input command answers `ERR unknown-outcome-unchecked` (exit 2); a successful document read (`url`, `title`, `text`, `tree`, `find` without `browser`, `editfields`) with `XD_PROFILE` equal to the latched profile clears it; `target`, `shot`, `find browser` and a read of another profile do not. Input under another profile while the latch exists → `ERR unknown-outcome-unchecked` naming the latched profile. When the latched profile's Chrome is gone (the pid has exited or has another start time), the next call clears the latch and logs `latch cleared: bound Chrome gone`, since the page the input might have reached no longer exists; `launch` of that profile is then allowed. Under a latch, `close --force` sends only signals (no keystrokes), so a hung Chrome can always be ended.
- **Expected host.** `XD_EXPECT_HOST` (optional for most input, required for `typesecret` / `typesecretedit`; at least two labels, a single label such as `com` → `ERR bad-argument`): before the input, the host of the document the input lands in must equal it: for typing and keys, the document that contains the focused element; for `click` and `clickxy`, the document that contains the hit-test target; for `invoke`, the match's own document (each walked up to the nearest document, so a cross-origin login, payment or permission iframe is judged by its own origin, not the top page's). It must equal it or end in `.` + it, compared at the host boundary; otherwise `ERR wrong-host` (exit 2). For secrets the host must equal it exactly. The check repeats after the last keystroke on the destination document (the one the input landed in); if that document has gone (a submitted iframe, a navigation) the result reports that, not `wrong-host`. The top document's host is reported in the post-state, not compared. `nav` is exempt (its focus is the omnibox), and the post-`nav` host check covers it. Two labels is a floor, not a public-suffix check. An empty or unreadable URI → `ERR no-active-document`.
- **Input only into the bound window and the intended element.** At the start of a typing command the driver pins the active window id and the focused accessible object (which, for a typing command, must be inside the active document unless the command is `nav`'s omnibox step). Before every keystroke and click: the wrapper-alive check, the operator rule, and, for typing, the focused accessible object, queried synchronously, must still be the pinned one; X input focus (`XGetInputFocus`, walked up through parent windows to the client top-level; `PointerRoot` or `None` refuses) and the window manager's `_NET_ACTIVE_WINDOW` must both be the pinned window. The driver also listens, for the length of the command, to AT-SPI `focus` and `document:load-complete` events (asynchronous, so they back up the synchronous per-keystroke query): a focus change away from the pinned element, a new window or a load of a document in the pinned element's document chain stops typing at once with `refused: focus left the target mid-typing (stopped)`, nothing echoed. No EWMH window manager → `ERR no-window-manager`. A keyring or polkit prompt (another pid) therefore refuses input. Before typing, the driver reads the keyboard lock and latch state (`XkbGetState`): Caps Lock, a latched modifier or a locked non-default group → `ERR modifier-locked` (exit 2), nothing typed and nothing toggled (toggling would change the operator's state). Num Lock is ignored, since no typed character depends on it.
- **Operator rule.** Two parts. (1) Before a command: the driver keeps, in memory during its run and written on every exit path, the server's last-input time after its own last injected event (server time minus `XScreenSaverQueryInfo` idle, after `XSync`) as the own-input mark. The mark is kept per display, beside the per-display lock (`/run/user/<uid>/instar-xdrive-<display number>.mark`; a mark left by a restarted server reads as "operator active" until 30 s of idle or the driver's next own write, which fails safe), and written only while that lock is held, so one agent's input is never another agent's "operator". The operator counts as active when idle is below `XD_OPERATOR_IDLE_MS` (default 30000) and the server's current last-input time differs from the mark by more than the tolerance; the tolerance ships as `min(2 x the live gate's measured p99, 50 ms)`, and a measurement above 50 ms is a FAIL row: the driver then ships answering `refused: operator presence unmeasurable` on such a display, and the skill states the limit. This is the Windows driver's exact-equality rule with a measured tolerance. (2) During a command: `x-drive.py` selects XInput2 raw key, button and motion events on the root window for its whole run. An event from any device other than the `Virtual core XTEST` devices stops the command (Xvnc viewer input and physical input). XTEST events are counted against the driver's own injections, all made in this process (it flushes with `XSync` after each and drains its own; XTEST devices are identified by their `XIQueryDevice` attachment, not by name alone): an XTEST event beyond that count, or one arriving while nothing of its own is outstanding (the 150 ms click settle, the gap between keystrokes), is foreign and also stops the command. That second half catches operator input relayed through XTEST by `x11vnc`, `x0vncserver`, Chrome Remote Desktop's X11 host or RustDesk. Both are checked before every keystroke and click: `refused: operator active (stopped)` (exit 2). No XInput2 2.2 on the display, or idle time unreadable → `refused: operator presence unmeasurable` (exit 2). Stated limit: a foreign XTEST event perfectly interleaved with the driver's own is not distinguishable. `XD_ALLOW_FOCUS_STEAL=1` and an `XD_OPERATOR_IDLE_MS` below 30000 are honoured only against a current `normalChromeBrowser.unattendedMachine` record, with the same shape (non-empty `declaredBy`, integer non-zero `topicId`, an `at` within 30 days), the same `node -e` reader and the same no-node-means-attended rule as `ndrive.sh`; otherwise they are dropped, warned and the dropped name logged. The overrides relax only part (1) and the window-raise refusal of `focus` / `switch`; part (2), the stop on the operator's input during a command, is never overridable.
- **Hit-test and pointer check before every click.** As in the `click` row. This is the rule the proof's Step 5 earned; the 150 ms move-then-recheck closes a page swapping the element on hover, and the pointer-position check closes the pointer having moved. The gap between the last check and the click (a few ms) remains; the post-state read is the backstop.
- **Browser-UI dialogs are the operator's.** `click` / `invoke` with `browser` scope, `clickxy` on a point whose hit-test chain is inside one, and `key` / `ctrl` / typing with the focus inside one, all refuse in any browser-UI dialog, alert or bubble outside the document (permission prompts, password save, dangerous download, extension install): `ERR browser-dialog-operator-only`.
- **No synthetic events.** All pointer and keyboard input goes through XTEST from the driver's own process (`XTestFakeMotionEvent`, `XTestFakeButtonEvent`, `XTestFakeKeyEvent`); the proof's `--window` trap (Step 7) cannot arise because no `xdotool` input command exists. No `XSendEvent`, no AT-SPI `generate_keyboard_event` / `generate_mouse_event`, no synthetic hover. Field focus for `typeedit` is AT-SPI `grab_focus`, verified by the `focused` state, as Windows uses UIA SetFocus.
- **No typed text on argv.** Every typing command (`type`, `typeedit`, `typesecret`, `typesecretedit`) types through `libXtst` from the driver's own memory: the text reaches the driver on stdin, piped straight from the caller through the wrapper, never through an environment variable, a file or any argument; a positional text argument is refused (`ERR bad-argument`). The wrapper passes stdin through untouched (no `read`, no here-string, which older bash spools to a temp file); `x-drive.py` reads it and refuses empty input (`ERR bad-argument: empty input`) before any input. A text whose length times the measured per-keystroke cost would pass the deadline minus 5 s is refused before typing (`ERR text-exceeds-deadline`). Keysyms are looked up on the current keymap; a character with no keycode on the layout is refused before anything is typed (`ERR untypable-character`, no index or count) rather than remapped (remapping would change the global keymap). Secrets: one non-empty printable line, never echoed, no length printed, no Return appended.
- **Page text is untrusted.** Unchanged shared rule; the AT-SPI tree is page text.
- **Things that hold the operator rule shut.** A program that resets the X idle timer (a mouse jiggler, `XResetScreenSaver` callers) keeps `refused: operator active`; the skill names this cause.
- **Recovery limit.** A pending `release` sends key-ups for every key on a display where the operator was idle at that moment; a key the operator presses in the same instant can be released. Rare and harmless; listed in the side-effects review.
- **Secrets after typing.** Only `password text` values are masked. The skill says: after typing a secret into a plain entry (a one-time code), clear the field or leave the page before any read, and never take `shot` on a sign-in callback page (the address bar is in the image; `url` is redacted).
- **Activity log.** One content-free JSON line per call, refusals included, to `.instar/logs/normal-chrome-browser.jsonl` with `via: xdrive`: when, command, exit code, the names of any honoured or dropped override variables and the declaration's topic and time; never arguments, never page content.

### What the existing tools say on Linux after this lands

The macOS tools keep `ERR macos-only`, with the message's last sentence changed to name `xdrive.sh` on Linux. `ndrive.sh`'s `ERR windows-only` names `xdrive.sh` the same way. The skill's three-case "Where it runs" list becomes: macOS, Windows-from-WSL, Linux on X11 (with the Wayland refusal stated).

### Headless servers and virtual displays

The driver needs a desktop session: an X server, a session D-Bus, and the AT-SPI bus launcher. A cloud VM without a desktop has none of these. Cirrus's arrangement (a TigerVNC user service running a full XFCE session on `:1`) is the proven one: the operator can watch and take over through a VNC viewer, and the AT-SPI bus is started by the session. A bare `Xvfb` with no session is not proven; the skill names TigerVNC + a desktop as the setup, and `ERR no-desktop-session` says what is missing. On an operator's own laptop the same arrangement (a second display for the agent) removes input collisions with the operator entirely; the shared-display path stays supported because it is what a person watching their own screen expects. The driver never starts a display, a desktop or a bus itself.

### Browser care on Linux

The macOS care sweep (`BrowserCareSweep`) runs only on macOS, and there it only watches (it runs dry and closes nothing). On Linux the ledger line is a record (bounded at one entry per profile); nothing sweeps forgotten Chromes, and `close` is the cleanup the skill requires at the end of every task. The `browser-instance-ledger` retention note in the state-coherence registry and the `src/commands/server.ts` comment that only macOS helpers keep a ledger are corrected to say this.

## Multi-machine posture

Default posture is unified: the skill, the card and the scripts are shipped content, identical everywhere through the update path.

- The browser profiles the driver acts on.
  - machine-local-justification: physical-credential-locality impossible-because="a signed-in Chrome profile holds live session credentials on that disk, encrypted by that Linux user's keyring or, with the basic store, protected only by file permissions; Chrome's profile lock (SingletonLock) makes a live profile single-writer on one host, and a `gnome-libsecret` profile's key sits in that machine's keyring; replicating a `basic` profile would copy usable credentials between machines, which the skill forbids" permanence=permanent

## Alternatives considered

- **Flip the session-wide accessibility switch** (`org.a11y.Status IsEnabled=true` or the GNOME key) instead of `ACCESSIBILITY_ENABLED=1`. Rejected: it changes every application on the operator's desktop; the per-process variable was proven sufficient.
- **Raw D-Bus calls (`gdbus`/`busctl`) to the AT-SPI bus instead of the `gi` bindings.** Possible, but a tree walk is thousands of calls and the Collection match rules are awkward to marshal from the shell; the typelib is one small distro package.
- **`xdotool type` for typing.** Rejected: the text sits on argv, and a character missing from the layout makes xdotool rewrite the global keymap.
- **Idle time alone for operator presence during a command.** Rejected: the driver's own keystrokes arrive every few milliseconds, so any operator input during typing would hide behind them. The XInput2 listener lives only for one driver run, so no daemon is needed.
- **`ydotool` (kernel uinput) to reach Wayland.** Not chosen: it needs root or the `input` group, injects into whatever has focus with no way to check which window that is, and AT-SPI extents are not global screen coordinates on Wayland.
- **The XDG RemoteDesktop portal / libei on Wayland.** Not chosen: per-session consent at the screen fits presence rules but not an unattended VM, and the active-window and coordinate problems remain.
- **Chromium (distro or snap).** Not supported in this version: the snap's confinement cannot use a profile under a hidden folder in `$HOME`, and the proof ran on Google Chrome only.
- **Playwright with a "stealth" configuration.** Rejected by the skill's founding rule: an automated browser presented as a person.
- **A dedicated display for the agent as the only path.** Giving the agent its own Xvnc display removes most input collisions, and it is the recommended setup on a server and on a Wayland laptop. The shared display stays supported because a person working on their own X11 desktop expects to watch the agent there, and the operator-presence rules exist for that case.
- **One wrapper for Windows and Linux.** Rejected for the reason the cross-platform spec kept two command surfaces: the mechanisms differ; a merged script would be harder to test on either.

## Side effects and rollback

- Existing Linux agents: two new scripts, changed skill text and card; nothing runs until invoked. macOS and Windows agents: changed refusal text and skill text only.
- On the Linux machine, a launch creates the profile directory under the agent home and a Chrome process with renderer accessibility on for its whole life (CPU and memory cost recorded by the live gate).
- Accepted unknown: whether a site's passive risk scoring can tell a Chrome with accessibility on from one without. `navigator.webdriver` is unaffected and no port opens; the live gate shows pages still work, not that scoring is unchanged. The skill states this.
- Rollback: revert the release. The installed `xdrive.sh` / `x-drive.py` stay on disk (the installer only overwrites) and still work, but receive no fixes; the skill copy keeps the Linux section until the next update; the card follows the cross-platform spec's revert behaviour: the older migrator appends the v2 card beside v3 until the next forward update removes the stale v2 section, so for that window the agent sees two cards.

## Frontloaded Decisions

- **Accessibility and passive scoring:** accepted unknown, stated in the skill and in Side effects; not a blocker.
- **Wayland:** refused with `ERR wayland-unsupported` and the ways out; no Wayland driver is built. Linux support covers X11 desktops and VMs; a current GNOME desktop (no Xorg session) is reached only through a second TigerVNC session for the agent.
- **`invoke` and user activation:** shipped behind `canfocus`; the skill states the live gate's measured answer, and until measured says "may not count as a person's click; use `click` for OAuth-style buttons".
- **Typing:** every typing command types through `libXtst` from stdin; `xdotool type` is never used.
- **Profile location:** `.instar/state/playwright-profiles/<id>` only. A profile the operator set up elsewhere (Cirrus's `~/.config/chrome-instar`) is not driven; the agent creates a profile in the profiles folder and the operator signs it in once.
- **Password store:** `gnome-libsecret` when a secrets service answers and its default collection is unlocked, else `basic` with a warning; recorded per profile at creation.
- **Browser:** Google Chrome only; Chromium refused.
- **Dependencies:** the wrapper refuses and prints the install line; `init` does not check; whether the agent runs the line is the judgment row in the decision table (floor: measured line only, `sudo -n true`, an operator-asked task in progress, logged; default: send the operator the line).
- **Operator watching over VNC:** watching is not input; the driver may act while the operator watches, and the operator's first touch stops it. The skill says so.
- **Wayland live test:** a headless `weston` + Xwayland session on Cirrus; no second host needed.
- **Sign-in repair on Linux:** unchanged by this spec.
- **Browser care on Linux:** no sweep in this spec; `close` is the cleanup.
- **Lint:** population widened to `.py`; both files declared non-blocking (self-scoped refusals) and content-pinned.
- **Interpreter:** `/usr/bin/python3 -I`.
- **Operator presence:** per-display own-input mark with a measured tolerance before a command; XInput2 source-device listener plus XTEST event counting during it.
- **New profiles:** only with `--new`; registry id rule.
- **Typing input:** stdin for every typing command.
- **Input mechanism:** all input in-process through libXtst; no `xdotool`.
- **Closing:** `close` never kills a Chrome with a blocking dialog or unsaved input; `--force` only on the operator's say-so.
- **Profile per call:** `XD_PROFILE` required on input and read commands.
- **File API:** profiles and driver state never served.
- **Deadlines and caps:** `XD_CMD_TIMEOUT` 60 s (10-900), D-Bus 5 s, nav and `XD_EXPECT=nav` 15 s, lock wait 30 s (0-900; the skill tells the agent to set its own tool timeout above lock waits + command timeout + 10 s), close 10 s / 20 s, `find` 200 candidates, `text`/`tree` 200000 nodes / 20 MB, outfiles 24 h / 200 MB, activity log 5 MB. Derivations: 200 candidates is about 1.5 s of per-candidate name reads at the proof's measured rate (the live gate replaces it with a 3 s budget if it proves too small); 200000 nodes / 20 MB is roughly ten times the proof's largest page and ends earlier on the deadline anyway; the D-Bus 5 s timeout is ten times the slowest single call measured; 15 s for a navigation is three times the slowest measured (4.7 s).
