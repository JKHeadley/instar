# One Question For Several Conversation Changes

## Problem and scope

Moving several conversations currently takes a separate confirmation question for each one. The Chief of Staff reported repeated confirmation questions in handoff42296876. This document cites that relay, not an independently inspected owner quotation. Build its immediate batch slice: one question can list several target conversations, one exact native-reply yes applies their described settings, and one plain completion gives the result. Keep the existing long shown deadline, intentional reminders and noncancellation by interleaved messages. A limit on how often the agent creates new questions must never block an owner who is answering a question already asked.

Restart-safe intent continuity is the separate immediately following slice allowed by that assignment. The initial combined draft and both rounds' findings are preserved privately at profile-confirmation-batch-and-restart-round2-draft.md and profile-batch-round{1,2}-*. No restart carry-over, auto-repost, survivor durability or new archive guarantee is claimed by this slice. After a restart, old receipt grants remain invalid under the existing lifetime-and-receipt repair. Do not mark the whole assignment complete when this slice lands.

## One completion and owner-funded reminders

One generation-local synchronous CAS owns acknowledgment for the accepted inbound. Concurrent consumers share the saved result but only that claimant sends the aggregate completion. Timeout after send is unknown delivery and is not automatically resent. A later actual owner inquiry can receive the saved result. The existing delivery/notification lifecycle also owns a typed acknowledgment-delivery incident: it reconciles known receipts, retries only a verified definitely-not-dispatched failure under existing transport policy, and raises one bounded terminal unknown-delivery notice when acceptance cannot be established. This incident cannot reapply settings or blindly send another success. The agent owns follow-through; the owner need not ask to discover a terminal delivery failure. Preserve actual failure notices and normal message receipts. Inspect both polling and lifeline ingress so a consumed confirmation does not produce a delivery checkmark as well. Do not suppress unrelated ordinary-message acknowledgments or model text by matching strings.

For a fresh verified owner turn that identifies pending questions or asks for a new/corrected change, first-party verified ingress after agent-signature reconciliation mints an opaque source/principal/inbound handle. The conversational agent judges which identified requests need clarification. The server validates every selected request and performs side-effect-free validation and exact formatting before spending the handle by synchronous CAS immediately before dispatch of one aggregate question or reminder, never one post per request. This includes a corrected target, patch or engine requiring a fresh descriptor; it bypasses only creation churn and does not require an unchanged pending question. Only compatible plans with distinct target IDs (or identical duplicate effects) may combine; for an unchanged reminder union, use the earliest original deadline and atomically supersede constituent controls only when the new actual receipt is registered AND every constituent remains pending and unclaimed. If any constituent reply wins during send, leave the aggregate receipt inactive and preserve every other pending control; explain the changed situation without applying anything from that aggregate. A fresh owner-requested new/corrected proposal is a separate descriptor with the normal newly shown lifetime, not a reminder union; its new receipt does not revive or extend any prior grant. Conflicts in an unchanged reminder union require one plain clarifying question and apply nothing. If the aggregate does not fit, the agent chooses a fitting fully disclosed subset or sensible sequential partition from the already clear task; it asks the person only when their preference is actually missing. It never silently omits targets or posts a burst of separate questions. The HTTP size refusal supplies enough diagnostics for that planning. Apply the same actual-formatter budget to the aggregate completion: when names and runtime details do not fit, send concise independent settings and runtime summaries: settings counts include fully saved, preview-only and refused fields; runtime counts include verified, pending, skipped and failed with details available on owner inquiry; never silently drop a failed target or emit multiple success posts. No caller-supplied owner ID or bypass flag can mint the allowance.

The handle bypasses only creation churn, not principal, placement, deadline, exact consent or actual receipt checks.
