# Preview Job Definition Migration

## Problem statement

Jobs can be present in the old job file, in individual schedule manifests, or in both. An identical slug can conceal a different executor, enabled state, or placement. Jobs already reports file setup issues, but that report does not explain which definition the loader selected or what would change in a migration. The owner needs that evidence before authorizing a separate transition.

This draft follows [Jobs, Projects, and Standing Responsibilities](jobs-projects-standing-responsibilities.md) and its canonical definition direction. The same umbrella also covers B2 project custody. **Structure beats Willpower** governs the reconciliation path. **Cross-Store Coherence Is an Invariant**, **Cross-Machine Coherence**, and **Signal vs. Authority** govern the preview's identity, visibility and limits.

## Frontloaded Decisions

1. Use a disjoint preview branch on the existing authenticated Jobs reconciliation resource. The normal Jobs page gives an eligible owner a **Preview job migration** action even with no structural issues. The action is manual and has no repair or confirmation behavior.
2. Require a current owner-private operator session before file access and before serialization. The console explicitly obtains and supplies the existing server-verified operator X-Instar-Operator-Session using the private unlock pattern in dashboard/console/chats.js:1528. The ordinary Jobs bearer, setup bypass, a raw PIN and a shared or device credential alone cannot request the preview.
3. Show the loader-selected source or an evidence-backed suppression reason, proposed canonical mapping or unresolved disposition, and direction of approved safe changes. Compare actual inputs while keeping loaded definition, scheduler state and future mapping independent.
4. One Jobs view reports enrolled machine coverage. A development build can read the serving machine's files. A complete multi-machine preview requires per-machine owner authorization and authenticated request-bound snapshots.
5. Keep preview evidence advisory. The preview cannot establish cutover readiness, retire a writer, change the loader, restore evidence into execution, or suppress existing warnings.

## Proposed design

Use GET /jobs/reconcile?preview=job-definitions. Accept exactly preview=job-definitions for a first page and exactly preview=job-definitions with one cursor for continuation. Any request containing preview or cursor parameters reserves this branch. Reject malformed or duplicate parameters without invoking ordinary reconciliation. Branch before doing any structural scan, path resolution or worker admission. Verify feature availability and owner-private authorization. The preview returns a separate schema without calling the ordinary structural scanner or including its paths, summaries or errors. Ordinary reconciliation at src/scheduler/AgentMdReconcile.ts:107–215 and src/server/routes.ts:21517–21530 retains its behavior and authorization. The action appears in the ordinary owner Jobs page, including a clean inventory. New and updated installs use the same operator session flow. Reverify the same session, current owner and flag synchronously before serializing, after all worker and peer work. Cancel or discard on disconnect, lost authorization or disable. Use no-store responses and omit consumer data from errors and logs.

Reuse pure normalization and validation from JobLoader and AgentMdJobLoader. Keep the preview separate from their unbounded file reads. Resolve the catalog from the scheduler's approved configured jobsFile, including a supported custom root. Constrain other inputs to their declared trusted roots. Open only regular files on pinned handles, check type, identity and limits on that handle, read bounded bytes from the same handle and reject symlinks, special files and path escape. Before returning, verify stable critical files and bounded directory membership, including expected absence, portable journal, locks, signatures and declared body inputs. A new manifest, replaced handle, lost negative proof or checked input changing makes the affected winner unknown. Extract or reuse a pure selection and suppression routine shared by the preview and production loader. If the existing loader cannot adopt it without changing authority behavior, require differential tests against the actual production loader on the same stable inputs, including duplicates, override/trust interactions, journal ownership, and revoke suppression. Apply actual precedence and portable journal suppression. Leave withheld legacy imports undispatchable.

Compare enabled state, executor kind and normalized options for all four accepted literals, schedule and timezone, placement, runtime limits and gate, delivery behavior, and body and lock provenance. Enumerate source revisions before precedence folds them. Represent invalid rows, identical duplicates, case collisions, missing files and journal-owned slugs with no runnable materialization. Report every effective occurrence the production loader and scheduler keep for that slug, or a suppression reason. A singleton verified effective occurrence can yield a canonical mapping that preserves behavior. If multiple occurrences survive or loader-to-scheduler correspondence cannot be verified, leave a single-manifest mapping unresolved. Test two valid legacy definitions with the same slug and different schedules against the actual loader and scheduler and match their disposition. A script or skill reference must bind to the same authorized runner identity, content and policy evidence through the existing validation path. A matching name or path alone is insufficient. A missing, changed or unverified runner binding leaves its mapping unresolved and cannot promote execution authority. Label both endpoints of each comparison. For example, a disabled legacy variant shadowed by an enabled manifest can show “legacy disabled, selected enabled,” while “selected enabled, proposed enabled” is unchanged on migration. Show directional detail only for approved non-sensitive facts. Do not treat current run-state evidence as a variant or a proposed migration. For private configuration, show field categories only. Return no raw content, paths, exceptions, credentials or equality fingerprints. Matching body text across prompt and agentmd formats does not make the executors equivalent. Report execution parity separately from ownership disposition. Use the existing verified accountable-principal evidence only if present. A known runner with unknown ownership can show execution parity while owner assignment and migration mapping stay unresolved. Do not guess an owner or change existing access or execution. Compare live scheduler state through its read-only validated generation and mark unverified state unknown. Preserve the distinction between same-path validated-body fallback at JobScheduler.ts:528–621 and the proposed mapping.

Run in a cancellable dedicated worker under one evaluation per serving machine, a bounded heap, incremental enumeration and preparse byte limits. Before cohort enrollment, measure real catalog sizes and slow hosts against the hard envelope. Initial test bounds are 1,000 filesystem entries, 10,000 legacy rows, 1 MiB per file, 8 MiB aggregate input, 250 output rows, 512 KiB encoded output and two seconds per worker. Use nonblocking filesystem operations in the preview subprocess. Do not run synchronous filesystem operations on its main thread or wait for them on the server loop. Cooperatively cancel where possible, force termination when needed, and hold the admission slot until observed exit. If the source storage cannot support the tested envelope, report it unavailable and preserve ordinary Jobs. Overlapping requests receive busy with retry guidance. Report the failed component or limit without raw data. Order a complete snapshot by controlled status, normalized slug, source slot, and stable validated occurrence ordinal. For legacy occurrences derive that ordinal from the original parsed array offset. For manifest and diagnostic rows derive it from the canonical confined relative path and a reproducible record position. Keep those coordinates internal and out of source precedence. A different production winner changes the continuation fingerprint. Reversed directory enumeration with the same decisions stays in the same display order. Bind the fingerprint to the validated ordered rows, critical input membership and selection decisions. Emit bounded redacted rows for each variant or diagnostic, with its safe group label. A slug with many variants may span pages. Reserve 1 KiB of a job-page response for its cursor and fixed-size coverage summary and advance after the last item actually emitted, whether the row or encoded-byte cap is first. Keep each emitted row's safe fields short and bounded. An owner can reach conflict 251, tied duplicate variants around that boundary, and records beyond the byte cap without knowing their slugs. A short-lived authenticated encrypted cursor binds session, serving machine, selection, snapshot fingerprint and next position. Expose no clear digest or slug in the cursor and store no persistent cursor registry. Re-run the same bounded read and return continuation only on the same complete snapshot. On mismatch, expiry or different process, ask the owner to restart. An incomplete input scan can return scoped leads and cannot offer a complete continuation or establish absence.


The comparison necessarily reveals whether private definitions exist or collide. Current team job shares supply no verified projection of every contributing row or the absence and coverage signals for a whole inventory. A preview for shared jobs requires an approved scoped comparison projection and its own evidence.

### Cutover and restore boundaries

The existing completion marker is a timestamp written at `src/server/routes.ts:21565–21594`. It quiets the deprecation audit and can suppress an updater attempt. The existing CLI migrates prompts only and its abandon branch removes whole target directories at `src/commands/jobMigrate.ts:203–219,248–321,344–350`. Preserve these as diagnostic historical facts. This preview never calls either mutation or interprets marker presence as convergence.

The existing two-rename save at `src/scheduler/AgentMdAtomicSave.ts:81–150` and version check at `src/server/routes.ts:21645–21696` are per-job operations. The CLI legacy writer at `src/commands/job.ts:32–73` and Jobs toggle at `src/server/routes.ts:22079–22104` can still write the old file. Portable operations pause and refresh the local scheduler at `src/server/routes.ts:21086–21103` and record import provenance in `src/core/JobPortableSync.ts:315–422`. These do not provide a shared writer fence. A later cutover needs an authenticated authority epoch, complete writer and admission drain, parity at a verified high-water, and compatibility writes through the canonical adapter. Before publication, its kill switch stops transition and retains the old authority. After publication, it holds unsafe actions while recovering forward from the authoritative revision. Turning the preview off only stops its collection and presentation.

`src/core/BackupManager.ts:247,925–981` includes the old file by default and restores files individually. A future migration restore is an explicitly authorized, validated forward import against the current authority epoch. Legacy copies, unmatched manifests, old machine state and imported/revoked records cannot acquire execution authority by being restored. Restore and destructive rollback are outside this preview.

## Multi-machine posture

Reuse only the active enrolled identity roster logic in src/core/JobCoverageMonitor.ts:120–126,305–313. Unknown membership makes pool coverage unknown. URL reachability and the Jobs pool cache cannot substitute for the roster. The one Jobs view represents all verified enrolled machines, with unchecked coverage for known offline peers. Job row pagination is per machine. The initial request selects the serving machine. The eventual authenticated pool path will offer a verified machine selector from the coverage page and a server-issued first-page cursor for that machine. Never interleave rows from multiple machine catalogs, even for identical slugs and order keys. Bind each cursor to that catalog snapshot, its authorized machine and the current roster. A selected peer definition changing between pages invalidates that peer cursor. Initial job pages contain only bounded coverage summary counters and a separate encrypted coverage cursor. Use the exact preview request with either no cursor or one encrypted cursor that declares the server-chosen job or coverage lane. Scope continuation to the matching owner session, machine, policy and current membership epoch. Coverage pages contain at most 100 bounded redacted machine-alias rows within the existing byte cap, advance after the last emitted row, and restart if membership or applicable ACL changes. Do not include raw topology or long untrusted labels. If the roster cannot be bounded and authenticated, report unchecked pool coverage without complete counters.

The intended pool reader needs signed machine-bound replies containing expected machine and membership epoch, scoped owner proof, request nonce, redacted payload digest, snapshot time and completeness. The origin verifies current owner scope and eligibility before forwarding. The peer independently verifies its current scope and returns only authorized metadata. The origin verifies the reply and owner scope again at render. A signed peer reply alone does not prove a later revocation is absent. The separately reviewed pool carrier must supply a current peer authorization fence bound to release and order revocation with that release, or withhold the peer rows, aliases and counts and show unchecked coverage. A test revoking access after peer signature but before origin serialization must see unchecked coverage and no private projection. Shared-bearer cached Jobs requests and unsigned generic Mesh RPC replies lack that proof. Use no downgrade to either. The first development increment checks serving-machine inputs and shows other machines unchecked. A reviewed authenticated pool read and positive offline-peer, roster-loss, mismatched reply and remote revocation tests remain fleet release conditions. No durable preview state or shadow registry is created.

## Decision points touched

- Owner admission — invariant; basis: irreversible-consequence; evidence: require verified owner/private server context before catalog reads, and deny scoped and setup-only access.
- Comparison and coverage — invariant; basis: enumerable-domain; evidence: validated loader decisions, fixed field categories, bounded reads and explicit incomplete outcomes.
- Conflict disposition — judgment-candidate. Floor: keep all inputs and current behavior. Default: leave a divergent or uncertain row unresolved. Arbiter: the configured owner uses a future reviewed migration workflow. Fallback: when evidence or owner authority is absent, report unknown.
- Cutover and restore — invariant; basis: irreversible-consequence; evidence: the preview has no mutation path or authority-bearing output.

## Maturation plan

- **test-agent-live:** Use the shipped Jobs view with zero structural findings against an authenticated disposable server. Check a custom legacy path, all four executor types, an identical and divergent slug, overrides, pinned and journal-owned jobs, a revoked import, invalid and case-colliding entries, a manifest appearing after enumeration, symlink and special-file refusal, a stalled worker, a stale historical marker, opposite enabled-state variant differences with unchanged migration outcomes, runner targets changed behind the same name, verified runner with unknown accountable principal, reversed directory order with unchanged and changed winners, coverage large enough to require its own pages, exact output schema for all four executors, effective duplicate occurrences in the real scheduler, same sort keys on different machines and stale selected-peer cursor, and continuation beyond both the 250-row and encoded-byte limits including a single slug with multiple pages and ties crossing a page. Assert no writes, refresh, job start, or payload disclosure.
- **dev-agent-live:** An owner runs a preview against a consenting development agent's existing definitions. Compare result sensitivity and current precedence with trusted local evidence. Verify an enrolled-but-unverified machine is explicit and no private preview data reach it. Record largest observed catalog, peak worker memory, p95 time and denial, invalid and cancellation behavior on typical and slow tested hosts. Require bounded two-second response handling, recovery or honest busy while the old worker exits, normal Jobs responsiveness and complete continuation for the supported target catalog. Leave the cohort dark outside designated tests if measured input and consumer envelopes fail.
- **fleet:** Enable the flag only on specifically designated disposable and consenting development installations while collecting test evidence. Keep all other installations dark until the cohort requirements pass. Require the operator to record the fleet availability decision after the signed pool path passes. Each preview remains manually requested. Honor the kill switch on existing and new installations.
- **graduation criterion:** Unit, authenticated HTTP, real server and normal Jobs lifecycle evidence include owner/guest/device boundaries, in-flight revocation and flag shutdown, bounded busy and incomplete results, continuation past omitted rows and restart on source change, journal suppression, scheduler body fallback ambiguity and zero scheduling effects. No migration enrollment follows preview graduation.
- **dark-window:** The preview flag remains off outside designated qualification installations until test and development evidence is recorded. Disabling it keeps ordinary reconciliation available.
