# Normal-Chrome browser skill: one method for macOS and Windows — plain-English overview

> The one-line version: the Mac way and the Windows way of driving a normal, signed-in Chrome become one built-in skill with one set of rules, and the Windows tool ships to every agent, with Instar's safety rules enforced in a small wrapper around it.

## The problem in one breath

Some web tasks have to be done as a particular signed-in account, and account pages (sign-in, billing, settings, usage) often refuse or behave differently for an automated browser. Instar now has two proven ways around that, but they were built separately: Echo's method on the Mac, which runs small pieces of code inside a normal Chrome window, and PP's method on Windows, which clicks and types with real mouse and keyboard input and reads the page the way a screen reader does. Each knows things the other does not. Worse, an Instar agent on a Windows machine runs inside WSL, which reports itself as Linux, so today's skill tells it the method is Mac-only and to give up.

## What already exists

- **The `/normal-chrome-browser` skill (Mac).** Shipped on 21 October 2026 with three small tools: open a normal Chrome for one profile, run JavaScript in its tab, and read the page's own state. Confined to the agent's own browser profiles; refuses to run off macOS.
- **PP's Windows driver.** One PowerShell script that launches a clean Chrome (no debug port), binds to it, and then clicks, types and reads it with real Windows input and the accessibility tree. Verified on a sign-in and an OAuth popup that automation could not get through. Echo reviewed it and accepted version 5.
- **The update machinery.** Instar refreshes built-in scripts on every update, and has a documented rule for changing the text of a skill that is already installed.

## What this adds

One skill, same name, with a shared rules section both drivers follow and a short driver section for each operating system. The Windows script ships exactly as reviewed and live-tested (the same bytes, checked by hash), together with a small wrapper that is the way Instar agents run it. The skill is honest about what each side can do: real input on Windows counts as a real person's click for things like opening a sign-in popup; the Mac tools run code in the page and cannot produce that. Nothing fakes a person's presence; that was removed on purpose before and stays removed.

Secondary changes:
- **The wrapper enforces Instar's rules on Windows.** It refuses to touch the operator's own Chrome profile, refuses anything that looks like a launch flag in a URL slot or a stray quote that could smuggle one (so a debugging port can never sneak in), accepts only a real chrome.exe as the browser to start, keeps each agent's "which Chrome am I driving" record separate from other agents on the same Windows account, only honours the "take focus anyway" override when the agent's config records that the operator declared the machine unattended, asks the driver whether anyone is using the machine before the one command that can open a window without a real click, reaches the desktop from a background Windows session through the task scheduler, and writes one content-free line per call (command, result, which route, never arguments or values) to the same activity log the Mac tools use.
- **Each side's lessons now protect the other.** The Mac launcher also refuses flag-shaped URLs and opens Chrome in the background instead of pulling focus from whoever is at the keyboard. The Windows section gains the Mac lessons: read why a page refuses before guessing, check the result by reloading, how to schedule an unattended step, and the stale API-token trap. PP's hard-won Windows lessons are written down too: focus text fields through the accessibility tree rather than by clicking coordinates, turn off extensions for a scripted sign-in so a password manager cannot scramble the fields, run `canfocus` before any live test, and the PowerShell 5.1 traps.
- **Three platform cases, stated plainly.** Mac; Windows reached from WSL (the shell an Instar agent on Windows actually runs in; other Windows shells are untested and the wrapper says so rather than guess); and Linux with no Windows underneath, which is not built and is tracked as a separate item (ACT-138).
- **Agents that already have the first version of the skill get the new text on their next update.** An untouched copy is replaced whole; an edited copy keeps every edit and gains the Windows section at the end. The one-line note in every agent's instructions now says Mac and Windows, and the old note is replaced rather than duplicated, with a guard so that only the exact shipped text is ever removed.

## The safeguards

**No automation signature.** Both drivers launch an ordinary Chrome with no remote-debugging port. The Windows script accepts only a short allowlist of harmless window flags; the Mac launcher accepts none; both wrappers refuse a flag riding in a URL slot.

**Never the operator's own browser, never their keyboard.** The Mac tools work only on profiles inside the agent's folder. On Windows the wrapper refuses the operator's Chrome profile folder, and the driver acts only on the one Chrome it launched or bound, checks that window has focus before every click or keystroke, stops typing mid-word if focus moves, and refuses to take focus at all while the operator has used the machine in the last 30 seconds or has a full-screen app in front. The skill is honest that this check does not run when the operator is using the very window the agent bound, which is why automation always gets its own profile.

**Secrets stay off the record.** On Windows a password is piped in on standard input and the script never prints it or even its length. The skill says the same for both platforms, and adds that a one-time sign-in link is a secret too and never goes on a command line.

**Check, don't assume.** A URL, a toast, or an exit code is only a symbol. On both platforms the agent reloads and reads the page again before reporting a result. Even the live test's "PASS" is bound to the exact file that was tested, by hash.

**Only what was asked.** Real input is for the actions the operator asked for. If a page withholds a button, the agent finds out why and tells the operator; it does not make the button work. A passive risk score treating real input as real is not a bypass; an active human check (a CAPTCHA, a phone confirmation) is the operator's to answer, never the agent's.

## What ships when

Everything in one release. Two live tests run on the operator's own Windows machine before the pull request opens: one of the Windows driver (already done: every command and every refusal passed, at three screen scalings) and one of the wrapper that Instar agents call it through. That second test exists because the first one found something important: on that machine Instar runs inside WSL in a background Windows session that cannot see the desktop at all, so the wrapper now hands the driver to the desktop session through Windows' own task scheduler, with no password, no install and no admin rights. The wrapper's first live run found four real bugs in that hand-off (a launch that always reported failure because it waited for Chrome itself to exit; a rare empty answer from Windows that sent the call down the wrong path; a timeout message that always claimed the full wait; and the driver being read over the network share on every call); all four are fixed; the second run then found that Windows' own PowerShell loses a finished process's exit code unless the script keeps a handle to it, which made every success look like a crash, fixed with one line; the third run passed on every row; the fourth passed too but left one stray diagnostic line on the error output; the fifth found that line again at one more place the fix had missed, with every real behaviour still passing, so the fix was made as a class (every place in the script that reads a file the same way) and the final wrapper gets its own run. The PR opens when both tests pass and the tested files are byte-for-byte the shipped ones. If the wrapper test is blocked, the PR opens with the Windows half clearly marked as not yet live-tested, in the PR, in the skill, and on the wrapper's own output, and a tracked item carries the re-test. If it fails, the wrapper is fixed and the new version gets its own run; each version runs once and only the run on the final version decides. The number of runs is a signal, not a rule (the operator ruled out bare numeric rules on 29 September 2026; this document carried a five-run limit until the fifth run reached it, and now says what blocks instead): the build is reported as blocked, with nothing merging and a tracked re-test, when a run fails on something new after a run where every behaviour passed, when the same problem comes back after it was fixed as a class, or when the Windows machine cannot run the test. If the test could not run at all, the pull request still opens with the Windows half plainly marked as not yet live-tested, by the operator's standing instruction. No report within three hours of the build being ready is reported as blocked too.

## What you actually need to decide

Nothing new: the operator asked for this consolidation on 21 October 2026 and approved continuing. The two things to know: the Windows driver is PP's work, shipped unchanged and credited as such, with Instar's rules in the wrapper around it; and the only new setting is a record in the agent's config that a machine is unattended, naming who said so, in which conversation, and when. The agent writes that record only when the operator says so, and it is what unlocks the driver's "take focus anyway" mode.
