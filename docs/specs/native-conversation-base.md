# Native conversation as the base for every chat platform

This spec is one of two siblings. It holds the shared framing and slices 3a, 3b and 3c; the other, `native-conversation-any-machine-access.md`, holds slices 3d, 3e and 3f (acceptance cases F4 and F5).

Source read at `d54f26884` (main, 2026-11-11). Paths are relative to the repo root. Nothing here is built.

## 1. Problem

### 1.1 What the operator asked for

All three messages are in the Telegram log of topic 141876, authorship `human`, read from the log on 2026-11-11.

Message 141877 (10:20 PST) opened the request: "I feel like we have an opportunity to make conversations much more robust for all platforms."

Message 141887 (10:28 PST), the two middle paragraphs (the message opens "continuing..." and has a further closing paragraph):

> "Instar now has native conversation support. I feel like we should leverage this as much as possible for all chat platforms. In other words, if Instar receives the message, regardless of platform, it should handle everything natively and ROBUSTLY (yes, including handling images/media) and then use this to empower any other chat interface such as telegram.
>
> Essentially, we want native instar chat (both the app and the web/dashboard) to be the main "base" of all conversations while still supporting and leveraging chat platforms such as telegram and slack, and increasing their robustness if possible by sending messages when they system detects the message didn't go through."

Message 141905 (10:40 PST), the hard requirement:

> "You should always have FULL insight/access to any conversation AND the session behind it, regardless of what machine you are on."

### 1.2 What is true today

Instar has a replicated native conversation log (`src/core/AppConversationStore.ts`, `AppConversationsReplicatedStore.ts`) and a content-addressed media store beside it (`AppMediaStore.ts`, `AppMediaReplicator.ts`). It accepts `telegram:<topicId>` and Slack keys (`AppConversationStore.ts:184`), but only app messages and `platform-media` events are stored there. A Telegram message and the agent's reply live in a per-machine rotating log, delivery evidence in the origin store of the machine that ran the send, transcripts on the machine that ran the session. Each has its own cross-machine path, and four of them failed on 2026-11-11.

### 1.4 Evidence that corrects the reports

Both reports say the outcome route answers from the local store only (`src/server/telegramOriginRoutes.ts:174-202`). Observed on the Mama PC: a reply held `lease-not-held` read `delivered` on that route 66 seconds later, because the forward ladder writes the holder's receipt locally (`recordForwardedAcceptance`, `src/commands/server.ts:32660`). The route stays blind when the holder ended the reply (a remote owner's local `not-delivered` is downgraded to `unknown`, `telegramOriginRoutes.ts:197-199`), when the local row is evidence only, and on a third machine. F2 was the first of these.

Read for this revision:

- A reply recovered through the queue is written to topic history with its **acceptance** time (`src/messaging/TelegramAdapter.ts:1746`). When a session's acknowledgment and full reply are both queued, the acknowledgment's row is newer than the reply's draft time, and the timestamp rule retires the reply because of the same session's earlier message. This fits F1 (the session's account in message 141906 says the Studio reported the full reply `suppressed`).
- `lateRecoveredReplyNotice` (`src/messaging/telegram-origin/SessionDeliveryNotice.ts:17`) has no caller in `src/`. Nothing marks a late reply today; r1 called that marking "existing" and was wrong.
- Pool history from this machine still reports one peer as `peer URL refused`. F4 is live.

**The F1 cause is not yet read (owner Echo, due 2026-11-12, before the 3a build starts; deferral CMT-057).** A retirement writes no reason to any store or audit row. Its only trace is a line in the Studio's server log: `retired overtaken queued reply <operationId>` (`TelegramOriginRuntime.ts:696`) for the timestamp rule, or the duplicate-content refusal for the content check (`TelegramOriginService.ts:293-297`). The Studio answered questions about these replies on the day (message 141906), so the line can be read through its session. If it shows the timestamp rule, 3a fixes F1 as designed. If it shows the content check, 3a does **not** fix F1: that check is the one retirement the causal rule keeps, it should fire only after the platform accepted the same text, and a reply ended there while the user had nothing means the duplicate record was wrong and is the next thing to read. F1 is not claimed fixed until the line is recorded here. If the line has rotated out of the Studio's log, "unreadable" is recorded instead, and F1 then rests on the 3a live proof replaying the topology of topic 141868.

## 2. Target architecture

Both reports recommend the same option and this spec adopts it: **the replicated native event log is the canonical record of every conversation; each platform is an independently operable door; delivery truth stays with the machine that ran the send.**

1. **One record.** Every message is an immutable event in `AppConversationStore` under its canonical key. Event ids derive from platform message ids, as `platformMediaMessageId` does (`AppConversationStore.ts:187`), so a re-poll or a second machine appends nothing new.
2. **Doors are never silenced by the base.** A door delivers even when the record cannot be written. Phase 1 writes no message events, so this window does not exist yet. Phase 3 must name the repair before it relies on this.
3. **Delivery truth at the execution owner.** Replicas carry copies of evidence and never turn missing evidence into "not delivered".
4. **One resend authority per door.** "Safe to resend" needs the owner's classified verdict of non-delivery and proof that no machine still holds the reply. Everything else is `pending`, `unknown` or `delivered`.
5. **Uncertain is not failed.** An unknown outcome never causes a second answer and is never described to the user as "did not reach you". Only a definite non-delivery is handed back.
6. **Attachment ids, not machine paths.** A local path is produced on the machine that runs the session, by server code, from a structured field. Text a person typed is never read as a path.
7. **Any-machine reads over signed machine transport**, and the session behind a conversation is copied so a sleeping machine does not take it away (3f).
8. **Audience is enforced where a person is answered** (`deviceMayUse`, `accessStamp`). "Any machine" does not mean "any principal".

Reused, not rebuilt: the conversation and media stores and their replicators, the `pending_deliveries` follow-up, the origin store and outbox, `OriginForwardToHolder` and its supersede path, the `telegram-origin` verb, `topic-history-pull`. Slices 3a to 3e add one mesh verb, one small table, no daemon and no new send to the user.

## 3. Phase 1: slices 3a to 3c

Phase 1 has six slices. 3a and 3b share the reason set and the `receipt` answer and are built together. 3c is independent. 3d, 3e and 3f are in the sibling spec `native-conversation-any-machine-access.md`. Owner for every key and date: Echo, effort topic 141876.

### 3a. A reply is ended only for a cause (F1)

**Cause, read from code.** A queued session reply is reviewed before recovery delivers it (`TelegramOriginRuntime.ts:668-700`); `queuedReplyOvertaken` retires it when any message is newer than its draft time (`QueuedReplySupersession.ts:5-16`). For a reply this machine wrote and still holds, the draft time is `authoredPreparedAt` in the local hold detail (`OriginForwardToHolder.ts:316`, read at `TelegramOriginRuntime.ts:675-676`). That field does not travel: a forward carries only the sealed operation (`OriginMesh.ts:104,137-141`), the holder's `submit` handler runs no review, and the holder retires a forwarded reply only in its own recovery pass (`TelegramOriginRuntime.ts:613`), on the sealed `admission.preparedAt`. A retirement leaves only a `console.info` (`TelegramOriginRuntime.ts:696`): the state writer refuses a reason on `suppressed` (`OriginStoreBackend.ts:799-805`), four call sites write it with none (`TelegramOriginRuntime.ts:658`, `:696`, `TelegramOriginService.ts:296`, `:837`), and the attention scan skips it (`OriginStoreBackend.ts:864-869`). A recovered reply is sent from sealed bytes (`TelegramOriginService.ts:430`), and nothing marks it late.

**Change.**

1. *Timestamps no longer end a reply (the causal rule, the only rule).* The queued-reply review is removed, not switched off: the `reviewQueuedReply` option, its pool read (`TelegramOriginBoot.ts:74,217`, `server.ts:7676-7698`), the 15-minute peer wait and the module `QueuedReplySupersession.ts`. A queued reply is delivered. That includes an `imported-legacy` reply, which the review also covered (`TelegramOriginRuntime.ts:678`). The one remaining retirement of a reply is the sender's content check, which fires only on platform acceptance of the same text in the same destination (`TelegramOriginService.ts:288-297`). It runs on the execution owner, where the evidence is. The historical-notice retirement (`TelegramOriginRuntime.ts:646-664`) is unchanged; it never ends a reply.
2. *A late reply says so in its own first line.* A session reply (`producerKind: 'session'`, `sendMessage`) is late when it is dispatched more than 300 s after it was first drafted. A late `imported-legacy` reply has no session; it is delivered unmarked and counted `lateUnmarked`.
   - *The 300 s value is not derived from evidence.* It is inherited from `recoverableLatencyCeiling` (`src/config/ConfigDefaults.ts:1991`). It labels and gates nothing: a reply under it is delivered exactly as written, and its author already knows it was held (the reply script reports the hold, `telegram-reply.sh:635`). Every reply delivered through recovery is counted with its delay whatever its age (`recoveredUnderThreshold` for those under 300 s), and the 2026-11-25 review reads the ones under 300 s and sets the value from them.
   - *Carrier.* Two nullable columns on `telegram_origin_operations`, `first_prepared_at` and `late_marked_at`, added idempotently at open. They are set when a replacement is admitted and copied to every later successor. They are columns, not hold detail, because moving a row from `held` to `admitted` clears the hold detail (`OriginStoreBackend.ts:818-819`). An operation with no `first_prepared_at` uses its own `admission.preparedAt`. A reply whose `late_marked_at` is set is never marked again. The columns are the author's own record; what the execution owner reads is the sealed envelope field `firstPreparedAt` (Mechanism).
   - *Mechanism.* Sealed bytes cannot be edited, so the machine that holds the authored text replaces the operation. The replacement's wire text is the first line, a blank line, then the authored text; it is planned again, so its part count can differ. Its send-policy input (`policyInput`, the content-check key, kept apart from wire text by `prepareBot`, `TelegramOriginService.ts:421,446`) stays the authored text, so the content check still recognises a reply that did arrive. Its envelope `createdAt` and its `admission.preparedAt` are one value, the replacement time: equal because `validOriginAdmission` requires it (`OriginAdmissionSeal.ts:23`, enforced at admit, `TelegramOriginService.ts:552`, and at the holder's submit, `OriginMesh.ts:135`, on every release since September), and fresh because item 7 needs that. r5 sealed `createdAt` as the original's time and left `preparedAt` fresh; that check refuses the split, and the import path r5 cited sets both to one value (`TelegramOriginService.ts:371,377`), so it is withdrawn. The look-back start travels as its own sealed envelope field, `firstPreparedAt`, set from `first_prepared_at`. The content check looks back only to the time it is given or 15 minutes (`OutboundContentDedup.ts:190-201`), and it is given `record.createdAt` today (`OriginContentDedup.ts:21`); it is given `record.firstPreparedAt` instead when the field is present, so on an owner that runs this release the look-back covers the original's whole life. An older owner ignores the field and looks back 15 minutes: against an older owner, a replacement whose text Telegram accepted more than 15 minutes before the replacement was made is not stopped by the content check and can be delivered a second time. That bound is stated here and not closed. The field needs no version gate. An older receiver tolerates an unknown field in the envelope: the attestation and the canonical compare run over the received envelope with whatever keys it carries (`OriginAttestation.ts:40-43`, `OriginMesh.ts:114`), and the store keeps the envelope bytes whole and checks only named fields (`OriginStoreBackend.ts:228-233`). It does not tolerate one in the admission, which the store rebuilds from fixed columns (`admissionOf`, `OriginStoreBackend.ts:561-578`), so a field placed there would be dropped and the digest would fail on the next read; that is why the field is in the envelope. This was read at `d54f26884` only, and the live proof with the holder on the previous release is where it is confirmed. Its `deadlineAt` is the original's. If the added line would push the reply past its part limit, or the replace is refused, the reply goes out as it is and is counted `lateUnmarked`.
   - *The replacement stays a session reply.* A recovery pass has no producer context, and a prepare made there today is sealed as `telegram-server` automation with no session (`runAsUnboundAutomation`, `server.ts:32597`; `TelegramOriginService.ts:134,153-155,422`). A replacement sealed that way would drop out of every reader that selects on the envelope: the session-exception scan (`OriginStoreBackend.ts:872`), the line of item 5, the text route of item 6 and this item's own test for "late". So the replacement is prepared under the original operation's stored producer record (kind, producer id, session id, harness, author): one service method re-enters that scope from the record. The envelope stays `producerKind: 'session'` with its session binding and no reader changes. If the record cannot be re-entered, no replacement is made and the reply goes out unmarked (`lateUnmarked`).
   - *Where, forwarded reply (the F1 topology).* On the authoring machine at each forward attempt; the forwarder holds the text in `holdDetail.text` and replaces through the existing path (`deps.prepare` and `supersedeWithAdmission`, `OriginForwardToHolder.ts:462-468`, `OriginStoreBackend.ts:620-641`), which leaves the replacement `held`, as a forward row must be.
   - *Where, the author is the execution owner (every one-machine agent).* `supersedeWithAdmission` always writes the replacement `held` (`OriginStoreBackend.ts:634`), and direct recovery sends only `admitted` rows (`TelegramOriginRuntime.ts:598-616`), so that path cannot carry it. The store method gains `replacementState: 'held' | 'admitted'` with the same refusals (every child queued, nothing claimed) in the same single transaction. Direct recovery, before it reserves an attempt, replaces a late unmarked session reply with `replacementState: 'admitted'` and sends the replacement in the same pass. `onRecoveredMessage` is given `first_prepared_at` and `late_marked_at` beside `admission.preparedAt`.
   - *Wording.* `lateRecoveredReplyNotice` is changed (signature, text and its unit test) to take `(firstPreparedAt, now)` and return "Late reply, written more than N minutes ago and held up in delivery. It answers an earlier message:" (hours above 90 minutes), and null under 300 s. N is the age when the line is sealed. "More than" keeps the line true however much longer delivery takes.
   - *Limit.* A reply already admitted at an owner that then stalls past 300 s was sealed by another machine, and the owner cannot mark it. It is delivered unmarked and counted (`lateUnmarked`); its author is told so by item 5. Deferral CMT-058.
3. *Supersession is not retirement.* A `superseded` operation is followed to its successor everywhere it is read. If the successor fails, the original's status is that failure. An admitted replacement is never treated as delivered.
4. *A new owner runs no timestamp review on any reply.* An older owner still does, in its own recovery pass, on the sealed `admission.preparedAt` of whatever it holds. Item 7 handles what that produces.
5. *The author is told when its reply went out late, and what the user saw.* On the authoring machine, when a late reply's receipt is recorded (`recordForwardedAcceptance`, or `onRecoveredMessage` for the owner's own) and the bound session is running (`isSessionLive`, `server.ts:7666-7669`), one line goes to it through `sessionManager.sendInput`. N is the delivered age, from `first_prepared_at` to the receipt. The wording is chosen from the recorded `late_marked_at` of the operation that was accepted, never assumed:
   - marked: "Your reply `<operationId>` was delivered N minutes after you wrote it. It carries a first line telling the user it is late. Follow up here if it is no longer right."
   - not marked: "Your reply `<operationId>` was delivered N minutes after you wrote it. No late notice could be added, so the user has no sign that it is late. Follow up here if it is no longer right."

   One line per recovery pass lists every id, grouped by those two cases. The store records the line as a keyed operation event (`<operationId>:late-line`) so a restart does not repeat it.
6. *The reply text has a route.* The lines of item 8 point at a new route, `GET /telegram/origins/operations/<operationId>/text`: Bearer, ids of 8 to 64 characters as on the outcome route (`telegramOriginRoutes.ts:177`), answered only on the authoring machine for an operation whose session binding is local. The binding says where the operation belongs, not who may read it, so the caller must also be authorized for the operation's conversation: the handler applies the check the conversation's history read applies (`deviceMayUse` on `telegram:<topicId>` of the operation's own destination, `read`, `routes.ts:21691`) and answers `unknown-operation` when it fails (a caller holding the API token passes it, as on the history read; the check is what keeps the route closed to a person if a device rule is ever added). A device token is refused outright: the path is not in `DEVICE_ALLOWLIST` (`mobilePairingRoutes.ts:2271,2531`) and is never added, and the handler itself refuses any caller whose principal is not the API token, so the refusal does not rest on the allowlist alone. It returns the authored text: `holdDetail.text` for a forwarded row (it survives expiry); the sealed `policyInput` for any row with no `holdDetail.text` (a reply this machine sent itself, or a forwarded row settled as unknown, whose detail was cleared with its hold reason); and `gone` once the purge has removed the row's detail.
7. *An ending with no stated reason is never final.* The `receipt` answer carries the owner's `reason`, `outcome` and `failure` (§3b).
   - Owner definite **with** a stated cause. `suppressed` with a reason: the forwarder records `suppressed-at-holder` with `holdDetail.holderReason` and stops. The replacement is newly prepared, so its sealed `admission.preparedAt` and `createdAt` are the replacement time (the original's time travels as `firstPreparedAt`, item 2) and the old owner's timestamp rule sees a fresh reply instead of retiring it again on the same evidence; its `deadlineAt` and its content-check key are the original's, so the old owner's content check still stops it if the text arrived within the 15 minutes an older owner looks back (item 2).

A row with `ownerUnstated`, settled or not, keeps its uncertainty across a lease change, exactly as a row whose `lastAttempt` is `outcome-unknown` already does (`OriginForwardToHolder.ts:389-413`): before any local send and before the holder-change supersede, the new route asks the previous owner (`detail.machineId`) for its receipt, with the existing `receipt` ask. That would send a second copy. The `ownerUnstated` path reads the receipt's raw `state` together with its `outcome` and `failure` fields, and a `suppressed` state with no `outcome` counts as "no reason" (the test stub's old holder answers exactly `state: 'suppressed'` with no `outcome`, and nothing is sent). If the previous owner cannot be reached, or answers again with no reason, nothing is sent by anyone: the row stays as it is and is handed back to the author with the uncertain wording. What the new sender's own content check has not seen proves nothing about what the old owner sent. A settled row is unresolved, not ended. A running authoring session gets one line: "Reply `<operationId>` was ended by the machine that sends to Telegram, which runs an older version and gave no reason. The user may already have this text. ### 3b. The outcome route gives the owner's verdict (F2)

**Cause.** §1.4. The owner's `receipt` handler already computes the classified verdict (`OriginMesh.ts:69`) but returns the raw state (`:71`), and answers only the authoring machine (`:63`).

**Change.**

1. *The `receipt` answer carries the verdict.* It gains `outcome` and `safeToResend` (from `classifyOperationOutcome`), `reason` (the closed set of §3a item 9; the receiver drops any other value), `failure` (`refused`, `never-left` or `deadline`, for a definite non-delivery), `supersededBy`, `duplicateOfMessageId`, `role`, `holding` and, on an `execution-owner` answer, the envelope's `originMachineId`, so a machine with no local row learns which machine to ask as author. `answeredBy` on the route's answer is the authenticated mesh sender, never a body field; the asker matches it to the envelope's owner and ignores the body's `executionOwnerMachineId`, which a `no-record` answer stamps with the answerer's own id (`OriginMesh.ts:60-61`).
2. *The classifier reads reasons.* `classifyOperationOutcome` (`OriginOperationOutcome.ts:78-84`) answers:
   - `duplicate-content`, or `suppressed-at-holder` with that `holderReason`: `delivered`, `safeToResend: false`, "the user already has this text".
   - `superseded`: follows `supersededBy` (visited-set; a repeat id answers `unknown`).
   - `known-failed`, `expired`: `not-delivered` with `failure`, only after its existing unresolved-dispatch check.
   - `quiet-notification-recorded`, `historical-notice-retired`, `recorded-by-caller`: `not-delivered`, `safeToResend: false`, "ended on purpose".
   - a `suppressed` row with a null reason (written before this release), or a held row with `ownerUnstated`: `unknown`.
3. *`reader: true`.* The command gains an optional `reader`. It relaxes two checks, `record.originMachineId === sender` and `record.executionOwnerMachineId === this machine`; `role` replaces the second. The agent, operation id, origin id, digest and key-epoch checks stay. The machine answers about its own row:
   - `execution-owner` (the envelope names this machine): full verdict.
   - `author` (this machine wrote it): `holding: true` while its row is `admitted`, or `held` with no `ownerVerdict` (§3a item 7), or has an unresolved forward; else `false`. `supersededBy` when its row is `superseded`. No verdict, and no terminal state: the r3 field `uncertainAttempt` is removed, because row 9 no longer reads the author's answer.
   - anything else: `origin-receipt-unavailable`.
   The forward ladder never sends `reader`, so a reader answer cannot free a re-forward.
4. *The route answers locally when it can, then asks.* No ask is made when: this machine is both the execution owner and the author (always so on a one-machine agent); the local verdict is `delivered`, `partially-delivered` or duplicate (a definite receipt); or this machine is the author, its row is `held` or `admitted`, and no forward attempt has been dispatched (the answer is `pending`, which is what the reply script reads straight after every held reply, `telegram-reply.sh:635-639`). Otherwise the route asks the envelope's execution owner, and, when this machine is not the author, the author. Running on the execution owner skips only the owner ask, never the author check: when another machine wrote the reply, rows 6 to 8 still need that author's `holding` and replacement answer, so the owner asks the author before any `safeToResend: true` and answers `unknown` by row 8 if the author is silent. With no local row it asks the lease holder once with `reader`; only an answer with `role: 'execution-owner'` is used, and the author is then asked at the `originMachineId` that answer carries. A pure function `resolveOutcome(local, owner, author)` in `OriginOperationOutcome.ts` applies the first matching row:

| # | Evidence | Answer |
|---|---|---|
| 1 | local or owner verdict `delivered` / `partially-delivered` | the same, with message ids |
| 2 | owner or local reason `duplicate-content` | `delivered`, detail "the user already has this text" |
| 3 | local, owner or **author** `superseded` | the answer for the successor, by this same table |
| 4 | owner verdict `pending` | `pending` |
| 5 | owner verdict `unknown`, local `unknown` from an unresolved dispatch, or a local `ownerUnstated` row | `unknown`, `why: 'owner-unresolved'` |
| 6 | owner verdict `not-delivered`, and the author is not holding and has not replaced it | `not-delivered`, `safeToResend` as the classifier gives it, source `execution-owner`, with the reason and `failure` |

Every other local verdict is returned as `unknown` with **`safeToResend: false`**, plus `ownerAnswered: false` and `why: 'timeout' \| 'refused' \| 'old-version' \| 'owner-read-off'` |

   Rows 5, 8, 10 and 11 are the rule "absence is not non-delivery". Row 11 is FD-5 stated as code: a local row that classifies as `not-delivered`, `safeToResend: true` (`OriginOperationOutcome.ts:28,78`) is never passed through when this machine is not the owner and the owner's answer is missing. Row 9 is the one case where an owner's "no record" permits a resend, and it needs the owner to have answered: the forward ladder already calls that answer a definite non-admission (`OriginMesh.ts:54-59`), and the author's own row supplies the other half of FD-5. It is evaluated only where the author's row is local. The `author` answer carries `holding` and `supersededBy` and nothing else, and `holding: false` is also what an author answers for a reply it delivered itself after the lease came back (`OriginForwardToHolder.ts:423-432`) or ended on purpose, so on any other machine row 9 could say "safe to resend" for a delivered reply. Those machines get row 10. Nothing is lost by this: the session that would resend is the author's, on the author's machine. A `no-record` or `not-admitted` answer is definite from an owner of any version (the ladder reads it so today, `server.ts:32652`), so for such an answer row 9 is matched before row 11. The ladder's own reading of `no-record` is unchanged; it re-forwards, it does not tell anyone to resend.

### 3c. A photo is readable on the machine that runs the session (F3)

**Cause.** A Telegram photo is downloaded to the polling machine and the message text becomes `[image:<absolute path>]` plus the caption (`TelegramAdapter.ts:6593-6604`); the lifeline (`lifeline/TelegramLifeline.ts:1490,1599`) and the app-to-Telegram path (`server/mobilePairingRoutes.ts:1986-1994`) write the same tags. The text travels as a bare string (`deliverMessage` `payload`, `server.ts:31118`) and through the durable inbound queue, whose row has no structured field (`PendingInboundStore.ts:189-214`). The injector turns every `[image:…]` or `[document:…]` in the text into "read the file at `<path>`" with no check (`SessionManager.ts:9146-9167`), so anyone who can post in the conversation can point the session at any readable file. `[video:…]` and `[voice:…]` are trusted too (`appMediaTypes.ts:168-170`), and Slack and iMessage have their own copies of the transform (`server.ts:11204-11219`, `:4105-4130`). With native media on, the file is also copied into the blob store as a replicated `platform-media` event (`TelegramAdapter.ts:6596`), which usually reaches the serving machine after the message.

**Change.**

1. *The trust rule, by source.* File lines shown to a session are built by server code from a structured field, in one function, `buildInboundSessionText(text, media)`. Every path-tag form (`image`, `document`, `video`, `voice`, `file`) found in person-supplied text is made inert (the bracket is escaped). The escape is applied first on the machine that receives the text from the platform, before the text is forwarded, queued or logged, and again in the builder; escaping twice changes nothing. The escaped form is one the previous release's injector patterns do not match (`SessionManager.ts:9146-9167`), so a receiver that has not updated never sees a live tag from an updated poller: without this, such a receiver would ignore `media`, inject the text, and still turn a typed `[image:…]` into a file read. Lines the server itself injects later (`[file now available: <path>]`) go through `sendInput` and do not pass the escaper.
2. *Producers.* Each moves to the field:

   | Producer | Change |
   |---|---|
   | Telegram adapter (photo, document, video, voice) | sets `media: [{ kind, platformMessageId, filename, capture }]`; `capture` is `pending` or `off` (native media off on the poller). A new poller sends `media` on every message, as an empty list when there is no file, so a receiver can tell a new poller from an old one. `filename` passes through `displayName` (`appMediaTypes.ts:149-157`) on the poller. Its own download path is passed in process only. |
   | Lifeline forward | sends the same field with `localPath` to the local server; accepted only on the lifeline's authenticated local route, after a realpath check inside the download directories. From a lifeline process still on the old build, only a tag at position 0 of the text is read, with the same check; everything after it is person text. |
   | App file into a Telegram topic | passes `media: [{ kind, attachmentId, filename }]` (the attachment is already in the media store) in place of tag lines. |
   | Slack and iMessage adapters | keep their tags and their machine-local paths (FD-12), and escape path-tag forms in the person's text and caption before adding their own tag. That closes the typed-tag file read there without moving any Slack data. |
3. *Carriers.* `media[]` must survive each:

   | Carrier | Change |
   |---|---|
   | mesh `deliverMessage` | gains `media`. The `payload` text always also carries one fixed, path-free sentence per file, built by server code: "[The user sent a photo (attachment `<platformMessageId>`, `<name>`). It is stored on another machine and cannot be opened here.]" An older receiver ignores `media` and injects the sentence, so its session knows a file was sent and which one. A new receiver with `media` present removes that exact sentence and builds the real line. No capability advert is needed. |
   | durable inbound queue | `entries` gains a nullable `media TEXT` column (idempotent `ALTER TABLE` at open). The drain passes it to the builder. A row written before the migration, or read by older code after a downgrade, still has the sentence in `payload`. |
   | spawn and respawn bootstrap, pending-inject ledger | the builder runs once on the serving machine before spawn or inject; the ledger stores its output, whose paths are local to that machine. |
   | topic history and message type | the logged text is the caption plus `[photo]`, `[file: <name>]`, `[video]` or `[voice note]` (the forms `deviceTextForRow` already produces, `appPlatformMedia.ts:110-125`), never a path. The type classifier (`server.ts:2629-2632`) reads `media[0].kind`. |
   | message from an older poller (a tag in the text and no `media` field at all) | resolved by the message's own platform message id through item 4; the path is discarded. A message that carries `media: []` came from a new poller, and a tag in its text is person text. |
4. *Resolution through the attachment store.* A pure module `src/core/platformMediaForSession.ts` resolves each entry on the serving machine with no network wait. It runs before `commitReceipt`, inside the existing per-session order, so receipt-then-inject stays adjacent (`server.ts:3788-3797`); a local copy that fails becomes the copying line and never blocks.
   - the `platform-media` event and its blob are here: `AppMediaStore.sessionCopy`, then `intoConfinedInbox` (an existing target is reused). The bytes come from the content-addressed store under the hash the event records.
   - the event is here, the blob is not: `[file still copying: <name>]`, a `pending_deliveries` row and `replicator.want`, as the app path does (`AppConversationService.ts:414-421`).
   - the event is not here yet and `capture` is `pending`: the same line, and a waiter row (item 5).
   - `capture` is `off`, or native media is off here: the in-process path when the file was downloaded on this machine (realpath-checked), otherwise "The user sent a file that is stored on another machine and cannot be opened here."
5. *Waiting for an event: durable, reconciled, and never a give-up.* `pending_deliveries` cannot hold the wait: its key is `attachmentId` and `sha256` is `NOT NULL` (`AppMediaStore.ts:92`), and neither is known before the event. A new table in the same database holds it: `pending_media_events (eventId PRIMARY KEY, conversationKey, platformMessageId, displayName, kind, createdAt, toldAt, convertedAt)`.
   - *Insert, then look again.* The waiter row is written first and the event store is read a second time after the write. An event that lands between the resolver's first look and the insert is found by the second look.
   - *Conversion is idempotent.* `convertPendingMediaEvent(eventId)` writes one `pending_deliveries` row per attachment (`INSERT OR IGNORE`) and sets `convertedAt`, in one transaction. If the blob is already on this machine (the same bytes were sent before), the row is written `ready` and `[file now available: <path>]` is injected at once, because `resolvePending` fires only when a blob lands. Only the call whose transaction set `convertedAt` injects, so the listener and the sweep running together give one line.
   - *Three callers, one of them a sweep.* The append listener (`addAppendListener`, which fires for replicated commits) is the fast path only. A reconciliation sweep runs at server start and in the existing periodic pending pass (`AppConversationService.ts:689`): it checks every unconverted waiter against the event store and converts those whose event is present. A missed listener call, or a restart between the event's commit and the conversion, costs one sweep interval and loses nothing.
   - *The sweep also retries a "now available" line that could not be injected.* `resolvePending` moves a row from `waiting` to `ready` before it tries the follow-up and deletes the row only when the follow-up returned true (`AppConversationService.ts:614-643`). For a Telegram key nothing reads a `ready` row afterwards: `pendingContext` is called only from the app delivery path (`appConversationPool.ts:506`) and the periodic pass touches `waiting` rows only. So a blob that lands while no session runs for the topic (still starting, reaped, or restarting) would leave a session that was told "still copying" and never hears again. On each pass the sweep re-tries the injection for every `ready` row of a Telegram key and deletes the row only after `sendInput` returned true.
   - *At 300 s the session is told, and the wait goes on.* The same sweep, for a waiter that is unconverted, untold and older than 300 s, injects: "The file `<name>` has not arrived on this machine yet. It may still come, and you will get a line here if it does. To check now: `GET /conversation-media/path?conversationKey=<key>&platformMessageId=<id>`." `toldAt` is written only after the injection; with no running session for that topic the line waits for a later pass. The row is kept. An event that arrives later still converts and still produces "now available". A waiter ends, with no further line, at the existing `PENDING_DELIVERY_TTL_MS` (7 days, `AppMediaReplicator.ts:66`).
   - *No definite wording here.* The serving machine cannot tell a capture the poller refused (`copy-failed`, `record-failed`, `store-unreadable`, `appPlatformMedia.ts:61-106`), or a crash between download and capture, from a slow event, so it never says the copy failed. 300 s is when to tell the session, not when to stop. It is the existing recoverable ceiling, not a measured value: the serving machine records the event lag it observes and the 2026-11-25 review sets the tell-time from the measured p99.
   - The poller's degradation text for a refused capture says "The session still received it" (`AgentServer.ts:7301-7303`), untrue for a session on another machine; it is reworded.
6. *The file arrives by itself.* `resolvePending` (`AppConversationService.ts:614-643`) gains a second injector for `telegram:<topicId>` keys, which delivers `[file now available: <path>]` to the session serving that topic on this machine. If the topic's session has moved, the new machine has no row; the session there gets the file through item 7 or with the user's next message.
7. *A manual fetch.* `GET /conversation-media/path?conversationKey=telegram:<topicId>&platformMessageId=<id>` (or `&attachmentId=`), Bearer plus the conversation bind check of `/app/media-path` (`routes.ts:23277-23280`). It validates both ids with the existing pattern (`appPlatformMedia.ts:62`), checks the attachment belongs to the conversation and is not purged, waits `MEDIA_PATH_WAIT_MS`, and returns a confined local path or `not-on-this-machine` with `replicator.whyNotHere`.

**Limits.** Bytes follow the conversation only where native media is on (`isMobileMediaEnabled`, `mobilePairingRoutes.ts:237-244`); Echo's pool has it on, and elsewhere the session is told the truth (deferral CMT-048). In a mixed-version window, a tag typed by a person into a message forwarded by an older poller is treated as a file that has not arrived and gets the 300 s line. An older poller forwarding to an older receiver behaves as today until one of them updates. `/sessions/:name/attachments` stays refused for a session on another machine (deferral CMT-050).

**Config and migration parity.** Items 4 to 7 follow the existing media switch; items 1 to 3 are on, no switch. One nullable column and one table, both created idempotently at open; downgrade is covered by the sentence in `payload`. ## 5. Risks

**Duplicates.** Covered by FD-5, FD-13 and the §3b table; `unknown` never resends and never prompts a re-answer, and a missing owner answer forces `safeToResend: false`. A provider that accepted a request and lost the answer cannot be made exactly-once; the classifier keeps that honest (`OriginOperationOutcome.ts:5-14`). A replacement (late mark, older owner) keeps the authored text as its content-check key, so the owner's check stops it if the text did arrive.

**Late replies.** The causal rule delivers replies the old rule ended, so a stale answer can land after the conversation moved on. This is the 2026-11-04 symptom that the removed rule was built to stop (FD-3), returning with a label. It says it is late in its first line, is bounded by the existing deadline, its author is told what the user saw, and it is read and judged on 2026-11-25. After a long holder outage several late replies can land together, each with its own first line. There is no setting that brings the old rule back; that is a version rollback.

**Privacy and security.** No slice adds a route a phone or team member can call: the one new HTTP read of message text, the reply-text route, refuses device tokens and requires the caller to be authorized for the operation's conversation (§3a item 6). 3c closes a file-read path that exists today on Telegram, Slack and iMessage. Every new read is a signed, recipient-bound verb checked against the registry and key epoch; no bearer token goes to a new place, and a timeout never causes one to be sent. `reader` widens who may ask about an operation to any active same-agent machine, for state and ids only. The reply-text route answers only on the authoring machine, under that check. Later phases put platform text on every machine; each event carries its `accessStamp`, and `purge` and `tombstone` must reach every copy. Transcript privacy is covered in the sibling spec.

**Power loss and load.** A media waiter survives a restart and is reconciled by the start-up sweep. A session line injected but not recorded is injected again on the next pass. 3b makes no mesh call for the common case (a held reply read straight after sending) and otherwise one coalesced call per operation inside 4 s; 3c adds no network wait.
