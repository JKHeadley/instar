# Sending email from an agent

Owner: Echo. Fourth in the backup work order (`recommended-services.md`, Frontloaded Decisions). Closes the `gap` on the `email` row. **Attribution:** the row is on the list by operator decision of 2026-11-03, recorded in the parent spec's Frontloaded Decisions, which cites the operator's message in topic 135786; this spec inherits that pointer and adds no claim of its own about what the operator said.

## Problem statement

An agent has no way to send mail. A person who wants a scheduled report in their inbox cannot have one, and the `email` row stays unavailable with no backup.

## Scope

**Send only, to the owner only.** Reading mail is out of scope: a different trust surface (inbound untrusted text), and nobody asked for it. Sending to anyone other than the owner is refused in code. Honest limits are stated where they apply: a mailbox app password is a credential the provider scopes, and the dashboard PIN stops mistakes, not a hostile agent (parent, "Which proof"); where this spec can do better than the PIN by construction, it does.

## Design

### Three account shapes, and who the mail goes to

The person chooses one; all three are presented as good, with each one's concession stated and none ranked (standard: The Person Decides).

| Shape | Sends from | Mail goes to | How the recipient is fixed |
|---|---|---|---|
| **A. Resend account in the person's name** (the default proposed) | Resend's shared sender (`onboarding@resend.dev` until a domain is verified) | the owner's address, typed by the owner on the confirm page and confirmed by the proof code (below) | Resend has no API that tells the code which address the account was opened with, so the recipient is the owner's typed, code-confirmed address; and Resend itself refuses any other recipient on an account with no verified domain, a second wall under the first. Verifying a domain later removes that wall, so this version never verifies one and `verify` fails if a domain appears. **The recipient is also the account's address:** a change of recipient in shape A is refused on the page with the fixed reason `recipient-is-the-account` and the page says a different address means a new setup (a no, then a yes with the new address, which opens a new account). Concession: the sender address is Resend's, not the person's. |
| **B. The person's own mailbox** (Gmail or iCloud) | the person's address | the person's address | the owner types their address on the confirm page like the other shapes, and the key route refuses a credential whose SMTP username is not that address, so a session can never point shape B at a mailbox of its own choosing; `to` and `envelope.to` are that address. No code is needed: the mailbox is the owner's by the match. Concession: an app password lets a program send as the person to anyone and read their mailbox; this code only ever sends to them, and only this code is checked. |
| **C. A mailbox of the agent's own** that the owner provides | the agent mailbox's address | the owner's address, typed and code-confirmed as in A | Concession: the owner has to have a spare mailbox to give, and a session that holds that mailbox's credential can read the proof code in its Sent folder (the honest limit below). A recipient change in shape C is a new page yes with a new code. |

### Owner-only, by construction

- `EmailSender.sendToOwner(subject, text)` has no recipient parameter. The recipient is derived per shape (table above); each transport refuses a `to` that differs from it, and SMTP sets `envelope.to` to the same value, so the RCPT line is bound, not only the header.
- **The owner types the recipient in every shape; in A and C the proof mail's code confirms it, and the row is `working` in those shapes only after the code; in B the credential must match it.** The confirm page (the owner's PIN surface) gains one field for this service, the recipient address (validated as a single bare address, lowercased, 254 characters at most per RFC 5321, no display name, comma or angle brackets). The POST carries it to the server, which stores the plaintext under `email_recipient` in the vault (on the granting machine; the cross-machine secret sync replicates it like every vault value, so the hash below protects the journal, not the vault) and a keyed hash in the yes row (`recipientHash` = HMAC with the machine identity key, so a replicated row is not dictionary-reversible; a new optional field on `ChoiceRow`, learned by `validateRow` and the store schema; an older machine in a mixed pool rejects the row as `invalid`, which it may, because a grant is per machine anyway). The setup session never **sets** the address: the key route for this service accepts the credential JSON only, refuses any `recipient` field, and in shape B refuses (`recipient-mismatch`) a credential whose SMTP username differs from the stored `email_recipient`; in shape A the session reads `email_recipient` to open the account with it. Changing the address is a new page yes, by construction (and in shape A a new setup, above). **Double opt-in:** the proof mail (below) carries a six-digit code; the row becomes `working` only when the owner enters that code on the confirm page. **How the code relates to the yes:** the yes consumes the confirm token and writes the grant as the parent describes; the recipient is stored at that moment and the row is `unproven`. When `prove` sends the proof mail it mints a separate `email-opt-in` nonce (keyed hash with the minting machine's identity key, bound to the `recipientHash`, 30-minute expiry; the nonce record and its attempt counter are durable beside the grant, so a restart does not reset the five misses; the page is re-opened on the minting machine, which the link's host already fixes). The owner enters the code on the same confirm page, re-opened with the PIN; five wrong entries or expiry void the nonce only: the grant and the stored credential stand, the row stays `unproven`, no report is emailed (every report falls back to the topic), and a fresh proof mail may be sent inside the daily bound. Five attempts: `invariant; basis: enumerable-domain; evidence: a six-digit space is 10^6, so five tries bound a guess to 5 in a million`. Thirty-minute expiry: `judgment-candidate; floor: never past 24 hours (a code that outlives the day outlives the daily proof bound); default 30 minutes`. **Proof mails to a not-yet-confirmed recipient** (shapes A and C) are bounded to three a day per agent, and shape A's account-opening signup mail counts as one of them (it reaches the same not-yet-confirmed inbox), so on the first day of shape A at most two proof mails follow the signup; and twenty in all before the row needs a new page yes with a re-typed address (`invariant; basis: irreversible-consequence; evidence: a proof mail to a mistyped stranger cannot be recalled; the daily and total bounds cap the harm`); their text is fixed and names nothing but the agent's name (the envelope in shape C necessarily shows the agent mailbox's address). **Honest limit (inherited from the parent, "Which proof"):** the dashboard PIN stops mistakes, not a hostile agent. The code closes typos and a session without the sending credential; a session that holds it can read the code, in shape C from the agent mailbox's Sent folder and in shape A through Resend's own `GET /emails/{id}`, which returns the sent text. So in A and C this version guarantees owner-only against mistakes and against sessions that lack the credential, and says so on the page. When `ownerProof` ships (owner-authentication), the recipient binds to it with no change to stored choices. Shape B needs no code: its recipient is the owner-typed address the credential must match, and its honest limit is that the mailbox belongs to whoever owns the supplied app password.
- Every outbound subject and body passes the deterministic credential-exposure guard **before the outbox row is written** (the existing credential-exposure guard that already holds Wall 1 authority over every outbound Telegram text, per the Outbound Message Gate; Signal vs Authority: this spec adds no new authority and no new matcher, it routes one more outbound surface through the guard that already has it, and the grant of that authority is the guard's own, not this spec's; a live secret is refused with reason `credential-exposure` and nothing is stored). Plain text only, no attachments; subject prefix fixed (`<agent name>: `), CR/LF stripped.

### Transports

`EmailTransport.send(message) → { outcome: 'accepted' | 'refused' | 'unknown'; providerId?: string; reason: FixedReason }`. `accepted` means the provider took responsibility, never that the mail arrived. Reasons are a closed set of fixed strings; provider error text never surfaces (SMTP and HTTP errors can echo credentials).

1. **Resend** via `fetch`: `POST /emails` with `from` Resend's shared sender, `to` the account address, `subject`, `text`; never `cc`, `bcc`, `reply_to`, `headers`, `attachments`, `html`. `429` → `refused`/`provider-rate-limited`. `401` → `refused`/`credential-refused` (the breaker, below). **`403` with Resend's recipient-restriction error** (the domain-less account refusing a `to` other than its own address) → `refused`/`provider-recipient-refused`: not a credential refusal, never trips the breaker; the row falls back and the service row goes `unproven` with that reason, because it means the stored recipient is not the account's address (a changed account, or a mistyped recipient the signup mail went to). Any other `403` → `credential-refused`. Status: `GET /emails/{id}`. **Key:** the setup session creates a *full access* key on the account it opened (a sending-only key cannot read status or answer a non-sending probe); the account holds nothing but this agent's sends and no domain. Honest limit beside shape A's concession: a full-access key could add and verify a domain, which would remove Resend's own recipient wall; so `verify` also **fails when `GET /domains` returns any domain**, and the only recipient check left is this code's. The account's own password is generated by the setup session and stored under `email_provider_account` (listed in `stop`); the person regains the account through Resend's password reset to their own inbox. Free tier at the time of writing: 100 a day, 3,000 a month (re-checked at build time).
2. **SMTP via `nodemailer`** (a reviewed dependency added in this change). Presets only: Gmail `smtp.gmail.com:465` (implicit TLS) and iCloud `smtp.mail.me.com:587` (STARTTLS, `requireTLS`). No Outlook.com preset (app-password SMTP retired for personal accounts). Certificate checked against the preset host; AUTH never in the clear; host and port never from a session. Workspace accounts whose admin disabled app passwords: fixed reason `provider-refuses-app-passwords`. Shapes B and C both use this transport; shape B's recipient is the SMTP username, shape C's is the bound recipient.

### Delivery, not a send result

`Delivery = 'delivered' | 'accepted-unproven' | 'failed' | 'unknown'`.

- Resend: every send carries `Idempotency-Key: <row id>`, so a repeated attempt for the same row (a crash or a lease handoff before the attempt marker replicated) is deduplicated by Resend; `delivered` only when `GET /emails/{id}` says so; `bounced`/`complained` → `failed`; anything else after the 30-minute status window → `unknown`. Polling off any request thread, backoff 5/10/20/40 s then every 5 minutes until the window ends (`judgment-candidate; floor: never more than one status read a second per row and never past the status window; default as stated`).
- SMTP: a final `250` is `accepted-unproven`, named as such wherever SMTP is mentioned; nothing ever upgrades it. **It is a terminal state for a report** (the row ends `accepted`, no fallback): for shape B the recipient is the person's own mailbox, and for shape C the inbox was proven at setup by the code. SMTP has no idempotency, so a handoff before the attempt marker replicates can deliver one report twice; the parent accepts one duplicate at a handoff and so does this spec. The rollout rule reads "delivered, accepted (SMTP), or fallen back".
- **Two fallback deadlines, stated apart:** an explicit `refused` (including `budget-exhausted`, `provider-rate-limited`, `provider-recipient-refused`, `credential-exposure`), in every shape, falls back within 120 s; a Resend message still `unknown` at the end of its status window falls back then (window default 30 minutes, adjustable `email.statusWindowMinutes`, hard maximum 60 minutes independent of the knob). Both are tested. A copy may therefore arrive twice; that duplicate is intended and the confirm page says so ("if I can't be sure the email arrived, you also get it here").

### A durable outbox, drained

`email-outbox` is its **own replicated store kind** (declared like `TopicPinReplicatedStore`: `op: 'put'`/`'delete'` records, HLC-ordered, a store-side record bound `EMAIL_OUTBOX_MAX_ENTRY_BYTES` = 24 KB under the journal's 80 KB replicated cap). **Rate:** the outbox emitter enforces its own token bucket of 20 records a second before it writes (the `*_BOUNDS` constants elsewhere are declarations nothing enforces, so this one is enforced in the store's `put`), and the journal's shared bucket (100 burst, 50 a second for every kind) is the second bound. Each transition re-emits the full row (about five `put`s per emailed report, 24 KB each at the record bound, so about 120 KB a report and 12 MB a day at the Resend cap). **Retention: `rotateKeep: 3` with `maxFileBytes` 16 MB in the kind's `DEFAULT_RETENTION` entry (beside its `JournalKind`, `JOURNAL_KINDS`, `rateBuckets`, `nextSeq`/`highWaterSeq`/`opKeys` and retention-constructor entries), never `0`**: three archives plus the live file hold about five days at the cap. The outbox is a delivery queue, not a memory store: every report it carries is also held by its destination (the mailbox, or the topic's history, which is memory-governed), so what rotation removes is a transit copy, never the only copy. The row carries report content (`topicText`, redacted but the owner's), and the code marks a content-bearing store with `rotateKeep: 0` (rotate but never delete) as a compliance defect; three archives of 16 MB plus the live file is the whole history, so growth is bounded, and the fold tolerates a tombstone whose `put` has rotated away (a delete with no live row is a no-op, as the pin store's fold does). **Live rows survive rotation (checkpoint rule):** the journal has no pre-rotation hook and rotates per machine on its own byte count, so the checkpoint is a cadence, not a hook: the holder's hourly sweep re-emits every non-terminal row and today's budget aggregate as fresh `put`s (each with a new HLC, since the journal dedupes on record key plus HLC, so the re-emit is a newer copy of the same key and wins the fold), **paced at ten records a second and checked**: the journal's `emit` drops a record when its token bucket is empty, so the sweep reads each emit's outcome and re-queues a dropped row for the next tick rather than counting it done; the fold reads the current file plus the three archives; because the live set is re-emitted at least hourly and an archive holds far more than an hour of records at the stated volumes, every live row and the day's aggregate are present in the retained files on every machine. **Capacity (backpressure):** the live set is bounded at 200 non-terminal rows; past that, a new report's row is admitted with `topicText` cut to the status line (under 300 bytes) so a long relay outage cannot outgrow the retained files (200 rows at 24 KB is under 5 MB, inside one 16 MB file), and the Telegram outage sentinel's existing notice is what tells the person. Tested: a live set larger than the retention allowance would have been, rotation during a long relay outage, same-day rotation and restart without the budget resetting, then a handoff. **The owner's report text never enters the replicated journal:** the replicated row holds metadata and hashes plus the destination-safe `topicText` (≤ 8 KB after JSON escaping, the subject ≤ 200 characters; the serialized record is measured before admission and cut to fit, with a closing line "the full report is in our conversation"), while the owner's full text (≤ 16 KB) lives holder-local in `state/email-outbox-text/<id>` and is deleted the moment the row goes terminal.

Row: `{ id, createdAt, subjectHash, textHash, topicText, fallbackTopicId, status, attempts, providerId?, sentAt?, relayId? }`. **States and transitions (complete):**

| From | Event | To |
|---|---|---|
| (new) | row + local text written, `attempts: 0` | `pending` |
| `pending` | lease held at fire time, `attempts` incremented, transport called | `pending` (attempts ≥ 1) |
| `pending` (≥ 1) | Resend `accepted` with `providerId` | `sent` (polling) |
| `pending` (≥ 1) | SMTP `accepted` | `accepted` (terminal) |
| `pending` (≥ 1) | `refused` (any fixed reason) | `falling-back` |
| `pending` (≥ 1) | transport `unknown` (a timeout, a dropped connection, no `providerId`) | `falling-back` within 120 s, like a refusal: the provider may or may not have the message, which is the intended duplicate |
| `pending` (≥ 1) | restart or handoff finds it (provider outcome unknown) | `falling-back` |
| `pending` (0) | restart or handoff finds it | `pending` if this holder has the owner text, else `falling-back` |
| `sent` | status `delivered` | `delivered` (terminal) |
| `sent` | status `bounced` / `complained` | `falling-back` |
| `sent` | status window ends | `falling-back` |
| `sent` | restart or handoff | `sent`: polling resumes from `providerId` for the remainder of the window measured from `sentAt` (the window is absolute, not restarted) |
| `falling-back` | the holder sends the topic copy with its line directly through `deliverJobReport` and Telegram acknowledges it (a message id) | `fallen-back` (terminal), the message id recorded |
| `falling-back` | the direct send fails and the copy is **accepted into the durable relay queue** (`PendingRelayStore`, a per-machine SQLite that survives restarts and retries; `enqueue` is insert-or-ignore on the delivery id, so the outbox row id is the idempotency key and a crash between acceptance and the state write re-runs to the same entry) | `relay-queued` (non-terminal, checkpointed like every live row; `relayId` recorded) |
| `relay-queued` | the relay sentinel delivers the entry (`sentinel:recovered` for this row's delivery id, which is the outbox row id) | `fallen-back` (terminal) |
| `relay-queued` | lease handoff | the successor finds a non-terminal row with `topicText` and sends the copy itself; the standby's queued entry is refused by the lease (409, non-retryable) and the sentinel retires it; the parent's accepted one-duplicate-at-handoff is the worst case |
| `falling-back` | Telegram unavailable and the relay queue unavailable, or shutdown | stays `falling-back`; retried by the holder with backoff 1, 2, 4, 8, 15 minutes then every 15 minutes, **with a breaker: after 24 hours in `falling-back` (about 100 attempts) the timer stops and the row waits for the Telegram adapter's reconnect event (new in this change: the adapter emits once when its consecutive poll errors fall back to zero), the relay sentinel's `sentinel:recovered`, or the next lease handoff to resume**, so the self-triggered action count settles (`judgment-candidate; floor: never faster than once a minute, never slower than once an hour while the timer runs, the breaker never discards a row; default as stated`); the row still drains (Accepted Intake Must Drain) on the resume event or the drain on stop; the Telegram outage sentinel's existing notice tells the person; a restart or handoff picks it up like `pending` (0) with `topicText`, which every holder has |
| `fallen-back` | nothing | terminal |

Terminal rows (`delivered`, `accepted`, `fallen-back`, `failed`) get an `op: 'delete'` tombstone 24 hours later (`judgment-candidate; floor: no tombstone before the row is terminal, and `fallen-back` is terminal only on Telegram's acknowledgment, never on queue acceptance; default 24 hours, so a dashboard row shows a day of history`), and the fold hides them; earlier record lines persist in the file until rotation, which is why no owner text is ever in them. A row that cannot be admitted (record too large even after the cut) is created directly in `falling-back` with the status line. The holder-local text folder is outside state backups and named in the memory-privacy posture. `GET /email/outbox?limit=` lists rows with hashes only.

**Who sends (Ownership-Gated Side Effects):** emailing a report is a state write (the outbox append), so a job with `email` in `deliver` is `writesState`. **The guard this leans on, honestly:** the `writesState` role guard (`ws43RoleGuard`) is live on development agents and dark on the fleet today, and what fences a fleet standby's scheduler is `state.readOnly`; so this spec does not rely on either alone: **the email hook itself never enqueues locally when `!holdsLease()`**: a standby whose scheduler fired the cron anyway forwards the report to the holder through the same `email-send-forward` command the one-off uses (below), with the execution id as the idempotency id, so the holder appends the row and sends; if the holder is unreachable the standby carries the report to the job's topic itself through the ordinary Telegram fallback path with the `not-set-up-here` line (a Telegram send from a standby is refused by the lease, so that copy waits in the standby's relay queue until the lease returns or the holder drains it), and nothing is dropped. **Ownership is checked again at fire time**: the queue worker re-reads `holdsLease()` before every transport attempt and before every fallback send, so a row enqueued by a holder that has since lost the lease is left for the new holder (the row is replicated; the successor's recovery sweep takes it). **Durable intent before completion is acknowledged:** the outbox row (`pending`, `attempts: 0`, with `topicText` set to the status line until the body is rendered) is written as part of the job's completion bookkeeping, before the completion is recorded as done, and **the execution record carries the row id (`emailOutboxId`) written in the same bookkeeping step**, so the marker outlives the row's tombstone. The transcript read, the body render and the send follow off the completion path. A crash between bookkeeping and the row is covered by a reconciliation sweep at boot and hourly: a completed execution whose job has `email` in `deliver` and **no `emailOutboxId`** gets a `falling-back` row with the status line and the marker; an execution with a marker is never reconciled again, whether or not its row still folds (tombstoned rows are terminal by definition). Tested with crashes before the render and before admission, and with reconciliation after tombstoning and after rotation. A session's one-off on a standby is forwarded to the holder through **a new authenticated mesh command, `email-send-forward`** (`{ subject, text, fallbackTopicId }`): the existing `pool-view-fetch` carries only view reads and `telegram-origin` only `{ topicId, chatId, text }`, so neither can be reused; the command gets its row in the mesh RBAC table, a holder handler that runs the holder's own guard, outbox, budget and queue exactly as a local one-off, and a stated trust rule: **the standby validates the session's origin token** (it is that machine's session), **and the holder trusts the signed mesh envelope** for the caller's identity and `fallbackTopicId`, never a bare header. The command carries a caller-supplied idempotency id (the standby's outbox-style row id, minted before the forward), and the holder answers an existing row for a repeated id, so a mesh timeout after the holder accepted does not duplicate the one-off on re-issue. The holder re-runs the topic-level readers check on the carried `fallbackTopicId` itself (`topicHasOtherReaders(topicId)`, extracted from today's job-taking `notifyDestinationHasOtherReaders` so a one-off without a job can use it), never trusting the standby's check alone. The holder's answer (the row id, or a fixed refusal) is returned; if the holder is unreachable the route answers `holder-unreachable` and the session tells the person in one line. Nothing is dropped silently. **A holder without the credential or grant** (the lease moved to a machine the owner never said yes on) falls every row back within 120 s with cause `not-set-up-here`, and that machine's dashboard row says setup is needed there; this is the parent's per-machine rule, inherited and tested (failover to an unprovisioned holder).

**Accepted intake must drain:** turning the switch off (`email.enabled: false`) or stopping the service drains the outbox first (every non-terminal row is fallen back to its topic with its line), then the service stops. A revert of this change is preceded by that drain (rollout step below), so rows an older version cannot read are already terminal.

### The setup recipe (`email-v1`)

- **Shape A (Resend).** The owner types the recipient on the confirm page (it is also the address the agent opens the account with). The agent opens the account in a normal browser with that address; the signup mail Resend sends counts against the day's proof-mail bound (above). Resend emails a verification link to that inbox: a credential sent to the person, the parent's "a code sent to their phone" case, asked for through one Secret Drop and completed by the agent in its browser; the person never opens Resend. Resend's terms are a decision: the confirm page's account text names them and the yes is the acceptance. The agent creates the full-access key, stores it through the key route (plain text body, nothing printed) and notes on the row that the account holds nothing else.
- **Shape B (own mailbox).** The owner types their address on the confirm page, as in A and C. The agent needs an app password. It is provider-site work, so the agent does it in a normal browser signed in as the person, with the person's password and any sign-in code through Secret Drop, entered only through the stdin wrapper (never argv), consumed in one pass and never stored. The browser profile is a throwaway created for this step and deleted on every exit path (success, failure, abandonment); its lifetime defaults to 20 minutes and a waiting Secret Drop (a sign-in code on its way) extends it, to 60 minutes at most (`judgment-candidate`: floor deleted on every exit path and never past 60 minutes; default 20); the person is told to expect their provider's new-sign-in alert. **The agent never changes the person's account security without the person's explicit yes:** if the provider requires two-step verification before app passwords exist and it is off, setup stops with the fixed reason `provider-requires-two-step` and tells the person in one sentence what it means (a permanent change to how they sign in, with a second factor they hold), offering shapes A and C, or, if they decide so, their explicit yes to that change through the confirm page's decision text, after which the agent enrols the person's own phone number as the factor (never a factor the agent holds). The browser is signed out of the provider before the profile is deleted. `stop` removes the stored app password and tells the person it still exists in their account's app-password list, offering to revoke it with one more sign-in if they want.
- **Shape C (agent-owned mailbox).** The owner supplies the mailbox's address and password through Secret Drop, and types the recipient on the confirm page.
- **Key route** stores one JSON value under `email_sending` (`shape`, `transport`, credential, preset, and for B the SMTP username); it refuses a `recipient` field, and in shape B refuses with `recipient-mismatch` a username that differs from the stored `email_recipient`. The vault value is the version the proof binds to.
- **Two checks.** `verify` (the regular one, called by the in-use probe and a new regular re-check for key recipes that this change adds, since today only copy recipes re-check) sends nothing: Resend `GET /domains` (200 with no domains pass, any domain fail, 401/403 fail, else unknown); SMTP connect, TLS, AUTH, QUIT (235 pass, 535 fail, else unknown). `prove` (a new optional hook on `SetupRecipe`) runs from the setup session, on the lease holder, after the key is stored: it sends the proof mail ("Your agent can now email you", with the opt-in code in shapes A and C) and reads `Delivery`; **the row is `working` on: A, `delivered` plus the code entered on the page; B, `accepted-unproven` (said in those words; the recipient is the typed address the credential matched); C, `accepted-unproven` plus the code.** **One passing proof per credential version:** the result is keyed by the hash of the stored credential value plus the `recipientHash`; a pass for the same version is returned, never re-sent; a failed or unknown proof for the same version may be retried ten minutes apart, so a transient failure recovers. **Which bound wins:** in shapes A and C the unconfirmed-recipient bound rules (three mails a day including the first proof and, in A, the signup mail: so one retry on A's signup day, two in C); in shape B, whose recipient is confirmed by the match, three retries ten minutes apart (`judgment-candidate`: floor one pass per version and never past the day's proof bound or the provider cap; default as stated). A loop cannot spend the provider cap.
- `stop`: drains the outbox (above), removes the stored credential, `email_recipient` and `email_provider_account` (only when setup stored them); the provider account stays the person's.

### Using it: reports by email

- A job gains `deliver?: Array<'telegram' | 'email'>`: in `jobs.json` (`validateJob` has no closed field set, so an older instar ignores it; tested) and in `AGENT.md` jobs through the manifest path (`PerSlugManifest`, `validateManifest`, `manifestToJobDefinition`, and `ALLOWED_FRONTMATTER_KEYS`). An older agent **withholds** an `AGENT.md` job carrying an unknown key, so `deliver` is documented as `jobs.json`-first and the `AGENT.md` form is marked "needs this version or later" in the upgrade note.
- **Quiet by Default holds.** `email` is a per-job opt-in the owner makes on their own message as proof, like the per-job push choice; it never overrides a quiet job. `['email']` emails the report that would have gone to Telegram; `['telegram', 'email']` does both. Script jobs are excluded (their runner has no report text; the field is refused with a fixed reason).
- **Hook point and body:** `JobScheduler.notifyJobComplete`, with the summary built as two texts, the owner's (pre-redaction) and the topic's (redacted where the destination has other readers); the report path is extracted into `deliverJobReport(job, ownerText, topicText)` (lazy topic creation, recreate-on-delete and the hold handling as today) so the email branch and the later fallback call the same function. **The body is not the pane tail:** today's summary is the last 500 characters of a tmux pane that is usually gone, and the existing `readJobTranscriptEvidence` returns an audit digest with a 1,500-character cap, so this change adds a new accessor, `renderJobReportForOwner(job)`, over the same transcript reader: the job's final assistant message, uncut to the 16 KB bound, rendered to plain text (Telegram markdown and code fences stripped by a fixed converter with tests). **The accessor is framework-neutral; its readers are per framework:** today only claude-code has a readable transcript, so a job labelled codex, gemini or grok gets the status line as its body until a reader for that framework exists, and the accessor's interface does not change when one is added. When no transcript text exists the email carries the status line and nothing is skipped. The transcript read and the send both run after completion bookkeeping, off the completion path, through a serial queue (concurrency 1, `judgment-candidate; floor: 1 to 4; default 1: one message at a time keeps the provider cap and the budget record single-writer`; transport timeout default 15 s, adjustable `email.transportTimeoutSeconds` within 5–60; a timeout is `unknown`). **One transport attempt per row, then fallback** (`invariant; basis: irreversible-consequence; evidence: a second attempt without the provider's idempotency can double a report; Resend's own idempotency covers the crash-replay case, so a deliberate retry adds nothing`).
- **Fallback, always, with one voice:** on `failed`/`unknown`/`refused`, or email not set up, `deliverJobReport` carries the report to the job's topic with one plain line on why. The line is bounded per cause (`not-set-up`, `not-set-up-here`, `refused`, `unproven`) and per fixed reason within the cause, re-armed when either changes (`judgment-candidate`: floor one line per cause-and-reason per hour, conservative default one per day, adjustable `email.fallbackLineEvery`). A refused credential is an internal failure first: Self-Heal Before Notify applies (re-run `verify`; a fresh fail reopens the setup commitment through the existing re-check machinery; `max-notification-latency: 120s` from the first refused send to the fallback line; class `recoverable`). **Credential breaker:** one credential refusal (`535`, `401`, a `403` that is not Resend's recipient restriction) stops sends until `verify` passes (`invariant; basis: external-constraint; evidence: the provider's authenticated refusal says the credential is bad, so another send cannot succeed; re-armed only by a verify pass`); budget, rate and recipient refusals are not credential refusals.
- One-off: `POST /email/send-to-owner { subject, text }` (bearer + `X-Instar-Request` + the session's origin token; a caller with no origin token is refused with `no-origin-session`): same sender, guard, outbox, queue, delivery tracking and fallback; `fallbackTopicId` is derived from the authenticated session's origin token, never from the body. A one-off has one text, so when the session's topic has other readers (`notifyDestinationHasOtherReaders`) the route refuses up front with `topic-not-owner-only` rather than ever falling an owner-only text back into a shared conversation. The route is HTTP, outside the MCP external-operation gate; the fixed recipient and the guard are its controls, and `CapabilityIndex` says so beside its email trigger.

### Budgets

The daily budget is **a reservation, not a count of successes**: the lease holder keeps one per-day aggregate record in the outbox kind (`email-budget:<date>`, `put`, single writer) and increments it before every transport attempt, proof mails included, whatever the outcome; crashes therefore count conservatively. **What is guaranteed, honestly:** on one holder the reservation never exceeds the cap. Across a lease handoff, replication offers no barrier, so the attempts one holder made after its last replicated record are invisible to the successor: the local reservation can be exceeded by at most that in-flight tail (the parent accepts the same one-duplicate exposure at handoff), and **the provider's own `429` is the hard cap**, which the code treats as `budget-exhausted` for the rest of the day (`invariant; basis: external-constraint; evidence: the provider enforces its published cap, Resend 100, Gmail 500, iCloud 1,000, re-checked at build time; the local reservation is a best-effort reading of it, never the authority`). **One day for every holder:** "today" is the agent's email day in one timezone, `email.timezone`, defaulting to the granting machine's zone recorded on the yes row at setup, so two holders in different zones never keep two "todays". Within the cap, no fixed split: the reserve for reports is **derived from the day's remaining scheduled emailed jobs** (the cron of every job with `email` in `deliver`, counted to midnight in that zone); a one-off may use anything above that reserve (`judgment-candidate`: floor the cap; the reserve is computed, not configured; adjustable only by the owner's job choices). Over budget → `refused`/`budget-exhausted` → fallback. **Absence is not exhaustion:** a day with no record yet reads as zero sends; only an unreadable store (a failed read, a corrupt record) reads as exhausted (Verify the State: uninitialized is not stale).

### Surfaces

- `POST /email/send-to-owner`, `GET /email/outbox?limit=`, `GET /recommended-services/email/status` (row state, shape, masked recipient, today's budget) for the dashboard row; the `email-send-forward` mesh command (holder-side).
- Agent awareness: a section in `.instar/reference/messaging-2.md` (rewritten on update) plus its INDEX line and a `CapabilityIndex` entry with the proactive trigger ("the person asks to get something by email → set up email if it isn't, then `POST /email/send-to-owner`").

## Frontloaded Decisions

- Three account shapes presented as equals with stated concessions; Resend in the person's name is the one proposed as default (Echo's proposal, stated to the operator in topic 135786 on 2026-11-07 21:25 PT and standing unless the operator objects; the operator's approval of this spec is the decision).
- `nodemailer` for SMTP; Gmail and iCloud presets only; no Outlook.com.
- Resend: full-access key on the agent-created, domain-less account; the account holds nothing else; a recipient change in shape A is a new setup.
- The recipient is never set by a session; typed by the owner in every shape, confirmed in A and C by a code from the proof mail, matched against the credential's username in B. In A and C the code's honest limit (readable by a session that holds the sending credential) is stated on the page.
- Verification links and sign-in codes are credentials handed through Secret Drop; the agent does the browser work; the agent never changes account security settings without the person's explicit yes.
- Outbox as its own replicated kind with `rotateKeep: 3`, 16 MB files, live rows and the budget aggregate checkpointed hourly and tombstones after 24 hours; owner text holder-local and deleted at terminal; the outbox row is written before completion is acknowledged, with a reconciliation sweep; the budget is a per-day reservation record in one agent timezone with the provider's `429` as the hard cap; the lease holder sends, a standby forwards its fired reports to the holder and the holder re-checks at fire time, without relying on the dev-gated role guard; completed executions carry `emailOutboxId`; the hourly sweep checkpoints live rows and the budget aggregate; the live set is bounded with status-line admission past 200 rows; the fallback retry has a 24-hour breaker that resumes on reconnect; Resend sends carry an idempotency key; relay enqueues are keyed by the row id; a standby one-off travels by a new `email-send-forward` mesh command with its own idempotency id.
- **Per-machine grants are the parent's decision**, not this spec's: `recommended-services.md` (converged and approved) settled that a yes authorizes the machine it names, and every recipe inherits it; this spec adds no machine-local surface of its own beyond the deleted-at-terminal owner text.
- No reading of mail; no HTML; no attachments.

## Multi-machine posture

- **Grant: per machine** (the parent's rule: a yes authorizes the machine it names; `activeGrant` checks it). A second machine takes its own yes.
- **Credential, recipient and provider account (`email_sending`, `email_recipient`, `email_provider_account`): written by the machine that took the yes.** The cross-machine secret sync replicates every vault key outside its local-only prefixes (`machineIdentityRecovery.*` and the legacy `google_passkey_*` prefix), so these values do reach the other machines where the sync is on; a machine without a grant never sends regardless (`hasGrant`), so a synced value alone changes nothing. No machine-local justification is claimed: the values are replicable, and the authorization to use them is per machine by the parent's design. A holder without a grant falls back with `not-set-up-here` (above).
- **Outbox and budget record: unified**, one replicated kind, holder-only writer, one email day in one timezone; **owner report text: holder-local by design** (`machine-local-justification: operator-ratified-exception` is not claimed; it is simply not replicated because it is deleted at terminal and the destination-safe `topicText` is what a successor needs), falling back with `topicText` on a handoff.
- **Opt-in nonce: minted and checked on one machine** (keyed with its identity key; the confirm link names that machine's host), beside the grant it belongs to.
- **Sender: one voice**, the lease holder, re-checked at fire time; a standby forwards both its fired scheduled reports and its sessions' one-offs by the signed mesh command, never enqueuing locally. The dev-gated `writesState` role guard, where live, is a second fence, never the only one.
- **`verify` result: not stored**; re-run where needed.

## Self-heal

Refused credential: `verify` re-run on the next regular check; a fresh fail reopens setup through the existing bounded re-check (one re-check, then the setup commitment and one notice). Breaker as above; dedupe key `email:refused`; audit in the outbox rows (hashes and reasons). A `provider-recipient-refused` 403 sets the row `unproven` with that reason and asks for the page once (the recipient must be re-typed); it does not loop.
