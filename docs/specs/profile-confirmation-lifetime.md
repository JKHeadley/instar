# Confirmation requests remain available and visibly delivered

## Problem statement

A conversation can ask permission to move another conversation to a different coding engine. The question should remain available long enough for a person to answer, and a failed delivery must never look like approval.

Chief assignments 30c14d58-2240-48b3-9ad5-75d68a8c75d6 and 7cfecd0c-14de-4ec5-8980-e0c81c26a9a9 relay feedback fb-5f146e89-035 and fb-3146e534-ad9. This is a separate repair built on frozen PR 3653, not an amendment of its verified candidate. Extend the human response window, state its deadline, deliver intentional re-arms, and make every attempted confirmation explainable without widening consent authority.

Observed production evidence: logs/topic-profile-changes.jsonl records confirm-armed at 22:48:47.466Z and expired at 22:55:56.088Z. It records another armed event at 22:57:11.399Z, but the topic history contains no delivered fresh question before owner message 147086 at 22:57:24Z. Another arm occurred at 22:59:22.285Z. The reported duplicate-content hold and current legacy arm-before-send/catch-disarm path explain a plausible missing outcome. Compaction is correlated, not proven causal. Verify the final cause with a reproduction; never label a missing question as an accepted confirmation.

The deployed legacy mechanism differs from 3653: 3653 already requires an actual delivery receipt, stores several identified questions, preserves requests across agent messages, and varies intentional reminder text. Build on those controls rather than restoring ambiguous bare-yes selection.

## Proposed design

This changes the questions that ask permission to move a conversation to another coding engine. The frozen parent renders a server-owned description of the exact settings and runtime effect (the consequence core), and records which machine currently owns both conversations and at what ownership version (the placement stamp). These values must still match when applying.

### Time and retention boundaries

Validate the configured duration as finite, positive and capable of producing a safe finite deadline; invalid values use the provisional default and expose a configuration diagnostic. Compute expiresAt once at preparation, rounded up to a whole second, and display seconds plus a timezone so the visible instant equals the enforced instant. Prepare all validation/merge work against a detached candidate, including an absent topic. Do not call a mutating entryFor helper that publishes an empty entry before validation. Place the final expiry guard immediately before publishing the first confirmed state assignment, after synchronous validation/merge work, including the shadow-only path. An expired absent-topic attempt must remain absent after another topic flushes and the store reloads, and must not block mutateIfAbsent. Expiry is tested at that synchronous assignment commit point: now < expiresAt is required; equality is expired. Expiry aborts only work that has not reached that assignment. If the deadline passes during an asynchronous flush after valid assignment, report the actual saved or rolled-back outcome; never report expiration as if no mutation started. Test both successful persistence and rollback during a paused flush. A reply that arrived before the deadline but waited past it is rejected with the honest explanation that the request expired before it could be applied, followed by the existing fresh-question path. A receipt arriving at or after expiry is recorded as delivered-but-expired, never as a transport failure; it does not activate that new attempt. These cases must not silently restart or extend the timer. Configuration changes affect new requests only.

### Lifetime and wording

Identified proposal expiry is independent of switchNowConfirmTtlMs, which remains unchanged for legacy recovery commands. A new proposal captures one immutable expiresAt when created. The provisional default human window is 24 hours; this is a configurable product default, not a constitutional floor. Reviewers must contest it against actual delayed human replies. A reminder does not silently extend a deadline. An explicit fresh proposal after expiry receives a new identity and deadline. At the existing API boundary, POST propose with identical source, target, patch, consequence and placement while active intentionally reuses the same request and immutable deadline, creating a new visible reminder attempt. It is not an independent duplicate grant. The explicit remindRequestId operation likewise reminds that exact request; different changes retain independent identities. No new caller idempotency-key protocol or live replacement protocol is added. An active unchanged request is reminded under the same identity; after expiry a fresh proposal has a new identity. Independently requested changes, even to the same target, remain independent. Existing exact-change revalidation rejects an older question once its described consequence no longer matches current settings. This addresses the incident without adding successor activation races.

Every delivered question states its absolute deadline with an explicit timezone and how to answer: "Reply to this message with yes. I can apply this change until [date and time, timezone]." Prefer the verified owner's configured timezone; use labeled UTC when unavailable. The provisional 24-hour choice is not inferred from the seven-minute incident: it deliberately accommodates a full normal day and existing operator authorization requests also use a 24-hour human response window. It remains configurable, not a hard safety ceiling. The same immutable deadline appears in all reminders and the request status. Invalid timezone configuration falls back to UTC and cannot prevent delivery.

### Delivery and auditing

Every initial question, intentional reminder, and fresh re-arm contains its existing short request reference plus a readable Reminder ordinal; do not add a second opaque token to visible prose. The visible request reference and readable ordinal identify the request when asking for help and distinguish deliberate reminders without adding unexplained transport jargon. Normal outbound duplicate prevention remains enabled. OutboundContentDedup normalizes whitespace only; distinct identities must remain distinct through the actual origin adapter. A suppressed, held, failed, or missing-receipt send is never recorded as delivered. Intentional retries use a new registered attempt, not a duplicate bypass flag.

Audit prepared, delivered, delivery-failed or delivery-uncertain, expired, reply-rejected, applying, applied, and acknowledgment-failed transitions with request/attempt and native message IDs, safe reason enums, timestamps, and existing principal fields. Do not log secrets or incoming prose. Attempt terminal audit emission even when send fails or acknowledgment throws, and expose audit-unavailable honestly when it fails. A reply without native identification applies nothing; if verified owner and current request context permit, the existing registered reminder operation can supply a fresh question. Several candidates require clarification, never latest-request inference. An exact unbound yes in a conversation with a known prepared or delivery-uncertain proposal records no-native-identification or delivery-unconfirmed, applies nothing, and receives a plain explanation through normal conversation. The agent can request a registered reminder after checking the current owner and actual change. Do not claim compaction caused the failure, infer a latest request, or silently discard this reply. Other ordinary conversation remains ordinary conversation, with no claim of application absent a write outcome.

### Authority and race checks

Only the exact existing literal yes rule, verified owner, native reply to a delivered request, current source confinement, current placement ownership/epoch, unchanged consequence core, unexpired and unconsumed request may mutate. Move mode-specific patch splitting and runtime-plan construction into the same locked preparation snapshot that renders and verifies the displayed consequence. Do not compute a live/preview plan before acquiring the lock and then execute it merely because a separately recomputed question matches. The locked preparation returns one immutable patch/runtime plan used through the write; later callbacks cannot reinterpret it under another regime. Recheck owner, source, placement, unchanged consequence and expiry against that same snapshot. Test question-preview, reply-preparation-live, lock-preview observations and require zero live-setting writes or live runtime actions. Consumption happens before apply; the commit guard verifies that this invocation owns the consumed apply reservation, rather than wrongly requiring unconsumed status at commit. No language model chooses consent. Agent messages and context compaction do not delete requests. Restart restoration does not refresh placement stamps or authorize transfer. A former holder cannot start a new settings or runtime action after ownership moves. Carry the expected placement stamp through the onProfileWrite handoff into the queued idle executor and revalidate immediately before it begins a restart or first start; a check before handing work to a queue is insufficient. A stale queued action reports skipped-after-transfer separately from saved settings, never auto-retries on the former holder. Test ownership transfer after handoff while waiting for idle, then releasing the executor. Preserve the existing local commit point: final ownership/epoch validation and in-memory settings assignment occur synchronously inside the write lock. A transfer during paused asynchronous preparation must cause zero stale assignments and zero stale runtime actions. A transfer after that valid assignment but during asynchronous durable flush is not represented as an earlier rejection: report settings saved when persistence succeeds, and suppress stale runtime actions through the post-flush eligibility check. Do not claim a local lock prevents every disk flush after remote transfer, and do not add a distributed persistence fence in this incident repair. Tests distinguish the two orderings explicitly.

## Decision points touched

- Exact yes plus native receipt, verified owner, exact current change and unconsumed request — invariant; basis: irreversible-consequence; evidence: accepting a different person, target or mutation would spend operator consent on an unauthorized change.
- Single-use consumption and no restored authority — invariant; basis: irreversible-consequence; evidence: replayed inbound IDs or a restored old pending snapshot can apply an already consumed mutation.
- Request lifetime default 24 hours — judgment-candidate; floor: finite positive immutable displayed deadline, current owner and exact-change checks, no automatic extension; arbiter: operator configuration, with provisional full-day default if absent and an explicit configuration diagnostic plus that same default if invalid. Independent review contests the choice; it is not a constitutional ceiling. Expiry never relaxes owner or exact-change checks.
- Choosing whether an ordinary reply warrants a reminder — judgment-candidate; floor: only a server-validated registered reminder or clarification, never application; arbiter: normal conversational agent; conservative default and unavailable-context fallback: say "This reply did not start another change. I’ll check the saved settings and runtime state," then recover or ask for the missing intended change. Do not imply an interrupted original action never ran.
- Choosing among multiple requests — invariant; basis: enumerable-domain; evidence: a verified native reply identifies exactly one delivered anchor or none; ambiguous unbound text cannot select a patch. Clarification is the non-mutating fallback, never latest-wins inference.
- Lost server generation or interrupted application — invariant; basis: irreversible-consequence; evidence: a lost registry cannot establish an unconsumed grant, so replay cannot start a mutation. Explain uncertainty about any original action, recover actual state and never infer replay authority.
