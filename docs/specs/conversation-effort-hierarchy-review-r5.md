# Conversation and Effort Hierarchy — Review Round 5

**Reviewed:** v3 draft, installed Instar contracts, official Telegram/Slack documentation, and DAWN's verified MacBook review, 2026-11-04. **Status:** DAWN findings incorporated; implementation proof gates remain open.

## Architecture review

The mixed graph must include `coordinates` in its single-parent cycle check. Earlier drafts checked effort containment and conversation delegation but left the effort-to-conversation seam ambiguous. V3 now defines one mixed-node forest and keeps cross-links outside it. A move is one placement event, avoiding a half-applied remove/add pair. The selected storage design follows `AppConversationStore`'s durable source event file with derived index and uses `CoherenceJournal` as transport. Replicated envelope records are keyed by immutable event ID, so different corrections union; the graph reducer, rather than the envelope's last-writer-wins rule, computes placement conflicts. Implementation still must prove gap repair and two-machine replay with the real transport.

An offline-peer walkthrough caught a contradiction in v2: it marked only recent messages/platform metadata partial while implying the graph tree itself was complete. A peer can miss graph events. V3 now labels its graph revision and tree potentially incomplete until the missing event set is repaired and hashes converge; it never erases the last verified tree.

The durable unrotated source file raised a retention concern: owner-supplied effort titles could persist after a delete/forget action. V3 now bars transcript/summary text from graph events, requires peer-wide cache/index redaction and crash-safe compaction before accepting free-text headers, and lets read-only rollout use titles from existing authorities in the meantime. This is an implementation gate, not a claimed completed erasure mechanism.

The multi-machine source audit found a standby-write gap. A locally fsynced graph file on every machine would conflict with the existing standby write guard and could create two authorities during a partition. V3 now requires one write-admitted machine, signed/idempotent forwarding from standby, a pending-or-unknown result when delivery is ambiguous, and repair of the new writer's graph revision before it accepts corrections after failover.

A final event-format audit caught a circular signature definition: a receipt cannot sign a hash that includes the receipt itself. V3 now hashes only a canonical placement core, then signs that hash together with the verified owner principal, authentication method, admission epoch, and idempotency key. The receipt is stored beside the core and checked with machine trust and admission evidence on every peer. An event missing that proof is quarantined and makes the projection partial. V3 also has explicit out-of-order replay fixtures for concurrent moves, same-destination heads, late causal parents, a forged owner label, and duplicate event IDs with changed payloads. These are specification vectors; the implementation suite must execute them against the real reducer.

The replay review then found that “preserve the last valid forest” was order-dependent unless the prior placement is derived from event ancestry rather than arrival sequence. V3 now defines a pure event-set projection, common-ancestor fallback for incompatible heads, and an all-primary-edge cycle check with a two-effort cycle fixture. Under the current edge directions, `coordinates` enters the generic check but cannot itself form a path back from a conversation to an effort; a cross-link does not participate. These rules are still an implementation-facing model, not measured two-machine convergence.

An API consistency pass removed two stale phrases that contradicted the event model: “atomic move pair” and singular `fromEdgeId`. The change endpoint now specifies one placement event whose request names every observed head in `replacesPlacementEventIds[]`; this also handles two same-destination heads that the UI displays as one row. The server validates that observed head set before durable commit.

A retention pass noticed that an unrotated signed event log can persist actor identifiers as well as titles. V3 now restricts owner-only v1 events to an opaque agent-local owner principal; Telegram/Slack sender IDs, dashboard tokens, and device secrets remain at ingress and do not enter the graph event or receipt. A future delegated editor needs its own pseudonym and deletion contract. This minimizes personal data but does not replace the required crash-safe redaction test for user-authored headers.

An authority-boundary pass removed `set-viewer-preference` from the shared graph event kinds. A person's collapse state, filters, and pins belong to a principal-scoped preference authority and must not advance the structural graph revision. This keeps MSP view changes from becoming owner graph writes or entering the durable structural log.

Source inspection of `WriteAdmission` found a narrower seam than the proposed receipt requires: it has a synchronous lease-holder/read-only verdict for cluster-shared writes, but does not itself attach durable proof to an event. A follow-up inspection found `LeaseCoordinator.currentEpoch()` and `currentLease()` and `FencedLease.verifyLease()` already provide the signed lease ingredients. V3 now requires the graph write path to bind and persist that proof with its receipt, check it on peers, and test old-epoch replay, split-brain refusal, and a lease change during commit. The primitive exists; the graph-specific binding does not.

The write-surface review found one more required integration point: `WriteDomainRegistry` classifies routes and store operations. V3 now calls for both graph correction routes and graph source writes, including background imports, to be classified `cluster-shared`. A route-only guard would leave a bypass through non-HTTP writers.

The replication-reader review found that `CoherenceJournal` returns after a nonblocking enqueue, while its replicated commit observer waits for fdatasync. `ReplicatedStoreReader` is the installed no-clobber union funnel for peer records. V3 now requires an explicit merge between locally fsynced source events and that peer union so the local writer sees its acknowledged event before journal emission, while dropped-origin/conflict rules still govern peer data. Restart and refused-enqueue fixtures must cover this exact seam.

## Privacy and foundation review

`MobilePeople.mayUseConversation` defines owner/MSP grants. The current flat mobile list filters after merge and may advance its cursor over hidden rows; the graph API must filter first. The more serious underlying issue is `TopicMemory.formatContextForUser`: it filters recent messages, then includes the topic-wide summary and purpose. `TopicMemory.search` has no viewer parameter. Reusing either output in an MSP hierarchy view could leak private content. V3 requires viewer-scoped digest generation and message-level search authorization; separate bug feedback `fb-ac09bb24-fcd` records the foundation issue. Dashboard v1 is owner-only until a real human-principal seam exists.

`TopicMemory` updates its rolling summary at session end, which is too late to be the sole input for a parent status view during long worker activity. V3 now specifies source-event-triggered, debounced digest refresh with watermarks, topological primary-edge rollup, cross-link deduplication, and stale-on-failure behavior.

The review also found no existing effort-sharing grant. V3 therefore keeps owner-authored effort names, paths, and rollups owner-only; MSP mobile users retain their authorized conversation inventory and personal filters without seeing the owner's effort tree. Global placement changes require the owner principal. This is a deliberately narrower v1 permission contract, not a claim that a readable Telegram topic makes its parent effort public.

The dashboard owner-auth seam is now identified in source: `/dashboard/unlock` returns a short-lived `operatorSessionToken` separately from the ordinary API bearer token, and routes can verify the `x-instar-operator-session` header with `verifyDashboardOperatorSession`. V3 requires both proofs on owner graph routes. This resolves the design ambiguity; the implementation still needs a route-level test that bearer-only calls fail and a cross-machine re-unlock path.

## Product review

V3 specifies desktop two-pane and mobile single-column Conversations flows, original transcript dominance, front-door breadcrumbs, source-linked decision badges, correction/undo/conflict sheets, flat inventory, stale/partial states, and accessible actions at 320 px. This is a written interaction contract, not a visual or screen-reader prototype. Prototype validation remains a build gate before default-on.

Paper walkthrough at 320 px: the owner opens a root effort, taps a fourth-level worker, reads the original transcript, and opens the path sheet to return to the front door. Search for that worker instead opens the same transcript with Back to results and Go to front door. A correction sheet lists candidate parents by name and path, previews one move, and after commit leaves focus on the moved worker with Undo announced. If another correction raced, the sheet shows the last agreed path and both permitted destinations; the user selects one resolution.

A local clickable sample at `conversation-effort-hierarchy-prototype.html` now exercises the desktop two-pane and mobile single-column layout. It shows an effort containing a front-door conversation that delegates to worker conversations, plus a four-level path through a mobile sub-effort, transcript context, move preview, undo, and a conflict demonstration. Product review caught a mismatch with the owner's noise goal: the first desktop sample exposed every worker row by default. The default Overview now shows only top-level efforts; workers appear after opening a branch or choosing All conversations. A Chromium run at 320 px verified the quiet initial state, traversed the deep path, checked front-door children, moved and undid the worker, resolved the sample conflict, saw no page error, and found no horizontal overflow. A desktop run checked that All conversations and search expose a worker with its front-door path, then Overview returns to a quiet root-only list. A keyboard pass opened the move sheet with Enter and checked focus returned to the conversation after move and undo. This is interaction evidence with sample content, not a production app integration or a screen-reader evaluation. Source-link actions remain placeholders; exact authorized linking is an implementation acceptance test.

## Platform review

Official Telegram Bot API documents `hideGeneralForumTopic` only for General; closing or deleting an ordinary topic does not provide reversible, per-user worker hiding. Telegram Bot API topic support in private chats is now documented and does not change that limit. Slack's custom sections are user-visible preferences on paid plans; mute/hide is a client setting. Slack has channel and message deep links, with permission checks. The Instar app/dashboard must own the hierarchy and quiet-worker filter; Telegram and Slack adapters provide identity, history, and navigation.

The review found a credible optional Telegram noise workaround: new worker topics in a separate forum group that the user mutes/archives as a whole. It preserves histories and links but requires a second group and user-side archive choice; no existing topic moves automatically. Slack's optional analogue is user-managed custom sections or a worker channel with threads, with discoverability and permission tradeoffs. V3 records both as opt-in pilots, not core platform promises.

Installed `TelegramAdapter` has a main `chatId` and optional `issuesChatId` with disjoint topic space. A worker group is not a configuration-only reuse of that issues route; it requires a separate worker-chat namespace, routing, and identity tests. V3 now says so explicitly.

A live import probe found a source-shape mismatch relevant to title inference: `TopicMemory` listed 166 topics with zero populated names and only 40 rolling summaries, while the Telegram adapter listed 170 topics, 166 named. Fifteen title values repeat across 30 named rows. V3 now requires scoped identity joining and unmatched-row reporting. Reading `TopicMemory.listTopics()` alone would make title inference appear impossible; trusting title similarity from adapter metadata alone would still miss history/summary coverage and cross-chat identity.

V3 also adds on-demand conversational use in existing Telegram topics and Slack threads: owner asks for cited effort status, worker list, or placement provenance; a worker can link back to its front door. Chat corrections use verified owner identity, a preview, expected revision, and the same graph write API. This meets the user's platform-leverage question without claiming a platform sidebar can be controlled.

The installed `SlackPrincipalResolver` already maps an authenticated Slack `U…` ID to a registered principal and role, while the adapter has an authorized-user check. V3 now requires both for Slack graph corrections and rejects display-name authority. The exact route wiring remains an implementation test, not a missing design choice.

## DAWN substantive findings and disposition

1. **A topic history can look complete while its tail is missing.** DAWN's 30-day Telegram injector exceeded roughly 20 KB; the harness moved it into a file and exposed only an old 2 KB slice. A new session reopened decisions already settled in the missing tail. Her fix used a bounded recent slice, a required 14-day catch-up file, and a Stop hook that refused an answer if the catch-up was not read. V3 now requires read receipts and a structural coverage gate before claiming a complete digest or verified result. A partial on-demand answer may be shown only with the missing range named. Implementation may reuse a hook or enforce the same invariant inside digest generation; a prose reminder is insufficient.
2. **Single-machine logs gave half a conversation.** DAWN's cross-node read merged the logs from every machine. V3 now names contributing machines and stores and their high-water marks in digest coverage, plus missing ranges. The word “partial” by itself is not an adequate explanation.
3. **A lost timezone changed a decision.** DAWN saw a UTC timestamp lose its `+00:00` suffix and be read as local late-night time, causing work to be put off. V3 now requires full offset-bearing wire times and explicit local zone in freshness/digest presentation, including chat.
4. **Upward reports can launder claims into facts.** DAWN's most expensive case was work called done after a commit that had not landed. V3 now separates a worker claim/source from outcome-specific verification evidence/state. “Done” requires a source proving the actual claimed outcome; a commit is not evidence of merge or deployment. Parent notices and status badges follow the same rule.

An adversarial pass on those changes found two further design requirements. First, a source list built only from the histories that answered would silently mark a half-history complete; v3 now requires an independently maintained machine/store inventory and expected high-water marks before the digest coverage gate can pass. Second, treating any missing history as proof that a directly cited artifact is unverified would conflate scope: a verified merge can be reported within a partial digest, while an effort-level completion claim remains blocked until its full coverage and outcome evidence are established. The first standards rerun surfaced a third gap: graph replication alone would leave memory-bearing worker history stranded on the first machine. V3 now requires recoverable authorized history ranges through replicated segments or verified platform fetch, and an observer-loss recovery test. These are review findings incorporated into the current design, not implementation results.

DAWN explicitly supported the Conversations tree, one primary parent with cross-links, owner-only placement, and advisory suggestions until a pilot. She singled out “missing history is named, never treated as nothing happened” as a hard acceptance test. This is her stated review position, not a production validation of the implementation.

## Verdict and next checks

V3 resolves the model-shape ambiguity and makes the privacy boundary much more precise. DAWN's review exposed four handoff/history risks, now encoded as gates and test cases. A first post-review 94-standard rerun found that source history itself needed a machine-loss recovery contract; that gap was addressed and the next rerun flagged zero possible violations. The sample flow has a narrow-screen browser pass; it still needs a real screen-reader pass and integration with authorized data. This is a reviewed design with explicit build gates, not a production validation of event repair, owner auth, or digest coverage.
