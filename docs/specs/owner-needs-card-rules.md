# Needs-you Cards That Can Be Finished in Place

## Problem statement

An owner saw a disk cleanup card with a button to open the dashboard. The agent could handle the cleanup. An audit of the 41 visible Needs-you rows found that all 41 used dashboard links, including approvals and credential requests. The audit recommended one agent route, one navigation summary removal, three vague asks for retirement or clarification, and 36 rows for in-place conversion or exact source authority review. The pooled disk card was additional to the 41 displayed rows.

## Proposed design

Apply one owner-card admission check before presenting an item from an operational source. The source resolves who can act from its authoritative state and assigns agent-fixable work to its existing owning session or project. Agent-fixable disk cleanup, context repair and sign-in repair use that path. If source authority establishes that only the owner can act, it supplies exactly one typed action. Unknown ownership holds the presentation and remains visible to the source owner.

A source supplies instructions from a reviewed template with typed parameters from that source’s trusted state. Slots accept exact enumerations, display names or numeric values. Reject an inserted command or sentence. The phone update procedure takes no free-text instruction parameter. The admission check rejects dashboard directions in prose as well as navigation fields. An instruction card contains all steps needed to perform the owner action. For example, it can describe how to update and reopen the app on the phone. A step that sends the owner to a dashboard page is inadmissible. Retire the card on its exact source success event or a scoped owner acknowledgment when the source explicitly permits acknowledgment. The supported action families are approval, Secret Drop credential collection and ordered instructions. An approval action references either one current approval request or one current batch disclosure that binds several requests. In both cases there is exactly one card action. Approval and decline are choices within that action. If any dashboard or other navigation action remains, hold the card and return it to its owning source for repair. Do not use a dashboard page, work board link or conversation link as an action or fallback. Approval and credential references must resolve to existing current requests for this exact owner. The check cannot create authority or remove an approval hold.

In the owner Needs composer, enforce the check before merging, counting, caching or paginating owner cards. The owner web, app and Mac clients render the typed action in place and retain their existing approval and credential authorization. Team views retain their own authorization and projection. The app and Telegram renderers validate the typed action again immediately before rendering or emitting a card. Telegram only posts to a verified owner audience when that renderer can complete the action in place. Until a signed per-owner approval handler or a protected in-place credential form exists on that surface, keep those card types with the source. Telegram may render text instructions that remain safe and useful if the request is reassigned. Keep ownership-sensitive instructions on a surface that revalidates current ownership before showing them. Revalidate caller, request and ownership at execution for action handlers. An old action message after reassignment returns only a generic unavailable status. A malformed or unresolved action never emits a dashboard fallback.

This first completion batch contains the five requests identified in the audit. Additional batching policy requires its own scope decision. Model it as one stamped approval-batch action referencing the existing completion requests. The disclosure can submit a subset of answered choices and leaves unanswered items pending. An empty submission is refused. Test a five-request disclosure with one submitted choice and verify the other four stay pending. Reuse Identity’s paired-device presence challenge, disclosure digests, and signed receipt design. Give project completion a distinct signed action routed to the Chief of Staff completion authority. Bind the exact projects, binding versions, visible evidence and each owner choice to one disclosure. Offer an individual Approve or Decline choice within the single disclosure. The signed bundle records each choice. Recheck each item on execution and return durable per-item outcomes. Key each completion request by project binding and its exact completion episode. Atomically consume the expected request version and verify the signed evidence revision and current eligibility for either choice, regardless of which disclosure or device carried it. The same choice can recover its result, and an opposing choice cannot mutate the consumed request. The completion authority records the result with the project transition, or supports exact recovery by that same key. Test interruption after the first project completes and exact retry of the bundle. Test evidence retraction between signing and execution. Also test two eligible devices submitting opposing choices for the same pending version. A decline consumes that request and leaves the project open without permission to complete it. Repeated evaluation keeps the declined episode quiet. A documented new completion submission with changed verified outcome or binding starts a new episode. A disputed or stale project stays open while other approved projects can finish. The Work Board approval-to-start action keeps its current scope.

In Attention, apply the same check to owner entry points for list, pool, detail and the mobile owner detail. Preserve agent lifecycle and incident access through an explicit authenticated agent path. Route agent-fixable observations to the existing owning session or project before they can produce an owner notice. Read-side suppression is a compatibility backstop for older or stale rows. Source rerouting is idempotent by source item and episode and does not close the item. A held row must stay visible to its source. If a current, verified owner ask lacks an in-place action, show only an aggregate unavailable status without the request title, project or action. Revalidate current owner, request and episode immediately before serving or redisplaying cached sensitive instructions. A cache hit never substitutes for that read. If the holder cannot establish current ownership, expose only generic source availability independent of whether a request exists. Do not derive a status from another owner’s history. A recovered holder must resolve the exact current owner and request again before restoring the card.

## Decision points touched

- Who can act — judgment-candidate; source authority owns the decision. Unknown ownership holds the owner card and returns it to its source.
- In-place action count, schema and reference binding — invariant; basis: enumerable-domain; evidence: one supported action and no handoff.
- Approve, decline or submit a credential — invariant; basis: irreversible-consequence; evidence: existing request validation and current owner authorization remain the execution boundary.

## Multi-machine posture

Apply the owner projection after pooling and to both detail paths. For bounded peer pages, continue scanning raw pages until enough admitted rows are found or every source is exhausted. Owner counts cover admitted rows only. An opaque, authenticated continuation preserves each source scan position and the owner binding without exposing held rows. Return it even if the bounded scan admits no rows. Expose incomplete coverage if the bound is reached; never turn a page of held rows into a complete empty answer. Resolve action references using the source authority on its current holder. If the holder is unavailable, hold the action. Keep operational records in their existing source stores. Do not replicate credential contents or create a second owner notice.

## First source corrections

Route disk cleanup and context recovery to their owning agents. Route automatic sign-in diagnosis to the account project. Preserve any live operator approval hold for sign-in repair and present it only as an in-place consent action when the source can supply one. Remove the Work Board overflow row from the owner model. Withdraw the exact waiting episodes for Instar App, Remote Access and Feedback Reports once the coordinator can write a verified retirement. The record retires only the specific ask. It does not finish, pause, or grant approval for the project. These source corrections do not remove an existing approval hold.

## Verification and rollout

Unit tests exercise the three allowed actions, agent work, unknown custody, zero or multiple actions and dashboard handoffs. Integration tests cover both owner route families, local and pooled attention, mobile and web, direct detail reads, invalid references and no side effects on listing. Provider tests verify disk and automatically repairable sign-in go to the owning project. Production lifecycle tests verify each enabled surface and action combination. App and web in-place actions must complete without navigation. Telegram safe instructions must render directly and stay safe on reassignment. Telegram approval or credential cards stay with their source until the corresponding in-place feature passes its own execution test. The agent path retains held items. Negotiate support for the in-place schema from a tested client capability. Activate Echo enforcement after supported web, phone and Mac clients demonstrate their enabled approval, credential and instruction combinations, and Telegram demonstrates safe instructions and suppression of unsupported actions. Test a held-only prefix longer than the full scan limit and use its continuation to reach the eligible card. Test sensitive instructions after reassignment following a cache fill. A downgraded client after activation receives a plain update-required status without the pending card details or a dashboard link. The source continues to hold the unresolved decision. Test this downgrade and a reassignment while the holder is unavailable.

## Maturation plan

- **test-agent-live:** Exercise route fixtures and the production lifecycle with synthetic requests.
- **dev-agent-live:** Enable for the Echo owner surfaces after in-place actions work in the supported clients.
- **fleet:** Extend to other agents after the Echo audit and rollout checks pass.
- **graduation criterion:** A real approval, credential request and direct instructions are visible and usable in place, and a real agent-fixable item reaches its source without an owner card.
- **dark-window:** Revisit within 28 days if any client or source still cannot meet the criterion.
- **ladder:** not applicable: owner presentation rules follow the tested client rollout rather than a separate registered ladder.
