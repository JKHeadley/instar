# Needs-you Cards That Can Be Finished in Place

## Problem statement

An owner saw a disk cleanup card with a button to open the dashboard. The agent could handle the cleanup. An audit of the 41 visible Needs-you rows found that all 41 used dashboard links, including approvals and credential requests. The audit recommended one agent route, one navigation summary removal, three vague asks for retirement or clarification, and 36 rows for in-place conversion or exact source authority review. The pooled disk card was additional to the 41 displayed rows.

## Decision points touched

- Admission — invariant. basis: enumerable-domain; evidence: the typed owner action union and source-vetted request identity. Admission requires a matching declared action type, one target, current owner authority and reviewed presentation. These are exact facts from the request service. Only an allowlisted server adapter may declare an action from the authenticated source and audience. A raw writer field, peer display payload, title, source label or urgency is a signal. Include a negative test for a spoofed ownerAction declaration. Unknown authority leaves the source request pending and discloses no details.
- Source ownership — judgment-candidate. When the source cannot establish whether an ask genuinely needs the person, the owning project resolves it under its existing authority. The deterministic floor keeps the item with the source and supplies no owner action. The owning project may route a separate request to Chief of Staff with evidence. A missing arbiter leaves the item held. A source failure on a known approval produces an unavailable status without granting action.
- Execution boundary — invariant. basis: irreversible-consequence; evidence: signed actions can change the bound source decision, so the read cannot execute them. Owner projection does not release holds or execute source work. Signed execution has its existing recheck of current request and caller.
- Migration — invariant. basis: enumerable-domain; evidence: explicit false, explicit true, or absent are the only supported settings. Existing and newly installed agents load the same default-on setting when the release is ready. Migration preserves an explicit rollback value. Validate both startup paths.

## Multi-machine posture

Owner decisions use authoritative source reads on the current serving holder and the existing merged or replicated read for the corresponding source. Account credentials remain on the authorized machine. machine-local-justification: physical-credential-locality. The owner projection is request-scoped and is rebuilt from the current sources. It creates no new replicated database and treats incomplete peer views as unavailable. The project queue owns agent work and the source retains its record across owner-view filtering.

A read has a ten-second end-to-end budget and at most eight concurrent source checks. A bounded scan uses at most 500 authorized candidate checks per response. A timeout or work limit makes coverage incomplete and reports a lower bound with an owner-bound continuation. It cannot certify a final total. Batch repeated exact lookups only within the same request and current authority snapshot.

For retention proof, record the source key and the id of the corresponding agent-visible record or a verified destination receipt. The owner count is not that receipt. Keep an unresolved routing item held at its source when no project intake is yet available.

## Proposed design

Apply one owner-card admission check before presenting an item from an operational source. The source resolves who can act from its authoritative state and assigns agent-fixable work to its existing owning session or project. Agent-fixable disk cleanup, context repair and sign-in repair use that path. If source authority establishes that only the owner can act, it supplies exactly one typed action. Unknown ownership holds the presentation and remains visible to the source owner.

A source supplies instructions from a reviewed template with typed parameters from that source’s trusted state. Slots accept exact enumerations, display names or numeric values. Reject an inserted command or sentence. The iPhone update procedure uses the reviewed TestFlight template and takes no free-text instruction parameter. The server renders steps from the template and sends those steps to the client. The owner list renders only reviewed copy selected by a template identifier that matches the exact action type. It accepts no free-text presentation object and refuses navigation fields. The signed consent view shows the authorized source disclosure. An instruction card contains all steps needed to perform the owner action. For example, it can describe how to update and reopen the app on the phone. A step that sends the owner to a dashboard page is inadmissible. Retire the card on its exact source success event or a scoped owner acknowledgment when the source explicitly permits acknowledgment. The supported action families are approval, Secret Drop credential collection and ordered instructions. An approval action references either one current approval request or one current batch disclosure that binds several requests. In both cases there is exactly one card action. Approval and decline are choices within that action. If any dashboard or other navigation action remains, hold the card and return it to its owning source for repair. Do not use a dashboard page, work board link or conversation link as an action or fallback. Approval and credential references must resolve to existing current requests for this exact owner. The check cannot create authority or remove an approval hold.

In the owner Needs composer, enforce the check before merging, counting, caching or paginating owner cards. The owner web, app and Mac clients render the typed action in place and retain their existing approval and credential authorization. Team views retain their own authorization and projection. The app and Telegram renderers validate the typed action again immediately before rendering or emitting a card. Telegram only posts to a verified owner audience when that renderer can complete the action in place. Until a signed per-owner approval handler or a protected in-place credential form exists on that surface, keep those card types with the source. Telegram may render text instructions that remain safe and useful if the request is reassigned. Keep ownership-sensitive instructions on a surface that revalidates current ownership before showing them. Revalidate caller, request and ownership at execution for action handlers. An old action message after reassignment returns only a generic unavailable status. A malformed or unresolved action never emits a dashboard fallback.

For a trust approval shown on a paired device, use the existing accepted-device request list and the signed approval challenge. Bind the displayed request to its request ID and proposal hash, and resolve it again under that device's current acceptance when the person acts. Keep the full disclosure in the consent view. The existing device approval route remains the authority and returns the outcome. A console session can read its eligible Needs You list, but the device approval requires the accepted device's presence signature. A disposable browser can exercise the signed flow only when its fixture explicitly supplies a paired test principal and a test signer. A bearer token on its own cannot stand in for either.

The first completion batch is an authoritative manifest of the five exact request episodes identified by the source. Audit positions and titles do not establish identity. Additional batching policy requires its own scope decision. Model it as one stamped approval-batch action referencing the existing completion requests. The disclosure can submit a subset of answered choices and leaves unanswered items pending. An empty submission is refused. After a partial submission, issue a fresh disclosure and signature for only the still-pending requests. Re-read their evidence. The original submission remains available for exact receipt recovery. Test a five-request disclosure with one submitted choice and verify the other four stay pending. Reuse Identity’s paired-device presence challenge, disclosure digests, and signed receipt design. Give project completion a distinct signed action routed to the Chief of Staff completion authority. Bind the exact projects, binding versions, visible evidence and each owner choice to one disclosure. Offer an individual Approve or Decline choice within the single disclosure. The signed bundle records each choice. Recheck each item on execution and return durable per-item outcomes. Key each completion request by project binding and its exact completion episode. Atomically consume the expected request version and verify the signed evidence revision and current eligibility for either choice, regardless of which disclosure or device carried it. The same choice can recover its result, and an opposing choice cannot mutate the consumed request. The completion authority records the result with the project transition, or supports exact recovery by that same key. Test interruption after the first project completes and exact retry of the bundle. Test evidence retraction between signing and execution. Also test two eligible devices submitting opposing choices for the same pending version. A decline consumes that request and leaves the project open without permission to complete it. Repeated evaluation keeps the declined episode quiet. A documented new completion submission with changed verified outcome or binding starts a new episode. A disputed or stale project stays open while other approved projects can finish. The Work Board approval-to-start action keeps its current scope.

For the separate Attention detail and notification acceptance slice, apply the same check to owner entry points for list, pool, detail and the mobile owner detail. The first release claim covers the Needs You list routes and their clients. Existing direct incident access and notification authorization continue under their own policies. Preserve agent lifecycle and incident access through an explicit authenticated agent path. Route agent-fixable observations to the existing owning session or project before they can produce an owner notice. Read-side suppression is a compatibility backstop for older or stale rows. Source rerouting is idempotent by source item and episode and does not close the item. A held row must stay visible to its source. Count undeclared and agent-owned rows diverted from the owner projection. Count known approvals whose verification fails separately and show that they could not be checked without providing an executable action. A confirmed stale approval disappears without an unavailable status. If a current, verified owner ask lacks an in-place action, show only an aggregate unavailable status without the request title, project or action. Revalidate current owner, request and episode immediately before serving or redisplaying cached sensitive instructions. A cache hit never substitutes for that read. If the holder cannot establish current ownership, expose only generic source availability independent of whether a request exists. Do not derive a status from another owner’s history. A recovered holder must resolve the exact current owner and request again before restoring the card.

### Pooled reads and pagination

Apply the owner projection after pooling for the Needs You list. Local and peer detail handlers will use the same projection in the separately tracked Attention detail slice. For bounded peer pages, continue scanning raw pages until enough admitted rows are found or every source is exhausted. Preserve source ID, source-assigned opaque item identity and episode through pooling. Apply source authority classification before cross-source covers or deduplication can remove an eligible action. Owner item counts cover admitted rows only. A bounded incomplete response reports only an explicit lower bound, including zero confirmed so far, and omits an exact total. An opaque, authenticated continuation preserves each source scan position and the owner binding without exposing held rows. Resume at the first unreturned candidate in each source, including a usable candidate already scanned but displaced by the page size. Revalidate before return. Return the continuation even if the bounded scan admits no rows. Expose incomplete coverage if the bound is reached; never turn a page of held rows into a complete empty answer. Resolve action references using the source authority on its current holder. If the holder is unavailable, hold the action. Keep operational records in their existing source stores. Do not replicate credential contents or create a second owner notice.

## First source corrections

Route disk cleanup and context recovery to their owning agents. Route automatic sign-in diagnosis to the account project. Preserve any live operator approval hold for sign-in repair and present it only as an in-place consent action when the source can supply one. Remove the Work Board overflow row from the owner model. Withdraw the exact waiting episodes for Instar App, Remote Access and Feedback Reports using a separate coordinator withdrawal record. The source resolves a live authorized coordinator and current lease. Under its write lock it atomically checks the exact project binding, episode, request version and pending state against owner decision execution. An exact retry returns its recorded withdrawal. A rebound, revised or consumed request cannot be retired by this operation. Publication and action execution both recheck the current exact withdrawal. The record retires only the specific ask. It does not finish, pause, or grant approval for the project. These source corrections do not remove an existing approval hold.

For Chief of Staff waits, derive the episode from the first effective waiting check and the request version from the published decision and the source record that supplied its wording. Carry-forward checks preserve the version when the request is unchanged. A new episode or a changed action or disclosure gets a new identity. Use the complete coordinator journal to resolve past withdrawals, so rotating the journal tail cannot make an old ask reappear. An incomplete read returns unavailable.

The session manager's conversation lock is local to its process and currently protects session launch and audience changes. It does not serialize Chief of Staff decisions across machines. The coordinator writer must own the compare and append under the serving lease, with the lease epoch fenced at the write. For a request-bound completion, gather evidence first, then under that same writer boundary reload the binding and exact request, check withdrawal and pending state, and commit the decision. The shared project finish path currently emits a verified check before its final recheck. Treat that check as a decision side effect and place it behind the withdrawal fence, along with the close. Test both orderings, that a withdrawal during evidence gathering prevents either write, and that a journal rotation preserves the withdrawal.

The journal flush writes queued records one line at a time before syncing them. A two-line flush can therefore persist only the verified check after an interruption. Store a request-bound approval as one journal entry containing the exact request identity and both the verified evidence and close transition. Project and request readers must apply those effects together from that entry. Test restart before append and after append but before acknowledgement. The exact retry must recover the recorded decision.

The existing emitter acknowledges queue admission. The flusher can retry a guard-refused batch later, and its durable sequence watermark covers the stream rather than proving that a specific decision was appended. Before enabling the coordinator adapter, provide a writer that checks the expected lease epoch at the disk append boundary, prevents a refused decision from being retried after a lease change, and acknowledges the exact durable record. Verify lease loss between preparation and append, guard refusal followed by a later flush, and restart recovery of an append whose acknowledgement was lost.

## Release activation and migration

Use `needsYou.ownerAdmission.enabled` as the runtime setting. On the first PR, an absent value keeps the legacy projection. On the subsequent fleet rollout, an absent value resolves to true on both startup paths. The existing-agent migration writes true only when the value is absent and is idempotent. Explicit false remains a rollback setting. In a mixed-version fleet, only the node that performs the final owner projection can certify the new contract. Never treat a legacy peer's displayed row as an owner action solely because it was displayed. A holder that cannot provide current authority contributes a generic unavailable source result.

Before the default-on release, run the disabled and enabled paths on disposable agents. Verify all nine sources, the upgraded and downgraded clients and a known pending approval. When a device needs pairing or enrollment, keep the real approval pending under its existing authority. A known owner receives a generic couldn't-check status until the device can act. Pairing or enrollment becomes a separate owner action only when its source supplies a verified, supported in-place step. The rollout proof must include the current Work Board policy decision waiting for a paired device. For an owner who has no accepted device, exercise existing local Mac device pairing and acceptance in Changes to approve, then reopen the exact pending proposal. Prove that the same request becomes actionable without a substitute consent or duplicate ask. If the owner has no usable authorized pairing path, keep activation held for that rollout. Unsupported clients receive the update-required status. Their source requests remain pending. Clients do not append pending approvals or FleetAsk rows to schemaVersion 2. They hydrate only the exact action reference already admitted by the server, and discard stale actionable cache before showing a fresh list. SchemaVersion 1 keeps the legacy behavior. The continuation token is opaque and bound to the caller and current projection. Each client encodes it in the request URL before signing. Keep new execution adapters off until they independently pass their own action tests.

Owner-facing counts are computed only over audience-authorized input. Source results distinguish an authorized current action, known owner verification unavailable, confirmed stale or refused, audience unknown or different, and authorized agent work or undeclared public records. Undeclared audience-authorized records and agent work contribute to the diverted count. Unknown or different audience never contributes to a row, count or request-specific note. An unavailable verification contributes to the approval status only when a separate current audience check has already established the request belongs to that owner. Generic source availability can be reported without reference to any individual request.

The first-release check is an exact owner action that remains reachable on an eligible client, alongside agent work excluded from the owner list and retained in its actual source queue. Check duplicate source keys, cross-source covers, bounded scans with a held prefix, reassignment during a read, a source failure after audience verification, and mixed-version peers. The gate's diverted count measures projection. Source queue acceptance is separate evidence. The first slice does not change trust policy, close any project or choose a new action on behalf of the owner. The Dashboard Home count and strip both use the same authorized projection, including the unavailable approval status. Upgrade the real client request and renderer before activation. The synthetic canary uses an explicitly authorized internal fixture through the same admission path. If that fixture is unavailable, disable its legacy scheduler with an explicit availability state so the rollout does not create false misses.
