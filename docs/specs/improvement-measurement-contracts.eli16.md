# An improvement needs a real before and after

A feature can count its activity and still do the wrong thing. The existing measurement contract already says which numbers to check, their targets and how often to check. This change lets that same contract name the intended outcome, the person or process accountable for reviewing it, the evaluation method and version, and the quality safeguards. It also names the exact stored observations used as its baseline.

Writing down a baseline number is not enough. The existing measurement store must contain the matching observation, with the same source, time, value, sample count and version. The current value must be the latest recorded one, fresh enough and compatible with the baseline. A missing, stale, future, ambiguous or incompatible record leaves the comparison unavailable. A busy neighboring feature cannot push the baseline out of sight merely by filling a recent-results list.

The existing summary shows how many current measurement subjects have a declared outcome contract. That count is not universal coverage and does not mean their baselines were verified. Asking for one feature shows its detailed baseline/current evidence, sample counts and numerical change. It does not announce that the feature improved: an owner still has to judge whether the measured outcome and quality safeguards are the right ones. The same facts survive a read from another machine; unsupported or malformed peer evidence remains an explicit gap.

Old contracts stay compatible. This adds no database, scheduler, promotion authority or new background loop. Adding a baseline changes the recorded contract version series and restarts its comparison/soak, so it cannot manufacture a gain by quietly changing the rules. The larger effort still owes independent universal coverage, generic effort contracts, useful visual history, an at-a-glance check and evidence of recurring corrective review. This patch is the recorded-contract foundation for that work, not a claim it is all complete.
