# Replies after a restart: order and honest delivery notices

A server update can interrupt a Telegram reply after it was written but before it reaches the conversation. Instar keeps some failed replies in a delivery queue and retries them. In the November 3 case, one older reply reached Justin about an hour late, after newer answers. Another reply went through two known failures, then an attempt whose result could not be confirmed; it expired without a clear explanation in the conversation. A previous fix, PR #2696, made confirmed recovered messages appear in history and raised attention for one kind of held send. It did not change the order of queued replies or explain uncertain outcomes.

This change makes the older queued reply go first when the legacy recovery queue has several replies for one topic. The current origin outbox also rechecks its durable records after a restart. If a session reply is still held, has definitively failed, or has an unknown outcome, Instar puts a plain explanation in the conversation and the Attention hub. The explanation does not claim that an uncertain message was lost or delivered. It asks the person to request a restatement, because resending blindly could produce a duplicate. When a reply arrives at least five minutes late, Instar says that an earlier reply may be out of order.

The original reply text and retry identity are unchanged. A notice is keyed to the original operation, so repeated recovery checks do not keep posting the same notice. The existing retry limits and six hour deadline still apply. These notices may themselves be delayed if Telegram is unavailable, so the durable Attention item remains as a second place to see the problem. Reverting this change restores the previous behavior without a data migration.
