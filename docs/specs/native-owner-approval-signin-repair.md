# Native owner approval for automatic sign-in repair

Status: dark server and app contract. The first action is the standing automatic sign-in repair policy. Existing dashboard PIN confirmation remains available as a backup. Promote, Chief of Staff project binding, and paired-agent coordination follow with separate action identifiers and exact validation, using the same confirmation carrier.

## Authority and eligible keys

Only the current owner may approve through an active paired installation authenticated by the existing signed mobile request path. The approval uses the dedicated Secure Enclave biometric-current-set key from first-phone enrollment. Generic presence keys and keys that accept a device passcode are ineligible. Initially the enrolled iPhone confirms with Face ID. The Mac can open the proposal and hand it to that paired iPhone. Direct Touch ID confirmation requires a separately enrolled Mac current-set key and affirmative installed-device evidence first. Keep biometric proof and PIN proof distinct in the audit.

Use the existing device transport signature for every request to the exact paired origin. The server resolves key and ownership from trusted current state. Independent eligibility evidence is required for the installed app and key. An app assertion about the local biometric result cannot replace that evidence. Revocation, key replacement or an authority change invalidates an open challenge.

## Wire contract

Expose the following only through the authenticated paired-app routes. The paths are proposed and presently unmounted. Mobile requests use the existing device signature with the exact method, path and body. For signed arrays use the exact compact JSON bytes emitted by ECMAScript `JSON.stringify`, encoded as UTF-8 without a byte order mark or newline. Slashes stay literal, and strings use JSON escaping. Clients may preserve the verified wire bytes if their encoder differs. Return sensitive responses with `Cache-Control: no-store`; the lists carry no secrets or raw repair credentials.

- `GET /mobile/owner-approvals` returns `{ inventory, signerKeyId, signature }`. The compact UTF-8 JSON inventory array is `["instar.owner-approval.inventory.v1", origin, authorityId, ownerRevision, deviceId, expiresAtMs, [[requestId, proposalHash], …]]` with bytewise ascending request IDs. The Ed25519 signature is unpadded base64url of a signature by the already-verified authority key over the array bytes. Expiry timestamps on this wire are canonical decimal strings of UTC epoch milliseconds.
- `GET /mobile/owner-approvals/:requestId` returns `{ disclosure, signerKeyId, signature }`. The compact UTF-8 JSON disclosure array is `["instar.owner-approval.disclosure.v1", origin, authorityId, ownerRevision, deviceId, requestId, "subscription-relogin.configure.v1", effect, expiresAtMs, [[machineId, machineLabel, expectedRevision, configDigest, [accountLabel, …]], …]]`. Lists are in server-issued order, with unique target machine IDs sorted bytewise. The authority signs the exact array as above. `proposalHash` is lowercase hex SHA-256 of the exact UTF-8 disclosure bytes. The effect and account labels shown to the owner are the signed values. A stale list cannot create authority.
- `POST /mobile/owner-approvals/:requestId/challenge` takes `{ proposalHash }` and returns `{ challenge, signerKeyId, signature }`. The signed challenge array is `["instar.owner-approval.confirm.biometric.v1", origin, authorityId, holderEpoch, holderIncarnation, ownerRevision, deviceId, deviceKeyHash, biometricKeyHash, biometricKeyGeneration, requestId, actionId, proposalHash, challengeId, nonce, expiresAtMs, localAssurance]`. Use positive canonical decimal generations, UUID challenge IDs, a fresh unpadded base64url 32-byte nonce, and the shorter of the proposal expiry and the holder's challenge expiry. For iPhone the assurance literal is `face-id-current-set-v1`. The app compares the entire challenge to the signed disclosure, active device and key before prompting, then signs the exact challenge bytes. The fixture uses the first-phone dedicated key's canonical P-256 DER SPKI hash and strict low-S DER signature in unpadded base64url.
- `POST /mobile/owner-approvals/:requestId/approve` accepts `{ proposalHash, challengeId, localAssurance, signature }`. The server reconstructs the challenge from its own state. It verifies the exact paired device and key, current owner and holder epochs, proposal, action and both expiries. The shared durable acceptance consumes the challenge and records the exact approval before dispatch. Exact retry recovers the same receipt and target results. A different challenge, signature, proposal or principal cannot reuse it. Unreachable authority or uncertain application stays pending.

## Same policy write as PIN

Start by extracting the existing `/subscription-relogin/configure-pool` target validation and mandate writer so both authority carriers call that service. For each target, use the existing normalized configuration, `expectedRevision`, and `subscriptionReloginConfigureDigest`. Keep the current target scope, action, digest and generation comparisons, suppression of unattended backup codes, existing peer delivery, per-machine results and restart behavior. Standing approval does not approve a manual repair episode, sign-in recovery credentials, or a different target list. Neither the mobile client nor the signer chooses the final writer inputs.

Add a distinct authenticated biometric provenance with the same action bounds. Update verification on recipient machines to accept only the new exact evidence profile before issuing biometric-approved mandates to those targets. The PIN author and unlock identifiers are for PIN only. An older recipient that cannot verify the biometric provenance remains unavailable for that target. Never label a biometric approval as a PIN unlock. No automatic retry broadens the selected targets or remints an ambiguous decision.
