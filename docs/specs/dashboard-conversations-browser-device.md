## 1. Problem

Operator request, topic 134088, 2026-11-07 19:06–19:07 PST: "chats should be accessible from the dashboard as well" (screenshot: Work > Sessions shows only a terminal pane), and "that is: the native instar conversation support, just like the iphone app. Again, this should be like telegram web app vs telegram phone app".

The conversations the Instar iPhone app shows (app-native conversations, Telegram topics, Slack conversations) are reachable only from a paired phone. The dashboard console shows sessions as terminal panes. The send, rename, delete and media routes accept only a paired device's signature (`docs/specs/mobile-native-conversations.md` §4.10), so the console's Bearer token cannot use them, and it must not: a message's `originVerified` mark means "a key the owner approved through a human channel signed exactly this text", and the Bearer token, which every process of the agent can read, cannot mean that.

## 2. Goals

- A **Conversations** page in the dashboard console with the same conversations the iPhone app lists (`GET /mobile/conversations?scope=pool`), newest first, each labelled App, Telegram or Slack.
- Open one and read its history as chat bubbles; send text; send and see photos and files; start a new app conversation; rename and delete an app conversation. Same server routes and data, a different client.
- Desktop: list on the left, the open conversation on the right. Phone width (390 px): the list or the conversation, with Back.
- Every message the browser sends carries the browser's own device signature and reads back `originVerified: verified`. No Bearer token or PIN session ever stands in for a device signature.
- A browser key is approved through the same human channel a phone would be on that agent, never by something weaker; no agent- or third-party-authored content (views, posted files) can use it; and a browser-signed message is distinguishable from a phone-signed one on every machine running this version, from authenticated data (the signed ledger activation row), because a browser key is weaker than a phone's Secure Enclave key (§4.1); an older machine shows it as "couldn't check", never as phone-signed (§4.3).
- Ships dark behind a dev-agent-gated switch (live on Echo, dark on the fleet).

Not part of this feature: unread counts (built separately on `echo/unread-messages`; this spec leaves the hook in §4.10), push notifications to a browser, recording voice notes in the browser.

## 3. What exists (instar main 7818e81aa, v1.3.1719)

- **Device keys and signed requests** (`src/core/MobileDeviceKeys.ts`, `docs/specs/mobile-device-keys.md`). A device is a P-256 key. Each request carries `X-Instar-Device`, `X-Instar-Device-Time` (ms, ±60 s, `DEVICE_TIME_WINDOW_MS`) and `X-Instar-Device-Sig`: strict low-S DER ECDSA-P256-SHA256, base64url, over `instar-device-v1\n<deviceId>\n<host>\n<METHOD>\n<pathWithQuery>\n<timeMs>\n<sha256hex(body)>`. A per-device in-memory replay set (3 min, ≤2,000) refuses a repeated canonical string.
- **The device authenticator** (`deviceAuthenticator`, `mobilePairingRoutes.ts` ~2109): the exact `DEVICE_ALLOWLIST`, per-device rate buckets (default 120 a minute `deviceRateOk` ~598; media reads 120; upload chunks 240; sends unmetered with native on), the person check, and, with multi-route on (`svc.ownNames`, dev-gated), a Host that must be a proven own name arriving over local TLS (a TLS socket or a loopback peer; cloudflared and `tailscale serve` connect from loopback). With multi-route off, the signature is checked against the stored host only. A notification-token branch returns before the allowlist.
- **Device registry and key ledger.** `.instar/state/mobile-devices.json` (machine-local, re-read and rewritten on every call, unknown fields preserved) holds device records; pending → `approvePending`/`applyConfirm` → active. `mobile-device-key-ledger.jsonl` (replicated, append-only, machine-signed) holds activations (`approvedVia`: `telegram-dm | dashboard-pin | owner-phone | owner-agent`) and revocations; ledger row first, registry second; boot reconciliation repairs either side. Revocation of a record on another machine is attempted once per peer (`forwardRevoke`, ~1838; there is no outbox, despite `mobile-device-keys.md` §126 saying so), and a ledger revocation row alone already makes every machine's authenticator refuse that key (`isRevoked`, ~2173) once the row replicates. `verifyRecordedOrigin` judges stored messages against the ledger.
- **Who may approve a key** (`docs/specs/mobile-pairing-approve.md` §3.3, `approvalPath()` ~343): with a Telegram owner, only the owner's private Telegram chat (a code, or the Approve tap on that private message) or an owner phone's Face ID; "the PIN never approves a phone on an agent with a Telegram owner". Without a Telegram owner, a PIN-unlocked dashboard session approves (`dashboard-pin`). Introducer agents may approve phones (`owner-agent`). The parent spec (§4.4) states the boundary: neither path holds against a process running as the agent's OS user, which can read the PIN in config.
- **Conversation routes** (`mobileConversationRoutes.ts`, `mobileSlackRoutes.ts`, `mobilePairingRoutes.ts` `POST /mobile/chat/:topicId`, `routes.ts` `GET /telegram/topics/:id/messages`, `mobileMediaRoutes.ts`): list, create, rename, delete, send, browse, sync (`events`: app only, this machine only, answers at once; 404 when not stored here), Slack and Telegram read/send (Telegram send needs the serving machine), chunked media upload (`appMediaTypes.ts`: 1 MiB chunks, ≤50 MiB a file, ≤10 files and ≤64 MiB a message), device-signed media download (`202 {state:'fetching', retryAfterMs}` while copying from a peer). Writes idempotent by `requestId` (`<13-digit ms>-<uuid v4>`, remembered 24 h).
- **Presence-key routes** assume a Secure Enclave key that signs only after Face ID; the server trusts the iOS app for that.
- **Pages on the agent's origin.** Besides the dashboard, the server serves HTML at `/view/:id` (agent-written markdown rendered with `marked`, not sanitised, no CSP, `src/publishing/PrivateViewer.ts`, `routes.ts` ~27836–28046; a view held on another machine is relayed by `proxyViewToHolder`, which copies only the content type), its PIN page (unlock by a script `fetch` that sends no Bearer header, while `authMiddleware` exempts only `GET /view/*` with a valid `?sig=` — so the unlock answers 401 through the real middleware today), first-party templates (secret drop, MCP approve ~15976–16018, others), and `/dashboard/preview/` (`dashboardPreview.ts`): agent-published work-in-progress console pages served by `express.static`, on purpose with the operator's own token. IndexedDB, `BroadcastChannel` and `localStorage` are shared by every page of one origin, whatever the path; `sessionStorage` is per origin and per tab.
- **Attention items**: `raiseLockedSecurityItem` (`AgentServer.ts` ~582) is the pattern for a security notice that reaches the owner with or without Telegram (Telegram attention item, else `LocalAttentionItems` plus a push to owner phones). Attention items carry no action buttons.
- **The console** (`dashboard/console/`): static ES modules; `route()` rebuilds the shell on every `hashchange` and re-runs the whole (async) page function every 30 s unless `refreshHeld`; it clears only its own timer on navigation (Home has its own ad-hoc `homeRun` teardown); pure `*-model.js` view models; `ui.js` helpers; probe tiles; the two-pane Sessions layout. CSP blocks `blob:` images. No IndexedDB or WebCrypto yet.
- **Parallel work.** The conversation-graph project (branch `feat/conversations-ui-1105`, not on main) plans `#/work/conversations` and `dashboard/console/conversations*.js`; this spec uses other names (§4.13).

## 4. Design

### 4.1 The browser device record

A browser is a device like a phone, with differences in setup (§4.2), allowed routes (§4.4) and key storage.

- **Key in the browser.** WebCrypto P-256 ECDSA, `extractable: false`, kept with `{deviceId, machineId, host, keyHash, enrollmentId, status}` in IndexedDB (database `instar-console`, store `device`), **one record per machine** of the agent, keyed by the `machineId` the server reports. A secure context is required (https, or `http://localhost` / `127.0.0.1`); elsewhere the page names the agent's secure address.
- **What protects the key, and what does not.** `extractable: false` is an API restriction: page script cannot export the key, so it cannot be copied out through the page. It is not hardware confinement, and it does not stop script running on the same origin from asking the browser to sign while a page is open. Two kinds of same-origin script exist:
  - *Authored content* (agent-written views, files people post): §4.12 moves it off the origin (sandboxed), and §4.8 never opens a posted file as a page. It cannot use the key.
  - *Code the agent's own server serves* (the installed console files, the `/dashboard/preview/` pages): a process running as the agent's OS user can change these, and while the operator has such a page open it can make the browser sign. That is inside the same OS-user boundary §4.3 states, and it cannot be removed while the console and the key share an origin. `browser-device.js` refuses to load the key outside `/dashboard/console/` (a guard against casual reuse, not a boundary).
  So a browser key is weaker than a phone's Secure Enclave key, whose signing code the agent cannot change. Consequences: approval needs the agent's human channel (§4.2); a browser may call only the conversation routes (§4.4); every activation is announced (§4.2 step 10); and the key's ledger activation row carries `client: 'browser'` (signed by the activating machine), so every message a browser signs is shown as browser-signed (§4.3).
- **Record.** New fields: `client: 'browser'` (absent means a phone), `browserPublicKey` (the key; `publicKey` is never set on a browser record), `fingerprint`, `enrollmentId`, `setupState` (`notifying` while the approval message is being sent, then `awaiting`), `notifyingSince`, `activating?` (the activation intent, §4.2 step 10), `replaces?` (`{deviceId, keyHash}` of the record it retires), `effects` (the activation effects still to complete: `revokeReplaced`, `notice`, each with `attempts` and `nextAt`), `lastSeenAt`. Person: the owner. `deviceName`: the operator's choice, default "Browser on <platform> (<localhost | tunnel | Tailscale>)", `cleanText`, 60 characters.
- **`lastSeenAt`.** `DeviceRegistry.touch(id, at)` writes it, at most once a minute per device, from the authenticator after an accepted signature (the authenticator already reads the registry file on every request). `touch` re-reads and rewrites the file in one synchronous step like every other registry change, decides "once a minute" from the `lastSeenAt` it just read, and never refuses or delays the request: a failed write is reported through `featureEvidence.recordAtMostEvery` (once an hour). Shown as "last used on this machine"; "not used yet" when unset.
- **Fail closed on downgrade.** An older instar version reads only `publicKey`, so it cannot authenticate a browser record (lookup answers unknown-device; reconciliation skips it).
- **Every reader of a device key, decided.** One helper, `deviceKeyOf(d)` (`d.publicKey`, or `d.browserPublicKey` when `d.client === 'browser'`):

| Reader | Browser record |
|---|---|
| Authenticator lookup and `admittedIdentity` key hash (~2169–2176) | `deviceKeyOf` |
| Duplicate-key checks (`createPending`, new `createPendingBrowser`; across `publicKey`, `browserPublicKey`, `presenceKey` and the ledger) | `deviceKeyOf` + all three fields |
| Fingerprint (`publicDeviceView`, `waitingFields`, approval DM, `GET /mobile/pairing-requests`) | `fingerprint` set at creation from `deviceKeyOf` |
| `waitingPhones()` (~698) and everything built on it: `approveOutcome`, `contestOthers`, the one-waiting rule, `GET /mobile/pairing-requests` | `deviceKeyOf` — pending browsers whose `setupState` is `awaiting` are waiting devices (a `notifying` one is not); they count in the one-waiting rule, so a browser and a phone waiting at once both fall back to the code (the safer behaviour) |
| `noteLinkTaken` / taken codes (~664–672) | not reached (browsers redeem no link) |
| Ledger `recordActivation` row body, `validateLedgerRow`, `mergeLedgerRows`, and the replicated store's field list (`KNOWN`, `MobileDeviceKeyLedgerReplicatedStore.ts` 25) with `ledgerRowFromReplicatedData` | `recordActivation` reads `client` from the device record itself (so boot reconciliation's backfill of a browser's missing row also carries it); a browser activation row carries `client: 'browser'` inside the signed payload; `validateLedgerRow` returns null for a row whose `client` is present and not `'browser'`, and keeps it when it is; `client` is added to the replicated envelope's known fields so it survives replication between machines on this version; the merged view exposes it as `client` |
| Ledger `recordActivation`, `recordRevocation`, reconciliation (`MobileDeviceKeyLedger.ts` 226, 234, 264, 287) | `deviceKeyOf` |
| Signed-origin record builder `buildSignedOrigin` (`mobileConversationRoutes.ts` ~951) | `deviceKeyOf` — browser sends store a full origin |
| Owner-device admission for pool Slack reads and remote media (`mobileOwnerDeviceAdmission.ts` 32) | `deviceKeyOf`, and `isCurrent()` also requires the browser switch on for a browser |
| `activeOwnerPhone` (`mobileConsoleTicket.ts` 223, 277) | fails closed on purpose (reads `publicKey`; also refuses `client: 'browser'`) |
| Team routes (`teamRoutes.ts` 185) | fails closed on purpose |
| Introducer approval (`mobilePairingIntroducer.ts` ~312, `owner-agent`) | refuses a browser: a browser needs a human channel |

A ratchet test lists these call sites and fails when a new direct `.publicKey` read of a `DeviceRecord` appears outside `deviceKeyOf` and the two deliberate fail-closed sites.

**Registry methods** added to `DeviceRegistry`: `createPendingBrowser`, `setSetupState(id, state, onlyIf)`, `setActivating(id, intent)` (writes only to a record that is still `pending`, is not declined, carries no `activating` yet, and is `awaiting` — or, on the dashboard path, is the record this same request created; otherwise it writes nothing and returns false, and the activation stops with `409 not-pending`), `activateBrowser(id, effects)` (sets `active` from a record that carries `activating` — pending, or expired — which happens only when a version without these rules ran in between (a downgrade and re-upgrade), since this version's expiry skips records with `activating` — never declined — clears `activating` and `setupState`, and writes `effects`, in one write), `setEffects(id, effects)`, `touch(id, at)`, and `removeIfStillSettingUp(id)` (removes only a record that is still `pending`, still `notifying` and has no `activating`; it also drops the record's issued code and decline nonces). Every read-modify-write re-reads the file in one synchronous step, as today. Expiry and pruning never touch a browser record that carries `activating` or non-empty `effects`: `expireAllPending` (boot and lease loss) and the `normalize` TTL expiry skip records with `activating`, and the 200-tombstone pruning of revoked records skips records with `effects`. **Decline never races an approval:** `decline(id)` and the three-wrong-codes rule change only a pending record with no `activating`; a record that already carries `activating` has been approved, so the Decline tap and the owner phone's id-based decline (`mobilePairingApproval.ts`) answer "already approved — remove it in People > Phones if this wasn't you" (never `declined: true`), and a wrong code is refused without declining it. A record with `activating` is no longer a waiting device (`GET /mobile/pairing-requests`, the Approve tap, the one-waiting rule), so it cannot be approved twice. In one process this race can only arise across a crash between step 10.1 and 10.3 (decline nonces and codes do not survive a restart); the tests simulate that window. Because each of these is one synchronous read-modify-write of the registry file, whichever of approval and decline writes first wins, and the other sees its result.

### 4.2 Setting up a browser

The browser asks to be set up; the owner approves it through the agent's own approval path, as for a phone.

New Bearer route `POST /mobile/browser-devices`, body `{ publicKey, deviceName?, enrollmentId, timeMs, proof, replaces?: { deviceId, sig } }`, header `X-Instar-Operator-Session`. In order:

1. `503 browser-devices-off` unless `mobilePairing.browser.enabled`, `svc.enabled()` and `mobilePairing.native.enabled`. `429 pairing-paused` while `pairingPaused()`.
2. **Bound host**, computed before anything else and without the session: either (a) the Host is a proven own name (`svc.ownNames.accepts`) arriving over local TLS — or, with multi-route off, the configured pairing origin host — host = that name; or (b) the peer is loopback, the Host is exactly `localhost:<port>` or `127.0.0.1:<port>` (this server's port), and the request carries no header whose name starts with `x-forwarded-`, `forwarded`, `cf-`, `cdn-loop`, `tailscale-`, `x-real-ip` or `true-client-ip` — host = that exact string. Else `403 not-secure-address`.
3. `publicKey` parses as a P-256 point; `enrollmentId` has the `requestId` format; `proof` is a strict low-S DER signature by `publicKey` over `instar-browser-enroll-v1\n<host>\n<publicKey>\n<enrollmentId>\n<timeMs>`, `|now − timeMs| ≤ 60 s` (the device time window; the client signs with its corrected clock, §4.6). Else `400 browser-proof-invalid`.
4. **A retry of the same setup is answered here**, before anything is charged: a browser record on this host with the same key and `enrollmentId` → its current state (`202 {state: 'notifying'}` while the approval message is still being sent — a record `notifying` for more than 30 s (three times the helper's 10 s delivery limit, so only a crash or an exception during sending leaves one behind) is removed with `removeIfStillSettingUp` and answered `409 approval-unavailable`, and the boot pass and `leaseTick` remove such records too; else `200 {deviceId, machineId, host, status, approval, fingerprint, expiresAt}`), and nothing else happens. The same key with another `enrollmentId`, another key with this `enrollmentId`, or the key anywhere else in the registry or the ledger → `409 duplicate-key`.
5. **Operator session.** `403 operator-session-required` unless the principal is the Bearer token and `verifyDashboardOperatorSession` accepts the header, and the session has not already created a record.
6. **Limits.** Browser records pending or active on this machine, not counting the record a valid `replaces` names, must be below `mobilePairing.browser.maxBrowsers` (default 10), else `429 too-many-browsers` listing this machine's browsers by "last used". Setups are limited to `mobilePairing.browser.maxSetupsPerHour` (default 6) per machine, else `429 too-many-setups` saying when the next one is allowed. The count is of setup records created in step 8 within the last hour, kept as a list of `{deviceId, at}` entries in the registry file (entries older than an hour dropped on write). Steps 4 to 8 — the retry check, the operator-session check, these limits, `replaces` and the record write that also marks the session used — run in one synchronous step with no `await` between them (the operator-session check and the ledger reads are synchronous), so two concurrent setups can neither both pass the last free slot nor both use one PIN entry. Every removal by `removeIfStillSettingUp` — not delivered, no lease, no approval path, or stuck in `notifying` (including at start-up) — drops that record's entry in the same write and so gives its slot back. Retries and refusals before step 8 do not count. Pending browsers do not count toward the phones' `MAX_PENDING`.
7. **`replaces`** (optional): `sig` is a signature by the replaced record's key over `instar-browser-replace-v1\n<old deviceId>\n<new publicKey>\n<host>\n<new enrollmentId>`, checked against the public key in the ledger's activation row for that device (any machine). Refused (`400 replaces-invalid`) when the signature fails, the old key already has a ledger revocation row, or another pending record on this machine already names it.
8. **Create pending** (`createPendingBrowser`: `status: pending`, `setupState: 'notifying'`, `client`, `browserPublicKey`, `fingerprint`, `host`, `deviceName`, `enrollmentId`, `replaces`, owner person, the phone's pending expiry) and mark the operator session used.
9. **Approval**, by `svc.approvalPath()`:
   - `telegram`: this machine must hold the serving lease, else the record is removed (`removeIfStillSettingUp`) and `409 approval-unavailable` ("Set up this browser from the machine serving Telegram"). The owner gets the existing private message (moved into a shared helper used by redeem and this route), worded for a browser: "A browser is asking to use your conversations with <agent>. Approve only if you are setting up a browser right now and this key matches the one it shows. Browser key: <fingerprint>. Browser name: <name> (the browser chose this name). If you did not start this, tap Decline." plus the code line. Delivered → `setupState: 'awaiting'`. Not delivered within the helper's 10 s → `removeIfStillSettingUp` and `409 approval-unavailable` with the existing detail (a retry with the same `enrollmentId` then starts over and needs the PIN). A record is a waiting device for approval (the Approve tap, `GET /mobile/pairing-requests`, the one-waiting rule) only once it is `awaiting`; while `notifying` nothing can approve it, so a removal can never delete an approved browser. With `mobilePairing.approve.enabled` on, the Approve tap and an owner phone's Face ID approve it (it appears in `GET /mobile/pairing-requests` labelled "Browser"); with it off, the code typed into the browser (`POST /mobile/device/confirm`) is the only path. Recorded `telegram-dm` (tap or code) or `owner-phone`. The owner's replies for a browser say "browser", not "phone" (§4.7).
   - `dashboard` (no Telegram owner): the live operator session approves in this request. It does not go through `approvePending` (whose approve switch and one-waiting rule belong to the code-free paths); like `/mobile/device/confirm` it writes the ledger activation row and then `applyConfirm`, with `approvedVia: dashboard-pin` on both.
   - `null`: the record is removed (`removeIfStillSettingUp`) and `409 approval-unavailable`.
10. **On activation, wherever it happens** (`approveOutcome`, `/mobile/device/confirm`, or this route), for a browser record, in this order, each a durable write before the next:
    1. the activation intent: the pending record gets `activating: { approvedVia, at, effects: [revokeReplaced?, notice] }`;
    2. the ledger activation row (with `client: 'browser'`);
    3. the registry record `active` with `effects` copied from the intent, in the same `applyConfirm` write, and `activating` cleared;
    4. `revokeReplaced`: the activating machine writes the ledger revocation row for the replaced key itself (`recordRevocation` with the key from the ledger activation row). The row replicates through the ledger's replicated store; every machine's authenticator refuses a key with a revocation row, and the holding machine's boot reconciliation completes its registry. `forwardRevoke` is called once in addition, best-effort, only to make it take effect sooner;
    5. `notice`: `raiseBrowserActivated`, built like `raiseLockedSecurityItem`: id `mobile-pairing:browser:<deviceId>`, priority HIGH, category security, title "A browser can now send messages as you", body naming the browser, its key fingerprint, how it was approved and a link to People > Phones where it can be removed; a Telegram attention item when Telegram is configured, else the local attention list plus a push to owner phones. It is raised at once — Self-Heal Before Notify does not apply, because this is a security event for the owner, not an internal fault.
    Each effect is removed from `effects` when it completes (`recordRevocation` finding the row already present counts as complete). **Recovery** runs once when the key ledger is attached to the pairing service (in `AgentServer`, next to the existing ledger reconcile; the service constructor's `expireAllPending` has already run by then, and it skips records with `activating`), and then from the pairing service's existing 5 s `leaseTick` (placed before its lease-holder early return, and running whatever the browser switch says, since it only finishes recorded work) guarded by an in-memory "browser work pending" flag set by that start-up scan and by any write that leaves work behind, so a machine with none does no extra reads: a browser record with `activating` and a ledger activation row is completed through `activateBrowser` (steps 3–5), whatever its pending/expired status; one with `activating` and no ledger row has `activating` cleared and is marked `expired` (the approval never completed; the browser shows "not approved — set up again"); with no ledger attached at all (no signer, or native conversations off) recovery decides nothing, leaves `activating` in place and reports once through `DegradationReporter`; a browser record of any status with non-empty `effects` has them retried (a notice for a browser already revoked says it "was set up and has since been removed"). Retries back off from 30 s doubling to 1 h, one attempt in flight per effect; after 24 attempts one `DegradationReporter` report names the browser and the effect (and a lease move, when that is why a notice fails) and the effect stays, retried hourly and at every boot — an identity effect is never abandoned. At that point a failing `notice` is also raised once on the local attention list with one push to owner phones, and the effect records `fallbackRaisedAt` so later retries attempt only the Telegram item (the push's dedupe key in `raiseLockedSecurityItem` changes on every call, so it is never repeated by retry); and when more than 20 records carry effects, one further report says so. The dedupe id keeps a retried notice to one Telegram item; the fallback push is sent once.
    **Rows an older peer rejected.** A machine on an older version accepts a browser row's replication envelope (its store schema ignores the unknown `client` field) and its journal sync stores the entry exactly as received (`JournalSyncApplier` appends the raw entry); only its ledger ingest rejects it (`bad-signature`, §4.3). An upgrade restarts that machine, and its existing boot read of peer streams (`loadOriginRecords` → `ingestReplicated`, in `server.ts`) re-validates every stored row against the new store schema, which keeps `client`, so the row is then accepted — activation and revocation rows alike, whether the activating machine is still running, offline, or the browser has since been revoked. Nothing is re-published. This holds while the rows are within the replica files' retention (4 MB × 8 rotations, `CoherenceJournal.ts`), far more than the ledger's rows need.
11. Audit `featureEvidence('mobilePairing.browser')`: `fired` on created/activated/replaced, `held` on each refusal, `error` on a write or effect failure. Answer `201 {deviceId, machineId, host, status, approval, fingerprint, expiresAt?}`, `Cache-Control: no-store`.

Wrong confirmation codes for a browser count in the same 24-hour wrong-code budget as phones (one budget guards the one code channel), with browser wording in the decline and pause messages.

**Client side of setup.** Under a Web Lock `instar-browser-setup` the page re-reads IndexedDB; with no usable record for this machine it reads `GET /mobile/browser-devices/status` (for `machineId`, `serverTime`, `approvalPath`, limits), generates the key, writes `{keyPair, enrollmentId, machineId, status: 'enrolling'}` **before** sending, forgets any cached operator session, asks for the PIN, and sends. A lost response is recovered by sending the same request (step 4; no new PIN; a `202 notifying` answer is retried every 2 s for up to 30 s, then shown as "The approval message could not be sent" with Try again). The IndexedDB record's `machineId` is taken from the setup answer, not from the earlier status read. While pending, the page shows the fingerprint, where to approve, a code box, and a countdown to the `expiresAt` the server returned, reading `GET /mobile/device` every 5 s. A `declined` or `expired` status there (a successful answer, from the machine the setup was sent to) stops the polling, deletes the key and offers a new setup with the reason; `active` opens the list. Every tab loads the key from IndexedDB; none keeps a private copy.

### 4.3 What each approval proves

- `telegram-dm` / `owner-phone`: the person who can read the owner's private Telegram chat, or unlock an owner phone, approved this exact key fingerprint.
- `dashboard-pin` (only with no Telegram owner): someone unlocked the dashboard with the PIN. A process running as the agent's OS user can read the PIN and the Bearer token, so on such an agent it can create a browser key whose messages verify. That is the boundary phones already have there (parent spec §4.4). Such a process can also dismiss an attention item, so the activation notice is best-effort; the lasting record is the ledger activation row, the People > Phones row, and the "approved on dashboard" mark on every message from that key. On one machine such a process could rewrite those state files too; on a multi-machine agent the other machines keep their replicated ledger copies.
- **Browser or phone, from authenticated data.** A browser's ledger activation row carries `client: 'browser'` inside the activating machine's signed payload. History rows gain `originClient: 'browser'` when the verdict's ledger row says so, so the dashboard shows "signed from a browser" ("signed (this browser)" for its own key) and the session tag says 💻. Mixed versions: an older machine's `validateLedgerRow` drops the unknown field, so the signature it recomputes fails and it rejects that one row (logging a warning, no retry loop); messages from that browser key then read `unknown` ("couldn't check on this machine") there — never phone-signed. Phone rows are unchanged byte for byte. One limit: the iPhone app is not changed by this spec and shows its generic signed mark for a `verified` browser message; it receives `originClient` and can show it when the app is updated (fb-c5049bee-69a, a condition of fleet graduation). <!-- tracked: CMT-002 --> The verdict, `approvedVia` and `client` of a message come from one ledger view lookup per response (one helper replacing the separate `originApprovedVia` calls).

### 4.4 What a browser device may call

`DEVICE_ALLOWLIST` rules gain `browser?: true`. The authenticator, after the signature is verified and before the person check, refuses a `client: 'browser'` device on any rule without it (`403 browser-device-not-allowed`); closed by default. The notification-token branch refuses a browser. Named:

- `GET /mobile/device` (pending, active, declined, expired — the setup page learns a decline or expiry from it), `POST /mobile/device/confirm` (pending or active); `POST /mobile/devices/:id/revoke` with `:id` equal to the signing device (the route refuses a browser revoking any other device, `403 own-device-only`; owner phones keep their existing power).
- `GET /mobile/conversations`, `POST /mobile/conversations`, `PATCH|DELETE /mobile/conversations/:uuid`.
- `POST /mobile/chat/app/:uuid`, `GET /mobile/chat/app/:uuid/messages`, `GET /mobile/chat/app/:uuid/events`.
- `GET /telegram/topics`, `GET /topic/list`, `GET /telegram/topics/:id/messages`, `POST /mobile/chat/:topicId`.
- `GET /mobile/chat/slack/:id/messages`, `POST /mobile/chat/slack/:id`.
- `POST /mobile/media/uploads`, `PUT /mobile/media/uploads/:id/chunks/:i`, `GET /mobile/media/uploads/:id`, `GET /mobile/media/:sha256`.

Everything else is refused, including every presence-key, console-ticket, permission, desktop, dashboard-PIN, team, people, pairing-approval, introducer, session-control, push, attention and owner-summary route. Route-internal owner-phone checks are decided in §4.1's table. With the switch off, every browser-device request is refused `403 browser-devices-off`.

### 4.5 The loopback rule

A browser bound to an own name signs with that Host (existing rule). A browser bound to a loopback host is accepted only when the device is `client: 'browser'`, its stored host is a loopback host, the request's Host equals it exactly, the peer is loopback, and none of the forwarding-header prefixes of §4.2 step 2 are present — in both multi-route modes. A phone never matches. These prefixes are a denylist of what the HTTP modes of the fronts instar configures (cloudflared ingress, `tailscale serve` https) add; the live proof records the real header set of both fronts as a contract test. A front in raw TCP pass-through mode, an `ssh -R` tunnel or a local reverse proxy that rewrites Host and strips headers would look like loopback; those are machine-owner configuration, inside the OS-user boundary of §4.3. In every case the private key and its human approval are still required; the rule only scopes where a signature is valid.

### 4.6 Is this browser still set up? (never wipe a key on a guess)

The key cannot be exported, so deleting it is permanent. The page deletes it only on a definite answer.

- New Bearer route `GET /mobile/browser-devices/status[?keyHash=<hex>]`: `503` when off; else `{ enabled, machineId, nickname, serverTime, approvalPath, approveEnabled, telegramSend, limits: { maxFiles, maxMessageBytes, maxFileBytes, chunkBytes }, key? }` (limits from `appMediaTypes.ts`; `key` only when `keyHash` is given). `key` is `{ state, reason? }` with `state` one of: `active`, `pending`, `declined`, `expired` (this machine's registry); `revoked` (a ledger revocation row for that key hash — replicated, definite on any machine); `elsewhere` with `{ machineId, nickname }` (a ledger activation row written by another machine and no record here); `not-found` (no record here and no ledger row); `unknown` (the ledger could not be read). `reason` names a recent refusal of this key on this machine when one is known (`stale-time`, `host-refused`, `replay`, `rate-limited`).
- **Precedence** when the status route decides `key.state`: the ledger cannot be read → `unknown`; a ledger revocation row → `revoked`, whatever the registry says (the registry on the key's machine completes the revocation only at its next boot); otherwise this machine's registry state; otherwise `elsewhere` or `not-found`. `publicDeviceView` and the `maxBrowsers` count apply the same rule, so a ledger-revoked browser is shown and counted as revoked everywhere at once.
- Every signed call's `401` body names the answering machine (`machineId`). One status check is in flight per browser at a time (made by the poll leader); signed reads pause until it answers.
- On a `401` from a signed call, the page asks the status route, and deletes this machine's key (and the current tab's unfinished sends) only on:
  - `revoked` (from any machine), or
  - `declined`, `expired` or `not-found` **from the machine the key was set up on** (the status answer's `machineId` equals the IndexedDB record's).
  It then shows the setup card with the reason ("removed", "declined", "the approval window ran out — this can also happen when the agent restarts", "not approved").
- Any other answer keeps the key:
  - `elsewhere`, or `not-found`/`declined`/`expired` from another machine (ledger replication can lag a tunnel move): show "This browser was set up on <nickname>; this address is now served by <this machine>." with "Set up this browser here", which runs §4.2 with a new key and — only when the old key had become active — a `replaces` signed by the old key (a key that never got past pending has no ledger row to replace; its old machine expires the record itself); the old record is retired by the ledger revocation row of §4.2 step 10. A tunnel that moves back and forth costs one such setup each way.
  - `active`: a transient refusal — refresh the clock offset and retry, up to 5 times with backoff; then show "This browser's messages are being refused" with the `reason` in words (for `stale-time`: "your computer's clock is N minutes off") and Retry.
  - `unknown`: show "Couldn't check this browser right now" with Retry.
- **Clock.** The page keeps an offset from `serverTime` (and the `Date` header) and uses corrected time for signatures, the setup proof, the time inside each `requestId`, and the unfinished-send age. When the offset is more than 2 minutes, the page also says "your computer's clock is N minutes off" (signing still works).
- A 429, 503 or network error never touches the key.
- **Forget this browser** (page menu): self-revoke (signed); on failure, Bearer `POST /mobile/devices/:id/revoke`; the IndexedDB record is deleted only after a confirmed revoke.

### 4.8 The Conversations page

- **Route and files.** `#/work/chats`; `dashboard/console/chats.js` (view), `chats-model.js` (pure view models and the poll scheduler), `browser-device.js` (keys, signing, clock, setup). CSS `chat-`. A "Conversations" tab in the Work group (`GROUPS`, `NATIVE_PAGES`, `CONSOLE_ONLY_TABS`) and a probe tile that appears when the status route answers 200; with the switch off the page shows "Conversations in the dashboard are switched off on this agent." Phone-mode alias `chats`.
- **Lifecycle (a change to `console.js`, applied to every page).** `route()` passes each page `ctx.onDispose(fn)` and keeps a navigation token; before rendering another page (or re-running the same page on the 30 s cycle) it calls the registered disposers in try/catch (a throwing disposer is reported and does not stop navigation); a disposer registered after its page was left is called at once. A page may register `ctx.onQuery(fn)`: when only the query of the current path changes, `route()` calls it instead of rebuilding the shell. A page may be registered self-refreshing, so the 30 s cycle does not re-run it. Home (the `else` branch of `route()` in `console.js`, not an entry in `pages`) receives `ctx` too, and its `homeRun` teardown moves onto `onDispose`; its disposer closes over its own run object, and both its timer and `route()`'s `refreshTimer` are covered by the tests. A query-only change on a page that registered `onQuery` skips the sheet close, `newArrival()` and the scroll to top; on a page that did not, it rebuilds as today. Every existing page behaves as before (they register nothing); `tests/unit/console-dom.test.ts` and the Home tests stay green, and new tests cover a late disposer, a throwing disposer and a query-only change. The chats page registers all three: `?c=` changes swap its conversation controller; dispose stops timers, aborts reads, releases its Web Locks and revokes every `blob:` URL; it never repaints the open conversation, the composer, scrolled-back history or an upload in progress.
- **List.** Signed `GET /mobile/conversations?scope=pool`; rows with title, kind label, last activity, preview; "Show more" via `nextCursor`; "New conversation" asks for a title (1–80 characters). Machines that did not answer are named under the list (`pool.failed`).
- **Conversation.** Bubbles: operator right; agent left; Slack participants left with their name. Operator bubbles show delivery state (sending / delivered / not delivered with `deliveryDetail` / unknown — "check the conversation") and the origin mark for all five verdicts: `verified` "signed" (+ "approved on dashboard" when `originApprovedVia` is `dashboard-pin`; "this browser" for its own key), `redacted` "signed — an invite or desktop code was removed", `failed` "⚠ signature does not check out", `unknown` "couldn't check on this machine", `none` nothing. All server and third-party text is rendered as text nodes only. No signed write (send, create, rename, delete, setup, forget) is ever started from URL or hash parameters; each needs an action in the page. "Earlier messages" pages backwards with `?scope=pool`.
- **One poller per browser.** Each visible tab announces its one open conversation (or none) over a `BroadcastChannel` and re-announces every 10 s; the leader drops an announcement older than 25 s and accepts at most 8 conversations in the union; the focused tab's conversation always gets a slot (displacing the least recently focused one); a tab whose conversation has no slot shows "Live updates paused here — this conversation refreshes when you click into this window". 8 is a fixed client default. A new leader broadcasts "which conversations are open?" and carries on the backoff state, which the leader broadcasts with each result. A hidden tab withdraws its announcement and aborts its queued lock request. The tab holding the Web Lock `instar-chat-poll` — requested only by visible tabs and released when the tab is hidden or closed, so another visible tab takes over — refreshes the list every 30 s and polls the union of announced conversations, broadcasting results; other tabs only render. The scheduler in `chats-model.js` counts every signed read the page makes (list, pool reads, polls) and spends at most `pollBudget` of them a minute (default 60: a default under the server's 120 per device, shared by every tab, leaving the rest for reads the operator causes), at default intervals: app `events` every 4 s; Telegram and Slack newest page every 5 s on this machine only, with a `?scope=pool` read on open, on "Earlier messages" and every 30 s; an app conversation whose `events` answers 404 (not stored here yet) uses a `?scope=pool` newest-page read every 15 s until `events` answers. With several conversations open the intervals stretch to stay inside the budget. Reads never overlap. A 429 doubles the interval (honouring `Retry-After`) up to 30 s; a success halves it back. Nothing polls while no tab is visible.
- **Composer.** Multi-line; Enter sends, Shift+Enter newline; Send disabled while empty. On a Telegram topic when sending is not available here (`telegramSend: false` or `409 not-serving`), the composer says "Sending to Telegram works from the machine serving Telegram" and is read-only. Each message gets a `requestId` when first sent; unfinished sends (`requestId`, text, upload ids, first-sent time, and the `deviceId` and `machineId` that signed it) are kept in that tab's `sessionStorage` until final, and are retried only under that same device; once the key in use differs (a new setup, a tunnel move), they are shown as "unknown — check the conversation" and never re-sent, because the server deduplicates on `(deviceId, requestId)` (a send in flight when its tab closes is not recovered by another tab; the conversation shows whether it arrived). Final: a delivery state, `404` (conversation gone), `403`, `409` (shown as "check the conversation"). Unfinished sends whose `requestId` time is more than 23 hours old (server-corrected) are shown as "unknown — check the conversation", never re-sent (the server forgets `requestId`s after 24 hours). They are cleared when this machine's key is deleted. While a send or upload is in flight the composer carries `data-interaction-open`. **Credential-shaped text** gets the same choice as on the phone (mobile-native-conversations.md §4.2): before sending, the page runs the same check locally and on a match asks "This looks like a password or key. If you send it, it is saved in this conversation's history on every machine of this agent, in plain text. Send it through a Secret Drop link instead, or send as written?" The operator decides; the check never blocks a send. The check is `dashboard/console/credential-shape.js`, a browser copy of `detectOutboundCredential`'s patterns, kept equal by a parity test that runs both on one fixture set. The copy keeps three behaviours exactly: it checks only `HARD_WALL_CREDENTIAL_KINDS`, it scans both the raw text and the text with `INVISIBLE_INTERLEAVE` characters removed, and text over `MAX_SCAN_BYTES` counts as a match; the fixtures include invisible-character, oversize and excluded-kind (`jwt`, `bearer-token`, `labeled-secret`) cases.
- **Attachments.** A file picker with the limits from the status answer. Upload one file at a time, chunks one at a time, a 429 retries the same chunk after the interval, a progress bar; then the send.
- **Media display.** Signed `GET /mobile/media/:sha256?ref=<conversation key>`, cached by `sha256` for the open conversation, at most 3 in flight; a 429 re-queues with its placeholder. Images load when scrolled into view; video, audio and files on click. A `202 fetching` is retried after `retryAfterMs` for up to 60 s, then "Still copying from another machine — Retry". **Only these types become a viewable `blob:`**, created with the type from this list: `image/jpeg`, `image/png`, `image/gif`, `image/webp`, `video/mp4`, `video/quicktime`, `audio/mp4`, `audio/mpeg`, `audio/ogg`, `audio/wav`. Everything else (SVG, HTML, XML, PDF, HEIC, unknown) becomes an `application/octet-stream` blob behind a `download` link. Blob URLs are revoked on dispose and on conversation change.
- **Rename and delete** (app conversations): from the header menu; delete asks to confirm.
- **Layout.** At ≥900 px a two-pane grid like Sessions (list `minmax(300px,420px)`, conversation `1fr`), composer at the foot. Below 900 px: the list, or the conversation with Back; the open conversation is in the hash (`#/work/chats?c=<kind>:<id>`).

### 4.12 Pages that render authored content leave the origin

Every response under `/view/` — the PIN page, the unlocked view, the `?sig=` tunnel link, and a view relayed from the machine that holds it — gets `Content-Security-Policy: sandbox allow-popups allow-popups-to-escape-sandbox allow-downloads` (no `allow-same-origin`, no `allow-scripts`, no `allow-forms`). It is set by a path middleware on the machine that answers the browser, matching the lowercased path, so a relayed view is sandboxed whatever the holder (of any version) sent. A sandboxed page runs in an opaque origin with no script and no access to the console's IndexedDB, `BroadcastChannel`, `localStorage` or `sessionStorage`. `marked` passes raw HTML through, so an agent-written view can contain `<script>`; under this policy it does not run. Rendered views need no script, so they look and work the same. The PIN page, rendered under the sandbox, shows no form, only: "This view is protected by a PIN. Unlocking protected views isn't available at this address right now."

The PIN unlock is not changed by this spec. Through the real auth middleware it answers 401 today (the PIN page's script `fetch` sends no Bearer header, and `authMiddleware` exempts only `GET /view/*` with a valid `?sig=`); under the sandbox the PIN page shows the plain notice above instead of a form that cannot work. Repairing the unlock needs its own design (a durable, escalating per-view lockout, relaying the PIN to the holder machine, a Bearer exemption) and is in the feedback queue as fb-fa94058c-e42. <!-- tracked: CMT-003 -->

A ratchet test enumerates every way `src/server` can send HTML — `setHeader('Content-Type', 'text/html…')`, `.type('html')`, every `res.send(` of a string, every `sendFile`, and every `express.static` mount — and requires each to be classified: **sandboxed** (renders agent- or third-party-authored markup: `/view/*`), **first-party template** (instar code, every interpolated value escaped: MCP approve, secret drop, the 503 page, `/dashboard/pair`, `/dashboard/desktop.*`), **first-party console** (`/dashboard/console/`, the legacy dashboard, whose agent and third-party text goes through escaping or DOMPurify), or **agent-served code** (`/dashboard/preview/`, inside the OS-user boundary of §4.1). A new site fails the test until it is classified, and the test also requests an upper-case `/VIEW/` path to check the sandbox still applies.

This part ships without the browser switch, as a security correction under "User-Facing Fixes Ship Live": it closes an exposure that exists today (an agent-written view can read the console's Bearer token from `localStorage`), and it has no per-agent off-switch because turning it off would only reopen that exposure; rolling back means an older version.

## 5. Multi-machine posture

- **Browser device records:** machine-local, like phones. machine-local-justification: physical-credential-locality — the private key lives in one browser's IndexedDB for one origin, and a device record binds that key to the one machine serving that hostname: the signature covers the host and only the machine serving it accepts the device (the posture `docs/specs/mobile-device-keys.md` line 111 already gives phones, approved and shipped in commit 1776c2ed3: "tunnel move means re-pair"; prohibited-by=the pairing spec's one-machine-per-hostname rule, TEMPORARY until multi-host serving is designed). When the tunnel name moves to another machine, that machine answers `elsewhere`; the browser keeps its old key (IndexedDB holds one record per machine) and is set up again there with a new key whose `replaces` retires the old record through a ledger revocation row the new machine writes (§4.2 step 10), which replicates to the old machine. People > Phones lists every machine's browsers (`?scope=pool`). On an agent with a Telegram owner, a browser can be set up only on the machine serving Telegram (the code travels through it); a dashboard opened on another machine says so.
- **Browser key activations and revocations:** replicated through the device-key ledger, so a browser's messages verify on every machine and a revocation is definite everywhere.
- **Conversations shown:** proxied-on-read through the existing `?scope=pool` reads; sends follow existing pool ownership and forwarding; Telegram sends need the serving machine, as for phones.
- **Activation notice:** raised once, by the machine where the activation happened.
- **`/view` sandboxing:** a response header set by whichever machine answers the browser, including relayed views; no state.

## Frontloaded Decisions

- The browser is its own signed device (the brief's recommendation), not a Bearer or PIN session sending on a phone's behalf; the smaller alternative (Bearer reads, no sending) was rejected because sending is the feature and a Bearer-signed send would make `originVerified` meaningless.
- Approval follows the agent's existing approval path unchanged: with a Telegram owner, the owner's private Telegram chat (Approve tap or code) or an owner phone's Face ID; without one, the live PIN session. The PIN never approves a browser on an agent with a Telegram owner. Introducer agents never approve a browser.
- The PIN is asked for at every setup; an operator session creates at most one record; a retry of the same setup costs nothing.
- `approvedVia` keeps its values and meaning; the browser kind is `client` on the machine-local record and, signed, on the replicated ledger activation row.
- A browser record stores its key as `browserPublicKey`; readers are assigned in §4.1's table and enforced by a ratchet test.
- Browser devices may call only the routes in §4.4 and may revoke only themselves.
- Pending browsers whose approval message was delivered (`awaiting`) are waiting devices for approval purposes (they count in the one-waiting rule); all pending browsers are excluded from the phones' `MAX_PENDING` and share the wrong-code budget. A browser record carrying an activation intent or unfinished effects is never expired or pruned.
- A loopback-bound browser is supported (§4.5) in both multi-route modes.
- The key is deleted only on a definite answer (§4.6); IndexedDB holds one key per machine.
- Every browser activation raises one owner notice through `raiseBrowserActivated` (Telegram attention item or local attention list plus push), linking to People > Phones; no attention action buttons are added.
- `/view` pages are sandboxed out of the origin in this change (§4.12), independent of the switch.
- Changes to `console.js` routing: `ctx.onDispose`, `ctx.onQuery`, self-refreshing registration; Home's teardown moves onto `onDispose`.
- Before setup the page shows only the setup card; it reads no conversations with the Bearer token.
- Names: `#/work/chats`, `chats*.js`, `browser-device.js`, `chat-` CSS, nav label "Conversations".
- New switch `mobilePairing.browser.enabled` (dev-agent gated, `resolveDevAgentGate`, read live), `mobilePairing.browser.maxBrowsers` (default 10) and `mobilePairing.browser.maxSetupsPerHour` (default 6).
- Live proof: the live-test harness with demo channels from `vault://demo/*` (§7). Owner-phone approval of a browser is driven live with a software presence key on a harness owner phone (as `tests/e2e/mobile-pairing-approve-alive.test.ts` does); the iPhone's own Face ID prompt is unchanged app behaviour outside this feature's surfaces.
- The `/view` sandbox ships live under "User-Facing Fixes Ship Live" (§4.12); the PIN unlock is not changed here (fb-fa94058c-e42). <!-- tracked: CMT-003 -->
- The replaced browser is retired by a ledger revocation row written by the activating machine; `forwardRevoke` is only an extra.

## Configuration, rollout and rollback

- `mobilePairing.browser.enabled`: omitted means live on a development agent and dark on the fleet; requires `mobilePairing.native.enabled`. Declared in `src/core/devGatedFeatures.ts` (name `mobilePairingBrowser`, justification "a new signing client identity; proven live on the development agent before any fleet exposure"), `src/data/feature-ladders.json` (id `mobilePairing.browser`, risk `sensitive`, flag path `mobilePairing.browser`, metrics matching the `featureEvidence('mobilePairing.browser')` kinds), `src/core/types.ts`, `src/server/CapabilityIndex.ts`, the post-update awareness text, an `upgrades/next/dashboard-conversations.md` fragment with the user-facing sections, and the side-effects artifact.
- Off: the setup and status routes answer 503, browser-device requests are refused 403, the tile is hidden and the page shows the off text. Phones are unaffected. The `/view` sandbox and the `console.js` lifecycle hooks are always on (they change no behaviour a user relies on: the PIN page's unlock already answers 401 through the real middleware, and under the sandbox the page shows a plain notice that unlocking is not available at this address instead).
- **Rollback:** switch it off. Records and ledger rows stay, so messages already sent keep verifying. Revoking a browser works with the switch on or off. Rolling back to an older version: browser records cannot authenticate (§4.1); a machine that ran this version and is rolled back keeps the browser activation rows it already stored (its ledger view reads local rows without re-checking signatures), so there it shows browser messages as plain `verified` with no browser mark — a limit of rolling back, not of a mixed pool; a revoke done there writes no ledger row for the browser key, and on upgrade reconciliation (via `deviceKeyOf`) adds it from the registry. The older version's `/view` has no sandbox again (today's state).
