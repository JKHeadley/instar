# Native session screen for the Instar iPhone app

## Problem statement

Operator request (Justin, Telegram topic 134088, 2026-11-03 22:01 and 22:55 PST): the chat's session button should open a NATIVE session screen in the app, not the legacy dashboard in Safari, and the app should cover features natively. Plan of record: `.instar/lanes/app-native-coverage-plan.md` §3 and build-order rows 1-2.

Today (verified on origin/main 7df9eeea6):

- A paired phone signs each request with its Secure Enclave device key. `deviceAuthenticator` (`src/server/mobilePairingRoutes.ts`) admits a device-signed request only when it matches `DEVICE_ALLOWLIST`. `GET /sessions` is on it; `GET /sessions/:name/output?lines=N` and `POST /sessions/:name/input {text}` (`src/server/routes.ts`) are not, so a phone gets 403 `device-not-allowed`.
- The chat's session button calls `GET /mobile/conversations/session?ref=…` and opens the returned `dashboardUrl` in Safari, where the dashboard asks for its PIN. The PIN-unlocked dashboard can already read every local session's output and type into it.

## Proposed design

### Server

1. **Two allowlist entries** in `DEVICE_ALLOWLIST`:
   - `GET /sessions/<name>/output` — `statuses: active`, `body: 'none'`, `ownerOnly: true`, own bucket `session-output` at 90 requests/minute (a 1.5 s poll is 40/minute; this keeps polling from eating the shared 120/minute read allowance the chat list needs).
   - `POST /sessions/<name>/input` — `statuses: active`, `body: 'json'`, `ownerOnly: true`, own bucket `session-input` at 12 requests/minute (human typing; `sendInput` → `rawInject` → `performTmuxInjectionEffect` runs synchronous tmux calls plus a 0.5 s, or 1.5 s for Codex, post-paste pause on multi-line text, as the dashboard's input route does, so the bucket also caps how long one phone can hold the event loop). On top of the per-phone bucket the router keeps ONE machine-wide window: at most 12 device inputs a minute across all phones (sends never overlap because `sendInput` is synchronous; a refused or failed send still uses its slot and its replay digest, which is safe because nothing was typed twice and the phone signs a retry afresh), so the worst-case event-loop hold from phone typing is about 18 s a minute however many owner phones exist. The dashboard's WebSocket `input` frame calls the same synchronous `sendInput` with no limit at all, so this path is strictly more bounded than the one it mirrors; making the tmux injection itself asynchronous changes every injection caller (Telegram, Slack, dashboard, jobs) and is filed as instar feedback, not done here.
   - A rule with its own bucket is counted ONLY in that bucket, not in the shared 120/minute read allowance (the existing `ownBucket` behaviour in `deviceAuthenticator`), so the two counts are independent.
   - The allowlist sees the lower-cased path, so `<name>` is matched there by `[a-z0-9_-]{1,200}` (the lower-case image of the route's `SESSION_NAME_RE`, `[a-zA-Z0-9_-]{1,200}`). The router reads the name from `req.params` with its case kept and checks it against `SESSION_NAME_RE` itself; the lower-cased path is never used as the name.
2. **`ownerOnly` rule flag** (new, generic). After the device's person is resolved, a rule flagged `ownerOnly` refuses any phone whose person is not `role: 'owner'` with 403 `owner-phone-required`. MSP phones (people and roles) and unassigned phones never reach these routes. Neither route takes a conversation reference, so neither is `conversationRef`.
3. **Named rule buckets.** `deviceBucketOk(deviceId, perMinute, bucket)` keys its window by `deviceId + bucket`. The media-chunk rule keeps the bucket name `default` (behaviour unchanged); the two session rules get their own names, so heavy media upload never starves typing and vice versa. A key whose window has emptied is deleted, so the map holds only devices active in the last minute.
4. **A device-only router** `createMobileSessionTerminalRouter` (`src/server/mobileSessionTerminalRoutes.ts`), mounted in `AgentServer` immediately BEFORE the main routes, only when `this.mobilePairing` exists (the same condition as every other mobile router; with pairing off, device headers authenticate nothing, so no request is a device request). `authMiddleware` with the device authenticator is mounted far earlier, so the principal is set before this router runs. For a request whose principal is not `device` it calls `next()` at once, so the Bearer path reaches the existing handlers byte-for-byte unchanged. For a device request:
   - Re-checks the owner role (defence in depth; the authenticator already refused non-owners) and the session-name shape (400 `bad-session-name`).
   - **Session binding.** Both routes take an optional `sid=<session id>` query parameter. The output answer always carries the session's immutable record `id`. The app sends `sid` from the very first request whenever it knows the id (every `GET /sessions` row carries `id`), and from the first output answer onward in every case. Opening from the chat button, whose lookup names only the tmux session, opens whatever session runs under that name at that moment (the one driving the chat), and binds to its id from the first answer. If the name now resolves to a record with a different `id` (the session ended and its name was reused), the router answers 409 `session-replaced` ("This session ended and a new one took its name. Reopen it from the sessions list.") and neither reads nor types.
   - **Machine binding.** Both routes take an optional `machine=<machineId>` query parameter (signed with the path, as every query is). The app sends it whenever it knows the session's machine (every `?scope=pool` row carries `machineId`, the local ones included). When it is present and is not this machine's mesh id, the router answers `session-on-other-machine` for that machine at once ("You opened a session on X. Open it from X.", which repeats the phone's own request rather than claiming X's state), without looking at local records, so a remote row can never open or type into a local session that happens to share its name. When this machine has no mesh id (a single-machine install, which has no other machine to bind to), the parameter is ignored; such an install's rows carry no `machineId`, so the app omits it.
   - Resolves the name to exactly one **running or starting session record on this machine**, matched exactly in a fixed order: `tmuxSession`, then `id`, then `name`. The first field that matches any record decides; if that field matches more than one record, the answer is 409 `ambiguous-session` (nothing is read or typed). Only registered sessions are reachable from the phone; a bare tmux session that Instar does not track is not. (The Bearer input route passes the raw name straight to `sendInput`; this change leaves the Bearer route unchanged, and that gap is filed through the instar feedback API before this change's PR opens, with the receipt id named in the PR.)
   - Output: `lines` clamped to 1..2000 (default 200; the app polls 200 every 1.5 s and asks for 2000 once only when the person scrolls to the top, so 2000 is never the steady-state cost). The pane is read with `SessionManager.captureOutputAsync` (a non-blocking `execFile`), never the synchronous `captureOutput`, so a phone's polling never stalls the server's event loop. Answers `{ session, sessionId, tmuxSession, output, startedAt, machineNickname }` with `Cache-Control: no-store`. **Credential redaction:** before answering a device, the router replaces in the pane text every occurrence of this agent's API token, the dashboard PIN, and any `sig=<hex>` private-view signature (the same rewrite `stripViewSignatures` applies to other device answers) with `[redacted]`/`sig=removed`. Redaction is exact replacement, so a credential split across a wrapped line, interrupted by escape codes or encoded differently can still reach the phone. That residual exposure is accepted: this route is owner-only, and the owner's PIN unlock (`POST /dashboard/unlock`) already hands the API token itself to the same phone, so the owner's phone can never learn more through the pane than the PIN already gives it. The redaction removes the common printed forms so they do not sit in the app's screen. A record whose pane cannot be read answers `session-not-running`.
   - **Replay across a restart.** The device verifier's replay set is in memory (mobile-device-keys §2.3), which that spec accepts because every allowlisted route was idempotent or carried durable dedupe. Device input is the first allowlisted route that is neither, so it carries its own durable replay record: before anything is typed, the router writes the SHA-256 of the request's canonical signed string (the same string mobile-device-keys §2.3's replay set keys on) to `<stateDir>/state/mobile-session-input-replay.json` (atomic write; entries kept 3 minutes, longer than the verifier's ±60 s window). A digest already present answers 409 `replay` ("This exact request was already received, so it was not typed in again."); a record that cannot be written answers 503 `replay-record-unavailable` and nothing is typed (fail closed). This holds across restarts and whatever the phone's clock says, because it keys on the exact signed request, not on time.
   - Input: `text` must be a non-empty string of at most 8000 characters (multi-line text is pasted as one bracketed paste by `rawInject`'s tmux step for every framework, so an embedded newline never submits early) (the composer's limit; the Bearer route allows 100 KB) containing **no control characters except newline and tab**: any other C0 control (U+0000-U+001F), DEL (U+007F) or C1 control (U+0080-U+009F) is refused with 400 `bad-text` ("Only plain text can be typed into a session from the phone."). So Esc, Ctrl-C, Ctrl-D, carriage return and escape sequences cannot be sent: the text arrives as plain characters followed by the framework's submit. Sent through `SessionManager.sendInput` (`rawInject`: strips forged bracketed-paste markers and submits per framework). InputGuard is not applied, on purpose and as on the dashboard: the text is the owner's own typing, not inbound third-party text. Answers `{ ok: true }` meaning the session's input path accepted the text: for most sessions it was pasted into the pane; for a Codex session with the delivery journal on (Stage B), `rawInject` first records the text in the inbound delivery journal (`InboundDeliveryStore`, the same journal every message to a Codex session goes through, kept with the text as for a Telegram message) and may hold it behind an earlier message until that one is taken, so `ok` can mean "queued". Either way, `ok` never means the agent acted on it. A refused send (Codex: no rollout baseline yet, e.g. while starting or restarting, or the delivery journal is unavailable) answers 409 `send-failed`: "The session could not take your text right now. It may be starting or restarting; try again in a moment."
   - **InputGuard** is not applied (decision point below).
   - **Input audit.** Every accepted device input appends one line to `<stateDir>/logs/mobile-session-input.jsonl`: time, device id, person role and userId, session id and tmux name, text length. Never the text. The file is rotated to `.1` when it passes 2 MB (one generation kept). The log is machine-local: it lives on the machine whose session received the text, which is the only machine that could.
   - **Session not here.** On a local miss for a request whose `machine` equals this machine's id, the answer is `session-not-running` with no fan-out: the phone asked about THIS machine's session, and a same-named session elsewhere is a different session. Otherwise, on a local miss the router asks the pool whether another machine lists a running session with that name (the same peer `GET /sessions` fan-out `?scope=pool` uses, 3 s timeout, the first 16 peers in `resolvePeerUrls` order, only for device requests, only on a miss). If two or more peers list the name, the answer is `session-location-unknown` (no machine is named, because the name does not identify one session). If the pool has more than 16 peers, the unasked ones count as unanswered: a name no asked peer lists is then `session-location-unknown`, never "not running". The peer match uses the same order as the local one (tmux name, then id, then name) on the peer's rows. **Bounded:** a "runs on machine X" answer for a name is cached for 15 s and a "not running"/"location unknown" answer for 3 s (keyed by name, shared by every device; a session that moves, ends or starts inside that window is reported from the cache until it expires, and the app's next open asks again), and concurrent misses for the same name share one in-flight lookup, so a phone (even a modified one) causes at most one fan-out per name per 3 s (15 s once found elsewhere); at most 8 distinct names are looked up per device per minute (a sliding window whose entry is deleted when it empties), beyond which the answer is `session-location-unknown` without a fan-out. The machine's nickname in the answer comes from THIS machine's registry (`verifiedEntityName(machineId, registry nickname)`), never from the peer's own self-description; a machine this registry does not know is described as "another of your machines". Found elsewhere → 404 `{ error: 'session-on-other-machine', reason, ownerMachine: {machineId, nickname} }` with the reason in the exact words the "Open session" lookup uses (`This chat runs on <nick>, not on this machine…` becomes `This session runs on <nick>, not on this machine…`; the sentence shape is shared by one function). Not found on any machine that answered → 404 `{ error: 'session-not-running', reason: 'This session is not running any more. It may have finished or been closed.' }`. If one or more peers did not answer (timeout, refusal) and none listed it, the location is UNKNOWN, not "not running": 404 `{ error: 'session-location-unknown', reason: 'This session is not running on this machine, and I could not reach your other machines to check where it is.' }`. A single-machine install (no peers) answers `session-not-running`. The router never proxies output or input to another machine.
5. **CapabilityIndex** gains one sentence naming the two device routes. The CLAUDE.md template gains one bullet after the "Open session" bullet, and a `PostUpdateMigrator` patch inserts it into existing agents, guarded by the sniff string `native session screen`:
   `- The app's native session screen (owner phones only) reads \`GET /sessions/<name>/output\` and types with \`POST /sessions/<name>/input\`, phone-signed, on servers that support it (an older server answers 403 \`device-not-allowed\` and the app offers the dashboard instead). Only sessions running on this machine; plain text only, no keys. Each typed message is logged without its text in \`logs/mobile-session-input.jsonl\`. When the operator asks "did I type that from my phone?", read that log.`

### App (`apps/instar-ios`)

- `SessionView` (SwiftUI): header with session name, machine and start time (from the output answer's `startedAt`, else the list row or lookup that opened it); monospaced, selectable, scrolling output rendered as plain text (`UITextView` with no data detectors, never Markdown) after stripping ANSI/CSI, OSC (including OSC 8 links), DCS and other escape sequences, every C0/C1 control except newline and tab, and bidi override/isolate characters (U+202A-U+202E, U+2066-U+2069); the output is hidden whenever the scene is not active, so the app-switcher snapshot never holds pane text (the app already locks behind Face ID or the passcode on background, `AppLock`); polls output every 1.5 s while visible and in the foreground, pauses on background and on disappear. **Polling brakes:** a transient failure (offline, timeout, 429, 5xx) doubles the interval up to 30 s and a success resets it to 1.5 s; after 5 consecutive transient failures polling stops and the screen shows the error with a Retry button; a terminal answer (404 not running / on another machine / location unknown, 409 session-replaced or ambiguous-session, 403 not allowed or route missing, 401) stops polling at once and never retries by itself; after a 409 the composer is disabled with its draft kept, and the person reopens the session from the list; **snapshot semantics:** each poll answer REPLACES the text (never appended or merged), so repeated identical lines need no matching. While following (scrolled to the bottom) the view shows the latest 200-line snapshot. When the person scrolls up, following stops: the visible text freezes, polls continue and only raise a "New output, jump to latest" button. A "Show earlier output" control at the top fetches one 2000-line snapshot and shows it (still frozen). "Jump to latest" returns to following with the newest 200-line snapshot; a composer that posts to input; errors in plain words (not running, on another machine, location unknown, only the owner's phone, server too old, offline).
- **Composer rules.** Before the first send in a foreground period the app requires owner authentication within the last 5 minutes (`AppLock.recentAuthentication(within: 300)`, which exists on the app's current branch); if it is older, iOS asks for Face ID or the passcode first. Control characters other than newline and tab are removed before sending (the server refuses them anyway). A send is **never retried automatically**: on success the draft clears and the line "Sent. It appears in the output when the session takes it." shows; on a server refusal the draft stays with the reason; if the request may have reached the server (timeout, dropped connection) the draft stays and the screen says "This may not have been sent. Check the output before sending it again."
- The chat's session button opens `SessionView` natively when the lookup answers `active: true`; otherwise it shows the lookup's plain reason as today. If the agent's server is too old (the output route answers 403 `device-not-allowed`), the view shows a small "Open in dashboard" link to the `dashboardUrl` the lookup returned (from the sessions list, where there is no lookup, it says the agent needs the latest Instar update). 403 `owner-phone-required` shows "Only the owner's phone can open sessions." with no dashboard link. No other path opens Safari. The app needs no server-version check: the route's answer is the feature test, so a reverted or older server degrades to the dashboard link.
- A native sessions list on the agent's detail screen (`GET /sessions?scope=pool`, device-signed; already allowed for every active phone): rows show name, machine and how long the session has run; tapping opens `SessionView`. A remote row opens the same view, which shows the server's "runs on another machine" reason (an older server answers 403 and gets the update message instead). The list is shown to every paired phone, as `GET /sessions` already is; opening a session is what is owner-only.
- `SessionView` sends `machine=<machineId>` on both routes whenever it knows the machine (from the list row or the lookup's `ownerMachine`/self id), so the server never confuses a remote session with a same-named local one.
- Pure parts (ANSI strip, session-row parsing, duration text, error mapping) live in a small file with unit tests.

## Symbols and the states they claim (Verify the State, Not Its Symbol)

- **"Session is here"** — symbol: exactly one `running`/`starting` record in this machine's session state matching the request's name (tmux name, then id, then name). State claimed: a live pane on this machine. Corroboration: `captureOutputAsync` must return a pane (tmux answers for the real process); a record whose pane is gone answers `session-not-running`, the same as no record. Unmeasurable: n/a (both are local reads).
- **"Session runs on machine X"** — symbol: peer X's own `GET /sessions` lists an active session with that name (cached at most 15 s). (A signed `machine` parameter naming X is not this symbol: that answer repeats the phone's claim, "You opened a session on X. Open it from X.", and the phone took X from X's own row.) State claimed: the session lives on X. Corroboration: X's answer comes from X's own state over the authenticated mesh. Unmeasurable (peer silent, or a peer beyond the 16 asked): `session-location-unknown`, never "not running" and never a guessed machine.
- **"Phone is the owner's"** — symbol: the device record's resolved person has `role: 'owner'`. State claimed: the owner holds this phone. Corroboration: the owner's private pairing code confirmed the key, the request is signed by that Secure Enclave key, and the key ledger shows no revocation. Unmeasurable (person unresolvable): refused `person-unknown`. Phones paired before people-and-roles carry no role and resolve to the owner; they were confirmed with the owner's private code, so this holds. The person holding the unlocked phone is checked by the app lock (Face ID or passcode on every return to the app) and again before the first send in a foreground period.
- **"Text was typed in"** — symbol: `sendInput` returns true. State claimed: the session's input path accepted the text — pasted into the pane, or (Codex with Stage B on) journaled and possibly queued behind an earlier message. Not that the agent acted on it. Corroboration: the text appearing in the pane on a later output poll; for a queued Codex delivery that can come late, so text not yet visible after a poll or two is not proof of failure, and the app says so ("It appears in the output when the session takes it"). Unmeasurable: the app never claims more than "Sent", and the pane itself is the proof the person reads.

## Decision points touched

- **Device allowlist membership for the two session routes** — `invariant`. Deterministic by design: an exact method + path pattern + status set, the same shape as every existing allowlist entry. There are no competing signals; the question "may a signed owner phone reach this route" has one answer.
- **`ownerOnly` refusal of non-owner phones** — `invariant`. The person's role is a resolved registry fact (people and roles §3.4), not a heuristic. Fails closed: an unresolvable person is already refused (`person-unknown`) before the flag is read.
- **Per-rule rate buckets** — `invariant`. A fixed per-minute count, the existing primitive; refusal is 429, retried by the app's next poll.
- **"Session not here" classification (local miss → pool lookup → reason)** — `invariant` for the access decision (a miss is always 404; nothing is proxied or allowed by it). The machine named in the reason is a signal shown to the operator, not a gate. If any peer fails or times out and none listed the session, the answer is `session-location-unknown` (never "not running", which would claim a state nobody measured); it never names a machine it did not see.
- **InputGuard not applied to device input** — `invariant`. InputGuard screens third-party inbound text bound to a topic; this text is the owner's own typing from the owner's signed phone, as on the dashboard, whose input route also skips it. The control-character filter and the paste-marker strip still apply.
- **Machine binding (`machine` parameter not this machine → answered as another machine's session)** — `invariant`. An exact id comparison with this machine's mesh id.
- **Session binding (`sid` differs from the resolved record → 409 session-replaced)** — `invariant`. An exact id comparison; it can only refuse.
- **Machine-wide device input window (12 a minute, one at a time)** — `invariant`. A fixed count; refusal is 429.
- **Credential redaction of device output** — `invariant`. Exact string replacement of known values; it changes only what a device sees.
- **Durable input replay record (digest present → refused; record unwritable → refused)** — `invariant`. An exact digest lookup; it can only refuse, and it fails closed.
- **Device input text filter (control characters refused)** — `invariant`. A fixed character class; there is no judgement in whether a byte is a control character.
- **Device session name resolution (exact, fixed order, ambiguous → 409)** — `invariant`. Deterministic exact matching; ambiguity refuses rather than guesses.
- **App send retry** — `invariant`. Never automatic; an uncertain outcome is shown to the person, who decides after reading the pane.
- **App polling cadence** — `invariant`. A fixed interval with exponential failure backoff (1.5 s → 30 s cap), a 5-failure breaker that stops polling until the person taps Retry, and terminal answers that stop at once. Bounded per No Unbounded Loops; the server's buckets are the second brake.

## Multi-machine posture

- Session output and input: `machine-local-justification: hardware-bound-resource` — a session's pane is a tmux pseudo-terminal on one host; `capture-pane` and `send-keys` work only on that host. The phone's request lands on the machine it signed for; a session elsewhere is named (from this machine's registry), never proxied. A proxied posture would need a device-signed hop between machines; it is not requested and is not part of this change.
- The allowlist, `ownerOnly` flag and buckets are code, identical on every machine. Buckets are per-process memory (as today's buckets are); a phone talking to two machines has two independent buckets, which is the existing posture.
- The sessions list reads `?scope=pool`, the existing merged read, so the phone sees every machine's sessions with their machine name.
- No notices and no generated URLs are added. The durable additions, the input audit log and the input replay record, are machine-local by the same hardware reason: they record input on the machine whose pane received it. The replay record is not replicated. With multi-route on, a signed request names the Host it was sent to and only the machine that owns that name accepts it, so a replay to another machine is refused. With multi-route off, each machine verifies against its own device registry (`mobile-devices.json`, per machine): a replay to another machine is refused unless that machine holds the same device record AND is now serving the same paired host (a tunnel moved or state restored from a copy) within the 60 s signing window. That residual case is an accepted risk: the replaying party must already hold a captured TLS-protected request signed by the owner's Secure Enclave key, and the result is the owner's own text typed once more on a machine that is now the paired host.

## Security

- **What it grants.** An owner phone can read a local session's pane and type into it. The owner's PIN-unlocked dashboard already grants exactly this (Sessions tab, WebSocket `subscribe`/`input`). The phone's key was confirmed by the owner's private 6-digit code at pairing and lives in the Secure Enclave. Nothing beyond that is granted: no keys (Esc, Ctrl-C), no attachments, no kill, no spawn, no unregistered tmux sessions, no other machine.
- **What it does not grant.** MSP phones, unassigned phones, pending/declined/expired/revoked phones, the notification read token, and unsigned requests are all refused before any route runs. A revocation in the device-key ledger takes effect at once (existing behaviour).
- **Replay and tampering.** Every request is signed over method, host, exact path and query, time and body; edits fail the existing verifier, and replays fail it within one server process. Input is the first allowlisted device route that is neither idempotent nor deduplicated, so it adds a durable replay record of each accepted request's signature digest, written before typing and kept 3 minutes: a captured input cannot be typed twice, across restarts and regardless of the phone's clock.
- **Prompt injection.** Typed text enters the session the same way the dashboard's typed text does, through `sendInput`/`rawInject`, which strips paste-boundary forgeries; control characters are refused before that. The text is the owner's own instruction. For Codex sessions with Stage B on, the text is kept in the existing inbound delivery journal, as every message to that session is.
- **Output exposure.** The pane may show secrets the session printed; the PIN dashboard shows the same pane to the same owner. The agent's own API token, the dashboard PIN and private-view `sig=` values are redacted for devices (above), and the residual case (a split or encoded credential) is within what the owner's PIN unlock already gives the same phone. Other secrets a session prints (a third-party key it was told about) are shown, as on the dashboard. The response is `no-store`.

## Verification

- Unit: allowlist shape, `ownerOnly`, named buckets and their cleanup, text filter, name resolution order and ambiguity, miss cache and per-device cap, reason wording.
- Integration (production `authMiddleware` + `deviceAuthenticator` + the new router + a stub main router to prove Bearer pass-through): owner phone allowed for output and input; the token, PIN and `sig=` redacted from device output; `sid` mismatch → 409; `machine` = self with a local miss → not running without a fan-out; two peers listing the name → location unknown; the machine-wide input window; `machine` naming another machine answered without touching a same-named local session; the same signed input sent twice (including after a router restart with the same state dir) refused as `replay`; more than 16 peers with no hit answers location-unknown; a legacy phone record with no role is treated as the owner; MSP, unassigned, pending, revoked (registry and ledger), notify-token and unsigned requests refused; Bearer-only requests reach the main handler untouched; on-another-machine, not-running and location-unknown answers; 400 `bad-text`; 409 ambiguous; 429 per bucket.
- E2E: the production `AgentServer` boot path with mobile pairing on: a signed owner phone reads a real session record's output (stubbed tmux capture) and the route answers 200, not 503 or 403.
- App: unit tests for the pure parts; a simulator screenshot of `SessionView` with seeded output. The live phone check against a running agent is part of Echo's TestFlight ship step for this change.

## Rollback

Revert the PR. The two allowlist entries, the `ownerOnly` rule flag, the router and the bucket naming vanish; phones get 403 `device-not-allowed` and the app shows "Open in dashboard". No config is added. Durable additions: the input audit log (an append-only file a revert leaves in place, harmless), the 3-minute input replay record (a small file of digests, harmless when left) and one CLAUDE.md bullet inserted by migration; the bullet is worded to stay true on a server without the routes (it names the 403 fallback), so a revert leaves no false self-knowledge. App side: an installed app build cannot be recalled, which is why it feature-tests the route on every open and needs no server version.

## Maturation plan

- **test-agent-live:** The integration suite drives both routes through the production device authenticator with real signed requests (owner allowed; MSP, unassigned, pending, revoked, notify-token, unsigned refused; replay across a restarted router refused), and the e2e test boots the production `AgentServer`, pairs a phone through redeem and confirm, and reads and types into a session record.
- **dev-agent-live:** Echo's own agent and Justin's paired phone: the session button and the sessions list open the native screen against Echo's live server, reading and typing into a real session, before the app build goes to TestFlight.
- **graduation criterion:** One week of the owner using the native screen with no refused legitimate request other than the documented ones (not running, another machine), no input typed twice (replay record) and no credential seen in device output; the input audit log and the device refusals are the evidence.
- **fleet:** Rides the existing `mobilePairing` switch: wherever mobile pairing is on, owner phones get the two routes. No separate switch, because the routes add no capability beyond the owner's PIN unlock and a revert removes them.
- **dark-window:** None of its own; it is as dark as `mobilePairing` is on each agent, and follows that entry's ladder.
- **ladder:** mobilePairing

## Frontloaded Decisions

1. Owner phones only (not MSP), per the build request; MSP access to sessions is not requested.
2. Local sessions only; a remote session is named, not proxied.
3. Polling (1.5 s), no device-signed WebSocket: the WebSocket authenticates once at connect with the bearer token and has no per-frame signature design, which a device key would need.
4. Composer limit 8000 characters; output read limit 2000 lines.
5. Buckets: output 90/min, input 12/min, named per rule.
6. No key buttons (Esc, Ctrl-C) in this change; control characters are refused so text cannot stand in for keys.
7. Never auto-retry an input send; uncertain outcomes are shown.
8. The sessions list is shown to every paired phone; opening a session is owner-only, with a plain message for others and no dashboard link.
9. No app feature switch or minimum server version: the route answer is the feature test.
10. Input audit to `logs/mobile-session-input.jsonl` (length, not text), rotated at 2 MB; durable 3-minute replay record for input.
11. Miss lookups cached 15 s per name, single-flight, at most 8 names per device per minute.
12. Approval source: Justin's request in topic 134088 (2026-11-03 22:01, 22:55 PST); the design grants no more than the owner's PIN unlock already grants.
