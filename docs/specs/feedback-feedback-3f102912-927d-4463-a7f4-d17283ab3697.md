# Login-expiry detection misses new Claude Code wording

## 1. Problem

On 2026-11-13 a Claude Code session showed **"Login reached its time limit"** after its sign-in
ran out. None of the existing recovery paths fired:

- the account stayed `active` in the pool,
- the session was not moved to another account,
- the conversation did not move to another engine (Codex),
- the user got no notice.

The report says the session could not respond for about 4.5 hours while the pool looked healthy.

### Root cause

All automatic handling of an expired CLI login starts with one signal,
`classifyLoginExpired` in `src/core/LoginExpiredSignature.ts`. It only matches a line when the
line starts with one of a fixed list of phrases:

| List | Phrases (anchored at line start, after the lead glyph) |
|---|---|
| `LOGIN_EXPIRED_FRAMES` | `Login expired`, `OAuth token (has) expired`, `Invalid API key … /login`, `Please run /login` |
| `MESSAGE_LED_ONLY_FRAMES` | `Not logged in … /login` |

"Login reached its time limit" begins with `Login reached`, so it matches none of them. Every
pattern is anchored at line start, so a `· Please run /login` suffix would not help either. The
classifier returns `{ loginExpired: false }`.

Every consumer downstream already works with any wording. They receive the matched line as text
and never parse it again:

- `SessionManager.endIfLoginExpired` (rerouted job sessions) ends the session and reports a degradation.
- `SessionManager.reportInteractiveLoginExpired` (topic sessions) passes the session to
  `InteractiveLoginExpiredRecovery`, which swaps accounts and notifies the user.
- `SessionManager.listSessionsAtLoginScreen` lists sessions that are stuck at a login screen.
- `QuotaPoller.observeCliLoginExpired` changes the account to `needs-reauth`. It gets this input
  through the two `SessionManager` paths above.

The defect is therefore a single gap in detection. Because the classifier never matched, nothing
downstream had a chance to run.

### Why this keeps happening

This is the third Claude Code wording change for the same condition:

1. 2026-10-18: `Login expired · Please run /login`
2. 2026-10-25: `Not logged in · Run /login` (CMT-1008)
3. 2026-11-13: `Login reached its time limit`

Each time, the new wording went unnoticed until a person saw a stuck session. A miss leaves no
trace: the classifier does not report that it saw an auth-looking line it could not recognise.

## 2. Evidence

- Reporter text (scrubbed, untrusted): reported on 2026-11-13, citing CORR-432/433 on the Inspec
  laptop. *"Login reached its time limit" matched no LoginExpiredSignature frame; pool showed
  active; no swap, no Codex fallback, no user notice.* The report suggests behaviour-triggered,
  LLM-judged detection, tracked as CMT-1735.
- Code reading (this draft) confirms that no frame in `LoginExpiredSignature.ts` matches a line
  that starts with `Login reached its time limit`.
- The report gives only the leading phrase. It does not show the lead glyph or any suffix that
  may follow, such as `· Please run /login`. The fix below must therefore work with the phrase
  alone.

## 3. Existing related work

`docs/specs/never-silent-conversation.md` (approved on 2026-11-13 after the same incident) adds
an LLM judge for unanswered conversation messages. The judge has a wording-agnostic
`engine-login` class, and when it reaches the confidence floor it calls
`QuotaPoller.observeCliLoginExpired`. In that design, `classifyLoginExpired` is only a *hint* to
the judge. As currently wired in `src/commands/server.ts`, that system:

- is turned on only by the dev-agent gate (`resolveDevAgentGate`),
- does not swap or change engines unless `monitoring.neverSilent.actions` and
  `frameworkFallback` are set (both are off by default),
- covers conversations only. It does not cover rerouted job sessions, which reach
  `endIfLoginExpired`.

So the LLM classifier this report asks for already exists for conversations. This draft does
**not** redesign it and does **not** change its gates or defaults. Turning it on for more agents
is a separate decision for the operator (see §6). This draft fixes the deterministic signal that
the rerouted path and the interactive path still depend on. It also stops future wording misses
from going unnoticed.

## 4. Proposed fix

The fix has two small parts, both inside `src/core/LoginExpiredSignature.ts` and the
`SessionManager` paths that already call it. It adds no new I/O, network hosts, shell-outs or
pool authority.

### 4.1 Recognise the reported wording (message-led only)

Add one pattern to `MESSAGE_LED_ONLY_FRAMES`:

```ts
/^login reached its time limit\b/i,
```

This goes in the *message-led-only* list, not the general list. The phrase does not contain
`/login`, so it is weaker than the existing frames. A `⎿`-led tool result, such as a session
printing a log, must not be able to mark an account. This uses the same precision rule CMT-1008
set for `Not logged in`. Tail-gating, glyph-leading and line-start anchoring are unchanged, so
prose that mentions the phrase mid-line still does not match.

### 4.2 Make future wording misses visible (signal only, no pool change)

Add a second pure function to the same module:

```ts
export function classifyUnrecognisedAuthFrame(paneText: string, opts?: { tailLines?: number }):
  { suspect: boolean; line?: string };
```

It returns `suspect: true` only when **all** of these hold:

- `classifyLoginExpired` on the same pane returned `loginExpired: false`,
- the line is in the live tail (same `liveTail` and tail-gating as the main classifier),
- the line is message-led (`⏺`/`●`), and is not a `⎿` tool result,
- after stripping the lead glyph, the line *starts with* `login`, `sign-in`, `signed out`,
  `session expired`, or `auth`, or the line contains the literal `/login` token.

The match line is clamped to 160 characters, as `matchedLine` is today.

This is an **observation, not an authority**. When `reportInteractiveLoginExpired` or
`endIfLoginExpired` does not get a login-expired verdict but does get `suspect: true` that lasts
for `LOGIN_EXPIRED_DWELL_MS`, it emits one
`DegradationReporter.report({ feature: 'SessionManager.loginExpiredSignature.unrecognisedFrame', … })`
per session per episode. Repeats use the existing `INTERACTIVE_LOGIN_REPORT_RETRY_MS` backoff.
The report includes the clamped line so the operator sees the new wording the first time it
appears, not hours later.

It does **not** kill the session, swap accounts, or call `observeCliLoginExpired`. Turning a
suspect line into an action stays with the deterministic frames (4.1) and the never-silent judge
(§3).

### 4.3 Out of scope

- No change to the never-silent judge, its prompt, its gates or its defaults.
- No new LLM call in `SessionManager`'s monitor tick.
- No change to `QuotaPoller`, `InteractiveLoginExpiredRecovery`, or account and pool storage.
- No new config keys.

## 5. Regression test plan

All tests are pure or use in-memory fakes. They use no network, no home-directory paths and no
credentials. Any filesystem use goes in a temp dir that the test creates (`fs.mkdtempSync`) and
removes itself. No existing test is weakened, skipped or deleted.

1. **`tests/unit/LoginExpiredSignature.test.ts`**. Add these cases (all fail on the current code):
   - `'matches the 2026-11-13 "Login reached its time limit" frame (message-led)'`:
     `⏺ Login reached its time limit\n❯ \n` gives `{ loginExpired: true, messageLed: true }`,
     and `matchedLine` starts with `Login reached its time limit`.
   - The same with the `●` lead, and with a `· Please run /login` suffix.
   - Precision guards (these pass before and after the fix, and lock in the boundary):
     `⎿  Login reached its time limit` gives `loginExpired: false`. Prose such as
     `⏺ The pane said "Login reached its time limit" earlier.` gives `false`. The frame scrolled
     out of the 12-line tail gives `false`.
2. **`tests/unit/LoginExpiredSignature.test.ts`** gets a new `describe('classifyUnrecognisedAuthFrame')`:
   - A made-up future wording such as `⏺ Login session ended · Run /login` gives
     `suspect: true`. This fails before the fix because the export does not exist.
   - Every frame `classifyLoginExpired` already recognises gives `suspect: false`, because those
     belong to the main classifier.
   - `⎿`-led lines, unrelated message-led prose (`⏺ Logged the result to the file.`) and empty
     panes give `suspect: false`.
3. **SessionManager interactive path.** Add a test next to the existing interactive login-expired
   coverage, using the same fake pane-capture and clock approach as the current
   `reportInteractiveLoginExpired` tests:
   - `'an interactive session showing "Login reached its time limit" is handed to the recovery sink after the dwell'`.
     The fake pane returns `⏺ Login reached its time limit`. Advance the clock past
     `LOGIN_EXPIRED_DWELL_MS`, then assert that the sink was called once and that `matchedLine`
     contains the phrase. This fails on the current code because the sink is never called.
   - `'an unrecognised message-led auth line reports one degradation and never calls the recovery sink'`.
4. **SessionManager rerouted path.** Add a test in `tests/unit/rerouted-login-expired-awareness.test.ts`
   or next to it: a rerouted job session showing the new frame is ended with reason
   `rerouted-login-expired` after the dwell. This fails on the current code because the session
   holds its slot.

The one test named as failing first and then passing is case 1:
`classifyLoginExpired > matches the 2026-11-13 "Login reached its time limit" frame (message-led)`.

## 6. Open questions for the operator

1. **The LLM classifier the report asks for.** It already exists as the never-silent judge, but
   only on dev agents and with actions off. Should it be turned on (judge only, still notice-only)
   for all agents? Judging that needs an evaluation step first: record its verdicts against the
   frame corpus from §5 plus real incident panes, and check its precision and recall before any
   action flag is turned on by default. This draft proposes the evaluation but does not change
   any defaults.
2. **Exact wording.** The report shows only the leading phrase. If a captured pane shows a
   different glyph or suffix, the pattern in 4.1 should be adjusted to match it. The suspect
   signal in 4.2 is the safety net in the meantime.

## 7. Rollback

Both parts are additive and pure. To roll back, revert the commit. With 4.2 reverted, the
degradation report simply no longer fires. No state migration is involved.
