# Idle Codex model switching

## Outcome

A person can change the model inside a running Codex conversation. Instar needs to tell that choice apart from a saved default before it could ever help apply a newer model at idle. This slice delivers an owner-scoped diagnostic that reports stored model policy separately from the verified configured thread model and eligibility. Eligibility concerns possible idle switching. A stored pin identifies policy intent only. An exact live or inherited classification requires the owner-bound runtime proof. The diagnostic keeps existing conversations running as they are. The mutation contract below defines the evidence a separate implementation would need to change that behavior. It grants no current switching authority.

## Current capability

The installed integration starts interactive Codex in a terminal pane. `src/core/ModelTierEscalation.ts` marks Codex launch-time-only and `src/core/ModelSwapService.ts` refuses in-flight changes for that capability. Neither the recorded launch model in `SessionManager.ts` nor a historical `turn_context` model in the rollout reader identifies the model selected in a live process after a native edit. The live account rate-limit reader starts a separate app-server and reads account metadata. The origin Codex canary starts its own thread and calls `turn/start`. These interfaces establish account or isolated-thread capabilities only. The inspected repository has no process-bound live-model read or all-input barrier wired for existing terminal sessions.

The locally generated experimental app-server schema for Codex CLI 0.171.0 exposes a possible future read adapter. `ThreadReadResponse.Thread.model` reports current configured model when loaded, latest persisted model otherwise, or null. Its `status` distinguishes `notLoaded`, `idle`, `active` and `systemError`, and its `sessionId` identifies a tree shared by threads. A response alone does not establish the live process or the exact thread. An unloaded response or unrelated app-server cannot qualify. It also exposes `thread/settings/update` with an exact `threadId` and an optional model override for subsequent turns. The generated response has no model field, so verify the result with a fresh read against the same loaded thread. This is the preferred eventual zero-turn in-place path when the owning app-server transport, input barrier and installed-runtime behavior have been demonstrated. The schema also exposes `ThreadResumeResponse.model` and `TurnStartParams.clientUserMessageId`. A resume response needs subsequent live verification. The message ID schema gives no guarantee of durable acceptance or deduplication. The `turn/start` model override applies to a turn and subsequent turns, so it cannot serve as a zero-turn idle model transaction. A process-bound owner transport and installed-runtime tests are still required.

`TopicProfileOrchestrator.ts` has topic coordination and Codex capture-at-kill tied to a spawn fence. Its generic resume flow can fall back to a persisted mapping or fresh continuation. Automatic model reconciliation requires stricter exact-conversation custody and must use only the compatible primitives. `SessionRefresh.ts` does not supply the entire exclusive input and receipt contract. No mutation adapter qualifies on current evidence.

## Observation slice

Ship a classifier that can be exercised through a read-only server-owned observation entry point. Evaluate on demand against the owning machine using an immutable dependency bundle containing read access only. The observation path performs no model turn, sends no terminal bytes, starts no child, writes no rollout or queue record, and schedules no restart. A bounded diagnostic result includes the current eligibility reason, evidence freshness, current policy version and a target model only when policy resolution and compatibility establish one. Use the existing server bearer authentication and dashboard operator-session verifier, then verify current local conversation ownership for the exact session. A general session list or output endpoint is insufficient. Require all three proofs before returning a diagnostic. Deny ambient paired-device or team membership and peers without the current ownership epoch. This machine-maintenance endpoint is operator-only. Authorized team access to messages and conversation history continues through the existing conversation controls. The diagnostic never treats a team member as the machine operator and does not issue an operator session. Keep raw terminal text, rollout content, paths, credentials, and account identifiers out of the response and any diagnostics. Read-only status remains machine-local and must not become a remote command or a routing fact. Unknown ownership returns a refusal without revealing session evidence. Use only bounded, already-available policy, account and CLI capability snapshots. A stale or missing entry remains unknown, with no account probe, process spawn, pane scrape or fallback. Bind policy and the cached result to the durable TopicProfileStore revision of the exact topic and the active policy revision. Recheck both revisions, ownership and process incarnation before serving the result. Every live claim must also match an owner-issued observation revision covering native settings and turn or input state, with a gap marker when native events were missed. Recheck that revision before responding. A current independently sufficient exclusion, such as a verified exact pin or a runtime whose unsupported version is established, returns ineligible with a reason even when other runtime evidence is gapped. A missing capability snapshot gives unknown eligibility unless an independent exclusion applies. Without that exclusion, a stale, mixed, or gapped snapshot returns unknown. Live fields remain unknown in either case and may carry the last observation timestamp. Name the owner-verified native field configuredThreadModel. It describes the setting for subsequent turns. Any executing-model claim needs separate exact-turn evidence and is outside this diagnostic. Keep the evidence result model and unsupported path framework-neutral. This first adapter evaluates the reviewed Codex subscription policy. A different provider can qualify its own model policy through the same adapter contract. Record a fixed, low-cardinality set of aggregate diagnostic reasons and fixture or authorized development truth-match counts through the existing metrics owner without retaining conversation details. Capture a pilot baseline and compare accuracy, unknown reasons and adapter coverage at the weekly review as installed versions change.

Use verified launch provenance only when available. Represent legacy, unknown, pinned, default-following and native or otherwise overridden as distinct states. A new launch provenance record, when introduced, must be written from the trusted effective-model resolution path before that process can be a candidate. Bind session and native conversation identity, machine, process start identity, selected account handle, requested moving selector, compatible launch model and policy revision. Offer no inference from existing records that merely say “config-default” or contain a launch argument. The day-one positive control is a stored exact-model pin. Inherited live eligibility stays unknown until verified launch provenance and native selection evidence are wired. ## Mutation contract

Automatic mutation remains disabled until an adapter for a supported Codex runtime/version can prove the following conditions in installed-environment tests. Apply Ownership-Gated Side Effects. This reviewed catalog covers subscribed Codex Sol and Astra. Local runtimes have distinct model identities and report outside-catalog status in this slice. A separately reviewed local policy can qualify a local adapter against the same runtime and continuity requirements. Run under the current conversation owner lease and exact process-incarnation fence. Prefer a guarded in-place transaction through the exact owning runtime. Consider exact resume under the same subscribed account only when in-place switching is unavailable and the resume path independently qualifies. Any alternative needs the same contract.

1. Obtain explicit opt-in and valid inherited-selector provenance. Old or previously native-edited sessions require fresh explicit adoption of that selector. Preserve human intent with a runtime-observable selector origin and settings revision, or prove exclusive ownership of every settings path from launch. A same-model explicit choice, change away and back, or gap in observed settings events invalidates inherited eligibility. Resolve the target under the current config and reviewed catalog, compatibility and account policy. Equal, older, unrecognized or quota-substituted targets are ineligible. This slice never migrates accounts or selects a metered lane. The selection policy revision and installed runtime capability version are part of the attempt identity.
2. Verify selected live model in the same active runtime and thread independently of stored launch state or transcript. Require authoritative work and pending-input evidence from the runtime. Acquire an exclusive input admission barrier covering native terminal, runtime clients, platform delivery and queued work. Prove no active turn, child work, attachment or pending input is in flight and close the race between that check and mutation. A quiet pane, a quiet timer, an editable prompt or a prior turn event can corroborate but never grant admission.
3. Under the barrier, revalidate owner epoch, exact process incarnation, current model and conversation, selector origin, native settings revision, compatibility, opt-in and policy revision. Serialize native settings, topic pin writes and opt-in revocation through the same mutation authority, or require the receiver to compare their exact revisions atomically at apply. If an exact pin or revocation commits before the mutation, reject the model update. An installed path without a shared serialization authority remains observation-only. Before any change, durably journal the original session, native thread, verified account binding, independently verified original and destination model, attempt identity and delivery cursor. A replacement also requires a durable retrievable reference to the exact resumable rollout and its admissibility under the same account without a trial turn. An in-place operation holds input after a lost acknowledgment. A read showing either the original or destination model is conclusive for the mutation only after a receiver-confirmed terminal status for that exact journal attempt, an ordered read after its confirmed completion, or revocation that proves a delayed write cannot apply. An uncorrelated read or matching destination with a still-pending request remains ambiguous and cannot reopen input. A missing or mismatched journal prerequisite leaves the existing process running.
4. Use the existing termination/launch authority with the exact fence when replacement is required. Every native and platform input path starts closed on a replacement until the journal is reconciled and the postcondition passes. The barrier survives a coordinator crash or comes up closed from the unresolved journal, including when the new process first becomes reachable. For in-place switching, use only a supported runtime transaction with equivalent fencing and post-checks. Never spawn a fresh conversation or silently fall back to another account or model. Verify live model, native thread, account and ownership from the resulting process before reopening input or reporting success.
5. Keep messages in the existing durable delivery custody. The receiver must atomically persist acceptance keyed by stable delivery ID before acknowledging or acting on the payload, with recovery applying accepted work idempotently. Retries return the prior acceptance outcome. Require durable receiver acceptance whenever an attempt may replace the process, dispatch a payload or replay one. For a zero-turn in-place update, an independently verified barrier and unchanged thread, process and delivery cursor can prove no dispatch or replay occurred. If neither proof applies, block automatic mutation. Sender receipt and pane echo do not establish receiver acceptance.
6. Use a single serialized attempt per fenced conversation and intent. The receiver must verify the current mutation fence at apply time, or the ownership transfer must drain and revoke the prior transport before a new owner acts. A delayed request from a displaced owner must never apply. The successor reconciles the durable journal before dispatch or another attempt. Before mutation, a known intact process may be reopened and reevaluated. After mutation, unknown outcomes remain in recovery custody, with no blind retry or replay. An authoritative result for the exact process can resolve the pending state. A supported exact recovery to the prior model may be attempted under the same verified identity and account. Keep the original evidence and queue custody on an ambiguous outcome. Record a recovery-required status in the owning journal and let the current owner use the existing recovery supervisor to obtain an authoritative read or surface a bounded operator recovery request. The input gateway can acknowledge safe durable intake and report the hold without dispatching to an uncertain thread. The current owner keeps a separate authenticated recovery and status control reachable while the affected thread is fenced. Confirm held input without reporting it dispatched. The existing recovery supervisor deadline opens a visible owner escalation that can hear the operator and offer an authenticated safe resolution or cancellation of the model attempt while held input stays in normal durable custody. The deadline cannot authorize a fresh conversation or replay. Uncertain acceptance never becomes replay permission.

## Decision points touched

- Observation eligibility — invariant; basis: enumerable-domain; evidence: an explicit pin, local provider, unsupported runtime or unknown identity excludes automation.
- Admission and postcondition — invariant; basis: irreversible-consequence; evidence: interrupting an active session can strand its work, and reopening delivery on an unverified thread can lose or duplicate messages.
- Recovery ownership — invariant; basis: irreversible-consequence; evidence: overlapping owners can accept the same delivery or advance incompatible session state. Require current epoch and durable reconciliation before acting.

## Evidence and machine ownership

A positive observation uses exact identities resolved by the owning machine inside its existing authority boundary. The logical conversation has one eligible owner. Process incarnation, native input state and local subscription account verification are properties of that owner. When ownership moves, the successor needs durable journal and delivery custody through the existing exact-conversation transfer path before any future actuation; an implementation without transfer custody remains observation-only. A process ID, age or version, a parsed terminal footer, a thread label, and a completed-turn rollout row are advisory. Independent runtime readback must match the native thread and process incarnation. Unknown process, account, ownership, model, intake or receipt evidence disables mutation.

machine-local-justification: hardware-bound-resource — process incarnation and native-terminal admission exist on the host owning the process.
machine-local-justification: physical-credential-locality — exact subscription account verification uses the account binding available to the owning runtime. Account credentials do not transfer in the journal.

## Frontloaded Decisions

1. Deliver owner-scoped, cache-only observation in this slice. Unsupported paths report unavailable, and all mutation ports are absent.
2. Bind positive evidence to exact thread ownership and process incarnation. Require selector intent and a settings revision before treating a session as inherited.
3. Qualify in-place model update first. Exact resume is eligible only when its additional continuity requirements hold.
4. Require receiver-enforced fencing and durable delivery custody before actuating. Leave ambiguous outcomes with the current owner and recovery supervisor.

## Verification

- Unit-test signal boundaries for current versus stale incarnation, legacy versus trusted provenance, model and account mismatch, no compatible upgrade, unknown work/input state and revoked opt-in. Assert unavailable observations leave the decision unknown and invoke no write or process port.
- HTTP integration verifies bearer and operator-session authentication, exact owner custody, redacted output, refusal for unauthorized device or peer, a cold or stale evidence cache, the same unpinned session with verified unsupported version and unavailable capability snapshot, pin removal against a gapped runtime snapshot, a pin change without process restart between reads, an ownership transfer during a read, and absence of subprocesses, mutation routes and dispatched work.
- Production-wiring lifecycle test starts the server with a fake supported observation adapter and a real session record. Verify an idle unpinned candidate can be described, along with busy, pinned, local and unknown cases. Assert no session, process, queue or rollout changes. For the installed pilot, seed two topics with different exact pins and record their expected bindings independently of the profile resolver. Change one without restarting either runtime, verify both readbacks, and verify that missing runtime evidence stays unknown.
- Before mutation eligibility, exercise a real supported runtime on an isolated fixture. Verify an exact same-model selection, a native edit away and back, missed selection events, delayed old-owner mutation after transfer, lost in-place acknowledgment, a read overtaking a delayed update and a matching destination while the request remains pending, an exact topic pin and opt-in revocation committing between preflight and receiver apply, draft keystrokes and a concurrent message across admission, native input after replacement launch and before verification, a gapped runtime snapshot before and after pin removal, and an alternate recovery control during a held dispatch, PID reuse, owner transfer, preflight failure, restart between journal and swap, crash after termination and before replacement launch, native revision or a new turn between cache fill and response, crash immediately before and after durable receipt, incorrect model, wrong account, resume mismatch and idempotent reboot recovery. Exact conversation continuity, one accepted delivery per ID and no automatic dispatch on unknown evidence are graduation requirements.
