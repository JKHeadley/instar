# Codex 429 exits: failed sessions and visible reports

A Codex fixer can receive an HTTP 429 from OpenAI, exhaust its own retries, and exit. tmux keeps the failed pane so Instar can inspect its exit code. That retained pane still makes `tmux has-session` succeed. In the reported November 4 incident, five fixer sessions stopped within minutes, yet their work was described as running and no clear alert identified the rate limit.

Instar already has a five-second session monitor that checks `pane_dead` and a job scheduler that uses a session's final status to decide whether a job succeeded. It also has a live-prompt rate-limit sentinel, but that sentinel cannot recover a process that has already exited. The change joins those existing pieces at the point where the monitor confirms a dead pane. It reads the retained Codex pane's final output, requires a nonzero exit code and an explicit `429 Too Many Requests` response, then records the session as failed with a named reason. The job scheduler therefore records a failed run and releases its slot. The monitor removes a dead job pane and emits a one-time event that creates a high-priority Attention item, reports degradation, and tells a bound Telegram topic when available.

This path reports the failed work plainly and asks for a retry on another signed-in Codex account or after the limit resets. A retry is not launched automatically here because the dead job may have written partial files or performed external actions before the 429; replaying it without the job's own idempotency rules could duplicate those effects. A normal clean exit and other frameworks keep their existing classification. A real-tmux test covers a retained Codex 429 after the startup window, checks the failed status and event, verifies that it no longer occupies running capacity, and confirms the dead job pane is removed.

The repair also handles a small timing gap in tmux: it can say the terminal is dead before the process exit code has arrived. Instar now waits for that result instead of treating a missing exit code as success. If the process was stopped by a signal, that also counts as a terminal result. Tests cover both monitor modes, a real process held at this timing boundary, clean exits with old error text, and repeated checks that must not send duplicate notices.
