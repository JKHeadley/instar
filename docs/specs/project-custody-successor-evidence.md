# Verify Project Evidence After a Machine Loss

## Problem statement

[Canonical Project Custody](canonical-project-custody.md) requires proof that a project change acknowledged as shared survives the loss of its original holder. Existing Chief of Staff records travel on the authenticated machine sync path. It is useful to know whether a second machine can display a known, independently replicated item decision from its own durable state after the originating machine is isolated. That narrower result leaves the parent issue, #3753, open. This increment measures the existing path with the origin unavailable during a cold survivor read without changing where projects are written or who can act on them.

**Cross-Machine Coherence** governs the independent recovery claim. **Signal vs. Authority** keeps the evidence from qualifying a new writer or granting access. **Cross-Store Coherence Is an Invariant** protects the current project authority from a second write path.

## Frontloaded Decisions

1. Qualify exactly one existing Work action, a fixture owner device marking an owner-judged item checked on a synthetic Chief of Staff project. Use the existing mobile presence challenge, action writer, journal sync and owner read paths. Stand-in device keys in the simulator exercise the exact production challenge validation. Genuine phone presence is a separately recorded acceptance and cannot be implied by this proof.
2. Require two separately installed and enrolled machines with independent durable storage. Record the established project and item baseline on B. Perform the native action on A, independently verify the exact replica on B, isolate A and read B through the normal owner Work view after a cold B restart.
3. Report the acknowledged local write, B's durable receipt of the exact origin occurrence and B's authorized projection as separate facts. Without independent B evidence, incomplete input or a cold normal read, the positive recovery claim is unproven. Require a distinct immediate-isolation probe whose result cannot be counted as shared success.
4. Verify B's current read authority at exposure. Use the existing mobile reader against an active owner and against restricted and formerly authorized credentials. If B cannot establish current role, revocation, applicable source state or erasure posture in the isolated run, withhold recovered content and report unavailable.
5. Keep the exercise synthetic and evidence-only. The diagnostic performs no writes and creates no runtime endpoint, state registry, receipts that carry authority, project actions or failover permissions. Only the authorized fixture setup, native action signed by the enrolled fixture device and controlled test-device revocation use existing write paths. Leave the canonical writer, cutover pointer and #3753 gate in place.

## Proposed design

### Authoritative inputs and data handling

Use the installed, feature-enabled Chief of Staff and mobile Work stack. This design is a bounded qualification procedure with an optional local evidence collector. The collector reads through existing interfaces or inspects the two disposable homes from outside the server process. It may not edit or seed the journal, manufacture an accepted receipt, set a project state, bypass or replace the device proof, copy durable bytes between homes, expose another network surface, or add fallback authority. Test materials use a unique synthetic project and harmless item text. Use only separately installed fixture machine identities and enrolled fixture devices from the approved Studio and Mac Mini test environment. The development witness exercises the real physical hosts, with simulator-backed device identity and secrets. When needed, use only the dedicated live-test bot fixture on one polling process. Keep live user and agent services outside the test topology. The consenting test owner is accountable for the raw proof and can authorize independent reviewers in the restricted environment. Published results use opaque host and project aliases and expose only controlled proof outcomes. Keep raw logs, phone credentials, presence proofs, project text and journal payloads inside the restricted test environment.

The normal writer is `POST /mobile/work/projects/done-item` in [mobilePermissionsRoutes.ts](../../src/server/mobilePermissionsRoutes.ts#L1108), through [workProjectActions.ts](../../src/server/workProjectActions.ts#L21) into [ChiefOfStaffLoop.appItemCheck](../../src/core/ChiefOfStaffLoop.ts#L1224). The native route verifies the current paired owner phone and consumes a one-time presence proof over the exact action. The loop verifies the current open project, unique judgment item and goal/item fingerprint, then waits for local journal durability before returning success. Use a fixture that has not yet been checked and confirm that B initially projects the unchecked item. The recorded tap ID is server-generated. Its survival proves the origin recorded the fixture owner device’s decision through this path. That records accepted fixture-key signatures and says nothing about hardware owner presence. The record by itself supplies no separately verifiable owner signature.

### Witness protocol

1. Preflight A and B. Record independently installed disposable agents on two physical hosts, their distinct identities and origins, independent homes, active compatible send/receive gates, approved synthetic owner and restricted devices, the complete two-machine enrolled writer roster and the known baseline binding and unchecked item. Confirm there is no production process, third writer, shared disk, proxy, tunnel repair path or another source alias that could serve or modify this fixture across the isolation boundary. Verify that B can authenticate the intended owner and produce the baseline through the shipped Work route before isolation. If any preflight proof is absent, mark the qualification unavailable before the tap. Keep both homes frozen against unrelated writes to the fixture. Allow the native owner checkout and test-device authority procedures required by the case.
2. The owner-device simulator invokes the regular Work action on A using its enrolled keys and the server-issued exact presence challenge and obtains its ordinary success result. Record which native origin occurrence represents that tap. Bind the journal envelope origin, kind, sequence, record key and hybrid logical clock (HLC) and the stream metadata incarnation to the exact payload. The ChiefOfStaffStore owner-item-check payload fields are conversationKey, bindingHlc, itemId, itemChecked, checkRef and askId, which is the tap nonce in buildOwnerItemCheckEvent. Compare the complete canonical occurrence privately, including record type, event, actor classification, timestamp and app-device message reference. The action response does not expose askId. Establish it from the unique new journal event in the isolated action window. Read incarnation from the origin stream and B peer sidecar. If the installed version lacks any required positive binding, fail preflight. The origin occurrence must be unique across the fixture action window. If safe mapping of the action to exactly one occurrence fails, stop the positive case. The simulator’s native response and A's own journal are local evidence.
3. Observe B's native receive path independently of the HTTP response from A. The [signed journal pull](../../src/core/PeerPresencePuller.ts#L270) feeds the [receive applier](../../src/core/JournalSyncApplier.ts#L498). Its [replica append](../../src/core/JournalSyncApplier.ts#L848) calls fdatasync before reporting the record as applied. Establish the exact origin occurrence by matching B's persisted record, including the origin stream and incarnation, sequence and action fields, against the source and received frontier. Confirm origin, kind, incarnation and a contiguous applicable receive interval, with its retained lower bound, independently pinned pre-tap and final isolated source heads, and per-kind receiver head. Examine explicit gaps and quarantine. A latest lastHeldSeq or later clean batch does not prove an earlier compacted gap closed. Require complete head coverage to assert absence or no newer action. An exact persisted event can establish positive historical custody even if other history is incomplete. Use read-only observer access in the test homes. A missing or quarantined target occurrence, wrong incarnation, unreadable evidence needed to bind the exact target or unavailable receive evidence makes exact receipt unproven. Other gaps defeat only assertions whose required interval intersects those gaps.
4. End A's ability to participate in serving or repair. Stop it and block its network path to B and the client for the positive case. Confirm A is unreachable across each serving and repair path, then cold-restart B before the first positive request. Record B process epoch and request destination or response machine identity. Run the client directly against B, bypassing caches or proxies that could use A. Keep A unreachable until all positive and negative reads complete. Open B's ordinary mobile Work Projects view with the current owner device. Verify the owner HTTP evidence from `GET /mobile/work/projects`, [owner view](../../src/server/workProjectsRoutes.ts#L373), and the rendered checked item. The [native fold](../../src/core/ChiefOfStaffStore.ts#L630) applies the item fingerprint and later authoritative events. The ordinary projection's [bounded loadUnion](../../src/commands/server.ts#L31810), wired at [server.ts](../../src/commands/server.ts#L31990), and independent durable receive comparator are different checks. Do not use the result or the create-path complete union to certify the receive frontier. Require the current binding and item to match the expected fields and the qualified observation to account for any relevant newer check, uncheck or reopen. A later edit or ended scope can leave the older positive record historical. Unknown coverage leaves the projection unproven. Do not infer a missing record from omission in a filtered view.
5. Use a fresh fixture in the immediate-isolation case. Pin A's pre-tap head. Isolate A when it returns native success, before replication verification or repair. Keeping it stopped and isolated, inspect A's disconnected test home read-only and identify the exact occurrence against the pre-tap head, then use it as the comparison target against a pinned read-only B receive snapshot. Record the order of native response, isolation and B cutoff. If ordering evidence is incomplete, state only that B held the event by the observed cutoff. Do not infer receipt at acknowledgment. Without an exact A occurrence, report the comparison unproven even if B shows a checked item. A visible exact replica is a positive replication observation only. An exhaustive read of B's pinned replica and interval actually retained at the cutoff can establish that the exact occurrence was absent from B's inspected local storage, even when B received only through the preceding sequence. A gap, unreadable segment, ambiguous retention or incomplete inspection leaves that local absence unproven. Neither assertion says what B held at A's acknowledgment. That case does not require or imply another writer, an acknowledgment barrier, or recovery of an idempotent mutation response.

Each case records a start, an outcome and a summary of which assertions were observed. Allowed assertion outcome labels are observed, unproven, unavailable, denied and failed. A forbidden disclosure is failed. An overall observed qualification requires independently durable receipt, isolation, cold authorized projection and both negative controls. Record which aliased credential and gate each outcome tested. Preserve exact matching internally while publishing only fixture aliases, controlled reasons, timestamps and independently verified evidence boundaries. One record can establish this one observed case only. Multiple homes on one machine, mocked transport, bypassed or mocked presence verification, file copies and fixture writes directly to a journal can check procedure logic or input validation. They cannot qualify the real two-machine case.

### Authorization during isolation

Read only via the installed authenticated mobile Work path. Test an active owner, an enrolled restricted member or guest and a previously authorized fixture phone whose revocation B's current authority has observed. Use fresh native signed-device requests and verify B’s current authority and relevant source state. Record the ordered positive trace: exact target occurrence on B, valid pre-revocation read by the soon-to-be-revoked device, held-here revocation on B, verified A isolation, B cold restart, first current-owner fixture read, two negative reads and final current-owner fixture read. Do not issue the first post-restart request until B’s required state is verified without reading the fixture content. First require a signed GET from that exact active fixture phone returning the item from B. Revoke that fixture phone on B through the existing POST /mobile/devices/:id/revoke route and require native held-here completion. Reject pending or forwarded outcomes. Bind its prior successful read, revocation record, B registry state after boot and post-restart denial to the same device. Use a distinct authorized owner-device simulator identity for the later positive checks. First record an authorized owner GET containing the exact fixture from the cold B process, immediately issue both negative requests against the same process, and repeat the successful owner request. Avoid client caches and keep the fixture fixed. An unrelated signature, bearer fallback, rotated token without native revocation evidence, expired request or wrong scope cannot substitute for the requested revoke check. Require B to authenticate the intended restricted fixture principal and evaluate its current role for that fresh request. Then require denial or an empty response. For both negative devices inspect the entire response, including error fields and nested or partial data. No project or item metadata may appear. Require the formerly authorized device denial to be attributable to B’s observed matching revocation, using the native proof rather than status alone. Record the tested credential alias and gate. An empty response without evidence of the role evaluation is unproven. If B cannot verify the fixture's current authority without A, close the canary output with unavailable and omit item values and identified rows. An old durable replica is never authorization to expose content from an excluded role. Do not claim disconnected authority propagation, project-audience invalidation on all compatibility routes, or mid-request safety from this approved scope. Check read prerequisites before making a content-bearing request. Score both requested negatives on what the route actually returned. A forbidden response is failed even if the collector suppresses it. The existing normal read checks role before an owner cache. The action response's [fresh row builder](../../src/server/workProjectsRoutes.ts#L411) relies on earlier action verification, so it is excluded from the isolated revocation proof.

### Cutover and change-control boundary

The witnessed native carrier proves a replicated historical item event within the specified boundary. It cannot certify a canonical accepted revision, project successor choice, attempt generation, durable authority seal, unanimous installation witnesses, shared delivery before acknowledgment or exact mutation retry recovery. The sole recorded holder loss neither elects B nor changes its permissions. Keep the current writer layout. Do not put a project mutation, pointer write, admission change, automated advice or repair action behind this evidence.

The parent spec still needs an ordinary-edit seal and a mutually exclusive abort before changing writers. An ordinary edit must bind the current actor authorization, predecessor, candidate and attempt in the transaction that makes the choice irrevocable. A close additionally needs the parent spec's exact checklist and evidence validity. A timeout, missing peer or newer lease does not show the old attempt never sealed. The original enrolled members must durably retire the attempt, or a separately enrolled loss proof must account for the earlier seal and acceptance head and fence every capability that could revive it. Without either proof, hold cutover. Existing [graph-specific recovery](../../src/core/GraphWitnessService.ts#L491) is a comparison, not a project seal or loss authority. It checks a witnessed prior head, source manifest and current fence. [Graph adoption](../../src/core/GraphWitnessService.ts#L361) revalidates an exact known operation and keeps certified operations on the redistribution path. Existing journal receive, local file replacement and SQLite commit offer no equivalent shared project acceptance by themselves.

## Decision points touched

- Fixture and read access — invariant; basis: irreversible-consequence; evidence: current native owner proof and checked item authorization delimit use of synthetic data. Unverified authority closes disclosure.
- Independent replica witness — invariant; basis: enumerable-domain; evidence: the precise origin, action identity, durable local receive, isolation and cold read can each be checked. Missing evidence leaves that claim unproven.
- Accepted revision and cutover — invariant; basis: irreversible-consequence; evidence: the result supplies no authority-bearing fact to promotion or writer admission. The parent contract remains independently gated.

## Maturation plan

- **test-agent-live:** Exercise the procedure with synthetic records in disposable homes. Verify wrong origin and incarnation, missing and stale rows, no safe preflight, cold restart, current owner and restricted/invalidated read proofs, and safe unproven outcomes. Confirm no new runtime write or capability.
- **dev-agent-live:** Qualify on the separate Studio and Mini disposable installations with independent durable storage, real mesh transport and native challenge checks using fixture simulator keys. Run the positive case and the separate immediate-isolation case. Record exact mechanisms and coverage for both. If the machine pair or fixture-device proof is unavailable, leave physical survivability pending. Record real-phone device presence as a separate acceptance result, unavailable until genuinely exercised. A simulator result does not satisfy that acceptance.
- **fleet:** Publish the redacted evidence for review. No fleet behavior or feature flag changes.
- **graduation criterion:** Obtain an independently reviewed real two-machine artifact for the native exact event, replica durability, holder isolation, cold authorized read, and passing restricted and separately revoked read outcomes. If either negative assertion or revocation evidence is unavailable, qualification remains pending. Include the immediate-isolation probe result in the same reviewed artifact, even when its receive frontier is unknown. That probe does not itself confer a shared acknowledgment guarantee. Parent #3753 closure, writer promotion and cutover require separate evidence.
- **dark-window:** The qualification runs only in authorized synthetic environments and only while the existing capabilities and required access checks are available.
