# B2 — Give each project one record and a recoverable history

Instar can currently show different project lists in Projects and Chief of Staff. A verified Chief of Staff closure can also survive even when its status mirror is behind. B2 makes the project record authoritative once the migration can preserve that history and the acknowledged record can survive a holder loss. It follows [A1's authority, disclosure and recovery contract](canonical-records-and-work-discovery.md).

B2 covers the existing project roster, project lifecycle and checklist writes, source migration, custody and read clients. It changes no job definitions, scheduler authority, job discovery, standing-mode defaults, or automatic continuation and dispatch policy. An approved active session retains its ordinary execution path. Turn-end continuation, project-wide cumulative continuation budgets, and any new admission or dispatch authority require their own reviewed design, including A2 where applicable.

## Frontloaded decisions

1. One canonical project owner accepts all project writes, including automatic deterministic closure. Chief of Staff keeps separate supervision evidence.
2. Protect revision, choice, installed acceptance proof, and mutation result under the enrolled custody contract. Local staging and proof that every authorized member can recover the accepted revision are distinct outcomes. Only the latter permits the new revision to serve as the current shared record.
3. The pilot is opt-in and covers a single authorized project custody domain. A kind-wide pointer can publish only when all enrolled projects and physical writers share a compatible verified member set and policy. Mixed physical namespaces stay at read-only inventory.
4. A time-bound closure needs live authority when it receives an irrevocable close seal. Earlier candidate votes do not prolong a lease. If authority lapses first, a different candidate needs durable proof that the old attempt never sealed and cannot seal or become accepted.
5. Existing job and dispatch boundaries remain unchanged. Graduation requires a positive canonical write on the development agent after isolated two-machine and authorization proof.

## Canonical record and entry points

The InitiativeTracker project service owns the verified project ID, project mode and goal, phase/status, owner and audience, checklist head, item definitions and authorization, accepted status/check evidence, authorized conversation links, and idempotent results for existing project mutations. TaskFlow SQLite is the target materialization when its adapter can prove the custody contract below. The authoritative accepted revision and cutover pointer, rather than a TaskFlow row or a Chief of Staff binding, establish current state after publication. No fallback owner or second writable store activates automatically.

Keep Chief of Staff supervision records for conversation intent, cadence, check verdicts, notes and historical actions. A supervision record may reference a canonical project or exist on its own. PlanDoc creation and current Project/Work mutations use the project service. A Chief of Staff binding updates supervision only after cutover, and an authorized existing project-affecting tap calls the canonical project service with project ID, current checklist/item revision and stable source occurrence. A verified conversation link does not independently authorize a mutation. Every paired Chief of Staff evidence check, restart, redirect and project-status note resolves the current canonical goal and checklist immediately before it builds its input. Cadence, parking evidence and previous supervision observations still come from Chief of Staff. Record exact canonical goal revision, checklist revision and evidence input revision with each classification, verdict and evidence-hash cache key. Carry those revisions into the ordinary action check. A goal or checklist change invalidates the verdict and its cached evidence match, even when the new instructions could be rendered from the current goal. Replay the applicable evidence under the new canonical revisions and obtain a new verdict before considering action. At spawn, restart or redirect ingress recheck those exact validated heads, current authority and the reason the chosen action still follows. A changed input holds the old action and forces a new observation and judgment or no action. Test a goal edit after judgment but before ingress where existing work satisfies the new goal. No redirect or restart occurs from the invalidated verdict. If no authorized canonical head is available, retain the supervision evidence and hold project-directed advice or action. A binding's older goal or checklist never becomes a fallback. The supervision-only case may still use its own active binding.

The existing deterministic close in ChiefOfStaffLoop's ordinary check cycle uses the same canonical service for a paired project. A `done-verified` check is evidence. The close command carries the observed project and checklist revision, exact passed item evidence, verified binding and check occurrence, existing operator lease and initiating authority. Derive its idempotency key from that occurrence and canonical close operation, independent of the presentation route. Preserve automatic closure only where the existing owner explicitly empowered the host to close this project from its exact deterministic checklist under the current lease and stated evidence policy. A check or verdict supplies evidence without creating that delegation. Honor each checklist item's own permission. An existing `agent-may-certify` item may accept verified assessment by its authorized agent for the exact item and checklist revision, using the evidence and evaluator established by that source contract. A declaration without verifiable delegation, evidence, or a working enrolled evaluator remains unverified. An owner-confirmed item still requires its own authorized owner confirmation. Certifying any item, including the last one, does not confer authority to close the project. A separate already verified close delegation may apply after all required items and evidence validate. A changed goal, new consequential owner judgment or missing close delegation uses the existing owner confirmation path. A mixed checklist test has a qualifying delegated item and an owner-confirmed item. Verify only the former can be certified by the approved agent and the host does not infer permission to close. The project owner validates exact checklist, delegated authority and independently verified evidence validity again at sealing. An edit or lease expiry before the irrevocable close seal described below prevents closure and preserves the check evidence. Chief of Staff can still verify or close conversation-only supervision under its separate contract. For a project it can say finished only after canonical acceptance. Neither an automatic result note nor a legacy status mirror can create a separate project closure.

Projects, Work and Chief of Staff render authorized subsets of one canonical project roster and document their inclusion rules. A project-only row keeps its ID and optional conversation links. A verified pair keeps its project ID and separate supervision ID. A conversation-only row is labeled supervision and has no invented project identity. Ordinary cards or auto-registered specs cannot instantiate projects. Preserve caller permissions at every write and read, including derived status, counts and evidence links. Show last accepted data as stale or unavailable when its current scope cannot be proven. Do not expose new pending goals or audience metadata across authorization boundaries.

## Deterministic source mapping

Inventory InitiativeTracker legacy JSON or TaskFlow, and the Chief of Staff journal, with exact revisions, source scopes, and covered intervals. Before final fence this is a preview only. A project ID or a source-verified alias can establish a join. A title or similar text cannot. Retain originals unmodified, including lifecycle events and legitimate unpaired supervision. A verifiable project-only row does not require a fabricated binding. For projects with multiple bindings, gather all joined source records before deciding an outcome.

1. Fold one conversation's binding and lifecycle under the current ChiefOfStaffStore rules. A hybrid logical clock (HLC) is the source's version stamp combining a clock reading, sequence and machine tie-breaker. Preserve the winning binding HLC, event HLC, lifecycle action, actor authorization, and winning state's native evidence. The HLC orders records within their valid source fold. It confers no authority to choose conflicting goals or closures across bindings.
2. Map each checklist item from the exact tuple of source conversation, winning binding revision and original item ID. Preserve original item text, goal, verification rule and delegation authority whether or not any check occurred. The existing owner-item check reference is a digest of goal, item ID and item text. Attach it and any verified check occurrence as evidence when present. They do not define the item or confer target authorization. A newly confirmed checklist migrated before its first tick has every item and no invented evidence. Its unchecked items remain unverified. Each canonical item has a stable ID and current revision. Bind migrated evidence and future approval to its exact target item/checklist revision and separately verified actor authority. Merge equivalent evidence only after matching goal, current checklist semantics, source item identity or explicit owner-verified equivalence, and compatible delegation; otherwise retain both as separate evidence with the unresolved choice. Record reproducible native-to-canonical mappings for retriable migration.
3. Where one source-proven, authorized and current closure applies, preserve it even if the InitiativeTracker status mirror did not update. A later authorized reopen under the source fold or a superseding checklist revision makes the earlier closure historical. Evidence supporting an old goal cannot satisfy the new one. Two bindings with conflicting valid goal, checklist, delegated authority or lifecycle outcomes preserve both and hold project cutover for the owner. Do not use last timestamp, whichever store answered first, or permissive merge to turn that conflict into a verified completion. Missing source coverage is a gap, distinct from a conflict.
4. The accountable human owner resolves disputed identity, authority and lifecycle choices that could change a record. A reversible decision to keep distinct records separate can remain as an evidence-backed default without asking for a new approval. The project service records the selected mapping, supporting original evidence, owner and observed version. Before seeking a decision, the migration worker prioritizes authorized original evidence that could settle the discrepancy, including binding and checklist revisions, lifecycle ancestry and verified aliases. Use the existing source deadlines and lease/interactive resource ceilings for each read. An incomplete batch schedules bounded retry of unsettled evidence or a read from another authorized retained source. It does not turn an arbitrary scan cutoff or transient read failure into a question for the owner. After retry and replay are exhausted, retain the provisional records and report the coverage gap. Request an owner decision only when source evidence establishes a genuine conflicting or missing authority decision that the owner can resolve. A later effective revision must be revalidated before the choice can publish. Reordering equivalent source events or retrying the converter has the same result. Verify final mapping by semantic state and exact evidence refs, not just total rows.

## Accepted revision and custody

Use the existing authenticated replicated-record transport only when the installed project adapter proves the record, membership, selection and durability protocol end to end. Existing TaskFlow SQLite by itself and last-writer-wins folding are insufficient for this claim. The stored project snapshot covers the full authorized revision, checklist and status, ownership/audience attributes, references and exact mutation result keys. A record carries agent/project scope, project generation, authoritative predecessor/head, revision digest, enrolled holder/authority epoch, current signed membership epoch, active attempt generation, immutable mutation identity and a projection checkpoint or full data sufficient to rebuild local reads.

For a pooled project, the signed current membership identifies every installed member authorized for the project custody scope. Independent failure-domain durability is required when that set has more than one member. A member without permission receives no protected state. The following sequence is required for a shared acceptance.

1. The current owner stages one candidate against the proven presently accepted predecessor. Before requesting the first choice, it verifies and binds the exact mutation, source occurrence and actor authority to the candidate. For a time-limited operation this includes the exact current operator lease, project/checklist head and bound expiry. Staging or signing a choice never extends that lease. Each current authorized member verifies scope, parent, policy, epoch and candidate, then durably stores the complete recoverable candidate and its signed choice before acknowledging. Derive the candidate digest from the canonical payload, predecessor, mutation ID and active attempt generation. A choice covers agent/project generation, membership and holder epochs, predecessor, attempt generation, candidate digest, mutation ID and bound authorization. Every seal, choice/install certificate, receipt, abort, delivery witness and recovery/replay operation carries and verifies that same attempt generation. Persist the authenticated active and retired generation fence before allowing new votes. Retrying within an attempt reuses its identity. Reusing a mutation ID and otherwise identical payload after a valid abort must use the new generation and candidate digest. Old choices, receipts, or credentials cannot count toward the new attempt or reopen the retired one.
2. The member durably chooses at most one successor for that predecessor in the active attempt, including across restart and incoming holder changes. An owner retry may collect the same candidate's receipts. A higher lease, clock reading or membership version cannot erase a choice. Persist choice and head checks under the same local serialization/durability boundary. The complete choice certificate contains every currently enrolled authorized member's choice for the exact candidate. Before that certificate can authorize a Chief of Staff close, the current owner under the existing close and lease serializer must durably seal it while the original bound checklist, principal and lease still authorize that close. Bind each supporting item's verifier, source revision, observation time and applicable source freshness or revalidation rule to the candidate. Each enrolled evidence rule declares whether it proves an immutable fact, attests to an observation sufficient for an explicitly authorized validity interval, or requires a live condition guaranteed through sealing. The source owner defines which form it can actually attest to under its existing verification and budget. Immutable proof still requires correct artifact revision and current authorized use. Interval proof carries source-authenticated observation and valid-until bounds tied to source authority and any invalidation rules; the enrolled closure policy explicitly accepts that kind of historical observation for the duration. The seal must fall inside all applicable intervals and confirm any required revision, rescission and access checks. A new HTTP read, cache TTL or prompt confidence alone cannot promise a remote page or mutable status stays valid through sealing. If the owner policy requires a live condition, require a source-pinned revision, reservation or equivalent authoritative guarantee that remains enforceable through the entire seal transaction, not a sequence of fresh reads. A source that cannot supply the required form is unknown for automatic closure and leaves the evidence pending for existing authorized review. An expired, withdrawn, unavailable or changed positive check cannot be sealed by a live operator lease alone. Test an unpinned source changing after its final read and before seal, plus an independently approved interval observation that remains sufficient. If reevaluation produces different evidence that cannot be verified under the bound evidence revision, record it separately and use the old-attempt resolution protocol before a new candidate. The seal binds the complete choice certificate digest, the verified evidence references and admitted operation. The enrolled carrier must provide recoverable evidence of this authorization before any member can install that choice certificate as eligible for acceptance. Recovery may distribute an already valid seal for the same operation and cannot invent or backdate it. A newly renewed lease does not retroactively repair the expired attempt.
3. If policy, checklist or lease becomes stale before the irrevocable seal, no member can install it as accepted. Recover any prior seal/acceptance proof before aborting. For that same predecessor, the original enrolled authorized membership must durably attest that no member has observed a valid seal or accepted proof and irrevocably close the old attempt before acknowledging an abort choice. A member that could still accept or serve the old attempt cannot attest abort. A unanimous signed abort certificate installed under the same custody and authorization contract is the ordinary proof when all original authorized members remain reachable. After member loss, the independently authorized membership/recovery path may use another already supported mechanical proof only if it verifies the full prior authoritative seal-and-acceptance head, positively proves the exact attempt never sealed and could never have accepted, and durably fences every legacy capability that could seal or revive it. Record that proof and its authenticated new generation before admitting another candidate. Mere absence from an accessible peer, stale lease, member removal or incomplete history does not satisfy this test. It retains prior choices and advances the attempt generation; it does not advance accepted project state. Only then can a new unrelated edit compete for the predecessor. When neither the ordinary abort nor the proven recovery path is available, retain the last accepted view and keep the next mutation pending or refused. Membership changes never waive old-attempt safety. Test a lease expiring after the first choice, then an ordinary edit before and after safe abort across restart. Also replay the same mutation ID and payload under the new attempt generation. Deliver a former choice or install receipt late and verify it cannot vote, seal or change the new attempt.
4. Each member verifies the assembled choice certificate and its required authority seal, durably installs it with the full revision, and signs a choice-certificate installation receipt. The accepted proof is this certificate plus all signed choice installation receipts. A member stages the complete accepted proof and its idempotent mutation result durably. That installs local custody without advancing the publicly readable current project head. Keep the staged revision unavailable to ordinary Project, Work and Chief of Staff reads and all notes/redirects until the same member can prove shared delivery completion, current membership/authority, and the applicable accepted cutover pointer or prior canonical authority epoch. Each member then signs a separate accepted-proof installation witness over exact accepted proof and result digest, membership and durable generation. Shared success is verifiable only from all those witnesses, or fresh authenticated confirmations from all bound members of their persisted copies. Before returning shared success, the owner distributes the complete witness set durably to every enrolled member alongside the accepted proof. The carrier's recoverable delivery-completion records must positively show each member installed the exact complete set and mutation result. A first response and every matching retry apply this same test. A collected set held by one coordinator, a record that sends were queued, or the earlier choice install receipts never establish complete distribution. Use the existing Conversations delivery-completion proof as an architectural precedent only. The project adapter must independently prove durable collection, distribution and holder-loss reconstruction for its scope. Before a successful response, the completion proof must be independently recoverable from every enrolled member even with the holder gone. Acceptance of that proof attests to installation of the witness set and result, rather than creating another mutation or a chain of new accepted revisions. A survivor lacking complete shared delivery, membership or applicable authority pointer proof serves only the previous authorized shared accepted revision labeled stale, or unavailable when prior current access cannot be proven. A matching mutation retry reports pending/unknown shared acknowledgement until it can verify the same all-member delivery completion, even if it holds the complete witness set. Once that proof is recoverable, the same retry returns the reconstituted accepted result without another mutation. Under verified one-member membership, this establishes local acceptance and explicitly no independent recovery copy.
5. On holder or membership transition, recover prior accepted head, choices, seal or abort proof, and any reconstructible installation receipts and witnesses before new writes. Finish the same accepted or safely completable authorized attempt. Conflicting choices or missing proof do not select a later revision. They preserve staged states and hold shared writes. The enrolled carrier must meet each of these boundaries on current installed machines, or custody migration stays at read-only shadow.

Before shared delivery completion and current authority proof, the requester may receive a receipt with pending/retry status for this same write. This is an operation status and may not disclose new project state. Authorized readers keep the previous certified head with visible freshness or unavailable coverage. An offline member in the still-enrolled authorized set blocks shared acceptance. Never acknowledge success before proof becomes recoverable from each enrolled member without the holder. Current permissions and erasure still apply to recovered revisions. An excluded member loses current write and serving authority and cannot use old local materialization to answer as current. Use existing verified roster transition and erasure policy, with an explicit safe stop if those cannot guarantee this contract.

## Cutover and recovery

Ship the inventory and compatibility readers first. Keep the current project writers and authority unchanged while census, mapping, source parity or carrier proof is incomplete. Do not launch a second TaskFlow writer. Enroll compatible writer ingress and create a read-only shadow materialization from reviewed mappings.

Use an exclusive project-kind cutover admission held by the InitiativeTracker project owner. Its authoritative state and fence generation are committed as a dedicated cutover record in the enrolled project-authority journal, on the same authenticated custody and durable-choice path as project revisions. A local TaskFlow flag or shadow file cannot publish authority. This is the proposed acceptance boundary, not a claim that the current carrier provides it. The owner holds the cutover admission from the final source drain through verified pointer CAS. Each supported write ingress acquires that admission or a shared writer permit under the same current epoch. Once drained, the physical boundaries are:

- InitiativeTracker's legacy `initiatives.json` replace. Quiesce any process that can replace the shared file outside the epoch contract. Hold shared physical file writes until a single serializer can preserve both the project records and other initiatives. Keep backups and prove no unadmitted process can touch the active file during the fence.
- TaskFlow's existing `withWriteTransaction` (`BEGIN IMMEDIATE`). The project adapter checks the current cutover phase and writer permit at the transaction boundary; unrelated TaskFlow writes may continue only where the physical transaction provides isolation from project rows and the target head. A shadow target update is not a canonical project mutation. Quiesce direct or older writers that do not participate.
- Chief of Staff's replicated `chief-of-staff-record` emitter for binding/lifecycle mutations and the current automatic/tap close and InitiativeTracker mirror paths. Gate these project-affecting paths with the same admission and drain queued old actions. Notes/checks and standalone conversation supervision may continue only when the final source boundary proves they cannot rewrite the protected project fold or mapping. Otherwise pause the relevant shared writer for the drain.

Prove all old writer processes/adapters, cached callbacks and replay paths are fenced, or hold publication. Separate physical source and target stores may be kept stable by quiescence and verified heads under this durable admission, not by treating SQLite's transaction as a lock on the other stores.

Record the final source high-water and prove all accepted old mutations through it. Read a stable target head and verify exact ID, owner, checklist, goal, status, and evidence correspondence, including unresolved holds. Use the A1 authenticated cutover receipt and compare-and-swap publication. Initially allow kind-wide publication only when one independently verified common custody policy and the same authorized installed-member set cover every affected project in the physical source and target. Validate that compatible scope at every later project create, import, ownership or audience change, and when an adapter or membership epoch changes. Reject an incompatible new project or widened audience before staging payload or replicating anything. It can remain an authorized, unaccepted proposal in its original source if policy permits, without establishing another writable roster. A revocation, narrower audience or member exclusion never waits for the common custody contract to recover. Immediately withhold affected content, invalidate derived records and serving proofs at the governing authorization epoch, and enforce current access on every read even when it requires returning unavailable. Suspend further project writes affecting the incompatible domain until a reviewed custody change or compatible re-enrollment proves safe. A historical accepted proof cannot restore withdrawn access, drive another send, or justify replication to a now-ineligible member. The operator authorizes this opt-in scope before final fencing. A shared file containing mixed membership or incompatible disclosure policy remains on the old authority with read-only inventory and authorized reporting. No fallback pointer, forced roster widening or per-project option can bypass a physical shared writer. Future mixed-domain support requires a separately reviewed partitioned storage and commit design.

Publish a signed `project-authority-cutover` record under the existing enrolled journal authority and the complete acceptance proof above. The pointer carries only agent-scoped authority selector, previous pointer, fence epoch, verified custody-policy and membership digests, and an opaque commitment to the exact migration receipts. Project IDs, target heads, checklist text, counts, source cursors and original evidence stay in scope-authorized migration receipts. The common domain's authorized custody members verify the complete receipt set and the pointer commitment before accepting publication. A project reader or unauthorized member does not receive the physical manifest or other project metadata. Lost holder recovery verifies the locally persisted pointer, receipt proof and authorization before choosing either source. The irrevocable cutover point is durable, recoverable sealing of the verified publication candidate under the current fence, before any member can install pointer acceptance. From that moment the legacy writer permits remain permanently retired. Full accepted pointer and its shared delivery-completion proof authorize the canonical writer; the seal or one member's local acceptance alone does not. During partial installation, loss of the holder or lack of complete current publication proof, reject writes on both authority paths as retryable and serve the last authorized verified view with truthful coverage. Recovery must complete the same sealed pointer or remain fenced. Before the seal, reopen legacy writers only after a positively proven durable abort closes the exact publication attempt, verifies prior authority and unchanged source head, and excludes any competing recoverable publication seal. Lack of a complete pointer on one peer never proves abort. Readers discover the sealed/accepted/aborted pointer state from their verified local authority journal or an authorized current owner. With identical shadow bytes on two machines, only valid pointer proof establishes cutover. A survivor missing the proof serves the verified prior view with stale or unavailable authority as applicable and refuses promotions. If the installed carrier cannot prove the durable cutover choice, installation receipts, local pointer discovery and predecessor recovery, stop at shadow inventory with the old authority intact. An unresolved project conflict holds promotion wherever current physical writers cannot safely isolate the project. No per-project authority fallback on a whole-file writer. Before the irrevocable seal, a positively proven reversible abort resumes the original current authority without losing late writes. After that seal, a recovery or presentation change cannot release legacy writers. After publication, compatibility routes write through the current owner. Presentation rollback may read authorized canonical state through the old client shape. It cannot reactivate old project writers. Persist an interrupted-cutover outcome so restart follows the authority pointer rather than guessing from files. A reverse authority migration must preserve every later accepted mutation.

The production two-machine test uses separately staged homes and distinct durable stores. Enroll both machines for the same project. From the normal write surface, change an owner/checklist/status revision and obtain a verified accepted response. Immediately terminate and isolate the original holder before any additional copy or repair. With the old holder unreachable, the survivor uses its own verified record and certificate to return the exact accepted revision, checklist evidence and idempotent result through the normal authorized project views. It may read the accepted state while it lacks the old membership's proof for a new write. Prove mutation remains pending or refused until a separately authorized membership transition verifies predecessor, current custody and fence. Then test an authorized successor write and a stale old holder return. Inject crashes after staging, after incomplete votes, after one member installs the choice certificate while another has not, and after only one member installs complete accepted proof. Isolate the holder before shared witnesses distribute. The survivor with only an installed local proof cannot expose the staged revision in any normal read, recommendation or note. It serves only the previously authorized certified head with incomplete coverage, or unavailable. A retry stays pending when final-installation and shared-delivery proof are absent. Compare both reads and retry outcome. Also crash the holder after it collects all installation witnesses but before the set is installed at its peer. Restart the holder with the peer offline and require the same pending result from original and retry paths, then complete distribution when the peer returns. Repeat with holder isolation immediately after shared success and verify the idempotent result from locally recoverable completed distribution proof. Run a mixed-membership shared legacy file on two machines and prove publication is held without moving either writer or disclosing the protected project to the other roster. After a successful cutover, attempt an incompatible project create and import, a widening audience change, and a revocation that makes the domain incompatible. Verify no inadmissible payload is staged or replicated. Ordinary owner/member/guest revocation tests verify stale locally installed proofs, views, histories and compatibility paths cannot expose a project after the source audience epoch changes, even when the authority is disconnected or further writes are held. Repeat holder isolation immediately before and immediately after accepted cutover pointer publication with identical shadow data. Neither survivor decides from the shadow alone. Only the authenticated locally recoverable publication can establish the new authority, or the survivor reports authority unavailable. Crash after exactly one member installs the pointer's accepted proof. Restart both roles separately with the other unavailable, issue ordinary writes through both compatibility and canonical routes, and verify all legacy writers stay fenced and no canonical writer starts without verified shared proof. Recover the original sealed pointer and prove one canonical acceptance after distribution. Replay the same mutation ID and test competing candidates for one predecessor, including a paused holder's attempted write after transfer. Show exactly one accepted head and truthful pending outcomes.

## Decision points touched

- Existing source identity, checklist and lifecycle validity — invariant; basis: irreversible-consequence; evidence: mismapping a checklist item or actor can create a verified closure the owner never approved. Verify source revision, goal, actor and exact item binding before applying its evidence.
- Conflicting identity, goal or lifecycle evidence — judgment-candidate. The accountable owner can verify one source mapping, retain distinct records, or hold for evidence. The project service accepts only a current scoped choice. On uncertainty retain both originals and do not promote the affected writer.
- One durable choice and one accepted head — invariant; basis: irreversible-consequence; evidence: a second successor for one predecessor can lose acknowledged project state or duplicate an existing project mutation. Each member chooses once under the current authorized lineage. Require complete certificate and local proof before shared success.
- Access, writer fence and cutover — invariant; basis: irreversible-consequence; evidence: a stale owner or a leaked checkpoint can create conflicting state or disclose private project evidence. Verify both source and destination scope, authority and migration heads and enforce closed rollback behavior.

## Multi-machine posture

Project custody uses the existing authenticated replica transport with the exact enrolled authority/verification adapter above. It stays inactive where the adapter cannot retain full state, recover durable choices and certify the set. A local materialization or derived roster is rebuildable from accepted evidence. The installed holder remains the only write owner, and all allowed readers see the last accepted scoped state or an explicit stale/unavailable gap. The project-scope member set and cutoff are independently authorized. The first release is limited to explicitly opted-in configurations with one common compatible project custody domain across the affected physical writers. B2 changes no job or conversation graph custody protocol.
