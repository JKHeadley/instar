# Codex device-limit tripwire

## Problem

On 2026-10-31 OpenAI published "Understanding card and device limits in ChatGPT": one device can use only a limited number of paid personal accounts (Go, Plus, Pro 100/200/500). Past the limit the user sees **"Device limit reached"** at sign-in, or is signed out later even after a successful purchase. Signing out of another account does not free a slot. Business, Enterprise, Edu and Free accounts do not count. The number is not published (one unverified report says 2), and neither is the exact wording of every surface.

Echo runs 5 personal Codex accounts on each of 3 machines (Mama PC, Mac Studio, Mac Mini). All 15 cells were signed in and reading quota at 2026-10-31 13:31 PDT. The operator chose to keep that layout and add detection (topic 134294, 13:39 PDT), and asked that the detection not be a brittle string match but use Jev (13:47 PDT).

Today a device-limit lockout would be handled badly in three places:

1. **Quota poll.** `codexLiveRateLimitReader` throws away the app-server's error text (`:216-225`). A device-limit refusal becomes `auth-failed` (if its message matches the auth regex) or `unavailable`. `auth-failed` plus a signed-out `codex login status` on two polls marks the account `needs-reauth` with cause `cli-signed-out-auth-refused`, which is **actionable**, so the sign-in repair starts.
2. **Running sessions.** Codex sessions have no pane watcher (`SessionManager.ts:2968` gates the login-expired detector to `claude-code`). A session stuck on a device-limit screen sits there.
3. **Sign-in repair.** No page class or helper hard line describes a device-limit page. The CDP driver classifies it `unknown`; the agent-session helper ends `agent-sign-in-unfinished`, which **is on the slow-retry allowlist**. Each retry meets the same wall: up to 12 drives per incident per cell, against a provider that has just told us we are over a limit, which can read as abuse.

## Proposed design

### 0. Shape: two actions, two evidence bars

| Action | What it does | How it undoes itself | Evidence required |
|---|---|---|---|
| **Stop one repair** | Ends one sign-in repair episode `failed` / `device-limit` (terminal, never slow-retried, no per-episode notice, does not count as a helper hard line) | The next incident starts a fresh repair as today; unattended mode is untouched | One judge verdict `device_limit` on a sign-in page, or the helper LLM's `device-limit` report |
| **Bench an account on a machine** | Persisted `statusCause: 'codex-device-limit'` on that machine's pool record: not placed, not a swap target, repair refused, sessions moved off | Two clean live reads (§6), or the operator (§6) | **Two separate app-server refusals** of `account/rateLimits/read`, 5–60 min apart, each freshly judged `device_limit`, plus the machine floor (§4) |

Screen text and pages never bench an account; they can only start a fresh provider read or stop the repair they were seen in.

### 1. The judge: `CodexDeviceLimitJudge` (Jev first, Luna referee)

New module `src/core/CodexDeviceLimitJudge.ts`, built on the existing pattern (`MachineLoadAssessor`, `JevCascade`). It holds no authority; §4 decides what a verdict does.

- **Input:** one text snippet plus its `source` (`read-refusal` | `initialize-error` | `login-status` | `sign-in-page`), the account id and this machine id. Preparation, in order: take only the JSON-RPC `error.message` (and `error.data` when a string) for the two app-server sources, the CLI's status lines for `login-status`, the visible main-content text for `sign-in-page`; cap at 2 KiB; `scrubForStore` (secrets); then **mask personal data**: e-mail addresses, the account's own e-mail and nickname, phone-number shapes (including masked ones like `•••-1234`), personal names the page labels as such, and provider identifiers (UUIDs, long hex ids, `user-` / `org-` / `acct` prefixed ids, device ids), replaced by fixed placeholders. A scrub error, truncation or masking failure ⇒ no call, `undecided`.
- **What leaves the machine:** the prepared snippet, to TypeSafe (Jev) and, on doubt, to the Codex `fast` tier (Luna). Stated in the CLAUDE.md bullet (§11).
- **Jev question** (`systemone`, model `jev-1.13.0`, endpoint and vault key `typesafe_api_key` as the other Jev integrations): choice `lockout` with labels `device_limit` (the provider refuses this account because this device has reached its limit of paid accounts), `signed_out` (ordinary expired, revoked or missing login), `other` (rate limit, outage, plan, network, local tool error, anything else) and `cannot_tell`. The snippet is fenced as untrusted data, as `buildRefereePrompt` already does for the referee: instructions inside it are content to classify, never instructions to follow.
- **Referee:** asked when Jev's top probability is inside `DEFAULT_CASCADE_BAND` (0.30–0.70), when Jev says `cannot_tell`, or on the cascade's random audit. One true/false statement: "the provider is refusing this account because this device has reached its limit of paid accounts". The referee runs on a **different signed-in Codex account than the one being judged and not a benched one**: a dedicated `CodexCliIntelligenceProvider` (not the shared `jevReferee`, which runs on the default home) is called with `IntelligenceOptions.accountOverride` set to an account picked by `QuotaAwareScheduler.selectAccount(accounts, { framework: 'codex-cli', nowMs }, judgedId)` over the pool minus any account that is suspected or benched, and with `requiredRoute: { framework: 'codex-cli', modelId: <the fast-tier model> }` plus `model: <the fast-tier model>` and `strictModelPin: true` (the provider reads the model from these, not from `requiredRoute.modelId`; `requiredRoute` also forces `subscriptionOnly` and the file credential store for that call; a referee call held by the reader's strict-child limit past its timeout counts as unavailable) so a missing override fails instead of falling back; `askReferee` gains optional `accountOverride` and `requiredRoute` it passes through. With no such account the referee is unavailable; it never falls back to the default home. Timeout 15 s (clamped ≤ 20 s). A referee call that itself fails, is refused (including an auth refusal of the referee's own account), or is shed by the host spawn cap counts as unavailable.
- **Verdict (truth table, the whole rule):**

  | Jev | Referee | Verdict | Deciders |
  |---|---|---|---|
  | `device_limit`, confident | not asked | `device_limit` | 1 (Jev) |
  | `device_limit`, confident | asked (audit), true | `device_limit` | 2 |
  | `device_limit`, confident | asked (audit), false | `undecided` (contradiction) | — |
  | in band or `cannot_tell` | true | `device_limit` | 1 (referee) |
  | in band or `cannot_tell` | false | `not_device_limit` | 1 |
  | `signed_out` / `other`, confident | not asked | `not_device_limit` | 1 |
  | `signed_out` / `other`, confident | asked (audit), false | `not_device_limit` | 2 |
  | `signed_out` / `other`, confident | asked (audit), true | `undecided` (contradiction) | — |
  | any confident label | asked (audit), unavailable | Jev's verdict | 1 |
  | unavailable | true | `device_limit` | 1 (referee) |
  | unavailable | false | `not_device_limit` | 1 |
  | any non-answer | unavailable | `undecided` | — |
  | unavailable | unavailable | `undecided` | — |

  `undecided` is never a device limit. The output carries the number of agreeing deciders (logged; it does not shorten the two-observation rule in §4). Every reachable combination is in this table and is tested as a matrix.
- **Budget:** every call counts, Jev and referee together: machine-wide daily cap 100 (seeded from the log; `intelligence.jevCodexDeviceLimit.maxChecksPerDay`) and a per-account daily sub-cap 10. Cap reached ⇒ `undecided`, recorded as an expected capacity outcome (`deviceLimit.capExhausted` counter and a log row), not a degradation; the referee is never a fallback for an exhausted cap. Identical text is not re-judged for cost: the snippet is normalised (digits, UUIDs, hex ids, timestamps stripped) and hashed, and a machine-wide verdict cache keyed by `(source, hash)` holds `device_limit` / `not_device_limit` verdicts for 24 h (`undecided` is never cached). A cache hit does not count against the budget, carries `cached: true`, and never adds deciders. **A cached verdict never moves state:** any judgement that could establish or change state (a first observation for a non-suspected account, a confirmation, a page verdict) bypasses the cache and is judged fresh for this account, within the budget. The cache only answers repeat reads that can take no action (scheduled reads of an already benched account).
- **Judge outage:** `undecided` because Jev and the referee are both unavailable raises one `DegradationReporter` event `CodexDeviceLimitJudge.unavailable` per outage episode. The disposition on that path is closed and explicit: no suspicion, no bench, no stopped repair. Nothing falls back to a phrase match; the pre-existing sign-out handling (which this feature does not own or change) simply continues.
- **Provenance:** each judgement's prepared snippet, question, raw answers, probabilities and referee answer go to a machine-local file under `.instar/state/codex-device-limit-provenance/` (14-day retention, mode 0600). It is kept machine-local the same four ways the existing judgement provenance is: `.gitignore` entries for both `state/` and `.instar/state/` roots (plus an idempotent `PostUpdateMigrator` gitignore migration), the file viewer's `NEVER_SERVED_PREFIXES`, and `BackupManager`'s exclusion list; one test checks all four. The shared judgement-provenance log gets a row whose `contextRedacted` is only `{ source, snippetHash }`.
- **Grading, kept honest:** each bench records three separate facts, never collapsed: `agreement` (how many deciders said `device_limit` across the two confirmations), `observed` (`released-without-sign-in` | `released-after-sign-in` | `operator-released` | `still-benched`) and `grade`. `grade` is `right` or `wrong` only when the topic's verified operator (the authenticated sender matching `GET /topic-operator/:topicId`; agent-signed messages excluded) answers on the notice ("yes, that was the device limit" / "no, it wasn't"); the grading principal is recorded; any other reply leaves it `unknown`. Neither a persisting refusal nor a later recovery is treated as proof of the original cause; `released-without-sign-in` is counted as a *possible* false bench in the meter's breakdown, not as a wrong grade. Rows go to the log (§8) and to the LLM Decision Quality Meter under decision point `codex-device-limit-judge`.

Why not a phrase match with authority: the wording is unpublished and may be localised, and the same phrase appears in OpenAI's help article, in agent conversations (including the one that produced this spec) and in feedback issues.

### 2. Where the judge's input comes from

The judge never runs inline in the poll loop or a repair step. Each source records a pending judgement and returns at once; `CodexDeviceLimitJudge.enqueue` runs it asynchronously, single-flight per account, and hands the verdict to §4. At most one pending judgement per (account, source), newest replacing older; a machine-wide cap of 2 × the number of Codex accounts; overflow is `undecided` and logged.

- **A, the read refusal (the only bench source).** `codexLiveRateLimitReader`'s `auth-failed` and `unavailable` variants gain an optional `refusal?: { stage: 'read'; text: string }`, carrying the JSON-RPC `error` object text of the `account/rateLimits/read` (id 2) response, held in memory only. This is the local Codex app-server's reply to a request for this login. Nothing in that reply proves OpenAI itself generated the error (a proxy, a CLI bug or a local fault can produce text too), so provenance is treated as uncertain and the authority is kept narrow to match: two separate fresh judgements, the machine floor, self-release on clean reads, and the operator's set-active and per-machine ignore list. stderr is never read.
- **A-init, the initialize error (trigger only).** The id-1 error text is carried as `refusal: { stage: 'initialize' }`. It may come from the local app-server handshake, not OpenAI, so a `device_limit` verdict on it only requests a fresh read (§3); it never counts as a confirmation.
- **A′, login status (second opinion only).** `CliLoginStatus` gains `checkWithText(home)` returning `{ verdict, text }` (the CLI's own status lines; the existing call becomes this one, so no extra process). It describes locally cached login state, so a `device_limit` verdict on it only requests a fresh read; it never counts as a confirmation.
- **B, a Codex session's screen (trigger only).** For `codex-cli` sessions with a verified `subscriptionAccountId` (resolved through `accountForReads`), excluding relogin helper sessions, in both the interactive and the rerouted/job branch of the monitor tick (a new codex call site next to `endIfLoginExpired` and `reportInteractiveLoginExpired`): one async capture (`capturePaneAsync`) per session per 20 s (`INTERACTIVE_LOGIN_CHECK_INTERVAL_MS`), live tail of 12 lines (`paneTail.liveTail`). A broad recall trigger (`/device|limit|log ?in|sign ?in|signed out|logged out/i`) held 60 s calls `requestCodexCheck(accountId)`. The screen text is never judged and never benches. Brakes: one request per session per 10 min; after a check that found the account working, none until the matched tail changes or 60 min pass; per-session maps are pruned with the existing live-session eviction loop.
- **C, the sign-in repair page.** In `ChromeCdpReloginBrowser`, a page the in-page classifier marks `unknown` on an auth-flow origin (`https://auth.openai.com`; `https://chatgpt.com` paths under `/auth/`) has its main-content text judged with `source: 'sign-in-page'`. The drive does not wait: it continues as today, and a `device_limit` verdict stops it at its next step boundary through the same abort path `settleForDeviceLimit` uses. A page judgement is bound to the repair attempt id and a page-navigation generation counter; it is discarded (logged `stale-verdict`) if the drive has navigated to another page or the attempt has settled by the time it arrives. The agent-session helper (already an LLM reading the page) accepts a new hard line `device-limit` (§4 lists the exact edits).

### 3. Read discipline

- **What a clean read is (one definition, used everywhere):** a live app-server result `kind: 'ok'` (`source: 'codex-app-server'`) for that home. A rollout-file fallback snapshot is **not** a clean read: it never clears suspicion, counts toward release, resets a refusal count, makes a verdict stale, or fires trigger B's "account working" brake. Tested with a refusing poll that falls back to the rollout file.
- **One post-read handler for every read.** `pollAccount`'s Codex branch returns the live read's outcome (`ok` / `auth-failed` / `unavailable`, with any `refusal`) alongside its snapshot instead of returning `null` early. One shared `afterCodexRead(slotAccount, outcome, snapshot)` handler, keyed on the attributed `slotAccount.id` (from `reconcileIdentity`), runs for the scheduled poll, `requestCodexCheck` and confirmation reads alike: it first enqueues any refusal for judgement, then runs today's `onCodexAuthRefused` streak unchanged, then the `restores` predicate (with the device-limit hold), the counters and ledger `observe`. Each caller is tested, including an `auth-failed` refusal from the scheduled poll reaching `enqueue`.
- **Single-flight per home:** a `CodexReadGate` wrapper around `codexLiveUsageReaderDetailed` holds one in-flight read per resolved `CODEX_HOME` (the home `accountForReads` returns, so a credential re-point cannot produce two readers on one home); every path, including the scheduled poll, goes through it, and a caller that finds a read in flight awaits that result instead of reading again. The referee never runs on the judged account's home (§1). `UNAVAILABLE` becomes a fresh object per result so a `refusal` can never leak between accounts.
- **`requestCodexCheck(accountId)`** (triggers B, C, A-init, A′): one live read now through single-flight; inside 10 minutes of the last read for that account it returns without reading.
- **`scheduleConfirmationRead(accountId, delayMs)`** (bench and release confirmations): bypasses the 10-minute floor and the benched-account backoff, still single-flight; at most one pending per account.
- **Concurrency:** `CodexReadGate` also caps poller-family Codex live reads at 2 per process (the reader's existing strict-child cap covers only `subscriptionOnly` reads, which the poller does not use). Waiting reads are queued in priority order (scheduled poll and confirmation/release reads ahead of trigger reads); a trigger read whose 10-minute floor would be violated by the wait is dropped. A read that cannot run neither confirms, releases, nor resets any counter.
- **Freshness of async verdicts:** each queued judgement carries the account's credential fingerprint, the read's sequence number and the switch state at read time. Before a verdict acts, it is dropped (logged `stale-verdict`) if since then the account had a clean read (as defined above), its credential changed, the switch was turned off, or the account was added to `ignoreAccounts` (§6).

### 4. What a verdict does

**Bench (only from source A):**
1. **First observation** (a fresh `device_limit` judgement for this account on an A refusal): the account becomes *suspected*: persisted `deviceLimitSuspectedAt` on the pool record, and a confirmation read scheduled 5 minutes later (`scheduleConfirmationRead`). No episode is mutated: the relogin service's retry scheduler (`SubscriptionReloginService`, where slow retries are started) gains a gate, supplied through runtime deps, that reads the pool record and defers a retry while the account is suspected or benched and the switch is on; the pure `isSlowRetryEligible` episode check is unchanged. No bench, no swap, no notice.
2. **Bench** when a second A refusal **5–60 minutes after the first** is also freshly judged `device_limit` for this account, **and** the machine floor holds: at least one *other* Codex account on this machine has, as its **latest completed live read**, a clean read taken within the last 60 minutes, and is neither suspected nor benched. A real device limit leaves the accounts under the limit working; every account refusing alike points at something else (an outage, a CLI bug, a shared misjudgement), so then nothing is benched: the accounts stay suspected until expiry and the machine notice shows a HIGH line "all Codex accounts here are refusing alike; not benched". A machine with only one Codex account therefore never benches (stated in Honest limits). Model agreement on one read never substitutes for the second observation. Then `QuotaPoller.markDeviceLimited(account)`:
   - `pool.update(id, { status: 'needs-reauth', statusCause: 'codex-device-limit', deviceLimitSince })` in one write. `UpdateAccountInput` and `update()`'s whitelist gain `statusCause`, `deviceLimitSince`, `deviceLimitSuspectedAt`, `deviceLimitNextReadAt`, `deviceLimitRefusedReads`, `deviceLimitReadsStopped`; the PATCH route does **not** accept any of them (a Bearer holder cannot bench).
   - **Benched** means exactly `status === 'needs-reauth' && statusCause === 'codex-device-limit'` on the attributed record (`slotAccount.id`). Every reader uses that predicate.
   - **Repair admission reads the pool**: `evaluateSubscriptionReloginAdmission` takes the pool record's `statusCause` and refuses a benched account with a new reason `device-limit-benched` before the cause check. The pool record is the authority; the ledger is bookkeeping.
   - Ledger, best-effort: `observe(transition-to-needs-reauth, causeClass: 'codex-device-limit', corroboration: 'exchange-corroborated')` for an `active` account, or `supersedeCause` (§5) for one already `needs-reauth`. A ledger that is absent or not writable raises a degradation; the bench and the admission refusal stand on the pool record.
   - Repair: `SubscriptionReloginRuntime.settleForDeviceLimit(accountId)` settles every non-terminal episode for that account on this machine through the store, by state: `suggested` → `refused` / `device-limit` (an existing legal, terminal, never-retried transition); `approved` / running → a new store transition to `failed` / `device-limit`, then, if this process holds the drive's controller, its abort signal is fired too; the orchestrator's `cancelledResult` reports a terminal result for `failed` / `device-limit`. No episode is labelled `cancelled-by-operator`. A transition or CAS error is logged as a degradation and never undoes the bench on the pool record. Tested for each non-terminal state. A waiting slow retry is deferred by the scheduler gate (step 1).
   - Sessions: `DeviceLimitSessionMover` lists live sessions whose `subscriptionAccountId` (via `accountForReads`) is the benched account. Interactive ones go through `onQuotaPressure` (framework-safe: Codex to Codex only) with the existing `decideLoginExpiredSwap` brakes (one try per session per 10 min, at most 3) and protected-session refusal. Moves are serialised per machine, at most one every 30 s, and each re-reads the source's benched predicate and the target's headroom just before it runs, so simultaneous benches do not pile every displaced session onto one account. Job sessions are not moved; their next run is placed on an eligible account. `observeCliLoginExpired` is not used.
   - Idempotent: a benched account is not re-marked.
3. **Suspicion ends** on a `not_device_limit` verdict, on a clean read, when 60 minutes pass with no second observation (logged `suspicion-expired`), or on switch-off: `deviceLimitSuspectedAt` is cleared, which lifts the scheduler gate. `undecided` leaves the suspicion to expire. Today's two-poll rule runs on its own throughout; a repair it admits meanwhile is stopped by step 2 if the bench lands.
4. **Time to bench:** at least 5 minutes after the first refusal (the confirmation read), typically 5–6; a judge that is slow or down delays it, never shortens it.

**Stop one repair (sources C and helper):** the episode ends terminally `failed` with `failureClass: 'device-limit'`. Exact edits: `device-limit` is added to `HARD_LINES`, `parseHelperBody` gains its branch, and the helper's hard-line handler settles it `{ outcome: 'refused', failureClass: 'device-limit' }` (not `operator-only`, so it never parks in `waiting-operator-only`, and not `agent-hard-line`, so `helperHardLines` and unattended graduation are untouched); the orchestrator's `refused` failure-class union and the store's validated failure-class array both gain `device-limit`; `device-limit` is not on `SLOW_RETRY_FAILURES` and is not breaker or re-admission evidence. Then `requestCodexCheck(accountId)`: only that read's A verdicts can bench.

**Notifications for episodes ending `device-limit`:** the per-episode `onTerminal` / `onOperatorOnly` notice is skipped for `failureClass: 'device-limit'` (its own test); the machine notice (§7) is the only voice, and it lists stopped repairs as well as benched accounts, so a refused repair is never silent. The episode's `device-limit` ending is also shown on that cell in the dashboard and in `GET /subscription-relogin` (blockers: "repair stopped at a possible device-limit page").

### 5. Ledger: cause supersede

`SubscriptionLoginLedger.supersedeCause(accountId, causeClass)`: in one transaction, on the open episode for (account, this machine), update `causeClass` in place and append a `cause-superseded` event `{ from, to, at }`. Incident id kept; not counted as a re-login; no `relogin-resolved` event. No open episode ⇒ no-op `no-open-episode`. Admission re-runs per attempt (`SubscriptionReloginRuntime.admissionFor`), so the next attempt refuses `cause-not-actionable`. `codex-device-limit` joins `SUBSCRIPTION_LOGIN_CAUSE_CLASSES`, deliberately not `ACTIONABLE_CAUSES`.

### 6. Release, backoff, switch-off

- **One rule in the store:** a private `SubscriptionPool` helper clears `statusCause`, `deviceLimitSince`, `deviceLimitSuspectedAt`, `deviceLimitNextReadAt`, `deviceLimitRefusedReads` and `deviceLimitReadsStopped` whenever a write moves `status` to anything other than `needs-reauth` without setting them itself. Both status writers call it: `update()` and the enrollment commit (`completeValidated` → `VERIFIED_EMAIL_COMMIT`, which sets `status` directly). So every writer of `active` (the restore in `afterCodexRead`, a successful repair's `finalizeSuccess`, enrollment completion, credential repointing, follow-me, the PATCH route) ends a bench consistently. Tested through the repair-success and enrollment-completion paths.
- **Hold:** `afterCodexRead`'s restore predicate gains a device-limit hold beside `cliLoginExpiredHolds`, checking both `attributedId` and `account.id`: a benched account is not restored by a single clean read. The hold derives from the persisted pool record, so a restart keeps it.
- **Release by the provider:** the first clean read calls `scheduleConfirmationRead(…, 5 min)`; a second clean read releases (`status: 'active'`, which clears the fields), ledger `transition-to-active` best-effort, `observed: released-without-sign-in` (or `released-after-sign-in`). Any refusal resets the count.
- **Backoff while benched:** persisted `deviceLimitNextReadAt`: the scheduled read for a benched account runs 1 h after the bench, then doubling, capped at **6 h**; a restart keeps the schedule. **Breaker:** persisted `deviceLimitRefusedReads` counts consecutive refused scheduled reads at the 6 h cap; at 8 (about two days) scheduled reads for that account stop (persisted `deviceLimitReadsStopped`), logged as a P19 breaker, and the machine notice says it is no longer checked automatically. B and C trigger reads, the operator release and any new sign-in still run a read, which resets the breaker on a clean result. Both fields reset on a clean read, on any release (store rule), on switch-off, on a credential change, and are set fresh by a new bench; tested across a restart after the breaker tripped, followed by a release and a re-bench.
- **Release by the operator:** any writer of `active` (the existing `PATCH /subscription-pool/:id`, a successful repair, enrollment completion) ends the bench through the store rule and records `observed: operator-released` (or the matching kind) on the next poll; it sets nothing else, so two new confirmations can bench again.
- **"Keep using it anyway":** a per-machine list `subscriptionPool.codexDeviceLimit.ignoreAccounts` (account ids, read live). A listed account on that machine is never suspected or benched, and an existing bench on it is cleared on the next poll; C and the helper can still stop one repair (cheap and self-undoing). This deliberately adds **no new authority path**: it has exactly the posture of the on/off switch: both live in that machine's own `.instar/config.json`, are read live, and are written by the agent on that machine on the operator's word; neither is added to `PATCHABLE_CONFIG_KEYS` (so no API caller gains a new write), and either one only ever restores today's behaviour, which a Bearer holder can already do for one account with `PATCH /subscription-pool/:id`, so there is no new mandate type to forge or replay. The conversational surface is primary: the operator says "keep using X on the Studio anyway" and the agent writes the list into that machine's own config (from a session on that machine); the notice says so. A cross-machine signed release button was designed in review round 5 and removed in round 6: the existing mandate delivery accepts only the follow-me re-mint shape, and a release mandate shaped to fit it would also authorise a re-mint enrollment, a privilege escalation; the ignore list gives the operator the same outcome without that surface.
- **Switch off** (`subscriptionPool.codexDeviceLimit.enabled: false`): the next poll sets every benched cell `active` (clearing the fields), clears every suspicion and pending confirmation read, drops pending judgements, records `transition-to-active`, and lets today's two-poll rule decide afresh from new evidence; the scheduler gate also checks the live switch, so retries resume at once. No cause is invented. Tested while suspected, and across a restart.

### 7. One notice per machine

The bench and the move are the self-heal; the notice reports them.

- `conditionKey: codex-device-limit:<machineId>`, id `codex-device-limit-<machineId>`, `category: 'subscription-device-limit'`, `source: 'agent'`, `sourceContext: 'codex-device-limit-tripwire'`. One row per machine; its body lists every benched account on that machine (nickname, since when), every repair stopped at a possible device-limit page in the last 24 h (nickname, when, whether the confirming check benched it), and the *all refusing alike* condition while the machine floor is blocking benches (§4), and refreshes when any of these changes.
- **Priority:** `normal` while the machine still has a signed-in Codex account; `HIGH` when it has none. A row listing only stopped repairs (no bench) is `low`; a row carrying *all refusing alike* is `HIGH`. At most one row per machine.
- **Why notify when the move absorbed it:** the operator explicitly asked to be told (topic 134294, 13:39 PDT); the lost slot cannot be recovered by any self-heal, only by the operator's layout decision. So one calm row per machine; the urgent level is reserved for a machine left with no Codex account.
- **Text, per kind of line:** *benched*: the account's refusals on that machine look like OpenAI's device limit (judged by Jev twice; not proven to come from OpenAI); it is benched there only; other machines and accounts carry on; no sign-in will be tried there; signing out of another account does not free a slot, so the real choice is which machine keeps which accounts, and leaving it benched is fine; to keep using it there anyway, tell the agent and it adds the account to that machine's ignore list. *Repair stopped*: a sign-in attempt for the account stopped at what looked like a device-limit page; a check is running, nothing is benched, and a later sign-in will be tried as usual. *All refusing alike*: every Codex account here is refusing in the same way, so this is probably not the device limit; nothing is benched. *No longer checked*: the account has been refused for about two days; automatic checks stopped (§6).
- **Re-notify brake:** a row cleared and re-opened for the same machine within 24 h refreshes silently.
- **Clear:** `registerAttentionConditionResolver('subscription-device-limit', fn)` (return type `'cleared' | 'active' | 'unknown'`): `unknown` for items outside the category or for another machine's id; `cleared` when this machine's pool has no benched account, no repair stopped at a device-limit page in the last 24 h, and no *all refusing alike* condition (which ends when any Codex account on the machine reads clean or every suspicion expires); else `active`.
- **Delivery dependency:** on a machine without the serving lease the post goes through the existing forward-to-holder path and waits as a held operation if the holder is down. The pool record survives that.
- Nicknames are HTML-escaped.

### 8. Observability

Never snippet text, a credential or session content. The real wording lives only in the machine-local provenance file (§1).
- Dashboard Subscriptions grid: a benched cell reads "Suspected device limit: benched on this machine" and hides Sign in / Repair (signing in cannot help).

### 9. Switches

- `subscriptionPool.codexDeviceLimit.enabled` (read live): the whole tripwire. Omitted ⇒ resolved by the development-agent gate: **on** on a development agent (Echo, where the operator asked for it), off on the fleet until graduation (Maturation plan); an explicit value always wins. Not a security control: off only restores today's behaviour (§6). It lives in the machine's own config file (not patchable over the API).
- `subscriptionPool.codexDeviceLimit.ignoreAccounts` (string[], default empty, read live): per-machine "keep using it anyway" (§6).
- Fixed constants (not config, by design, to keep the surface small): 5-minute confirmation delay, 5–60-minute pairing window, two clean reads, 1 h → 6 h backoff, 8-refusal breaker.
- `intelligence.jevCodexDeviceLimit` (`{ enabled?, maxChecksPerDay?, perAccountPerDay?, timeoutMs?, referee?: { enabled?, timeoutMs? } }`). Omitted ⇒ on wherever a `typesafe_api_key` or a second signed-in Codex account exists; without either the judge returns `undecided` and the tripwire takes no action (the helper's own `device-limit` report can still stop a repair).

### 10. Multi-machine posture

machine-local-justification: physical-credential-locality — the limit is enforced by OpenAI per device against the Codex login stored on that machine's disk, and the subscription pool cell is that machine's own login.

Machine-local **by design**: the pool record, the ledger, the bench and the provenance file are per machine. Visible across machines through the existing proxied read `GET /subscription-pool?scope=pool`. Notices are keyed by machine, so each machine speaks only for itself. When account follow-me replication is on, `status` already replicates through the meta projection (harmless: consumers only count it where the account is held locally); `statusCause`, `deviceLimitSince` and `deviceLimitSuspectedAt` are kept out of `projectAccountToMeta` (tested).

| Source | Symbol read | State claimed | Independent corroboration | Unmeasurable result |
|---|---|---|---|---|
| A | The local app-server's JSON-RPC error to `account/rateLimits/read` for this login (provenance uncertain: not proven to come from OpenAI) | The provider refuses this login on this device because of the device limit | A second, separate refusal 5–60 min later, both freshly judged; the machine floor (another account's latest read clean); release needs two clean reads | No text, prep failure, judge down or cap ⇒ `undecided` ⇒ today's behaviour |
| A-init, A′ | Local handshake error / the CLI's cached login status | Nothing that can bench | They only request a fresh A read | — |
| B | Sign-in-ish words in a Codex session's live tail | Nothing (a session can print anything) | They only request a fresh A read | Read unavailable ⇒ counted, nothing changes |
| C | Judged text of an `unknown` auth-flow page, or the helper LLM's report | This one sign-in attempt cannot complete | The attempt's own success test cannot pass; any bench needs A | Page unreadable / judge down ⇒ existing handling |

Symbol without state (a help article, a conversation, an injected or relayed page, a proxy body) ⇒ only an A refusal can count, it needs two confirmations, and a page can only stop one repair at no lasting cost. State without symbol (the judge reads a real lockout as `signed_out`) ⇒ today's behaviour: one repair runs; its page is judged by C and the helper can report the hard line, which stops the retries.

## Interactions

- **Login-expired recovery:** shares the capture cadence, tail helper and swap brakes; not its `observe` step. Claude sessions are unchanged.

- **Credential repointing:** every read, mark and move goes through `accountForReads`.
- **Slow retry / breaker / unattended graduation:** `device-limit` is not on the allowlist, not breaker evidence, and not counted as a helper hard line.
- **Placement / quota-aware placement / signed-out machine skip (CMT-1051):** unchanged code; a benched account is not executable, and a machine whose Codex accounts are all benched reports `no-signed-in-account`.

- **Jev integrations:** a new feature key in shared metering, the decision-quality meter and daily caps; no shared state.

## Honest limits

- The judge can be wrong. A false bench needs two confirmations and holds one account on one machine until two clean reads (if the login actually works) or the operator; `released-without-sign-in` is counted, so a pattern of possible false benches shows in the decision-quality meter. A false `signed_out` falls back to today's behaviour, where C and the helper still stop the retries on the page.
- Most grades will stay `unknown`: neither a lockout that persists nor a later recovery proves the cause, so only the operator's answer on the notice grades a bench. `released-without-sign-in` is the measurable early-warning signal.
- If OpenAI enforces the limit only at sign-in and the app-server keeps answering, nothing is benched; that is correct (the account works).
- Without a Jev key and without a second signed-in Codex account the tripwire takes no action; only the helper's own `device-limit` report stops repairs.
- Internal Codex routing on a benched home relies on the existing failure-swap (see Interactions).
- A machine with only one Codex account never benches (the machine floor needs another account working); the helper and C still stop its repairs.
- The notice cannot tell the operator the limit's number.
