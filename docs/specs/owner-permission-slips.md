# Sign a finite permission slip from chat

## Problem statement

An owner can ask in chat to approve a specific set of work. Let the agent turn that message into an exact proposal, open it in the paired Instar app, and obtain one authenticated presence decision covering the disclosed items.

## Proposed design

Chat text proposes work and never authorizes it. Record the authenticated source message locator and digest, with no raw chat text in links, logs or routable receipts. Bind one current proposal to the source and actor; repeat delivery returns it or an explicit owner-visible supersession. Only verified source provenance may cause proactive owner attention. Then resolve the requested items through the existing owner trust approval and Work Board services. The first slice supports existing owner Approve actions on cards that the current Work Board path proves eligible. Generic tasks, unspecified work, other principals, unauthorized cards, multiple agent authorities, external money or security exceptions, and unsupported action kinds are outside this slice. Each card may still have its existing downstream approval requirements. If an item cannot be unambiguously resolved or proves ineligible, show which item needs correction and refuse the requested slip. A revised list must be explicitly disclosed as a fresh set. All rows share one authenticated owner and serving authority. Six distinct Work Board cards are the requested example, without creating a general count cap. Reuse existing approval envelope and transport capacity limits, require complete disclosure, and keep a finite atomic application set. Each distinct card is bound to its current immutable authority epoch, card ID, material hash, title, action and eligible revision. The exact set is frozen. A new specification or changed action requires a new slip.

The server creates a pending record in the existing Changes to approve feed and returns a chat deep link for it. A link carries only an opaque locator and a trusted app route. It conveys no authority, secret, browser key or approval result. The app verifies the exact paired agent origin before requesting the proposal through signed device transport. The link opens the existing approval detail UI and never signs or dispatches on open. Feed, detail and receipts require fresh authorized owner read access; missing, unauthorized and stale origin locators reveal no private card information. The same ordered, canonical server disclosure appears whether the owner opens the link or finds the slip in Changes to approve. On narrow layouts keep the **Approve these items** action discoverable and present a scrollable accessible disclosure before explicit confirmation, without using a scroll threshold as consent. The sheet shows the authenticated source reference and safe context, each full current action and material title or blocked content, limits and expected card transition, and the fact that reaching an approval decision does not prove the work completed.

Reuse the established signed owner-device write gate and user presence challenge in `mobilePermissionsRoutes.ts`. Use a new purpose for this exact finite decision, binding slip ID, canonical disclosure digest, six-card set where applicable, action and card revisions, device presence key generation, owner and acting agent identities, origin, epoch and challenge expiry. Use the existing decision challenge policy. Require the same current owner/approver and serving lease when consuming it. A chat reply, copied URL, bearer token, device-only signature or single-card challenge cannot authorize the slip. Decline and cancel follow the ordinary owner decision model. Any item becoming ineligible before consent blocks the entire decision and prompts review of a new exact snapshot.

In one fenced authority transaction check the slip is pending, the challenge unused, and all exact card authority/material revisions and relevant policy epochs still current. Conditionally transition the slip, consume the challenge, record the validated decision and enqueue a stable application row per distinct item. Approval, denial and cancellation serialize at that boundary. Two paired devices may see separate challenges but only one terminal slip decision can exist. The commit is the authorization event. WorkBoardService's current synchronous single-card tap and best-effort transcript/poke path do not implement that transaction. The first build must supply a durable slip journal and outbox bound to the same serving fence, or prove the existing store has an equivalent atomic cell; it may not loop over ordinary taps as the authorization step. Enable only a typed WorkBoard transition adapter whose card-state writes and slip revision checks share the fenced authority boundary. Apply each approved action through its existing owner tap policy with exact expected state and current owner restrictions. Reuse one canonical logical transition identity across both slips and ordinary taps, with a deterministic WorkCard event ID and durable receipt. A pending item must honor current revocation, owner correction and lease/owner epoch. Existing downstream pickup gates remain in force. In the same transaction as an applied receipt, persist pending transcript and wake projections with distinct deterministic IDs. Reconcile each independently and do not wake before its durable WorkCard tap exists. Bind pickup to the exact recorded cause through WorkBoardPickupController; wake is advisory and a missed wake is discovered by the durable cause scan. A mutation that already happened can only reconcile its matching receipt. Unknown execution gets an explicit state and retry is limited to verified safe reconciliation; a material card change after signing blocks that item without adding or changing any other item. The fenced serving authority runs the existing scheduler path for an outbox worker on commit, startup, handoff and its bounded normal cadence. Record oldest pending age and stable outcome. Back off and retry a safe reconciliation read only. Existing owner review receives exhausted or unverifiable items without blind redrive. The UI distinguishes signed, applied, stale and unresolved approval per item and separate pickup and work completion. Retain used challenge and decision evidence through existing replay and recovery policy. Signing approval for the set does not promise atomic pickup or completion across the independently applied cards.

## Multi-machine posture

One slip belongs to one agent authority and serving lease. Peers forward to its existing owner decision surface and cannot sign on behalf of the owner or use cached pending records as authority. Serve redacted history through the current authorized decision surface with live reader proof; an isolated peer does not disclose cached private slip details. Transfer the journal through the same verified accepted-owner serving-fence handoff required by eligible workloads; if the existing path cannot prove complete transfer, the slip stays unavailable. Enable handoff only after a verified slip journal and outbox transfer with stable application IDs. On missing state, a queued application remains fenced until the new writer reconciles it. No auto-replay from old storage. Link opening on an iPhone already paired to the serving origin is supported even if the chat was read on a different computer.

## Decision points touched

- Interpret a source message into a proposed exact set — judgment-candidate; floor: the typed server adapter admits only current eligible actions; arbiter: verified owner reading the exact disclosure.
- Consume a finite owner signature — invariant; basis: irreversible-consequence; evidence: acting on the wrong cards would turn unauthenticated chat or mismatched scope into authority.
- Apply and reconcile each granted action — invariant; basis: enumerable-domain; evidence: exact item ID, action revision and durable receipt define the only authorized state transition.
- Handle a changed or unsupported item — invariant; basis: irreversible-consequence; evidence: substituting a changed item would execute a scope the owner never signed.

## Verification

At rollout verify the native Changes to approve and chat deep-link handling on isolated and opted-in development agents before fleet enablement. Expose discovery in CapabilityIndex and new-agent/in-place migration guidance. Existing one-card and paired-app approval remain available through their current policy. Unit checks bind the signed disclosure, every action and item revision, provenance, expiry, current owner and origin. Integration proves six items produce exactly six authorized application rows, rejects extra, missing, duplicate, reordered or changed items as applicable, and shows zero rows on commit failure or a concurrent card edit that wins. Test two valid device challenges and cancellation versus approval as competing terminal transitions. Prove an unattended worker drains an eligible item and shows queue age, with crash tests between tap, receipt, transcript and wake. Lifecycle tests cover phone deep link entry, restart before and after commit, changed item after commit, idempotent application and transcript/wake, replay, and fenced handoff. Compare the card list and per-item result with the owner-facing review. Do not infer the six sample cards are currently eligible or apply them as part of fixture testing. Standing approval grants are a future separate authority surface.
