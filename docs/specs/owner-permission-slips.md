# Sign a finite permission slip from chat

## Problem statement

An owner can ask in chat to approve a specific set of work. Let the agent turn that message into an exact proposal, open it in the paired Instar app, and obtain one authenticated presence decision covering the disclosed items.

## Proposed design

Chat text proposes work and never authorizes it. Record the authenticated source message locator and digest, with no raw chat text in links, logs or routable receipts. Dedupe by authenticated source, actor and durable per-set intent reference. Contextual interpretation of the authenticated owner message must determine whether sets are explicitly independent. If intent is uncertain, show a correction proposal without minting an approvable set. Each eligible disclosure shows if other independent sets from the same source remain unsigned. The server atomically persists one accepted grouping and assigns the intent references per source and actor before returning links or asking for attention. Concurrent proposals and delivery retries recover that grouping, even if parser output changed. A material correction uses explicit supersession. Ambiguous parsing cannot mint another slot or silently split a requested set. Only verified source provenance may cause proactive owner attention. Then resolve the requested items through the existing owner trust approval and Work Board services. The first slice supports existing owner Approve on eligible Not Started Work Board cards, with the exact canonical disclosure plus current title/material hashes. The existing console route serially taps up to ten displayed cards under a PIN and provides no app consent transaction. This native path is bounded by the canonical transport byte ceiling and proven atomic insertion capacity for the measured maximum rendered set. The console’s ten-tap display behavior is precedent for a different serial path and supplies no finite-slip cap. If existing transport and transaction measurements cannot establish an envelope, stay dark. Reject oversized or unrenderable sets before consent and never truncate them. Generic tasks, unspecified work, other principals, unauthorized cards, multiple agent authorities, external money or security exceptions, and unsupported action kinds are outside this slice. Each card may still have its existing downstream approval requirements. If an item cannot be unambiguously resolved or proves ineligible, show which item needs correction and refuse the requested slip. A revised list must be explicitly disclosed as a fresh set. All rows share one authenticated owner and serving authority. Six distinct Work Board cards are the requested example, without creating a general count cap. Reuse existing approval envelope and transport capacity limits, require complete disclosure, and keep a finite atomic application set. Each distinct card is bound to its current immutable authority epoch, card ID, material hash, title, action and eligible revision. The exact set is frozen. A new specification or changed action requires a new slip.

The server creates a pending record in the existing Changes to approve feed and returns a chat deep link for it. A link carries only an opaque locator and a trusted app route. It conveys no authority, secret, browser key or approval result. The app verifies the exact paired agent origin before requesting the proposal through signed device transport. The link opens the existing approval detail UI and never signs or dispatches on open. Feed, detail and receipts require fresh authorized owner read access; missing, unauthorized and stale origin locators reveal no private card information. The same ordered, canonical server disclosure appears whether the owner opens the link or finds the slip in Changes to approve. On narrow layouts keep the **Approve these items** action discoverable and present a scrollable accessible disclosure before explicit confirmation, without using a scroll threshold as consent. The sheet shows the authenticated source reference and safe context, each full current action, material title, stable card reference and trusted distinguishing project or source context, limits and expected card transition, and the fact that reaching an approval decision does not prove the work completed.

Reuse the established signed owner-device write gate and user presence challenge in `mobilePermissionsRoutes.ts`. Use a new purpose for this exact finite decision, binding slip ID, canonical disclosure digest, six-card set where applicable, action and card revisions, device presence key generation, owner and acting agent identities, origin, epoch and challenge expiry. Use the existing decision challenge policy. Require the verified current owner and an enrolled presence device expressly eligible for this distinct finite decision on the current serving lease. A delegated or one-time approver does not qualify. A chat reply, copied URL, bearer token, device-only signature or single-card challenge cannot authorize the slip. Decline and cancel follow the ordinary owner decision model. Any item becoming ineligible before consent blocks approval and prompts review of a new exact snapshot. Card eligibility is an approval precondition only. Current owners can decline or cancel a stale pending slip without generating any application rows.

In one fenced authority transaction check the slip is pending, and the challenge unused. For approval, also check all exact card authority/material revisions and relevant policy epochs are still current. Conditionally transition the slip, consume the challenge, record the validated decision and, only for approval, enqueue a stable application row per distinct item. Approval, denial and cancellation serialize at that boundary. Two paired devices may see separate challenges but only one terminal slip decision can exist. The commit is the authorization event. WorkBoardService's current synchronous single-card tap and best-effort transcript/poke path do not implement that transaction. The first build must supply a durable slip journal and outbox bound to the same serving fence, or prove the existing store has an equivalent atomic cell; it may not loop over ordinary taps as the authorization step. Enable only a typed WorkBoard transition adapter whose card-state writes and slip revision checks share the fenced authority boundary. Apply each approved action through its existing owner tap policy with exact expected state and current owner restrictions. Reuse one canonical logical transition identity across both slips and ordinary taps, with a deterministic WorkCard event ID and durable receipt. A pending item must honor current revocation, owner correction and lease/owner epoch. Existing downstream pickup gates remain in force. In the same transaction as an applied receipt, persist pending transcript and wake projections with distinct deterministic IDs. Reconcile each independently and do not wake before its durable WorkCard tap exists. Bind pickup to the exact recorded cause through WorkBoardPickupController; wake is advisory and a missed wake is discovered by the durable cause scan. A mutation that already happened can only reconcile its matching receipt. Unknown execution gets an explicit state and retry is limited to verified safe reconciliation; a material card change after signing blocks that item without adding or changing any other item. The fenced serving authority runs the existing scheduler path for an outbox worker on commit, startup, handoff and its bounded normal cadence. Record oldest pending age and stable outcome. Back off and retry a safe reconciliation read only. Existing owner review receives exhausted or unverifiable items without blind redrive. The UI distinguishes signed, applied, stale and unresolved approval per item and separate pickup and work completion. Retain used challenge and decision evidence through existing replay and recovery policy. Signing approval for the set does not promise atomic pickup or completion across the independently applied cards.

### Ordering and recovery

Create a replacement and terminally supersede a pending slip with its challenges in one fenced transaction. If approval won first, the replacement path exposes that decision and its applications. The same canonical WorkCard transition identity comes from authority, card ID, exact action and its current action generation or eligible folded predecessor on both ordinary and slip paths. A new eligible generation can be approved again. Record which authority actually caused the single transition. Test both race orderings and lost replies.

The verified owner can stop remaining unapplied rows under fresh owner proof bound to the slip and the exact set shown at challenge issuance. At commit stop the intersection of that signed set and the rows still pending under the same identities. Return interim applications separately. This cannot stop, add or substitute a row outside the signed set. Stop and application serialize at the fenced item commit. Preserve applied history and existing downstream controls. On planned lease handoff under the same owner, a provably unapplied row may continue under the current writer with its original identity and revalidated eligibility. An owner change fences remaining prior-owner rows without applying them. Use a fenced journal with durable intersecting quorum of accepted owner machines, or a proven owner-authorized equivalent surviving loss of any single serving machine. Membership changes use the same accepted-owner governance and a witnessed handoff. No unwitnessed single installation may issue or commit a slip. Gate the offer on current durability capability, show unavailable or pending if quorum is lost, and keep current one-card paths where allowed. The signed decision and item rows are acknowledged only after quorum durability. After acknowledgment a new writer can recover a receipt through the quorum. Dispatch still requires a current fence. A local tentative decision is not visible as signed and no worker may pick it up before durable decision and application ownership are proven. Before acknowledging an applied item, protect its receipt or an authoritative deterministic WorkCard event from which the successor can reconstruct it. If writer loss interrupts that record, dedupe from the recovered exact event and projection causes or fence the unresolved item until evidence arrives. A surviving peer with current owner proof may read history via the current quorum or authenticated commitment evidence for that exact record under the current authorized epoch. A tentative local row or missing commit certificate never appears as signed or applied. Verify writer loss immediately before and after quorum commit with both client acknowledgments lost. History never authorizes new work from cached state. Without verified complete state, hold uncertain effects for reconciliation and do not create replacement authority from an older restore. Test planned handoff, ownership change and abrupt loss separately.

A correction view lists ineligible items without offering approval or reducing the list. If the paired app is unavailable, leave the slip pending and retain independent ordinary one-card approval where allowed. This slice does not offer or create standing grants.

## Multi-machine posture

One slip belongs to one agent authority and serving lease. Peers forward to its existing owner decision surface and cannot sign on behalf of the owner or use cached pending records as authority. Serve redacted history through the current authorized decision surface with live reader proof; an isolated peer does not disclose cached private slip details. Transfer the journal through the same verified accepted-owner serving-fence handoff required by eligible workloads; if the existing path cannot prove complete transfer, the slip stays unavailable. Enable handoff only after a verified slip journal and outbox transfer with stable application IDs. On missing state, a queued application remains fenced until the new writer reconciles it. No auto-replay from old storage. Link opening on an iPhone already paired to the serving origin is supported even if the chat was read on a different computer.

## Decision points touched

- Interpret a source message into a proposed exact set — judgment-candidate; floor: the typed server adapter admits only current eligible actions; arbiter: verified owner reading the exact disclosure.
- Consume a finite owner signature — invariant; basis: irreversible-consequence; evidence: acting on the wrong cards would turn unauthenticated chat or mismatched scope into authority.
- Apply and reconcile each granted action — invariant; basis: enumerable-domain; evidence: exact item ID, action revision and durable receipt define the only authorized state transition.
- Handle a changed or unsupported item — invariant; basis: irreversible-consequence; evidence: substituting a changed item would execute a scope the owner never signed.

## Verification

At rollout verify the native Changes to approve and chat deep-link handling on isolated and opted-in development agents before fleet enablement. Expose discovery in CapabilityIndex and new-agent/in-place migration guidance. Existing one-card and paired-app approval remain available through their current policy. Unit checks bind the signed disclosure, every action and item revision, provenance, expiry, current owner and origin. Integration proves six items produce exactly six authorized application rows, rejects extra, missing, duplicate, reordered or changed items as applicable, and shows zero rows on commit failure, denial, cancellation or a concurrent card edit that wins. Test stale dismissal, identically titled cards with different stable references, differing duplicate source parses, the maximum admitted disclosure and overflow, loss of quorum just before and after acknowledgment, and writer loss between local tentative signature and durable worker eligibility. Test two valid device challenges and cancellation versus approval as competing terminal transitions. Prove an unattended worker drains an eligible item and shows queue age, with crash tests between tap, receipt, transcript and wake. Lifecycle tests cover phone deep link entry, restart before and after commit, changed item after commit, idempotent application and transcript/wake, an item that applies during the signed Stop prompt while the remaining members still stop, replay, and fenced handoff. Compare the card list and per-item result with the owner-facing review. Do not infer the six sample cards are currently eligible or apply them as part of fixture testing. Standing approval grants are a future separate authority surface.
