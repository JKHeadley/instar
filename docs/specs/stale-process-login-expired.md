# A single session's expired-login screen must not bench a working login

## Problem (observed live, 2026-11-20, Mac Studio, account `sagemind-adriana`)

At 19:39:38 one Claude Code session under the `sagemind-adriana` login showed the CLI's own `Login expired · Please run /login` line. `QuotaPoller.observeCliLoginExpired` found that the stored credential READS, and treated the screen as authoritative: the account moved to `needs-reauth` (cause `cli-login-expired-observed`), with a hold that keeps it there for up to 12 hours (`CLI_LOGIN_EXPIRED_HOLD_MAX_MS`) while the stored credential's fingerprint is unchanged. Something set the account active at 19:39:45. A second sighting from the same stuck session re-marked it 11 seconds later.

Meanwhile:
- every quota poll (19:51, 20:02) read the usage endpoint successfully with that same stored credential, and the hold overrode each one (`loginCheck` stayed `signed-out`);
- the assisted repair opened a `url-code-paste` login at 19:42, and the enrollment reissue sweep re-minted it at 19:53, 19:55 and 19:58 (the operator-visible "sign-in restarting itself" loop). `completeIfAlreadySignedIn` never runs for an account that is not `active`, so the sweep can never close it;
- at 20:02 a fresh `claude -p "Reply with exactly: OK"` with `CLAUDE_CONFIG_DIR` set to that login's folder answered `OK`. The login worked.

**Why one screen is not proof the login is dead (hypothesis, consistent with the evidence).** A Claude Code process holds its OAuth tokens in memory. Several processes share one login folder. When one of them refreshes, the refresh token rotates, and a long-running process can be left holding a token the provider no longer accepts. That process shows `Login expired`, while a NEW process reading the stored credential works. The two observations are a pane screen at 19:39 and a successful fresh process at 20:02. The design does not depend on rotation being the cause: it depends only on the fact that one process's screen can be wrong about the stored login, and it tests the stored login directly. The 12-hour hold, keyed on "stored credential unchanged", cannot tell this case from a dead login, so it benches a working account and drives a pointless re-login loop.

## Design

The probe result is a **signal**. The quota poller stays the only **authority** over pool status, and relaxes only on a conclusive, current, positive proof.


Add one stronger check, and let the existing authority (the quota poller) weigh it: a **fresh-process proof**. Start a new Claude Code process on the login's own folder and make one real, minimal model call. This is the same proof `/subscription-signin` already names as the definition of signed in ("a real authenticated call must work").

### D1. The probe: a contained, real authenticated call on the stored login

`QuotaPollerDeps.freshLoginProbe?: (account: { id; configHome }) => Promise<FreshProbeResult>`, where `FreshProbeResult = { verdict: 'ok' | 'refused' | 'unavailable' | 'not-run'; reason: string; at: number }`.

Wired in `server.ts` as a closure that reads the live switch on every call (D6). It is built next to the existing `claudeKeyProbe` and reuses its pieces:
- **Arguments:** `-p "Reply with OK." --model <resolveCliFlag('fast')> --max-turns 1 --tools '' --output-format stream-json --verbose --setting-sources '' --strict-mcp-config --mcp-config '{"mcpServers":{}}' --settings '{"disableAllHooks":true}' --no-session-persistence --disable-slash-commands`. No tools, no MCP servers, no hooks, and NO settings sources at all (`--setting-sources ''`, verified to run on Claude Code 2.1.329 on 2026-11-20), so neither the login folder's `settings.json` nor any project settings can supply an `env` block or an `apiKeyHelper`, and no transcript written into the login folder. TokenLedger therefore sees no transcript, and the feature-metrics row below is the only record (no double count).
- **Environment:** start from `process.env`, delete every name for which `isCredentialEnvName()` is true, and also delete `ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, `CLAUDECODE`, `CLAUDE_SESSION_ID`, every `CLAUDE_CODE_USE_*` (Bedrock, Vertex and other third-party providers), every `ANTHROPIC_BEDROCK_*` / `ANTHROPIC_VERTEX_*`, and `AWS_PROFILE`. Then set `CLAUDE_CONFIG_DIR` to the account's ROUTED folder (`accountForReads(account).configHome`, the same folder the poller reads the credential from), never the raw enrollment `configHome`. The only credential the probe can use is the login folder's own stored one.
- **Proof the login authenticated:** the stream's first line (`type: system`, `subtype: init`) carries `apiKeySource`. It must be `none` (no API key or env token was used), AND the same line's `served_by_anthropic` must be `true` (first-party Anthropic, not a third-party provider). Anything else gives the verdict `unavailable` (reason `non-login-auth`). Verified on the Studio on 2026-11-20 (Claude Code 2.1.329): a stored-login call reports `apiKeySource: "none"` and `served_by_anthropic: true`, and the full containment flag set runs successfully. The captured output is committed as test fixtures.
- **Accepted risk:** the probe is one more process that may write `<configHome>/.claude.json` while live sessions write it too (a known concurrent-write hazard in that file). `--no-session-persistence` and the fixed working directory keep its writes minimal, and the probe runs at most 6 times per account per 12 h.
- **Fixed working directory:** `<stateDir>/state/fresh-login-probe/` (created once), so `.claude.json` gains at most one project entry, never one per probe.
- **Spawn budget and reservation order:** the call goes through `wrapIntelligenceWithSpawnCap` (the host-wide spawn semaphore), as `claudeKeyProbe` does. The per-account reservation (D1b) is written INSIDE the semaphore's admitted callback, immediately before the process starts, and the process starts only after that write commits; if the write fails, the slot is released and nothing spawns. A shed (host at its cap) never reaches the callback, so it reserves nothing and returns `not-run`. No separate concurrency cap is invented.
- **Timeout** 30 s, the same as `claudeKeyProbe`'s `PROBE_TIMEOUT_MS` (a one-turn call measured on the Studio on 2026-11-20 took 1.7 s, `duration_ms: 1673`). This holds a host spawn slot for at most 30 s.

Verdicts, read from the stream's final `type: result` line (the same JSON object `--output-format json` returns), never from the reply's wording:
- `ok`: exit 0, `type: result`, `subtype: success`, `is_error: false`, `num_turns ≥ 1`, at least one entry in `modelUsage`, `usage.output_tokens > 0`, and the login authenticated (above). The model produced a reply through the stored login, whatever the words were.
- `refused`: `classifyClaudeAuthFailure(<result line>)` returns `rejected` (Anthropic's 401) or `no-auth`. Both existing readers (`classifyClaudeAuthFailure`, `isUsageLimitOutput`) parse ONE JSON object, so the probe passes them only the final `type: result` line, never the whole multi-line stream. A not-logged-in run reports `subtype: success` with `is_error: true` (captured fixture), which is why `ok` requires `is_error: false` and never relies on `subtype` alone.
- `not-run`: a spawn-cap shed (an error for which `isCapacityUnavailable(err)` is true; any other thrown error is `unavailable`), or the result line is the CLI's usage-limit wording (`isUsageLimitOutput`). An account at its usage limit is not evidence either way about its login. A usage-limit answer was a real spawn, so it counts toward the ceiling and is treated like `unavailable` by the scheduler: it takes a backoff step and counts toward the breaker (D1b). Four usage-limit answers in a row therefore trip the 24 h breaker and raise one degradation.
- `unavailable`: anything else (timeout, spawn failure, non-JSON output, network error, non-login auth).

Raw stdout and stderr are never logged. Only the verdict, the reason token and the exit code are logged.

**Token accounting (Token-Audit Completeness).** Each probe that ran records one row: `featureMetricsLedger.record({ feature: 'QuotaPoller.freshLoginProbe', kind: 'llm', outcome, tokensIn, tokensOut, tokensCached, latencyMs, model: <the resolved id from modelUsage>, framework: 'claude-code', door: 'claude-code-cli' })`, where `outcome` is `fired` for `ok`, `noop` for a usage-limit `not-run` (it ran and concluded nothing), and `error` for `refused` or `unavailable`. `feature` IS the attribution component (`FeatureMetricRecord.feature` is documented as `IntelligenceOptions.attribution.component`); this call does not go through an `IntelligenceProvider` because it must run on a specific login folder, so the row is written directly at the call site, and the attribution lint is satisfied by the component string. Tokens come from the JSON `usage` field and are left unset when absent (never a fabricated zero). A `not-run` shed records `outcome: 'shed'` with no tokens.

### D1a. The probe must not cause what it detects

A fresh process whose stored access token is expired or about to expire refreshes it, which rotates the refresh token and could strand the other sessions on that login. That is exactly the failure being diagnosed. Note the scale of this risk: a probe is one more Claude Code process on the login, which is what instar already does every time it places a new session there, and sessions refresh as a matter of course. The probe adds no class of rotation that normal placement does not already cause. It is still kept out of the refresh window as far as instar can tell:
- **Probe only with time left on the stored access token.** The probe closure reads the stored `expiresAt` through the existing `CredentialStore` read that `OAuthRefresher` uses (`ClaudeOauth.expiresAt`); the QuotaPoller's token resolver, which returns only the token string, is unchanged. A probe runs only when `expiresAt − now ≥ 15 min`, a margin wider than the CLI's own pre-expiry refresh window. When expiry is unknown or inside the margin, the verdict is `not-run` (reason `token-near-expiry`), and today's behaviour applies.
- **A credential change during a probe is unattributable, so it has one outcome:** the result is discarded (`stale-probe-result`, through the commit-time check below). A sibling session's ordinary refresh and a probe-caused refresh look identical from before/after reads, so neither is treated as proof of the other and probing is never switched off for it. If the change happened while `expiresAt` was already inside the margin (which D1a prevents), it counts as `unavailable` for the breaker.

### D1b. Scheduling and brakes (No Unbounded Loops, Capacity Safety)

State is kept per **account** (not per fingerprint, so a rotation cannot reset it), holding the last verdict, its fingerprint and time, a consecutive-`unavailable` count and a spawn log.
- **A conclusive verdict is final for its credential.** After `ok` or `refused`, the account is not probed again until its stored fingerprint changes, OR newer contrary evidence for the same credential arrives: the poller's own usage read returning an authentication failure invalidates a cached `ok`, and a successful authenticated usage read does NOT invalidate a cached `refused`. A new pane sighting is not newer evidence; it is the very signal being tested.
- **`unavailable` backs off:** 30 → 60 → 120 → 240 min. After 4 consecutive non-conclusive spawned results (`unavailable`, or a usage-limit `not-run`) the breaker trips: probing stops for that account for 24 h or until its fingerprint changes, whichever comes first (the breaker is persisted, so a restart does not clear it), and one `DegradationReporter` event is raised. With the breaker counting usage-limit answers too, an account stuck at its limit is probed at most 4 times per 24 h after the first conclusive-less run, not 6 per 12 h indefinitely.
- **`not-run` from a spawn-cap shed** changes no counters and no state; the next sighting or poll may try again, after at least 5 min. (A usage-limit `not-run` takes a backoff step, above.)
- **Hard ceiling, whatever the outcomes:** at most **6 probe spawns per account in any rolling 12 h**. This bounds even an adversarial mix (ok → credential change → refused → change…) and is the settling bound tested below.
- **One in flight per account** (the promise is shared). The host spawn cap bounds concurrency across accounts.
- **Persisted, and reserved before launch:** a spawn's timestamp is written BEFORE the process starts. All writes to the file go through one in-process serial queue (the server is the only writer), each write replaces the file atomically (write a temp file, then rename), and a probe launches only after its reservation write has committed. Concurrent reservations for different accounts can therefore never drop each other. The per-account spawn timestamps, consecutive-`unavailable` count and breaker state are written to `<stateDir>/state/fresh-login-probe.json` (small, bounded to the last 12 h of timestamps per account), so a server restart, or a restart loop, cannot reset the ceiling. Cached verdicts stay in memory: after a restart the first sighting probes again, which counts against the persisted ceiling.
- **The ceiling counts every spawn, whatever its verdict**, including a `not-run` usage-limit answer. A login that keeps answering at its usage limit is therefore probed at most 6 times per 12 h. The ceiling is a rate bound (≤ 12 tiny calls per account per day while sightings persist), and that rate is the settling guarantee across renewed windows.

**Applying a result (validate, then cache, then apply).** Each account carries `lastContraryAt`: the time of the latest evidence AGAINST a cached `ok` for its current credential. That is a fresh process failing after an in-place refresh (D4), the poller's own usage read answering an authentication failure, or a credential change. A probe records its start time, its routed-slot fingerprint and the live switch. When it completes it is checked FIRST: if the fingerprint changed, the switch is off, or the probe started before `lastContraryAt`, it is discarded (`stale-probe-result`) and NOT cached. Only a result that passes becomes the cached verdict, and only a cached verdict is ever applied. A status change the poller makes itself (for example the mark at the end of D2's wait) is not contrary evidence, so a probe answering `ok` after that mark still releases the hold its own wait created (D3).

**Conclusive verdicts expire.** A cached `ok` or `refused` holds until the credential changes, contrary evidence arrives (for `ok`), or 12 h pass, whichever comes first. A past `refused` therefore never stands forever against a provider-side recovery.

### D2. Before marking (in `observeCliLoginExpired`)

`observeCliLoginExpired` keeps its signature and gains an optional `{ awaitProbeMs?: number }`. It has three callers in `server.ts`, and each states its wait:
- **The rerouted-session sink** (`server.ts` ~17982, fed by `SessionManager`'s rerouted-login-expired path for one-shot/job sessions). It already calls fire-and-forget (`void`), so it passes `awaitProbeMs: 20_000`: nothing waits on it, and it no longer marks before the probe can answer.
- **The interactive recovery** (`server.ts` ~17989, `InteractiveLoginExpiredRecovery`), which passes `awaitProbeMs: 20_000` (D4).
- **NeverSilentWatcher** (`server.ts` ~20451). It is NOT only a notice: its `engine-login` path can feed `decideNeverSilentAction`, which may return `swap` (another account) or `fallback` (another engine). It passes `awaitProbeMs: 0` and receives the `probe` disposition. With `pending`, or with `ok` WHILE the recovery has an in-place refresh pending or still possible for THIS session, it takes no swap or fallback and does not mark the account; its action for that tick is `wait` (the person gets the ordinary waiting notice, not silence). The recovery exposes, per session, whether an in-place refresh is in progress or still allowed (not failed, within the per-session and per-account bounds, ownership held, session eligible). If the refresh failed (`refresh-failed`), was refused by a bound, or the session is not one the recovery handles, NeverSilent records a session-scoped fall-through and acts exactly as it does today, even with a cached `ok`. The suppression also has an absolute clock: for one incident (NeverSilent's existing per-conversation incident, the one `GET /never-silent/incidents` lists), NeverSilent holds off for at most **3 minutes** from its first `wait`, WHATEVER the refresh state: not started, started, stalled, or reporting success while the session still has trouble. After 3 minutes it falls through and acts exactly as today. The first-`wait` time is stored on the persisted incident record (`NeverSilentStore`), so a server restart or restart loop cannot restart the 3 minutes; the new waiting notice is an instar notice and never closes the incident (only a real delivered reply does). A refresh that works ends the incident by itself (the session answers). So the hold-off is never longer than 3 minutes per incident, never the 12 h verdict life. (Basis for 3 minutes: the recovery runs after the monitor's 1-minute dwell and waits at most 20 s for the probe, so a refresh that is coming normally starts and finishes well within 3 minutes; a missed or stalled one costs the person at most 3 minutes before today's handling.) The waiting notice for this case gets its own wording ("Restarting this conversation on its own sign-in"), not the generic still-working text. Wiring: the `observeLoginExpired` dependency returns `{ reason, probe }`, and `decideNeverSilentAction`'s policy input gains `loginProbe` and `inPlaceRefreshPossible`. With no cached verdict and no probe running, it starts one (wait 0) and treats the result as `pending`. Only on `refused` or `inconclusive` does it proceed as today. So NeverSilent never marks the account, opens a repair or moves the session while a probe for that credential is running. The recovery and the rerouted sink are the only callers that mark, and only when their own 20 s wait ends without an `ok` (the recovery then is not run any swap while the probe is still `pending`, D4).

Callers within the same moment share one probe per account (one spawn). D2's probe and disposition logic also runs on the existing `already-held` path (an account already needs-reauth for this cause), which today returns before `markNeedsReauth`.

After the stored credential is found to read, and before `markNeedsReauth`, with the live switch on:
1. If a cached conclusive verdict exists for this credential (D1b), use it.
2. Otherwise start a probe (or join the account's in-flight one) and wait up to `awaitProbeMs` (the recovery passes 20 s, below the probe's own 30 s timeout; a one-turn call measured 1.7 s on the Studio on 2026-11-20). The route observer passes the same value, so whichever caller arrives first starts the probe and both share it.
3. Decide, and return an explicit `probe` disposition alongside the existing fields: `'ok' | 'refused' | 'pending' | 'inconclusive'` (`pending` only while a probe for this account is still running; `inconclusive` for a completed `unavailable` or `not-run`, the ceiling or breaker reached, or the switch off):
   - `ok`, and the account is currently `active` or held only for `cli-login-expired-observed` ⇒ do NOT mark and do NOT set a hold; if the account is already held for this cause, release it here through D3's path (this call does not wait for the next poll). Return `{ marked: false, reason: 'stale-process', staleProcess: true, accountStatus }`, and log the screen time and the probe time together: `[QuotaPoller] account X: session S showed an expired login at T1; the stored login answered a real call at T2 — treating S as holding a stale token (the stored login passed the probe; why S failed is not proven)`.
   - `refused` ⇒ mark + hold (today). **A pane mark never weakens an existing bench:** if the account is already `needs-reauth` for another, stronger cause (for example `still-authfailed-after-refresh`), the pane path leaves that latest-mark cause in place rather than overwriting it with `cli-login-expired-observed`, so a later `ok` cannot release it.
   - No verdict within the wait (`unavailable`, `not-run`, the switch off, or still running) ⇒ mark + hold (today, the floor). A probe still running keeps running, and if it lands `ok` it releases the hold through D3, and D4's re-offer then refreshes the session in place.

With the switch off, steps 1–2 are skipped entirely (no cached verdict is consulted). That is exactly today's behaviour.

### D3. Releasing a hold (when a probe lands, and on each poll)

When a probe's `ok` is applied (commit-time check passed, live switch on) for an account whose CURRENT status is `needs-reauth` with `statusCause` `cli-login-expired-observed` (the poller records the cause of each account's LATEST mark; today `markNeedsReauth` only logs it, so this record is new. Any mark for another cause, such as `still-authfailed-after-refresh`, overwrites it, and this path restores an account only while that latest-mark cause is `cli-login-expired-observed`):
- Delete the hold under BOTH keys `pollOne` checks (`attributedId` and `account.id`). Log `expired-login hold released (the stored login answered a real call)`.
- Restore the account to `active` through the same path a hold-free authenticated poll uses. `loginCheck = ok`.

`pollAccount` itself never awaits a probe. During an active hold with a successful usage read, it applies a cached `ok` for the current credential if one exists and the live switch is on. Otherwise it starts one (subject to D1b) in the background and keeps today's behaviour for this poll. `pollAll` gains an in-flight guard, so overlapping passes cannot start while one is running.

Once the account is `active`, the reissue sweep's existing `completeIfAlreadySignedIn` closes the stale pending login on its next tick: it still requires its own live identity read, so it can never close a login that is genuinely broken.

### D4. The stuck session restarts on its own login

The session that showed the screen is stuck on that screen (whatever the exact cause in its process); a fresh process on the same stored login is the remedy the evidence supports. Today the recovery moves a session only when the pool says `needs-reauth`, and moves it to ANOTHER account through the quota-pressure swap. That swap excludes the source account, and when no alternate exists it raises a false "every account is at its usage limit" attention item. For a stale process neither is right.

Change in `InteractiveLoginExpiredRecovery`:
- The `observe` dependency's result type gains `staleProcess?: boolean`. A new dependency `refreshInPlace(sessionName): Promise<{ ok: boolean; reason?: string }>`, wired in `server.ts` to `SessionRefresh.refreshSession({ sessionName, reason: 'stale-login-token', fresh: false, configHome: <the session's own account's routed folder>, accountId: <the session's own account>, callerClass: 'recovery' })`. The conversation resumes rather than starting over. Passing the session's own `configHome` and `accountId` is required: without them `refreshSession` relaunches under the parent's login, which would silently move the session. `callerClass: 'recovery'` is the existing class for a server-internal restart. With `configHome` equal to the session's current folder, `refreshSession`'s account-swap preparation (`ensureInteractiveReady`, `placeResumeTranscript`) acts on the same folder and changes nothing; a test covers that, restarts the session's process and resumes its conversation on the SAME account. A new dependency `stillShowsExpired(sessionName): boolean` re-reads the pane with the same parser the monitor's dwell uses.
- At observation the recovery captures the session's identity: its tmux session name, its native Claude session id, its pane process id and its routed account. Immediately before dispatching ANY refresh or swap after the wait, it re-reads all four, re-reads the pane (the CLI's expired line must still be the latest message) and re-checks conversation ownership, and acts only if all hold. Otherwise it does nothing (`session-changed` or `not-showing`). A session relaunched under the same name, or moved to another account, during the wait is left alone (`outcome: 'session-changed'`).
- The recovery passes `awaitProbeMs: 20_000` to `observe`, so on the FIRST sighting it already knows whether the process is stale before choosing between refresh and swap.
- When `staleProcess: true` and the live switch is on: if the pane no longer shows the CLI's expired line as its latest message ⇒ `outcome: 'not-showing'`. Nothing is done and nothing is claimed about the session's health; the monitor's existing detectors still watch it, and a reappearing screen is a new sighting. Otherwise ⇒ `refreshInPlace`, under the existing per-session cooldown and attempt budget, plus a per-account bound of at most 3 in-place refreshes per account per 10 min. That bound sits above `SessionRefresh`'s own per-window limit (5 per 10 min, across all sessions), so the stricter of the two applies. Outcome `refreshed-in-place` when `refreshInPlace` returns `ok: true`. When it returns `ok: false`, the outcome is `refresh-failed`: the original process was not replaced, so its screen reappearing is NOT a second process failing and is not contrary evidence; the next re-offer may try the refresh again within the bounds, and after the per-session attempt budget the existing swap path applies. The refresh is only dispatched when this machine still OWNS the conversation: the same placement/lease ownership check the session manager uses before acting on a topic session must pass at dispatch time. A live local tmux session alone is not proof (it can outlive a lease transfer). A conversation that moved during the wait is left to its new owner.
- `probe: 'pending'` ⇒ the account is marked and the session is NOT swapped yet. The recovery returns `outcome: 'probe-pending'`, and the monitor's existing re-offer after the retry interval re-runs `handle`, by which time the probe has landed.
- `probe: 'refused'` or `'inconclusive'` ⇒ today's path (mark + existing swap). So a swap happens only when the stored login was shown dead or could not be checked, never while a check is still running, and a stale process proven stale is never moved to another account's quota.
- **Account and session outcomes are decided separately.** If the same session shows the screen again after a SUCCESSFUL in-place refresh (its native session id or pane process id changed, so a replacement process is the one showing it), the SESSION takes the existing swap path (it has now failed twice on this login, so it is moved). For the ACCOUNT, the repeat screen counts as contrary evidence (`lastContraryAt` is set, so the cached `ok` is dropped and the account is marked as today). The account's status then follows the next probe on its own merits: if a later probe answers `ok`, the account is usable again for other sessions, but that does not undo the session's move. Two fresh processes disagreeing about one login never flips the session back and forth.
- The `not-confirmed` early return now exempts `staleProcess`. The stale-process branch runs BEFORE the existing `swap-disabled` check (`subscriptionPool.loginExpiredSwap.enabled`), because an in-place refresh is not a swap: turning account swaps off does not stop a stale session from restarting on its own login. The live switch that governs the new branch is `subscriptionPool.freshLoginProbe.enabled`. Protected sessions remain excluded. The quota-pressure swap and its no-alternate notice are never used for a stale process.

### D5. Bounds summary (Bounded Blast Radius)

- At most 6 probe spawns per account per rolling 12 h. Probes run only while a sighting or hold exists for that account, and never concurrently for one account. Concurrency across accounts is held by the host spawn semaphore.
- Each probe is one `fast`-tier turn with no tools, metered in the feature-metrics ledger.
- At most 3 in-place session refreshes per account per 10 min, plus the existing per-session cooldown.

### D6. Switch and rollout

`subscriptionPool.freshLoginProbe.enabled`, read on every call through `liveConfig`. **Default on everywhere** (User-Facing Fixes Ship Live): this is the fix for an operator-visible fault (a working account benched, a sign-in restarting itself), and every failure path of the probe falls back to today's behaviour. Its cost is bounded (at most 12 one-turn calls per account per day, only while an account shows an expired screen). The CMT-1438 dev-gate convention is for new capabilities; this change only narrows an existing false positive. `false` ⇒ nothing is probed, no cached verdict is read, and D4's new branch is never reached, which is exactly today's behaviour. The key is not registered in `devGatedFeatures.ts`. Like the neighbouring `subscriptionPool.loginExpiredSwap.enabled`, its default lives in code (an absent key reads as on), so existing agents get it with the update and no config migration is needed; an operator `false` in config is honoured live.

## Decision points touched

| Decision point | Classification | Floor / justification |
|---|---|---|
| Pane sighting with a readable credential: mark needs-reauth or not | judgment-candidate | Floor: today's behaviour (mark + hold) is the default and the last rung. The arbiter is the probe: a real authenticated call through the stored login (the proof `/subscription-signin` defines as signed in), in the same contained shape as `claudeKeyProbe`. The action space is bounded to {mark + hold, do not mark}. Only a cached conclusive `ok` for the current credential relaxes. |
| Hold release on a landed `ok` | judgment-candidate | Same floor and arbiter. The validate-before-cache check (fingerprint, `lastContraryAt`, switch) discards stale results. |
| Stuck session: refresh in place vs swap vs nothing | judgment-candidate | Floor: the existing swap path for a confirmed dead login. Arbiter: the cached probe verdict plus a fresh pane re-read. Bounded action space {nothing (recovered), refresh in place, existing swap}. Refresh-in-place is bounded per session (existing) and per account (3 per 10 min). |
| Probe verdict classifier | invariant; basis: enumerable-domain; evidence: the CLI's structured JSON has a closed set of fields (type/subtype/is_error/api_error_status/modelUsage/usage/apiKeySource); `classifyClaudeAuthFailure` and `isUsageLimitOutput` are the existing, tested readers of those fields, and every unrecognised shape maps to `unavailable` | A deterministic parse of the CLI's own structured verdict, never the model's wording. |
| Probe gating on token expiry (15 min margin) | invariant; basis: irreversible-consequence; evidence: a probe that refreshes rotates the refresh token, which can strand every other process on the login (the failure being fixed), and cannot be undone. The margin must exceed the probe's own worst-case duration (30 s timeout) plus the CLI's pre-expiry refresh window. That window is not published, so the margin is a generous guess and the residual risk is stated: a probe inside an unknown wider window is equivalent to placing one more session on the login (D1a), not a new failure class. The test pins only instar's gate against a recorded `expiresAt`. An unknown expiry fails closed to `not-run` | Fails toward not probing, which leaves today's behaviour in place. |
| Spawn ceiling (6 per account per 12 h, persisted) and unavailable backoff (30→240, breaker 4) | invariant; basis: external-constraint; evidence: Bounded Blast Radius (the 2026-06-20 fork-bomb incident came from unbounded `claude -p` spawns). With conclusive verdicts final per credential, a healthy or dead login needs 1 probe per credential; 6 per 12 h allows 1 conclusive + 4 unavailable + 1 retry after a credential change, and the 240 min ceiling keeps the four retries within one 12 h hold (30+60+120+240 = 450 min < 720) | Ceiling reached ⇒ `not-run` ⇒ today's behaviour. |
| In-place refresh bound (3 per account per 10 min) | invariant; basis: external-constraint; evidence: each refresh spawns one session process; on a login shared by several sessions, one rotation can strand several sessions at once, and 3 per 10 min lets each of the typically 1–3 stranded sessions restart once per cooldown window while bounding a storm | Over the bound ⇒ the session waits for the next window; nothing else changes. |

## Frontloaded Decisions

1. **Probe model:** the `fast` tier through `resolveCliFlag('fast')`, as `claudeKeyProbe` does. It proves the credential, not quality.
2. **Unavailable, not-run and disabled all mean conservative:** a probe that cannot conclude never relaxes the hold.
3. **Ships live, with a live off switch:** default on everywhere (D6), because it narrows an existing operator-visible false positive and every failure path is today's behaviour.
4. **The stale session is refreshed in place on its own account**, never moved by the quota-pressure swap.
5. **Codex is out of scope:** the hold is Claude-only (`observeCliLoginExpired` only considers `claude-code` accounts), and Codex already has its own live app-server read.
6. **The genuinely-dead-login re-mint loop is not this spec's to fix.** When a login really is dead, the reissue sweep re-mints its pending code on expiry. That journey is owned by `docs/specs/stale-followme-login-reissue.md` (the existing reissue work) and is unchanged here. This spec removes the false-positive cause of the loop.
7. **CMT-1008 stays as the floor.** One pane screen with a readable credential still marks when no conclusive probe verdict exists. Dropping that rule would let sessions keep being placed on a truly dead login until a probe concludes. With this change the floor only applies for the seconds before the first probe lands, or when probing cannot run (and then it is loud: the breaker raises a degradation).
8. **Preventing rotation stranding at its source is out of scope** (that would mean every session re-reading the stored credential on a 401, inside Claude Code itself, which instar does not own). This change detects it and recovers from it.

## Multi-machine posture

machine-local-justification: physical-credential-locality

Machine-local by design: a login folder and its stored credential physically live on one machine, and each machine's poller probes only its own slots. The probe's effect is not invisible to other machines: the resulting pool `status` (active vs needs-reauth) already replicates through the existing pool-scope read (`projectAccountToMeta`), so a release on one machine shows on every machine's Accounts page, as any status change does today. No new state, notices or URLs. No status surface changes. Follow-me copies of one account on other machines hold their own credentials: `AccountFollowMeOrchestrator` defaults to the `re-mint` mechanism (a fresh login minted on the target machine), and `credential-transport` needs an explicit allowlisted mandate. Where a mandate did transport one token to several machines, D1a's expiry gate reduces the chance that a probe refreshes (and so rotates) the shared token; it does not eliminate it, as stated in D1a.

## Maturation plan

- **test-agent-live:** a throwaway agent with one pool login. Force a stale-process screen by running a long-lived session, refreshing the stored login from a second process, and letting the first session hit its next turn. Observe: no needs-reauth mark, `[QuotaPoller] ... stored login answered a real call` in the log, the session refreshed in place, one feature-metrics row. Then remove the login's credential and confirm the probe answers `refused` and today's mark + swap path runs.
- **dev-agent-live:** on the Echo development agent (default on) for one week. Watch the feature-metrics rows for `QuotaPoller.freshLoginProbe` (count, verdict mix, tokens), the `stale-probe-result` and breaker log lines, and NeverSilent incidents with the new waiting notice. Any `ok` followed within the hour by a `refused` for the same unchanged credential is investigated before graduation.
- **fleet:** the switch defaults on in `ConfigDefaults`, so the fleet receives it with the release; there is no separate flip. If the dev-agent week shows a wrong `ok`, the code default is flipped to off in the next release (and operators can set `false` live meanwhile).
- **graduation criterion:** on the development agent, at least one real expired-screen sighting resolved by a probe `ok` without a needs-reauth mark, with no wrong `ok` (an `ok` contradicted by a `refused` on the same unchanged credential within an hour) and no breaker trip caused by the probe's own behaviour. A zero sighting count is not a pass: if none occurs naturally in the week, the test-agent scenario is re-run on the development agent and counts once.
- **dark-window:** none. It ships live, because it narrows an existing operator-visible false positive and every failure path is today's behaviour. The criterion is judged within 14 days of merge; the result and any switch change are recorded on the tracking action, never left unresolved.
- **ladder:** not applicable: a fix that ships live by default, the live off switch is the rollback (test agent, then development agent week, as above)

## Rollback

Pure code change. Set `subscriptionPool.freshLoginProbe.enabled: false` (read live) and every probe answers `not-run`, which is exactly today's behaviour. Reverting the commit does the same. Persistent state is small and harmless: `<stateDir>/state/fresh-login-probe.json` (spawn timestamps and breaker per account) and the fixed probe working directory with its single `.claude.json` project entry. The cached verdicts and the hold stay in memory. With the switch off, the file is never read or written.

## Awareness

`INTERACTIVE_LOGIN_EXPIRED_BULLET` (`src/scaffold/templates.ts`) currently states that a later quota poll does not flip the account back while the saved credential is unchanged, which becomes false. The bullet text is edited to say: one session's expired screen is first checked against the stored login with a real call; if that works, the account stays usable and only that session is restarted on the same account; if it fails, or cannot be checked, the account is marked and the session moved as before. Existing agents get the change through a `PostUpdateMigrator` step that replaces the exact previous bullet text with the new one, in place, so `CLAUDE_KEY_HEALTH_BULLET` (anchored after it at the existing migrator lines) keeps its position. The previous text is kept as `INTERACTIVE_LOGIN_EXPIRED_BULLET_V1`, and the replacement step runs before the existing `CLAUDE_KEY_HEALTH_BULLET` insertion block, so that insertion anchors on the new text. The step is idempotent, does nothing when the old text is absent (a hand-edited copy is left alone), and is tested against a fixture of the real previous text.
