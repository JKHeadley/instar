# Project rows that say something

## 1. Problem

The Projects list on the Work door (`GET /work/projects`, `GET /mobile/work/projects`, `src/server/workProjectsRoutes.ts`) shows each project's goal, its done list and its cards, and one link to the conversation. The Chief of Staff knows much more and keeps it to itself:

- At every check it writes one plain sentence about the project (the judge's reason, stored as the check's `note`), for example "All six setup recipes are released; whether offers are switched on for real agents is unreadable, so done is unconfirmed." The row shows that sentence only when the state is "Not known yet".
- It marks a project "Waiting on you" but the row never says what for.
- It knows which done items are automatic checks and which only the owner can judge, but the row shows only pass / fail / unknown, so an owner-judged item reads "unknown" forever.
- It knows when the next check is due, and whether it stopped retrying after restarts without progress or because the weekly restart limit (the breaker) tripped. The row shows neither.

And the owner cannot act from the row: there is no "check now", no Pause / Resume (the only pause path is the agent asking in Telegram with a cited owner message and the owner tapping a button, `cos-owner-pause-record`), and no way to say "this judged item is done" short of the whole-project "Confirm it's done" button in the Chief of Staff's note.

## 2. What already exists

- `ChiefOfStaffLoop.projectsOverview()` (one union read, every bound project with its verdict, last check, done list, done-item results, owner pause and newest check note). `projectsSummary()` computes `nextCheckAt`, `nextActionAllowedAt`, `restartsWithoutProgress`, `breakerTripped` from the same fold (`foldProjectCheckState`).
- `checkProject()` (private): gather evidence, judge, record a check-event, act (restart / redirect under the action protocol's backoff and the lease), queue note lines. Run only by `tick()` on the serving-lease holder; `markDirty()` makes a project due on the next tick if its last check is at least `dirtyGapMinutes` (30) old.
- Owner pause store and fold (`owner-pause` / `owner-resume` lifecycle events, `by: 'owner-tap'`, fields `who`, `quote`, `messageRef`, `askId`; newest by HLC wins; an `askId` decides once). `planDue`, `derivedNeeds`, the action protocol's in-lock fence and the liveness reconciler all honour `pausedBy` (`cos-owner-pause-record` §3.3). That spec names "a device-signed owner control in the Instar app" as the stronger proof it did not build (fb-0ac4fffb-148).
- The phone write gate (`src/server/mobilePermissionsRoutes.ts`, `docs/specs/mobile-native-permissions.md` §3.3): only an active owner phone, over local TLS, with a configured console PIN and an enrolled presence key, signs `POST /mobile/permissions/challenge {action, target, …}` to get a single-use challenge bound to one exact action line, then sends the write with `challenge` and `presenceSig` (Face ID / Touch ID over `permissionPresenceMessage(deviceId, host, challenge, line)`). Work-card taps, approvals and (in PR #3374) "make a card" and "make this group a project" use it.
- The device allowlist (`DEVICE_ALLOWLIST` in `src/server/mobilePairingRoutes.ts`): each phone route, owner-only or a team tier, with its rate bucket.

## 3. Design

Words: the **serving lease** is the machine-wide lease that decides which machine runs the Chief of Staff's ticks (`holdsLease`); the **check-in lease** is the owner's Chief of Staff check-in (`lease.live`, renewed by an owner check-in), without which the Chief of Staff takes no action.

### 3.1 The row (read; showing these is already approved)

Every field below is additive on `ProjectRow`; no existing field changes meaning (`done.items[i].state` stays the evidence result, `done.met` stays the count of passing items), so the console's current model (`dashboard/console/projects-model.js`) keeps working. `schemaVersion` stays 1: every field is additive, and a client detects the new ones by the presence of `actions`. All words are server-written, so every surface says the same thing. No field is cut on the server: the check note is already bounded at 500 characters when stored, and item text at 2000 by the binding validator; a client that shortens text for layout shows an expand.

```
latestReport: { text: string, at: ISO, confirmed: boolean } | null   // §3.1.1
waitingOnYou: { why: string, items: string[] } | null                // only when state is 'waiting-on-you' (§3.1.2)
checks: { last: ISO | null, next: ISO | null, nextWords: string | null, here: boolean, requested: { eligibleAt: ISO } | null }
stopped: { reason: 'no-progress' | 'breaker', restarts: number, words: string } | null
paused: { at, quote, via: 'app' | 'telegram' } | null    // unchanged shape plus `via`
bindingRef: string            // the done list's version, signed by Finish (§3.5)
done.items[i]: { id, text, state, kind: 'check' | 'owner-judged' | 'agent-may-certify', stateWords, checkedByYou: { at } | null, canMark: boolean, checkRef }
done: { …, checkedByYou: number, waitingForYou: number }
actions: {
  checkNow: { allowed: boolean, why: string | null, notBefore: ISO | null },
  pause: 'pause' | 'resume' | null,      // the one toggle that applies; null when done
  finish: { allowed: boolean, why: string | null },
}
```

**3.1.1 `latestReport`.** The newest check note that says something (a carried-forward "no new evidence" is skipped, as `projectsOverview` already does), whitespace collapsed, never cut by the read. (The loop stores at most 500 characters per note; that store-time cut now ends at a word with an ellipsis, so a cut note shows that it was cut.) It is a report of where the project stands, not an instruction, so it is named that, and it carries the check's verdict honestly: `confirmed` is false when that check's recorded verdict is `unknown` (the floors refused the judge's reading, or the evidence could not be gathered); the words are then shown as "Not confirmed: <text>" by the server-written `text`. Reason codes the loop writes itself are mapped to words: `gather-failed` → "The last check could not read the project's evidence."; `owner-confirmed` → "You confirmed it is done."; `every deterministic done item passes` → "Every automatic check passes."; `every deterministic done item passes; judgment items pending` → "Every automatic check passes; the items only you can judge are waiting for you."; any other bare `word-word` code → "The last check could not run." `null` when there is no check yet. The existing `why` field (Not known yet only) is kept as is.

**3.1.2 `waitingOnYou`.** `items` are the ids of the owner-judged items not yet checked by the owner (their full text is on `done.items`). `why`: when every automatic check passed at the last check and owner-judged items remain unchecked, "Every automatic check passes. It needs you to check <n> item(s)."; when every automatic check passed and every judged item is checked, "Every automatic check passes and you checked the rest. Tap Finish to close it."; (with no automatic items these read "There are no automatic checks; it needs you to check <n> item(s)." and "You checked the rest. Tap Finish to close it."); otherwise the latest report's text; when neither exists, "The Chief of Staff marked it as waiting on you but did not say why."

**3.1.3 Done items.** `kind`: `check` for a `deterministic` item; for a `judgment` item, `owner-judged` when its `certify` is `owner-confirms` (the default) and `agent-may-certify` when the owner delegated it at binding. The loop does not honour `agent-may-certify` yet (it pends every judgment item on the owner, per its own comment). So: an `owner-judged` item must be checked by the owner before Finish; an `agent-may-certify` item may be checked but need not be, and Finish confirms it, exactly as today's one-tap Confirm-done confirms every judgment item. The owner is never asked to do the delegated judgment item by item; the distinct kind keeps the delegation visible and stays correct when the delegated judge is built. `state` is the last check's result for a deterministic item and `unknown` for a judgment item (unchanged). `checkedByYou` is the owner's check (§3.3) or null. `stateWords`: check `pass` "Passes", `fail` "Fails", `unknown` "Not checked yet" when no check has run and "Could not be checked at the last check" when one ran and could not read it (an unknown is not a skip); owner-judged "Checked by you" or "Waiting for you to check"; agent-may-certify "Checked by you" or "You let me certify this; until I can, it waits for you". `canMark` is true for a judgment item on an open project. `checkRef` is the SHA-256 (hex) of the UTF-8 JSON array `[goal, id, text]` (`JSON.stringify`, so a newline inside the goal or the text can never shift a boundary between them), the value a Mark checked tap signs (§3.3): what the owner judged is that item in the context of that goal. The binding validator allows any short text as an item id and does not require ids to be unique; an item whose id is shared by another item in the same binding gets `canMark: false` and the words "This item's id is used twice in the done list, so it cannot be checked on its own; Finish still confirms it." (the fold could not tell the two apart).

**3.1.4 Checks.** `last` = `lastCheckAt`; `next` = the fold's `nextCheckAt`, computed with the same per-project jitter `tick()` uses (today `projectsOverview` and `projectsSummary` omit it, so a shown time could differ from the real one by up to 10%). `next` is null when paused or done. `nextWords`: "Paused, so it is not checked" when paused; "Finished" when done; "Checked on the next round" when there is no check yet; else null (the client formats the time). `here` is whether the machine answering holds the serving lease (§3.2). `requested` is set while a queued Ask for an update (§3.2) is newer, by HLC, than the last check; `next` then shows its first eligible tick instead of the cadence time, with `nextWords` "You asked for an update; checked on the next round", so the row and the 202 answer never disagree.

**3.1.5 `stopped`.** When the fold says `parked` (state `stopped-retrying`): `breaker` when `breakerTripped`, else `no-progress`; `restarts` = `restartsWithoutProgress`; words "I restarted it <n> times without progress, so I stopped. Unpark it from the Chief of Staff's note to let me try again." or "It hit the weekly restart limit, so I stopped. Unpark it from the Chief of Staff's note to let me try again." Unpark from the phone is not in this slice (Frontloaded Decision 6).

**3.1.6 `actions`.** From the same fold the action routes use. `checkNow.allowed` is false with words when paused ("It is paused.") or done ("It is finished."); `notBefore` is the time from which a tap runs at once instead of being queued (null when it runs at once now, and null when `checks.here` is false: on a machine that does not run checks every tap is queued). `pause` is `resume` when paused, `pause` when open, `null` when done. `finish.allowed` is true only when every automatic item's last result is a pass (true when the project has none), every `owner-judged` item that can be checked on its own is checked by the owner, and it is open (the read uses the last check's automatic results; the Finish route uses the same `finishTarget` test for the owner's checks and the binding, and re-gathers the automatic results at the tap, so a stale pass in the read can never close anything); otherwise `why` names what is missing ("<n> item(s) still need your check." / "Not every automatic check passes yet.").

The read stays owner-only (spec work-front-doors §4.4); a member's or guest's phone still gets the empty answer. The 10-second read cache is dropped after every write in §3.2–3.5, so the answer a route returns is fresh.

### 3.2 Ask for an update (no Face ID)

- `POST /mobile/work/projects/check` (owner phone, device-signed, allowlisted owner-only, its own bucket) and `POST /work/projects/check` (bearer, for the console and the agent). Body `{ key }`.
- Why no Face ID: it asks the Chief of Staff to do sooner what it does on its own every cadence, within the same authority and brakes. It approves nothing.
- "Done" everywhere in this spec is the binding's close record (`foldBindingState(...).closed`), never a verdict: a `done-verified` check under a lapsed check-in lease is still open (and takes Finish), and a reopened project is open even though its newest check says `done-verified`. Closed projects are not listed in the read; `checkNow` and the phone routes read the binding fold and answer 409 `done` for a closed one.
- The eligibility gap is one tick less one minute (`tickMinutes` default 15, floor 5, minus 60 s), the same for the run-now path and for a queued request's tick, so a tick that fires a few seconds early still honours a request one tick old.
- When the project's newest check is younger than the eligibility gap, or this machine does not hold the serving lease, or a tick is running here, the request is queued (next bullet) instead of run; it is never refused for timing. Basis: the most any request can do is make one project due on each tick, which is the loop's own fastest rate, and a check whose evidence has not changed carries the verdict forward without a judge call. Both callers (the owner's phone and the bearer) follow the same rule; the bearer is the agent's own path and costs at most what the phone does.
- On the serving-lease holder, when no tick or other check is running and the newest check is older than the eligibility gap: `ChiefOfStaffLoop.checkNow(key)` runs now — first `settleOpen` (as a tick does), then exactly `checkProject()` for that one project (evidence, the judge or the carried-forward verdict when nothing changed, the check-event written and made durable before any action, any restart or redirect under the action protocol's backoff, the breaker and the in-lock owner-pause fence; `leaseLive` and the grace-tick rule as `tick()` computes them; restarts share ONE budget with the ticks: the loop counts the restarts it started in the last gap, by ticks and by Ask for an update alike, and `restartsPerTick` caps that count, so requests on many stalled projects back to back cannot start more restarts than a tick may; a check over the budget still runs and records, and marks the project dirty, as a tick's does. The count is the holder's process memory (checks and restarts run only there), as the per-tick count is today; a restart of the process or a lease handoff starts it at zero, and the durable brakes still hold across that (the per-project backoff `nextActionAllowedAt` and the weekly breaker, both folded from records). A tick that fires while an Ask for an update is running is not dropped: it runs as soon as that check ends (they share the loop's one-at-a-time flag). 200 `{ ok: true, project: <fresh row> }`; 503 `not-recorded` when no new check-event landed.
- Queued: the request is recorded as a `check-requested` lifecycle event (`by: 'owner-tap'` from the phone, `'chief-of-staff'` from the bearer, the current `bindingHlc`, `at`), replicated like every Chief of Staff record. The holder's `planDue` treats a project whose newest `check-requested` is newer (by record HLC, not wall clock, so a machine whose clock runs ahead cannot keep a project due) than its last check-event as due on the first tick at which that last check is older than the eligibility gap — the same eligibility rule as the run-now path, so a request queued just after a check never causes a second check seconds later. 202 `{ ok: true, queued: true, eligibleAt, words: "The Chief of Staff will check it on its next round, within about <2 × tickMinutes> minutes." }` with the current row. The words are a promise about a running holder; the row's `checks.next` and `checks.last` show when a check actually happened. Nothing is lost on a standby and nothing runs twice: only the holder checks, and one check satisfies every request older than it.
- The queued record is made durable (`awaitDurable`) before the 202; 503 `not-recorded` when it was refused.
- Refusals: 503 `chief-of-staff-off`; 404 `no-project`; 409 `paused`, `done`. A second request while one is queued and not yet honoured answers 202 with the same words and writes nothing new.

### 3.3 Mark checked (Face ID)

An owner-judged (or agent-may-certify) done item gets "Mark checked"; a checked one gets "Uncheck". A check records the owner's judgment on that item; it never closes the project by itself (Finish does, §3.5).

- Challenge: `POST /mobile/permissions/challenge { action: 'project-item-check', target: <key>, itemId, checkRef, value: 'checked' | 'unchecked' }`. Line: `project-item-check <key> <checkRef> <checked|unchecked>`: the item is named by `checkRef`, which covers its id, so an id with spaces or any other character the binding allows never has to appear in the line. The key is checked with the store's own conversation-key rule (`isValidConversationKey`, which allows the upper case Slack ids `TARGET_PATTERN` refuses); `itemId` is any 1–64 character string (the binding's own bound); `checkRef` 64 lower-case hex.
- The challenge route gains a precheck hook for the three project actions (`projectTapRefusal`, injected like the trust lease check it sits beside) and runs the domain checks before it issues a challenge, so a known refusal never reaches Face ID: the project is bound and open (404 `no-project`, 409 `done`); the item exists and its id is not shared (404 `no-item`, 409 `duplicate-item-id`) and is a judgment item (409 `not-owner-judged`); the current goal and item text give `checkRef` (409 `item-changed`, "This item or the project's goal changed since you saw it. Pull to refresh."). The write route `POST /mobile/work/projects/done-item { key, itemId, checkRef, value, challenge, presenceSig }` runs them again after the proof and before writing.
- Record: a new `binding-lifecycle` event `owner-item-check`, `by: 'owner-tap'`, with `itemId`, `checkRef`, `itemChecked` (boolean), `who` = "owner", `at`, `messageRef` = `instar-app:<deviceId>`, `askId` = `app-<16 hex random>` (the tap's own nonce), and the current `bindingHlc`. The validator accepts it only with `by: 'owner-tap'`, a boolean `itemChecked`, a 64-hex `checkRef` and the short fields within the existing bounds; `itemId`, `checkRef` and `itemChecked` join `KNOWN_FIELDS`. Every proven tap is recorded, even when the local fold already shows that value (a decision made before replication arrives is never dropped, as `cos-owner-pause-record` §3.2 requires); durable (`awaitDurable`) before 200.
- Fold: `foldBindingState` adds `ownerChecks: Record<itemId, { at, who }>`, in this order: first, per item id, the newest event by record HLC wins, whatever content it was made on (so an uncheck made under other wording is never skipped, and a withdrawn check cannot return after a revert); then that newest event counts only if it is a check and the CURRENT goal, id and item text give its `checkRef`, so changing that item's wording or the project's goal voids its check, while edits to other items, the links or the cadence do not; an event older (by HLC) than the newest owner `reopened` event does not count, so reopening a finished project starts its judgments afresh; an `askId` already seen is ignored.
- The note's "needs your OK" block (`confirmItem`) lists only the judgment items not yet checked.

### 3.4 Pause and Resume from the phone (Face ID)

- Challenge: `POST /mobile/permissions/challenge { action: 'project-pause', target: <key>, value: 'pause' | 'resume', noteHash? }`. Line: `project-pause <key> <pause|resume> <noteHash|none>`, where `noteHash` is the SHA-256 (hex) of the optional typed note's exact UTF-8 bytes as sent (no trimming), at most `OWNER_PAUSE_QUOTE_MAX` (4096) characters, the store's existing quote bound.
- The challenge route checks the binding rule before issuing (as `requestOwnerPause`): a pause needs a confirmed, open binding (404 `no-project`, 409 `done`); a resume needs a confirmed binding that is paused, open or closed (409 `not-paused`). The write `POST /mobile/work/projects/pause { key, value, note?, challenge, presenceSig }` re-hashes the note, must match the signed line, and re-checks.
- Record: the existing `owner-pause` / `owner-resume` event: `by: 'owner-tap'`, `who` = "owner", `at` = now, `quote` = the owner's note when given, else "Paused in the Instar app." / "Resumed in the Instar app.", `messageRef` = `instar-app:<deviceId>` (only this route writes that prefix; a Telegram ask's `messageRef` is an attribution marker, `[source: …]`), `askId` = `app-<16 hex random>`. Every proven tap is recorded, even when the local fold already agrees. No new store field: the existing validator, fold, loop skip, execution fence and reconciler apply unchanged. Durable before 200.
- A Telegram pause ask outlived by a newer owner decision does nothing once that decision is visible: `ownerPauseTap` (on the Telegram callback machine) ignores an ask whose `sentAt` is older than the newest owner pause or resume event in its union, and clears it. A phone decision written on another machine reaches it by replication (normally seconds); a tap on the old button before then is still the owner's own tap on an ask they were shown, and is recorded as their newer decision (newest by HLC wins). Accepted: both are the owner's own acts, and the row always shows the current state. The comparison is of two machines' wall clocks (the ask's `sentAt`, the decision's `at`); the fleet's clocks are NTP-synced; under skew a newer ask can read as outlived (the owner sees "That action no longer applies." and the agent asks again) or an older ask can survive (its tap is still the owner's own decision, recorded as their newest).
- `paused.via` is `app` when `messageRef` starts with `instar-app:`, else `telegram`.
- Spec addition to `cos-owner-pause-record` (its §3.2 says only the Telegram tap pauses): a presence-signed tap on the owner's own phone is the owner's own act. It proves who (the active owner phone's enrolled presence key), what (one signed line naming the project, pause or resume, and the note's hash) and now (a single-use challenge bound to device, Host and that line), the proof that spec named as the stronger one (fb-0ac4fffb-148). The cited-message floor exists to stop the agent putting words in the owner's mouth when the agent asks; here the owner acts, so there is no cited message, and any words recorded are the owner's own typed note. The console PIN still cannot pause (unchanged, tested).

### 3.5 Finish from the phone (Face ID)

- Challenge `{ action: 'project-finish', target: <key>, bindingRef }`; line `project-finish <key> <bindingRef>`, where `bindingRef` is the row's `bindingRef` (the winning binding's HLC as `physical.logical.node`). Write `POST /mobile/work/projects/finish { key, bindingRef, challenge, presenceSig }`.
- Checks at challenge and again at write (the same `finishTarget` predicate the read's `finish.allowed` uses, plus the evidence gather at write): bound and open, `bindingRef` equals the current binding (409 `project-changed`), every `owner-judged` item checked by the owner (409 `not-all-checked`); `agent-may-certify` items, and items whose id is shared (which cannot be checked on their own), are confirmed by this binding-scoped tap, as Confirm-done confirms every judgment item today. A project of only automatic checks can be finished too (the close still needs every automatic check to pass on evidence gathered at the tap): that is the owner's way to close one whose `done-verified` check came while the check-in lease had lapsed. A paused project can be finished (Confirm-done is allowed on a paused project, `cos-owner-pause-record` Frontloaded Decision 9). A project with no automatic items is finished on the owner's checks alone: the parent rule ("every deterministic item passes now and every judgment item carries an owner tap") holds. Today such a project never becomes a Confirm-done candidate in the note (the loop's done-candidate test needs at least one automatic item), so it has no conversational close either; this change makes a judgment-only project that the judge reads as `claims-done` a Confirm-done candidate too, so the note offers its Confirm-done button in Telegram, the conversational equivalent of Finish (work-front-doors Frontloaded Decision 9).
- The note's Confirm-done line for a project with no automatic items says "says it is done; it has no automatic checks, so it needs your OK." instead of claiming automatic checks passed.
- A Finish tap is also a check-in (`checkIn({ renewedVia: 'app', principal: 'device:<deviceId>' })`, the record the phone's existing `POST /mobile/chief-of-staff/check-in` writes), made before the close, so an owner who has just used Face ID is never told to go and check in first. Pause, Resume and Mark checked taps count as a check-in the same way, as every Chief of Staff tap does (`cos-owner-pause-record` §3.2); a proven tap that is then refused (for example `item-changed`) still counts, since the owner did prove presence. The three Face ID routes share the device allowlist's `owner-presence` bucket (12 a minute) on purpose: it is the bucket for every owner Face ID tap.
- Then the existing owner Confirm-done steps (`ownerTap`'s confirm-done path, shared code): the check-in lease must be live, the deterministic items are re-gathered at the tap and must all pass, the `done-verified` check-event (owner-confirmed) is written and awaited durable before the lifecycle close, and the initiative is mirrored completed. After the last wait (the gather, then the durability of the verified check-event) and immediately before the close is written, with no wait between, the union is read again and the `bindingRef` and every owner check are re-verified; an Uncheck, Reopen or binding edit that landed during either wait refuses the close (409 `project-changed` / `not-all-checked` / `done`), leaving only the owner-confirmed check-event behind, as a failed Confirm-done does today. One that is written on another machine and has not replicated by then is not seen: accepted, because the close is the owner's own signed tap and Reopen undoes it. The close record carries the binding HLC it was verified against, so a binding edit that replicates in later voids the close as `foldBindingState` already does for every `closed` event. Each outcome is distinct (the shared steps return a reason, not one "ignored"): 200 with the row; 409 `checks-fail` with the failing items' text; 503 `gather-failed` ("I could not read the project's checks just now, so nothing closed. Try again in a minute."); 503 `not-recorded` when the verified check-event or the close record is refused or not durable (the close's own write is now checked and awaited, where today its outcome is ignored); 503 `union-unreadable` when the re-read after the gather fails; 503 `chief-of-staff-paused` only if the check-in write itself failed.
- Why a separate Finish instead of closing on the last item check: a close is the consequence, so the owner's signed line names it, and it happens at the tap against evidence gathered then, never weeks later against whatever a future check finds.

### 3.6 Where it runs

- The pause, item-check, finish and check-request writes are journal records (`chief-of-staff-record` store), replicated like every Chief of Staff record, written on whichever machine the phone reaches and folded by every machine. Checks run only on the serving-lease holder; elsewhere a check request is recorded and the holder honours it (§3.2). Finish runs `ownerTap`, which closes from any machine as the console confirm-done does today.
- A phone write needs the phone write gate's existing preconditions: phone permission actions on, local TLS, an active owner phone with its presence key, and a console PIN configured (the gate refuses `console-pin-not-set` without one).
- The proof of each phone write is the gate's own audit trail (`state/mobile-permission-actions.jsonl` on the machine that verified it: device, action kind, target, status), as for every phone write. The replicated record carries the device id in `messageRef`; it does not carry the signature. A process with shell access that writes the journal directly is out of scope, as in `cos-owner-pause-record` §3.6.
- `WriteDomainRegistry`: the existing `POST /work/projects/` entry's note is amended to name both stores it now covers (`project-app-record` and `chief-of-staff-record`); a `POST /mobile/work/projects/` entry is added, `machine-local` with the `ws2x-replicated` story (the Chief of Staff journal stream), like `POST /chief-of-staff/`.

### 3.7 Clients

This change is the server contract. ## Decision points touched

| Decision point | Classification | Basis |
|---|---|---|
| Who may pause, resume, mark a judged item or finish from the phone | invariant; basis: external-constraint; evidence: the owner phone's presence key signs one exact action line over a single-use challenge (the phone write gate, `mobile-native-permissions` §3.3); the parent specs require the owner's own tap for a pause and for each judgment item | the owner's Face ID is the authority; no agent path, no PIN path on these routes |
| Ask for an update: run now or queue | invariant; basis: external-constraint; evidence: the loop's own configured `tickMinutes` is the fastest rate it checks any project; a request can only make a project due on the next tick, never refuse | no new limit; nothing is refused for timing |
| Who runs a check | invariant; basis: enumerable-domain; evidence: exactly one machine holds the serving lease and runs ticks; a second machine checking would double judge spend and actions (single-writer, as `tick()`) | holder runs now; elsewhere a replicated request the holder honours |
| An item check counts only while that item's text and the goal are unchanged | invariant; basis: irreversible-consequence; evidence: a check counted against wording or a goal the owner never judged could let Finish close a project on a judgment the owner did not make | per-item hash of goal and text in the record; any change of either voids it, no judgement of whether the change matters |
| Finish closes only with every judged item checked, at the tap, with fresh evidence | invariant; basis: external-constraint; evidence: chief-of-staff-topic "Declare done and close": every deterministic item passes now and every judgment item carries an owner tap | the existing confirm-done path, reached by a signed line that names the close |
| Finish on a project with no automatic items | invariant; basis: external-constraint; evidence: the parent's done rule is satisfied vacuously for automatic items and fully by the owner's taps; without it such projects have no owner close | the owner's per-item taps plus the signed Finish |
| A reopen clears the owner's item checks | invariant; basis: irreversible-consequence; evidence: an owner reopens a finished project because it is not done; carrying the old judgments would offer Finish again on judgments the owner just withdrew | HLC order against the newest `reopened` event |
| A Telegram pause ask outlived by a newer owner decision is ignored | invariant; basis: enumerable-domain; evidence: both the ask's tap and the phone decision are the owner's own acts; comparing their wall-clock times can err either way under skew, and either error leaves an owner decision recorded and visible on the row (at worst the owner re-taps, or the agent asks again) | the newest owner decision's `at` against the ask's `sentAt` |
| Agent-may-certify items: checkable, not required for Finish | invariant; basis: enumerable-domain; evidence: the loop pends every judgment item on the owner today (`checkProject`, "agent-may-certify … is not yet honoured"), and the existing Confirm-done confirms them in one tap; requiring the owner to tick delegated items would make them do the delegated work | the row shows the delegation as its own kind |

## Multi-machine posture

Replicated (unified). The new `owner-item-check` and `check-requested` lifecycle events and the phone's `owner-pause` / `owner-resume` events ride the `chief-of-staff-record` store and the order-independent fold. Mixed versions: three steps differ. Validation on receive: an older build accepts a record with fields it does not know (the envelope validator drops them from its validated copy, counted, never rejects). Persistence: the journal applier writes the entry exactly as received (`JournalSyncApplier` serializes the received entry; validation returns only a verdict), so the bytes on disk keep every field. Reads: each read validates again with the reading build's schema, so after the older machine updates it reads the full record. (`cos-owner-pause-record` says the store "is not lossless": that is about the older build's own reads, which this matches.) Until then it stores the new events as unknown lifecycle events, counted in `GET /chief-of-staff` `unknownLifecycleEvents`, and ignores them: an older holder does not honour a queued check request (the project is checked at its cadence instead), and item checks only affect the row and Finish, both of which run on new builds. Phone pauses are the existing event shape, which every current build honours. Finish runs the existing confirm-done write. No machine-local state is added; the read cache is per process, as today.

## Frontloaded Decisions

1. Ask for an update needs no Face ID; Pause, Resume, Mark checked and Finish do.
2. Both judgment kinds can be checked by the owner; only `owner-judged` items must be checked before Finish; Finish confirms delegated items as Confirm-done does.
3. An item check counts whenever the content it judged (goal, id and item text) is the current content: changing either voids it, and restoring exactly the same wording restores it, because the owner judged exactly that content. A reopen voids it for good.
4. Item checks never close a project; the owner's Finish does, at the tap, through the existing confirm-done path.
5. The phone pause uses the existing pause event; the quote is the owner's typed note or a fixed sentence naming the app.
6. Unpark from the phone, and Pause / Mark / Finish from the console, are not in this slice: the console PIN cannot prove the owner (unchanged), and Unpark stays on the note's button and the console PIN tap. The existing console PIN confirm-done route is unchanged; its PIN proof is already under review in fb-0ac4fffb-148.
7. Off a holder, inside the tick interval, or while a tick runs, Ask for an update is a recorded request the holder honours on its next tick; it is never refused for timing and never proxied.
8. Per-item checks are a phone action. Their conversational counterpart is the whole-project Confirm-done the note already offers (it confirms every judged item in one owner tap), the same owner decision in one step; a per-item Telegram flow would add a button per item to a note capped at eight buttons. The dashboard gets the per-item actions only when the console has an owner proof stronger than the PIN.
9. Who approves: Echo under Justin's standing rule (only constitution changes need him) and his go in topic 134088; no constitution file or CODEOWNERS path is touched.

## Rollback

Every change is additive. A revert removes the routes; clients then see 404 on the action routes and rows without `actions`, and hide the buttons (§3.7). `owner-item-check` and `check-requested` events already written become unknown lifecycle events that the reverted build stores, counts and ignores, so nothing stalls and nothing closes because of them. Phone pauses stay valid pauses after a revert (the existing event), and the owner can resume them from Telegram as before. Projects closed by Finish are closed by the existing confirm-done record and reopen the existing way.
