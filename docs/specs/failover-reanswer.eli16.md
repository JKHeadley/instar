# Failover must remember the previous answer

A user sent a message to Echo's Studio. The Studio saved a record saying it had started processing that message, then sent the work to the Mama PC, which owned the conversation. The Mama PC answered. The Studio's record did not close because the answer was sent by a different machine. Two days later, a temporary connection problem made the Studio think the Mama PC was gone. The Studio saw its old open record, ran the message again, and started a new session with only its own partial topic history. The user received a second, different answer.

This change gives the owner machine the original message key when it accepts a forwarded message. Its reply can then close the same key and broadcast the completion marker to the router. Recovery also reads the pooled topic history before replaying an old record. If that history contains a possible reply after the original message, recovery holds the row without asking the agent to answer again. A maintainer can then select the exact reply and reconcile the legacy row through an authenticated route. If a prior owner cannot be checked, recovery leaves the row alone until evidence returns. A new session reads the pooled history and gets an explicit warning whenever some earlier history may be missing. The warning stops it from presenting a local log's silence as proof that the user was ignored.

The two remaining open messages in topics 133072 and 137342 have owner replies visible in pooled history. After deployment, the maintainer reconciliation route can close those rows against the reviewed exact replies without replay. Tests cover an owner answer, a lost completion marker, and a broken link between two throwaway server nodes. The change is reversible by reverting the code; it does not migrate user data.
