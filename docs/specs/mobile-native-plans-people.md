## 1. Problem

Operator request (Justin, Telegram topic 134088, 2026-11-03 22:01 and 22:55 PST): the Instar iPhone app should do every feature natively instead of opening dashboard pages. The plan of record (`.instar/lanes/app-native-coverage-plan.md`) lists, among the rows still web-only: **Plans** (projects and initiatives), **What I've learned about you** (learned preferences and the scrubbed correction ledger) and **Other agents** (Threadline peers and the channel registry). This change covers those three, read-only.

A paired phone signs each request with its device key, and `deviceAuthenticator` admits only paths in `DEVICE_ALLOWLIST` (`src/server/mobilePairingRoutes.ts`). `/initiatives`, `/projects`, `/preferences/session-context`, `/corrections`, `/channels`, `/threadline/pairing` and `/threadline/peers/health` are Bearer-only, so today the app can show these only in the PIN-gated console web view.

Nothing the phone sends can change a plan, a preference, a correction, a pairing or a channel.

## 2. What exists (instar main 181183ecd)

- **Plans page** (`dashboard/console/plans.js`, `plans-model.js`): reads `GET /initiatives` (every record; projects are records of kind `project` carrying their `rounds`), `/initiatives/digest`, `/projects`, `/projects/:id` per open project (children = records whose `parentProjectId` is that project), `/blockers`, `/autonomous/throughput-floor`, `/pool`, `/telegram/topics`. It groups plans into Needs you / In flight (touched in 7 days) / Idle / Older (untouched 14+ days) / Finished, with plain lines ("round 2 of 4 · 3 of 5 pieces merged", "step 3 of 5", "waiting on you: …"). The console says "Plans on this machine." The tracker is `ctx.initiativeTracker` (`initiatives.json` in this machine's state dir).
- **What I've learned about you** (`learned.js`, `learned-model.js`): reads `GET /preferences/session-context` (the injected block; one line per preference, `- <text> (confidence 0.80, seen 3×)`; `scope: 'mesh'` when the server merged other machines' preferences), `GET /corrections?limit=20` (records already scrubbed by `CorrectionLedger.toApiView`; the raw conversation is never stored), `/state/conflicts`, `/pool`. Words: "sure / fairly sure / not yet sure", "seen N times", a status sentence per correction, "Still watching" vs "Earlier". It is advisory and says so.
- **Other agents** (`agents.js`, `agents-model.js`): reads `/threadline/health`, `/threadline/pairing`, `/threadline/pairing/invites`, `/threadline/peers/health?scope=pool`, `/threadline/conversations?scope=mesh`, `/threadline/observability/threads`, `/pool`, `/telegram/topics`. One row per agent: claimed name (verified so an id never stands in for a name), pairing state in words ("Paired", "Pairing not finished", "Blocked"), and delivery health ("Answered 2 h ago", "Nothing back for 6 h", "Messages waiting at the relay"). Peer message bodies appear only inside a conversation's history.
- **Channel registry** `GET /channels` (Registry First table in CLAUDE.md): one row per code-defined channel (`threadline-relay`, `a2a-telegram`, `mutual-ssh`, `peer-http`, `user-telegram`, `user-slack`, `user-whatsapp`, `user-imessage`) with `state` (`working | broken | half-built | reachable-no-credential | not-configured | unknown`), `direction`, `audience`, purpose text and an evidence `detail` string. The console has no page for it; CLAUDE.md tells the agent to read it before saying a peer is unreachable.
- The merged mobile read pattern: `src/server/mobileCapacityRoutes.ts` (PR #2712): `ownerOrBearer`, `phoneText` (shared `scrubSecrets`, whitespace folding, length cap), `rowKey` (one-way row keys), `singleFlight` (15 s single-flight cache for answers that fan out to peers), `DegradationReporter` on read failure, owner-only allowlist entries with their own rate bucket.

## 3. Design

### 3.1 Three purpose-built routes

New module `src/server/mobilePlansPeopleRoutes.ts`, mounted inside `createRoutes` beside the capacity routes, reading the same server-side sources the console's routes read:

| Route | Reads | Answers |
|---|---|---|
| `GET /mobile/plans` | `initiativeTracker.list()` here + each online peer's `GET /initiatives` (proxied-on-read) | `{ schemaVersion: 1, generatedAt, enabled, selfState, headline, counts, sections: { needsYou, inFlight, idle, older, finished }, unread, offline, truncated }` |
| `GET /mobile/learned` | the `/preferences/session-context` answer (extracted into a shared function, no behaviour change) + `correctionLedger.list({limit: 40})` here + each online peer's `GET /corrections?limit=40` | `{ schemaVersion: 1, generatedAt, headline, advisory, preferences, corrections, changeLine }` (shapes below) |
| `GET /mobile/agents` | the `/channels` report (extracted into a shared function, no behaviour change) + pairings (`/threadline/pairing?scope=pool` view) + delivery health (`/threadline/peers/health?scope=pool` view) | `{ schemaVersion: 1, generatedAt, headline, agents, truncated, pairing: { state, reason }, delivery: { state, reason }, channelsState, channels, channelSummary, unread }` |

Enums on the wire: every `selfState`, `preferences.state`, `corrections.state`, `pairing.state`, `delivery.state` and `channelsState` is `ok | off | unavailable` (`channelsState` is `ok | unavailable`); a channel row's `state` is the registry verdict (`working | broken | half-built | reachable-no-credential | not-configured | unknown`, anything else read as `unknown`) and its `tone` is `ok | attn | bad | unknown | off`; an agent's `health` is `dark | stale | queued | unconfirmed | rejected | answered | sent | quiet | unknown`. The app parses every enum leniently (an unknown value is shown with neutral styling, never a decode failure), and its parsing tests include unknown values.

Each answer is built by a pure summarizer from an explicit field allow-list (unit-tested on both sides of every rule).

**MobilePlan** (one row per top-level plan; a record whose `parentProjectId` names a project on the same machine folds under it, as in the console): `key` (rowKey of the plan's machine and id, unique per row), `title` (verified display name, scrubbed, cap 120; "Project name unavailable" / "Initiative name unavailable" otherwise), `kind` (`project | initiative`), `status`, `statusWords`, `line` (the console's `projectLine` / `initiativeLine` without the "worked on … ago" part), `needs` (the console's `needsYouWords`, scrubbed, cap 200, or null), `touchedAt` (ISO), `fromFeedback` (bool), `machine` (the verified nickname of the peer the record came from, from this machine's registry, never a field inside the record; "another machine" when that peer has no verified nickname; null for this machine). A status this server does not know counts as not finished for the needs-you causes too. "Verified display name" means `verifiedEntityName(id, title)`: a non-empty title that is not the id and not id-shaped. Every cause of `needs` is read from the record itself (`needsUser`, status `awaiting-user`, `unacknowledgedAdvanceCount` / `firstLaunchAckAt` / `rounds` on a project record), so a peer's records carry the same causes as this machine's. Grouping and order copy `buildPlansPage`: finished statuses → `finished`; every other record (an open status, or a status this server does not know, e.g. from a newer peer, which is grouped as open and shows its own status words, never dropped) untouched 14+ days → `older`; else needs-you → `needsYou`; touched within 7 days → `inFlight`; else `idle`; each newest-touched first. `finished` keeps the 20 newest (`counts.finished` is the full count). Cap 200 rows overall (`truncated`). Headline copies the console: "No longer plans are running." or "N plans in flight. M need you." **Blockers and autonomous runs stay in the console** (the app says so in one line); they are separate subsystems with their own routes.

Never returned: record ids, `specPath`, `targetRepoPath`, `links`, `telegramTopicId`, `feedbackWorkKey` (only the `fromFeedback` boolean), `prNumber`, `mergeCommitOid`, `ownerMachineId`, phase or round internals other than the words in `line`, any machine id.

**Merging across machines (plans and corrections).** Identity: a correction id is `CORR-<machineId>-<seq>` (`CorrectionLedger.nextId`), unique across machines, so equal ids are copies of one record. A plan id is a name chosen when the plan is made and nothing replicates plans between machines, so a plan's identity is (machine, id): plans are never merged across machines, and the same id on two machines is two rows, each naming its machine (a hidden plan could hide a request waiting on the owner; a duplicate row cannot). A plan's children and parent are resolved inside its own machine. Time: plans use the newer of `lastTouchedAt` and `updatedAt` (and of their children's), corrections the newer of `updatedAt` and `detectedAt`; each is parsed, then a missing, unparseable or more-than-5-minutes-ahead time becomes 0; that one normalized time drives the merge, the grouping and the shown date. A 0 time is serialized as `null` (`touchedAt`, `at`), and the app shows no date for it; an undated plan is grouped as the console groups one (age 0). A correction with the same id on several machines appears once. This machine's copy is offered first; a peer copy replaces the held one only when its time is strictly newer, and a time more than 5 minutes ahead of this server's clock counts as no time at all, so a peer cannot take over a record by future-dating it and a tie keeps this machine's copy. A peer that did not answer (error, timeout, a body over 2,000,000 characters, or a body without its list) is counted in `unread`; a peer answering 503 with the route's documented switched-off error (`Initiative tracker not configured`, `correction-learning disabled`) is off there and not counted; any other 503 is counted in `unread`. Registered machines the pool does not count as online are not asked and are counted in `offline` (both named by verified nickname only; an unnamed one is counted, not named). The headline is scoped "(on the machines that answered)" when anything was unread or offline, or this machine's own read failed.

**This machine's own read.** `selfState` is `ok | off | unavailable` (a throwing tracker read is `unavailable`, reported). Off here with no peer rows and no unreached peer → `enabled: false`, "Plan tracking is off on this agent."; unavailable here with no peer rows → "Can't read plans right now."; otherwise the peer rows show with the scoped headline.

**MobileLearned.** `preferences`: `{ state: 'ok' | 'off' | 'unavailable', reason, items: [{ key, text, sureWords, seenWords }], total, notLoaded, truncated }` (cap 50). Items are the block's lines in the block's own (priority) order, parsed with the console's `PREF_LINE` rule; `text` passes `scrubSecrets` and the console's `clean` (control and bidi characters removed) and is capped at 280. `off` = correction learning disabled (the route's 503). The console's "includes what my other machines learned" line is not carried: the union path marks every answer `scope: 'mesh'` even on one machine, so the label would claim more than is known. `corrections`: `{ state, selfState, reason, watching: MobileCorrection[], earlier: MobileCorrection[], shown, unread, offline, truncated }`. `state` is `ok` when any machine's rows were read (with `reason` saying this machine's could not be when so), `off` only when correction learning is off here and no machine was unread or offline (every machine known off), else `unavailable` with the unread/offline note. `truncated` is true when the merge exceeded 40 rows or any machine returned a full page of 40 (older records may exist there). **MobileCorrection**: `key` (rowKey of the record id), `summary` (the already-scrubbed `scrubbedSummary`, scrubbed again, cleaned, cap 280; the kind words when empty), `kindWords`, `statusWords` (the console's `correctionStatusWords`), `at` (updatedAt or detectedAt), `reopened`, `machine` (verified peer name or null). Watching = status `open | reopened` and kind not `noise` (the console's `isWatching`). Merged across machines by record id (the merge rule above); newest first; 40 rows at most. `advisory` is the console's advisory sentence; `changeLine` is "To change one, tell me in chat." Never returned: record ids, `topicId`, `dedupeKey`, `routedVia`, verify windows, the raw `learning` text (not served by the ledger either). Machine-disagreement notices (`/state/conflicts`) stay in the console.

**MobileAgents.** `agents`: one row per peer fingerprint across pairings and delivery health: `key` (rowKey of the fingerprint), `name` (the claimed name verified against the fingerprint, scrubbed, cap 80; "Unnamed agent" otherwise), `trust` (`paired | paired-elsewhere | unfinished | blocked | old-check | other | not-paired`) with `trustWords` (the console's `pairingWord`: "Paired", "Paired (on another of my machines)", "Pairing not finished — waiting for the other side to finish", "Blocked (the old word check did not match)", "Started with the old word check — pair by invite instead", "Not paired"), `health` (the console's `peerWords` kind: `dark | stale | queued | unconfirmed | rejected | answered | sent | quiet | unknown`), `healthWords` and `healthDetail` (the console's word and sub, built server-side from the delivery row's timestamps and counts only), `tone` (`ok | attn | bad | unknown`), `lastHeardAt`. Across machines one pairing state stands for the agent, by this order: `verification-failed` on any machine → `blocked` (a problem is never hidden behind another machine's pairing); else `mutual-verified` held by this machine → `paired`; else `mutual-verified` read from another machine (the pool merge's `remote: true` rows) or `identity-verified` → `paired-elsewhere`; else `invite-accepted` → `unfinished`; else `pending-verification` → `old-check`; an unrecognised state → `other` ("Pairing state unknown"); no pairing row → `not-paired`. This is a display label only: it authorizes nothing (pairing authority stays in the trust manager on each machine). The delivery row with the freshest evidence (newest ack, inbound or send) stands for the agent's health. Order: bad, attn, unknown, ok; paired first; then name. Cap 100 (`truncated`). The name is the name the agent claims (never an id); it is shown beside its pairing state, which is the trust signal. `pairing.state`: `ok | off | unavailable`; `delivery.state`: `ok | off | unavailable` (with a plain reason). `channels`: one row per registry channel, `{ key (the channel id, a fixed code identifier), name (fixed words: "Agent network relay", "Agent messages through Telegram", "Machine-to-machine SSH", "Direct peer HTTP", "Telegram", "Slack", "WhatsApp", "iMessage"; an unknown id reads "Another channel"), audience (`agents | you`), state, stateWords, directionWords, tone }`; `channelSummary` copies the registry's counts. A registry that could not be resolved answers `channels: []` with `channelsState: 'unavailable'`. The `unread` field names machines whose pairing or delivery rows did not arrive.

Never returned from agents: fingerprints (full or short), public keys, pairing ids, invite ids or codes, SAS words, trust profile fields other than the pairing state, message bodies, thread ids, topic ids, the channel registry's `detail`, `purpose`, `whenPreferred` and `cost` free text, peer error text, machine ids.

The "never returned" lists above are about structured fields: none of those fields leaves the server. Free text the console already shows the owner (plan titles and reasons, preference sentences, correction summaries) is shown the same way; it can mention a path or a number the way the console can, and it is not rewritten beyond the cleaner below. All free text that is shown (plan titles and reasons, preference text, correction summaries, agent and machine names) passes one cleaner: Unicode-normalized, control and bidi-override characters removed, `scrubSecrets`, whitespace folded, length-capped. Text written by peers (their plan titles and reasons, their correction summaries, peer agents' claimed names) is untrusted. All of it is display-only data, never instructions, for the phone and for any agent reading these routes with the bearer token. SwiftUI renders it as plain text.

**Observability.** A read that fails answers `500` with a fixed code (`plans-unavailable`, `learned-unavailable`, `agents-unavailable`) and records one `MobilePlansPeople.read` degradation (route and error class only) through `DegradationReporter`. A part that fails inside an answer (one source of three) becomes that part's `unavailable` state and is reported the same way; the answer still returns 200 with the other parts. A peer's failure is never silent: it is the `unread` entry.

### 3.2 Who may read them

Three entries are added to `DEVICE_ALLOWLIST`: `GET /mobile/plans`, `GET /mobile/learned`, `GET /mobile/agents`, each `statuses: active`, `body: 'none'`, `ownerOnly: true`, with their own bucket (`plans-people-reads`, 20 per minute) so pull-to-refresh cannot use up the chat list's read allowance and cannot multiply peer reads. Inside each route `ownerOrBearer(req, bearerOk)` (imported from `mobileCapacityRoutes.ts`) admits only the bearer token (checked explicitly) or a device whose person resolves to role `owner`; everything else gets `403 owner-phone-required`. Earlier layers answer first, unchanged: `ownerOnly` refuses an MSP device at the device layer, an unknown person gets `403 person-unknown`, the notification read token gets `403 notify-token-not-allowed`, and revoked, pending, unsigned, replayed or tampered device requests get `401 device-unauthorized`. Every answer carries `Cache-Control: no-store`. The raw Bearer routes stay off the allowlist. The owner check and the device checks run on every request before the cache; the cache holds only the built summary, one per route (no route takes a query), shared by the bearer and owner phones. Pool answers are cached single-flight for 15 s per route; a read that throws is not cached, and a part that read as unavailable stays for at most those 15 s.

### 3.3 The app

Three SwiftUI screens in `apps/instar-ios` (agent home), in new files `PlansPeopleData.swift` (parsing, unit-tested) and `PlansPeopleViews.swift`, opened from a new "Plans and people" section on the agent's detail screen: **Plans**, **What I've learned about you**, **Other agents**. Pull to refresh; no background polling. A `403 device-not-allowed` or `404` reads "This agent's server is too old to show this here. Update the agent to see this here." A `403 owner-phone-required` / `person-unknown` reads "Only the owner's phone can see this." Parsing tests are listed in `project.yml`'s test target.

## Decision points touched

| Decision | Classification | Justification |
|---|---|---|
| Device allowlist admits the three GET paths for active owner devices | invariant | Route-level authentication by exact path, the existing deterministic device model; no competing signals. |
| `ownerOrBearer`: bearer or owner-role device only | invariant | Authorization from the authenticated principal's resolved role (Know Your Principal); fails closed for unresolved people. |
| Field allow-list in each summarizer | invariant | A fixed redaction contract: only listed fields leave the server. |
| Plan grouping, correction watching/earlier split, agent ordering and health words | invariant | Display classification copied from the console's documented rules so phone and console agree; it gates nothing and blocks nothing. |
| Merging the same correction id across machines (newest copy wins); plans never merged | invariant | Display de-duplication of copies of one record (correction ids are machine-qualified); plans keep (machine, id) identity so nothing is hidden; no write follows from it. |

## Verify the state, not its symbol

No detector, gate on agent behaviour, or LLM judgment is added. The display states the owner reads:

- Plan `needs`: symbol = `needsUser`, status `awaiting-user`, or an unacknowledged project advance. State claimed = the plan is waiting on the owner. Corroboration = the plan's own `status` and line shown beside it (the console uses the same rule). Unmeasurable: a record that cannot be read is not listed and the answer says how many machines did not answer.
- Plan `statusWords`: an unknown status reads its own words when it is a short slug, else "unknown"; such a record is grouped as open (by age), so it is counted and shown, never dropped.
- Preference `sureWords` / `seenWords`: symbol = the block line's `confidence` and `seen` suffix. A line without the suffix shows its text with no sure-word and "seen once" (the console's parse). Unmeasurable: an unreadable block → `unavailable`, never an empty "nothing learned".
- Plan and correction lists' completeness: symbol = which machines answered. Corroboration = `unread`, `offline` and `selfState`, which scope the headline. Unmeasurable: a machine not in the registry at all cannot be named; the answer never claims "every machine".
- Correction `statusWords`: symbol = the ledger's `status` and `occurrenceCount`. Claimed state = how far the correction got toward a kept preference. Unmeasurable: an unknown status reads "Status not recorded", never "Saved".
- Agent `health`: symbol = the delivery ledger's timestamps and flags (`dark`, `stale`, `lastRelayStatus`). The words copy the console's, which already say what the ledger cannot tell ("it may be offline, or listening at another address — my ledger can't tell which"; "unconfirmed: not known lost, not known delivered"). Unmeasurable: no delivery row → `unknown` ("can't tell if it's reachable") when the delivery read failed, "no delivery record yet" when it answered without one; never "reachable".
- Channel `state`: symbol = the registry's probe verdict. `unknown` reads "Can't tell" and is never counted as working (the registry's own rule).

## Frontloaded Decisions

1. Purpose-built trimmed routes instead of allowlisting the raw Bearer routes (same as #2706 and #2712).
2. Read-only. No acknowledging a round, stopping a plan, forgetting a preference, pairing or unpairing from the phone (operator brief).
3. Owner phones only; MSP phones refused (people-and-roles owner-only default).
4. Plans: projects and initiatives only. Blockers ("In the way") and autonomous runs stay in the console; the app names them in one line.
5. Learned: preferences and corrections. Machine-disagreement notices stay in the console.
6. Other agents: names, pairing ("trust") and delivery health, plus the channel registry verdicts. No conversations, message bodies, fingerprints, invites or pairing actions. "Trust" means the pairing state, which is what the console shows; the trust manager's internal level is not shown by the console and is not returned.
7. Channel rows carry fixed names and the verdict only, never the registry's evidence `detail` (it can echo adapter error text).
8. Bearer may read the summaries too (no new power: it already reads the raw routes).
9. Row caps: 200 plans, the 20 newest finished plans (with the full finished count), 40 corrections read per machine and 40 shown after the merge, 50 preferences, 100 agents. Every capped list carries `truncated`, and the app says so: "Some plans are not shown here; each machine's console lists its own plans." (the console reads only the machine it is served from). (Contested in round 1 as user-visible; decided here rather than tagged cheap.)

## 4. Security

- Widened device-key access is three read-only GET paths, owner phones only, each a subset of what the owner already reads with the bearer token or a console PIN session. No structured id, path, fingerprint, key, invite, message-body, raw-error or config field is returned; owner-visible free text is shown as the console shows it (see §3.1).
- Correction summaries were scrubbed when recorded and are scrubbed again here; preference text, plan titles and reasons pass the shared `scrubSecrets` redactor and a length cap.
- Raw routes stay off the allowlist (tests on both sides). MSP, unresolved-person, notify-token, revoked, unsigned, replayed and tampered requests are refused (tests on both sides). No write path is added; a POST to these paths is refused by the device check.
- Fan-out: each route reads every online peer at most once per 15 s (single-flight cache) behind its own 20-per-minute device bucket; peer reads time out at 5 s and count as `unread`.

## 5. Multi-machine posture

- Peer reads use the existing pool peer transport (`poolPeerFetch`, the same path and the same agent token the merged `/subscription-pool?scope=pool` and `/mobile/spend` fan-outs already send to the agent's own machines); no new forwarding mechanism. Bodies over 2,000,000 characters are not parsed (the 5 s timeout bounds the read itself).
- Plans: **proxied-on-read**: this machine's tracker plus each online peer's `GET /initiatives` (5 s timeout), each plan shown with its machine (never merged across machines); unanswered peers in `unread`, offline machines in `offline`. (`initiatives.json` is not replicated by any named path today, so reading peers is what makes the answer unified.)
- Preferences: **replicated** through the existing preferences paths `/preferences/session-context` already reads (the `multiMachine.stateSync.preferences` union reader, or the `ws21PreferencesPool` replica merge); with both off it is this machine's store, exactly what the session-start hook and the console show.
- Corrections: **proxied-on-read**: this machine's ledger plus each online peer's `GET /corrections?limit=40`, merged by record id; unanswered peers in `unread`, offline machines in `offline`; each row from a peer names its machine.
- Pairings: **proxied-on-read** through the existing `/threadline/pairing?scope=pool` merge (`pairingPoolMerge`). Delivery health: **proxied-on-read** through the existing `/threadline/peers/health?scope=pool` merge.
- Channel registry: machine-local by design. machine-local-justification: physical-credential-locality — each verdict describes this machine's own live connections (the relay socket held with this machine's identity, the Telegram/Slack/WhatsApp/iMessage adapters bound to credentials on this machine's disk); another machine's verdict is not this machine's channel. The app labels the section "Channels on this machine".
- Device authentication: the phone's device record lives on the machine it paired with. machine-local-justification: physical-credential-locality — the device key verifies only on the machine holding its record; this change adds no device state.
- No new durable state, no user-facing notices, no generated URLs.

## 6. Tests

- **Unit** (`tests/unit/mobile-native-plans-people.test.ts`): `summarizePlans` grouping both sides of the 7-day and 14-day lines, needs-you from each cause, child folding on the same machine only, project and initiative lines, the same id on two machines as two rows with distinct keys (machine named, unnamed peer counted), finished cap, overall cap, never ids/paths/links; `summarizeLearned` preference line parsing (with and without the confidence suffix), off/unavailable, correction watching/earlier split, noise never watching, merge by id, scrub of a planted credential, cap; `summarizeAgents` pairing words, every health kind, unknown when delivery failed vs "no record yet" when it answered, ordering, verified names (a fingerprint-like name is refused), channels named by fixed words with no detail text, unknown never counted working; the allowlist has exactly GET for the three paths, owner-only, own bucket, and none of the raw routes; the owner-only named set in `tests/unit/mobile-session-terminal.test.ts` gains the three.
