# Measuring delayed Telegram sends

Some replies reach Telegram quickly, while others wait until the fifteen-second network timeout expires. A timeout does not tell us whether the network was slow, the server was too busy to handle the answer, or Telegram accepted a message whose answer was lost. Restarting the server did not resolve the observed problem, and a fresh copy of the same Node runtime can reach Telegram quickly. We need measurements from the process that is actually sending the reply.

This change adds two small diagnostic records around the network request for a text message. The first says that the request is starting. The second says either that HTTP response headers arrived or that the request failed. Both carry the same process-local number. The completion record includes elapsed time, event-loop delay samples, and the process's event-loop utilization during that interval. It never contains the destination, message, bot credential, URL, or exception text.

The records are observations. A headers record does not mean that Telegram delivered the message: the existing receipt checks still decide that. A histogram without samples is reported as unavailable, because a newly enabled probe can miss an early pause. Event-loop utilization covers everything happening in the process during the request, so it cannot identify which feature caused a pause. The next investigation must compare these records with other evidence rather than declaring a cause from one number.

The change leaves connection pooling, polling, network deadlines, admission rules and retry decisions alone. At most sixteen event-loop histograms can run at once. A failed logger or unavailable probe must not change the original response or error. Removing the change restores the previous diagnostic behavior without a data migration. The review is about whether these measurements are private, bounded, correctly placed, and honest about their limits; it does not approve a transport fix or prove delivery recovery.
