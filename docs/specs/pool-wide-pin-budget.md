# One wrong-PIN budget for the whole agent, not one per machine (SEC-170)

## 1. Problem statement

The dashboard PIN unlocks the agent's dashboard. A correct PIN entered on a public unlock page returns the agent's permanent key (SEC-150). To slow guessing, unknown browsers share one hard budget of 20 wrong guesses per 5 minutes (`GLOBAL_PIN_KEY` in `src/core/PinAttemptStore.ts`, `globalFailureBudget` in `src/core/PinThrottle.ts`).

That budget is kept per machine, in each machine's own `state/pin-attempts.json`. The PIN itself is the same on every machine (it is a synced secret). So a stranger who knows N of the agent's addresses gets N × 20 guesses per 5 minutes against the one PIN. `docs/specs/identity-security-piece1c-pin-policy.md` §4 names this residual and defers it. `docs/specs/dashboard-pin-throttle.md` records the per-machine count as an operator-ratified exception, on the grounds that guesses at one machine's address are not information another machine should act on. That premise does not hold when every machine checks the same secret. SEC-169 (PR 3647) stopped a public page from listing every machine's address, but addresses can still be learned other ways, so the budget itself must be bounded agent-wide.

This spec replaces that one exception, for the global unknown-browser budget only.

## 2. What is bounded, and what stays as it is

**Bounded agent-wide: the global unknown-browser failure budget, 20 per 5 minutes for the whole agent.** It covers every attempt that reaches `GLOBAL_PIN_KEY` today: an attempt that is not a genuinely local request and has no **honored** `instar_pin_ok` marker. A marker that is still valid but has passed its abuse cap is no longer honored (`PinThrottle`), so those attempts are charged like any unmarked attempt. The build defines the predicate as "not local and no honored marker" and tests the switch from an honored to an abused marker on all three consumers:
- `POST /dashboard/unlock`, through `publicPinAdmit`, `publicPinFailure` and `publicPinSuccess` (`src/server/AgentServer.ts`);
- `POST /dashboard/session/step-up`, through the same helpers;
- the email-code confirm, through `publicCapPinCheck` (`src/server/routes.ts`, built by `createMandatePinCheck` with `clearOnSuccess: false`).

**Unchanged and per machine:** a browser with an honored marker is admitted before any budget (its abuse cap of 50 is a secondary brake on a stolen cookie and stays per machine); the machine's own local budget (`local-direct-unmarked`, 10 per 5 minutes); per-source backoff and the per-network brakes in `PinThrottle`; approval links (5 wrong PINs per live request) and every signed-in check; the paired phone app, which never uses the PIN budget.

## 3. The design: a fixed share per machine, counted locally

**Each machine owns a fixed share of the agent's 20 per 5-minute window: `floor(20 / N)`, plus one try for the first `20 mod N` machines in the agreed id order, so the shares add up to exactly 20.** N is the number of machines in the agent's **agreed membership** (§4): every machine that has been paired and is not retired, including this one. Each machine keeps counting its own unknown-browser attempts in its own store, exactly where it counts them today, but its limit is its share instead of 20. Every attempt at a machine's address is counted by that machine, so a stranger who knows every address gets at most the sum of the shares, 20, per window. A stranger who knows one address gets that machine's share only. Each machine's window is its own fixed 5-minute window, as today, and the windows are not aligned, so in a short span across a window edge a stranger can reach up to twice that, 40. That edge property already exists today on every single machine. The bound assumes every machine runs this build with the switch on (§6) and that any "gone for good" confirmation is correct (§4).

There is no lead, no cross-machine call on the PIN path, no handover and no pause. The build replaces the fixed `GLOBAL_MAX_ATTEMPTS` (`src/server/AgentServer.ts`) and `GLOBAL_PIN_MAX_ATTEMPTS` (`src/server/routes.ts`) with one `PinShareProvider` that returns the machine's applied share. The store, `publicCapPinCheck`, and the unlock and step-up helpers all read from it, so no consumer keeps the old 20. A machine cut off from the others keeps admitting new browsers within its share. A machine that was never paired has N = 1 and keeps today's 20.

**Count before comparing, durably.** Today the store increments after a wrong PIN and keeps enforcing in memory when a write fails, so a restart after a failed write could forget counted guesses. For this key the build changes the order: the attempt is counted and the count is written and flushed (`fsync` of the file and its folder) before the PIN is compared, and a correct PIN gives the count back. If the write fails, the attempt is refused and the degradation `PinBudget.persist` is reported once per episode. This costs one flush per counted attempt and one per give-back. Refusals do not write. A give-back happens only on a correct PIN, and it is flushed before the success is answered, so the writes are bounded by the counted attempts plus the correct PINs in a window. Concurrent attempts on one machine are serialized by the store, so they can never pass the share.

**What the numbers mean today.** Echo has five active machines, so each machine offers 4 tries per window. Two machines give 10 each. The remainder is handed out one try each, so the shares always add up to exactly 20 (five machines get 4 each; three get 7, 7 and 6). A share of 0 happens only on an agent with more than 20 machines, where no division of 20 can give every machine a try. A machine at share 0 refuses unknown browsers, and the agent raises one Needs-you item saying so in plain words, with a choice of which machines hold the tries. A smaller share does not cost the owner anything in ordinary use: the owner signing in from a new browser needs one or two tries.

**Alternatives weighed.**
- **One count kept by the lease-holding machine (the lead).** This was the previous design of this spec, through eight review rounds. Every remote attempt reserved a count at the lead. A machine cut off from the lead refused every new browser, and an unplanned handover paused new browsers for 5 minutes plus one lease life. Bounding it during a split lease needed signed votes, nonces, vote locks that survive restarts, and membership agreement, and every review round found another gap. It also let an attacker draining one address block new browsers on every machine. The fixed share keeps the same bound with none of that machinery, and it degrades better.
- **A replicated count.** Rejected. The log's lag lets each machine spend a full budget before it hears of the others' spending.
- **Live borrowing from idle machines at sign-in time.** Left out of the first build, on evidence rather than effort. Borrowing at the moment of a PIN attempt puts a cross-machine call back on the PIN path. That restores the dependence on reachable peers that made the lead design refuse new browsers whenever machines lost touch. Its only gain is for an owner signing in from a brand-new browser on a machine whose share an attacker has just spent, during that window. The owner then still has the other machines, a browser that unlocked before, the phone and the machine itself. The case is measured: dev-agent-live counts every refused new browser by cause. If even one refusal of a new browser happens outside a counted attack, the security session builds borrowing, or a weighted division, before it raises the fleet packet. That is a tracked commitment opened when the build merges.

## 4. Agreed allocation

The shares depend on who is in the pool, so every machine must use a safe share when machines are added or retired. **The general rule: a machine may lower its own share at any moment, alone; it raises its share only on a fully acknowledged allocation, after one more window.**

- **The allocation table.** The agent's division is one table: `{ seq, members, hash, shares: { machineId: n }, transfers: [ { transferId, from, to, amount } ] }`. `members` is the sorted list of non-retired machine ids. `seq` orders tables: a machine proposing a new table uses one more than the highest `seq` it has seen, and two tables with the same `seq` are ordered by `hash`. A higher table supersedes a lower one. The shares in a table always sum to at most 20. **A table is valid only if** it is signed by a pool machine, its `members` equal the non-retired machines in the receiver's own registry, its `seq` is at least the highest valid `seq` the receiver has seen (an older table, even a validly signed one, is ignored and lowers nothing), and its shares are the canonical division of its members (§3, equal with the remainder in id order), changed only by the transfers it records. A transfer counts only if its giver signed that exact `transferId`, `to` and `amount`, and the amount is at most the giver's own entry; a table carrying any other transfer is invalid. A table of any other shape is valid only if the owner signed it from the phone, which is how a weighted division would be chosen. An invalid table is ignored entirely. Membership itself changes only through the registry, which changes only by a pairing or the owner's retirement. So one faulty or compromised machine cannot drop others from a table and set their shares to 0. Gaps in `seq` are allowed, so a machine back from a long time offline accepts the current table as soon as its registry has caught up. `seq` is an unbounded integer, and an owner-signed table may restart it, so no single table can leave the pool unable to make the next one. A table with no entry for a machine gives that machine share 0.
- **What each machine stores.** `<stateDir>/state/pin-share.json` holds the table it applies, its own applied share, its `admitFrom` time (before which it admits no one) and the signed acknowledgments it holds for the newest table. It is written atomically and flushed before any change it records takes effect, and every write also replaces a second copy, `pin-share.prev.json`, so a damaged file is recovered locally from the copy. The applied share is stored, never recomputed upward from membership. If both copies are missing or unreadable on a paired machine, its share is 0. A fetched table, however well acknowledged, proves only past agreement, not what the machine still holds after transfers. So the machine recovers only through a new table: it proposes one with a `seq` above any it can fetch, and it raises its share only when that table is acknowledged under the rules below, plus one window. Alone, it keeps refusing only new browsers: the owner's ways in (§5) never depend on this budget, so the owner can still sign in there with a browser that unlocked before, the phone, or on the machine itself. The machine first tries every peer, with the acknowledgment backoff (5 seconds doubling to 60). After 24 hours without an answer it stops trying, and starts again as soon as any peer is seen in the pool view or makes a signed call. Only if no peer has answered after 30 minutes does the agent raise one Needs-you item saying so in plain words. The machine keeps trying, and the item closes by itself once the new table has been acknowledged.
- **Waits use a clock that cannot be set.** Every wait in this section (a newcomer's `admitFrom`, the one window before a raise) is timed on the machine's monotonic clock while it runs. After a restart, a wait still in progress starts again in full from boot, so a clock change or a restart can only lengthen it.
- **Seeing a new table.** A machine applies `min(applied share, its entry in the new table)` from any valid table at once, including in its current window. If its count already exceeds that, it refuses until its window resets. Only after that write does it send a signed acknowledgment, `POST /api/pin-budget/ack`, naming the exact `seq`, `hash` and shares. **A machine acknowledges a table only if** its `members` equal the non-retired machines in its own registry, and it includes every machine the acknowledger holds an outstanding transfer to or from. Otherwise it refuses and waits for a table that does. **A transfer ends** when its recipient is retired, including the owner removing a pairing that never finished, and the retirement is complete: the recipient has acknowledged it, or the owner has confirmed it gone for good. Until then it stays outstanding. The capacity goes back to the giver only through the raise rule, in a fully acknowledged table, after one window. So a recipient that never heard of its retirement cannot spend alongside the returned share. A newcomer enters the replicated registry at pairing, so every holder of any capacity is eventually a member. Every member must acknowledge before anyone raises, and acknowledging means applying the lower of its share and its entry. So once a table is fully acknowledged, every holder is at or below that table's entries, which sum to at most 20. Two pairings at once, A pairing C while B pairs D, give two tables that each omit a newcomer. A refuses B's table (it omits C, A's transfer), and B refuses A's (it omits D). Neither completes, and both machines only lower meanwhile. Once the registry carries both newcomers, a table listing all four is proposed and completes. An acknowledgment counts only for the table it names, never for a later or earlier one. When a machine holds acknowledgments from every machine in the table's `members` (and, for a retirement, from the retired machine as well), it records them, waits one window (5 minutes), and only then raises its applied share, and only to its entry in the newest valid table it knows, minus every outstanding transfer it has given. That subtraction is the fence for a hand-down made while a raise is pending. Example: machine B, cut off, finishes a raise for an older table T while machine A hands 2 of its share to newcomer C. A never raises above its entry in T minus 2, B is at or below its entry in T, and C holds only the 2. So the sum stays within the 20 of T. A newer table arriving during the wait cancels the raise, and the rule starts again for that table. This one rule covers a pairing, a retirement, both at once, and a remainder shift that would raise one machine's share. Retries use backoff, doubling from 5 seconds up to 60. After 24 hours of failures to one machine, the sender stops, reports the degradation `PinBudget.ackUndelivered` once, and sends again only when that machine is next seen. A stopped retry only delays a raise.
- **A pairing.** The pairing machine proposes the new table with the newcomer in `members`, and applies its own lowered entry at once like everyone else. So that the newcomer can be used before every machine acknowledges, the pairing machine also hands it part of its own applied share. It first durably writes its applied share lowered by that amount, together with a transfer record carrying a fresh `transferId`. Only after that write does it send the newcomer a signed transfer. The newcomer writes `{ applied share: amount, admitFrom }`, five minutes on its monotonic clock, before it admits anyone. That way the giver's window begun under its old share has ended by then. The newcomer writes its `pin-share.json` row at pairing, before the shared PIN reaches it, so it is never counted as a never-paired machine with 20. Transfers stay in the table until a fully acknowledged table that includes the newcomer supersedes them. A restart of either side reads the stored applied share and transfer, so the handed-down amount is never counted twice. The default amount is half the giver's applied share, rounded down. If that is 0, the newcomer asks the next reachable machine with a share of 2 or more, by the same signed hand-down. **The same hand-down serves any machine at share 0** that is not retired: a machine that lost both copies of its allocation, or a newcomer whose pairing machine had nothing to give. It asks any reachable peer with a share of 2 or more for a giver-signed hand-down, and admits after one window. So a machine is at 0 for more than one window only while no peer with a share to spare can be reached, and the owner's ways in work throughout.
- **A retirement.** The retired machine, on learning of it, writes share 0 to `pin-share.json` and applies it at once, and only then acknowledges, including when it holds a handed-down share. A machine that never acknowledges, such as one gone for good, holds the others' raise back. The owner can instead confirm from the phone that the machine is gone for good (wiped, lost or destroyed). That confirmation is recorded with the retirement, but it stands in for the machine's acknowledgment only when the pool's own evidence agrees. No machine may have received any signed call or capacity report from it for 7 days, the same silence that puts it on the owner's list. So the confirmation takes effect as soon as the owner gives it, provided the silence still holds. Each machine records the last signed contact from every peer, and the pool view merges those records. If any machine's record cannot be read, the evidence counts as unmeasured and the raise keeps waiting. Until then the gone machine's share stays reserved, so the owner's tap alone never hands out a share a still-running machine could be spending. If the owner was wrong and the machine still runs, cut off for over 7 days, the most it can add is its old share.
- **Kept coherent with the machine registry.** The registry is the source of membership; the table records how the 20 is divided. On every registry change and once an hour, each machine compares the table's `members` with its registry. If they differ, it proposes or acknowledges the newer table, applies the smaller share at once, and reports the degradation `PinBudget.membershipDiverged` once per episode.
- **Machines silent for 7 days.** The agent keeps one Needs-you item for the whole agent that lists every machine silent for 7 days or more. It offers "retire" or "gone for good" for each, and says in plain words that they are holding the guess limit lower. The item is updated in place as machines go silent or come back, and it closes by itself when none are silent. The owner decides; the agent never retires a machine itself. Dismissing it keeps it quiet until something new happens: another machine goes silent, or a pairing or raise is being held back by a silent machine's missing acknowledgment.
- **An older build** ignores acknowledgments, so a change that needs agreement waits until it updates. Meanwhile the older machine keeps its own 20 (§6).

## 5. Lockout and recovery for the owner

The owner's normal ways in never depend on this budget: a browser that unlocked before on that machine's address and is still honored, the paired phone app, and the machine itself. They work during an attack and when machines are cut off.

**What changes, said plainly:**
- An agent with several machines now has the protection it was meant to have: its machines' shares add up to 20 per window, not 20 each. As today on a single machine, a burst across window edges can reach twice that in a short span.
- Each machine's own budget for new browsers is smaller. An attack at one address can spend that machine's share faster than it could spend 20, and a new browser there then waits until the window resets, as it does today when the budget is spent. The other machines are unaffected.
- A newly paired machine admits new browsers after 5 minutes, within the half-share handed down by the machine that paired it, and gets its full equal share once every machine has acknowledged it. In the first 5 minutes the owner signs in there with a browser that unlocked before, the phone, or on the machine itself.

**Alerts.** With a small share, a few owner typos could spend it, so a spent share alone is not called an attack. A machine raises the existing brute-force alert (`DashboardPin.bruteForce`, with its 30-minute cooldown) when its share is spent by failures from more than one source, or when it has been spent in two windows in a row. A share spent by one source in one window gets the per-source backoff and a quiet log line, as a burst of typos does today. Whatever the pattern, the agent raises the alert when failures across all machines reach 20 within one hour, so a slow attacker spreading small bursts is still reported. That count comes from the pool view's regular pull of each machine's failure counts. It is used only for the alert and tolerates the pull's lag.

**Recovery.** No manual step. A share refills with its window. A damaged counter file pauses that machine's budget for one window, as today. A damaged `pin-share.json` is recovered from its second copy. If both are damaged, that machine's share is 0 for new browsers until it has proposed a new table, every machine has acknowledged it, and one more window has passed. It starts that on its own as soon as any peer answers. The owner's ways in are unaffected.

## 6. Migration and mixed versions

- **Development agents first.** `security.pinBudget.poolWide` follows the development-agent gate: when it is omitted, it is on for a development agent and off on the fleet. An explicit true or false always wins. It is read from the settings file only, never patchable through the API (the same fence as the other security keys). Off means today's 20 per machine.
- **Every machine advertises** `pinBudgetPoolWide: true|false` and its current share in its capacity flags, so the pool view shows each machine's state.
- **An older machine** keeps its own 20 until it updates. That is the residual during a rollout, no worse than today.
- **Turning it on** starts from a first table. Each machine, on enabling, proposes `seq` 1 as the canonical division of the non-retired machines in its own registry, and applies the lower of 20 and its own entry at once. It then follows §4: it applies the lower entry of any valid table it sees, and acknowledges only a table matching its registry. Until registries agree, a machine whose registry has not yet heard of a newly added machine may hold a share too large by at most one share per machine it does not know. That transient residual lasts only as long as the registry takes to sync, and is never larger than today's 20 per machine.
- **No data migration.** One new file, `pin-share.json`, which older builds ignore. The existing counter file is unchanged.

## 7. Multi-machine posture

The global PIN budget becomes unified by division: each machine enforces a fixed, agreed share of the agent's one limit, and no share is counted twice. The count itself stays on each machine by design, because every attempt at an address reaches only that machine. The share is derived from acknowledged membership that every machine agrees on. This supersedes the `machine-local-justification` in `docs/specs/dashboard-pin-throttle.md` for that budget only. The per-source backoff, the per-network brakes and the marker abuse cap stay per machine under that spec's exception. With the switch on, once the first table is fully acknowledged, it closes the residual named in `docs/specs/identity-security-piece1c-pin-policy.md` §4.

## 8. Configuration and fixed limits

- `security.pinBudget.poolWide` (boolean, file-only; omitted means on for a development agent, off on the fleet, per `resolveDevAgentGate`).
- The agent's budget stays 20 per 5 minutes; a machine's share is `floor(20 / N)` plus one for the first `20 mod N` machines in id order.
- When a spent share raises the brute-force alert (spent by more than one source, or in two windows in a row; otherwise per-source backoff and a log line): judgment-candidate. Floor: the alert never changes what is admitted, so a missed or extra alert cannot loosen the bound; every spent share is counted in the pool view whether or not it alerts; and the agent raises the alert anyway when spent shares across all machines reach 20 within one hour. Arbiter: the security session, from the spent-share records during dev-agent-live. Fallback: the rule as stated.
- The notice timings (30 minutes with no peer before telling the owner about a lost allocation; 20 failures across machines within one hour for the agent-wide alert): judgment-candidate. Floor: neither changes what is admitted, so a late or early notice cannot loosen the bound, and every refusal and failure is counted in the pool view regardless. Arbiter: the security session, from dev-agent-live records. Fallback: 30 minutes and one hour.
- The acknowledgment backoff doubles from 5 seconds up to 60 seconds. The wait after agreement is one window (5 minutes). The silent-machine proposal comes after 7 days, and again after 30. Each is classified below.

## 9. Verify the State, Not Its Symbol

- **An admitted attempt** has one symbol: the store's count after a successful flush. The state it claims is that this attempt is counted against this machine's share. The corroboration is the store file on disk, re-read in the tests after a simulated crash. A failed write is unmeasured and refuses.
- **A raised share** has one symbol: `pin-share.json`. The state it claims is that every machine agreed to that exact table. The corroboration is the set of signed acknowledgments naming its `seq` and `hash`, kept beside it, one per listed machine, or the owner's recorded "gone for good". A missing acknowledgment means the raise has not happened. **A newcomer's first share** is corroborated by the giver's durable transfer record with the same `transferId`.
- **The graduation check** applies once the first table (§6) has been fully acknowledged on every machine; measurements from before that point are reported separately as the transitional residual §6 states. It has two parts, read through the pool view. First, every attempt a machine admitted was admitted while its count was below its applied share at that moment; each counted attempt records the applied share it was admitted under. A count above a share lowered later in the same window is allowed, as long as no attempt was admitted after the lowering. Second, the applied shares of all machines, read at the same moment, never sum to more than 20. A breach of either is a finding. A machine whose store or share cannot be read is reported as unmeasured, never as within the bound.

## Decision points touched

- Bound the global unknown-browser budget agent-wide: the agreed per-machine shares sum to at most 20: invariant; basis: irreversible-consequence; evidence: a correct guess returns the permanent agent key (SEC-150), and per-machine counting of 20 multiplies the guessing rate by the machine count. The figure 20 per 5 minutes is the existing ratified budget of `docs/specs/identity-security-piece1c-pin-policy.md` for one machine; this spec keeps the agent at that ratified limit rather than reopening the number. Changing the number is that spec's decision, and an agent of more than 20 machines does not exist today.
- How the 20 is divided among machines: judgment-candidate. Floor: the shares sum to at most 20, every share is part of the agreed membership version (so a change of division follows the same agreement rule as a change of membership), and no machine's share is negative. Arbiter: the security session, from which machines owners actually sign in at during dev-agent-live. Fallback: equal shares of floor(20 / N), with the remainder (20 mod N) given one each to the first machines in the agreed version's sorted id order, so the shares always sum to exactly 20. On an agent with more than 20 machines, 20 of them hold one try each and the rest hold none; that is unavoidable with a total of 20, and the owner can choose which machines hold them. A division weighted by where the owner signs in is a later change under the same floor.
- Count and flush before comparing; refuse on a failed write: invariant; basis: irreversible-consequence; evidence: a count that exists only in memory is lost on restart, and a restart could then allow guesses that were already spent.
- Lower a share at once on seeing a larger membership, without agreement: invariant; basis: enumerable-domain; evidence: a smaller share can only reduce what the machines allow together.
- A new machine's handed-down share comes only out of the pairing machine's own applied share, which the giver durably lowers before it sends the transfer, and the newcomer uses it only after one window recorded on disk: invariant; basis: irreversible-consequence; evidence: an amount taken from a share already inside the 20 cannot raise the total, and the window lets the giver's window begun under its old share end.
- How much the pairing machine hands down (half): judgment-candidate. Floor: never more than the giver's own share, given up before the new machine admits anyone. Arbiter: the owner may choose a different split at pairing; otherwise the security session tunes it from dev-agent-live. Fallback: half, rounded down.
- Raise any share (pairing, retirement, both at once, or a remainder shift) only after every listed machine acknowledges that exact table, plus one window: invariant; basis: irreversible-consequence; evidence: a machine that has not yet lowered its share, or has not ended a window begun under the old share, would otherwise spend alongside the new share and pass 20.
- A missing or unreadable allocation means share 0 until a new table is fully acknowledged plus one window; the applied share is stored and never recomputed upward: invariant; basis: irreversible-consequence; evidence: a recomputed share could forget an outstanding hand-down and pass 20, and 0 cannot.
- Acknowledge a table only if its members match your registry and it includes every machine you hold an outstanding transfer to or from; a lost allocation recovers only through a new fully acknowledged table: invariant; basis: irreversible-consequence; evidence: a table that omits a capacity holder, or an old table reused after a loss, can raise shares while that holder still spends, passing 20.
- Accept a table only if its members equal your registry's non-retired machines and its shares are canonical for them (apart from giver-signed transfers) or owner-signed: invariant; basis: irreversible-consequence; evidence: without it, one faulty or compromised machine could publish a table that drops or shrinks others and stop new-browser sign-in agent-wide.
- A raise never exceeds the table entry minus the machine's own outstanding transfers: invariant; basis: irreversible-consequence; evidence: a hand-down made while another machine's raise for an older table is pending would otherwise be counted at both the giver and the recipient.
- A machine at share 0 may receive a giver-signed hand-down from any reachable peer with a share of 2 or more, usable after one window: invariant; basis: irreversible-consequence; evidence: the amount comes out of the giver's own share, which it durably lowers first, so the sum cannot rise.
- Build live borrowing or a weighted division before the fleet packet if dev-agent-live records any new-browser refusal outside a counted attack: judgment-candidate. Floor: the owner's ways in never depend on the budget, and the bound holds either way. Arbiter: the security session, from refusal causes counted during dev-agent-live. Fallback: build it.
- Tables are ordered by seq then hash, and an acknowledgment counts only for the exact table it names: invariant; basis: irreversible-consequence; evidence: an acknowledgment reused across tables could raise a share no machine agreed to.
- Let the owner's "gone for good" confirmation stand in for a missing machine's acknowledgment, once no machine has had signed contact from it for 7 days: judgment-candidate. Floor: only the owner, from the phone, can confirm; the pool's contact records must corroborate it, and unreadable records keep the raise waiting; a wrong confirmation adds at most that machine's old share, and waiting only keeps the guess ceiling lower, never touching the owner's ways in. Arbiter: the security session, from how long machines are cut off and then return during dev-agent-live (a machine back after more than 7 days would show the window is too short). Fallback: 7 days, the silence that already lists a machine for the owner, so the owner's tap takes effect at once in the ordinary case.
- When to list a silent machine for retirement (7 days, in one agent-wide item that re-raises only on something new): judgment-candidate. Floor: the agent only proposes, never retires; a silent machine only keeps the limit lower, and the share stays at least 1 on any agent of 20 or fewer machines. Arbiter: the security session, from how long machines sit silent before the owner retires them during dev-agent-live. Fallback: 7 days, long enough that a laptop away for a weekend is not listed.
- The acknowledgment backoff (5 seconds doubling to 60, stopping after 24 hours of failure to one machine until it is seen again): judgment-candidate. Floor: a missing acknowledgment only delays a raise. Arbiter: the security session. Fallback: 5 seconds, 60 seconds and 24 hours.
- Keep marked browsers, the local budget, the phone app and approval links outside the bounded budget: invariant; basis: enumerable-domain; evidence: the owner's ways in are a closed list (§5) and none depends on this budget today.

## Frontloaded Decisions

## Tests

- **Unit, the share:** with N = 1, 2, 3, 5, 20 and 21, the shares are 20; 10 and 10; 7, 7 and 6; 4 each; 1 each; and 1 each for 20 machines with 0 for the last. They always sum to 20. For every N from 1 to 40 and every position a new machine's id can take, adding a machine never raises any existing machine's share. A machine refuses the attempt after its share. Concurrent attempts on one machine never pass the share. Share 0 refuses and raises one Needs-you item.
- **Unit, count before compare:** on all three consumers the attempt is counted and flushed before the compare. A wrong PIN stays counted, a correct PIN gives it back, a failed write refuses without comparing, and a crash after the flush and before the compare keeps the count after restart. The existing PIN tests are updated for this order, including mock stores.
- **Unit, allocation table:** applying a table takes the minimum of the applied share and the new entry at once; a combined retirement and pairing that would raise one machine's share through the remainder raises it only after full acknowledgment plus one window; an acknowledgment naming another seq or hash never counts; a higher seq supersedes, and equal seqs order by hash; two machines pairing two newcomers at once produce tables that each omit a newcomer, both are refused by the machine holding the omitted transfer, and only a table listing all four completes; a machine refuses a table whose members differ from its registry. A machine that lost both copies and fetches an older fully acknowledged table stays at 0 until a new table is fully acknowledged plus one window (the 10 and 10, then 7 plus a 3 transfer, case). Crash tests: a giver crashing between lowering its share and sending the transfer, and after sending it, never leaves the total above 20 after restart; a newcomer restarting before `admitFrom` still waits; a donor whose equal share would be unchanged after a sixth machine joins keeps its lowered share across restart. A missing `pin-share.json` gives share 0 until a new table is fully acknowledged plus one window; fetching an older acknowledged table restores nothing. A newcomer writes its row before the shared PIN arrives and is never treated as never-paired.
- **Unit, membership:** seeing a larger membership lowers the share at once, including mid-window. A new machine admits after 5 minutes within the half-share the pairing machine handed down, and the pairing machine's own limit drops by that amount at once. It moves to the equal share only after it holds acknowledgments from every listed machine and 5 more minutes pass. A retirement raises shares only after every old machine acknowledges, or the owner confirms "gone for good", plus one window. The retired machine drops to 0 when it learns of its retirement. A registry that disagrees with the table applies the smaller share and reports `PinBudget.membershipDiverged` once. An unsigned or non-pool acknowledgment is refused. An older build that never acknowledges holds a raise back. Retries to an unreachable machine stop after 24 hours with one degradation report, and resume when it is seen again.
- **Unit, transfers:** a table recording a transfer the giver did not sign, or larger than the giver's entry, is invalid and lowers nothing. A transfer to a machine that is retired, or to a pairing the owner removed, stays outstanding until the recipient acknowledges or the owner confirms gone for good, and then the giver's share returns only after a fully acknowledged table plus one window. A retired recipient writes 0 before it acknowledges.
- **Unit, table validity and first table:** a table that is not canonical and not owner-signed, or whose members differ from the receiver's registry (including a table listing only its proposer), is ignored and lowers nothing. A machine back after many table changes accepts the current table once its registry matches. A replayed older table lowers nothing. A table with a very large `seq` does not stop later tables, and an owner-signed table can restart `seq`. A table without an entry for this machine gives it 0. A newer table during the raise wait cancels the raise. Enabling proposes seq 1 from the registry, and a machine with a stale registry lowers on seeing the other machines' valid table, within the stated residual.
- **Unit, provider and alert:** the store, `publicCapPinCheck` and the unlock and step-up helpers all read the share from `PinShareProvider`, and none keeps a fixed 20. A share spent by one source in one window raises no brute-force alert; spent by two sources, or in two windows in a row, it does.
- **Unit, silent machines:** two machines silent for 7 days appear in one agent-wide Needs-you item, updated in place; dismissing it keeps it quiet until a third goes silent or a raise is held back by a silent machine. "Gone for good" raises shares once 7 days pass with no signed contact recorded anywhere, at once when the machine is already listed, and waits while any machine's record is unreadable.
- **Unit, zero share and fence:** a machine that lost its allocation gets a hand-down from a reachable peer and admits after one window. A giver with an outstanding transfer never raises above its entry minus the transfer while a cut-off peer finishes an older raise, and the sum stays within 20.
- **Unit, markers:** an honored marker is never counted. An abused marker on all three consumers is counted against the share.
- **Unit, never paired:** a machine whose registry never held another machine keeps 20.
- **Integration, real routes:** on a server configured with N = 5, the 5th wrong PIN from an unknown browser is refused with today's 429 words. Marked browsers, local callers and approval links are never counted. The capacity flags show the share.
- **End-to-end:** two real servers as a pool. Each allows 10 wrong tries per window and refuses the 11th, for 20 in total. Stopping one leaves the other admitting within its share. A browser that unlocked before still works on both.
