# One file on a Windows PC extends the agent to that PC

## Who this is for (read this first)

**For most people, the Instar desktop app is the recommended way to use Instar on a computer.** Instar Connect is for one narrower case: a Windows PC that your existing agent should be able to *use*, where installing a full agent is not possible or not wanted. Examples: a PC that cannot run the agent, a look-only arrangement, short-term help, or a borrowed or shared PC.

Justin approved this direction on exactly those terms (topic 141385, message 145272, 2026-11-18 16:00 PST): "great! I think that makes perfect sense. As long as we make it very clear what the use case is and that we recommend the main Instar desktop app for most users, then I approve". So every surface this spec adds says the same. **The offer depends on what the person wants.** If they want Instar on this computer (to chat with their agent, or to run an agent here), the agent recommends the desktop app (Mac now; Windows once it is released). If they want their existing agent to *use* this PC, the agent says in one line that the desktop app cannot do that yet and offers Connect. This rule lives in the awareness entry (`src/data/awareness/windows-pc-extender.md`) and is tested there. The download page and the PC window both state the use case in their first lines.

## Problem statement

Justin, topic 144319, message 4609198818115544, 2026-11-18 13:57 PST: "I really really really like the idea of a single file that can be run on a Windows machine that gives an agent access", the ideal way "to extend an agent to a machine, other than using the official In[star app]". The Chief of Staff put it on the easy-setup project (topic 143810) the same day with five requirements: one signed file; pairing approved from the owner's app; nothing stored that a stolen file could reuse; a remover; and a full-wipe test on Justin's third machine when it is available.

Today a person who wants their agent to use a Windows PC has no path unless an Instar agent already runs inside WSL on that PC:

- The Remote Desktop companion (`scripts/install-windows-desktop-companion.ps1`, `src/native/remote-desktop/windows/InstarDesktopCompanion.cs`) is compiled on the PC by PowerShell and listens on loopback/WSL only; it serves an agent on the same PC.
- `instar pair` / `instar join` adds a whole mesh machine. It needs a terminal, Node and the instar package, and the typed code alone authenticates the join; the owner's phone is never asked (`src/commands/machine.ts:466-469`).
- The Windows-app lane's test zip (`.instar/lanes/windows-app/instar-test-pc-setup.zip`) is four files, needs an administrator, installs Tailscale and the SSH server, and adds one hardcoded public key.
- No Windows code signing or packaged `.exe` exists anywhere in the repo.
- Email cannot carry an attachment (`src/email/transports.ts:66`), so the file reaches a PC by a link.

What this spec builds is **not** another owner device. The Mac QR pairing (`docs/specs/mac-qr-pairing.md`) makes a paired computer an *owner device*: `role: 'owner'`, full access, able to mint codes and approve other devices (`src/server/mobilePairingRoutes.ts:1312-1316`). A Windows PC that the agent drives is the opposite direction: a machine the agent controls, which must hold **no** authority over the agent. Reusing the Mac pairing unchanged would let the agent, which runs commands as the PC's user and can therefore sign with the PC's key, act as an owner device on its own server.

## Proposed design

This is the **smallest safe form**, chosen under the convergence cut rule after round 4's findings rose (see the convergence report). It rests on three choices:

1. **The PC is a restricted `extender` device, not an owner device.** It can be driven by the agent and has no power over the agent.
2. **Each PC is bound to one agent machine, its *home machine*.** The PC connects only to it, pins only its key, and is redeemed, held, lowered and removed there. Sessions on the agent's other machines reach the PC by asking the home machine. The reason is the PC's trust: it must check every frame against keys the agent cannot add to on its own, and one pinned machine key plus the owner's phone key is the smallest such set. Draft 3's key set across machines produced holder handover, stale-holder and revocation-lag problems three rounds running; draft 4's remote "move" needed a standing mailbox on instar.sh that brought its own blocking, replay and cost problems. Here, changing the home machine is done at the PC: the person presses "Connect again" in the tray and scans once.
3. **The instar.sh drop is used only while a person is pairing,** exactly as the approved Mac pairing uses it, with a paste fallback. There is no standing channel outside the PC's socket.

This outbound-socket, one-server-per-endpoint shape is the standard remote-management agent pattern (MeshCentral's agent, Intune's management extension); what this spec adds is the owner's phone as the only door in, and an endpoint that holds no authority over its server. Embedding an existing agent (MeshCentral, RustDesk) was not chosen because their trust model has a server administrator, not the owner's phone, as the authority, and their binaries carry existing antivirus reputations as remote-access tools; using TUF directly for updates remains an option for the builder if its .NET client meets the same checks.

### The person's journey

1. The person tells the agent what they want. If it is Instar on this computer, the agent recommends the desktop app. If it is their agent using this Windows PC, the agent says in one line that the desktop app cannot do that yet and replies with the Connect download link and one line on what will happen. The download page's first line says who Connect is for and links to the desktop app for everyone else.
2. On the PC the person opens the link. It downloads `Instar-Connect.exe` for the PC's architecture (x64 or Arm64, from the browser's `Sec-CH-UA-Arch` client hint, which the download page requests with `Accept-CH` and `Critical-CH`, since Arm PCs' browsers often report x64 in their user agent; x64 when unknown, which runs under emulation on Windows 11 on Arm; Firefox does not send the hint, so the page also offers both builds by name, and Windows 10 on Arm, which cannot run x64, is told to pick the Arm64 build). The same file serves every agent and person; it holds no secret and no agent address.
3. Double-click. Nothing asks for administrator rights.
4. The window's first line says: "Instar Connect lets your existing agent use this PC. To use Instar on this computer yourself, get the Instar desktop app instead." Then: "This lets an Instar agent use this PC as you." Two choices, neither pre-selected: **"Full control"** (the agent can do anything you can do on this PC) or **"Look only"** (the agent can see the screen and read your files, and change nothing; it can still read anything in those files). It then shows a QR code, with "Paste instead" below it.
5. On the phone: Instar app, "+", **"Connect a Windows PC"**, scan, pick the agent. The app shows which of the agent's machines will hold the PC (below) and lets the person pick another.
6. On the PC, the window shows the agent's name, its owner's name (each clipped to 40 characters with an ellipsis), the home machine's address and a short key fingerprint, with the warning: **"Only connect your own agent, from your own phone. No support person, bank or company will ever ask you to do this. If someone on a call or chat asked you to, press Cancel."** Connect becomes active after a short wait (default 8 seconds). If a known remote-control program (a shipped list: Quick Assist, AnyDesk, TeamViewer, ScreenConnect, Splashtop, RustDesk, LogMeIn, Chrome Remote Desktop, UltraViewer, Zoho Assist, and screen-sharing apps that let someone else see the QR code: Zoom, Microsoft Teams, Discord, Webex, and Google Meet in a browser) is running, the warning is stronger ("A remote-control program is running. If someone else is controlling this PC, press Cancel"), the wait is longer (default 30 seconds), and the phone approval shows the same line. It is a warning, not a block: the person decides. The QR code is the pairing secret: anyone who can see it can try to pair, which is why the phone approval names the PC and its key fingerprint, and why screen sharing raises the warning.
7. On Connect, the phone shows "<agent> will be able to <run programs and use files | see the screen and read files> on <PC name> as you", with the PC key fingerprint matching the one it scanned, and the person approves with Face ID. The PC closes to a tray icon. The agent says in the conversation: "I can now use <PC name>."

**Paste instead.** If the phone cannot reach instar.sh or the PC cannot read the drop, the app offers "Send as a link": the same sealed blob (sealed to the PC's one-time key `k`, so any channel is safe) goes out through the phone's share sheet, the person sends it to themselves by any route, and pastes it into the PC's "Paste instead" box.

Actions for the person: open a link, run the file, pick a choice, scan, Connect, approve on the phone.

### Device class: `extender` (no authority over the agent)

- A separate class, `extender`, set **by the server at mint**, never claimed by the device. The phone's "Connect a Windows PC" action, presence-signed, mints a code on an extender branch of the mint route whose `CodeEntry` carries a new field `deviceClass: 'extender'` (the existing `boundKey` carries the PC key `d`); `PairingPerson.role` is not widened. The redeem route gets the same extender branch. Both skip the owner-pairing preconditions that do not apply (the Telegram approval path and lease checks, `mobilePairingRoutes.ts:1268-1273`), keep the existing address rules (`pairingOrigin()`, `redeemHostEligible()`), and on success write only a pending `computerExtenders` row, never `DeviceRegistry.createPending`.
- Extenders are **never written to the per-machine `DeviceRegistry`**, whose roles existing checks treat as owner-like when not `team` (`src/server/mobilePairingRoutes.ts:615-650`). The existing device middleware therefore never recognises an extender key; `/computers/link` authenticates only against the extender store. A deny-by-default unit test walks every mounted route and asserts an extender-signed request is refused everywhere else.
- Approval uses a new extender-only route, `POST /mobile/extenders/:id/approve`, which accepts only a presence-signed approval (Face ID) from the owner's paired phone. Older app builds never call it; the generic approve routes, the Telegram code and button, and the dashboard refuse extender requests.
- **The Instar app is required to connect a PC (security floor).** Admission gives the agent command over a person's computer, so it needs a human-presence approval the agent itself cannot produce (an operator session or a Telegram button proves the conversation, not a person at a phone). The app's presence signature is the only such approval Instar has; a dashboard passkey approval would meet the same need but does not exist and needs its own security spec. This is an exception to "neither the app nor the dashboard is required", recorded in the frontmatter and named in the approval ask. Android is not in v1's done line; it is tracked as its own item owned by the Android lane.

### Which machine is home

A home machine must have a pairing address and must hold the owner's phone as a paired device, because phone authentication is per machine (`MobileDeviceKeyLedger`: "device authentication stays machine-bound"). Among those, the app proposes the machine it is talking to when it qualifies, preferring a machine with a named tunnel over one reachable only by Tailscale, then the most recently seen (`lastSeen` in the machine registry). The person can pick any qualifying machine. The phone makes the mint on the chosen machine directly at its address, so the code, redemption, approval and first socket are all on the home machine. Before showing Connect the PC checks that it can reach the home origin; if not (for example a Tailscale-only home and a PC not on the owner's tailnet), it says in plain words "This PC can't reach <machine>. It needs <machine>'s web address, or Tailscale on this PC." and offers to scan again for another machine.

### Stores

- `computerExtenders`: a new append-only replicated kind on the compliance-hold retention class (never pruned): extender records, mode changes, home-key rotations, revocations. Rows are written by the PC's home machine, signed with its machine key, and accepted only under that machine's pinned identity key (the `mobileDeviceKeyLedger` rule); the one exception is a **retirement row**, which any machine may write when it carries an owner-signed record naming the retired device (used by Connect again when the old home is gone). Machines on older builds never read the new kind. It gets its `state-coherence-registry.json` entry, an entry in `RECONCILER_ALLOWLIST` with the reason "written only by the server extender routes; no CLI path", and backup inclusion.
- The call audit is **machine-local on the home machine** (it is the only machine that sees the calls), read from other machines through a proxied read, and included in that machine's backup.

### Pairing hand-off (reuses the Mac sealed drop)

- The PC generates its device key: P-256 in Windows CNG under the person's profile, non-exportable, TPM-backed (Microsoft Platform Crypto Provider) when present, the software provider otherwise. Honest limit: a non-exportable key still signs for any process running as that Windows user, and malware running as that user can extract the software provider's key. That matches the person's own privilege; the extender class is what keeps such use from reaching the agent's owner powers.
- The QR uses the Mac flow's carriage (`mac-qr-pairing.md` §2-§6) in a new type `instar.sh/pair-pc` v1 carrying the drop slot `r`, the one-time seal key `k`, the device public key `d`, the PC name `n` (clipped to 40 characters), and `m`, the mode chosen on the PC. The drop slot is refreshed every 120 s, as on the Mac.
- The phone seals to the drop slot: the home machine's origin, the code, the agent and owner names (clipped to 40), the home machine's public key (Ed25519, 32 bytes) and the phone's presence public key (P-256, 65 bytes). At its largest (a 253-character host) this is about 1,100 base64url characters, under the drop's 2,048-character cap; the phone refuses to seal anything larger rather than truncate.
- The PC opens the drop (or the pasted link) and shows the Connect confirmation. On Connect it redeems at the home machine, proving possession of `d` and sending the mode signed by `d`; this creates a pending row. The phone then shows that row's mode and PC key fingerprint, and the person approves (the Mac order: redeem first, then presence approval).
- **Addresses.** The home machine's pairing address under the existing, approved rules (`docs/specs/install-experience.md` §6, approved by Justin 2026-11-02; `pairingOrigin()`): its Cloudflare named tunnel, or its Tailscale name. The program never installs Tailscale. An agent with neither is told so before minting and offered its existing address setup. The quick-tunnel limit is inherited from pairing as a whole, not added here; free addresses for every agent are the job of `docs/specs/hosted-relay.md`, which this program picks up without change when it ships.

### The PC checks the agent, not only the reverse

- The PC pins two keys: the home machine's key (for frames) and the owner's phone presence key (for raises and for owner-signed changes).
- **Encrypted channel: Noise KK, from existing libraries.** At pairing each side also creates a long-term X25519 key: the PC binds its X25519 public key with one signature by its device key `d`, and the home machine binds its own with one signature by its pinned signing key; both bindings are checked once and the X25519 keys are pinned beside the signing keys. Every connection then runs the standard `Noise_KK_25519_ChaChaPoly_SHA256` handshake (both static keys already known to each side) using maintained Noise implementations, never a hand-built hybrid. Choosing them is the first build step: each library is named with its version and last release date in the build plan, and one with no release in the last 18 months is not used; if no maintained library qualifies on either side (.NET or Node), that side implements only the KK pattern over libsodium's X25519, ChaCha20-Poly1305 and SHA-256 primitives, must pass the same vectors, and gets an independent cryptographic review before the first public release. Both sides are checked against the published Noise test vectors and a shared set of cross-language vectors in the test suite. The Cloudflare tunnel carries only ciphertext. Frames are not signed one by one: Noise's transport keys and nonces already bind every frame to this connection and these two peers and refuse a replayed, reordered or altered frame, and signing each frame with a TPM-backed key would slow file chunks and input. The PC's X25519 static key is a software key (Windows' TPM cannot hold Curve25519 keys), stored with DPAPI for the current user (non-roaming), so on its own it could be copied off the PC. To keep "impersonating the PC needs the PC", the device key `d` (TPM-backed where a TPM exists; otherwise a software CNG key, in which case the PC's identity is only as strong as a software key and the window says so) also signs the Noise handshake hash, under its own purpose string `instar-pc-connection-v1`, **once per connection** as the PC's first transport message, and the home machine accepts no call until that signature verifies. No application data travels inside the handshake messages themselves.
- **The initial grant is checked by the PC.** The phone's Face ID approval signs an owner-signed record (below) of kind `grant` binding the PC key `d`, the home key, the mode and the pairing attempt, with order number 0. The home machine hands it to the PC as its first encrypted transport message after the handshake and after the PC's `d` signature over the handshake hash has verified (the home machine sends nothing before that verification), and the PC enables nothing until that record verifies against the phone key it received in the sealed drop. A server that skipped the phone approval therefore cannot make a working PC. The grant is applied **once**, at pairing: accepting it durably establishes the pairing (pinned keys, mode, order number 0), and later connections, including after weeks offline, authenticate only by the pinned keys and use that stored state; the grant is never sent or applied again. If that stored state is missing or fails its check, the PC enables nothing and shows Connect again.
- **Owner-signed records** (grant, raise, home-key rotation, phone-key change, retirement, and the owner's direct Lower or Remove below) are signed by the phone's presence key over a canonical encoding of the **whole record**: a versioned purpose string (`instar-pc-order-v1`), the device id, the PC key fingerprint, the order kind, every value the order sets (the new mode, the replacement home or phone key and origin), the time it was signed, and an **order number** that the PC keeps durably. **Orders that add authority** (grant, raise, home-key rotation, phone-key change) must carry exactly one more than the last number the PC applied. **Orders that reduce authority** (the owner's Lower and Remove) are **not checked against the order number at all**: the PC checks only the purpose string, device id, PC key fingerprint, the phone key's signature and the 10-minute expiry. Applying one sets the PC's number to max(current, the order's number) + 1, which also voids any raise signed earlier. So no home machine, stale mirror or offline tray Lower can block the owner's Lower or Remove; a replayed Lower or Remove can only reduce authority, and only within its 10 minutes (a replayed Lower may undo a raise made after it; the owner signs the raise again). The PC treats a record as a Lower only if the mode it sets is no higher than the current mode; otherwise it is a raise and is checked against the order number. **Every mode change advances the number**, including a Lower from the tray or a home-signed Lower from the console, so a raise signed before any later change can never apply. A record also expires 10 minutes after it was signed (the PC allows 5 minutes of clock difference). After each handshake the PC reports its current number in a transport message signed by `d` and bound to that connection's handshake hash, so the home machine can delay the number but not fake it; the home machine mirrors it and the phone checks the PC's signature before signing; for an authority-adding order a mismatch is refused and the phone re-reads and asks again.
- **Home key rotation** (including Machine Identity Recovery) reaches the PC only as a frame signed by the old key and countersigned as an owner-signed record. The record carries **both** replacement home keys: the new signing key and the new X25519 static key, the latter bound by a signature from the new signing key. The PC replaces both pinned keys in one durable write, closes the current connection, and from then on refuses a handshake from the old X25519 key (tested). If the old key is gone (a lost disk), the person uses "Connect again" at the PC.
- **Owner phone change**: a new phone key reaches the PC only as an owner-signed record from the old phone; if the old phone is lost, the person uses "Connect again" at the PC. The tray's Stop, Disconnect and the Windows uninstall work without any phone.
- The device-signed upgrade request uses the existing device-signature scheme with its 60-second window and replay guard (`src/core/MobileDeviceKeys.ts:16-17`).

### What the agent can do (v1)

Two modes, held and enforced by the PC:

| Mode | What the agent can do |
|---|---|
| Full control | Run PowerShell commands as the person (never elevated, inside a Windows Job Object, with a time limit the calling session states, default 2 minutes); list, read, write and delete files the person can reach and stream files both ways; take screenshots; type and click; open the default browser on a page. |
| Look only | Take screenshots; list and read files the person can reach, except the credential folders below. Nothing that changes the PC. |

Honest capability statement, in the window and the consent text: **"Full control" means the agent can do anything you can do on this PC.** Command running, file writing and typing each amount to that, so they are not offered as separate switches. **"Look only" still lets the agent read what is in your files and on your screen**, which can include passwords shown on screen or saved in documents. By default Look only refuses a shipped list of credential locations (`%USERPROFILE%\.ssh`, browser profile folders for Edge, Chrome and Firefox, `.aws`, `.azure`, `.config\gcloud`, `.kube`, `.docker`, `%APPDATA%\Microsoft\Credentials` and `Protect`, `.gnupg`, `.git-credentials`, `.npmrc`, other Chromium browsers' profiles, and common password-manager and chat-app data folders); the list is a floor against the usual places, not a guarantee, and the person can lift it on the PC.

- **Typing while you work.** Under Full control, typing and clicking wait until the person has not used the keyboard or mouse recently (default 30 seconds) and never act over a full-screen app. A sub-option, "may type and click while I am using the PC", lifts that. This is courtesy, not containment.
- **Lowering** (Full control to Look only, or disconnecting) can be done from the tray, from the app or from the web console; the home machine applies it before answering and sends it to the PC.
- **Raising** (Look only to Full control) needs an owner-signed record (Face ID on the phone), verified by the PC itself, so the agent cannot raise its own access. The phone shows a raise prompt only when the owner started it in the app, or when the PC asked for it from its tray: the tray request is signed by the PC's key `d` and is shown only within 2 minutes of signing. Under Look only the agent cannot run code on the PC, so it cannot produce that signature; but an agent that once had Full control may have left something running as the person that can, so **once a PC has been in Full control, tray-started raises are off for its key** and raises come only from the app. The Lower text says so: after Full control, a Lower stops the program's own commands, and only Connect again (a new key, after the person checks the PC) is a clean start.
- **Protecting the mode from the agent.** The mode, the order number and the person's lifts (credential folders, typing wait) are stored signed with the PC's CNG key, with a second copy under HKCU; if both fail the check the PC drops to Look only and refuses owner-signed records until the person uses Connect again (the number never resets). Honest limit: under Full control the agent runs as the person and can sign with that key, so this protects Look only and nothing under Full control. **Which paths are allowed is decided before anything is opened:** in Look only, only paths on local fixed drives are accepted; UNC and network paths, mapped network drives, `\\?\GLOBALROOT`, device namespaces and named pipes are refused without being opened, so a requested path can never start network authentication. Under Full control the same refusal applies to the program's own file route for Look-only-protected locations. Then every file check is also made on the file actually opened: the program opens the path with reparse points not followed, reads the final path from the open handle (`GetFinalPathNameByHandle`), and checks that against the refused locations, so a link, junction, short name or `\\?\` alias to a refused place is refused, and the check and the read use the same handle. In every mode the program refuses, through its own file path, its own state and install folders, the HKCU Run key, the Startup folders and the Task Scheduler folder, and the input path refuses to act while the program's own window is in front. The consent text says that under Full control, Stop and Remove work only as long as the agent has not changed the PC to prevent them, and that changes the agent made stay after removal (the remover lists the startup entries and scheduled tasks the audit shows the agent created).
- **Locked PC.** While Windows is locked or showing the administrator prompt's secure desktop, screenshot and input answer `pc-locked`; commands and files still run under Full control.
- **No elevation in v1.** A command that needs an administrator gets `needs-administrator`; the agent tells the person it cannot do that on this PC yet and never asks them to run it.

### Lasting safeguards against tech-support scams

The most likely abuse is a scammer talking a stranger into connecting the scammer's agent; the names the PC shows are chosen by that agent, so the safeguards do not rely on them alone:

- At each Windows sign-in the PC shows a notice for 15 seconds: "Connected to <agent>, owned by <owner>", with a one-click Disconnect.
- Whenever a new agent session starts using the PC, the program's own small window (not a Windows toast, which Do Not Disturb hides) names it ("<agent> started using this PC") with Stop; repeated calls from the same session do not repeat it. This is a consent signal on the controlled PC, not a chat notification.
- The tray icon changes while anything runs. **Stop** cancels everything the program started (closes the Job Object, killing every child process it holds) and refuses new calls until the person presses Resume. Honest limit, said in the tray and consent text: a Job Object does not hold programs a command started another way (through WMI, Task Scheduler, a COM server or Explorer), so Stop ends the program's own processes and may not end those.
- The download page and the window carry the same "no support person will ask" text. Owner of this threat: the easy-setup project.

### Agent side

- Route family `/computers` (dark behind `computers.enabled`): `GET /computers`, `POST /computers/:id/exec`, `/files/*`, `/screenshot`, `/input`, `/open-url`, `GET /computers/:id/audit`.
- **Calls from other machines.** A session on another machine submits the call to the home machine over mesh RPC as a small control message carrying a caller-made `callId`. The home machine first writes the call durably as `dispatching` (its intent to send), then sends it, then records `sent` and later `done` with the result. On restart, every call found in `dispatching` or `sent` is treated as **possibly executed**: it is reported as `unknown` and never sent again on its own; the session decides whether to check the PC and retry. Each call carries the caller's creation time and an issue time stamped by the home machine inside the encrypted channel, and `callId`s are scoped to the PC's device id. The home machine binds each `callId` to its first issue time **permanently** (a small durable index kept for the device's lifetime); a retry reuses that original time, and the home machine refuses before sending any `callId` whose original time is older than 7 days, so an expired call can never be re-sent with a fresh time. If the home machine's index is lost or rebuilt (a restore, or Machine Identity Recovery onto a new machine), it records when the new index was created and refuses any `callId` it does not hold whose creation time is before that; a home-key rotation also moves the PC's low-water mark up to the rotation time. The PC writes each `callId` durably as `pc-admitted` (a different name from the home machine's `accepted` answer) **before** it starts running it, keeps them for 7 days, and keeps a durable low-water mark: it refuses any call whose issue time is before now − 7 days (allowing 5 minutes of clock difference) or before the moment its store was created after a loss or corruption (strict, no tolerance), as `expired-retry`. A retried `callId` it already holds is never run again: the PC returns the stored outcome, or `already-ran-result-lost`; one it accepted but never finished (the PC crashed mid-run) is returned as `outcome-unknown` and not run again. So a delayed duplicate can never run a second time. The home machine answers `accepted` at once, and the caller collects the result by `callId` (and stream tickets for anything large). A home machine that cannot be reached gives `home-offline`; a PC that is not connected gives `pc-offline`.
- **When the home machine is offline.** The agent tells the owner once per outage, in the conversation where the PC was asked for: "<PC name> is unreachable while <machine> is off. If <machine> is not coming back, press Connect again on the PC to move it to another of my machines."
- **Who may call.** The route filter admits only sessions serving the owner's own conversation, identified by a new server-held per-session credential issued only when the server spawns a session for an inbound message from the owner on one of the owner's conversations (Telegram topic, app conversation or Slack thread), recorded with the session's spawn reason. It does not depend on the Telegram-only origin credential (`OriginSessionRegistry` is wired only when Telegram is on), and scheduled jobs, which also get origin credentials today, never get this one. The credential is stored durably with the session record and refreshed each time an owner message is delivered into the running session, so it survives server restarts and updates. Other spawned sessions are refused, and the agent bearer token alone is refused. A session that receives typed input through `POST /sessions/:name/input` from anything other than the owner's own message (`src/server/routes.ts:13067`) loses `/computers` until the owner's next message. **Honest limit, stated in the consent text:** Instar's sessions all run as one computer user and can read each other's credentials, so this filter stops ordinary and accidental use by jobs, not a session deliberately working around it; and the owner's own conversation can read web pages, email and tool output. Under Full control, the agent as a whole, including anything it reads, can reach the PC. Look only is the choice for a person who does not want that.
- **Bulk deletes wait for the owner** (accident protection only, not containment: under Full control a command can delete anything without this route). A delete through the Files route of a whole folder, or of more files at once than the owner's setting (default 50), is held with state `awaiting-owner` and a Work Board card is opened ("<agent> wants to delete <folder> (<n> files, <size>) on <PC name>"); only the owner's tap approves it, and an unanswered card expires after 24 hours as `refused-timeout`. This screens structured file deletes only. PowerShell commands and typing are not screened: under Full control a command or keystrokes can delete anything the person can, which the consent text already says. The External Operation Gate is not used here, because it would see every PowerShell command as opaque and ask about all of them.
- **Why not team sharing in v1.** A PC belongs to one person, and sharing it needs per-person session audiences bound into `/computers` plus a signed sharing grant per PC; neither exists. Team sharing of a PC is tracked as its own item on the easy-setup project with the Chief of Staff.
- **Results and files:** everything from the PC enters the agent's context as untrusted data, never instructions. An inline result defaults to 1 MB and the caller may ask for more; beyond the inline size nothing is cut: the result returns the start and the end of each stream (where errors usually are) with `overflow: { stream, omitted: { from, to }, totalBytes, ticket }` and a ticket for the whole stream. Larger results and all files travel through a **new resumable file relay** (modelled on the ticket pattern of `DesktopMeshStreamRelay`, which itself is a live-display pipe and is not reused): 256 KB chunks with resume by offset, written straight to disk, pausing (not closing) on backpressure, and also used to cross from the home machine to the calling machine. A file that would leave less free space than the Disk Steward's floor on the receiving machine is refused with `no-space`, naming the size.
- **Load:** each call has an id and chunks of different calls interleave. One slot is always kept for quick calls (screenshot, input); the home machine admits further calls while the socket's buffered amount stays under the PC's window and the PC's reported load allows, taking sessions in turn, and answers `pc-busy` beyond that.
- **Audit:** each call writes a metadata row on the home machine: when, which session and person asked, what kind, duration, exit code, byte counts, and the command text with credentials redacted; never file contents or output. Repeated screenshots and input merge into counted rows. Old rows move to the home machine's backup archive by age under the Disk Steward's space rules, never deleted. The read is paged by a `(time, rowId)` cursor, 100 rows a page.
- **Surfaces:** the web console gets a Devices page backed by `GET /computers` (online state, home machine, the mode the PC confirmed, audit, Lower, Remove). The iPhone app gets the "Connect a Windows PC" path with the home choice, the extender approval, the raise, the direct Lower/Remove and the PC's page; the app lane (`echo-instar-desktop-app`) builds it in this project from a contract in `.instar/vm-test/app-coordination.md`, tracked as a commitment, with its build number on this project's completion list.
- **Awareness:** one entry, `src/data/awareness/windows-pc-extender.md`, shown only when `computers.enabled` is on.
- **Config:** `computers.enabled: false` added to ConfigDefaults so existing agents get it through `migrateConfig`; It is listed in the dark-gate exclusions (destructive capability, not dev-gated) and gets a `/features` entry so its state is reported truthfully; Echo turns it on with its own config override. The switch is read live: turning it off takes effect without a restart.

### Connection, liveness and revocation

- The PC opens an outbound WebSocket to its home machine's origin. No listening port on the PC, no firewall change, no SSH. The upgrade uses the server's existing WebSocket manager, compression off. A Noise transport message is at most 65,535 bytes including its 16-byte tag, so each 256 KB file chunk travels as several Noise messages whose payload (after the tag and a chunk header of offset, part number and part count) stays under that limit; the part count is capped at 8 and a reassembled chunk may not exceed 256 KB, and is reassembled and checked before it is written; the WebSocket frame cap matches the Noise message size. A cross-language test vector covers a chunk spanning several messages.
- Heartbeat: a ping every 30 seconds; two missed pongs drop the connection on both ends.
- **Lower and Remove** are applied on the home machine before success is returned: the row is written locally, the PC's queue closes for new calls, the frame is sent, and running calls the new mode forbids are cancelled. One machine holds both the socket and the decision, so no other machine can admit a call the owner has refused. Asked on another machine, the request is forwarded to the home machine. If that fails, the app sends the owner-signed Lower or Remove **directly to the home machine's own address** (which it has from pairing), and the home machine passes it to the PC, which verifies the phone's signature itself. The app shows the change as **pending until the PC confirms it** (the PC signs an acknowledgement that the home machine records); if the phone cannot reach the home machine at all, the app says so plainly, that the PC may still be connected, and that Stop or Disconnect on the PC works at once, and keeps retrying while open. A home machine that refuses to pass an owner order on is outside what v1 protects against.
- When the PC's socket drops, the PC cancels running **commands** (closes the Job Object) and on reconnect reports, for each, two separate facts: the cancellation (`cancelled-disconnected`: the program stopped waiting for it and ended its own processes) and the outcome (`outcome-unknown`). **A cancelled command never means it had no effect**: it may have changed files or settings before it was stopped, or after its result was lost. The agent tells the session exactly that and never retries a cancelled command on its own; the session checks the PC before deciding. File transfers pause and resume by offset if the connection returns within 10 minutes. A file being written goes to a temporary file beside the target and replaces it only when complete, so a dropped transfer never leaves a cut-off file; an abandoned temporary file is deleted after the 10 minutes.
- Reconnect: full-jitter backoff from 1 second doubling to a 5-minute ceiling. Refusals carry a kind and a wait:
  - `retry-after`: wait as told.
  - `update-required`: self-update (below), then reconnect.
  - `unknown-device`: keep retrying (the home machine may be restoring from backup).
  - `feature-off`: probe once a day.
  - `device-revoked`: remove only when the answer carries the revocation row signed by the pinned home key; otherwise treat as `unknown-device`.
  - A plain 404 on the socket path (a home machine on an older build) is treated as `feature-off`.
- **Breaker.** After 7 days without a handshake the breaker trips: the tray says "Can't reach <agent>'s <machine>" with Connect again, Stop trying and Remove, and attempts drop to once an hour. The PC never gives up on its own, because a home machine can be away for weeks; it stops only when the person chooses Stop trying or Remove, or on a signed revocation.

### Remover

- What triggers removal: the person's Disconnect in the tray or the Windows uninstall; a revocation row signed by the pinned home key; or an owner-signed Remove from the phone (not checked against the order number).
- "Disconnect" in the tray, the Windows Settings > Apps uninstall entry (per-user, HKCU), and an owner Remove all end the same way: cancel running calls (close the Job Object), tell the home machine it is leaving (best effort), delete the CNG key, delete `%LOCALAPPDATA%\Instar\Connect\`, delete the HKCU Run and uninstall entries, then exit and delete the install folder `%LOCALAPPDATA%\Programs\Instar Connect\` through a one-shot cleanup started at exit.
- An owner Remove writes the signed revocation row first, then sends the frame; a PC that is offline removes itself at its next handshake. "Connect again" (to move to another machine) is a fresh pairing with a new key: it deletes the old CNG key, the old X25519 key and the old order-number and `callId` state on this PC before creating new ones; the approval on the phone also signs a retirement record for the old device id, and the new home machine writes it as a retirement row, valid even if the old home is gone for good.

### Updates

- The first transport message after the handshake carries the protocol version and build number; the server answers `update-required` below its minimum. The PC fetches the manifest from the fixed release address `https://github.com/JKHeadley/instar/releases/download/instar-connect/instar-connect-manifest.json` (a fixed tag, as the Mac app's appcast uses, because the repo's "Latest" release is not this program) (never a URL the server supplies) and checks, before running anything: the manifest is signed by the **Instar Connect release key** (Ed25519; public key compiled into the program; private key kept non-exportable on the release host, never in the agent's shared vault or on its other machines) **and** carries Justin's release approval: a presence signature (Face ID) from Justin's phone key, also compiled into the program, over the manifest hash. Each release therefore needs one tap from Justin on his phone, which the agent cannot produce; this is part of what his yes covers. A new release key, or a new phone key for Justin, is announced in a manifest signed by both current keys. A third key, the **offline release-recovery key** (an Ed25519 key in the PIV slot of a hardware security key Justin holds, signing the announcement bytes directly; its public key also compiled in), may on its own announce a successor phone key for Justin and nothing else; this covers the expected case of Justin replacing his phone. Every key announcement carries a **key epoch**; the PC stores its current epoch durably and refuses any announcement at or below it, so an old announcement cannot bring back a lost or stolen key. A key announced by the recovery key alone takes effect only 7 days after **this PC first saw** the announcement (stored durably as pending; never counted from a time inside the announcement, which could be backdated), and a cancellation signed by the current phone key, carried in the same manifest channel, voids it. Honest limit: someone holding the current phone key could cancel every recovery announcement and so stop releases; that halts updates but grants no code on any PC. Manifests carry an expiry (default 30 days); a PC that sees only an expired manifest stays on its build and says "can't check for updates" in the tray, so a stale manifest served forever is noticed. The signed manifest carries `minimumBuild`, which every PC enforces itself; raising it is the emergency stop for a bad release. Honest limit: it helps only once a newer good build exists (which needs Justin's tap), and a PC whose updater is itself broken stays on its build and shows "Update needed: download the latest Instar Connect" with the download link. The manifest carries an RFC 3161 timestamp; the downloaded build's Authenticode signature chains to the Microsoft root with a publisher identity-validation OID (under `1.3.6.1.4.1.311.97.`) that is in the allowlist **compiled into the running program**; the SHA-256 matches; and the build is newer than the installed one. All checks must pass, so the agent's machines alone (release key and signing account) cannot push code to PCs without Justin's tap. A change of publisher (for example to SageMind) ships as a build signed under the current identity whose compiled allowlist adds the new one; Honest limit: if Justin's phone key and the recovery key are both lost with no announced successor, fielded PCs cannot update until each person reinstalls from the download link. If the manifest fetch or a check keeps failing, the PC stays on its build, retries hourly, and says so in the tray. The PC never runs a build that fails any check.

### Building, signing, publishing

- One self-contained .NET 8 single-file executable per architecture (win-x64, win-arm64). The capture and input classes from `InstarDesktopCompanion.cs` are compiled in; its `Main` and `TcpListener` are not, and a Windows test asserts the program opens no listening socket. Ed25519 verification uses a bundled library (the .NET 8 base library has none).
- Signed with Microsoft Artifact Signing under the individual identity **Justin Headley**, the publisher name of the Mac app. This needs an Azure subscription in Justin's name (about US$10 a month) and a one-time identity check with his ID. Both go to Justin as one four-part request (problem, exactly what changes, what yes does, what no or waiting does) after this spec is approved and before the first public release. If Microsoft does not enrol an individual in his country, that request names signing under SageMind instead. Unsigned builds are never published.
- Built and signed on a Windows host the agent controls (the Mama PC, with any other reachable Windows machine as fallback). Assets go to GitHub Releases of the instar repo; the download link (instar.sh/pc, the `site/` project) redirects to the right asset.
- **Release gate** (after approval, before the first public link): Defender file analysis; a fresh Windows install downloads and runs the signed build with Defender and SmartScreen on. A Defender detection fails the gate; SmartScreen's first-run warning for a new publisher passes it, and the download page shows the publisher name the person should see and says to stop if it differs. Because this program does what remote-access tools do, detections can arrive after release: a weekly job re-submits the current build to Microsoft's file analysis and records the verdict, the PC reports `blocked-by-security-software` when it cannot start a command or its own update, and the agent tells the owner in plain words. PCs under company policy control (AppLocker, WDAC) are not supported in v1, and the download page says so.

### Packaging: the separate file now, a desktop-app mode later

A side-by-side comparison (`docs/specs/reports/windows-one-file-extender-vs-desktop-app.md`) found that the desktop app cannot do this today: its two doors either create a brand-new agent on the PC or make the PC an owner device, and neither lets an existing agent use the PC. The Windows desktop app exists but is not released: `apps/instar-ios` branch `echo/windows-app-m1` (657aa31, 2026-11-18) has `InstarWindows` with a Pair sheet (`InstarWindows/App/PairSheet.cs`) and no public download yet. It recommends that, long term, this design live inside the Windows desktop app as a third door, **"Let my agent use this PC"**, rather than as a second program, because one program is easier to explain and saves a second signing, updater and download path.

- **v1 ships as the separate file**, because the Windows desktop app is not released yet (no public download); the separate file can reach people before it. Its download page and window say who it is for and point everyone else to the desktop app. This choice is open to Justin: building Connect into the Windows app from the start (for example as a checkbox on its Pair screen, "Also let this agent work on this computer") is the alternative under his consideration, and the approved frontmatter waits for his answer.
- **When the Windows desktop app ships**, the same PC side moves into it as that third door, owned by the Windows app lane as a row in its plan. Nothing in the server side changes: the `extender` class, the extender-only approval route, the home machine and the stores are shared. Inside the app the command handler runs as its own process with its own extender key, never the app's owner key, and on a borrowed PC the app starts in that mode only, with no chats and no owner pairing.
- The separate file then stays available only for borrowed PCs, if real requests for that appear; otherwise it is retired with a final update that points to the desktop app.

## Decision points touched

- Whether a PC may become an extender — invariant; basis: irreversible-consequence; evidence: an extender runs commands as the person, so admission is only the owner's presence-signed approval on the extender-only route for a server-minted extender code; no code alone, Telegram, dashboard or agent path.
- Whether an extender key is accepted on a route — invariant; basis: enumerable-domain; evidence: one accepting route (/computers/link), authenticated only against computerExtenders; every other mounted route refuses, checked by a walk of the route table.
- Whether a call runs on a PC — invariant; basis: enumerable-domain; evidence: two modes held by the PC, each call kind mapped to the modes that allow it, checked at the PC.
- Whether the mode may be raised — invariant; basis: irreversible-consequence; evidence: a raise gives command over the person's computer, so only an owner-signed record with the next order number, verified on the PC, is accepted.
- Whether an owner-signed record is current — invariant; basis: enumerable-domain; evidence: an authority-adding record must carry exactly the last order number plus one, an authority-reducing record (Lower, Remove) is not checked against the number, each with matching purpose, device id, key fingerprint and every value it sets, signed by the pinned phone key.
- Whether a PC enables any mode — invariant; basis: irreversible-consequence; evidence: only after a grant record signed by the phone key from the sealed drop verifies on the PC.
- Whether a call reaches /computers — invariant; basis: irreversible-consequence; evidence: a command on someone's PC cannot be undone, so only a session serving the owner's own conversation, by its conversation credential, and not after non-owner input; stated as a filter, not an isolation boundary.
- Whether a PC removes itself — invariant; basis: irreversible-consequence; evidence: removal deletes the key; only the person at the PC, a revocation row signed by the pinned home key, or an owner-signed Remove (checked for purpose, device, key and expiry) triggers it.
- Whether a frame is from the agent — invariant; basis: enumerable-domain; evidence: the PC accepts only a Noise KK session with the pinned home X25519 static key (bound to the pinned home signing key), and Noise's transport nonces refuse any replayed, reordered or altered frame.
- Which machine holds a PC — invariant; basis: enumerable-domain; evidence: exactly one, the home machine recorded in its extender row; changed only by Connect again at the PC.
- Which machine is proposed as home — judgment-candidate; floor: only machines with a pairing address where the owner's phone is paired; default: the machine the phone is talking to, preferring a named tunnel, then most recently seen; arbiter: the person, who picks on the phone.
- Whether a bulk file delete runs — judgment-candidate; floor: a folder delete always waits for the owner; default: more than 50 files at once also waits; arbiter: the owner's tap on the Work Board card, expiring after 24 hours as refused.
- Whether a release may run on PCs — invariant; basis: irreversible-consequence; evidence: an update runs new code on every connected PC, so only a manifest with both the release key signature and Justin's phone presence signature is accepted.
- How long an owner-signed record stays valid — judgment-candidate; floor: an authority-adding record must carry the next order number and any mode change advances it (a Lower or Remove is not checked against the number); default: 10 minutes after signing with 5 minutes of clock difference; arbiter: the owner, who signs again if it lapses.
- Connect wait on the PC — judgment-candidate; floor: Connect is never instant and the scam warning is always shown; default: 8 seconds, 30 when a remote-control program runs; arbiter: the person, who may Cancel at any time; reviewed at graduation from live-proof timings.
- Whether a running remote-control program stops pairing — judgment-candidate; floor: the stronger warning shows on the PC and on the phone approval; default: warn and wait longer, never block; arbiter: the owner's presence approval.
- Which folders Look only refuses — judgment-candidate; floor: the shipped credential list is refused by default; arbiter: the person on the PC, who can lift it.
- Typing while the person is active — judgment-candidate; floor: never over a full-screen app and never within the person's recent activity unless they lifted it; default: 30 seconds since the last input; arbiter: the person's sub-option.
- How long a tray raise request stays valid — judgment-candidate; floor: it must carry the PC's own signature; default: 2 minutes; arbiter: the owner, who approves or ignores it.
- How long a command may run — judgment-candidate; floor: Stop and the Job Object always cancel it, and the tray shows it running; default: 2 minutes; arbiter: the calling session states the time it needs.
- How many calls run at once — judgment-candidate; floor: one slot always free for quick calls, buffered bytes never above the PC's window; arbiter: the home machine, from the PC's reported load, taking sessions in turn.
- How much of a result is inline — judgment-candidate; floor: nothing is cut, head and tail are kept and a ticket names what was omitted; default: 1 MB; arbiter: the calling session.
- Whether a file transfer is refused — judgment-candidate; floor: never leave less than the Disk Steward's free-space floor; arbiter: the Disk Steward on the receiving machine.
- Reconnect timing and the breaker — judgment-candidate; floor: never faster than 1 second with full jitter, never more than once an hour after the breaker trips, the tray always shows the tripped state; default: trip after 7 days; arbiter: the server's refusal sets the wait inside the floor, and the person decides in the tray to keep trying, stop or remove; reviewed at graduation.
- How long audit rows stay online — judgment-candidate; floor: rows are archived, never deleted; arbiter: the Disk Steward's space rules.

## Multi-machine posture

- Extender records, mode changes, home-key rotations and revocations: unified, through the `computerExtenders` replicated kind (written by the home machine, signed by its key).
- The PC's binding to its home machine: unified as data (every machine sees which machine holds a PC and submits calls to it); the live socket terminates on the home machine only.
- machine-local-justification: physical-credential-locality — the PC pins the home machine's own signing key, which lives on that machine's disk and is never copied; only the holder of that key can answer the PC's handshake.
- The call audit: proxied-on-read from the home machine, which is the only machine that sees the calls.
- Calls from sessions on other machines: proxied to the home machine over mesh RPC by `callId`; results cross through the resumable file relay.
- Pairing codes: machine-local on the home machine.
- machine-local-justification: physical-credential-locality — the pairing code is a one-time secret held only as a hash on the machine that minted it, as the converged Mac pairing (docs/specs/mac-qr-pairing.md) declares.
- The home-offline notice: sent once per outage by the machine serving the owner's conversation.

## Rollback

- `computers.enabled: false` (read live) unmounts `/computers` except the handshake endpoint, which stays to answer `feature-off`. New calls are refused, running calls are cancelled, every connected PC gets a `feature-off` frame and its socket closes; PCs keep their pairing and probe once a day.
- A build in the field is retired by raising the minimum build (PCs self-update) or made inert by revocation.

## Frontloaded Decisions

- A separate `extender` class kept out of `DeviceRegistry`, with no authority over the agent.
- Each PC bound to one home machine, proposed as the phone's current machine (named tunnel first, then most recently seen) among those where the owner's phone is paired, chosen by the person; moved by Connect again at the PC.
- The instar.sh drop used only during pairing, with a paste fallback; no standing remote channel.
- Two modes, Full control and Look only, with honest text about what each means; credential folders refused under Look only by default.
- Raise only by an owner-signed record verified on the PC; authority-adding records carry the PC's next order number, the owner's Lower and Remove are not checked against the number, so they can never be blocked.
- Callers: owner-conversation sessions by a server-held credential issued at conversation spawn and refreshed on each owner message, as a filter with its limit stated; no team sharing yet (tracked).
- Bulk file deletes through the Files route wait for the owner's tap on a Work Board card; commands and typing are not screened, as the consent text says.
- Frames encrypted end to end between the PC and the home machine with the standard Noise KK handshake from maintained libraries on both sides, cross-language test vectors, and no per-frame signatures.
- Instar app (iPhone) required as a security floor; a constitution exception that needs Justin's yes, named in the approval ask. Android tracked by the Android lane.
- Scam safeguards: warning plus wait at Connect, stronger warning and longer wait (never a block) with a remote-control program running, a sign-in notice and a per-session notice in the program's own window.
- Addresses: the existing approved pairing rules (named tunnel or Tailscale); quick-tunnel support comes with the hosted relay.
- Per-user, no administrator, no elevation in v1.
- Updates trusted only with all of: the release key on the release host, Justin's Face ID release approval, the Authenticode identity in the compiled allowlist, and the hash.
- Signing: Microsoft Artifact Signing, about US$10 a month, publisher "Justin Headley"; asked of Justin as its own four-part request after approval, before the first public release. Done for this run does not wait for it.
- Hosting: GitHub Releases behind instar.sh/pc. Release host: the Mama PC.
- C#/.NET 8 single file, sharing capture and input code with the Windows companion.
- v1 scope: commands, files, screenshot, input, open a browser. Not v1: elevation, team sharing, remote move, quick-tunnel and same-network addresses, Android, Instar sessions on the PC, other operating systems.
