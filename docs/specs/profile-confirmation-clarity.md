# Clear pending engine-change questions

## Problem statement and authorization

The current engine-change echo exposes framework identifiers. Only one request can wait in a chat, later agent messages cancel it, and an intentional reminder can disappear as duplicate content. This slice fixes those defects while retaining exact consent. The broader model-authority proposal and the subsequent numbered-affirmative grammar are parked unapproved.

Chief of Staff message `3ef983bf-3127-4a50-a348-a96feca62208` (GET /messages/3ef983bf-3127-4a50-a348-a96feca62208) says: “Structure applies the change only on an exact match: the existing bare 'yes' to an identified pending request” and “For any other reply, such as '1) yes' or a quoted request plus yes, nothing is applied.” A judge may send a reminder, “never consent.” This final disposition supersedes the earlier instruction admitting numbered replies.

## Frontloaded Decisions

1. Preserve platform-authenticated owner checks, forwarded-message refusal, cross-topic eligibility/field allowlist, configured TTL and current send-rate guard. No body-supplied sender, peer-asserted identity, copied text, regex or model decision can authorize a write. Existing unrelated recovery-command grammar is unchanged.
2. Add identified proposals alongside the legacy recovery slot, with a random immutable request id, deeply copied patch, destination, complete rendered consequence, disposition fingerprint, ownership epochs and per-attempt delivery receipts. Different questions coexist. A request is equivalent only if confirming conversation, destination, kind, canonical patch, both current ownership epochs and freshly rendered consequence all match. An invalidated old epoch is excluded from reuse; reproposing after a move away and back creates a new id. Repeating an equivalent active request sends a reminder of the same id without extending expiry. No replacement/supersession endpoint is added in this slice.
3. The new identified-proposal path applies only when the owner's entire text is exactly `yes` after outer whitespace trimming (no numbering, quotes, reference suffix, punctuation or conditions), and native Telegram reply metadata identifies a successfully delivered receipt for that request in this conversation. The inbound platform message id must be later than that receipt. Never fall back to another request after an unknown, unrelated, expired or conflicting reply. A proposal reply cannot fire the legacy recovery slot. As soon as any competing proposal/reminder send starts, suspend older legacy bare-yes matching, not merely after its receipt callback. Await the same bounded settlement before either native-reply or unthreaded legacy arbitration; on timeout no legacy operation may run. Only definite non-delivery plus delivered-id ordering can restore its prior bare eligibility. When a newer identified proposal question or reminder is delivered, disable any older recovery slot’s bare-yes path; it cannot fire on an unthreaded yes meant for the new question. Preserve reply-bound recovery only if supported, otherwise disarm that older recovery challenge. A later freshly echoed recovery challenge retains its existing behavior. Test both prompt orders using actual delivery ids, not call completion order. Legacy no-selector behavior is not expanded to new proposals.
4. Every other message, including “1) yes”, a quoted request plus yes, a partial quote, a reference or mixed instructions, reaches the existing conversational agent intact. It applies nothing. The agent may judge that it resembles an answer and call the proposal route’s explicit reminder operation `{remindRequestId}` for one reminder of an independently identified existing request; that judgment has reminder authority only. The reminder derives its opening from the stored requested action and engine, or uses the neutral “Reply to this message with yes to confirm the change below,” and repeats the complete stored consequence and per-field fates; it is fully sufficient to authorize the stored request even if the owner reads only the reminder. The reminder operation accepts no replacement patch and never creates a new proposal: load the immutable registered patch by id, recheck eligibility and fresh consequences, then send; expired or changed requests return fresh-proposal-needed without creating one. If the referent is unclear, ask which change the owner means using the conversation name, action and stable reference; two changes in one conversation must stay distinguishable. That clarification itself never writes settings. The agent requests a server-rendered clarification using `{clarifyPending:true}` on the proposal route, rather than assembling pending details itself. The server loads the confirming conversation’s pending requests, rechecks current audience and destination eligibility, and sends a clarification containing only eligible destination/action/reference labels. An unreadable or shared audience gets only a generic question with no pending details. This operation never creates a proposal, changes a patch or grants consent; it uses the same bounded reminder delivery lane. Test two pending changes after a private conversation becomes shared. Also fail the audience read with two pending requests and assert the actual sent text is generic and contains neither destination, action nor reference. There is no new classifier on ingress and no model call on the exact-yes path. Ship an awareness entry for this use of the existing agent, not a separate regex consumer.
5. Track pending sends per attempt. Each callback records its delivered id against its own request/attempt, never “the latest.” Keep prior successful receipt ids so replying to the original works after a reminder. A failed reminder preserves earlier receipts; a never-delivered request is removed only once all pending attempts finish and none succeeded. If a fast native reply arrives while a potentially matching send is pending, await settlement within an explicit overall deadline bounded by the existing Telegram request budget (not each individual retry's timeout). On overall timeout execute nothing, preserve the question, record that inbound id’s terminal timeout outcome, and route the original message normally. Recheck expiry before suggesting another reply; if the question expired during the wait, offer a fresh question instead of an impossible retry. A receipt arriving later never makes redelivery of that same inbound id executable; only a fresh first-party reply may approve. No permanent unknown-selection result is cached before receipt settlement.
6. Consume a selected request once before invoking the existing write surface; preserve that surface's existing eligibility/write failure semantics. Synchronously reserve the confirming conversation and authenticated inbound message id before the first asynchronous wait, and store a shared pending-result promise through selection and write completion. Cache the committed result before attempting acknowledgment; track acknowledgment delivery separately, so a failed send cannot erase a saved result or reject its cached successful outcome. Redelivery returns the saved result and may retry only the acknowledgment, never the mutation. Test successful flush, failed acknowledgment, then duplicate inbound delivery. Concurrent redeliveries join that result rather than reselecting or reporting unknown after the request is consumed. Retain the first matching outcome, including unknown/ambiguous, for the ephemeral challenge lifetime. Test duplicate delivery while the write flush is deliberately paused: one write and consistent responses. Redelivery cannot select another remaining request. Agent messages never delete identified proposals. TTL cleanup bounds proposal, attempt and inbound-outcome indexes; rate pressure never deletes delivered valid questions. Reminder attempts share the existing implementation's five-per-ten-minute per-topic send budget (DEFAULT_MAX_PROPOSALS/DEFAULT_PROPOSAL_WINDOW_MS); retries of one attempt charge once, and exhausted budget preserves receipts and expiry. This explicit send-budget decision bounds deliberate reminder delivery without inventing a new global quota.
7. Render the actual destination name and friendly engine names from frameworkFacts. Explain actual engine/account effect, restart/recent-context consequences, preview-only and refused fields honestly; never promise full transcript preservation or unsupported quota savings. Every question carries its stable reference and asks for a native reply with yes. Each deliberate reminder has a unique attempt marker so it can arrive despite exact-content deduplication; transport retries of that attempt reuse its text. A suppressed/recorded send is not delivery and never yields a receipt.
8. Recheck source-audience, destination eligibility and current placement before every question/reminder and again inside the mutation boundary. Bind both ownership epochs: a transfer away and back still invalidates the request. Epochs come from SessionOwnershipRegistry.read(topicKey).ownershipEpoch, ownerMachineId and status; use the same registry instance read by placement. The confirmed-write guard executes synchronously inside the profile mutation lock with no await between the final registry reads and authoritative in-memory profile/shadow assignment. Local ownership CAS and that synchronous commit point serialize on the same event loop. Recheck epochs after durable flush before any runtime handoff; a transfer observed during flush forbids the old owner’s runtime action. Record and disclose the successful settings write separately from the skipped runtime action, without claiming nothing was saved or demanding approval again for an already effective value. After the parent transfer carrier reconciles the successor’s profile, inspect its effective settings; prepare a fresh question only for a still-outstanding change. Test the successor’s reconciled profile and acknowledgment as well as the old process surviving. The parent profile carrier remains responsible for cross-machine profile continuity; this slice makes no new global distributed-transaction claim. A readable absence of a placement record retains the parent's local-owner convention; a failed configured registry read is unknown, not absence. If destination belongs to another machine, direct the owner to confirm there rather than forwarding human authority. The new proposal path compares the complete disclosed consequence under one topic lock, including live/preview/refusal and interruption/defer behavior. Use one compound live+shadow operation and one durable flush; if regime/binding/consequence changed, write nothing and ask a fresh question. No new busy/protected-session interruption permission is granted.

## Proposed implementation

Extend ProfileConfirmSlots with a separate identified proposal collection and explicit request/attempt APIs. Keep the legacy recovery slot isolated. Routes validate eligibility, render, register an attempt, send its immutable text and complete that attempt with an actual delivery id. In ingress, only an exact yes with a native reply reaches identified proposal matching. A reply to a proposal is never reinterpreted as a recovery command. All non-exact and unresolved text continues through normal agent delivery. An exact reply to a known expired question gets a plain, scoped recovery message. Replay a recorded earlier outcome while available. After restart/receipt cleanup, an unmatched reply might concern an already-applied question or ordinary conversation: route it normally and, if needed, say only “I did not apply a profile change from this reply,” never claim its old question was inactive or never applied. A delivery-wait timeout says “I could not verify that delivery in time; reply again to the question,” since the proposal remains available for a fresh reply. Existing legacy commands use their existing slot when no identified-proposal reply is involved.

Pass the stored registered patch and disclosed consequence into the existing write surface. Its internal confirmed-write guard compares a fresh render plus eligibility/ownership at the actual mutation lock. A new compound operation commits the live and shadow fields together; do not nest the old separately locking mutators. Receipt identity is never taken from the caller's prose.

No exact-copy matcher, text-reference consent grammar, semantic consent judge, durable distributed approval ledger or new interruption action ships. Complete quotes and numbers are conversational context for reminders only. The literal prompt is: `Move the Instar dashboard makeover conversation to Codex? I will restart it with a summary of the recent work. Request R-a17c39f2. Reply to this message with yes.` A mixed model change says plainly when that model setting is only recorded for preview rather than applied. The literal example applies to the legacy immediate-restart regime. In fully live mode, also disclose whether changing engines removes automatic heavy-work escalation, as required by Topic Profile §9; reminders repeat that effect. Renderer tests assert the friendly destination, consequences and per-field fate, including fully live escalation loss.

## Multi-machine posture and recovery

These remain ephemeral platform/ownership-bound challenges, not accepted durable operations. Restart or ownership change invalidates the old challenges; the successor can only reissue a fresh destination-bound question and can never infer old consent. The parent's durable profile-transfer path remains unchanged. Outgoing question/reminder text and successful profile/audit writes still use the existing canonical conversation/profile history; the local nonce/receipt index is not the sole copy of what was offered. Read-only history can travel without ever rearming expired consent. No second machine, off-machine store or new grant replication is required. The existing platform identity and local ownership epoch are physical authenticated ingress state, not a peer's assertion of a human sender.

## Experience fit

Several independently answerable questions survive progress messages. The normal successful journey is a clear named question and a native reply containing yes. A non-exact answer does not vanish: it reaches the agent and can produce a short reminder instead of an unsafe inferred change. An expired question, changed consequence or transferred destination requires a fresh question. There is no silent success and no new model consent authority.
