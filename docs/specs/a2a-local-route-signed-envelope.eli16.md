# Proving who sent a message on the same-computer route (ELI16)

Agents can message each other in two ways. One goes through a shared relay on the internet. The other is a shortcut used when both agents run on the same computer: one hands the message straight to the other's server.

The relay way proves who is sending. Every message carries a digital signature made with the sender's private key, and the receiver checks it against the sender's public key before reading the message. A forged or altered message fails the check and is thrown away.

The shortcut never proved anything. The sender wrote its own name into the message, and the receiver believed it. The only thing the receiver checked was a password-like token that any program on the same computer could read. An earlier change made the shortcut look the sender's name up in a trust list, but it still took the name on faith. That earlier change said so plainly and pointed at this one.

This change closes that gap. Every message on the shortcut now carries the same kind of signature the relay uses. The receiver looks up the sender's name in its own list of agents it has met and checks the signature against the public key it has on record for that name. The identity it then passes to everything downstream is worked out from that verified key, never copied from the message. If the message has no signature, the signature does not match, the message claims a fingerprint that is not the one on record, the message was addressed to a different agent, it is older than ten minutes, or it is a byte-for-byte repeat of one seen in the last ten minutes, the receiver refuses it with a clear, typed answer that says which check failed and whether the fix is on the sender's side or the receiver's. A refused message is never recorded anywhere: no inbox entry, no history row, no attribution to a conversation.

The review process changed three things about the first draft. First, a receiver that has never met a sender no longer waits for a human to run a discovery tool: on first contact it fetches the sender's key itself, from the same place the discovery tool reads, records it, and checks the message again. It only ever adds a key it does not have; it never swaps out a key it already holds, because whatever process happens to answer on that port must not be able to take over a known agent's name. It tries at most five times per sender, then stops and reports. Only a sender that is not registered as running on that computer, or whose server does not answer, stays unknown — and that is reported to the operator, not just counted. Second, the drafts had a hole: one of the two sending programs, when a message was refused, would park it in an offline folder that the receiver empties at its next start without checking any signature, so a refused message could sneak in later. Now a refusal is final on that path (the send fails and says why), and anything that does legitimately wait in the offline folder is checked with the same signature rule when it is picked up. Third, the receiver's own identity on record is now derived from the key it verifies against; a stale or hand-edited fingerprint in its list can no longer make a message look like it came from someone else.

Both programs that use the shortcut now sign what they send, using the identity key each agent already has, and never sign on behalf of a different name. An older receiver that does not know about the signature simply ignores it, so agents can update in any order.

There is no switch to turn this off. A safety check with an off switch is not a safety check, and another agent's own backup route has been waiting for this proof to exist before it is turned on. The operator accepted the cost, which is this: while the agents on one computer are at different versions during an update (up to about half an hour apart, longer for an agent that is not auto-updated), an updated receiver refuses an older sender's unsigned messages; those go over the relay instead, or the send fails and says so. Both cases show up by name in the receiver's log and on its private health page.

Two limits, said plainly. The check does not stop a program running as the same user on the same computer, because such a program can read every agent's private key anyway. And the key on record was taken on first contact from the agent's own server on that computer, so the signature proves continuity with whatever answered there when the key was recorded — the same footing the relay's discovery stands on — not a stronger kind of identity; mutual verification is a separate feature.

**What ships now.** The signature check on the shortcut, live for everyone, with self-service key fetching on first contact, a terminal refusal on both sending programs, a signature check on the offline folder, and counters on each agent's private health page.

**What needs deciding later.** Whether to merge the offline folder's one-boot pickup into a timed sweep, and whether the discovery tool should merge rather than replace its list.

**Status.** Approved for building under the operator's directive for this commitment (Justin, Telegram topic 9210, 2026-10-09).
