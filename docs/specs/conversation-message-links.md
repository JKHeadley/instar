# Links That Open The Selected App Message

Choosing Copy Link on an App message should give you a link that opens that exact message. Today the dashboard can highlight a selected message, but searches only a few pages before asking you to keep looking. This change adds the missing Copy Link action and opens an older App message directly, without losing your draft or marking newer unseen messages read.

This is a complete App-link increment on open card wc_4d8dd0e0144b636e. Exact Telegram and Slack links, quoted replies, forwarding, editing and single-message deletion remain owned increments on that card. They are not completed or implicitly approved by this change. Provider-source namespace and offline canonical lookup findings remain preserved in the platform draft/reports, rather than being waived by calling local aliases global. No provider log/schema or new evidence subsystem ships in this App-only increment.

## Existing Source And Authority

AppConversationStore already indexes messageId/eventId and pages by the raw stored `(at,eventId)` tuple. The existing app-message emitter, replicated-kind schema, journal commit ingest and boot peer-stream catch-up carry these immutable message events between installed members. This feature persists no new knowledge or link-basis record: it projects identifiers from an actual held message under the existing current reader and message ACL. It asserts neither a globally complete/latest history nor recovery from an offline origin. Known stale/Pending authority remains unavailable. A local miss stays recoverable uncertainty; a new all-member read quorum is unnecessary.

Reuse the ordinary active signed-device/browser admission. Capture the actual signature admission and re-resolve its device/key/person/grants before returning private identifiers; never replace it with a newly reassigned person. Owner admission may reuse mobileOwnerDeviceAdmission; non-owner App readers retain their existing actual standing and grants without becoming owner. Apply conversation-read permission and pairing.mayReadStored to the actual validated message. Agent bearer calls require literal reader=owner and the actual resolved owner; signed callers cannot choose a reader. Notify-token principals are excluded. No copied URL grants access.

## Exact Link GET

The default-off `mobilePairing.native.messageLinks.enabled` flag controls link generation, exact target and context history modes, the compatible dashboard entry, and action advertisement for web and native. With the flag off, a direct exact link GET and exact/context history return 503 `message-link-unavailable` for admitted callers. The versioned dashboard entry shows an unavailable state without initializing ordinary history. Legacy dashboard entry, ordinary history and previously supported legacy navigation keep their existing behavior. Test direct invocations with the flag off, as well as a previously generated link reopened after disabling and re-enabling the flag.

Add `GET /mobile/conversations/message-link?ref=app:<uuid>&messageId=<target>`; only agent calls add reader=owner. Optional targetKind is event, message or legacy (default legacy). Accept each scalar field once and reject unknown/array fields. Normalize App refs with the existing canonicalConversationRef parser and reject non-App refs as unsupported400. This new route is narrowly added to DEVICE_ALLOWLIST and BROWSER_ROUTES, body none. The general agent /messages/link route remains outside the device allowlist.

Legacy targets accept message ID or event ID, preserving existing `m` links. Explicit event and message kinds search only their corresponding index/domain; the discriminator grants no authority. Both are nonempty opaque strings of at most 128 characters without ASCII controls, matching validateAppEvent's literal `str(r.messageId,128)` and `str(r.eventId,128)` in AppConversationStore. Parameterize all index queries and scope them to the requested canonical conversation. Verify the actual event is message/media-message. Apply actual current per-message visibility to each validated candidate before deciding ambiguity; hidden candidates cannot change the result for a single visible candidate. If two distinct visible messages remain, return masked unavailable instead of guessing. An unreadable candidate keeps the lookup unavailable rather than guessing its visibility. Return the canonical message ID on success.

Add a narrow typed source read: found with validated event, absent-local, or unavailable with internal reason. Keep the old null-returning convenience accessor compatible. An index error, indexed unreadable file or invalid stored event is unavailable, never an unstamped readable row. The exact link lookup reuses existing indexes and exact file offsets; it does not scan history, repair source, or create an index/token registry. Context paging below uses an indexed range scan with private permission filtering.

Every response uses Cache-Control:no-store. Success is exactly:

```ts
{ok:true, platform:'app', ref:string, messageId:string, url:string, servedBy:string,
 authority:{kind:'native-store',scope:'held-source'},
 position:{at:string,eventId:string}, localOnly?:true}
```

`at` is the actual stored string. Its maximum 64 characters is inherited directly from validateAppEvent's `str(r.at,64)`, not a new eligibility rule. `eventId` is the actual stored event ID, distinct from messageId. Build the URL through existing console-origin/messageLinks helpers using the versioned entry `/dashboard/console/message-link-v1/` and append `e=<encoded actual eventId>` to the dashboard hash. New links always use this separate typed event query, never an ambiguous canonical-message-ID `m`. The web parser accepts exactly one e or one legacy m, rejects mixed/repeated target fields and sends targetKind=event for e, legacy for m. This preserves unambiguous existing m links and guarantees that copying by event ID still opens the same event when another message has that token as its public message ID. Serve this distinct entry with revalidated HTML and versioned compatible assets. It must require a valid typed route before chat initialization. An older server must return unavailable or 404 at that path without falling through to the ordinary dashboard shell. Verify against a baseline server and a previously cached ordinary dashboard in real Chrome. Verify no latest-history request or read marker in either unsupported case. Establish this compatibility before enabling generation. It contains no PIN, token, message body, signature, source proof or access grant. The existing localOnly origin limitation stays explicit.

## Direct Target History

Opening an already-held link must not depend on generating another shareable URL. Extend the existing `GET /mobile/chat/app/:key/messages` with scalar `target=<message-or-event-id>` and optional targetKind using the same closed kind grammar. Reuse the same exact lookup and current ACL. Target mode is mutually exclusive with legacy before/after/scope and the paired context continuation mode described below: contradictory modes return400 bad-message-target. New modes apply the same explicit agent reader and original signed-reader continuity policy as Exact Link GET; legacy history policy is unchanged. Ordinary history requests remain unchanged.

Seek inclusively using the existing `(at,eventId)` index and actual raw tuple: `(at < target.at) OR (at = target.at AND eventId <= target.eventId)`. Return ordinary oldest-first history and normal per-row projection; use the structured context continuation defined below. The default page is 50. Reuse the existing browseMessages clamp of a requested page size to 1 through 100; a request for 101 returns the bounded page and continuation, not an error or an ineligible target. With stable reader permissions, all older authorized rows remain reachable through exclusive context pages using `nextContextBefore` and the paired `beforeAt` and `beforeEventId` request fields below. This changes no existing page-size policy and imposes no lifetime history limit. Basis: protocol-agreed pagination, with the existing approved mobile-native-conversations.md §4.5 browse contract and browseMessages query as evidence; this increment does not introduce a new eligibility floor. A regression case requests 101 and proves target inclusion plus a working continuation rather than refusal. The authorized target must actually survive projection into the returned page. Never reconstruct an ordering timestamp from milliseconds or invent a string successor.

Add literal `anchorApplied:{requestedTarget:string,messageId:string,eventId:string}` only on successful target history. The client verifies it and the actual target bubble. A200 from an older server that ignored target and omitted/mismatched this evidence is unsupported; it cannot paint a false navigation success. No opaque anchor codec is needed.

Context continuation is explicitly structured, since raw timestamps/event IDs may contain commas and the old before delimiter cannot represent them safely. Return `nextBefore:null` plus `nextContextBefore:null|{at:string,eventId:string}` for new context responses. That pair names the oldest returned authorized row, not a hidden physical row. The next request uses both beforeAt and beforeEventId, each URL-encoded independently, and optional limit/agent reader. Reject a partial pair, target/targetKind mixed with a pair, legacy before/after/scope mixed with either new mode, unknown fields and multiple values. Validate raw at<=64 and eventId<=128 against the exact actual current readable boundary event in this conversation, then seek exclusively by the structured tuple. Return literal `contextApplied:{at:string,eventId:string}` matching the request. A client requires that evidence before applying continuation; an old server ignoring these fields cannot silently send it back to latest.

Use a shared per-actual-store inFlight counter and server-owned `mobilePairing.native.contextHistoryMaxConcurrentScans` policy, initially 2. This is a reversible judgment-required resource policy, not a hardware fact, permission floor or eligibility rule. Existing per-device rate limits do not bound bearer/all-device concurrency; session/spawn WorkAdmission is not an HTTP scan lease and is not reused. Every signed/agent context scan shares the same limit, with no pending queue. Competing scans receive retryable429 context-busy. Point link reads, ordinary legacy reads and all sends are exempt. A valid policy is a positive safe integer; invalid configuration records degradation and uses the initial default rather than silently disabling reads. Lowering the configured budget never cancels admitted scans. Release only when the actual scan exits/finally completes, including abort/error, never merely when cancellation is requested. Before merge, measure 1/2/4-scan peak memory/event-loop delay and concurrent point-read/send latency through the normal bounded verification allocation; explicitly retain or adjust the initial policy from that evidence. No new LLM per read, queue, persistence or background timer is introduced. The server reads indexed physical chunks into bounded request-local memory, validates actual stored events and filters by current message ACL until it has n+1 authorized rows or the retained source ends. Hidden-only chunks advance only the private internal boundary. No hidden ID, count or physical offset enters the public cursor. Return at most n authorized rows; an additional authorized row establishes a nextContextBefore. A read failure/interruption before establishing the requested boundary/page is masked recoverable unavailable, never false EOF or latest fallback. Yield between chunks, honor request cancellation and recheck the original reader/grants, the target or continuation boundary, every output row and the extra row used to establish continuation after asynchronous work. If any recheck fails, return masked recoverable unavailable without a page or cursor. Perform final validation and serialize the response without another asynchronous yield. Test revocation of only the extra row after it is collected and before final validation. This is a structured query/projection helper on the existing index, not a new index, token registry or repair system. Ordinary legacy before/pool requests and their response shape remain unchanged.

## Failure And Privacy Outcomes

Malformed/multiple/unknown fields return400 bad-message-link-request, or400 bad-message-target on history. Missing explicit owner representation returns403 reader-required. Loss of original device/key/person standing returns403 reader-no-longer-authorized, without locator bytes. Unknown and forbidden conversations share404 unknown-conversation and no source detail.

Within an authorized conversation, hidden, absent-local, indexed-unreadable, ambiguous and unresolved targets share409 `{error:'message-not-available-here',retryable:true,scope:'held-source'}`. It says this serving copy cannot provide the target now, not global deletion. Internal closed reasons feed existing degradation/evidence channels; the response reveals no storage path, hidden ID, ACL reason or parse exception. Missing feature/dependency or URL origin returns503 message-link-unavailable. URL construction failure affects Copy Link only; direct target history can still work. Apply current authorization before any private failure detail and again before returning after asynchronous work.

## Frontloaded Decisions

1. Existing current reader and actual message visibility are the only authority (invariant: permission scope).
2. A stateless positive held-event projection reuses actual App replication; local uncertainty is recoverable, not global absence (invariant: state evidence and continuity).
3. Both existing message/event target domains work; ambiguity refuses (compatibility choice).
4. Direct inclusive target history is independent of Copy Link origin and requires literal applied-target evidence (ordering/compatibility choice).
5. Separate contiguous context preserves drafts and suppresses cumulative markers until fresh latest (interaction choice).
6. Every operator Send proceeds independently of history; synchronous composer admission preserves one request identity and the existing exact Stop priority remains unchanged (delivery/idempotency invariant).
7. The actual selected Copy Link action confirms clipboard success (operator action/evidence choice).
8. Typed generated links, fresh-gesture clipboard recovery, request-identity outcome bookkeeping and structured privacy-safe context continuation are frontloaded compatibility/interaction choices.
9. Provider exact links retain their physical-namespace/offline-carrier findings on the open card; no legacy provenance is invented here (tracked scope sequencing).

Retain the content-free diagnostic snapshot before page disposal as the first accepted release baseline, naming server/web version, evidence owner, scenario/sample counts and unknowns. The server/web owner and native app owner compare the same scenarios in subsequent normal candidate/release checks and the existing project parity recheck; unavailable real-client evidence is unknown, not pass. This uses existing retained verification artifacts, not a new collector or scheduled job.

simplestRobustRoute: One indexed App target reader, one exact link GET, an additive structured history mode, the existing message-options sheet/renderer/send machinery and a small shared scan policy. Rejected larger routes include provider provenance carriers, new databases/queues, all-member per-GET quorums, a standalone locator service and a runtime telemetry collector.

No cheap-to-change-after tags. Lessons engaged: real three-tier wiring and live proof; actual state rather than symbols; existing durable App replication; structured schema bounds rather than judgment about people; preserve Stop and old URL benefit; a standalone user explanation. Resource defaults control page presentation, never eligibility. No new persistence, queue, timer or authority system.

## Native client integration

Advertise `messageActions.copyLink: true` as an optional field on each readable App conversation row in the existing signed `GET /mobile/conversations` response. Emit it only when this increment's default-off `mobilePairing.native.messageLinks.enabled` setting is on and the serving route has the native store and a shareable configured HTTPS origin. Omit the field for other providers, unavailable dependencies and older servers. Treat absence and any value other than literal true as unavailable. The capability describes route availability while each GET independently enforces current reader and target permissions. The client discards the advertisement when the pairing or conversation changes, and replaces it on the next successful list refresh. Test older and updated server lists, flag off/on and pairing change. Offer Copy Message Link only when the current pairing advertises the action on the current conversation and the selected row has settled server message and event IDs. Opening a menu does not make an API call. At the click, capture pairing, conversation and both settled IDs. Use the same typed event request and response checks as the web action. Write the pasteboard only after a valid answer attributable to that capture and while the window still represents the same signed context. Preserve draft text, attached files, scroll position and focus. A refused request leaves the pasteboard unchanged.

Give the client stable error classes for session or conversation authorization failure, a target unavailable to the current reader, and transport or replica uncertainty. Hidden and missing targets within an otherwise readable conversation share the same target-unavailable outcome. The server cannot reveal the presence of a hidden message to distinguish it from a removed one. Use an ordinary authenticated HTTPS locator and exact bounded anchor for a recent or off-page target. A miss cannot select a nearby row. Prepare fixtures for recent, off-page, denied and removed targets and current paired scope before client integration.

Native Copy Message Link accepts only the authenticated paired agent's shareable HTTPS console origin and the canonical path `/dashboard/console/message-link-v1/#/work/chats?c=<encoded app:uuid>&e=<encoded eventId>`. A localhost-only result is unavailable for native copy. The signed request remains bound to the captured pairing. The response's serving machine is provenance and cannot select a new agent or authorize a host. The anchor response is the exact `{requestedTarget,messageId,eventId}` tuple plus the matching visible row in a single local retained history page. No merged or partial page can substitute for that row. After a holder move, retain the conversation and event IDs and require the same exact authorized row on the current paired route. Unresolved routing or replication is unavailable.


## Native Contract Review Disposition

The fourth review of this draft (Codex Astra) identified three design issues and one pagination inconsistency. The draft now requires typed event lookup at copy time, final authorization of the continuation look-ahead row, and an additive per-conversation capability on the signed list. It also consistently specifies paired context pagination. These corrections await confirmation. The draft remains unapproved.

The fifth review confirmed the previous corrections and identified three remaining gaps. This revision specifies continuation recovery, flag-off behavior for direct callers and existing links, and a versioned dashboard entry that cannot silently open the latest chat on an incompatible client. The versioned path supersedes the earlier native handoff path and requires a baseline compatibility test. These changes await confirmation.
