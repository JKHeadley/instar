# A last awake machine can leave the mesh, and a server with no machine identity boots

Feedback item: `feedback-d2bf749f-6792-4477-846f-f2d023888597`
Cluster: `cluster-single-machine-mesh-cannot-leave-instar-leave-refuses-awake`
Severity: critical (a production outage of about 12 minutes, plus no supported way out)

## 1. Problem

An agent that was once paired into a multi-machine mesh, and now runs on a single machine, has
no supported way out of the mesh:

1. **`instar leave` refuses.** `leaveMesh()` (`src/commands/machine.ts:757`) exits with status 1
   whenever the local registry entry has `role === 'awake'`, and tells the operator to "hand off to
   another machine first: instar wakeup". When every other registry entry is dead or stale, no
   machine can take the handoff. The command that should cover this case refuses it.
2. **Leaving by hand crashes boot.** Removing `.instar/machine/identity.json` should land on the
   path that `MultiMachineCoordinator.start()` (`src/core/MultiMachineCoordinator.ts:410-415`)
   already handles: `_enabled = false`, `_role = 'awake'`. `server.ts` describes this as "the
   designed single-machine degradation" (`src/commands/server.ts:15869`). The reporter says the
   server instead crash-loops (`TypeError: Cannot read properties of undefined (reading 'resolve')`
   followed by a `libc++abi … mutex lock failed` abort). It came back only after `identity.json`
   was restored.
3. **The only working lever is too broad.** Today the one way to stop the lease commits
   (`chore(mesh): lease epoch N → m_…` / `lease renew epoch N`, from `GitLeaseStore`) is to set
   `gitBackup.enabled: false`. That works because `server.ts` picks `GitLeaseStore` only when a
   `GitSyncManager` exists (`src/commands/server.ts:5835-5945`). Turning it off also stops all
   git backup. On the reporter's agent these lease commits were 399 of 429 commits per day
   (about 93%), all coordinating a pool of one.

## 2. Evidence

There is one report (n=1, received 2026-08-26). The evidence bundle has no truncation marker, but
triage marked the evidence incomplete: the full stack trace for the boot crash is missing. The log
excerpt has the `TypeError` message and the native abort, but no frames.

- Environment: macOS (Darwin 25.6.0), Node 22. The registry has 3 machines; 2 have been dead
  since 2026-06-08 and 2026-06-27. One is `awake`. `gitBackup.enabled: true`.
- Path 1 matches the code exactly: the `entry?.role === 'awake'` guard in `leaveMesh()` does not
  check whether any other active, non-revoked machine exists.
- Path 2: after `mv .instar/machine/identity.json /tmp/` (the signing and encryption keys stay in
  place), the supervisor logged 25 spawns in a row that failed before binding. Restoring the file
  fixed boot at once.
- Cadence: the reporter names `HEARTBEAT_WRITE_INTERVAL_MS = 2 * 60_000`
  (`MultiMachineCoordinator.ts:106`) as hardcoded with no config knob. The commits they quote are
  `GitLeaseStore` lease writes (`GitLeaseStore.ts:86-87,121`). Their rate comes from the lease
  renew cadence (`seamlessness.leaseTtlMs`-derived), not only from the heartbeat constant. The
  implementer should confirm which timer drives the 120 s commits.

### Not yet established (implementation must pin these down first)

- **Which dereference crashes.** A code read finds several places where identity-less boot is not
  safe on its face. None has been proven to be the `'resolve'` crash:
  - `MultiMachineCoordinator.start()` returns early, so the private `heartbeatManager` (and
    anything else built after line 415) stays `undefined`. `coordinator.managers` still exposes it
    as if it were always present (`MultiMachineCoordinator.ts:394-400`).
  - Some `server.ts` consumers guard on `coordinator.enabled && coordinator.identity`; others call
    `coordinator.managers.identityManager.*` directly or depend on `selfMachineId`. Each consumer
    has to be audited.
  - The leftover signing and encryption keys, plus a registry that still lists this machine, put
    the install in a half-state. Code that keys off "keys exist" or "registry has machines" instead
    of `hasIdentity()` may still take the mesh path.
- The native `mutex lock failed` abort is probably a consequence: the process is torn down while a
  native addon (for example the SQLite or keychain binding) holds a lock. It is likely not a
  separate bug, but this should be confirmed.

## 3. Proposed fix

Three parts. Each can ship on its own, but parts A and B should land together, because part A
produces exactly the state that part B makes bootable.

### A. `instar leave` lets the last machine leave

In `leaveMesh()`:

1. Compute `otherActive`: registry machines other than self with `status === 'active'`, no
   `revokedAt`, and (where available) a heartbeat newer than the failover timeout.
2. If self is `awake` **and** `otherActive` is non-empty, keep today's refusal and handoff
   instructions unchanged.
3. If self is `awake` and `otherActive` is empty, go ahead on the last-machine path:
   - Require confirmation (`--yes`, or an interactive prompt). The prompt says that this
     machine is the last one, that it will keep running as a single machine, and that git backup
     settings will not change.
   - Refuse while the local server is running (check `/health` the same way
     `resolveAwakeMachine` does). Tell the operator to stop it first, so the running coordinator
     never sees its identity disappear. A follow-up could do the switch live; it is out of scope.
   - Revoke self in the registry, as today. Destroy the escrowed recovery key, as today.
   - **Back up first, then delete.** Before calling `removeLocalIdentity()`, copy
     `identity.json`, the local key material and `registry.json` to
     `.instar/machine/left-<ISO timestamp>/` (mode 0700). This makes the exit reversible by hand.
     Deleting keys stays the default for the multi-machine path. On the last-machine path the
     backup is what makes "safe" true.
   - Print what happened and the exact restore steps.
4. Stale peers stay in the registry, marked as they are. `leave` does not revoke other machines.
   `instar machine remove` is still the tool for that.

### B. Booting with no machine identity really works

1. Add a boot-level regression test before changing anything. Set up a temp project the way the
   reporter's was: `gitBackup.enabled: true`, a git repo, a registry with this machine plus stale
   peers, signing and encryption keys present, and `identity.json` **absent**. The test drives
   server startup (the existing e2e production-boot harness under `tests/e2e/` is the closest
   pattern) and asserts that it reaches bind. It must fail first and show the real stack. That
   stack settles the open question in §2.
2. Make the coordinator's no-identity state complete. `managers` should return typed nullable
   fields, or a no-op `HeartbeatManager` stub, so callers cannot get `undefined` silently. Fix
   every `server.ts` consumer the type change exposes by gating on `coordinator.enabled`.
3. When `coordinator.enabled === false`, skip lease construction completely. Use neither
   `GitLeaseStore` nor `LocalLeaseStore`. Single-machine means always awake, as `start()`
   already says.
4. Leftover keys or registry entries without `identity.json` must not take the process down.
   Log one line saying mesh is off because there is no machine identity.

### C. Mesh enablement is separate from git backup

1. Add `multiMachine.mesh.enabled` (default: on when an identity exists). The existing
   `multiMachine.enabled` field is described in code as "near-dead", and real multi-machine agents
   never set it, so reusing it is risky. When the new flag is `false`, the coordinator starts in the
   no-identity single-machine mode from part B even if an identity exists. No lease store, lease
   commits or heartbeat writes are created. Git backup keeps running under `gitBackup.*` alone.
2. Optional, and lower priority: expose the heartbeat and lease-renew cadence as config, with a
   safe lower bound. It is not needed to fix this item, because part C.1 removes the commits
   completely for single-machine agents.
3. A small follow-up could be considered: when the registry has no other active machine, the
   lease could use `LocalLeaseStore` even with git backup on, since there is no peer to share the
   lease with. This changes failover semantics if a peer later comes back, so it needs its own
   review and is not part of this fix.

## 4. Tests (planned)

- `tests/unit/machine-identity.test.ts` or a new `tests/unit/leave-mesh-last-machine.test.ts`:
  - awake + another active peer → still refuses (current behavior is kept).
  - awake + only stale or revoked peers + `--yes` → revokes self, writes the `left-*` backup, and
    removes the identity.
  - awake + no peers + no confirmation → refuses with a clear message and changes nothing.
  - local server running → refuses.
- A boot test (e2e harness): no `identity.json`, keys and registry present, `gitBackup.enabled:
  true` → the server binds, `coordinator.enabled === false`, and no lease store is built.
- Config test: `multiMachine.mesh.enabled: false` with an identity present → no `GitLeaseStore`,
  and git backup is still wired.

## 5. Rollout and risk

- Part A only adds a path for a case that today has no exit. The multi-machine refusal is
  unchanged.
- Part B is a crash fix. The risk is that some consumer relied on the `undefined` manager failing
  loudly. The audit in B.2 has to be thorough.
- Part C ships off by default (the flag is absent, so today's behavior holds). Single-machine
  operators opt in.
- Not in scope: rejoining after a last-machine leave (normal pairing covers it), and live
  mesh-off without a restart.
