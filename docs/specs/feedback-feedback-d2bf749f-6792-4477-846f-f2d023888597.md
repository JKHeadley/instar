# The last machine can leave the mesh, and a server with no machine identity boots

## Problem statement

A mesh that has shrunk to one awake machine has no supported way to stop being a mesh, and the
only unsupported way (deleting `identity.json`) takes the server down at boot. Three coupled
defects, one reporter, one production outage of about twelve minutes.

1. **`instar leave` refuses the last machine.** `leaveMesh()` in
   `src/commands/machine.ts:777` exits with "Hand off to another machine first: instar wakeup"
   whenever the local registry entry has `role === 'awake'`. It never asks whether another machine
   exists to hand off to. For a registry with one awake machine and only dead peers the sanctioned
   exit is unreachable.

2. **A boot with no machine identity is documented as the designed degradation but is not
   survivable.** `MultiMachineCoordinator.start()` (`src/core/MultiMachineCoordinator.ts:412`)
   handles the no-identity case by disabling the coordinator and returning `awake`, and
   `src/commands/server.ts:15795` describes this as "the designed single-machine degradation".
   The reporter's server crash-looped twenty-five times with
   `TypeError: Cannot read properties of undefined (reading 'resolve')` followed by a native
   abort, and booted cleanly the moment `identity.json` was restored. The decision "this boot has
   no mesh identity" is made once by the coordinator, but at least four later boot stages re-derive
   it by calling `hasIdentity()` themselves, and one of them *creates* an identity mid-boot
   (see §Analysis). The degraded path is therefore never actually exercised as a whole.

3. **Stopping the mesh's git traffic requires disabling git backup.** The lease store is
   `GitLeaseStore` whenever a `GitSyncManager` exists and the registry is tracked
   (`src/commands/server.ts:5809-5846`). `GitSyncManager` is constructed only when
   `gitBackup.enabled !== false` (`:5744`). So a single-machine deployment that wants its backups
   but not a `chore(mesh): lease epoch …` commit every two minutes has no knob: 93% of the
   reporter's daily commits coordinate a pool of one.

## Analysis

### Why the leave guard is wrong for the last machine

The guard protects against orphaning an agent: an awake machine must not vanish while a standby
expects to be promoted by handoff. That invariant only has content when another active machine
exists. The guard checks role, not peers, so it also blocks the one case where leaving is the
only correct action: decommissioning the mesh itself.

### Why the identity-less boot crashes (two confirmed defects, one unlocated throw)

The boot sequence in `src/commands/server.ts`, with `identity.json` absent and keys present:

1. `:4817` — `coordinator.start()` sees no identity, sets `_enabled = false`, role `awake`.
2. `:5612-5629` — `localSigningKeyPem` stays `''` (gated on `coordinator.identity`).
3. `:5726` — the entire mesh-init block is skipped: `gitSync`, `leaseTransport`,
   `peerEndpointRecorder`, `getSelfMeshEndpoints`, `meshResolver`, `registrySyncDebouncer`,
   `leaseCoordinatorRef` all stay `undefined`. This is correct for a single machine.
4. `:6705` — `bootTelegramOrigin()` runs whenever a Telegram channel is enabled. At
   `TelegramOriginBoot.ts:68` it calls `generateIdentity({ name: 'Local machine' })` because
   `hasIdentity()` is false. A **new** machine id is minted, written to `identity.json`, and
   self-registered as a **second awake** machine in the registry. The coordinator still believes
   there is no identity.
5. `:23534` — `meshSelfId` is re-derived from `hasIdentity()`, which is now true. The identity
   reannounce, recovery bearer, observed-endpoint and session-router wiring all start for a
   machine the coordinator never initialised, with `meshResolver` undefined and an empty signing
   key.

Defects confirmed by reading: (a) the degraded boot is not one decision but several independent
re-reads of `hasIdentity()`, and (b) one of those re-reads has a side effect that silently
converts "no identity" into "fresh awake identity" and pollutes the registry. Whether the
reporter's `TypeError` fires in step 5 or somewhere else cannot be settled from the single
truncated stack line; every call site named `resolve` that is reachable in this state was
inspected (`resolveMeshPeerUrl` guards an undefined resolver at `src/core/resolveMeshPeerUrl.ts:28`;
`HttpLeaseTransport.ts:272` asserts non-null but is only constructed inside the skipped block).
The reproduction test in §Acceptance pins the site; the fix in §D2 removes the whole class
regardless of where the first dereference happens.

Note on the reporter's "restore identity.json fixed it": if step 4 ran to completion the
`mv` back would have overwritten the minted identity, which is consistent with the clean boot.
The test must assert that no identity is created, not merely that the server listens.

### Why the lease commits are coupled to backup

`selectLeaseMedium()` answers "can git carry `registry.json`?", not "is there anyone to
coordinate with?". For a mesh of one, a durable shared CAS is pointless: there is no second writer.
The boot code already knows the peer count (`:5772-5776`) and already has a local store
(`LocalLeaseStore`) wired for the no-git case. The missing piece is using that knowledge.

Related observation, out of scope but worth a follow-up: the reporter sees the *acquisition*
message (`lease epoch N → holder`) every 120 s, not the renewal message. With
`leaseTtlMs` defaulting to 90 000 ms (`src/config/ConfigDefaults.ts:929`) and the check tick at
120 000 ms, a solo holder's lease expires between ticks and is re-acquired with an epoch bump
each time. That is why the epoch climbs and why each tick is a commit.

## Proposed design

### D1. `instar leave` permits the last machine to exit

In `leaveMesh()` (`src/commands/machine.ts:757`):

1. Compute the peer set from the registry: entries other than self with
   `isRegistryEntryActive(entry)`. Split into **live peers** (`lastSeen` within
   `LEAVE_PEER_LIVE_WINDOW_MS`, proposed 24 h) and **stale peers** (active in the registry but not
   seen inside the window).
2. If self is `awake` and at least one live peer exists → today's refusal, unchanged wording.
3. If self is `awake` and there are no live peers → **last-machine exit**:
   - Print what is about to happen: the agent becomes a single-machine install, stale peers are
     listed by nickname and last-seen date, local keys are deleted, re-pairing is required to
     rebuild a mesh, and git backup is unaffected.
   - Require confirmation: `--yes` on the command line, otherwise an interactive y/N prompt
     (refuse when stdin is not a TTY and `--yes` is absent). Leaving the last machine is
     irreversible for the keys.
   - Clear `registry.lease` (holder, expiry, nonce; the epoch is kept so a later rejoin cannot
     reuse a lower epoch), then run the existing sequence: `revokeMachine(self)`, destroy the
     escrowed recovery key, `removeLocalIdentity()`.
   - Stale peers are **not** revoked automatically; the listing is informational. Revoking a dead
     machine is `instar machines remove` and stays a separate decision.
   - If the server is running, print the instruction to restart it. A running server that loses
     its identity file keeps timers alive that call `loadIdentity()`; the clean state is reached on
     the next boot (D2). Optionally, when the local server answers on `config.port`, POST the
     existing internal restart route; this is a nicety, not a requirement.
4. If self is `standby` → unchanged.

The 24 h window is a constant, not config: it only distinguishes "someone may still be about to
take over" from "nobody has been here for a day". A peer that was seen within the window is a
live peer even if its heartbeat is late, so the guard errs toward refusing.

### D2. One boot-time decision for "this machine has no mesh identity"

Principle: `coordinator.start()` is the single authority. Every later stage must read
`coordinator.identity` (or `coordinator.enabled`), never call `hasIdentity()` afresh, and nothing
after `start()` may create an identity.

Changes:

1. **`TelegramOriginBoot` stops minting identities.** It takes an optional
   `machineIdentity: MachineIdentity | null` from the caller (`coordinator.identity ?? null`).
   - When an identity is passed, behaviour is unchanged.
   - When `null` and the registry has **no** machines at all, this is a genuine fresh install that
     reached the server before `instar init` wrote an identity; keep today's mint but log it as
     a one-line `[telegram-origin] minted first machine identity` so it is visible.
   - When `null` and the registry **already lists machines** (the post-exit case), do not mint.
     Run the origin service with a local-only principal: `machineId` is the agent's project name
     prefixed `local:`, `publicMachineName` is the host name, and origin key resolution uses the
     agent-local key path that `resolveIdentityOriginKey` already falls back to when no per-machine
     epoch exists. The exact fallback for origin key material is Open Question 1.
2. **Late mesh wiring reads the coordinator.** At `src/commands/server.ts:23534` and the other
   re-derivations (`:8268`, `:8538`, `:22973`, `:29360`, `:29558`), replace
   `identityManager.hasIdentity() ? loadIdentity().machineId : null` with a boot constant
   `const meshIdentity = coordinator.identity ?? null` captured right after `start()`. The block
   at `:23536` then stays dark on an identity-less boot, as the skipped mesh-init block requires.
3. **`meshResolver` loses its definite-assignment assertion.** Declare it
   `PeerEndpointResolver | undefined`; the compiler then forces every consumer outside the
   mesh-init block through `resolveMeshPeerUrl`'s existing undefined guard or an explicit check.
   This also surfaces any dereference the reproduction test does not reach.
4. **Boot log line.** When the coordinator is disabled, print
   `Multi-machine: disabled (no machine identity; registry lists N machine(s))` so an operator
   who deleted the identity sees the degraded mode named rather than inferring it from silence.

### D3. A mesh of one keeps backups and drops lease commits

1. New config knob, flat under `multiMachine`, read once at boot:

   ```ts
   /** Lease medium policy. 'auto' (default): local store when no other active machine is
    *  registered, git store otherwise. 'git' restores today's behaviour unconditionally.
    *  'local' never commits the lease (operator accepts no durable cross-machine CAS). */
   leaseMedium?: 'auto' | 'git' | 'local';
   ```

2. In the boot wiring (`src/commands/server.ts:5766-5776`), after `peerCount` is computed:
   `auto` with `peerCount === 0` → `leaseMedium = { medium: 'local', reason: 'solo-mesh' }`.
   `GitSyncManager` is still constructed and `gitSync.sync()` still runs, so backup and registry
   pull are untouched; only the lease store and the `RegistrySyncDebouncer` (already gated on
   `medium !== 'local'` at `:5788`) go local. The existing boot line
   `Lease store: LocalLeaseStore (…)` gains the reason `solo mesh — no other active machine`.
3. **Peer arrival while solo.** The medium is a boot constant today. When the coordinator's lease
   tick observes the active peer count go from 0 to ≥1 under `auto` + local medium, raise one
   Attention item: "A machine joined; restart to move the lease onto the shared git medium." The
   joining flow already ends with the operator at a terminal, and a two-machine mesh with one side
   on a local store is only a window until that restart. Automatic medium switching is deferred
   (Open Question 2).
4. **Cadence knob.** `multiMachine.heartbeatWriteIntervalMs` (range-validated 30 000 – 600 000,
   default 120 000) replaces the hard-coded `HEARTBEAT_WRITE_INTERVAL_MS`. The check interval
   stays constant; only the write cadence is operator-tunable. This addresses the reporter's
   request (c) without touching lease semantics.

### Non-goals

- Fixing the solo-holder re-acquire-every-tick behaviour (TTL 90 s vs tick 120 s). Documented
  above as a follow-up; D3 removes its commit cost for a mesh of one.
- Automatically revoking stale peers during leave.
- Changing pairing, wakeup or failover semantics for meshes with two or more live machines.

## Acceptance criteria and tests

Failing-then-passing test (the one named in the result file):

- `tests/e2e/identityless-boot-single-machine.test.ts` —
  `boots with no identity.json, mints nothing, and reports multi-machine disabled`.
  Fixture: a state dir whose `machines/registry.json` lists three machines (self awake,
  two stale `active` peers with `lastSeen` months old), `registry.lease` naming self,
  `signing-key.pem` and `encryption-key.pem` present, no `identity.json`, a Telegram channel
  enabled with a dummy token, `gitBackup.enabled: true` in a throwaway git repo. Boot the server
  in-process using the harness from `tests/e2e/machine-identity-activation-boot-order.test.ts`.
  Assert: the server reaches listening; `identity.json` still does not exist; the registry still
  has exactly three machines; `/health` reports `multiMachine.enabled === false`; no
  `uncaughtException` was recorded. Today this test fails at the "no identity.json" assertion
  (step 4 above) and, per the reporter, at listening.

Supporting tests:

- `tests/unit/leave-last-machine.test.ts` — `leaveMesh()` against a temp registry (pattern from
  `tests/unit/wakeup-targets-awake-machine.test.ts`): refuses with a live peer; proceeds for the
  last machine with `--yes`; clears `registry.lease` and revokes self; refuses without `--yes` when
  stdin is not a TTY; never revokes stale peers.
- `tests/unit/telegram-origin-boot-no-mint.test.ts` — with a populated registry and no identity,
  `bootTelegramOrigin` does not call `generateIdentity`; with an empty registry it does, once.
- `tests/unit/lease-medium-solo.test.ts` — extend `tests/unit/lease-medium-wiring.test.ts`:
  `auto` + `peerCount === 0` selects `local` with reason `solo-mesh`; `git` ignores peer count;
  `GitSyncManager` construction is still present on the solo path.
- `tests/unit/multi-machine-coordinator.test.ts` — `heartbeatWriteIntervalMs` is read, range
  clamped, and defaults to 120 000.

Operator-visible acceptance:

- On the reporter's registry, `instar leave --yes` succeeds, prints the two stale peers, deletes
  local keys, and the next server boot logs `Multi-machine: disabled (…)`.
- With `gitBackup.enabled: true` and `leaseMedium` unset, a solo machine produces no
  `chore(mesh): lease …` commits; `instar backup`/scheduled backup commits continue.

## Rollout

- D1 and D2 are bug fixes with no fleet gate: D1 only changes behaviour on a code path that
  currently exits 1, D2 only changes boots that currently crash or silently mint.
- D3's `auto` default changes the lease medium for every solo machine on the fleet. Ship with
  `leaseMedium: 'git'` as the explicit rollback and the boot log naming the chosen medium. The
  Attention item in D3.3 is the safety net for the first peer join after rollout.

## Open questions for review

1. **Origin key fallback without a machine identity.** `resolveIdentityOriginKey` is keyed by
   machine id and epoch. Confirm that an agent-local principal id is acceptable for a
   single-machine install, or whether the origin service should simply be disabled when the
   coordinator is disabled and the registry is non-empty.
2. **Automatic medium switch on peer arrival** versus the Attention-plus-restart proposed in
   D3.3. Switching stores at runtime touches `LeaseCoordinator` construction; the restart path is
   smaller and matches how `instar join` already ends.
3. **Should last-machine exit also reset `registry.lease.epoch`?** This draft keeps the epoch
   for monotonicity. If a rejoined mesh is expected to start from epoch 0, the clear must be total.
4. **The exact `TypeError` site.** The reproduction test will name it. If it is outside step 5,
   D2.3's type change should still surface it at compile time; review should confirm no further
   `!`-asserted mesh locals exist beyond `meshResolver`.
