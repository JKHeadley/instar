## Problem statement

Justin requested a new standard in topic 69507 on September 5, 2026: every message sent by an Instar agent into Telegram must record the sending session's machine, harness, and model. Visible display starts enabled, but users may disable display without disabling recording. This conversation repeatedly had to verify which machine and model were answering after a profile change.

The earlier Agent-Signature Provenance (ASP) feature distinguishes agent authorship from the operator's authorship when both use the operator's account. It does not automatically capture this runtime tuple. Its signer has no production caller in the inspected source; its formatting boundary also has a documented unresolved automatic-signing limitation. Preserve that security requirement without claiming it is already universally enforced.

This is an approved operational standard and implementation contract, not a deployment claim. Initial inspection used agent-home 1.3.1203. ## Proposed registry article

### Telegram Message Origin Is Mandatory; Its Display Is Optional

**Rule.** Every Telegram message or revision sent by an Instar-managed agent has an infrastructure-produced, durable origin record bound to that operation and its platform message identity. For session messages this records at least machine name, actual harness, and model, with stable agent/machine/session identifiers and the evidence for each value. Display of those three fields is ON by default. Authorized users may hide the display or individual displayed fields. Presentation settings never disable, erase, weaken, or rewrite recorded origin.

**In practice.** Capture origin from the submitting runtime, not message prose or the destination topic's pin. Freeze it before delivery; relays and retries preserve it and record the delivery machine separately. Apply the requirement to bot and managed browser sends, automation, edits, attachments and forwarding. Automation records its actual producer; absent session/model fields are not-applicable. Unavailable observations are unknown with a reason, not fabricated identities. Unknown is an attribution gap, never evidence of a verified model.

**Enforcement.** A mandatory preparation envelope, durable intent/outcome recording, and transport boundaries that require the prepared envelope. Inventory every supported sender, and verify the boundaries with behavioral bypass controls in unit, integration and production-initialization lifecycle tests. A footer helper, a post-send-only log or a prompt instruction does not establish compliance. All enabled transports must meet the contract before claiming complete rollout.

**Earned from.** Justin's topic 69507 machine/model verification sequence and earlier operator-account authorship requirement.

**Traces to the goal.** A coherent agent can account for which instance spoke. The user can see this without repeatedly asking, while choosing how much metadata appears in the conversation.

**Placement.** An operational child of Interaction / Truthful Provenance. Update both tree-edge declarations and regenerate the hierarchy in the current source tree. The requested core requirements are direct operator authorization; the engineering decisions below are proposals, not separately ratified history.

## Terms

Harness means the engine running a session (for example Codex). Mesh/pool means the machines hosting one agent. Lifeline is the independent recovery process. A plan is one immutable logical operation; each child is one platform message or revision. A companion is an additional visible message linked to another message. Redrive means recovery attempting previously admitted work. Stampede processing is the existing queue behavior that condenses a burst; it must not erase this feature's child obligations. ASP is the existing same-message agent-authorship signature. Evidence sinks retain records; only the credential-owner outbox can authorize execution.

## Proposed design

### Canonical serialization

Use `instar-telegram-origin-v1`, a constrained profile of [RFC 8785 JCS](https://www.rfc-editor.org/rfc/rfc8785): canonical UTF-8 with no whitespace, recursively sorted object keys by UTF-16 code-unit order, preserved array order and exactly the JCS/ECMAScript primitive serialization. Thus solidus and valid non-ASCII remain literal, quote/backslash and controls use the JCS escapes, numbers use its ECMAScript spelling, and duplicate JSON keys and lone surrogates are rejected before interpretation. The additional schema restrictions reject undefined, non-finite numbers, non-safe integers and non-JSON object types. IDs including Telegram 64-bit peer/random IDs are decimal strings, not floating-point numbers. Do not normalize Unicode or reorder Telegram entities: text code points, entity order and UTF-16 offsets are preserved exactly. Optional fields are explicitly omitted by schema construction before canonicalization; null remains distinct. Destination is a versioned object with transport, accountId, chatId, topicId and message/inline/scheduled identity variants, rather than an ambiguous concatenated string. Media references contain immutable content SHA-256, byte length, MIME type and display filename; local secret paths are transport-private. Ordered albums/chunks remain ordered.

The canonical authored-content digest covers that schema's exact body/entities/media/destination and operation kind. For Bot API HTTP, each materialization separately hashes the exact serialized wire-body bytes, canonical method/destination and permitted content type. For the Web broker, the sealed boundary is the canonical RPC method and arguments before provider TL serialization/encryption, not nondeterministic encrypted MTProto frames. Credentials and authorization headers never enter stored digests or records. The Bot API transport sends the sealed bytes unchanged; the Web worker may perform required provider serialization but may not alter sealed arguments, entities, random ID or canonical authored text. Parent-origin and child-wire digest purposes are separate. Golden fixtures supply the exact input, canonical UTF-8 bytes and SHA-256 for astral Unicode/combining characters, entity order, string IDs, captions, albums and edits, suitable for any peer implementation to consume. Altering version or normalization without negotiation is an explicit protocol mismatch.

### Origin record and evidence

The immutable envelope contains schemaVersion, originId, agentId/name, originMachineId/name, sessionId, turnId, producerKind (session/server-automation/imported-legacy), producerId, harnessId/name, modelId, createdAt, operationKind, deliveryId, destination namespace, canonical-content digest, and the resolved display setting/version. Every required field has evidence status observed/configured/unknown/not-applicable, source and observation time. Unknown fields are null with a reason.

Resolve the exact submitting session through an infrastructure-issued session credential bound to agent, session and origin host. The present /telegram/reply route has no authenticated session identity; a caller-provided sessionId or metadata object alone is not sufficient. Introduce this binding at session startup and in shipped reply scripts. Cross-topic sends keep the submitting session, never the destination's mapped session.

Session.model currently means requested model/tier. Resolve active model through the harness's current-turn observations; index/cache by session and turn, invalidate on replacement/model change, and never synchronously scan entire transcripts on sends. An absent current observation may retain a separately labeled configured model, but cannot present a stale observation as current. Harness records establish what the harness reports, not cryptographic proof of the provider's internal execution.

Deterministic server notices use registered producer context and show automation/no session/no model. An LLM-composed notice references the actual call-ledger model; a delivery validator's model is not the author. The submitting parent remains identified when it incorporates helper output; helper provenance can be linked separately.

Append-only attempt records bind originId to attemptId, delivery machine, transport, state/timestamps, exact rendered-payload digest and actual returned platform identifiers. Store each chunk/album member and revision. Use account/chat/topic/message namespaces and explicit inline/ephemeral/scheduled variants; message_id=0 is not a confirmed durable message. Never store credentials, headers, cookies or full transcripts in the origin audit.

Trust boundary: trusted Instar runtime against missing/stale/spoofed request metadata. Do not claim resistance to a hostile process running as the same OS user with access to transport secrets or signing keys. Attribution never grants send permission or operator authority.

### Presentation and ASP

Default example: `Echo · Mac Studio · Codex · gpt-6-astra`, a separate compact line. Use the operator-managed friendly machine label; never derive public text from IPs, tailnet names, usernames, paths or secrets. Stable machine identity and send-time name remain recorded.

Proposed display configuration: enabled, machine, harness and model booleans, all default true. Place these under the existing Telegram configuration and conversation-profile authorities after checking their actual schema. Effective order: conversation override, agent defaults, built-in true. The existing authorized config-edit flow controls changes. No session-body option can silently suppress it. Setting enabled:false or setting all three field switches false hides the whole footer. Agent name is a presentational extra, not another mandatory field.

A conversation override changes a shared message's display for all readers; it is not personal per-viewer Telegram rendering. Settings affect newly prepared operations, not past messages. Origin recording/retrieval has no display-linked off switch. Presentation is captured once and retained through retry.

Reserve room for footer and any ASP tag before splitting. Preserve original content, entities and code-block validity. Each text chunk carries attribution. Captioned media uses its caption; captionless media and uneditable forwards use one linked attribution companion per logical operation/group only when effective display is enabled. Hidden-display sends create no cosmetic companions. Prepare child steps and their identity links together; companions never produce recursive companions. Unsupported rendering must be explicit before dispatch, never a silent omission.

Preserve original authorship for forwarded source content while recording the agent initiating the forward. An edit appends editor evidence and preserves the original author. Existing A2A marker parsing must continue to work.

ASP applies to the operator-account transports covered by the existing authorship requirement; this design does not expand ASP to every bot message. It requires a canonical receiver-visible body, not final HTML request bytes. Complete formatting, splitting and display planning, then sign every permitted normal/fallback variant before handoff using the owning agent's key capability. Prove verification against actual inbound normalization. A relay with no origin key can use stored signed variants; it cannot invent a new variant or mutate signed bytes. An unprepared variant yields signing-unavailable. The display toggle never removes ASP. Do not introduce a general sign-as-any-agent endpoint. ASP v1 authenticates body authorship, not the full hidden runtime tuple or account/chat namespace; the separate origin attestation below binds those fields even when the footer is hidden.

### Durability and failure behavior

Prepare → durably record intent → attempt → record result. Extend the existing pending-delivery authority rather than introducing a competing retry loop. Store protected payload/attachment references where redrive needs them; origin audit stores digests/references rather than redundant message bodies. Attachment lifetime must cover the retry deadline.

Use a transactional durable store, indexed bounded reads and cursor pagination. Both primary server and lifeline can prepare through the same durable contract without depending on the other process being alive. Concurrent writers must use the store's transaction/locking mechanism; an in-memory singleton does not suffice.

Recording fallback order: primary origin store, separately writable local durable spool, then one compatible authenticated peer accepting a durable origin record. The spool uses a distinct file/directory from the primary database and survives database locking or file corruption; by default it shares the host/filesystem and is NOT failure-independent for disk-full, device loss or host I/O stalls. A configured separate spool volume can improve that boundary. The peer is the only host-independent evidence fallback and receives at least 1,250ms of the fixed budget when the 250ms primary and 500ms spool windows are exhausted. All-sink failure still holds; do not market local redundancy as independent hardware resilience. Budget one attempt per sink and 2 seconds total (250ms primary, 500ms spool, remainder peer). These are evidence sinks ONLY; no fallback copy can admit executable work or grant an execution claim. A positive durable receipt allows submission to the ONE transactional outbox on the transport credential owner's machine. That outbox is the sole execution authority, shared by its main server and lifeline. If that outbox cannot durably admit/claim the operation, hold it; a healthy evidence mirror does not license another sender. Peer failover uses the existing credential-owner handover authority and cannot transfer an in-flight uncertain child into executable state. This deliberately avoids inventing a distributed commit/consensus protocol for audit fallback.

Primary origin-writer failure alone uses the bounded evidence fallbacks. Hold as audit-unavailable if no durable evidence sink acknowledges; independently hold if the sole execution outbox cannot admit/claim. Justin explicitly selected this hold policy. The pre-recorded notification contract below provides a bounded alert without recursive preparation. A prepared operation remains evidence if outcome persistence later fails, and remains outcome-unknown.

Do not blindly retry ambiguous external acceptance. A local deliveryId does not solve the Bot API accepted-but-response-lost case. Hold outcome-unknown and reconcile via concrete receipts where possible; use the existing recovery authority and bounded policy for the unresolved case. Clicking send or finding matching prose is not a receipt. Record each child outcome in groups/companions and only repeat steps established not to have been delivered. Partial delivery is not complete delivery.

Restart, session destruction, machine rename, model change and pin transfer do not rewrite prepared origin. Preserve the origin envelope through recovery rather than resolving it from today's topic session. Historical messages without evidence remain legacy-unattributed.

### Operator observability

Expose bounded aggregate pipeline metrics on the existing operator-authenticated health/audit surface, with the same scope and incomplete-peer coverage rules as audit reads. Count logical operations prepared/admitted/held/suppressed/expired/partially-delivered separately from physical children accepted/unknown/known-failed/scheduled and from actual transport attempts. Include capture evidence counts by harness/status and notification reserved/attempted/accepted/unknown/unavailable counts. These are measurements, never new permission or retry authorities. Update durable aggregates transactionally with their source events; retries, repeated reads and idempotent inserts cannot inflate them. Record sample time and coverage. While a shard/store is unavailable, return last-known counts labeled stale or unknown, never fresh zero. Aggregate hot/archive transitions preserve totals without double-counting. Test each transition's counting unit, duplicate writes, archiving and unavailable snapshots; raw audit rows and the activation test matrix do not substitute for this operator metric surface.

## Multi-machine posture

Origin and plan travel through the authenticated mesh relay with verified origin binding and content/destination digest. Relay receipt records name the delivery host independently. Negotiate origin-envelope support before handing a plan to another machine; incompatible peers return explicit protocol errors, never guesses from local state. Both versions must remain inspectable during upgrade.

Unified audit surface: proposed GET /telegram/origins with pool scope, filter/pagination and explicit unavailable-peer coverage; lookup by originId and platform namespace/revision. Physical shards remain queryable across topic movement. Transfer or preserve the retained shard before machine retirement. Conversation display preferences follow the existing replicated profile/config authority; the resolved origin-side preference/version travels with the operation and is not replaced by the relay's unrelated default.

Transport credentials/signing keys remain with their physical credential owner.

This marker applies only to credentials, not isolated preferences or an inaccessible audit. Pool reads enforce the same agent/conversation access checks as local queries and disclose incomplete coverage. Audit retention follows explicit operator policy independently of display; no silent truncation/rotation may claim complete retained history after dropping rows. Archived records stay inspectable.

## Binding and lifecycle contracts

These contracts specify implementation details using the Terms and existing-authority table above. The persistence design is a transactional outbox with a separate retained audit, extending the existing delivery authority.

1. **Session identity:** random opaque preparation credential, stored as a verifier hash, scoped only to one agent/host/session incarnation. Revoke new preparation on session termination/replacement. It cannot edit config, read audit, grant destination authorization or sign as another agent. Prepared delivery capability survives independently. Never log or relay the credential. Test wrong-host, stale-incarnation and cross-API use.
2. **Model observation:** harness adapters emit session-model-observed with sessionIncarnation, harnessId, turnId, modelId, observedAt and sourceEventRef only from actual runtime events. Codex's inspected source is current turn_context.model. Other adapters must name/test their corresponding event; requested Session.model never emits observed. Streaming binds its generating turn; tools/validators do not replace the author. Every supported adapter needs a current-model positive control; an always-unknown resolver fails wiring integrity. Existing health exposes counts by observed/configured/unknown and harness. Unknown remains deliverable with truthful metadata, but reports degraded attribution.
3. **Wire binding:** egress loads the immutable stored child plan. A valid reference cannot be combined with replacement body/destination/edit target/media/format/display settings. Bind the complete serialized request to the child digest immediately before dispatch, without validating one mutable object and sending another.
4. **Origin attestation:** sign a canonical versioned envelope using the registered machine key, covering agent/machine/origin/session incarnation, all runtime fields/evidence, full destination, operation kind, content/plan/variant digests and creation timestamp. Authenticate the peer as that originating identity. Persist originId to envelopeDigest: identical replay is idempotent; changed data under the same ID is rejected. Preserve original attestation through intermediate peers and recheck destination authorization at execution. ASP and this attestation serve distinct roles; changing hidden metadata under unchanged ASP must fail attestation.
5. **Atomic execution:** evidence sinks store inert prepared records. On the credential-owner machine, commit an origin copy, complete plan and executable admission atomically in its one transactional outbox. One logical parent owns unique childIds and outcomes. Extend PendingRelayStore claimCas/renewClaim/fenced transitions to each child; server/lifeline/relay workers use this same outbox. Abandoned in-flight claims become outcome-unknown, not automatically executable. Stale claimants cannot finalize outcomes. Fallback journals never own execution claims or run redelivery. A lost execution-admission/claim acknowledgement is resolved against this same outbox, never by switching sinks.
6. **Queue semantics:** DeliveryFailureSentinel.handleStampede must not summarize away children of a prepared operation. A six-plus-chunk message remains whole. Semantic suppression is distinct from transport idempotency: two sessions with identical prose each receive an origin and an explicit suppressed/delivered outcome. The script's content-only queue dedup cannot erase a second origin.
7. **Immutable recovery bytes:** redact delivered content before preparation. Tone-inspection redaction cannot replace payload bytes. Redrive preserves text/entities/format and signed variants; it must not re-redact or drop format. A later intentional transformation creates an audited revised plan before sending.
8. **Typed results:** distinguish prepared, suppressed, known-failed, accepted with concrete identity, scheduled, partial and outcome-unknown. Existing HTTP 200 suppressedDuplicate is not delivery evidence; existing delivered-ambiguous queue labels must be mapped from their actual reason. Retain pre/post-dispatch phase on timeouts; post-dispatch uncertainty never becomes generic retryable HTTP 0. Migrate script guidance that suggests resending merely because matching prose was not found.
9. **Supervision:** receipt classification and executable transitions remain deterministic. The project's LLM-Supervised Execution standard still requires Tier 1 supervision of the critical recovery pipeline. Attach a diagnostic consult to DeliveryFailureSentinel's uncertain-result branch through the shared bounded LLM queue, to examine discrepant browser/transport evidence and produce a diagnosis or request a read-only receipt probe. It has no receipt-classification or retry-grant authority: immutable validators alone consume concrete returned evidence. It cannot invent receipts, change origin or resend a possibly accepted child. Limit one consult per originId, 30 seconds; failure/budget exhaustion leaves outcome-unknown. Existing bounded retry only handles definitive non-delivery. The send path and durable fallback never wait for the consult.
10. **Durability/performance:** WAL synchronous=FULL for intent/claim commits, fsync for fallback records; promise process-crash and OS-acknowledged durability, not immunity to device destruction. Store work runs off the serving event loop; short transactions contain no network calls. Do not inherit PendingRelayStore's five-second main-thread busy wait. Bound the whole preparation-to-response pipeline against the actual script and sentinel timeouts.
11. **Capacity/retention defaults:** 1,000 active logical operations, 256 MiB active payloads, 100 children per plan. The six-hour deadline starts at original preparation and the nine-attempt ceiling is per child, persisted across restarts/transfers and every format variant. Neither episode labels nor fallback sinks reset them. Admission over limits returns capacity-unavailable before dispatch; no silent truncation. Expiry stops recovery and records expired-unresolved. Metadata/receipts remain until the operator explicitly changes retention; retain 30 days hot and older records in bounded, indexed, manifest-backed archives. Payload/attachment cleanup after deadline/terminal completion never deletes the retained origin or receipt tables. Existing disk health owns pressure reporting. These are tunable admission defaults, not claims about today's config. Sizing rationale: 1,000 active operations bounds concurrent obligations to one thousand pending conversations; 256 MiB bounds payload working storage to roughly 256 KiB per active operation; 100 children caps a single operation at 10% of the logical admission budget while allowing long formatted replies; six hours bounds persistence recovery to one operator work period; nine attempts permits the existing bounded retry schedule without indefinite activity. These are explicit engineering ceilings, not measured workload percentiles. Operators may tune them within validated positive finite ranges; counters, original deadlines and receipt uncertainty never reset when changed.
12. **Audit authorization:** initially operator-only, through an explicit audit-read scope resolved by the existing dashboard/operator authority. Session preparation and relay credentials cannot enumerate. Do not equate the general agent bearer token with verified human identity; add an explicit scope if current main lacks one. Apply the check to direct IDs, filters, counts, cursors and peer requests. No cross-conversation metadata leak through pagination.
13. **Pool pagination:** freeze authorized shard membership and per-shard upper sequence watermarks on page one; order by createdAt/machineId/originId/revision. Cursor contains independent shard progress and coverage. Missing shards make the answer incomplete, never complete-and-exhausted. A recovered shard requires a new snapshot or explicit shard-resume cursor so its old rows cannot be skipped by a global timestamp. Inserts appear in a new snapshot. Archive retrieval uses the same coverage contract. Machine retirement requires verified count/digest transfer plus readable destination lookup before removing its shard.
14. **Rolling activation:** install compatible storage/readers first, upgrade writers/lifeline/peers, enroll or replace existing sessions, then activate. Refuse complete activation with an enabled old writer or generic writable agent Telegram profile. Accepted legacy queued work gets an imported-legacy origin with explicit unknown evidence and its own receipts; never infer it from current settings. Queue cleanup and archive retention are separate.
15. **Signature freshness:** ASP v1's 900-second acceptance window is unchanged. Prepared signed variants carry an absolute dispatch deadline of signedAt + 780 seconds, reserving 120 seconds for clock/transport delay; never send a known expired signature. Freshness assumes signer/verifier absolute clock skew at most 60 seconds and remaining transport delay at most 60 seconds. Known skew beyond 60 seconds holds as clock-unsynchronized until clock health recovers; unknown receiver skew is an explicitly unverified operating assumption, not proof of synchronized clocks. Excessive unseen skew/delay can cause signature rejection and held signing/receipt uncertainty, never relaxation of inbound freshness. Pagination does not share this timing assumption. If the owning agent signing capability is still available, it may renew a tag over the same immutable canonical body and origin binding, with a fresh nonce and an audited signing attempt. Otherwise hold signing-unavailable until renewal or the original recovery deadline. Do not relax inbound replay/freshness rules for queued messages. A delayed origin-host-loss case can remain undelivered; never claim indefinite offline signing capability.
16. **Operator-account message forms:** do not send unsigned content first and authenticate it in a later companion. An Instar receiver could have already attributed the first message to the human. Operator-account broker operations must carry the required ASP proof in the same text/caption as each message. A natively captionless/uneditable form that cannot do so returns unsupported-authorship-form BEFORE any content is dispatched, regardless of cosmetic display settings. Offer an explicit signable representation such as a document with caption; never silently alter media semantics. This constrains the newly proposed broker, not a claim that the current Bot API already supports these methods. It avoids expanding ASP into a new multipart security protocol solely to add runtime metadata. Bot captionless messages may still use cosmetic companions when visible; their sender is already the bot. The rejected post-hoc security-companion design is recorded in the review report, not represented as supported.
17. **Key lifecycle:** envelopes include signing key ID/epoch. Use the existing machine-identity registry's rotation/revocation history; retain public verification keys with their valid intervals and record acceptance-time verification. Revocation stops new acceptance from the revoked key; historical records report whether verification occurred before revocation and the current key status, never relabel compromised history as freshly trusted. Key loss yields explicit inability to attest, not regenerated origin. Test rotation/revocation across a queued operation and archive lookup.
18. **Hidden linkage and audience:** when display is hidden, ordinary bot messages link through the private ledger and full platform namespace, not a covert visible/zero-width token. This respects the request to hide display; ledger backup/archive is load-bearing. Persist platform chat-migration aliases without rewriting original identities. Default display applies to every authorized destination, including external/shared chats, as requested; labels are treated as outgoing content by the existing disclosure authority. Operators control safe friendly names and can hide fields. Do not silently change defaults based on guessed audience, and do not promise a forward/copy by a human will preserve private audit linkage.
19. **Authorized derivation:** an immutable parent plan specifies canonical authored content, destination and allowed rendering variants plus narrow derivations. Only signature timestamp/nonce renewal and receipt IDs in bot cosmetic companion links may be derived; content, origin and destination cannot change. Materialize a derived child as a new immutable signed/sealed version, persist its digest and parent/input links, and verify it before claiming that child for dispatch. The parent/child identity and retry budgets do not reset. Old materializations remain inspectable and cannot execute after a replacement wins the fenced child claim. Reserve bounded child count and maximum companion bytes before admission; never discover unbounded new children after partial delivery.

Alternative considered: force every send through the Bot API. Rejected because a bot cannot replace the authorized capability of sending through the operator's logged-in account, which is expressly part of this request. The separate broker preserves that capability with a controlled writable profile. Footer-only-on-change and browser best-effort-only recording would weaken the direct per-message requirement and are not adopted.

User-account alternative: TDLib/MTProto is a strong alternative with explicit send-success updates and message identifiers. TDLib also requires its own application parameters and user-authorization lifecycle; existing Web login state cannot simply be assumed to be an enrolled TDLib client. The proposed Web broker retains the already authorized browser capability. Its receipt adapter must correlate the submitted operation's client random_id with the server-assigned message ID/update (or a direct server send-result ID), full peer/chat identity and final content state through a version-tested Telegram Web adapter. DOM text, a click, or a temporary local bubble ID never suffices. If that adapter cannot obtain the correlation, hold outcome-unknown rather than claiming delivered. Require a feasibility spike against concrete upstream Web client code before implementation, then a version-drift capability canary before each broker activation. The completed non-sending spike found Web K's exposed manager RPC returns server Updates; this is an incidental client implementation seam, not a stable public API, and carries ongoing adapter maintenance. Its exact asset hashes, source maps and anonymous RPC canary are retained in the review evidence. Authenticated managed-profile send/receipt validation remains required before activation. Bound any worker-internal retry activity by the same immutable request/random ID and dispatch deadline; an outer timeout does not cancel a Web worker. On deadline, close the owning broker browser process before allowing later work, retain possibly-in-flight/unknown state, and never mint a replacement random ID for an uncertain send. This integration must be falsified with delayed/duplicate updates and concurrent same-text sends before activation. If Web cannot supply correlated server receipts, use an explicitly enrolled TDLib/MTProto transport as the preferred alternative; do not pretend existing browser cookies establish that login, silently convert transports or claim the browser path complete. Technical feasibility is an implementation verification obligation, not a new unresolved operator policy decision. Sources: [TDLib authorization and send updates](https://core.telegram.org/tdlib/getting-started), [updateMessageID](https://core.telegram.org/constructor/updateMessageID), [updateShortSentMessage](https://core.telegram.org/constructor/updateShortSentMessage).

Replication alternative: replicating all retained audit rows would simplify local reads and improve offline coverage, but it copies indefinite history onto every enrolled peer and needs a new retention/replication policy. This design chooses explicit federated reads plus existing backups, with offline coverage shown rather than hidden. Fallback origin copies are not a full replicated history. Pagination does not assume synchronized clocks: immutable createdAt values supply an arbitrary stable sort, while each shard's frozen sequence membership and independent cursor prevent clock skew from skipping records. Privacy/availability implications of indefinite replication are not silently introduced by adding metadata.

The diagnostic consult has a concrete consumer: its structured diagnosis and requested read-only probes are recorded on the existing delivery failure record for the recovery worker/operator inspection. Only validated probe results can update the deterministic receipt state. Correctness of send/receipt/retry invariants does not depend on the LLM returning successfully; supervision is a diagnostic requirement, not a second delivery authority.

The displayed footer remains per-message as requested; footer-only-on-change is not the default. enabled:false or all three field switches false yields no cosmetic footer, while recording continues.

## Migration, rollout and rollback

New and existing agents receive default-true display with idempotent migrations preserving explicit false. Update queue/profile/config schemas, relay protocol, reply scripts, browser integration, agent-awareness template and existing-agent sections together. Derive the sender denominator from fresh source and running transport capabilities. No text-only or bot-only implementation may claim all Telegram messages are covered.

Validate with mocked network and dry-run rendering, then an authorized development-agent trial covering text, browser, hidden-display persistence, attachment and cross-machine relay. Fleet activation requires all enabled transports to meet the matrix. Implementation order is explicit: retain the authorized browser capability through the bounded Web K compatibility adapter first, with the concrete feasibility proof above; support the explicitly enrolled public MTProto alternative under the same typed broker as the production fallback when that compatibility adapter cannot pass. A TDLib-first rewrite would not itself enforce the user-requested browser path, and new application/account authorization cannot be assumed from existing browser cookies. There is no operator prohibition on enrollment; it is simply not a prerequisite to building and validating the already-authorized browser path. Do not ask for an extra login merely to avoid implementing that approved path. Browser activation specifically requires the tested Web build/manager canary, authenticated principal and destination verification, and a permitted send joined to its actual server receipt. The Instar Telegram integration maintainer owns adapter drift response. Run the canary at each broker process activation and recheck the loaded client build immediately before every prepared operation; a changed or unsupported build cannot write. A failed broker canary keeps that transport held and updates health immediately. Before operator escalation, perform at most one safe fresh-process/reload plus read-only canary recheck, without submitting or replaying any message. If that bounded recovery fails, emit one existing attention item per failed build for the maintainer/operator. Persist the attempted-recovery/attention latch through the existing bounded self-action authority, honor its 15-minute episode brake, and never turn failed writes into a browser-restart loop; no repair-time SLA is promised. Two consecutive upstream builds failing the supported adapter trigger the defined public-MTProto migration path instead of another speculative private-seam patch; preserve existing authorized browser access read-only while enrollment is resolved. explicitly enrolled TDLib/MTProto is the preferred alternate implementation and is used if Web cannot meet the receipt contract. Repeated upstream Web drift is a trigger to move to that public MTProto transport under the same origin service, preserving operation/random IDs, outcome-unknown holds and required account enrollment. This is the defined migration path, not a claim that a new account login already exists. Disabling only display is a supported rollback while capture/reads remain; an old binary that drops new envelopes is a noncompliant rollback, never silently safe. Test queued new-schema operations during rollback before advertising it.

| Browser activation result | Required behavior |
| --- | --- |
| Tested build, authenticated principal/destination, durable random ID and verified server receipt proof pass | Web compatibility adapter may activate |
| Canary or principal/receipt proof fails | Hold writes; one bounded read-only recovery, then existing attention escalation |
| Two consecutive unsupported upstream builds, or Web cannot meet the receipt contract | Use the defined explicitly enrolled public-MTProto alternative; do not assume a login or replay uncertain work |

## Maturation plan

- **test-agent-live:** Run the production-initialization factory with real stores and mocked network in the isolated test agent, including all acceptance failures and the enabled-writer conformance matrix before the development trial.
- **dev-agent-live:** Activate on the authorized development agent after required checks pass, exercising the already specified text, browser, hidden-display persistence, attachment and cross-machine relay trial; record actual receipts and remaining coverage gaps.
- **fleet:** Ship compatible readers/storage before writers through the existing update/migration path; activate each agent only when its enabled writer, session and profile enrollment matrix satisfies the rolling-activation contract.
- **graduation criterion:** Every enabled sender family has its positive proof and independent bypass/failure controls, all required tests pass, retained audit and optional display work in the development trial, and the activation matrix reports complete coverage. Registration or a passing bot-only test never suffices. The existing Side-Effects Review standard supplies independent evidence validation before each maturation transition.
- **dark-window:** Zero additional soak after the stated acceptance and enrollment checks pass: proceed to activation. Before they pass, report implementation/activation incomplete with the concrete failing obligation; do not present a disabled feature as shipped or let a time delay override the existing activation gates. Register the ship-time maturation decision on the existing maturation track so any incomplete stage retains its established review cadence.

## Evidence boundaries

Topic pins prove desired settings, not current runtime. Session records prove registration, not the current model. Current-turn harness events support harness-reported model identity but not provider execution attestation. An origin row proves preparation, never external delivery. A footer is display, not independent authentication. A concrete Telegram receipt proves its specific acceptance state, including scheduled/ephemeral variants. Egress lint proves only its analyzed source population; behavioral sabotage must independently demonstrate each claimed boundary, including browser bypasses. Missing or stale measurements stay unknown.

Unit, authenticated HTTP integration, and production-initialization lifecycle tests are all mandatory, with real store/resolver wiring. Each positive control needs a corresponding negative or deliberate sabotage control.

3. Default display and every explicit false setting work; persisted metadata and retrieval are unchanged by visibility. Repeat migration preserves false.
4. Retry/restart/transfer after session destruction retains origin and distinguishes delivery host; corrupt queue metadata and incompatible peers never silently default.
5. Boundary-length Unicode/Markdown/HTML, code blocks, caption groups, forward and captionless plans preserve content and attribution; invisible originals remain refused.
6. ASP verification survives rendering, splitting, fallbacks and visibility settings; tampering fails; A2A marker semantics survive. Signatures never confer operator authority.
7. Fault injection before intent, after network acceptance and before outcome persistence yields distinct honest states. Lost receipts never become blind duplicate sends; partial companions/groups remain partial.
8. Edit history retains creator/editor; forwarder is not original author; legacy histories are not falsely backfilled.
9. Forged session identity, arbitrary model strings, invalid mesh binding, unauthorized preferences and cross-user audit queries fail at their corresponding boundaries.
10. Feature-alive E2E constructs real components and retrieves real records; cross-machine audit reports unavailable shards and still resolves retained records after topic moves.

12. Six-plus children survive stampede processing; identical prose from separate sessions gets separate intent/suppression records. Redrive retains exact pre-redacted content/format; HTTP 200 suppression never becomes a delivered receipt.
13. Racing server/lifeline/relay workers get one child claim. Crash after claim/acceptance never creates another send. Ambiguous sink/authority selection cannot yield competing executors.
14. Primary contention/corruption exercises durable fallback within budget; all-sink failure remains visible locally. Queue cleanup/archive/retirement preserve retained origin retrieval. Missing-peer pagination never falsely reports complete history.
15. Every supported harness has a positive current-model control; an always-unknown resolver fails health. Missing observations still permit truthful degraded sends when a durable sink is available. Supervisor failure cannot fabricate success or trigger unsafe retries.

18. Restart-during-outage acceptance: lose the owning process and its permit while recording remains unavailable; restart the production factory with the origin worker still failed. Health/dashboard must explicitly report recording unavailable and notification unavailable after restart, never a fabricated zero-held count or successful notification. ### Recording-outage notification

Justin explicitly selected hold and notification. Ordinary messages remain held when recording or the execution outbox cannot admit them. This is an operator-approved failure policy, not an inferred restriction.

**N1 — Exclusive entry point and bypass controls.** The sole public orchestration API is `TelegramOriginOutageNotifier.requestHoldNotice(operatorAlertDestinationId)`. It accepts only an already-authorized alert-destination identifier, never text, method, origin fields or serialized request data. Its private reservation/consumption capability is minted by the origin service and cannot be constructed from a plain request object. IPC exposes the same narrow request. Hard invariant: only `TelegramOriginOutageNotifier` may consume preclaimed outage permits. A source boundary lint restricts imports/calls of the private consumption entry point to that module, and behavioral boundary tests reject counterfeit ordinary-operation references even if the lint is sabotaged. Ordinary preparation APIs cannot create the reserved claim class or invoke a chosen notice variant. Sabotage tests attempt arbitrary text/destination/variant injection and counterfeit permits through ordinary HTTP preparation, direct egress and IPC; none may create a network effect.

**N2 — Fixed notice and operator-hub routing.** While storage is healthy, prepare and durably reserve one exact fixed bot automation notice per authorized operator alert destination: "Messages are being held because their origin could not be safely recorded. Delivery is paused while recording is unavailable." Route this operational alert through the existing attention/notification authority to the operator's configured alert hub, consistent with the standing one-hub alert policy; do not create per-message topics or notify third-party external recipients. Operator-account conversations where the bot is absent are explicitly covered by that same operator alert hub. Coalesce held work across those conversations into one hub notice per outage generation. If no authorized bot-reachable operator alert destination is configured, health/dashboard declares notification-unavailable; never invent a recipient or send through the human account as an emergency bypass.

**N3 — Immutable display variants.** Record its machine and automation origin, authorized destination and finite display variants before an outage. Preseal the at most eight distinct machine/harness/model visibility combinations (disabled/all-fields-hidden shares the no-footer variant), all under ONE preclaimed notice child. Each variant is an immutable exact wire request. The parent explicitly permits selecting the already-recorded variant matching current effective display bits at fire time; this selects bytes, never re-renders them or creates another claim. Machine/producer labels remain the recorded reservation snapshot. This is a narrow pre-authorized choice for fixed outage notices, not mutable origin for ordinary messages. Cosmetic preference version changes alone do not invalidate the notice.

**N4 — One process owner and bounded IPC.** The sole transactional outbox pre-claims the notice while healthy, atomically binding its single-use permit to exactly one named process/boot incarnation (normally the lifeline, or the main process on installations without a lifeline). This is a special claim class with no reclaim, not a second execution authority. Other processes request consumption through bounded authenticated local IPC; an IPC timeout never transfers the claim or permits their own send. No in-memory capability is assumed shared across OS processes. Exclude this special reservation from ordinary claim reclamation, redrive and stampede processing.

**N5 — Fire-time application policy.** On outage after the bounded recording fallbacks fail (or the sole outbox fails admission), permit only the configured operator alert hub, current Instar outage-notice permission and current credential ownership; select the presealed variant using current effective display bits. Application permission defaults on and has the explicit Telegram messaging setting `messageOrigin.outageNotice.enabled: false` to opt out without disabling origin recording. Telegram applies each recipient's personal mute/archive behavior. Instar does not claim to inspect those private client settings. Configuring a hub is not proof that the topic exists or that delivery succeeded: the single permitted network attempt records concrete acceptance, concrete failure (including a known missing topic), or uncertainty. None grants a fresh notice retry.

**N6 — Independent policy projection.** An independent observer reads the existing agent configuration (including actual SecretMigrator/SecretStore resolution in a bounded worker) and operator-hub state into a validated, versioned memory projection, separate from the origin database/outbox worker and its recovery loop. It refreshes actual source observations at most every five seconds; a projection is usable for at most 30 seconds and never beyond its own expiry. Fire-time access performs no disk/network/origin-worker read. Config/vault/key-file invalidation, changed resolved credential (including same-account token rotation), malformed/unreadable source or observer failure invalidates permission; rereading a cached snapshot never renews it. Current credential ownership is checked independently before wire dispatch. Both main and Lifeline use this shared bootstrap; bounded IPC does not create authority when its source is unavailable. Explicit opt-out, disabled Telegram messaging, lost ownership or changed hub binding suppresses the reserved notice without rewriting it; expose the reason and replenish only after storage recovery. Missing, expired or invalid policy suppresses as state-unavailable. Cosmetic preferences select the matching presealed variant. Fault injection must stop both recording workers while leaving this observer alive and prove the notice reaches mocked network; separately revoke/expire/fail this application authority and prove suppression. This terminal bounded recording failure is the required self-heal exhaustion for Justin's requested notice; do not add another repair loop or delay behind unrelated recovery. The private-client-state requirement in the earlier draft was an implementation overconstraint added after the user's hold-and-notify instruction, and is corrected here; no new user approval is inferred.

**N7 — One network attempt.** After those checks, consume the callable in-memory capability before any await and make exactly one network attempt through the visibility and fire-time ownership/permission checks. Do not call retrying sendToTopic/apiCall paths, recursively prepare a notice, or change the sealed body during the outage. Ambiguous acceptance stays unknown.

**N8 — Recovery and generation.** A new generation may be reserved only after confirmed recovery; previous permits are never reused after restart. This notice is already durably recorded, so it does not bypass the always-record rule.

**N9 — Observable outcomes and limits.** Expose held work plus notificationAttempted and notificationOutcome in live health/dashboard state and broadcast the state change. Persist the event/receipt when storage recovers. Notification is an attempted delivery, not proof the user received it: an operator without a reserved alert destination, process restart during outage, revoked destination permission or Telegram/network failure can prevent Telegram notification. Do not promise an impossible unconditional notification under those conditions.

**N10 — Capacity and paced coalescing.** Bound ready notice reservations separately at 1,000 authorized alert destinations and 8 MiB total exact requests (at most 8 KiB for all variants of each reservation combined), so they cannot exhaust ordinary delivery slots. Both count and byte ceilings are independently enforced; 1,000 reservations each using 8 KiB totals about 7.8 MiB, below the independent 8 MiB byte ceiling. Ordinary held conversations coalesce by operator alert destination, so an outage across 1,000 conversations with one operator produces ONE notice, not 1,000. Across distinct authorized operators sharing a bot, the owner paces at most 10 notice attempts per second through its existing outbound pacing authority (or the stricter existing limit), with a bounded queue of at most 1,000 permits. This is at least 100 seconds for a full 1,000-destination fan-out at that cap; Telegram/network availability may make actual delivery slower or fail. Permission and variant checks run at dequeue, before single-use consumption; shutdown or unknown attempt never triggers a second send. The fixed queue drains once and cannot schedule new notices without storage recovery. Exceeding the reserve leaves health/dashboard notification coverage explicitly incomplete and never licenses unrecorded notices. The fixed notice makes no completion-time promise, and holding must retain the existing bounded original payload/deadline rather than silently dropping the work or granting an unsafe duplicate retry.

Implementation verification remains required: the sender inventory, authenticated browser delivery, migration and activation checks are not implied by resolved operator decisions.
