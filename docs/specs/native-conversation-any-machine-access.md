# Any-machine access to conversations and the sessions behind them

This spec is one of two siblings. It holds slices 3d, 3e and 3f; the other, `native-conversation-base.md` (the parent), holds the shared framing and slices 3a, 3b and 3c.

Source read at `d54f26884` (main, 2026-11-11). Paths are relative to the repo root. Nothing here is built.

## 1. Framing

The problem, the operator's messages, the five acceptance cases, the corrected evidence and the target architecture are in the parent (`native-conversation-base.md` §1 and §2) and are not repeated here. This spec carries the part of Phase 1 that answers message 141905 (10:40 PST, topic 141876, authorship `human`):

> "You should always have FULL insight/access to any conversation AND the session behind it, regardless of what machine you are on."

It builds parent §2 item 7 (any-machine reads over signed machine transport, and the session behind a conversation is copied so a sleeping machine does not take it away) under item 8 (audience is enforced where a person is answered; "any machine" does not mean "any principal"). Its acceptance cases are F4 and F5 of parent §1.3. Each is a real failure from 2026-11-11 and each needs a passing live proof before the effort is called done:

| # | What happened | Passes when |
|---|---|---|
| F4 | The Mama PC could not read the M5 Pro transcript ("peer URL refused") or the Studio's ("token refused"). Justin's dashboard showed both. | A session reads any awake machine's transcript and pool history with no shared token (slice 3d). After slice 3f, a machine that is asleep is answered from the copied transcript, and the answer states how far the copy reaches. |
| F5 | Justin's reply typed in the dashboard session view did not arrive. | The dashboard never clears a reply it cannot confirm, offers a second send only where the receiving machine can recognise a repeat, says why a reply was refused, and when a send stays unconfirmed it says so plainly and asks the session itself whether the text arrived. It never asks the person to check. |

Parent §1.4 records that pool history from the Mama PC still reports one peer as `peer URL refused`: F4 is live. Slice names (3d, 3e, 3f), decision numbers (FD-n) and section numbers continue the parent's, so a reference reads the same in both files. "Phase 2" and the later phases are outlined in parent §4.

## 3. Phase 1: slices 3d to 3f

3d and 3e are independent of each other and of the parent's slices. 3f is built after 3d, under its own short spec. Owner for every key and date: Echo, effort topic 141876.

### 3d. Signed transcript and history reads (F4)

**Cause.** `/sessions/:name/transcript?machineId=` proxies with this machine's own API token (`routes.ts:12404-12421`); the pool history fan-out does the same after a credential URL guard that reports "peer URL refused" (`routes.ts:21749-21754`); `/sessions?scope=pool` uses the same hop (`routes.ts:12086-12087`).

**Change.**

1. *New verb `session-transcript-pull`* in `src/core/MeshRpc.ts` (command union near `:308`, registered-peer class near `:596-621`), served by `src/core/sessionTranscriptPull.ts`, modelled on `topicHistoryPull.ts` and registered beside it (`server.ts:29250`). Modes: `transcript` (`{ session, before?, limit?, full? }`, through `findSessionTranscript` and `readTranscriptPage`, 1 to 500 entries, default 150, `SessionTranscriptReader.ts:87`) and `list`. An answer that would pass the byte cap keeps the newest whole entries and returns `truncated: true` with a `before` cursor; with full text that is an ordinary outcome for a large page, not an error. The machine serves only sessions recorded on itself, never a path.
   - *What the reader returns, stated as it is.* `readTranscriptPage` does not return raw rows. It returns entries taken from each record: message text cut at 4,000 characters with a bare `…` (`SessionTranscriptReader.ts:30,33`), a tool call as its name and up to 200 characters of its input (`:35-40`), no tool results, and several entries can share one record offset. r3 said "every row can be read in full" on top of this reader, which was false.
   - *The clip is disclosed and can be lifted.* The reader marks every entry whose text it cut with `clipped: true`. It gains one option, used by `full=1` on the routes and `full: true` on the verb, that turns the 4,000-character cut off, so a clipped entry is read whole by asking for the same page again with `full`. No clip is silent and every message text can be read in full.
   - *What 3d does not serve.* Tool inputs beyond the one-line summary, and tool results. The raw record reaches other machines with slice 3f. The CLAUDE.md text says this, so a session does not take the digest for the whole record.
2. *Audience follows the conversation; redaction is partial.* A transcript holds what was said in the conversations its session served, so the owner is shown it only where the owner may see those conversations (access comes only from the owner's signed team record). It is readable by the owner and by the agent for its own operation, and by nobody else: members and guests see messages under the existing team rules and never a session's working record (constitution: *An Instar Agent Always Serves a Team*, answered under Team posture).
   - *The stamp.* The machine that ran the session lists every conversation that session served (`conversations`, by conversation key) on every verb answer and, in 3f, on every checkpoint. The audience is not frozen into the stamp: the machine that answers a person resolves it at read time from its own copy of the signed team record, with the place resolution the spawn entries already use (`TeamAccessLog`, `confined.json`, `TeamConfinement.placeForEntry`, `MemoryPrivacy.audienceFor`), so a change to the team record made after the transcript was written takes effect on the owner's next read on that machine. The currency rule is kept, for the owner's read only, as one test the machine can evaluate by itself: with team access on, the read is refused while the team log has a gap (`teamLog().gaps()`) or the team puller is refusing (`refusing()`: not yet settled after a start, a peer known to be awake that has gone unanswered past the bound, or the opt-in strict rule, `TeamAccessSync.ts:96-99,279-285`). These are the two facts behind `access-being-checked`, the answer that stops team phones today (`teamRefusal`, `mobilePairingRoutes.ts:520-525`). The refusal reads: "This machine cannot confirm who may see this session right now." The owner's read needs the rule because the one refusal the owner meets, a session of someone else's private conversation, is decided from the team record. It is stricter than the owner's read of messages, which those two facts do not stop, because a transcript holds more than the messages; it also stops a session's read through the route while it holds. Stated limit: the test does not refuse on a machine whose peers show no sign of being awake (by design, `TeamAccessSync.ts:91-95`), so a machine cut off before a conversation became private to someone else still shows the owner that session. r5's two further clauses are withdrawn: "has not synced since the newest revocation it could know of" cannot be evaluated by the machine it describes, and the comparison of a checkpoint's `conversations` set with the age of the team record is not needed, because a checkpoint's rows hold only content of conversations known when it was cut, so the union over the checkpoints held is the right audience for the rows held. A signature proves who wrote a record, not that it is the latest. A session with no conversation (a job, a hand-started session) is the owner's. A session that served several conversations takes the most restrictive result: a person may see the transcript only if they may see every one of those conversations. If the list or the team record cannot be read while team access is on, the audience is `unreadable` and the transcript is shown to no one.
   - *Who is answered: the owner.* r5 also answered members and guests through `deviceMayUse`; that is withdrawn. A transcript is a session's working record, not the conversation's messages: every text the session was given (injected lines, continuation and compaction summaries, messages from other agents), all its narration, and each tool call with part of its command (`SessionTranscriptReader.ts:35-40,45-62`). A grant opens a conversation's messages, past and future (`team-roles-and-access.md:150`). It does not open that record, for two reasons read from the team design: a session of that conversation from before the grant ran unconfined, with the owner's reach, and "an unconfined session can read the agent's token and files" (`team-roles-and-access.md:67,150-154`); and the per-reader rule that holds back what a session wrote without knowing of the reader's grant is applied to messages (`mayReadMessage`, `TeamAccessMerge.ts:241-245`) and to nothing in a transcript. So members and guests see messages under the existing team rules and never a session's working record. No device route is added: no rule in `DEVICE_ALLOWLIST` lists the transcript route, the phone's history route stays `ownerOnly` (`mobilePairingRoutes.ts:2271,2451,2531`), and no slice adds a route a phone or team member can call. The transcript route (the local read, the signed read, and in 3f the read from a copy) answers the owner in the dashboard's History view and refuses a transcript whose audience does not include the owner: "This session serves a conversation that is private to someone else." The owner sees the sessions of conversations the owner can see, and the session of another person's private conversation only after a grant in the team record puts the owner in its audience. A member read is deferred to sessions launched confined with the reader's grant in their access vector (§4).
   - *The agent's own reads.* Server code moves transcripts between the agent's machines for its own operation (the verb, and 3f replication), as it already moves the conversations themselves, which are replicated to every machine. The dashboard and an owner-reach session use the same API token, so the route cannot tell them apart and applies the refusal to every HTTP caller. That agrees with `team-roles-and-access.md`: text from a confined conversation never loads into an owner-reach session.
   - *An answer with no `conversations` field* (an older machine, reached by the bearer fallback). On an agent that has never had a team (no access files exist) it is served as today, so a team of one loses nothing. On an agent with team access on it is refused: "That machine runs an older version and cannot say whose conversation this session served."
   - *Stated limit, accepted.* This is a route rule. A session running for the owner on a machine can read the transcript files on that machine's disk directly, 3f copies included, and no route rule can stop a file read. The team record governs what the agent shows people, not what a process on the box can read. `team-roles-and-access.md` §5 states the same limit for the conversation log, and nothing here closes it (§5 Risks).
   - *Redaction.* The serving machine removes its own API token and dashboard PIN (`redactForDevice`) from each entry before it is clipped or cut. A transcript holds other secrets; the audience rule, not redaction, is what limits who reads it.
3. *The routes try the verb first.* They fall back to the bearer hop only on a definite answer from the peer that it cannot serve this kind of read: the mesh reason `no-handler` (`MeshRpc.ts:780`), a peer whose version advert is absent or older than the release that carries the verb, or, for pool history, an answer that does not echo `shape: 'pool'` (item 4). `claim-unauthorized` alone never permits it: an older peer answers an unknown verb with it from the RBAC default, and so does a real denial. Each is remembered per peer, kind and version. A timeout or any other error is reported as that machine's failure and never downgrades to sending the token. The transcript route forwards `redact=device` and `full`, the first of which the proxy drops today (`routes.ts:12408-12410`).
4. *`topic-history-pull` gains* `before`, `beforeMessageId`, `limit` up to 100 and `shape: 'pool'` (adds `messageId`, `eventId`, `provenance`, the origin join). For `shape: 'pool'` text is not clipped and the byte cap is 512 KiB, the page and cap of the bearer pool read it replaces (`routes.ts:21700,21757-21758`); the verb's default shape keeps its own limits (`topicHistoryPull.ts:14-18`). A capped answer returns `truncated: true` and the oldest cursor. The answer echoes `shape`.
5. *Asleep is said plainly, and capability is tracked per kind of read.* A machine that does not answer is listed with its id, name and last-seen time, and `asleepOrUnreachable: true`. Each answer names its transport per machine (`via: 'signed' | 'bearer'`). The route records, per member machine id, which kinds of read that machine has itself answered in signed form and at which version: `signedCapable: { transcript, list, historyPool }`. One kind answered says nothing about another: a machine can have the history verb and not the transcript verb, or the verb and not the pool shape. The status read lists `bearerFallbackNeededBy: [{ machineId, kinds }]`: for each registered member, the kinds not yet verified. FD-18 and CMT-051 read that list.
6. *A row larger than the cap is returned in pieces, never skipped and never a stall.* Both verbs build a page newest first and stop before the row that would pass the cap. When the newest remaining row is alone larger than the cap, the answer is that one row, cut at the cap on a UTF-8 boundary, with `rowTruncated: { row, totalBytes, from: 0, to }`. `row` is the history row's `eventId` or `messageId`, or, for a transcript entry read with `full`, its record offset and its index within that record. Ordinary transcript paging uses that same entry identity: the `before` cursor is a record offset plus an entry index, never an offset alone, so a page that ends between two entries of one record neither skips nor repeats an entry. The rest is read with `{ row, byteFrom }`, which returns the next range of the same row and the same marker until `to` equals `totalBytes`. A row is redacted before it is cut, and `totalBytes` and every range are counted in the redacted row, so a secret cannot leave in two pieces. The page cursor (`before`) always moves past that row, so a caller that does not want the remainder is not held behind it. The routes pass the marker and the continuation through; a session sees "row cut at N of M bytes" with the way to read on.
7. *The caps are tuning within a floor.* Floor: every message text and every history row can be read in full (with `full`, and by continuation when one is larger than the cap), the cursor always advances, and every clip or cut is marked in the answer with the way to continue. Values: 512 KiB is the size at which today's pool fan-out already rejects a peer's answer (`routes.ts:21757-21758`), so it is the consumer's existing bound; a fan-out to the 16 peers that route allows (`:21750`) then holds at most about 8 MiB, under the server's 12 MB body limit (`AgentServer.ts:1880`). 500 transcript entries is the reader's own page bound (`SessionTranscriptReader.ts:87`) and 100 history rows is the bearer read's (`routes.ts:21700`). Changing a value changes page size and nothing else. A Telegram text is far below 512 KiB, so for history the oversized-row path is reached only by a synthetic row in tests.

**Config and migration parity.** On, no switch. Mixed versions are covered by the fallback both ways and by the missing-field rule of item 2. CLAUDE.md template, through `migrateClaudeMd()` with a content guard: reading another machine's transcript needs no shared token; an asleep machine is named; the read is a digest whose clipped entries are marked and read whole with `full`; a cut row comes with its continuation; a transcript of someone else's private conversation is refused.

**Tests.** Unit: `sessionTranscriptPull.test.ts` (unknown session; truncation keeps the newest entries and returns the cursor; token and PIN removed; no path; **an entry over 4,000 characters is marked `clipped` and is whole with `full`**; **audience: a session with no conversation is the owner's; a device-signed request for a transcript is refused for a member and for a guest, whatever they have been granted; with team access on, a team log with a gap refuses the read and so does a refusing team puller, and a replica whose peers show no sign of being awake does not refuse; a byte cap that falls inside a multi-entry record: paging with `before` returns every entry exactly once; one conversation confined to another person excludes the owner; two conversations take the more restrictive; an unreadable list or team record with team access on gives `unreadable`; a grant made after the transcript was written admits the owner on the next read and a revocation refuses it**) and `topicHistoryPull.test.ts` (new fields, `truncated`, the `shape` echo, an older peer). **Both: one row larger than the cap between two ordinary rows is returned alone with `rowTruncated`, its continuation reads the rest byte for byte, the cut falls on a UTF-8 boundary, a token placed across the cut appears in neither piece, and paging with `before` reaches the older row without reading the remainder.** Integration, `pool-reads-signed.test.ts`: two servers with different API tokens; ### 3e. The dashboard never loses a reply quietly (F5)

**Cause, by reading.** The console composer sends a WebSocket frame and clears the text as soon as the socket write returns (`dashboard/console/sessions.js:314-316`); it never reads `input_ack`. For a session on another machine the relaying server answers `subscribed` itself before the peer link is active (`WebSocketManager.ts:445-449`), relays a rebuilt frame `{ type: 'input', session, text }` (`:487`) and returns nothing; a link that is not `active` drops the frame (`PeerStreamProxy.ts:179-194`). The serving machine refuses remote input unless `dashboard.poolStream.allowRemoteInput` is set (`WebSocketManager.ts:341-344`). The default is off and this machine's config has no `poolStream` block (read 2026-11-11), which is a sufficient cause for F5 wherever the dashboard and the session were on different machines.

**Change.** The default stays off.

1. *The serving machine says what it can do.* When the peer link for a session becomes active, a new serving machine sends `{ type: 'input_caps', session, inputAck: 2, remoteInput: <boolean> }` as its first frame for that session, and the relay forwards it. An older serving machine sends some other first frame; the relay then emits `input_caps` with `inputAck: 1` itself. Until `input_caps` arrives the composer is disabled and reads "Connecting to that machine…". For a local session the server sends `input_caps` with `subscribed`. The peer link is shared by every browser client of this server, so the relay keeps the last `input_caps` per session and replays it to a client that subscribes after the link is active.
2. *The draft is kept until its own acknowledgement.* The `input` frame carries `clientInputId`, random and made in the browser (`/^[A-Za-z0-9_-]{16,64}$/`, validated before it is echoed); the relay passes it through (`:487` changes). The composer keeps the text and files, marks them "sending", and clears them on one event only: an `input_ack` with `success: true` and the same id. That holds however late the acknowledgement arrives, including after the draft was shown as not confirmed. An acknowledgement with no id, or with another id, clears nothing.
3. *The server always answers, and never types twice.* `WebSocketManager` echoes the id on `input_ack` and on each `gateWrite` error (`:330-350`, `:477-495`). The relay returns `{ type: 'error', code: 'peer-stream-lost', session, clientInputId }` when there is no proxy or the relay did not send; `relayInput` and `relayFrame` return a boolean.
   - *Seen ids are keyed by session and id, nothing else.* The serving machine records `(session, clientInputId)` before it writes to tmux and answers a repeated id with the original ack, without writing again. r3 also keyed by client connection. The server has no stable client identity (`clientId()` is the socket's remote port or a random number, `WebSocketManager.ts:737-740`), and for a relayed input its client is the peer link, which is new after a drop, so every retry after a reconnect would have been an unknown id. With a random id of 16 or more characters, two tabs choosing the same id is not a case.
   - *The ack goes to the sender only.* The serving machine acks on the connection the frame came in on. For a relayed frame the relay remembers which browser client sent each pending id and passes that ack to that client alone; today a peer frame is fanned to every client of the session (`:400`).
   - *Retry.* A retry reuses the id and is flagged `retry: true`. A known id gets the original ack. A flagged retry whose id the server does not know is refused `input-retry-unknown` and not typed: the server cannot tell a first try that never arrived from one it has forgotten (it restarted, or the id was evicted), and typing on a guess could type the text twice.
   - *Retention is tuning within a floor.* Floor, which holds whatever the retention: an id the server does not know is never typed on a flagged retry, so forgetting an id can refuse a retry and can never cause a second write. Value: the newest 256 ids per session, in memory. Its basis is the memory bound only (about 64 bytes an id); no measurement derives 256. The evidence is collected: the serving machine counts evictions and unknown retries (`inputIdsEvicted`, `inputRetryUnknown`), and the 2026-11-25 check raises the value if any session shows both.
4. *A second send only where a repeat is recognised.*
   - `inputAck: 2`: after no answer, the composer offers "Send again", which reuses the id.
   - `inputAck: 1` (older serving machine): frames go without an id, as today. That machine's acknowledgement has no id and is fanned to every client subscribed to the session (`WebSocketManager.ts:400`), so it proves only that some input was written, not that this draft was. It **never clears a draft**. The draft goes straight to unresolved (item 5). An id-less `input-not-allowed` or `session-not-found` shows the refusal sentence and keeps the draft. There is no send control: that machine cannot recognise a repeat, so a second send could type the text twice.
5. *An unresolved draft stays unresolved, is shown honestly, and the session is asked.* A draft is unresolved when no acknowledgement with its id has arrived 8 s after the send (the label changes then and nothing else does), when the serving machine cannot acknowledge by id (`inputAck: 1`), or when its retry was refused `input-retry-unknown`.
   - *It is not resolved by evidence that only resembles it.* r3 searched the session's transcript for the draft's text and cleared the draft on a match. That is removed. Two sends of the same text ("yes"), from one person or two, are one row or two that no text comparison can assign, and a read taken around the send can miss or include the row. An unresolved draft clears on its id-carrying acknowledgement, late ones included, or when the person discards it.
   - *The agent follows up, not the person.* Once per draft, when it becomes unresolved, the console sends the session one line as an ordinary `input` frame with a fresh id of its own. No frame type and no server path is added. If the session cannot be typed into at that moment (the link is down, or `input_caps` has not arrived), the line is sent when `input_caps` next arrives while the page is open and the draft is still unresolved. The line is fixed:

     "[dashboard] A message typed in the dashboard at HH:MM (input `<clientInputId>`) could not be confirmed as delivered to this session. This line is from the dashboard, not from the user. In your next reply to the user, say whether a dashboard message reached you around that time and what it said. If you do not recall one, say only that you cannot confirm it. Do not say it was lost and do not ask for it again."

     The line is not retried and is not itself followed up. Its text is not the draft, so it cannot type the draft twice. The session's answer goes to the person in the conversation and can only confirm arrival: a session that does not recall the message proves nothing (the input carries no id the model sees, and it may still arrive), so the draft stays unresolved, shown as "not confirmed", and no resend is suggested on that basis. The answer does not clear the draft; the id-carrying acknowledgement or the person's Discard does.
   - *Controls.* `inputAck: 2` with no answer yet also offers "Send again". `inputAck: 1` and `input-retry-unknown` offer Copy and Discard only. The unresolved draft sits above the composer, which stays free for a new message.
6. *What the operator reads.*
   - refused: "Not sent: typing into sessions on another machine is switched off on that machine. Your text is still here."
   - link lost: "Not sent: the connection to that machine dropped. Your text is still here."
   - the serving machine answered `input_ack` with `success: false`: "Not sent: that machine could not type into the session. Your text is still here."
   - unresolved, and the line of item 5 was acknowledged by its own id: "Not confirmed yet. I have asked the session whether your text arrived, and it will answer in the conversation. Your text is still here."
   - unresolved, and the line was not acknowledged or could not be sent: "Not confirmed yet. I tried to ask the session whether your text arrived and could not confirm that either. Your text is still here."
   - `input-retry-unknown`: "Not sent again: that machine has no record of your first try, so it cannot tell whether a second would repeat it." followed by the unresolved sentence that applies.
   - When `input_caps` says remote input is off, the composer is read-only with the first sentence before anything is typed (`POOL-DASHBOARD-STREAM-SPEC.md` §2.4).
   No sentence asks the person to look at the session or to check anything.
7. *Key frames only report.* A `key` frame gets an id and an ack, shows a failure, and is never restored or retried: a repeated Enter or Ctrl-C is an action.

The legacy dashboard page (`dashboard/index.html:4705`) keeps today's id-less path. A dashboard reply is still raw terminal input with no place in the conversation; that is Phase 2.

**Config and migration parity.** On, no switch; no change to `allowRemoteInput`. Dashboard files ship with the package. Mixed versions are covered by items 1, 4 and 5.

**Tests.** Unit: `WebSocketManager.test.ts` (id echoed on ack and on each refusal; a repeated id is written once, also mid-write; **a repeated id arriving on a different connection is still recognised and gets the original ack on that connection**; an unknown flagged retry is refused; the relayed frame keeps the id; **the relay passes an ack only to the client that sent its id**; `input_caps` comes first, is synthesised as `1` for an older peer, and is replayed to a client that subscribes late; an evicted id refuses its retry and is counted) and a composer model test for every state, including **an id-less acknowledgement leaves the draft in place; an acknowledgement with the draft's id that arrives after the draft was shown as not confirmed clears it; the session line is sent once per draft, waits for `input_caps` when the link is down, and is never sent twice**. ### 3f. Transcripts are copied to every machine (F4, message 141905)

Owner Echo. Its own short spec by 2026-11-18, live by 2026-12-02 (deferral CMT-047). The decisions below are fixed here so that spec does not reopen them.

1. *Destination: unified.* Every machine of the agent holds a copy of every session's transcript, so any single machine can read the session behind a conversation with every other machine off.
2. *Incremental checkpoints.* The source machine copies new transcript rows as they are written: when its existing transcript poller sees growth (`TokenLedgerPoller` already tracks a byte offset per file) and at session end. (`SleepWakeDetector` reports a stall or a wake after the fact, `SleepWakeDetector.ts:295,333,414`; nothing fires before sleep, so there is no before-sleep checkpoint.) A checkpoint is an append-only replicated record, built on the same replication code as conversations but kept in a store of its own that no device or team route reads: `{ sessionId, sourceMachineId, seq, fromOffset, toOffset, sourceThroughOffset, rowCount, firstAt, lastAt, sha256, bytes, conversations }`.
3. *A manifest with explicit coverage.* Each machine derives, per session, `{ throughOffset, throughAt, complete, sourceMachineId }` from the checkpoints it holds; a gap in `seq` stops coverage at the gap. A read on any machine returns rows plus that coverage and whether the source is awake. It never presents a partial copy as the whole transcript: "copied through 14:02; the machine that ran it is asleep; later rows are not here yet."
4. *Audience and secrets.*
   - *Audience.* A copy follows the same rule as the read of §3d item 2. Each checkpoint carries `conversations` as the source knew them when the checkpoint was cut; a read from a copy takes the union over the checkpoints it holds for that session, resolves the audience at read time on the reading machine, and is refused to the owner exactly where the live read would be, the currency refusal of §3d item 2 included. The copies sit on the agent's own machines, which already hold the same conversations. No device or team route reads the store; that sentence is the rule, and nothing in §3d says otherwise now that member answering is withdrawn.
   - *Redaction by whole rows.* The source removes its own API token and dashboard PIN before a checkpoint leaves it. A transcript file is one record per line and a secret contains no line break, so a secret always lies inside one row. The source therefore redacts row by row and a checkpoint contains only whole rows; the one thing held back between reads is a trailing row that is not yet complete. r3 described a held-back window of bytes inside the stream as well; with whole rows it is not needed and is removed.
   - *Offsets and hashes describe the redacted rows.* `fromOffset`, `toOffset`, `bytes` and `sha256` are positions in, and a hash of, the concatenated redacted rows, which is what a replica holds and can verify; consecutive checkpoints are contiguous. A redaction changes length, so the source file position travels separately as `sourceThroughOffset`.
   - *Restart.* `sourceThroughOffset` is the source file offset of the end of the last whole row emitted, never the position read so far, and it is written in the same transaction as the checkpoint it belongs to. Nothing read and not yet emitted is lost by a crash: after a restart the source reads again from that offset, which is a row boundary, where no redaction state is carried.
   - *Tests the 3f spec must carry.* A token placed across two file reads at every split position appears in no checkpoint and not in the replica's concatenation; a partial trailing row is held back and appears whole in the next checkpoint; a replica verifies each `sha256` against the bytes it holds; a crash with a partial row buffered, and a crash between a checkpoint's write and the next read, each resume with no gap and no repeat; a read from a copy is refused to the owner for a session of someone else's private conversation.
5. *Reads.* The 3d route answers from the live source when it is awake and from the local copy when it is not, and says which.
6. *Left to the 3f spec:* chunk size, the replication budget and disk floor (`ReplicationBudget`, Disk Steward), retention, and backfill of transcripts that predate it.

## 5. Risks

**Privacy and security.** A transcript is shown to the owner only, inside the audience of the conversations its session served, on a machine whose team log has no gap and whose team puller is not refusing; a member or guest is shown none, and no device route is added (§3d item 2). Accepted risk, stated plainly: a session running for the owner on a machine can read the transcript files on that machine's disk directly, and route rules cannot stop file access. The team record governs what the agent shows people, not what a process on the box can read. 3f puts copies on every machine of the agent (FD-11, not reversible), the same machines that already hold the conversations. Every new read is a signed, recipient-bound verb checked against the registry and key epoch; no bearer token goes to a new place, and a timeout never causes one to be sent.

**Power loss and load.** A dashboard draft lives in the browser until it is acknowledged by id or discarded. An unresolved draft costs one extra line typed into its session, once. 3d makes one call per peer, as today; a row larger than the cap costs one further call per 512 KiB of that row, and only when the caller asks for the rest.
