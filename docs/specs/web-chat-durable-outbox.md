# Web Chat Pending Sends Survive Tab Closure

## Outcome And Scope

A user who presses Send while disconnected can close the tab, reopen the dashboard and have that same pending message sent when this approved browser reconnects. Retain text and selected file bytes before clearing the composer. The connection line says Updating while actual current-page reads catch up. This implements parity rows W3/W6 for the assigned offline-send card: retain unsent text/files across closing the tab and show the complete connection line. Chief directed this card in handoff e478a9bb-ff0b-47ea-9d2f-e1004d267fbb: “Return to the durable web offline-sends card you chose (wc_9da6a822b3133f76). Carry it to a commit and send it to me.” W3 means durable pending sends; W6 means connection recovery status.

This is an encrypted pending-send store, not a received-message/history cache. The separate history-cache privacy decision stays open. No service worker, closed-browser execution, alternate device enrollment, new provider, server message database, retry authority or signing protocol is introduced. Automatic sending requires an open/running dashboard and a fresh, authorized browser identity. Offline delivery is not claimed before server acceptance. Existing message-link source stays in its separate verification custody.

## Grounded Existing Seams

`chats.js` clears the composer before send(), uploads before saveUnfinished(), stores plaintext in sessionStorage, drops beyond 50 and resumes only the opened conversation. `browser-device.js` already persists non-extractable signing keys in IndexedDB; never export or repurpose them. Its signedFetch reads mutable record across an awaited signature and needs an exact captured-identity check. `net-state.js` declares fresh before onBack completes; self-refreshing Chats is skipped by the console's ordinary reconnect refresh.

Existing media start uses `(deviceId, requestId)` and immutable metadata; identical chunk PUT is idempotent, and GET upload status reports completion. Existing MobileChatRequests reserves final sends before effects, rejects changed payload and retains results. Telegram already checks request age before NEW effects when no retained result exists; the App/Slack exact-stop gaps are repaired below, not claimed as existing behavior. These authorities, not an invented client send ledger, decide acceptance. Browser keys represent the approved owner device; current server permissions remain authoritative.

## Local Storage And Cryptography

Add `dashboard/console/chat-outbox.js`. Use a separate origin-local IndexedDB database `instar-chat-outbox`, schema 1, with stores for epochs, scope keys, entries and file parts. Leave the existing `instar-console` device schema/version unchanged; rollback must not break enrollment through a version mismatch. The new store is a client pending-send queue, not another agent/server message store.

Generate a separate non-extractable AES-GCM-256 CryptoKey per signing identity scope and an independent non-extractable HMAC-SHA-256 key for opaque conversation-order index keys (never an enumerable unkeyed destination hash); persist it through structured cloning. Never export a signing key, derive encryption from it or store a bearer/PIN/session credential. Encrypt text, destination/holder/label, filenames, file bytes, upload descriptors and final send JSON. Clear metadata is limited to schema, opaque scope/request identifiers, revision/epoch and part keys needed for lookup. Bind encrypted values to schema, exact scope, message request ID and immutable admission ID through additionalData; bind each part to file/part position. Each encryption/update uses a fresh random 12-byte IV and a 128-bit tag. Do not reuse a nonce for a progress update.

Use typed ciphertext/Blob parts, not base64 file JSON. Release each plaintext file buffer after encryption and keep admission memory bounded by the existing advertised aggregate message-byte limit plus one file buffer. No new lower eligibility cap is introduced. Serial preparation is an initial reversible implementation strategy, not an input-admission rule. Process selected files one at a time; storage parts use the already-advertised media chunk geometry, without reducing eligible file size. The original file digest and immutable metadata are computed before network admission. No asynchronous crypto/File read runs inside an IndexedDB transaction. Prepare ciphertext first, then commit key/epoch checks, entry and parts atomically. Treat CryptoKey cloning, transaction abort, QuotaExceededError, unavailable storage and decryption/integrity failure as actual failures, never successful queue admission.

The key is origin-local encryption, not protection against trusted origin script using it or an operating-system administrator. Request browser persistence where supported; a denial is not fabricated as a grant. Ordinary tab/browser closure must preserve the committed queue in the real profile test. Site-data deletion, profile destruction and platform eviction are not remote backup or guaranteed recoverability. Do not show an unsolicited happy-path warning for hypothetical eviction.

## Composer Admission

Capture one submission attempt before its first await: exact device/machine/host/key identity, current app/sign-in generation, canonical conversation, original Slack holder, text, files and one original message request ID. Mint each file's upload-start ID once here. Do not derive a destination from whichever chat happens to be open later.

Resolve the existing credential-shaped-text choice for the exact captured text BEFORE making any queue entry eligible. Secret Drop/cancel commits nothing drainable; another tab cannot send while that choice is open. For ordinary queued sends, persist encrypted content and file bytes successfully before clearing any composer input, showing Saved/Queued or beginning an upload. Exception: a current explicit online text-only exact stop may take one direct signed attempt if outbox persistence fails, under the captured live identity and fresh current server authorization. Retain its draft until actual acceptance; a lost response is unknown and never creates automatic replay or a Saved claim. A broken pending-content store must not itself prevent current emergency control. If persistence fails, retain the actual draft/tray and show an actionable failure. Guard the in-progress admission so a second click cannot create two operations from the same submission attempt. After commit, clear only the still-matching captured draft/files; a newer draft or tray is not cleared. Submission into one chat never consumes another chat's draft.

Enumerate queued entries asynchronously, not an unbounded synchronous stringify/getAll of file data. There is no silent drop-oldest count, age purge or plaintext fallback. Only decrypt an entry under its matching approved identity scope. Recovered queue items are the user's own pending content; do not read or persist received conversation history to render them.

## Identity, Logout And Deletion

The retained actor is the existing signed browser identity tuple: host, machineId, deviceId and public-key hash. Store no copied grant or claim that local state authorizes network sending. Before reconnect draining, obtain fresh browser status for that key and the current machine, verify active status/capabilities and use current server-corrected time. An elsewhere/replaced/unknown identity is held, never automatically rebound. A definitive revocation uses the existing key-removal rule.

Capture the signing record/key before signature preparation. Revalidate matching identity plus caller liveness/generation after crypto and immediately before invoking fetch. A replacement record must not sign or send an older entry. Check identity after storage, decryption, upload and retry awaits as well. The existing server rechecks device/person/grants; no client verdict bypasses it.

Bind each authenticated console session to its durable epoch once at sign-in/startup; a sibling tab never adopts a newer epoch merely because another Send or route opens. After epoch invalidation it must sign in again before admission. Every queue read/drain and physical-attempt admission requires the entry admission epoch to equal the bound session epoch, plus the exact scope epoch; matching identity alone never revives an old row. Every queue write checks a durable scope/global epoch and entry revision in the same transaction. Updates require an existing row and matching generation; a stale callback cannot recreate a deleted row. Sign-out first stops/aborts the current app's workers, then durably advances the outbox session epoch BEFORE attempting content erasure. The invalidation transaction also marks cleanup-pending, which prevents any fresh session from binding/admitting until cleanup completes. After invalidation commits, a separate atomic deletion removes rows/parts/keys and clears cleanup-pending only if the same epoch is still current. A startup may finish that exact pending cleanup before binding. A stale cleanup transaction cannot erase a newer epoch's admissions; a superseding logout owns its own cleanup. A deletion abort cannot restore the prior session's admission authority. Retain existing browser enrollment. Distinguish failure to invalidate (do not claim sibling sessions stopped; notify visibly and retain retry) from failure to erase (already fenced but cleanup incomplete). A content-free localStorage logout fence/broadcast also invalidates live sibling instances immediately; the durable epoch is the reopen authority, never the broadcast alone. Clear the bearer as today. Do not claim pending content was cleared if storage cleanup failed; report that concrete failure on the sign-out screen.

Every definitive key-removal decision clears that identity's outbox: revocation/Forget, and same-enrollment-machine declined, expired or not-found. The same answer from another machine preserves it. Cleanup checks expected key identity. This clears the identity's outbox and encryption key before removing its signing record. These are two databases: use explicit ordered cleanup, not a false claim of cross-database atomicity. Pass the expected key identity into deletion and recheck it, so a delayed result cannot delete a replacement enrollment. Failure is visible/retryable, not silently ignored. An already dispatch-admitted or uncertain network request cannot be unsent by local sign-out/deletion. Removal of a saved copy never claims server cancellation.

## Durable Upload And Send State

Encrypted entry phases are prepared, uploading, ready, submitted, held and accepted. `submitted` means the request may have begun, not that it was delivered. File descriptors contain the fixed upload-start ID, immutable hash/name/type/size and, when known, upload ID/completion. Retained bytes survive closure before upload completion.

Before interpreting missing chunks, read upload status: completed uploads may have removed chunk rows. Reconcile lost final-chunk acknowledgments through GET status; complete advances, assembling waits, actual conflict/unknown/expiry holds. For each file, repeat the same upload-start request and immutable metadata. Persist its returned upload ID before progressing; a lost response is recovered by that same ID. Resume missing chunks, never change bytes at an index, and observe GET status until complete. An empty received/missing list is not completion. Respect current server limits and Retry-After. An explicit unknown/conflict/expired upload is held with content intact; do not manufacture endlessly fresh upload IDs.

Persist the final exact POST path, frozen Slack holder and serialized JSON before the first final POST. Use the existing signed bytes/contentType path, not reconstruction from current UI data. Every replay uses that same message request ID/body. Do not replace attachment descriptors, strip a field or mint a new message ID after an uncertain attempt. Server idempotency/reservations remain the effect authority.

The server, not the old client-only 23-hour shortcut, decides whether the original request is still valid or has a retained result. Repeating the original identity/body lets it return its result or refuse an expired NEW operation before effects. Freeze the operation request ID, including its embedded time, path and serialized body. Every physical attempt gets a fresh server-corrected signing HEADER timestamp/signature; never refresh the operation ID/time or mutate application bytes automatically. Unknown, conflict, expired or definitely refused entries stay encrypted and visibly held for review; no silent discard. A new user-authored send is distinct from automatic recovery. An ambiguous prior send gets Check conversation as its primary action, never an automatic NEW message operation. A status-0/lost-ack or 202 permits only exact original-ID/body replay under the current server capability and age/result authority; explicit outcome-unknown/payload-conflict/expired/definite-refusal holds without replay. At retry exhaustion a submitted uncertain entry shows Check conversation and the disclosed Resume original request action, which can complete the same original operation but never mints a new message ID. New user-authored sends remain separate and explicit. Outbox network calls use the signing layer's single-physical-attempt API, never Chats.call's internal 401 loop. Upload status GET and upload/chunk/final writes have separate immutable step keys and independent persisted budgets. Exhausted/uncertain PUT attempts never consume the remaining bounded read-only reconciliation budget: after a lost seventh final-chunk acknowledgment, reopen may GET completed status and advance without an eighth PUT. A failed GET consumes its own step budget; it does not reset a write budget. Every target HTTP result, including 401 followed by active status, returns to the persisted attempt ledger before another target attempt. Status reads do not silently reissue a target request. Test repeated 401/active across reopening with no more than seven target attempts until explicit user renewal.

Release pending bytes only after an actual durable server acceptance/result identifies the message, or explicit local removal/sign-out/revocation. A connection error/202 is not acceptance. Failed/unknown messages remain recoverable locally. Preserve existing dispatch/delivery labels: server acceptance is not provider delivery.

Persist exact-stop evidence as matched, unmatched or unknown against the last known advertised set at admission. Unknown (including legacy missing evidence) holds for a current explicit Send; never coerce unknown to unmatched. Persist whether exact-stop membership matched at admission and recheck the current advertised canonical set before EVERY recovered final POST. A match at either admission or recovery holds for a current explicit Send; a server upgrade adding a stop phrase must not turn a saved ordinary entry into automatic emergency control. Exact emergency-stop text is recognized only from the server's existing canonical exact-stop set advertised with support, never a substring or guessed keyword. A fresh online Send may authorize one immediate stop attempt in that live user interaction, bypassing pending conversation ordering so an earlier upload cannot delay emergency control. It must be invoked by the live submission path immediately after successful durable admission, not saved as a background permission. If that immediate path cannot run, or the submission includes files requiring asynchronous preparation, hold it; completing an earlier upload never releases a saved stop. Any interruption, failed/uncertain attempt, offline admission, closure or reload holds it with its text intact and no automatic replay. Show Check conversation and Use text in composer; an explicit current Send is a new user operation, never an automatic ID refresh. Client recovery must not dispatch a never-received saved stop from session A after it sees session B. This is a recovery-admission guarantee, not a new target-bound server stop protocol: an already admitted first HTTP request may be delayed in transit and the existing server still interprets it at receipt. Do not claim local holding can recall that request; session-bound stop authority remains the separate message-actions design. No new stop authority or guessed session binding is introduced.

## Cross-Tab And Reconnect Execution

Use one drain per authenticated console session, independent of page navigation; stop it on sign-out/session disposal. Chats subscribes for local pending presentation but does not own execution. An old tab paused across sign-out cannot acquire a new epoch or start a new logical operation without fresh sign-in.

Automatic recovery REQUIRES an origin-wide Web Lock around each active preparation/network step, including automatic part decryption. Hold one chunk buffer at a time, release it before releasing ownership, and release the lock during server cooldown waits so another conversation can progress. Browser lifecycle releases ownership when a tab closes; do not create an expiring client lease or guess that a paused owner is dead. A waiting tab revalidates epoch, identity, row and attempt admission when it acquires ownership. No-lock browsers retain durable content but do not start automatic recovery: show Automatic recovery needs a browser update, with an explicit Resume original request action for a bounded user-driven fallback. No silent drop, actor substitution or changed IDs. This is a coordination-capability limit, not a content/count/age eligibility quota. Test zero automatic HTTP without Web Locks and safe original-ID explicit fallback.

Manual no-lock fallback still uses the same persisted suboperation IDs, immutable metadata, exact final JSON and epoch/revision CAS. Before a physical step or decrypting its part, commit logical attempt admission against the live row. Duplicate user-driven HTTP may occur, but it repeats the same logical operation and existing server start/chunk/send idempotency must prove one upload identity and one message effect. This proves effect safety, not a fictitious origin-wide physical-memory bound. No new lease, kill action or arbitrary expiry is added.

Conflicting progress never overwrites the winning final JSON. Terminal deletion/epoch change wins over late progress. If a server storage failure makes a suboperation uncertain, hold rather than create a new operation. Use existing backoff/Retry-After and server rate limits; do not raise them. Bound each failed immutable suboperation to the existing upload ceiling of six retries (seven attempts). Each HTTP attempt uses the console's 20-second request deadline, giving 140 seconds of configured client response-wait deadlines across seven attempts. This does not bound server work, actual elapsed time across closure or late timer wakeup, or already-admitted effects; timed-out work can still complete. Honor a finite server Retry-After with one same-ID scheduled continuation; never shorten it or poll while waiting. While running continuously, configured response waits plus scheduled delays are 140 seconds plus at most six actual finite backoff/server-cooldown intervals; actual elapsed time may be longer when closed or timers run late. These waits do not reset the attempt budget. Independently confirmed successful chunk/phase progress starts the next finite suboperation; neither repeated 202 nor a health probe is progress. Persist attempt admissions and nextEligibleAt through entry CAS so sibling tabs or reopening cannot reset the failure budget or shorten a server cooldown. A single cancellable same-ID timer rechecks epoch/identity when it wakes. On exhaustion pause with encrypted content/progress intact and a plain Retry original action; no self-rearming timer starts a new episode. Reconnect and reopening only resume remaining attempts/cooldowns; they NEVER reset an exhausted budget. A new submission starts only its own entry. Only explicit Resume original request authorizes another bounded episode for that held entry; flapping connectivity cannot manufacture repeated batches. Timeout after invocation remains uncertain and never permits a changed ID/body. Deduplicate by scope/original request ID and retain phase/reason/attempt metadata locally without message text. No automated operator notice source is added. Enumerate all eligible scoped entries on approved dashboard start/reconnect, independent of which chat is open. No closed-browser background delivery is promised.

Assign each entry a monotonic per-scope/per-conversation sequence in the same atomic admission transaction. This orders successful durable admissions; overlapping uncommitted preparations in different tabs do not reserve a queue position before commit. The delayed-upload test commits the earlier entry before starting its upload and admitting the correction. Before a final POST admission, atomically check earlier pending entries in that conversation; a second tab cannot overtake an earlier upload. Keep blocked later messages visible. A held predecessor blocks automatic final admission until accepted or explicitly removed; provide the deliberate Send before this held message action for a later entry, recording only the specific predecessor IDs the user chose to bypass without changing its frozen application body or original ID. It is never a broad skip-all flag: another earlier uploading entry retains its place unless separately explicitly included. Test a held and an actively uploading predecessor together. Never infer permission to bypass from a timeout or page navigation. Test two tabs with an earlier delayed attachment and a later text correction, plus explicit held-predecessor bypass.

Old sessionStorage rows migrate only through a successful encrypted commit with a stable scope/request-ID import receipt in the same transaction, then removal of the old row. Retain that content-free receipt through accepted/local entry removal while the legacy source could survive; a crash between stores must not permit re-import after removal. Logout invalidates the old session before legacy import, persists an origin-wide legacy-retired marker with that invalidation, and retires its known source rows. Every new-client startup/import and resumed sibling checks that marker before reading/rendering legacy text; once retired, untagged legacy source rows are erased on discovery, never re-imported into a fresh sign-in or shown in its tray. A suspended sibling is tested through logout and sign-in with both plaintext storage and tray empty. Untagged legacy rows from an unsupported old client cannot regain new-format session eligibility after this explicit logout boundary. Never copy an unsupported legacy row into a new automatic operation. Preserve original IDs/text/upload descriptors. An untagged legacy row cannot prove that no intervening sibling-tab logout occurred: import it as held for explicit review, with zero automatic sends, even after fresh sign-in. Auto-replay requires a proven same-session epoch plus an exact recognized App/Telegram shape whose original path/body can be reconstructed; unknown fields, missing original Slack holder or actor mismatch become retained review items. Never guess a prior destination or throw away a legacy row before durable import.
