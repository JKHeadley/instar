# Resume verified attachment copies after a receiver restart

## Problem statement

The receiver currently remembers the peer that supplied a partial file only in memory. In a disposable two-store run, the source served offset 0, then returned busy for offset 1,048,576. The receiver retained a one MiB file. After reopening its real stores and replicator, it unnecessarily requested offset 0 again from the same peer, then completed the file. Whole-file integrity still passed. Correct that restart behavior at current limits. Source continuity is mandatory for extending an incomplete file because the current copier deliberately keeps each partial tied to one peer and uses that custody when diagnosing failures and deciding whether to keep a prefix. Resuming a locally plausible prefix from an unproven peer would relax source continuity and change breaker evidence. A complete file with unknown provenance is a separate recovery case, where no new bytes are appended and full length/hash alone can establish publishability without peer blame.

## Frontloaded Decisions

Retain the existing 50 MiB media limit, slice size, load admission, retry budgets, mesh verb, request authentication and existing app behavior. Use two explicit, default-false switches under the existing app media configuration: peerResume.requestProof and peerResume.serveProof. Both production sides must pass verification before activation. An off receiver ignores durable checkpoints and preserves ordinary behavior. An off source omits proof and replies as before. Cleanup of retired unreferenced checkpoint rows stays independent of enablement and runs under the receiver writer lock. This scope concerns restart of an in-progress receiver, not raised upload limits or storage synchronization between unrelated agents. Persist only receiver-local bookkeeping. Reuse the current copy lifecycle and review procedure before release.

## Proposed design

Replace the process-local source attribution for a partial file with a local SQLite checkpoint bound to the existing pull row. Use a dedicated additive pull_parts table in the existing local app-media index, without changing upload state or its durability setting. The checkpoint records hash, total length, authenticated source identity and registration key identity, exact committed length, and a local generation for the regular part file. Store filesystem identity without lossy number conversion, and include device, inode, precise size and change/write times. If those checks cannot establish a matching regular descriptor on the supported filesystem, use the established offset-zero behavior. Pull, serve, upload and public import/export payloads do not contain pull_parts fields. Include the receiver signing-key identity in each row in addition to the source identity. A copied SQLite snapshot cannot resume on another receiver when that receiver has a separately provisioned signing key or when the file generation differs. Explicitly exclude cloned signing identities from supported topology. No assurance claim for a clone with all compared identity values preserved. A same-host restore without the exact descriptor generation starts at zero. Explicitly trace shared state replication and restore boundaries before activation.

### Responding machine proof

MeshRpcClient signs the outbound request and currently reads ordinary unsigned JSON. It has no independently authenticated responder key, and production routes can use plain HTTP. A configured peer URL, a successful status, or the outbound request signature cannot prove the peer supplied the response. Add an explicitly requested, optional authenticated app-media slice reply on the current verb. Preserve legacy request and reply behavior for unchanged peers.

When opt-in is offered, the handler takes command, authenticated sender and verified envelope. The dispatcher also supplies the exact sender key used at request validation before any asynchronous handler work. In addition to the envelope nonce, the client provides a new cryptographically random challenge for each opted-in slice. The signer and verifier both use UTF-8 encoding of one compact JSON array in this fixed order: ["instar-app-media-slice-proof/v1", responderMachineId, responderSigningKeySha256, requesterMachineId, requesterSigningKeySha256, exactRequestNonce, exactChallenge, blobSha256, totalBytes, offset, byteCount, sliceSha256]. Key hashes are lowercase SHA-256 of DER SPKI from the verified or signing key, not opaque client claims. Use lowercase 64-character hex for digests and the random 32-byte challenge, canonical 88-character padded base64 for the 64-byte signature, and ASCII mesh IDs and nonces. For opted-in proof support accept m_ followed by 16 to 32 lowercase hex digits and an envelope nonce of 1 to 96 characters drawn from ASCII letters, decimal digits, colon, underscore and hyphen. This covers the existing generated m_ plus 32 hex IDs and the live mesh nonce format with a Date.now integer and increasing counter. When either machine ID or the outgoing nonce cannot use the supported format, the sender omits the proof offer and uses existing offset-zero whole-hash copying. That transfer cannot create a checkpoint. If a formerly expected identity changes during opt-in handling, the source returns a typed no-bytes refusal. The receiver re-resolves its own and selected peer identity under the normal authenticated registry and determines eligibility independently. The refusal body itself cannot grant a downgrade or continuation. Counts are safe whole nonnegative numbers encoded as JSON numbers. One shared encoder implements both ends. Add a fixed signing vector with exact encoded bytes, fixture key, signature and expected result. No application-level defaults or length concatenation are permitted. No identity or key claim in the command substitutes for the actual verified key. Recheck the currently active sender and signer key/membership and source's unpurged same-size reference and file identity after asynchronous work and immediately before signing. If the opted-in serving route loses any of these checks after reading, return a typed refusal with no bytes. Never return the buffered slice as unsigned success after a failed recheck. Legacy unsigned success is limited to the explicit source-off or old-peer path.

Apply a byte ceiling to the decoded HTTP response stream before buffering or parsing JSON for opted-in slice calls, including legacy and error responses. The response limit is 4 × ceil(APP_MEDIA_SLICE_BYTES / 3) + 1024 UTF-8 bytes, or 1,399,128 bytes at the existing 1 MiB slice cap. The allowance covers compact JSON punctuation, bounded numeric fields, version, at most one base64 signature and a machine-readable bounded refusal reason. No signer identity or transcript is echoed in the reply. Both sides enforce pre-parse byte count and valid UTF-8. Prove the maximum-size signed and unsigned shape fit, and exercise exactly the limit and one byte above it in a chunked stream. Cancel on overflow, including chunked responses, without changing unrelated RPC verbs. Validate expected encoded length before base64 decoding, and require exactly the existing requested slice extent, min(slice cap, total minus requested offset). Detect noncanonical, malformed or out-of-range replies without presenting them as an authenticated peer result. Verify one proof per slice against the pinned active key and exact outstanding nonce and challenge. Derive the next offset only from verified offset and actual verified positive byte count. Derive completion only from equality with the current same-size reference. A remote completion boolean cannot decide either. The existing legacy path remains available under its final whole-file hash.

A prefix is durable only if every accepted slice since offset zero has valid proof from the same active key. Do not upgrade a prefix begun on the legacy path just because a later response includes proof. Proof absent at offset zero can select the legacy in-process path. Proof absent on a response claiming successful slice bytes at authenticated nonzero offset, whether before or after a restart, discards that reply and retires the exact checkpoint and part under current custody. Attempt offset zero on the next existing retry opportunity, where a downgraded peer can continue on the legacy path. Present but invalid proof rejects the response bytes and follows current retry/backoff. Leave the last durable checkpoint and unchanged file intact because an unverified error cannot invalidate previously verified bytes. Any independent current access, registration or file-generation loss still retires progress under the normal custody rules. Do not assign authenticated corruption blame to an unverified reply. Busy is an unsigned refusal with no bytes and no new evidence. Preserve the prior valid checkpoint and existing no-backoff accounting, then try the same pinned offset on the next existing tick. This deliberately retains current pinned-source behavior. An indefinitely busy but still eligible source can hold the prefix even if another peer is ready. When the pinned peer becomes offline or breaks eligibility, an alternate starts at offset zero, never on the earlier peer’s bytes. Test both stable busy preservation and that eligibility transition. Changing peer fairness and retry policy is a separate behavior change. A missing proof on a successful reply is a different case. Hold at most one authenticated chain and one current challenge per existing in-flight request. Test proof withholding and key rotation during the transfer, and ensure absence during a peer downgrade never loops on the same nonzero request.

Before requesting, compare the part and checkpoint, current unpurged reference and its size, disk admission, and freshly active eligible source, key and breaker. Check unchanged keys and pull/reference/disk custody again after the await. The checkpoint can optimize the next request only, and cannot widen content access. Do not keep a SQLite transaction or filesystem mutation lock open across a mesh request.

Use nonblocking no-symlink opens where supported, verify a regular file with one link and exact generation, and require exact byte-count writes. A new offset-zero part uses exclusive creation after retiring stale state. Capture its descriptor generation after the entire slice has been written and fsynced. Then update checkpoint and retry state together, while still under the existing single receiver tick and state-root writer custody. No read lock is held over mesh I/O. After any exact-write, fsync, or SQLite commit failure, do not advance counters or reuse optimistic progress. Close the descriptor, follow the existing failure and backoff path if the current writer and pull generation still hold, then reread the committed row and reopen the file on the next attempt. If a transaction outcome is ambiguous, durable readback alone decides. A nonmatching incomplete file restarts at zero. A complete candidate may use the existing independent whole-file recovery path. Test injected write/fsync/commit failures without a process restart, including commit failure after successful fsync and failure while recording backoff itself. Verify counters, current-generation ownership, and the first next request. A failure before the committed transaction leaves no usable progress for those bytes. If length or generation changes between opening and writing, free the owned descriptor and retire stale state. A missing, too-short, too-long or altered partial with a legacy/missing/malformed checkpoint starts at zero. Overlong crash residue is discarded rather than truncated. On process termination where SQLite loses a transaction, the mismatched file falls back safely. A successful filesystem sync alone cannot create a committed checkpoint.

Before publication, require a successful fsync of the exact verified descriptor and independently hash the entire candidate using a verified open descriptor in the existing bounded appMediaWorker infrastructure and compare exact length/hash to the live reference. After hashing, synchronously revalidate the writer lock, regular-file descriptor and part path identity, a current live reference of the exact same size, and disk floor, then invoke publishPulled with no intervening asynchronous step. This only excludes replacement by other supported local writers that share custody. State-root writeability by arbitrary local processes is outside the app-media contract. Check for the exact live total length before discarding an otherwise stale checkpoint. If its fsync fails, do not publish or increment the landed counter. Retain/back off under current writer custody and retry the sync before publishing. A whole candidate left after a crash, including after final slice fsync but before its checkpoint commit, or produced by a legacy version, may still be accepted through full verification without source attribution; it is not permission to extend any incomplete legacy file. Only attribute a bad final hash to a peer when exact source and file custody remain established. Reference loss, completion, terminal retirement, and stale part restart remove their checkpoint with existing part cleanup. Preserve busy behavior, byte accounting and no second reservation for a prefix already represented by a reference.

### Receiver writer custody

Use the existing production SingleInstanceLock revalidation. Inject the lock authority from both commands/server and AgentServer service constructors. An override using INSTAR_ALLOW_SECOND_INSTANCE cannot act as a second same-root media writer. A concurrently running older override binary cannot honor this contract and is outside supported rollout. Roll back sequentially. Before handing the receiver to an old binary, stop its work, acquire the original writer lease under the new runtime, record its fail-closed rollback epoch and retire all resume checkpoint metadata under that custody. The older runtime may leave part files or rearm pull rows without changing the new generation. On re-upgrade, require the recorded retirement or refuse to trust old progress until all checkpoint metadata has been retired under the new elected writer. An old receiver cannot extend from a new checkpoint. Verify sequential downgrade after a committed slice, old metadata-only rearm and old file mutation/completion separately, followed by re-upgrade. Guard periodic pull cleanup, partial writes/checkpoint updates, inventory rearm, nudge/want/dirty entry points and final publication, including old offset-zero compatibility behavior on a receiver with either or both flags off. An off but overridden process has no mutation authority. Test elected proof-on and overridden proof-off processes sharing a root. Register local part/checkpoint custody in the existing state coherence registry. Under elected writer custody only, add an opaque nullable generation column to the existing pulls table via idempotent schema initialization and create pull_parts. A proof-off override cannot initialize these tables or mutate receiver files. On the first writable use of a legacy row, initialize it under the writer lock. Every new row and the existing unrecoverable-to-active rearm transition gets a new random generation. Hurry, ordinary retry/backoff, busy and checkpoint updates keep it. The pull_parts row records that same generation. Capture the persisted pull generation and in-memory service generation before any await. Retirement/recreation or unrecoverable rearm supersedes an old completion even with proof off and no pull_parts row. Test replacement during a suspended request and verify the new row and part are untouched. Stop and transport replacement invalidate the service generation synchronously so no old completion can mutate after a mesh or worker await. Recheck generation and lock on return from every await and before the synchronous mutation sections. Keep any worker-owned descriptor open until terminal acknowledgment, even when a stopped generation may no longer publish. Keep worker termination and descriptor lifetime bounded at the worker boundary. Verify a new elected receiver may start while the old worker still owns the descriptor without allowing stale publish, close or deletion to affect the new part. If custody is unknown or lost, leave the old part and retry row untouched for its rightful receiver. Do not start a new retry loop, gated notice or source-role escalation. Existing copy failures use current retry and reporting. Add a test that stops a receiver during pending mesh and during worker hash, then starts the replacement before releasing both old responses. Only the replacement may publish or remove part state.

## Multi-machine posture

Peer content continues to flow through existing signed mesh app-media-pull.
machine-local-justification: hardware-bound-resource
A checkpoint names an on-disk file and descriptor generation on the receiver. It has no valid meaning on another filesystem or another state root. It is intentionally excluded from any peer transfer and cannot grant additional source authorization.

## Decision points touched

| Decision | Classification |
|---|---|
| Continue an exact partial | invariant; basis: irreversible-consequence; evidence: extending an unknown source/file misattributes the transfer and creates bytes never proved for its checkpoint |
| Reject or restart on missing custody | invariant; basis: enumerable-domain; evidence: a valid row, matching regular file, live equal-size reference and authenticated unchanged eligible source are all required |
| Publish the completed file | invariant; basis: irreversible-consequence; evidence: a final size, SHA-256, live reference and disk check are the existing publication floor |
| Clear a retired checkpoint | invariant; basis: enumerable-domain; evidence: a landed, purged or discarded part has no valid incomplete receiver state |

## Verification

Use the existing disposable real-store reproducer. Focused unit checks should show the first post-restart request is at 1,048,576 and final content is byte-identical. Exercise legacy partials, mismatched identity or registration key, offline peer, prior short write, fsync-before-commit residue, stale or replaced part, hash failure attribution, reference purge before and after mesh await and hash, disk floor, and source replacement. Verify valid legacy and crash-complete files are locally hashed and can land while the old source is offline. A wrong hash in a crash-complete file without valid source attribution may not be blamed on a peer. Test schema initialization on an existing known DB. Integration uses existing app-media cross-machine fixtures with an authenticated mesh request and restart. A lifecycle test constructs the production service, reopens the receiver with a continuing source, and explicitly asserts that its first authenticated post-restart transport request is 1,048,576 on a verified host-local filesystem that exposes stable descriptor identity across reopen, as the macOS disposable probe does. An unsupported-file-identity fixture must independently prove the offset-zero fallback. Verify old in-flight writer exclusion and cleanup after the real lifecycle stops. Full suite stays with the verification coordinator.

## Open design checks

The existing source lookup is meshIdMgr.getSigningPublicKeyPem paired with isMachineActive; verifyEnvelope currently returns only a boolean/reason. Add exact verified key custody for the opted-in handler, and expose the immutable client-built envelope only to the opt-in reply verifier. Protect the existing generic result path from a protocol change beyond this opted-in verb. Demonstrate production lock callback availability and track rollback behavior if the old binary reopens a retained checkpoint and part. Measure signing and hashing cost against the existing eight-slice tick budget.
