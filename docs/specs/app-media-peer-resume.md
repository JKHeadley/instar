# Resume verified attachment copies after a receiver restart

## Problem statement

The receiver currently remembers the peer that supplied a partial file only in memory. In a disposable two-store run, the source served offset 0, then returned busy for offset 1,048,576. The receiver retained a one MiB file. After reopening its real stores and replicator, it unnecessarily requested offset 0 again from the same peer, then completed the file. Whole-file integrity still passed. Correct that restart behavior at current limits.

## Frontloaded Decisions

Retain the existing 50 MiB media limit, slice size, load admission, retry budgets, mesh verb, request authentication and existing app behavior. Use two explicit, default-false switches under the existing app media configuration: peerResume.requestProof and peerResume.serveProof. Both production sides must pass verification before activation. An off receiver ignores durable checkpoints and preserves ordinary behavior. An off source omits proof and replies as before. Cleanup of retired unreferenced checkpoint rows stays independent of enablement and runs under the receiver writer lock. This scope concerns restart of an in-progress receiver, not raised upload limits or storage synchronization between unrelated agents. Persist only receiver-local bookkeeping. Reuse the current copy lifecycle and review procedure before release.

## Proposed design

Replace the process-local source attribution for a partial file with a local SQLite checkpoint bound to the existing pull row. Use a dedicated additive pull_parts table in the existing local app-media index, without changing upload state or its durability setting. The checkpoint records hash, total length, authenticated source identity and registration key identity, exact committed length, and a local generation for the regular part file. Store filesystem identity without lossy number conversion, and include device, inode, precise size and change/write times. If those checks cannot establish a matching regular descriptor on the supported filesystem, use the established offset-zero behavior. Pull, serve, upload and public import/export payloads do not contain pull_parts fields. Include the receiver signing-key identity in each row in addition to the source identity. A copied SQLite snapshot cannot resume on another receiver when that receiver has a separately provisioned signing key or when the file generation differs. Explicitly exclude cloned signing identities from supported topology. No assurance claim for a clone with all compared identity values preserved. A same-host restore without the exact descriptor generation starts at zero. Explicitly trace shared state replication and restore boundaries before activation.

### Responding machine proof

MeshRpcClient signs the outbound request and currently reads ordinary unsigned JSON. It has no independently authenticated responder key, and production routes can use plain HTTP. A configured peer URL, a successful status, or the outbound request signature cannot prove the peer supplied the response. Add an explicitly requested, optional authenticated app-media slice reply on the current verb. Preserve legacy request and reply behavior for unchanged peers.

When opt-in is offered, the handler takes command, authenticated sender and verified envelope. The dispatcher also supplies the exact sender key used at request validation before any asynchronous handler work. In addition to the envelope nonce, the client provides a new cryptographically random challenge for each opted-in slice. The signer and verifier both use UTF-8 encoding of one compact JSON array in this fixed order: ["instar-app-media-slice-proof/v1", responderMachineId, responderSigningKeySha256, requesterMachineId, requesterSigningKeySha256, exactRequestNonce, exactChallenge, blobSha256, totalBytes, offset, byteCount, sliceSha256]. Key hashes are lowercase SHA-256 of DER SPKI from the verified or signing key, not opaque client claims. Hashes and challenges use one strict ASCII representation; counts are safe whole nonnegative numbers and are encoded as JSON numbers. One shared encoder implements both ends. Add a fixed signing vector with exact encoded bytes, fixture key, signature and expected result. No application-level defaults or length concatenation are permitted. No identity or key claim in the command substitutes for the actual verified key. Recheck the currently active sender and signer key/membership and source's unpurged same-size reference and file identity after asynchronous work and immediately before signing. Omit signed success if these checks fail.

Apply a byte ceiling to the decoded HTTP response stream before buffering or parsing JSON for opted-in slice calls, including legacy and error responses. The bound is the maximum base64 slice extent plus the fixed bounded versioned envelope, known machine-key/nonce lengths and bounded reason. Cancel on overflow, including chunked responses, without changing unrelated RPC verbs. Validate expected encoded length before base64 decoding, and require exactly the existing requested slice extent, min(slice cap, total minus requested offset). Detect noncanonical, malformed or out-of-range replies without presenting them as an authenticated peer result. Verify one proof per slice against the pinned active key and exact outstanding nonce and challenge. Derive the next offset only from verified offset and actual verified positive byte count. Derive completion only from equality with the current same-size reference. A remote completion boolean cannot decide either. The existing legacy path remains available under its final whole-file hash.

A prefix is durable only if every accepted slice since offset zero has valid proof from the same active key. Do not upgrade a prefix begun on the legacy path just because a later response includes proof. Proof absent at offset zero can select the legacy in-process path. Proof absent on a response claiming successful slice bytes at authenticated nonzero offset, whether before or after a restart, discards that reply and retires the exact checkpoint and part under current custody. Attempt offset zero on the next existing retry opportunity, where a downgraded peer can continue on the legacy path. Present but invalid proof refuses that response, clears unsafe progress, and follows current retry/backoff. Do not assign authenticated corruption blame to an unverified reply. Busy is an unsigned refusal with no bytes and no new evidence. Preserve the prior valid checkpoint and existing no-backoff accounting, then try the same pinned offset on the next existing tick. A missing proof on a successful reply is a different case. Hold at most one authenticated chain and one current challenge per existing in-flight request. Test proof withholding and key rotation during the transfer, and ensure absence during a peer downgrade never loops on the same nonzero request.

Before requesting, compare the part and checkpoint, current unpurged reference and its size, disk admission, and freshly active eligible source, key and breaker. Check unchanged keys and pull/reference/disk custody again after the await. The checkpoint can optimize the next request only, and cannot widen content access. Do not keep a SQLite transaction or filesystem mutation lock open across a mesh request.

Use nonblocking no-symlink opens where supported, verify a regular file with one link and exact generation, and require exact byte-count writes. A new offset-zero part uses exclusive creation after retiring stale state. Capture its descriptor generation after the entire slice has been written and fsynced. Then update checkpoint and retry state together, while still under the existing single receiver tick and state-root writer custody. No read lock is held over mesh I/O. A failure before the committed transaction leaves no usable progress for those bytes. If length or generation changes between opening and writing, free the owned descriptor and retire stale state. A missing, too-short, too-long or altered partial with a legacy/missing/malformed checkpoint starts at zero. Overlong crash residue is discarded rather than truncated. On process termination where SQLite loses a transaction, the mismatched file falls back safely. A successful filesystem sync alone cannot create a committed checkpoint.

Before publication, independently hash the entire candidate using a verified open descriptor in the existing bounded appMediaWorker infrastructure and compare exact length/hash to the live reference. After hashing, synchronously revalidate the writer lock, regular-file descriptor and part path identity, a current live reference of the exact same size, and disk floor, then invoke publishPulled with no intervening asynchronous step. This only excludes replacement by other supported local writers that share custody. State-root writeability by arbitrary local processes is outside the app-media contract. A whole candidate left after a crash, or produced by a legacy version, may still be accepted through full verification without source attribution; it is not permission to extend any incomplete legacy file. Only attribute a bad final hash to a peer when exact source and file custody remain established. Reference loss, completion, terminal retirement, and stale part restart remove their checkpoint with existing part cleanup. Preserve busy behavior, byte accounting and no second reservation for a prefix already represented by a reference.

### Receiver writer custody

Use the existing production SingleInstanceLock revalidation. Inject the lock authority from both commands/server and AgentServer service constructors. An override using INSTAR_ALLOW_SECOND_INSTANCE cannot act as a second same-root media writer. A concurrently running older override binary cannot honor this contract and is outside supported rollout. Roll back sequentially with the original writer lock held after stopping the newer instance. Guard periodic pull cleanup, partial writes/checkpoint updates, inventory rearm, nudge/want/dirty entry points and final publication, including old offset-zero compatibility behavior on an opted-in receiver. Register local part/checkpoint custody in the existing state coherence registry. Capture the persisted generation of the individual pull as well as the service lifecycle when starting any pull. Retiring/recreating or materially rearming a pull creates a new opaque generation, superseding any old completion for the same hash. Test replacement during a suspended request and verify the new row and part are untouched. Stop and transport replacement invalidate the service generation synchronously so no old completion can mutate after a mesh or worker await. Recheck generation and lock on return from every await and before the synchronous mutation sections. If custody is unknown or lost, leave the old part and retry row untouched for its rightful receiver. Do not start a new retry loop, gated notice or source-role escalation. Existing copy failures use current retry and reporting. Add a test that stops a receiver during pending mesh and during worker hash, then starts the replacement before releasing both old responses. Only the replacement may publish or remove part state.

## Multi-machine posture

Peer content continues to flow through existing signed mesh app-media-pull.
machine-local-justification: hardware-bound-resource
A checkpoint names an on-disk file and descriptor generation on the receiver. It has no valid meaning on another filesystem or another state root. It is intentionally excluded from any peer transfer and cannot grant additional source authorization.

## Decision points touched

| Decision | Classification |
|---|---|
| Continue an exact partial | invariant; basis: irreversible-consequence; evidence: extending an unknown source/file misattributes the transfer and creates bytes never proved for its checkpoint |
| Reject or restart on missing custody | invariant; basis: enumerable-domain; evidence: a valid row, matching regular file, live equal-size reference and authenticated unchanged eligible source are all required |
| Publish the completed file | invariant; basis: irreversible-consequence; evidence: a final size, SHA-256, live reference and disk check are the existing publication floor |
| Clear a retired checkpoint | invariant; basis: enumerable-domain; evidence: a landed, purged or discarded part has no valid incomplete receiver state |

## Verification

Use the existing disposable real-store reproducer. Focused unit checks should show the first post-restart request is at 1,048,576 and final content is byte-identical. Exercise legacy partials, mismatched identity or registration key, offline peer, prior short write, fsync-before-commit residue, stale or replaced part, hash failure attribution, reference purge before and after mesh await and hash, disk floor, and source replacement. Verify valid legacy complete chunks can be recovered only by full verification. Test schema initialization on an existing known DB. Integration uses existing app-media cross-machine fixtures with an authenticated mesh request and restart. A lifecycle test constructs the production service, reopens the receiver with a continuing source, and explicitly asserts that its first authenticated post-restart transport request is 1,048,576 on a verified host-local filesystem that exposes stable descriptor identity across reopen, as the macOS disposable probe does. An unsupported-file-identity fixture must independently prove the offset-zero fallback. Verify old in-flight writer exclusion and cleanup after the real lifecycle stops. Full suite stays with the verification coordinator.

## Open design checks

The existing source lookup is meshIdMgr.getSigningPublicKeyPem paired with isMachineActive; verifyEnvelope currently returns only a boolean/reason. Add exact verified key custody for the opted-in handler, and expose the immutable client-built envelope only to the opt-in reply verifier. Protect the existing generic result path from a protocol change beyond this opted-in verb. Demonstrate production lock callback availability and track rollback behavior if the old binary reopens a retained checkpoint and part. Measure signing and hashing cost against the existing eight-slice tick budget.
