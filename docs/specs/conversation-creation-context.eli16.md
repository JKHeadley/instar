# Keep Generated Chats With The Work That Created Them

Some App chats exist because the agent created a Work Board card or started a session. Today those chats look like unrelated conversations because their creation record does not say where they came from or which conversation should contain them. That is why useful backing chats can become clutter at the top of the chat list.

This change records the source and intended parent when a new chat is created. The app can then show it under the right work, or clearly say that it still needs a place. The record is durable and travels with the conversation between the agent's computers. An older computer may omit the new details when forwarding a chat. When that happens, this increment reports the placement as unknown or unplaced instead of guessing. It does not promise recovery while the original computer is offline. The deeper synchronization repairs are separately tracked. It does not guess from a title, and a later deliberate move in the Chief of Staff's tree takes priority over the original parent. If the server cannot read that tree, it says it cannot tell instead of inventing a placement.

Existing chats are treated more carefully. The server will offer a read-only preview matching exact Work Board card references to their backing chats and showing where the recorded evidence suggests they belong. An unclear source stays unclear. The preview does not move, rename, hide or delete anything, and it does not offer an apply button. There will be no automatic cleanup of old chats in this change.

The new details are visible only to the owner and the agent, just like the existing Chief of Staff parent information. A team member who can read a child conversation does not gain access to its parent, card or session. Ordinary message streams do not carry these private creation details. Recording a parent never grants permission to see either conversation.

This is the first server step for the Mac parity request. The Apple app session still owns the layout, its fixed Chief of Staff place and the releases. The next server cards cover mute and reversible archive, then the individual message actions. The server pull request is ready only when its real creation paths and preview pass tests and shared full verification. The card is complete only after the Apple session also proves the nested and unresolved cases in an exact native build through the user's channel. A draft field, successful API response or merged file alone does not prove the original clutter is fixed.
