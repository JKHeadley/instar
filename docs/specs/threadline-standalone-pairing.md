# Threadline without Instar

## 1. Why

Justin, topic 61599, 2026-10-15: *"threadline should NOT require Instar. It should be a self-sufficient service/protocol that any agent can use."*

Today it does require Instar for everything that makes a channel safe for secrets. The standalone package, `threadline-mcp` (0.4.4, `packages/threadline-mcp`), lets any agent discover others, message, keep contacts and notes, and set a self-assigned trust label. But it:

- sends every message as **plaintext** base64 JSON. Only Instar's `MessageEncryptor` encrypts (X25519 from the Ed25519 identity, HKDF, XChaCha20-Poly1305) and signs the envelope;
- has **no verified pairing**. Its `trust` field (`unknown | seen | conversed | trusted`) is set by the agent itself and proves nothing about a key;
- has **no credential gate**. Nothing refuses to send a secret to an agent whose key nobody verified.

Invite pairing (instar 1.3.1352, spec `a2a-pairing-invite-link.md`) fixed the human step, but only inside Instar. Someone running `threadline-mcp` in Claude Code cannot pair with anyone, and cannot pair with an Instar agent at all.

## 2. Decisions

**D0. The principle (Justin, topic 61599, 2026-10-15T18:51Z).** *"Instar should do what it can to further streamline the processes and optimize them, especially between Instar agents, but the fundamental requirements of agent to agent communication should be self contained in Threadline (and the external packages we develop that both Threadline and Instar use)."* So identity, pairing, encryption and the credential gate belong in Threadline's packages, and work fully without Instar. Instar's Telegram buttons, dashboard card, replication across machines and convenience routes are streamlining layered on top. They are never the only way to do something fundamental. Every later decision here follows from this, and future Threadline work should be checked against it.

**D1. One implementation, in a package with no Instar imports.** New `packages/threadline-core` holds: the Ed25519 sign/verify and X25519 derivation, with `isX25519BoundToIdentity`; the message envelope (encrypt, decrypt, sign, verify), byte-compatible with Instar's `MessageEncryptor`; the invite format, transcript, MAC key, tag and check code (today's `PairingInvite.ts`); the protocol engine (today's `PairingInviteFlow.ts`); a file-backed invite store and a pinned-key store; and the credential-gate predicate (D7). Its only runtime dependency is `@noble/ciphers`. It defines its own small interfaces instead of importing Instar's types: a `InviteTrust` (the calls the flow makes on a trust store: pin, mark verified, demote, forget, look up by fingerprint) and a minimal `PinnedProfile` type (fingerprint, identity key, state, verifiedAt, pairingId, via). Instar's `AgentTrustManager` implements `InviteTrust`; `threadline-mcp` uses core's file-backed store. The SAS word list and its file loading stay in Instar, because core does not need them. `threadline-mcp` keeps its own `identity.json` format (base64 raw keys); it hands core the public key as hex, and reads a 0.4.4 `identity.json` as it is.

**D2. Wire compatibility is the acceptance test.** A `threadline-mcp` agent and an Instar 1.3.1352+ agent must pair with each other and then exchange an encrypted credential. Same envelope, same four invite ops (`pair-invite-accept|used|finish|ack`), same transcript. Core's tests include envelope vectors generated by today's `MessageEncryptor`, and the envelope and invite wire formats are frozen to those vectors: core is a published interface, so a format change is a new version of the protocol, not a patch.

**D3. The person approves through the MCP host, not through the agent.** `threadline-mcp` uses MCP **elicitation**: the server asks the host to put a question to the person and return the answer. This boundary is **host-cooperative**, and is described that way in the tool text and the README. The host is what shows the question to a person. A host that answers elicitations in code (an SDK client set to auto-accept, a hook, a headless runner) removes the person from the loop, and the server cannot tell. In Claude Code the question appears as a dialog and waits for the person. Approval is an explicit choice in an enum (`decline` or `approve`, `not-them` or `finish`), and the safe choice is listed first, so an auto-resolver that picks the first option, or presses an "allow/continue/yes" pattern, declines. Elicitation wording avoids the phrases Instar's permission-prompt auto-resolver looks for, and a test checks that. A pending question waits up to 10 minutes for the person; after that it counts as no answer, and nothing is decided. It is used for the two operator acts:
- **Accept** (recipient): "Pair with the agent that calls itself X, which says it belongs to Y? Check code: K7Q2." Decline / Approve.
- **Finish** (inviter): "The agent that calls itself Z accepted your invite. Finish only if that is who you sent it to." Not them / Finish.

Names in these questions are what the other agent claims, always quoted and framed as claimed (the agent that "calls itself" the name), after cleaning (NFKC; bidi, zero-width and control characters removed). Look-alike names are compared after NFKC.

**D4. The invite stays out of the model where the protocol allows it.**
- **Recipient.** `threadline_pair_open` takes no invite argument. It elicits "Paste the invite you were sent" from the person, so the invite goes from the person to the server and is never in the model's context, transcript or logs. The tool returns only the invite's id.
- **Inviter.** The person needs the invite text to send it, so the inviter's agent sees it in the tool result, as in Instar's MCP `invite` action. Single use, the short expiry and binding to a known peer limit the damage, and so does the second-accept alarm.
- **Invite text.** Core owns one host-neutral sentence for the invite message: "Ask your agent to open a Threadline invite, and paste this into the box it shows you, not into the chat." Instar's invite text uses it too.
- **An invite in a message.** An inbound message containing an invite is refused before the model sees it, and recorded as a leak alarm. Outbound, `threadline_send` refuses a message containing a token that decodes as an invite with a valid checksum, a known secret format, in every mode (D6a). Text that only looks like the `tlinv1:` prefix is sent, and the send is logged as a signal. This refusal is best-effort: an invite split up or re-encoded passes. The real protection is single use plus the second-accept alarm, not the string match.

**D5. No terminal, ever. An app that cannot ask the person gets a local approval page.** (Justin, topic 61599, 2026-10-19: "any workflow where the user has to enter commands in a terminal is unacceptable", and the same day: "this needs to be compatible with more than just claude code ... focus on the most popular.") The terminal fallback of r3 is removed (threadline-mcp 0.5.1, PR #2204). Where the app supports elicitation (Claude Code, Cursor, VS Code, the ChatGPT desktop app; see D12), the questions appear in the app (D3). Where it does not (Claude Desktop, among the most popular), the pairing tools instead return a link to a **local approval page**:
- The page is served only by the process that owns pairing (§5), only on `127.0.0.1`, on a random port, only while one pairing question is waiting, and at a path carrying a one-time random 256-bit token. Links always use `127.0.0.1`, never `localhost`. It closes when the question is answered or after the same 10 minutes as D3 (no answer, nothing decided). A request with no `Host`, or a `Host` other than `127.0.0.1:<port>`, is refused (DNS rebinding); a POST whose `Origin` is present and not `http://127.0.0.1:<port>` is refused; every form post carries a per-question token; the page sends no-store, frame-deny and a strict content-security policy.
- **The model never sees the link** (Echo, round 2, R2-1). The pairing owner opens the person's default browser at the page itself. The tool result says only that a page opened in the browser, and carries neither the URL nor the token, so an agent that can fetch local URLs has nothing to fetch. Only if opening the browser fails does the result include the link, marked as a weaker fallback because the agent can then see it; status records that fallback.
- The person opens the link in their browser. For opening an invite, the page asks them to paste the invite there (it never passes through the chat, as in D4), shows the claimed names and the check code, and offers Decline / Approve. For Finish, it shows the claimed names and the check code and offers Not them / Finish. For forget, Keep / Unpair. The safe choice is first, as in D3.
- The tool does not wait for the person: it returns at once ("a page opened in your browser; it stays open for 10 minutes"), the pairing step runs in the background with the page asking each question, and `threadline_pair_status` shows the outcome.
- **Boundary, stated plainly in the tool text and the README:** with the browser opened by the server, the token never enters the model's context, and what remains is software running as the same user, which is out of scope (§6). In the fallback where the link had to go through the chat, the boundary is weaker, and the tool text says so. The page also shows the check code, for people who want to confirm it with each other.
- The choice between the app's dialog and the page is made by the client's declared `elicitation` capability at runtime, never by app name (R2-3), so a wrong claim about an app in D12 degrades to the page instead of breaking.
- An app with neither elicitation nor a way to reach a browser (a headless runner) cannot pair, and the tools say so in plain words, naming no command.

**D6. Encryption is per pinned peer and never silently downgrades.**
- **Sending.** `threadline-mcp` encrypts every ordinary message to a peer whose identity key is pinned, to the X25519 key derived from the PINNED key, never to a key the relay presented. One exception keeps messages readable: an acceptor still waiting for the inviter's Finish sends as before pairing, because the inviter holds no key for it yet. That wait is limited to the invite's maximum lifetime plus 10 minutes; after that, sends to it are refused with "your invite was accepted but its person never finished", shown in status. To an unpinned peer, messages stay plaintext, and the sending agent is told so.
- **Encrypted inbound.** A message that fails to verify or decrypt with the pinned key is refused, not shown as plaintext. An encrypted message from an UNPINNED sender is refused too: `threadline-mcp` has no pin to check it against, and it never treats one as a credential.
- **Plaintext inbound from a pinned fingerprint.** On the relay path the only evidence of a plaintext envelope's sender is the relay, so plaintext arriving under a pinned fingerprint is delivered as **unverified**: labelled "claims to come from <peer>, neither encrypted nor signed, the relay could have written it", never "from <peer>", never a credential, never a pairing op other than the accept, and never answered in plaintext. If such an envelope is signed by the pinned key it is attributed; no sender signs plaintext today, so in practice it is always unverified.
- **No downgrade after encryption.** The first time a pinned peer sends us **encrypted ordinary chat**, that is recorded (`encryptedSeen`), and from then on plaintext under its fingerprint is refused outright, so a relay cannot downgrade a peer that has spoken to us encrypted. Pairing ops and credentials do not set the mark: they are always encrypted, even from Instar versions before D9. Who can set the mark today: Instar before D9 encrypts ordinary chat only to a key the relay hands it, and `threadline-mcp` registers no X25519 key with the relay, so a pre-D9 Instar peer never sends `threadline-mcp` encrypted chat and never sets the mark. Only a D9 sender does, and D9's switch (§7) decides when that starts. In `threadline-mcp` the mark lives in the pin record (`pinned-keys.json`), so it shares the pin's fate: it is created with the pin, and removed only when the person forgets the pin. In Instar (step 6) the mark is a separate record merged into the trust profile, because a mark replicated across machines has to survive an inherited pin being revoked and re-inherited; it is dropped when the pinned key changes, and removed only when the person unpairs (Instar has no forget; unpairing is `markVerificationFailed`). If the pin store cannot be read, its peers count as unpaired until it is repaired, and plaintext under any fingerprint is then labelled unverified rather than shown as plainly from that agent (§5). A `threadline-mcp` 0.5.0 build from before r3 kept the mark in `threadline/encrypted-chat-peers.json`; the pairing owner folds that file into the pins once and renames it, and if it cannot be read, every pinned peer is treated as seen (fail-safe). Status says so in both cases.
- **The state files are a cooperative boundary.** An agent that can edit `pinned-keys.json`, or delete the mark, can undo these rules. The files are `0600` in the person's state dir, and the README says the protection is against the relay and other agents, not against software running as the same user.

**D6a. Listener proxy mode is opt-in.** By default `threadline-mcp` keeps its own relay connection. Only when the person sets `THREADLINE_USE_LISTENER=1` does it send through a local Threadline listener on `THREADLINE_SEND_PORT` (default 7711). Through a listener it cannot pair or encrypt, so `threadline_pair_invite|open|finish` refuse with that reason, and an ordinary message to a peer it holds a pin for is refused rather than sent through the listener in plaintext. Messages to unpinned peers go through the listener as before. The invite refusal (D4) applies in every mode.

**D7. The credential gate.** The core predicate is a pure function over a pin record and the envelope key: allowed only if the pin's state is `mutual-verified`, the pinned key's fingerprint matches the peer, the full pinned key is the one compared, and the envelope is encrypted to the X25519 key derived from that pinned key (checked with `isX25519BoundToIdentity`). If the store cannot be read, it refuses. `threadline_send` gains `credential: true`, which is allowed only when the predicate says yes. The credential flag travels inside the encrypted, signed body, so the relay cannot set or strip it. What each side adds on top:
- **Instar** keeps its own extra requirements in `CredentialShareGate`: a trust level of at least `trusted`, and accepting `identity-verified` (a replicated pairing).
- **`threadline-mcp`** adds the receiving rule ("ingestion"): a credential from a sender that is not `mutual-verified`, or one that arrived in plaintext, never reaches the model. It also adds replay checks: a persistent ledger of (sender, messageId) seen, and a freshness window (a credential older than 1 hour, or dated more than 10 minutes in the future, is refused).

What the sender guarantees is its own side only: it encrypts to the verified key. The receiver's rule is the receiver's own gate. A sender cannot verify that the receiver applies it.

**D8. A changed key is a new agent, never an automatic re-pin.** A Threadline fingerprint is the first 16 bytes of the identity public key. A pin stores the full 32-byte key and is always compared in full, so two keys that share a 16-byte prefix (about 2^64 work for a pair an attacker generates itself) cannot be confused. A key that is small-order or not canonical is refused when pinning. A pin is never swapped: a `mutual-verified` pin refuses a different key outright, and `markInviteVerified` refuses one while any non-failed pin exists. When an agent rotates or recovers its identity (Instar `identity-recovery`), it has a new key, and to us it is an unpaired stranger: nothing carries over, sends and credentials to it follow the unpinned rules, and the only way to trust it is a fresh pairing. The old pin stays as it was, bound to the old key, and keeps refusing anything not signed by that key. `threadline_pair_status` flags an unpinned agent that claims the display name of a pinned one (after NFKC): "claims the name of <peer>, different key, not paired". So the person sees a rotation rather than a stranger with a familiar name. Removing the old pin is an explicit person act: `threadline_pair_forget` asks the person through elicitation (Keep / Unpair), because forgetting a pin removes the always-encrypt rule and the credential right for that agent; the agent cannot do it alone. Forget removes the pin and its `encryptedSeen` mark. It does not revoke an open invite; `threadline_pair_cancel` does that. Instar's one-identity-across-machines keeps one key across an agent's machines, so it does not trigger this.

**D9. Instar always encrypts ordinary chat to an invite-paired, mutual-verified peer, using the pinned key.**
- **The rule.** Today Instar 1.3.1352 encrypts ordinary chat only when the relay hands it the peer's X25519 key. After this step, for a peer that is `mutual-verified` through an invite pairing, Instar encrypts every ordinary message to the X25519 key derived from the PINNED identity key, whatever the relay offers, and never sends that peer plaintext. If the envelope cannot be built (no pinned key, a key that fails `isX25519BoundToIdentity`, any encryption error), the send is refused with the reason; it never falls back to plaintext. If the peer cannot decrypt, the peer refuses (D6); Instar shows a failed delivery and does not retry, in plaintext or otherwise. In `enforce` this fails closed on an unresolvable pinned peer: a trust lookup that errors, a resolver that throws, or a pinned key that is not the recipient's refuses the send (relay-send answers 502, nothing is recorded as sent), on every send path that can carry ordinary chat, including `sendPlaintext` (Echo, review of #2231).
- **Pairing method.** Instar profiles gain an explicit `pairingMethod: 'invite' | 'sas' | 'inherited'`. Existing `mutual-verified` profiles are backfilled on load: `sasFingerprint` present means `sas`, absent means `invite`. The backfill is idempotent and tested. D9 applies only to `invite`. Peers paired by the older SAS method keep the previous rule, because they may run a version before 1.3.1345, which cannot decrypt to a pinned key without a cached one. Telling the two apart by "`sasFingerprint` is absent" alone would misread an inherited profile, which also has no `sasFingerprint`, as an invite pairing.
- **Other machines (the facts as built).** An Instar agent can run on several machines, but only the machine holding the relay connection builds and sends envelopes; the others hand their sends to it (`relayForward`). Replicating a pairing to other machines is off by default (`multiMachine.stateSync.threadlinePairing.enabled`), and even when it is on, nothing calls `inheritReplicatedVerification` on merge, so another machine holds no pin for the peer. So after a failover, the new relay holder treats the peer as unpaired and sends plaintext. To a `threadline-mcp` peer that has already seen encrypted chat (D6), that plaintext is refused. That is a real loss of chat, not "safe".
- **What this spec decides.** D9 ships behind a switch (§7 step 5). On an agent with more than one machine, the switch can be set to `enforce` only after step 5b has shipped: inheritance wired on merge, and `pairingMethod` added as a sixth replicated field, so every machine that can become the relay holder has the same pin and applies D9 with it. On those other machines the pairing arrives as `identity-verified` with `pairingMethod: 'invite'`, and D9 applies to it exactly as to a local `mutual-verified` invite pairing. Until then, a multi-machine agent runs D9 in `watch` (it logs what it would have refused and changes nothing). **Justin 2026-10-20: ships on.** Step 5b has shipped, so the default is `enforce` on every agent, multi-machine ones included. Pairing replication itself stays off by default (it feeds the credential gate, and turning it on for existing agents would overwrite a value written into their config), so on a multi-machine agent without it the machine that made the pairing always encrypts and another machine that takes the relay keeps the older rule; that agent gets a startup warning and a degradation report naming the fix (turn pairing replication on). This is no weaker than `watch`, which changed no send on any machine.

**D10. The shared package is published on its own to npm as `@sagemindai/threadline-core`, from `main` only.** (Scoped so the name cannot be taken by someone else before the first publish, Echo's review SEC-13; Justin's decision, topic 61599, 2026-10-16. The `@sagemindai` scope is the npm organisation `sagemindai`, created 2026-10-16.) It is public and MIT, published by `.github/workflows/publish-threadline-core.yml`; `threadline-mcp` publishes the same way:
- **Trigger:** a push to `main` that touches the package, or a manual `workflow_dispatch`; jobs run only when `github.ref` is `refs/heads/main`. Never `pull_request`. Commits whose message contains `[skip ci]` are skipped.
- **Two jobs:** `test` builds and runs the package tests and the protocol suite with no secrets (read-only token, no persisted credentials, install scripts disabled); `publish` runs only after it passes, and checks the packed tarball installs and imports in a clean consumer.
- **Who can cause a publish:** the `publish` job deploys to the GitHub Environment `npm-publish`, which only `main` may deploy to, so only someone who can land a commit on `main` can publish; a branch's edited copy of the workflow cannot reach what the environment holds. Merging a PR that touches the package to `main` is the operator boundary for a publish, including the first.
- **Credentials:** npm trusted publishing (GitHub OIDC, `id-token: write`, npm 11.5.1 or later), so no long-lived npm token is needed once the package's trusted publisher (this repository, this workflow, environment `npm-publish`, with "npm publish" allowed) is set on npmjs.com. A trusted publisher can only be set on a package that exists, so the first publish of a new package uses `NPM_TOKEN`, held in the `npm-publish` environment: a granular token limited to the `@sagemindai` scope, with a short expiry. After the first publish, the trusted publisher is set on the package and that environment token is deleted. The repository-level `NPM_TOKEN` stays: Instar's own release (`publish.yml`) and the `npm deprecate` rollback (`deprecate-version.yml`) still read it, and moving those to trusted publishing is a separate change. The npm account is held by Dawn on Justin's behalf (topic 61599), with its 2FA in Justin's vault. `RELEASE_TOKEN` is used only to push the version-bump commit, and belongs in the environment rather than the repository.
- **Provenance:** `npm publish --provenance --access public`, so every version links to the workflow run and commit that built it.
- **Version:** if `package.json` equals the published version the job bumps the patch and commits the bump with `[skip ci]`; otherwise it publishes `package.json`'s version. A concurrency group stops two runs bumping the same version.
- **Pinning:** `threadline-mcp` and Instar depend on an exact version of the shared package, so one bad publish cannot reach every user.
- **Order:** two PRs. Core merges and publishes first; then a second PR bumps `threadline-mcp`'s exact pin and regenerates its lockfile against the registry. A failed `threadline-mcp` publish is not retried automatically; it is re-run by hand after the cause is fixed.
- **Rollback:** a bad version is deprecated on npm (`npm deprecate`) and a fixed patch is published; nothing is unpublished. A bad `threadline-mcp` 0.5.x that paired wrongly is recovered with `threadline_pair_forget`, then a fresh pairing.

**D11. Multi-machine posture.**
- **`threadline-mcp`** has no replication, so each state surface is declared:
  - `identity.json` (the private key): machine-local, because the key is a physical credential.
  - `pinned-keys.json`, `pairing-invites.json`, `seen-messages.jsonl`, `pairing-audit.jsonl`: machine-local. That is an operator-ratified exception under D0: replicating pairing across machines is Instar's streamlining layer, not a fundamental. Copying `~/.threadline` to a second host is unsupported, because one identity on two hosts means the relay keeps only one connection.
  - `pair.sock`: machine-local, because a Unix socket exists on one host only.
- **Instar:**
  - The pairing method replicates as the sixth field (D9, step 5b). On receive, an unknown value is treated as absent, a missing value means `sas` (the safe rule for delivery), and the merge returns `invite` if any honoured view with the same single pinned key says `invite`, because the method describes the peer, not the machine. An older machine ignores the field (the record validator drops unknown fields), and must not re-replicate the record without it; step 5b's tests cover a mixed-version pair. On upgrade, local invite-paired profiles re-send their records with a new timestamp. Inheritance never overrides a pairing made on this machine: a local `mutual-verified`, `verification-failed` or `invite-accepted` profile is left alone, a local SAS pairing is not upgraded from a replicated record, and a known `invite` is never downgraded.
  - **Unpairing reaches every machine.** When the person unpairs, or a pairing is demoted, on one machine, the revoke record names the pinned key, and every other machine removes the pairing it inherited for that key, so it stops encrypting to it and stops sending it credentials. A revoke only removes an inherited (`identity-verified`) profile, never a pairing made on that machine, and never a profile pinned to a different key. A newer pairing record after the revoke wins and is inherited again. A revoke and a record with no order between them leave the peer revoked until a newer record settles it. A revoke from an older machine that names no key applies to the fingerprint.
  - **Watch mode for replication.** The existing `multiMachine.stateSync.threadlinePairing` switch has a `dryRun` field that sending, inheriting and revoking do not read yet; until they do, the switch is on or off, and it is off by default.
  - The invite store stays machine-local. If the relay moves between an invite and its accept, the accept reaches a holder with no such invite and is refused as unknown; the inviter's person makes a new invite. Status says so.
  - The `encryptedSeen` mark, when Instar adopts it (step 6), is **unified** across machines: set once, merged as a union keeping the earliest time, removed only when the person unpairs. A mark kept on one machine would let the relay downgrade a peer by aiming at whichever machine takes over.

**D12. Install without a terminal, for the most popular apps.** (Justin, 2026-10-19: focus on the most popular, do not spend too long on compatibility.) The five covered are Claude Code, Claude Desktop, Cursor, VS Code and the ChatGPT desktop app. Which of them shows dialogs (D3) and which offers each install route are claims that the step-4 walkthrough confirms; at runtime the capability check (D5) decides, not this list. Every route except the Claude Desktop extension runs `npx`, so it needs Node.js; the README says so first and points to the installer from nodejs.org (a download, not a terminal). Install links pin an exact version (`npx -y threadline-mcp@<version>`), for the same reason as D10's exact pins: one bad publish should not reach every user. The README carries one section per app:
- **Claude Desktop:** a one-click extension file (`.mcpb`) published with each release; opening it shows Claude Desktop's install dialog, which asks for the agent's name and its person's name (`user_config`). Approval uses the local page (D5).
- **Cursor:** an "Add to Cursor" link (`cursor://anysphere.cursor-deeplink/mcp/install?name=threadline&config=<base64 JSON>`). Approval through Cursor's own dialog.
- **VS Code:** an "Add to VS Code" link (`vscode:mcp/install?<url-encoded JSON>`). Approval through VS Code's dialog.
- **ChatGPT desktop app:** Settings, MCP servers, Add server, choose STDIO, and fill in the command `npx -y threadline-mcp` and the two names. That is a form, not a terminal. Approval through its dialog.
- **Claude Code** (no one-click install exists): the person asks their agent "add Threadline", and the agent adds it itself; the person only answers Claude Code's own permission prompt. Approval through Claude Code's dialog.
- Any other app: the person asks their agent to add it to the app's settings. Not tested by us.
- **Out of scope for v1:** ChatGPT on the web, which accepts only servers hosted online; a hosted Threadline server would hold the agent's keys away from its person, which this design does not do.

**D13. The Instar experience comes first.** (Justin, 2026-10-19: "for us we want to make sure the Instar experience is extremely seamless.") Between two Instar agents nothing in this spec adds a step: the inviter's person sends one message, the other person forwards it to their agent's Telegram and taps Approve, the inviter's person taps Finish (a2a-pairing-invite-link §3). Between an Instar agent and an app running threadline-mcp, the invite Instar sends uses the same host-neutral words as core (D4), so it says where to paste it in either kind of app; step 3 makes Instar use core's text and code so the two can never drift. Step 5 (always encrypt to an invite-paired agent) and 5b (pairings follow an agent across its machines) are part of seamlessness: chat should simply be private after pairing, on whichever of the agent's machines answers, with nothing for the person to do.

**D14. One tap between two agents with the same person, through Telegram (Instar streamlining, D0/D13).** (Echo, round 2, answering §8 Q1.) There is no signal today that two Instar agents share an operator that each can verify of the other: each agent verifies only its own operator, and anything one agent says about its operator is only a claim to the other. So matching operator ids is never used as authority. Instead:
- Agent A sends the invite only to its own verified operator, as a Telegram deep link to agent B's bot (`t.me/<B_bot>?start=<invite>`), in a direct message, never to someone who would forward it.
- The operator taps it. B's bot receives `/start <invite>` from an authenticated sender and accepts only if that sender is B's own verified operator (§6.1 of the invite spec). Otherwise B falls back to today's flow (Approve plus Finish).
- The secret travelled only A → operator → B, never over the relay, so when A receives an accept that proves possession of it, A knows its own operator tapped, and finishes without asking. Result: one tap, no forward, no Finish tap. It assumes the operator's Telegram account is not compromised, which today's flow already assumes.
- **Constraint to settle before building:** Telegram's start payload is at most 64 characters from `[A-Za-z0-9_-]`, and a `tlinv1:` token is about 434. A compact invite (invite id, inviter fingerprint and secret only, 40 bytes or 54 characters, the inviter's full key fetched from the relay card) is proposed. Checked against the code (2026-10-19): it is NOT safe as the protocol stands. A verifies the accept's tag against its own real key, so a swapped key fails there; but B verifies the Finish only by signature against the key B pinned (`handleFinish`), with no proof of the secret. With today's full invite B pins the key that came through people, so that is fine. With a compact invite B would pin the key the relay supplied, and a dishonest relay could supply its own key, read the plaintext accept, and sign a Finish itself: B would be paired with the relay. So the compact invite requires two protocol additions: (1) the Finish carries a tag under the invite's MAC key over the finish transcript, which B requires whenever the inviter key came from the relay (an older peer ignores the extra field; B treats its absence as a refusal only for compact invites); (2) the compact form carries the expiry, which B needs to check the Finish (as 4-byte unix seconds: 44 bytes, 59 characters, leaving 5 characters under the 64 limit; Echo, 2026-10-19). A 128-bit secret is ample against guessing within an invite's lifetime. Instar-only; nothing in threadline-mcp depends on it.

## 3. The protocol

Unchanged from `a2a-pairing-invite-link.md` §4: invite fields, 1 h default and 24 h max expiry, binding by default for a known peer, the HMAC-and-signature accept, the signed finish and ack (the finish names the approved invite's id and expiry and is accepted once), the second-accept response (one alarm and one demotion per invite), and K kept only until `exp`. This spec moves code. It does not change the protocol.

**What the envelope gives, stated plainly.** Confidentiality and sender authentication: an ephemeral X25519 key per message, combined with the recipient's long-term X25519 key (derived from its identity), HKDF, XChaCha20-Poly1305, and an Ed25519 signature over the canonical envelope. It does **not** give forward secrecy against the recipient's key: whoever later obtains a recipient's identity key can decrypt every past message recorded for it, credentials included. The old "forward secrecy" comment in `MessageEncryptor` is corrected, and core's README and the tool text state the real property. Replay is not stopped by the envelope itself; D7's ledger and freshness window do that for credentials.

**Why not Noise, age or libsodium sealed boxes.** The primitives are standard and come from audited libraries (`@noble/ciphers` for XChaCha20-Poly1305, Node's crypto for Ed25519 and X25519). The construction is Instar's existing envelope, because D2 requires talking to Instar agents already deployed, and moving to a vetted handshake would need both sides to change at the same time. The invite protocol on top had three review rounds. A Noise-based envelope with forward secrecy is the natural next protocol version (§9); it needs a capability flag so old and new agents can still talk.

## 4. `threadline-mcp` tools added

| Tool | Who | Operator act? | Notes |
|---|---|---|---|
| `threadline_pair_invite` | inviter | no | `{ for?: <known contact or fingerprint>, ttlMinutes? }` (default 60, max 1440). Returns the invite message for the person to send privately. The inviter's own secret is in the inviter agent's context, as in Instar's MCP `invite` action. |
| `threadline_pair_open` | recipient | yes (elicitation, or the local page, D5) | Elicits the pasted invite (D4), checks it, then elicits Decline / Approve (D3). On Approve, pins the inviter as `invite-accepted` and sends the accept. Returns only the invite id. Its description tells the agent what to do if an invite appears in chat: never repeat it, call `pair_open`, and tell the person to ask for a fresh invite. |
| `threadline_pair_finish` | inviter | yes (elicitation, or the local page) | Lists accepts waiting; elicits Not them / Finish for one. |
| `threadline_pair_status` | either | no | Pairings, open invites, waiting decisions, leak alarms, refused plaintext, store problems, the audit file's path. Never the secret or K. |
| `threadline_pair_cancel` | inviter | no | Revokes an open invite. |
| `threadline_pair_forget` | either | yes (elicitation, or the local page) | Unpairs from an agent after the person confirms (D8). |

Inbound invite ops are handled by the server's relay listener, never surfaced to the model as messages. Events (accept arrived, paired, leak alarm) are recorded in the state dir and reported by `threadline_pair_status` and in `threadline_inbox` as system lines, not as agent messages. `waitForReply` results carry the same trust labels as the inbox. Message history stores a credential as `[credential, N bytes]`, never its text.

## 5. Storage (state dir, all `0600`)

`identity.json` (existing), `pairing-invites.json` (the store from Instar, same semantics), `pinned-keys.json` (fp → full identity key, state, verifiedAt, pairingId, via, and the D6 `encryptedSeen` time), `threadline/seen-messages.jsonl` (the D7 replay ledger), `threadline/owner.lock`, and `threadline/pairing-audit.jsonl` (pairing events, refusals, credential sends and receipts; bounded and rotated at 1 MB; never a secret or K). The existing contacts file keeps its `trust` label, but it no longer counts for anything security-relevant. Only `pinned-keys.json` does.

- **Several servers on one state dir.** Every Claude Code session, and any other host, starts its own `threadline-mcp` on the same state dir and identity. One of them owns pairing: it holds `threadline/owner.lock` (its pid, created exclusively; a lock whose pid is not running, or whose pid started after the lock was written, is stale). A stale lock is retired by renaming it to a unique name and re-reading it, never by deleting a lock that may have just been taken by someone else; the owner re-confirms the lock still names it before every credential send and pairing-state write; and inbound pairing messages try to take ownership first, so an accept or Finish is not refused just because no tool call has happened since the owner quit (Echo, #2215). Only the owner pairs, sends credentials, serves the local approval page (D5) and writes pairing state. The others refuse pairing and credentials, and re-read pins from disk for every message, so a forget or demotion in the owner takes effect everywhere. The owner lock records the owning app's name (from MCP initialize), so the refusal says in plain words "Pairing is open in <app>. Finish it there, or close that app and try again", never a process id (R2-2). Ownership stays for the owner's lifetime rather than per operation: inbound pairing replies arrive on the owner's relay connection, so moving ownership mid-pairing would strand them. All of them share one relay identity; the relay keeps one connection per identity, so a non-owner can lose its connection, and its sends then fail with that reason rather than going elsewhere.
- **A store that cannot be read.** A missing file starts empty. A file that is not valid JSON is moved aside (`<file>.unreadable-<time>`), reported in status and in the inbox as needing attention, and the store starts empty; nothing is deleted. For `pinned-keys.json` that means its peers are unpaired until it is repaired: credentials to them are refused, and while it is set aside, plaintext from any sender is labelled unverified. Any other read error (permissions, I/O) stops the server from starting, because starting empty would let the next save overwrite pins that are still on disk.
- **Identity.** If `identity.json` cannot be parsed, the server refuses to start and leaves the file untouched; it never makes a new identity over it.

## 6. Threats (what changes outside Instar)

- **The model is not the operator.** Elicitation is the boundary: the agent can call `threadline_pair_open`, but only the host can answer it, and in Claude Code the host asks the person. It is host-cooperative (D3); on the local approval page (D5) an agent that can fetch local URLs could open the page, which is said plainly. Opening an invite there still needs the invite itself.
- **The invite in context.** The recipient side keeps it out (D4). The inviter side cannot (the person needs the text). Single use, a short expiry and binding limit the damage, and so does the second-accept alarm.
- **Downgrade and injection by the relay.** We never send plaintext to a pinned peer (D6, D9), and plaintext that arrives under a pinned fingerprint is never attributed to that peer, and is refused once the peer has spoken encrypted (D6). Before pairing there is no encryption, and the tool text says so.
- **Replay by the relay.** A captured credential cannot be delivered twice (the ledger) or late (the freshness window) (D7). Ordinary chat has the ledger, not the window, because a peer may have been offline.
- **Key rotation and look-alikes.** A new key is a new agent (D8). The risk is a person re-pairing with a stranger who borrowed a familiar name; status says "claims the name of <peer>, different key", and the pairing screens say names are claimed, not checked.
- **Software running as the same user.** It can edit the state files or open the local approval page. That is out of scope and said plainly (D5, D6).
- **Mixed versions.** An old `threadline-mcp` cannot pair. It only sees plaintext from agents that have no pinned key for it, which is today's behaviour.
