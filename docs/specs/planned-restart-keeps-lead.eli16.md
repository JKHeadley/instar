# A planned restart keeps the lead — Plain-English Overview

> The one-line version: from the moment the machine in charge is asked to restart, every one of its routine "I'm still here" renewals promises a few minutes instead of one, so the promise outlives the reboot and nobody else grabs the seat while it is coming back; on return it keeps asking the neighbours until one confirms nothing changed, and then carries on in charge.

## The problem in one breath

An Instar agent that runs on several machines has one machine "in charge" at a time: it reads messages, runs scheduled jobs, sends replies and runs the pool's pre-merge test run (the "merge line"). Being in charge is a lease that lasts 60 seconds and must be renewed constantly. When the machine in charge restarts its own server, nobody renews that lease while the process is down. A restart takes one to four minutes, so the lease runs out halfway through, another machine takes over, and when the restarted machine comes back it correctly declines to grab the lead from a live holder. Ten minutes later the system hands the lead back to the preferred machine, which restarts again to pick up its new duties, and the whole thing repeats. On 21 November 2026 the Echo pool spent an hour and a half in this loop and its merge line never ran.

## What already exists

- **The lease** — a signed, numbered ticket that says which machine is in charge and until when. Only one machine can hold it at a time; a new holder gets a higher number. The holder re-signs it every 30 seconds with a new "until" time.
- **Boot claim safety** (shipped the day before the incident) — a machine that has just started asks the other machines before taking the lead, and never takes it from a live holder. This is the right rule and stays.
- **The role-change restart** — a machine that gains or loses the lead restarts its server, because the job scheduler is only built at start-up. A later piece of work removes this restart, but update restarts and operator-requested restarts will always exist.
- **The hand-back** — if the preferred machine is healthy for ten minutes, the current holder hands the lead back to it.
- **The restart request** — every restart in Instar starts as a small file asking for one. A supervisor process notices the file, deletes it, stops the server (it waits only three seconds before forcing it) and starts the new one.

## What this adds

The moment any part of the server asks for a restart, and before the request file even becomes visible to the supervisor, the machine's routine renewals change in one way: instead of promising "mine for the next 60 seconds" they promise "mine for the next few minutes" (just under four minutes on Echo until the machine has measured its own reboots, then its slowest recent reboot plus a safety margin), they are made every ten seconds instead of every thirty (on the usual direct machine-to-machine channel), and each one is also saved to disk. The three kinds of restart that cause nearly every one on the machine in charge (a role change, an update, a restart asked for through the API) go further: they wait until a neighbour has confirmed the longer promise, or eight seconds, whichever comes first, before they make the request visible at all. When the machine starts again it finds its own unexpired promise on disk, keeps asking the others whether anything has changed (for up to two minutes, longer only while a neighbour is itself still booting), and once a neighbour confirms nothing has, it renews and carries on in charge. The other machines need nothing new to understand that; it is an ordinary renewal with a later time. Whenever the restart then happens, even if the server is killed abruptly, the last promise the others saw already covers the reboot. No new lease number, no tug of war, no second restart.

- The "someone asked for a restart" state is latched: once it begins it ends only when the request is withdrawn, when no part of the system would still act on it (the same rule the supervisor itself uses, which can keep a request alive for up to four hours while a test run holds it), or when the server exits. The supervisor deleting the file just before it stops the server cannot switch the longer promise off at the last second.
- A small signed note on the machine holds the latest long promise and why the restart was asked for; it is bookkeeping and measurement, not permission. On a plain file store the promise is also saved in the lease file, so losing the note costs nothing; on a shared git store the note is the only copy, and losing it costs the lead once, exactly as today.
- The longer promise is never longer than the time after which the other machines would treat a silent holder as gone (about five minutes fifty seconds on Echo), and never longer than ten minutes anywhere. An operator can set a fixed length, still under those limits.
- A machine that comes back to find every other machine dead or dark does not sit and wait: once the others have been silent for the same three probes over forty-five seconds that boot claim safety already uses to let a machine take the lead, it simply keeps its own seat on that same evidence — no new permission, and no second restart at boot to pick up its duties. What happens to a holder whose neighbours stay dark after that is unchanged from today.
- While the machine is waiting for a neighbour's answer it is not reading messages, so a planned restart now costs its reboot plus that wait (two minutes at most on a normal pool, longer only while a neighbour is itself still booting, and for the one reboot that follows a late confirmation, which waits out the whole promise). That is the price of never acting on the local file alone; the machine's own health reading shows the pending state while it lasts.
- A restart that was not asked for (a crash, a power cut, a hand-typed kill or a lifeline-level kickstart) changes nothing and behaves exactly as today, so a machine coming back from a crash still cannot grab the lead.

## The safeguards

**Never two machines in charge.** On return, the machine does not act as holder on the strength of its own file: until a neighbour has answered and the renewal has actually been confirmed by another machine, it reports itself as standby and sends nothing. If any neighbour shows a newer lease number or a live holder that is not this machine, it adopts that and steps aside, exactly as boot claim safety already does. This rule is tied to what is on disk, not to the switch, so turning the feature off cannot reopen the gap for a reboot that still has a long promise saved. During a genuine network split the pool keeps the behaviour it already accepted: both sides may answer until the split heals, and then the higher number wins.

**Never a pool stuck forever.** If the machine dies during its restart and never comes back, the longer promise simply runs out and the normal takeover happens.

**Nothing rides on the shutdown.** The first draft did its work as the server exited. Review against the code showed the supervisor removes the request file before stopping the server and kills it three seconds later, so an exit-time step would rarely run. This design does everything while the server is healthy; the exit only stamps a time into the note if it gets the chance.

**No new way in.** Nothing new travels between machines: a later "until" time on a renewal is something a holder could already send, and the one addition to the older dialling path (a request number the answering machine signs) uses fields that already exist. The note stays on the machine that wrote it, signed with that machine's own key, so a damaged or foreign note is ignored. The machine's reboot measurements are unsigned, so they are clamped when read and can never push the promise past the limits above.

**Same rule for every machine.** Whether the restarting holder is the preferred machine or not makes no difference to what it does or to what the others do.

**The cost, named.** A restart request can wait hours when a test run holds it. For all that time the holder's promise is a few minutes instead of one, so if it *crashed* in that period the others would take correspondingly longer to step in, and the pool's five-minute "someone answers" aim would be missed by that much. That was judged acceptable for the pending state only: the machine has been asked to restart, the period is bounded by the four hours a held request can wait, and a promise short enough to keep the five-minute aim could not cover the Studio's measured reboot and would bring the loop back. An operator's "restart now" through the API also answers up to eight seconds later than before, because the machine waits for a neighbour to confirm the longer promise first.

## What ships when

One pull request: the shared "a restart was requested" signal that every restart writer raises before the file appears, the pending-restart renewal with its faster cadence and disk copy, the boot-time rule and its fence in the lease coordinator, the signed note and the boot-time measurement, tests at all three levels including one that replays the night's loop and shows it gone, four one-sentence amendments to the parent takeover-ready-pool document and one to the role-restart document, registry rows and backup exclusions for the two new state files, a field in the machine's health reading showing the pending state, and five gaps in the foundations it builds around, each filed and tracked as a card under the post-mortem project (the supervisor's three-second kill, two processes racing to act on one restart request, the role-restart condition that a later change widened, a restart within a minute of taking the lead being held on the local file alone, and a returning machine with an old higher-numbered ticket being allowed to take over a live holder). It is switched on for development agents (Echo) and stays dark for everyone else until it has earned its way up the usual ladder. Once it is live on the Studio, the night's temporary setting that turned boot claim safety off there can be removed; the steps and the check that closes it are recorded on that item.

## What you actually need to decide

Nothing beyond the agent's own approval: this changes no constitution and no protected path. The question it answers is "should a machine that restarts on purpose keep the lead through its reboot, within a bounded window, while still never taking the lead from a live holder?" — and the answer built here is yes.
