# Codex sessions that stop, stall, or ignore a message

What looks like one problem from Telegram is actually several different problems wearing the same costume. A Codex screen can stop changing because it is safely waiting for GitHub, because one of Codex’s own helper processes is sitting open, because a message was pasted into the composer but Enter never took, because the turn finished normally, or because the session really died. Today some of Echo’s recovery code treats those states too similarly.

The clearest live example is the watchdog. It is meant to stop a shell command that is genuinely wedged. Earlier it interrupted a healthy release command while that command waited for GitHub; that was fixed. But afterward the same watchdog targeted `codex-code-mode-host`, which is part of Codex itself, not a command Echo asked to run. It interrupted two such hosts; one session recovered and the other died. The first part of this proposal gives framework-owned helper processes a narrow safety floor: if Instar can prove a process is Codex infrastructure inside a Codex session, the command watchdog cannot kill it. Real user commands still go through the existing stuck-command judgment.

The second problem is message delivery. Instar currently knows that it sent paste and Enter keystrokes into tmux. That is not the same as knowing Codex accepted the message. Echo’s logs show several messages where all four recovery keypresses were sent and the text still remained at the prompt. The proposal turns delivery into a durable state machine. Before any normal send or recovery key touches tmux, Instar records “armed,” then “started”; a crash in between can become honest “unknown” instead of blindly resending. “Dispatched” means only that tmux received keys. “Composer cleared” means the complete, bounded input box no longer matches the delivery, which still does not prove consumption. A brand-new Codex session has one chicken-and-egg case: its first message creates the transcript that will prove the message. Instar therefore permits only the exact saved startup message with a durable “genuinely fresh Codex spawn” marker to be sent through the same journal; resumed, recovered, and older unmarked records fail closed. It keeps the saved copy on any refusal, reports recovery as failed rather than successful, and Codex’s own first-message hook binds the new transcript from its beginning as soon as the session identity exists. If an older live pane never established that identity, later messages do not create false failed-delivery records or retry forever: after a startup grace, Instar keeps the inbound message, clears the unusable resume pointer, and replaces the pane with a genuinely fresh bootstrap carrying recent history. Only a matching new transcript turn inside Codex’s explicit start/complete task boundary means “consumed,” and only a later assistant item in that same task means “responded.” Current Codex may omit a redundant turn label from individual messages; if it supplies that label, Instar requires a valid exact match and otherwise records “unknown.” Message bodies do not enter audit logs.

An exhausted delivery then uses one separate, durable recovery episode rather than reopening its original delivery history. Operator stop, machine ownership, work in that session, newer messages, and once-only replay checks are hard vetoes. One composite authority applies those rules and includes a lightweight independent supervisor that may veto but cannot bypass them. Recovery refreshes only the affected Codex session through Instar’s existing canonical refresh path; it never automatically restarts the whole server. The old session must be gone and the new composer positively empty before replay. A sequencing lease prevents a newer inbound and the older replay from crossing. If any newer message wins first, the older one is reported as stale/lost and can never replay. One delivery can be replayed once; three acted failures open a durable breaker until verified consumption or operator reset.

Machine transfer is also part of the implementation rather than an assumed capability. The source re-encrypts live replay data specifically for the target; the target stores it under its own key before acknowledging and taking ownership. An old owner cannot act after handoff, and incompatible targets refuse the move.

Normal completion stays normal. A Codex turn that finished and has no explicit unfinished obligation should remain idle. A turn with an explicit checklist or autonomous-run obligation can use the continuation systems that already exist. Silence by itself never grants permission to press keys, kill a process, or restart a session.

The practical outcome is that “Codex stalled” becomes diagnosable: framework helper protected, command actively running, inbound awaiting acceptance, recovery exhausted, older inbound superseded, turn normally complete, or session dead. Each state has one owner and one bounded recovery path. The release ships protection and observation first. Automatic restart/replay stays off until at least 24 hours and 50 observed deliveries are clean, followed by one explicit canary.
