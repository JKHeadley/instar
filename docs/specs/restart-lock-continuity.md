# An unplanned restart or a locked screen no longer silently costs a machine its work

## Problem (observed Nov 17 2026, causes verified in code on main 0ae5dc0b4)

Four of the ten items in the operator's Nov 17 report share one shape: a machine went away or stopped being useful and no one was told, so work was lost silently.

1. **Item 7. Sessions that end in an unplanned restart are never resumed and never listed.** The operator restarted the M5 by hand. Three topic sessions ended with it (promise follow-through, a document approval, a security build), and none came back until someone wrote to each topic.
   - Session records survive a power loss (`state/sessions/<id>.json`). What happens to them at boot depends on the machine's role:
     - On the awake machine, `SessionManager.purgeDeadSessions()` reaps each one as `boot-purge-dead` with `knownDead: true`; `knownDead` skips work-evidence stamping (`SessionManager.ts:3232-3235`), so the row carries `workEvidence: []`, and `considerEnqueue` refuses it (`insufficient-evidence`).
     - On a standby machine (the M5), the boot purge is refused as `not-lease-holder` (`SessionManager.ts:3035-3037`, `3101-3108`; the awake check is set at `server.ts:12434`, before the purge at `server.ts:13647`). The M5's own reap-log for the incident shows exactly this: `skipped` / `boot-purge-dead` / `skipped:not-lease-holder` rows at 2026-11-18T05:20:44Z for `echo-promise-follow-through`, `echo-instar-security` and `echo-doc-approvals`, then `exited` / `process-exited` rows about a minute later from `recordExited` (`server.ts:13330`), which never reaches the resume queue.
   - Either way nothing is queued, and the boot reconcile from the reap-log takes only `midWork` rows.
   - `PostRestartProof` has no sessions row. Its own `limits` text says the row "arrives with planned-restart resume entries", which Part D of the self-maintenance spec has not built.
2. **Item 8. A peer that goes away gives no reason.** The throughput session learned why the M5 was gone only from the operator.
   - A graceful shutdown broadcasts nothing (`server.ts:37487`; `MultiMachineCoordinator.stop()` only clears timers).
   - `PeerCapacity` / `MachineCapacity` carry no away reason. `machineLiveness.ts:21-22` says "offline" is never derived because it "needs positive evidence (a shutdown announcement or the sleep gate), which this layer does not have."
3. **Items 1 and 2. A locked screen goes unreported, and the canary stays failed after the unlock.**
   - A locked machine that is enrolled for unattended maintenance reads `locked` (`lockState.ts`), but nothing raises it. The throughput session found the M5 locked only after Local Verify runs failed.
   - After the unlock, the M5's wedge end-to-end test kept failing until a restart: a locked console had left the test's LaunchServices canary stopped, and unlocking did not clear it. That was the test, not a monitor, and PR 3378 (merged) hardened it. Machine maintenance, and with it the wedge monitor, is not enabled on the M5 (`GET /machine-maintenance` there answers `not enabled on this agent`, dev-agent gated); the lock reader is created only inside that gate (`server.ts:27801`), so today nothing on the M5 reads its own lock at all.
   - Where the wedge monitor does run, nothing reacts to a locked-to-unlocked transition (the only reaction is desktop access's `noteUnlocked`, scoped to its grants).

## What already exists (and is reused, not rebuilt)

- `PostRestartProof` (`src/monitoring/machineMaintenance/PostRestartProof.ts`): rows are blocks in `runChecks`; adding a row means a `ProofCheckName`, a reader in `ProofReaders`, and a block.
- `ResumeQueue` + `ResumeQueueDrainer`: phase 2's revival path (not used in phase 1).
- `AutonomousLivenessReconciler`: revives autonomous runs whose state file is active and whose topic has no live session. Dark on the fleet.
- The reap-log (`ReapLog.ts`) already records every `boot-purge-dead` session with its topic.
- `CommitmentTracker.getActiveByTopicId` and `commitmentQualifies` (`src/core/gapBCommitmentEvidence.ts`): the existing test for "this topic has live agent-driven work".
- The signed mesh RPC (`MeshRpc.ts`), the peer presence pull every 30 s, `classifyMachineEmptyState` (`poolEmptyState.ts`).
- `WedgeMonitor` (role `maintainer` samples), `durable.f1PassedThisBoot`, the lock reader passed to it as `lockState()`.
- `EnrolmentController` (machine enrolled `unattended` / `proving`).

## Design

### A. Every session a restart ended is listed, with the ones that had open work marked

Phase 1 accounts for every ended session and names the ones that had open work; it does not revive anything automatically. Automatic revival through the resume queue is phase 2 <!-- tracked: CMT-1940 -->: three review rounds kept finding new failure modes in choosing which sessions to revive and when (when the machine actually went down, what counts as recent work, once-per-boot replay), while the accounting itself became stable. Until phase 2, an ended session resumes on its topic's next message, as today. What phase 1 changes is that every ended session is recorded and readable on its own machine, including the M5, and when sessions with open work ended, the owner is told once per restart (A.5). Bringing them back is phase 2.

**A.1 Census before cleanup.** At server start, immediately before `purgeDeadSessions()` (`server.ts:13647`), and so before anything rewrites a dead session's record (the earlier startup steps, `retireBoundedSessionsWhenPrivacyOff` and `enrollExistingOriginSessions`, touch only sessions with a live tmux session; the exit monitor starts much later, `server.ts:36985`; the E2E test pins this order), each agent writes a census of the records that were alive at the previous shutdown: every record in `state/sessions/` with status `running` or `starting` and `startedAt` before this OS boot. The boot time (`bootAt`) is read by a new `readBootAt()` that calls the existing pure parser `parseBootTime` (`readings.ts:260`, whose signature and callers stay unchanged) on macOS and reads, per platform: macOS, the `sec=` field of `sysctl -n kern.boottime`; Linux, `btime` in `/proc/stat`; otherwise `Date.now() - os.uptime() * 1000` rounded to the minute. If none can be read, no census is written and `GET /sessions/boot-census` reads `unavailable: boot time unreadable`; a pid-based fallback is never used, since it would make a new census on every server restart. The census stores, per record: the session id, `tmuxSession`, `telegramTopicId`, `jobSlug` and `startedAt`. It is written once per boot to `state/boot-session-census/<bootAt>.json` (temp file then rename); readers pick the current boot's file by `bootAt` within the restart ledger's same-boot slack (`LEDGER_SAME_BOOT_MS`), so the census, the ledger and the proof agree on which boot is which, and the directory keeps the newest 30 files. If a census within `LEDGER_SAME_BOOT_MS` of this `bootAt` already exists (a server restart within the same OS boot), it is not rewritten, so a later server restart cannot replace the first census with an empty one. The census is identified by session id, never by tmux name, so a reused name cannot join the wrong record. It belongs to the session layer, which runs on every machine whether or not machine maintenance is enabled, and it changes no reaping authority.

**A.1a No shutdown snapshot is needed.** A graceful server stop does not end sessions (tmux outlives the server and the handler only stops monitoring, `server.ts:~37640`), so their records stay `running` and the boot census already sees them. A record left `running` by an earlier crash is not hidden and not excluded: every census entry is listed, with its age shown, and an entry that started before the *previous* boot (the `bootAt` of the newest older census file) is labelled `started before previous boot`; when no older census exists, an entry older than 7 days is instead labelled `old (previous boot unknown)`, which states only its age. Either way the restart's role in ending it is unconfirmed. Such entries stay in the open-work review.

**A.2 Accounting.** Each census entry is then classified from its own record, by session id, once that record has ended (status no longer `running` or `starting`, as written by the purge on the awake machine or by the exit monitor on a standby): `ended`. A census entry whose record still reads running 15 minutes after the server started, with no live tmux session of that name serving that record (a reused name opens a new record and `supersedeStaleLiveRecords` closes the old one as `completed`, `StateManager.ts:311-345`), is reported as `ended (unconfirmed)` rather than dropped. Each ended topic session is marked `open work` when its topic has at least one commitment that is `pending`, agent-driven (not `blockedOn` the user), local in origin, and not beacon-paused or beacon-suppressed. Sessions whose topic has an active autonomous state file are marked `autonomous (reconciler)`, since the `AutonomousLivenessReconciler` already revives those where it is enabled, or `autonomous (reconciler dark)` where it is not. A commitment tracker that cannot be read marks the session `unknown` with the reason, never `no open work`.

**A.3 Where it shows.** Each agent serves the result at a new read, `GET /sessions/boot-census`, which answers whether or not the resume queue is enabled and accepts `?since=<bootAt>` to list every retained census after a given boot (the newest 30 are kept; a reader whose cursor is older than the oldest kept file is told the gap), (`GET /sessions/resume-queue` answers 503 when the queue is off, `routes.ts:12143-12147`, so it is not used): the boot time and, per ended session, its topic, its mark (`open work`, `autonomous (reconciler)`, `autonomous (reconciler dark)`, none, `unknown`), and `topicCurrentlyActive` (a live session serves the topic now; this is a present reading, not a record of when it resumed). Entries labelled `started before previous boot` are shown with that label and their age. Where machine maintenance is enabled, `PostRestartProof` (which already runs after every OS boot, planned or not, recording an unclaimed boot as `unattributed`) gains a `sessions` row on the host maintainer, reading the census module directly (not the route), showing its own agent's listing and naming each co-resident agent with a pointer to that agent's status. The row reports and never fails the proof. The `limits` text drops "the sessions row arrives with planned-restart resume entries".

**A.4 One quiet notice, and one named reader.** The listing is a state anyone can read. Its named reader in phase 1 is the machine stewardship daily pass (the agent's `stewardship-snapshot` job), which reads every machine's `GET /sessions/boot-census?since=<its last-read bootAt>` each day, keeps that cursor per machine, and lists every ended `open work` session from every boot since its last pass, so two restarts between passes are both reviewed. 

**A.5 Notice.** Phase 1 has no self-heal step, so, as the parent spec's Part E does when no healing step can act, it notifies directly rather than waiting: 15 minutes after server start, if the census has at least one ended session marked `open work` or `autonomous (reconciler dark)` whose topic is not active again, each agent reports one degradation for that boot (`feature: boot-census.open-work-ended:<machineId>`, `internalOnly: false`), naming the topics. It is sent at most once per boot per agent. Phase 2 replaces it with the after-revival notice <!-- tracked: CMT-1940 -->.

### B. A machine that goes away gracefully says why, and peers show it

**B.1 The announcement.** A new mesh command `{ type: 'machine-away'; reason: 'machine-restart' | 'server-restart' | 'stopping'; expectedBackInSec?: number; serverStartedAt: string }`. It is the "graceful-shutdown announcement" that Part D's drain step 4 names, built here so Part D's scheduled restart reuses it rather than adding a second one; it is a membership "leave" message in the usual sense (as in SWIM or Serf), confirmed by the failed probe that follows. On graceful shutdown (the existing handler at `server.ts:37487`, before `coordinator.stop()`), the server sends it to every peer with a resolved URL through the existing signed mesh RPC, in parallel, with a 2 s total budget. The reason is read from what this machine itself recorded, never guessed:
- `machine-restart` is sent from the restart path itself, right after `claimRung` and before the privileged restart command runs, when networking is still up; the shutdown handler sends it too only if that earlier send did not complete. It is used only when a restart has actually been dispatched for the current episode and generation: a `claimRung` record for rung 1 or 2 in the host ledger, read lazily and only where `HostMaintenanceStore` exists (it is built inside the maintenance gate, `server.ts:27444-27447`); without it the answer is "no rung" (the Restart now path, merged; a reservation alone, which may still roll or abort, never counts); `expectedBackInSec = 1200`.
- `server-restart` when a restart request was recorded in the last 2 minutes: `readLastRestartRequest()` (`core/restartRequestAttribution.ts:121`), written by `recordRestartRequest` before the supervisor deletes `state/restart-requested.json` (`lifeline/ServerSupervisor.ts:1764-1777`), so it is still there when the child shuts down. The auto-updater and any requested restart restart only the server, not the host; `expectedBackInSec = 300`.
- `stopping` otherwise, including an operator's hand restart or shutdown of the whole Mac, which the server cannot tell apart from a stop; no expected time. The reading says "stopped on purpose, reason not recorded", which is still positive evidence that it left rather than crashed.

During a whole-OS shutdown, the system may stop networking or end the process before the send completes, so the announcement is best effort there; a machine that leaves without it reads exactly as today. A send that fails or times out is logged and does not delay shutdown beyond the budget.

**B.2 The receiver.** `machine-away` gets its own registered-peer case in the mesh permission check (whose default arm refuses unknown commands as `claim-unauthorized`, `MeshRpc.ts`) and to the `MeshCommand` union and its permission switch in `MeshRpc.ts`, with its handler beside the other mesh handlers (`server.ts` around 30605). An older peer refuses it, which the sender logs. The dispatcher handler verifies the mesh signature (as every mesh command does), checks that the sender is a known pool machine announcing about itself, and records `{ reason, announcedAt, expectedBackBy, serverStartedAt }`, where `announcedAt` is the receiver's own clock at receipt and `expectedBackBy = announcedAt + expectedBackInSec` (so sender clock skew never enters the reading), for that machine id in a new in-memory map on `MachinePoolRegistry`, which `getCapacity` merges into its result as `awayAnnounced` (the registry is in-memory and rebuilt from heartbeats, `MachinePoolRegistry.ts:209-213`, so there is no capacity save to persist with). A receiver restart drops the record and the reading reverts to today's, which matches the announcement being best effort. It is idempotent per departing instance: a repeat with the same `serverStartedAt` keeps the first receipt's `announcedAt` and `expectedBackBy`, so a late duplicate or a replay cannot extend the deadline, and an announcement whose `serverStartedAt` is older than the recorded one is ignored. The announcement carries the departing server's instance id: its process start time, which the presence reply also gains as a new optional field (`serverStartedAt` in `PeerCapacity`). The record is cleared when a presence pull is answered by a different instance (the replacement came up, even if every pull missed the downtime), or when the same instance is still answering 15 minutes after the announcement (the shutdown did not happen). A pull answered by the same instance during the shutdown does not clear it. Both clears are logged. The OS boot id is not used, because a `server-restart` keeps it. An older peer whose presence reply lacks `serverStartedAt` falls back to: cleared by a successful pull that follows a failed one.

**B.3 The reading.** `classifyMachineEmptyState` gains an input `awayAnnounced`. When it is set and the machine is not online, the kind is `offline` with the reason in words ("restarting the machine, expected back by 08:20", "restarting its server, expected back by 08:05", "stopped on purpose, reason not recorded"). This is the positive evidence `machineLiveness` names as missing. With no announcement, the reading is unchanged (`unreachable`, `stale` or `unknown`). Past `expectedBackBy` (on the receiver's clock) plus 10 minutes, the reading names it: "said it would be back by 08:20 and hasn't returned". `GET /pool` rows carry `awayAnnounced`, so any session that depends on a peer (Local Verify, the relay queue, placement) reads the reason from the pool.

**B.4 No chat notices.** This is a state anyone can read. The existing paths that already notice a dark peer keep their own wording.

### C. A locked verify or self-maintaining machine is reported once

**C.1 Report.** A machine is *watched for locks* when either:
- machine maintenance is enabled there and it is enrolled `unattended` or `proving`: the wedge monitor's samples are read, as below; or
- it runs Local Verify: `buildLocalVerifyService` returned a service (as coordinator or peer-only; the role is decided by the lease at runtime, not config; `localVerifyWiring.ts:142-147`), whether or not machine maintenance is enabled. A peer-only helper (the M5) and a coordinator on an unattended or proving machine report on the lock alone; a coordinator on an attended machine (one its owner uses, such as the Studio) reports only while Local Verify work is queued or a run fails during the lock, so locking it for lunch does not alert. Next to `wireLocalVerifyPeers` (`server.ts:26814`), a 5-minute interval reads the shared `MachineLockStateReader`. It looks the reader up lazily through `getActiveMachineLockStateReader()`, because Local Verify is wired (`server.ts:26762`) before the reader is created. Creating that reader moves out of the machine-maintenance gate (`server.ts:27444`, set at `:27801`) to plain startup. Its constructor spawns nothing; each read is two probes with 3 s timeouts, cached 5 s, and it reads `not-applicable` off macOS (`MachineLockStateReader.ts:95-115`). Machine maintenance keeps using the same instance. Side effect: `/machine-maintenance/lock-state` (and `?scope=pool`) now answers 200 instead of 503 on machines where machine maintenance is off (`routes.ts:16207-16230`). Its 503 text and any test asserting it are updated. The M5 is this case.

A machine marked do-not-maintain is never watched. A machine whose maintenance ownership is `shared` (the parent spec's rule for the M5 on Echo) is still watched: the lock watch only reads and reports, and takes no maintenance action on someone else's machine.

When a watched machine reads `locked` continuously for at least `machineMaintenance.lockReportAfterMs` since the first `locked` reading (the watch schedules one extra reading exactly at that deadline, so the report never waits for the next regular sample; if that reading comes back `unknown`, for example a probe timeout, it is re-read once at once before the hold restarts) (default 10 minutes; continuity as defined below), it reports one degradation through `DegradationReporter.report` (`feature: machine-lock.screen-locked:<machineId of the reporting agent>`, a name that does not imply machine maintenance runs there, with the machine nickname and the time the lock was first seen; `internalOnly: false`, so it reaches the owner through the degradation alert path: this is the one owner-facing notice this spec adds). It is reported once per lock episode per host, not per agent. The episode lives in one host-level file, `~/.instar/host-maintenance/lock-watch.json`, written through the existing host lock and atomic-write helpers (`tryTakeLockOnce`, `releaseLock`, `atomicWriteFileSync` with stale-lock reclaim, `hostSemaphoreCore.ts:217-318`) under its own lock file, `lock-watch.json.lock`, never `HostMaintenanceStore`'s `plan.json.lock`, so lock-watch ticks never contend with `reserve()`, holding `{ episodeId, bootAt, firstLockedAt, continuousLockedSince, lastLockedReadingAt, report: { state: 'none' | 'pending' | 'delivered', claimedAt, by } }`. `episodeId` and `firstLockedAt` are fixed when the episode opens and never change, so the dedupe key never moves; `continuousLockedSince` is the start of the current unbroken run of `locked` readings and is cleared (the episode is marked interrupted, not ended) by an `unknown` or `screensaver-or-display-sleep` reading from any agent. Every agent's `locked` reading updates `lastLockedReadingAt` under the lock; a `locked` reading that finds `now - lastLockedReadingAt` greater than the watch interval plus 60 s resets `continuousLockedSince` to now, because nobody was reading in between. Continuity is a property of the host record, not of any one agent: an agent that restarts mid-lock inherits the unbroken run its co-resident agents kept, and a real gap with no reader restarts the hold, so continuity never bridges missing or uncertain evidence and a restarting sibling cannot postpone the report. It is keyed by the host episode, never by an agent's `machineId` (each agent keeps its own identity, `MachineIdentity.ts:170-180`). The first agent whose reading crosses the hold claims the report under the lock (`report.state: 'pending'`, with its agent name and `machineId`), calls `DegradationReporter.report` (which persists the event before dispatching it), and then marks it `delivered`. Every other agent on the same OS login, and the same agent after a server restart during the lock, sees `delivered` and stays quiet. A claim still `pending` after 2 minutes was left by an agent that crashed between claiming and reporting; any agent reclaims it under the lock and reports, so a crash cannot silence the episode (at worst the owner sees the report twice). The dedupe key is `host:<episodeId>`. Deduplication covers agents under the same OS login only; an agent under another OS user cannot read the file and reports on its own. An episode ends on the first `unlocked` reading, which clears the file. `DegradationReporter` mutes repeat alerts for the same feature for an hour (`DegradationReporter.ts:161`), so a second lock episode within an hour of the first is recorded but not alerted; that is accepted, since the owner was told about that machine's lock within the hour. A lock state of `unknown` or `not-applicable` never reports. Known gap: a Mac set to require the password only after a delay reads `unknown` under Part A's lock table, so it is never reported; that is stated, not hidden. The report goes to the owner, who is the one who can unlock the machine at its console; for the M5, which the parent spec treats as a shared machine, the report only tells the owner and touches nothing on it. If both watchers apply on one machine, the Local Verify watch defers to the wedge monitor, so one episode gives one report.

**C.2 Unlock triggers a diagnostic re-sample (where the wedge monitor runs).** Item 2's M5 failure was the wedge end-to-end test, fixed by PR 3378; this part only adds diagnosis on machines where the wedge monitor runs. On the first `unlocked` reading after a `locked` episode, if `f1PassedThisBoot` is false, the monitor runs one extra sample at once instead of waiting for its next tick. The canary result of that sample, and of each sample in the next 30 minutes (three or more: the monitor samples every 10 minutes when nothing is positive and every 2 minutes once F1 fails, `WedgeMonitor.ts:16-17`), is written to `logs/machine-maintenance.jsonl` as `post-unlock-canary` with the `open` exit code and whether the canary process was found stopped. No other behaviour changes; leftover canaries are handled by the existing paths.

**C.3 The operator's choice is separate.** Whether the verify Macs may stay unlocked and sign in by themselves after a restart is asked of the operator separately (it needs the login password at the console or a profile setting, and is his physical-security call). This spec works either way.

## Signal vs authority

Nothing here blocks or starts anything. A adds a census and a listing. B adds a reading. C adds a report and one extra sample.

## Verify the State, Not Its Symbol

- **A.** Symbol: a census entry (a record alive at the previous shutdown) whose record has since ended. State claimed: the restart ended that session. Corroboration: the census is taken before any cleanup and keyed by session id; the end is read from the same record afterwards; a record still running with no live tmux after 15 minutes is shown as `ended (unconfirmed)`. Unmeasurable: an unreadable records directory yields no census and the status says so; an unreadable commitment tracker marks sessions `unknown`.
- **B.** Symbol: a signed `machine-away`. State claimed: the machine is shutting down for that reason. Corroboration: the presence pull stops answering, and the record clears when a different server instance answers (the replacement came up, even if every pull missed the downtime), or when the same instance is still answering 15 minutes after the announcement (the shutdown did not happen). Unmeasurable: no announcement means today's reading.
- **C.** Symbol: `lockState: locked` for 10 minutes. State claimed: the console is locked. Corroboration: Part A's reader already reads two independent sources and returns `unknown` on disagreement; only `locked` reports. Unmeasurable: `unknown` reports nothing.

## Self-Heal Before Notify fields (C.1)

- **class:** recoverable (a person must unlock; nothing is lost while locked).
- **self-heal step / remediation-actions:** none is possible from the agent; unlocking needs the console. The report is the only action. Self-heal for the canary is C.2's re-sample.
- **max-attempts:** one report per lock episode. **max-wall-clock:** not applicable. **backoff:** not applicable. **dedupe-key:** `host:<episodeId>`. **breaker:** not applicable (no repeated action).
- **max-notification-latency:** measured from the moment the screen locks: up to one sampling interval before the first `locked` reading (5 minutes for the Local Verify watch, up to 10 for the wedge monitor), plus the hold, because a reading is taken exactly at the hold deadline: `1200s` at the defaults, and at most the interval plus the configured hold for any value. With a configured hold (1 to 60 minutes) it is at most the interval plus the hold, given `locked` readings throughout.
- **continuity:** the hold runs from the first `locked` reading while every later reading is `locked`. An `unknown`, `screensaver-or-display-sleep` or `unlocked` reading restarts the hold; only `unlocked` ends the episode, so a lock interrupted by an unreadable sample still reports at most once.
- **audit-location:** `logs/machine-maintenance.jsonl` (lock episode start and end, report sent).

## Self-Heal Before Notify fields (A.5)

- **class:** recoverable (the work resumes on the topic's next message; nothing is lost).
- **self-heal step / remediation-actions:** none in phase 1; revival is phase 2's self-heal <!-- tracked: CMT-1940 -->. As in the parent spec's Part E, with no healing step to wait for, the notice goes directly.
- **max-attempts:** one report per boot per agent. **max-wall-clock / backoff / breaker:** not applicable (no repeated action). **dedupe-key:** `boot-census:<machineId>:<bootAt>`.
- **max-notification-latency:** `900s` after server start (the 15-minute settle that lets late exits be recorded and quick resumes happen).
- **audit-location:** the census file itself records the report.

## Multi-machine posture

- **A: machine-local.**
machine-local-justification: hardware-bound-resource impossible-because="the sessions a restart ended were tmux processes on that machine's own tmux server, and the session records and census that account for them live on that disk"

  The sessions a restart ended were tmux processes on that machine; the census and its listing are that machine's, read through that machine's own server (and from any machine through the pool's per-machine reads).
- **B: unified.** The announcement goes to every peer, and every peer's `GET /pool` shows it.
- **C: proxied.** Each machine's maintainer reads its own lock; `GET /machine-maintenance/lock-state?scope=pool` (existing) shows every machine's reading from any machine.

## Risks and answers

- **A misses a session or lists a wrong one.** The census is per session id and taken before cleanup; a session created after the boot is never in it; a server restart within the same boot never replaces the first census.
- **B is forged.** Mesh commands are signed per machine; the handler accepts only a known pool machine's own announcement about itself.
- **B delays shutdown.** A fixed 2 s budget, in parallel.
- **C reports a machine its owner is sitting at.** Only machines enrolled unattended or proving and machines that run Local Verify are watched, and only after 10 minutes of continuous `locked`. An attended machine that runs a Local Verify coordinator is watched and reported deliberately: while it is locked, verification on it can fail.
- **Mixed versions.** An older peer answers `machine-away` with an unknown-command error, which the sender logs; an older sender never sends it, and readings stay as today.
- **Rollback.** Revert the change. The census files are inert to old readers; `serverStartedAt` is an optional presence field old readers ignore, and the away map is in memory.

## Frontloaded Decisions

- **No automatic revival in phase 1.** Every ended session is listed and open work is marked; revival through the resume queue is phase 2 <!-- tracked: CMT-1940 -->, after the listing has run for a week on the dev agent.
- **The census changes no reaping authority;** it only records what was alive before cleanup and reads what cleanup and exits did.
- **The proof row reports and never fails the proof.**
- **Away reasons:** three values, each from a record the machine itself wrote (`machine-restart` 20 minutes, `server-restart` 5 minutes, `stopping` with no expected time).
- **Two owner-facing notices, each at most once:** A.5's one degradation per boot per agent when ended sessions with open work have not come back 15 minutes after start, and C's one degradation per lock episode per host. Both go through the existing degradation alert path; nothing else in this spec messages anyone.
- **Lock report scope:** machines enrolled unattended or proving (where machine maintenance runs), and every machine that runs Local Verify whether or not machine maintenance runs; locked continuously for 10 minutes.
- **Config keys:** `machineMaintenance.awayAnnounceBudgetMs` and `machineMaintenance.lockReportAfterMs` are read with code defaults and are not written into config files, so no config migration is needed.
- **Rollout:** ships live with no new flag.
