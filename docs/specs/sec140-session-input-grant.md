# Typing into a session from the phone needs Face ID once every few minutes

## Problem statement

The phone can type into any running session, press keys (Enter, y/n, Ctrl-C) and drop files into it. Today those three routes (`POST /sessions/:name/input`, `/key`, `/attachments` in `src/server/mobileSessionTerminalRoutes.ts`) accept a request signed by the phone's **device key** alone. The device key is a Secure Enclave key that signs without the person: it proves the phone, not the person holding it.

Sessions run with full access to the machine, so typing into one is running code on it. The same phone needs its **presence key** (Secure Enclave, signs only after Face ID, Touch ID or the passcode) to close or move a session, unlock the desktop or reveal the PIN, but not to type a command. Typing is the weakest path to the most power. Whoever can make the phone sign while it is unlocked (malware or a jailbreak on the phone, a lost phone that is unlocked or gets unlocked, a coerced unlock) can run commands on every machine the phone reaches: the machine it talks to directly, and through the relay hop every peer with `allowRemoteInput` on.

What already holds and is kept: per-request device signatures (±60 s, revocation checked), replay protection (durable for input and keys), owner-only routes, per-device and per-machine rate limits.

Not in scope: the console ticket (already presence-gated), session controls (already presence-gated), the Bearer-token API (an agent-token holder already has full control of a machine; see Relay hop).

Also not in scope, and recorded as its own security ledger item: owner chat from the phone (`POST /mobile/chat/...`) is accepted on the device key alone and reaches the same full-access agent. It differs from typing in kind: it arrives as a message the agent reads and judges, tagged as from the phone, with no raw terminal, shell escapes, y/n keys or Ctrl-C. So SEC-140 closes raw, judgment-free input into a session; it does not close every way a stolen device key can ask the agent to act.

## Proposed design

### 1. A session-input grant

- **Challenge:** `POST /mobile/sessions/input-grant/challenge` (device-signed, owner phone) returns a 32-byte challenge bound to that device and the signed host, single use, from the existing `BoundSecretStore` with its existing limits (60 seconds, 4 per device, 64 in total), which the console sign-in, desktop unlock and PIN reveal already use for the same kind of presence challenge. They are reused, not chosen here: one Face ID prompt completes in seconds, a fifth outstanding challenge from one phone means the app is looping, and a refused challenge costs only a retry, which the app does once.
- **Grant:** `POST /mobile/sessions/input-grant {challenge, signature}`. The phone signs `instar-session-input-grant-v1\n<deviceId>\n<host>\n<challenge>` with its presence key; the server checks it with `verifyPresenceSignature` against the device's enrolled presence key. On success it returns a random 32-byte grant and its expiry. Only the SHA-256 of the grant is kept, in memory, bound to the device id on this machine. The challenge is bound to the signed host; the grant is not, so a phone that moves between the home network name and the tunnel name keeps its grant (every typing request still carries the device signature, accepted only over local TLS on the machine's own names).
- **Use:** the three typing routes accept header `X-Instar-Session-Grant: <grant>`. A grant is valid only for the device that obtained it, on the machine that issued it. The header is outside the device signature but useless without that device's signature; it is never written to audit rows, logs or error reports. **Grants travel only over the machine's local secure transport** (`arrivedOverLocalTls`, which counts the tunnel's loopback hop): the grant routes require it, and a typing request carrying the header over any other connection is refused without being processed. A phone that types over another connection is treated as unable to obtain a grant there (the `blocked` outcome when one is required). Tests cover issuance and use on each supported path through production authentication.
- **Switch and routes:** the two grant routes exist when the machine's `available` setting is true (Multi-machine posture) and accept the same transports as the typing routes. They and `DELETE /mobile/sessions/input-grant` (ends every grant this device holds on this machine) are added to `DEVICE_ALLOWLIST` as owner-only, phone-only (no browser keys), with their own rate bucket. A test ends a grant through production authentication and shows the next send needs a new one.
- **What it proves:** that the person confirmed with Face ID (or the passcode) when the grant was issued. It authorizes a window of typing; individual messages inside the window carry no separate proof. The app must create a fresh `LAContext` for every grant it requests, never reusing an already-authenticated one (the parent spec's rule for confirmations, mobile-native-permissions §2, §3.6), so each grant costs a real Face ID check.
- **Lifetime, so a conversation stays smooth:** a grant lasts **5 minutes since it was last used**, and never more than **30 minutes since it was issued**. Someone typing back and forth is asked for Face ID at most once every 30 minutes; a phone put down for 5 minutes asks again. The owner can change both; see Decision points. Every accepted typing request returns the grant's current deadline (`X-Instar-Session-Grant-Expires`, the earlier of idle and absolute), so the app always knows when to prompt next; continuous typing never prompts before the absolute limit. Test: continuous typing past minute five and up to the absolute limit, one prompt total.
- **Ends early on:** device revoked, owner role removed, the phone asking to end it (`DELETE /mobile/sessions/input-grant`), server restart (grants live in memory, so a restart costs one Face ID). Never written to disk, never replicated.
- **Not a dashboard-PIN gate:** unlike the owner-presence gate, a PIN is not required; the presence key is the proof. A device with no enrolled presence key cannot obtain a grant.

### 2. Staged enforcement

One setting, `mobile.sessionInputGrant.mode`, with three values. Every value accepts a valid grant.

- **`accept`** (the default on development agents at merge; see Rollout for the fleet): a request without a grant is still allowed, **except from a device that has used a grant before** (`grantSeen`, set the first time a grant is accepted; see Multi-machine posture). From then on that device's typing needs a grant. So the person's own phone is protected from the first time its updated app uses a grant, and a stolen device key from that phone cannot skip back to the old path. Devices whose app never asked keep today's behaviour.
- **`require`:** every typing request needs a grant. Devices that cannot obtain one (no presence key: today's Android, older iPhone builds) are refused with the message in section 4.
- **`off`:** today's behaviour exactly (rollback).

**Exposure during the window:** while the mode is `accept`, a device whose app has never used a grant (an iPhone on an older build, every Android phone) keeps today's device-key-only typing. The person's updated iPhone is covered from its first grant.

**Keeping the window visible (Close the Loop):** at merge a commitment is opened on the security ledger row: "SEC-140 enforcement window open: N owner devices still type without a grant". The weekly maturation review re-raises it with two counts per machine: owner-device pairings the write gate would currently **allow** without a grant (the remaining permission, from the same rule function, over every paired phone regardless of when it last typed), and grantless typing actually seen since the last review. It closes only when the first count is zero on every machine, or the owner records acceptance of the named remaining pairings (for example Android until its Phase 3) with a re-review date. Quiet weeks alone never close it. First-come enrolment is a separate exposure with its own ledger item: pairings with no confirmed enrolment stay named there until owner-confirmed enrolment exists or the owner accepts them, whatever this commitment's state. Android's Phase 3 date is asked of the Chief of Staff at merge and written into the commitment.

**Relayed typing counts per ingress machine.** A session on machine B can be typed into through any machine that relays to it, and B trusts that machine (section 5). So readiness and the Close-the-Loop counts are taken per ingress machine (every machine an owner phone types through), and fleet enforcement is complete only when every such machine applies the rule to every recent phone; a machine that cannot be reached is shown as pending, never as done. The mode is set pool-wide (Multi-machine posture), so normally every ingress has the same policy; the counts are what confirm it.

**What turns on `require`:** a one-tap owner decision, offered when, on every machine, every owner phone paired there has obtained a grant on that same machine, or the owner has marked it as not used for typing. The offer lists each phone with when it last typed and whether it has used a grant, so a phone used once a month is shown, not dropped by a cutoff; the agent weighs that history when it decides to make the offer. Readiness is a separate per-machine record, `grantUsedHere` (set only by a grant issued on this machine), distinct from `grantSeen`, which can arrive from another machine's row and drives enforcement only, or on a date the owner sets. The offer lists any pair not yet seen using a grant there, and lists pairings with no enrolled presence key as an open enrollment risk: under `require` they are refused today, but if their app later enrolls a key first-come (What the grant does not prove), a device-key holder could enroll one instead. Counting such a pairing as protected needs owner-confirmed enrollment (its own ledger item). It is never flipped automatically, because it can lock a device out of typing (No Single Device Lockout). Until Android ships a presence key (its Phase 3), the offer says plainly that Android phones would lose typing.

### 3. Telling the app

- `GET /mobile/sessions/controls` `typing` block gains the `grant` object below (`outcome`, `mode`, `available`, `expiresAt`). The app uses the field's presence to know the server supports grants, and the routes in section 1 exist only on servers that report it.
- **One rule, three outcomes, used by both the controls answer and the write gate.** For a typing request from a device on this machine:
  - **allow** when the mode is `off`, or the mode is `accept` and the device is not `grantSeen`;
  - otherwise (mode `require`, or `accept` with `grantSeen`): **grant-required** when `available` is true (a request without a valid grant gets 428), and **blocked** when `available` is false (403 `session-input-unavailable`, no prompt, message: "Typing from this phone needs Face ID, which isn't set up on this computer right now. Type from the dashboard, or ask me to turn it back on.").

  A `grantSeen` phone therefore never falls back to grantless typing because a machine's presence features were turned off; the owner can clear the phone (accept mode) if they want that. The controls answer reports the outcome as `grant: { outcome: 'allow'|'grant-required'|'blocked', mode, available, expiresAt? }`; an older server has no `grant` field and the app types as today. Tests cover each outcome and a change of `available` after a phone has used its first grant.

- **When the grant route answers `presence-key-missing`** (this machine has no Face ID key for the phone yet, for example a phone protected through another machine), the app sets up its Face ID key on this machine through the existing presence-key route (same transports), then obtains a grant and resends once. The "pair the phone again" text is used only when that setup is refused with `presence-key-set` (a different key is already enrolled here). This first-come setup carries the enrollment risk named in What the grant does not prove.
- **The app obtains a grant whenever the outcome is `grant-required`, and also whenever `available` is true and the mode is not `off`** (so the first grant happens on the first send and per-device protection starts), on its first send and whenever its grant has expired, without waiting for a refusal. On `blocked` it does not prompt and shows the server's text. That is what makes the per-device protection start: the first accepted grant writes `grant-seen`. A test starts from a clean pairing, sends once (a grant is obtained first), then shows a grantless second send is refused.
- An older server has no `grant` field; the app keeps typing as today.
- No field is added to the peer relay state: the grant is checked on the machine the phone talks to (section 5), so the peer has nothing to report.

### 4. When a grant is missing or expired

The typing routes answer `428 { error: 'session-input-grant-required', message, expired: boolean }` (428 Precondition Required, not 401, which apps read as "this phone is not recognised"). An updated app handles it as below. An older app that is refused (only in `require`, or after a downgrade) treats it as a failed send; it may show a generic error rather than these texts, which is stated in the `require` offer. The app half confirms how shipped builds display a 428.
- The app treats it as "ask for Face ID, then send again": it shows the system Face ID prompt, obtains a grant and resends the same text once. The person sees one Face ID prompt and their message goes through. A refused **key press** (Enter, y/n, Ctrl-C) is not resent automatically: the session may have moved on during Face ID, so after the grant the app shows the key again for a fresh tap. Test: the session's prompt changes during Face ID; no key is sent until the person taps again.
- If Face ID is cancelled or fails, the message stays in the input box, unsent, with the server's text: "To type into this session, confirm it's you with Face ID. Your message is still here; tap Send to try again."
- A `grantSeen` device that can no longer obtain a grant (its Face ID key is gone, or the app was downgraded) gets: "This phone was set up to confirm typing with Face ID, but it can't do that now. Update the app, or pair the phone again. You can still type from the dashboard." In `accept` mode the owner can also turn the requirement off for that one phone from the dashboard's device list (in `require` it stays required).
- A device with no presence key gets: "Typing into sessions from this phone needs Face ID or a passcode. Open the app's security settings to set it up, or type from the dashboard." (Android today: "Typing into sessions isn't available on this phone yet.")

### 5. The relay hop

The phone always talks to one machine (A). For a session on another machine (B), A relays the typing with the agent token, and B checks only that token. B cannot check a grant: presence keys are machine-local and not replicated, and a token holder can already type into B's sessions through B's own `POST /sessions/:name/input` (Bearer API, `routes.ts:13287`). So **the grant is checked on A before A relays**, under the same mode rules. B's `allowRemoteInput` switch is unchanged. Moving the hop to a signed machine-to-machine command would not stop a token holder, so it is out of scope.

### 6. Refusal, retry and replay

The grant check runs first, before the replay record is consulted or written and before any terminal effect or relay. A refused request (428) therefore has no effect and consumes nothing. The app's retry after Face ID is a new device-signed request (new time, new signature), so it is a new replay digest and is accepted once. `428 session-input-grant-required` is produced only by the phone's own machine, before any effect or relay; a status from a relay target is never passed through as 428 (A maps any downstream refusal or lost reply to its existing relay error, which the app never auto-retries). The app matches the status and the error code together. **The app retries automatically only after a definite 428 with that code** (the parent spec's lost-answer rule, mobile-native-permissions §3.6). On a timeout or a lost connection it cannot know whether the text or key reached the session, so it does not resend: it shows "I couldn't confirm this was sent. Check the session before sending it again." and keeps the draft. Tests: expiry then retry, for text, a key (Enter) and an attachment; each produces exactly one effect, and replaying the accepted retry is refused; a downstream 428 or a lost relay reply causes no automatic resend.

### 7. Attachments replay

Attachments get the durable replay record that input and keys already have, so a captured attachment request cannot be replayed after a restart.

## What the grant does not prove

The verified fact is that the phone's enrolled presence key signed the grant's issuance challenge. That this followed a fresh Face ID or passcode check depends on the genuine app creating a fresh `LAContext` for it (§1); the server cannot observe the prompt. The passcode is an accepted fallback, so someone who knows the phone's passcode can obtain a grant. The grant protects against a phone found unlocked, malware that cannot pass the system prompt, and a copied device key; it does not protect against someone who has the phone and its passcode. That key is enrolled first-come: the phone's own device key plus proof of holding the new key, and once set it cannot be replaced without pairing the phone again (`mobileConsoleTicket.ts`, the presence-key route). So for a phone whose app enrolled its Face ID key (the iPhone app does this after pairing), a stolen device key cannot mint grants. For a phone that never enrolled one (Android today), someone holding its device key could enroll their own key and then mint grants. This is the same first-come limit the console sign-in already has, and closing it belongs to enrollment (for example, enrolling the Face ID key during pairing), not to this spec. It is recorded on the security ledger as its own item. In `accept` mode such a phone is no worse off than today.

## How this fits with registration and chat

This fix is one of three that protect the owner's phone authority. The shared threat model is the document "What someone can do with a phone key, and what three fixes change" (Studio document fd351c3a).

- **Registration (SEC-142) must ship before or with this fix.** A grant is only as strong as the presence key it checks, and a phone's first presence key on a machine is accepted first-come on the device key alone. Until registration needs an owner confirmation through an already trusted channel (pairing approval, the dashboard PIN or a direct chat confirmation), this fix protects phones whose genuine app registered first, and the `require` offer lists every other pairing as an open registration risk. This spec does not turn on enforcement for a pairing whose registration is unconfirmed once SEC-142 provides confirmation; until then it says plainly what it covers.
- **Chat (SEC-143) stays open on purpose, and gets its own control.** Typing reaches the terminal directly: raw commands, key presses that answer prompts, Ctrl-C, files. Chat reaches the agent, which reads and judges each message. That difference is why typing is gated by a grant while ordinary chat is not: gating every chat message would make talking to the agent tiring for little gain. The chat control proposed in the threat model is narrower: each phone message carries whether it was confirmed with Face ID recently, and the agent asks for a Face ID confirmation before acting on an unconfirmed message that asks for something risky (running commands, changing access, deleting). It is specified separately; this fix neither depends on it nor claims to cover chat.

## Experience cost and the search for a loss-free fix

- **What a person notices, in the default `accept` mode:** on an updated iPhone, one Face ID prompt before typing after 5 idle minutes, and at most one per 30 minutes of active conversation. The message they typed is never lost: it is sent right after Face ID, or stays in the box. On Android and older iPhone builds nothing changes. That is the whole cost of the shipped default.
- **The loss in `require` mode** (Android and not-yet-updated phones lose typing until they support the grant) is not shipped. It is the owner's decision, offered only on evidence (section 2), and its offer states the loss.
- **Loss-free alternatives considered:**
  - *Device key alone, plus phone-side checks* (the app refuses typing on phones without a passcode, as the apps now do): protects against a phone with no lock, not against malware on an unlocked phone or an unlocked stolen phone. Not sufficient: the server still accepts a request the person never confirmed.
  - *Presence-sign every request:* proves presence each time but costs a Face ID per message, a larger loss than the grant.
  - *Grant tied to the phone's unlock state* (valid only while the phone stays unlocked since a Face ID): iOS does not give the server a verifiable unlock state; the app could only claim it, which proves nothing to the server.
  - *No server-checkable signal exists between those:* every proof the server can check that a person is present is a presence-key signature. The grant is the cheapest way to use one: one signature covers a stretch of conversation.
- So the shipped default has a small, bounded cost (one Face ID per stretch of typing), the cost is the minimum any server-checkable presence proof requires, and the larger loss (`require`) is left to the owner.

## Multi-machine posture

- **Grants:** machine-local. machine-local-justification: physical-credential-locality (a grant is a bearer secret minted on the machine the phone talks to against a presence key enrolled only there; the relay target never sees it, section 5).
- **`grantSeen`:** one answer per machine, the local device record's `grantSeen`, which records the set of `grant-seen` row ids it reflects. The device-key ledger (`src/core/MobileDeviceKeyLedger.ts`, present where the machine has a signing identity, replicated where native conversations are on) carries the changes between machines:
  - **Order on the first grant:** the local flag is written durably first; the grant is issued only after that write succeeds (if it fails: 503, no grant). Issuance is the enforcement transition. If the issuance answer is lost, the phone's next grantless send gets a 428 and the app obtains a grant and sends: recovery is automatic and costs one Face ID. `grantUsedHere` (readiness) is recorded only after a typing request succeeds with a grant on this machine. Test: lose the issuance answer, then send. The local write stores the pending row's identity (keyHash, epoch) with the flag. Then the ledger row is appended where a ledger exists; if that append fails, or the process stops before it, the grant still stands (the local flag protects this machine), a degradation is reported, and the same row is appended idempotently at the next start and on a retry timer until it lands. Test: stop between the local write and the append, restart, and a peer ingests the row. This follows the ledger's own rule of recording before acting.
  - The first accepted grant on a machine, when no un-cleared row of its own exists, writes a `grant-seen` row `{type:'grant-seen', keyHash, deviceId, epoch, seenAt, machineId, signerKeyHash, sig}` and adds its id to the local flag. `epoch` is part of the row id, so protecting a phone again after a clear yields a new row instead of a dropped duplicate (the build extends `ledgerRowId`, the replicated store's known-field list and its timestamp choice for `epoch`, `seenAt`, `clearedAt`).
  - **Ingest keeps the local flag current:** a verified `grant-seen` row for a device this machine knows (same key hash) adds its id to the local flag, on ingest and at boot.
  - **Clearing** (owner's dashboard action, `accept` mode only) writes a signed `grant-seen-cleared` row naming the exact row ids it clears. Each machine persists two sets per device, the verified `grant-seen` ids it has seen and the ids named by verified clears, and the flag is set while some seen id is not cleared. So a clear that arrives before the row it names still wins when the row arrives later, including across a restart in between (tested). A grant used later writes a new-epoch row no clear names, so protection comes back only through a real grant, never through a boot backfill. Delivery order does not matter and a replayed old clear changes nothing. Tests: both delivery orders, a replayed clear, clear on A then restart B (still cleared on both), clear then a new grant (protected again).
  - **The ledger being unreadable** does not change the answer: the local flag is used, and the read failure is reported as a degradation. Where no ledger exists (a single machine without a signing identity), the local flag still protects that machine, and the agent reports once that protection does not travel between machines.
  - **Enforced only where a grant can be obtained:** `available` is a machine setting, not a property of a request: true exactly when the presence-key route's own enrolment condition holds (`mobileConsoleTicket.ts` gate with `enrolment`: console sign-in on, or owner presence on, or native conversations on). The build extracts that condition, including the route's `svc.enabled()` and configured-agent-token checks, into one exported function that the enrolment route, the grant routes and the controls answer all call, so they cannot disagree. The enrolment route also requires the machine's local secure transport, as today; a phone that reaches a machine another way and has no key there gets `presence-key-missing`, cannot enrol, and sees the blocked text for that machine. Test: a phone with no key, console sign-in off and owner presence on, through its first send. Because enrolment needs the local secure transport and typing may not, the controls answer also reports `enrolmentReachable` for this request (whether this connection could complete Face ID setup), so a phone with no key here is told before any prompt: "Set up Face ID for this computer once while you're on the same network as it, or over its secure address." Tested separately from an already-enrolled phone on the same connection. The grant routes accept exactly the transports the typing routes accept, so any request that can type can also obtain a grant. Where `available` is false, the shared rule decides (section 3): a phone that is not `grantSeen` in `accept` mode types as today; a `grantSeen` phone, or any phone under `require`, is **blocked** there. No Single Device Lockout for that case: only typing from that phone on that machine is refused; the dashboard, chat and every other machine keep working; the refusal text names the fix, and the agent's own fix is to turn owner presence on for that machine (no PIN needed), which it offers as a one-tap yes whose card says in one line that this also turns on that machine's other Face ID controls (desktop unlock, PIN reveal). The `require` offer and the Close-the-Loop count list such pairs as blocked.
- **The mode setting:** per machine, in config. The owner decision in section 2 applies it on every machine in the pool through the existing config-apply path, and the agent reports which machines are in which mode.

## Frontloaded Decisions

- Grant over a per-message Face ID: per-message Face ID would make conversation from the phone tiring (Chief of Staff). Cheap to change after: no, it is the app contract.
- Defaults 5 minutes idle / 30 minutes absolute. Cheap to change after: yes, a setting.
- Default mode at merge `accept`, with per-device enforcement. Cheap to change after: yes, a setting.
- No PIN requirement for the grant. Not cheap: it is part of what the app shows.

## Migration

- Device records gain optional `grantSeen`. The device-key ledger gains two row types, `grant-seen` and `grant-seen-cleared`, validated like activation rows; older machines ignore unknown row types (verify in build: the replication reader must skip, not reject, an unknown type).
- Config gains `mobile.sessionInputGrant.mode` (absent = `accept`), `idleMinutes` (default 5), `maxMinutes` (default 30, never below `idleMinutes`). Read with defaults; no `migrateConfig()` step needed.
- Shipped apps: unchanged behaviour until they adopt grants (no `grant` field handling = today's flow).

## Observability

Per machine, in the signed-in `GET /mobile/sessions/controls` owner view and the security audit file `mobile-session-input.jsonl`: grants issued, typing requests with a grant, without a grant (allowed in `accept`), refused for a missing or expired grant, by device. These show when every active device uses grants (the evidence for the `require` offer) and whether people are being refused.

## Rollout and maturation

- **Test-agent rung:** e2e with the real server: grant issued against an enrolled presence key, input accepted with it, refused without it for a `grantSeen` device and in `require`, refused after the idle and absolute limits, refused after revocation, relay hop refused on A without a grant.
- **Development-agent rung:** Echo runs `accept` from merge; the iPhone app build that adopts grants (echo-instar-apple-app-rebuild) is used for a week. Evidence: grants issued and used, zero refusals of the owner's updated phone outside expired-grant retries, the audit counts.
- **Fleet:** until the development-agent rung graduates, the fleet default is `off`, so no fleet phone is restricted before the evidence exists: the grant routes and the controls field still ship, the updated app obtains grants where offered, and nothing is refused.
