## Problem statement

Every Claude Code and Codex session an agent runs starts its own Threadline MCP helper (`dist/threadline/mcp-stdio-entry.js`), a separate Node process that loads the agent's identity, builds a registry client and serves the `threadline_*` tools over stdio. Measured on 2026-10-27 (`docs/research/RUST-TRIAL-2026-10.md`, median of 7, registry off): first reply 155 ms; RSS 93.1 MB, of which 44.6 MB is private (`RssAnon`); long-running live helpers sat at 17–31 MB private. With N concurrent sessions that is N copies of the same tool server, and N identity/registry initialisations. A Rust helper would cut this to a few MB each but would duplicate identity, signing and registry-auth code in a second language (operator agreed 2026-10-27 to defer that).

The agent server is already running, already holds the identity, the trust store and the relay client, and already answers every call the helper makes (the helper's tools are thin wrappers over the same server's `/threadline/*` and `/messages/*` routes; note the `/threadline/*` routes are exempt from the bearer check and take the calling session's name from the request body, see D2). Serving the same MCP tools from the server over MCP's streamable HTTP transport removes the per-session process entirely.

`THREADLINE-NETWORK-INTEROP-SPEC.md` §3.2 already designs MCP transports (stdio / SSE / HTTP-streamable) for **network** clients with scoped tokens. This spec is the narrow **local** slice: loopback only, for the agent's own sessions. It does not open any port beyond the agent server's existing loopback listener and does not implement the network transports or `instar mcp-server token create`.

## Goals

1. A session can use the `threadline_*` tools without a per-session helper process, with identical tool names, schemas and behaviour.
2. The calling session is known to the server exactly as today (the helper forwards `INSTAR_SESSION_NAME` as `originSessionName`), so attribution is neither weakened nor strengthened.
3. Off by default; when off, transport selection is unchanged, and the only live changes are the long-wait fixes (Frontloaded Decision 12), the always-mounted route (D6) and the local secret file created at first boot (D2). When on and anything is unavailable at spawn, the session falls back to today's stdio helper.
4. Existing agents receive the capability on update (Migration Parity) without hand edits.

## Non-goals

- Network exposure, SSE, scoped capability tokens for third-party clients (interop spec §3.2.3).
- Changing tool semantics, the relay, trust or pairing.
- Removing the stdio helper (it stays as the fallback and for clients started by hand).

## Design

### D1 — Endpoint and per-request tool server

`POST /mcp/threadline` on the agent server, handled by `StreamableHTTPServerTransport` (`@modelcontextprotocol/sdk` 1.27.1, already a dependency) in **stateless** mode (`sessionIdGenerator: undefined`), default streaming (SSE) response mode. `GET` and `DELETE` answer 405, which the streamable-HTTP spec permits and both clients tolerate (they POST each JSON-RPC message). Express has already parsed the body, so the handler passes `req.body` as `parsedBody`; the route mounts its own `express.json({ limit: '256kb' })` before the global 12 MB parser, as `/completion-claim/observe` does.

**One tool server per request.** A stateless transport cannot be reused across requests and a server holds one transport, so each request builds a fresh `ThreadlineMCPServer` + transport, handles the one request, and closes both. The server is constructed with `transport: 'streamable-http'`, `requireAuth: false`, `auth: null`, then `setRequestContext({ authenticated: true, isLocal: true })` before the request is handled: the caller is one of the agent's own sessions, so it gets exactly the local-operator view and admin tools the stdio helper gives today (trust levels visible, trust/delete/pairing allowed). Privilege is unchanged, not raised. The build measures construction cost; if the median exceeds 5 ms it pre-builds the tool registration table once and attaches it per request (the cached-server alternative is impossible with this SDK).

**Shared dependencies are the server's own live objects, never second copies.** The route uses the instances the server already holds: `AgentDiscovery` and `AgentTrustManager` from `ThreadlineBootstrap`, and the `ThreadResumeMap` built in `server.ts`. Two `AgentTrustManager`s in one process would be two debounced writers to one file, so a `threadline_trust` change could be lost; sharing one instance also gives the tools the server's `newFingerprintProfileLevel` setting, which a helper-built instance lacks today. With shared instances `reloadTrustBeforePairingRead` is `false`. When the relay is off and the bootstrap has no trust manager, the route builds one once at mount time and holds it for every request (never per request, which would recreate the two-writers problem). Two documented behaviour differences from the helper result: discovery's self-path is `projectDir` (the helper used `stateDir`), and the resume map carries the server's framework resolver. Both are the server's existing, more correct values.

**Registry: `registry: null`, exact parity with today.** Today's helper never has registry tools: `RegistryRestClient.authenticate()` sends an auth frame without `agentId`, the relay refuses it before anything else (`ConnectionManager.ts` ~179), and `setupRegistryClient` returns `null`. The helper logs on this machine show 101 registry setup failures (100 "Agent ID does not match public key", 1 timeout) and no successes, and the reviewing session's own tool list has no `threadline_registry_*` tools. So the HTTP path builds its tool server with `registry: null`: the same four tools are absent, nothing connects, and readiness does not depend on the registry. The missing `agentId` is filed as its own bug; when it is fixed, registry support on the HTTP path is a separate change. <!-- tracked: feedback fb-8972c480-a75 -->

**Calls behind the tools are unchanged.** `sendMessage`, `getThreadHistory` and the other server-backed deps still go through the same loopback routes the helper calls (`mcp-http-client.ts`), so every outbound gate and audit is the code that runs today. One change: `sendMessageViaHttp` gains an explicit `originSessionName` parameter (today it reads `process.env.INSTAR_SESSION_NAME`, which inside the server is the server's own environment); the stdio path passes the environment value, so its behaviour is unchanged.

**Long waits, for both transports.** `threadline_send` with `waitForReply` holds the inner `POST /threadline/relay-send` open until the reply arrives (schema allows 1–300 s), but the server's generic request timeout (30 s, `middleware.ts`) has no override for that route, so today any wait past 30 s gets a 408 even though the message already left; the stdio helper has the same cut-off, and its default `timeoutSeconds` (120) already exceeds it. This spec fixes the whole chain, for both transports, with the ordered deadlines under **Bounds** below: middleware overrides for `/threadline/relay-send` and `/mcp/threadline`, an undici `Agent` on the inner call in `mcp-http-client.ts` (Node's built-in `fetch` waits at most 300 s for headers, which a 300 s wait plus send time exceeds), the client tool timeouts, and cancellation of the reply wait when its request closes. This relay-send override ships live, not behind the flag: it is a bound on an existing route that already fails long waits today, and it changes stdio behaviour only by letting those waits finish.

**Bounds.** Ordered deadlines, each with headroom before the next, so every layer gets to say what happened: in time order: (1) `relay-send`'s reply wait is capped at 300 s by `waitForThreadlineReply`, which clears its own waiter; (2) the route answers the client at 320 s at the latest with a structured tool error saying the outcome is unknown and the message may already have been sent, so the model does not assume it failed; (3) the inner fetch's undici agent allows 325 s, so the route's own answer always comes first; (4) the middleware timeout override for both routes is 340 s; (5) the clients' tool timeouts are 360 s (Codex `tool_timeout_sec = 360`; Claude Code: `MCP_TOOL_TIMEOUT=360000` set in the environment of every claude-code spawn, stdio and HTTP alike, which is carved out of criterion 1 like Codex's timeout; the build confirms with a real 300 s wait). `sendMessageViaHttp` classifies an undici header/body timeout, an abort and a 408 as **outcome unknown** ("the message may have been sent"), not "failed to reach the server", on both transports, so a timed-out send is never presented as not sent. **Cancellation reaches the work, not just the socket:** `relay-send` gains a `res.on('close')` handler, acting only when `!res.writableFinished` (a premature close, not a normal completion; Node's request `close` can fire once the body is read, which would cancel healthy waits), that cancels the reply wait on both of its branches, and a request whose client is already gone when the waiter registers is cancelled at registration (the relay branch already exposes `cancelReplyWait`; the co-located local-delivery branch is given the same `onRegistered` hook), so a closed inner request ends the waiting (a message already sent stays sent); this also helps the stdio path. Capacity is counted per outstanding inner operation and released only when that operation's handler promise settles (for relay-send, bounded by its own 300 s cap), never merely when a fetch is abandoned or a deadline passes: releasing accounting would not stop the work. A handler with no cap of its own (discovery, pairing) that is still running at 360 s keeps its slot and is reported (`threadline.mcpHttp.stuckOperations` on `/health`, plus a `ThreadlineMcpHttp.stuck` degradation), so a stuck dependency shrinks capacity visibly instead of letting live work exceed the bound. The generic request timeout cannot be relied on for the outer request because streaming headers go out immediately. JSON-RPC batch arrays are refused with 400 (MCP 2025-06-18 removed batching; the SDK still accepts them, which would let one request carry many 300 s calls). At most 32 requests in flight on the route (429 beyond), of which at most 24 may be `waitForReply` calls, so 8 slots are never taken by waits (they can still be taken by other slow calls such as discovery); at most 4 per session name; a slot is released only when the request's inner operation has ended, not when the client disconnects or a fetch is abandoned, because the inner `relay-send` keeps running (and its message may already have left) after a disconnect. The route does not abort the inner call on disconnect: an abort would not un-send a message and would invite the client to resend it. The per-session cap is new behaviour (stdio never had one), keyed on a self-asserted header, so it is a courtesy against one runaway session; the global cap is the real bound.

### D2 — Credential and attribution (Know Your Principal, stated honestly)

**Credential: one per-agent local secret, not the agent token.** The route authenticates with `Authorization: Bearer ${INSTAR_LOCAL_MCP_SECRET}`, a 32-byte random secret in `.instar/state/local-mcp-secret` (a file like the lifeline ingress secret: mode 0600, created at first boot, on the key-material list; unlike the lifeline secret it is placed in session environments, which is where the agent token already is). It is checked in `authMiddleware` by one exact-path rule (`req.path === '/mcp/threadline'`, never a prefix) placed first in the middleware, before the no-token-configured skip and before the agent-id check, so the route is protected even on an install with no agent token and a mismatched agent id cannot change the outcome; the route handler repeats the constant-time secret check and the loopback and header refusals (as the `/internal/*` routes do), because Express matches routes case-insensitively and ignores a trailing slash, so `/MCP/threadline/` reaches the handler without hitting the exact-path rule. On that path, and only there, the middleware accepts this secret instead of the agent token (the agent token alone gets 401, and so does a handler-path refusal), compares it in constant time, and also requires a loopback peer, no `Origin`, and no `Cf-Connecting-Ip` / `X-Forwarded-For`. The secret is accepted on no other route, never sent anywhere by the server, and never rotated by tunnel events. That is why it is not the agent token: the agent token rotates after a tunnel backup relay is used, and running sessions keep their old value, so HTTP-wired sessions would lose their tools after every rotation (rounds 2 and 3 tried a previous-token grace and found it reopened exactly the path the rotation closes: a backup relay forwards raw TCP from 127.0.0.1 with no forwarding headers). A secret that never travels has nothing for a rotation to revoke. Rotating it by hand (delete the file, restart) is the operator's lever; running HTTP sessions then lose the tools until restarted, which the `ThreadlineMcpHttp.callFailure` degradation reports.

Sessions spawned while the flag is on receive it (flag off: not passed at all, so flag-off spawn arguments stay byte-identical) as `INSTAR_LOCAL_MCP_SECRET` via `-e INSTAR_LOCAL_MCP_SECRET=${omitAuth ? '' : secret}` on every spawn site that passes `INSTAR_AUTH_TOKEN` (`SessionManager.ts` ~4061 and ~4470, which honour `omitAuthEnv`; ~7063 `spawnInteractiveSession` and ~7623 `spawnTriageSession`, which have no stripped mode and always pass it, as they do the agent token); other spawners (`PipeSessionSpawner`'s `claude -p` pipe sessions, the interactive pool, provider headless transports) stay on stdio and are not counted in `sessionsOnStdio`, which covers only sessions SessionManager records; the name already matches the credential pattern, so child-process scrubbing covers it, and it is also added to the exact list in `src/core/credentialEnvNames.ts`; the file joins both key-material lists in `src/core/keyMaterialPaths.ts` (the path-prefix list and `KEY_MATERIAL_FILES`, which drive the gitignore entries, the backup exclusion and the file-viewer refusal), the state-coherence registry and the write-domain registry, like the lifeline secret. It grants nothing the session's own `INSTAR_AUTH_TOKEN` does not already grant; it only reaches this one route.

That attribution is **self-asserted, exactly as today**: the stdio helper reads `INSTAR_SESSION_NAME` from its own environment, and the routes behind the tools (`/threadline/*`) are exempt from the bearer check and take `originSessionName` from the request body. A per-session token was considered (round 1) and rejected: it would make attribution correct only on this route while any local process can still post `relay-send` with any session name, so it would add a credential, a persisted token map and restart machinery without adding a boundary. Binding `originSessionName` to a verified session credential on the routes themselves is a separate, larger change outside this spec's slice, filed as feedback fb-a9c21fc7-1bd; attribution does not get worse here.

**Sessions deliberately stripped of authority stay stripped.** A spawn with `omitAuthEnv`, a confined spawn, or any spawn launched with an empty strict MCP config never gets the HTTP entry, and its launch arguments are byte-identical to today's. (They are spawned with the local secret blanked, so the route would refuse them anyway; the rule keeps them from even being offered it.)

**Browser and DNS-rebinding defence.** The transport's `enableDnsRebindingProtection` is on with `allowedHosts` set to the exact loopback host:port the client config uses, and any request carrying an `Origin` header is refused (403). Loopback-only: a request whose socket `remoteAddress` is not `127.0.0.1` / `::1` / `::ffff:127.0.0.1` is refused, and so is one carrying `Cf-Connecting-Ip` or `X-Forwarded-For`. These are defence in depth, not the boundary: the local secret is the boundary. A local reverse proxy or backup relay that forwards remote traffic from 127.0.0.1 without those headers reaches the route, and is refused unless it holds the secret, which the server never sends anywhere.

### D3 — Client wiring

Both wirings are built from one function that also produces the URL the launcher checks (D4), so the configured URL and the checked URL can never differ (an explicit `config.host`/`bindHost` stops the server listening on 127.0.0.1, so the function uses the server's actual loopback listen address).

- **Claude Code.** Every claude-code spawn that is not stripped (D2) gets one per-spawn MCP config passed with `--mcp-config` (not `--strict-mcp-config`), holding only `threadline` as `{"type":"http","url":"<url>","headers":{"Authorization":"Bearer ${INSTAR_LOCAL_MCP_SECRET}","X-Instar-Session":"${INSTAR_SESSION_NAME}","X-Instar-AgentId":"${INSTAR_AGENT_ID}"}}`. That covers interactive topic sessions, non-topic interactive sessions, the headless/job lane, the rerouted lane and the Threadline reply spawns; today `buildSessionMcpFlags` runs only for topic sessions with dynamic MCP on, so this is a new call on the other paths, and a unit test covers each path. When dynamic MCP is on, its own per-topic strict config is used instead of the stable file: its `threadline` entry is replaced by the HTTP entry when the resolved set contains `threadline`, and left absent when it does not (one writer, one `--mcp-config`). Because the headers are `${VAR}` references, the file's content is identical for every session, so it is one stable per-agent file (`.instar/state/session-mcp-config/threadline-http.json`, rewritten only when the URL changes), never one file per spawn and never a literal token. The bootstrap's stdio registrations in `~/.claude.json` and `.mcp.json` are never edited, so hand-started clients keep stdio.
  **Verified 2026-10-27 on Claude Code 2.1.310** with a real `claude -p` against a header-logging loopback server: both headers arrived expanded (the token at its real length, the session name literal-free), and the same-named per-spawn entry replaced the global stdio entry entirely (no `mcp-stdio-entry` child process was started). So non-strict mode is used and no server list is rebuilt.
- **Codex.** **Verified 2026-10-27 on codex-cli 0.156.1:** a `-c` override, even an inline table, merges into a `[mcp_servers.threadline]` table from the shared `~/.codex/config.toml` (written by `instar codex connect`), and the file's `command` makes Codex refuse the result ("url is not supported for stdio"); disabling an entry that does not exist also fails ("invalid transport"). So the launcher adds the HTTP server under its own name, `-c 'mcp_servers.threadline_local={url="<url>",bearer_token_env_var="INSTAR_LOCAL_MCP_SECRET",env_http_headers={"X-Instar-Session"="INSTAR_SESSION_NAME","X-Instar-AgentId"="INSTAR_AGENT_ID"},tool_timeout_sec=360,startup_timeout_sec=20}'` (verified to parse as `transport: streamable_http` with both header fields), and adds `-c mcp_servers.threadline.enabled=false` **only** when parsing `$CODEX_HOME/config.toml` (default `~/.codex/config.toml`) with `smol-toml` (already a dependency) yields an `mcp_servers.threadline` table; a parse error counts as absent, so a commented-out header can never produce the startup-breaking disable, replacing today's per-spawn stdio override on both the interactive and the headless Codex launch paths. A project-scope `.codex/config.toml` entry is not checked; that is a miss, which fails safe. The detection's failure direction is safe: a missed entry leaves the shared stdio helper running beside the HTTP server (duplicate tools, still working, reported once as `codex-shared-entry-not-disabled`), never a session that fails to start. Codex sessions therefore see the tools under the `threadline_local` server name; tool names themselves are unchanged.

**Client-version gate.** Both checks above are recorded in a per-framework verified-floor table in the launcher (`claude-code: 2.1.310`, `codex-cli: 0.156.1`); a framework with no entry always gets stdio, which is how D5's "stays on stdio" is expressed. At spawn the launcher reads the installed version (Claude Code's is already resolved for the retained-binary copy; Codex's via `codex --version`, cached per binary path); a version below the verified floor, or unreadable, is a readiness failure for that framework (stdio + `unverified-client-version`). A newer version is admitted; if it ever breaks the wiring, the per-session first-call record (D4) and the call-failure degradation surface it (`ThreadlineMcpHttp.callFailure`: reported once per framework per hour when a wired session's request fails authentication or the route answers 5xx).

### D4 — Fallback, never silent

Readiness is a real HTTP self-probe, run once at boot (after the listener is up), again whenever the flag is switched on or the listen address changes, and every 5 minutes while it is failing; the flag is read live at each spawn. The result is cached; spawns read the cached result and never wait on it (an empty cache counts as not ready). The probe sends, under the reserved session name `__readiness-probe` (excluded from the first-call record, the transport counts and the per-session cap), an authenticated `initialize`, `tools/list` and one read-only call (`threadline_agents`, which touches the shared discovery and trust objects) to the exact URL the client configs carry, with the same headers the clients send, so it exercises middleware order, the route's own body parser, `allowedHosts` and the shared dependencies, not just the handler. It fails (reason `not-listening-on-loopback`) when the server has no listener on `127.0.0.1`, `::1` or `0.0.0.0`; an explicit non-loopback `config.host` or mesh bind override is exactly that case. If the flag is off, the probe has failed, the session is a stripped one (D2), or the client version is below its floor (D3), the spawn uses today's stdio entry unchanged.

A flagged spawn that falls back reports a degradation (`ThreadlineMcpHttp.fallback`, with the reason) so a fallback is never silent; it is reported once per (framework, reason) per server process, with a running count in the health field, so a permanent fallback does not repeat on every spawn. The route records each session name's first successful call; the authenticated `GET /health` gains `threadline.mcpHttp: { enabled, sessionsOnHttp, sessionsOnStdio, sessionsOnHttpNeverCalled, fallbacks: {<framework>: {<reason>: count}} }`. The transport each session was given is stored in its persisted session record (not only in memory), so the counts stay correct across a server restart; a session whose record predates this feature counts as unknown. `sessionsOnHttpNeverCalled` counts HTTP-wired sessions older than 10 minutes with no call yet; it is a prompt to look, not proof of breakage, because a session may simply not have used the tools. Values the server cannot measure are `null`, never 0.

A session on HTTP whose server goes away loses the tools until the server returns. Today each helper also needs the server for every tool call, so this removes a process without adding a dependency. One difference, named: the helper answers `initialize` and `tools/list` on its own even while the server is stalled, while an HTTP client connecting during a stall may fail its first `initialize`; criterion 7 tests that the client recovers on its next connect.

### D5 — Server restart and machine moves

There is no per-session state to persist: the local secret (a file that persists) and the session name survive a restart in the session's own environment. What a restart does test is the client: a stdio helper simply waits, while an HTTP MCP client sees refused connections while the server is down, and instar servers restart on every update. The build verifies, per framework with a real session, that the client recovers on its next tool call after the server returns (criterion 6). A framework whose client does not recover stays on stdio (version floor not raised for it), because losing the tools on every update is worse than the helper's cost. A topic moved to another machine is respawned there by that machine's launcher with that machine's URL; nothing crosses machines.

### D6 — Configuration and rollout

`threadline.mcpHttp.enabled` (default **false**; an explicit operator flag, not the dev-agent gate, because it changes how every session is spawned). The flag controls only which transport new spawns get. The route itself is mounted whenever Threadline runs, regardless of the flag, so switching the flag off never cuts off sessions already wired to HTTP, including across a server restart; they keep working until they end or are restarted (and then get stdio). Mounting it unconditionally exposes nothing new: it requires the local secret, from loopback only. Migration Parity: no settings or hook migration is needed while off; the CLAUDE.md template line describing the flag and the health field is added in `src/scaffold/templates.ts` and mirrored by a content-sniffed `PostUpdateMigrator.migrateClaudeMd` step.

## Decision points touched

- **Route admission (local secret by an exact-path rule, loopback, no Origin/forwarding headers)** — `invariant`. A deterministic constant-time secret check plus fixed defence-in-depth refusals; no competing signals.
- **Spawn-time transport choice (HTTP vs stdio)** — `invariant`. Flag off, readiness failed, stripped session, or framework verification failed ⇒ stdio, which is today's behaviour, so the conservative answer is always available.
- **Relay-send deadline and close-cancellation (ships live)** — `invariant`, fixed bounds on an existing route.
- **In-flight caps (32 global, 24 waits, 4 per session name)** — `invariant`. Fixed numeric bounds (Bounded Blast Radius); a refused call returns 429 and the client may retry.
- **Existing outbound gates** — `invariant` (unchanged): tool calls run the same loopback routes and outbound gates as today; no existing gate is modified.

## State vs. symbol (P20)

- **Readiness.** Symbol: the cached HTTP self-probe passed. State it claims: a new session's client will be served at the URL it is given. Corroboration: the probe is a real authenticated `initialize` + `tools/list` + `threadline_agents` over HTTP to that exact URL with the clients' own headers, so it covers middleware, body parsing, host checks and the shared deps. Bidirectional: the probe can pass while a particular client version cannot use the entry (covered by the version floor and the first-call record), and can fail while the route works (a transient stall), which costs only a stdio session. Unmeasurable (probe never ran, threw): not ready ⇒ stdio plus a degradation report.
- **`sessionsOnHttp` / `sessionsOnStdio`.** Symbol: transport recorded at spawn. State it claims: which transport each live session was given (labelled so), not that its tools work. Pruned when a session ends. Unmeasurable ⇒ `null`.
- **`sessionsOnHttpNeverCalled`.** Symbol: no successful call recorded for an HTTP-wired session older than 10 minutes. State it suggests: possibly broken wiring. Bidirectional honesty: the symbol is present for a healthy session that never needed the tools, so it is surfaced as "never called", never as "broken"; a session whose calls all fail is caught by the call-failure degradation, not by this count.

## Multi-machine posture

Each machine's sessions talk to that machine's own server over loopback; the route refuses non-loopback peers. No new shared state is introduced: one per-machine local secret (`.instar/state/local-mcp-secret`, gitignored state, never synced, excluded from backups via the key-material list; each machine generates its own); one per-agent MCP config file holding only a loopback URL and `${VAR}` references, regenerated per machine from that machine's own listen address. The health counts are per-machine operational observations, read per machine from that machine's authenticated `/health` (the unauthenticated `/threadline/health` is deliberately not used, because it is public and has no pool view); nothing is replicated.

## Frontloaded Decisions

1. Default off, explicit flag `threadline.mcpHttp.enabled`, not the dev-agent gate — decided (D6).
2. Stateless transport, one tool server per request, local-operator context — decided (D1).
3. Credential = one per-agent local secret accepted only on this route (not the agent token, which rotates); attribution = self-asserted session header, as today; no per-session token — decided (D2).
4. Server's live trust/discovery/resume objects are shared, never duplicated — decided (D1).
5. Server-backed deps keep their loopback calls; only `originSessionName` becomes a parameter — decided (D1).
6. Claude Code: one stable per-agent `--mcp-config` file (non-strict; verified to replace the global stdio entry and to expand `${VAR}` headers on 2.1.310), on every non-stripped claude-code spawn path; shared config files never edited; never a literal token on disk — decided (D3).
7. Codex: HTTP server added as `threadline_local`; the shared file's `threadline` entry disabled only when detected (verified on 0.156.1) — decided (D3).
8. Bounds: ordered deadlines 300/320/325/340/360 s (reply wait, route answer, inner fetch, middleware, client), cancellation of the reply wait on close, per-operation capacity accounting, 32/24/4 in-flight caps, 256 KB body — decided (D1).
9. Client-version floor per framework, below/unreadable ⇒ stdio — decided (D3).
10. Route mounted whenever Threadline runs; the flag selects transport for new spawns only — decided (D6).
11. Registry: `registry: null` on HTTP, exact parity with today's always-failing helper registry; readiness independent of the registry — decided (D1).

## Acceptance criteria

1. Flag off: spawn arguments byte-identical to today for both frameworks on every spawn path, except the live long-wait fix: Codex's stdio override gaining `tool_timeout_sec = 360` and claude-code spawns gaining `MCP_TOOL_TIMEOUT=360000` (unit); the route stays mounted and still serves a session that was wired before the flag went off (integration).
2. Flag on, per supported framework (versions at or above the verified floor): a real Claude Code session and a real Codex session each list and call `threadline_send` and `threadline_history` with no `mcp-stdio-entry` process for them (e2e), and two concurrent sessions' sends each carry their own `originSessionName`.
3. The local secret is required (401 without, and 401 for the agent token alone); non-loopback peer, `Origin` header, `Cf-Connecting-Ip`/`X-Forwarded-For` all 403; other `/mcp/*` routes unaffected (integration).
4. Output parity: `threadline_discover` and `threadline_agents` return the same result over HTTP as over stdio for the same state; a `threadline_trust` change made over HTTP is visible to the relay's trust manager (same object) (integration + wiring test that the route's deps are the server's instances, not null, not copies).
5. Stripped spawns (`omitAuthEnv`, confined, empty strict config) get no HTTP entry and unchanged arguments (unit, every spawn path).
6. Server restart: a real Claude Code and a real Codex session started before the restart call the tools after it (recorded live checks); a framework that fails this stays on stdio (D5).
7. Fallback: readiness failure ⇒ stdio, tools work, one degradation report; a client connecting during a stalled server recovers on its next connect (integration).
8. Bounds: a 300 s wait completes and the client receives the result; a request whose inner wait outlives the response deadline gives the client the outcome-unknown error before the client's own timeout; closing the inner request ends the reply wait (no waiter left behind) and capacity returns only then; the 33rd concurrent request gets 429; a batch array gets 400; a disconnected request keeps its slot until its inner call settles; a `waitForReply` of 300 s completes over HTTP and over stdio (integration, fake timers where possible).
8a. Local secret: accepted on `/mcp/threadline` only (refused on every other route, refused with an `Origin`, `Cf-Connecting-Ip` or `X-Forwarded-For` header, refused from a non-loopback peer); an agent-token rotation does not affect wired sessions; stripped spawns get it blanked on every spawn path; an install with no agent token configured still refuses the route without the secret (middleware + unit).
9. Feature alive in CI (e2e): booting through the same initialisation path as `server.ts` with the flag on, the boot probe fills the readiness cache, a flagged spawn's arguments carry the HTTP entry, and the SDK's streamable-HTTP client gets a working `tools/list` and `threadline_send` from `POST /mcp/threadline` (not 404, not 503). The real-framework spawns of criterion 2 are recorded live checks in the PR.
10. Version gate: a client below the verified floor or with an unreadable version gets stdio plus one `unverified-client-version` report (unit, both sides of the boundary).
11. Measured and recorded in the PR: per-session private memory and first-call latency, flag on vs off.
