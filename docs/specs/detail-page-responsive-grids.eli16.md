# Detail pages that use the window

The Accounts screen in a wide window left a large empty area on the right. The same layout habit affected other detail screens: the page stopped growing at a fixed width and kept meaningful records in one tall list. People had to scroll even when the window had room to show related cards side by side.

The web dashboard now uses the full content area after its navigation. Account records become separate cards, and existing detail sections use a reusable grid. The grid chooses its column count from the space actually available to those cards. It uses a readable minimum measured relative to text size, so a narrower window or larger text reduces the number of columns. One card can fill its row. Accounts keep their provider headings and each usage limit keeps its own percentage and reset time.

This applies beyond Accounts: computer cards, machine care, Health, Ideas, Notifications, Feature Maturation and the standard section pages use the same rule. Headings, filter controls and primary owner requests keep their order. Chat history, file browsing, terminals, work boards and document reading retain their own workspace layouts. Long explanatory paragraphs remain constrained for readability even when their containing page is wider.

The change is visual. It does not add an approval flow, start a job, send messages, change a source read or alter any permission. Existing buttons still do the same things. Its verification includes narrow phones, minimum laptop windows, wide windows, larger text and both themes. Browser previews use privately captured read-only responses; they are evidence of the source layout, not proof that a release has reached a person's device. A code revert restores the old layout without migrating any stored data.
