# Read Practice-Fold Replies After All Stop Hooks Finish

## Problem Statement

Practice folding reads `last_assistant_message` from a Stop hook. The command reporter sends no whole reply; the native path bounds its text. The runner therefore cannot parse the full handoff. The previous implementation proposal hit its six-round review cap and remains incomplete. This is a fresh design, not a claim that the old proposal converged.

## Observable Must-Haves

The live runner reads the complete answer to exactly its injected request, across tool calls, and only after Claude Code writes the summary of all Stop hooks for that answer. A blocking Stop hook prevents acceptance. An unrelated user prompt cannot provide the answer. Failed injection, timeout, shutdown or transcript uncertainty releases the waiter and existing fold cleanup runs. Practice folds stay off pending qualification.

## Proposed Design

1. Generate a unique request ID for each handoff attempt and put it in the first line of the existing internally generated request. The request ID is correlation, never authority and never a model-generated choice.
2. Before injection, open the current transcript and capture its inode/device, byte length and newline boundary. A missing, unreadable or partially written baseline aborts before injection. For the first attempt pass expectedFromEntryId from the clean-stop snapshot: a bounded baseline-tail read on this same descriptor and size must show the VERY LAST complete record has exactly that UUID. Never search backward past unknown records. Any intervening record, missing UUID or partial boundary aborts before injection; appended bytes after the captured size go through normal request matching, never a recaptured later EOF. Require the initial setLockWindow(fromEntry) write to succeed before injection. The arm operation returns a bounded reply promise and cancel function. Use the same opened file descriptor throughout the wait; replacement, observed truncation or disappearance aborts. Required producer contract: each opened transcript inode is append-only during an attempt. Polling cannot prove absence of same-inode truncate-and-regrow between samples; no such guarantee is claimed. Document and qualify this assumption against the executing CLI before activation. A writer without that contract is unsupported until it supplies a generation signal. No fallback to hook text or an unarmed wait is allowed on the production path.
3. Read only appended bytes, up to the existing 4 MiB parsing boundary in total per attempt. If a poll observes more growth, process the permitted prefix first: a qualifying summary whose complete newline is inside the boundary wins; otherwise decline on overflow. A summary ending one byte beyond the boundary cannot qualify. This result must not depend on polling schedule. Poll every 250 milliseconds while the wait is live, reading only new bytes and incrementally parsing newly completed records only, keeping a bounded UUID map and one incomplete suffix. Ancestry walks have a visited set and a record-count bound. Keep the original five-minute capture deadline. Move the existing thirty-second lock renewal to a runner-owned hold-lifetime timer: it remains active during reply capture AND audit until live-session release/cleanup. Failed renewal marks ownership lost and cancels any current capture; an in-flight audit may finish but its result cannot authorize further injection or staging. Require a fresh generation-checked renewal before each injection/send-back and before final endpoint writing. Clear this timer on every exit and live-session release. The live phase has a hard deadline at started + RUNNER_DEFAULTS.foldDurationMs - 1000ms, strictly before the fixed fold-hold expiry. One runner-owned deadline timer cancels capture and releases live carriers through end() even if audit is still pending; late audit results cannot inject, stage or mutate the completed fold. Every held-phase asynchronous wait (including arm/open, injection and audit) is raced against terminal cancellation from deadline, shutdown or ownership loss, so runShadowFoldOnStop itself settles and boot clears inFlight even if an underlying audit never resolves. Pass cancellation into async arming so a descriptor opened late closes without injection. Detached operations have rejection handlers and no state mutation after cancellation; every resumed continuation rechecks cancellation before writes. Each await continuation and final endpoint write checks this deadline and ownership again. Do not extend any carrier beyond this bound. Fake-clock tests must prove a stalled audit cannot retain a coordinator lock while its inbound hold expires. A single read is in flight; cancellation closes once and stale work cannot settle another attempt. A failed or thrown injection cancels in finally. A stopped latch is set before unsubscribe: reject later triggers/arms and cancel an async open that resolves after shutdown before it can inject. Register ownership before awaiting open, so shutdown covers arming and armed captures alike. No event retry schedules or time-based text stability guesses.
4. Parse complete newline-delimited records only. Incomplete suffix stays pending; malformed complete records, duplicate UUIDs, unknown ancestry, oversize content or a rotated/truncated transcript terminate with unavailable, never a partial reply. Do not log transcript text.
5. Find the first main-thread user record whose complete content equals the generated injection text, including its header and request ID. It must have a UUID. Any intervening user OR assistant conversation encountered before this request aborts: the parser never scans forward to rematch a later pasted request. Only descendants of this request may answer it. The request parentUuid must equal the verified baseline expectedFromEntryId on attempt one, or the previous committed summary UUID on send-back; compare that known UUID directly even though its record precedes the appended bytes. The ancestry walk stops at this matched request after that boundary equality check. An exact request on an older branch cannot qualify. Live qualification must verify this producer relationship; unsupported variants decline. Before the request, any complete record other than that exact request aborts (supported metadata skip set is empty). After the request, a later real user prompt closes its scope. Tool-result user records consisting entirely of structured tool_result blocks may continue the scope. Synthetic hook feedback is recognized only as an isMeta===true main-thread user whose UUID is the direct parent of a Stop hook_blocking_error attachment, with both on the complete chain from the corresponding summary to its candidate. An incomplete prospective feedback chain remains pending, never accepted; incompatible user input closes scope. isMeta alone is insufficient. A pasted header before the arm offset is absent from the read. A pasted header after the scope closes never reopens it.
6. Process appended complete records in order. At each summary boundary, the candidate answer is the newest main-thread assistant message already seen in scope, regardless of stop reason. That latest message must itself end with `end_turn` (stop_sequence remains unqualified and is rejected), with exactly one text-bearing record containing exactly one text block; preceding linked records of the same message ID may contain thinking but no text. Local empirical evidence found only thinking→text or text-only, never multiple text fragments. Return that one block verbatim. Multiple text-bearing records or multiple text blocks are unqualified/ambiguous and decline, even if equal or prefix-related; no concatenation, deduplication or snapshot guessing. `tool_use` commentary is not a final answer; a summary whose nearest assistant ancestor is tool_use is nonqualifying, never a reason to select an older end_turn answer. Content records must form a valid parent chain back to the request; sidechains cannot answer the main request.
7. Completion boundary: a main-thread `system` record with subtype `stop_hook_summary` whose parent chain leads to that candidate message. The nearest assistant ancestor must equal the candidate message's last linked record UUID. Walk the complete chain, including linked hook result attachments and synthetic hook feedback. The blocking verdict applies only to the summary-to-current-candidate segment; separately validate ancestry from that candidate to the original request. An earlier blocked candidate on that longer request ancestry does not poison a later corrective answer. Reject a candidate with any linked `attachment` whose `hookEvent` is `Stop` and type is `hook_blocking_error`. Do not infer success from `failedHookErrorIndexes` or `preventedContinuation`: measured blocked examples have empty indexes and false continuation flag. Nonblocking hook errors alone do not reject the answer. Missing summaries keep the attempt pending to the bound; no individual `hook_success` substitutes for a summary.
8. A blocked candidate remains unaccepted; a later assistant answer in the same injected request may qualify once its own all-hooks summary arrives. Once the first qualifying summary is committed, capture once and return `{text, endEntryId}` where endEntryId is that committed summary UUID, together with the opened transcript identity and exact byte offset immediately after the summary newline. Before a send-back injection, arm against this previous committed cursor on the same inode and incrementally validate all intervening bytes, including audit-time growth. Any real user or assistant conversation in that gap, an incomplete record, replacement or uncertain continuity aborts before reinjection. No arbitrary metadata skip is permitted: initially the supported pre-request metadata set is empty, so any complete record before the exact next request aborts. This conservative availability restriction is explicit; the new reader starts from the previous committed cursor so a user arriving between gap validation and injection is also caught. Each send-back keeps this continuity proof back to the first attempt; it never resets eligibility by starting after unseen work. Feed text to the existing parse/verify/audit pipeline. The final accepted attempt's endEntryId fixes BOTH the fold lock-window toEntry and staged packet endpoint; do not re-read the transcript after audit to expand either endpoint. Require setLockWindow(toEntry) to return true before releasing into shadow probing or staging a packet; a refused write aborts and performs existing cleanup with no packet staged. A user turn appended during audit must remain outside both endpoints. Any later record, even one included in the same filesystem read, cannot retroactively change that captured answer. A torn suffix after a qualifying committed summary does not undo it. Match the expected Claude session ID wherever records supply one, and reject a mismatch. Duplicate UUIDs or unsupported record shapes before completion abort rather than infer safety. On each existing thirty-second renewal tick, a false renewal or missing session cancels the capture and aborts the optional attempt; never ignore lost ownership. Check capture still live before injection. Existing safety/benefit checks, hold release, grading, model provider and activation gates remain unchanged.

## Decision Points Touched

- Reply association and completion are protocol invariants; basis: enumerable-domain; evidence: request marker, UUID ancestry, explicit assistant stop reasons, explicit Stop result types and summary subtype.
- The parser decides no semantic quality. Existing verifier and LLM audit retain that job.
- Missing or ambiguous protocol evidence ends only this optional practice attempt, never blocks a person or kills a session.

## Multi-Machine Posture

The request transcript is read on the machine that owns and runs that session. No transcript is copied to another machine by this change. Existing topic lease and fold record synchronization remain unchanged. This is not a new cross-machine state store: the open descriptor and polling task are transient handles to the existing executing process. A session transfer or transcript replacement aborts the optional attempt; the new owner can perform a later attempt through normal scheduling.

## Tests and Evidence

- Unit: full reply with a preceding thinking record, exact preservation of the one qualified text block, rejection of multiple text blocks/text-bearing records (including cumulative/equal/prefix forms), tool use/result continuity, exact request ID, quoted/pasted markers, wrong/unknown/duplicate ancestry, sidechain, unrelated prompt, blocked Stop followed by clean retry, misleading summary flags, nonblocking hook failures, summary for another message, a new nonterminal assistant message before an older message's delayed summary, a user turn between the clean-stop snapshot and first arm with no injection, an assistant continuation between first arm and the exact request, never-resolving audit reaching deadline with runner promise settled and boot inFlight cleared, audit resolving after cancellation causing no later writes, right nonce/text/session but older request parent on first and send-back attempts, unsupported complete record declining immediately versus incomplete suffix waiting to bound, failed initial fromEntry write, ownership loss during audit with send-back and no reinjection, a user turn appended during audit followed by accept and by send-back, refused endpoint writes with no staged packet, identical bytes across polling schedules with summary newline exactly at and one byte beyond the byte limit, missing summary, torn/malformed records, overflow.
- File lifecycle integration: arm-before-inject immediate reply, incremental split writes and UTF-8, truncation/rotation/missing file, unchanged file does not reparse, cancellation and shutdown, a stale read cannot settle a new attempt, bounded resource cleanup. Use real temporary JSONL files and a fake clock where appropriate.
- Replace the hook-text reply fixture in tests/e2e/context-budget-fold-shadow-alive.test.ts with actual file appends and missing/truncated hook payload; this proves the actual source. Existing HTTP integration and production initialization E2E must demonstrate that the runner uses the armed transcript source when the feature is available; no test-only fallback can satisfy production wiring.
- Empirical metadata-only transcript study informs summary semantics; no copied private conversation text enters fixtures. Recorded Claude Code versions delimit known protocol evidence. Unsupported complete records decline immediately; missing summaries and incomplete suffixes wait only to the original bound. Neither accepts an unproved answer.
- Full suite through the shared coordinator; no competing manual suite.

## Maturation Plan

- **test-agent-live:** deterministic file lifecycle and production wiring checks, no live Claude calls while the current zero-Claude constraint applies.
- **dev-agent-live:** only after merge, turn-end reporter deployment and explicit measured qualification, resume a small practice run on Echo and inspect its exact request/reply association, full handoff parse, cleanup and recorded grade. Practice folds remain off until then.
- **fleet:** follows the existing folding feature ladder; no new default flip in this fix.
- **ladder:** not applicable: defect fix within the existing context-budget practice-fold feature; no new feature flag.

## Rollback

Revert the fix and keep practice folds off. No durable state format changes; no content is replicated. Existing timeout/backoff and fold cleanup remain.

## Open Questions

None for implementation. The summary-linked assembly study found 22 thinking→text and 41 text-only messages, each with exactly one text block; no multi-text assembly is qualified. Only 63 of 483 terminal assistant records in the local metadata sample had a summary; that sample has no denominator of eligible injected practice requests and is not an availability estimate. Availability remains unqualified; live qualification must measure qualifying summaries and successfully parsed handoffs per injected practice request. Empirical coverage is limited to recorded Claude Code 2.1.329 and 2.1.330 shapes. Missing summaries on other versions time out safely; additional live-version qualification remains a rollout requirement, never grounds to weaken completion checks.
