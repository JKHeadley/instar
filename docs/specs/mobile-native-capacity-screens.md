## 1. Problem

Operator request (Justin, Telegram topic 134088, 2026-11-03 22:01 and 22:55 PST): the Instar iPhone app should do every feature natively instead of opening dashboard pages. The plan of record (`.instar/lanes/app-native-coverage-plan.md`, build-order rows 6 and 9) names the next read-only rows: **Accounts usage** (which subscription accounts exist, signed in or needing sign-in, 5-hour and weekly usage with reset times), **What thinking costs** (the spend view), and **Resource usage** (CPU and memory for the server and each session).

A paired phone signs every request with its Secure Enclave device key, and `deviceAuthenticator` admits only routes listed in `DEVICE_ALLOWLIST` (`src/server/mobilePairingRoutes.ts`). What the console's Accounts, Spend and Resource usage views read is Bearer-only, so today the app can show these only through a web view.

This change is READ ONLY: no sign-in start or repair, no spending-limit, freeze or arming change, and nothing else the phone sends can change an account, a limit or a process.

## 2. What exists (instar main 8285a7ef0)

- **Accounts** (console `dashboard/console/accounts.js` + `accounts-model.js`): reads `GET /subscription-pool?scope=pool` (one row per account per machine, merged across online peers by `poolPeerFetch` with 5 s timeouts; each row spreads the whole `SubscriptionAccount` record, including `configHome` (a filesystem path), `identityDrift` evidence and other internals, plus `loginCheck`, `machineId`, `machineNickname`; `pool.failed` lists peers that did not answer), `GET /subscription-pool/in-use` (the account this machine's sessions are running on, with its email), `GET /subscription-relogin?scope=pool` (sign-in repair episodes) and `GET /pool` (machine names). The page shows each account once (its freshest usage reading), its email, its tightest usage window ("62% of 5-hour · resets 4:10 pm") and the second, the machines it works on with a signed-in / needs-sign-in state each, and a "Needs you" list of sign-ins to fix.
- **What thinking costs** (console `costs.js` + `costs-model.js`): reads `GET /routing-spend/summary` (recorded pay-per-use cost on this machine's ledger, priced on read, with each row's cost basis; dev-gated, 503 when dark), `GET /routing-spend/caps` (paid routes: committed spend against daily and lifetime caps, status), `GET /routing-spend/enable-status` (whether spending limits are on and enforcing), `GET /tokens/summary` (Claude conversation tokens in the window; Codex lifetime totals of sessions active in the window), plus background-check metrics, per-conversation token lists and the routing map. Time windows: today, 7 days (default), 30 days. The page says "Figures are this machine's own ledger."
- **Resource usage** (legacy dashboard tab `resources` and the console's machine sheet "What's using it", `machines-model.js` `usageOf`): reads `GET /resources/summary?sinceHours=1` (per source: `agent-server`, `aggregate`, `session:<sessionId>`; current, average and peak CPU % and memory). Session names come from the session list. 503 when the resource ledger is off.
- People and roles (`docs/specs/mobile-app-people-and-roles.md`): every device resolves to a person with role `owner` or `msp`. `DEVICE_ALLOWLIST` rules may carry `ownerOnly: true` (added by the native session screen, `docs/specs/mobile-native-session-screen.md`): the device check itself refuses a non-owner phone with `403 owner-phone-required` before the route runs.
- The just-built ops screens (`docs/specs/mobile-native-ops-screens.md`, PR #2706, open at the time of writing) set the pattern this spec follows: purpose-built trimmed routes, pure summarizers with an explicit field allowlist, owner-or-bearer, opaque row keys, `no-store`, a degradation on read failure.

## 3. Design

### 3.1 Three purpose-built routes, not the raw ones

New module `src/server/mobileCapacityRoutes.ts`, mounted inside `createRoutes` so it reads the SAME server-side functions the console's routes use. The existing handlers are refactored to call extracted functions, with no behaviour change to them except the peer-attribution hardening in §3.1:

| Route | Reads | Answers |
|---|---|---|
| `GET /mobile/accounts` | `subscriptionPoolScopeView()` (the `/subscription-pool?scope=pool` payload, extracted from that handler), the in-use resolver (`/subscription-pool/in-use`; the server's cached resolver, one instance for the server's life, never one per read) and this machine's sign-in repair episodes (`subscriptionRelogin.store.list()`, as `/subscription-relogin` reads them) | `{ schemaVersion: 1, generatedAt, enabled, localUnreadable, headline, needsSignIn, usable, accounts: MobileAccount[], unread: { count, names }, offline: { count, names }, truncated }` |
| `GET /mobile/spend?window=today\|week\|month` | This machine: `routingSpendSummaryResult('day', hours)` (extracted from `/routing-spend/summary`, the same call the console makes: `grain=day&sinceHours=24\|168\|720`) and `tokenLedger.summary` / `codexSummary` (`/tokens/summary?since=now-hours`). Each online peer: the same two reads over `poolPeerFetch` (bearer, 5 s timeout), as `/subscription-pool?scope=pool` does. This machine's limits: `composeCapsView()` behind the same dev gate as `/routing-spend/caps`, and the money-layer surface's `status()` (`/routing-spend/enable-status`) | `{ schemaVersion: 1, generatedAt, window: { key, label, costSince, tokensSince }, headline, recorded, limits, conversations }` |
| `GET /mobile/resources` | `resourceLedger.summary(sinceMs)` for the last hour (`/resources/summary?sinceHours=1`), session names from `sessionManager.listRunningSessions()` | `{ schemaVersion: 1, generatedAt, enabled, machine, windowHours: 1, headline, total, server, sessions: MobileProcess[], truncated }` |

An unknown or missing `window` value reads as `week` (the console's default). The window is the console's: a 24-hour window on the daily rollup includes the current and previous UTC day buckets (`sinceDays = ceil(hours/24)`), so "Today" can cover up to about 48 hours. The answer therefore returns what each figure actually covers: `window.costSince` (the start of the earliest UTC day bucket counted, `startOfUtcDay(now - ceil(hours/24) days)`) and `window.tokensSince` (`now - hours`, the exact window the token ledger uses), and the screen states both under the figures ("Cost counted from Mon 00:00 UTC, in whole days; tokens from the last 24 hours"), plus the route's own `horizonNote`. The chip keeps the console's label; the coverage line makes it honest.

Every answer always carries `schemaVersion` and `generatedAt`; the disabled shapes below list their other fields in full. Every `state` field is one of the values listed for it. The app renders any value it does not know (a newer `basis`, `status`, `state` or `signIn`) as "unknown", never as a guessed state, and ignores fields it does not know.

Each route maps the raw rows through an explicit allowlist of fields (pure summarizers, unit-tested). Nothing is spread from a source record.

- **MobileAccount**: `key` (first 16 hex of sha256 of a fixed prefix and the account id: stable across refreshes and opaque; account ids are not secret, so the hash hides nothing that matters and is not a protection), `name` (verified nickname, else verified email, else "Account name unavailable"), `email` (the account's own login email, shown the way the console shows it, only when it passes `verifiedEntityName` and a plain `local@domain` shape, length-capped at 120; else null), `kind` ("Claude", "Codex", "Gemini", "Grok", "Pi", else "Other"), `inUse` (the in-use resolver names this account AND the account has a row on this machine; the resolver reads this machine's own auth surface, so a peer's row is never "in use here"), `signIn` (`needs-sign-in` if any machine's state is `attn`; else `signing-in` if any is `working`; else `signed-in` if any machine is `ok` with the label "signed in" (status `active` AND `loginCheck: 'ok'`; an unknown status is never `ok`, whatever its check says); else `signed-in-unchecked` if any is `ok` without a passed check; else `unknown`), `windows` (each usage window on the freshest reading, `{ label: '5-hour' | 'weekly' | 'Fable weekly', pct (rounded integer, ≥ 0), resetsAt (ISO, or null) }`, highest first; from `fiveHour`/`sevenDay`/`fable`, or Codex's `primary`/`secondary`, reading `utilizationPct` or `usedPercent` and `resetsAt` or `resetsAtIso`, as the console does), `usageLine` (the console's words: "62% of 5-hour", or "No reading yet.", or for a Grok account "Usage isn't readable for this kind of account."), `tone` (`bad` at ≥ 90%, `attn` at ≥ 75%, else null), `readingAt`, `stale` (reading older than 60 minutes, the console's `READING_STALE_MS`), `machines` (`{ name, isSelf, state: 'ok' | 'attn' | 'working' | 'unknown', label }` per machine row; names verified, else "This machine" / "A machine with no name yet"). Machine state copies the console's `cellState`: a sign-in repair this machine is running for the account (episode state `approved`, `starting`, `running`, `in-progress`, `navigating` or `awaiting-code`) → `working` "signing in now" (this machine's own rows only: peers' repair episodes are not read, so a peer's row under repair shows its pool status); status `needs-reauth`, `signed-out`, `expired` or `broken` → `attn` "needs sign-in"; `active` with `loginCheck: 'signed-out'` → `attn` "login check failed" (a checked failure is never shown as signed in); `active` with `loginCheck: 'ok'` → `ok` "signed in"; other `active` → `ok` "signed in (not re-checked)"; anything else → `unknown` with the status word (status must match `^[a-z-]{1,24}$`, else "unknown"). Order: accounts needing sign-in first, then by kind, then highest usage. Cap 100 (`truncated`).
- **Accounts population.** Accounts cover this machine and the online peers (the same population as the console's Accounts page). Registered machines the pool does not count as online are not read; they are listed in `offline: { count, names }` (verified registry names; listed only when this machine knows its own id), and `offline` and `unread` come from the same peer source (`resolvePeerUrls`: within one peer snapshot a machine is either asked, and can land in `unread`, or not asked, and is `offline`, never both; the two reads take separate snapshots milliseconds apart, so a machine changing state in that instant can appear in both or neither, accepted as long-tail); a registered machine that is gone for good keeps the headline scoped until it leaves the registry (accepted: truthful, and the note names it); any offline machine scopes every conclusion "(on the machines that answered)" exactly as an unreached peer does, so an account that lives only on an offline machine can never hide behind a complete-sounding headline.
- **Peer attribution and freshness.** In the extracted pool view, a peer's rows are attributed to the peer that was asked (`p.machineId`) and named from this machine's registry, never from a machine id or nickname the peer put in its rows (the console gets the same hardening). A usage reading dated more than 5 minutes in the future is not evidence and can never win "freshest reading". Usage percentages that are not finite numbers are dropped (no reading), never shown as 0; a percentage is shown as reported (it can exceed 100).
- Accounts headline: "1 account needs signing in." / "N accounts need signing in." when any do (the phone counts accounts; the console counts account-and-machine sign-ins, so the numbers can differ, and the phone does not claim the console's count); else the console's usage headline ("Every account is nearly out.", "<name> is nearly out; others have room.", "Plenty left: the busiest account is at 62%.", "No usage readings yet."). When any machine did not answer (`unread.count > 0`), any registered machine is offline (`offline.count > 0`) or this machine's own pool could not be read, every conclusion is qualified "(on the machines that answered)", and the screen shows the partial note. `needsSignIn` counts accounts, `usable` counts accounts with at least one `ok` machine. `unread` names the PEERS in `pool.failed` by verified registry name only (count may exceed names); this machine's own `failed` row (its pool unreadable) is not a peer: it sets `localUnreadable: true` ("This machine's account list can't be read right now." when nothing else was read). A pool that is not set up answers `{ schemaVersion, generatedAt, enabled: false, localUnreadable: false, accounts: [], headline: "The account pool is not set up on this agent.", needsSignIn: 0, usable: 0, unread, offline, truncated: false }`.
- **Spend `recorded`** (proxied-on-read across machines): `{ state: 'ok' | 'off' | 'unavailable', reason, netUsd, tokens, unpricedTokens, subscriptionTokens, amortizedUsd, howWords, horizonNote, machines: [{ name, isSelf, state: 'ok' | 'off' | 'unavailable' | 'unreached' | 'offline', netUsd, unpricedTokens }], rows: [{ key, model, route, basis, usd, tokens, unpricedTokens, priceStale, notLiveYet }], truncated }`. Each machine's ledger is read on that machine; totals add the machines that answered, except `amortizedUsd`, which is this machine's declared subscriptions only (subscription costs are per-machine config and the same subscription may be declared on several machines, so it is never summed; the screen labels it "this machine"); rows with the same model, route and basis are added together across machines; each machine's own total is listed. `basis` is the console's `basisWord` (`estimated`, `provider-reported`, `subscription`, `unpriced`, `basis not stated`); `usd` is null for `unpriced` (and stays null when merged with a priced row of the same key, which cannot happen because basis is part of the key); a provider-reported row uses `providerReportedUsd`. `model` and `route` are the console's `modelWord` / `doorWord` plain names. `key` is a hash of door, model and basis. Cap 50 rows. A machine is `off` when its spend view's dev gate is closed (here: the gate check; a peer: a 503 whose error says the view is not enabled), `unavailable` when its ledger or price authority is missing, on any other 503 or failure, `unreached` when a peer did not answer, `offline` when a machine is registered in the pool but the pool does not count it as online (it was not asked; its spend is not in the totals). The machine population is every registered machine: this one, each online peer (asked), and each registered offline machine (listed, not asked; listed only when this machine knows its own id, so it never lists itself). For conversation tokens, a missing token ledger (here, or a peer's 503 from `/tokens/summary`, whose only 503 is that) reads `off` ("not tracked here"). Machine names are the registry nickname verified against the machine id and scrubbed; a peer's name never comes from the peer. `recorded.state` precedence: `ok` when at least one machine's ledger was read successfully (totals add only those machines); else `off` when every machine that was asked (offline machines excluded) is `off`; else `unavailable` (no totals are returned in `off` or `unavailable`). Merged rows carry a flag (`priceStale`, `notLiveYet`) if any contributing machine raised it.
- **Spend `limits`** (this machine's; see §5): two sources with two states, as in the console. `routesState: 'ok' | 'off' | 'unavailable'` (the caps view; `off` when the spend view's dev gate is closed), `routesReason`, `routesSentence`, `routes: [{ key, name, status: 'Open' | 'Closed' | 'Not open' | 'Frozen', committedDayUsd, dailyCapUsd, committedLifetimeUsd, lifetimeCapUsd, heldBy, committedElsewhere }]`, `storeUnreadable`, `truncated`. `heldBy` names the route's designated machine (the go-live designation `meteredLeaseHolder`, not a live lease; the app words it "designated machine"): "this machine" when it is one of this machine's ids (the money layer writes the designation with `config.machineId ?? 'single-machine'`, so both that id and the mesh id count as this machine), else its verified registry name, else "another machine" when this registry cannot name it, or null when the route has no designated machine; its id is never returned. Committed spend is booked on the designated machine, so when `heldBy` is another machine `committedDayUsd` and `committedLifetimeUsd` are null and `committedElsewhere: true` ("recorded on <heldBy>"), never this machine's $0; when there is no designated machine or it is this one, the figures are this machine's committed ledger; and `controlsState: 'ok' | 'off' | 'unavailable'` (the money-layer status; `off` when the surface is not built on this machine), `sentence`, `enforcing`, `notEnforcingWhileOn`. A route's `name` is built from the provider and route words only (`doorWord(provider) · doorWord(door)`), never from `keyRef`. `sentence` maps every lifecycle state as the console does: `enforcementReady` → "Limits are on and enforcing"; `enable-pending-restart` → "Limits are turned on but wait for a restart to start enforcing"; `probe-failed` / `construction-failed` → "Limits are turned on but not enforcing (<state>[: <component>])"; `disabled` or absent → "Spending limits are off"; any other `^[a-z-]{1,40}$` state → "Limits: <state words>", else "Limits: state unknown"; plus "; a paid route is frozen", ending "on this machine." (the money-layer status is the answering machine's own and names no holder, so the sentence never names one). `notEnforcingWhileOn` is the console's `spendingNeed`. Of the money-layer status only `lifecycleState`, `enforcementReady`, `anyKeyFrozen` and `failingComponent` (only if it matches `^[A-Za-z0-9 ._-]{1,48}$`) are read; nothing else from it is returned. Never returned: `keyRef` (hashed into `key`), `meteredLeaseHolder`'s id (only the verified name in `heldBy`), the store error text (a boolean `storeUnreadable` only).
- **Spend `conversations`** (proxied-on-read, the same machines): `{ state: 'ok' | 'off' | 'unavailable', reason, claude: { count, tokens, line } | null, codex: { count, tokens, line } | null, machines: [{ name, isSelf, state }] }` from each machine's token ledger, added across machines (state precedence as for `recorded`, computed independently from the token reads), with the console's rule that Claude and Codex are never added together (Claude counts events in the window; Codex counts each active session's lifetime). No per-conversation list, no project paths.
- Spend headline: "About $4.20 of pay-per-use cost this week on this machine." (one machine) / "… across 3 machines." (only when every machine's ledger was read) / "… on the 2 machines that answered." (whenever any machine is `off`, `unavailable`, `unreached` or `offline`, and the screen lists which and why); "No pay-per-use cost this week …" only when no tokens went unpriced, else "No priced pay-per-use cost this week …; 12k tokens had no price on file." (a $0 is never claimed for unmeasured use); "Spend figures aren't available on this agent."; "Can't tell what AI use cost."
- **MobileProcess** (resources): `{ key, name, ended, stale, cpuPercent, memoryBytes, avgCpuPercent, peakCpuPercent, peakMemoryBytes, newestAt }`. `server` is the `agent-server` source ("The agent server"); `total` is `aggregate`; `sessions` are the `session:` sources, running ones first by current CPU, highest first, cap 30. A session's `name` is its running session name (scrubbed, capped 80) or "A session that has ended" when it is no longer running; an ended session has `ended: true` and no current CPU or memory (null), only its hour's average and peak. `key` is a hash of the session id. A row whose newest sample is older than 5 minutes (the sampler runs every 30-60 s) has `stale: true` and the screen says "last read … ago" for it, never "now". `machine` is this machine's verified nickname, else "This machine". Headline: "Instar is using 12% CPU and 1.4 GB of memory now (peak 40% in the last hour)." when the total is fresh; "Last recorded 20 min ago: Instar was using … No newer reading." when it is stale; "No total reading yet." without one. A ledger that is off answers `{ schemaVersion, generatedAt, enabled: false, machine, windowHours: 1, headline: "Resource usage isn't recorded on this agent.", total: null, server: null, sessions: [], truncated: false }`.

Never returned (as fields): `configHome` or any path, account ids, machine ids (including a paid route's designated machine id), session ids, PIDs, the money-layer status's machine id and nickname, enable sources, config snapshot time, settling count and restart fields, `identityDrift` evidence, `statusCause`, email gaps, the in-use resolver's own email field, device-limit counters, credential or token fields, `keyRef`, raw error text, peer error reasons, project paths, PIDs. The only email returned is each account's own login email, which the console already shows the owner on the Accounts page.

Free text a source writes (account nicknames, model ids, session names, machine nicknames) passes through `scrubSecrets` (the shared deterministic redactor), is whitespace-folded and length-capped. All of it is display-only data, never instructions, for the phone and for any agent reading these routes with the bearer token. SwiftUI renders it as plain text.

`generatedAt` is when the answer was built (stamped inside the 15-second cache, so a cached answer keeps its build time), not how old the data is: freshness is carried by `readingAt`/`stale` per account, `unread` for peers that did not answer, and `newestAt` per process.

**Observability.** A read that throws answers `500` with a fixed error code (`accounts-unavailable`, `spend-unavailable`, `resources-unavailable`) and records one `MobileCapacityScreens.read` degradation (route and error class only, no data) through `DegradationReporter`. A spend part that throws is recorded the same way and reported inside the answer (`unavailable` with a plain reason) while the other parts still show; it does not 500 the whole answer. A peer that does not answer is named in the answer (`unread`, or a machine line `unreached`), not recorded as a degradation (it is the designed tolerant path, as for the console's pool reads).

**Cost of a read.** `/mobile/accounts` and `/mobile/spend` fan out to online peers (5 s timeout each, so a slow peer makes the read take up to about 5 s; the app's existing read client times out at 12 s). Each answer is built at most once per 15 seconds (per spend window), single-flight: concurrent and repeated reads in that time share one build, so phone refreshes cannot multiply peer reads; a failed build is not cached. The in-use resolver is the server's cached one (its own 60 s cache), never constructed per read. `/mobile/resources` is a local SQLite read.

### 3.2 Who may read them

Three entries are added to `DEVICE_ALLOWLIST`: `GET /mobile/accounts`, `GET /mobile/spend`, `GET /mobile/resources`, each `statuses: active`, `body: 'none'`, `ownerOnly: true`, not a send route, not `unassignedOk`, with one shared bucket of their own (`ownBucket: 20` per minute, `bucket: 'capacity-reads'`), so pulling to refresh never uses up the chat list's read allowance. The allowlist matches the path only; the signed path includes the query, so `?window=` is covered by the signature. The raw Bearer routes (`/subscription-pool`, `/subscription-relogin`, `/routing-spend/*`, `/tokens/*`, `/resources/*`) stay off the list.

`ownerOnly` makes the device check refuse a non-owner phone (`403 owner-phone-required`) before the route runs. Inside each route, `ownerOrBearer(req, bearerOk)` (defined in this change's module; the open ops-screens PR #2706 defines the same eight-line rule in its own module, and both stay valid whichever merges first) checks again (defence in depth): only the agent's bearer token, checked explicitly with `bearerMatches(req, authToken)` (a missing principal is never read as "bearer"; it fails closed), or a device principal whose resolved person is the owner. Everything else gets `403 owner-phone-required`. A phone whose person was removed gets `403 person-unknown`; revoked, expired, pending, unsigned, replayed or tampered requests get `401 device-unauthorized`; the notification read token gets `403`. Every answer carries `Cache-Control: no-store`.

Why owner-only: subscription accounts, money and machine load are the owner's operational view; the MSP grant switches (people-and-roles §3.5) do not cover them.


### 3.3 The app

Three SwiftUI screens in `apps/instar-ios` (agent-home repo, separate commit) in new files, reachable from the agent's detail screen through a sibling **"Capacity"** section beside "Is everything up?": **Accounts**, **What thinking costs**, **Resource usage**. Plain language; pull to refresh; no background polling. Accounts needing sign-in come first with "Signing in is done from the dashboard for now." A `403 device-not-allowed` or `404` reads "This agent's server is too old to show this here. Update the agent to see this here." `403 owner-phone-required` or `person-unknown` reads "Only the owner's phone can see this." Spend has the three window chips (Today, 7 days, 30 days). A partial answer shows a plain note naming each missing machine and why: on Accounts whenever `unread.count > 0`, `offline.count > 0` ("Laptop is offline and wasn't read") or `localUnreadable`; on spend whenever any machine is not `ok` (switched off, can't be read, didn't answer, offline). The parsing tests include an offline-only Accounts answer (no unread peers, local pool readable); a stale reading or sample says its age. Answers are kept in memory only while the screen is open (no disk cache: the URL session used is the existing ephemeral client, and the answers include login emails). Parsing is unit-tested; the new test file and parsing file are listed in `project.yml`'s test target.

## Decision points touched

| Decision | Classification | Justification |
|---|---|---|
| Device allowlist admits the three GET paths for active owner devices (`ownerOnly`) | invariant | Route-level authentication by exact path plus the resolved role, the existing deterministic device model; no competing signals. |
| `ownerOrBearer`: bearer or owner-role device only | invariant | Authorization from the authenticated principal's resolved role (Know Your Principal); deterministic, fails closed for unresolved principals. |
| Field allowlist in each summarizer | invariant | A fixed redaction contract: only listed fields leave the server. |
| Account sign-in state, usage tone, spend basis words, resource ordering | invariant | Display classification copied from the console's documented rules so phone and console agree; it gates nothing and blocks nothing. |

## Verify the state, not its symbol

No detector, gate on agent behaviour, or LLM judgment is added. The display states are symbols the owner reads:

- Account `needs-sign-in`: symbol = pool row status in the needs-sign-in set. State claimed = the login on that machine no longer works. Corroboration = the poller's `loginCheck` and status, the same signal the console shows; the phone shows "signed in (not re-checked)" (and the account `signed-in-unchecked`) when `loginCheck` is not `ok`, and "login check failed" (needs sign-in) when the check found the login signed out, so an unchecked login is never presented as verified and a failed check is never presented as signed in. Unmeasurable: a status outside the known set → `unknown` with its word, never "signed in".
- Usage percentage: symbol = the latest quota reading. State claimed = how much of the window is used. Corroboration = `readingAt` shown with it, and `stale` after 60 minutes. Unmeasurable: no reading → "No reading yet.", never 0%.
- Spend: symbol = the ledger rollup priced on read. Each row keeps its basis (estimated / provider-reported / subscription / unpriced); unpriced tokens are counted, not given a dollar figure. Unmeasurable: gate closed → `off`; no ledger → `unavailable` with its reason, never "$0".
- Resources: symbol = the newest sample per source. Corroboration = `newestAt` per row. Unmeasurable: no aggregate sample → "No total reading yet.", never 0%.

## Maturation plan

No flag, by design: the change is read-only, returns a strict subset of what the console already shows the owner, writes no state, and a revert is the whole rollback. The ladder below is a set of post-ship checks, not a gate.

- **test-agent-live:** the unit, integration and e2e tests in §6 on a real server boot: a phone paired through redeem/confirm reads all three routes (200), and the raw routes stay 403 for it. The app screens are checked in the simulator with seeded answers (screenshots), including the old-server message.
- **dev-agent-live:** (before the operator can see it) the server routes alone are invisible to the operator: only an app build with these screens shows them, and the app ships separately (TestFlight). Before an app build carrying these screens goes to the operator, Echo drives the three screens in the simulator app paired to Echo's own updated server (a device of Echo's, not the operator's phone) and records a PASS/FAIL matrix per screen (happy path, partial/peer-unreached, switched-off states, MSP refusal, old-server message). That matrix is the Live-User-Channel Proof artifact for the app build; it is tracked as an Echo commitment opened with the PR.

## Frontloaded Decisions

1. Purpose-built trimmed routes instead of allowlisting `/subscription-pool`, `/routing-spend/*`, `/tokens/*`, `/resources/*` (operator brief).
2. Read-only: no sign-in start, repair or cancel, no limit, freeze, arming or spending-switch change from the phone (operator brief).
3. Owner phones only, enforced twice (`ownerOnly` in the allowlist and `ownerOrBearer` in the route); MSP phones refused.
4. Emails: each account's own login email is returned because the console's Accounts page shows it to the owner; no other email (in-use resolver, email gaps) is returned.
5. Accounts and spend (recorded cost and conversation tokens) are pool-wide, proxied-on-read across online peers; paid-route limits and resources are this machine's (§5 gives the reason for each).
6. The spend screen carries recorded cost, paid-route limits and conversation token totals. Background-check metrics, per-conversation token lists and the routing map stay in the console for now (cheap-to-change-after: an additive field on a versioned read-only answer).
7. Sign-in repair episodes are read for this machine's own rows ("signing in now"); a peer's row under repair shows its pool status (reading peers' episodes would add a second fan-out per read). Cheap-to-change-after (an additive read-only state on a versioned answer).
8. Bearer may read the summaries too (no new power: it already reads the raw routes).
9. Row caps (100 accounts, 50 spend rows, 30 paid routes, 30 sessions), the 1-hour resource window, the 5-minute sample staleness line, the 15-second answer cache and the 20-per-minute bucket: cheap-to-change-after (display or rate limits on a read-only answer; each is one constant).
10. A separate `mobileCapacityScreens` CapabilityIndex entry with no prefix (the `/mobile` prefix stays owned by `mobilePairing`; the empty-prefix precedent of `singleMachineFailoverGap` and `missingLoginSession`), rather than editing the `mobilePairing` entry that the open ops-screens PR also edits.
11. `amortizedUsd` is this machine's declared figure only, never a sum across machines (a money figure: frontloaded, not cheap-to-change).
12. Committed spend on a paid route is shown only where it is booked: null with `committedElsewhere` on any other machine (a money figure: frontloaded). `heldBy` (a published field naming a machine) is a verified name only, never an id (identity: frontloaded).

## 4. Security

- Widened device-key access is three read-only GET paths, owner phones only (checked in the device layer and again in the route). Each answer is a strict subset of what the console already shows the owner: no paths, ids, credentials, raw errors or config fields (a paid route's designated machine appears only by its verified name, as the console's paid-route sheet shows "Held by").
- The raw Bearer routes stay off the allowlist (tests on both sides).
- MSP, removed-person, notify-token, revoked, unsigned, replayed and tampered requests are refused (tests on both sides).
- No write path is added; a POST to these paths is refused by the device check (`device-not-allowed`).
- Peer rows cannot claim another machine's identity, and a future-dated reading cannot win (§3.1).
- The spend view's dev gate is honoured per machine: where a machine's spend view is switched off its line is `off`; any other failure is `unavailable`; `recorded` aggregates by the precedence in §3.1.

## 5. Multi-machine posture

- Accounts: **proxied-on-read** through the extracted `/subscription-pool?scope=pool` fan-out (each online peer's plain `/subscription-pool`, 5 s timeout), peers that did not answer named in `unread`.
- In-use account (`inUse`): machine-local-justification: physical-credential-locality — it is resolved from this machine's own Claude login state; it is set only on accounts with a row on this machine and reads "in use here".
- Sign-in repair episodes: read for this machine's rows only. machine-local-justification: physical-credential-locality — a repair drives the login on the machine whose browser profile and login folder it uses; a peer's row shows its pool status.
- Spend recorded cost and conversation tokens: **proxied-on-read** — each online peer's plain `/routing-spend/summary` and `/tokens/summary` over `poolPeerFetch` (5 s timeout), added on read, each machine listed with its own total and state. (The console's page is still this machine's ledger; the phone shows more machines, each of which the owner can already read on that machine's console.)
- Spend limits: machine-local-justification: physical-credential-locality — the caps store, committed money ledger and money-layer status are kept where the metered credential is used (the money-layer enable surface spec declares the same key). The sentence says "on this machine"; each paid route names its designated holder (`heldBy`); a phone paired with another machine sees that machine's view of the limits, as its console does.
- Resources: machine-local-justification: hardware-bound-resource — CPU and memory samples measure this machine's processes. The answer names the machine (`machine`); a phone sees the machine it reaches, as the console says ("read on that machine").
- Device authentication: the phone's device record lives on the machine whose address it paired with. machine-local-justification: physical-credential-locality — the device key verifies only on the machine holding its record; this change adds no new device state.
- No new durable state, no user-facing notices, no generated URLs.
