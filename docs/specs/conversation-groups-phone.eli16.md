# Conversation groups from the phone, in plain words

**What this is.** Justin decided that what Instar called an "effort" is, in everyday words, a "group" of conversations. The agent already looks through the owner's conversations and suggests groups (for example, "these four chats are all about the shop launch"). Until now the owner could only see and accept those suggestions on the dashboard in a browser. This change gives the Instar phone app what it needs to do the same, and lets a group become a tracked project later. The app screens themselves come in an app update (tracked separately); this change is the agent side.

**What already existed.** The suggestions, the Accept and Reject buttons on the dashboard, and the Chief of Staff, which tracks projects: a conversation tied to a goal, a done checklist and the code repositories the work lands in. Turning something into a project needed the dashboard PIN.

**What is new.**
1. The phone can list suggestions, accept one, or reject one. Accepting is now one request to the agent, which does all the steps itself: make the group, name it, move each conversation in. The dashboard uses the same single request. Every step uses a request number worked out from the suggestion itself, so accepting the same suggestion from the dashboard, the phone, or another of the owner's machines still makes exactly one group.
2. On a group, the owner can ask "make this a project". The agent drafts it: a goal from the group's name, one "finished when the owner says so" item, and the conversation the project is tied to. The owner can put in their own goal, checklist and repositories. What the conversations are about is shown beside the draft but never copied into the goal by itself, because other people may have written that text and the goal steers what the agent does on its own afterwards.
3. The owner confirms the exact draft with Face ID on their phone. Before writing anything, the agent checks the group still matches (same name, still holds that conversation) and that the conversation is not already a project, reading its whole project history to be sure. Only then is the project created, with the same write the dashboard's PIN button makes.

**The safeguards.** Only the owner's own paired phone (or the owner's unlocked dashboard) can use these; another person's phone and the agent's own access key are refused. No job or timer accepts a suggestion, and only a Face ID tap creates a project. The draft carries its own fingerprint, so any of the owner's machines can check it, and a changed or swapped draft is refused. Only the machine currently in charge decides a project confirm, and it says so before Face ID is used rather than after. An existing project is never overwritten from what the agent can see, and if the agent cannot read its whole history it refuses instead of guessing. A slow step answers "still working" and the next call carries on; after five minutes without progress it says so plainly and keeps its place. If something goes wrong in a way the agent cannot sort out, it hands the decision back to the owner (Accept again, or Reject) instead of getting stuck.

**What is accepted, stated openly.** A project made on another machine in the last moments, which has not reached the machine in charge yet, cannot be seen there; this is how project records already work today (the dashboard has the same gap and no check at all), so this change narrows it. Suggestion decisions are still kept per machine until the separate sharing work (already in review) lands.

**What you need to decide.** Nothing beyond the standing approval: this touches no constitution file.
