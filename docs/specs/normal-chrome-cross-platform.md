# Normal-Chrome browser skill: one method for macOS and Windows

## Glossary

- **PR 2283:** the change merged on 2026-10-21 that shipped `/normal-chrome-browser` as a built-in skill with three macOS helper scripts (`chrome-launch.sh`, `chrome-js.sh`, `chrome-mainworld.sh`) under `.instar/scripts/browser/`. Spec: `docs/specs/normal-chrome-builtin-skill.md`.
- **PP:** another Instar agent, the author of the Windows driver. Its driver was code-reviewed by Echo (v5 accepted) and handed over for Instar at the operator's request.
- **Native Browser Drive / `native-drive.ps1`:** PP's Windows driver. A single PowerShell 5.1 script that drives a normally launched Chrome with real OS input (Win32 `SendInput`) and reads the page through the Windows UI Automation accessibility tree. No CDP, no `--remote-debugging-port`, no WebDriver. SHA-256 of the reviewed, live-tested file: `9bacd88a373fe524c31173906f6a667084031fd3e0b232de9b1db14bc0c99e0e`.
- **`ndrive.sh`:** the wrapper that runs `native-drive.ps1` through `powershell.exe` from WSL. The Instar entry point on Windows and the place the Instar-side rules are enforced. WSL only: it needs `wslpath`; Git Bash and other shells are untested and refused (`ERR wsl-only`).
- **The bridge:** `ndrive.sh`'s way of reaching the operator's desktop from a WSL shell that Windows runs in session 0: a one-shot Task Scheduler task registered for the current user with `-LogonType Interactive`, which runs the driver on the interactive desktop (session 1) and relays its output through files.
- **User activation:** the browser's record that a real person interacted with the page. Opening an OAuth popup, for example, requires it. Real OS input produces it; JavaScript run in the page does not.
- **Operator-active rule:** the Windows driver's refusal to TAKE keyboard focus while the operator has used the machine within the last 30 seconds (or has a full-screen window in front).
- **Migration Parity item 5:** instar's rule that updating an EXISTING built-in skill's content needs a dedicated idempotent `PostUpdateMigrator` migration, because `installBuiltinSkills()` only writes missing files.
- **Topic 128220:** the Telegram conversation where the operator asked for this.
- **The Mama PC:** the operator's Windows 11 machine where the Windows live tests run. Instar runs there inside WSL, started by `wslservice`, in Windows session 0.

## Problem statement

Instar now has two ways to drive a normal, signed-in Chrome without an automation connection, each on one operating system, each written separately:

- **macOS:** PR 2283's skill and scripts. The agent runs JavaScript in a profile's Chrome through pid-addressed Apple Events. Proven on account pages; refuses to run off macOS.
- **Windows:** PP's `native-drive.ps1`. The agent clicks and types with real OS input and reads the page through UI Automation. Proven on 2026-10-20 on a sign-in that a debug-port Chrome was refused on and on an OAuth popup that never opened under CDP, and live-tested in full on the Mama PC on 2026-10-21 (every command, every refusal, three display scalings; `VERDICT: PASS`; report `.instar/lanes/native-drive-wintest-report.md` on that machine).

The operator asked (topic 128220, 2026-10-21 17:43 and 17:49 PDT) to consolidate them into ONE method every agent gets. Today an agent on Windows has no built-in way in; worse, an Instar agent on a Windows machine runs inside WSL, where `uname` says `Linux`, so the shipped skill tells it the method is macOS-only and to report a wall. And the Mama PC test found that WSL's own route to Windows, `powershell.exe` through interop, lands in session 0 on that machine, where no desktop is visible: PP's documented WSL entry point could bind a profile and then nothing it did could reach a window. Each side also carries safety rules and lessons the other lacks: the Windows driver never takes focus from an active operator, allowlists launch flags, and never prints a secret or its length; the macOS skill has the "read the page's reason before guessing" diagnosis, verify-by-reload, the scheduling notes, and the API-token pitfall.

## Proposed design

One built-in skill, still named `normal-chrome-browser` (it is still Chrome, so no rename migration is needed), with a shared rules section, a short driver section per operating system, and the two Windows files shipped as installed helper scripts beside the macOS ones. The Windows driver ships byte-identical to the file the live test ran; everything Instar adds on Windows lives in the wrapper, which is itself live-tested on the Mama PC before the PR opens.

1. **Skill content.** `NORMAL_CHROME_BROWSER_SKILL_CONTENT` in `src/data/builtinSkillContent.ts` is restructured. The shared rules (`NORMAL_CHROME_BROWSER_SHARED_RULES`) and the Windows driver section (`NORMAL_CHROME_BROWSER_WINDOWS_SECTION`) are their own constants, composed into the full skill and into the appendix the migration adds to an edited copy (item 3), so the texts cannot drift. The frontmatter gains `metadata.instar_skill_version: "2"` (a free-form metadata map, like the `user_invocable` key every built-in skill already carries) so later content updates can key on a version instead of growing a chain of pinned hashes.
   - **Where it runs:** three cases. macOS: the Apple Events tools. Windows, reached from WSL (the shell an Instar agent on Windows runs in; any other Windows shell is refused with `ERR wsl-only` rather than guessed at): `native-drive.ps1` through `ndrive.sh`; an agent in WSL is on Windows for this skill as long as `ndrive.sh` can reach `powershell.exe`, and a session-0 shell is bridged (item 2), not refused. Linux with no Windows underneath (no `powershell.exe`): not built; the macOS tools stop with `ERR macos-only`, `ndrive.sh` with `ERR windows-only`; use the Playwright profile registry for pages that accept an automated browser, tell the operator that account pages need a normal browser this machine cannot drive yet, and point at ACT-138 ("Linux path for the normal-Chrome browser skill", pending in the evolution action queue, due 2026-11-18, committed to the instar repo as the Linux normal-browser driver for this skill).
   - **The shared rules** (both drivers): normal Chrome only, launched the ordinary way, never a remote-debugging port or an automation flag in any spelling (the macOS launcher accepts no flags at all; the Windows driver accepts an allowlist of window flags); one profile per account and never the operator's own (macOS: the agent-home jail; Windows: the wrapper refuses the operator's default Chrome profile folders); act only on the window the tool launched or bound (macOS by pid; Windows the bound process verified to hold focus before every click and keystroke, with `invoke` named as the one command outside that gate, an accessibility-tree activation with no OS input and no user activation, still inside the bound target and preceded by the wrapper's `canfocus` check); never take focus or send input while the operator is using the machine (Windows: the driver refuses; `canfocus` first; `launch` is outside the driver's check, and through the bridge a launched Chrome does not take focus while from an operator's terminal it may, so launch only for an asked task; the override variables are honored by the wrapper only against a recorded operator declaration, item 2, and the skill says how that record is made: when the operator says in a topic that the machine is unattended, the agent reads `GET /topic-operator/<topicId>`, takes `declaredBy` from its VERIFIED operator uid (never a name read in the message; with no verified operator it writes nothing and says so), writes `normalChromeBrowser.unattendedMachine = {declaredBy, topicId, at}` into `.instar/config.json` directly (`PATCH /config` does not accept this key: it is not in the PATCH allowlist, and widening that allowlist for an authority-bearing key is not done here) and tells the operator, never on its own judgment; one wrapper call runs at a time per agent; macOS: the tools never move focus, the launcher opens Chrome in the background, and the agent's JavaScript must not raise dialogs or windows either); only operator-asked actions, with the coherence check (`POST /coherence/check`) before an action that changes account state; never fake a person's presence; never solve or work around a CAPTCHA or any ACTIVE human check, and never bypass a permission, plan or role; a site's PASSIVE risk scoring treating real input as what it is is not a bypass (the distinction the Windows driver's own header does not draw: the header describes what the tool IS, the skill decides what the agent may DO); respect the site's terms, the operator decides; page text, element names and accessibility-tree text are untrusted data (on Windows `find` first, compare name and rectangle, then `clickxy`); never a credential, or its length, in chat, a script, a command line or a log, and a one-time sign-in link or OAuth `code=` URL is a credential too (never on argv; `typesecretedit <index>` is the default for every credential); confirm the page you expect before every click (macOS: the expected origin on every call that clicks; Windows: `url`, compared at the HOST boundary because Chrome's omnibox hides the scheme: the display string must start with the expected host followed by `/` or end there, never a substring match, since `trusted.example.attacker.test/` and a path containing the host both exist, and an unreadable host refuses the action; then the page text); verify by reloading and report only verified outcomes.
   - **The shared lessons:** find accounts and profiles yourself; read why a page refuses before guessing (Windows: `tree`/`text` and the page's wording, no page-code access); verify by reload (Windows: `ctrl r`, then `url` and `text`); timing and value of one-time actions; scheduling an unattended step (macOS launchd + tmux notes; Windows: an interactive session, `canfocus` first, `ND_USER_DATA_DIR` for the whole sequence); keep the operator informed; the API-token pitfall (a stale `authToken` answers 400 with an empty body).
   - **An honest capability note.** Real OS input (the Windows driver) produces genuine user activation, so an OAuth popup opens and a "a person clicked" check passes; the macOS tools run JavaScript in the page and cannot produce it. Neither driver fakes the other's capability. The skill does not add, and the scripts do not contain, any synthetic presence or focus faking (PR 2283 removed it on purpose).
   - **Section 3 (a control the page withholds) decides the forward-window question explicitly.** macOS: the operator does the one click or brings the window forward (the tools cannot and must not fake it). Windows: on an idle machine the driver may bring the bound window forward and give the real click for an action the operator asked for; what stays forbidden on both is synthetic presence signals, calling the endpoint behind a control, editing the DOM, and answering a human challenge the page presents. This supersedes PR 2283's "the operator brings the window forward" for the Windows driver, where real focus is the mechanism, not a synthesized signal.
   - **macOS driver section:** the three tools and their rules from PR 2283 (pid targeting, origin check, exit codes, activity log, Preferences first-run note, profile jail), condensed, plus the launcher's two new rules (item 2).
   - **Windows driver section:** the wrapper as the entry point and everything it enforces; the bridge and why it exists (the live test's session-0 finding, quoted); the command table; exit codes (0 / 2 / 1, and 64 for the wrapper's own refusals); the safety model as the script implements it, stated honestly (the operator-active check runs only when the target is not already in front; a window the operator opens on the bound profile counts as the target, which is why automation gets its own profile; `launch` outside the check; `invoke` outside the focus gate but behind the wrapper's `canfocus`; the per-character check is per process, not per field; `find` then `clickxy`; tokened URLs never through `nav` and `url` not printed right after an OAuth redirect; `url` is the omnibox display string; `editfields` on a page with no document exits 2 and should be polled; a launched Chrome lands behind, so `focus` or `click` first); PP's lessons (field index over coordinates; `--disable-extensions` against password-manager autofill; `AttachThreadInput` with a verified result; PowerShell 5.1 pitfalls; `WSLENV`; `canfocus` before any live test; test the idle logic read-only); what the live test covered (Windows 11, one monitor, 100/125/150 %; Windows 10 and two monitors untested); and what to check after an interrupted bridged run.
   - **Credit.** The skill and this spec credit PP as the author of the Windows tool. No site names or account identities from PP's notes appear anywhere.
   - **Recovery table** with macOS rows (from PR 2283, condensed) and Windows rows for every driver refusal and every wrapper refusal (`ERR windows-only`, `ERR profile-reserved-folder`, `ERR bad-profile-path`, `ERR bad-url`, `ERR bad-chrome-exe`, `ERR bad-argument`, `ERR state-unavailable`, `ERR busy`, `ERR session-unknown`, `ERR no-interactive-desktop`, `ERR no-interactive-session`, `ERR bridge-unavailable`, `ERR bridge-timeout`, `ERR canfocus-failed`, `ERR wsl-only`, `ERR driver-crash`, `ERR secret-shaped-url`, `ERR bad-outfile`, `ERR expected-host-mismatch`, `ERR expected-host-unreadable`, `ERR unknown-outcome-unchecked`, `ERR driver-timeout`, the `canfocus` refusal before `invoke`); a unit test asserts every `ERR` token the wrapper can emit appears in the skill text.

2. **Helper scripts.** `BROWSER_SCRIPT_NAMES` in `src/commands/init.ts` grows from three to five: `native-drive.ps1` and `ndrive.sh` join the macOS three in `src/templates/scripts/browser/`, installed by the same `installBrowserScripts()` (both init paths, `refreshScripts()`, `PostUpdateMigrator.migrateScripts()`), always overwritten on update. All five land on every platform (the installer is platform-neutral and byte-preserving: UTF-8 read and write, LF kept, no BOM added; each script refuses the wrong platform itself). `MACOS_BROWSER_SCRIPT_NAMES` names the three the shell-driving tests run.
   - `native-drive.ps1` ships **byte-identical** to PP's reviewed v5 (SHA-256 `9bacd88a…`): the file the Mama PC live test ran is the file every agent installs, and a unit test pins the hash. It keeps its allowlist of launch flags, its target binding, its foreground gate before every `SendInput` burst, its operator-active rule, and its never-print-secrets behaviour. Its header's description of passive bot scoring stays as PP wrote it; the skill text carries the rule that governs use. The file is UTF-8 without a BOM; its non-ASCII bytes are all in comment lines (PowerShell 5.1 reads them as ANSI, harmlessly), which is the state the live test exercised. The two diagnosability suggestions in the live-test report (a session check at bind time; naming the session in the "no visible window" message) are answered by the wrapper's session detection rather than by editing the driver.
   - `ndrive.sh` is where Instar's rules live on Windows (the driver takes any directory, any url and any executable; the wrapper does not), in this order; an argument refusal exits 64 before PowerShell runs, a safety or busy refusal 2, a state, bridge or crash failure 1, as each item states:
     - **Platform:** no `powershell.exe` reachable → `ERR windows-only` (exit 2), naming the macOS tools; no `wslpath` → `ERR wsl-only` (exit 2): every Windows path the wrapper hands over or reads back is translated with it, Git Bash has none and has not been run against (ACT-140's test plan names a Git Bash row).
     - **Argument hygiene:** the driver joins Chrome's command line from strings (PowerShell 5.1's `Start-Process` does not quote), so a double quote, a backtick or a control character inside a profile path, a url or the chrome.exe path could close a token and smuggle a flag; all three refuse those characters, no argument at all may carry a newline, and the two numeric knobs (`ND_BRIDGE_TIMEOUT`, 10–900 s; `ND_LOCK_WAIT`) must be integers before they are interpolated anywhere (`ERR bad-argument`). The checks run in this order: newline on every argument, the command name included (first, so no value is echoed back in a refusal before it is known to be a single line); no argument after the command name may start with `-` and there are at most three (PowerShell binds a dash-led argument as a NAMED parameter before the positional ones, so `target -Cmd nav -A1 <url>` would have run `nav` past a call classified as `target`; the driver's flags are set only through `ND_*` variables); the knobs; profile, url, chrome.exe for the command's own slots; `ND_USER_DATA_DIR`.
     - **Profile jail** (`launch`/`attach`'s first argument and `ND_USER_DATA_DIR`): the operator's DEFAULT profile folders of Google Chrome (`…\Google\Chrome\User Data`, `…\Google\Chrome`, and the Beta / Dev / SxS variants) and of Chromium (`…\Chromium\User Data`; the driver binds any `chrome.exe`), either slash, the whole path lower-cased → `ERR profile-reserved-folder`; anything that is not an absolute drive-letter path (`C:\…` or `C:/…`) on the local Windows filesystem (a relative or WSL path, a `\\server` or `\\wsl.localhost` share), or that carries a `..` component or an 8.3 `~` alias → `ERR bad-profile-path`. A trailing backslash is stripped before the driver sees the path (a `\"` would escape the driver's closing quote). An operator Chrome running with a custom `--user-data-dir` is outside this rule, which is why the skill says automation gets its own profile.
     - **Url rule** (`launch`'s url, `nav`'s url): a scheme (`https://`, `http://`, `about:`, `chrome://`, `file://`, case-insensitive) and no whitespace or quote → otherwise `ERR bad-url`. For `launch` this closes the flag channel; for `nav` (typed into the omnibox) it keeps the argument a URL. A url whose query OR fragment carries a credential-shaped key (`code`, `token`, `access_token`, `id_token`, `refresh_token`, `oobCode`, `api_key`, `apikey`, `key`, `secret`, `password`, `otp`, `auth`, `sig`, `signature`, `ticket`, `assertion`, `session`; after `?`, `&`, `#` or `;`, percent-encoding in the name decoded first, with literal backslashes doubled before the `%b` decode so a `\c` or any other escape in the url cannot truncate what the check sees, and lower-cased AFTER decoding so `%43ode` is `code`) is refused on both (`ERR secret-shaped-url`, exit 64), and NO url refusal echoes the url (a malformed one may carry a credential too): a url on argv is readable by every process on the machine, so the rule "a tokened URL never goes on argv" is enforced as far as a name list can enforce it; the check is bounded (a path-segment token or an unlisted name passes) and the wrapper's own argv has already carried the value by the time it runs, so the skill keeps the rule in the agent's hands and says what to do instead (the operator opens the link in their own session, or `nav` to the page without the parameter). The same rule, same list, no echo, is in `chrome-launch.sh` for macOS. `ndrive.sh url` redacts the VALUE of such a parameter in its output (`code=<redacted>`), and when the DECODED output carries a credential-shaped name the literal pass could not see (a percent-encoded name), every parameter value on that line is redacted instead; the output-side twin, bounded the same way. The skill's host-boundary check on `url` (and `ND_EXPECT_HOST`) matches an expectation written the way Chrome displays the host, port included and punycode as punycode; a display with an unexpected port, or a Unicode-rendered international name (which an ASCII expectation cannot express), does not match, and the skill says that refusal is expected, what to read next, and never to call it a wall.
     - **chrome.exe rule** (`launch`'s optional third argument): an absolute local path ending in `\chrome.exe` → otherwise `ERR bad-chrome-exe` (a wrapper script could add any flag).
     - **Outfile rule** (`text`/`tree`/`shot`'s outfile): an absolute local Windows path with no `..`, `~`, `.` segment, doubled separator, wildcard character (`*`, `?`, `[`, `]`: the frozen driver writes with a wildcard-expanding `-Path`), component ending in a dot or a space (Windows strips them, so the spelling would not name what it says) or quote → otherwise `ERR bad-outfile` (exit 64); the driver opens it from its own session, where a `\\wsl.localhost` path is untested, so the skill's "local path only" is enforced rather than remembered. The profile jail refuses the same alternative spellings (`.` segments, doubled separators, trailing dots or spaces in a component, wildcards) rather than normalizing them, so no spelling of the operator's default folder gets past the reserved-folder patterns.
     - **Command name:** canonicalized to lower case and allowlisted against the driver's commands before any slot check (`ERR bad-argument: unknown command`, exit 64): the driver's own `switch` is case-insensitive, so `LAUNCH` would otherwise have reached it past the launch-slot checks.
     - **The secret line** (`typesecret`/`typesecretedit`): read ONCE by the wrapper, for both routes, before anything is sent: nothing on stdin, an empty line, or a line with a character outside printable ASCII is refused (`ERR bad-argument`, exit 64, the value never echoed). The driver would clear the field and type "" for an empty line; a non-ASCII line was MEASURED on the Mama PC (second wrapper run) to arrive as its UTF-8 bytes and be typed wrong, silently (15 characters became 19), so it is refused rather than typed wrong; the assigned path for a credential that genuinely contains such a character is that the operator enters that one value themselves in the window, which the skill's recovery row says. A non-ASCII TEXT argument (`type`, `find`, `click`, …) is passed with a stderr warning: argv transit was not measured. The direct route feeds the line to the driver's stdin; the bridge writes it to the per-call stdin file. "Control character" in these rules means every ASCII control byte (`[[:cntrl:]]`), not only newline and tab.
     - **Focus-override gate:** `ND_ALLOW_FOCUS_STEAL`, and an `ND_OPERATOR_IDLE_MS` below the 30000 ms default, pass through only when `.instar/config.json` carries `normalChromeBrowser.unattendedMachine` as an object with a non-empty `declaredBy` string, a non-zero integer `topicId` (JSON number, not a string) and an `at` that parses as a past timestamp no older than 30 days (a declaration expires and is re-recorded on a fresh instruction; the shape the skill tells the agent to record on the operator's instruction; a bare `true`, a missing `at` or a wrong type is not accepted); otherwise the variable is dropped with a warning and its NAME is recorded in the activity line. Raising the threshold is always allowed. Reading the record needs node; without node the machine is treated as attended, with a warning saying why. This is a cooperative boundary like the binding file (the file is agent-writable; the gate proves a current record of the right shape exists, not who wrote it): it exists so the decision is a recorded, dated one, not an env var set mid-run.
     - **Per-agent binding file:** `%LOCALAPPDATA%\native-drive\instar-<agent>-<hash>\target.json` (the agent home's basename plus 8 hex of the full home path, so two homes with one basename never share state), a local Windows path like the driver's default (never a `\\wsl.localhost` share, which the driver has not been run against), so two AGENTS on one Windows account cannot rebind each other's target; the sessions of one agent share it on purpose (one agent, one actor), and a scripted sequence sets `ND_USER_DATA_DIR` for the whole sequence so a rebind by anyone else cannot redirect it. `%LOCALAPPDATA%` is read from PowerShell once with stdin closed, must be a plain drive-letter path (no quote, backtick, `;`, `&`, `|`, wildcard character or control character, the wildcard rule because the frozen driver writes the binding file with a wildcard-expanding `-Path`; an apostrophe, as in a user named O'Brien, is fine because every PowerShell interpolation is single-quote-doubled and the VBScript line is a double-quoted literal from which `"` is already refused), and is cached at `.instar/state/native-drive/localappdata.txt`; a cached value that is not such a path or whose directory no longer exists (checked through `wslpath`) is re-probed. When it cannot be read at all the wrapper refuses (`ERR state-unavailable`, exit 1) rather than fall back to the driver's shared per-user default; the same token covers a lock pid file that cannot be written and an orphan check that answered nothing. A caller's `ND_STATE_FILE` wins once it passes the outfile rule (a clean local Windows path, so a `\\wsl.localhost` path cannot slip in by mistake); an explicit override pointing at a shared file is the caller's deliberate choice to share binding state, and forfeits the per-agent isolation, which the skill says.
     - **One call at a time per agent:** two sessions of one agent calling the wrapper at once would interleave real input on the same bound Chrome (one session's Ctrl+L mid-way through another's `typesecretedit`), which the driver's per-character check cannot see because the target still holds the foreground. A per-agent lock (`.instar/state/native-drive/lock.d` under the agent home, holding a file NAMED after the owner's pid, `pid.<pid>`) serializes calls, waiting up to `ND_LOCK_WAIT` (90 s; 0–900, `ERR bad-argument` beyond) before `ERR busy` (exit 2; the message names the lock path and how it is reclaimed). The protocol uses two atomic primitives and never renames: `mkdir` creates the lock for exactly one caller; a reclaim removes exactly the DEAD owner's pid file, by its name, so a live owner's file is never touched, and then `rmdir`, which succeeds only for an empty directory (if any other pid file has appeared, the directory stays and is re-read). A lock with no pid file (its owner killed between `mkdir` and the file's creation, a window of microseconds; a failed creation gives the lock back at once) is reclaimed once it is older than the wait and in no case under 5 s (seconds-granular mtime: a lock created an instant ago cannot be reclaimed before its pid file lands, whatever `ND_LOCK_WAIT` says); the owner reads its file back after creating it, retries the acquisition if a waiter removed the fresh lock in that instant, and gives the lock back and retries if a second pid file sits beside its own (the directory was replaced under one of them), so two callers never both hold it; every loop iteration that does not reclaim sleeps and counts, so the wait is bounded by `ND_LOCK_WAIT`; a call removes only its own pid file and then the directory if empty. The lock is held for the whole call, including a bridged wait. Two more things can run a driver this lock does not see, and both are checked by the orphan guard before anything is sent, ONCE per call on BOTH routes (a direct call from an operator terminal included): this agent's scheduled tasks still RUNNING (a bridged driver can outlive a killed wrapper), and a driver an earlier call wrote down as possibly still running after its own timeout (`.instar/state/native-drive/survivor`: pid, start time or `-`, and the wrapper's epoch; checked by name and start time, treated as alive when the start time is unrecorded or unreadable, removed when gone, and a start-time-less record is decided by the live process's own start time: a powershell on that pid that started AFTER the record was written is a different process and the record is dropped, one that started before is treated as the driver; only when the start time cannot be read at all does record age decide, at 1200 s, the one age-based assumption left). The guard runs the 4 s `Get-ScheduledTask` enumeration (measured in the second live run) only when something on disk says an earlier call was interrupted: a bridge work folder left behind (a bridged call creates its folder BEFORE registering its task and removes it only at its own end, after the task is unregistered, so a killed wrapper leaves one), a survivor record, or a lock just reclaimed from a dead owner; with none of those, no bridged task of this agent can be running and the enumeration is skipped. Either orphan is waited for up to `ND_LOCK_WAIT` and then refused with `ERR busy`; an enumeration or probe that answers nothing usable (after one retry, the same retry the session probe has; the enumeration runs under terminating errors and prints a count only after it succeeded) is UNKNOWN and refuses with `ERR state-unavailable` (exit 1), never "no tasks". A wrapper killed by a SIGNAL while its bridged call is in flight (the Bash tool's timeout, a tmux kill) runs its exit trap: the trap truncates the secret file, LEAVES the work folder as the leftover marker (it removes the folder only when `rc.txt` exists, or when no pid and no launch marker were ever written), writes the driver's pid and start time to the survivor record, sets the unknown-outcome latch when the interrupted command was an input command, and releases only the lock; the PowerShell poll it leaves behind writes its verdict into the folder (`verdict.txt`) when it ends, and the next call's sweep adopts a `driver-still-running`, `driver-unverified-live` or verdict-less pid from any leftover folder into the survivor record (and sets the latch) before anything else, so a killed wrapper never hides a live driver. A latch or survivor write that FAILS keeps the work folder as the marker and says so on stderr, never silently. A bridge root `wslpath` cannot translate is UNKNOWN too and refuses (`ERR state-unavailable`), never "no leftovers". Both waits are bounded on wall time (`date`), not on iterations, because each probe round itself costs seconds. The DIRECT route runs the driver under coreutils `timeout` for the same `ND_BRIDGE_TIMEOUT` (present in WSL; where it is missing the wait is unbounded and the skill says so), with stdin from `/dev/null` for every non-secret command (a tty read inside `timeout`'s process group would stall on SIGTTIN) and `-k 10` (TERM at the deadline, KILL ten seconds later, so an ignored TERM does not leave the wait unbounded): a driver that does not finish has its WSL-side process ended and the call answers `ERR driver-timeout` (exit 1, latched), so a hung driver cannot hold the per-agent lock; whether the Windows driver ends with its WSL-side process is UNMEASURED (the direct route under `timeout` has not run live), and the direct route records no pid, so a driver that outlives it is a stated window below. Stated windows: a task the scheduler's own execution limit stopped is no longer Running, and whether that stop ends a driver or a Chrome the runner started has not been measured (the wrapper's own timeout fires first and handles the driver by pid); a recycled pid can look alive for one wait; a DIRECT-route driver whose wrapper was killed by ANY signal (the trap runs but has no folder or pid to record on that route), or that outlived the direct route's `timeout` (the WSL-side process is signalled, not re-checked), leaves no folder, task or record, so the next call does not see it (only the latch, on the timeout, holds input until a read); a driver whose pid the runner never recorded (the launch marker exists, the pid file does not) is reported as an unknown outcome and latched but is invisible to the orphan guard; a `.ps1` called directly bypasses all of it. The spec's claim is therefore "one driver at a time per agent, within those named windows", not "sessions never collide".
     - **`WSLENV`:** the five `ND_*` names are APPENDED to a caller's value, never overwrite it (an environment variable reaches the Windows process only when `WSLENV` lists it).
     - **`canfocus` before `invoke`:** the wrapper runs the driver's read-only `canfocus` first and refuses (exit 2) when the operator is active, because `invoke` sits outside the driver's foreground gate and can open a window. Only exit 2 from `canfocus` means "operator active"; any other failure of that pre-check (a bridge error) is relayed with its own message as `ERR canfocus-failed`, never mislabelled. Through the bridge that is two task round trips, so the check-to-act window is a few seconds wide; the skill says so. The per-agent lock's liveness check is `kill -0` on the recorded pid; a recycled pid can make a dead owner look alive for one wait, then `ERR busy`: the safe direction, stated in the wrapper.
     - **The bridge:** the wrapper reads its PowerShell's Windows session id (stdin closed), once more if the answer is empty (the first wrapper live run saw an empty answer in about 2% of calls, and an earlier wrapper then went direct and launched Chrome invisibly into session 0: bug 2 of that run). A session id that still cannot be read is refused (`ERR session-unknown`, exit 1) unless `ND_BRIDGE=direct` (a terminal the operator opened) or `ND_BRIDGE=task` is set; `ND_BRIDGE=direct` is honored ONLY for an unreadable id, and a MEASURED session 0 refuses it (`ERR no-interactive-desktop`, exit 2), since a direct `launch` there is exactly the invisible Chrome of bug 2. In session 0 (or with `ND_BRIDGE=task`), it first checks that a user is logged on to the desktop (an `explorer.exe` in a session other than 0; otherwise `ERR no-interactive-session`, exit 2, rather than a timeout) and that `wscript.exe` exists (a removable feature on new Windows builds; otherwise `ERR bridge-unavailable`); each probe answers yes or no by exit code, and a probe that fails to RUN (any other exit, the interop hiccup) is retried once and then reported as "could not probe" (`ERR bridge-unavailable`, exit 1), never as the negative fact. a caller's `ND_SCRIPT` is used as given) with `-WindowStyle Hidden`, writes a launch marker (`launching.txt`), touches the process handle and arms a trap that ends the just-started driver if recording its pid fails (`$null = $p.Handle`: in PowerShell 5.1 a `-PassThru` object without a cached handle reads `ExitCode` as null once the process has exited, which the second wrapper run measured as a 0-byte `rc.txt` on every bridged call, so every success relayed as `ERR driver-crash`), records the driver's pid to `pid.txt` and its start time to `pidstart.txt`, then waits for THAT process only (`WaitForExit()`, never `Start-Process -Wait`, which waits for descendants and so never returned for `launch` while Chrome lived: bug 1 of the first wrapper run) and records its exit code to `rc.txt`, with stdout/stderr redirected to `out.txt`/`err.txt`, all under `%LOCALAPPDATA%\native-drive\instar-<agent>-<hash>\bridge\<run>\`; the driver's stdin is `stdin.txt` in that folder (always present; it carries exactly one line for `typesecret`/`typesecretedit`, kept even when the caller's `printf '%s'` sends no trailing newline, and never empty for a secret command, since the wrapper refused an empty or missing line before anything was sent; empty for every other command; overwritten and deleted with the folder when the call ends; every relay file is read and written by literal path, so a `[` or `]` in `%LOCALAPPDATA%` is not a wildcard); the `ND_*` variables are set in the runner; the task is unregistered in a `finally`; the wrapper waits up to `ND_BRIDGE_TIMEOUT` (120 s) for `rc.txt`, relays `out.txt` and `err.txt`, and exits with the relayed code when it is a real 0-255 code (anything else, a negative crash code or an empty file, is `ERR driver-crash`, exit 1, never folded modulo 256 into a success; ## Verify the State, Not Its Symbol (P20)

- **`url` (Windows) / `location.href` (macOS)** is a SYMBOL of which page is showing; the STATE is what the page says. `url` is the omnibox's display string (no scheme), so it is compared at the host boundary (prefix `host/` or the bare host), never as a substring. Corroboration: read the page text after a reload (`text` on Windows; `document.body.innerText` on macOS). Unmeasurable (`omnibox not found`, `NO_PID`, `ERR no-result`): exit nonzero, report "could not read", never "done".
- **Exit 0 from `click`/`type`** means the input was sent to the target window, not that the page accepted it. Corroboration: reload and re-read. The skill says a toast or a "clicked" line is not proof.
- **`find`'s printed name** is the page's own label. Corroboration: the rectangle and the surrounding `text`; then `clickxy` those coordinates rather than trusting a substring match.
- **`canfocus` → yes** means the session's last input was older than the threshold OR was the driver's own; it is not proof the operator is away. Unmeasurable: the driver fails closed (refuses input) when the foreground check fails.
- **The bridge's `rc.txt`** is the symbol of a completed driver run; the state is the driver's exit code and output. Corroboration: `out.txt`/`err.txt` are relayed with it. Unmeasurable (no `rc.txt` within the timeout): `ERR bridge-timeout`, exit 1, worded as an UNKNOWN outcome (the driver may still be acting); never a relayed success, and never an automatic retry.
- **The PowerShell session id** is the symbol; the state is "this process can see the desktop". Corroboration: the live tests measured `EnumWindows` = 0 and `GetForegroundWindow` = 0 from a session-0 shell and a working desktop through the task (the wrapper run's `target` returned a real window handle through the bridge). Unmeasurable (the probe prints nothing, which the wrapper run saw in about 2% of calls): the wrapper probes once more, then REFUSES (`ERR session-unknown`) unless `ND_BRIDGE=direct` or `=task` is set; it never falls through to the direct path, because the first wrapper run showed that path launching an invisible Chrome into session 0. **An `explorer.exe` outside session 0** is the symbol of an interactive logon; the state "the desktop is usable" is not fully proven by it (a locked screen passes), so the driver's own checks and the timeout remain the backstop.
- **`open -g`** is a flag (symbol); the state is "the frontmost application did not change". Corroboration: checked live during the build (System Events frontmost process before and after a fresh-profile launch) and recorded in the build report.
- **The live-test `VERDICT: PASS`** lines are symbols; the state is "the shipped bytes passed". Corroboration: the SHA-256 values in each report equal the shipped files' pinned hashes (the driver report already does; the wrapper report must), plus per-command outcomes. Unmeasurable (no report, or no hash): blocked-on-gate, never PASS.
- **The migration's hash check** proves the installed bytes equal the first shipped bytes; it does not prove the agent never relied on them. That is why only an exact match is replaced and an edited copy only gains an appendix.
- **The `ndrive.sh` activity line** records what the wrapper saw (command, exit code, route, override names); it is a durable trace that makes reports checkable, not proof of what the page did.

## Multi-machine posture

Default posture is unified: the skill, the CLAUDE.md section and all five scripts are shipped content, identical on every machine through the normal update path (no state). The surfaces that are not unified:

- The browser profiles both drivers act on.
  - machine-local-justification: physical-credential-locality impossible-because="a signed-in Chrome profile's cookies are encrypted with the OS user's keystore (macOS Keychain / Windows DPAPI) on that disk; a copied profile cannot decrypt them, and the skill says never to copy a profile between machines" permanence=permanent
- The Windows binding file (`%LOCALAPPDATA%\native-drive\instar-<agent>-<hash>\target.json`) and the driver's own-input tick file beside it.
  - machine-local-justification: hardware-bound-resource impossible-because="they name a live browser process id and an input tick of one Windows session on one machine; neither exists anywhere else" permanence=permanent
- The wrapper's `%LOCALAPPDATA%` cache (`.instar/state/native-drive/localappdata.txt`, gitignored), its per-agent lock directory (`.instar/state/native-drive/lock.d`, removed when the call ends), its survivor record (`.instar/state/native-drive/survivor`: the pid and start time of a driver that may have outlived its timeout, removed when that process is gone), its unknown-outcome latch (`.instar/state/native-drive/unknown-outcome`, removed by the next successful page read) and the per-call bridge work folder (`…\bridge\<run>\`: `native-drive.ps1` (the per-call local copy of the driver), `runner.ps1`, `run.vbs`, `stdin.txt`, `pid.txt`, `pidstart.txt`, `out.txt`, `err.txt`, `rc.txt`, `bridge.out`, `bridge.err`, deleted when the call ends or swept by a later call).
  - machine-local-justification: hardware-bound-resource impossible-because="the cache names a folder of one Windows user profile on one disk and is re-probed when stale; the lock, the survivor record and the latch name live process ids and the page state of one machine's browser; the bridge folder carries one call's files for one interactive session and is deleted with the call" permanence=permanent
- The unattended-machine record (`normalChromeBrowser.unattendedMachine` in that machine's `.instar/config.json`, a per-machine file).
  - machine-local-justification: hardware-bound-resource impossible-because="it declares that ONE machine's keyboard and screen are unattended, which is a fact about that hardware and nothing else; the skill tells the agent to write it on the machine the operator means, never on the machine that happens to serve the topic" permanence=permanent
- The activity log (`.instar/logs/normal-chrome-browser.jsonl`, written by the macOS tools and by `ndrive.sh`): proxied-on-read. It is an operational record of calls made on that machine, read across machines through the existing file API (`GET /api/files/download?path=.instar/logs/normal-chrome-browser.jsonl`), which is how this spec's own gates read the Mama PC's reports.

No user-facing notices, no durable topic state, no generated URLs.

## Alternatives considered

- **Two skills (`normal-chrome-browser` for macOS, a new one for Windows).** Rejected: the rules and lessons are the same method; two skills would drift, and an agent in WSL would still read the macOS skill first.
- **Rename the skill to something platform-neutral.** Rejected: it is still Chrome, and a rename needs a migration that moves or removes the old skill directory on every agent, for no behavioural gain.
- **A dispatching façade (`browser <cmd>`) over the two command surfaces.** Rejected for now: the two drivers do different kinds of thing (evaluate JavaScript in a page vs. send OS input and read an accessibility tree), so a common verb set would hide which capability the agent is using, which is exactly what the honest capability note exists to make visible; and a façade is a third surface to test on both platforms. The shared rules and shared lessons are the merge; the command surfaces stay honest about their mechanism.
- **Edit `native-drive.ps1` (a URL-scheme check in `launch`, a Chrome-folder refusal, a reworded header, an `F5` key, a session check at bind time).** Rejected: the live test ran on PP's v5 bytes and the shipped file must be the tested file; every one of those protections is enforced in the wrapper instead, the header's description is answered in the skill text, reload uses the existing `ctrl r`, and the session condition is detected by the wrapper before the driver is ever called.
- **An existing UI Automation library (FlaUI, pywinauto).** Not used: PP's driver is in-box PowerShell 5.1 and .NET with no package install and no admin, which is what an operator's Windows machine can be assumed to have; a library would add an install and update surface per machine for a capability the driver already provides.
- **An operator-idle check around every macOS Apple Event.** Rejected: the macOS tools never move focus or send OS input; the only focus-taking step was the launch, which `open -g` fixes. An idle check around JavaScript that runs in a background tab would refuse harmless reads.
- **The binding file on the agent home via a `\\wsl.localhost` UNC path.** Rejected in favour of a per-agent folder under `%LOCALAPPDATA%`: the driver's file I/O has only been run against local paths, and a failure there would break the primary Windows path untested.
- **Refusing to act from a session-0 shell and telling the agent to find an interactive terminal.** Rejected: on the operator's own Windows machine Instar is started by a service and there is no such terminal; the bridge is the in-box route the live test proved, and it is what makes the method reachable for an Instar agent at all.
- **Refusing to run the Windows driver until a PASS lands (on BLOCKED).** Not chosen: the operator's standing instruction for BLOCKED is to open the PR with the Windows half marked not yet live-tested; the mark is made in-band (the wrapper prints it) and the re-test has a tracked closer.
- **A session component in the binding-file name.** Not chosen: one agent is one actor; the per-agent lock serializes its calls, and `ND_USER_DATA_DIR` for a scripted sequence is the stated per-sequence guard; the claim is "two agents" plus "one call at a time".
- **A persistent interactive-session broker** (one long-lived logon task in session 1 serving a file queue) instead of a one-shot task per call. Not chosen now: it would remove the ~5 s per-call registration cost and most of the stale-sweep machinery, but a resident input-capable process is a larger standing surface than a task that exists for one call, and it needs its own liveness, restart and shutdown story; a per-call task is what the live tests proved. Recorded under ACT-140 as the thing to weigh if the per-call cost becomes the limit.
- **Supporting Git Bash as a second Windows shell.** Not chosen: an Instar agent on Windows runs in WSL, every live test ran from WSL, and under MSYS the path translation the wrapper relies on does not exist; the wrapper refuses rather than guess.
- **Adding `normalChromeBrowser` to the `PATCH /config` allowlist.** Not done: in that allowlist the authority-bearing sub-keys are fenced one by one (`OPERATOR_ONLY_SESSION_KEYS`, `intelligence.*` but `selfActionGovernor`), and money and mandate state live outside it entirely; the unattended-machine record IS authority for the override, so it belongs with the fenced state, not the patchable keys; the skill writes the file directly on the operator's instruction, on the machine the operator means, the way other authority-bearing config is handled. No server route is built for it: the write is one key in one file on one machine, which the agent already does, and a route would add a second writer to authority-bearing state without removing the file edit.
- **A per-call server-side coherence check inside the wrapper.** Not done: the wrapper has no server token in every call path (a bare tmux or Task Scheduler context), and the Coherence Gate is a conversational-context judgment; the shared rules name `POST /coherence/check` before an account-state change as the agent's step, the same posture PR 2283 took.

## Side effects and rollback

- Existing agents: the installed `normal-chrome-browser/SKILL.md` is replaced when it is byte-identical to the first shipped version, otherwise it gains the appendix (Echo's edited copy is modified in that way) and a `SKILL.shipped.md` sibling; two new scripts appear under `.instar/scripts/browser/`; `chrome-launch.sh` is refreshed (url rule, `open -g`); the CLAUDE.md section is replaced in place when it is the shipped v1 text, otherwise added beside the edited one; the shadows lose an exact v1 copy and gain the new section. On a Windows agent the first bridged call creates `%LOCALAPPDATA%\native-drive\instar-<agent>-<hash>\` and a one-shot scheduled task per call that is unregistered when the call ends.
- The seven-dimension side-effects review is `upgrades/side-effects/normal-chrome-cross-platform.md`; its under-block items name what the wrapper does not cover (a caller who edits the wrapper or calls the `.ps1` directly; the same-profile case where the operator uses the bound window; an operator Chrome on a custom profile directory; a kill between the stdin write and the exit trap; the agent-writable config record).
- Rollback: revert the release. The installed files are inert. The previous release's `migrateClaudeMd` sniff looks for the OLD heading, so after a revert the v1 section is appended again beside the new one, and the two disagree on platform ("macOS only" vs "macOS + Windows") until the next upgrade, whose stale-v1 removal fixes it; the skill copy is not reverted (the old release's migrator does not touch it) and the new scripts stay in place (harmless).
