**Constitutional fit:** The primary parent is **Structure beats Willpower**: durable delegation edges, corrections, and source-linked digests carry an effort across session boundaries instead of asking each new session to reconstruct the organization from memory. **The Body and the Mind** determines the authority split: storage and exact graph invariants are structural, while semantic placement and “meaningful change” require contextual judgment with evidence and correction. **Near-Silent Notifications**, **An Instar Agent Is Always a Multi-Machine Entity**, and **Cross-Store Coherence Is an Invariant** constrain the notification, replication, and projection seams below. This feature advances a coherent agent that can preserve and surface its work without demanding the operator reconstruct it each morning.

## Frontloaded Decisions

1. **Effort is its own thin graph node.** It may link to an Initiative, which remains the work-status authority. An unlinked effort may hold an explicit outcome and next action. This avoids forcing every conversational grouping into TaskFlow while preserving project/task tracking.
2. **One primary placement, many cross-links.** The default Conversations tree contains each effort or conversation once. Other effort memberships and sibling/dependency relations appear as labeled links. A conflict retains the last agreed placement until resolved.
3. **Owner-first dashboard, role-aware mobile.** The ordinary dashboard API token is also available to agents and does not prove a human unlock. The existing `/dashboard/unlock` issues a separate short-lived `operatorSessionToken`; the server verifies it through `verifyDashboardOperatorSession` using the `x-instar-operator-session` header. The first dashboard hierarchy is an owner view behind that proof. MSP mobile views use the existing device person and grants. A shared, multi-person dashboard graph waits for a real human-principal seam; an agent bearer token never impersonates one.
4. **No external-client hiding claim.** Instar provides front-door filtering in its own app/dashboard. Telegram and Slack adapters preserve history and deep links and offer accurate client-side guidance, but do not promise to hide arbitrary worker conversations for a user.
5. **Suggestion-first backfill with live delegation capture.** Historical inference proposes placements. Explicit user actions and authenticated dispatch/spawn delegation records can create edges. An owner-facing Overview waits until manual placement is available and a real-topic probe shows useful roots; merely inferred workers remain in All and are never silently hidden. Auto-placement and broad default activation require a measured pilot and a separate decision.
6. **Owner controls shared placement.** The owner may correct global hierarchy edges. An MSP may read only authorized nodes and change their own principal-scoped view preferences, stored outside the structural graph; an MSP cannot move a shared node or inspect hidden provenance in v1. A future delegated editor role requires its own grant and audit contract.
7. **One write-admitted machine at a time, all-machine durable success.** A graph correction sent to a standby is forwarded to the machine currently admitted to write this agent's shared state. Acknowledgment requires durable application on **every installed machine in the signed membership epoch**, including any standby, plus an independent recovery witness for the acknowledged tail. A sleeping or unreachable installed machine keeps the correction pending rather than silently missing agent-known hierarchy. Every installed machine therefore has the full acknowledged graph and decision state locally and can operate coherently if all peers later disappear; it never depends on a peer read for already acknowledged memory. An unavailable machine can be removed from membership only through an explicit authenticated decommission/replacement action, never just because a write is waiting. This trades correction availability during a partition for the single-machine survivability standard; pending edits remain reviewable and can commit when the machine returns. Agent-wide acknowledged knowledge is the final-certified state held by every installed machine. A source or owner answer observed while another machine is physically asleep is explicitly pending local/witness-backed information, not a claim that the sleeping machine already knows it; on reconnection that machine repairs before serving a current view. While the independent witness remains durable, it retains every `Saved` pending source, request, answer, and correction until all members receive a terminal certificate. The stronger no-peer-dependence guarantee for **acknowledged** state remains local on every installed machine; pending recovery explicitly depends on the remote witness and is never described as locally acknowledged. A sleeping surviving machine repairs those items from that witness on wake **before** it serves a current view, even if every other installed machine has permanently disappeared; it does not depend on a peer machine or reconstruct knowledge from prose. The last acknowledged state remains locally usable during the repair, labeled stale. An event observed only locally before witness intake is `Saving`, never acknowledged as durable agent knowledge. The UI names this freshness boundary rather than calling pending state globally complete. Because new pending sources and owner answers are still continuity-bearing information, this remote-witness recovery path is the **operator-ratified scoped exception for this design** to the literal any-single-machine survivability standard; see `conversation-effort-hierarchy-standard-decision.md`. Justin approved choice A on 2026-11-05 at 00:37 PST. The installed checker still flags the literal rule until its registry is amended, and owner-facing activation still requires the implementation gates below. The strict all-member-wait alternative was considered but not selected.
8. **Audience-bound chat output.** A verified owner request establishes who asked, not who can read the reply. In v1, owner-scoped status, paths, and notices go only to a verified owner one-to-one destination or owner-scoped app panel. Shared or unknown-audience chats receive a neutral pointer to the authenticated app.

## 1. User outcome

Justin can work from a small set of top-level conversations. Delegated worker conversations remain durable, searchable, and directly reachable, but do not demand attention by default. An owner-private parent view reports the state of its descendants in concise, traceable terms; a shared Telegram or Slack front door points to that view without copying private facts into shared history. The app and dashboard show the same hierarchy and let Justin correct it. The structure can represent projects, tasks, and adjacent efforts without forcing every conversation to be a project or every project to be a conversation.

Success means Justin can find an effort and its original evidence quickly, identify what needs a decision at the top level, and descend into any worker conversation without losing its history. A wrong inferred relationship is easy to detect and correct. The system never claims that a Telegram or Slack client hides topics it cannot hide.

## 2. Existing contracts to reuse

- `TopicMemory` stores per-topic messages, recent context, and incremental summaries. The Topic Intent and three-level awareness work already separate whole-topic, recent arc, and current work; this design uses those signals as evidence, not as a new competing summarizer.
- `InitiativeTracker` has `kind: project|task`, `parentProjectId`, `rounds[].itemIds`, status, blockers, and links including topics. Plans currently folds child initiative rows under a project. This remains the structured work tracker.
- Conversation identity uses Telegram topic IDs, minted negative IDs for Slack, and native app conversation keys. The native app `GET /mobile/conversations` merges app, Telegram, and Slack rows into a flat newest-first list, with device and role filtering. Existing IDs, routing, histories, signatures, and session handoff remain authoritative.
- Topic-project bindings are scope controls; a hierarchy edge never grants project access. Threadline and dispatch can provide delegation evidence when available, but their availability is configuration dependent.

## 3. Core concepts and data

`Effort` is a user-relevant ongoing objective. It has an opaque, non-title-derived stable ID, owner, optional primary parent effort, optional project scope, and links to existing Initiative records. At most one `primaryInitiativeId` owns its displayed lifecycle, current outcome, next action, and blockers; secondary Initiative links are shown as related work without silently aggregating status. An effort without a primary Initiative uses an erasable, separately replicated `EffortHeaderStore` for its title and explicit outcome/next action. That store is not part of immutable graph event payloads. Importing a project/task hierarchy creates links to those same records; it does not silently mutate them.

`ConversationRef` is a stable platform-qualified reference to a Telegram topic, Slack channel/thread, or native app conversation. It resolves through the existing conversation registry and app store; it is not a new routing ID. `ConversationRole` is `front-door | worker | reference`, scoped to an effort; viewer-specific display belongs in `ViewerPreference`. A conversation may participate in multiple efforts, but one primary placement determines its location in the default tree. A platform conversation's deletion or inaccessibility leaves an inspectable tombstone and its graph provenance; it must not redirect to another ID.

`Relationship` is a versioned typed edge: `contains` (effort → effort), `coordinates` (effort → conversation), `delegates-to` (conversation → conversation), `depends-on`, `related-to`, or `supersedes`. Exactly one primary incoming placement edge per node is active in the default view: `contains`, `coordinates`, and `delegates-to` together form one acyclic mixed-node forest. An effort may be contained only by an effort; a conversation may be coordinated by an effort or delegated to by another conversation. Other typed links form a graph and may cross effort boundaries. Each edge stores creator, evidence references, source (`user | explicit-agent-action | imported | inferred`), confidence if inferred, creation time, and supersession history. User corrections have durable precedence. A semantic similarity score is never itself authority to assign work or reveal a conversation.

`ConversationDigest` is a viewer-scoped versioned projection of source messages and work records: objective, trend, decision records, separate worker claims and verified results, blockers, next action, update watermark, source citations, and freshness. A digest line never upgrades a worker's own report into verified completion just because it was repeated by a parent. Summaries are orientation, not proof of decisions or outcomes. The parent rollup cites child digest versions and records omitted/unavailable children rather than silently presenting a complete view. The write-admitted machine produces a digest version keyed by viewer scope and a canonical hash of input source IDs, versions, coverage, and graph placement. A replicated derived-cache channel carries that version and its authorized source refs; peers compare citations, coverage, and verification state, not model prose. Revocation invalidates affected versions on every peer before they are served again.

`DecisionRecord` is a source-backed attention projection, separate from prose summaries. Its stable key is the originating source ID and version plus a stable occurrence ID within that source and decision kind; two independent questions of the same kind in one message remain distinct. A source edit explicitly maps each prior occurrence to a continuing, superseded, or new occurrence and cannot silently answer its siblings. It records `open | answered | superseded | expired`, the owner who can answer, source and resolving refs, creation/update timestamps with offsets, and the authority that established each transition. Authenticated typed `decision-request` and structured work records may become open records. New agent asks emit typed decision metadata automatically through the conversation send path, so the owner does not have to classify them. Legacy untyped prose uses a conservative deterministic candidate rule: authenticated agent author, owner-addressed destination or explicit owner mention, an unquoted sentence containing `approve`, `choose`, `confirm`, `authorize`, or `decide` in imperative/question form, and an exact source span. A match yields a source-linked `Possible decision` attention cue without committing a DecisionRecord or sending a notice; the owner can answer from that cue. Other ambiguous prose stays in optional review, and no generated rollup or quoted text qualifies. The write-admitted machine persists a typed decision transition through the same witnessed shared-write discipline, with exact source ID and classification evidence; peers replay that record instead of rerunning a model and silently disagreeing. Semantic extraction from ambiguous prose produces a candidate for review, not a visible decision cue. An answer requires an exact source or explicit owner correction; a newer digest sentence does not clear it. Expiry occurs only when the source carries a due/validity limit, otherwise it remains open until answered or superseded. A false positive can be dismissed with a source-linked correction. Primary-edge rollup deduplicates by stable key, including cross-linked conversations. Decision transition records and their source versions replicate and rebuild deterministically after restart. The decision projection ships with digest increment D; earlier read-only screens show no decision badge. A typed `decision-request` emitted by the authenticated agent/work path carries a source version, occurrence ID, owner target, question kind, and optional due time. Legacy untyped prose that meets the deterministic rule is surfaced as a `Possible decision` cue; other prose remains a candidate in the optional `Review decisions` sheet under All. Neither is an automatically committed DecisionRecord or eligible for a notice. The typed source supplies its stable occurrence ID; when the owner promotes prose, the promotion records the exact source version and a distinct occurrence ID. The write-admitted source/decision service maps edited versions only when the source carries the same structured ID or an exact edit relation; an ambiguous edit keeps the prior occurrence open and creates a candidate for owner review rather than auto-clearing or duplicating it. A labeled real-topic corpus covers direct asks, rhetorical offers, unrelated replies, two questions in one message, and ambiguous edits with fixed expected outcomes. A threaded owner reply citing that occurrence, an owner selection of the question while answering, or an adapter-verified owner confirmation can link an answer; an unrelated unthreaded reply cannot. The in-app `Answer` sheet collects answer text or a typed choice, displays the exact worker conversation and its current audience before send, and uses the existing authenticated conversation send path with an idempotent operation/outcome key. The send-intent key is the stable logical decision occurrence ID plus answer attempt ID. Before any adapter send, the witness durably compare-and-swaps the **occurrence-wide answer claim** from unclaimed to this attempt, stores the send intent and current owner/epoch proof, and rejects every competing attempt on any device or writer epoch while that claim is unresolved. A later automatic attempt ID is admitted only after the prior one has a witnessed terminal `not-sent` outcome backed by **positive proof that the old attempt cannot still dispatch**; absence from a ledger or platform lookup is not that proof. An explicit owner-signed possible-duplicate override is the sole exception. A sent or ambiguous attempt never permits automatic re-send. This makes a confirmed send discoverable after writer loss and enforces at most one automatic dispatch attempt per occurrence, apart from an explicit owner override with a possible-duplicate warning. With no provisioned witness, structured Answer and Dismiss controls show `Sync setup needed`; with a provisioned but unreachable witness they show `Sync unavailable`. Neither state sends; the source conversation remains open for the owner's ordinary chat path. An ambiguous send outcome stays `Checking answer` and cannot be retried under a new key. A successor first searches the app/platform outcome ledger using the stable send key, then an authoritative platform message lookup where available. It records witnessed `sent` only with exact delivery evidence and `not-sent` only with an adapter/gateway proof that no platform dispatch occurred and any old dispatch token is fenced. Lookup absence remains undetermined. If neither can determine delivery after bounded recovery, it moves to `Answer needs review` with the exact worker conversation and prior attempt. The owner can mark the known sent message with its exact ref, mark a verified not-sent outcome, or explicitly choose `Send again` after a possible-duplicate warning; the last action creates a new attempt only under an owner-signed override recorded by the witness. No automatic resend occurs. Every structured answer traverses a single durable `AnswerSendGateway` outside the writer process; agents cannot call the platform directly for this operation. The gateway checks the witness occurrence claim and epoch fence at dispatch admission, persists `dispatch-started` before the one platform call, and never retries an ambiguous call. A stale writer cannot dispatch after its claim is fenced. The witness serializes cancel-before-dispatch against gateway admission; after `dispatch-started`, Cancel returns `not-cancelable:answer-claimed`, even when delivery is unknown. Positive `not-sent` means the gateway rejected or durably aborted before any network call and fenced the old token. A confirmed send is `Answer sent · syncing` while its decision transition waits for other machines; this state is non-actionable and visible in Pending. No second answer action appears for that occurrence. Sending does **not** wait for every installed machine to certify the decision transition. Only a confirmed send outcome with exact answer source ref **and** witness-durable pending transition may hide the owner's active cue as `Answer sent · syncing`; failed or ambiguous sends keep the cue active until outcome resolution. The worker receives at most one automatic send attempt, and later graph certification links the same answer ref without re-sending. If that transition cannot certify because its occurrence was superseded, a dependency was refused, or its heads changed, the witnessed send ref persists in `Answer needs linking` attention. The owner may link it to the correct occurrence or explicitly resolve the mismatch; the system never re-sends or silently restores an unanswered cue. A shared worker topic requires audience preview and existing send authorization; private owner report data is never copied into the answer by default. The source sheet offers `Answer` and `Dismiss` with exact ref, plus the original source; dismissal is a source-linked owner correction rather than silent expiry. While any installed member is asleep, a newly observed typed owner decision request can be shown as source-linked `Question` attention in the authorized Overview and attention list. This is a local observed-source projection, clearly separate from a committed `DecisionRecord`: the cue itself cannot trigger a notice, clear an existing decision, or claim fleet-wide completion. Only the independently durable explicit source occurrence may trigger a time-bound notice through the witnessed one-voice delivery ledger, after audience proof. The same source occurrence key deduplicates its pending cue and later committed decision; reconnection collapses them to one record without duplicate notice. A pending cue links to the exact original source, and synchronization details are available on demand. If the owner answers while replication is pending, an owner-local `Answer sent · syncing` overlay removes the active attention cue for that viewer without claiming a committed transition; it remains visible in Pending details until certified. A source-backed typed, time-bound decision request may use the one-voice notice operation while its durable decision transition is pending, provided the notice origin has independently durable source capture and audience proof; the stable occurrence key survives later certification and suppresses duplicate notices. Pending and answer overlays are available only with increment D. Cue priority is `Conflict`, `Answer needs linking`, `Answer needs review`, `Checking answer`, `Decision` or pending `Question`, `Source needed`, `Possible decision`, then evidence `Partial`; an answered syncing item is not active attention. Notices never describe an uncertified decision as fleet-committed. In a multi-machine fixture, the cue remains discoverable while an installed member sleeps, then converges once with the member back.

**Answer gateway custody and failure domain.** `AnswerSendGateway` is a new managed service distinct from the installed writer and the plaintext-blind `GraphWitnessService`. It is the only credentialed path for structured answer sends. It receives an owner-authorized, audience-previewed encrypted answer payload from the admitted conversation service; it decrypts only in isolated dispatch memory using a short-lived delivery key sealed to the gateway, never a witness-held content key. It durably stores opaque occurrence/attempt IDs, fence phase, destination ref, ciphertext payload with a per-attempt erasable key, and outcome ref. It does not persist plaintext or platform credentials in logs; platform credentials come from its protected runtime secret store. After confirmed send or terminal no-send, it destroys the payload key and ciphertext. If it crashes after `dispatch-started`, recovery treats delivery as ambiguous and never retries automatically. Witness outage disables new dispatch and owner resolution. Forget-source includes gateway ciphertext, transient payload key, and logs in its purge dependency inventory; only opaque dedupe/fence/outcome metadata survives. A gateway loss or replacement requires a witnessed fence and owner recovery before another structured answer may start. During witness outage, new gateway dispatch and owner resolution are disabled; an already admitted platform call may still finish, so a locally requested Forget suppresses Instar serving but cannot claim to recall that in-flight external call. Recovery fences the source and resolves the send before reporting fleet erasure complete.

A citation is a typed source pointer, never a free-form generated URL: Telegram `{chatId, topicId, messageId}`, Slack `{workspaceId, channelId, messageTs}`, native app `{conversationKey, eventId}`, Initiative `{id, version}`, or a typed work-evidence ref such as commit, merge, deployment, test result, or dispatch record with its authority and immutable version. A resolver creates a current link only after Instar authorization; platform access is verified only when a mapped platform identity makes that possible, otherwise the link is labeled possibly unavailable. A result stores `claimedOutcomeType`, `claimSourceRef`, and outcome-appropriate `verificationEvidenceRefs[]`. Deterministic rules may verify `committed` from a repository commit, `merged` from a merge record, `deployed` from deployment evidence, and `tested` from a test-run artifact; one stage never verifies a later stage, and the worker's own claim cannot verify itself. Unsupported outcome types stay `unverified`. A digest records `viewerScope`, source high-water marks, authorized-message count, `evidenceCoverage` (`complete | partial | unavailable | erased`), `replicationState` (`current | pending | recovering`), contributing machines and stores, `catchUpReadProofs` for required catch-up, and omitted-source reasons that the viewer is permitted to know. A changed source version invalidates the derived digest; a stale digest remains visible with its age and explicit timezone, not silently relabeled current. The parent rollup deduplicates one decision/result by stable source ID even if the same conversation appears in multiple efforts through cross-links.

`ViewerPreference` is per person and device sync: for the owner, preferred root efforts, collapsed branches, `front-doors-only | all` filter, muted worker notices, and ordering. It changes presentation only. It cannot bypass channel permissions or mute a Telegram/Slack client by implication. An MSP's v1 preferences are restricted to controls derived from their authorized flat conversation inventory, such as recency ordering and personal hide/collapse; they receive no graph role, front-door marker, path, or role-based filter behavior.

### 3.1 Normative identity and authority

The graph key is a typed `ConversationRef`, not the locally minted numeric alias used by some existing consumers. Telegram's ref contains the chat and topic ID. Slack's v1 ref uses the structured `(channelId, threadTs?)` tuple under the existing enforced single-workspace rule; workspace ID is upgradable metadata, not an immutable key string. When multi-workspace identity ships, a schema-versioned v2 ref adds the workspace ID and migrates aliases without moving graph edges. App's ref contains its UUID; the app registry's local negative alias is never used as a graph key. A resolver validates the ref against the existing conversation registry or app store and returns a current local routing target only at the point of opening or sending. A ref is identity, never delivery authority or permission. If a platform tuple cannot be verified, the graph can retain a historical read-only node but cannot invent a live destination.

The graph owns only hierarchy and presentation metadata. `InitiativeTracker` owns Initiative lifecycle and blockers; Topic Intent owns conversational evidence; platform stores own transcripts and message origin; the conversation registry owns routing identity; the notification system owns delivery. An effort linked to an Initiative reads its status from InitiativeTracker and records the source version in its projection. It never writes a second status copy. A hierarchy correction changes graph placement only and cannot rebind a topic to another project, move a session to another machine, or grant another person access.

### 3.2 Event and projection contract

Store graph changes as append-only, idempotent events with a stable event ID, graph schema version, subject ref, operation, actor principal, accepting machine ID, source authority, evidence refs, creation time, and causal parents. A move request names the current subject placement heads it observed; the accepted event records those heads rather than trusting a client-provided global revision as authority. A move is one atomic `set-primary-placement` event naming the old placement head(s) it replaces; `parentRef:null` unlinks. If the subject is the current certified front-door conversation **or is named as the replacement by a pending front-door choice**, every placement operation (move, unlink, undo, resolve, accepted suggestion, or dispatch placement) is refused or dependency-held until the relevant front-door change certifies, is canceled, or is replaced. The same server-side guard applies to every ingress. Move/unlink of the certified front door is refused until the owner chooses another front door or clears that assignment through `set-front-door`; the preview says which effort depends on it. The two operations are separately certified, so a move never leaves a dangling front-door role. It cannot half-apply as a separate remove and add. Edge and event IDs are immutable. No graph event contains user-authored title/summary text, deletes a transcript/Initiative/platform topic, or changes a topic-project binding. Per-person collapse, filters, pins, and archive-from-Overview belong in a separate principal-scoped view-preference store; they cannot alter placement or grant access.

The v1 operation contract is finite:

`explicit-agent-action` has a narrow service ingress in storage increment A: a verified dispatch/spawn record naming parent and worker conversations may produce only a `delegates-to` placement, on the write-admitted machine. The ingress verifies the internal service principal, the source record's machine signature and typed refs, then issues a graph authorization receipt tied to that record and admission epoch. A plain API bearer, generated prose, or a claimed agent role cannot use it. An agent event may replace an earlier agent event for the same worker but may not name or supersede a user head; if the user already placed that worker, the new delegation becomes a cited suggestion or cross-link candidate. The reducer enforces this precedence even if the agent event is causally later. Repeated dispatch delivery uses the source record ID as idempotency key. A real dispatch-to-edge test runs before read-only tree exposure. If a sleeping member blocks certification, the owner-only read-your-writes projection shows the new worker under its proposed parent with `Not yet on all devices`, while the canonical revision remains unchanged. Parent digest input hashes include pending placement IDs and label the route as pending; source-backed attention follows that proposed parent to the nearest visible front door or app attention list without claiming a committed edge. A later certificate merges the same worker, decision, and notice occurrence once; a refused delegation removes the overlay and preserves its source/audit record. Other devices obtain the pending projection from the witness-backed owner pending list.

Every machine replays the same authenticated event set into a deterministic graph revision and materialized tree. The projection stores source versions and a freshness watermark. A user move concurrent with an inferred placement wins. Concurrent, incompatible user moves create a visible placement conflict and keep the last agreed placement until resolved; deterministic replay must produce the same conflict on every machine. Any event set that would form a containment/delegation cycle is quarantined as a conflict with evidence, leaving the previous valid tree. An unavailable peer does not erase durable graph nodes.

The graph is a separate store because its nodes and relationships span conversations and lightweight efforts, while TaskFlow represents work execution. Import adapters project existing Initiative parent links and topic links into candidate graph events with source IDs; the graph never rewrites those source records. This choice must be checked against the exact current multi-machine journal and TaskFlow consumer contracts before implementation.

### 3.3 Graph invariants

1. A graph node is an `EffortRef` or a typed `ConversationRef`. Each has at most one active primary parent; zero means a root. Cross-links never count as a primary parent or grant access.
2. `contains`, `coordinates`, and `delegates-to` share one cycle check across both node kinds. A conversation can have a delegated conversation child, but cannot contain an effort. A conversation may be a front door only for one primary effort. Moving it requires a prior certified front-door reassignment or clear. Other memberships are cross-links.
3. Primary placement cannot silently cross incompatible topic-project bindings or owners. The system proposes a `related-to` link instead; changing a binding uses its existing authority and separate action. A graph correction is never a routing or permission change.
4. One placement event applies atomically to one subject. Undo and conflict resolution are new events that name the heads they replace. A tombstone preserves the ref and history but never authorizes a send.
5. A digest cites source message/work IDs, input coverage, and source versions. A missing or inaccessible child is omitted from a limited viewer's projection; an owner sees its explicit missing-history marker. No global summary is silently substituted for a viewer-specific digest.

Project compatibility uses the conversation's existing binding and the nearest ancestor effort's explicit `projectScope: Set<ProjectId>`; an empty set means an owner-private, cross-project organizer, not an access grant. A delegated conversation inherits the same effective check through its parent conversation. Bound project P under a scope containing P is allowed, including a multi-project scope. Bound P under an empty scope is allowed for the owner without rebinding P. Bound P under a nonempty scope excluding P is refused as a primary placement and may be suggested as a cross-link. An unbound conversation under an empty scope is allowed; under a nonempty scope it needs an explicit owner correction and remains unbound, with a visible “not project-bound” detail. A verified delegation can add such an unbound child only as a suggestion until the owner confirms. Cross-owner placement is refused regardless of scope. Table-driven acceptance covers unbound, same-project, different-project, unscoped, multi-project, delegated child, and cross-owner cases; no row changes the topic binding.

## 4. Inference and correction

### 4.0 Topic history as working context

A dedicated topic is the primary conversational record for a workstream, but it is not assumed to be a complete session transcript. A source can be absent because it lived only in a tool result, was never reported back into the topic, was truncated by a context window, belongs to another machine not yet synced, or is private to another person. The hierarchy therefore uses topic history for orientation and explicit decisions/results, then follows citations to durable artifacts, Initiative records, or original messages when it needs proof. It never infers “nothing happened” from a quiet or partial topic.

The parent rollup format is fixed enough to be useful across many workers: **objective; worker claims and independently checked results as separate fields; decision needed from the owner; blocker and owner of next action; exact evidence links; freshness with timezone; contributing machines/stores and missing coverage; omitted or unreachable children visible to this owner**. Every result line carries `claimText`, `claimSourceRef`, `verificationState` (`verified | unverified | contradicted`), `verificationEvidenceRefs[]`, and `checkedAt` with timezone. A worker's statement that work is “done” is an unverified claim until a source proves the intended outcome. A commit proves committed code, not merged code; a merge proves landed code, not deployment; a sent message or closed record proves only that action. The parent may say “worker reports complete” with its claim source, but may say “completed” or emit a done notice only when the outcome-appropriate verification evidence is present. A routine progress line changes the on-demand digest without generating a parent chat message. This preserves the concise topic history that motivated the feature while keeping the facts verifiable.

Illustrative owner-private front-door reply, with source labels standing in for permission-checked exact links: “**Objective:** make delegated conversations easy to follow. **Verified result:** the mobile correction walkthrough passed at 320 px [browser result source]. **Worker report, not yet verified:** the change is ready to ship [worker message source]; no merge or deployment check is recorded. **Decision needed:** choose the first real-topic pilot group [work decision source]. **Next owner:** Echo is checking implementation contracts [review record]. **Freshness:** checked 2026-11-04 10:45 PST (UTC−08:00); histories from Studio and Mini contributed, one worker's unique MacBook source history is missing. **Coverage:** partial; 3 of 4 workers checked. **Omitted:** one unreachable worker is named to this owner without guessing its status.” The actual reply includes only facts authorized for every recipient of that private destination and live citation targets; it never says “all clear” when coverage is partial. In a shared or unknown-audience topic, the reply is a neutral app pointer instead.

### 4.1 Digest maintenance

`TopicMemory`'s rolling topic summary is currently updated on session end, so it cannot be the only trigger for a timely parent rollup. A new authorized source message, explicit delegation event, Initiative status change, or graph placement correction enqueues a bounded digest refresh keyed by source ID and viewer scope. The write-admitted machine owns generation of a given input-hash/version; other machines serve the replicated, access-scoped version or mark it stale and request repair, rather than independently writing divergent prose for the same version. The worker digest records its source watermark; parent digests refresh from changed child versions in topological order through primary edges only. Cross-links do not trigger a second parent cascade. Generated rollups carry an origin tag excluded from source-message extraction and from verification evidence, preventing their own claims from feeding the next digest. Debounce bursts and deduplicate decisions/results by stable citation ID so 100 routine worker events may update one digest without sending 100 parent messages. A refresh failure leaves the prior digest visible with stale age and coverage, and retries from the durable source watermark; it never replaces a known digest with an empty “all clear.”

Coverage is enforced at the synthesis seam, not merely displayed afterward. A source inventory built from the agent's machine registry, source registrations, and ingestion watermarks records relevant machine/store pairs and expected **Instar-observed** high-water marks for the requested window; the pipeline cannot derive `complete` merely from the sources it happened to read. Before producing a `complete` digest, an effort-level done notice, or an inference suggestion that claims full-history evidence, the worker reads a bounded recent slice **and** the required catch-up range/artifact covering that window from every inventoried source. The pipeline records `catchUpReadProofs` and checks them against expected watermarks; if a required catch-up was not read from any authorized durable copy or a required evidence store is unavailable, it cannot label evidence coverage complete or claim the effort as a whole is done. A result can still be called verified for a narrowly stated outcome when a direct authoritative artifact proves that outcome, but the enclosing digest remains partial and cannot imply that all work is accounted for. It may answer an on-demand question with a clearly partial result and named missing sources, but it must not assert that no work happened. This is a structural gate at the digest/report path, not a prompt reminder. DAWN's history-injector failure showed why: a large injected history was silently truncated to an old slice, and the session had no way to infer the missing tail from that slice alone.

Coverage metadata names contributing machine IDs, source stores, oldest/newest observed messages, and high-water marks, plus missing or stale machine/store ranges visible to the viewer. `partial` alone is insufficient. Every digest timestamp and freshness label renders an explicit timezone: canonical wire timestamps use full RFC 3339/ISO 8601 offsets or `Z`, and UI/chat show the user's local zone alongside an inspectable absolute time. Never truncate the offset from a source timestamp or use a zone-free clock hour as a reason to defer work. DAWN observed a UTC hour misread as local time after its `+00:00` suffix was cut off.

Memory-bearing history and catch-up artifacts must survive loss of the machine that first observed them. For each authorized conversation source, the ingestion contract records a durable source ID, observed coverage range, source high-water mark, and a recovery location. Each inventoried source holder supplies a window-covering signed high-water attestation or a witnessed source bundle for the requested window. A sleeping member that is the only holder of a worker log, local artifact, or possibly newer session tail makes `evidenceCoverage:partial` and is named even if the writer has all other data; a sleeping member that only lacks a replica changes `replicationState` alone. A last-known high-water mark cannot prove no newer local source exists. The source inventory records whether a member is an origin holder or only a replica so the two cases cannot be conflated. Coverage has two separate fields: `evidenceCoverage` (`complete | partial | unavailable | erased`) describes whether the synthesizer actually read the required, authorized evidence window; `replicationState` (`current | pending | recovering`) describes where its protected source/digest version has reached. Source segments, decision transitions, and derived digest versions must eventually replicate to every installed machine for single-machine survivability, but a sleeping member changes `replicationState`, not the writer's `evidenceCoverage`. Before the writer advertises an owner-visible complete digest, its exact input range must be independently durable at the capture/witness seam, so writer loss does not erase it. A member missing the required local range serves only its labeled last-known version or repairs from the witness; it never presents another machine's complete claim as its own verified local read. Telegram Bot API has no general history-fetch method for ordinary bot topics; Telegram recovery therefore depends on observer-time, access-controlled replicated segments and continuity of the bot's received update stream, never a later platform backfill or per-topic message-ID gap check. The `complete` label means the requested window is covered by Instar's **observed capture**, not that Telegram's full platform history is known; a window before bot observation, after a known update gap, or when the synthesizer lacks a required segment stays evidence-partial; an installed machine awaiting replication instead shows one screen-level sync state. Telegram message deletions outside Instar are not reliably reported to the ordinary bot, so the UI cannot claim immediate cache erasure from a platform delete; Instar's own forget action must drive its cache erasure protocol. Slack history/replies may repair a range only when current token scopes, retention, pagination, and rate limits are verified; otherwise it also uses replicated capture or stays partial. Native app transcript replication supplies its own durable source. The graph pointer or a surviving digest alone never substitutes for original evidence. A machine calls its locally rendered digest evidence-complete only after validating its own authorized input range or an independently durable source bundle; a sleeping replica-only peer does not make the writer's evidence incomplete; a sleeping unique source holder does. Claims that all machines have the data require `replicationState:current`. Privacy filtering still happens before any limited-view cache or response. The official [Telegram Bot API update methods](https://core.telegram.org/bots/api) and [Slack history method](https://api.slack.com/methods/conversations.history) are the platform basis for this distinction.

**Telegram observed-capture ledger.** One fenced poller/webhook owner records Telegram update offsets, received update IDs, source message IDs, capture start, bot visibility configuration, and explicit downtime intervals. In the normal healthy-witness path it durably writes the raw authorized update and a source-segment index to a local source file and the independent witness **before** confirming or advancing the Telegram update offset; this capture threshold does not wait for a sleeping installed member, because Telegram retains pending updates only for a limited period. Handoff transfers the last durably confirmed offset and witness chain to the next poller before it starts, with an overlap-safe idempotency key per update. During witness outage or before witness provisioning, the poller still processes updates and may advance offsets after **local fsync** so normal Telegram work does not stall. It records those intervals as `local-only` in the capture ledger, with source IDs and offset bounds, and sets `evidenceCoverage:partial` for affected complete-history claims until independent backfill succeeds. If the sole local copy dies before backfill, the successor records a durable unrecoverable `gap` from the last witnessed offset; it never guesses the missing content or labels that window complete. A repairable poller downtime interval remains `unobserved pending recovery` while Telegram can still deliver retained updates, becoming `gap` only when retention or another failure makes it unrecoverable. More than one locally captured batch can proceed during the outage; the UI exposes the local-only limitation in details, not on every tile. Outgoing bot messages are captured from the send operation/outcome ledger with source IDs and marked `outgoing`; an ambiguous send remains unresolved until the origin confirms it. The ledger records periods when the bot could not observe messages because of privacy mode, missing membership, permissions, or polling downtime; it never fills those periods by guessing from per-topic message IDs. A retention-expired or otherwise unrepairable update interval is a durable `gap` in `evidenceCoverage`. The detail view names the Instar capture start and any gaps; `complete` always means complete **within a stated observed window**. Kill-before/after-offset-confirmation, overlapping-poller, sleeping-member, failover, and retention-expiry tests are required before source history powers a complete digest.


Authoritative edges arise from a user move or an authenticated live dispatch/spawn delegation with parent and child IDs. A verified imported project/task link is a cited candidate until the owner accepts it; import never bypasses the owner/dispatch authority table. The engine proposes **historical** matches from topic titles, older dispatch records, topic intent, initiative links, and message evidence. A proposed edge includes supporting and contradicting evidence, confidence, and affected visibility. High confidence still does not override a user correction. Ambiguous or cross-project matches remain suggestions. Never infer ownership, user identity, or permission from content similarity. Live delegation capture ships in storage increment A so a new worker can enter the tree without a manual owner move; historical candidates never become primary placement on their own.

Corrections are first-class events: move under another parent, mark related, unlink, set front door, or reject a suggestion; personal hide/archive belongs to viewer preferences. Each action shows a preview of affected rollups; a placement change never changes access. Detect cycles and stale **subject heads** at write time; return a conflict with the current tree and preserve both attempts for audit. A rejected suggestion is a durable negative constraint until the user reverses it. `All` has one optional `Review suggestions` entry, with each candidate showing the proposed parent and source; `Accept`, `Reject`, and an optional selected-batch accept are explicit. A batch returns one independent result per candidate and leaves failed/conflicting items for review. The default Overview has no suggestion queue or bulk toolbar.

## 6. Notifications and external clients

Worker messages remain in their original conversation. Instar updates the parent digest when a worker changes. A parent notice requires a concrete operator decision or a usable completed result verified against evidence for that actual outcome; a worker's completion claim alone is ineligible. Routine blocker and progress changes wait in the digest unless they create a time-bound decision that the operator must make. The nearest primary-ancestor front door is a candidate destination, not automatic permission to publish: a notice containing owner-scoped facts may go only to a verified owner one-to-one chat or the owner-scoped app panel in v1. When audience membership cannot be proven, including the normal shared Telegram group case, use an in-app attention cue and at most a neutral private/app pointer. An effort with no front door uses the app. A budget-exhausted eligible decision remains visible in Overview and its filtered attention list, never silently discarded. A typed, time-bound owner decision request may be notice-eligible while its decision transition waits for an asleep member, but only from independently durable source capture with a stable occurrence key, one-voice outcome ledger, and the same private-audience proof. The notice labels the source question rather than an uncertified decision state. An owner answer locally hides active attention as `Answer sent · syncing`; the pending transition remains inspectable until certified. Reconnection cannot create a second notice for the same occurrence. A replicated notice identity is the stable logical decision occurrence ID (or verified result ID) plus notice kind and authorized audience scope; source edits and placement changes retain that logical identity, while the selected destination is stored separately. Two questions in one message therefore have separate notice identities, and moving an already-notified question cannot trigger another notice to the same audience. This identity selects one write-admitted sender; delivery uses the existing operation/outcome ledger, so an ambiguous send remains held until the origin proves delivered or not-delivered rather than being blindly retried after failover. The pilot measures worker-originated native pings as well as parent notices; routine bot sends may use Telegram silent delivery only as an opt-in setting, never a claim to mute user or platform notifications. No automatic per-message mirroring or one-topic-per-task creation. A burst test must show that many worker events collapse into a small, stable number of parent notifications. A user can temporarily follow a worker conversation directly.

Telegram supports separate forum-topic history, names, links, and notification choices. The documented hide operation applies to General only; closing an ordinary topic prevents new messages and deletion removes history. Instar's `front-doors-only` view is therefore an Instar app/dashboard feature. Slack's user sidebar sections and mute/hide controls are complementary; threads and channels each have navigation tradeoffs. Platform adapters provide accurate deep links and optional naming/notification guidance, without claiming to control per-user client layout via bot APIs.

Use platform-generated or existing-adapter deep links only after Instar authorizes the viewer to see the underlying node/source. When the viewer has a mapped platform identity, re-check platform access if the adapter can; without such a mapping, label the link `May require access` and offer the in-app record, never claim that generating a permalink verified permission. Slack message links should use `chat.getPermalink` or an adapter-validated equivalent; a Slack channel redirect may include its workspace/team ID. If a platform link is unavailable, show the durable graph node and an honest unavailable state rather than guessing a URL. The Telegram and Slack claims above were rechecked against the official [Telegram Bot API](https://core.telegram.org/bots/api), [Bot API changelog](https://core.telegram.org/bots/api-changelog), [Slack deep-linking guide](https://api.slack.com/docs/deep-linking), [Slack sidebar preferences](https://slack.com/help/articles/212596808-Adjust-your-sidebar-preferences), and [Slack custom sections](https://slack.com/help/articles/360043207674-Organize-your-sidebar-with-custom-sections) on 2026-11-04.

### 6.1 Optional platform-native organization

The first release keeps existing Telegram and Slack conversations in place and lets Instar's Conversations view provide the hierarchy. For a user who mainly works in Telegram, a later opt-in topology could put newly created worker topics in a separate worker forum group while front doors stay in the main group. Telegram can archive and mute an entire chat, so that group could be kept out of the main chat list while its topics and histories remain reachable by link. This requires a second group with correct bot membership and permissions; Telegram's chat archive is a user-side choice, and existing topics are never moved or deleted automatically. Instar's current Telegram adapter has one main `chatId` and an optional `issuesChatId` with a disjoint topic-ID space, not a generic worker-group slot. The pilot therefore needs explicit worker-chat routing/namespace and cross-chat identity tests; it must not repurpose the issues chat or assume a config change alone suffices. The graph treats both groups through full `(chatId, topicId)` refs. This is a viable noise-reduction pattern to test, not a claim that the Bot API hides an ordinary topic. Telegram's [official archive guidance](https://telegram.org/blog/folders) describes muted chats remaining archived; the [Bot API](https://core.telegram.org/bots/api) documents forum-topic creation and sending.

In Slack, a user can organize channels and DMs in custom sections on a paid plan and can mute/hide conversations. Instar may suggest a naming convention or a worker section, and may deep-link to a worker channel or thread; it should not claim to set another person's sidebar. Putting all workers into threads of one channel reduces channel count but can make long-lived work harder to find and permission boundaries coarser, so it needs a separate opt-in pilot. The app's own tree remains the reliable cross-platform hierarchy.

### 6.2 Conversational use in Telegram and Slack

The hierarchy is useful in chat even when the client has no tree UI, but the **destination audience is checked before any owner-scoped service read enters an agent session**. The chat adapter binds each request to a verified destination and resolves an audience capability before calling `service-digest` or `service-node`. A shared or unknown-audience session receives only a neutral pointer capability; the service refuses owner title/path/count/digest/source fields, even if the requester is the owner. It cannot place a private digest in model context and rely on post-generation text inspection. A private destination gets a separate owner-bound session or structured, source-filtered renderer whose output route is fixed to that destination. A later switch to a broader route invalidates the capability. A canary private title in a shared-topic prompt-injection test must never enter that session or its output.

The audience oracle covers both current platform recipients and Instar readers who can open retained history, including MSPs with topic access, and the possibility of later joiners reading old messages. V1 rich owner reports and notices are allowed only in a verified one-to-one Telegram bot chat or Slack DM with an owner principal, or inside the authenticated owner app. A normal Telegram forum group, including an apparently one-human group, is treated as shared because the Bot API cannot prove and continuously enforce all recipients and future history readers. Slack public/private channels and guests likewise receive only neutral pointers unless a later explicit content-sharing grant and retained-history policy prove the full audience. A private bot chat that is exposed in an MSP-readable Instar inventory is not owner-private; it is excluded from that inventory or receives a neutral pointer. Owner reports in the app are rendered in a viewer-bound Conversations panel, never inserted into the ordinary native app transcript that an MSP `ownerConversations` grant can expose. Every list, transcript, search, sync, and deep-link read rechecks the viewer grant and item audience, including after a later grant change. A separate owner-only report item remains owner-only even if an MSP later gains access to the underlying conversation. Immediately before a private Telegram/Slack send, the adapter revalidates destination identity and audience capability; a grant or route change between read and send fails closed. Platform membership-change signals invalidate cached audience proof; unknown or stale proof fails closed. The front-door topic remains the user's concise work history and accepts on-demand requests, but a group front door points to the owner-private report rather than echoing the report into group history. Generated rollups carry source-dependency tags and are excluded from future digest/verification evidence. These are on-demand responses in existing conversations, not new notification streams or copied transcripts. Acceptance covers Telegram private/group and membership change, MSP-readable topic, Slack DM/public/private channel/guest, and later history readers.

An owner may propose a correction in chat, such as moving the current worker under a named effort. An agent session can create only a pending proposal, never commit from generated text or a relayed “yes.” The adapter resolves the source conversation and verified sender identity, presents the old/new path privately, and issues a short-lived proposal bound to owner principal, destination, observed subject heads, and idempotency key. Commit requires an adapter-verified Telegram callback or Slack interaction from that same owner, bound to the proposal and consumed once; if the platform cannot supply that proof, the owner uses the signed app/dashboard correction sheet. Telegram uses the authenticated sender user ID and existing owner mapping. Slack uses its existing `SlackPrincipalResolver` on the authenticated Slack `U…` ID, then requires a registered `role: owner` principal and the adapter's authorized-user check; display name, message text, another member's click, and replayed callback never establish authority. The admitted writer rechecks current heads, project scope, cycle rules, and audience privacy before commit. If identity or destination is ambiguous, it offers the app sheet rather than guessing. A chat reply can never change platform membership, topic-project binding, or channel notification settings. This conversational layer follows the tree and correction increments, so it does not create a second hierarchy authority.

## 7. APIs, storage, and migration

Add authenticated endpoints for: read tree with cursor and viewer scope; read node, relationships, provenance, and digest; create/correct/supersede edges with observed subject heads; request inference suggestions; accept/reject suggestions; check an uncertain write by idempotency key; and separately read/write principal-scoped view preferences. Mobile variants require device signatures and the existing person/role boundary. Do not route agent messages through a new graph ID. Structural graph writes use idempotency keys and append-only events, with deterministic projection rebuild and multi-machine convergence. View-preference writes use their own principal scope and existing preference authority, without touching the graph revision. A tombstone retains identity and edge history. Validate cross-project scope, principal, and current ownership at fire time for any side effect.

### 7.1 Proposed API shape

- `GET /conversation-graph/roots?view=overview|all&cursor=...` returns permission-filtered nodes, a stable next cursor, graph revision for diagnostics, source freshness, and partial live-data markers. `GET /conversation-graph/nodes/:ref` returns a node, primary path, children, typed cross-links, digest, provenance, and source versions. A ref in a route is a canonical base64url encoding of the discriminated JSON ref, never a title or local numeric alias. `GET /conversation-graph/suggestions` returns candidate edges with evidence and contradiction fields. `GET /conversation-graph/changes/status/:idempotencyKey` distinguishes queued, preparing, committed, canceled, refused, and temporarily unknown without inviting duplicate retries.
- `POST /conversation-graph/changes` accepts one idempotent operation and the observed heads for the subject or edge key it changes. An unrelated graph event does not make a move conflict. The server rechecks parent scope, cycle, and permission predicates at commit. It returns the new global revision or a typed `409 placement-conflict` with current subject heads and reviewable competing edits. `POST /conversation-graph/suggestions/:id/accept|reject` records an explicit decision; reject creates a durable negative constraint. An optional batch acceptance endpoint applies each candidate independently, returns one result per candidate, and never silently auto-places the rest.
- An internal, read-only `service-digest` path accepts authenticated agent identity **and a destination-bound audience capability** minted by the platform adapter before the read; requested owner scope alone is insufficient. A shared/unknown audience capability returns only a neutral pointer, so owner-scoped facts never enter that agent session. A private owner-bound capability fixes the output destination and expires on audience or route change; this path never grants a graph write. Chat correction proposals use a separate pending-proposal store and adapter-native confirmation, not a service write of owner placement.
- `POST /conversation-graph/changes/cancel` accepts an owner-authenticated idempotency key for a cancel-eligible unsent operation and races atomically at the witness with final commit. A confirmed answer send returns `not-cancelable:answer-sent` while its transition continues to certification. `GET /conversation-graph/pending` is owner-scoped and returns witness-durable queued, preparing, canceling, answered-syncing, and waiting-machine entries for every owner device. `POST /conversation-graph/decisions/:occurrenceId/answer|dismiss|supersede|re-source` uses exact source refs and confirmed conversation-send outcome for answer. `POST /conversation-graph/forget` accepts a typed source/header identity and a verified authority proof, returns local suppression plus fleet completion status, and is available from the source/header detail sheet. A non-owner proof is either a source provider's signed deletion event bound to the same source ID or a verified data-subject erasure request bound to that subject and source; a generic service bearer or message text is insufficient. The privacy/erasure service records the proof and only erases Instar-held copies within that authority.
- Mobile equivalents are device-signed and use the same person and role filtering as `GET /mobile/conversations`; global placement writes require the resolved owner principal. MSP devices may update only flat-inventory-derived personal preferences, never shared placement or owner-graph filters. Dashboard graph routes require both ordinary API authentication and a live `x-instar-operator-session` proof verified through the existing dashboard operator-session store. A bearer token alone is refused. A standby dashboard session re-unlocks on the admitted writer before a correction; it is not treated as portable proof. The app and dashboard consume one shared projection module, not separate placement logic. Responses never expose hidden descendants through counts, cursors, search timing, or summary text.

The exact URL spelling is provisional. The contract to freeze in implementation review is the typed ref, graph revision, idempotency, correction semantics, privacy-filtered pagination, and honest partial-data markers.

### 7.2 Storage integration decision

The installed `CoherenceJournal` already transports typed, per-machine append-only streams and its receiver verifies sender binding, schema, sequence, and durable apply. The generic replicated-record envelope adds a hybrid logical clock and an `observed` witness for concurrent updates. It is the preferred transport seam for a new `conversation-graph-event` kind, provided implementation adds that kind to both the journal's static kind list and replicated-kind registry, validates a bounded graph-specific schema, and proves the peer pull path advertises and applies it. The existing `app-conversation-event` kind is for native transcript events and must not be reused for graph changes. `InitiativeTracker` writes through TaskFlow when wired; it is not the graph's write authority.

The graph reducer must preserve all valid placement events and compute a conflict from incomparable user corrections. Use the generic replicated envelope with `recordKey = immutable eventId` so different events union rather than compete for one last-writer-wins record. A duplicate event ID is idempotent when its canonical core, payload hash, and authorization receipt match; the final commit certificate may attach later and must then verify against that unchanged event. A different core/receipt or conflicting certificate is quarantined. Each placement event records `replacesPlacementEventIds`, the current subject heads the author observed. A head is an accepted placement event not replaced by another accepted event. One head yields one placement. Two heads with the same destination coalesce for display but remain in the audit. Two incompatible user heads create a visible conflict, keep the last agreed placement, and require a resolution event that names both heads. A user head defeats a concurrent inferred or explicit-agent head without erasing it. The HLC orders display only; it cannot confer precedence over an incompatible user edit. Missing causal parents hold an event unapplied and mark the projection partial. Cycles across subjects quarantine the involved candidate placements and preserve the last valid forest.

Projection is a pure function of the same verified event set, never the order in which a peer received it. Per subject, validate the causal DAG, compute unreplaced heads, and collapse identical destinations only for display. For incompatible heads at the same authority level, the fallback parent is the latest common **causal placement event** in the event DAG, if unique; the X/Y/Z fixture retains X even when X is not a tree ancestor of Y or Z. If no unique common causal placement exists, the canonical projection places the subject at unresolved/root with an unknown-previous-path marker. A lower-authority head cannot replace or dislodge a verified owner head even if causally later. After provisional parents are selected, run one cycle check across `contains`, `coordinates`, and `delegates-to`. In a mixed-authority cycle, lower-authority candidate heads are held out first; the owner placement stays. In a same-tier owner cycle, retain the latest common causal placements when they form an acyclic forest, otherwise project the involved nodes deterministically as unresolved/root with an explicit cycle marker. This canonical result and its hash depend only on the verified event set. A UI may temporarily show its last verified local snapshot for availability, but labels that as a separate retained view with its own older revision and `partial`; it never calls that snapshot the canonical projection of the new event set. Event IDs may sort diagnostics, never choose a winning parent. Cross-links are checked for authorization and ref validity but never enter the primary-parent cycle calculation.

The canonical placement **core** has `eventId`, `schemaVersion`, `subjectRef`, `parentRef | null`, `placementKind`, `replacesPlacementEventIds[]`, `actorPrincipal`, `sourceAuthority`, `evidenceRefs[]`, and `createdAt`. `payloadHash` hashes only that canonical core. `authorizationReceipt` is a separate accepting-machine signature over the core hash, verified principal and authentication method (owner or narrow dispatch service), admission epoch, and idempotency key; it is excluded from the core hash to avoid a circular definition. A final `commitCertificate` binds the core hash, receipt hash, source sequence/predecessor hash, signed installed-machine membership epoch, signed lease epoch, durable receipt from every installed member, and an independent durable witness signature. The witness proof of preparation is not an acknowledged commit watermark. Every installed member durably receives the final certificate and its historical verification material before API success; the witness advances the committed watermark when it signs the valid final certificate after all durable member receipts. A member seeing only a prepared core, receipt, or witness proof retains an uncertified pending intent and never promotes it to the canonical tree. The replicated envelope adds `recordKey`, `hlc`, `op`, `origin`, and `observed`. The write-admitted machine verifies the owner's device signature, Telegram/Slack callback, dashboard operator session, or authenticated dispatch record at the request boundary and persists the signed receipt with the event. It replicates the receipt and final certificate, never a live PIN, bearer token, or device secret. Peers require the receipt's verified principal to equal the core's `actorPrincipal`, validate its accepting-machine signature, historical lease proof, and witness proof, and require the signed machine to match the envelope origin before trusting a correction. Each transport hop is authenticated separately; a forwarding hop need not be the event's original signer. A peer lacking required trust/admission proof quarantines the event and marks its projection partial instead of silently accepting it. IDs and source refs are bounded and validated before a write is durable. A resolution payload names every conflicting head it resolves and the selected parent. A rejected suggestion uses a stable candidate key so repeated inference cannot recreate the same proposal until the owner reverses the rejection. Materialized child order is a presentation preference, never the conflict tiebreak.

Reducer fixture for one subject: `A` places worker under effort X. `B` and `C` both replace `A`, one selecting Y and the other Z. Event arrival orders `A,B,C` and `C,A,B` must yield the same two-head conflict, with X as the last agreed parent and no unannounced move. `D` names both B and C as replaced heads and selects Y; after D reaches both peers they show one head under Y. If a peer receives D before either parent, it holds D unapplied and reports a partial revision. If B and C select the same Y, the UI shows one destination but keeps both events until a resolution names both. A concurrent inferred placement does not dislodge a verified owner move; an agent event causally later than a user placement cannot replace that owner head. A forged owner label without a valid receipt is quarantined; a replay with the same event ID and changed core hash is also quarantined. Every fixture compares accepted event-set hashes and rendered tree after each peer has the same valid events. The ordinary single-writer API serializes two owner edits to the same subject: the second request with stale observed subject heads returns 409 before event creation. An unrelated event does not conflict. The two-head fixture is a recovery/split-brain defense, not the expected result of two normal app taps.

Cross-subject cycle fixture: efforts E1 and E2 begin as separate roots. One valid candidate places E1 under E2 while another places E2 under E1. The primary-parent graph has a cycle regardless of arrival order; both candidate heads are surfaced as a cycle conflict and the projection keeps both prior root placements. A later resolution that removes one candidate yields the same forest on both peers. The cycle checker accepts all three primary-edge kinds, although current direction rules mean an effort→conversation `coordinates` edge cannot by itself close a path back to an effort. A `related-to` cross-link between E1 and E2 does not create a cycle conflict.

Read and write APIs carry a global projection revision computed from sorted accepted event IDs plus canonical payload hashes for diagnostics and convergence. Write preconditions compare the relevant subject/edge heads, not that global revision; an offline edit may be queued with its observed heads and replayed only after revalidation. The app shows both proposed destinations and the last agreed parent when two user edits conflict. A resolution written on one machine must converge to the same head set and tree on every peer.

The graph's authority is a fsynced append-only event source, following `AppConversationStore`'s source-file-plus-derived-index pattern, with one signed **installed-machine membership epoch** and an independent durable recovery witness. The admitted writer fsyncs an event; every installed member durably applies the core/receipt and necessary memory-bearing source bundle and returns a durable receipt; the always-on `GraphWitnessService` in a distinct failure domain durably witnesses the prepared event. The writer then builds the final `commitCertificate` from that epoch, all member receipts, and witness proof, and every installed member durably receives the certificate and retained verification material. The witness signs the certificate and advances the committed watermark after verifying all durable member receipts; the writer disseminates that certificate to every member and waits for each member to persist it before the API returns success. An interrupted dissemination returns `pending-or-unknown`; a survivor promotes only a locally validated final certificate, never a merely witnessed prepared intent. A later status lookup can confirm a committed certificate even when the original response was lost. A sleeping or unreachable installed machine therefore keeps the correction pending; it is not silently removed from the replication obligation. Membership changes only by authenticated decommission/replacement with a signed transition and full state transfer to any replacement, never as an automatic timeout workaround. A locally fsynced but unwitnessed or not-yet-all-machine-replicated event returns `pending-or-unknown`, with status lookup by idempotency key; a single installed machine still needs an independent durable backup witness for acknowledged corrections. Every installed machine holds the full acknowledged graph, decision transitions, and authorized source context locally, so loss of all peers reduces throughput but does not erase information the agent already acknowledged. Journal transport and a reconstructed local outbox retry nonblocking emission. A derived index or snapshot is rebuildable and never outranks source/witness evidence. Journal retention may rotate, so a peer detecting an unacknowledged or interrupted transfer repairs from durable source or witness, validates IDs, hashes, and the commit chain, and never promotes pending data to canonical state early. The witness holds the highest acknowledged watermark, so a successor whose former writer is dead compares against its own local state and the witness before accepting writes. Initial rollout verifies identical event-set hashes and projections after concurrent moves, restart, emission refusal, a sleeping installed peer that blocks acknowledgment, explicit membership replacement, and permanent loss of the writer after local append but before journal emission. This is the selected storage design; implementation review must prove the exact all-machine replication, witness, and repair wiring before it can become authoritative.

**Ordered pending operations.** The admitted writer keeps one fsynced, idempotent queue per agent for graph, decision, and header writes. The queue intake threshold is independent durability: before the UI says `Saved` or hides an answered cue, the independent witness durably stores the core, authorization receipt, dependencies, and necessary source bundle. Before that threshold the UI says `Saving`, retains the active cue, and offers no read-your-writes guarantee. The witness exposes the pending set to a successor, including queue order and cancel records, so writer loss after `Saved` cannot erase an accepted request. Each entry has an operation key, owner/source authority, observed committed heads, earlier pending dependencies, affected refs, source bundle, and status `queued | preparing | certified | canceled | refused`. New requests validate against the committed projection **plus earlier pending entries in queue order**, including a provisional cycle check and front-door eligibility after every earlier queued placement. A queued front-door choice cites any pending placement that makes its target directly coordinated; it cannot certify if that placement is canceled or refused. A later placement that would move its pending or certified target away is refused or held until a separately certified replacement/clear. **Exception:** a Move/Unlink of the currently certified front door checks only certified front-door state and is refused until a replacement or clear operation itself certifies; an earlier queued front-door change cannot make that Move eligible. A second owner move of the same subject replaces a still-queued move after a witness-certified cancel under the same owner proof; after prepare it queues as a dependent successor or asks for a fresh choice, never creates a self-conflict. Create-effort, header write, then move into that effort form an ordered dependency chain; a failed predecessor refuses dependents visibly. EffortHeaderStore writes use the same all-member final-certificate rule, with separate erasable payload keys; a header is not announced as saved everywhere while pending. Dispatch ingress also queues in order. After the intake threshold, the owner sees read-your-writes overlays labeled `Saved · Waiting for MacBook` (or `Waiting for sync` if the member is unknown), with a Pending list and machine details on demand. The canonical shared tree remains at its last certified revision; other devices never mistake the overlay for committed state. A known sleeping member gets no blind Retry action. Cancel is offered before certification only for unsent proposals; a confirmed answer send is never cancelable. Witness-certified cancellation clears an eligible overlay immediately, and Undo is offered after commit. A cancellation whose witness is unavailable stays visibly `Canceling · Waiting for sync`. A pending queue with its dependencies survives writer restart and failover.

**Witness and membership recovery.** A functioning independent durable witness is provisioned before corrections are enabled, including on a one-machine install; The selected substrate is a new always-on `GraphWitnessService` on a distinct failure domain from the writer: it has a machine-independent signing key, transactional durable log, atomic compare-and-swap fence per agent/epoch/idempotency key, receipt/source-bundle store, and erasure tombstone support. A sleeping installed laptop and a passive backup without atomic fencing/signing are ineligible. It runs on a managed remote failure domain outside the entire installed-machine set; an installed peer, even an always-on one, is not the sole witness for Saved pending recovery. The agent provisions this service with its configured service credentials when available. Setup tests reachability, distinct failure domain, signing identity, atomic fencing, source recovery, and erasure before turning on corrections. If provisioning cannot be completed, the agent marks corrections `Sync setup needed` in the app and continues read-only operation; the owner is not asked to run shell commands. The service is new implementation work, not an installed primitive. The witness operator sees only opaque IDs, hashes, fence metadata, and ciphertext bundles. The writer encrypts source/pending bundles before upload; each installed member receives a sealed decryption-key envelope under its registered device key, and the witness never holds plaintext content keys. Erasure tombstones revoke and destroy retained envelopes/ciphertext; membership recovery rotates envelopes for surviving members. Signature verification uses hashes and durable receipts, not plaintext inspection. A witness compromise cannot read owner transcripts or effort text by itself. This privacy boundary and encrypted recovery from a surviving member are implementation acceptance gates. if none exists, graph corrections and header writes show `Sync setup needed` and stay disabled, while read-only history remains available. The signed membership epoch records installed members, witness identity and fence, and an owner-authenticated transition authority. A verified owner recovery ceremony may decommission a dead, stolen, or permanently unavailable member using the latest certificate and source bundle from any surviving member or backup; it does not require the removed machine to transfer state. The ceremony requires owner device/operator proof, an independent witness or replacement backup, a monotonic fence handover, and an explicit audit record of every pending operation that is adopted or refused. It cannot claim to erase data from an unreachable stolen device; local encrypted-at-rest protection and key revocation limit exposure. A returning removed machine must rejoin under the new epoch, import the tombstone/certificate chain before serving, and cannot certify an old queued write. If only one machine survives, the owner ceremony fences the old epoch through the independent witness before enabling new writes, preventing an old holder from reappearing as a second writer. Loss of the sole witness disables new certified corrections until a replacement witness is provisioned and the owner recovery ceremony validates the highest surviving certificate. These transitions are explicit product states, not automatic timeouts.

**Successor reconciliation.** Before a new writer accepts writes, it unions all available source, witness, and member receipts by idempotency key and validates the historical lease and membership chain. A final certificate already signed by the witness is redistributed; a member lacking it shows a partial tree until it validates the certificate. An intent with a valid original receipt but no final certificate is adopted under the new epoch only after revalidating current subject heads, dependencies, owner proof, and witness fence; otherwise a witnessed abort permanently marks its idempotency key `refused` or `canceled` and fences the original attempt. A confirmed answer send or unresolved send attempt is handled separately: the successor preserves its occurrence-wide witness claim and send/outcome ref, investigates the delivery result, and continues the transition when possible. A stale or refused transition after confirmed delivery becomes `Answer needs linking`; it never cancels the sent answer or reopens the occurrence as though nothing was sent. Status becomes `committed`, `canceled`, or `refused` after reconciliation, not indefinitely `unknown`; retry of the same key reads that outcome and never creates a second event. Canonical inclusion begins at a locally validated final certificate; partial dissemination can temporarily produce different labeled revisions, then repair converges them before further writes. The one-fenced-witness design does not expect two independently certified partition writes; if historical corruption creates two verified owner heads, the reducer still surfaces the existing conflict defense. A failover fixture kills the writer at each stage through certificate delivery, including a lease change, and checks one terminal outcome and one final tree.


The installed `CoherenceJournal` enqueue is nonblocking and its replicated commit observer fires only after fdatasync, which is why enqueue alone cannot acknowledge a graph correction. The installed `ReplicatedStoreReader` is the no-clobber union funnel for registered replicated kinds. The canonical projection combines locally **final-certificate-validated** source events, including a not-yet-journal-emitted event whose final certificate is durable, with the reader's peer event union through an explicit adapter that deduplicates by event ID and quarantines mismatches. A locally fsynced event still awaiting its final certificate is a pending intent overlay, never a committed tree change or revision. The implementation test must prove that the local overlay does not bypass the reader's dropped-origin and conflict rules for peer data. Rebuild after restart rescans source and pending proof state, retries journal emission, and reconciles ambiguous intents before claiming peers are current.

Only the machine with current write admission for the shared graph commits new events. Installed `WriteAdmission` supplies a synchronous lease-holder/read-only verdict for `cluster-shared` writes. Installed `LeaseCoordinator.currentEpoch()` and `currentLease()` expose the effective epoch and signed lease; `FencedLease.verifyLease()` checks a holder signature against the registered machine key. The graph path binds the receipt to that signed lease and admitted verdict, then obtains a `GraphCommitWitness` signature from the always-on `GraphWitnessService` that has durably stored the event and a monotonic fence/watermark record. A witness already fenced to a newer epoch refuses a new old-epoch endorsement. The commit seam rechecks admission and epoch immediately before append and before returning success; if authority changed or witnessing failed, the response is `pending-or-unknown` and the event is reconciled under its stamped proof. Historical validity is a pure function of event core, original signed lease, immutable machine-key/trust history, witness proof/fence history, and causal parents, **not** the reviewing peer's current epoch. A valid final-certified epoch-1 event arriving in epoch 2 is accepted; a newly attempted write by the fenced old holder cannot get a valid new witness proof and is quarantined. One fenced witness must refuse two competing new certificates across a partition. If corruption or historical migration presents two independently verified owner heads, the reducer still displays a conflict rather than silently selecting one. A key rotation retains verification material for historical signatures while revocation prevents new endorsements. This witness binding is integration work, not an installed primitive. A standby device correction forwards the signed, idempotent intent through the existing machine routing seam and returns the admitted writer's witnessed result; it never appends to its replica. A dashboard operator session bound to the standby is not forwarded as an owner proof: the owner re-unlocks on the admitted machine or uses a device-signed route. Ambiguous forwarding returns `pending-or-unknown` and an idempotency-key status URL; the UI says `Checking save` with status lookup, never false success. If the status identifies a sleeping member, it says `Saved · Waiting for MacBook` and offers no blind Retry; Retry appears only after reconciliation refuses the old attempt and the owner chooses a fresh operation. Closing the local overlay is only a dismissal and leaves a persistent Pending entry with its idempotency key; it is never called cancellation. A real Cancel action is eligible for unsent, uncertified graph/header/decision proposals only. For an answer claim, the witness and gateway serialize Cancel against `begin-answer-dispatch`: Cancel succeeds only with positive proof that gateway dispatch never started and the token is fenced; a started or ambiguous dispatch returns `not-cancelable:answer-claimed`. Once an answer send has a confirmed delivery outcome, its pending decision transition cannot be canceled; the UI says `Answer sent · syncing`, and closing the overlay does not affect the durable send or later certification. For an eligible operation, Cancel sends the same idempotency key to the fenced witness, which atomically signs either a cancel certificate or the final commit certificate, never both. Cancel completes on the witness signature even while a member sleeps; members discard the uncertified intent when they reconnect. If the witness is unreachable, the UI says `Canceling · Waiting for sync` and does not claim cancellation. If commit wins, Cancel reports already committed and offers compensating Undo. The status endpoint must distinguish queued, preparing, certified/committed, canceled, refused, and temporarily unknown, with waiting-machine details on demand. On failover, the new writer repairs against the highest witnessed committed watermark before accepting placement writes. Offline mobile intents keep observed subject heads and are revalidated on submit. Tests cover delayed valid old-epoch delivery, forged/stale endorsement, split-brain conflict, signer rotation, a lease change mid-commit, and writer loss before witness completion.

### 7.3 API examples and privacy boundary

An overview response has `revision`, `asOf`, graph `partial`, screen-level `replicationState`, `items`, and `nextCursor`; each owner item has a typed `ref`, `title`, optional `attentionCue`, and optional expanded metadata (`role`, `primaryPath`, `visibleChildCount`, `digestVersion`, `sourceFreshness`). A decision or `Question` attention cue appears only after decision increment D ships. `nextCursor` is a signed keyset cursor over a short-lived authorized result snapshot, bound to viewer, grant version, query/filter/sort, and snapshot ID. An unrelated graph revision does not invalidate it; grant revocation, expiry, or an unavailable snapshot returns a typed restart response. No raw graph count or unfiltered cursor position is returned. The same authorization predicate applies before pagination, aggregate counts, search ranking, digest generation, and notification selection. A graph edge never grants transcript access.

An atomic move request carries `{operation:"set-primary-placement", subjectRef, parentRef, replacesPlacementEventIds, idempotencyKey}`. It names every current subject head, including multiple heads displayed as one destination. A successful response returns the new global revision, final commit certificate, and an undo token scoped to the actor and edit; undo is a new compensating event, not deletion. A `409` returns `code:"placement-conflict"`, `lastAgreedParent`, `proposedParents`, and safe source descriptions, all filtered to the actor's permissions. If one proposed parent is inaccessible, the server withholds its identity and asks for a fresh authorized placement rather than leaking a private node. A mobile offline queue may hold this intent locally, but the server rechecks role, project scope, current subject heads, cycle rules, and platform availability at submission time. A pending/unknown result exposes a status lookup and `Checking save` until witness intake is known. A witness-durable request waiting on a sleeping member shows `Saved · Waiting for MacBook`; closing that local overlay is only dismissal and the entry remains in the owner Pending list. The fenced witness atomically signs either Cancel or the final commit certificate for the same idempotency key; if commit wins, the UI offers Undo. Retry is not offered while a known member sleeps.

### 7.4 Existing mobile authorization and pagination seam

The installed mobile conversation route uses `mayUseConversation`: an owner phone may read its conversations; an MSP phone may read Telegram topics, Slack only with the owner's Slack grant, its own native app conversations, and owner app conversations only with the `ownerConversations` grant. Another MSP's app conversation and unknown refs are denied. Pool reads fail closed for an MSP when a peer app row has not yet replicated to the answering machine. Graph reads must call the same predicate on every conversation source, including linked children reached through an effort; graph membership does not change the grant.

The current flat list merges rows and then filters inaccessible ones, so its cursor can advance over hidden rows. That behavior is preserved for the legacy flat route, but it is insufficient as the hierarchy's count and pagination contract. The hierarchy endpoint must build a viewer-authorized projection first, then sort, count, paginate, and issue a cursor over that projection. A viewer's cursor must be unusable by another viewer or after grant changes; its authenticated scope, grant version, and retained snapshot are checked on every page. Unrelated edits do not restart a valid cursor. An effort whose only children are inaccessible must not reveal their number, titles, or existence through an empty-state message. A cross-link to a hidden conversation is omitted, while the owner's graph retains the relationship.

In v1, owner-authored effort titles, digests, primary paths, and provenance are owner-only because the installed Initiative and graph contracts do not supply an effort-sharing grant. An MSP's Conversations tab still shows the authorized flat conversation inventory and original transcripts, with their own collapse/filter preferences, but does not receive the owner's effort tree or a path that names hidden effort nodes. A later shared-effort view must be backed by an explicit grant and independently reviewed source-level filtering; topic access alone does not imply access to an effort rollup. This conservative behavior keeps the owner experience rich without leaking cross-topic work context to another person.

Acceptance matrix: owner, MSP with no extra grants, MSP with Slack grant, MSP with `ownerConversations` grant, and two different MSP identities each open Conversations, search, and a paged list. Owner also opens effort detail, digest, and child tree. MSP receives no owner effort title/path/digest in v1, even when they can read one of its Telegram topics. Test grant revocation between pages, an unreplicated peer app row, an inaccessible conflict destination, and a hidden-only effort. In every case, the same conversation visibility decision applies to transcript deep links and graph metadata. The dashboard's operator-session proof maps only to the owner principal in v1; on a different machine the viewer re-unlocks if that machine cannot verify the prior machine's short-lived proof.

`TopicMemory` is an evidence source, not a viewer-safe digest API. Its installed `formatContextForUser` filters recent messages but includes the topic-wide rolling summary and purpose; its `search` returns message text without a viewer argument. The hierarchy must never reuse those outputs directly in an MSP or other limited view. Generate each digest from source messages after message-level privacy filtering, then store it with a visibility principal/scope and source message IDs. Search results likewise pass message-level authorization before text or ranking leaves the server. If complete authorized history cannot be fetched, show a partial digest rather than mixing a global summary into a viewer-specific one. A separate foundation bug has been filed as feedback `fb-ac09bb24-fcd`; hierarchy acceptance includes a mixed private/shared topic test regardless of that fix's timing.

### 7.6 Data minimization and deletion

Graph transport events carry only opaque typed IDs, relationship facts, source references, and an opaque agent-local actor principal; they never copy user-authored headers, transcript text, generated digests, previews, external Telegram/Slack sender IDs, dashboard tokens, or mobile device secrets. Effort IDs are random opaque values, never title-derived slugs. In owner-only v1, the durable owner principal is the agent-local owner role identity verified at ingress; external sender proof stays at that request boundary. A future delegated-editor role needs its own pseudonym/retention contract. An unlinked effort's free-text title, outcome, and next action live only in a separate versioned `EffortHeaderStore` record addressed by opaque `headerId`; graph events reference that ID without including plaintext or a deterministic title hash. The header store uses independently erasable encrypted payloads/keys and a witnessed, signed erasure ledger keyed by `headerId`. Instar-captured transcript content uses a typed `(sourceKind, sourceId)` erasure identity that covers **all versions** of the source, not only one edit. The finite `forget-header` and `forget-source` operations, authorized by the owner or a verified source/subject erasure obligation, record a signed tombstone and immediately suppress local serving; erasure is a priority control operation outside ordinary pending queue order. It first blocks new ingest, serving, notice sends, and affected answer gateway dispatch for the target source identity, then tombstones it. The witnessed erasure fence atomically competes with `begin-answer-dispatch`: erasure-first fences the gateway token, purges the unsent payload, and records terminal `not-sent`; dispatch-first follows the started/ambiguous outcome path and never claims recall of a platform send. It purges matching queued/prepared plaintext source bundles, source-derived pending decision cues, and held notices, while preserving only opaque answer claim/attempt, dispatch phase, exact non-content send ref, and outcome metadata needed to prevent a second send; dependent pending operations either cite a still-valid independent source or are refused before certification. A witnessed erasure fence prevents an older queued operation from reintroducing text after the tombstone. The purge worker then destroys per-source or per-derived encryption keys and purges payloads from source segments, journal payload envelopes, recoverable backups, indexes, search, rendered transcripts, decision projections, viewer-scoped digests, answer gateway payload/log stores, and caches. Immutable graph cores and signatures contain only opaque refs and remain verifiable. The purge inventory also covers `TopicMemory` rolling summary and purpose text, source-bearing session transcripts, agent memory files, and active model contexts. Managed summaries/transcripts/memory are deleted or regenerated from surviving authorized sources through a source-dependency index. An active session holding the source is invalidated and restarted before it can send another answer; model context cannot be surgically erased in place. Historical external model/provider logs and platform-sent copies may be outside Instar control and are named limits in the forget status, never silently counted as purged. A source-to-derived dependency index follows generated rollups and structured quoted/replied content, including re-captured outgoing bot messages; an affected derived item is erased or regenerated without the forgotten source. A plain user retyping or external platform copy with no machine-readable lineage cannot be guaranteed erased by Instar; the UI states that platform copies remain under platform deletion authority. Generated rollups never become evidence for a later verification.

Erasure completion follows the same all-installed-member durable discipline as graph corrections. The owner sees `Removed here · Waiting for MacBook` while a peer is offline: this machine suppresses the text immediately, but does not claim fleet-wide forget. An offline installed peer may continue serving its previously acknowledged local text until it receives the tombstone; a completed forget guarantees every installed member has applied the tombstone and destroyed its local keys. This explicit pending state preserves independent offline operation without falsely promising remote deletion. An authenticated decommission/replacement can remove a permanently lost member from future membership, but cannot remotely erase a stolen powered-off device; encrypted-at-rest keys and revocation are the residual protection. A rejoining member synchronizes the erasure ledger **before** it serves or retransmits old sources; tombstones dominate payloads and an interrupted purge resumes after crash. A backup witness refuses retransmission of tombstoned payloads. The coverage reason `erased` is distinct from `partial`: a digest may say the source was removed and may no longer use it to verify a result; an open decision citing only erased evidence sets `sourceInvalidated:true`, displays `Source needed` below Conflict/Decision/Question in cue rank, and cannot produce a fresh notice. The owner may re-source it with a new exact authorized source, dismiss it, or supersede it; none of these actions restore forgotten text. The owner can inspect exactly which dependent claims were invalidated. Acceptance forgets an edited Telegram message quoted in another captured reply and summarized in an outgoing rollup while a peer sleeps, crashes during purge, rejoins, and replays the update; no Instar-held plaintext returns through transcript, journal, search, repair, or digest, while graph hashes still verify. The user-facing status stays pending until all installed members apply the erasure or a valid membership transition excludes a lost member.

**Erasure and answer-state matrix.** If a question or answer source is forgotten while an answer claim is pre-dispatch, ambiguous, awaiting owner review, sent-and-syncing, or sent-but-unlinked, purge its plaintext and all derived text immediately. Keep the opaque occurrence/attempt key, witness fence, gateway dispatch phase, outcome, and non-content send reference until the deduplication and audit retention period expires. A pre-dispatch claim whose erasure fence wins must terminate `not-sent` with a fenced gateway token; a started or ambiguous dispatch remains blocked from automatic re-send and may become `Answer needs review`. A confirmed send whose transition loses its source becomes `Answer needs linking`, not a canceled answer. UI uses `Source removed` and source-independent outcome state, never the forgotten question or answer text. Re-source requires a new exact authorized source and owner proof; no erased text is reconstructed. A forgotten question or answer payload makes the old `override-answer-send` ineligible. After re-source, any new send uses newly authored answer text, a fresh audience preview, an owner-confirmed possible-duplicate override, and a new witnessed attempt; the original opaque claim/outcome stays visible for audit.

On rollout, backfill **candidate** links from existing `parentProjectId`, Initiative topic links, topic bindings, and historical dispatch references. Mark provenance and avoid treating a directory binding as a delegation edge. Capture new authenticated live dispatch/spawn delegations in A. Keep existing app and dashboard routes valid. Build the read-only projection first as a dark diagnostic, then manual correction from All, then source-backed decisions and suggestion review behind separate flags. Owner-facing beta activates only when the real inventory probe shows useful roots from live delegation/manual placement or D's reviewed candidates; it never presents an almost-empty inferred tree as complete. Off-switch returns the flat conversation list and leaves underlying histories and initiatives intact.

History coverage is explicit and scoped to Instar's observed capture window. Each conversation records whether that window is complete, partial, or unavailable, its start, oldest/newest observed message, known ingestion gaps, and contributing source. Telegram history before bot observation is unknown unless a separately authorized import exists; the ordinary Bot API cannot backfill it. Inference and digest generation consume the coverage marker in-band. A truncated or missing observed range cannot support a confident parent assignment or a complete summary. A parent rollup that omits a child because its history is unavailable says so next to the summary and still lets the user open the known conversation.

## 8. Review and acceptance

Review lenses: DAWN's topic-history experience; architecture and migration; dashboard and mobile UX; privacy/permissions; multi-machine convergence; notification volume; inference accuracy; Telegram/Slack platform truth. Required questions: Can an effort contain multiple conversations? Can one conversation serve several efforts without duplicate notifications? What happens when a worker is moved, deleted, or inaccessible? Does a parent's summary admit missing children? Can a second user infer a private child from a count? Can a corrected relationship reappear through inference?

Acceptance scenarios: explicit parent→worker delegation survives restart and machine transfer; two levels of delegation roll up once with source links; a user moves a wrongly inferred worker and the correction persists; a related sibling appears as a cross-link without duplicating the tree; native app create-and-assign and undo work; older app clients retain the flat list; Telegram and Slack deep links open correct conversations; 100 routine worker events produce zero parent chat notices while a genuine decision or verified result can produce one bounded notice; inaccessible children leave no title/count/preview leak; an offline or behind peer retains its last verified tree but labels the graph revision itself partial until convergence; graph replay yields the same projection on each machine once complete.

DAWN's history and report failures add hard scenarios: a large handoff that exposes only an old slice cannot yield `complete` until the required recent and catch-up artifacts are actually read and their receipts recorded; a machine-local log containing half the conversation must be detected against the source inventory, name the missing machine and store, and avoid an all-clear or “nothing happened” result; every source, digest, and freshness timestamp retains its explicit offset and renders the operator's local zone; a worker's “done” statement backed only by a commit remains `unverified` and cannot produce a completed badge or notice for merge or deployment; a merge without deployment evidence likewise cannot claim deployed; claim citations and verification citations remain distinct and permission checked. A directly verified merge may be shown as such within a partial digest, but cannot silently become an effort-level done claim. These scenarios exercise the synthesis gate itself, not just final display labels.

Metrics: time to find an effort, top-level conversations scanned, correction rate by inference source, digest citation coverage, stale digest age, notification volume, inaccessible/partial tree rate, and user navigation depth. A measured pilot with real topic trees is required before auto-placement or default hiding is enabled.

The live awake Echo machine reported 164 Telegram topics on 2026-11-04, with 81 active in the preceding seven days and 47 in the preceding day; 28 have more than 100 recorded messages. This is enough scale to test the actual noise problem rather than a toy three-topic tree. The pilot samples recent and older topics across size bands, compares inferred edges with explicit delegation/project evidence and owner corrections, and records false parent assignments, missing-history rates, and top-level notice counts. Suggestions remain advisory until the pilot demonstrates high precision with no cross-project or private-content placement error; the separate activation review sets the numeric threshold from that sample rather than inventing one in this draft.

The awake machine's Initiative list contained 1,440 task rows and no `topic` links in the returned snapshot. That is a concrete warning about backfill coverage: an Initiative link import alone will not reconstruct the conversation tree here. Import should show “unlinked” and a coverage measure, then use explicit delegation and topic evidence for reviewable suggestions. It must not manufacture a complete hierarchy from title similarity.

A live source-shape check on 2026-11-04 found 166 `TopicMemory` `/topic/list` records, only 40 with a rolling summary, and **zero** with `topicName` populated. Of 48 topics active in the preceding day, only 11 had a rolling summary. The Telegram adapter's `/telegram/topics` inventory separately exposed 170 topic records, 166 with a name. Fifteen title values were duplicated, covering 30 named rows, so title text is especially unsafe as an identity or sole placement signal. Title-based suggestions can use verified adapter metadata, but cannot read names from `TopicMemory.listTopics()` alone; summaries are sparse and must not be treated as a complete title/history source. The two inventories also differ in count. The importer must join only after assigning each adapter row its configured chat scope and full `(chatId, topicId)` identity, report unmatched/unnamed rows, and avoid conflating the main and issues or future worker chats that reuse a topic ID.
