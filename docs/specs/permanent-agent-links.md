# Permanent agent links (instar.sh/a)

## Problem statement

Justin, topic 141385, 2026-11-17 15:21 (verbatim): "I'm wondering if it is at all possible to leverage instar.sh to give agents a permanent url? This would be an additional option we could provide to agents, obviously not required as we never require external/third party/centralized dependencies. However, if possible, this would allow agents to have a permanent url and would enable deep linking to the iphone and mac/windows apps". 15:22: "I would want this to, if at all possible, still leverage the agent's cloudflare or tailscale network so they could still be considered a private network. It would need to be secure". He approved the design doc (doc c101c6b8, topic 144473, "approved", 15:56 PT).

Today a link to an agent page is one machine's address (`https://<host>/…`). Each machine of an agent has its own names (a named Cloudflare host or a Tailscale name; quick-tunnel addresses change on every restart and are never used for pairing, `pairingOrigin()` in `src/server/mobilePairingRoutes.ts` ~1106), and the only app-opening links (`instar.sh/pair`, `instar.sh/doc`) carry one machine's address in the fragment, so they select the agent by address and break when that name changes or that machine is away. There is no link that names *the agent*.

### 1. The link (v1)

```
https://instar.sh/a#v=1&i=<canonical id>&t=<target>[&r=<ref>][&c=<comment key>]
instar://a#<same fragment>            (explicit-button / pasted fallback)
```

- `i`: the agent's existing canonical id, 64 lowercase hex = SHA-256(`instar-agent-id-v1` || 32-byte raw Ed25519 public key) (`src/identity/types.ts` `computeCanonicalId`). No new identity scheme, no name registry.
- `t` ∈ `home` | `doc` | `conversation`. v1 grammar, frozen:
  - `home`: no `r`. `doc` and `conversation`: `r` required.
  - `doc`: `r` = document UUID, lowercase 8-4-4-4-12 (`^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`); optional `c` = comment key, the server's existing pattern `^[A-Za-z0-9._:-]{1,200}:[0-9a-f-]{36}$` (`isCommentKey`, `src/documents/rows.ts:153`; the app's `Docs.isCommentKey` is the same), so at most 237 characters.
  - `conversation`: `r` = native app conversation UUID (same pattern), or `tg:` + a positive topic id under the server's own rule for Telegram conversation ids, a positive safe integer (`Number.isSafeInteger(id) && id > 0`, `src/server/mobileConversationRoutes.ts:170`): `^tg:[1-9][0-9]{0,15}$` and value ≤ 9007199254740991 (fits Swift `Int64`; kept as a string end to end). Slack conversations are NOT addressable in v1 (their app ids are machine-qualified negatives; two machines can share a number).
- Wire encoding and length: fields are `key=value` joined by `&`. A `%` is accepted only as `%3A`/`%3a` inside `r` or `c` (the two fields whose patterns contain `:`, which some apps encode); any other `%` makes the link invalid. Those two fields are decoded exactly once and then checked against their patterns. So a deliberately generous upper bound on the fragment (it pairs the longest target name with `c`, which the grammar never allows together, and counts every character of `c` as encoded; do not tighten it) is `len("v=1&i=&t=conversation&r=&c=") + 64 + 36 + 3×237`; input longer than that (computed from the grammar, not separately chosen) is rejected before decoding.
- Parser rules (one shared parser for universal link, `instar://`, and in-app paste; Swift and JavaScript share one table of accept/reject vectors checked into both test suites): decode once, validate the decoded value; duplicate keys, unknown keys, unknown `v`/`t`, a field the target does not take, or any field failing its pattern → invalid (explain, open nothing). No field is ever concatenated into a URL, API path or file path: the app builds fixed calls from parsed typed values.
- **A link only navigates.** It never approves, decides, sends, retries, shares, pairs or changes settings. It carries no credential, address, title, prefill or callback.
- Privacy statement (exact wording for docs/awareness): "The part after `#` is not sent in the normal web request to instar.sh. Anyone who has the whole link, and software that handles it (the chat app, clipboard, browser history), can read its agent and page identifiers. The link holds no password or access." The fallback page's no-network behaviour depends on instar.sh serving the page unmodified. Possession of a link alone grants no access to the agent. The canonical id is a stable identifier; sharing a link discloses it. A comment key (`c`) is `<author person key>:<uuid>` (`src/documents/rows.ts`), so a link with `c` also discloses who wrote that comment; `POST /agent-links` includes `c` only when the caller passes `comment` explicitly, and the awareness entry says so.

### 2. Agent server (optional, off by default)

Config: `agentLinks.enabled` (boolean, default `false`, read live per request, so turning it on needs no restart). Absent = off. Nothing changes for an agent that never turns it on.

**2a. `GET /mobile/agent-link/identity?nonce=<base64url, 32 bytes>`** (device-signed only, active devices, all person roles — added to `DEVICE_ALLOWLIST` and to the team route tiers like `GET /mobile/routes`; `Cache-Control: no-store`; it reuses the existing per-device request limits of the device-signed mobile routes; the app calls it at pairing, on the existing routes refresh, and at most once per row on a tap that finds no bound row, so no new limit is introduced (a rate-limited answer is a no-change answer, §3b)).
- Off → `404 {error:"agent-links-off"}`. The app then holds no live binding for this pairing (see 3b).
- Identity read through `readIdentityKeyFile(…, {repair:false})` (`src/identity/IdentityKeyFile.ts:194`). Both existing readers fall through to the Threadline file when `identity.json` is unusable or encrypted (`readAgentIdentityForHandover`; the Threadline loader `src/threadline/client/IdentityManager.ts` ~262-289, which also rewrites the legacy file to match on load). This route is stricter, so it can never report an id peers might not know: it refuses instead of guessing. if `<stateDir>/identity.json` exists, it alone decides — unusable → `409 {error:"identity-unreadable"}`, encrypted private key → `409 {error:"identity-key-locked"}`, no fall-through. `<stateDir>/threadline/identity.json` is used only when `identity.json` is absent. If both files are readable and hold different public keys → `409 {error:"identity-split"}` and nothing is signed. Neither file → `409 {error:"no-agent-identity"}`. The id is **computed** from the decoded public key, never taken from a stored `canonicalId` field. Unit tests cover each case and assert that, for a normal state dir, the route's id equals `computeCanonicalId` of the key the Threadline identity loader uses. **This route never mints, repairs on disk, or rewrites an identity.**
- Transcript encoding: `nonce` is the unpadded base64url form of exactly 32 bytes; any other encoding (padding, standard base64, other length) → `400 {error:"bad-nonce"}`, so one nonce has one string. `host` is the device middleware's verified host exactly as attached to the request (`instarDeviceHost`, `src/server/mobilePairingRoutes.ts` ~2943: an own name over local TLS, or the stored paired host); never read from query, body or headers; if it is empty (the middleware's fallback is `''`) the route refuses with `409 {error:"no-verified-host"}` and signs nothing. The app uses the very host string it already put into its device signature for that request: the signature only verified because the two sides agreed on it, and the server verified the signature against exactly the value it attaches (`canonicalString(…, parts.host ?? dev.host, …)` in `src/core/MobileDeviceKeys.ts:165`; `instarDeviceHost = host ?? stored host` at `mobilePairingRoutes.ts:2943`), so no second normalization rule exists to drift (`normalizeRequestHost`, `src/core/MobileOwnNames.ts:49`, drops `:443` and keeps any other port). Shared test vectors include a host with a non-default port, and an integration test checks the proof verifies over the host the request was signed for, for both a stored-host and an own-name request. `deviceId` is the authenticated principal's id. The **host** anchors the proof: device ids are assigned by the agent, so a malicious agent can choose one, but it cannot get a phone to sign a request for another agent's host.
- Out of scope, stated: two agents running as the same OS user on one machine can read each other's identity file; a Mac-app loopback pairing tells them apart only by port. This feature adds nothing there and fixes nothing there.
- Evidence: each outcome (served, off, bad-nonce, no-verified-host, no-identity, key-locked, unreadable, split) records one `featureEvidence` row under `agentLinks` (the pattern `mobilePairingRoutes.ts` uses), at most once a minute per outcome and device (the same 60-second window the existing `mobilePairing` evidence rows use, `mobilePairingRoutes.ts` ~1258, so a refreshing phone cannot flood the log); integration tests assert one row for each outcome. A `served` row means the proof was sent, not that the app accepted it: the app's binding state is the corroboration, read in the live proof. This is how an operator sees whether links are being bound and why not.
- Order of checks (fixed, so tests and evidence are deterministic): flag off → nonce → verified host → identity → sign.
- Success → `{ v:1, canonicalId, publicKey:<base64 raw 32>, proof:<base64 Ed25519 signature> }`.
- **Possession proof (closes the "another paired agent claims this id" attack).** The server signs exactly this UTF-8 transcript and nothing else:
  ```
  instar-agent-link-proof-v1\n<canonicalId>\n<deviceId>\n<host>\n<nonce>
  ```
  `deviceId` and `host` come from the device authenticator's verified request (the device id the signature belongs to and the host the device signed for), never from query or body. `nonce` must decode to exactly 32 bytes. The fixed prefix is domain separation: no other Instar signing format begins with it, so the route cannot be used as a signing oracle for rotation, recovery, ASP or threadline messages. There is no route that signs caller-chosen bytes.
- Not included in v1: `previousIds`. Key rotation has no callers in Instar today (`createRotation` in `src/identity/KeyRotation.ts` is unused) and there is no persisted rotation history. If rotation ever ships, it must add an app-verified chain of dual-signed `RotationProof`s; until then a key change is treated as an identity change (3b).

**2b. `POST /agent-links`** (Bearer, agent-facing) body `{ target, ref?, comment? }` → `{ url, appUrl }` built with the same grammar (and round-tripped through the one parser), or `404 agent-links-off`, `400 bad-target`, or the same `409` codes as §2a — it uses the §2a reader, so it never makes a link for an id §2a would refuse to serve. It returns a reference only: it creates no share, no access grant, no pairing. When this machine knows its peers' identity fingerprints (the existing identity-coherence observations, `src/core/AgentIdentityCoherence.ts`; a peer that can't be read counts as unknown, never as "same", and produces no warning) and any differs from its own, the response adds `warning:"split-identity"` with the machines named: a link made here will not open through rows paired to those machines (§3b). Each result records a `featureEvidence` row under `agentLinks`. Known gap, stated: it does not warn when a peer machine has links turned off; rows paired only to that machine show "Links are turned off on this agent." (The agent shares the link in a conversation as it would any link; access is decided when the app opens it.)

**2c. Awareness entry** `src/data/awareness/agent-links.md`: what it is, that it is optional, how to turn it on (`agentLinks.enabled: true`), how to make a link (`POST /agent-links`), the privacy statement, and that recipients need their own pairing and access.

### 3. App (iPhone + Mac; `apps/instar-ios`, branch `echo/mac-app-m1`)

**3a. Learning the binding.** Each outstanding identity call (pairing, routes refresh, or a tap-time re-check, which may overlap on one row) has its own nonce, and each answer is checked against its own nonce only. Each call also takes the next number of a per-row generation counter; an answer older than the newest state-changing answer already applied to that row is ignored (no-change answers — a 409, a network error — do not move the mark) (so a late proof cannot undo a newer `off` or `mismatch`), and forgetting or re-pairing a row discards its outstanding calls. For each device-paired agent, at pairing and on each existing routes refresh (no new timer), the app generates a fresh 32-byte nonce, calls 2a, and accepts the response only if: `SHA256("instar-agent-id-v1" || publicKey) == canonicalId` over the decoded 32 bytes, AND the Ed25519 signature (CryptoKit `Curve25519.Signing.PublicKey`) verifies over the transcript the app builds itself from its own outstanding nonce, its own device id, the host it signed the request for, and the returned id. Anything else is ignored (no binding change).

**3b. Binding lifecycle per pairing row** (`Agent.linkId: String?`, `Agent.linkIdState: none | bound | mismatch | off`). One transition table, applied to each refresh answer; Swift unit tests cover every cell, including `bound → off → bound` and `bound → mismatch → bound`:

| Answer from the identity route | stored id absent | stored id = X |
|---|---|---|
| valid proof for X | store X, `bound` | `bound` (from any state) |
| valid proof for Y ≠ X | — | keep X, `mismatch` |
| `404 {error:"agent-links-off"}` | `off` | `off` (X kept) |
| any `409` (no identity, key locked, unreadable, split) | unchanged | unchanged |
| any other 404 (an older server without the route), other status, invalid proof, network error | unchanged | unchanged |

- `mismatch` rows are not used for link resolution until the person re-pairs or X comes back. Never silently replace (covers a hostname that changed hands, a replaced machine, a restore with a different identity).
- A machine whose identity differs from the agent's other machines (a split, e.g. a pairing from before the identity handover) is a row that binds to *its own* id from the start, so it never reaches `mismatch`: links made on the other machines don't open through it, and `POST /agent-links` there warns `split-identity` (§2b). Repairing the split is the existing identity adoption path's job; after a repair, that machine proves the agent's id, so its rows go to `mismatch` and each device paired to it pairs again once (the conservative rule: never silently replace a binding).
- `bound` means "proven at the last successful refresh". A stale binding can at most send a tap to the endpoint that row already talks to; the server still checks access, and the next refresh corrects the state.
- Forgetting the agent removes the row and its binding (existing forget path). Bindings live on the device and are not part of any backup.
- Identity matching never merges pairing rows or moves credentials between them.

**3c. Opening a link.**
1. Parse (§1). Invalid → "This link isn't valid." No network.
2. Candidates = rows with `linkIdState == bound` and `linkId == i`. If none is bound, the app first runs one identity call on each row that could become a candidate — rows holding `linkId == i` in `off` or `mismatch`, and rows with no stored id in `none` or `off` (a device paired while links were off, or before the agent had them) — one call each, run through the app's existing routes-refresh path (the same per-agent requests, concurrency and timeout it already uses to refresh every paired agent, so a tap costs no more than one ordinary refresh), applies the §3b table, then looks again. These calls go only to endpoints the app already talks to and carry no link data; rows already bound to a different id are never called. A server behind an id-less row learns that an identity refresh happened at that moment (so, that the person opened some link), not which agent or page. So a link works on the first tap after the agent turns links on. If there is still no candidate, the message says why: a row with `linkId == i` in `mismatch` → "This agent's identity changed since this device paired. Pair again to open its links."; in `off` → "Links are turned off on this agent."; no row holds `i` but an id-less row answered `off` → "This device may not be paired with this agent, or links are turned off on it."; no row holds `i` but an id-less row's check could not finish or could not be verified (network error, timeout, a `409`, a rate-limited answer, or an invalid proof) → "Instar couldn't check this link right now. Try again in a moment."; otherwise → "This link is for an agent this device isn't paired with." The app keeps local counts of each outcome (opened, not paired, mismatch, off, couldn't check, chose among several) and of rejected identity answers (`proof-invalid`, `id-hash-mismatch`, kept apart from network errors) in its existing diagnostics screen, so a systematic proof failure is visible instead of looking like "not paired".
3. One → open it. Several rows that all carry the same person and role (one agent, same access, several machines; "same" means owner = owner, or the same team person key; MSP rows from different machines are always different, since their reader keys include the machine) → open without asking, trying them in most-recently-refreshed order, each at most once per tap, starting with the row whose last routes refresh succeeded most recently; only if a row cannot be reached may the next such row be tried. "Cannot be reached" is the app's existing rule for a read: the row's `AgentClient.exchange(resendable: true)` (`InstarApp/AgentClient.swift:120`) — which already tries every route of that row (Tailscale, Cloudflare) — throws unreachable (any network error, timeouts included) or ends on a status in `RouteFailover.frontCouldNotReachAgent` (`InstarApp/AgentRoutes.swift:142`: 502, 504, 520–530, which covers Cloudflare's 530 when the machine behind a named tunnel is off). The request that decides it: before switching screens, the opener makes one read the app already has, `GET /mobile/device` (the device's own status, allowed for every role), through that row's `exchange(resendable: true)`; it navigates on any answer from the agent and moves to the next equal row only when that read is unreachable. If every equal row is unreachable, the person sees "Instar couldn't reach this agent right now. Try again in a moment." Any answer from the agent itself, including not-found or denied on the target's own screen, is final: the app cannot and does not tell "not on this machine" from "not allowed", so it never probes other rows with a target. Rows that differ in person or role → ask (grouped: rows with the same person and role form one choice, and failover then runs within the chosen group), showing saved name, host, and the person/role of each row. Never pick by privilege.
4. Navigation uses the chosen row's local `Agent.id` (never `agentId`, which is the name) and the existing `NotificationRoute` path, with two new kinds: `home` and `conversation(ref)`; documents use the existing `.document(id, comment:)` kind with `decide` always nil.
5. **Link entry is read-only.** A conversation opened from a link is entered in a `fromLink` mode that does not run outbox restore/delivery (`ChatView.restoreOutbox` and the connection-return send hook) on that entry; queued messages wait for the normal non-link entry or the person's explicit retry. Read markers are ordinary and documented as such.
6. A link never opens over the lock screen, never under an open sheet, and never triggers the waiting-phone Approve card that the app shows on coming to the front: a link activation suppresses that automatic card for that activation; the pending navigation waits until unlock, and the person can cancel it.
7. The opened screen shows a one-line banner "Opened from a link · <saved agent name>".
8. Every access check stays on the agent's server; an owner's link opened by a member gets the member's result (possibly "unavailable"), revealing no title. The same "unavailable" result, with no title, is what a person sees when the chosen machine does not hold the target (see "Where each target lives" below).

**3d. Platforms.**
- iPhone: AASA gains `/a` and `/a/`; `applinks:instar.sh` entitlement exists. Add `instar` to the iPhone target's `CFBundleURLTypes` so the fallback button works.
- Mac: AASA gains a details entry for `AG9AE2H87X.io.sagemindai.instar.mac` with `/a` and `/a/` only (not `/doc` until its Mac handler exists). Add `com.apple.developer.associated-domains = [applinks:instar.sh]` to `InstarMac.entitlements` (App Store/TestFlight, provisioned). For `InstarMacDirect.entitlements` (Developer ID): add it only if the build embeds a provisioning profile that carries the capability, and the ship script checks the signed app launches (a restricted entitlement without a profile stops the app launching; Sparkle would spread that). Otherwise the Direct build uses `instar://a` from the fallback page and in-app paste. `MacWindow` handles `instar://a` and web-link activity with the same parser.
- `instar://` can be registered by any app on Mac and Windows. The `a` path is handled separately from the existing `join` path and only navigates (§3c); a squatting app that receives a link learns only the ids in it.
- Windows (topic 144319) and Android: same contract later; out of this spec's build. Windows starts with `instar://a`; Android adds `/a` to its existing intent filter.

### 4. instar.sh (`site/`)

- New `site/public/a/index.html`: a plain static file, not an Astro page (every Astro page on this site gets Starlight's injected prefetch script; a static file is copied verbatim, so it loads only its own script), `referrer no-referrer`, CSP in a `<meta>` tag `default-src 'self'; script-src 'self'; connect-src 'none'; img-src 'self' data:; style-src 'self' 'unsafe-inline'; base-uri 'none'; form-action 'none'` (no `frame-ancestors`: browsers ignore it in a meta tag, and the page holds nothing worth framing). Script is a same-origin file `site/public/a.js` (the existing `/doc` page's inline module is blocked by its own CSP in production today: the page renders only its logo). Parses the fragment with the §1 rules, never inserts it as HTML, makes no network request. Shows: "This opens in the Instar app", **Open in Instar** (`instar://a#…` rebuilt from the parsed typed values in canonical order, never the raw fragment), **Copy link** (copies the rebuilt canonical `https://instar.sh/a#…` form), a line about pairing, and install links. No redirect, no address, no sign-in prompt.
- `doc.astro` is NOT changed by this spec. Review found its script is blocked by its own CSP in production and that it would forward a browser to the host in the fragment; reviving it would make instar.sh a forwarder, the exact thing `/a` refuses. That is its own reviewed change (tracked separately), with the trade-off stated there.
- `apple-app-site-association.ts`: add `/a` and `/a/` (the static build may serve either form) to the iPhone entry; add the Mac entry with the same two paths.
- Built-output check: the built `a/index.html` loads exactly one script (the same-origin file) and no third-party script, style, frame, image or other fetched resource; plain navigation links (install pages) are allowed. That reads the HTML (a symbol); the state it stands for — the script actually runs under the CSP — is checked separately by a headless browser against the deployed `https://instar.sh/a#…`: the parsed target text renders, the button's `href` is the `instar://a#…` form, and the console shows no CSP violation (the `/doc` page passed an HTML check while its script never ran).

## Multi-machine posture

- Canonical identity: `unified` when the agent's machines share one identity through the existing identity handover (`AgentIdentityHandover`, `a2a-single-agent-identity`). This spec adds no identity state. A machine with a different identity (a split, e.g. paired before the handover existed) binds its rows to its own id, so links made elsewhere don't open through it and the link builder warns (§2b, §3b); repairing the split belongs to the existing adoption path.
- Pairing rows and addresses: each pairing row belongs to one machine and holds that machine's stable names only (named Cloudflare host or Tailscale name, never a quick-tunnel address: `pairingOrigin()` ~1106, `stableOrigin` in `MobilePairing.ts` ~55); `GET /mobile/routes` keeps them current. So an agent's link reaches it through any machine this device is paired with that holds the same identity.
- Where each target lives (what "the link names the agent, not a machine" does and does not promise):

| Target | Where it lives | Opened through a row on a machine that lacks it |
|---|---|---|
| `home` | every machine | always opens |
| `doc` | replicated by pull between machines (`src/documents/sync.ts`); a new document can be missing on a peer briefly | "unavailable", no title; opens once synced |
| `conversation`, app UUID | on every machine when native app conversations replicate (`AppConversationsReplicatedStore.ts`); otherwise on the machine that created it | "unavailable", no title |
| `conversation`, `tg:<id>` | the machine serving that Telegram topic (`mobileConversationRoutes.ts` ~171, ~629); a standby may not hold it | "unavailable", no title |

  This spec stores no conversation or document content and changes no replication: it inherits what each target's own feature already guarantees (the table describes today's behavior). A link opened through a machine that lacks the target gets "unavailable" and the person can open it again later or from another device; the app does not try other rows on an answer (§3c step 3).
- `agentLinks.enabled`: per-machine config (like every config key today). machine-local-justification: operator-ratified-exception — config is per-machine across all of Instar; Justin approved the design that names this flag (doc c101c6b8 v1, topic 144473 "approved" 2026-11-17 15:56 PT). If one machine is off, its pairing rows go `off` and links resolve through rows of machines that are on.
- App bindings: device-local by design (per pairing row, never synced), like the existing route cache: machine-local-justification: physical-credential-locality (bound to the device key that signed the pairing).
- Generated URLs: name the agent, never a machine. They keep working when a machine's address changes or the agent adds/removes machines, as long as the device is paired with a machine that holds the same identity; the machine the app picks must also hold the target (failover between equal rows covers an unreachable machine only, table above).
- Migration parity: no `migrateConfig` step (absent `agentLinks.enabled` means off, read live). The awareness entry reaches existing agents through the awareness registry on update. The AASA file and the app ship outside agent updates.

## Frontloaded Decisions

1. Link names the agent by full canonical id, not a name or short fingerprint. (Both reviewers; a name needs a registry.)
2. instar.sh stores nothing; no browser redirect in v1. (Both reviewers; Justin approved doc.)
3. No `previousIds` in v1 (no rotation exists to source them).
4. Conversations: native app UUIDs and Telegram topic numbers only.
5. Off by default; identity never minted by this feature (agents without an identity get `no-agent-identity`; the existing guarded identity creation paths stay the only ones).
6. Link-opened conversations do not flush the outbox.
7. Mac Direct build: entitlement only with an embedded profile and a launch check; otherwise `instar://` fallback.
8. Equal rows (same person and role) open without asking; different person or role asks; only a row unreachable under the app's existing read rule (`exchange(resendable: true)` / `frontCouldNotReachAgent`) moves to the next equal row.
9. `/doc` page changes are out of this spec (separate reviewed change).
10. Identity file: `identity.json` alone decides when present; the Threadline legacy file only when it is absent; both readable and different → refuse (`identity-split`).
11. Out of this spec, decided as later work: an opt-in browser address hint (show the host, ask first); the Windows and Android clients (topic 144319 for Windows); identity continuity if key rotation ever ships.

## Left behind (reviewed, deliberately not changed)

- Conformance gate: a target that only lives on one machine shows "unavailable" through another machine's row. That is the existing behaviour of each target's own feature (this spec stores and replicates nothing); making conversations survive any single machine is those features' work.
- Conformance gate: the 60-second evidence window drops repeats within a minute; the window matches the existing pairing evidence and the app's own counters keep exact counts.
- Telegram topic ids are unique within one chat; Instar agents serve one supergroup, which `tg:<id>` assumes (the server's own conversation ids make the same assumption).
- No warning when a peer machine has links off (§2b states the gap).
- A tap that finds a bound row which is unreachable does not re-check id-less rows of other machines; they bind at their next routes refresh.
- Each row is tried once per tap (conformance gate: a retry could recover a transient failure). The person can tap again, and the "couldn't check" message says so; a retry loop would add waiting to every refusal.
- Prior art: the link is a self-certifying identifier in the style of `did:key` or Matrix `matrix.to` links, without their registries or resolvers.

## Live proof (on Echo, before "done")

A real `https://instar.sh/a#…` link to an Echo conversation and to a document, sent in Telegram and in Slack (the two user channels; the link is posted as ordinary text in each): tapped on the iPhone opens the Instar app at that page with the banner; clicked on the Mac (from the Telegram and Slack Mac apps, and in Safari) opens the Mac app at that page — in a browser that does not hand universal links to apps (e.g. Chrome), the safe page with a working **Open in Instar** button is the expected result; opened in a plain browser shows the safe page whose **Open in Instar** button opens the app. Plus: the headless check of the deployed page (§4); an unpaired id → refusal, with the app's network log showing no request that carries link data and none to a row bound to another id (id-less rows get one identity call each); a `mismatch` and an `off` row each give their own message; two rows with different roles → the choice sheet; a link opened through a second Echo machine's row, and, with one Echo machine's server stopped (so all of that row's routes fail), an equal row on the other machine opening the link; the Mac Direct build (universal link if it carries the entitlement, otherwise `instar://` from the safe page); a malformed link → "not valid".

## Rollback

Flag off (`agentLinks.enabled: false`) at once stops the link builder and the identity route on that machine; rows already `bound` keep opening links until each device's next routes refresh moves them to `off`. That window is harmless: a link only navigates, and the server checks access on every request. The site page and AASA entries are static and harmless when unused; reverting the site commit removes them. App builds without the handler cannot resolve these links: the fallback page still opens, but its button and paste need an app update.

## Work Card Navigation Extension

`target: "card"` takes a required `ref` matching `wc_[0-9a-f]{16}` and no comment. It uses the existing agent identity, pairing selection, and per-request authorization. It grants no access and performs no card action. Server, site, and native parsers must agree on the shared vectors. Older clients refuse this new target until updated.

An authenticated dashboard card offers **Open in Instar**. The explicit action calls the existing authenticated `/agent-links` builder, then shows **Continue in Instar** with the checked permanent URL. The current web card remains available, including when links are disabled or cannot be built. The public `/a` page remains a no-network app fallback; it does not discover dashboard addresses or redirect to arbitrary origins.
