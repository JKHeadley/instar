# ELI16 - W27 Between-Window Admission Gate

This change adds a narrow preflight gate for W27 charter activation. The purpose is simple: before the next window can treat its charter as active, the system must prove that the observer evidence it depends on is present in the store and has the basic structure needed for review. The gate does not decide which observer corpus is correct. It only refuses activation when evidence is missing, malformed, or pretending away a known mismatch.

The gate checks two observer full-history receipts in Telegram topic 43003. Each receipt must point to an actual stored message id, declare that it read full history instead of only the current window, name its canonical source and canonical store, provide a date span, provide population counts, state extraction and dedupe rules, include a corpus hash, include quotes, include an assessment, and name stored message ids backing the receipt. It also checks that semantic-author rows keep agent-through-operator rows separate from Justin's rows, because classifying an agent-account row as Justin is exactly the kind of evidence error this gate exists to catch.

The gate also checks the prior window's tenet reaffirmation receipts. There must be a start receipt, a middle receipt, and an end receipt, and each must point to an actual stored message at its stated store location. This keeps the activation decision tied to durable evidence instead of a loose claim that the receipts existed somewhere.

The last required behavior is mismatch disclosure. The gate requires the package to surface both known corpus mismatches: Pathway says Observer 1 union archive has 2469 messages and 137 authors while Observer 2 store has 2809 messages and 122 authors; Observer 1 topic 36966 says Observer 1 union archive has 1448 messages and 299 authors while Observer 2 store has 1503 messages and 289 authors. A package that omits either mismatch is refused. This is important because silently choosing one corpus would hide the very thing reviewers need to see.

The implementation is intentionally bounded. It adds one pure validator, one CLI command, and one authenticated HTTP endpoint. The CLI is `instar gate between-window --package <file>`, with optional `--store` and `--json`. The HTTP endpoint is `POST /gate/between-window-admission`; it returns 200 when the package passes and 409 when it refuses. Tests cover parser decisions, each required negative control, route integration against store-facing fixtures, and a lifecycle-style refuse-then-pass path through the live endpoint.

Repair note: the HTTP endpoint lives under the new top-level `/gate` route prefix. That prefix is now classified in the shared capability registry as internal operator admission machinery. It is deliberately not advertised in `/capabilities`, because this is not a user-facing or agent-offered feature. The endpoint is a controlled preflight tool for the W27 charter-opening evidence package, while `/capabilities` remains the list of ordinary capabilities an agent can discover and describe.

The change has blocking authority, but only for hard structural admission invariants. It does not judge message meaning, operator intent, or which corpus is semantically better. That makes it a deterministic boundary validator rather than a low-context meaning filter. Rollback is a normal code revert: the gate writes no durable state and adds no migration.
