# Native remote desktop quality plan

Status: implementation in progress. Justin's 2026-10-28 phone test found 12–13 second sessions, a small scrolling viewer, and choppy pointer movement. This plan extends the approved remote desktop and blocker hand-off design. The operator flow remains: open Instar, enter the existing dashboard PIN, choose a machine, control it, Stop. No Telegram step or terminal task is introduced.

## Evidence and review

- The Mac prototype takes a ScreenCaptureKit screenshot in a fresh Swift process every frame and aims for a 500 ms gap between frames. Input and readiness also spawn a process per operation.
- The server encrypted frames before the bandwidth decision; the browser required exact sequence continuity. A deliberately dropped encrypted frame therefore caused the next frame to close the viewer. This is a deterministic code defect. The audit recorded two recent connected sessions ending after 12–13 seconds, but lacks a close reason, so it cannot prove that this defect caused those specific closures.
- The stream closed on more than eight queued inputs and on any capture error. Continuous phone movement can exercise both paths.
- The image already declared `touch-action: none`; the rest of the page remained scrollable and the image did not capture the pointer. Independent Astra, Claude Fable 5, and Gemini 4 Argon reviews all recommended a viewport-sized touch surface and a trackpad interaction model. Fable and Argon assumed the touch rule was absent; source inspection corrected that detail.

## Delivery steps

### 1. Reliability and phone control

1. Accept strictly increasing authenticated frame sequence numbers. A missing frame is normal under backpressure; a duplicate or older nonce is refused. Keep a fresh AES-GCM key for each grant.
2. Retry isolated capture failures with a small fixed bound. Grant revocation, expiry, permission loss, and invalid crypto still stop immediately. Capture errors never turn into unbounded retries.
3. Coalesce consecutive pointer moves and scroll deltas. Preserve every click and key action in order. Bound the queue; a discrete-command flood beyond the cap is refused.
4. Give the active viewer the entire dynamic phone viewport, including safe areas. Browser page scrolling cannot compete with remote gestures. Keep Stop visible.
5. Default touch to a relative trackpad: one finger moves, tap clicks, two fingers scroll, with a Direct mode for touch-to-target. Locally render the pointer between video updates. Mouse users retain direct control.
6. Distinguish deliberate Stop from an unexpected connection loss. A target-observed transport loss may resume the same bounded session with fresh keys. If the browser loses the connection while the target still sees a half-open stream, the same browser may prove possession of the current grant generation and replace that stream atomically. Stop and other terminal endings never reopen. No input is replayed.

Acceptance: real Mac capture/input/revoke proof; eight-minute active session with no unintended close under normal link; synthetic backpressure with frame drops and burst input; iPhone Safari and Android Chrome portrait/landscape checks; no document movement during gestures; Stop prevents any later input. The ten-minute grant and two-minute idle policy remain intact for this step.

### 2. Persistent native host and adaptive capture

The per-action Swift processes are replaced by one grant-owned capture helper and one input helper, each with bounded IPC and a self-exit when its control pipe closes. ScreenCaptureKit `SCStream` supplies continuous frames; the capture helper retains only the newest frame, while the sender skips unchanged images. Target a measured 10–15 fps at phone resolution with adaptive JPEG/WebP quality. Input and video run independently, with a cursor metadata path. A transport failure permits a bounded reconnect only after authority and identity checks, without replaying clicks or keystrokes.

Acceptance: at most one capture helper and one input helper per active grant; both exit on Stop, expiry, crash, and server restart; sustained 10–15 fps during motion on a documented connection; no unbounded frame queue; measured input and glass-to-glass latency; explicit offline/permission explanations.

### 3. Video quality across machines

Use native screen capture plus hardware H.264 encoding where available. The browser decodes through a capability-tested path with a still-frame fallback. Measure WebCodecs support on actual target browsers before choosing that path; no model review's compatibility claim is treated as proof. Keep the existing authenticated WebSocket first, then compare WebRTC as an optional transport if measured latency justifies its signaling/NAT cost. The protocol carries screen geometry, cursor, codec, keyframes, acknowledgements, and congestion feedback. Windows and Linux host adapters share the grant and browser protocol but use their own OS permission and capture/input boundaries.

Acceptance: repeated user tasks (small-target click, window drag, long-page scroll, Unicode typing, modifiers), 30 fps under active motion on supported hosts, measured p95 visual latency under documented LAN and tunnel conditions, recovery from link interruption, and live proof on each advertised platform. PIN-only operator UX and immediate revocation are invariants throughout.

## Rollout and durability

The current Mac preview is an overlay on Echo's installed package and can be replaced by an Instar update. The feature must land in the release/update path before it is presented as durable. Each stage needs unit, HTTP integration, production boot, and real browser/host checks. An emulated phone viewport does not substitute for a physical phone run. Screen images and input content stay out of logs; diagnostics record only reason codes and timing.

## First pass measurements, 2026-10-28

The public HTTPS viewer ran in a Chrome phone emulation at 390×844 for eight active minutes. The image filled the dynamic viewport, the surface reported `touch-action: none`, a touch gesture caused neither page scroll nor `pointercancel`, and Stop removed the frame. The browser observed a changed encrypted frame at all sixteen 30-second checks. A separate ten-second count saw 24 loaded images, about 2.4 fps. This proves the earlier few-second disconnect is absent in this path, but it also confirms the screenshot process is well short of smooth video. Physical Safari and Android checks and the continuous capture stage remain acceptance work.

## Continuous capture implementation status

The next branch replaces per-frame screenshot launches with a ScreenCaptureKit stream in a single native capture process. Its pipe carries length-prefixed JPEGs, including a zero-length reply when the desktop did not change. The Node wrapper retains only the last frame; the target skips encryption and transport for identical frames. The process exits when the grant ends or its pipe closes. The capture source requests up to 60 fps, while the bounded WebSocket sender requests at up to 20 fps and caps video at 10 Mbps. The grant checks still run at every operation; the slower native readiness probe is shared for at most 500 ms because the native capture and input helpers independently check the OS session on every request.

A live local helper read produced a valid JPEG, then two zero-length unchanged replies. A ten-second animated-window probe was limited by the test window itself (about five UI updates per second under elevated machine load), so it is not valid evidence for the 10–15 fps acceptance target. Production-boot, public-browser, device and latency measurements remain required before calling this step complete.

Astra's follow-up review found that a changed frame discarded by the sender's bandwidth gate could be incorrectly marked as delivered. The sender now commits the image digest only after `ws.send` queues that record. A unit regression covers the unchanged-screen retry, and native pipe tests exercise fragmented replies, malformed lengths, premature exit, cancellation, and timeout. Its final pass also found that a native helper closing its stdin could crash the parent on an uncaught `EPIPE`; stdin errors now close the affected helper through the same generation-guarded failure path. Tests send a valid capture or input reply, close helper stdin, then verify the next request fails without crashing. The public phone-emulated viewer also survived a rapid pointer burst without scrolling or closing.

A local Core Animation motion check with a 30 fps ScreenCaptureKit minimum interval requested 208 native frames in 12 seconds and observed 93 distinct images, about 7.8 distinct images per second, with no capture errors. Raising the capture source interval to 60 fps and repeating the same check yielded 213 requests and 145 distinct images in 12 seconds, about 12.1 distinct images per second, with no capture errors. The sender still requests at most 20 times per second and enforces its 10 Mbps limit. This meets the interim native-boundary motion target in one local run; public-browser throughput, sustained load and physical-device targets remain open.

The continuous build then delivered 193 images in a 12.5-second public HTTPS Chrome phone viewport, about 15.4 per second, while the active viewer remained connected. The live Mac production-boot check passed PIN unlock, encrypted frame, mouse movement and revoke. A local phone-emulated viewer remained connected for eight minutes and saw changed images at 13 of 16 thirty-second checks. The original Stop UI waited for the HTTP revoke response before clearing the image; under heavy server load that took longer than 700 ms even though the stop audit landed. The viewer now blanks and disables controls immediately, ignores late frames, and continues the target revoke request. A public phone-emulated pointer burst and immediate-blank check passed.

Two long public-tunnel checks were interrupted by Echo server replacement and an intermittent tunnel 502 during concurrent repository verification. These are observed deployment and transport limits, not evidence of a continuous-capture failure. Long public-tunnel stability, physical phone behavior, glass-to-glass latency and the full test suite remain open before this stage is called complete.

Follow-up diagnosis found repeated `[SleepWake] Tunnel restarted` events while the Mac remained awake and a public desktop controller was active. The local viewer held for eight minutes under the same capture and input path. Wake recovery now verifies that the current public tunnel reaches this agent's authenticated identity before replacing it. A healthy connection is preserved even if timer drift falsely signals a wake; a broken connection is repaired even if a half-open desktop socket remains. The recovery guard serializes overlapping wakes and discards a failed probe if another path replaced the tunnel during the check. A long public run on this guard is required before claiming the public connection is stable.

The next public run lasted nearly seven minutes, then both ends reported an abnormal WebSocket close while Echo's HTTP endpoint remained available. The server now logs one bounded closure reason without grant, operator, screen, or input data. An initial browser-only retry passed a forced disconnect test, but Astra found it could reopen access after deliberate revocation or expiry. That retry was removed from the live preview. The revised recovery keeps one logical request identity, stops old input, and permits at most three fresh-key replacements within the original ten-minute and idle deadlines. Stop, revocation, expiry, protocol failure, and authority failure remain terminal. The browser queries target state before requesting resume, keeps Stop visible while reconnecting, and fences old socket events. A 30-second ticket is idempotently returned only to the same browser proof while unconsumed, allowing recovery from a lost HTTP reply. A local test proxy abruptly cut the viewer WebSocket with code 1006 while keeping HTTP available and simulated one lost ticket response; the viewer opened a second encrypted stream about 1.1 seconds later, then Stop blanked and revoked it.

An eight-minute public check then failed near 150 seconds: the browser reported a lost WebSocket while the target still considered the old grant connected. The target stopped it later at idle expiry. The browser could not use the target-observed interruption path in this case. A signed takeover now binds the previous browser key and current connection nonce to a fresh attempt ID and replacement keys. The target checks the same dashboard PIN session, original deadlines, and a three-replacement cap, then invalidates the old stream before activating the replacement. Concurrent admission waits for its local indicator before takeover. The browser tracks the verified replacement generation even if the WebSocket upgrade never opens. Astra identified and reviewed those race conditions. A fresh public Chrome phone-emulated run stayed live for eight active minutes through the real tunnel, with a changed image at each of sixteen 30-second checks and touch movement throughout. The 390×844 viewer had no page scroll or pointer cancellation. Stop blanked it immediately, and the target audit recorded a stop with 10–99 input actions. A separate 12.5-second public motion sample on the same build loaded 211 images, about 16.9 per second, while staying live; Stop cleared it. This is a browser-emulated check, not a physical phone or a measured glass-to-glass latency result. Full-suite validation remains open; the earlier failed check is not acceptance evidence.

The final retry pass keeps temporary HTTP status failures separate from the three actual grant replacements. A controlled browser test lost two status responses, one ticket response, and two WebSockets while the target retained each old stream; it opened a third encrypted stream and Stop revoked it. Astra found no P1/P2 issue in the bounded retry change. A 12.5-second public motion smoke check on that viewer build loaded 212 images, about 17.0 per second, and Stop cleared it. The prior eight-minute run covered the same capture and signed-takeover path; this last retry-counter change did not alter capture or grant admission.

## Bounded input semantics candidate

The next isolated branch adds explicit mouse button down/up at a normalized target coordinate. The native input stream posts dragged mouse events while a button is held; the phone viewer has Drag/Release and physical mouse down/up. Pending pointer moves flush before release so the final drag coordinate stays ordered. It also adds a bounded set of key down/up controls: Command, Control, Option, Shift, navigation keys, and common shortcut letters. The phone viewer exposes modifier toggles and key buttons; physical keyboard events forward only while the viewer is active and outside its text field. A one-shot key waits for its down command to be queued before sending up.

The browser tracks pending and uncertain held-control sends. A rejected down/up initiates the bounded reconnect path. While any control is held, it sends authenticated one-second pings; the target ends a half-open stream after five seconds without that liveness, which invokes grant cancellation and native release. Stop, target-observed loss, signed takeover, and an unexpected native input-helper exit also cancel held controls. An idle helper exit immediately terminates the owning grant. The macOS fallback release helper receives only keys/buttons that this grant held or had in flight. A replacement grant's input waits for the old helper to exit and for a scoped release success reply. Missing acknowledgement or failed OS readiness leaves this host instance closed to new input. macOS cannot distinguish a local user holding the identical key at the same instant. A server restart also creates a new host instance and loses a failed release barrier; it does not prove the old control was released. Both are residual risks for the live trial and later durability work.

Swift compilation, TypeScript checking, and focused unit tests cover input ordering, queue coalescing, missed liveness, Stop/interruption/takeover cleanup, malformed transitions, touch scroll without an accidental click, physical keyboard forwarding, one-shot down failure, uncertain native ACK, and release failure. A gated production-boot test now uses a dedicated temporary Mac window to observe drag, modifier, and revoke release events; it has not been run while the preview may be in use. Physical phone ergonomics and measured input latency still require a coordinated check. This isolated input pass did not implement hardware video encoding or establish AnyDesk parity.

## Hardware video candidate

The integrated quality branch adds a Mac VideoToolbox H.264 encoder behind the same signed desktop grant and encrypted WebSocket. The browser selects it only when WebCodecs reports support for the fixed AVC baseline contract; it otherwise uses the JPEG stream. A decoding error requests an authenticated JPEG fallback within the same bounded session. The sender caps video bandwidth and queued bytes, reserves room for control messages, and requests a fresh keyframe when a dependency is dropped. Stop, takeover, and decoder replacement fence late frames and release their resources.

The combined branch passed 64 focused unit checks on 2026-10-28 for grants, transport, native helpers, video bounds, browser decoder cleanup, and touch behavior. Its HTTP integration file passed all five route checks. A first production-boot run passed the dark default, PIN budget, and route-wiring cases, but its live input case skipped after the test's own synthetic events reset macOS's idle clock. The corrected live test checks local idleness before its first input and checks controller occupancy again before resumed input. The next combined gated run passed all five production-boot cases, including live drag, modifier release, revoke, H.264 keyframe decryption, and native decode through ffmpeg on this Mac. Public browser video, physical phone ergonomics, latency, long public-tunnel stability, and the full suite remain open. The installed Echo preview is still the earlier continuous-JPEG build; this H.264 candidate is not a user-testable release yet.

## Hardware video candidate

The next isolated branch negotiates H.264 only when the browser reports support for the exact AVC Baseline 3.1 WebCodecs configuration. The target's signed grant and response bind the codec, Annex B framing, maximum even 960×540 geometry, protocol generation, and connection nonce. Each key access unit carries SPS/PPS/IDR. The native VideoToolbox encoder requires hardware acceleration, checked real-time and no-reordering properties, and a 15 fps rate. A missing encoder or browser decoder switches that logical session to JPEG compatibility mode; a resumed session signs the H.264-to-JPEG change with the original browser key. The session and original deadlines remain in force.

The sender requests at most 15 frames per second and budgets video to 5 Mbps per host, with at most 750 kB queued for video and room for control traffic. This restores the approved blocker hand-off §3 bounds in place of the continuous-preview branch's 20 fps/10 Mbps settings. Authenticated keyframe requests are limited to one per 500 ms; a compatibility fallback is accepted once per stream. A dropped access unit forces a fresh keyframe before decoding resumes. The browser bounds its decoder queue, closes every decoded frame, and rejects decoded geometry outside the signed frame header. Windows/WSL host companion and headless refusal remain separate platform work.

This candidate has compile and synthetic protocol coverage; it has not yet shown live hardware encoding, WebCodecs behavior on physical phones, or measured fps and latency. A gated production-boot Mac test is prepared to decrypt a key unit and decode it with ffmpeg after the input-quality live trial finishes. No AnyDesk parity is claimed.
