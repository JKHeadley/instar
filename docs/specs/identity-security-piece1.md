# Local dashboard access and safe identity defaults

## Problem statement

Section 12 of the approved identity settings design (25a8682be) puts the local browser link first. It gives an owner a route back into the dashboard before an update changes their usual sign-in or chat. The rest of piece 1 protects the source and destination of messages, preserves Basic sign-in, and stops disclosing dashboard PINs. The agent and any program able to read its OS account's files can produce evidence of locality. Locality alone supplies no evidence of a person's intent. The signed owner record, device enrolment, general browser session cutover and confined member tools belong to later pieces.

## Proposed design

### 1. Give the person at the computer a way in

Implement `instar dashboard open` and the same action in the local desktop launcher. Both resolve the selected agent with the installed CLI's config resolver. Support explicit print mode on a terminal for SSH with a local forwarded port. Keep the ordinary Basic dashboard available throughout. Before issuing a link, the CLI sends a random challenge to the selected local listener and verifies its response using a per-agent OS-private boot secret shared only with the installed listener. A version string, process name or self-reported agent ID cannot satisfy this check. Bind the ticket to that listener identity, machine, intended action and exact browser origin. Print mode requires an interactive terminal, takes the forwarded browser port explicitly, and warns that the link is private. Use the canonical browser origin `http://localhost:<port>`, including when SSH forwards a different port. Test IPv4, IPv6, WSL NAT and mirrored networking on supported hosts. Use the configured listener and existing WSL transport discovery. Only the exact resolved WSL host peer is additionally eligible on this route. Leave native same-host device enrolment at its existing proof floor. Refuse a tunnel, proxy, public host, forwarding headers, unknown machine, missing or mismatched Origin on exchange, or unresolved gateway. Never change a listener's network exposure to make an exchange work.

Only the local agent OS account can mint. Use a 256-bit random secret and independent public ticket ID. Store the digest, audience, agent, machine, origin and expiry in a machine-local SQLite database. Protect the directory (0700), DB, journal and launcher files (0600) using owner-checked local storage and exclusive creation, with symlink and file-replacement guards. On WSL keep secrets on its Linux filesystem. For an ordinary open, write a minimal owner-readable single-use local launch document that navigates to the exact local URL with the ID and secret in the fragment. The OS launcher sees only the private file path. The native launcher may instead use a platform URL handoff whose process arguments and diagnostic logs expose no secret. In WSL the Windows browser must be able to open the private document via the user's WSL path. Where private handoff cannot be established, offer a deliberate terminal-only print or normal dashboard sign-in. Delete the document through SafeFsExecutor after exchange or expiry, including on recovery from a crash. WSL support assumes the Windows account that owns the distribution plus its Linux user. Verify the private launch document and chosen listener are inaccessible to an unrelated Windows user, do not appear in OS diagnostics, and discard unsafe launcher paths. Mirrored networking uses loopback. NAT uses a supported, verified local-only Windows forwarding configuration. Keep ordinary sign-in if this machine cannot prove the prerequisite. The macOS local app invokes the same installed CLI for the selected agent, via its existing local launch integration in the separate InstarMac checkout. Echo owns the CLI/launcher contract and tests it with the Mac app owner in that app's own worktree. This adds no new phone or Windows application release in piece 1; piece 3 owns the Windows companion work. Exclude ticket material and browser keys from backups, sync, public links, telemetry and transcripts.

Use an isolated same-origin exchange page with a restrictive CSP, no cache, no referrer and no third-party resources. Verify the deployment has no controlling service worker on that path, including after upgrade. On load the browser copies the fragment into memory and clears it from the URL. It creates or restores a nonextractable WebCrypto key for this origin and agent. The backend issues a short-lived challenge bound to the ticket, agent and intended public key. The browser proves possession and submits the ticket and signature with an exact-origin JSON POST. Check request locality, audience, expiry, digest, challenge and signature before binding. In one database transaction, consume the challenge, bind the ticket to the key and create one locality credential; never create credentials for two keys on the same ticket. A crash before commit rolls back. A lost response can be recovered by the same key using a fresh signed challenge, the ticket ID and the committed binding, even after the fragment has been erased. Resume the same unspent action with its original deadline. Save the public ticket ID, action ID and the non-extractable key in origin-scoped IndexedDB before starting the exchange. Use the explicit action/credential ID as the key for lookup. A different key has no claim on that credential. Challenges are single-use and bind the operations they protect. Keep expiry checks inside the transaction. User-initiated revocation or expiry prevents recovery.

A browser holding the local key proves locality to a closed set of consumers: render the local recovery screen, submit the locality part of Basic recovery where the parent permits, and use the verified-local PIN budget. It gets no dashboard API authorization until normal sign-in succeeds. Use the explicit ID and the origin key. Keep the new local proof independent of ambient cookies and existing dashboard-session names; two agents on separate localhost ports must work in the same profile. Require the origin-bound key's signature on a single-use challenge covering the exact action, parameters, method, audience, origin and credential ID. Verify the peer, Host and Origin again at use. A session on another machine or local port cannot silently inherit this predicate. A local process running as the same OS user remains within the declared locality boundary.

The ticket defaults to 15 minutes, matching the parent convention for person-started flows. Treat it as a launch/retry default subject to timing evidence from the slowest supported path. The grant proves locality for one named ceremony. It expires with the launch ticket. Recovery or replacement always needs a freshly minted, action-bound link. Prevent a completed grant being replayed by atomically recording the action outcome with consumption. Return the same outcome on a proven same-key retry. Reading status, signing in or an ordinary page reload cannot renew the grant. The 12-hour and 30-day settings in §11.16 govern later dashboard sessions and confer no standing local reset privilege. Retain bindings across a normal restart until the original deadline. Sign-out, revocation, restore and expiry invalidate them. Restore hooks rotate a local generation outside the backup and delete prior locality state before listening. Exclude the entire directory on export and import even for custom include paths. Copying the whole OS account remains within the stated trust boundary. Use capped exponential backoff with jitter and Retry-After within the original deadline. A retry button remains available until expiry. Offer ordinary sign-in on expiry.

Treat the existing desktop setup defaults (10 browsers and six setups per hour in mobileBrowserDevices.ts) as initial sizing guidance for 10 concurrent tickets per agent/OS user. Allow one active challenge per ticket and key, never invalidate another key's challenge on an unproven request. Bound challenge creation per verified ticket digest. Unknown IDs allocate no durable state. To reopen a claimed ticket after response loss, load its prior key binding, then challenge that key alone. Expire challenges with the original ticket. Use the five-second SQLite busy timeout already used by RecoveryAdmission, off the main request event loop. Perform small bounded prune transactions on maintenance ticks and retry contention within the originating deadline, showing a busy state rather than invalid credentials. Existing active grants survive pressure and legitimate new launches get a retry or Basic sign-in. Echo can tune these starting budgets on measured evidence in the PR; one binding and one effect per ticket are invariant. SSH print mode shows an intelligible recovery choice on the same terminal.

### 2. Preserve sign-in during upgrade

Stage the local path before retiring PIN guidance. The updater runs a headless mint/exchange/check using a probe-only audience which no recovery, PIN or owner-action route accepts. This verifies wiring, not a real owner sign-in. Record real browser completion separately. Census existing owner paths, email/paired private channels where supported, WhatsApp verifier availability, Telegram paired owner, tunnel routing, group PIN exposure and the last successful remote unlock. If the current channel cannot verify inbound data, keep the dashboard recovery path available and surface verified setup instructions on a previously established private path, or the local status page if none exists. Never fall back to unsigned input. Where only the actual browser or remote route can establish success, show the owner that pending proof. Preserve the sign-in/recovery entry point until that proof exists. New announcements never disclose a PIN. For Basic reset with no approving device, use the local ceremony under §10. If a PIN was posted in a group or the history is uncertain, persist a monotonic disputed-claim marker and require an eligible verified owner channel or approving device that predates migration, or interactive OS administrator authentication. Password-free privilege elevation cannot settle a disputed claim. Freeze the eligible pre-migration proofs once through the active lease holder, using a versioned CAS and immutable reference to the verified custody evidence. A missing or conflicting snapshot stays disputed. On merge a dispute wins, and eligible proofs are intersected until corroborated by the authoritative holder. A partition never widens the set. Only OS-confirmed interactive reauthentication is admissible as administrator proof. A group means a multi-party platform conversation verified through metadata. Unreadable history is uncertain. A new device admitted using only the PIN cannot corroborate itself. Clear the dispute only upon the parent’s qualifying owner commitment. Record proof kind and revision; a rerun cannot refresh this snapshot. If no qualifying proof exists, retain Basic and the status page; the operator approved that outcome in §10. No CLI-only exception. Use an existing OS-authenticated administrative recovery where available. An unavailable admin proof stays unavailable. Preserve the status page and existing working sign-in while the claim is pending. Show a replacement PIN or authenticator secret once to the person. Keep the old credential until a fresh sign-in with the replacement succeeds on the owner's actual access path. Keep at most one pending replacement for the credential and role revision, with the same proof and 15-minute person-started deadline. Begin via compare-and-set, commit once after successful fresh sign-in, and expire or abandon without revoking the old credential. Record start and commit with their actual proof and send a secret-free, deduplicated notice on existing verified owner channels and the private status page. The probe-only audience cannot generate a reset or notification. General PIN/token rotation and migration of existing dashboard master credentials belong to piece 4.

Fix the source of PIN attempts at every consumer including dashboard unlock, dashboard session step-up, and mandate PIN. The GET unlock-check route reports transport eligibility and never charges a guess. Current unlock uses callerAddress and PinAttemptStore when enabled. Step-up currently computes its own key. Use one policy for charging attempts atomically, across unlock and step-up for the same PIN, with independent remote per-source and aggregate limits and existing bounded local and recognized-browser handling. Preserve stronger existing checks and per-agent rollout gates. Treat a forwarded address as evidence only if the service receives it on an origin transport dedicated to its configured tunnel, where only the managed tunnel process or its private local transport can submit a normalized address. A loopback socket plus public Host is insufficient to establish that origin. If that deployment cannot isolate ingress, put such requests in the aggregate/unattributed remote pool. Never use arbitrary headers to identify or exempt a client. Keep the fresh, action-bound local link, established owner device, and existing recognized-browser recovery usable when the remote pool is exhausted. A valid credential for locality or a known browser still has to supply the PIN and any configured second factor. Use the existing five failures per source and twenty aggregate per five minutes for ordinary remote attempts, and the existing ten failures per five minutes for the local unmarked budget. Normalize addresses with the existing resolver. Charge the verified-local budget to (agent, machine, current PIN generation), independent of the number of mints or browser keys. Bare loopback receives no new local exemption. Preserve existing recognized-browser treatment, signature and second-factor requirements. Use a bounded source table for unmarked callers in the shared verifier. Charge a failed ordinary remote guess against the aggregate and its admitted source in one operation; a successfully authenticated source may clear only its own counter. Expire the aggregate by window, never as a side effect of another caller's success. Because the live aggregate closes after twenty failures per window, at most twenty distinct failing sources in that window need separate attempt records per credential. Sources above the active bound still receive the aggregate ceiling without evicting a currently locked source. Govern old-window cleanup and recognized/local state separately. Receiver routes use the common verifier, including mandate PIN and step-up; no local duplicate Map can reset its protection. Keep attempts on durable credential-owner storage. Before piece 4, each machine owns its current PIN; all aliases of that credential route through its verifier. A partitioned proxy cannot mint a fresh budget. Return a status page with that credential holder's known sign-in address and local recovery. A verified browser, verified private recovery route and local route retain their existing limits. On corrupted or inaccessible persistent counters, hold ordinary remote PIN verification instead of resetting the budget. Reserve an independently rate-limited path for a browser with the pre-existing signed marker or a pre-existing verified private-owner recovery procedure. Before promotion verify a remote owner has an actual reserved route, including from a fresh remote browser if their normal browser is unavailable. An anonymous new browser with only a shared PIN is indistinguishable from strangers until it supplies some independent proof. Where no such proof exists, the remote aggregate cannot guarantee availability under sustained traffic. Keep staged promotion held, display this limitation, and offer enrolment of an eligible recovery route. Never exempt an unverified caller. Exercise the real tunnel and a direct or shared-proxy install before graduation.

### 4. Authenticate delivery and preserve member conversations

Move the existing LifelineIngressGuard to enforce under the shipping plan below. Reuse its paired local secret and existing transport, bounded recovery, and authenticated Telegram ingress. Distinguish evidence of the forwarding process from evidence of a person. Verify the outer transport before trusting sender fields or touching any message, callback or early handler. Require the current checkpointed platform update/logical delivery ID for duplicate suppression. Preserve existing freshness and stronger origin checks on paths that already require them. Queue only previously authenticated updates with an original ID. A later successful handshake cannot authenticate a prior unproven body. Before switching polling ownership transfer the last acknowledged platform cursor to the supported poller; use the existing single-poller lease, never two pollers. Unproven input is discarded with a non-sensitive metric; if the source supports it, recover the original from the authenticated platform before any dispatch. Otherwise notify through the established owner channel and ask for the action again. A compatibility handshake proves the sender/receiver pair can exchange a real authenticated canary. For all prior guard states, only verified original ingress can reach an owner/member/candidate control. Armed with valid proof dispatches after checking the actual person and destination. Missing, mismatched, unreadable, pre-arm, disabled/bypass and explicit observe cannot yield sender authority. On an independently verified platform envelope process using that envelope's actual sender. Otherwise an informational message may only take the existing stranger path without untrusted-body forwarding, and a callback is refused. Retire any bypass that grants sender trust from a config flag. Observe can count the effect on ordinary delivery while never executing an unproven privileged action. During mixed-version rollout retain authenticated polling or queue authenticated updates with their original provenance. Unproven callbacks never run, and no downgrade dispatches privileged content. Updaters or storage faults produce a held status and a recovery notice through an established path. The receiving application never restarts a live server as a remedy. For token-protected middleware, absence of a configured token refuses everything behind that middleware. Minimal health, public sign-in and initial exchange have separate, explicitly enumerated public or independently proven routes. Bind public health to its existing minimal payload. For an existing token-less installation, the idempotent migrator invokes the same private credential provisioner as fresh setup before the new listener accepts protected traffic. Store it once and reconcile setup-managed clients; unreadable/external client settings keep the rollout pending. Do not return the token in public setup. No-token decision order is unconditional at the protected middleware. Resolve the authoritative credential on each request. If missing or unreadable, return service unavailable before examining any request credential or delegating to a protected handler. This includes master bearer, dashboard scoped token, mobile session, device key, signed view, internal, peer and streamed protected routes. Change bearerMatches to return false when the configured secret is absent, including detail/peer-health callers. No runtime test mode may opt production out of the rule. Keep the minimal GET /health and GET /ping responses and nonsecret static sign-in/status shell registered independently ahead of this boundary. Restrict the new public transport to the exact local page, challenge, exchange and outcome method/path under a dedicated prefix; their handlers require the proof for the respective stage. The status page reveals only availability. Enumerate existing pre-mounted providers, peer protocols and ticket-only pages in the code-owned route manifest and assert their specific independent proof in the mounted router. A pre-auth mount is not an exemption from a missing dependency. Refuse operations requiring the missing credential even when the API is reached via another ingress. The nominal authenticated health or pool detail is unavailable. For a token-free upgrade the installer/private setup provisions a credential before protected services are enabled; a public HTTP request can never provision or retrieve it. iMessage consumes the native row service/provenance before dispatch. SMS or unknown service remains unverified and can receive only the supported stranger response.

Import paired identity evidence separately from legacy topic-operator candidates. Candidates retain the parent's conversation continuity for previously established solo conversations but cannot approve devices or use owner-only controls. A verified team member always gets the member path, even if a topic labels them operator. A completely unknown sender gets the stranger path. A private Needs-you item asks an owner to confirm ambiguous records using a current qualifying proof as in §10. Identify solo by verified private conversation metadata and its prior person/session mapping. A candidate in a shared topic or an allowlisted person without a recorded role gets a separate tool-free conversation pending confirmation. Privileged control requires a verified owner or session person and current share. Known private solo participants retain reduce-only stop/interrupt of their own session. Unbound controls in shared topics refuse. Place unclaimed confirmation and enforcement items on the local status/dashboard surface. A candidate’s chat cannot ratify them. Never promote on first tap or as an automatic result of local sign-in. Classify all callback prefixes by actual effect in the parent §5 table. A stop within the person’s own scope can reduce authority. An unclassified callback or a control that increases authority goes through its existing stronger proof or is refused. The owner or a verified session's person may control the session within the current share. Existing stronger approval gates still apply. Carry authenticated person, role/share revision, target session, scope and stable ID through queue, callback, resume, dispatch and outbound routing. Recheck authorization at delivery and consumption. A role/share change cancels stale work and restarts that person's session with its current permissions.

A member gets one tool-free conversation per agent/person/topic. Its runner starts with an empty tool and MCP allowlist, a private working directory, and no agent credential in the environment, prompt, shared storage or context. Where the runtime cannot supply this boundary, use the existing tool-free conversation service or hold the message for a capable executor. It has no shell, browser, vault, cross-person memory or fallback to a privileged runner. Store private history in that person's namespace, including after a resume or a lease move. A pre-upgrade session with tools cannot be inherited by a member; quarantine its history from member context, retain owner-authorized access to it, and start a clean conversation. Enforce owner capacity and fair per-person queuing inside existing session caps. Check role/share before executing every tool-bearing step, cancel queued work and suppress stale output on revocation, and record any previously committed effect. Apply author/selection filtering at shared-store reads used by topic-history injection, indexing, search, summaries, session start, resume, compaction and scheduled jobs. Test that adding an unfiltered consumer fails the wiring guard. Apply recipient/share checks at delivery; in a shared channel send private replies on the member's verified private route or hold them with a non-sensitive prompt. No private history goes to a shared transcript or an owner job by default. Notify each affected person privately once per upgrade, aggregated by the lease holder. Preserve independent conversation and authorized visibility. Until confined tokens and scoped storage ship in piece 7, member-controlled tools would run with the owner's rights; the approved interim behavior in §6.2 keeps the conversation usable.

Enumerate jobs that read shared conversations before enabling isolation. Their first step can read only the authorized member messages and runs tool-free. The server prepares a read-only selection card showing the exact derived text, source, proposed job and intended next run. The person only chooses whether to include it. The server binds immutable content digest, source revision, destination, job, occurrence and share/role revision. At Basic require the established owner proof including the configured second factor; preserve stronger requirements. A person-started card defaults to 15 minutes for approval and an agent-started request to 24 hours (§11.11). The accepted selection targets one named scheduled occurrence, including its time and normal job grace window. It expires if that occurrence is missed and cannot apply to a later recurrence. Recheck scope and signed selection at consumption. Persist actual proof type, one-time admission and cancellation. Coalesce a held contribution per job and message revision; a duplicate tick cannot page the owner again. Oversize input is split or held visibly rather than silently truncated. Pass selection as labelled data; tool actions retain independent approval requirements. Jobs requiring an unselected contribution hold that step and offer the owner the selection view. Existing owner-only jobs continue.

## Decision points touched

- Locality and proof issuance — invariant; basis: external-constraint; evidence: approved §4.6 requires machine, peer, host and possession, and excludes tunnel requests.
- Ticket redemption and scope — invariant; basis: irreversible-consequence; evidence: two independently eligible keys or unauthenticated reuse would transfer the locality credential to someone else.
- Ticket lifetime, concurrent mints and pressure — judgment-candidate; floor: single-key binding, finite expiry and bounded storage; arbiter: release owner using measured OS/SSH launch times and pressure tests before enabling.
- Recovery of an unspent local grant — invariant; basis: irreversible-consequence; evidence: only the prior key may resume the same action before the original expiry, otherwise the recovery mechanism transfers authority.
- Inbound disposition and control — invariant; basis: enumerable-domain; evidence: verified owner, verified member within share, unconfirmed legacy conversation, stranger and malformed input have separately defined routes above.
- Member routing and owner job selection — invariant; basis: external-constraint; evidence: approved §6.2 requires a tool-free conversation and explicit owner selection before any member text reaches a job with tools.
- Credential cutover and disputed claims — invariant; basis: irreversible-consequence; evidence: losing the last working sign-in or transferring a disputed account without a previously trusted proof violates §10.
- Enforcement promotion — judgment-candidate; floor: release stages, no unexplained owner/job refusal and each affected enabled job observed or waived by name; arbiter: owner through the existing approved Basic card when a new policy requires consent.

## Frontloaded Decisions

1. Reuse the existing native device proof only for its original audience. The link uses a distinct audience and a common local mint for CLI and desktop.
2. Use authenticated provider input and existing team roles. Topic labels, body assertions and receipt strings never supply authority.
3. Separate the software release ladder from the owner's per-agent change in policy. Additive link and truthful receipts need no level change. Member isolation, candidate-only owner controls and PIN nondisclosure apply on upgrade. Known-invalid authentication is refused immediately. The fresh protected middleware always requires a configured credential; the upgrader preflights existing consumers before activating a new configuration. Newly enforcing PIN/relay policy follows §10 observation and consent unless already explicitly enabled. Until authenticated relay proof works, preserve independently proven traffic, re-fetch where possible and discard unverified bodies. No setting introduced here can reduce an existing floor.

## Durability, backlog and notices

The current BackupManager intentionally excludes team authority state from ordinary snapshots. Keep TeamAccessLog and share revisions out of export and import, including custom includes; re-fetch current authority from the signed team log after restore. Member-private histories, indexes and quarantined content are excluded from ordinary plaintext snapshots and git sync. For lease moves use a currently authenticated, access-controlled team conversation transfer to the new capable holder under the same person's namespace, with acknowledged cursor and no automatic transfer to owner context. Until the actual private transfer is demonstrated, keep the person's history at its authoritative holder, serve authorized reads there or report it unavailable. Never restore private data or old permissions from an ordinary snapshot. Add a restore transition that rotates the local generation before serving, invalidates outstanding local grants, pending selections and replacements, then reconciles with the current custody log. On a partition retain the dispute and refuse new authority. Keep disputed-claim snapshots, deduplicated notices, selections, replay receipts and delivery watermarks in the lease holder’s acknowledged operational log, keyed by agent, recipient and event. Keep the signed TeamAccessLog exclusively for its established role, share and device/browser bindings. Operational cursor updates cannot grow that authority log. Re-fetch current receipts and delivery watermark from their authenticated holder before replay. Retain the current verifier's live PIN attempt windows across restore. Missing trustworthy counters hold remote checks until the risk window passes or current counters are recovered. Exclude the entire ticket, journal, launch and member-private directories via BackupManager's unconditional import/export rules for both relative path forms. An ordinary backup must contain no private member text, ticket, old authority or credentials.

Use the already configured session admission limits for authenticated queueing, including per-person fair share and an owner slot. If the configured limit permits only one session, owner access remains available and member input waits in that person's queue. As initial tuning defaults reserve at most one queueful of the existing configured session count per person, bounded globally by the existing ingress queue limit. Use the original accepted delivery TTL with no extension, pace drain to available capacity, reevaluate scope and authorization on every dequeue, and keep only the authenticated platform ID after expiry for deduplication. Overflow is visible and returns backpressure to the authenticated sender. Never retain unproven relay bodies. For selection notices keep one prompt per job and watermark, and one aggregate pending confirmation per agent. The lease holder routes a recovery notice once per state transition to the verified owner or alerts topic, with no secrets or private member text. Use existing bounded repair/backoff, honour Retry-After, record one open item until recovery and clear on proof. Urgent loss of all primary ingress uses the existing alerts path immediately. Observe degraded, pending and recovered on the dashboard.

## Multi-machine posture

- Local ticket store, transient launch file and exchange challenges — machine-local-justification: physical-credential-locality
- Browser locality key, handle and machine generation — machine-local-justification: physical-credential-locality
- Lifeline IPC secret — machine-local-justification: physical-credential-locality
- Per-agent authenticated roles, shares, notices, pending selections and delivery deduplication use the signed team log for current authority and a separate lease-holder queue for verified delivery. Store member conversation and memory under per-person namespaces. Route resumes to the authorized holder. A partition or unavailable privacy store queues at authenticated ingress. An older executor incapable of isolated routing cannot receive a member message. Hold such work until the actual receiving lease holder proves capability, blocking mixed-version cutover if an older ingress could still route it unsafely. Preserve the owner channel during the update. Piece 2 owns the general minimum-build fence.
- PIN policy follows the credential being verified. Enforce remote aggregate and per-source budgets through the authoritative credential holder across exposed listeners, while the proven local recovery budget stays with the machine-bound proof. No disconnected endpoint gains a fresh remote guess budget. Bound retries through existing queue/health machinery. Only the active owner of an ingress sends notices or acknowledges completed work. Persist replay records with the queue through transfer.
