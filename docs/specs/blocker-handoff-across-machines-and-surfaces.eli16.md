# Blocker hand-off across machines and surfaces — ELI16

When I truly need your help, I should ask for the smallest thing that solves the problem. If a one-time code or password is enough, I should give you a secure way to provide just that. I should offer a live view of one of your machines only when simpler options have failed. Before asking, I have to check what I can do myself and prove why your help is needed. The existing blocker system needs one real request recorded before it can formally classify the blocker; this design sends that minimal request first, then verifies the classification before it spreads the request or offers machine access.

The request will have one underlying record, even if you see it in Telegram, Slack, dashboard chat, or the dashboard's attention list. Each place will show the same machine, task, and current status. If you solve it in one place, I'll verify that the original problem is actually fixed, then mark the other places complete. If a device is offline, its old message may take a moment to update; the dashboard will show when it last synced. A reply saying “done” will prompt verification, not erase an unresolved problem.

For the rare case when you really must operate a machine yourself, the dashboard will offer a short remote-control session for that machine. Enter your dashboard PIN to open the selected machine’s logged-in desktop. You can click and type in its open apps, including changing files and settings. You do not have to open another bot chat, copy a command, or compare a fingerprint. The session expires after ten minutes, ends sooner if idle or disconnected, and can be stopped immediately. The PIN proves you have the dashboard credential; it does not separately verify your Telegram identity. I won't see the live screen through this session, and the system won't save video or keystrokes. Closing it doesn't claim the task succeeded; I'll check the actual result afterward. The goal is to make this work on every machine where an agent is installed, including Macs, Windows PCs, Linux desktops, and Windows hosts running an agent inside WSL. That requires a working display and input adapter on each kind of machine. A headless machine or a host missing permissions will say clearly that remote control is unavailable and offer another way to solve the blocker. If the machine holding the original blocker evidence is offline, another machine can show the last known request but cannot safely grant control or declare it solved until the evidence is reachable again. We will only advertise a platform once a real end-to-end test proves it works.

After a manual fix, I may point out an existing auto-login or repair option that would prevent the same interruption next time. I will ask once for that kind of task, remember a refusal, and respect a firm “don't ask again.” If you later express frustration about repeatedly doing that same work, I may offer the specific option once more. Saying yes starts the normal approval setup; it does not silently give me new access.

This is a security-sensitive addition. The first release stays behind a development gate, with remote control disabled until the machine adapters and identity checks pass live tests. Your approval here is approval of the design; the capability will be enabled only through the explicit rollout steps in the full spec.
