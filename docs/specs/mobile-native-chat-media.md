## 1. Problem

The Instar iPhone app's native conversations (docs/specs/mobile-native-conversations.md) carry text only: `POST /mobile/chat/app/:conversationKey` takes `{text, requestId}`, 1–4000 characters, and the device authenticator refuses any device request whose body is not JSON (`415 device requests must send JSON`). In Telegram the operator can already send the agent a photo, a file or a voice note, and the session receives it as a local path. An operator who moves from Telegram to the app loses that. Operator direction, 2026-10-31 21:59 PDT: native app conversations should be "similar to telegram". This spec brings media to the app's conversations with at least Telegram's capability, and keeps every app-sent file inside the signed-record guarantee of mobile-native-conversations.md §4.6.

## 2. Goals

1. **Send media from the app.** Photos, videos, voice notes and arbitrary files, with an optional caption, into a native conversation, a Telegram topic or a Slack conversation continued from the app.
2. **The session receives a local path**, in the tag forms Telegram uses today, so an agent needs no new skill to read what the operator sent.
3. **The agent can reply with files** into an app conversation, and the app shows them.
4. **Signed records cover the bytes.** The phone's signature over a media message covers the SHA-256 of every attached file, so a stored file can be checked against what the phone sent.
5. **No new weakness.** Files are never served in a way the app or a browser could execute, every download is an authenticated device request, an agent reply cannot attach the agent's own credential files by mistake (4.6 states exactly how far that protection goes), and nothing reaches Apple or a relay in readable form.
6. **Works on a single-provider agent.** Every part works on an agent with only a Claude subscription (voice notes included).

Non-goals: stickers, location, contact cards, polls, editing a sent message, background (app-closed) uploads, and thumbnails inside push notifications.

## 3. What exists (code survey, 2026-11-01, branch echo/mobile-native-conversations-inc2 at 3b1a60bae)

- **Telegram inbound** (`src/messaging/TelegramAdapter.ts`): `handlePhotoMessage` downloads the largest photo size to `<stateDir>/telegram-images/photo-<ms>-<messageId>.jpg` and routes `[image:<path>] <caption>`; `handleDocumentMessage` saves to `<stateDir>/telegram-documents/<ms>-<cleaned name>` and routes `[document:<path>] <caption>`; `handleVoiceMessage` downloads to `telegram-voice/`, transcribes through `resolveTranscriptionProvider` (Groq or OpenAI), routes `[voice] <transcript>` and deletes the audio. A Telegram `video` message has no handler and is not delivered. Nothing prunes `telegram-images/` or `telegram-documents/`. The Bot API's `getFile` serves at most 20 MB.
- **Telegram outbound media** exists only for internal automated senders (the origin outbox): `src/messaging/telegram-origin/OriginMultipart.ts` caps uploads at 50 MiB per file, 64 MiB per operation and 10 files and keeps the bytes in the durable outbox under their SHA-256 before dispatch. No session reply script sends a file to Telegram. The Bot API itself accepts at most 50 MB (decimal) per uploaded file.
- **Slack**: inbound `file_share` files are downloaded by `FileHandler` into `<stateDir>/slack-files/`; `FileHandler.uploadFile` uploads through Slack's three-step external upload with a `*.slack.com` host check.
- **App conversations** (mobile-native-conversations.md increments 1–2): per-conversation append-only JSONL with an SQLite index (`AppConversationStore`); `validateAppEvent` builds each event from the fields it knows and returns `null` for an unknown `kind`; the `appConversations` replicated-store kind drops fields not in its `knownFields` list and counts them; message events carry the signed `origin` and machine `receipt` (`AppRecordSignatures`, with versioned machine payloads such as `instar-app-redaction-v1`); `appInboundDispatch` writes the tag `[app:<alias> "<title>" from <owner>( (📱 signed))]` and a context file that says "Only relay conversational text — not tool output, file contents, or internal reasoning"; `POST /app/session-reply` accepts exactly `{conversationId, text}`.
- **Device authentication** (`deviceAuthenticator`, `src/server/mobilePairingRoutes.ts`): an explicit allowlist; canonical string `v1\n deviceId\n host\n METHOD\n pathWithQuery\n timeMs\n sha256(raw body)` under the phone's P-256 Secure Enclave key, ±60 s, replay guard (2,000 entries per device, 3-minute lifetime; a full guard answers 429); raw body kept by `express.json({limit: '12mb', verify: keepRawBody})`; a 120-per-minute authentication-time limit except on send routes. Device records are machine-local and bound to the paired hostname.
- **File opening** (`openCheckedDescriptor`, `src/server/fileRoutes.ts`): opens the resolved path and compares the descriptor's device and inode with the checked `stat` (it does not pass `O_NOFOLLOW`). `isNeverServed` matches key-material paths relative to the project directory.
- **Moving bytes between machines**: the `working-set-pull` mesh verb (`src/core/WorkingSetPull.ts`) moves files in slices of at most 1 MiB; its serve side reads and hashes the whole file synchronously at offset 0, which is acceptable for small working-set files and not for 50 MiB blobs. The replicated-store journal is not a place for file bytes (aggregate budget 64 MiB).
- **Push** (mobile-push.md): the APNs payload never carries content; the Notification Service Extension fetches a short title over `GET /mobile/attention/:id` with a narrow per-device notification read token.

## 4. Design

### 4.1 The media record: a new event kind

Media messages are a **new event kind, `media-message`**, not extra fields on `message`. An older version's `validateAppEvent` returns `null` for an unknown kind, so a replicated `media-message` is refused and counted there, never stored as a file-less or empty message (adding fields to `message` would be silently stripped by the older validator and kept forever, since events are immutable). A unit test runs the current `message` validator over a `media-message` record and asserts `null`.

A `media-message` has every field of `message` (`eventId, messageId, conversationKey, role, text, at, machineId, origin?, receivedAt?, receipt?`) plus `attachments`, 1–10 entries:

```json
"attachments": [{
  "attachmentId": "<sha256(messageId, index)>", "index": 0,
  "sha256": "<hex of the file's bytes>", "size": 1048576,
  "declaredKind": "photo" | "video" | "voice" | "file",
  "kind": "photo" | "video" | "voice" | "file",
  "mediaType": "<the sniffed type, 4.4>", "declaredType": "<what the sender declared>",
  "filename": "<as sent, 1-255 characters, untrusted>",
  "durationMs": 12000, "width": 4032, "height": 3024,
  "transcript": "<optional, voice only, ≤ 4000 characters, from the phone>"
}]
```

`declaredKind` is what the sender said; `kind` is what the bytes are (4.4). `durationMs`, `width` and `height` are optional display hints, never trusted for anything else. `text` may be empty in a `media-message`. Delivery events, browse, sync, the index, `lastPreview` and delivery-state reduction handle the new kind.

**Every new event kind and field is listed for replication.** The replicated record's `knownFields` gain `attachments`, `attachmentId`, `attachmentIds`, `provider` and `platformMessageId`, and `validateAppEvent` (whose accepted kinds the replicated store follows) gains the kinds `media-message`, `transcript`, `platform-media` and `purge` (4.5.1, 4.7, 4.9). A unit test round-trips one event of each new kind through the replicated envelope and asserts nothing is dropped.

**Size.** A `media-message` must fit the existing limits: the store's 256 KiB line, the origin's 64 KiB `bodyB64` and the replicated journal's 80 KiB entry. Preflight therefore builds the event exactly as it will be stored (with `origin`, `receipt` and attachments) and its replicated record exactly as it will be journaled, and refuses with `413 message-too-large` before any upload is claimed when the serialized record exceeds 72 KiB or `bodyB64` exceeds 64 KiB. As a quick first check the app keeps the signed body under 32 KiB and all transcripts under 4,000 characters, which always fits; the serialized check is the authority. A unit test stores the largest accepted media message and checks it against all three limits.

**Bytes are content-addressed** in `<stateDir>/app-media/blobs/<sha256[0:2]>/<sha256>`, written once, mode 0400. A blob is never written into the conversation JSONL, the replicated-store journal, a log or the message index.

### 4.2 Uploading from the app

The app uploads each file first, then sends one message naming the uploads. All routes are device-signed and allowlisted (4.10). Uploads run while the app is in the foreground or within the short background time iOS grants an app that was just backgrounded; uploads with the app closed are not supported, because every chunk must be signed within ±60 seconds of being sent and a closed app cannot sign.

1. **Start.** `POST /mobile/media/uploads` `{conversationRef, size, sha256, declaredKind, declaredType, filename, requestId}` → `{uploadId, chunkSize, received: [], expiresAt}`. `conversationRef` is the canonical key of the target: `app:<uuid>`, `telegram:<topicId>` or `slack:<team>:<channel>[:<thread>]` (the registry's canonical Slack key; a machine-local negative alias is never signed or stored). `chunkSize` is 1 MiB (1,048,576). Idempotent through `MobileChatRequestStore` on `(deviceId, requestId)` with payload hash over every field of the body except `requestId`: a retry returns the same `uploadId`, a changed field is `409 payload-conflict`. Refusals: `size` 1 byte – 50 MiB (`413 file-too-large`); the device has 4 open uploads or 256 MiB staged (`429 too-many-uploads`); this machine's staging area holds 1 GiB (`507 upload-staging-full`); the admission reservation for the file cannot be taken (`507 media-store-full` or `507 media-disk-floor`, 4.7); an unknown or deleted target (`404`). Staging counts chunks and the assembled file. A file whose `sha256` is already a live blob reserves 0 bytes.
2. **Chunks.** `PUT /mobile/media/uploads/:uploadId/chunks/:index` with `Content-Type: application/octet-stream` and the chunk bytes as the raw body: exactly `chunkSize`, except the last. `:index` is canonical decimal (`0` or `[1-9][0-9]{0,5}`), so `07` is refused. Each chunk is its own signed request, so the signature covers the SHA-256 of that chunk's bytes. The server checks that the upload belongs to the signing device, the index is in range and the length is exact, writes the chunk to `<stateDir>/app-media/uploads/<uploadId>/<index>`, fsyncs it, and records it with its SHA-256. A repeated chunk with identical bytes answers `200` again; different bytes for a recorded index are `409 chunk-conflict`. Chunks have their own per-device bucket of 240 per minute and do not draw on the 120-per-minute read allowance.
3. **Resume.** `GET /mobile/media/uploads/:uploadId` → `{received: [indexes], state, expiresAt}`. After a dropped connection or an app relaunch the app sends only the missing chunks. An `uploadId` this machine does not know answers `404 upload-unknown`; the app treats that as "start over" (it happens after the paired hostname moves to another machine, where the phone's device record also does not exist, so the phone must re-pair anyway, mobile-device-keys.md §4).
4. **Completion** is one idempotent procedure, `finalizeUpload`, used both here and by recovery: when the last chunk is recorded, a worker thread (never the event loop) concatenates the chunks in order into `uploads/<uploadId>/assembled` while hashing (or, if an `assembled` file already exists, re-hashes it), checks length and SHA-256 against the start request (`409 hash-mismatch` otherwise; the upload is discarded and the app starts over), sniffs the type (4.4), sets the file mode to 0400 and fsyncs the file and its directory, records the sniffed type and marks the upload `complete` in one database transaction, and only then removes the chunk files. Each step is safe to repeat. Until then `GET` reports `state: "assembling"`.
5. **Upload recovery** at boot and in the hourly sweep, so every crash point has one answer: a chunk row whose file is missing or the wrong length is dropped (the app resends it); a chunk file with no row is removed; an upload in `assembling` runs `finalizeUpload` again (which re-hashes an existing `assembled` file and, if it does not match, removes it and assembles again from the chunks which still exist, since they are removed only after `complete`); a `complete` upload whose chunk files remain has them removed.
6. **Expiry.** An upload not claimed by a send within 24 hours of its start expires; an hourly sweep removes its directory through `SafeFsExecutor` and releases its reservation. An expired `uploadId` answers `410 upload-expired`. Upload state is `<stateDir>/app-media/uploads/index.sqlite` (WAL).

### 4.3 Sending a media message

`POST /mobile/chat/app/:conversationKey` (and the Telegram and Slack send routes, 4.9) accept an optional `attachments` array in the same signed JSON body: `{text, requestId, attachments: [{uploadId, sha256, size, declaredKind, declaredType, filename, transcript?}]}`. Because the device signs the SHA-256 of this exact body, **the phone's signature over the send request covers the SHA-256, size, declared kind, declared type and filename of every attached file, and any phone-made transcript.** That is the binding between the signed record and the bytes. A body with `attachments` creates a `media-message`; without it, a `message`, exactly as today.

The send keeps the order of mobile-native-conversations.md §4.2 with these additions:

- **Preflight** checks each attachment: the upload exists, belongs to this device, targets this conversation, is `complete`, and its recorded `sha256`, `size`, `declaredKind`, `declaredType` and `filename` equal the body's (`409 attachment-mismatch`, naming the index). At most 10 attachments and 64 MiB per message (`413`). Text follows the existing rule (now 0–4000 when attachments are present) and exact-token removal; a caption is text. Phone transcripts and filenames get the same treatment as the caption before they are stored or delivered: `scanInbound` runs over them (so a dictated pending pairing code declines that pairing), and exact-token removal (pairing invites, desktop codes) applies to them. A message with any token removed, in its caption, a transcript or a filename, is a redacted record (4.13).
- **The idempotency hash** covers the text and, per attachment, `sha256:size:declaredKind:declaredType:filename:transcript-hash`.
- **Atomic claim, then persist.** After the request's atomic reservation, one SQLite transaction claims every named upload (`state: complete → claimed`, `messageId` set) and fails as a whole if any is not `complete` (`409 upload-already-sent`, releasing the request reservation), so two different requests can never consume the same upload. Then (a) each assembled file is re-hashed in a worker and renamed into the blob store (same filesystem, atomic); if the blob already exists the assembled copy is discarded; the blob and its directory are fsynced; (b) the `media-message` event with its `attachments`, `origin` and `receipt` is appended and fsynced; (c) the uploads are marked `sent`. A message event is never written before its blobs are durable.
- **Recovery.** A claim belongs to its send request. At boot and in the hourly sweep, recovery touches a `claimed` upload only when its claiming request is no longer in progress in this process (at boot, none is) and that request has been `entered` for more than 5 minutes (the parent's stranded-request rule), so a send that is still hashing or publishing is never undone. Then: a `claimed` upload whose `messageId` has a stored event is marked `sent`; one whose event is missing (crash between claim and persist) returns to `complete` if its assembled file is still there, or to `complete` pointing at the blob if (a) already ran. A blob with no referencing event is an orphan (4.7). Boot recovery of the send request itself is the parent's (§4.2 step 8): never re-dispatched blind.

### 4.4 Content types

The server decides a file's type from its bytes, never from its name or the sender's declaration:

- **Sniffing** reads the first 4 KiB against a fixed table in code: JPEG, PNG, GIF, WebP, HEIC/HEIF (`ftyp` brands `heic`, `heix`, `mif1`, `msf1`), MP4/QuickTime video (`ftyp` brands `isom`, `mp41`, `mp42`, `qt  `, `M4V `), M4A/AAC audio (`ftyp M4A `), Ogg/Opus, MP3, WAV, PDF. Anything else is `application/octet-stream`. There is no fallback to the extension.
- **Kind follows the bytes.** A `photo` must sniff as an image type, a `video` as a video type, a `voice` as an audio type; a mismatch gets `kind: "file"` (its `declaredKind` is kept for the signature check) and the response lists `reclassified: [index]`. The message is still delivered; a misdeclared file is never refused.
- **Any file may be sent as `file`.** What protects the operator is how files are served back (4.8), not a list of forbidden types.

### 4.5 How the session receives media

`appInboundDispatch` (and the Telegram and Slack dispatch for app-sent media, 4.9) gives the session one line per attachment before the caption, in Telegram's forms:

- photo: `[image:<path>]`
- file: `[document:<path>] (<display name>, <mediaType>, <size>)`
- video: `[video:<path>] (<duration if known>)`
- voice: `[voice:<path>] <transcript>` (4.5.1)

**Paths are server-chosen.** `<path>` is `<stateDir>/app-media/session-files/<messageId>/<index>-<safe name>`, where the safe name keeps only `[A-Za-z0-9._-]`, is clipped to 100 characters and gets the sniffed type's extension. The copy is made with a copy-on-write clone where the filesystem supports it (`COPYFILE_FICLONE`: APFS, btrfs and XFS reflink) and a full copy otherwise, mode 0400, so a session that edits or deletes its copy cannot change the stored blob through that copy.

**Display names cannot forge a tag.** The `<display name>` is the filename cleaned exactly like a conversation title (control characters, `"`, `[`, `]`, `(`, `)` stripped, whitespace collapsed) plus removal of the 📱 character, clipped to 60 characters; the media type is from the fixed table. The same cleaning applies wherever a filename reaches a session or a notification.

**History context is lazy.** The context file `appInboundDispatch` writes lists earlier media messages as `[image] <display name>` lines without paths and says: "To open an earlier file, run `app-media-path <attachmentId>`." That helper (installed beside `app-reply.sh`) calls `GET /app/media-path/:attachmentId` (Bearer, bind token, owner only), which makes the session copy (pulling the blob first if needed, 4.12) and prints the path. If the blob is not local and cannot be pulled within 30 seconds, the helper exits non-zero with a plain line ("this file is not on this machine yet; <peer> is not reachable") and never hangs the session. Building context never copies or pulls files. Because every blob replicates eagerly to every machine (4.12), the helper normally finds the blob already local; the pull it starts is only a fallback for the replication window that `singleCopyBlobs` measures and alarms on. The context file's rule line becomes "Only relay conversational text and the files you mean to send — not tool output or internal reasoning."

Session copies are removed by the hourly sweep 30 days after creation; `app-media-path` re-creates them.

#### 4.5.1 Voice notes

The app records voice notes as M4A (AAC) and **transcribes them on the phone** with iOS on-device speech recognition (`SFSpeechRecognizer` with `requiresOnDeviceRecognition = true`), sending the result as the attachment's `transcript`, covered by the phone's signature. So voice notes work on an agent with no transcription provider, and by default the audio never leaves the operator's devices and machines. If the phone has no on-device recognizer for the language, or recognition fails, the attachment has no `transcript`. A transcript is never cut: if it would exceed 4,000 characters (or push the message over the size check of 4.1), the phone sends the voice note without it, says so in the app ("too long to transcribe here; the agent gets the audio"), and the server-side fallback below applies, its transcript event being stored whole. The session's line then reads `[voice:<path>] (transcript too long for the phone; see the transcript note or the audio)` until the server transcript arrives.

For a voice attachment without a phone transcript, the owning machine uses the server-side provider `TelegramAdapter.resolveTranscriptionProvider` already uses (extracted into a shared `VoiceTranscription` module that both call), if one is configured; the result is stored as a separate `{kind: "transcript", eventId, messageId, attachmentId, text, provider, at, machineId}` event (machine-produced, unsigned, marked as such in the app). Server transcription has a 60-second limit; past it the message is dispatched without a transcript and the transcript event is appended when it arrives. With neither, the session receives `[voice:<path>] (no transcript)` and can still read the file. The audio is kept (unlike Telegram's handler, which deletes it).

### 4.6 The agent's reply with files

`app-reply.sh` gains `--file <path>` (repeatable, up to 10), placed before the message text like `telegram-reply.sh`'s flags. The script resolves each path to an absolute path and posts `{conversationId, text, files: [{path}]}` to `POST /app/session-reply`, which now accepts those three keys, allows empty `text` when `files` is non-empty, and still requires the bind token and ownership (`409 not-owner`). For each file the route:

1. **Confines the path.** After `realpath`, the file must be a regular file inside one of three roots: the project directory, the per-agent outbox `<stateDir>/app-media/outbox/`, or the OS temporary directory (`os.tmpdir()` and `/tmp`, after `realpath`). Anything else is `403 path-not-allowed`. Inside those roots it is refused (`403 key-material`) if it matches the file viewer's never-served list or a fixed home-level credential denylist matched by path component: `.ssh`, `.gnupg`, `.aws`, `.azure`, `.kube`, `.docker/config.json`, `.config/gh`, `.config/gcloud`, `.netrc`, `.npmrc`, `.pypirc`, any `.claude*` or `.codex*` sign-in directory, `Library/Keychains`, and any `.instar/` directory other than this agent's own `app-media/outbox/`. This is a confinement plus a denylist, not a guess about content.
2. **Opens it once and checks it.** The file is opened with `O_RDONLY | O_NOFOLLOW`, and the descriptor's device and inode must equal the checked `stat` (the `openCheckedDescriptor` comparison, plus `O_NOFOLLOW`), so a symlink swapped in after the check is refused. A file whose `fstat` shows more than one hard link is refused (`403 hard-link`), so a hard link to a key file under an allowed root cannot pass as an ordinary file.
3. **Limits and reservation before copying.** The checked descriptor's size is compared with the per-file (50 MiB) and per-reply (64 MiB, 10 files) limits (`413`), the disk floor is checked, and the admission reservation of 4.7 is taken for the reply's total size (`507 media-store-full` or `507 media-disk-floor`), all before any byte is copied. The copy then stops and refuses (`413`) the moment it passes the size it reserved, so a file that grows while being copied cannot consume more.
4. **Snapshot.** The bytes are copied from the checked descriptor into a private staging file (mode 0400, in `app-media/uploads/`), hashing while copying. Every later step reads that same snapshot, so a concurrent change to the source cannot slip past the scan.
5. **Credential wall on every file.** In a worker, every snapshot is scanned with the same live-credential check as reply text (`credential-exposure-guard`): text files as a whole, other files over their printable runs of 16 or more characters. A live credential refuses the reply with the existing non-overridable `422`, naming the file.

6. **Publishes the snapshot**: renames it into the blob store (already hashed), sniffs the type, and sets `kind` from the bytes (image → `photo`, video → `video`, audio → `voice`, else `file`; `declaredKind` is set equal to `kind`).

**What this protects against, stated plainly.** Confinement, the denylist, the hard-link refusal and the scan stop an agent from attaching a credential file by mistake or because a message talked it into naming one. They do not stop a session that deliberately copies a key into an allowed folder inside an archive or encrypted file: compressed and encrypted contents cannot be inspected. That is the same boundary mobile-device-keys.md §2.2 already states (a process running as the agent's OS user is not contained), and the recipient is the operator's own paired phone. The agent awareness text says this.

The caption goes through the existing outbound pipeline (credential wall, tone gate with its advisory 422, duplicate suppression keyed on text plus attachment hashes). The `media-message` (role `agent`) is appended after its blobs are durable, then the push trigger fires (4.11). An agent reply has no device `origin`; its attachments carry `sha256`, and the app checks every downloaded file against it before showing it (4.8).

### 4.7 Storage, capacity and freeing space

- **Admission is capped from replicated metadata.** `mobilePairing.native.media.maxStoreBytes` (default 20 GiB, read live) is an agent-wide admission cap. Every path that admits a new file into the agent (an upload start, an agent reply, a Telegram or Slack inbound copy) first takes a reservation on the admitting machine. Agent usage is computed from replicated metadata, not from local disk: the sum of `size` over the distinct `sha256` values referenced by the live `media-message` and `platform-media` events this machine holds, plus this machine's open reservations, kept incrementally as a reference-count table in the store's index (updated when an event is indexed, tombstoned or purged), never rescanned per request. Event replication does not wait for blob pulls, so this sees other machines' completed admissions within the event-replication lag. **Honest limit:** another machine's admissions are visible here only once their events replicate, so the cap is a soft cap. In normal operation the overshoot is the admissions made during one replication interval; through a full partition, each side can admit up to the cap on its own, so the agent can hold up to the cap times the number of partition sides. That is accepted: the cap is a storage-planning limit, not a safety limit, and coordinating admissions across machines would make the phone's uploads fail whenever a peer is asleep. The disk floor below is the hard protection for every disk. A file whose `sha256` is already referenced reserves 0 bytes.
- **Physical floor for everything.** No machine writes a blob, by admission or by pull, while its volume has less than 5% or 2 GiB free (whichever is larger). Admissions answer `507 media-disk-floor` (inbound copies are skipped, the session still gets the platform's own download, and the app shows "file not kept: disk full"); pulls pause and the blob counts in `missingBlobs`.
- **Pulls are never stopped by the admission cap**, since a replica of an admitted file is the agent's memory, not new content.
- **What counts.** The cap counts live references. Blobs referenced only by deleted conversations live in `app-media/deleted/`, are reported separately (`deletedBytes`), and do not count, so deleting a conversation frees capacity under the cap without destroying anything. A tombstone moves a blob to `deleted/` only when no live reference remains on this machine.
- **Freeing disk is an operator action from the phone.** The app's Storage screen lists deleted conversations, and Telegram and Slack conversations with stored media, with their file sizes, and offers "Permanently remove files". That sends a device-signed `POST /mobile/media/purge` `{conversationKeys, requestId}` (idempotent through `MobileChatRequestStore`), which accepts tombstoned app conversations and Telegram or Slack conversations (a live native app conversation is refused with `409 conversation-live`: "Delete the conversation first, then remove its files"), and appends replicated `{kind: "purge", eventId, conversationKey, attachmentIds, at, machineId}` events. `attachmentIds` is the exact set of attachments in that conversation that the accepting machine holds when the request is accepted; a later attachment in a platform conversation is never covered. The set is recorded in the request's reservation first, then written as events of at most 500 attachment ids each, with `eventId` derived from `(deviceId, requestId, conversationKey, batch)`, so a crash midway resumes from the reservation and a repeat merges away; the request is `done` only when every batch is stored. A purged attachment no longer authorizes downloads, drives pulls, counts toward usage, `missingBlobs` or `unrecoverableBlobs`, so a machine that has not yet applied the purge cannot cause another machine to pull a removed file back, and no alarm is raised for a file the operator removed. On every machine that holds the purge, the blobs of those attachments that no unpurged attachment references are removed through `SafeFsExecutor`; the session copies of those attachments under `app-media/session-files/` are removed with them; the records stay, and their attachments read `bytes: "removed"`. A purged attachment that arrives on a machine after the purge (out of order) is never pulled. A purge is re-applied idempotently by the hourly sweep, and applying a tombstone first checks for a stored purge of that conversation, so a purge that arrives before its tombstone still takes effect. Purging a platform conversation removes Instar's media-store copies and session copies only: the platform keeps its own, and the original download files the Telegram and Slack handlers already keep (`telegram-images/`, `telegram-documents/`, `slack-files/`, outside this feature) remain. The Storage screen and the purge response say so in plain words.
- **Crash orphans are reclaimed.** A blob that no event this machine holds references, and that no upload or pending delivery names, is an orphan (only an interrupted write on this machine can make one: a send, an agent reply or a Telegram or Slack inbound copy, each of which writes the blob before its event; a pull needs a referencing event). The hourly sweep removes an orphan 7 days after it was first counted, through `SafeFsExecutor`. Apart from these two rules, nothing removes a blob.
- **Store-full notice.** When admissions are refused, the machine first self-heals: release expired uploads and abandoned reservations and recompute usage. If admissions are still refused, one attention item (`conditionKey: "app-media:store-full"`, cleared when usage drops below 90% of the cap) says how much is stored, how much sits in deleted conversations, and that the app's Storage screen can permanently remove files or that `maxStoreBytes` can be raised. The disk floor has its own item (`conditionKey: "app-media:disk-floor:<machineId>"`) naming the machine and how much space its missing files need; it clears when the floor is cleared.
- **`/health`** (authenticated) reports per machine `appMedia: {liveBytes, deletedBytes, stagedBytes, reservedBytes, blobs, orphanBlobs, missingBlobs, unrecoverableBlobs, singleCopyBlobs, inventoryAsOf, openUploads}`; `GET /health?scope=pool` merges machines, marking an unreachable machine `failed`. Counters that need a full reference scan (`orphanBlobs`, `missingBlobs`) come from the hourly sweep with its time in `inventoryAsOf`, and are `null` while the index cannot be read; never a fabricated 0.
- Paths are added to the state-coherence registry, to the Spotlight-exclusion list beside `telegram-images/`, and to the file viewer's never-editable paths.

### 4.8 Downloading media to the app

`GET /mobile/media/:sha256?ref=<conversationRef>` (device-signed, allowlisted, `active` devices only).

- **Authorization.** The device must be `active` at this request (a ledger revocation takes effect at once), and `<sha256>` must be referenced by an attachment of a message in the named live conversation, or by an unpurged `platform-media` event of that Telegram topic or Slack conversation (4.9; the event, not the rotating platform log row, is the reference). Anything else answers `404`, the same as a hash nobody holds, so the route cannot probe which files exist. There are no bearer-capability, signed or public media links. All paired devices are the operator's; per-device access means every request is checked against that device's current status.
- **Ranges.** `Range: bytes=a-b` is honored (one range per request; the signature covers the path and the empty body, and a range only selects which bytes of an authorized file are returned). The app downloads into its own cache with iOS Data Protection `complete`, and before showing or playing a file it hashes the complete cached file and compares it with the attachment's `sha256` and `size` from the history response; a mismatch discards the cached copy, shows "this file did not arrive intact, tap to retry", and is reported to the agent's degradation log through the next request. Ranged requests only fill the cache; nothing is displayed until the whole file is present and verified. The app never hands an Instar URL to a web view.
- **Response headers, always:** `Content-Type` = the sniffed type only if it is on the inline-safe list (the image, video and audio types of 4.4 and `application/pdf`), otherwise `application/octet-stream`; `Content-Disposition: attachment; filename="<safe name>"` for everything not inline-safe; `X-Content-Type-Options: nosniff`; `Content-Security-Policy: default-src 'none'; sandbox`; `Cache-Control: private, no-store`; `Cross-Origin-Resource-Policy: same-origin`. `text/html`, `image/svg+xml`, `application/xhtml+xml` and JavaScript types are never served as such.
- **Integrity.** Bytes are streamed with asynchronous positional reads from a descriptor opened with `O_NOFOLLOW` and checked against the blob's inode. A blob's hash is checked when it is written or pulled; the hourly sweep re-checks any blob whose mtime or size changed since its last check, and a weekly sweep re-checks all. A blob whose hash no longer matches its name is moved to `app-media/quarantine/`, reported as a degradation, and answers `410 media-unavailable`; it is then re-pulled from a peer like a missing blob. Mode 0400 does not stop a process running as the agent's own user from changing a blob; these checks detect it.
- **Not held here.** If the event is known but the blob is not on this machine, the route starts a pull (4.12) and answers `202 {state: "fetching", retryAfterMs}`. Once the blob is marked unrecoverable (4.12) the route answers `404 {error: "media-unavailable", detail}` in plain words. The app polls a `202` at most every 2 seconds and stops after 60 seconds, showing "still copying, tap to retry"; polling draws on the normal 120-per-minute read allowance.

### 4.9 Telegram and Slack continuation

- **App → Telegram topic.** `POST /mobile/chat/:topicId` accepts `attachments` exactly as 4.3. The message and blobs are stored under `telegram:<topicId>`, the session receives paths in the 4.5 forms, and the mirror into Telegram goes out through the origin outbox as `sendPhoto` / `sendVideo` / `sendVoice` / `sendDocument` (a media group for several files) with the caption "📱 <owner name> (from the app): <caption>". Files above 50,000,000 bytes (the Bot API limit) are mirrored as a text line "📱 <owner name> sent <display name> (too large for Telegram; open it in the app)". A failed mirror never fails or repeats the dispatch (`mirror: "failed"`), as for text.
- **App → Slack conversation.** Increment 3 depends on mobile-native-conversations.md increment 4 (the Slack send route). Same behavior, with the mirror through `FileHandler.uploadFile`.
- **Telegram and Slack media in the app's history.** When media is on, the Telegram and Slack inbound handlers also copy each downloaded file into the blob store (with an admission reservation, 4.7) and append a durable, replicated `{kind: "platform-media", eventId, conversationKey: "telegram:<topicId>" | "<canonical Slack key>", platformMessageId, attachments, at, machineId}` event to the app conversation store under the platform conversation's canonical key (the store that already keeps app-sent platform messages, never rotated). That event, not the rotating platform log, is the reference that authorizes downloads and drives pulls on every machine; the platform history row gets the same `attachments` for display. A device reading `GET /telegram/topics/:id/messages` or the Slack messages route gets those `attachments`, and the row text with the server path replaced by `[photo]`, `[file: <display name>]` or `[voice note]`; a device never sees a server path.
- **Telegram voice notes** are copied into the blob store before the existing handler deletes its download, so the app can play them; the Telegram session still receives `[voice] <transcript>` exactly as today.
- **Parity gaps stated, not fixed here**, each with an owner: a Telegram `video` message is not delivered to sessions today; files above Telegram's 20 MB download limit fail on the Telegram path; sessions cannot send files into Telegram or Slack topics (no reply script supports it). These are existing Telegram and Slack adapter limits, not app limits; they are filed as one instar feedback item at increment 1's ship ("Telegram/Slack session media parity: inbound video, >20 MB files, session file replies") so they are tracked, not dropped. The app's native conversations have none of these gaps.

### 4.10 Device routes

The allowlist gains (`active` devices only; `<uuid>` and `<upload>` are strict lowercase UUIDs; `<sha>` = `[0-9a-f]{64}`; `<idx>` = `0|[1-9][0-9]{0,5}`). Each rule now also names the request body it accepts, and the authenticator refuses a body of another type with `415` before checking the signature:

| Method | Pattern | Body |
|---|---|---|
| POST | `/mobile/media/uploads` | JSON |
| PUT | `/mobile/media/uploads/<upload>/chunks/<idx>` | `application/octet-stream`, ≤ 1 MiB |
| GET | `/mobile/media/uploads/<upload>` | none |
| GET | `/mobile/media/<sha>` | none |
| POST | `/mobile/media/purge` | JSON |

Existing rules all accept JSON (or no body), as today. The chunk route is mounted with `express.raw({type: 'application/octet-stream', limit: '1mb', verify: keepRawBody})` ahead of the global JSON parser, so the raw body is kept and the signature covers the chunk's bytes. The chunk route is exempt from the authentication-time read limit through a new allowlist rule flag (`ownBucket: 240`), separate from the send flag, and has its own 240-per-minute bucket.

**Replay-guard budget.** Chunks (240/min) plus reads (120/min) and sends (20/min) stay under the guard's 2,000 entries in its 3-minute window (at most about 1,140). The guard keeps its 2,000-entry bound, and the last 100 entries are reserved for send routes (the allowlist rule's existing `sendRoute` flag is passed to `verifyDeviceRequest` and on to `ReplayGuard.admit`, both of which gain that parameter): a non-send request is refused with 429 once the guard holds 1,900 entries, so an emergency stop is never refused because a large upload filled the guard, and memory stays bounded.

### 4.11 Push wording

The push payload is unchanged in kind: no content, no file name, no thumbnail reaches APNs. This spec defines the preview lookup for app replies, which mobile-native-conversations.md §4.7 leaves to the generic text:

- The push trigger for an app reply carries `{kind: "app-reply", conversationKey, messageId}` in the payload's `instar` block (identifiers only).
- The Notification Service Extension fetches `GET /mobile/chat/app/:conversationKey/preview/:messageId` with the per-device notification read token of mobile-push.md (its authority extended to exactly this route pattern, active devices only). The route answers `{title: "<agent name>", body}` from the local store: for text, the first 100 characters of the reply; for a `media-message`, a fixed phrase, "sent a photo" / "a video" / "a voice message" / "a file: <display name>" / "N files", then the caption's first 100 characters if any. A message not yet replicated to that machine is `404`, and the extension keeps the generic text.
- Folding, budgets and dedupe are mobile-push.md's, unchanged.

### 4.12 Several machines

- **Metadata replicates with the events.** `media-message` and `transcript` and `purge` events replicate through the existing `appConversations` kind.
- **Bytes replicate by pull, through a new verb.** `app-media-pull` (machine-authenticated mesh transport, the same transport as `working-set-pull`, its own code): the request names a `sha256` and a byte offset; the serving machine answers only if an unpurged local event (in a live or a deleted conversation) references that hash, opens the blob with `O_NOFOLLOW` and an inode check, and returns at most 1 MiB with asynchronous positional reads, without re-hashing (the blob's name is its hash, checked when written). At most 2 pulls are served at once per machine. The receiver writes slices to a temporary file, hashes it in a worker when complete, and renames it into the blob store only if length and SHA-256 equal the referencing event's; otherwise it discards it and counts a failure for that peer.
- **Every blob replicates eagerly.** Each machine pulls every unpurged blob referenced by an event it holds, including blobs of deleted conversations (they are retained data, so a tombstone that arrives before the file does not strand it), in the background, lowest priority: one pull tick every 5 seconds, at most 8 slices per tick (about 1.6 MiB/s, so a 20 GiB backfill takes about 3.5 hours), paused while this machine's `loadVerdict` (trustworthy-machine-load) is `saturated` or `impaired` for at most 1 hour at a time (after that, one slice per tick runs regardless until the verdict clears), and paused below the disk floor of 4.7 (never by the admission cap). Platform media is included, because a platform's copy is reachable only through that platform's credential on the machine that holds it.
- **Brakes on pulling (No Unbounded Loops).** Per blob: retry with exponential backoff from 30 seconds to 1 hour; after 7 days with no peer able to serve it, the blob is marked `unrecoverable` (counted, with one attention item per machine listing the affected conversations, `conditionKey: "app-media:unrecoverable:<machineId>"`), and pulls for it stop until a new event or peer inventory names a holder. Per peer: 5 consecutive verification failures open that peer's breaker for 15 minutes; a breaker that opens 3 times in a day stays open until the next day and raises one attention item naming the peer.
- **Copies are measured, not assumed.** Every hour each machine publishes an inventory of the unpurged blob hashes it holds (live and `deleted/`): a full sorted list on request, and otherwise a diff against its previous inventory, fetched by peers through the same mesh transport, and `singleCopyBlobs` counts unpurged blobs (native and platform media alike) that this machine holds and no peer inventory younger than 2 hours lists. A peer whose inventory is older or unreadable makes the counter `null`, never 0. If `singleCopyBlobs` stays above 0 for more than 1 hour while every peer is online, the machine first re-queues those pulls on its peers (by sending them the hashes); if the count is still above 0 an hour later, one attention item says which conversations' files exist on one machine only. While a peer is offline, the same item is raised once single-copy blobs are more than 24 hours old, naming the offline peer; and a counter that has been `null` for more than 2 hours raises it too, saying the copy count cannot be measured and why.
- **Residual risk, stated.** A machine lost before its blobs reached another machine loses those files, the same window in which its unreplicated events would be lost. Eager pull, the bounded load pause and the single-copy alarm keep that window short and visible; nothing in this spec makes it zero.
- **The owner pulls before dispatch.** A send accepted on a non-owner is forwarded with its event (mobile-native-conversations.md §4.8). The owner pulls the blobs before delivering to the session. If a blob cannot be pulled within 60 seconds, the session receives the message with `[file still copying: <display name>]` for that attachment, and a durable pending-delivery row `(messageId, attachmentId)` is recorded. When the blob lands, the owner injects one follow-up line into the conversation's session, `[file now available: <path>] (for the message "<first 40 characters of the caption>")`, de-duplicated by `attachmentId`; if no session is live, the next delivery's context includes it. A pending row older than 7 days is dropped with a line in the session's next context ("a file from <date> could not be copied to this machine"), and the blob's `unrecoverable` handling applies. The bytes are never lost on the accepting machine.

### 4.13 Signed records with media

`verifyRecordedOrigin` (mobile-native-conversations.md §4.6) handles `media-message` with one added check inside the exact text check: the signed body's `attachments` (decoded from `bodyB64`) must equal the stored event's `attachments` on `sha256`, `size`, `declaredKind`, `declaredType`, `filename` and `transcript`, in order, with stored `index` values 0..n−1. Any difference is `failed`. The effective `kind` and `mediaType` are the server's sniffing results and are not part of the check.

**Redacted media messages use a new payload version.** The existing `instar-app-redaction-v1` payload is unchanged and still used for `message` events. A redacted `media-message` carries `redaction.v: 2` and the machine signs `instar-app-redaction-v2\n<bodySha256>\n<sha256(stored text)>\n<sorted kinds>\n<sha256(canonical JSON of the attachment projection)>`, where the projection is, per attachment in order, exactly the stored fields `{sha256, size, declaredKind, declaredType, filename, transcript}` (the transcript and filename as stored, after token removal) (the signed `uploadId` is omitted because it is not kept), and canonical JSON is RFC 8785 (JCS). The accepting machine checks before signing that the projection equals the signed body's attachments on those fields (transcripts and filenames compared after applying the same token removal to the signed ones), so a verifier can recompute the hash from the replicated record and key history alone; verifiers choose the payload by `v` (absent = 1); the origin validator (`validateOrigin` in `AppConversationStore`), which today rebuilds `redaction` from `kinds`, `machineId`, `signerKeyHash` and `sig` only, keeps `redaction.v` (1 or 2), both when storing and when receiving a replicated record, and a unit test sends a v2 redacted record through the store and the replicated envelope and checks it reads `verified`; so no existing record changes verdict and a not-yet-upgraded peer never sees a v2 record (it rejects `media-message` entirely, 4.1). For a redacted media message the file list is vouched for by the accepting machine's signature over that hash, not directly by the phone's (whose signed body is not kept); the app shows it as "📱 signed, an invite or desktop code removed", as for text.

The verdict says the phone signed this text and these file hashes. Whether this machine holds matching bytes is a separate per-attachment fact in history responses: `bytes: "verified" | "not-here" | "mismatch"` with `bytesCheckedAt`. The app shows "📱 signed" only for a `verified` verdict and marks any attachment whose bytes are not `verified`. Agent-sent attachments read `none` for origin and carry the same `bytes` field.

## Multi-machine posture

- `media-message`, `transcript`, `platform-media` and `purge` events: **replicated** with the `appConversations` store kind.
- Admission usage for the cap: **derived from the replicated events** on every machine (4.7), with the bounded soft-cap overshoot stated there; only open reservations are local, and they become replicated events or are released.
- Blobs (native and platform media): **unified by full replication**: every machine pulls every unpurged blob eagerly (`app-media-pull`, verified), with measured copy counts and alarms (4.12). The on-demand pull in front of a read is a latency fallback for the replication window, not what survivability rests on.
- Session copies under `app-media/session-files/`: a per-machine cache **derived from the replicated blobs** and re-created on demand by `app-media-path`; it holds nothing of its own, like the parent spec's per-machine aliases.
- `/health` `appMedia`: per machine, **proxied on read** across the pool with `?scope=pool`.
- Upload sessions and staged chunks: machine-local. machine-local-justification: physical-credential-locality (an upload is authorized only by the phone's device record, which is bound to the machine serving the paired hostname, mobile-device-keys.md §4; on any other machine the same phone cannot authenticate, so the upload could not be continued there anyway, and a send turns it into a replicated blob).

## Decision points touched

| Decision point | Classification | Justification |
|---|---|---|
| A file's type and effective kind | invariant | Fixed magic-byte table in code; declaration and filename are never used; a mismatch reclassifies to `file`, never refuses. |
| Inline versus attachment serving | invariant | Fixed inline-safe list; everything else is `application/octet-stream` with `Content-Disposition: attachment`, `nosniff` and a sandbox CSP. |
| Whether a device may download a hash | invariant | Device active at request time plus a reference from a named live conversation or history row; otherwise 404. |
| Whether an upload, send or reply is accepted on size and capacity | invariant | Fixed size, body-size, count, staging, admission-cap (from replicated metadata, a stated soft cap) and disk-floor checks; upload ownership and hash equality. None reads content. |
| Whether a reply file path is allowed | invariant | Confinement to three roots plus the never-served list and a fixed credential denylist, by path component. |
| Live-credential check on reply files | invariant | The existing live-credential wall (`detectOutboundCredential`, `HARD_WALL_CREDENTIAL_KINDS` from `DURABLE_SECRET_PATTERNS`), already the one documented non-overridable outbound check for reply text (docs/specs/outbound-credential-wall-modern-key-formats.md), applied to the same exact-format key kinds in a file's text or printable runs; it adds no new kind and no heuristic. This spec does not create a new blocking authority: it routes files through the existing wall instead of around it, which an attached file would otherwise be. That wall's authority is the exemption class of `docs/signal-vs-authority.md` ("hard-invariant validation", "safety guards on irreversible actions": a leaked key cannot be un-leaked) together with Judgment Within Floors' "invariants are never delegated", exactly as recorded for the wall itself in outbound-credential-wall-modern-key-formats.md. The Standards-Conformance Gate's Signal vs. Authority flag on this row is the known conflict between those sources and the registry article's "one named exception" wording, tracked in ACT-027 (open), not a new authority here. A match refuses and names the file. |
| Hard-linked reply file | invariant | `fstat` link count greater than 1 refuses. |
| Purge and orphan removal | invariant | Purge only by an operator device request naming tombstoned or platform conversations, removing only unreferenced blobs; orphans only after 7 days unreferenced. |
| Signed-record verdict for a media message | invariant | Cryptographic checks; the byte check is a separate per-attachment fact and never upgrades a verdict. |
| Quarantine of a blob whose hash does not match its name | invariant | Hash comparison; the blob is moved, never deleted, and re-pulled. |
| Dispatch with "file still copying" after 60 seconds | invariant | Fixed deadline; the follow-up line is durable and de-duplicated. |
| Server transcription deadline (60 seconds) | invariant | Fixed deadline; the transcript event is appended later if it arrives. |
| Duplicate suppression of agent replies | invariant | Exact match on text plus attachment hashes, the existing suppression extended by the hashes. |
| Pausing pulls at the disk floor | invariant | Fixed free-space floor (5% or 2 GiB); the admission cap never stops a pull. |
| Pausing eager pulls under load | invariant | Consumes the existing `loadVerdict` signal (trustworthy-machine-load); this spec adds no judgment, only the pause rule on its two worst values. |
| Pull give-up and peer breaker | invariant | Fixed backoff, 7-day give-up, 5-failure breaker, 3-opens-per-day latch. |

## Frontloaded Decisions

- Media messages are a new event kind, `media-message`, so older versions refuse them instead of storing them without files.
- Uploads are chunked at 1 MiB with each chunk device-signed; the message's signed body carries every file's SHA-256, size, declared kind, declared type, filename and phone transcript.
- Limits match the origin outbox: 50 MiB per file, 64 MiB and 10 files per message; Telegram mirrors above 50 MB become a text line.
- Uploads run in the foreground (and iOS's short grace period), never with the app closed.
- Bytes are content-addressed blobs outside the journal; every blob replicates by eager verified pull with brakes and measured copy counts.
- Type comes from magic bytes only; non-inline types are always served as attachments with `nosniff` and a sandbox CSP; no bearer or signed download URLs.
- Voice notes are transcribed on the phone; server-side transcription is an optional fallback; the audio is kept.
- Agent reply files are confined to the project directory, the agent's outbox and the OS temporary directory, minus key-material paths and hard links, and every file is scanned for live credentials; deliberate copying inside an archive is outside this protection and said so.
- A media message is refused at preflight unless its serialized stored and replicated records fit (72 KiB record, 64 KiB `bodyB64`); the app keeps bodies under 32 KiB.
- Platform media references are replicated `platform-media` events, not rotating log rows.
- One agent-wide admission cap guards every new file; replicas are stopped only by a free-disk floor; deleted conversations' files do not count; only the operator, from the app, permanently removes files.
- Redacted media messages use a new `instar-app-redaction-v2` payload; v1 is unchanged.

## Configuration, rollout and rollback

- `mobilePairing.native.media.enabled`: omitted means live on a development agent and off on the fleet (the dev-agent gate), read at boot; requires `mobilePairing.native.enabled`. Off: the media routes answer `503 {error: "media-off"}`, sends with `attachments` answer `400 {error: "media-off", detail}` in plain words, `app-reply.sh --file` gets `503` and says so, the app hides the attach and record buttons, and Telegram/Slack inbound handlers do not copy files into the blob store. Pulls and the purge of already-stored files keep running, so switching off never strands a copy.
- `mobilePairing.native.media.maxStoreBytes`: default 21,474,836,480 (20 GiB), read live.
- **Migration parity:** `app-reply.sh` (with `--file`) and the new `app-media-path` helper are installed in all four places `app-reply.sh` already is: `init.ts`, `PostUpdateMigrator.migrateScripts` (always overwritten), the boot-time `AppReplyRelayInstaller`, and the `TemplatesDriftVerifier` version history (new SHAs added). The CLAUDE.md template (`generateClaudeMd()`) gains a separate section headed `### App conversation media` and `migrateClaudeMd()` adds it when that exact heading is absent (the existing app-conversation section is not used as the sniff): app messages may carry `[image:…]`, `[document:…]`, `[video:…]`, `[voice:…]` paths; earlier files open with `app-media-path`; reply with files using `app-reply.sh --file <path>`; files outside the project, the outbox and the temporary directory, key-material paths, hard links and files holding a live credential (in text or a printable run) are refused; compressed or encrypted contents cannot be inspected, so never attach an archive of credentials.
- **Increments**, each shippable alone: (1) the `media-message` kind, blob store, uploads, native send with attachments, session delivery and `app-media-path`, download route, `app-reply.sh --file`, signed-record attachment check, eager and on-demand `app-media-pull` with inventories, capacity and purge; (2) server-side voice transcription fallback; (3) Telegram and Slack continuation (sends with media, mirrors, platform media in the app's history), Slack after the parent's increment 4; (4) push preview for app replies; (5) the iOS app (attach, record and on-device transcription, upload with resume, cache, display, Storage screen).
- **Rollback:** switch `mobilePairing.native.media.enabled` off; blobs and events stay on disk and return when it is switched on. An older version ignores `app-media/` and refuses `media-message` events at validation (counted by the replicated store, never stored without their files); text messages are unaffected.

## Maturation plan

- **test-agent-live:** the E2E above passes on a throwaway agent with no messaging service and no transcription provider configured.
- **dev-agent-live:** on the development agent the operator sends a photo, a PDF, a voice note and a video from the TestFlight app into a native conversation, gets an agent reply with a file, opens everything in the app, sees the signed mark, and sees a photo continued into a Telegram topic.
- **fleet:** follows `mobilePairing.native.media.enabled`, dark on the fleet until the graduation criterion holds.
- **graduation criterion:** on the development agent, one week of daily media use with zero lost or corrupted files, zero `failed` verdicts on genuine messages, `singleCopyBlobs` back to 0 within 2 hours of every send while all machines are online (measured from inventories, not acknowledgements), no quarantined and no unrecoverable blob.
- **dark-window:** if not graduated within 30 days of release, the reason and a new date are recorded on CMT-1187.
