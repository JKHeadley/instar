# Approve a phone instead of typing a code: the plain version

Today, when you add a phone to an Instar agent, the phone opens a one-time link and then waits. You get a short code, either in your private Telegram chat or on a page you unlock with your PIN, and you have to read it and type it into the app on the phone. The operator asked to get rid of that step.

After this change you can simply say yes where you already are. Your private Telegram message gets an Approve button beside the existing Decline button. The pairing page and the older dashboard's Phones tab get an Approve button on each waiting phone, behind the same unlock that shows the code today, with no new PIN question. And if you already have a paired owner phone on this agent, it can list the waiting phone and approve it after Face ID, the same way permission slips work. The waiting phone is told where the button went and checks its own status, so it moves on by itself when you tap.

The code does not go away. Older versions of the app still need it, and it is the fallback if a button cannot work. There is also an off switch that puts everything back as it was.

The main risk is that a tap proves less than typing a code. Typing a code shows that the person reading the chat is holding the phone. A tap only shows that the owner said yes. So if someone got hold of a link, a careless tap could approve their phone. The safeguards: the link only works once, and if a second phone tries the same link, the first phone can no longer be approved with a tap and you are told; the message says to approve only if you are pairing right now and the key shown matches the app; it warns that the phone's name is chosen by the phone; if two phones are waiting at once, Approve is refused until you decline one; a phone meant for someone else still uses the code, because you cannot see that phone; and pairing is paused while someone is guessing codes. One gap remains and is stated in the spec: if a thief uses your link before your own phone opens it, and you tap Approve on a message you were not expecting, that phone pairs. It then shows in your Phones list, where you can remove it. Someone who holds this agent's API access remotely could use the same trick, where before they could never see the code. That is the one real step down in safety. It was accepted, because that access already controls the agent fully and you still have to tap, and the operator is being told. The off switch puts the code-only rule back. A tap only counts when it provably came from the owner, in the owner's private chat, and it works once, for one exact phone, until that phone's pairing expires. Agents themselves cannot approve using their ordinary access.

On an agent spread over several machines, a waiting phone belongs to the machine it contacted, and the approval has to reach that machine. Each path does this directly. If the machine serving Telegram changes, the pairing ends and you ask for a new link.

What to decide: nothing. It is on by default wherever pairing is on, it can be switched off or reverted, and phones approved this way stay paired.
