# Owner-approved actions over the stdio MCP transport

## Problem statement

SEC-018b (`docs/specs/owner-approved-sensitive-action.md`, merged dark as PR #3218) gates the irreversible `threadline_delete` MCP handler behind a device-signed owner approval. The gate is only effective on one of the two MCP transports:

- **HTTP transport** (`ThreadlineMcpHttpService`, in the agent-server process): the delete handler holds the in-process `OwnerApprovedActionStore` + `PendingApprovalRegistry` the `/mobile/action-approval` phone routes write to. Approval consume **and** the thread mutation (`threadResumeMap.remove`) both happen in the one server process. Gated. ✓
- **stdio transport** (`mcp-stdio-entry.ts`, a **separate per-session helper process**): constructs the same `ThreadlineMCPServer` **without** an `ownerApproval` dep and performs the mutation **locally** against on-disk state (`new ThreadResumeMap(stateDir,…)`; `this.deps.threadResumeMap.remove(args.threadId)` at `ThreadlineMCPServer.ts:1141`). Ungated.

stdio is the **default** (`threadline.mcpHttp.enabled` defaults false), so #3218's gate, once flipped, protects only opt-in agents. This companion is **required-before-flip**. While dark it is harmless (both delete as today).

### Why the naive "gate the stdio handler" design was rejected (Round-1 convergence)

Adding a loopback `consume` route + keeping the gate in the stdio handler + making `OwnerApprovalGate` async was rejected on five grounds, all verified against the merged code: (1) the three gate calls are **synchronous** so an async `consume` returns a truthy Promise → the approval block is skipped → **fail-open** on an irreversible action; (2) `enabled()` false skips the gate, and a stdio `enabled()` over the network that fail-opens to false skips it after the flip; (3) the mutation stays **local in the helper** while only the check crosses to the server — not enforcement at the authority; (4) the stdio helper authenticates to `/threadline/*` with `Bearer <agentToken>`, **not** `/mcp/*` + `local-mcp-secret`, so a route on the wrong boundary 401s → dead feature; (5) exposing caller-invocable `register-pending`/`clear-pending` enables a one-call targeted eviction of the owner's genuine pending entry (owner then can't approve) and caller-composed card text.

## Proposed design

**Move the whole gated action server-side; both transports invoke one atomic operation.** Enforcement, the live config read, the approval consume, the server-composed pending card, and the thread mutation all happen in the one server process.

1. **A server-side function `performApprovedDelete(threadId, ctx)`** in the agent-server process. In one server-side pass (the stores are in-memory and Node is single-threaded, so the consume and the mutation are one tick):
   - Read `security.ownerApprovedActions.enabled` from the server's **live config**.
   - **Verify the thread exists FIRST** (as the current handler does at `ThreadlineMCPServer.ts:1106-1109`). A non-existent `threadId` returns not-found and **registers nothing** — this is load-bearing (see the Residual section): it bounds any pending-registration flood to the agent's real threads.
   - **Cross-process authority (why a server-side delete is safe):** the mutation goes through `ThreadResumeMap.remove` → `ConversationStore.mutateSync`, which does **reload-per-op + per-record version CAS + atomic tmp-write+rename** (`ConversationStore.ts`): it reads the LATEST on-disk file immediately before committing and rewrites only its own record. So the server authoritatively deletes a thread the stdio helper created, and a later helper write to a **different** thread reloads the file (seeing the deletion) and preserves it — **a helper write cannot resurrect a server-deleted thread.** The existence-check `get()` uses a very-short-TTL snapshot cache, so it can be microseconds stale, but that is benign: a stale "exists" at worst registers a harmless pending for a just-deleted thread, and a stale "absent" just makes the owner's attempt a retry; the authoritative delete itself (`mutateSync`) always reloads. This is the primitive's "authoritative state stays local" contract, not new machinery.
   - **Disabled** → `threadResumeMap.remove` and return `{ ok: true }` (today's behaviour, server-side).
   - **Enabled, no valid approval** → do **not** delete; **register (or refresh) a pending entry keyed by `{purpose:'thread-delete', actionKey:threadId}`, deduplicated** (a repeat attempt on the same thread updates the existing entry's timestamp, never adds a second), whose `title`/`why` are **composed server-side from the server's own thread state** (never from caller input); return `{ ok: false, reason: 'owner-approval-required' }`.
   - **Enabled, valid approval present** → consume it, then (only on a successful consume) `threadResumeMap.remove`. **Ordering is consume-then-mutate**: this is crash-**safe**, not crash-atomic — a crash between the two leaves the in-memory approval gone on restart (it never persists) **and the thread intact**, so the owner simply re-taps and re-attempts. No journal is required *because* of this fail-safe ordering; a crash can never leave a consumed approval with an un-deleted-but-now-unapprovable thread in a harmful state (worst case: the owner re-approves).
   - **Approval key / revision binding:** delete binds by `actionKey = threadId` — the owner approved deleting *this thread*, and later messages do not invalidate "delete it". `revision` is forwarded verbatim (`{purpose, actionKey, revision?}`) and is **server-derived** for consumers that bind to reviewed state (the future trust-grant, where the granted level is the reviewed state); for delete it is absent by design. **This is a delete-specific exception to the parent primitive's general resource-state-binding + journal-recovery contract:** delete needs neither (threadId binding is complete; the crash-safe consume-then-mutate ordering above replaces journal recovery). The parent spec should carry a one-line note recording this exception so the two specs state one agreed contract, not two incompatible ones.
2. **A loopback route `POST /threadline/approved-delete`**, body `{ threadId }` only. **Auth:** the ordinary `authMiddleware` `Bearer <agentToken>` gate (exactly what every stateful `*ViaHttp` helper already sends — no new secret, no middleware edit), **plus an explicit loopback/Origin guard**. It does **not** reuse `evaluateLocalMcpAdmission` (that compares the *local-mcp-secret*, which the stdio helper does not hold, and fires only on the exact `/mcp/threadline` path — using it would 401 the helper → dead feature). Because a plain `/threadline/*` route is tunnel-reachable with the agent token, the route adds the **loopback/Origin/no-forwarding-headers portion** of the admission check (extracted from `evaluateLocalMcpAdmission`, *without* its secret compare) so it is genuinely loopback-only. The route is **NOT** added to `THREADLINE_PUBLIC_ROUTES`. It exposes **no** `consume`/`register-pending`/`clear-pending`/`enabled`/`has` action — the only thing a caller can do is attempt this specific approved delete.
3. **Both transports call `performApprovedDelete`:**
   - The **HTTP** MCP delete handler calls it in-process.
   - The **stdio** helper's delete handler calls `POST /threadline/approved-delete` via an `approvedDeleteViaHttp` helper (beside `sendMessageViaHttp`), and acts on the result: `ok:true` → done; `owner-approval-required` → return the "I've put the request on your phone" message; **a transport failure (timeout / lost response / non-200) → the outcome is UNKNOWN, not "failed":** the server may have consumed-and-deleted before the response was lost. The helper returns an explicit **outcome-unknown** message ("the delete may already have happened; check the conversation") and the owner/caller reconciles against authoritative thread state — it does **not** assert the delete failed, and it **never** performs a local delete as a fallback. (This mirrors the Threadline-send outcome-unknown contract.)
4. **The shared `registerDeleteTool` handler performs NO local `threadResumeMap.remove`.** The direct local mutation at line 1141 is deleted; both transports reach the mutation **only** through `performApprovedDelete` (in-process for HTTP, over the route for stdio) — the mutation lives in exactly one place. A partial refactor that routed only the *check* server-side while leaving the local `remove` would reopen Round-1 finding S4, so this is stated as a hard build requirement. `OwnerApprovalGate` is removed from the delete path (no async interface, no un-awaited-Promise fail-open); its sole consumer today is this handler. (Note: the primitive's future trust/pair/relay consumers each get their own server-side `performApprovedX` rather than inheriting a shared gate interface — consistent with Option C.)
5. **Build checks.** (a) An **enabled** delete with no approval does not mutate; (b) an **unreachable** op yields outcome-unknown and **no local delete**; (c) a **flood** of `approved-delete` behaves as the Residual section states — a non-existent `threadId` registers nothing, a repeated `threadId` occupies exactly one entry (dedupe), and the pending set is therefore bounded to the agent's real thread count (it does NOT assert the 128-FIFO can never evict — under a sustained flood with >128 real threads it can — an accepted, availability-only residual, see the Residual section); (d) a helper write to a different thread after a server-side delete does not resurrect the deleted thread (the `ConversationStore` reload-per-op guarantee above); (e) correct the primitive's stale `OwnerApprovedActionStore.consume()` JSDoc ("deletes first" → it deletes **last**, required for the revision no-grief behaviour).

Ships **dark**: `security.ownerApprovedActions.enabled` defaults false; disabled, `performApprovedDelete` just deletes. Observable behaviour is **byte-identical to today when the agent server is reachable**; a server-unreachable delete now fails closed (outcome-unknown) rather than deleting locally — an inherent, acceptable consequence of moving the op server-side (the stdio helper already depends on the server for every other stateful call).

## Decision points touched

- **`performApprovedDelete` enabled→consume→mutate — `invariant`; basis: irreversible-consequence; evidence: an unapproved `threadResumeMap.remove` is unrecoverable.** Delete iff (disabled) or (enabled ∧ a device-signed approval for `{purpose, actionKey, revision}` is consumed). Sole authority = the device signature, created only on the phone route after `verifyPresenceSignature`. Consume-then-mutate ordering is fail-safe on crash.
- **`enabled` read — `invariant`; basis: external-constraint; evidence: the operator's `security.ownerApprovedActions.enabled`.** Read server-side from live config; the stdio helper never computes it; an unreachable op is outcome-unknown + no delete, so an indeterminate `enabled` can never skip the gate.
- **Existence-check + dedupe before pending-register — `invariant`; basis: enumerable-domain; evidence: the set of registrable pending keys is bounded to the agent's existing threads, one entry each.** This bounds the pending-registration side effect so it cannot be used for an unbounded eviction flood.
- **Outcome-unknown on transport failure — `invariant`; basis: irreversible-consequence; evidence: a lost response does not prove the irreversible delete did not happen.** Report uncertainty + reconcile via thread state; never a local-delete fallback.

## Residual: bounded pending-eviction (honest disclosure)

Moving `register-pending`/`clear-pending` out of the caller's reach removes the one-call targeted eviction and the card-phrasing attack. It does **not** remove *all* lockout surface: because `performApprovedDelete` registers a pending entry on the enabled-no-approval path, a secret-holding local caller can still drive registrations by calling `approved-delete` repeatedly, and the `PendingApprovalRegistry` is a 128-entry FIFO, so a flood could evict a genuine pending entry (the owner's challenge then `409`s). This is **bounded and non-critical**: it is an availability/DoS on *approval*, never a delete bypass (the attacker always gets `owner-approval-required`, never a deletion); the existence-check bounds it to the agent's real thread count; dedupe-by-actionKey stops a single thread from multiplying entries; and it **self-heals per-attempt** — the owner's genuine re-attempt (or any benign path) re-registers the entry. The one case per-attempt self-heal does NOT cover is a *sustained* flood against an agent with >128 real threads, where the owner's pending could be re-evicted before they tap approve; that sustained-flood case is exactly what the per-caller rate cap closes. A per-caller cap on `approved-delete` would narrow this further, but this change deliberately does NOT add one: the residual is an ACCEPTED availability-only risk — the attacker only delays the owner's own approval, never deletes, and a same-host session holding the agent token could spam many server operations regardless. (The convergence report's Left-behind records the cap as an optional later hardening.) The earlier draft's claim that "the lockout surfaces do not exist" was too strong and is corrected here.

**Forward note for the shared pending registry:** `PendingApprovalRegistry` is a single 128-entry FIFO shared across `OWNER_ACTION_PURPOSES` (`thread-delete`, and later `trust-grant`). The bound above holds for delete because its `actionKey` is an existing `threadId` (an enumerable, existence-checked domain). **Any future purpose that registers a pending keyed by an attacker-suppliable value WITHOUT an equivalent existence/enumerability check would reopen an unbounded flood against the shared registry and could evict delete pendings.** Each new consumer's build must carry this same existence/enumerability guard; this belongs as a one-line requirement in the primitive spec.

## Multi-machine posture

- **`performApprovedDelete`, the route, the stores: `machine-local`.**
  `machine-local-justification: physical-credential-locality` — the `OwnerApprovedActionStore` + `PendingApprovalRegistry` are per-server-process in-memory state; the agent token + the loopback guard admit only same-host callers; the stdio helper's calls are hardcoded to `127.0.0.1:${serverPort}`. The approval is recorded by the phone route, consumed, and the delete performed on that same machine. Nothing replicates. The route itself holds no replicated state; it triggers a **pre-existing machine-local session mutation** (`ThreadResumeMap.remove` → local disk) through a new entry point, so it needs no `WriteDomainRegistry` entry (that registry governs replicated write domains, not machine-local session state).

## Frontloaded Decisions

- **Auth = `Bearer <agentToken>` via `authMiddleware` + an explicit extracted loopback/Origin guard** (not `evaluateLocalMcpAdmission`'s secret compare, not `THREADLINE_PUBLIC_ROUTES`). Reason: matches the stateful `*ViaHttp` calls the helper already makes (no new secret), while still enforcing loopback-only. Security rests on the route being attempt-approved-delete-only; both the agent token and the loopback are already within the distrusted session's reach, so neither is the security boundary — the device-signed approval is. (Resolves former Open Question #2.)
- **Commit sequencing (cheap-to-change-after): land `performApprovedDelete` as a refactor of merged #3218, or as this companion PR's first commits — decided either way** (internal, reversible, no durable/external/interface effect; pick whichever rebases cleaner). (Former Open Question #1.)
- **Rollback is a code revert, not a config flip (honest disclosure).** `performApprovedDelete`, the route, and the #3218 handler refactor ship **live**; only whether `enabled` returns true is dark-gated, and the flip disarms the approval *requirement*, not the plumbing.

## Maturation plan

- **test-agent-live:** a throwaway agent on the **stdio (default) transport**, feature on: a `threadline_delete` returns `owner-approval-required`, a real presence-signed approval then applies the delete once; a replay/expired/non-owner signer is refused; with the agent server made unreachable the delete reports **outcome-unknown and does NOT delete locally**; a flood of `approved-delete` against non-existent and real threadIds registers no unbounded pendings and does not evict the genuine one (within the 128 bound); and a server-side delete of a helper-created thread is not resurrected by a later helper write — all observed on the throwaway.
- **dev-agent-live:** enabled on the development agent (Echo) for one week alongside the primitive's delete consumer, with `threadline.mcpHttp` at its default (stdio); watch that real owner Face-ID approvals land over the stdio path and no legitimate owner delete is wrongly refused.
- **fleet:** flip `security.ownerApprovedActions.enabled` fleet-wide only together with the primitive's flip (never before this companion ships), after the dev-agent window and the graduation criterion hold — so the default transport is gated the instant the switch turns on, never after.
- **graduation criterion:** judged from the approval ledger on the **stdio path specifically**: at least one real owner-presence approval that applied a delete over the stdio transport, AND at least one forged/replay/unreachable-server attempt refused (no local-delete fallback), each observed. A zero count is not a pass.
- **dark-window:** at most 28 days from merge to the fleet decision, shared with the primitive's window; if the criterion has not held by then it stays dark and the plan is revisited rather than flipped on a clock.
- **ladder:** not applicable: a dark-shipped security hardening companion to the owner-approval primitive, not tracked on a formal feature-maturation ladder.
