# Exact Target Reads for Green Merge Handoffs

The green merge line currently obtains its target from the same bounded oldest-first authored discovery list used by periodic scans. That list intentionally returns at most 100 candidates. A fully verified newer pull request can therefore be absent, and the exact handoff reports not-listed before its normal eligibility checks. Actual 3714 and3731 journal records were green, then the line reported not-listed; both were EchoOfDawn-authored same-repository fix branches. For an exact local-floor handoff, production reads that one pull request by number through the same authenticated GitHub GraphQL adapter and full candidate projection. It requires the returned number match, state OPEN, base main and authenticated viewer author equality. The ordinary gather/ownership/hold/draft/head/record/lease/code-owner/safe-merge path still decides whether to act. A known exact handoff is not periodic discovery, so it neither expands nor depends on the paginated discovery list or its100-result ceiling. Regular ticks remain unchanged. A direct target read preserves all discovery-derived snapshots, namespace/ownership diagnostics and unrelated red-alert memory; absence from a singleton response is not a closed/merged observation. A malformed or failed direct read skips that handoff safely; it cannot fall back to merging another candidate. Legacy injected dependencies without the new seam retain their current bounded-list behavior.

No new author is trusted. No fork, changed head, draft, explicit hold, absent exact full record or failed current merge guard becomes eligible. The exact read is a fact-gathering signal; existing stateful merger and safe-merge retain authority.
