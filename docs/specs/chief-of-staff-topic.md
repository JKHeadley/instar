# Chief of Staff

## Problem statement

The operator is currently the only mechanism that keeps an agent's work moving. He opens a topic per effort. Then he has to keep returning to it: nudging work that stalls, checking that it hasn't drifted from its goal, and restarting a "24-hour autonomous session" so it continues but stops if he goes quiet. With dozens of topics, that chasing has become unmanageable (operator, topic 141014).

The ledger already exists, but nothing acts on it. On 2026-11-09 at 18:03Z, `GET /initiatives` on Echo returned 396 records: 24 active, 11 completed, 361 archived. `GET /initiatives/digest` flagged 24 items: 20 `stale` (up to 115 days without movement), 3 `next-check-due` (overdue since July/August) and 1 `needs-user`. Many pieces each notice something: the Initiative Tracker, the Project Scope digest, the autonomous-run Liveness Reconciler, the silence backstop, the Throughput Floor and PromiseBeacon. None of them owns the chasing. A digest only reports what is stuck. Nothing gets the work moving again.

## Operator decisions already made (topic 141014)

- **D-A, authority:** the Chief of Staff MAY restart and redirect work on its own, within each project's stated goal. (Operator answered "1) yes" on 2026-11-09 11:14 PT to the question: may it restart and redirect within each project's stated goal, or only nudge and report?)
- **D-B, pilot:** pilot on Echo first, then roll out to every agent. ("2) yes", same message.)
- **D-C, official and built-in:** it is an official part of every agent, not an add-on.
- **D-D, top of the list:** the topic always floats at the top of the conversation list, at least in the Instar app and the dashboard conversations.
- **D-E, go-to conversation:** it is the user's default place to talk to the agent.
- **D-F, tree:** every other conversation/topic sits below it in the official hierarchy.
- **D-G, tracking improvement:** this is the vehicle for tuning how Instar creates and tracks projects/efforts.

## Proposed design

### Non-goals

- The Chief of Staff (CoS) does not do project work itself. It directs project conversations and they do the work. This follows the rung rule, and the operator's 2026-08-07 correction in topic 36966: "you direct the pathway topic."
- It never changes a project's goal or definition of done. Only the operator changes those.
- It does not replace the existing trackers, digests, reconcilers or gates. It consumes them, and it stands down wherever one of them already owns a run (§2.4).

### 1. The tree (conversation hierarchy)

**1.1 Node types.** There is exactly one `chief-of-staff` conversation per agent. Under it sit **project** conversations, and under those sit **sub-topic** conversations. Every conversation that is not in the tree appears under an **Unfiled** group. "Done" is a filter on closed projects, not a node.

**1.2 Storage: one new replicated store.** All CoS state lives in a new replicated-store kind, `chiefOfStaff`, built on the existing replicated-record substrate (`ReplicatedRecordEmitter` + the HLC envelope; the same substrate as `AppConversationsReplicatedStore` and `TopicPinReplicatedStore`). It is NOT stored on Initiative Tracker records: those are TaskFlow-primary in a local SQLite file that is explicitly not synced across machines (`.gitignore` "TaskFlow registry — local SQLite … cross-machine sync of flow state is not in v1 scope"). Record kinds in the store, each keyed and merged as stated:

The substrate merges one whole record per key by highest HLC (`TopicPinReplicatedStore.mergeUnionToPins` is the pattern); it has no field-wise merge. So every record that two machines could write concurrently is **immutable and event-keyed**, and the mutable views are derived by reading the union:

| Record | Key | Mutability / derivation |
|---|---|---|
| `tree` (parent link) | conversation key `platform:id` (`conversationSortKey`: `telegram:<topicId>`, `app:<uuid>`, `slack:<id>`) | last-writer by HLC (only the owner's taps write it); tombstone on unparent |
| `binding` (goal, doneDefinition, checkCadence, linked repos/branches, linked initiative id, confirmedBy, confirmedAt) | conversation key | last-writer by HLC, written ONLY by owner taps; a binding without `confirmedBy = owner` is a draft and never acted on; its identity for closure purposes is its record HLC (two machines cannot mint the same HLC, so a counter is not used) |
| `binding-lifecycle` (closed / reopened, `bindingHlc`, by, at) | `conversationKey:hlc` | immutable; open/closed state is DERIVED (newest lifecycle event wins); a `closed` event is valid only if its `bindingHlc` equals the HLC of the binding record currently winning, so a closure verified against an older checklist can never override a concurrent owner edit; a `reopened` event is valid only when written by an owner tap (the CoS never reopens on its own) |
| `check-event` (verdict, evidence hash, evidence ids + ages, progressSeen, net-diff high-water mark, at, machine) | `conversationKey:hlc` | immutable; `restartsWithoutProgress`, `lastProgressAt`, breaker window, `nextCheckAt` and `nextActionAllowedAt` are DERIVED by folding `check-event` + `intent` records newest-first (a progress event resets the restart count; a later stale write cannot undo it because nothing is overwritten) |
| `intent` (action, conversation key, leaseEpoch, sequence, claimedAt, holder signature) and its **transition log** `outcome` (`executing`, `started` with run/inject id, `superseded`, `rejected`, `lost`, `aborted`, at, writer) | `conversationKey:leaseEpoch:sequence` and `…:outcome:<transition>` (one immutable record per transition, never replaced) | legal transitions: `claimed → executing → started`; `claimed → superseded | rejected`; `executing → rejected` (step 4, no receipt) ; `executing/started → aborted` (step 5); `started → superseded` (fence failed after spawn, carries the run id, followed by `aborted`); `claimed/executing → lost` only after a `rejected` written by the ownership machine. The ownership machine writes every transition except `lost`, which the holder writes. The derived state is the furthest legal transition present, so write ordering cannot change the terminal state |
| `renewal` (operator check-in: renewedAt, renewedVia, principal, event ref, machine signature) | `renewal:<hlc>` | immutable; the §4 owner predicate is applied ONCE, on the machine that received the inbound event, and that machine signs the record with its machine key (the mesh's existing per-machine signing identity); readers accept only records whose signature verifies against a known pool machine (trust boundary, stated plainly: a compromised pool machine could renew the lease; that is the mesh's existing single-agent trust model, not a new exposure). The lease is DERIVED: `expiresAt = max(renewedAt of signature-valid renewals) + operatorLeaseHours`. No stored `expiresAt` is ever trusted; an unsigned or unverifiable record is ignored (a Telegram message id cannot be re-fetched later, so it is kept as an audit ref, never as the proof) |
| `graduation` (pilot metrics snapshot, decision record) | date | immutable |

Registration and retention follow the substrate exactly: a new journal kind `chief-of-staff-record` is added to BOTH `ReplicatedKindRegistry` and the static `CoherenceJournal.JOURNAL_KINDS` (a kind missing from either advertises replication and replicates nothing), with a `DEFAULT_RETENTION` entry of `{ maxFileBytes: 8 MB, rotateKeep: 0 }`, the never-delete posture `topic-placement` uses, because the substrate's retention is size-based file rotation and a deleted archive would take `tree`/`binding` records and the breaker's event window with it. Growth is small: `check-event`s are written on due checks (≈1/project/day), `intent`s only on actions, so 20 projects produce well under 1 MB a year; per-key compaction is deliberately deferred to a follow-up <!-- tracked: CMT-1415 --> and the fold reads the whole journal. The emitter's per-kind rate cap is the substrate default. The streams live where the journal puts them, `state/coherence-journal/<safeMachineId>.chief-of-staff-record.jsonl` plus rotated archives; because `BackupManager`'s `includeFiles` is a static list whose glob supports one `*` in the last segment, the backup entry is the whole `state/coherence-journal/` directory, which captures this machine's stream and every peer stream it holds (so a restore on any machine carries the full union). Restore semantics are **new build scope**, because today's restore copies every snapshot file over the live file with no merge (`BackupManager.ts` restore path): writer lock files are excluded from the backup; a journal-aware restore never overwrites the restoring machine's OWN live stream (restored copies are merge-appended by record key, so a stale backup can never roll back a live writer's sequence) and restores peer streams only where the live file is missing. Until that restore path exists and is tested, `state/coherence-journal/` is backed up but EXCLUDED from the plain restore copy, so a restore can never silently delete `executing`/`rejected` records. Compaction stops being optional when the kind's live file passes 4 MB (half the rotation size); the deferral <!-- tracked: CMT-1415 --> is tracked as commitment CMT-1415 so it re-surfaces instead of rotting. The `multiMachine.stateSync.chiefOfStaff` flag is forced on whenever `chiefOfStaff.enabled` is true on a multi-machine agent; if it cannot be enabled the CoS refuses to start and says so (never a silent machine-local fallback).

The conversation key is the only identity that spans every conversation kind today: the Durable Conversation Identity layer (`src/core/conversationIdentity.ts`) covers Slack only, and app conversations use their own uuid. **Cross-store invariant:** the binding is the authority on a project's open/closed state; the Initiative Tracker record's status is a mirror. Each tick reconciles: binding closed and initiative not `completed` ⇒ set `completed`; binding open and initiative `completed` ⇒ set `active`; every mismatch is recorded as a `check-event` note. The CoS writes exactly two things on an initiative record: the one-way link (`links[]` entry of type `chief-of-staff-binding`) and the `status` mirror (`completed`/`active`), nothing else. Both writes go through a status-only tracker method that does not bump `lastTouchedAt` (§2.3). The mirror write happens on the lease holder each tick; if it fails, the binding stays authoritative, the mismatch is recorded, and the next tick retries, so a closure that lands in the binding but not yet in the tracker reads as "closed" everywhere the CoS is consulted and catches up in the tracker within one tick. Because the binding is replicated, another machine preserves the same project state when one machine is unavailable even though the Initiative Tracker store itself is local.

Replication unavailable on a machine ⇒ that machine treats the lease as expired and the loop does not act (least-harmful direction).

**1.3 Binding is the tracking improvement (D-G).** A conversation becomes a project under the CoS only with a confirmed `binding`: a one-paragraph `goal`; the `linked` repos and branches the work lands in (required; progress is measured there, §2.3); a `doneDefinition` checklist whose items are each tagged `deterministic` (PR merged into the default branch by SHA; a page at a URL in a linked domain whose body contains a named assertion string, fetch capped at 256 KB; a record in a named status; a file at a path with a named content check) or `judgment`, and each `judgment` item is marked either `owner-confirms` (default) or `agent-may-certify` (the owner delegates that one call to the CoS judge at binding time, so accepted work can drain without a human tap where the owner chose that); and a `checkCadence`. When the operator starts a new effort, the CoS (or the project conversation itself) drafts the binding and the operator confirms it with one tap through Approval-as-Data; the tap's principal must be the owner (§4). Until then the conversation stays Unfiled and is never restarted. That makes "a project without a definition of done" structurally impossible.

**1.4 Surfaces (D-D, D-F).**
- *App:* `GET /mobile/conversations` is keyset-paginated with a single total order and merges pages from peer machines (`mobileConversationRoutes.ts` `compareConversationRows`/`mergeConversationPages`), so the CoS stays in that stream at its natural position (old builds keep seeing it) AND the first page (no cursor) carries a separate `pinned` object with the same row, added after the peer merge; new builds render the pin, hide the in-stream duplicate by key, and draw a collapsible tree from `parentConversationKey` on every row. Older app builds ignore both fields. The `pinned` object and `parentConversationKey` are returned only to owner-role devices (§6).
- *Dashboard console:* the conversation list in `chats-model.js` (the time sort and the focus sort) gains a pinned-first step for the CoS, and the rows render as a tree. `needs-model.js` gets a CoS entry whose `reads` endpoint is `GET /chief-of-staff`, so items needing the operator count on Home.
- *Telegram:* forums cannot nest topics. The CoS topic is pinned in the forum; the tree is visible only in the app and dashboard. On a Telegram-only agent the pinned topic is the whole surface. Frontloaded, not cheap-to-change (it is user-visible and the pin is an external write): basis external-constraint, Telegram forum topics cannot be nested.
- *Slack:* where Slack conversations exist, the CoS appears as a conversation in the Instar app list exactly as above; Slack itself has no pin or tree.
- *No Telegram at all:* only the app conversation is created; lease renewal is by app or dashboard (§4).

### 2. The check-in loop

**2.1 Scheduling.** A tick runs every `chiefOfStaff.tickMinutes` (default 15) on the lease holder only: `LeaseCoordinator.holdsLease()` is read at tick entry AND again immediately before every action, with the lease epoch captured at tick entry; an action whose epoch no longer matches is dropped. A project is *due* when `nextCheckAt` has passed (`checkCadence` default 24h, minimum 1h, with ±10% jitter across projects) or when its dirty flag is set by an event (an autonomous run ends, a linked PR changes state, a commitment goes overdue). Events only set the dirty flag; a dirtied project is checked on the next tick and no sooner than 30 minutes after its previous check. After a lease-holder change, the first tick reads the replicated `check-event`/`intent`/`outcome` records and takes no restart action (grace tick). Gather walks bound projects only, at most 4 concurrently, with one PR listing per repo per tick shared across projects, and every network probe bounded by a 10s timeout that resolves to `unknown`. A tick that overruns the interval stops and the remainder waits for the next tick.

**2.2 Gather (deterministic).** Per due project collect, each item with source, id and age:
- merged/open PRs linked to the project and the *diff size excluding whitespace-only and generated files* of commits since the last check;
- the done checklist, each `deterministic` item evaluated now;
- autonomous-run state for the conversation (active/remaining, Liveness Reconciler row, Throughput Floor row, resume-queue state, any move in progress);
- whether a live session exists, read from the machine named in the conversation's ownership record, not locally;
- overdue commitments;
- the last owner message and last agent outbound (timestamps only, plus a bounded tail of text for the judge, §2.5);
- the digest reason.

Any item older than its freshness ceiling (sessions and run state: 2 ticks; PR state: 1 hour; everything else: 24h) or unreadable is `unknown`. Evidence is never inferred from its absence.

**2.3 Progress vs. activity (P20).** Two separate measures:
- **Progress** = a `deterministic` done item flipped to passing, or a change that *lands*: a PR merged into the default branch of a linked repo, or the net diff of a linked branch against the default branch exceeding its previous **high-water mark** by a non-trivial amount (default 20 non-whitespace lines outside generated files; the owner may lower it per project at binding, down to 1 for projects where one-line fixes are the work). The high-water mark is kept in the `check-event` history, so an oscillating branch (0 → 20 → 0 → 20) earns credit once, never again; a branch that legitimately shrinks earns credit only when it merges. Until a project has any linked branch with commits, progress can only come from a done item flipping, and the binding form says so when the owner confirms it. Progress updates `lastProgressAt`.
- **Activity** = anything else that changed: chat, pushes that do not grow the net diff, empty or churn commits, PR reopen/close cycles. Activity never resets the restart counters.

The digest's `stale` label is a symbol (`lastTouchedAt` older than 7 days, reset by any record write, and an unparseable timestamp reads as healthy in `InitiativeTracker.ts`). The CoS therefore never maps `stale` to `stalled`; `stale` is an input to the judge and nothing more. The unparseable-timestamp behaviour is filed as a separate foundation defect (see Left behind in the report).

**2.4 Who owns the run (stand-down rule).** Exactly one actor may act on a conversation at a time. Before any restart the CoS checks the run registry: if an autonomous run for the conversation is active with time remaining, or the Liveness Reconciler shows any non-idle state (`debouncing`, `respawned`, `capped`, `blocked-quota`, `blocked-pressure`, `blocked-not-owner`, `blocked-queue-owns`, `mid-move`), or the resume queue holds the conversation, or a move is in progress, the CoS records `moving-under-existing-owner` and does nothing. Run-state eligibility is explicit: a run record that is `completed`, `expired`, `failed`, or `operator-stopped` with no live session is history, not ownership, and does not block the CoS; `active-with-remaining`, `queued`, `capped`, `mid-move`, any Reconciler `blocked-*`/`debouncing`/`respawned` state, an open CoS `intent` with no outcome record from ANY lease epoch (so a holder that spawned just before failover still owns the slot until step 4 settles it; age never un-blocks, it only triggers settlement), and `unknown` (registry unreadable) all block. The same rule governs **redirects**: a redirect inject is a CoS action like a restart, it takes the same claim and lock (below), it is never sent into a run another component owns, and a redirect for the same unresolved evidence hash is sent once; it repeats only on new evidence, an owner tap, or after one full cadence with no reply (and counts toward the restart brakes as an attempt).

**The action protocol** is one small durable state machine, and all of it is **new build scope** (none exists in source today, and the spec does not pretend otherwise). An action moves `claimed → executing → started | superseded | rejected | lost | aborted`, every transition is an immutable record, and the only place two things are serialised is the ownership machine's per-conversation lock.

1. **Claim (lease holder).** The holder writes the `intent` record, signed with its machine key over `(conversationKey, leaseEpoch, sequence, action)`, and re-reads the stand-down list after one local emitter flush. That flush is a cheap early exit, not the arbiter: the **authoritative reservation is the ownership machine's lock in step 3**. When the ownership machine sees two open intents for one conversation (a failover race), it executes the one with the lower HLC and writes `outcome: superseded` for the other; an intent never blocks its own execution (self-exclusion by key). Every run producer (the CoS, the Liveness Reconciler, the resume queue) goes through the same ownership-machine lock, which is what makes the reservation exclusive.
2. **Route and verify (ownership machine).** The command is routed to the machine in the conversation's ownership record. Before anything else that machine verifies: (a) the signature belongs to `LeaseCoordinator.currentHolder()` and `freshRenewalWithin(currentHolder(), ttlMs)` is true (both existing calls, monotonic-clock based; a stale view ⇒ `rejected`, never execute: an isolated machine cannot authorise and an isolated former holder cannot be authorised); (b) its ownership record still names itself (moved ⇒ `rejected`); (c) `nextActionAllowedAt` (§2.7) has passed in its own fold of the replicated records, and a missing or lagging fold (newest `check-event` for the key older than 2 ticks) ⇒ `rejected`; (d) **no OTHER open intent for the conversation lacks an outcome**, with one exemption so the race in step 1 resolves instead of deadlocking: when every open intent is still at `claimed` (none `executing`), the lowest-HLC intent proceeds and the ownership machine writes `superseded` for the rest; any open intent that has reached `executing`, or that belongs to a previous owner, blocks until step 4 settles it. An epoch number alone is never authority; the signature plus the fresh lease view is.
3. **Execute under the lock.** Inside `SessionManager.withConversationLock` (the existing in-process per-conversation lock, `SessionManager.ts` ~7690; it is NOT reentrant and the public spawn already takes it, so step 3 calls the `*Unlocked` spawn and inject entry points) the machine repeats the stand-down check, then consults its **dedupe index**: an in-memory index over three durable sources, all of which survive a reboot: its own local coherence-journal stream (the replicated store's local write is a durable local append first and replicates afterwards), the peer streams it holds, and the run registry's `idempotencyKey`s. It is rebuilt from those on boot and on ownership adoption, and adoption carries a **transfer barrier**: the new owner accepts no command until the previous owner's stream has replicated through its newest `outcome` transition for that conversation (the cooperative transfer in the existing OwnershipReconciler is the handoff point where that checkpoint is exchanged); if the previous owner is unreachable, its open intents keep blocking under step 2(d), so the worst case is a stall settled by step 4, never a second execution. test-agent-live includes "ownership transfer after local execution but before replication". If any source cannot be read the action fails closed. A key already present returns the recorded outcome and does nothing else. Otherwise it writes `outcome: executing` for the key to the journal and **waits for it to be durable before spawning**: `emit` must return `accepted`, then a synchronous `flush()`, then a new `awaitDurableSeq(seq)` call (new build scope: today `emit` only queues for the 250 ms flusher, `flush()` returns nothing and swallows disk errors into `flushErrors`, and no call reports a record's sequence back) confirms `meta.highWaterSeq` has reached the record's sequence; any failure aborts the action as `rejected` before anything is spawned. Only then does it perform the spawn or inject with `idempotencyKey` and `cosNoRespawn: true` on the run state (injects record their inject id in the same journal record), and writes `outcome: started` with the run or inject id. A key found `executing` with no `started` after a reboot is settled by step 4, never re-executed.
4. **Recovery.** A command may still be in flight after the holder loses sight of it, so `lost` is never written by the holder alone: an open intent older than one tick (or older than `maxRunHours`, the `max-wall-clock` case) makes the holder ask the ownership machine, which under the lock either finds the key in the run registry or a `started` record (⇒ `started`, matched on the idempotency key, never on "a session exists"; a bare `executing` record with no registry match proves only that execution was attempted, so it is settled `rejected`, never `started`) or writes `outcome: rejected` for the key to the journal (durable, unified) and acknowledges; only after that acknowledgment does the holder write `lost` (counts as an attempt). Only the machine that wrote `executing` may settle that intent, because only it holds the run registry the receipt lives in; after an ownership move, an `executing` intent from the previous owner stays open until that machine is reachable again and settles it (the transfer barrier in step 3 covers settlement as well as commands). If the settling machine cannot be reached, the intent keeps blocking and the project is escalated in the note as "can't settle"; nothing is retried blind.
5. **Compensation.** Duplicates return the recorded outcome and are never compensated. The CoS stops a run only when that exact run id is known to be unwanted: its own fence failed after spawn (`superseded` with a run id), or the start reported failure (`aborted`). The Reconciler and resume queue read the same intent records and stand down while ANY CoS intent for the conversation has no outcome; `maxRunHours` only triggers step 4 settlement, it never un-blocks another producer.

**2.5 Judge (LLM, signal).** Skipped entirely when the evidence hash is unchanged since the last verdict (verdict carried forward, "no new evidence") or when every done item is `deterministic` and passing (goes straight to `done-verified`). Otherwise one call through `LlmQueue`, background lane, component `chief-of-staff`, under `chiefOfStaff.judgeDailyCents` (default 15; derivation: ≤20 bound projects × ≤2 judged checks/day × ~0.3 evidence-changed share ≈ 12 calls/day at Haiku-class cost ≈ 5¢, with 3× headroom); if admission is refused (`daily-spend-cap`, `component-budget`) the verdict is `unknown` and "judge budget exhausted" appears in the note. Input: goal, done checklist, the evidence bundle, and conversation tails wrapped as quoted untrusted data. The bundle is bounded with `boundedTail` (newest first) at `JUDGE_BUNDLE_BYTES = 48 KB` (derivation written beside the constant: the driver is cost, not context; at Haiku-class pricing 48 KB ≈ 14k input tokens ≈ 0.4¢ per call, so the `judgeDailyCents` budget of 15 covers ≈ 36 judged checks a day with the §2.5 call estimate of 12; a larger bundle would cut the number of projects the budget can judge) and the bound is disclosed in the prompt; if a done-checklist evidence item would be cut, the judge is not called and the verdict is `unknown` (P24). Deterministic evaluators fetch only URLs in the binding's linked domains and repos, capped at 256 KB. Output: one verdict from the closed set `moving | stalled | drifting | waiting-on-user | claims-done | unknown`, plus evidence ids. Authority floors applied AFTER the judge, in code:
- `stalled` and `drifting` must each cite at least one non-conversation evidence item that is fresh; otherwise `unknown`.
- `claims-done` from conversation text alone never becomes `done-verified`; verification is §2.6.
- Any cited id that does not resolve ⇒ `unknown`.
- `unknown` ⇒ no action.

**2.6 Act.** Bounded action space; every side-effecting action writes an `intent` record first and its outcome after (Standard B), and re-checks `holdsLease()`, the lease epoch, the operator lease (§4) and conversation ownership at the moment it fires.

| Verdict | Action |
|---|---|
| `moving` | Record. |
| `moving-under-existing-owner` | Record. |
| `stalled` | **Restart (D-A)** if brakes allow (§2.7). Live session ⇒ inject a continuation prompt. No session and no *blocking* run state (historical `completed`/`expired`/`failed`/`operator-stopped` records are allowed, §2.4) ⇒ start a bounded autonomous run (duration ≤ `chiefOfStaff.maxRunHours`, default 4) through the existing autonomous path, which applies the quota, spawn-cap and machine-pressure gates. Compensation per §2.4 step 5 only. |
| `drifting` | **Redirect (D-A).** Inject the goal, the remaining done items, and the evidence ids with structured metadata (PR numbers, SHAs, timestamps). Never raw quoted text. If the project's next reply argues the goal should change, that becomes one `waiting-on-user` item; at most one goal challenge per project per note cycle is forwarded, further ones are counted and the count appears on that item's line. |
| `waiting-on-user` | Queue for the note. No restart. |
| `claims-done` | Evaluate `deterministic` items now; `judgment` items marked `owner-confirms` go to the operator as a one-tap confirm, and items the owner marked `agent-may-certify` at binding are judged by the CoS judge under the same §2.5 floor (at least one fresh non-conversation evidence item cited, or the item stays unverified) with the cited evidence recorded. All pass ⇒ `done-verified`. Otherwise redirect with the missing items. A claim refuted twice ⇒ escalate in the note. |
| `done-verified` | Write a `binding-lifecycle: closed` event carrying the exact `bindingHlc` whose checklist was verified (invalid if the owner edited the binding meanwhile), mirror the linked initiative to `completed`, and report it in the note. Reversible by one owner tap (a `reopened` event). |
| `unknown` | Record. Three consecutive `unknown`s (default; judgment-candidate, §Fixed limits) ⇒ one aggregated "can't see" line in the note naming the unreadable sources. |

**Injected prompts** carry a provenance header `origin: chief-of-staff (automated)`. They are never presented as operator words and grant no operator-gated authority; the receiving session's outbound gates see them as automated input.

**2.7 Restart brakes (P19) and severity classes (Standard B).**
- `remediation-actions`: inject continuation and start bounded run, both idempotent by the §2.4 dedupe index (a duplicate returns the recorded outcome; compensation only per §2.4 step 5, by exact run id).
- `max-attempts`: 3 restarts without progress ⇒ project **parked** (no further restarts) and escalated in the note; a park is cleared by an owner tap or by progress.
- `backoff`: after each restart or redirect without progress the derived `nextActionAllowedAt` moves out by a doubling delay (24h → 48h → 96h). It gates every restart and redirect at execution (§2.4 step 2c) independently of check scheduling, so a dirty event (including the completion of the run just started) can make a project *checked* sooner but never *acted on* sooner.
- `breaker` (flapping): more than `breakerRestartsPerWeek` (default 5) restarts of one project in a rolling 7 days, regardless of progress in between, trips a breaker that parks the project and escalates; a trivial-progress flap cannot reset it because activity never counts, and a breaker park is cleared ONLY by an owner tap (progress does not clear it), so self-triggered restarts of one project converge to at most `breakerRestartsPerWeek` per week without the owner. The breaker's existence is the invariant; its number is a setting.
- `max-wall-clock`: a restart intent without an outcome after `maxRunHours` is settled through §2.4 step 4 (never marked `lost` unilaterally) and, once settled `lost`, counts as an attempt.
- `dedupe-key`: `conversationKey:leaseEpoch:sequence`.
- `max-notification-latency`: `noteCadenceHours` + 2h clock tolerance (26h at the default). A parked, breaker-tripped, or three-times-unknown project reaches the operator in the next note.
- `audit-location`: the `intent` and `check-event` records in the replicated store are the audit trail (metadata only). `logs/chief-of-staff.jsonl` is a per-machine derived log of the same records for grep, not an authority.
- Severity: `recoverable` heals first and reaches the operator only on exhaustion or the latency ceiling: stalled, drifting, judge budget exhausted, evidence source unreadable, transient spawn failure, the CoS loop not ticking (heal: loop restart by the poller in §2.9), lease-holder flapping (heal: the grace tick; nothing is restarted until a holder is stable for one tick). `immediate` notifies on the same tick while healing continues, and is reserved for exhaustion or security: a restart refused by a spend/pressure gate twice in a row (the heal has already failed twice), and a linked branch receiving commits attributed to a session not bound to the project (a deterministic, signal-only detector reading the session registry's worktree for the commit's branch; commits by the owner, by CI bots, or by the bound session after a move are excluded). Goal conflicts between projects are not detected by the CoS in this phase. A fourth `immediate` item in a day goes into the next note.

**2.8 Per-tick caps.** At most 2 restarts per tick agent-wide (a third waits); on lease renewal after a pause, overdue projects are restarted at that same rate rather than all at once, and the note lists what is still waiting.

**2.9 Watching the watcher.** The loop writes a last-tick record to the replicated store. An independent poller, the existing `guardian-pulse` job on each machine, records the LOCAL monotonic time at which it last saw a new last-tick record arrive and calls the pure `classifyCadenceLiveness(lastSeenMono, nowMono, staleAfter)` on that (the function takes monotonic ms; a remote wall-clock or HLC time is never fed to it), starting `uninitialized`; `stale` on the lease holder (last tick older than 3 intervals), or `uninitialized` for more than 3 intervals after boot, emits a degradation event. The heal for a liveness failure is a loop restart by the poller, bounded to 2 restarts per hour with doubling backoff; after that the alerts topic is used. A second, CoS-side check in the same poller folds the newest 20 `check-event`s and, when more than half are `unknown`, emits a separate *evidence-availability* degradation (budget exhausted, sources unreadable) that goes into the note's "Can't see" line and NEVER restarts the loop, because a healthy loop can produce `unknown`s and restarting it changes nothing (this is not a `classifyCadenceLiveness` state; that function returns only `uninitialized | healthy | stale`). `GET /chief-of-staff` shows the loop health first.

### 3. Talking to the operator (D-E)

- **The note.** Sent on `chiefOfStaff.noteCadenceHours` (default 24) at `chiefOfStaff.noteTime` (default 08:00 in the agent's configured timezone, else the machine's). Sections, each capped at 5 lines with "+N more" linking to the Chief of Staff page (the console page that reads `GET /chief-of-staff`, through the public tunnel link; with no public link the line names the page and carries no link, never a localhost one), each omitted when empty: **Needs you** (one-tap actions first), **Results** (only a verified finish, a failed restart, or a park; routine restart and redirect counts live in `GET /chief-of-staff`, not in chat), **Can't see** (one aggregated line). If none of those exist, no note is sent; the only exception is a single line when the operator lease will expire within 24h ("nothing needs you; I pause in 24h unless you check in"), because that line is actionable.
- **The note's layout (operator report 2026-11-12).** Projects that look finished and need the owner's OK are grouped under one headline with the count ("4 projects look finished and need your OK"); each gets its own short block: a short project name (the linked initiative title or conversation name, else the goal's lead cut at a word boundary, never mid-word), how many automatic checks passed, the judgment item(s) it waits on quoted from the done definition, and a phone-openable link to that project; each block's button names its project ("Done: <name>"), one per row. There is no single confirm-all button: each judgment item is the owner's own call, project by project. Message footers name the machine by its nickname, else its own name, and show the raw machine id only when no name exists.
- **Immediate messages**: at most 3 per day, deduped by item, only for `immediate` severity or a decision that blocks work; a fourth waits for the note.
- **Go-to behaviour.** Owner input in the CoS that belongs to a project is routed to that project conversation carrying `routed-by: chief-of-staff` provenance, with a one-line confirmation of where it went and a one-tap undo that sends a retraction into the project conversation (text already delivered to a live session cannot be unsent); when unsure, it stays in the CoS and the CoS asks. Anything that would exercise operator authority in the project (an approval, a go-ahead) is never routed as operator words: the CoS asks the owner to confirm it explicitly in the CoS first. A new effort described in the CoS gets a project conversation created, a draft binding, and a one-tap confirm. Project conversations keep talking to the operator directly as today.
- All sends use the one-voice lease and lease-holder routing. If the Telegram forum contains non-owner members (bots cannot list members, so the test is `getChatMemberCount > 2`, i.e. more than the owner and the bot, failing closed to DM when the count cannot be read), EVERY CoS outbound (notes, immediate messages, routing confirmations, binding drafts, clarifications, approval taps) goes to the owner by DM (`sendToOwnerDM`) rather than the forum topic; the forum topic then holds only the pin.

### 4. The safety switch: operator check-in lease

- **Renewal predicate (exact):** a renewal is accepted only when the inbound event's authenticated principal is the owner: a Telegram message or callback tap whose `from.id === ownerUserId` (resolved as the adapter does today: `ownerUserId`, else `promptGate.ownerId`); a message or tap from an owner-admitted device (`mobileOwnerDeviceAdmission`); or a dashboard tap in an owner-authenticated console session. Message content, provenance headers, relayed peer-agent messages, member/guest messages, bot-authored messages and the agent's own API calls never renew. If no owner id resolves on an agent, the lease can never be renewed and the CoS stays paused; the note says so.
- **Expiry:** derived per §1.2 from verified `renewal` records plus `chiefOfStaff.operatorLeaseHours` (default 72). No renewal records, an unverifiable signature, or a `renewedAt` in the future beyond clock tolerance resolves to expired (paused), never live.
- **While live:** the CoS may restart, redirect, close and reopen.
- **When expired:** no new restarts, redirects or closes. CoS-started runs finish their current bounded duration; every CoS-started run carries `cosNoRespawn: true` on its run state from spawn time (new field, new build scope), and the Liveness Reconciler and the silence backstop skip such a run whenever the derived operator lease is expired (enforced on read, so nothing has to be written to remote run state at expiry; test-agent-live proves it). Notes continue on cadence, opening once with "Paused — waiting for you to check in" and after that only as a line in Needs you.
- This replaces per-topic 24-hour renewals with one lease. Runs the operator started himself keep their own durations; the CoS lease governs only what the CoS starts.

### 5. Observability

- `GET /chief-of-staff` (bearer + owner principal): loop health (last tick, holder machine, breaker states), lease state, the tree (summarised; counts per node), and per bound project: last verdict, action, restart counters, next check. `GET /chief-of-staff/projects/:key` returns that project's cited evidence with sources and ages. Pagination for the tree.
- Every judge verdict is recorded through `DecisionQualityRecorder` (component `chief-of-staff`) and graded by two deterministic outcomes: progress within one cadence after a restart, and a `done-verified` not reopened within 14 days (a measurement window, not a behavioural cap).
- Retention: `check-event`/`intent`/`outcome` records follow the kind's never-delete retention (§1.2); the derived jsonl rotates by size like other instar logs.

### 6. Security

- **Trust boundary:** project conversations, peer messages and PR text are untrusted; they reach the judge only as bounded quoted data, and no authority-bearing verdict rests on them alone (§2.5 floors).
- **Authority boundary:** the CoS acts only on conversations with a confirmed binding in its own tree; the server rejects any CoS action on another key. Its side effects are exactly: inject prompt, start bounded run, stop own run (by exact run id), mirror initiative status `completed`/`active`, write `tree` (on owner taps), `binding-lifecycle: closed`, `check-event`, `intent`/`outcome`, `last-tick` and `graduation` records (never `binding`, never `renewal`, never `reopened`: those are owner-tap or inbound-event writes), send notes. It cannot edit goals, grant access, change config, merge PRs or approve anything for the operator.
- **Owner-only conversation:** the CoS conversation accepts input only from the owner principal; other input is dropped and logged. The pin, tree fields and `GET /chief-of-staff` are served only to owner-role callers. Project titles never appear in a shared conversation.
- **Lease and principal:** §4. Closing, reopening and reparenting require a live lease and an owner principal where a tap is involved, and each writes an `intent` record.
- **Audit log:** metadata only, mode 0600, excluded from support bundles.
- **Project titles never reach non-owners** by two mechanisms: the tree fields, pin and `GET /chief-of-staff` are served only to owner-role callers, and the note falls back to `sendToOwnerDM` when the forum has non-owner members (§3).

## Fixed limits

Every number below is a judgment-candidate default unless marked invariant; the invariants are about existence, not about a number.

- `tickMinutes` 15 — judgment-candidate; floor 5 (derived: the session and run-state freshness ceiling is 2 ticks, and run state is written no faster than the Reconciler's own tick); operator-set.
- `checkCadence` default 24h, minimum 1h — judgment-candidate: the CoS proposes per project at binding; the 1h floor is derived from the 30-minute dirty-flag gap × 2 so a scheduled check and an event check cannot both judge the same evidence window.
- 30-minute minimum gap between checks of a dirtied project; 4 concurrent gathers; 10s probe timeout — judgment-candidate defaults; the gap equals 2 ticks (the freshness ceiling); the concurrency keeps one tick's outbound GitHub/HTTP fan-out under the per-repo listing cache's benefit (4 projects share one listing) and well under the API rate limit.
- 3 restarts without progress ⇒ park — judgment-candidate within a floor: an absolute cap must exist (P19); 3 is the default and operator-adjustable per project; the breaker is the backstop.
- Breaker — invariant: a breaker that no setting can disable must exist; basis: irreversible-consequence; evidence: each restart spends subscription quota that cannot be recovered, and the per-restart gates bound one restart, not a sequence of them. `breakerRestartsPerWeek` default 5 is a judgment-candidate the operator may change; a legitimate counterexample is a project the operator restarts deliberately each day, which the operator handles by raising the setting for that project.
- `maxRunHours` 4 — operator-set default; judgment-candidate (the CoS picks ≤ this per restart).
- ≤2 restarts per tick — judgment-candidate within a floor: bounded by the spawn cap; exists so a boot or renewal never launches a storm.
- 3 consecutive `unknown` ⇒ aggregated note line — judgment-candidate; default 3; a single high-value project can set 1.
- Refuted-twice ⇒ escalate; one forwarded goal challenge per cycle — judgment-candidate defaults.
- Note cadence 24h — operator-set default. Invariant: a `max-notification-latency` must exist (Standard B); its value is `noteCadenceHours` + 2h.
- Immediate messages ≤3/day — judgment-candidate within the P23 bounded-notification floor; default 3; overflow goes to the note.
- `operatorLeaseHours` 72 — operator-set; shorter is strictly more conservative (only pauses work).
- Loop health: last tick > 3 intervals, or > 50% of the last 20 verdicts `unknown` — judgment-candidate defaults for the poller; loop restarts capped at 2 per hour with doubling backoff — judgment-candidate within the floor that some restart cap must exist (a loop still stale after two restarts needs a person, not a third restart).
- Lagging-fold reject (newest `check-event` older than 2 ticks) — the freshness ceiling applied at execution; a reject for this reason is recorded `rejected: lagging-fold` and surfaces in the note's "Can't see" line so a stalled replication is visible, not silent.
- 4 MB compaction trigger — crossing it emits a degradation event linked to CMT-1415.
- Section cap 5 lines — judgment-candidate; presentation floor from P17.
- Progress threshold 20 net non-whitespace lines — judgment-candidate default; floor "lands on the default branch or grows the net diff, not whitespace, not generated, in linked repos"; the owner may lower it to 1 per project at binding.
- `judgeDailyCents` 15, `JUDGE_BUNDLE_BYTES` 48 KB — judgment-candidate defaults with their derivations in §2.5; above the assumed project count the budget runs out and verdicts fall to `unknown` with a "can't see" line, which fails safe.
- `breakerRestartsPerWeek` upper bound 7 × 24 × 60 / `tickMinutes` / 10 (a tenth of the ticks in a week) — judgment-candidate; keeps a very high setting from disabling the breaker in practice.
- 256 KB evaluator fetch cap; ±10% cadence jitter; freshness ceilings (2 ticks sessions/run state, 1h PR state, 24h else); 14-day live-evidence window for triage; 14-day reopen window for grading — judgment-candidate defaults; the fetch cap bounds a single probe to under a second on any link, the jitter spreads due times across projects, the freshness ceilings match how often each source changes, and the 14-day windows match the digest's own staleness horizon doubled.

## Multi-machine posture

Default posture is unified; every surface below is unified through the `chiefOfStaff` replicated store unless stated.

- **Tree, bindings, binding-lifecycle, check events, intents and outcomes, renewals, graduation records, last-tick:** unified (the replicated store, §1.2; immutable event records, derived views, so the substrate's whole-record HLC merge is sufficient). The sync flag is forced on with the feature (§1.2).
- **The ownership machine's dedupe index:** an in-memory index over durable unified sources only (its own local journal stream, which is the replicated store's durable local write; the peer streams; the run registry's idempotency keys), rebuilt on boot and on adoption (§2.4 step 3). Every fact it needs (`executing`, `started`, `rejected`) is a journal record written BEFORE the step that depends on it, so nothing authoritative lives only in memory or only on one machine.
- **Initiative Tracker status:** a local mirror reconciled from the replicated binding each tick (§1.2 cross-store invariant); the authority is unified.
- **The loop:** runs on the lease holder only; epoch-fenced actions; grace tick after a holder change; the acting machine is the conversation's ownership machine (§2.4).
- **Telegram CoS topic id:** unified by the system-topic mechanism: `chiefOfStaff: 'chief-of-staff-topic'` is added to `SYSTEM_TOPIC_STATE_KEYS`, to the `systemTopicsHooks` recorder on the holder, to `readSystemTopicIds` behind `GET /telegram/system-topics` (`routes.ts`), and to the adoption loop's `ensureOwn` set, so `ensureChiefOfStaffTopic` creates it on the lease holder only (the `ensureAgentAttentionTopic` pattern) and standbys adopt it through `adoptSystemTopicId`.
- **App CoS conversation key:** unified (a `tree` record with a `role: chief-of-staff` marker).
- **Restarts:** act on the machine named in the conversation's ownership record through pool/transfer routing; the session-alive read is from that machine.
- **Derived jsonl log:** a per-machine cache of replicated records, not a surface; the authority is the store.
- machine-local-justification: *(none required; no surface is machine-local)*

## Maturation plan

- **test-agent-live:** a throwaway test agent with four synthetic project conversations: moving; stalled with a dead session; stalled with a Reconciler-owned run (CoS must stand down); claiming done with an unmerged PR. Proves restart, redirect, stand-down, done-verification, park and breaker, lease expiry pause and renewal, and a lease-holder failover with no double restart, through the real Telegram, Slack and app surfaces (Live-User-Channel Proof categories: happy path, channel parity, lifecycle, permission, failure/rollback, concurrency, idempotency, regression).
- **dev-agent-live:** the Echo pilot (D-B). Triage of the 24 active records, then 3 to 5 real projects bound, running for one week, metrics computed from the store and the decision-quality meter.
- **fleet:** delivered dark by the migration; graduation is role-based (test agent → development agent → fleet): a scheduled day-14 job writes a `graduation` record from the measured metrics and raises the fleet-default decision to the operator; the fleet default changes only after that record and the operator's own reading of the same metrics (presented with the record, one tap) agree.
- **graduation criterion:** measured, not recalled: zero owner-initiated restarts of a bound project during the pilot week (from the run registry); ≥80% of CoS restarts followed by progress within one cadence (from `check-event` records); no `done-verified` reopened; zero operator-found defects on the pin and tree. Partial pilot metrics ⇒ no graduation record is written as "pass"; the record says `incomplete` and the pilot extends one week.
- **dark-window:** 14 days dark on the fleet after dev-agent graduation; the day-14 record is scheduled, not remembered.
- **ladder:** chiefOfStaff.topic
