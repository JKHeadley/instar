# code review round 2 — GPT-6 Astra (codex CLI), 2026-10-26

Verdict: not ready.

Reviewed the current working tree against the revised spec and both round 1 code reports. Ran `git diff origin/main...HEAD` and `git diff`; the branch diff is empty, so the implementation is in the uncommitted changes, including the new test files. The findings below concern remaining gaps in the current implementation.

1. **P1 — The hard-exit timer can abandon the competing stop before the server is killed.** `src/lifeline/RestartOrchestrator.ts:185` and `src/lifeline/RestartOrchestrator.ts:204`. The five-second hard-exit timer starts before persistence and remains armed during `stopServer()`. If persistence reaches its two-second budget, the override then calls the real supervisor, which waits three seconds after Ctrl-C before force-killing the session. Both deadlines land at five seconds, and the older hard-exit timer fires first. A fake-clock probe using the real `ServerSupervisor.stop()` produced `send-keys → exit(1) → kill-session`; in production, the last action never runs. If the competing request was `launchctl bootout` and the server ignores Ctrl-C or has not finished shutdown, it survives without a successor lifeline. This is the unresolved deadline case of round 1's competing-restart finding. **Smallest fix:** clear the persistence hard-exit timer before entering the stop phase, give that phase its own budget, and ensure its timeout force-stops the server before exiting. Test a timed-out persist with the real three-second stop delay and a session that remains alive; the current override tests use an immediately resolved stop stub.

2. **P2 — Detach still permits supervisor operations already past their entry guard to mutate the server.** `src/lifeline/ServerSupervisor.ts:526`, `src/lifeline/ServerSupervisor.ts:639`, and `src/lifeline/ServerSupervisor.ts:434`. Both `stop()` and `performGracefulRestart()` check `detached` only before their three-second await. If a keep-server restart detaches during that wait, they still execute `kill-session` afterward. The graceful-restart path then refuses its own replacement spawn because `spawnServer()` does check `detached`. Separately, an outstanding `start()` probe can finish after detach and explicitly set `detached = false`, restarting health checks and removing the other callback fences. Controlled probes reproduced all three cases. Thus the round 1 answer that detach fences every path is incomplete: a concurrent server restart can kill a session being handed to the successor. **Smallest fix:** invalidate a lifecycle generation on detach and check it after these awaits, before killing, spawning, or rearming monitoring; preserve the explicit `evenIfDetached` stop override. Fence the delayed child-process kill in `cleanupChildProcesses()` too. Add pending-stop, pending-graceful-restart, and pending-start tests alongside the existing pending-health-probe test.

3. **P2 — A resolved starvation alert hides all later queue episodes for the same PR.** `src/commands/server.ts:22473` and `src/localVerify/localVerifyWiring.ts:117`. The revised per-PR key correctly deduplicates pushes during one queue stay, but `createAttentionItem()` returns an existing item unchanged, even if resolved (`src/messaging/TelegramAdapter.ts:4209`). After a PR leaves the queue and is queued again, its new entry can reach two interruptions and emit a new signal, yet the old resolved attention item remains resolved and no new notice is sent. That implements one alert for the PR's lifetime, rather than the revised spec's one per queue stay. **Smallest fix:** use the existing `upsertAttentionItem()` for starvation signals so a later episode refreshes and reopens the per-PR item; retain `starvedRaised` to prevent repeats within the same stay. Test a second queue episode after resolving the first attention item through the production signal wiring. The current E2E test stops at a `hooks.signal` spy and cannot detect this.

4. **P2 — Resume priority disappears when no main verify is ready.** `src/localVerify/LocalVerifyService.ts:338`. The early return for `mainIdx < 0` runs before the new search for `resumeFirst`. Consequently, with ready PRs `[ordinary, interrupted]` and healthy main, `decideStart()` selects the ordinary PR. The same occurs when a main entry exists but is in backoff. The revised spec explicitly promises that any ready interrupted PR goes before other PRs as well as main; the round 1 fix covers only queues containing a ready main entry. A direct decision probe reproduced index 0 instead of index 1. **Smallest fix:** evaluate the ready `resumeFirst` candidate before the missing-main early return, retaining the main-red exception. Add decision tests without main and with main in backoff; the new tests all include a ready main entry.
