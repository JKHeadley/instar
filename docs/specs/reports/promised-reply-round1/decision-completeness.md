## DESIGN findings

**D1. Notice authenticity: it would ride the unauthenticated plaintext wire (Echo input 1+2).**
`ThreadlineClient.sendAck` -> `sendPlaintextTyped` -> `sendPlaintextRaw` (client/ThreadlineClient.ts ~491-530). A `reply-notice` would take the same route. refuseDowngrade.ts comments describe plaintext as "the relay's word". A relay (or anyone who can write under a fingerprint the relay vouches for) can forge "No reply yet to your message from HH:MM" for a message the receiver never sent. The spec has no check that the notice's `inboundMessageId` refers to an outbound the receiver actually sent on that thread, and no rule for what to do when it does not. Decide: (a) send encrypted to the pinned key where one exists, plaintext only otherwise, and (b) the receiver drops (logs) any notice whose referenced id is not one of its own outbounds on that thread.

**D2. Trust and downgrade gates are not decided (Echo input 1).** Verified: `resolveRelayUnknownSenderTrust` allows only `ack` for every level (relayUnknownSenderTrust.ts ~86-110); `reply-notice` maps to its own operation, absent from `DEFAULT_ALLOWED_OPS` (AgentTrustManager.ts 254-256), so verified/trusted peers are refused under enforcement (default dryRun=true, so it only shows once enforcement flips). `shouldRefuseDowngradedPlaintext` exempts only `'ack'` (refuseDowngrade.ts:159), so a plaintext notice to a paired invite peer is refused as a downgrade, i.e. exactly the peers who matter. `InboundMessageGate.classifyOperation` treats any `content.type` as an operation too. The spec must state the decision per gate (exempt like ack, with the D1 binding check), name the files to change, and add the tests. "Decide both explicitly" is not a decision.

**D3. "Structured fields only" cannot travel on the current wire, and conflicts with section 5.** `encodePlaintextPayload` / `decodePlaintextPayload` (autoAck.ts end) carry only `{text, type, resend}`; decode drops every other field. So `reason`, times and `inboundMessageId` need a wire-format change that the spec never states. Section 5 also says an older peer "sees the notice as ordinary message content", which requires a human-readable `text`; Echo's rule says the receiver renders the template itself and takes no free text. Decide: `text` carries our fixed template (for older peers), structured fields ride alongside, and a current receiver ignores `text` and renders from the fields.

**D4. Receive-side cases are not enumerated.** Four inbound paths consume acks today: relay handler (commands/server.ts ~19296-19300), ThreadlineEndpoints.ts ~735-742, routes.ts relay-agent ~37120-37137 ("not stored, not routed"), and ThreadlineBootstrap's plaintext decode (~690-740). The spec says "a current receiver handles reply-notice as its own case" without naming them. Each needs the new case (no ack, no route, no spawn, append to history, not a waiter reply). Also the "older peer" bound is wrong: an older peer's session spawned by the notice can send a real chat reply, which our side must route as content, so the exchange is not provably "one round". State what the sender does with such a reply (route normally, and say so), or drop the bound claim.

**D5. Obligation capture has no source for `sessionName` or a reliable `inboundMessageId`.** `RelayAckSettler.settle(outcome)` takes only the outcome (autoAck.ts ~282-310); it knows neither session nor message id. On the `listener-delivered` path (server.ts ~19490) there is no per-message session at all, only a warm listener whose heartbeat is fresh, which is not proof that the message was read. Inbound `messageId` can be undefined (ThreadlineBootstrap ~111, "UNKEYED"); the canonical inbox id then becomes `crypto.randomUUID()` (ListenerSessionManager.ts 207), so the recorded id must be the canonical entry id, which the spec never says. Without a sessionName, the `session-ended` / `restart-lost` / fallback-close logic (sections 2 and 4) has no input. Decide: extend `settle()` to take `{sessionName?, canonicalMessageId}`, and specify the reason selection when sessionName is absent (listener path: treat as `still-working` unless the listener reader is dead).

**D6. Closing-reply hook points and the fallback identity are not specified.** Outbound replies leave via `/threadline/relay-send` (routes.ts ~38378+, with local-delivery, relay and forwarded branches) and MCP `threadline_send`. The spec names no hook point, and which branches count as "sent". The fallback ("same `sessionName`, exactly one open obligation") depends on `originSessionName`, which is optional in that route and absent on the listener path, so the fallback is unusable where it is most needed. Also a reply that fails (400/409 claim conflict) must not close. Decide the hook (after successful delivery verdict, in the one funnel), and what the fallback keys on when sessionName is absent (thread + peer only).

**D7. Symmetry (Echo input 4) not designed.** Only receive-side append is mentioned, in the input list. The sending side: the notice is sent by the server directly, bypassing `/threadline/relay-send`, which is where outbound is recorded (routes.ts 39485, `appendCanonicalOutboxEntry`). So our own notice would be absent from our thread log. Receive side: the relay-agent path explicitly does "not store" acks (routes.ts:37135); relay inbounds are not reliably in canonical logs (spec's own premise). Decide: sender appends outbound via `recordThreadMessage`, every receiver path calls it for `reply-notice`, with the message id of the notice, and tests for each path.

**D8. Factually wrong surface name.** The spec says "`/threadline/peers`". Code has `/threadline/peers/health` and `/threadline/peers/:fp/health` (routes.ts 19184, 19265), backed by `a2aDeliveryTracker.allPeerHealth`, a delivery-state table with no notion of a text notice. Decide what field/row carries "notice received from peer X at T about message M", and where it is stored. Test 7 asserts a surface that does not exist.

**D9. At-most-once across a crash (Echo input 3) contradicts the state machine.** Section 3 moves to `noticed` only after the verdict returns; a crash between send and verdict leaves `open` and resends. The `state` union has no `sending`. The client send is synchronous and returns an id, the verdict is a later relay frame; correlation by message id and the `unconfirmed` timeout are undefined. Decide: add `sending` (written before send), startup treats `sending` without a verdict as sent with verdict `unknown`, define the verdict wait timeout, and add the crash test (16 tests, none covers it).

**D10. `threadline_promise_close` surface is undefined, and deliberate-close breaks the spec's own promise (Echo input 5).** The tool does not exist (grep: only in this spec). Unspecified: MCP tool vs HTTP route, auth, whether one session may close another's obligation, awareness text location (PostUpdateMigrator awareness; the warm-session prompt at ListenerSessionManager.ts ~706 tells sessions to reply with inReplyTo and would need the new tool), and migration parity. Separately, a deliberate close sends the peer nothing, leaving a peer who was told "Composing response..." waiting forever; this contradicts the title ("always followed by a reply or a notice"), as do expiry-during-outage (section 4) and handover-without-store. Decide: either deliberate close sends the non-promising `NO_REPLY_ACK_MESSAGE`-style closing notice (a typed, non-spawning one), or retitle the guarantee and state the three exceptions.

**D11. Rollout flip has no forcing function; the one cheap-tag is rejected.** "Ships enabled only after a dry-run window shows..." names no owner, no deadline, and no mechanism (the Shadow-Mode trap in CLAUDE.md). Also the dry-run does not exercise the wire type: a notice that is only logged never reaches a peer, so the `reply-notice` type name and structured payload are a published interface decided with no soak; once any peer receives one it cannot be renamed, so the "default off, dry-run first" tag does NOT cover the wire format (non-cheap taxonomy: published interface and durable external side-effect). Decide the wire type and payload now as final, and add a deadline plus an auditor/state-file check (or auto-flip criteria) for the dry-run exit.
