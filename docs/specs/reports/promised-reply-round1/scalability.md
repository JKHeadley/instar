# Scalability review, Round 1: THREADLINE-PROMISED-REPLY-SPEC (v2)

Verdict: SERIOUS ISSUES (design-level, all fixable in-spec). Counts: DESIGN 5, PRECISION 3.

## DESIGN

D1. The inboundMessageId and sessionName cannot be "captured when the ack is settled" with today's plumbing.
Source: autoAck.ts `RelayAckStageInput` has no message id and no session name; `createRelayAckSettler.settle(outcome)` receives only a `RelayRoutingOutcome` string; `sendAck(recipient, text, threadId)` has no id. `listener-delivered` has no session name at all (a warm listener inbox, not a named session); `pipe-spawned` may. The spec must say the settler/stage is extended to carry messageId and a nullable holder (session name or "listener"), and what sessionName means (and how reasons are chosen) for listener-delivered obligations. Without this, section 4's reason selection (alive session check) is undefined for the warm-listener path, which is the likely path for thread-ff759fcf.

D2. Closing on `inReplyTo` conflicts with the existing reply validation, which the spec does not account for.
Source: routes.ts ~38430-38436 rejects (400) an `inReplyTo` that is not an authenticated inbound on that thread; `isAuthenticatedThreadlineInbound` (ThreadlineReplyValidation.ts) checks the listener inbox or ThreadLog `has(...,'inbound')`. The spec itself says relay inbounds often are not in the canonical log. So a reply carrying the correct `inReplyTo` for a relay inbound can be refused, and the model then retries without it (hitting the fallback). The spec's claim that test 9 works "using its own recorded id" is only true for the matcher; the send path may never reach the matcher. Also `tryClaimReply`/`retainReplyClaimFailure` (routes.ts 38440-39533) is an existing per-inboundId at-most-once reply claim ledger: the obligation should hook the same success point (after relayStatus != rejected), not a new outbound observer, and should reuse/key off that ledger. Resolve: state the hook point (post-claim success in the send route) and what happens when validation 400s.

D3. The fallback close rule (same sessionName + same thread + exactly one open) has no sessionName on the outbound side defined, and the warm-listener path has none.
Source: relayForward.ts:341 says originSessionName is never forwarded; outbound origin session is known only on the sending machine's route. State that the fallback runs on the owner machine's send route only, and that a forwarded send (holder != owner) cannot close the obligation, which yields false notices after a handoff. Also the "exactly one open" count races against concurrent acks (two inbounds acked between check and write): specify the close decision and the obligation write happen under one synchronous critical section (single in-process mutex or sync read-modify-write), since the store is shared by the ack path and the send path.

D4. Timer and store design is unspecified for scale; as written it invites a per-obligation setTimeout plus whole-file JSONL rewrites.
Growth: one row per promising ack, i.e. per inbound message to a live session. A busy agent (hundreds of inbounds/day across peers) yields tens of thousands of rows in the 7-day retention window and every state change is a JSONL update (append-only cannot mutate a row; the spec says JSONL "beside the thread log"). Specify: append-only event log (open/replied/closed/sending/noticed) with an in-memory index rebuilt at startup, compaction at prune time, and ONE periodic sweep (e.g. every 60 s) over open rows rather than a timer per row; async or batched appends off the ack path (the ack path is a relay receive hot path). Also bound the open set (cap per peer, e.g. 100) so a peer flooding messages cannot create unbounded open rows (the ack rate limiter `createAckRateLimiter` limits acks but the obligation must be tied to acks actually sent, which it is; state this explicitly and that rate-limited/skipped acks create no obligation).

D5. Echo input 1 and 3 are listed but the spec body does not yet say how they are satisfied; the code facts decide them.
(1) classifyRelayPlaintextOperation (relayUnknownSenderTrust.ts:54) returns any string type as the operation; `allowed` for non-ack ops needs `getAllowedOperationsByFingerprint(...).includes('reply-notice')`, and `untrusted` is always refused. refuseDowngrade.ts:159 exempts only `'ack'`. So `reply-notice` would be dropped for unknown and invite peers unless added to the table AND exempted (as ACK_OP is, relayUnknownSenderTrust.ts ~line 40/87 and refuseDowngrade.ts:159). Recommended: treat `reply-notice` like `ack` in both places (no routing, no session, only records), and state it in the spec. Precedent for a notice to a pinned peer already exists: `relayClient.sendNoticeToPinned` with one-per-peer-per-hour (refuseDowngrade.ts ~197-320); reuse its encrypted path and its per-peer limiter rather than inventing a second one. (3) At-most-once across a crash is specified only as a note; it needs to be in section 3 with the `sending` mark written (fsync'd append) before the send, and `unknown` added to the verdict enum (the interface lists only delivered/queued/rejected/unconfirmed).

## PRECISION

P1. Section 4 handover: "same agent becomes holder" and "store is shared or replicated" are not defined; ConversationStore has `ownerMachineId`, which is the existing owner concept (ConversationStore.ts:682-702); name it instead of `ownerMachine`.
P2. Sweep cost at startup with 24h ceiling is O(open rows); fine once D4 is applied, state it. A degradation signal (DegradationReporter, as used by neighbors) should fire if the store cannot be written, so that an outage of this feature is not invisible (fail-open note); one line.
P3. Per-peer-per-hour cap versus T = 30 min: a peer with obligations at 0:00 and 0:40 gets one notice; the second folds forward. State that fold-forward is intended and that the notice lists all open times.

## Echo inputs: addressed or only listed?
1 trust gates: listed only (see D5). 2 untrusted text: addressed in spirit (structured fields) but the interface lacks the notice payload shape; add it. 3 crash: listed only (D5). 4 symmetry: listed only; the receive case must call recordThreadMessage itself and the sender must record the outbound notice through the same funnel (routes.ts 39485 is the existing outbound call site). 5 awareness: listed only; also requires MCP tool registration in ThreadlineMCPServer.ts and warm-session prompt text (ListenerSessionManager.ts ~706).
