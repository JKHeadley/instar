# Console features review round 1 — GPT-6 Astra (codex CLI), 2026-10-25

Verdict: **not ready** as an implementation plan. The visual direction and most feature inventories are good, but the plans still contain incompatible security contracts, misleading action descriptions, and capability losses. These need changes before native pages replace their legacy counterparts.

Reviewed all six requested documents against the parent plan, the console, all 29 legacy tabs and their supporting modules, and the relevant server implementations. This was a source review, not a live browser test. Baseline commit: `4313dffb10cc7d8b5e66948cef11a25a250a99b0`; concurrent native-console implementation edits appeared during the review and are outside this plan review. Several prominent defect claims are correct: the PR metrics handler is absent; commitments are filtered to pending beacon records; profile history reads the wrong response shape; the pending-login container is not mounted; and project writes swallow failures (`src/server/routes.ts:3538`, `dashboard/glance.js:435`, `dashboard/index.html:9339`, `dashboard/index.html:10649`, `dashboard/index.html:9583`). The findings below are ranked by consequence.

1. **The shared PIN pattern conflates three different authorization contracts.** `00-patterns.md:59` retains a short-lived operator-session proof, while `people-settings.md:28` adopts pairing's retained **raw PIN**, and `capacity.md:46` promises one unlock per visit. Those are not interchangeable. `checkMandatePin` reads a body PIN, not the operator-session header (`src/server/routes.ts:13664`); pairing and mandate actions call it. Re-login accepts either proof or PIN (`src/server/routes.ts:34524`). Account setup and email repair still require a body PIN (`src/server/routes.ts:35824`, `src/server/routes.ts:34970`). The Accounts design also calls “Don't retry on its own” bearer-only (`capacity.md:349`), although repair-cell cancellation passes the operator gate (`src/server/routes.ts:34626`). Copying pairing's cache into every page would extend raw-PIN retention to mandates, whose current controller deliberately clears it (`dashboard/pairing.js:231`, `dashboard/mandates.js:451`).

   **Smallest fix:** keep one visual PIN sheet with explicit per-action adapters: bearer only, expiring operator-session header, or body PIN cleared after that action. Preserve exact server plan text and nonce binding for money and feedback commits. Make reusable proof on currently PIN-only routes a separate server change, not an implied property of the sheet. Keep the README's default of asking per action until that change is approved.

2. **“You told me” preferences would be forgeable, and forgetting is not just a small route wrapper.** The proposed new writes stamp `provenance: operator`, use bearer authentication only, and recommend ranking those entries above learned preferences (`people-settings.md:422`). Agent sessions hold that same bearer; the code explicitly explains this distinction at `src/server/routes.ts:35820`. A caller could therefore manufacture an operator-stated preference. The implementation estimate also misses persistence work: the manager's emission interface is put-only, with no delete path (`src/core/PreferencesManager.ts:184`), and the replicated schema coerces every provenance back to `correction-loop` (`src/core/PreferencesReplicatedStore.ts:149`). Generic tombstone support does not establish that “Forget” removes every origin's copy or prevents it returning through the alternative union readers (`src/server/routes.ts:28101`).

   **Smallest fix:** leave preferences advisory. Require server-verified operator proof before attributing a new statement to the operator or giving it special priority. Specify local deletion, replica handling, concurrent edits, and re-learning before promising “I'll stop loading this.” Ship the structured read first; make editing and forgetting a separate, tested backend change.

3. **Integrated-Being commitments are not duplicates of the Promises records.** The plan removes their status and sends readers to Commitments (`under-the-hood.md:470`, `:484`). But `/commitments` reads `CommitmentTracker` (`src/server/routes.ts:32784`), while ledger entries have their own mechanism, deadline, resolution and dispute fields (`src/core/types.ts:5356`, `:5405`). No mapping is established that makes a ledger entry appear on Promises. The assertion that no resolution route exists is also false: `POST /shared-state/resolve/:id` exists, requires a registered session binding, and implements self-assert/dispute; user-resolve remains 501 (`src/server/routes.ts:40718`). Finally, opening the chain does not solve missing later resolutions: `walkChain` follows `supersedes` backwards, not forwards to entries that supersede the selected record (`src/core/SharedStateLedger.ts:579`).

   **Smallest fix:** retain the ledger commitment's full record and status in its own detail sheet. Link to Promises only when an explicit, verified relationship exists. Correct the route inventory and keep unsupported human resolution actions absent. Report unknown status when later history cannot be established; do not claim the backwards chain proves it.

4. **“Pause at a safe point” misrepresents the existing Halt action.** The confirmation promises that the current round stops safely (`work.md:513`). In fact, execution notices `haltedAt` and terminates the child process group, escalating from SIGTERM to SIGKILL after its grace period (`src/core/ProjectRoundExecution.ts:595`, `:615`). This is an interruption, not a checkpoint guarantee. The new Resume action also omits its required targeting detail: `/projects/:id/resume` defaults to round zero when `roundIndex` is absent (`src/server/routes.ts:23706`). That risks recreating the very round-zero problem the plan aims to fix. Acknowledgment itself records permission; it does not synchronously start a round (`src/core/ProjectRoundRunner.ts:357`).

   **Smallest fix:** label Halt “Stop this round” and explain that it interrupts running work. Send the selected halted round's index on Resume. Distinguish “approval recorded,” “scheduled to resume,” and “running,” using the returned and subsequently observed state.

5. **The costs page promises conclusions its sources cannot prove.** “Subscriptions covered everything” and “Paid this window” (`capacity.md:437`) overstate a machine-local reporting view. The server distinguishes estimated, provider-reported, subscription-zero and unpriced cost, and separates reporting totals from committed cap usage (`src/core/routingSpendView.ts:30`, `:104`). More specifically, the proposed per-feature cost join cannot identify a paid route: feature `byModel` rows contain model and framework, while spend buckets contain door and model but no feature (`src/monitoring/FeatureMetricsLedger.ts:207`, `:252`). The same model can be served through different doors. Missing attribution cannot become “covered by subscription.” The promised conversation count also names a nonexistent Claude field: it is `summary.sessionsActive`, not `summary.sessionCount`; Codex has its own `codex.sessionCount` (`src/monitoring/TokenLedger.ts:161`, `:225`; `src/server/routes.ts:12708`).

   **Smallest fix:** say “Recorded AI cost on this machine,” retain the cost-basis and coverage labels, and keep committed limits separate. Show per-feature calls and tokens without dollars until feature-to-door attribution exists. Use the actual Claude/Codex count fields. Likewise, label routing usage as aggregate model usage unless it can actually be attributed to each routing lane.

6. **The “nothing is lost” inventory has concrete holes.** The clearest lost write is **Mark delivered**: legacy offers it on every displayed promise, including the waiting-on-you list (`dashboard/glance.js:520`, `:557`), but the new plan assigns it only to agent-owned rows (`work.md:425`). Other controls or records lack an explicit replacement: Spend's hourly/monthly/total choices (`dashboard/index.html:3771`); job history beyond the proposed “Last 20 runs,” where legacy provides 50 (`dashboard/index.html:8880`; `work.md:327`); Throughput's median push iterations (`dashboard/index.html:10682`); and arbitrary ledger-ID chain lookup (`dashboard/index.html:3550`). Class reviews and claim-verification observations are said to move into Process health, but that destination's inventory, layout and data section omit both sources (`people-settings.md:414`; `under-the-hood.md:540`; `dashboard/preferences-learning.js:330`).

   **Smallest fix:** add a compact old-control → native-control checklist and make it the replacement gate. Keep Mark delivered as a secondary action wherever it worked before. Put the less common history, metrics and lookup controls behind “More detail,” with Show more where needed. Add the two audit sections explicitly. A legacy footer is a valid temporary fallback, not completed native parity.

7. **Merging Health into Machines hides it without the promised safety net.** The rationale says Home already answers whether anything is broken (`capacity.md:220`). Home does not fetch `/systems/status`; it reads held-reply health, attention, sessions, commitments, pool and guards (`dashboard/console/console.js:349`). A subsystem failure need not appear in those sources. There is also a single-machine hole: the plan promises one machine card, but `/pool` can legitimately return `enabled:false` with `machines:[]` (`src/server/routes.ts:21517`). If the card is the only entrance, Health and resource usage become inaccessible precisely on ordinary installations.

   **Smallest fix:** always provide a “This machine” detail independently of pool availability. Keep a visible Health shortcut on Capacity, with a truthful local health summary; surface failures on the Machines landing page before requiring a drill-down. “Sessions + Paste” and “Projects + Initiatives” are sensible merges. “How I'm doing inside” is much less findable: give its tile a subtitle naming conversation history and recurring problems, and preserve the old names as searchable aliases.

8. **The global noise rule can hide unresolved trouble merely because it is old.** `00-patterns.md:37` excludes old untouched items from headlines, and `work.md:70` generalizes “probably already handled” across Work. In the reused Home implementation, even missed promises are excluded from the prominent missed set when untouched for 14 days (`dashboard/console/home-model.js:215`). Age is not evidence of delivery or resolution. Applied to the new pages, this can bury an overdue promise, expired credential or still-blocked project. Similarly, one job on two machines can have two different outcomes; collapsing it to one status would obscure which instance failed (`work.md:345`).

   **Smallest fix:** collapse repetitions and routine old records, but retain unresolved failure, overdue and approval counts regardless of age. Use “Older — still unresolved,” not “probably handled.” Define this per feature, and preserve per-machine state and action targets inside grouped jobs. The headline can remain short without asserting that unexamined work is finished.

9. **The Features repair still does not follow the complete state machine.** The plan correctly identifies broken toggles, then proposes `aware → interested → enabled` and says local-tier features switch directly (`people-settings.md:322`). All tiers obey the transition graph: `undiscovered` can only become `aware`; deferred/declined must return through aware; disabled can re-enable directly (`src/core/FeatureRegistry.ts:177`). A direct local enable still fails for a newly discovered feature. The added “Yes, for this kind” trust suggestion is also not an apply action: `/autonomy/elevation/record` only records an approval event (`src/server/routes.ts:31674`). This important screen remains partly a sketch rather than a specified working permission flow.

   **Smallest fix:** drive the sheet from the actual state and `validTransitions` returned by the feature detail route (`src/server/routes.ts:40043`), retaining the consent and activation challenge requirements. Test one fresh local feature, a fresh network feature, and a self-governing feature through activation and re-enable. Omit the trust-acceptance button until there is a real apply path; “Remember I said yes” should not masquerade as changing permission.

10. **The build order delays urgent phone workflows and includes too much new product work.** Promises and Machines are good early slices, and rebuilding the live terminal late is reasonable. But Accounts is fifth, missing replies are seventh, and Feedback approvals are bundled into the last stage (`README.md:89`). Those are operator interventions; Plans and a richer schedule can follow them. The group plans also give conflicting orders. Evidence drawers depend on IDs their host records may not carry; preference editing needs more than a type change; and Shipping introduces several new destructive controls. Pace is not yet grounded enough for its proposed headline: the API returns daily medians, from which a true whole-window median cannot be recovered, and result-cap failures return 503 rather than the proposed partial 1,000-PR dataset (`src/server/throughputRoutes.ts:84`, `:113`, `:127`, `:171`, `:206`).

   **Smallest fix:** choose one order: a minimal page/detail/action pattern proved by Promises; Machines with visible Health; Accounts sign-in repair and Messages to you; Features and maintainer Feedback approvals; then Plans, Schedule and read-only costs. Keep the terminal, advanced preference writes, universal Evidence drawers, new shipping controls and sophisticated comparison charts later. Reuse existing controllers where practical. Scope file search to the existing path-security rules, including resolved paths and never-served files, rather than an allowed-path name scan alone (`src/server/fileRoutes.ts:88`, `:246`, `:395`). Maintainer mode should remain the visibility preference the plan describes, never authorization; retain every server gate. Judge one representative populated, empty, failed and editing screen at phone size before expanding the pattern. That supplies a concrete aesthetic and usability test without building a framework for all 29 tabs first.

DONE.
