# Console features review round 3 — GPT-6 Astra (codex CLI), 2026-10-25

Verdict: **ready with changes**. The direction and build order are sound. The earlier PIN, cross-machine targeting, Health visibility, preference-write, and Development-layout findings have been addressed. The remaining changes below should land before the affected pages pass their native replacement gate.

Reviewed the six current feature plans, the parent plan, previous reports and review responses, and the relevant legacy controllers and server implementations. This was a source review, not a phone usability test. HEAD: `12fc2a3b844482e44a7cde001361ae5dbcb56f81`. Concurrent console implementation changes were present; this report judges the plans, not those unfinished changes. References to feature-plan filenames below mean `docs/specs/console-features/`.

1. **Moving the follow-me scan to a timer leaves its approval cards without a specified data source.** `README.md:94` requires a server timer, while `capacity.md:375` still promises follow-me approvals. Today those cards get their offers from the POST scan response, not from the listed account or pending-login reads (`dashboard/subscriptions.js:1203`, `:1226`). The scan builds the offer, including the server-resolved agent pair, and returns it directly (`src/server/routes.ts:35290`, `:35299`). Merely scheduling that work on the server does not make its result readable by the console. This is a remaining path by which an existing approval control could disappear.

   **Smallest fix:** include a read of the latest offers, with scan time and failure state, in the timer change—preferably as fields on an existing Accounts read. Alternatively, explicitly choose the scan-on-view-open option already mentioned at `capacity.md:435` and retain its response. Choose one contract across both documents; keep polling free of writes and keep the approval PIN gate.

2. **The combined token headline still adds incompatible time windows.** `capacity.md:645` promises “9.1M tokens … this week (Claude 8.2M, Codex 0.9M).” Claude's summary sums events inside the requested window (`src/monitoring/TokenLedger.ts:1100`). Codex instead sums cumulative session totals for sessions whose last activity falls inside the window (`:1360`); ingestion deliberately replaces each session's lifetime total (`:633`). A Codex session used both last month and today brings last month's tokens into “Today.” The proposed top-conversation list also names only `/tokens/sessions`, which returns Claude rows (`src/server/routes.ts:16129`), although a separate Codex endpoint exists at `:16115`.

   **Smallest fix:** show Claude's usage in the selected window separately from “Codex lifetime usage of sessions active in this window”; do not add them into a window-total headline. Add `/tokens/codex-sessions` for the Codex rows. A true combined window total requires a later ledger change, not client arithmetic. This is distinct from the already-corrected session-count field names and dollar attribution.

3. **The conversation-ledger headline claims live state its sources do not measure.** `under-the-hood.md:561` promises last-day decisions, agreements, open threads and threads gone quiet; `:618` assigns quiet threads to `stats.unclosedThreadsOverTtl`. The stats response has accumulated entry counts, not a daily aggregation or a current open-thread inventory (`src/core/SharedStateLedger.ts:108`, `:605`). Its TTL counter only has an increment method, with no production caller found (`:632`); the abandonment sweep emits ledger events instead (`src/threadline/ThreadlineRouter.ts:521`). Meanwhile `/shared-state/recent` is capped at 200 records (`src/server/routes.ts:40191`), and a `since` filter does not remove that cap (`src/core/SharedStateLedger.ts:479`). Neither a zero TTL counter nor a page of events proves that no thread is currently quiet.

   **Smallest fix:** lead with “Recent recorded activity,” count decisions and agreements only within the displayed records, and show recorded thread-opened/closed/abandoned events as events. Keep the raw TTL counter under Technical without treating it as a live health signal. Defer current open/quiet-thread totals until there is an authoritative read. The earlier commitment-resolution fix remains valid; this is a separate thread/count problem.

4. **Two merges still remove useful filters, despite retaining the records.** Other agents explicitly cuts the with/without-Telegram-topic filter (`people-settings.md:131`), which legacy exposes at `dashboard/index.html:4340`. Per-agent grouping and message-text search cannot answer “which conversations are not mirrored to Telegram?” The conversation-ledger chips likewise omit Notes, Self and System, and combine opened, closed and abandoned threads (`under-the-hood.md:566`); those are separate legacy filters (`dashboard/index.html:3500`, `:3513`). “All” preserves access to records but loses these ways to isolate them—particularly costly for an operator who ignores noisy lists.

   **Smallest fix:** keep a compact More filters sheet: Telegram topic present/absent for Other agents; every legacy kind and counterparty value for the ledger. The main phone view can still show just the useful few chips. Add those exact controls to the parity checklist. No additional page or backend is needed.

5. **Process health overlooks existing pagination and leaves its new totals underspecified.** `under-the-hood.md:706` proposes increasing `limit`, then stopping at 50 if there is no offset. The route already supports a `before` timestamp for paging (`src/server/routes.ts:16476`, `:16483`; `src/monitoring/FailureLedger.ts:527`). Separately, the new “This week” and “Still open” facts (`under-the-hood.md:668`) cannot be complete counts taken from the latest 10 or 50 problems. The analysis route supports `sinceDays`, but its response contains no open-status total (`src/server/routes.ts:16492`; `src/monitoring/FailureLedger.ts:613`).

   **Smallest fix:** specify Show older using the existing `before` parameter, and read `/failures/analysis?sinceDays=7` for the week's total. Until an authoritative open count is available, say “N still open among the records shown.” Do not turn a display limit into a whole-agent verdict or add an unnecessary offset API.

6. **Permission slips cannot reliably count all of today's decisions from its audit tail.** `people-settings.md:230` and `:260` promise a client-computed 24-hour allowed/refused count. `/mandate/audit` returns only the newest `limit` entries: 100 by default, up to 1,000, with no time filter or pagination (`src/server/routes.ts:13727`, `:13737`). The legacy request uses 200. On a busy day, older refusals can fall outside that tail while the new headline still appears to count the entire day.

   **Smallest fix:** label the figures “Among the latest N decisions.” Claim a complete time-window count only when the returned data demonstrably covers that window; otherwise retain the limited-history label. Keep chain integrity as its separate server-supplied fact.

7. **The latest Promises section has lost its action design, and the remaining checklist rule is too broad.** In `work.md:447`, the new design now ends after Arrival and Layout, jumping to Merge at `:461`; it no longer specifies the action sheet, action states or machine handling. The checklist still requires Mark delivered on every shown promise except `violated` (`README.md:215`), while the layout includes closed records. The server also refuses delivery for `verified`, `expired`, `withdrawn` and `delivered` (`src/monitoring/CommitmentTracker.ts:910`). Drop and Resume have different eligibility rules (`:850`, `:880`). The actions are still named elsewhere, so this is an incomplete plan rather than proof that the implementation removed them.

   **Smallest fix:** restore a short action table in the Promises section covering eligibility, confirmation/reason, machine target and refusal behavior for Mark delivered, Drop and Resume reminders. Replace the checklist's single-status exception with the server's complete eligibility rule. This is the one feature whose current action design is now less specific than its overview claims.

The major legacy defect claims checked still hold: missing PR metrics handler, wrong profile-history response shape, unmounted pending-login panel, POST-on-poll Accounts scan, and the misleading Health/Feedback failure paths. The mergers and renames are otherwise defensible with the specified subtitles, aliases and deep links. I found no additional confirmed loss of a legacy write action beyond the unresolved follow-me data path above.

No new PIN or operator-proof defect found in the revised plans. Keep the three adapters, one-request body-PIN clearing, exact plan text/nonces, local-only guard acceptance, and server gates. Maintainer mode remains a visibility preference, not a new access boundary; the developer-tools toggle must not imply otherwise. The file-search path checks are appropriately specified.

The 80/20 build order is right: prove the phone pattern, Machines/Health, sign-in and delivery interventions, permissions and Feedback approvals, then broader read views. Keep the terminal, preference writes, evidence drawers, advanced editor and new Shipping writes deferred. Cut the unsupported aggregate claims above rather than building new analytics to justify them. Keep the four-state phone acceptance check: these written sketches alone do not establish that the result is aesthetic or intuitive.

DONE.
