## ELI10 Overview

Jobs can show an owner which definitions disagree before a migration. It keeps selected behavior, recorded execution and proposed changes separate. A partial scan reports gaps and cannot authorize a migration. The first build observes the current machine and keeps unchecked peers out of the private result.

## Original vs Converged

It presents a bounded ordered preview with safe field categories and leaves unknown ownership unresolved. It adds no authority to a backup, a peer, or the preview result itself.

## Full Findings Catalog


### Round 1

**Verdict: SERIOUS ISSUES**

- **DESIGN — Problem statement / Proposed design.** The owner needs to know which definition won and what migration would change. The proposed categories describe relationships among current inputs. A `divergent` row labeled `enabled state` could describe either enabling or disabling a job. The umbrella’s *Canonical job definitions* section calls for a dry-run mapping per slug. Show the loader-selected source or suppression reason, the proposed canonical mapping, and the direction of any known change that is safe to disclose. Where choosing a variant requires owner judgment, show that the mapping is unresolved. Test two conflicts with opposite enabled-state changes and one journal-suppressed slug with no runnable winner.
- **DESIGN — Proposed design, bounded snapshot.** The spec requires fingerprint verification but does not say how to verify the set of inputs discovered. A new manifest can appear after enumeration while every file already read still passes its fingerprint check. The preview could then report a legacy-only winner with complete local coverage. Include directory membership and source absence in the consistency check, alongside the files that determine precedence. If verification fails or exceeds the deadline, mark the affected coverage incomplete and its winner unknown. Test a manifest appearing between enumeration and verification.
- **DESIGN — Frontloaded Decisions 1 / Proposed design.** The only specified UI entry point is the setup issues view. The draft keeps structural findings independent of preview findings, yet never specifies how an owner reaches the action when there are zero structural findings. Require the action to remain reachable in that view’s empty state or from Jobs itself. Verify the normal owner interaction with a structurally clean catalog.

The implementation files are cited but not inlined. These findings concern the specified behavior. Whether the current code already handles any of them is unverified.

- Conformance — Judgment Within Floors. Host protection warrants a ceiling, but the draft gives no evidence for rejecting a second request or stopping at 1,000 entries, 1 MiB per file, 8 MiB total input, 250 rows, 512 KiB output or two seconds; a valid 251st conflict or a stable scan on a slow disk could be served by coalescing, paging or choosing a work budget within measured hard ceilings.
- Conformance — Never Silently Cut the Data a Decision Depends On. The preview discloses truncation, but neither its input and output limits nor its status-then-slug cutoff are derived from producer capacity, consumer capacity or where the evidence needed to inspect a conflict resides.
- Conformance — An Instar Agent Is Always a Multi-Machine Entity. The fleet design gives the owner evidence only from the serving machine even when an enrolled peer is reachable, marks the peer unverified and defers authenticated retrieval without identifying a concrete obstacle to unifying the read.
- Conformance — An Instar Agent Always Serves a Team. Configured-owner-only admission rejects even a member whom the owner's signed team record authorizes to inspect a shared job, and the draft gives no reason why the redacted preview cannot honor that share.
- Conformance — Maturation Path — Test Agent → Development Agent → Fleet. The fleet rung keeps the preview capability opt-in without a recorded user-preference decision, although enabling the capability by default would still leave every preview run on demand.

Disposition. Defined selected behavior, stable directory inputs, clean Jobs entry and private request boundaries.

### Round 2

**Verdict: SERIOUS ISSUES**

- **DESIGN — Proposed design, comparison and mapping.** The draft requires a mapping that preserves effective behavior, yet its acceptance tests require both enabling and disabling changes. Neither section identifies the two states those arrows compare. A disabled legacy row shadowed by an enabled manifest could correctly show “legacy disabled → selected enabled” while migration itself changes nothing. Label both endpoints of every difference. Test that fixture in both directions and require an unchanged migration outcome whenever the proposed mapping preserves the selected state. Keep live scheduler state separately labeled.

- **DESIGN — Proposed design, bounded output and exact-slug drill-down.** The draft caps output at 250 rows and offers exact-slug lookup for omitted conflicts. It gives the owner no way to discover an omitted slug. With 251 distinct conflicting slugs and otherwise complete input, the owner needs an identifier the inventory may never show. Provide bounded continuation in a deterministic order, with a restart indication if inputs change between requests. Test that an owner starting without any slug names can reach all 251 conflicts through Jobs.

- **DESIGN — Proposed design, loader precedence.** The draft explicitly reuses loader normalization and validation, but leaves open how the preview reproduces winner selection and journal suppression. The umbrella’s *Canonical job definitions* section requires preservation of the previously validated effective variant. A separate precedence implementation could drift while still passing fixed examples. Extract a pure selection routine used by both paths, or require differential tests that run the production loader and preview against the same stable fixtures and compare winners and suppression outcomes. The inlined material does not establish whether such a routine already exists.

- **PRECISION — Maturation plan, dark-window.** The flag must remain off until development evidence is recorded, while that evidence requires an owner to run the preview on a development agent. Specify how the designated test and development installations enable it and which population remains gated pending that evidence.

- Conformance — Judgment Within Floors. A host needs a resource ceiling, but the draft does not derive why a second small request, a 1,001-entry inventory, 10,001 legacy rows, a file over 1 MiB, inputs over 8 MiB, a 251-row report, output over 512 KiB, or a healthy worker needing three seconds must be refused or cut short; measured host and transport ceilings could bound a judgment about how much work to admit or page.
- Conformance — Never Silently Cut the Data a Decision Depends On. The draft reports which limit was hit, but it gives no rule for which 250 rows survive an output cut or how the owner discovers an omitted conflict whose exact slug they do not already know.
- Conformance — Maturation Path — Test Agent → Development Agent → Fleet. The fleet plan makes an operator-recorded availability decision mandatory after the signed pool path passes, displacing the recurring model review and independently corroborated default-on change that govern graduation.
- Conformance — Observability — you can't tune what you can't see. The plan measures catalog size and host speed before enrollment and tests selected cases, but defines no ongoing measure of how often owners receive a verified comparison or can recover conflicts omitted from the initial view.

Disposition. Labeled both comparison endpoints and added actual loader equivalence, complete pagination and qualification enrollment.

### Round 3

**Verdict: SERIOUS ISSUES**

- **DESIGN — Multi-machine posture.** The peer checks owner scope before replying, and the origin checks scope again before rendering. The spec does not say how the origin learns that a peer revoked access *after signing its reply*. A valid signature and request nonce establish who answered which request. Neither establishes that the peer’s authorization is still current. Define how the origin verifies current peer scope at release, and show that machine as unchecked when verification is unavailable. Test revocation between receipt of a valid reply and serialization.

- **DESIGN — Proposed design, canonical mapping.** The preview promises a mapping that preserves effective behavior. The parent’s *Canonical job definitions* section requires unresolved treatment when a script or skill reference cannot be bound to its authorized executable identity without promoting its authority. The preview specifies checks for body and lock provenance but gives no equivalent decision rule for script and skill targets. Require each proposed mapping to identify the evidence that its runner binding preserves existing authority. When that evidence is missing, return a named unresolved disposition. Test an unchanged runner reference whose target has changed.

- **DESIGN — Proposed design, bounded continuation.** Both the 250-row limit and the 512 KiB encoded limit apply, but the acceptance test exercises only row 251. The byte limit can end a page earlier, and a single slug with many variants can exceed the entire page budget. A cursor pointing to the next row cannot finish that slug. Define the pagination unit, reserve space for cursor metadata, and advance from the last item actually emitted. Test a byte-limited first page and one slug whose variants require two pages, checking for omissions and duplicates.

- **PRECISION — Proposed design, request shape.** “Match the exact preview query shape” defines the initial GET, while continuation requires a cursor with no specified transport. Document the accepted continuation request and how malformed preview requests are rejected so they cannot fall through to ordinary reconciliation.

These are findings about the supplied contracts. The referenced implementation was not inlined, so its runtime behavior is unverified.

- Conformance — Judgment Within Floors. A physical resource ceiling is warranted, but the draft gives no measurements deriving one evaluation per machine, 1,000 entries, 10,000 legacy rows, 1 MiB per file, 8 MiB total, 250 rows per page, 512 KiB of output or two seconds per worker; a second small request, a large valid catalog or a slow healthy host could safely exceed an individual limit, so workload-sensitive admission and pagination within measured host and transport ceilings deserve consideration.
- Conformance — Never Silently Cut the Data a Decision Depends On. The preview discloses incomplete scans and offers continuation for complete snapshots, but its input and output limits lack the required derivation from what supported job catalogs can contain and what the worker, transport and Jobs view can accept.
- Conformance — Maturation Path — Test Agent → Development Agent → Fleet. The rollout selects specifically designated installations and requires an operator to record the fleet decision, bypassing the role-based rungs and recurring model review that opens a fleet-default change after two independent readings agree.
- Conformance — Observability — you can't tune what you can't see. The plan measures catalog sizes before enrollment and checks qualification cases, but neither shows how often owners using the shipped preview can identify the loader-selected definition and its migration effect or how often limits and missing peer evidence prevent that outcome.
- Conformance — No Manual Work (user *or* agent). After a cursor expires, a source changes or the serving process changes, the UI makes the owner restart an already authorized read that it could retry within a bounded budget while the owner session remains valid.
- Conformance — Documents Stand on Their Own. The opening introduces “slug,” “executor” and “B2 project custody” without defining them, leaving a reader unfamiliar with Jobs to infer what identifies a job, what runs it and why the related project work is mentioned.

Disposition. Pinned explicit continuation request, scope freshness, authorized runner identity, tie-breaking and byte-bound variants.

### Round 4

**Verdict: SERIOUS ISSUES**

- **DESIGN — Proposed design, pagination; Multi-machine posture.** The spec reserves 1 KiB for cursor and coverage metadata, caps the encoded response at 512 KiB, and requires the view to account for every verified enrolled machine. It gives no roster bound or continuation rule for coverage. With zero job rows, reducing the row count cannot make an oversized roster fit. Give coverage its own bounded continuation, bind it to the membership epoch, and test a roster whose encoded coverage alone exceeds the response cap.

- **DESIGN — Proposed design, canonical mapping; umbrella spec, Frontloaded decisions §4.** The preview requires a mapping that preserves effective behavior and explicitly checks runner authority, but its comparison contract does not specify how unresolved job ownership affects the result. The umbrella requires unknown legacy ownership to stay unresolved with existing execution and access preserved. Represent execution parity and ownership disposition separately. Test a legacy job whose runner is fully verified but whose accountable principal is unknown. Its preview should show both facts without assigning an owner.

- **DESIGN — Proposed design, loader selection and pagination.** The spec requires production-equivalent selection and stable pagination across duplicate variants. It does not define what makes an occurrence ordinal stable or whether it participates in precedence. If directory enumeration order changes between page requests, identical membership alone cannot establish identical row order. Derive display order from reproducible source coordinates independently of loader precedence. Bind the continuation to the resulting ordered rows and selection decisions. Test the same files enumerated in reverse order and require either exact continuation or an explicit restart if the production winner changes.

These are findings about the supplied contracts. The inline material contains no production loader source or measurements establishing actual roster sizes or enumeration behavior.

- Conformance — Judgment Within Floors. The spec requires host measurements but does not show why one worker, the entry, row and byte ceilings, or two seconds are the necessary boundaries; a valid 10,001-row catalog or a healthy slow host could yield only partial evidence where a measured host-safety floor would allow a larger scan.
- Conformance — No Manual Work (user *or* agent). The owner must manually request the read-only preview and restart it after cursor expiry or a snapshot change, even while the same authorization remains valid and the console could refresh the evidence automatically.
- Conformance — Maturation Path — Test Agent → Development Agent → Fleet. The rollout selects specifically designated installations and requires an operator to record the fleet decision, bypassing role-based enrollment and the recurring model review that opens a fleet-default change after two independent readings agree.
- Conformance — No Deferrals. The spec makes the authenticated pool reader a condition of fleet release but leaves delivery to a separately reviewed increment without identifying a same-PR tracked commitment for that work.

Disposition. Separated execution parity from owner disposition and added bounded roster coverage continuation.

### Round 5

**Verdict: SERIOUS ISSUES**

- **DESIGN — Proposed design, duplicate slugs.** The preview assigns rows to each source occurrence but asks for “the selected source” per slug. The umbrella says the scheduler chooses a winner. Neither inlined document establishes that every accepted duplicate produces exactly one runnable definition. Verify this against the production scheduler with two valid legacy rows sharing a slug and differing in schedule. If both survive, report both effective occurrences and leave the single-manifest mapping unresolved. If only one survives, make that behavior an acceptance assertion.

- **DESIGN — Multi-machine posture, pagination.** The cursor binds to the serving machine and membership epoch. The spec defines an order for job rows but gives no machine discriminator for two peers reporting the same slug, source slot and occurrence ordinal. Membership can also stay constant while one peer’s definitions change between pages. Define whether job pagination is per machine or pool-wide. Per-machine pagination can reuse the local ordering and snapshot check. A pooled stream needs an internal machine tie-breaker and a cursor bound to the contributing machines’ snapshot fingerprints. Test identical sort keys on two peers and a peer edit between pages.

- **DESIGN — Proposed design, comparison output.** The spec permits direction for “approved non-sensitive facts” and only categories for private configuration. Enabled state has an example, but the text never identifies who or what classifies the other fields. Two implementations could therefore disclose different details about delivery, placement or runner options while both claiming conformance. Specify an allowlist of output fields and allowed values, with category-only output as the default. Test the encoded response against that contract for all four executor types.

- Conformance — Judgment Within Floors. The draft makes one active worker, 1,000 entries, 10,000 legacy rows, 1 MiB per file, 8 MiB total and two seconds binding before measurements justify those boundaries; a stable 10,001-row catalog or a second request on an idle, well-provisioned host could fit a measured resource floor, within which admission and scan budgets could adapt.
- Conformance — Never Silently Cut the Data a Decision Depends On. The draft discloses incomplete scans and withholds absence claims, but it does not derive the input limits, the 250-job and 100-machine page sizes, the 512 KiB response ceiling, or the 1 KiB cursor and summary reservation from what producers emit and consumers accept.
- Conformance — Maturation Path — Test Agent → Development Agent → Fleet. The plan selects individual installations and leaves fleet availability to a manually recorded operator decision, bypassing role-based rungs and the recurring review that must independently evaluate graduation evidence and open the fleet default-on change.
- Conformance — Observability — you can't tune what you can't see. The proposed measurements cover catalog size, worker cost and request handling during qualification, but do not measure in service how often an owner-requested preview delivers a complete comparison or which limits prevent it.

Disposition. Made job pagination per machine, checked duplicate runtime behavior and fixed the allowed response fields.

### Round 6

**Verdict: MINOR ISSUES**

- **DESIGN — Proposed design, incomplete scans.** The spec allows an incomplete scan to return “scoped leads” and forbids it from establishing absence. It does not say when a lead may still be labeled *selected*. An unread manifest could override an observed legacy row. Define completeness per decision. Show the legacy occurrence as observed, and report its winner and mapping as unknown whenever an unchecked input could change either. Test a scan that reaches its entry limit before a competing manifest, alongside a slug whose result can be proved independently.

- **DESIGN — Multi-machine posture, offline coverage.** The spec asks the Jobs view to identify known offline peers as unchecked. It also requires withholding peer aliases and counts without a current peer authorization fence. The supplied umbrella spec calls for unknown coverage when a machine is unavailable, but neither document settles what the owner sees when roster access is current and the peer is offline. Specify whether roster authorization independently permits listing an enrolled machine. If it does, show the roster-authorized alias with unchecked catalog coverage. Otherwise show only the authorized pool-level status. Give the offline-peer test an exact expected response.

- **PRECISION — Proposed design, pagination envelope.** The job-page budget reserves 1 KiB for “its cursor” and the coverage summary. Multi-machine posture adds a separate coverage cursor, so a first page can carry both tokens. Apply the encoded-byte limit to the final response envelope, including both cursors, and test a byte-limited first page with both continuations present. Verify that the next job page begins immediately after the last emitted row.

These findings concern the inlined contracts. The cited implementation files and runtime measurements were not supplied, so none is a claim about observed production behavior.

- Conformance — Judgment Within Floors. A physical ceiling is justified, but the draft does not derive its exact one-worker, entry, row, byte, page, cursor-reserve or time limits from measured constraints: a valid 10,001-row catalog or a healthy slow host needing three seconds loses a complete preview, while capacity-aware admission and sizing could preserve it within a tested hard ceiling.
- Conformance — Never Silently Cut the Data a Decision Depends On. An incomplete scan is disclosed, but the input limits that determine whether the preview can identify a winner are set before measuring what supported catalogs produce and slow workers can consume, with no requirement to derive revised limits from those measurements.
- Conformance — Maturation Path — Test Agent → Development Agent → Fleet. The rollout uses specifically designated installations and requires the operator to record a fleet decision, bypassing role-derived cohorts and the recurring independent review that opens a default-on fleet change unless a recorded user preference keeps it off.
- Conformance — No Manual Work (user *or* agent). Even an authenticated owner preparing to authorize a migration must remember to request the read-only preview and restart it after cursor expiry or snapshot change, although the Jobs flow could collect fresh evidence automatically within the same authorization and resource limits.
- Conformance — Cross-Store Coherence Is an Invariant. The legacy catalog and schedule manifests can give different answers about a job’s effective configuration, yet the specified comparison runs only on owner request, leaving no scheduled check of their declared precedence and agreement conditions.
- Conformance — A Safeguard Must Leave a Benefit. The draft makes job pagination independent per machine but withholds even the serving machine’s verified preview from the fleet pending a separately reviewed peer carrier, without identifying what an installation with one enrolled machine gains from that restriction.
- Conformance — Occam's Razor — Simplest Robust Route. The design omits the required `simplestRobustRoute` assessment of whether shipping verified local results with explicit unchecked peer coverage would preserve the stated floors without making fleet availability depend on the new pool carrier.

### Internal findings

- Security. Initial authorization alone was insufficient after an awaited worker. The existing generic bearer verifier could admit a missing token. Require the current exact owner console session before any read and again before output.
- Integration. A combined response would invoke an unbounded legacy scan and expose its paths. Use a disjoint branch, retain old callers and explicitly attach the existing operator header in the shipped console.
- Adversarial. A directory entry can change after enumerating. Pin confined regular-file reads, verify membership and absence, reject symlink or special-file redirects and test deadline recovery.
- Decision completeness. Define cursor request shape and encrypted fields. Use stable occurrence coordinates, exact encoded limits and a deterministic order. Keep all production-effective duplicate rows unresolved if no unique mapping exists.
- Lessons and authority. An owner-only whole-catalog read needs independently verified identity and must withhold comparisons and metadata from shared scopes. A peer response without release-time auth cannot supply trusted catalog claims.

## Convergence verdict

Converged at the Tier 2 cap for the development-only read preview. The accepted interpretations above are binding preconditions and need tested evidence before cohort activation. No job definition authority, runtime scheduling, backup restore, remote private coverage, or fleet rollout is approved here.
