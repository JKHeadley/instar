# spec review round 2 — GPT-6 Astra (codex CLI), 2026-10-26

Verdict: **ready with changes**. The core fix addresses the measured incident: drift promotion detaches before asynchronous cleanup, so it no longer deliberately sends Ctrl-C to the server. Busy-server adoption, restoration-time alarms, and the alarm before the unclean-exit retry drop now match the revised spec. The remaining findings below concern current behavior, not answered round-one objections.

**Is leaving the server running safe?** Yes, on the described launchd/shared-tmux deployment. `ServerSupervisor.ts:1202` starts the server in a detached tmux session. The tmux daemon runs independently; exiting the lifeline does not send Ctrl-C into that session. Apple's [launchd manual](https://github.com/apple-oss-distributions/launchd/blob/main/man/launchd.plist.5) describes cleanup of the job's process group, and [tmux's daemonization code](https://github.com/tmux/tmux/blob/master/proc.c) supports the separate-process-group reasoning. This is source-backed reasoning, not a live launchd experiment or independent confirmation of the spec's Studio measurement.

There is no server-port or server-lock transfer: the same server keeps them. Quiesce removes the lifeline's own PID-guarded registration and lock (`TelegramLifeline.ts:565`, `:566`, `:106`); the successor acquires its lifeline lock before adoption (`:339`, `:393`). `ServerSupervisor.start()` now adopts an existing session even after failed health probes (`ServerSupervisor.ts:429`), then resumes the existing recovery rules. The supervision gap is acceptable, but its duration includes launchd scheduling, Telegram-origin initialization and topic setup (`TelegramLifeline.ts:371`, `:387`). Failed successor boot can prolong it. No new handoff protocol or `AbandonProcessGroup` setting is justified by this incident.

Ranked findings, with the smallest fixes:

1. **High — the competing-stop guarantee still loses to the exit timer.** Safety; spec line 28. `src/lifeline/RestartOrchestrator.ts:185` arms a five-second exit timer before persistence. Persistence can consume two seconds (`:194`); the new stop override then calls `stopServer` (`:204`), whose supervisor waits another three seconds before force-killing (`src/lifeline/ServerSupervisor.ts:526`). The already-armed timer expires first. If Ctrl-C has not stopped the server and the competing request was `bootout`, the lifeline exits with the server still alive and no successor. A controlled probe using the default budgets recorded the first exit while stop completion was still false. **Smallest fix:** clear the persistence hard-exit timer before entering the separately bounded stop phase, and give that phase enough time for the supervisor's graceful wait and bounded force-kill. Test persistence exhausting its budget with a server that ignores Ctrl-C. This is the remaining defect in the round-one competing-request fix, not a request to redesign restart arbitration.

2. **Medium — the new attention key suppresses later queue episodes for the same PR.** Incident gap; spec line 37 promises one item per PR *per stay in the queue*. `src/localVerify/localVerifyWiring.ts:117` emits the fixed key `local-verify:starved:<pr>`, and `src/commands/server.ts:22473` calls `createAttentionItem`. That method returns an existing item unchanged, including a resolved item (`src/messaging/TelegramAdapter.ts:4209`). A PR that leaves the queue, is requested again, and suffers two more interruptions therefore cannot raise a fresh visible alarm while the old item remains stored. A direct probe returned the old resolved item for the new alert. **Smallest fix:** use the existing `upsertAttentionItem` path for starvation signals (`TelegramAdapter.ts:4365`) so a later episode refreshes/reopens the same row; retain `starvedRaised` to limit emission within a queue stay. Test a resolved earlier episode followed by a new one.

3. **Medium — “detach fences every path” remains too strong.** Safety/factual mismatch; spec line 24 and its round-one resolution at line 69. The pending health probe and recovery timeout are now guarded correctly. However, `stop()` and `performGracefulRestart()` check `detached` only on entry (`src/lifeline/ServerSupervisor.ts:515`, `:627`). If either is already waiting when detach happens, it resumes and can still execute `kill-session` at `:530` or `:643`. An inert-command probe confirmed that a pending `stop()` continues into its force-kill branch after detach. This is narrower than the original finding: the earlier Ctrl-C may already have interrupted the verify, so it does not invalidate an otherwise quiet drift handoff. **Smallest fix:** recheck detach after each wait before destructive work, retaining the explicit `evenIfDetached` exception for the orchestrator's winning stop request. Alternatively, explicitly document already-started stops as an exception; do not claim complete fencing while relying on entry guards alone.

4. **Low — the explanation that every keep-server bucket means the server is already current is false.** Factual error; spec line 30, mirrored in `src/lifeline/RestartOrchestrator.ts:40`. `src/core/AutoUpdater.ts:1195` writes the server restart request, then writes the lifeline restart signal at `:1211`; it does not wait for the server to restart. Also, the 426 decision checks differing major/minor versions in either direction (`src/lifeline/versionHandshake.ts:46`), not specifically an older lifeline. **Smallest fix:** explain that these signals request a lifeline code reload and that a separately requested server restart remains the supervisor's responsibility (`src/lifeline/ServerSupervisor.ts:1602`). Do not use “server already current” as a universal safety premise. A focused test with both restart files pending would protect that division of responsibility without another coordination mechanism.

5. **Low — “before other PRs” only applies when a main verify is also ready.** Factual/ordering gap; spec line 41. `src/localVerify/LocalVerifyService.ts:338` returns the first ready PR when no main entry is ready, before it searches for `resumeFirst` at `:342`. A direct call with `[ordinary PR, interrupted PR]` and healthy main selects the ordinary PR. The normal incident path restores the interrupted PR at the front, so this does not block the main fix. **Smallest fix:** move the interrupted-PR selection before the missing-main early return, or narrow the spec to priority over a ready main verify. Add the no-ready-main case to the existing decision tests if retaining the broader promise.

**Over-engineering to cut:** none substantial. Keep detach/adopt, the two optional queue fields, and the existing attention channel. Do not add a separate verifier daemon, transferable locks, lane checkpoints, or another restart-hold RPC. The revised separation between service lifecycle tests and process-adoption evidence is reasonable for this scope; the tests should continue to state exactly what they exercise.
