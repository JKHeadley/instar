## Findings

### SP2-1 — DESIGN, Medium: Provider Lookup Has No Identified Bounded Exact Reader

**Evidence:** Draft line 36 permits an existing provider/log reader's “admitted scanning,” while the final decision-point paragraph says existing resource bounds are inherited. The actual Slack `history` seam (`src/server/mobileSlackRoutes.ts:679–708`) folds its cached tail, merges a 200-message ring, sorts, and slices. Its tail is capped at 5,000 lines/8 MiB (`:611–612,632–642,772`); it has neither a complete-history exact-ID index nor a completeness witness. Telegram's `getTopicHistory` (`src/messaging/TelegramAdapter.ts:4844–4865`) reads/caches a recent tail or falls back to a synchronous file scan. `getTopicHistoryBefore` (`:4907–4947`) loops synchronously over 1 MiB chunks until enough matching rows or the entire retained file ends. A chunk allocation size is not a bound on synchronous work; neither method exposes a scan-admission/yield budget.

**Failure:** An implementer cannot obtain bounded exact lookup merely by calling these seams with a larger limit. Repeating the Telegram scroll-back loop until the selected ID appears can block the server on a large log; treating Slack's tail exhaustion as absence would recreate the old error. Merely returning retryable unavailable forever also does not establish older-provider reply support.

**Resolution:** Name the selected exact provider source/reader and its completeness semantics before implementation. If extending the retained-log reader, specify finite raw byte/row chunks with cancellation/yield and actual shared admission; keep a private continuation/completeness witness and return unavailable when the admitted search is unfinished. If only a current retained exact witness can be supported in this increment, state that limitation and capability/readiness boundary explicitly. Do not invent a global retention scan, widen source eligibility using a resource threshold, or reuse a recent-page miss as a 404. This is the remaining implementation-cost contract for the already selected exact-identity design, not a request for provider URL work.

### SP2-2 — DESIGN, Medium: Indexed Evidence Does Not Bound Verification Or Establish Unique Consistency

**Evidence:** Draft lines 63–69 hash the entire witness into a deterministic evidence ID and require all valid evidence to agree, but only refer to “existing admission budgets.” Hash deduplication bounds identical replay, not distinct witness variants for one base. Current `AppConversationStore.appendWithEmit`/`ingestReplicated`/`write` (`src/core/AppConversationStore.ts:677–745`) expose append/replication behavior, not a budgeted quote-candidate verifier. Current `verifyRecordedOrigin` performs real ledger/history/signature work (`src/core/AppRecordSignatures.ts:260–338`). `MobileChatRequests.reserve` caps live per-device operations (`src/core/MobileChatRequests.ts:96–110`); it does not bound read-time evidence candidates or signature checks. The sibling App-link concurrent context-scan admission does not automatically govern a new quote-evidence projection loop.

**Failure:** One quoted base can accumulate distinct unknown/invalid/conflicting candidates. An indexed query followed by synchronous verification of all candidates is still unbounded per request and becomes multiplicative across a history page. Conversely, finding one valid reference and stopping early can present it as unique before a later valid conflicting candidate is checked. A request-local map saves repeated checks for the same base but does not bound distinct work.

**Resolution:** Specify the actual derived index key for base-scoped candidates, a captured candidate frontier/version, bounded materialized candidate windows, yielding/cancellation and the real admission owner for verification. A projection may become available only after the relevant frozen candidate set has been conclusively checked for consistency; unfinished work remains unavailable. Recheck that candidate evidence and current reader authority did not change across yields. Preserve all evidence and eligibility: do not arbitrarily keep the first N variants or demote unexamined candidates into invalid proof. Bind large-candidate and late-conflict fixtures to this rule. The resource policy must be explicit and contested rather than asserted to exist in the current operation ledger.

### SP2-3 — PRECISION, Medium: Refresh The Same Visible Page, Not Its Next-Page Cursor

**Evidence:** Draft line 89 says to refetch currently visible pages “using existing cursors.” Existing history cursors are exclusive continuation boundaries; for example the App history store's `browseMessages` (`src/core/AppConversationStore.ts:1353–1360`) uses the passed `before` boundary to load earlier rows. The sibling exact-link client similarly distinguishes its requested cursor from its resulting next cursor. The returned next cursor does not identify the page currently displayed.

**Failure:** On focus/reopen, refreshing each displayed page using its returned next cursor fetches a different, earlier page. That can leave a revoked quote's displayed row unrevalidated, or turn a quote refresh into an unnecessary cascading history scan. The intended clear-before-revalidate rule is correct, but this phrase is insufficient to implement the same-page refresh safely.

**Resolution:** Retain each displayed page's original request boundary (or its exact visible row identities under an authorized projection mechanism), invalidate old quote projections immediately, and refresh that same coverage under the current reader. A changed page or unfinished refresh remains pending/unavailable rather than certifying cached quote data. Keep ordinary paging and scroll position independent. This clarifies D12; it does not require a new cache or unbounded history reload.

Treat it as **PRECISION, Medium**: name the actual normal per-host/shared-resource admission and duplicate-run ownership rather than asserting every independent machine must be idle. That is honest scope accounting, not evidence that the broader multi-machine commitment standard is satisfied. A claim of fleet durability still needs its actual retained/pending/loss evidence or an explicitly scoped prerequisite/disposition. Do not resolve this signal by adding an unmeasured exhaustive witness search or a second quote-recovery service. Broader custody disposition belongs to the integration/security review.
- **Paraphrased stop and maturation flags:** These require their respective semantic-execution and release-lifecycle owners. They do not justify delaying the existing exact stop behind a provider scan or treating a throughput test as maturation proof. No performance-only pass is asserted for them.
- **Weak parent fit:** Exact identity and bounded responsive access support the selected outcome. The fit signal is not a substitute for the actual native menu, cache, and navigation evidence; that evidence remains a separate dependency.
