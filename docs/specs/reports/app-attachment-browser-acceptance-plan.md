# App chat attachment browser acceptance plan

This is a verification plan for the [draft attachment browser](../app-attachment-browse.md). The feature stays off by default. These cases describe work to perform before enabling it. The existing signed HTTP and AgentServer lifecycle results cover server wiring and verified file delivery, and browser rendering and playback still need their own evidence.

## Browser-facing fixtures

- Extend [the Conversations page fixture](../../../tests/unit/console-chats-page.test.ts) with the same active browser key, fake IndexedDB, per-page cleanup, and `verifySigned` assertions used for source-message navigation. Record the fetch signal, cache mode, method, signed URL and body. Add independently controllable JSON and binary response promises. In race tests deliberately resolve a stale mock even after its signal aborts. Spy on blob URL creation and cleanup, and on link clicks for downloads.
- Use [the chat model tests](../../../tests/unit/console-chats-model.test.ts) for strict response validation. Exercise browser state and interactions through the real page module, rather than substituting a model for the sheet.
- Use [production browser enrollment](../../../tests/e2e/dashboard-conversations-browser-alive.test.ts) and [production media upload](../../../tests/e2e/mobile-native-media-alive.test.ts) as the AgentServer fixture for the real-browser check. Serve the actual dashboard assets to a disposable Chrome profile at the exact configured `127.0.0.1:<port>`, bound on loopback with no forwarding headers. Use the real PIN enrollment and browser key storage with disposable credentials. A simulated Host header alone cannot prove the loopback binding.

## Focused browser tests

| Case | Expected evidence |
| --- | --- |
| Open the sheet on an App chat and choose a kind | One signed GET to `/mobile/chat/app/<chat>/attachments?kind=<kind>`. Older adds only the opaque cursor. Requests are uncached. Opening the sheet, listing and scrolling fetch no file bytes. No search, pool, hash-only media or peer request follows from a browse or open action. |
| Validate the response before render | Accept the expected version, local scope, matching kind, coverage, continuation and complete descriptor shape. Reject the whole page on wrong version or kind, an invalid cursor value or descriptor, or mixed valid and invalid rows. Render hostile-looking filename text literally and preserve a full accessible label for a long filename. |
| Walk sparse history within the foreground read budget | Three empty pages with distinct continuations stop with Older still available. A populated page stops the walk immediately. Double-clicking Older starts one read sequence. Each request is admitted against the existing browser read budget before starting. When the budget is exhausted, stop without skipping a continuation. Changing kind starts at the newest page. Exhaustion after any incomplete page keeps the incomplete notice. |
| Ignore superseded page or content responses | Hold JSON and binary bodies independently. Close with Escape, select a new kind, accept Older, lose foreground visibility, navigate to another chat, replace the sheet, and dispose the page while work is pending. Assert abort and no stale rows, playback, blob URLs or download clicks after late completion. For two attachment selections, complete their requests in reverse order. Only the latest selection may publish. Repeating Open for the same pending selection coalesces. Release each sheet-owned blob URL once. |
| Open a selected attachment | Only a deliberate Open sends a signed GET to `/mobile/chat/app/<chat>/attachments/<attachmentId>/content`. Confirm the exact ID even if another occurrence has the same bytes. A file shows an explicit Save action and stays unsaved until that action. An image renders only after Open. Audio and video controls render without autoplay. Non-viewable types use a download presentation without interpreting markup. |
| Handle unavailable or superseded uploads | A content `404 attachment-unavailable` marks that selected file unavailable while preserving the other results. A second file can still open. A content `429 attachment-open-busy` offers a manual Retry without starting another request. An invalid cursor offers a restart at the newest page. |
| Handle legacy servers and lost access | A browse `404`, legacy `403 device-not-allowed`, or unsupported response stays local and unavailable. Lost signed admission, an unknown conversation or media-off clears private results and playback. A signed `401` goes through the existing device-status handling and cannot silently retry an abandoned sheet action. |
| Preserve the current conversation | Set an unsent draft, select real File objects and scroll away from the bottom. Open the sheet, change kind, page, open an attachment and close it. The same chat retains draft text, selected files, rendered history and scroll position. The dialog has an accessible name, usable keyboard controls and Escape dismissal. |

The implementation seam is [the current chat view lifecycle](../../../dashboard/console/chats.js) and [the shared sheet](../../../dashboard/console/ui.js). Use [the browser device client](../../../dashboard/console/browser-device.js) for signed JSON calls or signed binary fetches with abort signals, and check the current sheet and selection after each asynchronous boundary. The ordinary attachment tile fetches images automatically, caches by content hash, retries existing download routes and triggers a Save click for files. It should stay on the ordinary history path. Reuse the [allowlisted blob types](../../../dashboard/console/chats-model.js) for the explicit-open presentation. Keep the sheet's requests and blob URL ownership separate. The stock chat JSON wrapper can retry after a `401`, and the existing `spent()` only accounts for a read. Use the device-status handling and budget check without letting inherited retry or accounting behavior start a new read after the sheet has become stale.

## Real browser acceptance

1. Start one disposable AgentServer. Verify the default-off response, then opt in only in the disposable fixture. Enroll a browser through the real dashboard and confirm the resulting device can open the signed App chat. Keep a second chat available for navigation.
2. Seed the first chat with at least 150 newer nonmatching messages and an older, valid captionless photo. Keep the photo out of the ordinary latest history page so an ordinary tile fetch cannot be mistaken for a sheet request. Also include a listed attachment with unavailable bytes, a separate openable attachment, and a long filename. Use valid image and browser-supported audio or video fixtures.
3. Set a draft and pick a file. On desktop and a phone-sized viewport of about 390 px, open the sheet and choose Photos. Observe three empty pages, a retained Older action, then the older photo. Prove no attachment bytes were fetched before Open. Open it and check image decode with nonzero natural width. Check a separate audio or video item's metadata and playback after an explicit user action, and confirm there was no autoplay. The unavailable result must leave its neighbor usable.
4. Hold one signed request using a test-only gate in the disposable fixture. Navigate to the other chat and release it after navigation. Confirm cancellation and absence of an old repaint. Reopen the first chat, prove the ordinary sheet-close path preserved draft, selected files and scroll, then use the fixture's revocation path to verify private results clear. Check keyboard access, Escape, filename wrapping and phone-width layout.
5. Record the selected browser cases, sanitized request paths and status codes, cancellation and blob lifecycle outcomes, and screenshots of the relevant desktop and phone states. Exclude auth material, raw cursor values and real chat data. Keep the browser result distinct from the server load measurements and full verification required by the draft.

## Disposable Chrome transport result

One case passed in the normal enforcing E2E lane on November 24. Real Chrome used the dashboard PIN to enroll a browser device against a disposable loopback AgentServer with an independent coordinator. The fixture uploaded a captionless PNG, verified the signed browse request returned 404 with discovery off, then enabled discovery in the disposable configuration. Signed browse and explicit exact-content open each returned 200. All 658 bytes matched the uploaded SHA-256 and Chrome decoded the image as 16 by 16 pixels. The fixture revoked the blob URL. The browser made two browse requests and one exact-content request.

Two earlier attempts stopped at fixture setup because browser enrollment lacked the required machine identity. The passing run used the real disposable coordinator. The run exercised browser transport and decoding through a local harness. Attachment-sheet rendering and the UI open gesture still require acceptance testing once a browser consumer exists. The running product configuration stays off.

Local evidence is in `.instar/state/build/attachment-browser-transport-coordinator-20261124.log`. The 19-path staged implementation patch still has SHA-256 `e0686d999222dc39d1f64b6d9a92f736309b03941656af611c9ffb9a614b1a93`.
