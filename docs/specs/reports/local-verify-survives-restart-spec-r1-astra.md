# spec review round 1 — GPT-6 Astra (codex CLI), 2026-10-25

Verdict: **ready with changes**. The core fix is right: restarting the lifeline does not require stopping a healthy server. The branch already implements A–C, but the survival and alert guarantees need the corrections below.

The process handoff is sound on the normal macOS launchd path. `ServerSupervisor.ts:1176` starts a detached tmux session; the tmux daemon and pane processes are independent of the exiting lifeline's process group. Apple's [launchd manual](https://github.com/apple-oss-distributions/launchd/blob/main/man/launchd.plist.5) describes cleanup of the job's process group, and [tmux's implementation](https://github.com/tmux/tmux/blob/master/proc.c) daemonizes its server. This supports the spec's process-group reasoning; it is not a live launchd handoff test. No new `AbandonProcessGroup` setting is needed. Linux needs its separate `KillMode=process` protection, which this branch already generates (`src/commands/setup.ts:1996`).

Adoption retains the same server process, listener, and server-owned state; there is no port or server-lock transfer. Lifeline cleanup removes only its own registry entry and PID-owned lock (`src/lifeline/TelegramLifeline.ts:106`, `:564`), and the successor acquires the lifeline lock before starting supervision (`:339`). Normal launchd replacement starts after the old process exits. The supervision gap is an acceptable tradeoff, but is not guaranteed to be ten seconds: launchd has a throttle, and the successor awaits Telegram-origin initialization and topic setup before `supervisor.start()` (`src/commands/setup.ts:1780`; `src/lifeline/TelegramLifeline.ts:371`, `:387`, `:393`). If successor boot fails, the server continues without that supervisor until boot succeeds. Healthy adoption also resets the startup grace (`src/lifeline/ServerSupervisor.ts:429`, `:1355`). Document those limits rather than introducing a new handoff protocol.

Ranked findings, with the smallest fixes:

1. **High — the successor can still kill the verify during adoption.** `start()` falls through to `spawnServer()` when its three health probes fail (`src/lifeline/ServerSupervisor.ts:421`, `:458`, `:1473`). Each probe allows eight seconds, with two 1.5-second delays: about 27 seconds of timeouts. `spawnServer()` then kills the existing session (`:1168`). A busy server running the full suite can therefore survive the old lifeline's exit and immediately be killed by the new one. This startup path bypasses the normal live-process, CPU-starvation and in-flight-operation tolerances (`:1967`). The spec's “unhealthy → fresh one” sentence conceals a destructive decision. **Smallest fix:** when the session still exists but adoption probes fail, begin bounded health supervision using the existing recovery rules; respawn immediately only when the session is gone. Test a temporarily unresponsive surviving server and a genuinely dead one.

2. **High — resuming first can suppress the new interruption alarm completely.** `checkStarved()` inspects only queued PRs (`src/localVerify/LocalVerifyService.ts:1053`). `enqueueMain()` calls `pump()` immediately (`:821`), whereas starvation is checked only by `tick()` (`:1018`). Thus, after boot, observing main can start the twice-interrupted PR before the first tick. Subsequent ticks never inspect that running entry. I reproduced this: two persisted interruptions, main observed before tick, PR running, zero starvation callbacks. **Smallest fix:** check the interruption threshold before any restored entry is started, or include the active PR in starvation checks. Add the boot → main observation → tick ordering to the test; the current interruption test calls tick first (`tests/unit/localVerify/LocalVerifyService.test.ts:583`).

3. **Medium — a second unclean exit drops the entry before it can raise the alarm.** Restoration increments interruptions and then applies the existing error-retry limit (`src/localVerify/LocalVerifyService.ts:716`). That limit is one retry (`src/localVerify/policy.ts:60`); on the second crash, `restoreQueue()` writes an error record and skips queue insertion (`src/localVerify/LocalVerifyService.ts:723`). Consequently, neither “resume first” nor the two-interruption signal happens. I reproduced an empty queue, one error record and zero starvation callbacks. **Smallest fix:** emit the interruption signal before terminal retry handling, and explicitly document that unclean exits retain the existing retry ceiling. There is no need to introduce unlimited crash retries.

4. **Medium — the justification for excluding other lifeline-only restarts is factually wrong.** The spec says version-skew and planned-upgrade restarts follow a server update that already honored the hold. The coordinated signal also comes from migration and server-side incompatibility handling (`src/lifeline/TelegramLifeline.ts:1883`), including the ingress-secret upgrade request (`src/server/routes.ts:3397`). These requests reach `initiateRestart()` without `keepServer` (`src/lifeline/TelegramLifeline.ts:869`, `:1917`). Even after a properly held update, the replacement server can have started new work before a later lifeline restart kills it. The earlier hold does not protect that new run. **Smallest fix for this incident-sized PR:** remove the claimed protection and explicitly scope survival to drift auto-promote. For broader coverage, make the identified version-only catch-up paths preserve the server too; keep deliberate server recovery separate.

5. **Medium — quiescing does not immediately remove the old supervisor's ability to kill.** `quiesceEverything()` awaits Telegram cleanup before reaching `detach()` (`src/lifeline/TelegramLifeline.ts:553`, `:570`). Meanwhile, a health probe or previously scheduled restart can still finish. `detach()` clears the repeating checks, but does not cancel an active probe or the restart timeout (`src/lifeline/ServerSupervisor.ts:486`, `:1431`, `:2248`). The orchestrator's one-second quiesce deadline can even expire before detach is reached (`src/lifeline/RestartOrchestrator.ts:139`). The normal immediate exit makes this a narrow window, not an inevitable failure. **Smallest fix:** detach synchronously before the first cleanup await for a keep-server restart, and use one stopped/generation guard to prevent outstanding supervisor callbacks from acting afterward. Test a pending health probe and a pending restart timer.

6. **Medium — the claimed lifecycle evidence is missing, and a focused test is red.** The spec says the E2E test stops a run, restores it, interrupts it again and delivers the signal. The actual addition directly invokes `seams.onStarved` before boot (`tests/e2e/local-verify-lifecycle.test.ts:97`, `:109`); it proves callback wiring only. The lifeline tests inspect source strings and call detach on a supervisor without a running session (`tests/unit/lifeline/drift-restart-keeps-server.test.ts:30`, `:48`). They do not prove process survival or successor adoption. The four named unit files produced **144 passes and one assertion failure** at `tests/unit/localVerify/LocalVerifyService.test.ts:343`: the expected payload omits `reason: 'waited'` and `interruptions: 0`. Vitest also reported a separate sandbox denial writing its shared results cache. **Smallest fix:** update that expectation, describe the wiring test honestly, and add one isolated lifecycle test that checks unchanged server/verify PIDs through lifeline exit and successor adoption. Exercise the two alert-loss cases above without running a 45-minute suite.

The persistence changes themselves are appropriately small: interrupted attempts remain counted, both optional fields round-trip through `queue.json`, and `resumeFirst` is consumed on start (`src/localVerify/LocalVerifyService.ts:1033`, `:1285`, `:1509`, `:1565`). The existing attention hook is the right delivery path (`src/localVerify/localVerifyWiring.ts:121`; `src/commands/server.ts:22472`), though delivery remains best effort.

Over-engineering to cut: none substantial in A–C. Keep the optional restart flag, detach operation, two persisted fields and existing attention channel. Do not add checkpointed test lanes, a new worker daemon, transferred server locks, or another restart-hold RPC for this incident. Correct the few lifecycle boundaries and the overstated guarantees.

DONE.
