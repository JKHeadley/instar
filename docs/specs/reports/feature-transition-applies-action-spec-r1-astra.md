# spec review round 1 — GPT-6 Astra (codex CLI), 2026-10-25

**Verdict: not ready.** The missing action call is real, and fixing the tunnel body and mounting file-viewer settings while disabled are sensible. But two actions target settings the runtime does not use, and the proposed “honest” state still claims more than the evidence supports.

Reviewed the spec and ELI16 against commit `8f6fdb3126fc795abfcdabd9fb903f65e9715c01`. File:line references below refer to that baseline; implementation edits appeared in the workspace during review. This is a source review, not a runtime test.

1. **High — Sending the actions still leaves important switches ineffective.** The spec says every action changes the key its feature reads. Threadline writes `threadline.enabled` (`src/core/FeatureDefinitions.ts:23`), but startup passes `threadline.relayEnabled` (`src/commands/server.ts:18778`); the relay also considers an environment override and standby status (`src/threadline/ThreadlineBootstrap.ts:385`). Autonomous Evolution writes `evolution.autoImplement` (`src/core/FeatureDefinitions.ts:196`), while its constructor uses the resolved `evolutionApprovalMode` (`src/commands/server.ts:17638`), derived from `evolution.approvalMode` or profile defaults (`src/core/AutonomyProfileManager.ts:140`). These are existing definition bugs that become central once the actions execute. **Smallest fix:** align the action and displayed config binding with the actual consumer for each feature. Where that requires a separate autonomy decision, explicitly mark the switch unsupported until wired. Test the runtime consumer after restart, not just whether JSON changed.

2. **High — “On and running” is unsupported, and “Off” can also be false.** A boot flag is not successful initialization: response review can be configured on but unavailable without an IntelligenceProvider (`src/commands/server.ts:19785`). Conversely, publishing starts unless explicitly disabled (`src/commands/server.ts:12988`), while the registry treats a missing config value as false (`src/core/FeatureRegistry.ts:990`). The proposed table can therefore call a working default-on feature “Off.” Returning `atBoot: configured` when bootstrap never ran invents boot evidence. **Smallest fix:** say “Configured on; runtime not verified,” use unknown for a missing boot snapshot, and resolve defaults consistently with the consumer. Keep restart advice qualified. No new liveness framework is needed. Change the ELI16 wording too.

3. **High — The operator consent path needs an actual dashboard flow.** The proof is legitimate: PIN unlock issues a separate token (`src/server/AgentServer.ts:1299`), and the verifier is wired at `:4601`. But it expires after 15 minutes (`src/server/DashboardOperatorSessionStore.ts:18`), stays only in browser memory (`dashboard/index.html:4444`), and is absent when the saved API token restores a session (`:4534`). “Send it when available” falls back to the same graph/consent errors this fix promises to remove. Also, the catalog switch stops propagation and never opens the disclosure (`:9145`); disclosures live in the detail view (`:9220`). A prior PIN unlock does not establish that the person saw the data implications being stored as explicit consent. **Smallest fix:** on high-tier enable, show the existing disclosure and an explicit Enable control; obtain fresh PIN proof when missing or expired. Have invalid supplied proof produce a clear re-unlock response. Keep Bearer-only discovery behavior separate. Topic-profile is an inaccurate precedent for mandatory proof: it explicitly uses the token only for attribution (`src/server/routes.ts:11389`).

4. **High — Concurrent switches and retries can apply an obsolete choice.** Registry transitions are synchronous today (`src/core/FeatureRegistry.ts:544`; `src/server/routes.ts:40080`). The proposal inserts an asynchronous HTTP call after recording the choice, with no ordering rule. An earlier disable can finish after a later enable and overwrite both config and `lastApply`. Telemetry disable already awaits remote deletion before changing local state (`src/server/routes.ts:32389`, `:32429`), so this is a concrete case. A client timeout also does not cancel the target handler or prove that nothing changed. **Smallest fix:** serialize the complete transition/apply/result sequence per feature, including retries; read retry state inside that sequence. Describe timeout as an unconfirmed outcome and re-read configuration before presenting or retrying it. Test overlapping enable/disable with a delayed target.

5. **Medium — The spec reverses bootstrap’s config precedence.** Section 2.3 says disk is merged over runtime “as bootstrap does.” Bootstrap actually uses `{ ...rawConfig, ...config }`, so runtime wins (`src/core/FeatureRegistry.ts:950`). This distinction matters: telemetry writes disk without updating runtime config (`src/server/routes.ts:32360`, `:32442`). Reusing bootstrap’s merge for current state would conceal a successful telemetry change. **Smallest fix:** explicitly distinguish the startup snapshot from the current saved setting: use disk precedence for the latter, with a documented fallback, and leave the boot snapshot immutable. Test with conflicting disk/runtime telemetry values. Correct the statement rather than silently changing bootstrap semantics.

6. **Medium — Failed choices disappear from the promised explanation.** After a refused enable, bootstrap clears the enabled row (`src/core/FeatureRegistry.ts:973`). The proposed table then says plain “Off,” even though section 2.6 promises the retained result will explain why the switch reset. A refused disable gets only “The setting is on, but the switch says off,” with no failure reason. The dashboard currently flattens only definition and state, discarding a sibling `effective` field (`dashboard/index.html:9094`). **Smallest fix:** retain and render the last failed attempt independently of the current status, for both directions and after restart; label it as a past attempt. Carry `effective` through the flattening step. No second desired-state store is necessary.

7. **Medium — Narrow the security claims to the boundaries that actually exist.** For the current static actions, I found no new general Bearer privilege from using the server’s token: feature requests already pass the same Bearer middleware (`src/server/AgentServer.ts:1397`; `src/server/middleware.ts:287`), and the config allowlist/fence still run (`src/server/routes.ts:2213`, `:32143`). Telemetry’s “human-gated” comment is not a backend proof check (`:32343`). However, mounting file settings while disabled newly exposes those handlers to Bearer callers; `/apply` permits replay without the transition’s consent/challenge checks; and caller-chosen `userId: 'default'` is not operator identity (`:40079`). Thus “one user’s switch never changes the agent for everyone” is not an authorization guarantee. The claimed standby protection is also absent: `PATCH /config` never calls the route-specific admission helper (`:2691`, `:32094`). **Smallest fix:** document these limits and the newly reachable file-settings operations; keep operator bypass strictly behind the real verifier. Pin the privileged HTTP client to the same server and the four exact method/path pairs, reject redirects, and never accept caller-supplied targets. This is containment, not a claim of an existing arbitrary-URL exploit. Remove the standby-refusal claim unless an explicit check is added; machine-local writes need not become a new cross-machine policy project.

8. **Low — Cut the extra retry surface and duplicate timestamp.** Section 2.4 already lets a verified operator set either state from *any* state. That includes setting the same state again, so section 2.1’s claim that a separate `/apply` route is the only recovery path is false. It adds another authorization and ordering path for little benefit. `last_apply_at` also duplicates `lastApply.at` without any proposed query needing an indexed timestamp. **Smallest fix:** let the existing operator command retry the same desired state under the same checks and serialization; keep one nullable JSON result column. Retain the small HTTP adapter if it avoids duplicating target validation. Skip a generic action framework, durable retry worker, or per-feature liveness engine for this fix.

DONE.
