# Review round 1 — GPT-6 Astra (codex CLI), 2026-10-25

**Verdict: not ready.** The diagnosis is sound, and explicit condition keys plus verified cause-based closes are the right 80/20 fix. But the proposed defaults can remove unresolved operator work, while the cleanup does not reliably reconcile the existing pile. These are design findings against the checked-out code; the fleet counts were not independently verified. Both documents were reviewed.

1. **Critical — two proposed “cause cleared” signals do not prove recovery (§3.3).** `SubscriptionReloginStore.ts:81` includes `failed`, `refused`, and `cancelled` in TERMINAL. Ending an attempt or admitting another attempt does not establish that the account works. `src/core/SubscriptionReloginStore.ts:518` also queues a terminal notification; `src/commands/server.ts:15530`–`15539` currently creates an attention item even for success. Closing during the transition can therefore be followed by a fresh success item. Separately, `src/messaging/telegram-origin/OriginStoreBackend.ts:495` returns only held forwards whose retry is **due now**, with a default limit of ten and other eligibility filters. An empty result can mean backoff, not delivery. This is a factual error in the proposed held-reply clear signal. Expired operations can mean definite loss or uncertain delivery (`src/messaging/telegram-origin/OriginForwardToHolder.ts:453`–`466`); reporting that loss does not fix it.

   **Smallest fix:** close sign-in conditions only on verified success or verified healthy account×machine state; update the existing item for failure or a new attempt. Route successful terminal notifications into that close operation. For held replies, query all unresolved operations for the topic, independently of retry scheduling and page limits. Keep a separate actionable loss/uncertainty item when necessary; do not mark it cause-cleared merely because reporting succeeded. Test failed repair and “held but next retry is tomorrow” as cases that must stay open.

2. **Critical — the 14/30-day rule can erase the very requests the operator must see (§3.4).** It includes ACKNOWLEDGED and IN_PROGRESS, unanswered approvals, and HIGH/URGENT failures. Silence is not evidence of completion. Some producers deliberately raise only once: `src/core/AttentionConditionStore.ts:80` returns `shouldRaise:false` for an active condition, and `src/core/StaleOwnerReleaseEngine.ts:778` obeys it. That engine explicitly asks for a manual decision when topics are stranded (`:784`–`787`). Such an item can expire while the cause remains active and never be raised again. The classifier also references `source==='agent'`, but `AttentionItem` has no `source` field (`src/messaging/TelegramAdapter.ts:341`); HTTP `source` is normalized into `sourceContext` (`src/server/routes.ts:20172`, `:20262`). Ordinary agent questions can therefore fall into the 14-day bucket. Existing `needsUser` (`TelegramAdapter.ts:386`) is ignored. Security detection by two text fields cannot guarantee protection for legacy mislabelled rows.

   **Smallest fix:** expire only explicitly identified disposable notice types. Keep unknown items, human decisions, `needsUser`, security/sticky items, and known-active conditions open until positive evidence or operator disposition. Enforce sticky protection in the common automatic-close path, not just the age sweep. Review legacy unknowns during cleanup. Correct the companion at line 19: this design actually sets `status:DONE`; a resolution string does not keep an item in an open-only view. Remove the promise that the next observation always restores it.

3. **High — the derived key can merge different losses or subjects, and prefix clearing can close the wrong episode (§§3.1–3.2).** UUIDs and long hexadecimal strings are not inherently volatile: they can identify the thing needing action. Concrete example: expired held-reply IDs deliberately contain an operation ID (`src/messaging/telegram-origin/OriginForwardToHolder.ts:455`); operation IDs can be UUIDs (`src/messaging/telegram-origin/TelegramOriginService.ts:351`). Two lost replies to the same topic have the same title/category/source (`src/commands/server.ts:27599`) and collapse when their UUIDs are blanked. Resolving one alias can then close the other loss. Preserving topic digits does not prevent this. Also, wiring an exact condition-store item ID as `idPrefix` is unsafe: IDs end in `:ep-N` (`src/core/AttentionConditionStore.ts:96`), so `:ep-1` also prefixes `:ep-10`.

   **Smallest fix:** cut the universal skeleton/title normalizer. Use explicit producer-owned condition keys for the high-volume sources, and exact IDs elsewhere. Keep operation identities when separate losses require separate action. Add an exact-ID clear option for condition-store callbacks; reserve prefix matching for audited, delimiter-bounded legacy migration rules. Test two operation UUIDs on one topic and episodes 1 versus 10.

4. **High — “bump and return” hides changing instructions, and changing only create leaves a second lifecycle (§3.1).** With the proposed account×machine key, “approve repair” and “tap the phone prompt now” hit the same open row. Rule 1 only bumps counters, so it preserves the old body and priority and sends no new instruction. Those are materially different actions today (`src/commands/server.ts:15518`–`15538`). Held aggregates likewise need their topic list refreshed. Meanwhile, `upsertAttentionItem` already refreshes and reopens independently (`src/messaging/TelegramAdapter.ts:4365`–`4379`), including resetting ACKNOWLEDGED/IN_PROGRESS to OPEN. `createOrReopenAgentHealthAttentionItem` is another independent writer (`:4393`). They would bypass rules implemented only in create. HTTP creation also currently drops the proposed `conditionKey` and `sticky` fields (`src/server/routes.ts:20255`–`20265`).

   **Smallest fix:** put explicit-key lookup, body/priority refresh, and closure rules in one helper used by these writers. Preserve operator progress on a mere repeat; surface a changed required action or increased urgency using the existing hub routing/throttle. Pass and validate the lifecycle fields at the HTTP boundary. Persist alias mappings and rebuild lookup indexes on load if aliases are retained. Test approval→phone-tap, not just create-twice-with-identical-text.

5. **High — reopening in place needs episode protection, or an old close can hide a new failure (§3.1).** A repeated delivery is not proof of a new episode. Blanket reopening makes retries resurrect completed work; conversely, an old alias or delayed acknowledgement can mark the reopened row done. Remote acknowledgements are durably queued using only item ID, machine, and status (`src/server/routes.ts:20637`). The receiving guard checks HIGH/URGENT priority, not episode identity (`:20559`–`20577`), so an old acknowledgement can close a new NORMAL episode. The 30-day WONT_DO exception only checks an exact ID: a timestamped successor can bypass it immediately because condition lookup considers only OPEN rows. The current status updater also retains old resolution text unless replaced (`src/messaging/TelegramAdapter.ts:4816`).

   **Smallest fix:** keep current episode IDs for producers that have not explicitly opted into stable-row recurrence. For stable rows, persist a small episode generation and require it on producer clears and queued remote acknowledgements; reject stale ones. Scope WONT_DO to the condition and current episode, independent of delivery ID. Reset old closure metadata on a genuine recurrence. Do not redirect an old episode's clear into the current one merely because it is an alias.

6. **High — the one-time sweep and restart behavior do not deliver the promised cleanup (§§3.2, 3.6–3.7).** The specified sweep expires old rows; it does not backfill keys, merge existing duplicates, or check current causes. Newly added transition hooks will not replay last week's terminal repairs or previously cleared conditions. `AttentionConditionStore.clear`/`clearSubject` skip already-inactive records (`src/core/AttentionConditionStore.ts:117`, `:128`); a crash after persisting the inactive record but before closing attention leaves the stores inconsistent. Existing attention loading simply restores rows (`src/messaging/TelegramAdapter.ts:4902`), with no reconciliation. Also, an enabled destructive pass two minutes after boot can run before the promised dry-run review and security-item check.

   **Smallest fix:** make one idempotent reconciliation pass serve startup and manual cleanup. For the selected producers, map known legacy IDs to explicit conditions, compare against authoritative current state, and close verified-cleared or redundant rows while retaining one current actionable row. Reconcile already-inactive condition records too; callbacks alone are insufficient. Persist keys/aliases with the rows. Keep automatic expiry dry until the initial reviewed pass finishes on each machine, then record raw local before/after counts and unresolved exceptions for all four machines. Unknown or unavailable producer state must remain unresolved. Test a restart between cause persistence and attention closure, plus a second cleanup run.

7. **High — the existing pool coalesce is not a safe cross-machine solution, and holder-only escalation can silence an outage (§3.3).** P17 uses only `sourceContext` when present (`src/server/routes.ts:20371`), discards subsequent bodies/IDs, and retains only their machine IDs (`:20434`–`20442`). It even applies to multiple local rows. Distinct NORMAL problems from one producer can disappear behind one row; without a status filter, a closed local row can mask an open remote row. HIGH/URGENT bypass coalescing (`:20430`), so the claimed view-level dedupe does not cover those piles. Separately, stale-owner ambiguity intentionally escalates on **any** quorum member (`src/core/StaleOwnerReleaseEngine.ts:770`) because topics are stranded while the owner's state cannot be proved. Requiring the serving lease holder to raise can suppress every witness when that holder is unavailable.

   **Smallest fix:** retain independent local escalation for ambiguous ownership. For pooled display, group only by a verified condition identity with the intended machine scope, preserving each actionable member's ID, machine, and status. Unknown identities stay separate. No cross-machine creation lock is needed. Test two accounts from one producer, a closed-local/open-remote pair, and an unavailable lease holder.

8. **Medium — cut the commitment/reminder expansion from this repair; its factual premises and wiring also need correction (§3.5).** The existing age predicate checks `owner==='agent'` but does not exclude `blockedOn:'user-input'` or `'user-authorization'` (`src/monitoring/CommitmentTracker.ts:1879`–`1890`), so the claim that all operator-blocked commitments escape it is false. Adding a second branch after the old one would still let those agent-owned rows use the old creation-age rule. The sweep supplies one fixed “presumed completed” reason to every eligible row (`:1808`–`1812`), and its default is dry-run (`:1871`), so changing eligibility alone does not implement the promised explanation or live expiry. Heartbeats are bookkeeping (`:2326`–`2335`), not proof the operator touched the request. A seven-day re-ask event, once-only tracking, new settings, and reminder delivery expand scope without fixing the attention pile.

   **Smallest fix:** defer commitment expiry and re-asks. If retained, handle operator-wait eligibility before the old branch, use an explicit meaningful wait-start timestamp, return a per-row disposition/reason, and make effective dry-run behavior explicit. Do not silently expire unanswered authorization just to reduce a count. For this release, keep explicit producer keys, verified closes, existing hub routing, and one auditable reconciliation/dry-run command. Cut the guessed-key engine, generic predicate-clearing surface, and extra lifecycle status API unless the cleanup actually needs them.

DONE.
