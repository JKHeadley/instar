# spec review round 2 — GPT-6 Astra (codex CLI), 2026-10-25

**Verdict: ready with changes.** The core approach is proportionate: send the existing action through its existing validation, retain one result, and distinguish saved settings from runtime evidence. The revision resolves most round-one findings. The remaining problems below are bounded fixes, but the claims about honest state and reliable operator switching are not yet met.

Reviewed the current spec, ELI16, earlier completed reports, and current working-tree code, including the implementation edits over `8f6fdb3126fc795abfcdabd9fb903f65e9715c01`. References below are to that working tree. Validation was source inspection plus small isolated probes of the dashboard functions and HTTP applier; I did not run the full application or test suite.

1. **High — Evolution can still be shown as off while configured to act autonomously.** The prerequisite rule in spec §2.3 is factually wrong for this consumer. `EvolutionManager` is constructed regardless of `evolution.enabled` (`src/commands/server.ts:13075`), and autonomous evolution is enabled from the resolved approval mode alone (`src/commands/server.ts:17638`). With `{ evolution: { enabled: false, approvalMode: 'autonomous' } }`, the proposed prerequisite calculation nevertheless changes `configured` to false and says Evolution System is off (`src/core/FeatureRegistry.ts:1114`). Separately, an absent approval-mode key counts as false (`src/core/FeatureRegistry.ts:1140`), even though the autonomous profile supplies `'autonomous'` (`src/core/AutonomyProfileManager.ts:71`, `:140`). A footnote about that default does not correct the boolean or boot snapshot. **Smallest fix:** remove this false prerequisite from the display calculation and resolve the approval-mode fallback using the existing autonomy manager's profile. For Evolution System itself, mark the switch unsupported/read-only until its consumer honors it; a working-looking switch over an ignored key preserves the original bug. Cover both concrete configurations above. This corrects the round-one prerequisite recommendation rather than accepting it blindly.

2. **High — The dashboard hides exactly the explanations the revision promises to preserve.** Spec §2.3 retains failures and `honestyNote` in every summary, but §2.4 only displays summaries outside plain `on`/`off`. The implementation does exactly that (`dashboard/index.html:9188`). After a refused enable and restart, `effective` can contain “Off. The last attempt … was refused,” yet the card renders no explanation. The always-running evolution caveat and unknown-runtime caveats also disappear under plain statuses. The detail panel does not render `effective` at all (`dashboard/index.html:9285`). An isolated call to `featEffectiveLine` confirmed the retained refusal produces an empty string. **Smallest fix:** always render `effective.summary` on the card and detail panel. This also makes keeping the durable result worthwhile. Round one's storage fix is good; its display fix is incomplete.

3. **Medium — An expired operator proof still strands the switch.** Spec §2.4 treats expiry as if the browser's proof becomes absent. Expiry only removes the server-side entry (`src/server/DashboardOperatorSessionStore.ts:41`); the browser retains the string, ignores the returned expiry (`dashboard/index.html:4499`), and immediately reuses any nonempty token (`:9198`). The route silently falls back to discovery rules when verification fails (`src/server/routes.ts:40131`), so a high-tier enable returns graph/consent errors instead of renewing proof. The isolated dashboard probe confirmed reuse without a PIN prompt. **Smallest fix:** distinguish an omitted proof from a supplied invalid proof. Return a specific re-unlock response for the latter; clear it in the dashboard, unlock once, and retry the already-confirmed switch. Track `operatorSessionExpiresAt` for normal expiry. Keep the omitted-proof agent path unchanged.

4. **Medium — The queue does not establish the promised ordering after a timeout.** Spec §2.1 says an earlier disable can never finish after a later enable. The queue waits for the HTTP client's promise (`src/server/routes.ts:39959`), but timeout destroys the socket and resolves that promise (`src/core/FeatureActionApplier.ts:142`); it does not cancel the target handler. Telemetry disable performs local deprovisioning and the config write after an awaited remote call (`src/server/routes.ts:32407`, `:32429`, `:32444`). Its normal five-second remote timeout reduces exposure, but is not a general cancellation guarantee. A probe using the actual applier and a delayed local handler produced `failed disable`, then `applied enable`, then a final disabled setting. Re-reading config once cannot detect a write that has not happened yet. **Smallest fix:** for the current asynchronous target, capture deletion credentials and finish local disable mutations before awaiting remote cleanup, so cleanup cannot later undo an enable. Test a target that outlives the client timeout, and describe timeout as unconfirmed in the actual result text. Scope the ordering promise to mutations that really share the ordering mechanism.

5. **Medium — The new consent dialog repeats false undo promises.** The dialog now displays `reversibilityNote` (`dashboard/index.html:9208`), but Threadline's note still promises immediate disconnection (`src/core/FeatureDefinitions.ts:35`), and Evolution System's note promises that disabling stops new activity (`:187`). `PATCH /config` saves settings and replaces runtime config fields; it does not stop those managers (`src/server/routes.ts:32233`). Evolution ignores its enabled key even on restart, and Threadline also has an environment enable override (`src/threadline/ThreadlineBootstrap.ts:385`). These claims directly contradict the revised cautious status wording. **Smallest fix:** correct the existing disclosure strings: distinguish saving a setting from stopping the component, name the relay override, and remove the evolution-disable promise. No new lifecycle machinery is needed for this wording fix.

6. **Low — Describe the legacy activation challenge as a protocol step, not human proof.** Spec §2.4 says the challenge proves a human confirmed. The ordinary transition returns the challenge to the same caller (`src/core/FeatureRegistry.ts:519`) and accepts it back (`:537`), alongside a caller-supplied consent record. That round trip cannot independently establish human presence. The separate operator-session verifier does have a PIN-backed issuance path (`src/server/AgentServer.ts:1299`, `:4601`). **Smallest fix:** correct the security description and tests: Bearer callers retain the existing consent/challenge protocol; only the operator bypass requires the separate proof. Do not claim all Bearer-only enables are refused. This is an existing limitation, not a newly introduced privilege escalation, and does not require redesigning consent in this patch.

**Security assessment:** I found no new general Bearer privilege escalation from the loopback client as constrained here. Its address comes from the accepted socket, its action body comes from static definitions, only four method/path pairs are allowed, and redirects are not followed (`src/core/FeatureActionApplier.ts:49`, `:99`, `:110`; `src/server/routes.ts:39978`). The shared Bearer middleware still applies (`src/server/AgentServer.ts:1397`), as do the config allowlist and executable-selection fence (`src/server/routes.ts:2213`, `:32143`). The client does not manufacture operator proof. Mounting file settings while disabled does newly let Bearer callers inspect/change those settings and enable file access without restarting; §2.7 now acknowledges that accurately. The ELI16's blanket “Nothing new is being allowed” should carry that same exception. Caller-chosen `userId` remains a courtesy rule, as the revision now states.

**80/20 and Occam:** Keep the small HTTP adapter, single nullable result column, and one transition route. The removed retry endpoint and duplicate timestamp should stay removed. Cut the false prerequisite handling and the cosmetic evolution switch rather than adding a generic dependency/liveness framework. The remaining fixes do not justify a durable retry worker, a second desired-state store, or a broad configuration-service refactor.

DONE.
