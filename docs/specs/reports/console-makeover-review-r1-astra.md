# Review round 1 — GPT-6 Astra (codex CLI), 2026-10-25

**Verdict: ready with changes.** A useful Home beside the existing dashboard is the right 80/20 move. Keep the legacy default until Justin calls MVP. The proposed iframe bridge needs more work than “one header change,” and Home needs explicit data contracts before it can promise honest state. The eight findings below are ranked by impact. This is a source review, not a live-browser acceptance test.

1. **High — Allowing same-origin framing expands trust beyond the console.** The change at `docs/specs/console-makeover.md:122` would relax every dashboard response through `src/server/middleware.ts:691`. `SAMEORIGIN` plus `frame-ancestors 'self'` blocks other origins, but permits other pages on this origin; it does not identify the console as the trusted parent. This matters here: `src/publishing/PrivateViewer.ts:287` parses stored Markdown into HTML and inserts it without sanitization at line 389; `src/server/routes.ts:25062` serves that HTML on the same origin. Such a view can contain a dashboard frame. The existing script-injection exposure in that renderer is pre-existing; permitting framing additionally enables deceptive embedding. The browser distinction is defined in the [W3C framing policy specification](https://www.w3.org/TR/CSP/#directive-frame-ancestors).

   **Smallest fix:** for MVP, open legacy tabs as ordinary page links and retain `DENY`. If embedding is indispensable, first isolate or sandbox untrusted same-origin HTML, limit the framing exception to the legacy embed response, and keep the console and ordinary dashboard unframeable. Preserve the existing resource-loading CSP, `nosniff`, and referrer policy; append the framing directive rather than replacing the CSP. Test trusted embedding, hostile same-origin content, and an external ancestor in a real browser. An `embed=1` query parameter alone is not an authorization boundary.

2. **High — Sharing the stored API token does not share a complete PIN unlock.** The claim at `docs/specs/console-makeover.md:143` overlooks the separate operator proof returned by `src/server/AgentServer.ts:1299`. Legacy keeps it only in page memory (`dashboard/index.html:4444`, `:4499`); reading `localStorage.instar_token` does not restore it. Its default lifetime is 15 minutes (`src/server/DashboardOperatorSessionStore.ts:18`). For example, assisted subscription re-login requires it (`src/server/routes.ts:34410`). Unlocking the parent console leaves a newly loaded legacy iframe without that proof, so some actions fail. Sharing the existing bearer token on the same origin is not itself a new security defect, but persisting the operator proof to make this work would weaken the current boundary.

   **Smallest fix:** explicitly distinguish viewing access from recent-PIN actions. Reuse `/dashboard/unlock` and require a fresh PIN in the active legacy page when its operator proof is missing or expired. Keep the proof in memory; never put it in URLs or persistent storage, and never weaken the server gates. If retaining a one-unlock iframe experience, specify an in-memory handoff to the exact child window with exact-origin checks and expiry handling. Verify stored-token startup, fresh unlock, reload, expiry, and a real operator-gated action. Validate stored tokens against a protected route: `/health` is public (`src/server/middleware.ts:163`), despite the legacy client's use of it as an authentication check.

3. **High — “Can't tell on request failure” misses successful but incomplete answers.** The acceptance rule at `docs/specs/console-makeover.md:159` does not cover stale observations, absent fields, disabled features, or partial pool results. Concrete traps: the held-forward summary starts at zero with `observedAt: null`, retains old data after a failed refresh, and separates currently held replies from unreported expiries (`src/messaging/telegram-origin/TelegramOriginRuntime.ts:291`, `:307`, `:326`). The prototype nevertheless equates zero with “replies are reaching you” (`console/prototype/build-console.py:80`). Attention pool reads return partial results successfully (`src/server/routes.ts:20483`), and commitments can return `enabled: false` with an empty list (`:32784`). Commitments use `scope=mesh`, not `scope=pool`, for the wider view (`:32795`).

   **Smallest fix:** add a six-row contract listing each block's route, fields, population, machine scope, freshness limit, and detail destination. Render blocks independently; preserve good data with its age while marking missing coverage. Distinguish “no held forwards reported here” from proof of delivery, and current holds from expired losses. Test HTTP 200 with missing, stale, disabled, malformed, and partial data alongside HTTP failures. Specify refresh and retry behavior, and preserve open drills during refresh. Treat three seconds as the normal-load target and five seconds as the failure deadline, not two unconditional promises.

4. **High — Existing deep links and the cutover path are only partly covered.** Forwarding `?tab=` at `docs/specs/console-makeover.md:151` misses session-only links: legacy deliberately omits `tab=sessions` and restores `?session=...` independently (`dashboard/index.html:7970`, `:7988`, `:8033`). File paths also need forwarding intact. Inside an iframe, legacy updates only its own address with `history.replaceState` (`:7995`), so copying or reloading the console address can lose the selected file or session. After the switch, the specified iframe URL `/dashboard?tab=...&embed=1` points back to the new console unless explicitly changed.

   **Smallest fix:** define one small URL adapter covering all registered tab IDs, `path`, and `session`, including session-only links. Specify the embed target before and after cutover, preserve the visible URL when selection changes, and make refresh and Back work. Add browser cases for an agent-sent file link with an encoded path, a session-only link, and an ordinary tab link through both route layouts. With ordinary legacy links, most of this bridge work disappears.

5. **Medium — Phone acceptance checks appearance, but not usable workflows.** Six independent glance blocks permit 30 tiles and up to 900 words, while the existing standard budgets the whole initial view at five tiles and 150 words (`docs/specs/dashboard-ux-standard.md:179`). Reusing `glance.js` six times does not enforce a page-wide budget. “No sideways scroll” also does not prove a phone keyboard leaves the terminal composer or a PIN dialog reachable. Replacing an iframe during refresh or navigation can discard file edits and subscription setup; the existing interaction-preservation rule is explicit (`dashboard/glance.js:22`).

   **Smallest fix:** give Home one overall summary, compact rows for the six questions, and expanded details on demand. Define an overall content budget. At 360/390 px, walk all 29 navigation entries, including “Under the hood,” and exercise terminal input with the keyboard open, file editing, a job action, and a PIN/code flow across a refresh. Count the menu-opening tap when checking the two-tap promise. Ensure header removal in embed mode leaves necessary controls and a usable scroll area. Keep a working “Open in legacy” escape on every embedded view.

6. **Medium — A time-based legacy removal can delete working features.** `docs/specs/console-makeover.md:148` allows removal after a default 30 days, while native rebuilds only begin later (`:176`). An embedded tab still depends entirely on the legacy implementation. Calling the shell MVP does not establish replacement parity for those tabs.

   **Smallest fix:** remove the removal deadline. Keep legacy for as long as any console view depends on it. Require a short, checked capability inventory before retiring it: all 29 tabs, their write actions, PIN gates, and old links must have working replacements. Update the ELI16's “stays available for a while” (`docs/specs/console-makeover.eli16.md:19`) to state that condition.

7. **Medium — Correct the current-code baseline before building against it.** The “flat strip” opening in both documents is outdated: `dashboard/index.html:927` implements a grouped dropdown at every width, and its five groups start at `:3077`. The existing standard already records grouped navigation as approved (`docs/specs/dashboard-ux-standard.md:11`). More materially, the promised ready-made machine states from PR 2355 (`docs/specs/console-makeover.md:85`) are not exposed by the inspected pool implementation: it returns `online`, `routerReceivedAt`, and optional transport conditions (`src/core/types.ts:2280`; `src/server/poolRopeCondition.ts:40`; `src/server/routes.ts:21524`). Session telemetry provides optional raw `lastActivity`, not a guaranteed plain-English last-action sentence (`src/server/routes.ts:10935`); the prototype displays the initial prompt (`console/prototype/build-console.py:216`).

   **Smallest fix:** describe the actual improvement as a cross-system Home and better labels. Name the concrete dependency supplying the new machine states, or define a small tested mapping from available evidence and show unknown when it is insufficient. Format recorded activity deterministically with a timestamp; label an initial prompt as the task, never as the latest action. Correct these claims in both versions of the plan.

8. **Lower — Cut work that delays the first useful, beautiful screen.** Group-summary pages repeat Home and add fetching and maintenance before the operator reaches an existing tool (`docs/specs/console-makeover.md:114`). Restyling all legacy embeds (`:63`) adds regression work across 29 tabs. Requiring both models to keep reviewing until both say “production-grade” (`:67`) has no bounded stopping condition and duplicates Justin's acceptance decision.

   **Smallest fix:** ship a polished native Home, grouped direct links, and the two cross-links first. Defer group summaries and legacy reskinning. Keep the new stylesheet, strong visual design, phone/desktop screenshots, and Justin's aesthetic acceptance bar; use one bounded review pass to catch concrete defects. Keep the proposed deferrals of browser takeover and outcome galleries. No new frontend framework, aggregate server, or generalized migration system is needed for this increment.

DONE
