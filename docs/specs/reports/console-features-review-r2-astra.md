# Console features review round 2 — GPT-6 Astra (codex CLI), 2026-10-25

Verdict: **ready with changes**. The revisions make this a practical plan. The separate PIN adapters, local Health entrance, corrected cost claims, preserved ledger commitments, and earlier Accounts/Feedback work answer the major round-1 objections. The remaining findings below need correction before their native pages replace legacy.

Reviewed the six current feature documents against the parent plan, legacy dashboard/controllers, native console, and relevant server implementations. This was a source review, not a browser acceptance test. HEAD at review: `e52c649374a642a8a913a0cd5eb521f6c10d7c10`. Concurrent console implementation edits were present and are outside this report. Findings are ranked by consequence; answered round-1 findings are not repeated.

1. **A pooled safety-check row can accept risk on the wrong machine.** `people-settings.md:342` combines `/guards?scope=pool` with **Accept the risk / Stop accepting it** on the displayed checks. Those writes have no peer target: `POST /guards/:key/accept-fallback` writes using this server's `stateDir` and `meshSelfId`, and DELETE does the same (`src/server/routes.ts:10637`, `:10646`). The same guard key exists on multiple machines. A button on “Mac Mini” served by Studio could therefore change Studio's acceptance while leaving Mini untouched. The PIN proves approval, not which machine the operator intended.

   **Smallest fix:** offer these buttons only on local rows, name the machine in the confirmation, and give peer rows an **Open on Mac Mini** link. Do not forward a PIN or assume the operator-session token works on another server. The revised PIN lifetimes and maintainer visibility rules otherwise look sound; retain the existing server gates.

2. **“Keep this one” still promises a preference write that the route does not perform.** Although editing was deferred, `people-settings.md:417` retains a two-version conflict picker and `POST /state/resolve-conflict`. The read returns version origins and clock stamps, not the two preference texts (`src/core/ConflictStore.ts:46`; `src/server/routes.ts:22408`). More seriously, the POST only calls `store.resolveConflict()` and returns success (`src/server/routes.ts:22452`). That method marks the conflict resolved; its contract explicitly leaves writing the chosen preference to the caller, which this route never does (`src/core/ConflictStore.ts:222`, `:245`). The UI would close the warning without making the chosen preference take effect.

   **Smallest fix:** remove **Keep this one** from this build along with the other preference writes. Show the conflict as advisory information. Put version retrieval, applying the winner, replication and operator attribution into the later preference-write change. This also keeps the supposedly read-only page genuinely small.

3. **The Other agents merge can hide conversations and remove bridge controls.** Its agent list is only the union of pairings and peer health (`people-settings.md:103`). Legacy conversations instead come directly from inbox/outbox history, including counterparties with no current pairing or health row (`src/threadline/ThreadlineObservability.ts:118`, `:145`). Those conversations need a visible home even when pairing or health is off. Likewise, replacing editable allow/deny lists with choices on known-agent rows loses adding an arbitrary name/fingerprint and removing an existing entry whose agent is no longer listed (`dashboard/index.html:4317`, `:4326`, `:7171`). Search is not a substitute for browsing history or editing those rules.

   **Smallest fix:** include counterparties from thread history and existing bridge rules in the agent list, distinguish “history only” from “paired,” and retain a small advanced add/remove rule editor. Keep remote conversation summaries separate from locally readable messages: the mesh conversation route supplies ownership records, while `/threadline/observability/threads/:threadId` reads this machine only (`src/server/routes.ts:18870`, `:18904`). Link to the holder for unavailable remote history. Also correct the legacy criticism at `people-settings.md:95`: rows already lead with the agent's name, with the thread ID beneath it (`dashboard/index.html:7250`).

4. **The parity checklist still has concrete omissions.** Resolved blockers become only **Cleared this week** (`work.md:715`), but legacy exposes every resolved entry returned, without a seven-day filter (`dashboard/glance.js:602`, `:622`). Autonomous throughput observations are declared moved to Work, with an alternative suggestion of Throughput, but neither destination specifies their display or data read (`capacity.md:47`, `:194`; legacy implementation `dashboard/index.html:6670`). Schedule explicitly cuts sorting (`work.md:389`), although grouping cannot replace sorting by priority, name or last run (`dashboard/index.html:8683`). These are remaining holes, distinct from the round-1 omissions that were repaired.

   **Smallest fix:** add **Older cleared blockers**, assign the autonomous-run panel to one concrete location in Plans with its existing decision and elapsed-time fields, and keep sorting behind an **All jobs / More** control. Add these exact cases to the switch-over checklist. The bridge-rule editor in finding 3 is the clearest remaining lost legacy write control.

5. **Schedule's new “Late” rule would manufacture noise from deliberately inactive jobs.** `work.md:335` defines late as a past `nextScheduled` and not running. `/jobs` returns every configured job and retains an existing saved `nextScheduled`, including for jobs now disabled or assigned elsewhere (`src/server/routes.ts:16626`, `:16632`, `:16651`). The scheduler registers only enabled jobs scoped to this machine (`src/scheduler/JobScheduler.ts:270`). An old saved deadline therefore does not prove that this machine missed work it should have done.

   **Smallest fix:** require `enabled` and `runsOnThisMachine` before applying the late test to each machine's row. Keep disabled and out-of-scope records out of the failure count. Describe the remaining result as “past its recorded next-run time,” with missing scheduling evidence shown as unknown. This needs a precise predicate, not a new scheduler subsystem.

6. **Shipping promises release information its read cannot provide.** `under-the-hood.md:237` promises “4 changes, oldest 2 days” or “Everything merged is released.” `/release-readiness` returns watchdog episode count, an oldest SHA, tick time and attention ID—not unreleased change count or the commit's age (`src/server/routes.ts:15919`). Episodes are keyed by the oldest unreleased commit and represent watchdog state, not one record per unreleased change (`src/monitoring/ReleaseReadinessSentinel.ts:315`). Zero episodes is not a release inventory. The promised last verification result also needs the existing keyed record endpoint, absent from the plan's data list (`src/localVerify/localVerifyRoutes.ts:104`).

   **Smallest fix:** show “Release watchdog: N unresolved episodes · last checked …,” link the attention item, and avoid claiming everything is released. Add `/local-verify/record?pr=&head=&base=` for detail where those keys are known. Pin a short field-to-display table now; leaving the core mapping until contract tests at build time makes Shipping less specific than the other plans.

7. **The restored claim-audit section treats audit rows as verified claims.** `under-the-hood.md:700` promises “Last 20 claims … 18 checked out.” The endpoint limits audit records, not distinct evaluated completion claims (`src/server/routes.ts:29878`). The stream mixes general claim observations, legacy completion verdicts, coverage-gap events and settlement events (`src/monitoring/ClaimObservation.ts:427`, `:481`, `:491`; `src/monitoring/CompletionClaimVerifier.ts:269`). General observations use `supported/refuted/unverifiable`; legacy observations use another vocabulary. A single message can contribute multiple records. The plan does not specify which population its denominator counts or preserve a prominent contradicted-claim state.

   **Smallest fix:** initially say **Recent claim observations**, retain **Evidence supports it / Evidence contradicts it / Couldn't verify / Not evaluated**, and keep coverage events separate. Do not calculate a success fraction until the record-type and deduplication rules are explicit. Preserve “advisory only” from the legacy detail (`dashboard/preferences-learning.js:270`). This is the main remaining generic feature sketch.

8. **Development's final layout puts the important phone action below two dashboards.** The revised build order correctly moves Feedback approvals forward, but the final combined page still orders Shipping, Pace, then Feedback (`under-the-hood.md:880`). Each section has its own facts and content; a worst-state headline at the top does not put the approval card within reach. Once Shipping and Pace ship, an operator entering the Work tile can again have charts and healthy work between him and the PIN action.

   **Smallest fix:** place a concrete pending approval card immediately under the Development headline, then use a small section selector or collapsed summaries for Shipping, Feedback and Pace. Keep direct links. The overall build order is now right for 80/20: Promises to prove the pattern, Machines/Health, Accounts and delivery, permissions and Feedback, then broader read views. Keep the terminal, comparison charts, universal evidence drawers and new Shipping controls deferred. Do not build a new cross-page intelligence engine to compose this one page.

9. **Correct three smaller inventory/API claims before implementation.** The Other agents fallback names bare `GET /pool/placement` (`people-settings.md:107`), but that route requires `?topic=` and returns 400 without it (`src/server/routes.ts:22468`); it is not a general pairing-holder lookup. Accounts promises a legacy link for unattended-repair settings (`capacity.md:393`), while its own inventory correctly says that route has no legacy UI (`capacity.md:349`); the dashboard controller has no configure form. Finally, the blanket Files claim that directory truncation is silent needs narrowing: nested folder responses already return `truncated` and `totalEntries` (`src/server/fileRoutes.ts:648`); the project-root branch omits them (`:561`), and the legacy client does not display them.

   **Smallest fix:** derive the pairing holder from actual pool/lease metadata, leave unattended repair read-only without a dead-end legacy link, and scope the Files change to adding root metadata plus displaying the existing nested metadata. These are corrections to the plan, not reasons to expand backend scope.
