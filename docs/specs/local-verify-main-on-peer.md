# A peer may run the main verify while main is healthy

## What this amends

`docs/specs/local-verify-capacity.md` (approved 2026-10-26), Part D, defines the peer:

> It runs single PR verifies handed to it and keeps their records in its own journal. It never merges, never posts commit statuses, never verifies `main`, never decides main health.

This spec changes the clause **"never verifies `main`"** to **"runs a `main` verify only when the coordinator hands it one, which the coordinator does only while main is healthy and the switch is on"**. The peer still never merges, never posts commit statuses and never decides main health. The other parent sentences that change with it are listed under "Also amended".

## Why

- Keeping `main` on the coordinator costs the line. Measured on the Echo test machines on 2026-11-17 (throughput brainstorm, experiment E3): a due `main` verify waited 82 minutes on average, and `main` verifies used 426 minutes of the coordinator's slot in the day, while the peer had gaps. Most of the 82 minutes is the 90-minute fair-share window, which stays. What this removes is the wait for one specific machine once main is due, and part of the coordinator minutes.
- The peer is already a merge-authorizing principal (the parent spec says so). A `main` record is different in reach, though: a PR record gates one PR, a `main` record gates the whole line. That is why the rule below limits what a peer-run `main` verify can do: it can confirm a healthy main green, or make it suspect. It can never make main red.

## The rule

1. **Who decides.** The coordinator alone queues `main` verifies, decides when one may start, and records main health (green, suspect, red, the main-red hold, the merge line's gate). A peer executes one attempt and returns one record for it. A handed run never writes the peer's own main-health file.
2. **Healthy only.** A peer is offered a `main` verify only while main health is `healthy`. While main is suspect or red every `main` verify runs on the coordinator, including the confirming re-run after a first failure. The same holds at import: if main is no longer healthy when the peer's record arrives (for any reason), the record is not judged in either direction; the entry returns to the queue and the coordinator runs it itself (audit `peer-main-unjudged`). So a red result from a peer moves main from healthy to suspect at most; main turns red only on the coordinator's own failing run, and a suspect or red main is cleared only by the coordinator's own green run.
3. **The switch.** `monitoring.localVerify.mainOnPeers` (boolean, default `false`, read live at each dispatch). Off or absent: every `main` verify stays on the coordinator, as before this spec. Turning it off does not touch an attempt already reserved; that one finishes or is taken back by the rules below.
4. **Fair share.** A free peer is offered `main` under the same rule as the coordinator's slot while healthy (`decideStart`): a PR that this peer could take goes first until main's oldest unverified merge is 90 minutes old; then `main` goes. A PR that has used up its peer attempts does not hold `main` back. The peer is never offered `main` by priority alone.
5. **One at a time.** The coordinator holds at most one `main` verify it will import: a pending `main` entry does not start on the coordinator while a peer holds one, and is not offered to a peer while the coordinator runs one or another peer holds one. (An orphaned peer run, rule 10, may overlap; it is never imported.)
6. **Never cancelled by a newer head.** A newer head of main queues behind a peer-run `main` verify exactly as it queues behind a local one. The head is fixed (moved to main's head as observed, per `main-verify-current-head`) before the dispatch snapshot and never changed while reserved.
7. **The peer checks the head itself.** The peer starts a `main` verify only if its own read says main contains that head: with T the head of `main` as the peer reads it from GitHub at that moment, the requested head is T itself, T's first parent, or that commit's first parent (a release commit sits on top of the verified head), or `git merge-base --is-ancestor <head> T` succeeds in the peer's own clone as it is (no fetch is made for the check; if the clone lacks T or the head, the check fails). The tip is always the GitHub read, never a local branch name. Otherwise it refuses (`head-moved`, or `pr-unreadable` when main cannot be read) and nothing runs.
8. **Unconfirmed refusals are counted, separately.** Such a refusal spends the attempt and does not count toward the peer's health breaker (the peer is fine for PRs). After 3 in a row from one peer, that peer is offered no `main` verify for 30 minutes, the audit log records `peer-main-paused`, and one deduped signal `local-verify:peer-main-unconfirmed:<machine>` is raised. An accepted `main` request resets the count and clears the signal. The count is in memory: a coordinator restart resets it. The peer keeps taking PRs throughout.
9. **Import.** Every import check of the parent spec applies unchanged to a `main` record (the same function decides): a valid record, the attempt id, the peer, the repository, head, base and base ref equal to the dispatch snapshot (for `main`: pr 0, head equal to base, base ref `main`), verifier version and policy hash equal to BOTH the snapshot and the coordinator's own at import time, the coordinator holding the lease now at the dispatch-time epoch, and a start time not before the dispatch. This spec adds one check: the record kind must match the dispatch kind (`wrong-kind` otherwise). An imported `main` record goes to main health only (`completeMain`); it never enters the PR index, the journal or the merge line. With a red record the peer returns the run's bounded reasons and failure list (at most 30 files, clipped messages); the coordinator re-validates and bounds them. If that detail is missing or malformed, main still turns suspect and the failing files are unknown until the coordinator's own re-run names them.
10. **A silent peer gives it back.** Because rule 5 blocks every other `main` verify while one is reserved, a reservation is taken back, and a cancel sent, when the peer has been unreachable for 5 minutes and for at least two polls in a row. The 5 minutes count from the later of the last answered poll, the dispatch, and the coordinator's own restart. An answer of "unknown attempt" keeps the parent's rule unchanged (taken back once the attempt is more than 2 minutes old), which is the shorter of the two. At each poll the first condition that holds decides, in this order: lease changed; main not healthy; unreachable too long; unknown past its grace; the 60-minute run bound. If the peer is alive but unreachable the cancel is lost and its run ends at the peer's own 60-minute bound, unimported, as for PR attempts. A peer that keeps answering "running" keeps the run up to that 60-minute bound, while main stays healthy. If main stops being healthy while a peer holds a `main` verify (for example an unverified-too-long alarm, or a restart that cannot read the health file), the reservation is taken back and cancelled at the next poll, about a minute, and the coordinator runs it itself (audit `peer-main-unjudged`); a suspect main never waits on a peer run whose verdict would not be used.
11. **Errors, attempts, lease.** An `error` record, an abandoned attempt or a refusal returns the entry to the coordinator's queue as an ordinary pending `main` entry (an `error` record is not judged). "The coordinator runs it itself" in this spec is a consequence of rule 2, not a mark on the entry: while main is not healthy the entry can only start on the coordinator. Main becomes healthy again only through the coordinator's own green run; after that a still-pending entry is ordinary again and may be offered to a peer within its remaining attempts. A newer entry that replaces it starts with its own two attempts. At most two peer attempts per entry, as for PRs; after that it runs on the coordinator. Peer `error` records do not use the coordinator's per-head error-retry count of 3; the two-attempt limit bounds them. If a newer `main` entry is already pending when one comes back, the returned one is dropped (the newer head covers it). The parent's "Lease moves" rule applies unchanged to a `main` attempt: a lease change abandons and cancels it, and a peer that becomes the lease holder cancels the attempt it is running.
12. **Clock.** The unverified-since time moves by the rule a local run already follows, with the coordinator's dispatch time in place of the local start time; the peer's clock is never used. If the verified head is still main's head as the coordinator observes it at import, nothing is unverified. Otherwise the time moves forward to the later of (a) the dispatch time, counted only if the dispatched head was main's head as the coordinator last observed it at dispatch, and (b) the time the coordinator first observed a newer head than the verified one; it is never later than now. As for a local run, a merge that GitHub already had but the coordinator had not yet observed at dispatch is treated as covered until its own observation queues the next verify (the existing 10-to-30-minute debounce); this limit is not new. After a coordinator restart (a) is not kept, so only (b) applies; if no newer head has been observed the head is current and nothing is unverified.
13. **Restart.** A reserved `main` entry is saved in `queue.json` (an unreserved one is still re-derived), so a coordinator restart resumes polling the same attempt. Never two reservations: the service never writes two, and a second one found at restore, or one found while a `main` verify is already running on the coordinator, is dropped and audited (the peer client is not wired yet at boot, so its run ends at the peer's own bound).
14. **Rollout and version skew.** The verifier version is a hash of the verifier's source graph and dispatch requires equal versions and policy hashes. So the code change itself changes the version: until both machines run it, no dispatch of any kind happens between them (as with every verifier change), and both must be updated together. A coordinator with this change never sends a `main` request to a peer without it.

## Also amended

These parent sentences change with the rule above. Each is quoted with its replacement.

- Capacity, Part D, Dispatch 1: "the next eligible entry in queue order: a PR verify (never `main`)". Becomes: a PR verify, or a `main` verify under rules 2 to 5 of this spec.
- Capacity, Part D, Dispatch 4: the peer refuses when "its own GitHub read of the PR fails eligibility (`checkEligibility`) or shows a head other than `headSha`". For a `main` request there is no PR to read; rule 7 of this spec replaces that check.
- Capacity, Part D, Results: "a `success` or `failure` record goes through the one completion path (`complete(record, 'peer')` …)" and Lease moves "(one completion rule, no special path)". A `main` record goes through the main completion path (`completeMain`), the same one a local `main` run uses.
- Capacity, Part D, Setup: a peer-only service "refuses every coordinator role (no `POST /local-verify`, no merge line, no status loop, no `main` verifies)". Becomes: no `main` verifies of its own; it runs one the coordinator hands it.
- Capacity, Tests: "held and `main` entries never dispatched" and "including when main stays local". Become: held entries never dispatched; `main` dispatched only under this spec; with the switch off main stays local.
- Merge-authority, Post-merge verify of `main`: "a `main` run already in progress is never cancelled". Still true for a newer head (rule 6). The complete set of exceptions, all for a peer-run `main` verify only, which is then run again: main stops being healthy (rule 10), the peer is unreachable too long or answers "unknown attempt" (rule 10), the lease changes (rule 11), and the 60-minute attempt bound. A `main` run on the coordinator is still never cancelled by any of these.
- Capacity, Part D, Never blocks local work: "The coordinator never waits on a peer before starting its own next run." Still true for PR verifies. The one exception is rule 5: a pending `main` entry waits while a peer holds a `main` verify; the coordinator starts PR verifies meanwhile.
- Merge-authority: "A `main` verify takes priority over PR verifies". Already replaced by fair share for the local slot; the same fair share governs a peer (rule 4).

## What does not change

- PR dispatch, PR import, the merge line, commit statuses and the restart hold for peer attempts.
- Main health's state machine, the first-failure re-run (now always on the coordinator when the first failure came from a peer, because of rule 2), the main-red hold's rules.
- A single-machine install, and any install with the switch off.

## Accepted limits (stated, not solved)

- A peer whose environment differs from the coordinator's can make a healthy main suspect by itself. Merging pauses until the coordinator's own re-run of that head ends: the wait for the coordinator's slot (it is usually busy, and while suspect one PR start may come first) plus one run of about 25 to 40 minutes. Green clears it, red confirms it. A dedicated signal for "the two hosts disagree on main" is not part of this change (queued as feedback); the disagreement is visible in the audit log (`main-record` after `peer-imported`).
- The green `main` record that seeds isolation re-runs may now come from the peer, so the peer's flaky set on green main becomes the coordinator's baseline.
- A coordinator rolled back to older code skips a saved reserved `main` entry; that peer attempt ends at its own run bound.
- The peer process sets its own in-memory "this run started on the current head" marker for a handed run. A peer-only service never reads it.

## Rollback

Set `monitoring.localVerify.mainOnPeers` to `false` (live, no restart): every new `main` verify stays on the coordinator. Code rollback: revert and restart both machines together (the verifier version changes). No migration.

## Tests

Unit (`tests/unit/localVerify/peerVerifier.test.ts`, block "a main verify on whichever host is free"): request shape (including `isolation` refused); import refusal by kind; failure-detail bounds; dispatch with the reservation saved before the send; fair share on both sides of the 90-minute window; switch off by default and turned off live; green import; red import with failing files, suspect, and the re-run kept on the coordinator; red import with missing detail; a record that arrives after main stopped being healthy is not judged (the test forces the health answer, it does not drive a real state change); a running peer attempt is taken back when main stops being healthy; a newer head never cancels and starts after; not offered to a peer while the coordinator runs main; silent peer; long-running peer kept; error record hands back; handed back beside a newer pending head; unconfirmed head not counted against the breaker; three unconfirmed in a row pause main for that peer with one signal while PRs still go; restart resumes; second saved reservation dropped and audited; unreserved main never saved; peer runs main with the attempt and returns failing files; crashed run answers with a valid error record; release-commit parent accepted, foreign head refused, unreadable main refused. `record.test.ts`: a main record with an attempt. Integration (`tests/integration/local-verify-peer-routes.test.ts`): a main verify over the real routes with the real client. E2E (`tests/e2e/local-verify-lifecycle.test.ts`): the production wiring reads the switch (off by default, on when set) and a peer-only service built by that wiring has the three reads the head check needs. 

Also unit: the unverified-since time after a green peer import with a newer head observed and a peer clock an hour ahead (rule 12). Also e2e: both services built by the production functions, the peer behind real HTTP routes, real records through the real completion paths: with the switch off main is not handed out; with it on the peer runs main after its own head check; its red result makes main suspect with the failing file kept; the re-run is never handed out; the coordinator's own red run then turns main red.

Not tested, stated: a merge landing between the coordinator's head observation and the dispatch (the limit stated in rule 12, shared with local runs); a coordinator restart while the reservation is held is tested at unit level only; the signal being cleared by an accepted `main` request (rule 8) and a saved reservation dropped because a `main` verify already runs on the coordinator (rule 13) have no test; a peer becoming lease holder during a `main` run relies on the existing peer-attempt test for that path.

## Measure after it is live

Turn the switch on for the Echo test machines only. Compare one day against the 2026-11-17 baseline: main's wait in queue (82 minutes), coordinator minutes spent on `main` verifies (426), every suspect that a coordinator re-run cleared (a peer false alarm, with its cost in paused-merge minutes), and every `peer-main-paused`.
