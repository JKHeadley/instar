# Project apps, part 2: custom apps

**Status:** draft for review, 2026-11-17. Effort topic: Telegram 143902.

## 1. What this adds

A custom app is one web page the agent writes for one project (a sales pipeline, a course tracker), shown one tap from the project like a builtin app (part 1). The agent writes it, so **its code is assumed hostile** (Justin 16:28: the real risk is a hijacked agent).

## 2. The honest security boundary

**In scope: an agent hijacked through content, acting only through Instar's API** — a prompt-injected job or session that calls the server, and the app's own code running in the owner's browser. Against that, every guarantee below holds.

**Out of scope, by nature: an agent with shell access on the host.** It holds the master token, the dashboard PIN (plain text in config), the machine signing key, the journal files and the console's code on disk. It can write records straight into the journal, pair a software "phone", or change the code the owner's browser is served. Nothing that host decides can be trusted, and this spec claims no protection against it — including the phone approval and the browser sandbox, which both depend on the host serving honest code. (Instar sessions do run with shell access; that is the platform's standing trust model, stated in every agent's instructions, and it is the same for every other Instar feature.)

What the design protects in scope:
1. **Which code runs** — only a version the owner approved on their phone (§3.4).
2. **What lives in the owner's browser** on the dashboard origin (the console's session and the browser device key) — the app can never read it (§3.6).
3. **Owner powers** (approvals, trust, PIN-gated controls, messages, sessions) — the app's key cannot reach them (§3.7).

## 3. Design

### 3.1 Identity

`appRef = custom:<appId>`, `appId` minted by the server (`pa_` + 16 hex). Created by the agent: `POST /project-apps` (Bearer) `{conversationKey, title (1-60), specPath}` → `{appId}`. The project must be a bound project the owner sees in Work.

### 3.2 Storage: a new journal kind `project-app-blob`

- **A separate kind with its own state-sync advert** (`multiMachine.stateSync.projectAppBlobs`, forced on with `projectApps.custom.enabled`). Every machine on a build with custom apps advertises it, so the apps' code and data reach every such machine; a machine on an older build has no custom apps at all (its rows simply don't show them) and nothing stalls (part 1 §3.2). Part 1 accepts the part-2 record types and `custom:` refs as inert stubs (part 1 §3.2, amended).
- **Content blobs:** immutable records `chunk:<appId>:<kind>:<keyGen>:<chunk id>` holding the chunk **encrypted** (AES-256-GCM with that app-and-kind's key of generation `keyGen`; the nonce is stored in the record) and **base64-encoded, at most 32 KiB raw plaintext per chunk**; because the key generation is part of the identity, identical plaintext saved after an erase (new generation) is a new chunk and never collides with one encrypted under a destroyed key; the emitter refuses any record whose complete serialized line exceeds 64 KiB (the journal bound is 80 KiB), so escaping can never push one over. Chunks split on byte boundaries and are reassembled before UTF-8 decoding. A chunk is shared only between revisions of the **same app and kind**, so erasing an app's data can never touch its source or another app. **Keyed hashes for data:** a data chunk's id and a data revision's `contentSha` are HMAC-SHA256 of the plaintext under that generation's data key (not plain sha256), so the journal lines an erase cannot delete hold nothing to confirm a guess about the contents against once the key is destroyed; the key holder computes the same ids, so dedupe and lookup still work. Source keeps plain sha256: an erase never destroys the source key, and the source hash is the version's identity on the owner's approval card.
- **Revisions:** immutable records `rev:<appId>:<hlc>` (HLC-keyed, so unique on every machine without an allocator): `{appId, kind: 'source'|'data', keyGen, contentSha (the whole document's hash: plaintext sha256 for source, keyed as above for data), chunks: [id…] (chunk ids within that kind and key generation), bytes, base (the revision it was written over), by: 'agent'|'app', note? (source; encrypted with the source key, below), epoch, at}`. Writing A → B → A makes three revisions that point at two contents.
- **One coordinator: the lease holder.** Writes, budget admission, version cards and their notices all happen on the lease holder, fenced by the lease epoch recorded on each revision. A write that reaches another machine is **forwarded server-side** to the holder over the existing machine-authenticated mesh send (the same forward-to-holder path the email outbox uses), so the frame and its `connect-src` never change; if the holder cannot be reached, the write answers 503 "Can't save right now: the machine that saves this app is unreachable" and the app keeps its unsaved state. A write is acknowledged after the holder's journal has it durably; other machines receive it by replication (the same durability every journal kind has; a holder lost before replicating can lose its last writes, stated on the row as "last saved on <machine> at <time>"). A write names its `base`; a stale base answers 409 `conflict` with the current revision, so one tab never silently overwrites another. Every admitted revision counts toward the day's budget whatever its epoch (a normal lease handover keeps the day's usage). A revision whose epoch is older than the lease epoch in force when it was journaled (a fenced old holder writing late) is not served and never opens a card; it is listed on the row as "a late write from <machine> was set aside".
- **Completeness:** a revision is usable on a machine only when every chunk is present and the whole hash matches. A machine serves the newest **complete** approved source; if a newer approved one is still copying, the frame bar says so.
- **Kept until the owner erases** (Disk Steward counts the app blob store and the kind's files, including ciphertext left after an erase): the kind uses `rotateKeep: 0` (no silent deletion); chunks are also written, still encrypted, to a content-addressed store on disk (`state/project-app-blobs/<appId>/<kind>/<keyGen>/<sha>`) so a reader serves a revision from that store and folds only the small revision records, never re-reading the chunk history at boot. Worst case with the default budget: 8 MiB a day ≈ 2.9 GB of saved bytes per app per year, stored twice on each machine (base64 ciphertext in the journal, raw ciphertext bytes in the disk store) — about 6.8 GB per app per year per machine; the row shows "this app has used N MB", the budget is the brake, and Disk Steward reports it with the machine's other disk use.
- **Size.** Per write: source ≤ 2 MiB, data ≤ 1 MiB by default (413 naming the limit). Per app per day: a byte budget (default 8 MiB) counting the serialized journal bytes of every write the app makes — revisions, chunks **and summary records** — admitted on the lease holder only, so it cannot be multiplied across machines; a summary write past the budget answers 429 like a data write. Per agent: at most 10 custom apps by default, so app creation cannot multiply budgets or cards. All four are owner settings raised only by a phone-approved card (§3.4); the defaults are starting values sized to one phone page load (a 2 MiB page over a phone tunnel) and an app that saves a 50 KB document about 160 times a day, not claimed limits of nature. Past the budget a write answers 429 and the app shows "Saving is paused until tomorrow".
- **Erasing, by destroying keys.** The journal has no per-key compaction (CMT-1415, not built) and `rotateKeep: 0` never deletes, so erasure cannot rely on removing journal lines. Instead **everything an app stores is encrypted at rest** (AES-256-GCM) with app keys that never enter the journal or secret sync (secret sync has no delete and no fetch, `src/core/SecretSync.ts`): a **data key** (data chunks and the app's summary record's headline and counts) and a **source key** (source chunks), each with a generation. Two phone-approved cards: **Erase <app>'s saved data** (destroys **every** data key generation of that app created up to the approve — an app-level watermark, so an older generation a returning machine offers later is covered too — everywhere, below, and deletes the data files from the disk blob store; the next write starts a new generation) and **Delete <app>** (destroys both keys, deletes every disk-store copy, and tombstones the app so it is not served). The journal lines that remain hold ciphertext no machine can read any more; the agent's change note is stored encrypted with the source key, and a version card shows it only while that key exists; after **Delete <app>** the card's note reads "(erased)". Cards otherwise carry only server-written text (the size and the check's findings, which name patterns, never quote content). **App keys, built here:** each machine keeps app keys in its own key file (`state/project-app-keys.json`, 0600), added to the backup blocklist in `BackupManager.ts` (next to the browser-profile entries) so no include setting can back it up. A machine that returns holding an older, unrevoked generation after a lease move offers it to the holder, so data saved under it stays readable. The lease holder creates a key generation; other machines **fetch** it from the holder over the existing machine-authenticated mesh send (a new `project-app-key-fetch` verb that answers only signed peers of this agent) when they first need it. **Destruction** is a replicated `project-app-key-revoked` record (`{appId, keyKind, gen}`, no key material) in `project-app-record`: every machine that sees it deletes that generation from its key file and refuses to store or fetch it again (a deny-list), so a revoked key can never come back. **An erase is not done until every live machine has it:** the lease holder pushes the revoke record to every reachable machine over the signed mesh and waits for each one's durable acknowledgement (a per-machine confirm record) before the card's result reads "Erased"; until then it reads "Erasing; waiting for <machines>", the app's data is not served anywhere, and the key fetch verb refuses that app. **The owner's approve is itself the revocation:** every machine treats a phone-presence owner approve on an `erase-data` or `delete-app` card (bound by its `project-app-version-card` record) as revoking the named generations, whether or not a `project-app-key-revoked` record has arrived; the lease holder writes that record as the durable, confirmable form. So a revocation cannot be lost with a holder that dies after the approve: the approve lives on the replicated Work Board. A machine that becomes lease holder first completes a journal sync of `project-app-record`, `project-app-blob` (revisions and their budget usage) and the Work Board's cards with every reachable peer before it admits any write or fetches, creates or hands out any app key; if the previous holder's acknowledged tail cannot be recovered from any reachable peer, **consistency wins**: writes for the affected apps are refused ("Can't save right now: catching up with <machine>") until it can, and nothing is guessed; a peer offering a generation that any synced approve or revoke covers is refused. **Catch-up barrier:** after a restart or a reconnect, a machine serves no custom-app data and fetches no app key until it has completed a journal sync of `project-app-record` with the lease holder since that start or reconnect (so it holds every revocation the holder holds); until then the frame says "Catching up with your other machines". The lease holder refuses to hand out a revoked generation. A machine that cannot reach the holder stays unavailable for custom-app data, never serving from keys it might no longer be allowed to hold. The row says "Erasing; waiting for <machine>" until every machine it can reach has reported the generations gone (a confirm record per machine), and only then "Erased". **Phones:** the projects answer marks an erased app's summary as erased, and a phone replaces its saved copy on its next successful read; a phone that is offline at that moment keeps its last saved copy until it reconnects — the row says so ("Phones refresh their saved copy when they next connect"). A withdraw tap never reverses a revocation. After a lease move the new holder fetches the current generations from any peer that has them before creating any; it creates a new generation only for an app whose key no reachable machine holds, and then says so on the row ("This app's saved data could not be read on any machine"). Backups: app keys are never backed up, so a restored backup cannot read erased data (and a restore of a live app re-fetches its keys from a peer). This satisfies the repo's personal-data rule (`LearningsReplicatedStore.ts`: never keep personal data beyond the owner's control) without a journal compaction that does not exist.

### 3.3 Records added to `project-app-record` (part 1's kind)

- `project-app-version-answer` `vanswer:<appId>:<contentSha>:<hlc>` (immutable): `{appId, contentSha, answer: 'reject'|'disable'|'enable', by, via, at}` — only the "no" direction and the on/off switch; "yes" lives on the Work Board card (§3.4).
- `project-app-version-card` (immutable, written by the lease holder each time it opens or rewrites a card): `{appId, contentSha?, gen, purpose: 'serve'|'allow-again'|'enable'|'budget'|'erase-data'|'delete-app', target? (the budget value, or the key generation being erased), cardId, materialHash, at}` (key `vcard:<appId>:<purpose>:<contentSha or target>:<gen>`) — the material hash of exactly what that card showed, recorded once, so a later build that words cards differently never invalidates an approval already given. Each approval request is its own generation; an approve counts only for the generation whose material it signed, so an old approval can never be replayed onto a newer request.
- **The served version is derived, never written** (the card and its approvals are the lease holder's, below): every machine on a current build computes it from (a) the Work Board's replicated cards — an approve record carrying `by.proof: 'presence'` whose person is the owner (the same owner check the phone route's `activeOwnerPhone` makes; a member's phone does not count), on a card of the server-owned version class named by a `project-app-version-card` record, with the approve's material hash equal to that record's `materialHash` (any generation for that content hash matches, so an agent that reverts to an earlier content with a new note still gets a working card) — and (b) the answers above. Rules: **decisions on a content hash fold by HLC over its generations**: a reject (Decline on any generation) blocks the hash; only a later phone approve on an `allow-again` generation unblocks it; a later reject blocks it again (tests cover reject → allow again → reject, and replaying any earlier approve); the served version is the newest approved, not-rejected, complete revision; a newest `disable` stops serving until an `enable` card is approved on the phone. So no single machine has to be alive or current for an approval to take effect.
- `project-app-summary` `appsum:<appId>` (last-writer by HLC): `{appId, keyGen, sealed (the headline and counts, encrypted under the app's data key generation), asOf, by: 'app'|'agent', at}` — never plain text in the journal; after an erase of that generation the row reads "(erased)". Bound to the app; a removed or replaced app's summary is not shown; `asOf` later than `at` is refused; drawn as plain text, never links. Size: the record stays within the kind's 64 KiB serialized cap; the row shows the first 140 characters and three counts and opens to the rest, so nothing is cut, only folded.

### 3.4 Which code runs: the owner's phone, through a server-written Work Board card

- **One open version card per app, made by the lease holder.** The card's identity is deterministic per app **and purpose** (`wc_` + the first 16 hex of sha256 of `<appId>:<purpose>`, a valid Work Board card id), so there is only ever one open card of each kind per app and a version card never collides with an erase or budget card. When a new source revision lands whose content is neither served nor already pending, the lease holder creates that card or **rewrites it** to the newest revision (any earlier approval no longer matches the new rendering, so it cannot serve). Content that is already served or pending gets no card.
- **The server writes every field the card shows**: title "Run <title> new version for <project>?"; need in plain words (what changed, quoting the agent's change note while its source key exists, the size, the check's findings) followed by a muted "For support" line with the full app id and content hash; `doneWhen`, `links`, `carrier`, `outward` set by the server; no `recommendation`. The card class is **server-owned**: the agent's edits to it are refused (403), and **a console tap on it is refused** (403 "Approve this on your phone"), except **withdraw-approval**, which only stops an app and is accepted from any surface so a PIN tap can never make the card read as approved while nothing runs.
- **Approval = an Approve tap on the card from an owner phone** (the Work Board phone route: active owner phone + presence signature binding the card's material hash). Decline writes `reject` for that content.
- **The same server-owned card class** carries the other phone-only decisions, each with its own purpose, card id and `project-app-version-card` record binding the material the phone signs: **Enable <app> again** (`enable`), **Raise <app>'s daily budget to N MB** (`budget`, target N), **Erase <app>'s saved data** (`erase-data`, target the data key generation) and **Delete <app>** (`delete-app`). Each takes effect only from a phone-presence owner approve whose material hash equals its record's. A Work Board **withdraw-approval** tap on a version card acts as `disable` for that app (the owner can stop a running app from any surface; a PIN tap may stop, never start).
- No new phone screen. With no paired owner phone, no custom app runs, and the row says "Custom apps need your phone to approve each version" with a link to pair one (accepted exception to "no single device lockout": every other proof is available to a hijacked agent; any paired owner phone can approve, so pairing a second phone removes the single device).
- Spec process (approved point 2): `POST /project-apps` and every custom-app offer need `specPath` (realpath confined to `docs/specs/` or `.instar/specs/`) whose frontmatter has `review-convergence` and `review-report`. A **process signal**, shown on the card.
- **Notices:** one message in the project conversation when an app's version card first opens; a rewrite of an open card sends nothing. The card stays on the Work Board and in Needs-you until answered.
- **Dependencies:** custom apps need the Work Board on and the phone write gate (`permissionActions`); the switch refuses to turn custom apps on without them and says which is missing.

### 3.5 The automated check on every version (a signal)

Each new source version is scanned before its card is made: external URLs in the code, `RTCPeerConnection`, `<input type="password">` or fields labelled PIN/password/code, `eval`/`Function(`, very long minified lines, base64 blobs over 50 KB. Findings go on the card in plain words ("This version asks for a password") so the owner sees them before approving. **The check never blocks**: the owner decides (Signal vs Authority).

### 3.6 Serving: the sealed frame

- **Wrapper:** `/dashboard/project-app/?app=<appId>` — Instar code. Draws a fixed top bar the frame cannot cover: "<title> · made by your agent for <project> · anything you type here goes to your agent", **Conversation**, **Close**; and `<iframe sandbox="allow-scripts allow-forms" referrerpolicy="no-referrer">`. `dashboardSecurityHeaders` gets a branch for this one path that sets the wrapper's own CSP including `frame-src <origin>/project-apps/<appId>/frame` (so the frame cannot navigate itself to another origin); the frame route never redirects (path matching in `frame-src` is ignored after a redirect).
- **Ticket:** `POST /project-apps/:appId/ticket` (dashboard session) → single-use, 60 s, bound to appId and the served version, held in memory (a restart drops tickets; the wrapper asks again). The frame route refuses without a valid unused ticket, and also when `Sec-Fetch-Dest` is present and not `iframe`. The ticket alone covers browsers that omit the header. Opening the frame URL directly gives a plain error page.
- **Frame response headers:** `Content-Security-Policy: sandbox allow-scripts allow-forms; default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data: blob:; font-src data:; connect-src <origin>/project-apps/<appId>/api/; form-action 'none'; base-uri 'none'; frame-ancestors <origin>`, where `<origin>` is the request's own origin only if it is one of the agent's known addresses (localhost, the tunnel URL, the named tunnel host, the Tailscale name), else 400. `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `ETag` = sha256, `Cache-Control: no-cache`.
- **Auth and CORS:** exact method+path regexes, never prefixes: `GET ^/project-apps/pa_[0-9a-f]{16}/frame$`, `(GET|PUT) ^/project-apps/pa_[0-9a-f]{16}/api/(data|summary)$`, added to the auth middleware's exact-shape list with a lint test. `corsMiddleware` gets a branch, ahead of the generic one, for exactly those api paths: `Origin: null` allowed, methods `GET, PUT, OPTIONS`, headers `X-Project-App-Key, Content-Type`, no credentials. On those paths the narrow key is the only gate.

### 3.7 The narrow per-app key

- Handed to the frame by the wrapper once per frame load via `postMessage(key, '*')` after the frame's `ready` (checking `event.source === iframe.contentWindow`; `'*'` because the frame's origin is opaque, accepted on purpose). The wrapper accepts only `ready`, `summary-changed` and `open-conversation` (no target: always the app's own project conversation).
- Minted by `POST /project-apps/:appId/key` (the wrapper's own console credential; refused while the app is disabled or has no served version): HMAC over `{appId, contentSha, rights: ['data:read','data:write','summary:write'], exp, epoch, nonce}`; `exp` = 15 minutes. **Renewal is bound to the loaded version:** the wrapper renews on its own timer (two minutes before expiry, while the page is visible), never because the frame asked, and only for the content hash the frame was loaded with; if the served version changed, renewal is refused and the wrapper reloads the frame with a fresh ticket for the new version instead of handing the old frame a new key. A failed renewal retries after 30 s, 1, 2, 4 and 8 minutes, then every 15 minutes while the page is visible, and stops when the page is hidden. After two hours of failures it stops for good on that page (breaker) and the bar says "Lost connection to your agent" with **Try again** (one tap restarts the back-off). Meanwhile the frame runs read-only and the bar says "Reconnecting…".
- **Revocation is eventual and bounded:** a machine that has not yet received a `disable` or a new served version keeps honouring a key it can verify until that key expires; every key lives at most 15 minutes, so a revocation reaches every machine within the replication delay plus 15 minutes. Tested with a partitioned machine rejoining.
- The HMAC secret: an app-key-file entry like the app keys (fetched from the lease holder over the mesh; created only when no reachable machine has one); never in config. Disable or a new served version bumps the app's `epoch`, revoking older keys.
- **Request rate:** the four api routes share a per-app token bucket of about 20 requests a second with a burst of 30, checked after the key; past it they answer 429 `too-many-requests` with a plain message. That number is a starting value, to be tuned from real use. The key's checks (the served version, the epoch, the approvals) are folded once per change to the records and memoised, never refolded per request.
- Accepted only in header `X-Project-App-Key`, only on the §3.6 api paths, only when the token's appId equals the path's and its version is still served. Everywhere else it is not a Bearer and gets a plain 401. Added to the log redactor next to bearer tokens.
- **Typed secrets:** there is no reliable detector for a password typed into a fake sign-in box (the outbound credential detector recognises key and token formats only), so none is claimed. The defences are the wrapper bar ("anything you type here goes to your agent") and the version check flagging password fields on the approval card (§3.5); the rest is a stated residual (§4).

### 3.8 Phones

The phone apps draw the custom summary natively (part 1). **Open** mints a console ticket with the phone's device key (the existing `mobileConsoleTicket` flow) and opens the wrapper URL with it in the in-app browser, so the wrapper has a console credential without a PIN. Approvals are Work Board cards the phones already show. No custom code runs in the native apps. Custom apps need the phone's write gate (`permissionActions`) on, as every phone tap does.

## 4. Security table

| Attack (by an agent acting through the API, or the app's own code) | Defence |
|---|---|
| Read the console's session, the browser device key, the dashboard DOM | CSP `sandbox` without same-origin → opaque origin, even top-level |
| Call owner routes | Holds only the narrow key; auth ignores that header → 401; tested against every owner route class |
| Another app's data | Key binds appId and version; path must match |
| Self-navigate to exfiltrate | Wrapper `frame-src` limits the frame to its own path; no redirects; browser test (Chrome, Safari, Firefox) |
| Top navigation / popups / modals | Not granted |
| Direct-open phishing page | `Sec-Fetch-Dest` (the browser marks a top-level open as `document`, refused); the single-use ticket is a second check for browsers that omit the header, though an API-hijacked agent could mint one itself |
| Fake sign-in box (Google, Apple, a password) | The bar says "anything you type here goes to your agent"; the version check flags password fields on the approval card before it runs. Residual: a password typed into an approved app reaches the agent; there is no reliable detector and none is claimed |
| Swap in hostile code after approval | Only an owner-phone Approve on a server-written card whose material matches the server's rendering for that content hash serves it; the agent cannot edit that card; a reject holds until a later owner-phone allow-again |
| Replay an old approval | Approvals bind one card generation's material; a reject holds until a later owner-phone `allow-again` approval; disable needs a fresh phone approval |
| Team member edits app code | Not Documents; only the agent's Bearer writes source |
| Key leak | ≤ 15 min, one app and version, revoked by epoch, redacted |
| Flood stores or the conversation | Per-write caps, a pool-wide daily budget only the phone can raise, one open version card per app (rewritten, not multiplied), one message when it opens |
| Residual: WebRTC/DNS covert channels | Not closable by CSP everywhere; bounded by what the frame holds (its own project data, a short-lived key); flagged on the card when the code uses `RTCPeerConnection` |
| Agent with shell on the host | Out of scope by nature (§2): it can forge approvals and change served code; nothing here protects against it |

## 5. Multi-machine posture

- `project-app-blob` (chunks, revisions): **unified**, its own kind and advert, `rotateKeep: 0` until an owner erase; the lease holder is the one writer (epoch-fenced); every machine serves reads of complete revisions.
- `project-app-record` additions (version answers, summaries): **unified**, part 1's kind (already forward-compatible).
- App keys and the narrow-key HMAC secret: **unified** through the `project-app-key-fetch` mesh verb from the lease holder (fetch before create) and revocation records; held per machine in a 0600 key file, never in the journal, secret sync or backups.
- Tickets: **machine-local-justification: physical-credential-locality** — a single-use, 60-second bearer secret held in one process's memory, deliberately never replicated.
- Approval cards: the Work Board's own replicated cards.
- Backup: both kinds are added to the backup manifest like the other journal kinds.

## 6. Decision points touched

| Decision | Class | Floor / basis |
|---|---|---|
| Frame isolation (CSP sandbox, no same-origin) | invariant; basis: irreversible-consequence; evidence: a same-origin script reads the console's session and the browser device key | not configurable |
| Narrow-key scope | invariant; basis: irreversible-consequence; evidence: owner-only powers must be unreachable from app code | 401 |
| Served version needs an owner-phone Approve on its server-written card | invariant; basis: irreversible-consequence; evidence: every API-reachable proof (Bearer, PIN) is available to a hijacked agent; only the phone's key and presence are not | nothing new runs |
| A reject of a content hash holds until the owner's phone allows it again | invariant; basis: irreversible-consequence; evidence: a replayed approval must never revive a version the owner rejected; only a fresh phone approval reverses it | rejected stays rejected |
