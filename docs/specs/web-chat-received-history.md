# Encrypted browser cache for received conversation history

## Problem statement

The web dashboard retrieves received messages when opening a conversation. A recent page that the signed browser has already loaded can be shown while the normal refresh continues. The dashboard's general weak-network cache intentionally excludes chat text. The pending-send outbox is an independent proposal and must not be a foundation for this change.

## Frontloaded Decisions

Justin approved storing an encrypted copy of received messages in that browser profile until sign-out, including the risk that a person using the already unlocked browser may read cached chats. Decision provenance is Chief handoff 951cb8e5-2008-4b10-b9cd-83fac3bb42e5, carrying Justin's statement at 2026-11-24T08:30:54Z in topic 141385. The feature starts off and has its own flag. Activation requires completed verification, including sign-out clearing the stored copy. This approval covers received message text and the minimum message identifiers and timestamps required to render it. It excludes storing attachment bodies, titles, drafts, queued sends, full transport responses, access credentials, or general activity status. Browser account and device setup stay the same.

## Proposed design

Use a separate IndexedDB database and a dedicated received-history adapter. Start from the visible chat's existing signed, authorized latest-read and rendering paths. Save a bounded snapshot of messages already admitted to that viewer, after a successful eligible owner's read. Never accept a raw network response, unsafely enriched browser broadcast, unverified holder, or historical team view as permission to persist. The signed response must bind the cacheable snapshot to the serving machine, device, owner, conversation and authorization revision. Reuse an existing signed scope if it supplies these facts, or add an explicit, versioned authorization projection. Trace App, Telegram and Slack read paths separately before claiming any of them supported. Pooled and forwarded snapshots need explicit source and access binding before being included.

### First supported read path

Implement App conversations on the verified local serving machine first. Retain the ordinary pooled history load. A separate signed local cache endpoint may consume one reserved optional-read slot per explicit chat open. If a matching encrypted candidate exists it returns only an authorization and content revision proof. If there is no candidate it returns a complete local newest page for the next open, without affecting the pooled renderer or purchasing an automatic second request on mismatch. Never run this request on polling, in hidden views, or when the origin cannot reserve an exclusive optional-read slot across tabs. Keep ordinary navigation available when optional capacity is unavailable. First-slice cold opens with no candidate have only ordinary live text. App event deltas, pooled/proxied rows, Telegram and Slack stay out of cache until separately verified.

Use the local App history signed device gate, current per-chat grant, and live record and stored visibility checks, plus mobileOwnerDeviceAdmission and explicit browser kind. A stable admitted person ID must exist. An owner phone, unbound legacy owner, team device, Bearer, incomplete frame, tombstone, capacity error or ambiguous ownership produces no cache eligibility. Do not infer custody from a local replica or AppConversationService.serves alone. Require a positive current holder record and generation from the authoritative ownership source. Fail dark on startup, restart or holder ambiguity. The route must capture a complete newest snapshot and its monotonic content revision together, then independently check access, live record, device and holder immediately before emission. An issue-time counter is insufficient. Ordinary App browse can omit unreadable framed records while returning success, so the seed needs exact completeness evidence from the underlying index and framed reads. In the preview path prove equivalent visibility without rerunning all history payload work, or there is no measured reason to enable caching.

Cache mutation order uses the captured snapshot revision, plus a persisted per-conversation generation in the same IndexedDB transaction as the ciphertext. Commit accepts only its captured sign-in epoch and scope generation, and a never-older content revision for that scope. Invalidation records a higher scope generation and removes the row atomically. Holder generation changes invalidate the scope, rather than resetting order within the same generation. A newer complete empty result is a replacement, and an older in-flight encryption may not undo it. Reconfirm authorization validity independently just before render, prioritize the current live result over a late decrypt, and expire the preview when its exact authorization proof expires, including on a temporary outage. A first experimental proof deadline of two seconds from request start will be contested against measured ordinary reads before becoming a product limit. Hide on tab backgrounding and revalidate on restoration. For performance compare on/off under identical network shaping for both proof and ordinary history. Preset a measurable preview improvement and maximum extra cost on clean cache misses before activation. Artificially delaying only history remains a race test.

Signed device enrollment, the feature flag, current owner identity and ordinary conversation access are prerequisites for reading the browser cache. At boot or on holder/owner/device change, complete normal access checks before restoring a snapshot. Once verified in the current live access context, a chat can paint its saved page first while an ordinary refresh is in flight. A live success replaces the page, even if empty. Explicit access loss, a disabled capability, confirmed message erasure and a revoked device hide the old page immediately and invalidate the relevant data. A transient network error may leave the preview visible only until the original proof expires in that context. Do not create an offline unlock path or enable privileged actions from cached data. Measure first visible render and full live replacement against an artificially delayed ordinary response. Render saved messages through a separate sanitized, read-only preview using the existing message text rendering. The normal chat list merges even empty live reads and calls read-marking, so never place preview rows into live bubbles, read-state, page cursors, quick-history hashes, message actions, pins, read receipts or optimistic send reconciliation. A successful empty live result removes the entire preview. Preserve any existing draft, attachments and scroll intent. Ignore a decrypt that finishes after the live page, auth loss or a chat switch. Do not add another unlock or pairing prompt. Clearly label saved content only while it is shown.

Encrypt snapshots with Web Crypto AES-GCM and a fresh random IV per write. Use a non-extractable browser-generated key stored as a structured-cloned CryptoKey in the same IndexedDB database. Bind ciphertext to its schema version, epoch and exact opaque record key in authenticated data. No plaintext or sensitive identifiers in row keys, database metadata, logs, service worker cache, localStorage or sessionStorage. Derive record addresses from the scoped identifiers with a per-epoch keyed identifier function. Do not use the general network cache's short bearer hash for identity. Limit snapshot size, total retained bytes, number of snapshots and concurrent serialization. A corrupt, oversized or unavailable cache should produce an ordinary live load. Add no retention period that outlasts sign-out. Enforce a fixed capacity by evicting old pages atomically with the write.

Use the browser database as the authority for the active cache epoch. Every write, clear or fresh epoch operation must order on the same object store transaction scope. Read key and generation before encryption and recheck within the write transaction before committing. A sign-out operation synchronously fences rendering and new work, then atomically removes every key and ciphertext row without depending on deleteDatabase or cooperation from another tab. Mark the old access epoch unusable so a late request, suspended tab or already running encryption cannot recreate it. A new sign-in creates a fresh epoch only after its usual proof and a successful cleanup transaction. IDB transactions plus the current sign-in marker must protect stale tabs across sign-out followed by sign-in to the same account. Storage, visibility, page restoration and logout events also fence in-memory rendering and remove cached content from the visible chat. Reads recheck after decrypt and before paint. Trace dashboard Console sign-out, legacy shared-token removal, signed browser revocation, cross-tab changes and failed startup validation. Sign-out always removes current access, even during a storage failure. Cleanup failure prevents cache recreation/restore and has an explicit retry disposition, with no claim that disk was cleared until the wipe commits and is read back.

### Sign-out entry points and failure handling

Expose a reachable ordinary Sign out action in the Console shell, usable without a network connection. Use the same cache teardown entry point from Console authorization loss or failed boot validation, Files reauthentication before reload, legacy dashboard session loss, and maturation's shared-token removal. A confirmed Forget this browser or erasure uses the appropriate device or chat invalidation, ordered on the same store mutation boundary. Audit additional same-origin writers of instar_token and make ticket replacement and deliberate re-authentication rotate a random marker even if the shared bearer is identical. A sibling event is a way to stop rendering promptly, never the only way to perform the database wipe. Before any enabling release, prove mixed-asset behavior. Old dashboard pages can remove and restore the shared bearer without calling a new marker protocol. Browser-stored bearer equality therefore cannot prove continuity after a cold boot. The first implementation can enable cache operations only in a document with a normal successful new unlock or equivalent signed ticket and fresh browser cache epoch. Cold boot without that proof must clean any existing cache and leave previews disabled for that document, while ordinary chat use continues. The transition may limit cache reuse across reloads. Demonstrate no old asset can silently bypass the wipe while an eligible document remains live; if there is no observable evidence, resolve compatibility structurally before enabling. Test pure legacy/Files sign-out with the Console closed and an old tab paused.

Record a durable cleanup-pending fence before logout navigation or reload. In-flight readers immediately stop rendering and writes require the original sign-in plus the exact persisted epoch and scope. A cleanup attempt from the older sign-in may not act on a newly established epoch. A new cache sign-in may not proceed until the prior wipe is committed and its result read back. Cleanup failures leave the cache disabled and retry on a later normal startup/unlock. If marker and database writes are unavailable, cached access stops. No later cold boot may use the retained bearer or epoch as continuity proof. Resume only after a read-back-confirmed wipe and fresh normal unlock. Close cached rows in visible tabs on auth loss, on pageshow and upon return to visibility; do not claim a sleeping tab has already processed an event. The proof target is logical browser-origin removal of rows and usable keys. It does not claim forensics-proof deletion, purge an unrelated origin, or protect a copied profile against someone able to run its scripts.

Rollback switches the feature off independently. Cleanup remains reachable when the flag is off. No server replay, new disk retention on the server, automatic enablement or registry changes.

## Multi-machine posture

Browser-owned records stay in the browser profile and origin.

Their key and enrolled device proof live in that profile. Existing remote reads continue normally, and may be persisted only under a verified holder and authenticated source binding. A browser receiving the same chat on a different agent origin starts with its own empty cache.

## Decision points touched

| Decision | Classification and basis |
|---|---|
| Save or restore | invariant; authorization, capability, scope and generation are required; missing proof falls back to live loading |
| Choose visible history | invariant; accept a cache page only in the active conversation and auth generation; a live success, including an empty result, supersedes it |
| Clear cache | invariant; sign-out ends access synchronously and a committed scoped database cleanup removes rows and keys; stale completions cannot reopen the epoch |
| Reject cache data | invariant; bad ciphertext, version, binding, size, revoked scope or off capability cannot render or be reused |
| Evict to budget | invariant; fixed, reviewed bounds with deterministic eligible eviction; the cache does not affect server persistence or history |

## Verification before enabling

Unit tests cover version/identity binding, ciphertext tamper, unavailable storage, table quotas, overlapping write and wipe, duplicate tab initialization and corrupt rows. Integration uses installed dashboard read and auth routes and verifies the eligibility projection for a signed owner, team device, revoked device, unscoped Bearer and a moved holder. A real browser runs ordinary unlock, chat navigation, cross-tab refresh and sign-out. Delay a history request and an encryption write independently, including sign-out followed by re-unlock with the same shared bearer. Inspect IndexedDB before and after sign-out, verify absence of keys and ciphertext from the whole cache, attempt stale writes and cached rereads from a still-open sibling tab, then repeat across page reload. Exercise tab suspension, privacy/storage failures, toggling off, concurrent session changes, and live replacement with empty and nonempty pages. Measure the delayed-network improvement and capture phone layout. Report per-origin clearing separately from browser-wide claims. Preserve the full verification coordinator's existing custody.

## Open design questions

Prove an App revision that covers content visibility, grant and holder changes. Measure the separate signed proof and set a bounded lifetime, snapshot count and total stored bytes based on real latest pages. Audit all same-origin sign-out and token replacement writers and exercise old assets on rollback. The approved privacy terms are settled.
