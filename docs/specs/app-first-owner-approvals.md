# Paired app first for owner approval requests

## Problem statement

Justin reported a Work Board policy request that answered undelivered because Telegram existed but he had never opened its private bot chat. AccountPathService already has accepted-device approval, yet chooses chat whenever a configured adapter exists. Pending trust requests are also absent from Needs-you. This slice fixes publication and discovery using the existing native approval consumer; the wider owner-decision transport audit is recorded separately and continues until every actual blocker is repaired.

## Proposed design

1. Read accepted-device eligibility fresh before choosing a delivery carrier: feature enabled, current acceptance for owner principal, active owner registry device, matching device and presence keys. A paired device alone is not consent to approve. The operator directive was relayed by Chief of Staff message 2d1d97d6-7ec4-43e2-87d8-6628be7ad19b: Justin said, "NOTHING should be dependent on telegram if the agent has a native instar app paried" (topic 141385, 2026-11-22 15:57 PST). For principal owner only, DeviceDirectory exposes an optional fresh active owner-device listing; an active native owner device with a valid pairing-key fingerprint (presence-key enrollment can occur during the existing acceptance ceremony) can receive a pending setup request without acceptance, but still cannot consume it until the existing acceptance ceremony succeeds. An accepted device wins over any configured chat, including one with accepted chat consent. With paired owner devices but no acceptance, record and list the device request with status awaiting-acceptance, via device; never demand Telegram setup. Legacy DeviceDirectory implementations without list use the accepted-device path only. Listing is a synchronous local registry read, not a network lookup. A thrown directory/list/get lookup is unknown, not an empty list: return a retryable not-recorded result with an availability-check explanation, preserve any existing request and expiry, and do not fall back to chat. Test a throwing directory with accepted chat. No new timing boundary is introduced. Existing exact request hashes, single-use challenges and consumption compare-and-set remain unchanged.
2. Record a device request durably before notifying. A push is only a contentless notification; the durable app listing is delivery. Push failure never removes a listed request or claims that a push arrived. No Telegram call is needed for this path. Return status sent when an accepted owner device exists, otherwise awaiting-acceptance with explicit app setup instructions; both use via device, requestId and expiry (the HTTP layer still hides approval code).
3. A repeated proposal with an existing open unexpired chat request without confirmed delivery evidence migrates that SAME request to the device carrier when an eligible paired owner device becomes available (accepted or awaiting the existing app setup ceremony). Preserve requestId, exact change, proposal hash and expiry. Do not withdraw/recreate it, reset its lifetime, or mint extra approval authority. Write a separate request-carrier record (adapter device, requestId, principal, proposalHash, original expiry) with deterministic immutable key; never fabricate a replacement base request. Retain carrier records by requestId even when the original request has not arrived. No row is published from a carrier record alone. When the original arrives, validate the marker against its requestId, principal, proposalHash and expiry; only then expose effective device carrier. Confirmed delivered-chat evidence wins for historical receipt verification; otherwise a matching device marker wins over unconfirmed chat. Add marker-before-base and base-before-marker replay tests, invalid marker tests and late confirmed chat delivery evidence. Serialize propose operations on the serving service, including fresh proposals, dedupe and migration, so fresh-request capacity checking and awaiting the durable write share one critical section. Release that section once durable preparation finishes, before any external chat send. Immediately before invoking the adapter, recheck the serving lease; if lost, suppress the former holder’s send and return not-holder while leaving the pending request visible for the new holder. Test a lease transfer at the write/send boundary: only the invocation that durably created a chat request owns its send task; duplicates return the pending state and do not send again. A stalled chat adapter must not block a subsequent app proposal. Re-read request state inside it. Carrier repair of an existing request does not pass fresh-request admission again: it exposes the same request already visible to the device consumer, without creating a request or extending authority. Existing limits still apply to fresh requests; migrations can increase delivered classification above that fresh limit and no fresh request is then admitted until the existing requests are answered or expire.
4. Existing delivered chat requests remain valid. The device consumer already accepts any open request for its principal. A device notice can point to that existing request without invalidating the chat receipt; the first consumption still wins. Duplicate no-op proposals do not send repeated notices. When a paired device is still unaccepted, repeated proposals retain awaiting-acceptance and app setup guidance; when accepted they return sent without recreating the request. Chat-only users keep the existing chat path for new requests, including an already accepted chat. An existing device-only request whose devices are all removed stays open with its original identity and expiry; it is not silently treated as delivered to chat even if a chat exists. Re-proposal returns no-approver with that requestId and recovery guidance using the same acceptance-chain rules: an existing accepted device must still match its key; after all acceptances are gone, use a new local first pairing (iPhone introduced by the local app, or locally bound Touch ID Mac). Reconnecting the former remote iPhone alone cannot recreate acceptance. Conditional local key-replacement remains available on a locally bound Touch ID Mac. Test sole-device revocation then remote-only reconnection. The dashboard shows no reachable device, not a nonexistent chat card. This intentionally preserves device-directed intent; it creates no new chat receipt or authority. Test the transition after revoking the sole device, both with and without accepted chat. For a paired unaccepted device plus accepted chat, the spec’s chosen app-first product policy wins (the operator directive motivates removing Telegram dependency; setup-first precedence over an already accepted chat is our explicit implementation choice) and the response truthfully says app setup is required. This trades immediate chat completion for the requested device-first experience, without conferring new approval authority. Pending undelivered requests stay visible even with no accepted device or failed chat delivery; opening Needs-you leads to a listing with the setup action/instructions, and the already shipped app Changes to approve view exposes Turn on before Approve.
5. For every chat send, write the pending request durably before calling the adapter, including already-accepted chats. Move all notifications after the corresponding durable request write; never push an unlisted request. Failed writes return not-recorded, no notification. No feature flag/default/acceptance rule is loosened. Chat send accepted but delivery-evidence write interrupted leaves the same pending request with unconfirmed delivery; no automatic resend is implied. Chat-only recovery reuses the existing authenticated owner acceptance-statement replay: AccountPathService.process sends pending unconfirmed cards when the owner repeats the unchanged acceptance statement, even if acceptance already exists (current service process acceptance branch). The UI gives those exact recovery instructions without exposing approval codes to the agent; tests restart after write/before send, replay a fresh owner statement receipt on the holder, and complete the same request from the resulting chat card. A re-propose alone cannot replay an uncertain send. Replying to an unconfirmed original chat card remains refused because its platform message id was never recorded; valid chat consent alone cannot prove that missing card receipt. If a late confirmed card record supplies the exact reply binding, the chat and app paths again compete for the same original consumption. Test both outcomes; never trust an agent-supplied platform message id. The send call can report known failure immediately, but the durable listing says unconfirmed whenever it lacks a delivered-card record, never asserts a known failure from missing evidence. An interruption test proves the request stays visible and approvable from an eligible app.
6. Publish trust requests in NEED_SOURCES via GET /trust/requests, with a stable per-request key, exact summary rendered as text, undelivered explanation, expiry filtering and link to the approval page. A failed read is unknown, never empty. Pending chat without confirmed evidence is labeled delivery unconfirmed, never definitely failed. App setup guidance preserves that uncertainty even after migration. Bearer listing carries no approval codes, keys or secrets. Add a delivery field to the device request listing so the native app can explain a pending undelivered chat request. Existing clients ignore added fields.
7. Publish current transport/setup availability in the bearer and native listings without exposing any key, so the dashboard chooses the next action from current eligibility independently of retained chat delivery evidence. Dashboard approval page lists requests and chooses continuation from current eligible app devices first, then the recorded chat carrier: paired Instar app for device requests, the private approval chat for delivered chat requests, or explicit app/chat setup and failed-delivery explanation for undelivered requests. It never approves with bearer/PIN. A qualifying iPhone with firstPairing/localInstall can use Turn on; local pairing on a computer is not proof that Touch ID exists. A Mac without Touch ID (including a Studio) cannot create an approval key: keep the request visible and direct the owner to the paired iPhone or a Mac with Touch ID. Never infer hardware capability from a pairing fingerprint. A locally paired computer without a presence key receives only conditional setup guidance, not a promise that Turn on works. A locally bound Mac with Touch ID can use the existing local key-replacement override even if another acceptance is current; guidance names this alternative instead of demanding another device. Test invalidated local key plus another current acceptance; another paired device needs an already accepted device to allow it, or a new local app first pairing when no acceptance exists. The listings name this setup state and exact next step; a remote-only iPhone without a valid acceptance chain is not promised that Turn on alone will work. Test this combination even with accepted chat: app-first remains explicit, pending and never silently grants consent. The iPhone/Mac Changes to approve view already lists requests and has the exact presence ceremony. Existing native Needs href handling opens ConsoleView, not that native view: the console page must name the actual navigation path (iPhone: the agent’s Permissions screen, Changes to approve; Mac: the agent window’s Changes to approve card; exact labels must be verified against each client), and must not claim a direct native jump. A coordinated app route can improve this later, but this slice needs a working explanation now. Coordinate app navigation for a Needs-you trust row with the Apple app owner; server delivery must not require a new app binary.

## Frontloaded Decisions

- A device acceptance, not mere pairing, is required for approval; setup remains the existing app ceremony. Pairing permits receiving requests and setup instructions only.
- Re-propose migrates an undelivered request without changing identity. It is not withdrawal and creates no extra approval.
- No chat fallback is attempted when the request is durably listed for an accepted device. Push availability is not approval availability.
- Fleet opt-out of trust approvals remains respected. No raw credential or approval code is exposed to the agent.
- A request on a non-holder remains governed by existing holder checks; no remote presence proof is forwarded or trusted.

## Multi-machine posture

Unified request/acceptance state uses the existing trustJourney journal and trust-grant-record replication. Only the serving-lease holder decides proposals and consumes proofs. Add an explicit service propose guard (including dedupe migration) returning not-holder with no writes or notifications when the lease is absent. Recheck before publication side effects inside the serialized operation; existing journal admission remains the durable writer floor. Every machine lists its replica honestly; a non-holder labels current device/setup availability unknown (not-holder) and tells the app to refresh against the deciding machine, never derives live eligibility from a stale replica. Test a holder withdrawal not yet present on the replica; writes and eligibility remain on the holder. Device private/presence keys remain on the paired hardware and are never replicated by this change. Push remains the existing pairing push path, contentless and deduped per request. No new URL contains credentials.

## Migration and rollback

Add the request-carrier metadata record to the existing trust record enum/schema. Old readers safely ignore it and still show the base open request; no grant or proof kind changes and no unknown action can apply. No config or installed-file migration. Carrier records carry no approval secret. The old no-chat/no-acceptance expectation is deliberately split: no paired device still yields no-approver; a qualifying paired device yields awaiting-acceptance and may approve the same request only after setup. New routing is runtime behavior; re-proposing an old open request performs its explicit idempotent carrier migration. Older clients ignore additive delivery metadata. Revert restores chat preference but does not erase requests or approvals. Existing device requests remain readable and approvable by the existing consumer.

## Verification

Unit: accepted owner device plus dead/unaccepted Telegram chooses device and never calls chat; accepted chat plus device also chooses device; revoked/rekeyed/wrong-principal/disabled devices cannot route; pending chat migration before and after device acceptance preserves id/hash/expiry; both replay orders retain carrier; concurrent distinct fresh proposals obey inherited creation caps; existing migrations do not strand requests at the fresh cap; non-holder emits nothing; accepted device works with legacy directory lacking list(); duplicate migration, failed durable write, request limits and push failure; chat-only unchanged. Device approval and chat/device race tests remain.
Integration: POST /trust/requests with both transports returns device carrier without Telegram acceptance; GET lists pending undelivered request and no approval code; Needs-you includes it, excludes ended/expired requests and reports unreadable source. Unaccepted and revoked devices cannot approve. A delivered chat request later reachable by an accepted device points to the app while retaining its original identity and chat receipt. A paired remote-only iPhone without first acceptance gets accurate setup guidance. A sole locally paired Mac without Touch ID gets phone guidance; standby current availability is unknown; a device-only request after sole-device removal keeps its id/expiry and shows recovery rather than a false chat action. A successful chat send followed by a delivery-record write failure remains visibly unconfirmed, not absent.
E2E: production AgentServer/trust-device binding with no working Telegram produces a durably app-listed request, sees it in Needs-you, consumes one exact signed presence approval, and applies only once. Full suites go exclusively through echo-increasing-throughput.
Live Studio: confirm an actual device acceptance and private route; after verified deployment re-propose the existing board-policy request unchanged, confirm via device and Needs-you visibility if it is still open and unexpired, then send requestId to Chief of Staff. Never approve it for Justin.
