# Relay Scope Detail

The channel registry is meant to answer a practical question: which peer communication paths are usable, and what exactly was measured to reach that verdict. The `threadline-relay` row already had a real runtime reading, but its wording did not name the subject of that reading. It said the relay reported ready and connected. That was true for the server process, because `/channels` asks the server's `threadlineRelayClient` for its state. It was not necessarily true for every other process that can send by relay.

That missing subject matters because Instar has more than one relay client path. The MCP tool path runs in a different process and owns a different relay client. During the incident that drove this fix, `/channels` reported `threadline-relay: working` while `threadline_discover` reported that its own relay was not connected and was serving cached discovery. Both surfaces were honest. The defect was that the registry row let a reader combine them into one false conclusion: "the relay is working, therefore my MCP send can reach this peer." A true statement became dangerous because it did not say whose truth it was.

The row now keeps the same `working` state when the server process relay client is ready and connected. That state is correct for what the probe measures. The detail now says the server process relay client reports ready and connected, and it explicitly notes that this confirms the server client, not another process client such as the MCP tool path, and not that any given send will land. The broken branch is scoped the same way: it reports the server process relay client values and says a server-process send would be refused, while another process client has its own state.

This is not a transport behavior change and not a downgrade. It is a precision fix to the registry's claim. The goal is that a future operator or agent can read `/channels` without accidentally treating server-process relay health as a promise about a separate sender process.
