# Pairing invite: say who may approve, and no "Delivered" when it was turned away — plain-English overview

**What went wrong.** You can pair two agents by forwarding a pairing invite into the receiving agent's Telegram chat. A user did this and the receiving agent answered that it could not approve the invite because it "hasn't been told who its owner is". Right after that, the agent's Telegram listener posted its usual "✓ Delivered" tick. Two things were confusing. First, "owner" sounded like it might mean the owner the *other* agent claims, when it really means the human who is allowed to approve new connections for the *receiving* agent. Second, "✓ Delivered" made it look like the invite had gone through, when it had been turned away.

**What changes.** Two small things, nothing else:

1. **Clearer words.** When the receiving agent cannot work out who may approve for it, it now says: "I can't tell who is allowed to approve new connections for me, so I can't approve this here." When someone other than that person forwards the invite (or taps a pairing button), it says: "Only the person who approves new connections for me can do this." Neither line names anyone or shows an id, and the first one no longer claims the setting is missing, because it can also be ambiguous (for example two different people have used the agent) or set to something unusable. Both still point to the dashboard's Threadline tab, where the invite can be pasted and approved with the PIN.
2. **No false "Delivered".** When the server turns a forwarded invite away (the approver check refused it, the invite was unusable, pairing by invite is off on this agent, or sending the reply failed), it now marks its answer to the listener as `refused`. The listener already knew how to read that mark and already skips "✓ Delivered" for refused messages; it simply never received the mark for invites before. A valid invite that is now waiting for the approver's Approve or Decline tap is *not* marked refused, so it is still acknowledged. Waiting is not the same as connected: nothing is paired until the approver taps Approve.

   One case needs care: the invite was valid and the pairing engine accepted it, but sending the Approve/Decline prompt to Telegram failed. The answer is still marked `refused`, but only so no "✓ Delivered" appears for a prompt that never showed up. It does **not** mean the pairing was declined, and nothing is undone: the engine's waiting entry (and the invite's topic note and button tokens) can stay until the invite expires. The invite still counts as handled and is never re-sent or replayed automatically.

**What does not change.** Who is allowed to approve is decided exactly as before; that logic was not touched. No owner is assigned automatically, no one is promoted to approver because they spoke first, and no trust or permission is granted. The invite secret is still swallowed by the server right away and never reaches a session, the message history or any log. Turned-away invites still count as handled, so the listener never queues or replays them later.

**What is still missing.** A proper one-time way to set who approves for an agent, and a way to resume an invite once that is set, are larger pieces of work still tracked separately (feedback fb-9566b1d3-f4d, topic 9210). This change does not do them.

**When you see it.** The new wording appears once the updated server is running. Skipping the tick also needs the Telegram listener (the lifeline) to be a version that reads the `refused` mark; that reader first shipped in v1.3.1731. A normal patch update restarts the server but does not necessarily restart a listener that is already running, so an older running listener keeps showing the old tick until it is restarted in the usual controlled way.

**Safeguards and rollback.** The change only removes a misleading tick and rewords two lines. Reverting the commit brings back the old wording and the old tick; there are no settings or stored data to repair.
