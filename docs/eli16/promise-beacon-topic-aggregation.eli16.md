# ELI16 — One promise-beacon summary per conversation cadence

The PromiseBeacon keeps an agent’s promises from disappearing during long work. Before this change, it treated every open promise as a separate notification source. If eleven promises were open in one Telegram topic and all eleven had real new output, the beacon sent eleven individually truthful messages in the same minute. The “don’t send unchanged filler” setting could not help, because none of those messages was filler. The backlog itself multiplied the message rate.

The beacon now puts one durable envelope around all qualifying notices for a conversation. The first notice starts the conversation’s notification cadence. Anything else that qualifies before that cadence ends is saved on disk and included in the next summary. A summary always carries the number of open promises and their short names, plus a separate list of the promises that actually had news. Twelve open promises therefore produce at most one user-facing message in a cadence window, not twelve.

The mixed case is deliberate. Suppose one promise has new terminal output and four have no new output. The summary says there are five open promises, lists all five, and gives a progress line only to the one with news. It does not repeat five “still working” claims and does not imply that quiet promises progressed. The topic rhythm uses the shortest effective cadence among its open promises. That preserves the timing of the most urgent promise, including at-risk adjustments and deadline pressure, while preventing slower promises from multiplying the number of messages.

Qualifying notices are not silently discarded. The pending count-and-list batch is written atomically under the beacon’s state directory before the method reports that it was queued. If the process restarts, startup scans those topic batches and re-arms their flush timers. Repeated qualifications for the same promise and notice kind are folded to the latest truthful wording while retaining an occurrence count. Ownership is checked again before a fresh batch is composed, so a promise that became agent-owned while waiting cannot suppress a user-owned sibling or leak its status through that sibling. An ambiguous failed delivery is different because it may already have reached the user: the beacon freezes its attempted summary and original send identity byte-for-byte and retries it no sooner than the same topic cadence; newer news waits behind that frozen prefix for the following summary instead of changing the meaning of the retry. Permanent delivery refusal, machine stand-down, agent-owned suppression, and Attention rerouting remain explicit typed outcomes rather than hidden loss, and retire only the items they actually attempted.

The same bound also covers lifecycle notices. A session-loss violation, escalation status, auto-pause, or turn-finished close-out that lands immediately after another beacon message waits for the next topic boundary; it is not allowed to punch a second hole in the cadence. Terminal state still changes immediately, so the message delay never delays authority or lets work continue incorrectly. A focused test proves the terminal notice remains durable and appears at the next boundary.

This is a Tier 1 change because it alters one monitor’s internal composition and scheduling, not an HTTP contract or server initialization path. Unit tests drive the real CommitmentTracker, durable files, delivery callback, restart recovery, exact cadence boundary, multiple topics, mixed-news case, and session-loss close-out. The runtime wiring receives one additive setting: `promiseBeacon.aggregateByTopic`, default `true`. Setting it to `false` restores the former per-promise delivery path without migrating or rewriting commitments.
