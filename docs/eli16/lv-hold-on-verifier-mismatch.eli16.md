# A verifier changed on disk holds the queue for the restart — plain-English overview

**What went wrong.** The local verifier is the thing that runs the test suite on each of our own pull requests before it may merge. It keeps a queue of pull requests waiting their turn. When the auto-updater installs a new instar version, it replaces the program files on disk first and restarts the server about a minute later. During that minute the OLD server is still running and still starting verify runs — but each run is a fresh child process, which loads the NEW files. The child notices that its code no longer matches the server's and refuses to run (that refusal is deliberate: a result must never be stamped with the wrong verifier version). The server, however, treated the refusal as if the pull request's run had crashed: it wrote an "error" result for the pull request, retried once, got the same refusal, wrote another error and moved on to the next pull request. Every pull request in the queue was burned this way within about one second (nine pull requests at 00:12:52Z and four at 10:36:40Z on 2026-10-24, then ten at 02:59:55Z the following UTC day — the evening of the 24th Pacific; each burst also posted a red "verify" status to GitHub for every one of them). Writing an error result also removes a pull request from the saved queue, so after the restart the queue came back empty. Each one had to be requested again by hand, on every release that touches the verifier.

**What changes.** A refusal of this kind is now recognised for what it is — "the installed verifier changed under us; the restart is coming" — and is no longer treated as the pull request's failure. The pull request goes straight back to the front of the queue with its attempt not counted and no result written. The server then enters a hold, like the existing pause it already uses while an update is pending, and starts nothing more until it is restarted. One line is written to the audit log when the hold begins. The next boot computes its version from the new files, finds the whole queue intact on disk, and resumes it in the same order. Nobody has to re-request anything.

**One check before spawning.** Before each run, the server now also compares the files on disk against its own version. When they already differ, it enters the same hold without spawning a child that would only refuse. If the server cannot read that answer (no answer, a file mid-replacement) it does nothing special — the child's own check still decides, exactly as before.

**Safeguards.** The hold is in memory only, so a restart always clears it. If the files later compute the server's version again (a flip that undid itself), the hold lifts by itself on the next tick. If a hold outlives the restart it waits for (fifteen minutes, where a restart takes about one), one attention signal is raised naming it — once, then quiet. The hold never writes or deletes a result, never changes who may merge, and every other crash is handled exactly as before: an error result and one automatic re-run.

**Rollback.** Revert the commit. There is no persistent state and no migration; reverting restores the old behaviour, which is the one that empties the queue.

**What you need to decide.** Nothing. Pull requests waiting for a local verify now survive a release instead of having to be requested again.
